== Purpose
_Requirements: link:{docs}/Requirements.adoc#PM-IMPL-5[PM-IMPL-5], link:{docs}/Requirements.adoc#PM-WF-1[PM-WF-1], link:{docs}/Requirements.adoc#PM-WF-2[PM-WF-2], link:{docs}/Requirements.adoc#PM-WF-16[PM-WF-16], link:{docs}/Requirements.adoc#PM-ARCH-4[PM-ARCH-4]_

Package `de.planmarshall.workflow.engine` is the deterministic interpreter of the workflow state machine. It runs one
verified unit of the Workflow DSL together with every sub-workflow the unit calls, chains the states that need no
outside event in one advance, and stops where the scope rests, ends, or carries a condition. Everything a run knows
lives in the workflow state store `mcp/status.json`: the engine reads the status, returns the next one, and keeps
nothing in memory between two advances, so a killed run resumes at the same state with the same call stack. Beside
the interpreter, the package resolves the entity a call addresses within its scope (<<_entity_addressing>>) and
decides how long the server holds open the two calls a model waits on, `pm_wait` and a running `pm_build`
(<<_waits_held_by_a_model>>).

The store and the ports the engine depends on belong to `pm-core` and are described in
link:../../../pm-core/doc/developer/core-store.adoc[Workflow State Store and Engine Ports]. The AST the engine reads
and the verifier it relies on are described in link:workflow-verify.adoc[Workflow Verification].

== Main Types
_Requirements: link:{docs}/Requirements.adoc#PM-IMPL-5[PM-IMPL-5], link:{docs}/Requirements.adoc#PM-WF-16[PM-WF-16]_

[horizontal]
`WorkflowEngine`:: The interpreter of one top-level unit. The constructor takes the unit, the `WorkflowCatalog` of
callable sub-workflows, the `WorkflowValidator`, the `PrimitiveRegistry`, a `ParameterBinder` that binds the
parameter record of a primitive from the status, and the `Ports` record (`JobStarter`, `QueueTaskCreator`,
`QuestionRecordReader`, `WorkflowClock`). Its operations are `start`, `advance` (with and without an event, each also
in a form that writes the new status into a `ScopeTransaction`), `restingWait`, `stepOut`, `raise` and
`unwindToFallback`.
`EngineStep`:: The sealed result of one operation: `Resting` (the resting state and the `AwaitedEvent` it waits for),
`Ended` (the outcome and outcome class of the top-level unit's terminal; the call stack is empty), and
`ConditionRaised` (the condition kind and its facts; state, phase and call stack unchanged). Every variant carries the
new `WorkflowStatus`.
`CallStack`:: The immutable call stack, bottom to top, of at most `MAX_DEPTH` (4) frames, the depth the store admits.
`push` adds the frame of a call, `pop` removes exactly one frame, `unwound` lists every frame top to bottom for an
unwind; `fromStore` and `toStore` convert between the AST frame `ast.CallFrame` and the store frame
`WorkflowStatus.CallFrame`.
`GuardEvaluator`:: The three-valued evaluation of guard expressions (`Held`, `NotHeld`, `CouldNotEvaluate` of
`ast.GuardResult`), the raise of the condition `guard_indeterminate` for the first guarded link whose guard could not be
evaluated (`raiseUndecided`), and the two-valued decision of a result guard over a frame's result record (`holds`).
`LoopBackBudget`:: The accounting of loop-backs and remediation budgets of a plan: `outlineLoopBack`,
`policyLoopBack` and `policyRetry` return `Charge.Granted` with the count raised, or `Charge.Exhausted` with the
outcome `exhausted` and the status unchanged.
`EngineEvent`:: The sealed event that resumes a resting state: `JobSettled(jobId, fate)`,
`TasksSettled(taskOutcomes, evaluatedOutcome)`, `QuestionResolved(questionId, outcome)` and `TimeElapsed(at)`.
`RestingWait`:: What a resting state waits for, derived from the status alone: the `AwaitedEvent` kind, the jobs bound
to the state (`active_job`, `active_jobs`) and the entities of its queue tasks (`active_tasks`). `accepts(event)`
decides whether an event is the one the state waits for.
`ModelWait`:: The wait the server holds open for a model, a bounded long-poll or a progress-reset wait. `Bounded`
answers at its window and emits no frame; `Progress` emits a frame at every interval after the start and answers at its
window. `answerAt`, `answersAt` and `progressFrames` are pure over the start and the window.
`WaitSelection`:: The one rule that selects a wait: `select(connection, progressToken, call, settings, clock)`.
`ConnectionSettings`:: The three `connection` values of a client profile a wait needs, with the profile-validation
bounds. `WaitSettings`:: The machine-wide progress upper bound and interval.
`ModelCall`:: The closed set of calls a model holds open: `PM_WAIT` and `PM_BUILD`.

[source]
----
                    advance(status[, event])
caller ───────────────────────────────────────► WorkflowEngine ──► EngineStep (Resting | Ended | ConditionRaised)
  │                                                │   │   │              │
  │                                  CallStack ◄───┘   │   └──► ports: JobStarter, QueueTaskCreator,
  │                         GuardEvaluator.holds ◄─────┘            QuestionRecordReader, WorkflowClock
  │                                                                       │
  └── WorkflowStatusStore.write(transaction, step.status()) ◄─────────────┘
----

== Interpreter
_Requirements: link:{docs}/Requirements.adoc#PM-IMPL-5[PM-IMPL-5], link:{docs}/Requirements.adoc#PM-WF-1[PM-WF-1], link:{docs}/Requirements.adoc#PM-WF-6[PM-WF-6]_

=== Only Verified Units Run

The constructor runs the `WorkflowValidator` over the unit and, through every `call` state, over every sub-workflow it
calls, directly or through another sub-workflow. A unit with a violation, a sub-workflow with a violation, or a called
sub-workflow the catalog does not hold is refused with `WorkflowEngine.UnverifiedUnitException` (an
`IllegalArgumentException` naming the unit and carrying the `VerificationResult`). No engine exists for such a unit
(link:../adr/workflow-engine/001-engine-runs-verified-units-only.adoc[ADR 001]).

=== One Advance

`start(scopeType, scopeId)` builds the first status of a scope at the unit's start state. Only a unit without entries
has one: a unit with entries is called, never started, and its start is refused with `IllegalArgumentException`. A
start state that declares `phase inherit` is admitted for the workspace scope only, whose phase is then `workspace`;
every other DSL phase is mapped to the value of the status store (`execute` to `phase-5-execute`, `epic` to `epic`,
and so on).

`advance(status)` continues from the current state. From there the engine chains, state after state, in one advance:

* entering a state makes it current: its phase applies (`phase inherit` keeps the phase the scope has), and the job
  and task bindings of the state left are cleared;
* an `auto` state binds the parameters of its primitive through the `ParameterBinder`, runs it, and takes the
  transition of the returned outcome;
* a `call` state pushes a frame and enters the sub-workflow at the state its entry binds (see
  <<_call_stack_and_exit_contracts>>);
* a terminal state of a sub-workflow pops one frame and takes the calling state's transition of the returned outcome;
* a terminal state of the top-level unit ends the run with `Ended`;
* a link, job, composite job, task or question state rests with `Resting`, parked as described in
  <<_wait_events_and_resumption>>.

An advance of a scope that carries a condition returns `ConditionRaised` with the status unchanged. An advance of a
scope that already rests (a link or question state, or a job, composite job or task state whose binding is in the
store) returns `Resting` with the status unchanged; it never starts the bound job again.

The engine returns the new status with `updated_at` from the `WorkflowClock`. The forms
`advance(status, store, transaction)` and `advance(status, event, store, transaction)` add it as one replace target to
the caller's `ScopeTransaction`, so the state change and the other writes of the transaction are one journaled write;
a status the advance did not change is not written again.

=== Selecting a Transition

Of the transitions of a state that route the returned outcome, the engine takes the one without a result guard or
whose result guard holds. Exactly one must match; none or two is the internal fault `undeclared_outcome`, never a
fallback. A verified unit routes every outcome of every primitive it names (Rule 2) and partitions the routes of one
outcome by result guards (Rule 6), so the fault is reachable only through a defect.

=== Invariants

* *Only verified units*: every unit the engine can enter passed the verifier when the engine was built.
* *One transaction per advance*: an advance computes one new status from one old one; the caller writes it in one
  `ScopeTransaction`. The calls, returns and `auto` states an advance chains are not persisted one by one.
* *One frame per return*: a terminal of a sub-workflow and a step-out pop exactly one frame; only the fallback of a
  spent condition budget unwinds every frame.
* *No state outside the store*: the engine holds no field that changes between advances. The current state, phase,
  call stack, bindings, counters and condition are read from the status passed in; `RestingWait` is derived from it.
* *Retry counts*: the engine counts no retry. It drops the `retry_counters` entries of every state of a sub-workflow
  when it pops or unwinds that sub-workflow's frame, in the same status write, and changes them nowhere else: entering
  and leaving states within a frame keeps them (link:../../../pm-core/doc/adr/core-store/005-retry-count-clearing-rule.adoc[ADR core-store 005]).

=== Failure Modes

[cols="2,3"]
|===
|Failure |Behaviour

|The unit or a called sub-workflow violates a verifier rule, or a called sub-workflow is not in the catalog
|The constructor throws `UnverifiedUnitException`; no engine is built.

|A primitive returns an outcome outside its declared outcome type, or a state has no or two matching transitions for
an outcome; this includes the `refused` outcome of a job start the `JobStarter` declined, in a job state that has no
`refused` transition
|`InternalFaultException` with the reason `undeclared_outcome`. The Workflow DSL specification gives every `job`
primitive the closed job outcome set, `refused` included, and the verifier requires a route for every outcome the
primitive declares; a primitive that declares fewer outcomes leaves the refusal without a route.

|The status names a state, sub-workflow, phase or primitive the verified units do not hold, a frame's calling
state is no `call` state, or a call names an entry its callee does not bind, or names none of a callee that does not
bind exactly one
|`InternalFaultException` with the reason `unresolved_name`.

|`start` is called on a unit without a start state, a unit with entries
|`IllegalArgumentException` naming the unit; no status is built.

|One advance chains more than `MAX_CHAIN` (1000) transitions
|`InternalFaultException` with the reason `unbounded_chain`.

|A guard could not be evaluated
|`GuardEvaluator.raiseUndecided` raises the condition `guard_indeterminate` naming the guard, the link and the
reason; the guard is never folded into held or not held.

|A question record of a resolution cannot be read
|The condition `precondition_unmet` is raised with the `question_id` and the reason; state and call stack stay.

|An event is not the one the resting state waits for, or the question record is still open or resolved with another
outcome
|`IllegalArgumentException`; the status stays as it is.

|A call would exceed the depth 4
|`CallStack.push` throws `IllegalStateException`.

|The `ParameterBinder` binds a record of another type than the primitive takes
|`IllegalStateException`.
|===

The internal fault reasons `undeclared_outcome`, `unresolved_name` and `unbounded_chain` are the engine's members of
`InternalFaultException.Reason` in `pm-core`.

[#_call_stack_and_exit_contracts]
== Call Stack and Exit Contracts
_Requirements: link:{docs}/Requirements.adoc#PM-WF-16[PM-WF-16], link:{docs}/Requirements.adoc#PM-WF-1[PM-WF-1]_

Implements link:{dsl}/06-reusable-sub-workflows.adoc#_call_stack_execution_persistence_semantics[Workflow DSL § Call-Stack Execution & Persistence Semantics]
items 1 to 4 and link:{dsl}/01-grammar.adoc#sub-workflow-exits[Workflow DSL § Result Guards & Sub-Workflow Exit Contract].

* *Call*: a `call` state pushes the frame `(callerWorkflowId, callerStateId, callerPhase, subWorkflowId, entry,
  boundArgs, pushedAt)`, the bound arguments of the call site and `pushed_at` from the clock, and enters the
  sub-workflow at the state its entry binds (<<_entering_a_callee_through_its_entry>>). A sub-workflow state that
  declares `phase inherit` keeps the caller's phase.
* *Resting inside a sub-workflow*: the status is written with the active call stack and the sub-workflow's state; the
  engine resolves the current state against the unit of the top frame, so the wait survives a restart.
* *Return*: a terminal of the sub-workflow pops exactly one frame, restores the caller's phase, drops the retry counts
  of every state of the left sub-workflow, and takes the calling state's transition of the terminal's outcome. Of an
  outcome routed twice, the transition whose result guard holds over the frame's result record wins; the result record
  is the facts the sub-workflow's primitives returned (`PrimitiveResult.updatedFacts`) in the same advance.
* *Step-out*: `stepOut(status)` is the implicit `step_out` of a resting link state of an operator wait in a sub-workflow.
  It pops exactly one frame and the calling state routes the outcome `stepped_out` once; a caller that is itself a
  sub-workflow routes it to a state of its own. A terminal of class `stepped_out` returns the same way. A scope in no
  sub-workflow, a scope with a condition, or a state that is no link state is refused with `IllegalStateException`.
* *Spent condition budget*: `unwindToFallback(status, fallbackStateId)` clears the condition, unwinds every frame,
  drops the retry counts of every unwound sub-workflow, and enters the fallback state of the top-level unit, all in one
  advance. No caller's `stepped_out` transition is taken, so no unit's own recovery state catches it.

The push, the chained states, the pop and the caller's routing are one advance and therefore one write
(link:../adr/workflow-engine/003-call-stack-in-one-transaction.adoc[ADR 003]).

[#_entering_a_callee_through_its_entry]
=== Entering a Callee Through Its Entry
_Requirements: link:{docs}/Requirements.adoc#PM-WF-16[PM-WF-16]_

A called unit has no start state: its frontmatter declares its entries, and its header binds each to a state
(link:workflow-ast.adoc[Workflow AST], link:workflow-verify.adoc#interface-rules[Workflow Verification § Interface
Rules]). The engine resolves the entry of a call when it pushes the frame:

* the entry the call names (`call <unit> entry <name>`), or
* the callee's sole entry, when the call names none.

It records that entry in the frame's `entry`, and enters the state the callee's entry binding names
(`WorkflowDefinition.entryBindings()`). The frame and its entry are written with the status in the transaction of the
call, like every other part of the frame (link:../adr/workflow-engine/011-call-enters-the-callee-through-its-entry.adoc[ADR 011]).
`CallStack.toStore` and `fromStore` copy the entry to and from the store frame `WorkflowStatus.CallFrame`, whose codec
writes and reads the member `entry` of every `call_stack` frame
(link:../../../pm-core/doc/developer/core-store.adoc#_the_call_stack[Scope Stores § The Call Stack]); a scope resumed
from the store keeps the entry of every frame. The return into the caller does not read the entry: it pops the frame
and routes the outcome as before.

The verifier makes the resolution total for a verified unit: a call names an entry its callee declares, or omits it
only for a callee with exactly one (rule 5). A call the engine still cannot resolve, an entry the callee does not bind,
or no entry named while the callee binds none or several, is the internal fault `unresolved_name`.

== Guards
_Requirements: link:{docs}/Requirements.adoc#PM-IMPL-5[PM-IMPL-5], link:{docs}/Requirements.adoc#PM-WF-16[PM-WF-16]_

Implements link:{dsl}/04-ast-node-model.adoc#guard-results[Workflow DSL § Three-Valued Guard Results] and the
engine side of link:{dsl}/04-ast-node-model.adoc#condition-overlays[Workflow DSL § Condition Overlays].

`GuardEvaluator.evaluate(expr, facts)` reads every atom through `GuardFacts` (`in_worktree`, `has_open_findings`,
`all_tasks_completed`, `predicate:<primitive>`), each itself three-valued. `and`, `or` and `not` propagate
`CouldNotEvaluate` unless the other operand decides: `NotHeld and anything` is `NotHeld`, `Held or anything` is
`Held`. `raiseUndecided(status, links, facts)` evaluates the guards of a state's links in declaration order and raises
`guard_indeterminate` for the first that could not be evaluated, with the facts `guard` (rendered in DSL form), `link`
and `reason`.

A result guard always decides: `holds(guard, result)` holds for a boolean field that is `true` and for any other field
that is present, inverted by `not`. `WorkflowEngine` uses `holds` to select among the routes of a returned outcome.
The offering of links is not part of this package; `evaluate` and `raiseUndecided` are its building blocks.

A condition overlay stops the scope where it is: `raise(status, kind, facts)` sets `pending_condition` with
`raised_at` from the clock and keeps state, phase and call stack. It refuses `integrity_breach`, which names the
breached store, and a status that carries a condition already.

== Budgets
_Requirements: link:{docs}/Requirements.adoc#PM-WF-7[PM-WF-7]_

`LoopBackBudget` keeps three counts of a plan's status, each only ever raised:

* `loop_back_iteration`, raised by every loop-back begun (an outline loop-back and a policy's `fix`); it bounds
  nothing;
* `outline_loop_backs`, bounded by the compiled `OUTLINE_LOOP_BACK_BUDGET` (1) or a raised budget of the plan
  instance;
* `policy_counters`, per remediation policy class `fix_used` and `retry_used`, bounded by the budgets the plan instance
  binds. A retry is no loop-back and leaves `loop_back_iteration` as it is.

A spent budget returns `Charge.Exhausted` with the outcome `exhausted`, and nothing is counted. The accounting refuses
a status of an epic or the workspace, a class outside the remediation policy classes, and a negative budget. Re-entering
a policy's unit reads the same counter, because the counter is in the status.

[#_wait_events_and_resumption]
== Wait Events and Resumption
_Requirements: link:{docs}/Requirements.adoc#PM-WF-2[PM-WF-2], link:{docs}/Requirements.adoc#PM-ARCH-4[PM-ARCH-4], link:{docs}/Requirements.adoc#PM-WF-16[PM-WF-16]_

Implements item 2 of link:{dsl}/06-reusable-sub-workflows.adoc#_call_stack_execution_persistence_semantics[Workflow DSL § Call-Stack Execution & Persistence Semantics]
and the bindings `active_job`, `active_jobs` and `active_tasks` of
link:{spec}/store-schemas/02-workflow-state-store.adoc[Store Schemas § Workflow State Store].

Entering a resting state parks it in the same status write:

[cols="1,3,1"]
|===
|State |Parking |Resumed by

|`job`
|Binds the job a job-starting outcome just reported (`PrimitiveResult.spawnedJobId`), or starts the job through
`JobStarter` and binds that: `active_job` names the state and the job, `active_jobs` holds the job's entry (status
`queued`, `started_at` from the clock). A refused start takes the state's `refused` transition.
|`JobSettled` of a bound job; the state routes the fate.

|`composite_job`
|Binds the state to itself in `active_job`.
|The event its primitive awaits (for example `TimeElapsed` for `TIME`); the primitive runs again and the state routes
its outcome.

|`job llm` (task state)
|Creates one queue task of the role for the state's entity kind through `QueueTaskCreator` and writes it to
`active_tasks` (state `queued`).
|`TasksSettled` naming exactly the state's task entities; the state routes the evaluated outcome.

|`question`
|Nothing is bound.
|`QuestionResolved`; the engine reads the record through `QuestionRecordReader` and routes the outcome only when the
record is resolved with the same outcome.

|`link` (operator wait)
|Nothing is bound: no task is opened, no job is started, and no worker and no model slot is held.
|No engine event; the operator's act through one of its links, or an engine-owned transition that ends the scope. The
wait is `OPERATOR_ACT`, so nothing decides it by time.
|===

A resting link state is an operator wait in every unit and every scope (link:../../../doc/specification/workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL § Waiting for the Operator]). Its `restingWait` carries `OPERATOR_ACT`; a `TimeElapsed` or any other engine event is refused, and the status stays as it is. A question state, by contrast, declares no link, and its own resolution edges await the answer.

`restingWait(status)` and `advance(status, event)` derive the wait from the status through `RestingWait`; an event the
wait does not accept is refused with the status unchanged. The transition that leaves a state clears its bindings.
After a restart the same status yields the same wait, and an advance of a parked state only waits
(link:../adr/workflow-engine/002-every-wait-is-an-engine-event.adoc[ADR 002]).

Not implemented in this package:

* fan-out task states (`each`, `role each`), whose entity list the package that computes it parks; parking one is
  refused with `IllegalStateException`;
* a persisted deadline of a composite job state that waits for time: the wait is derived as `TIME`, and the caller
  delivers `TimeElapsed`.

[#_waits_held_by_a_model]
== Waits Held by a Model
_Requirements: link:{docs}/Requirements.adoc#PM-WF-8[PM-WF-8], link:{docs}/Requirements.adoc#PM-IMPL-4[PM-IMPL-4], link:{docs}/Requirements.adoc#PM-ARCH-8[PM-ARCH-8]_

Implements link:{spec}/job-runtime/01-pipeline-and-subprocesses.adoc#_bounded_long_poll_progress_reset_waiting_primitives_pm_wf_8_pm_impl_4[Job Runtime § Bounded Long-Poll & Progress-Reset Waiting Primitives]
and the bounded wait, progress wait and progress interval rows of
link:{spec}/timeouts/01-job-budgets-and-waits.adoc#waits[Timeouts § Waits & Long-Polls].

A model holds exactly two calls open, a worker's `pm_wait` and a running `pm_build`; every other wait is the engine's
and is resumed by an `EngineEvent` (<<_wait_events_and_resumption>>). The server selects how it holds either one, with
no model involvement, from the calling connection's client profile and the request's progress token:

[cols="1,2,2,2"]
|===
|Call |Profile `progress_resets_timeout` |Progress token |Wait

|`pm_wait`, `pm_build`
|`false`
|any
|Bounded wait, `connection.bounded_wait_seconds`.

|`pm_wait`, `pm_build`
|`true`
|absent or blank
|Bounded wait, `connection.bounded_wait_seconds`.

|`pm_wait`
|`true`
|present
|Progress wait over the bounded window, held through it by the frames.

|`pm_build`
|`true`
|present
|Progress wait up to `progress_wait_max_seconds`.
|===

`WaitSelection.select` is the one rule of that table: a progress wait exists only where both the profile flag and a
non-blank token are there, and only a `pm_build` takes the progress upper bound; a `pm_wait` keeps its bounded window
even when it qualifies. A wait whose window is not longer than the machine's interval takes half its window as the
interval, so a progress wait always emits at least one frame. `ModelWait` is the value of the hold and knows no clock of
its own:

* a `Bounded` wait answers at `startedAt + window` and has no progress frame;
* a `Progress` wait answers at `startedAt + window` and emits a frame at `startedAt + n × interval` for every frame
  before the answer, so no gap between the start, two frames, or the last frame and the answer is longer than the
  interval.

`answersAt(instant)` states when the call is answered and `progressFrames()` lists the frames in order; a caller with a
virtual clock therefore drives a whole run without wall-clock time. The frames are what holds a host's tool-call timer
through the bounded window of a `pm_wait`, so the wait never ends as an MCP transport timeout.

`ConnectionSettings` carries `connection.bounded_wait_seconds`, `connection.idle_timeout_seconds` and
`connection.progress_resets_timeout` and repeats the profile-validation bounds: the bounded wait is 15 to 3600 seconds,
and for a host whose progress resets no timer it is at least 30 seconds below the idle timeout, at most the idle
timeout minus 30 seconds. `WaitSettings` carries
the machine's `progress_wait_max_seconds` (60 to 7200 seconds) and the interval (1 to 60 seconds), shipped as 1800 and
5 seconds; an out-of-bounds value is refused when the value is built, and the only adjustment is the interval of a wait
whose window is not longer than the machine's interval, halved to its window.

The relay that binds `pm_wait` and `pm_build` to these values and the `notifications/progress` sender are not part of
this package; the selection and the windows are.

=== Invariants

* *One rule*: the progress qualification (profile flag **and** token) exists only in `WaitSelection`; no call surface
  repeats it (link:../adr/workflow-engine/012-model-waits-selected-from-the-connection-profile-and-token.adoc[ADR 012]).
* *No frame gap longer than the interval*: a progress wait emits a frame at every interval after the start that falls
  before the answer, at least one, and its interval is between 1 and 60 seconds and shorter than its window.
* *The bounded window of `pm_wait` never widens*: a qualifying `pm_wait` is a progress wait whose window stays
  `bounded_wait_seconds`; only `pm_build` takes `progress_wait_max_seconds`.
* *A blank token is no token*: an empty `_meta.progressToken` selects the bounded wait.

=== Failure Modes

[cols="2,3"]
|===
|Failure |Behaviour

|The bounded wait is outside 15 to 3600 seconds, or not 30 seconds below the idle timeout of a host whose progress
resets no timer
|`IllegalArgumentException` from `ConnectionSettings`; no wait is built.

|The progress upper bound is outside 60 to 7200 seconds, or the interval outside 1 to 60 seconds
|`IllegalArgumentException` from `WaitSettings`; no wait is built.

|A `Progress` is built with an interval below one second or not below its window
|`IllegalArgumentException`; the record refuses the inconsistent value.
|===

Also reported by the package: a `pm_build` whose window ends while the build still runs answers `status: running` with
its `job_id`, and a `pm_build` continuing on an unknown or finished `job_id`, or one of another scope, is refused
`invalid_arguments` (Milestone 6, not in this repository yet).

and the `entity` argument of `pm_state` and `pm_do` in
link:{docs}/specification/mcp-tools/01-core-workflow-tools.adoc[MCP Tools § Core Workflow Tools].

An entity is addressed together with its scope and resolved from persisted state only: the status of the scope and,
for a bootstrap, its pending entry record. The binding of `pm_state` and `pm_do` and the bootstrap units themselves
follow in Milestone 7; this package provides the addresses, their grammar and their resolution.

[horizontal]
`EntityAddress`:: The scope type (`PLAN`, `EPIC` or `WORKSPACE`), the plan or epic id (empty for the workspace scope)
and the entity identifier as supplied. `fromArguments(planId, epicId, entity)` builds it from the arguments of a
scoped tool call, where `plan_id` `NO_PLAN` names the workspace scope. A malformed address (a `null` component, the
lesson store as scope, a scope id where none belongs or none where one does, `NO_PLAN` as a scope id) is refused with
an exception; everything about the identifier itself is decided by the resolver.
`EntityIdGrammar`:: The only place of the grammars no other type owns: the entity identifier
`^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$`, the `module_id` `^[A-Za-z0-9][A-Za-z0-9_.-]{0,56}$` of every entity that begins
with `enrich-`, and the `queue_task_id` `^qt-[0-9a-f]{16}$`. An entity that begins with `ent-` is an `entry_id` and must
parse as `core.store.EntryId` (`ent-` and 8 to 32 lower-case hexadecimal digits), which owns that grammar;
`EntityIdGrammar` consults `EntryId.parse` and declares no pattern of its own for it. Identifiers are compared
byte-exactly.
`EntityAddressResolver`:: Resolves an address against the status of the addressed scope and the unit that holds its
current state (the sub-workflow of the top frame, or the top-level unit): `resolve(address, hostStatus, hostUnit)`.
It takes the `PendingEntryReader` port and the `EntityKindRegistry` the units were verified against, writes nothing
and logs nothing.
`AddressResolution`:: The sealed result: `Resolved` (the address, the entity kind, and the `queue_task_id` of a task
entity) or `Refused` (a closed `Reason` and a detail for the caller's report). Its reasons are `invalid_arguments`,
`scope_not_found` and `entry_unreadable`.
`PendingEntryReader`:: The port of `core.spi`, the engine's read view of one pending entry record: its request
carries the typed `core.store.EntryId`, its read is `Live` with the kind (`plan` or `epic`), `Deleted`, or `Unreadable`
with the reason. The records are kept by `core.store.PendingEntryStore` of `pm-core`; the port is implemented over
that store in `pm-runtime`, a `StoreRefusal` of the store mapping to `Unreadable`. No class of `pm-core` implements
the port, no runtime adapter exists yet, and until one does only the test double implements it; see
link:../../../pm-core/doc/developer/core-store.adoc[Workflow State Store and Engine Ports].

=== The Entities of the Workspace Scope

[cols="2,2,3"]
|===
|Entity kind |Entity identifier |Resolved from

|`bootstrap-plan`, `bootstrap-epic`
|The `entry_id` of the pending entry record, under `plan_id` `NO_PLAN`
|The record read through `PendingEntryReader`: a live record of the kind `plan` or `epic`

|`enrich-module`, one task per module
|`enrich-<module_id>`, the entity the fan-out task works on
|The key of `active_tasks` of the current fan-out task state (`job llm enrich-module role … each …`)

|`lessons-review`, the lesson review
|Its `queue_task_id`: the state names no scope entity
|The `queue_task_id` of the one task in `active_tasks` of the current task state (`job llm lessons-review role lessons`)
|===

A task of a plan or an epic is resolved the same way, against the current task state of that scope. The entity kind
of a resolved task is the registered kind of the state that hosts it; a state naming an unregistered kind is a defect
of the caller's units and refused with an exception
(link:../adr/workflow-engine/009-entity-id-forms-of-workspace-task-entities.adoc[ADR 009]).

=== Resolution

. *Grammar*: an identifier that violates its grammar is `Refused` with `invalid_arguments`, before any read.
. *Entry*: an `entry_id` under a plan or an epic is `scope_not_found` without a read of the port. Under the workspace
  scope the record is read once: a live record of the kind `plan` resolves to `bootstrap-plan`, of the kind `epic` to
  `bootstrap-epic`; a deleted record (the bootstrap ended, or the sweep removed it) is `scope_not_found`; a record that
  could not be read, or that names another kind, is `entry_unreadable`.
. *Task*: any other identifier names a task of the addressed scope's current state. In a fan-out state (`each`,
  `role each`) it is the key of `active_tasks`; in a state that names no scope entity it is the `queue_task_id` of the
  task. A current state that hosts no task, or that holds no such task, is `scope_not_found`.

=== Invariants

* *Each grammar in one place*: `EntityIdGrammar` is the one place of the checks of the entity identifier, the
  `module_id` and the `queue_task_id`; the `entry_id` grammar is the one of `core.store.EntryId`, and the request of
  the port carries that typed id, so it never receives an unchecked string
  (link:../adr/workflow-engine/005-address-grammar-in-workflow-engine-only.adoc[ADR 005], amended 2026-10-13).
* *An unreadable entry is never live*: an `Unreadable` read is `entry_unreadable`, never `Resolved`, so a broken store
  is never mistaken for a bootstrap that can be addressed.
* *Another scope's entity is `scope_not_found`*: an identifier is resolved only within the scope the address names
  (Identifiers Rule 7); a valid identifier that names nothing there is `scope_not_found` (Rule 6). There is no
  dedicated cross-scope reason (link:../adr/workflow-engine/007-refused-address-is-a-value.adoc[ADR 007]).
* *A refusal is a value*: every refusal of a well-formed address is `Refused`; no refusal throws and none is logged
  (link:../adr/workflow-engine/010-no-log-records-for-addressing.adoc[ADR 010]).

=== Failure Modes

[cols="2,3"]
|===
|Failure |Behaviour

|An identifier violates its grammar
|`Refused` with `invalid_arguments`; the port is not read.

|A valid identifier names nothing in the addressed scope: an entity of another scope, a deleted entry, a task the
current state does not hold, or a current state that hosts no task
|`Refused` with `scope_not_found`.

|The pending entry record cannot be read, or names neither `plan` nor `epic`
|`Refused` with `entry_unreadable`.

|A malformed address, a status that is not the addressed scope's, a unit without the status's state, or a task state
naming an unregistered entity kind
|`NullPointerException` or `IllegalArgumentException`: a programming error of the caller.
|===

== Extending the Engine
_Requirements: link:{docs}/Requirements.adoc#PM-IMPL-5[PM-IMPL-5]_

=== A New Resting Kind

A resting kind is a new `StateBehavior` of the AST, which the verifier has to know first. In the engine:

. map it to its `AwaitedEvent` in `awaitedEventOf` and list it in `restingWait`;
. park it in `Run.chain`: bind what it waits for in the status, through a port of `core.spi` if something outside the
  store has to be started, and clear the binding in `Run.enter`, which every leaving transition passes;
. route it in `advance(status, event)` and decide in `advance(status)` when a stored binding means it is parked;
. extend `EngineEventTest` and `EngineResumeTest` with a fixture state of the new kind.

The `switch` statements over `StateBehavior` are exhaustive, so the compiler names every place a new kind must be
handled.

=== A New Event

Add a record to the sealed `EngineEvent` with its checks in the compact constructor, decide in `RestingWait.accepts`
which `AwaitedEvent` it matches and what it must name (a bound job, exactly the bound task entities), and route it in
`advance(status, event)`. An event must name what settled; it never carries a state to go to.

== Developer Pitfalls
_Requirements: link:{docs}/Requirements.adoc#PM-WF-1[PM-WF-1], link:{docs}/Requirements.adoc#PM-IMPL-5[PM-IMPL-5]_

* *Never fold an undecided guard.* A `CouldNotEvaluate` that is read as `NotHeld` hides a link, one read as `Held`
  offers a wrong one. Handle `GuardResult` exhaustively and raise `guard_indeterminate`.
* *A step-out is one frame.* Never unwind more than the frame of the unit that steps out: a commit that steps out
  inside a remediation unit returns to the remediation unit, which can still remedy. Only `unwindToFallback`, the
  fallback of a spent condition budget, unwinds every frame, and it takes no caller's `stepped_out` route.
* *A step-out is offered on resting link states only.* `stepOut` refuses every other state, so a model cannot leave a
  bounded wait of an `auto`, job or task state.
* *Persist in the transaction of the advance.* A caller that writes the new status in a later transaction than its
  other writes splits one state change into two.
* *Result records live for one advance.* The engine collects a frame's result record from the facts its primitives
  return in the advance that returns from it; result guards read nothing else.

== Decisions

* link:../adr/workflow-engine/001-engine-runs-verified-units-only.adoc[ADR 001]: the engine runs only units the
  verifier passes.
* link:../adr/workflow-engine/002-every-wait-is-an-engine-event.adoc[ADR 002]: every resting state is parked and
  resumed by a typed engine event.
* link:../adr/workflow-engine/003-call-stack-in-one-transaction.adoc[ADR 003]: call, chain and return in one atomic
  advance.
* link:../adr/workflow-engine/004-workspace-entity-kinds-addressed.adoc[ADR 004]: the workspace entity kinds addressed
  are the bootstraps and the workspace-hosted task entities.
* link:../adr/workflow-engine/005-address-grammar-in-workflow-engine-only.adoc[ADR 005]: the address types and grammar
  checks live in `workflow.engine` only, except the `entry_id` grammar, owned by `core.store.EntryId` since
  pm-mcp-core#51 (amended 2026-10-13).
* link:../adr/workflow-engine/006-entry-records-read-through-core-spi-port.adoc[ADR 006]: an `entry_id` is resolved
  through the tri-state port `PendingEntryReader`, implemented over `core.store.PendingEntryStore` (amended
  2026-10-13).
* link:../adr/workflow-engine/007-refused-address-is-a-value.adoc[ADR 007]: a refused address is a value with a closed
  reason.
* link:../adr/workflow-engine/008-resolver-beside-the-engine-ports.adoc[ADR 008]: the resolver is its own type beside
  the engine ports.
* link:../adr/workflow-engine/009-entity-id-forms-of-workspace-task-entities.adoc[ADR 009]: the entity kinds and
  identifier forms of the workspace task entities.
* link:../adr/workflow-engine/010-no-log-records-for-addressing.adoc[ADR 010]: addressing writes no log record.
* link:../adr/workflow-engine/011-call-enters-the-callee-through-its-entry.adoc[ADR 011]: a call enters the callee
  through its entry, named or the sole one, and the frame records the entry in the transaction of the call.
* link:../adr/workflow-engine/012-model-waits-selected-from-the-connection-profile-and-token.adoc[ADR 012]: a model
  wait is selected from the connection profile and the progress token, one rule in `WaitSelection`.
* link:../adr/workflow-engine/013-link-states-await-the-operator-act.adoc[ADR 013]: a resting link state is an operator
  wait and awaits `OPERATOR_ACT`; no engine event and no time ends it.
