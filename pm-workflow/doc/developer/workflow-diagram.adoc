= Workflow Diagrams (`workflow.diagram`) Developer Guide
:toc:
:toclevels: 3
:nofooter:

== Purpose

_Requirements: link:../../../../plan-marshall-documentation/doc/requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5]_

Package `de.planmarshall.workflow.diagram` renders the tree of a workflow unit, a `WorkflowDefinition`, as the documentation of that unit in three forms: a Mermaid state diagram, AsciiDoc state, link and outcome tables, and a table for terminal output.
Every form is a pure function of the unit, so the same unit always renders to the same bytes, which is what lets committed documentation be compared with the units it was rendered from.

The generator renders a unit; it does not decide which units are rendered or where the output is committed.
The default units, the committed diagrams and the drift tests that compare them belong to `plan-marshall-mcp` (see link:../adr/workflow-diagram/006-drift-tests-in-plan-marshall-mcp.adoc[ADR 006]).

== Types

_Requirements: link:../../../../plan-marshall-documentation/doc/requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5]_

[horizontal]
`WorkflowDiagramGenerator`:: The only public type: three static methods, one per form, each delegating to its renderer. It refuses an active state the unit does not have and checks nothing else of the unit.
`MermaidRenderer`:: Renders `stateDiagram-v2` with one composite state per phase value.
`AsciiDocTableRenderer`:: Renders, per phase group, the state table with the columns of the State Catalogue, the link table and the outcome table.
`AsciiTableRenderer`:: Renders the right-border-aligned table drawn with Unicode box-drawing characters.
`StateKind`:: The kind of a state (`auto`, `job`, `composite_job`, `call`, `link`, `terminal`, `awaiting_user`), derived from the sealed `StateBehavior` by a switch without a default arm.
`StateTransitions`:: The edges of a unit in declaration order with their label parts: the description of a state, the task label of a task state, the trigger of an engine transition, the source form of a guard, and the implicit links of a state.
`InstanceAnnotations`:: What the instance forms show beside the composed unit of a plan instance version, derived once from its header: the title `plan <plan_id> v<N> (<event>)`, the lane and posture (`-` when unset), the active state, every pruned element and every waived gate, as the wire names of the header in header order.
`InstanceMermaidRenderer`, `InstanceAsciiDocTableRenderer`, `InstanceAsciiTableRenderer`:: Render a plan instance version: the composed unit through the renderer of the same form, and the annotations beside it.

The renderers, `StateKind`, `StateTransitions` and `InstanceAnnotations` are package-private (see link:../adr/workflow-diagram/001-one-facade-three-forms.adoc[ADR 001]).

[source]
----
WorkflowDefinition (verified)
        │
        ▼
WorkflowDiagramGenerator ── renderMermaid ──────── MermaidRenderer ────────┐
        │                ── renderAsciiDocTables ─ AsciiDocTableRenderer ──┼── StateTransitions
        │                ── renderAscii ────────── AsciiTableRenderer ─────┘        │
        ▼                                                                           ▼
String (LF line endings)                                                       StateKind
----

== Usage

_Requirements: link:../../../../plan-marshall-documentation/doc/requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5]_

Render a unit that passed `WorkflowValidator`:

[source,java]
----
String diagram = WorkflowDiagramGenerator.renderMermaid(definition, Optional.empty());
String tables = WorkflowDiagramGenerator.renderAsciiDocTables(definition);
String terminal = WorkflowDiagramGenerator.renderAscii(definition, Optional.of("build.judge"));
----

An empty `activeState` renders the whole unit without a highlight; a present one adds the Mermaid style `active` and the terminal mark `*` with an `(ACTIVE)` line (see link:../adr/workflow-diagram/003-empty-active-state-renders-without-highlight.adoc[ADR 003]).
Write the terminal form as UTF-8 (see link:../adr/workflow-diagram/008-unicode-box-drawing-utf8.adoc[ADR 008]).

The excerpts below are copied from the golden files of the fixture unit `diagram/diagram-fixture.pmwf` in `src/test/resources/diagram/`.

=== Mermaid

The states are grouped by phase value into composite states `phase_<phase>` in first-declaration order; the states of phase `inherit` stay at the top level (see link:../adr/workflow-diagram/010-mermaid-phase-composite-states.adoc[ADR 010]).
A state is declared as `state "<id>" as <alias>`, the alias with `.` and `-` mapped to `_`, and described as `<kind> <target>`; a task state is described by its task label.
Every alias is unique within the diagram: since the grammar admits `build.judge`, `build-judge` and `build_judge` as distinct states, and a state `phase-build` maps to the composite of phase `build`, the aliases are allocated once per rendering, states in declaration order first, then the composites in first-declaration order, and an alias that is already taken gets the next free numeric suffix `_2`, `_3`, …; an allocated alias is never handed out again.
A unit without such a collision renders exactly with the plain mapping.
A transition of a declared link is labelled `<rel> <link_id> [<form>] [<guard>] / <outcome>`, an engine transition `<trigger> [<guard>] / <outcome>`, the trigger being the kind, `question` for the resolution outcomes of a question, or the task label of a task state.
A transition between two states of one phase stays inside the composite; every other transition follows at the top level after `[*] --> <start>`.

[source,text]
----
stateDiagram-v2
    state phase_review {
        state "review.entry" as review_entry
        state "review.prepare" as review_prepare
        state "review.ask" as review_ask
        review_entry : link
        review_prepare : auto diagram.prepare
        review_ask : awaiting_user clarification
        review_entry --> review_prepare : next proceed [noop] / done
        review_entry --> review_entry : submit choose [submit] [in_worktree or has_open_findings and not all_tasks_completed] / declined
        review_entry --> review_ask : retry again [noop] [in_worktree and not has_open_findings or predicate:diagram.ready] / done
        review_ask --> review_entry : question / answered
    }
...
    [*] --> review_entry
...
    build_commit --> diagram_done : call [result.pushed] / done
    build_commit --> review_ask : call [not result.pushed] / done
    build_commit --> diagram_failed : call / stepped_out
----

=== AsciiDoc tables

Per phase group, in first-declaration order, come a state table, a link table and an outcome table, each titled with the phase value; a link or outcome table is omitted for a group without links or transitions.
The state table has exactly the columns of the State Catalogue; *Defined in* is emitted empty because it is maintained by hand in the catalogue (see link:../adr/workflow-diagram/005-catalogue-columns-defined-in-empty.adoc[ADR 005]).
The link table lists the declared links and the implicit ones a state offers without declaring them: the `step_out` of a link state of a sub-workflow (rel `abort`) and one `consult:<role>` per `consult role` clause (rel `consult`).
A cell without content holds `-`; a `|` inside a cell is escaped.

[source,asciidoc]
----
|`build.implement`
|`build`
|`job`
|`build.compose`
|`task implementer each diagram.list-changes`; links `consult:reviewer`; outcomes `approved`, `lost`
|`build.judge`, `diagram.failed`
|
----

=== Terminal table

One block of lines per state in declaration order, separated by a rule; the column widths are the largest number of code points of their cells.
A task state shows its task label and its outcome transitions, never a link of its task's entity (see link:../adr/workflow-diagram/007-model-job-row-shows-role-and-outcomes.adoc[ADR 007]).

[source,text]
----
│ build.judge                                 │ -                │ -                                                                │ approved -> build.commit      │
│  task reviewer                              │ -                │ -                                                                │ lost -> diagram.failed        │
├─────────────────────────────────────────────┼──────────────────┼──────────────────────────────────────────────────────────────────┼───────────────────────────────┤
│ build.commit                                │ -                │ result.pushed                                                    │ done -> diagram.done          │
│  call diagram.callee                        │ -                │ not result.pushed                                                │ done -> review.ask            │
│                                             │ -                │ -                                                                │ stepped_out -> diagram.failed │
----

=== Instance forms

_Specification: link:../../../doc/specification/workflow-dsl/09-plan-instance.adoc#_display[Workflow DSL § Plan Instance, Display]_

A plan instance version, a `PlanInstance` of `workflow.plan`, is rendered in the same three forms (see link:../adr/workflow-diagram/011-instance-diagram-from-header-annotations.adoc[ADR 011]):

[source,java]
----
String diagram = WorkflowDiagramGenerator.renderInstanceMermaid(instance, Optional.empty());
String tables = WorkflowDiagramGenerator.renderInstanceAsciiDocTables(instance, Optional.of("finalize.merge-gate"));
String terminal = WorkflowDiagramGenerator.renderInstanceAscii(instance, Optional.empty());
----

Each form draws the composed unit through the renderer of its unit form, so the unit part is byte-identical to the unit form of `instance.unit()`, and adds what the header records beside the unit.
The pruned elements are absent from the composed unit, so they are listed beside it, never drawn as states of the unit.
An active state that is no state of the instance, a pruned state included, is refused with `IllegalArgumentException`.

[cols="1,3"]
|===
|Form |What it adds to the unit

|Mermaid
|A front matter whose `title` is `plan <plan_id> v<N> (<event>)`, written as a YAML double-quoted scalar; below the unit a composite state `pruned` with one state per pruned element (`<element> <id>: <reason> (<source_fact>)`) and a composite state `waived gates` with one state per waived gate (`<gate>: waived <waiver_id>`), each only when the header lists one. The active state is styled `active`. The identifiers `instance_pruned`, `instance_pruned_<n>`, `instance_waived`, `instance_waived_<n>` pass over every identifier the unit's diagram could use by the next free `_<n>`. Lane and posture are not shown.

|AsciiDoc tables
|A table `Instance <title>` with plan, version, composition event, lane, posture and active state before the unit tables; after them a table of the pruned elements (element, id, reason, source fact) and a table of the waived gates (gate, waiver id), each only when the header lists one.

|Terminal
|A property table (instance, lane, posture, active state) before the unit table with the active state marked; after it the tables of the pruned elements and of the waived gates, each only when the header lists one.
|===

The text of a label or cell, a plan id, a pruned element, a source fact, a gate or a waiver id, comes from the header and may hold any character, so every form makes it safe for the place that holds it, and a line break (a line feed, a carriage return or both, any other Unicode line terminator, and any other Unicode control character, that is the general category Cc: the C0 controls, DEL and the C1 controls U+0080 to U+009F) becomes one space in all three:

* Mermaid: in the label of a state a `#` becomes the entity `+#35;+` (so text that looks like an entity stays text) and a double quote the entity `+#quot;+`.
The front matter `title` is written as a YAML double-quoted scalar, `title: "<text>"`, with a backslash written as `+\\+` and a double quote as `+\"+`, so a title that holds `: ` or begins with a YAML indicator keeps the front matter well-formed; the title is one line already, so no other character needs an escape.
* AsciiDoc tables: a `|` is escaped as `\|` so that it never starts the next cell, and the line break that would end the table early becomes a space.
* Terminal tables: nothing is escaped; every line break and every other Unicode control character is replaced by a single space, so that no cell leaves its line and the right border stays aligned.

The replacement is one function, `InstanceAnnotations.singleLine`, which the three forms share, and it applies to the title of the instance as well.

The excerpt below is copied from the golden file `instance-fixture.mmd` of the fixture instance that `DiagramFixtures` builds from the unit `diagram/instance-fixture.pmwf` and a header written for the test:

[source,text]
----
---
title: "plan diagram-fixture v3 (plan)"
---
stateDiagram-v2
...
    state "pruned" as instance_pruned {
        state "step default:analysis-roundtrip: provider_unconfigured (integrations.sonar)" as instance_pruned_1
        state "state finalize.merge-dispatch: auto_merge_off (merge.auto_merge)" as instance_pruned_2
        state "policy_action finalize.remediate-ci/loop_back: local_only (derived.push_remote)" as instance_pruned_3
    }
    state "waived gates" as instance_waived {
        state "finalize.merge-gate: waived W-7" as instance_waived_1
    }
----

== Extension

_Requirements: link:../../../../plan-marshall-documentation/doc/requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5]_

=== A new `StateBehavior` variant

A new variant of the sealed `StateBehavior` fails to compile in `StateKind.of` and in the switches of `StateTransitions` (`links`, `engineTransitions`, `implicitLinks`, `description`, `engineTrigger`), none of which has a default arm (see link:../adr/workflow-diagram/004-kind-labels-from-sealed-state-behavior.adoc[ADR 004]).
Give the variant its kind, its description and its edges there; the three renderers read nothing else of a behaviour.
Then extend `diagram-fixture.pmwf` with a state of the variant, re-render the three golden files, review the diff and add a case to `StateKindTest`.

=== A new render target

Add a package-private renderer that reads its edges from `StateTransitions.of(definition)` and its kinds from `StateKind`, so its order and vocabulary are those of the other forms, and a public method on `WorkflowDiagramGenerator` that delegates to it.
Pin it with a golden file of the fixture unit beside the other three (see link:../adr/workflow-diagram/002-dedicated-fixture-and-golden-files.adoc[ADR 002]).

=== Changing the output

Any change of the output changes the golden files.
Render the fixture, review the new output by hand and commit it with the change; never edit a golden file to make a test pass.

== Invariants

_Requirements: link:../../../../plan-marshall-documentation/doc/requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5]_

Every form keeps these invariants (see link:../adr/workflow-diagram/009-byte-stable-output.adoc[ADR 009]); `WorkflowDiagramGeneratorTest` guards them on the fixture unit.

. *Declaration order*: states, links and transitions appear in the order the unit declares them, phase groups in the order their phase values are first declared; nothing is sorted.
. *Line endings*: every line ends with a line feed, also the last; no carriage return.
. *No environment*: no timestamp, path, locale or other environment data enters the output.
. *Byte stability*: two renderings of the same unit give identical bytes.
. *Encoding*: the terminal form contains box-drawing characters and is written as UTF-8; the golden files are read as UTF-8.

== Failure Modes

_Requirements: link:../../../../plan-marshall-documentation/doc/requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5]_

[cols="2,3"]
|===
|Situation |Behaviour

|`activeState` names no state of the unit
|`renderMermaid` and `renderAscii` throw `IllegalArgumentException` naming the state and the unit.

|`definition` or `activeState` is `null`
|`NullPointerException`.

|The unit did not pass the static verifier
|Not detected. The forms check nothing else of the unit; a transition target that is no state of the unit is rendered as it is named and stays outside every phase composite, its Mermaid alias allocated after those of the states and the composites.
|===

== Testing

* `WorkflowDiagramGeneratorTest` compares each form of the fixture unit with its golden file byte for byte, renders twice, checks the line endings, the active state, the refusal of an unknown one, the task-state rows, the `role each` label, every parameter type of the link table and the distinct Mermaid aliases of colliding state names, of a composite whose alias a state holds and of an undeclared target.
* The same test compares each instance form of the fixture instance with its golden file (`instance-fixture.mmd`, `.adoc`, `.txt`), checks that the three forms name the same pruned elements and waived gates, the active state, the refusal of an unknown or pruned active state, an instance without annotations, annotation identifiers that collide with the unit's, and the quoted front matter title of a plan id with a colon, a double quote and a backslash beside a plain-title control; the unit-form golden files are unaffected.
* `StateKindTest` maps each variant of `StateBehavior`, a plain and a composite job apart, to its kind label.
* `DiagramFixtures` parses the fixture unit and verifies it with `WorkflowValidator` before any test renders it, with the primitives, the entity kind `change` and the called sub-workflow `diagram.callee` registered in the test package.
