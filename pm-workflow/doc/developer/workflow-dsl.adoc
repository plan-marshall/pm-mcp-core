== Purpose
_Requirements: link:{docs}/requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5], link:{docs}/requirements/02-workflow.adoc#PM-WF-16[PM-WF-16]_

Package `de.planmarshall.workflow.dsl` is the line-oriented Workflow DSL: it reads the text of a unit into the
immutable tree of `workflow.ast` (link:workflow-ast.adoc[Workflow AST]) and prints a tree back to text. Every `.pmwf`
file opens with a frontmatter, which a reader of its own reads, and continues with the body, which the parser reads.
A refusal is a value with a rule, the resource, the line and the column; nothing in the package throws for a bad unit.

The grammar of the body is link:{spec}/workflow-dsl/01-grammar.adoc[Workflow DSL § Grammar]. This guide states the
format of the frontmatter, which the reader implements, and what the parser and the printer do with the frontmatter, the
entry bindings and the entry of a call. The decisions are recorded in `pm-workflow/doc/adr/workflow-dsl/`.

== Main Types
_Requirements: link:{docs}/requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5]_

[horizontal]
`UnitFrontmatterReader`:: Reads the frontmatter of a unit, and nothing else: `read(resourceName, source)` returns the
sealed `UnitFrontmatterReader.Result`, either `Read` with the `UnitFrontmatter` and the line the body starts at, or
`Refused` with a `Diagnostic` of the rule `FRONTMATTER`. It stops at the closing `---`, so the body need not parse.
`UnitLimits`:: The classpath location and the keys of the three limits of a project unit file and a unit frontmatter;
`de.planmarshall.core.config.LimitProperties` reads them when the classes load; an absent resource, an absent key or
a value that is not a number fails the load, never defaults.
`WorkflowParser`:: `parse(resourceName, source, origin)` reads a whole unit and returns the sealed `ParseResult`:
`Parsed` with the `WorkflowDefinition`, or `Refused` with the first `Diagnostic`.
`WorkflowPrinter`:: Prints a `WorkflowDefinition` as canonical source, so that parsing the printed text yields the same
tree, source locations aside (the round trip).
`Diagnostic`:: A refusal: the `RefusalRule`, the resource, the line, the column and what is wrong.
`RefusalRule`:: The closed set of the reasons a unit is refused: `FRONTMATTER`, `STRUCTURE`, `RESERVED_KEYWORD`,
`MISSING_SCOPE`, `DUPLICATE_ID` and `INSTANCE_HEADER`.

[source]
----
.pmwf text ──► UnitFrontmatterReader ── Refused(FRONTMATTER) ─────────────────► ParseResult.Refused
                     │ Read(frontmatter, bodyLine)
                     ▼
               WorkflowParser (body from bodyLine) ── Refused(STRUCTURE, …) ──► ParseResult.Refused
                     │
                     ▼
               ParseResult.Parsed(WorkflowDefinition) ──► WorkflowPrinter ──► canonical text
----

== The Read Order
_Requirements: link:{docs}/requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5]_

`WorkflowParser.parse` reads in two steps:

. *Frontmatter first.* The parser hands the whole text to `UnitFrontmatterReader.read`. A missing or refused frontmatter
  is returned as the parser's refusal, with the rule `FRONTMATTER`; the body is not read.
. *Then the body.* The lexer cuts the whole text into lines, and the parser keeps the lines from the reader's `bodyLine`,
  the line after the closing `---`. Line numbers are those of the file, so every refusal of the body names the line
  as an editor shows it. A body without a token is refused at `bodyLine`, column 1.

The lines of the frontmatter, which the lexer cuts with the rest of the text, are dropped before the parser reads a
line, so the lexer's comment rule (`#` to the end of the line) never applies to them: inside the frontmatter a comment
is refused.

=== The Lexer

`WorkflowLexer` cuts the source into lines, drops a comment from `#` to the end of its line, ignores indentation and
blank lines, and gives every token its 1-based line and column. A word is an `INT` when it is all digits, an `IDENT`
when it is lower case and starts with a letter, an `ENUM_VALUE` when it starts with a letter and contains an upper-case
one, and `INVALID` otherwise. A `-` directly followed by `>` ends a word, so `done->next` is three tokens. The JSON of an
`instance` line stays one token, so a `#` inside it is no comment. The lexer never refuses: an unknown character becomes
an `INVALID` token that the parser refuses where it occurs.

=== The Parser

`WorkflowParser` is a recursive descent over the grammar: the unit header, the optional `instance` line, the `scope`
clause with the `result` declaration of a sub-workflow (its inputs are the frontmatter's `input` lines; a body `param`
is refused), the `declare` and `decide` lines, `start`,
`migrate`, and every state form with its links, guards, transitions, result guards and step completions. A `link`
without a form takes `LinkRelation.defaultForm()`. Guards bind `not` before `and` before `or`; a guard nested deeper
than 32 parentheses (`WorkflowParser.MAX_GUARD_DEPTH`) is refused, which bounds the recursion.

The first refusal wins. Its `RefusalRule` is one of the members listed under <<_main_types>>; `STRUCTURE` covers a source
that does not follow the grammar. `MISSING_SCOPE` refuses a unit without a `scope` clause. `DUPLICATE_ID` refuses an
identifier declared twice in the file: a state, a `declare` name, a decision kind, a call argument and a link parameter,
an entry bound twice, and a value repeated in a list value or in a link parameter's `enum[...]` type. A repeated
frontmatter value, a repeated input name and a repeated `enum[...]` value of an `input_type` are the frontmatter reader's
refusal (`FRONTMATTER`, at the line and column), not the parser's.

A reserved keyword (`WorkflowParser.RESERVED_KEYWORDS`) is refused only where the grammar names a name: as an outcome
name, a parameter name, an entity kind, a role name, or a segment of a state, primitive or configuration key
identifier. Everywhere else the positional vocabularies stay usable: `link retry retry [noop]` and
`plan.allocate-remediation-tasks` parse. The unit id is read as a state identifier, so no segment of a unit id may be
a reserved keyword either.

The `derived_from <n>` clause of the header is recorded in `WorkflowDefinition.derivedFrom()` as `{<unit id> -> n}`.
It is admitted only in a unit parsed with the origin `PROJECT`; on a `DEFAULT` unit it is refused `STRUCTURE`, and a
revision of zero is refused for every origin.

The parser checks the grammar alone: it checks no identifier length bound, every verification rule is the verifier's,
and an `instance` line in a `PROJECT` unit parses.

A state whose body starts with `question <class>` routes the class's closed resolution outcomes and declares no `link`
clause; a link after it is refused `STRUCTURE` ("expected a state but found 'link'"). Every state whose body starts with
a `link` clause is a resting link state, an operator wait in every unit and every scope
(link:../../../doc/specification/workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL § Waiting for the Operator]).
The `scope` keyword admits `plan`, `epic`, `workspace`, `machine`, `entity` and `subworkflow`.

[#instance-header]
=== The Instance Header

The `instance` line of a plan instance version is one line of JSON. `InstanceHeaderReader` reads it with the streaming
`JsonParser` of `jackson-core` into `InstanceHeader` (`planId`, `version`, `event`, `inputs`, and the JSON exactly as
read) with its `InstanceInputs`: the configuration hash, the template and sub-unit references (`UnitRef`: unit, optional
file, digest, origin), the composition rule reference (`CompositionRules`: revision, digest), the plan facts digest, and
the three optional members, the realized-footprint digest, the change type and the providers digest. An optional member,
the file of a `UnitRef` among them, is a `@Nullable String` that is `null` when the member is absent or `null`; the reader
assigns the read text to the component directly, without wrapping it in an `Optional`.

The reader checks the structure of the plan instance header: the required members and their JSON types, and no member
named twice in any object. It ignores members it does not model, which stay in the JSON. A defect is a refusal
`INSTANCE_HEADER` whose message names the member, for example
`member 'inputs.templates[0].digest' of the instance header must be a string`; a header without `inputs` is refused. The
other schema checks (constants, enumerations, patterns, members it does not allow) are made by `HeaderSchemaCheck` of
`workflow.plan`. A `jackson-core` exception is mapped to the refusal and never rethrown.

[#unit-frontmatter]
== The Unit Frontmatter
_Requirements: link:{docs}/requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5]_

The frontmatter is the first part of every `.pmwf` file: what the unit is for a person, its type, the stable icon that
stands for it, its interface (the entries through which control arrives, the exits through which it leaves, the inputs a
call declares and what the unit reads), and where it comes from. It is read without the body, so a list of units, a
catalogue of building blocks or a process view shows a unit's name, description, type, icon and interface from it alone,
and a `call` is checked against the interface of its callee.

[source,yaml]
----
---
name: Commit and Push
description: Commits the changes of the plan's worktree and pushes its branch as the push mode says.
type: subworkflow
icon: git.commit
entry: commit
entry_description: The worktree holds the changes to commit, or is clean.
exit: done
exit_description: Commit and push are settled; the result record says what was committed, pushed, or landed.
reads_config: project.review.currency
reads_fact: push_remote
input: push_mode
input_type: enum[push|no_push]
input_description: Whether the branch is pushed.
input: attempts
input_type: int[1..5]
input_default: 2
modification_date: 2026-10-14
version: 1.0.0
author: plan-marshall
---
workflow git.commit_and_push version 1 format 1
scope subworkflow
…
entry commit -> git.inspect-worktree
----

=== Format

The frontmatter is a closed, line-oriented subset of YAML between two lines `---`, the first of which is the first line
of the file. `UnitFrontmatterReader` reads it with a parser of its own and never with a general YAML loader, so no tag,
anchor, alias or merge key is ever resolved
(link:../adr/workflow-dsl/005-frontmatter-read-by-its-own-line-parser.adoc[ADR 005]).

* *One field per line*: every line is `key: value` at column 1. There is no blank line, comment, indentation, nesting,
  flow collection, block scalar or document marker other than the two delimiters, and no line contains a control
  character, a format character (category Cf, a bidi override or a zero-width space among them), a line separator (Zl)
  or a paragraph separator (Zp). A frontmatter with one is refused with its category, its code point and its line, so a
  display value cannot reorder or hide what the operator sees
  (link:../adr/workflow-dsl/007-refused-characters-and-frontmatter-bounds.adoc[ADR 007]).
* *Bounds*: a project unit file holds at most the value of `pm.workflow.unit.max-file-bytes`
  (`ProjectUnitLoader.MAX_UNIT_FILE_BYTES`), a frontmatter holds at most the value of
  `pm.workflow.unit.max-frontmatter-lines` including its two `---` delimiters
  (`UnitFrontmatterReader.MAX_FRONTMATTER_LINES`), and a refusal echoes at most the value of
  `pm.workflow.unit.max-echo-length` characters of the source, marked with `...` where it cuts
  (`UnitFrontmatterReader.MAX_ECHO_LENGTH`). The three keys lie in
  `pm-workflow/src/main/resources/de/planmarshall/workflow/dsl/unit-limits.properties`, which each class reads when it
  loads; a missing resource or key fails the load, never defaults. The reader reads the frontmatter from the head of
  the source and never the body.
* *Line endings*: a line ends with a line feed (LF) or with a carriage return and a line feed (CRLF). The line ending is
  not part of the line, so a CRLF unit reads to the same frontmatter, with the same line and column numbers, as its LF
  twin. A carriage return anywhere else is a control character and refused.
* *Values*: a value is plain or double-quoted. A plain value has no leading or trailing blank, does not start with a
  YAML indicator character (`-?:,[]{}#&*!|>'"%@` and the backquote), and contains neither `": "` nor `" #"`. A
  double-quoted value is one line between `"` and `"` with the escapes `\"` and `\\` only. A value a plain scalar
  cannot carry is written double-quoted.
* *Closed keys*: the keys are `name`, `description`, `type`, `icon`, `entry`, `entry_description`, `exit`,
  `exit_description`, `reads_config`, `reads_fact`, `input`, `input_type`, `input_default`, `input_fallback`,
  `input_description`, `modification_date`, `version`, `author` and `signature`; any other key is refused. `name`,
  `description`, `type`, `icon`, `modification_date`, `version` and `author` occur exactly once, `signature` at most
  once.
* *Repeated `entry`, `exit`, `reads_config`, `reads_fact` and `input`*: a unit declares zero or more entries, exits,
  configuration keys, fact kinds and inputs, one value per line, the key repeated per value, kept in order and never
  collapsed. This is the one point where the frontmatter is not a YAML mapping. A `reads_config` value is an effective
  configuration key (the grammar `config_key`, one or more identifier segments joined by dots); a `reads_fact` value is a
  fact kind (an identifier); an `input` value is a `param_name`. No key lists a value twice, and the caps are 32
  `reads_config` values, 32 `reads_fact` values and 16 inputs.
* *Descriptions*: an `entry_description` stands directly below its `entry` line and an `exit_description` directly below
  its `exit` line, at most one each. A description below another key, below another description or as the first line is
  refused.
* *The input block*: an `input` line opens one input; `input_type` stands directly below it, exactly once, then
  `input_default`, `input_fallback` and `input_description`, each at most once and in that order. A sub-key out of that
  order, a second one of its kind and an input without its `input_type` are refused. The type is one of `enum[…]`,
  `int` with its optional range and `list<enum[…]>`, with the trailing `?` of the optional form
  (link:../adr/workflow-dsl/013-input-type-carries-the-optional-form.adoc[ADR 013]); a default or a fallback beside the
  `?` is refused as two ways to say the same. `input_default: []` is the empty list of a `list<enum[…]>` input, the one
  bracket form the reader admits at the start of a value.
* *Order*: apart from the descriptions and the input sub-keys, the order of the lines is free. The printer writes the
  order of the field table below.

=== Fields

[cols="2,1,6"]
|===
|Key |Occurs |Value and check

|`name`
|1
|The display name of the unit, 3 to 100 characters.

|`description`
|1
|What the unit does and when it is used, 1 to 1000 characters.

|`type`
|1
|One of the wire names of `UnitType`: `workflow`, `recipe`, `subworkflow`, `system`, `task`, `instance`
(link:workflow-ast.adoc#unit-types[Workflow AST § Unit Types]).

|`icon`
|1
|The stable icon id that stands for the unit in the visual language, `[a-z][a-z0-9._-]{0,63}` without a `..` segment.
The grammar admits no slash, backslash, blank or colon, so the value is an id and never a file path. The id is stable:
a change of the art keeps the id, and a rename needs an alias or a migration note in the client that delivers the icon
(link:../adr/workflow-dsl/008-required-icon-field.adoc[ADR 008]). The key is required within format 1.

|`entry`
|0..n
|The name of an entry: a DSL identifier `[a-z][a-z0-9_-]{0,31}` of the
link:{spec}/identifiers/01-general-rules-and-registry.adoc#id-dsl-identifier[Identifier Registry], unique among the
unit's entries. The header binds it with `entry <name> -> <state_id>`.

|`entry_description`
|0..1 per entry
|What a caller hands over or may assume when it enters through the entry on the line before, 1 to 500 characters.

|`exit`
|0..n
|The name of an exit, an outcome id of the same grammar, unique among the unit's exits, never `stepped_out` (the
implicit control exit of every sub-workflow).

|`exit_description`
|0..1 per exit
|What the caller can rely on when the unit leaves through the exit on the line before, 1 to 500 characters.

|`reads_config`
|0..32
|An effective configuration key the unit reads, in the grammar `config_key` (`project.review.currency`,
`workflow.mode`). The key must exist in the closed configuration the verifier is given, and it never carries the bare
value `derived` or the `derived.` stem: a derived fact is read with `reads_fact`
(link:../adr/workflow-verify/037-reads-config-never-names-a-fact.adoc[ADR 037]). Declared once.

|`reads_fact`
|0..32
|A derived fact kind the unit reads, an identifier without the `derived.` stem. The kind must be one the verifier's
`FactKindRegistry` holds. Declared once.

|`input`
|0..16
|The name of one input, a `param_name` (lowercase letters, digits and underscore, at most 32 characters) that is never a
reserved keyword and never a `reads_fact` kind of the same unit. Declared once. Its sub-keys follow, in order.

|`input_type`
|1 per input
|The closed type of the input, directly below its `input` line: `enum[…]`, `int` with its optional `[<low>..<high>]`, or
`list<enum[…]>`, with the trailing `?` of the optional form. The type is an `InputType`; the `?` is a component of the
declaration (link:../adr/workflow-dsl/013-input-type-carries-the-optional-form.adoc[ADR 013]).

|`input_default`
|0..1 per input
|The compiled default of the input: an enum value of its type, an integer within its range, or `[]` for a `list<enum[…]>`
input. A value outside the type is refused. It stands below `input_type` and never beside the `?`.

|`input_fallback`
|0..1 per input
|The configuration key that supplies the input when a call binds none: one the unit lists in `reads_config`, whose domain
the verifier checks against the input type, and whose compiled default an input with neither a default nor the `?` needs
(link:../adr/workflow-dsl/014-order-of-input-resolution.adoc[ADR 014]). It never stands beside the `?`.

|`input_description`
|0..1 per input
|What an absent input means and what a caller may assume, 1 to 500 characters. Shown to the caller and not part of the
`INV-GEN-1` contract.

|`modification_date`
|1
|The date of the last change of the file, `YYYY-MM-DD`, a valid calendar date not after the day of the validation,
taken in UTC.

|`version`
|1
|The plan-marshall release the unit was created with or delivered by, in the
link:{spec}/identifiers/02-registry-stores-to-web.adoc#id-release-version[release version] grammar
(`[0-9]+.[0-9]+.[0-9]+` with an optional `-` suffix of `[A-Za-z0-9.-]`, at most 64 characters). It is not the unit's
revision, which the `version` of the `workflow` header counts.

|`author`
|1
|Who made the unit, 1 to 100 characters: `plan-marshall` for the units compiled into the binary and only for them. The
reader checks the length; the reserved name is checked per level by the loader, on the author's NFKC-normalised,
format-character-free, stripped and case-folded form
(link:workflow-unit.adoc#_the_author_of_a_unit[Workflow Units § The Author of a Unit]).

|`signature`
|0..1
|Reserved for a signature over the file's content. It is carried with the unit and not verified; a missing one is no
finding.
|===

=== Refusals

The reader stops at the first refusal and reports it with the rule `FRONTMATTER`, the line and the column:

[cols="3,2"]
|===
|Refused |Where

|No frontmatter: the first line is not `---`
|line 1, column 1

|The frontmatter is not closed by a line `---`
|the last line, column 1

|A blank line, an indented line, a merge key (`<<`), a line that is not `key: value`, an unknown key, a repeated single
key, a description that does not stand directly below its element, a second description of one element
|the line, column 1

|A tag (`!`), an anchor (`&`), an alias (`*`), a flow collection (`[`, `{`), a block scalar (`\|`, `>`), a comment (`#`),
or another YAML indicator at the start of a line or of a value
|the line, column 1 or the column of the value

|A comment (`" #"`) or a mapping (`": "`) inside a plain value, a trailing blank, an escape other than `\"` and `\\`,
content after the closing quote, an unclosed double-quoted value
|the line, the column of the offending character

|A control character, a format character (Cf), a line separator (Zl) or a paragraph separator (Zp)
|the line, its column

|A frontmatter of more lines than `pm.workflow.unit.max-frontmatter-lines`, the two delimiters included
|the first line past the cap, column 1

|A field outside its bounds: a length, an unknown type, an icon outside the icon-id grammar, an entry or exit that is
no identifier or is declared twice, the exit `stepped_out`, an invalid or future date, a version outside the release
version grammar
|the line, the column of the value

|A `reads_config` value outside the `config_key` grammar or declared twice, a `reads_fact` value outside the identifier
grammar or declared twice, more than 32 of either
|the line, the column of the value

|An `input` name outside the `param_name` grammar, a reserved keyword, an input declared twice, more than 16 inputs
|the line, the column of the value

|An `input_type` outside its three types, a repeated enum value, an empty enum, a range that is no `[<low>..<high>]`, an
`input_type` that does not stand directly below its `input` or a second one
|the line, the column of the value, or column 1 of its own line

|An `input_default` or `input_fallback` out of its order, a second one, either beside the `?`, an `input_default` outside
the type, an `input_description` out of its order, a second one or beyond 500 characters
|the line, the column of the value, or column 1 of its own line

|An input whose `input_type` is missing
|the line of the next key, or the closing line, column 1

|A missing single key
|the closing line, column 1
|===

== The Body: Start State or Entry Bindings
_Requirements: link:{docs}/requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5], link:{docs}/requirements/02-workflow.adoc#PM-WF-16[PM-WF-16]_

After its declarations, the header of the body carries either one `start <state_id>` line or one or more
`entry <name> -> <state_id>` lines (the EBNF `start_decl | entry_decl , { entry_decl }`):

* the body declares no `param`: the inputs of a sub-workflow are the `input` declarations of its frontmatter, in one
  place with its entries and exits. A `param` line after the `scope` clause is refused as `STRUCTURE`, naming the
  frontmatter keys that replace it (link:../adr/workflow-dsl/012-result-stays-in-the-body.adoc[ADR 012]);
* a body with a `start` line and an `entry` line, in either order, is refused as `STRUCTURE` at the second of the two;
* a body with neither is refused as `STRUCTURE` where the one or the other is expected;
* an entry name bound twice is refused as `DUPLICATE_ID` at the second binding.

The parser keeps what the body says and compares nothing with the frontmatter. A unit whose frontmatter declares entries
but whose body has a `start` line, a declared entry without a binding, a binding of a name the frontmatter does not
declare, and a binding to a state the unit does not have all parse, and the verifier refuses them
(link:workflow-verify.adoc#interface-rules[Workflow Verification § Interface Rules], rule 1). One owner per check keeps
every verifier fixture parseable.

A `call` clause may name the callee's entry: `call <unit> entry <name> (…)`. The entry is kept as a `@Nullable String`
on `StateBehavior.SubWorkflowCall`, `null` when the call names none; whether the callee declares it, and whether the call may omit it, is the verifier's
(rule 5).

The keyword `entry` is positional, not reserved: it is read only at the start of a header line and after the callee of a
`call`, so a state id such as `setup.entry` stays valid. The keyword `start` is reserved.

[#call-values]
== Call Values and the Empty List
_Requirements: link:{docs}/requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5], link:{docs}/requirements/02-workflow.adoc#PM-WF-25[PM-WF-25]_

A call argument and a `declare` line carry a `CallValue` (the EBNF `call_value`,
link:{spec}/workflow-dsl/01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL § Grammar]): an
enumeration value, a non-negative integer, or a list of distinct enumeration values between `[` and `]`.
The list may be empty: `[]` is the list without an element, read as a `CallValue.EnumList` with no value, for example
`declare wait_after = []` of an asking variant that waits after no phase.
The empty list is the one change: every other list refusal of the parser stays (`STRUCTURE` for an unterminated list,
values without a comma between them, a trailing comma or a comma alone; a value listed twice), and what a list may hold where it is bound or declared
stays the verifier's and the declaration bounds' (link:../adr/workflow-dsl/006-empty-list-admitted-as-a-call-value.adoc[ADR 006]).
The printer writes the empty list back as `[]`, so it survives the round trip.

== The Asking Axis of a Task State
_Requirements: link:{docs}/requirements/02-workflow.adoc#PM-WF-12[PM-WF-12]_

A task state's `job llm` clause carries an asking axis after its role clauses: absent, `ask`, or `ask fresh`. The AST
holds it as one `StateBehavior.AskForm`; `ModelJob.ask()` answers whether any form is declared, and the form itself
decides whether the server may continue the task after its question (`allowsContinuation`). `ask fresh` offers the same
`ask` link and orders the server never to continue the task, which `workflow.question` decides together with the role's
bounds and the harness. On a `role each` state both forms are refused by the verifier through the same check. An
`instance-unit.pmwf`-style fixture with both forms is `dsl/valid/ask-fresh-unit.pmwf`, and the printer writes the form's
own text (link:../adr/workflow-dsl/010-ask-fresh-as-a-form-of-the-axis.adoc[ADR 010]).


== The Printer and the Round Trip
_Requirements: link:{docs}/requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5]_

`WorkflowPrinter` writes the frontmatter first, between its two `---` lines, in the order of the field table: `name`,
`description`, `type`, `icon`, each `entry` followed by its `entry_description`, each `exit` followed by its
`exit_description`, each `reads_config` and `reads_fact` value, each `input` followed by its `input_type` and its
`input_default`, `input_fallback` and `input_description`, `modification_date`, `version`, `author` and `signature`. A
value is written plain when a plain scalar can carry it and double-quoted otherwise (the rule is
`UnitFrontmatterReader.isPlain`, the reader's own, so printer and reader cannot
drift apart), with `\` written as `\\` and `"` as `\"`; the empty list default is written `[]`. Then come the unit
header (with `derived_from <n>` when
`derivedFrom()` holds a revision for the unit's own id), the `instance` line, the `scope` clause with the `result`
declaration of a sub-workflow, the `declare` and `decide` lines, the `start` line or the entry bindings in source order, the
migrations, and the states in declaration order, each after a blank line, with their clauses indented by nesting; a
`call` names the entry it names in the tree.

* *Links*: every link names its form, the default form included.
* *Guards*: a guard carries exactly the parentheses its precedence needs (`not` before `and` before `or`, both
  operators left-associative); a negated operand that is no single guard is always parenthesised, so a doubly negated
  operand is written `not (not x)`, because the grammar has no `not not`.
* *Ranges*: a range of a `text` or `int` type is written with both its bounds; `ParamType.Text` and `ParamType.Int`
  hold both bounds or none and refuse a single one.
* *The instance line*: the printer writes `InstanceHeader.json()`, the JSON exactly as it was read, and never
  re-serialises the parsed members, so the header's digest stays reproducible.
* *No checks*: the printer prints the tree it is given.

Parsing the printed text yields the same tree, source locations aside: the frontmatter, the order of the entries and
exits, the entry bindings and the entry of every call survive the round trip. A frontmatter whose lines were in another
order is printed in the order of the table, and the descriptions stay with their elements. Printing the parsed tree
again gives the same text: canonical source is a fixed point of parse and print.

== Adding a Refusal
_Requirements: link:{docs}/requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5]_

. Decide who owns the check. The parser refuses only what the text alone decides: the grammar and the uniqueness of an
  identifier within the file. Everything that compares two parts of a unit, or a unit with another, is a rule of the
  verifier.
. Refuse it where it is found, with the line and the column of the offending token: in the frontmatter reader for the
  frontmatter, in the parser for the body. Reuse a `RefusalRule` when one names the reason; add a member, with its
  Javadoc, only for a new kind of reason.
. Add a malformed fixture below `src/test/resources/dsl/malformed/`. It opens with a valid frontmatter, unless the
  frontmatter itself is what is refused, and states its expectation in a comment
  `# expect: <RULE> line <n> column <n>` directly below the closing `---` (as the first line of a fixture without
  frontmatter). `WorkflowParserRefusalTest` refuses every fixture of the directory with exactly that rule, line and
  column.
. A refusal of the frontmatter is also a case of `UnitFrontmatterReaderTest`.

== Developer Pitfalls
_Requirements: link:{docs}/requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5]_

* *Never read the frontmatter with a general YAML loader.* A YAML loader resolves tags, anchors, aliases and merge keys,
  collapses the repeated `entry` and `exit` keys into one, and accepts what the closed format refuses. Read it through
  `UnitFrontmatterReader` only, also where only the name or the type of a unit is wanted.
* *Count lines from the file.* The body's line numbers are those of the file, the frontmatter's lines included. A
  fixture's expected line moves with every line its frontmatter gains.
* *Do not compare in the parser.* A check of the bindings against the declared entries in the parser would refuse the
  verifier's fixtures before the verifier sees them.
* *Fixtures are written for the test.* A test unit below `src/test/resources/dsl/` is written for the case it covers,
  never copied from a default unit of the product: model-facing content lives only in `plan-marshall-mcp`, and no
  artifact of `pm-mcp-core` carries it.
* *Print the instance JSON as read.* The printer writes `InstanceHeader.json()` verbatim; code that builds an
  `InstanceHeader` supplies the canonical JSON itself, because nothing re-serialises the parsed members.
* *Reserved words in names.* A name that reads naturally can be refused because one of its segments is reserved: a unit
  called `question.something` or a primitive `link.check` does not parse, and neither does a state id with the segment
  `start`.

== Decisions

* link:../adr/workflow-dsl/001-parse-result-is-a-sealed-value.adoc[ADR 001]: the parse result is a sealed value.
* link:../adr/workflow-dsl/002-line-oriented-parser-and-round-trip-printer.adoc[ADR 002]: a line-oriented lexer and
  parser, and a production printer that round-trips.
* link:../adr/workflow-dsl/003-unit-without-scope-refused.adoc[ADR 003]: a unit without scope is refused.
* link:../adr/workflow-dsl/004-instance-header-json-kept-as-a-string.adoc[ADR 004]: the instance header JSON is kept as
  a string.
* link:../adr/workflow-dsl/005-frontmatter-read-by-its-own-line-parser.adoc[ADR 005]: the frontmatter is read by a line
  parser of its own, its refusals are values of the rule `FRONTMATTER`, and the frontmatter of a composed instance is
  derived from its template.
* link:../adr/workflow-dsl/006-empty-list-admitted-as-a-call-value.adoc[ADR 006]: the grammar admits the empty list `[]`
  as a call value, and nothing else of the grammar changes.
* link:../adr/workflow-dsl/007-refused-characters-and-frontmatter-bounds.adoc[ADR 007]: the frontmatter refuses format,
  line and paragraph separators, is bounded at the value of `pm.workflow.unit.max-frontmatter-lines` lines, and a
  refusal echoes at most the value of `pm.workflow.unit.max-echo-length` characters.
* link:../adr/workflow-dsl/008-required-icon-field.adoc[ADR 008]: every unit declares the required `icon` key.
* link:../adr/workflow-dsl/009-question-states-declare-no-links.adoc[ADR 009]: a question state declares no `link`
  clause, and the parser refuses one.
* link:../adr/workflow-dsl/010-ask-fresh-as-a-form-of-the-axis.adoc[ADR 010]: the asking axis is one `AskForm` value
  (`none`, `ask`, `ask fresh`), and `ask fresh` is refused on a `role each` state exactly as `ask` is.
* link:../adr/workflow-dsl/011-the-grammar-carries-no-phase-clause.adoc[ADR 011]: the grammar and the printer carry no
  `phase` clause; `phase` stays a reserved word and is refused.
