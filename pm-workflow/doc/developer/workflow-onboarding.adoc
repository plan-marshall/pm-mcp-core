== Purpose

The engine half of the machine's automatic onboarding and of its aspects: the vocabulary of what the run decided, and the
routing of `onboard.next` between the aspects, the automatic run's result and the machine's settings. The units
(`onboarding.pmwf`, the aspect sub-workflows, `auto.consent`, `auto.result`) are resources of `plan-marshall-mcp`; this
package is what those units run where the run is deterministic, and it is provable over fixtures without a workflow.

== Types

[cols="2,4"]
|===
|Type |What it is

|`OnboardingAspect` (`core.config`)
|The closed list of the aspects in the fixed order of the guided and the automatic run, named by the aspect unit's own
prefix (Workflow DSL § Machine Scope, item 3): `language`, `harness`, `catalogue`, `roles`, `store`, `providers`,
`defaults`; `next()` walks it, and a `reconfigure:<aspect>` link names it. It lives in `pm-core` because the machine's
settings of `pm-runtime` name the same aspects.

|`OnboardRun`
|How an aspect is called: `first_run`, `auto`, `reconfigure`.

|`ProposalReason`
|Why the automatic run decided a value: `system`, `only_supported`, `all_supported`, `all_found`, `default`, `available`,
`tool_logged_in`, `asked`; each carries its `onboard.auto.reason.<reason>` message key.

|`OnboardingProposal`
|One item of the result: the aspect, the key, the value, the reason and the check line that confirmed it. `asked()` is the
one reason that marks an item the run could not decide.

|`AutoOnboardingResult`
|The items of one run: `decided()`, `undecided()`, `of(aspect)` and `value(aspect, key)`.

|`OnboardingRouter`
|The routing of `onboard.next` as a value: `returned(run, aspect, openedFrom)` and `change(result, aspect)`, each answering
a `Route` (an aspect call, or `completed`, `result` or `settings`).
|===

== Routing

The first run and the automatic run take the aspects in `OnboardingAspect`'s order. After the last aspect the first run
opens `onboard.completed` and the automatic run opens `onboard.auto-result`. A `change` on the result calls that one aspect
with `onboard_run: reconfigure`; the assembly supplies the aspect's current values from `result.of(aspect)` as the proposal,
because the router reads no state. Because the run value alone cannot say where a
later run returns, `returned(..., OpenedFrom.RESULT)` leads back to the result and `OpenedFrom.SETTINGS` back to
`settings.choose`. A change naming an aspect the result carries no item of is refused: there is nothing to change.

== Failure Modes

* A `change` for an aspect the result does not carry throws `IllegalArgumentException` naming the aspect.
* A `reconfigure` return without its origin, and a `first_run` or `auto` return with one, are refused: the run and its
  origin must agree.
* A `Route` of another target that names an aspect or a run is refused by its constructor, so a route either calls an
  aspect or names a state.

== Testing

`OnboardingResultTest` holds the aspect order, the closed reason list with its message keys, and the decided/undecided
split; `OnboardingContractReplayTest` replays the `onboarding-contract` scenarios over the router, including the whole
automatic run in order and the change-on-result return.
