== Purpose

`de.planmarshall.workflow.setup` is the project setup's state machine and the one setup gate the machine scope's
onboarding decides. The machine is not configured until the first run of its onboarding has reached
`onboard.completed`; while it has not, no plan, an epic, or a project onboarding starts
(link:../../../doc/specification/workflow-dsl/01-grammar.adoc#machine-scope[Workflow DSL § Machine Scope], item 6;
link:../../../doc/specification/workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL § Waiting for the
Operator], item 6).

== Main Types

`MachineOnboarding`:: The onboarding as the gate reads it from the machine scope's `WorkflowStatus`. It is complete when
the status rests in `onboard.completed`, or when the `onboard_run` member says `reconfigure`: a later run of one aspect
is entered from the machine's settings and is only possible after the first run. Its `pendingSteps` are the steps of the
`onboard_steps` member whose state is neither `done` nor `skipped`, in their order, and `missingStep()` names the first
as an `Optional<String>` (empty when no step is pending); `fromStatus` refuses a status of another scope and an `onboard_steps` member that is not the array of step objects the`fromStatus` refuses a status of another scope and an `onboard_steps` member that is not the array of step objects the
schema admits (link:../../../doc/specification/store-schemas/02-workflow-state-store.adoc[Store Schemas § Workflow State
Store]).

`SetupGate`:: The one guard. `decide(act, onboarding)` admits a step of the onboarding itself and an operator verb in
every state; every start (`START_PLAN`, `START_EPIC`, `START_PROJECT_ONBOARDING`) is refused `machine_not_onboarded`
while the first run is incomplete. `decideStep(step, onboarding)` refuses an act over the local API that needs a step
that is still pending with `onboarding_incomplete` and the HTTP status `409`; an act whose step is done is admitted even
while another step is pending. A refusal names the step and both of the operator's clients, `web` and `cli`, where the
onboarding goes on.

A caller that finds no machine status passes no `WorkflowStatus`; it treats the onboarding as incomplete — no step is
`done`, and the missing step is the entry state of the machine unit — and lets the gate refuse the start. The gate does
not invent a status.

`ProjectOnboardingStart`:: The start of a project's onboarding, as `project.checkout` reaches it
(link:../../../doc/specification/state-catalogue/15-project-onboarding.adoc#state-catalogue-project-onboarding[State
Catalogue § Project Onboarding]). `start(onboarding, inspection)` asks `SetupGate.decide` first and answers a
`MachineNotOnboarded` with the gate's reason, status, missing step and clients, or, once the machine is onboarded, the
checkout inspection's own `CheckoutRefused` (`enrolment_root_conflict` among its reasons) or `Admitted`. The inspection
is a functional interface, so the call site owns what it reads; the gate is consulted before it runs
(link:../adr/workflow-setup/002-the-start-consults-the-gate-before-the-checkout.adoc[ADR 002]).

`SetupRunDerivation`:: The `setup_run` a setup call records at `setup.entry`
(link:../../../doc/specification/state-catalogue/06-setup-epic-other.adoc#state-catalogue-setup[State Catalogue § Project
Setup]). `derive(entry, configDirectoryPresent, recorded)` takes the entry the caller named — one value of `SetupRun`,
where `integrations` is an entry that derives `FIRST_RUN` and is never a recorded run — and keeps the run an interrupted
call already recorded; otherwise an `integrations` entry continues the first run, a primary checkout without
`.marshall/config/` is a first run, an `aspect` entry is that one aspect, and every other call reconciles. The four
entries (`SetupRun`) and the six aspects (`SetupAspect`) are closed lists of `core.config`, so the names exist once
(link:../adr/workflow-setup/003-the-setup-run-is-derived-from-server-facts.adoc[ADR 003]).

== Invariants

* *Admission is read, never assumed*: only `onboard.completed` or a reconfigure run opens the gate; an absent or `null`
  step list names the current state as the missing step. A present list that is not an array of step objects is refused
  as unreadable.
* *The onboarding and the operator stay open*: an incomplete first run never refuses the onboarding's own steps or an
  operator verb.
* *One status, one scope*: `MachineOnboarding.fromStatus` refuses a status that is not the machine scope's.
* *No time limit, no fallback*: the gate itself decides nothing by time; it is re-read on every act.
* *The machine's guard comes before the checkout*: `ProjectOnboardingStart` consults the gate first, so a refusal of the
  machine cannot be masked by anything the requested checkout would have answered, and an unreadable checkout is never
  touched while the machine is still being onboarded.
* *The recorded run wins*: a `setup_run` already recorded is never re-derived, so an interrupted first run whose
  `.marshall/config/` already exists stays a first run rather than turning into a reconcile.

== Failure Modes

[cols="2,3"]
|===
|Failure |Behaviour

|The machine status does not exist
|The onboarding is not complete; a start is refused `machine_not_onboarded`, naming the current state and both clients.

|`onboard_steps` is not an array of step objects
|`MachineOnboarding.fromStatus` refuses the status with `IllegalArgumentException`; the caller reports an unreadable
machine state rather than admitting a start.

|A later run of one aspect is in progress
|The gate stays open: the status carries `reconfigure`, and every start and act is admitted.

|The machine is onboarded and the requested checkout is refused
|`ProjectOnboardingStart` answers `CheckoutRefused` with the inspection's reason (for example
`enrolment_root_conflict`) and its detail, and opens no entry.
|===
