= ADR 001: Static Verifier Remaining Rules Architecture and Boundary Design
:nofooter:

== Status

Accepted

== Date

2026-10-12

== Context

Work package `static-verifier-remaining-rules` (Roadmap Milestone 3, PLAN-41) implements the static AST verification checks left open by `static-verifier-and-fuzzer` (PLAN-10):
Rules 1, 2, 3, 4, 6, 7, 8, 9, 10, 11 (11a, 11b), and 12.

Key architectural questions addressed in this package:
1. How should external entity kinds, question classes, and schemas be resolved during static verification without coupling `WorkflowValidator` to runtime containers?
2. How should sub-workflow calls (Rules 6 and 7) be checked across units for acyclicity, depth limits ($\le 4$), and parameter/result binding contracts?
3. How should cycle awaited-event detection (Rule 11) distinguish between automated infinite loops (engine-chained) and interactive or asynchronous workflow states?
4. How should violations be attributed and ordered to guarantee deterministic test assertions and negative control matching?

== Decision

1. **Immutable Registries**:
We introduced immutable registries (`EntityKindRegistry`, `QuestionClassRegistry`, and `SchemaRegistry`) configured with specification defaults via `.defaults()` and extensible via `.with(...)`. This separates parser syntax validation from static verifier type-binding checks and allows test suites to inject mock or unregistered items cleanly.
(Superseded by link:005-rule-6-stepped-out-and-registries.adoc[ADR 005]: the shipped defaults carried placeholder entity units and missed the `ask` question class; the corrected defaults are recorded there.)

2. **Workflow Catalog for Call Graphs**:
We introduced `WorkflowCatalog`, an immutable catalog of parsed sub-workflow definitions. `WorkflowValidator` queries `WorkflowCatalog` to:
- Verify sub-workflow existence and parameter type compatibility (Rule 6).
- Ensure routing of `done` and `stepped_out` terminal outcomes (Rule 6).
(Superseded by link:005-rule-6-stepped-out-and-registries.adoc[ADR 005]: `stepped_out` belongs to the exit contract only where the callee can return it through a resting-link implicit `step_out` exit.)
- Traverse the call graph to verify acyclicity and maximum nesting depth of 4 (Rule 7).
- Verify that called sub-workflows do not declare resting links when invoked from plan or epic workflows (Rule 10).

3. **Classification of Awaited Events in Cycles**:
Rule 11 separates:
- **Engine-chained cycles (Rule 11a)**: Cycles consisting exclusively of automatic execution steps (`AutoStep`, `SubWorkflowCall`). These require an explicit decreasing `cycleMeasure` to ensure termination.
- **Resting cycles (Rule 11b)**: Cycles passing through states that halt engine execution awaiting external events (`InteractiveLinks` waiting for client/user action, `QuestionWait` waiting for operator answers, `JobStep` waiting for job settlement, `ModelJob` waiting for task completion). These naturally pause execution and satisfy the awaited event constraint.
(Superseded by link:003-rule-11b-per-link-awaited-event.adoc[ADR 003]: satisfaction is decided per traversed link, not per state; a `NOOP` self-loop with no external wait does not satisfy the cycle.)

4. **Deterministic Diagnostic Attribution**:
Violations are created with precise `SourceLocation` tokens:
- Transition-specific defects (unreachable target, invalid outcome, abort terminal target, invalid parameter) point to the transition or link clause line.
- State-wide defects (missing return-evaluation outcomes, state ID collisions, DAG cycle roots) point to the state declaration line.
- Sub-workflow result schema violations point to the workflow header location.
All violations are ordered first by state appearance in the AST, then by `VerificationRule` enum definition order.

== Alternatives Considered

1. **Deferring Sub-Workflow Graph Checks to Engine Launch**:
Deferred validation would simplify the verifier by checking sub-workflows only when called at runtime.
*Rejected*: The specification strictly mandates that structural call cycles, invalid depth, and contract mismatches must be caught ahead of execution.

2. **Hardcoding Entity Kinds and Question Classes in the Validator**:
Hardcoding could avoid registry classes.
*Rejected*: Inflexible; prevents domain extensions and project-specific question or entity models from registering their types.

3. **Treating All Links as Non-Awaiting**:
Assuming links do not await events unless they have a `SUBMIT` form.
*Rejected*: In workspace workflows, resting link states halt the engine awaiting external user/client interaction. Treating them as non-awaiting incorrectly flagged valid interactive loops as infinite CPU spins.

== Consequences

* Complete coverage of Rules 1 through 12 in `WorkflowValidator` with 27 discrete `VerificationRule` constants.
(Superseded by link:002-rule-9-firing-model.adoc[ADR 002], link:003-rule-11b-per-link-awaited-event.adoc[ADR 003], link:004-rule-3-configuration-reachability.adoc[ADR 004], and link:005-rule-6-stepped-out-and-registries.adoc[ADR 005]: PLAN-41 shipped the rule slices with gaps — the once-per-firing model with the unconditional `SUCCESS` fallback, per-state awaited events, the vacuous transition-level configuration check, the unconditional `stepped_out` contract with placeholder registry units and the missing `ask` class. This plan closes them; the rule count is unchanged.)
* Pure static analysis: no runtime side-effects or network dependencies.
* Robust negative testing: every added check has a dedicated refusing fixture verified against an exact rule, state, and source line.
* Clear integration seam for `project-units-and-invariants` (Milestone 3) and `workflow-engine` (Milestone 4).
