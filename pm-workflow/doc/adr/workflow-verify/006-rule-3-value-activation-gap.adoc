= ADR 006: Rule 3 Configuration Reachability Is a Seam
:nofooter:

== Status

Accepted. Rewritten by the work package `static-verifier-residuals`: the Boolean enumeration with all-keys-true activation that this record kept in PLAN-54 is removed (link:004-rule-3-configuration-reachability.adoc[ADR 004]), so Rule 3 configuration reachability as a whole is the seam. It closes when the specification states how a configuration value activates a guard.

== Date

2026-10-14

== Context

The specification (Workflow DSL, § Static AST Verification Rules, Rule 3) checks reachability for every combination of the values of the configuration keys the unit's guards declare in `depends_on_config`: every enum value, `true` and `false` for a boolean. A state or outcome transition that no combination reaches fails validation; one that some combinations do not reach is reported with those combinations.

The specification gives each key its domain (enum or boolean) but no rule by which a value makes a guard true, and the grammar's `depends_on_config` clause names keys only, never a value a link needs. Without that rule the verifier cannot tell under which values a link is active: a unit with a link that needs `mode=strict` followed by a link that needs `mode=lenient` (the case in which no combination reaches the second link's transition) cannot even be written. The all-keys-true activation the verifier used instead could refuse nothing, and it was removed (link:004-rule-3-configuration-reachability.adoc[ADR 004]).

== Decision

1. Rule 3 configuration reachability is a named seam, not checked and not claimed: the enumeration of the values of a `depends_on_config` key, the rule by which a value activates a guard, the report of a state or transition that some combinations do not reach, and the refusal of a state or transition no combination reaches, with its refusing fixture (a link needing `mode=strict` followed by a link needing `mode=lenient`).
2. The gap is raised with the specification as the issue https://github.com/plan-marshall/plan-marshall-documentation/issues/71["define how a `depends_on_config` value activates a guard"] in the repository `plan-marshall-documentation` (§ Source).
3. The check is written when the specification answers the issue, against the rule it states.

== Alternatives Considered

1. **Inventing an activation rule** (for example: a link is active for every value of its keys, or the key name encodes the value):
The enumeration of enum values could be written today.
*Rejected*: the verifier would check a rule the specification does not state and refuse or admit units by it; the verifier checks the specification, it does not refine it.

2. **Extending the grammar with a value per key** (`depends_on_config mode=strict`):
The value a link needs would be in the unit.
*Rejected*: a grammar change is a specification change; it belongs in `plan-marshall-documentation` first, and the filed issue asks for it.

3. **Keeping the Boolean enumeration until the issue is answered (PLAN-54)**:
*Rejected*: under all-keys-true activation the check refuses nothing and its advisories rest on the invented activation (link:004-rule-3-configuration-reachability.adoc[ADR 004]).

== Consequences

* `VerificationRule` has no configuration-reachability constant, and `UnitGraph` no configuration substrate.
* The checklist of `WorkflowValidatorTest` lists configuration reachability as a seam with this ADR.
* The package files `doc/plans/static-verifier-rule-gaps.adoc` and `doc/plans/static-verifier-residuals.adoc` name this seam; the developer guide names it with this ADR.
