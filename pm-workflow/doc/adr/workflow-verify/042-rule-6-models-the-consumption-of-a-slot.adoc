= ADR workflow-verify 042: Rule 6 Models the Consumption of a Slot
:nofooter:

== Status

Accepted

== Date

2026-11-21

== Context

The bind removes a slot from the status at the first read (ADR `workflow-input/003`), so a second read of the same slot can
only fail at run time with `precondition_unmet` / `input_unbound`. Rule 6 proved only that every path to a read passes a
state that fills the slot; it did not count the reads. A unit that fills a slot once and reads it from two calls, or binds
one slot to two inputs of one call, verified and then failed on the second read — a unit the verifier declared sound and
the engine refused. The analysis of `PLAN-V2-157` found the shape (`a = slot.m, b = slot.m`) and left it to this plan.

== Decision

* Rule 6 records, per slot, every state that reads it. The unit is refused when one state reads the same slot twice, and
  when for any ordered pair of distinct reading states `R` and `S` a path from `R` to `S` passes no filling state: the
  read at `S` would find the value `R` consumed.
* The check is pairwise and order-independent: the declaration order of the states does not matter, and a fill between the
  first and the last read of a slot does not serve a read in between. `dominatedByAny` started from `R` is the walk; the
  number of reads of a slot is small, so the pairwise form costs nothing measurable.
* The dominance check stays: consumption says a slot is read once, dominance says it is filled before that read.

== Alternatives Considered

* *Leave it to the run time.* Refused: the run-time refusal is a safety net for a unit the verifier never saw, and a
  verified unit that fails its first call is exactly the defect this plan closes.
* *Count every read and compare the neighbours in declaration order.* Refused: a fill between the first and the last read
  of a slot does not serve a read in between, and two states declared out of flow order would compare in the harmless
  direction only. The pairwise, order-independent form refuses exactly a read no fill can serve.
* *Count every read of a slot, whatever the fills.* Refused: a slot a unit refills between two reads is served by the
  refill, so a bare count would refuse a sound unit.
* *Model the consumption as part of the dominance graph (a read removes an edge).* Refused: the graph carries no state
  values, a per-read reachability pass per call would multiply the cost measured in ADR 039, and the count is exact where
  a graph trick is an approximation.
* *Refuse only a second read inside one call.* Refused: a slot read by two calls is the identical hazard, and the
  run-time failure is the same.

== Consequences

* `WorkflowValidatorTest § Slot consumption` pins the shapes: the two-calls read, the two inputs of one call, the refilled
  slot that verifies, two fills that do not separate two reads on one path, a pair whose states are declared out of flow
  order, and a third read whose fill lies on one branch only; `verify/passing/slots-and-inputs.pmwf` stays the matched
  control (one fill, one read), and the default plan unit and the compiled invariants are unchanged.
* A unit that wants two calls to use the same text fills two slots, or the callers take the value as an input.
