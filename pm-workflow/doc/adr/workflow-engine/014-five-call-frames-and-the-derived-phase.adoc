= ADR 014: Five Call Frames, and the Phase Derived from the Stack
:nofooter:

== Status

Accepted

== Date

2026-10-28

== Context

The engine admitted at most four call frames (`CallStack.MAX_DEPTH`, `WorkflowStatus.MAX_CALL_DEPTH` and the depth
rule of `VerificationRule.CALL_GRAPH_DAG`). The flat plan unit was the root frame, so a plan that called a
sub-workflow that called a sub-workflow had three frames left. With the phases as sub-workflows the phase level adds
one frame to every call path, so the same plan needs one frame more.

== Decision

* The limit is five in every place that states it: `WorkflowStatus.MAX_CALL_DEPTH`, `CallStack.MAX_DEPTH` and its
  push, and the verifier's depth rule in `WorkflowValidator` / `VerificationRule.CALL_GRAPH_DAG`. A fifth frame is
  admitted and a sixth refused, statically and at run time alike.
* The phase of a status is derived, in this order, from the phase unit on the call stack, the phase unit of the
  current unit, the plan unit's call state `phases.<name>`, and the state identifier's prefix in a flat unit; an ended
  status whose phase already matches is returned unchanged.
* `CallFrame` carries no caller phase (ADR workflow-ast 003).

== Alternatives Considered

1. *Keep four frames and let a phase be unrepresented on the stack.* Rejected: the phase is the unit on the stack, so
  without its frame a nested call could not report its phase.

== Consequences

Every call path gains one frame; a unit nested deeper than five frames is refused by the verifier and by the push.
The status codec and the store record the same limit and no caller phase, so a status written before this change
read by a path that encodes the phase would disagree; nothing is released and the format stays 1 (R13).
