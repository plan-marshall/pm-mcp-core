= ADR 008: The Provider, Footprint and Change-Type Rules Prune Derived Targets
:nofooter:

== Status

Accepted

== Date

2026-10-14

== Context

The specification named four rule families, posture aside, by their prune reasons (`provider_unconfigured`, `footprint_disjoint`, `change_type_exempt`, `recipe_override`) without stating which facts they read or which elements they prune.
The step catalogue marks `default:finalize-step-simplify` and `default:adr-propose` as the steps of the lane class `prunable (no_code_delta)`; `default:analysis-roundtrip` needs an analysis provider.
The rule language reads one fact per rule, and Sonar is the only analysis adapter shipped.

The fourth family left the specification afterwards: the simplify recipe is a workflow of its own (`recipe-workflows`), so the prune reason `recipe_override` left the `prune_reason` enumeration of the header schema, and with it the plan fact `recipe_id`.
The same alignment replaced the configuration fact `merge.auto_merge` by the `self_merge` declaration of the bound asking variant (ADR link:015-axis-levels-and-overrides-carried-in-plan-facts.adoc[015]).

== Decision

The shipped rule file carries one rule per family, with targets derived from the catalogue:

* `analysis-provider-unconfigured`: `integrations.sonar` unset prunes `default:analysis-roundtrip` (`provider_unconfigured`).
* `no-code-delta`: a `footprint` disjoint from the code and build globs prunes `default:finalize-step-simplify` and `default:adr-propose` (`footprint_disjoint`); an empty or unknown footprint keeps them.
* `report-change-type`: `change_type` in `analysis`, `verification` prunes `default:finalize-step-simplify` (`change_type_exempt`).

No family prunes a floor-immune step. The specification is corrected to state exactly these targets.
The file holds no rule over `recipe_id` or `merge.auto_merge`; `CompositionRules` refuses a rule over either, because neither is a registered fact any more.

== Alternatives Considered

1. *Leave the families without rules until the specification names targets.*
_Rejected_ by the operator: the reasons exist in the header schema, and the targets follow from the catalogue.
2. *A provider rule per configured provider, or over a derived list of providers.*
_Rejected_ for this slice: the rule language reads one fact per rule, and Sonar is the only adapter.

== Consequences

* The provider rule reads only `integrations.sonar`. A second analysis adapter needs either a derived fact (the configured analysis providers) or a conjunction in the rule language before its own rule can be added.
* Several rules can prune `default:finalize-step-simplify`; the composer lists it once, with the reason of the first rule in file order.
* A composer test that expects no prune must set `integrations.sonar`.
