= ADR 021: The Landing Variant Is Checked Where the Composition Binds It
:nofooter:

== Status

Accepted; amended 2026-11-21 (PLAN-V2-163, carried item 36(a)): the check belongs to the start of a plan only

== Date

2026-11-16 (amended 2026-11-21)

== Context

Workflow DSL § Plan Behaviour Axes, item 3 asks that a landing variant be validated where a project is known — the
project's setup, a plan's start, a plan's settings — refusing `landing.pull-request` without a provider of the project and
`landing.main` on a base branch the provider reports as protected, each with the reason. The machine's own check exists
(`MachineDefaultsValidation` of `runtime.config`) and never reads a repository.

The plan instance's composition is where a plan's start and a later `override` bind the axis; a plan's settings are the
same event, since a changed value composes a new version. The alternative was a validator that the setup and settings code
calls on its own, leaving the composition free to bind a variant no check had seen.

== Decision

* `LandingVariantValidation` is a pure check in `workflow.plan`: it takes the variant and a `Project` value (a pull-request
  provider, a protected base branch) and answers a verdict with the reason.
* `PlanInstanceComposer` gains `compose(request, project)`: for the `start` composition it validates the *bound* landing
  variant before composing and refuses the version with `invariant_failed` and the reason in its violation line.
  `compose(request)` keeps its signature and composes without the check, for a caller with no project known.
* *Amendment of 2026-11-21:* the check belongs to the start of a plan only. Every later composition of a running plan
  (`outline`, `plan`, `config_adopted`, `waiver`, `override`, `fallback`, `empty_harvest`, `replan`) skips it and keeps
  the variant the start admitted. As
  first decided, every event but the post-run-only `fallback` and `empty_harvest` was checked, so a waiver or a replan
  of a running plan was refused with `invariant_failed` once its base branch had become protected after the plan began:
  a fact of the project that changed under the plan blocked work the plan had already been admitted to do.
* The `Project` value is passed per call, not stored in `CompositionRequest`: the record's facts stay the values the
  composition reads, and a request built by a caller without a project is unchanged.
* The check does not decide which level set the variant: the reason names the variant, and a machine default that does not
  fit the project is refused for that project at its start. The project's setup and the plan's settings surfaces are the
  server assembly's: this module delivers the check and the composition call site, and the landing names those call sites
  owed.

== Alternatives Considered

1. *A new `refusal` value (`landing_not_fit`) in the composition log.* _Not taken_: the log's `refusal` is a closed enum of
   the store schema (`position_not_contained`, `invariant_failed`); a new value would change the schema and every reader
   for a validation the composer already reports as a violation line.
2. *A component on `CompositionRequest`.* _Not taken_: the record is constructed positionally by several callers; an
   optional component there would either break them or become a second, silently-nullable input path for a value that is
   the caller's knowledge, not the plan's fact.
3. *Validating only in the setup and settings code.* _Not taken_: the composition would then bind a variant no check had
   seen whenever a caller forgot the call, which is the fail-open path this item exists to close.
4. *Checking every composition of a running plan* (the first form of this decision). _Not taken_ since the amendment: a
   later branch protection would refuse a waiver or a replan of a plan whose landing the start had admitted.

== Consequences

* A caller that knows the project passes it; a plan start whose bound landing variant does not fit is refused before a
  version is written, and its reason names the variant and the missing provider or the protected branch.
* An `override` that binds a new landing variant to a running plan is not landing-checked by the composition; a caller
  that changes the landing of a running plan validates the new variant itself.
* The composer stays a value in, value out: the check reads no store and writes nothing.
* `LandingVariantValidationTest` holds the table of variants; `PlanInstanceComposerTest` holds the refusal, the control
  that a fitting project composes the same text as no project at all, the `landing.main` refusal on a protected branch
  at the start, and the waiver and replan compositions of a running plan that a later protection does not refuse.
