= ADR 003: Versions and the Composition Log Are Written Over the Plan's `ScopeTransaction`
:nofooter:

== Status

Accepted

== Date

2026-10-14

== Context

The versions of an instance live in `plans/<plan_id>/instance/plan.v<N>.pmwf`, never rewritten, and every composition attempt appends one line to `instance/composition.jsonl`.
A server event composes its version in the transaction that enters the target state, so the version, its log line and the state change must commit together.
`pm-core` already provides the `ScopeTransaction` of a plan scope, with its digest sidecar.

== Decision

* `PlanInstanceStore` lives in `workflow.plan` and is constructed with the `JournalScope` of a plan; it refuses any other scope type.
* It writes only through a `ScopeTransaction` the caller holds and commits: `recordComposed` stages the version file, the sub-unit texts and the log line, `recordAttempt` the log line alone. `pm-core` is not changed.
* A version file that exists already is refused with `IllegalStateException` before anything is staged, so a version number is checked again where it is written.
* The store creates `instance/` and `mcp/units/` before staging, because the transaction writes into existing directories.

== Alternatives Considered

1. *A store type in `pm-core`.*
_Rejected_: the instance is a concept of the workflow; `pm-core` would have to know the version and log formats, and the transaction already covers what the store needs.
2. *A transaction of the store's own.*
_Rejected_: the version would commit apart from the state change of the server event that composed it.

== Consequences

* The digest sidecar of the plan covers every file the store writes through the commit.
* The plan lock makes the caller's transaction the only writer of the scope.
* A caller that writes a version must open and commit the plan transaction; the store never commits.
