= ADR 001: The Automatic Run's Vocabulary and Its Router
:nofooter:

== Status

Accepted

== Date

2026-11-16

== Context

CLI & Security § Automatic Onboarding defines `auto.result`: one item per value the run decided, each with the aspect, the
key, the value, a reason from a closed list and the check line that confirmed it; the items the run could not decide are
those the operator was asked. State Catalogue § Machine Onboarding defines who walks the aspects: the first run and the
automatic run take them in a fixed order, a `change` on the result calls one aspect as a later run
(`onboard_run: reconfigure`) and its return leads back to the result, and a later run opened from the settings returns
there.

The units (`onboarding.pmwf`, the aspect sub-workflows, `auto.consent`, `auto.result`) are resources of
`plan-marshall-mcp`. `pm-workflow` held no vocabulary for a proposal or a result, so nothing in this repository could state
what the run decided or where it goes next.

== Decision

* The new package `workflow.onboarding` carries the engine half:
  `OnboardingAspect` (the closed list in the fixed order), `OnboardRun` (`first_run`, `auto`, `reconfigure`),
  `ProposalReason` (the closed reason list with its `onboard.auto.reason.<reason>` message key),
  `OnboardingProposal` (the item) and `AutoOnboardingResult` (the decided values and the items that were asked).
* `OnboardingRouter` answers the routing as a value: `returned(run, aspect, openedFrom)` names the next aspect or the state
  the run ends in, and `change(result, aspect)` opens one aspect as a later run. A later run must name where it was opened
  from, because only that decides whether it returns to the settings or to the result; the run value alone cannot carry it.
* `change` refuses an aspect the result carries no item of: a change needs a value to change, and a result that never
  recorded the aspect is a defect of the run, not an empty change.
* The router reads no store and writes nothing; the units that emit the routes are the assembly's.

== Alternatives Considered

1. *A wider run enum (`RECONFIGURE_FROM_SETTINGS`, `RECONFIGURE_FROM_RESULT`).* _Not taken_: `onboard_run` is a closed list
   of the specification; adding values would change the DSL for a fact that belongs to the call stack, not the run.
2. *Putting the vocabulary in `pm-core` beside the stores.* _Not taken_: it is not a store value; it is the shape of a
   workflow's result, and `pm-workflow` is where workflow results live.
3. *Leaving the routing to the units.* _Not taken_: the routing is the one part of the run that is deterministic and
   provable here; leaving it in `plan-marshall-mcp` would leave the branches untestable in this repository.

== Consequences

* The automatic run's result and the change-on-result path are provable over fixtures here
  (`OnboardingResultTest`, `OnboardingContractReplayTest`), and the units are named owed.
* A result item with reason `asked` is the only undecided item; every other reason is a decision the run made.
