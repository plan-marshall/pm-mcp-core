= ADR 003: The Asking Task Records the Consultation Before the Consultation Task Is Created
:nofooter:

== Status

Accepted.

== Date

2026-10-24

== Context

Following a `consult:<role>` link creates a queue task of the consulted role and records the consultation on the asking
task in the same transition (`model-work/05-consultation.adoc#consult-link`). The queue task record of the asking task
carries the consultation entry, the consultation task names the asking task in `consultation_of`, and both live in one
`QueueStore`. `QueueStore.updateAll` revises the records that exist and keeps their count and ids; it cannot add a
record. Adding a record is `QueueStore.create`, which takes the queue lock in its own transaction.

The two writes can be ordered in only these ways: record the entry first, create the task second; create the task
first, record the entry second; or widen `QueueStore.updateAll` to add records.

== Decision

`ConsultationService.open` validates the ask, draws the consultation id, records the entry on the asking task and moves
it to `consulting` in one `QueueStore.updateAll` transaction, then creates the consultation task with
`QueueStore.create`. When the task cannot be created, the failure propagates; the open entry is settled `unavailable`
by `ConsultationService.reconcile` after the creation grace the caller passes. A consultation task therefore never
exists before its asking task lists it, and a worker can never be offered a consultation the asker does not know.

`QueueStore.updateAll` is not widened: the queue store is `core.queue`'s, its write discipline is specified in
`store-schemas/16-task-queue.adoc`, and this package owns no part of it.

== Alternatives Considered

1. *Create the task first, then record the entry.*
   _Rejected_: a worker of the consulted role can be offered the task in the window, answers it, and finds an asking
   task that does not carry the consultation. Its answer is then refused, and closing the created task on a refused
   transition would revoke a lease a live worker holds.
2. *Widen `QueueStore.updateAll` to add records.*
   _Rejected_: it changes the shared queue store's write contract for one caller and moves the id-allocation decision
   into the revision callback.
3. *Create the task inside the same lock transaction by a second store.*
   _Rejected_: it duplicates the queue lock and the record write.

== Consequences

* A worker is only ever offered a consultation its asking task lists.
* A crash between the two writes leaves an asking task in `consulting` with an open consultation whose task does not
  exist. `ConsultationService.reconcile` settles it `unavailable` once the entry is older than the creation grace, so
  the asking task continues on its own judgment; a consultation task the protocol closed without an answer is repaired
  the same way.
* A create failure propagates; the entry it left is settled `unavailable` by `reconcile` after the creation grace the
  caller passes.
