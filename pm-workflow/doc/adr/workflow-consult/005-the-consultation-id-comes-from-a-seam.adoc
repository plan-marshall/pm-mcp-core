= ADR 005: The Consultation Id Comes From a Seam
:nofooter:

== Status

Accepted; amended 2026-11-22 (PLAN-V2-170): the free-id check moved into the transaction that records the consultation
and counts recorded consultation ids, and the draw is bounded by `MAX_ID_DRAWS` with the refusal
`consultation_ids_exhausted`.

== Date

2026-11-21

== Context

`ConsultationService.open` names the consultation task by an id it draws itself, and that id is the
`consultation_id` the asking task's submit must list. The service drew it from `QueueTaskId.random()`, so a
consultation of the scenario replay harness got a different id on every replay: no two replays of one scenario wrote
byte-identical stores, and a scenario script could not name the id in `worker_do submit:change {consultation_ids: …}`.
The accepted-submit half of regression scenario 14 therefore ran as a direct `validateSubmit` call in
`ScenarioReplayRunnerTest`, outside every script (PLAN-V2-163, carried item 33(a)).

== Decision

* `ConsultationService` takes the source of its consultation ids as a `Supplier<QueueTaskId>` in a second constructor.
  The one-argument constructor keeps `QueueTaskId::random`, so production draws its ids as before.
* A drawn id the queue already holds is skipped and the next one is drawn, as for the random source. The check runs in
  the same transaction that records the consultation, and counts a consultation id any asking task records as taken
  whether or not its consultation task exists yet, so two opens that draw the same id cannot both record it; the draw
  therefore runs under the queue lock. After
  `ConsultationService.MAX_ID_DRAWS` (`64`) taken draws in a row the open is refused `consultation_ids_exhausted`
  instead of spinning: a seam that cannot yield a free id is a stuck source, not a reason to loop (PLAN-V2-170).
* The scenario replay harness passes a counter of its fixtures that hands out `qt-c000000000000001`,
  `qt-c000000000000002`, … in order, a range apart from the counter of the other queue tasks, so a script names the id
  its submit lists and the replay writes the same stores every time.

== Alternatives Considered

1. *A counter inside the service.* Not taken: production ids stay random, so the counter would be a test switch in
   production code; the supplier keeps one code path and lets the harness choose.
2. *Seed the random source.* Not taken: `QueueTaskId.random()` is shared by every queue task, and a seed would make the
   ids of other tasks depend on the order of the replay as well.
3. *Keep the direct `validateSubmit` call.* Not taken: no passing script would hold scenario 14, and a replay of a
   consultation scenario would stay non-reproducible.

== Consequences

* A consultation scenario replays to byte-identical stores, and its accepted submit passes through the replay.
* The id rule of the record is unchanged: a consultation's `queue_task_id` is its `consultation_id`.
* `ScenarioReplayRunnerTest` replays scenario 14 twice and compares the stores.
