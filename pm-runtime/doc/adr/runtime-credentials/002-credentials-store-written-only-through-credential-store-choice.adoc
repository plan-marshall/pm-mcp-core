= ADR 002: `credentials.store` Is Written Only Through `CredentialStoreChoice`
:nofooter:

== Status

Accepted

== Date

2026-10-17

== Context

`credentials.store` of `machine-config.json` is aspect-owned: the specification lets only the credential-store aspect
of the machine's onboarding and the store move write it, and refuses every other writer with `aspect_owned`. Other
writers of the same file exist (the plain configuration endpoint among them) and race on its read-modify-write. The
work package also had to decide how the two refusals that are not failures of a store, `onboarding_incomplete` and
`aspect_owned`, are thrown: as new reasons of `SecretStoreException` or as an exception of their own (question q2 of
the work package).

== Decision

* Only `CredentialStoreChoice` writes the key, through its two `record` methods: `record(transaction, store, writer)`
  for the switch of the move, and `record(locks, user, store)` for the credential-store aspect, which carries the
  integrity key at the first recording (ADR 006). The writer is a closed enum, `CredentialStoreChoice.Writer`
  (`CREDENTIAL_STORE_ASPECT`, `STORE_MOVE`, `OTHER_CONFIGURATION`); a writer that does not own the key is refused with
  `aspect_owned` before anything is acquired, and while a move is open every writer but the move is refused with
  `aspect_owned` as well, while the move records only while its record exists (ADR 004).
* The write runs under `locks/machine-config.lock`, taken after `locks/credentials.lock`: the document is re-read
  inside the lock, every other member kept, `revision` incremented and the file replaced in one atomic write; an
  absent document is created with the required keys at their schema defaults.
* The two refusals are the nested `CredentialStoreChoice.Refusal` with its own `Reason` (`ONBOARDING_INCOMPLETE`,
  `ASPECT_OWNED`), so that `SecretStoreException.Reason` stays a failure of a store. `credential_store_unavailable`
  is a failure of a store and became the reason `UNAVAILABLE` of `SecretStoreException`.
* Either store, recorded or not, is given by the package-private `CredentialStoreChoice.backendOf(Store)`, which the
  move and the first recording use.

Rationale not recorded beyond keeping `SecretStoreException.Reason` a failure of the store.

== Alternatives Considered

* The reasons `ONBOARDING_INCOMPLETE` and `ASPECT_OWNED` on `SecretStoreException.Reason`: not taken, since a caller
  that maps a store failure to its error code would meet requests that never reached a store.

== Consequences

* No class but `CredentialStoreChoice` writes `credentials.store`; a new writer of `machine-config.json` uses
  `Writer.OTHER_CONFIGURATION` and is refused for the key.
* A caller catches `CredentialStoreChoice.Refusal` and `SecretStoreException` apart and maps each to its own code.
* The `423` mapping of `credential_store_locked` and the endpoint refusal stay with the assembly.
