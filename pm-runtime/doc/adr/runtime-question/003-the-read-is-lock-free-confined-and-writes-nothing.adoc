= ADR 003: The Read Is Lock-Free, Writes Nothing and Is Confined
:nofooter:

== Status

Accepted

== Date

2026-10-20

== Context

The question log is appended under the scope's lock, and an append may run while the engine asks for a record. The
settled design of the project paths (PM-SEC-2) confines every project path through `WorkspaceConfinement` and returns a
refusal as a `ConfinementOutcome`, never as an exception. The port's read has no failure mode: it answers `Unreadable`.

A read that took the scope lock would block the append, and the engine would wait on a lock it has no reason to hold.

== Decision

* The adapter calls `QuestionLog.read()`, the lock-free snapshot of the log. It takes no lock, creates no store, writes
  nothing and repairs nothing; a torn tail is reported, not cut.
* It passes the log path through a `WorkspaceConfinement` over the runtime base, the root of the project store. The
  public constructor builds that confinement itself, so a caller cannot hand the adapter the enrolled repository root
  (under which no question log lies); the package-private constructor that takes a confinement exists for the refusal
  tests only. `Rejected` is `Unreadable` with the outcome code `path_traversal_rejected` and the reason's wire name.
* Because reading through a link would follow a path the store refuses on its write side, the confined canonical path
  must equal the resolved store path; a difference is `Unreadable` with
  `the question log is not reached by its canonical path`.
* The base the constructor is given is canonicalized where it exists, so a symlinked ancestor of the runtime base does
  not turn every read into a refusal.

== Alternatives Considered

1. *Taking the scope lock for a consistent view.*
_Not taken_: it blocks every append for the duration of the read and violates the requirement that a read is a read.
The log is append-only and a snapshot sees the content before or after a write, never a part of one.

2. *Reading the confined canonical path through a second store class.*
_Not taken_: it would duplicate the codec, the line handling and the invariant checks of `QuestionLog` in `pm-runtime`,
and the adapter is specified to read over `QuestionLog`.

3. *Using the confined canonical path while `QuestionLog` reads the resolved path.*
_Not taken_: that is a check-then-act on two different paths; the path the check approved must be the path that is read
or the read must be refused.

4. *Passing the enrolled repository roots, as the other readers of `runtime.workspace` do.*
_Not taken_: the question store is no repository file — it lies in the per-project machine store below the runtime base
— so the repository roots would refuse every log, and the read would be dead in production. The adapter therefore fixes
the root to the runtime base and offers no public way to pass another.

== Consequences

* An append and a read never wait for each other.
* A read leaves the file tree of the scope exactly as it is; `QuestionLogRecordReaderReadTest` asserts names, sizes and
  modification times before and after.
* A log reached through a symbolic link is unreadable; the store is reachable by its real path, which is what the
  assembly configures.
* The confinement root is fixed by the constructor rather than supplied by the assembly: the question store is no
  repository file, so the enrolled repository root of `runtime.workspace`'s other readers is the wrong root here, and a
  wiring that could pass it would make every read unreadable.
