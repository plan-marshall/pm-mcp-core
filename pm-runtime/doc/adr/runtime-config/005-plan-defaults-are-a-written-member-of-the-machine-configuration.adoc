= ADR 005: Plan Defaults Are a Written Member of the Machine Configuration
:nofooter:

== Status

Accepted

== Date

2026-11-16

== Context

Store Schemas § Machine Configuration Store declares `plan_defaults` with the machine's variant of each plan behaviour
axis and an optional posture, and Workflow DSL § Plan Behaviour Axes, item 2 makes it the machine level of the axes.
`MachineConfigurationCodec` copied the member through untouched — deliberately, because the store owned only `providers`,
`sources.documents_mode` and `cleanup` — so nothing in this repository could write the machine's level, and the
composition's machine level had no reader of a value it could trust.

== Decision

* `PlanDefaults` is the typed value of the member: the three axis variants and the optional posture, each checked against
  the schema's closed list; `MachineConfigurationSchemaParityTest` reads the lists out of the schema and fails on drift.
* `MachineConfigurationCodec` now owns the member: it reads it (a member the document does not set takes the schema
  default), replaces it in one write, and keeps a partial member partial when another setting is written.
* `MachineConfigurationStore.writePlanDefaults(defaults, revision)` is the writer. It runs in the same transaction as the
  other members and answers a change against an older revision with `SettingsConflict` and the current defaults, so the
  first change wins and the second is refused — the rule the two existing writers already follow.
* The reader of the composition's machine level is `PlanAxisLevels` of `workflow.plan`, fed with the raw member. The store
  does not import the workflow module: the values travel as plain strings. The schema keeps the closed lists,
  `MachineConfigurationSchemaParityTest` holds the store to them, and `PlanFacts.Axis` keeps the axis vocabulary in the
  workflow module.

== Alternatives Considered

1. *A separate `plan-defaults.json` store.* _Not taken_: the schema declares the member in `machine-config.json`; a second
   document would split one operator act over two locks and two revisions.
2. *Reading `plan_defaults` pass-through and validating in the composition.* _Not taken_: a value the schema refuses would
   then be accepted by the store and refused much later, at a plan's start, with no writer to point at.
3. *Duplicating the variant lists in `pm-runtime` without a parity test.* _Not taken_: the schema is the closed contract;
   the parity test is what keeps the two lists one.

== Consequences

* The machine's level of every plan behaviour axis is writable and readable; a plan's composition can bind it.
* A partial `plan_defaults` member (for example only `posture`) reads at the schema defaults and survives another
  setting's write unchanged.
* `MachineSettingsWritersTest` holds the two-changes-against-one-revision case for the new writer.
