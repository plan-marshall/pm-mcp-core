= ADR 012: The icon sanitiser is an allow-list with compiled bounds
:nofooter:

== Status

Accepted.

== Date

2026-11-21.

== Context

A harness icon is fetched from the maker's server and stored in the machine's icon store, then served to both clients
from the runtime's own origin (Harness Profiles § Harness Icons; Store Schemas § Harness Icon Store). The bytes are
therefore untrusted input that a browser renders, so the accept step is a trust boundary (R09): an SVG can carry a
script, an event handler, a reference to another origin or a `data:` URL, and a PNG can carry free text beside its
pixels. The store also has to decide what "sanitised" means in a way a reviewer can check against a closed list, because
a deny-list of known attacks is only as good as the attacker's last idea.

== Decision

The accept step (`IconSanitiser`) refuses a candidate above `256` KiB, decides the media type from the bytes and never
from a file name, and hands the bytes to one of two sanitisers.

The SVG sanitiser (`SvgSanitiser`) is an **allow-list**. A closed list of elements is kept (`svg`, `g`, `title`, `desc`,
`defs`, `clipPath`, `mask`, the shape elements, the two gradients, `stop`, `pattern`, `image`, `text`, `tspan`); an
element outside it is refused. A closed list of attributes is kept; an attribute outside it is dropped. `script`,
`foreignObject` and `use` are refused by name before the allow-list is consulted. Every attribute whose name begins with
`on` is refused. Every `href` — either namespace — must be a fragment of the same document, so an external URL and a
`data:` URL are both refused. A `style` that contains `url(` or `@import` is refused, and every `url(...)` of any other
attribute must name a fragment. The document is parsed with the JDK's StAX reader configured without a DTD and without
external entities, and a document that declares a DOCTYPE is refused before the reader sees it, so no entity is ever
expanded. The rendered result is written in the SVG namespace, so it is the allow-list of the input and nothing else.

The PNG sanitiser (`PngSanitiser`) walks the chunks as the format defines them: the signature, an `IHDR` with a positive
size first, an `IEND` last, a checksum per chunk and no byte after the end. An unknown critical chunk is refused. The
text chunks (`tEXt`, `zTXt`, `iTXt`) are stripped; every other chunk is copied with its own checksum, so the image is
unchanged.

The accept step is bounded as a whole: `256` KiB per candidate, `64` elements of nesting and `5000` elements per
document, so a document cannot exhaust the runtime while it is rendered.

== Alternatives Considered

A deny-list of the attacks the review named was rejected: it is exactly the list of attacks already known, and an
allow-list states the surface that may be served instead, which is what the review and a later change can check.

Dropping an element outside the allow-list, rather than refusing the document, was rejected: an unknown element is a
shape this sanitiser does not understand, so a document that carries one is refused and the operator sees why, rather
than being served a silently different icon.

Using an XML or image library was rejected without an operator decision: the JDK's StAX reader and a chunk walk over the
already-bounded bytes do the work, and the plan adds no dependency.

Rendering the SVG with `XMLStreamWriter` was rejected in favour of the hand-written emitter: the emitter states the
namespace once, escapes every text and attribute value itself, and has no configuration of its own that a later change
could weaken.

Keeping the PNG's text chunks and refusing the image was rejected: the text is metadata the icon never needs, and
stripping it keeps a legitimate icon usable while guaranteeing that no free text reaches a client.

== Consequences

A candidate that is not on the allow-list is refused with the reason code that names the fault, and the store writes
nothing. A stored SVG contains only allow-listed elements and attributes, so a later review reads the list rather than
the input. The lists grow only with a decision recorded here: a new element or attribute is a change of this ADR.

The sanitiser opens no connection and never resolves a reference, so the outbound-call guard (`OutboundCallsArchTest`,
`runtime.guard`) stays as it is and its exemption map is not touched. The outbound fetch itself is deferred to the
profile that declares the `source` form; no shipped profile does, so the store stays empty and the monogram remains the
icon of every harness.

The bound and the two structural bounds are compiled constants. A harness whose icon is a richer SVG than the list
allows is shown by its monogram, which is a visible, benign outcome rather than a stored document the runtime cannot
reason about.
