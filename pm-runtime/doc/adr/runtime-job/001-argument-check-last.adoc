= ADR 001: The Argument Check Is the Last Stage of the Pipeline, and the Scope of Its Rules
:nofooter:

== Status

Accepted

== Date

2026-10-12

== Context

Work package `verify-not-resolve` (Roadmap Milestone 4) implements the verify-not-resolve pipeline of a job in `pm-runtime` package `runtime.job` (PM-EXEC-1, PM-EXEC-2).
The specification names the checks of the pipeline (enrolment, working directory, executable and digest, arguments) but leaves open in which order the argument check runs relative to the others.

The arguments are the part of a job a caller, and through the caller a model, controls most freely.
Looking at them early would mean parsing and matching caller-controlled input for a job whose executable is not yet known to be the enrolled one, and a refusal for an argument could hide that the executable itself was tampered with.

Three further questions were left open by the plan and settled during implementation:

1. The configuration specification (`domain-extensions/06-configuration.adoc`, Forbidden Free Flags) refuses the free flags `-D`, `-f`, `--file`, `-s`, `--settings`, `--init-script` "in canonical build jobs". The first implementation refused them in every caller-supplied argument of every job kind, so a host tool call such as `git status -sb` was refused.
2. How the short flags are matched: alone only, or with an attached value.
3. What a project script job does with its arguments: whether they are appended to the argument vector, and how a job whose `binding` differs from the script's enrolled binding is refused.

A fourth question came up in the review of the pull request: a `HostToolCall` can name an enrolled interpreter, for example `python3` with `-c <code>`.
Stage 2 checks only the path and digest of the host tool, the binding and the argument schema apply only to a `ProjectScriptCall`, and the forbidden free flags only to canonical build jobs, so arbitrary code a caller supplies would run through a verified interpreter.

A fifth question came up in the same review (ReDoS): `ArgumentSchemaValidator` matches an enrolled `pattern`, a Java regular expression, against a caller-supplied string with a backtracking engine and no time budget.
A pattern such as `^(a+)+$` takes exponential time on a hostile string, and the verification runs while the project's enrolment lock is held, so one job could tie up the verification and block other work that needs that lock.
`maxLength` was already checked before `pattern`, and a pattern that does not compile admitted no value, but a `pattern` without `maxLength` was matched against a string of any length.

== Decision

1. **The argument check runs last.**
`ArgumentCheck` is stage 3 and runs only after the enrolment (stage 0), the working directory (stage 1) and the executable with its digest (stage 2) passed.
The first stage that refuses decides; a later stage never runs.
A job refused for its executable is therefore refused as `executable_digest_mismatch` or `build_config_changed` even if its arguments would also be refused, and nothing a caller supplies is looked at for a job whose executable is not verified.

2. **Shell metacharacters are refused in every job kind; the forbidden free flags in canonical build jobs only.**
A shell metacharacter (`|`, `;`, `&`, `$`, `` ` ``, `>`, `<`) is refused as `argument_rejected` in every caller-supplied argument of every job kind: the module of a build job, every argument of a host tool call, every string and member name of a project script's arguments.
The forbidden free flags are refused as `argument_rejected` only in canonical build jobs (`WrapperBuild`, `HostToolBuild`), where the caller supplies the module; there they would redirect the build to other settings, another project file or injected properties.
A host tool call and a project script are not checked against the flag list: their arguments stay bound by the enrolment of the tool, and those of a project script by its argument schema.
This follows the scope the configuration specification states and is the operator's decision taken during the implementation.

3. **Short forbidden flags are matched as prefixes in build jobs.**
`-D`, `-f` and `-s` are refused alone and with an attached value (`-Dfoo=bar`, `-fother-pom.xml`, `-sother-settings.xml`); the long flags alone and with `=value`.
A long flag that only begins like a forbidden one (`--filesystem`) is not refused.

4. **Project script arguments are a typed value, not words of the argument vector.**
The arguments of a `ProjectScriptCall` are a JSON value (`JobRequest.Value`).
They are validated against the script's enrolled `argument_schema` by `ArgumentSchemaValidator` and are not appended to the argument vector; the script receives them as a value.
The verified job carries exactly the validated value (`VerifiedJob.projectScriptArguments`, empty for every job that is no project script), so the launch step hands the script what stage 3 checked and nothing else.

5. **A binding mismatch is refused as `executable_not_enrolled`.**
A project script job whose `binding` (worker kind and target) is not the script's enrolled binding is refused by stage 2 as `executable_not_enrolled`: the script is not enrolled for that use.

6. **An enrolled interpreter is not directly callable.**
A `HostToolCall` whose host tool is an enrolled interpreter is refused by stage 3 as `argument_rejected`, whatever its arguments, none included.
An interpreter is a host tool that the enrolment records as the interpreter of a wrapper (`python3` of `pw`), of a host tool that is a script (`ruby` of `asciidoctor`) or of a project script (`python3`); the set is derived from the enrolment, not from a list of names, so a `python3` that interprets nothing enrolled stays an ordinary host tool.
An interpreter then runs only through what it interprets: a project script, bound by its binding and its argument schema, a script host tool or a wrapper, each of which stage 2 starts with the verified interpreter first.
The rule sits in stage 3 because `argument_rejected` is a stage 3 reason and the stage order stays as it is: an interpreter that is not enrolled or whose digest drifted is refused by stage 2 first.
The refusal names the host tool, never the arguments.
This is the operator's decision on the security concern raised in the review.

7. **Enrolled patterns require `maxLength`.**
A `pattern` is matched only against a string whose length the `maxLength` of the same schema has bounded.
`maxLength` is checked first; a string for a schema that carries a `pattern` but no `maxLength` is refused by stage 3 as `argument_rejected`, with the detail `pattern without maxLength at <path>` (the path, never the value), before any regular expression is compiled or evaluated.
The operator who enrols a pattern therefore also enrols the longest string it is ever matched against, which bounds the backtracking cost of the pattern.
The bound itself is bounded: a schema of type `string` with a pattern admits `maxLength` at most 256 code points, and the enrolment policy refuses a schema above that ceiling
(link:../runtime-enrolment/007-a-global-ceiling-on-the-enrolled-pattern-length.adoc[`runtime-enrolment` ADR 007]).
+
*Lock scope, the finding.* The enrolment lock belongs to the caller.
Stage 0 (`EnrolmentCheck.verify`) acquires the project's enrolment lock in the `LockTransaction` the caller passes, and `LockTransaction` releases its locks only all together in `close()`; it offers no release of one key.
The pipeline neither opens nor closes that transaction, so stages 1 to 3 run under the enrolment lock for as long as the caller keeps its transaction open, and the pipeline cannot release the lock after stage 0 without closing the caller's transaction.
Of the two cases the review fix distinguished, the second applied: the lock is owned by the caller, outside this package, so the caller and the pipeline's stage order were not changed.
The requirement is stated in the Javadoc of `VerifyNotResolvePipeline` and in the developer guide (Stage 3, Pitfall 7): stage 3 runs under the lock and is bounded by `maxLength`, and the caller closes its transaction as soon as `verify` returns, never keeping the enrolment lock while it launches or waits for the job.
This is the operator's decision on the security concern raised in the review.

== Alternatives Considered

1. **Argument check first, as the cheapest check**:
Matching the arguments needs no file access and would refuse many bad jobs early.
*Rejected*: it parses caller-controlled input before the executable is verified, and its refusal would mask a tampered executable or build configuration, which the operator must see first.

2. **Forbidden flags in every job kind**:
The first implementation applied the flag list to every caller-supplied argument.
*Rejected*: it refuses ordinary host tool calls (`git status -sb`, `git log -f`), and the specification scopes the list to canonical build jobs; the arguments of host tools and project scripts are bound by their enrolment and schema.

3. **Metacharacters only in build jobs, like the flags**:
*Rejected*: the argument vector is never passed through a shell, but a metacharacter in an argument has no legitimate use in a verified job and would be dangerous for any consumer that ever interprets it; refusing it everywhere costs nothing.

4. **Exact matching of the short flags**:
*Rejected*: `-Dexec.executable=/bin/sh` is the attack the rule exists for; only a prefix match refuses it.

5. **Appending project script arguments as `--key value` words**:
*Rejected*: it would invent a command-line convention the specification does not define and reintroduce argument parsing on the script's side; the typed value is validated once against the schema.

6. **A distinct reason for a binding mismatch**:
*Rejected*: the closed set of ten reasons is confirmed by the operator; a script used for another binding is, for that use, not enrolled.

7. **A forbidden-flag list for interpreters** (`-c`, `-m`, `-e`, `-r` and the like):
*Rejected*: an interpreter runs code from many places (a flag, a script path, standard input, a module name, environment variables it reads); a list can only name the ones known today and every gap is a code-execution path. Refusing the direct call closes all of them, and every legitimate use already has its enrolled route.

8. **Accepting the enrolment as the trust boundary**: the operator enrolled the interpreter, so any call to it is authorized.
*Rejected*: the operator enrolls an interpreter to run the project scripts, script host tools and wrappers that need it, not to run whatever a caller, and through it a model, passes; that is the free resolution the pipeline exists to prevent.

9. **A non-backtracking regular-expression engine** (RE2/J or similar), whose matching time is linear in the string:
*Rejected*: it is a new dependency of `pm-runtime`, which needs the operator's approval and is not part of this fix; it would also change the dialect of the enrolled patterns (no back-references, no look-around). Mandatory `maxLength` bounds the cost with the engine the JDK provides.

10. **A time budget per match** (matching on a worker thread, or over a `CharSequence` that aborts after a deadline):
*Rejected*: a deadline makes the verdict depend on the load of the machine, so the same job could be verified once and refused once, against the deterministic pipeline; a worker thread that is not interruptible inside the engine keeps burning the processor after the deadline.

11. **Trusting operator-authored patterns**: the operator enrolled the pattern, so its cost is the operator's concern.
*Rejected*: the operator authors the pattern, but the caller, and through it a model, chooses the string; a pattern that is harmless on the values the operator had in mind can backtrack exponentially on one a caller crafts, and it does so while the enrolment lock is held.

== Consequences

* Stage order is a tested invariant: `ArgumentCheckTest` shows that a job refused in stage 2 never reaches the argument check, and that with the executable verified the same arguments are refused.
* `ArgumentCheckTest` refuses each forbidden flag in a wrapper build and an npm build and verifies the same flags in a host tool call; it refuses every metacharacter in a host tool call, and a metacharacter in a project script value and in a member name.
* `VerifyNotResolvePipelineTest` shows that a verified project script job carries exactly the validated arguments and an argument vector without them, and that a wrapper build and a host tool call carry none.
* `ArgumentCheckTest` refuses a host tool call of `python3` (with `-c` and without arguments) and of `ruby`, shows that the interpreters are derived from the enrolment, and verifies a project script through `python3`, `asciidoctor` with its `ruby` prefix and a `git` call; `VerifyNotResolveAdversarialTest` refuses the interpreter host tool call over the whole pipeline, with its positive control.
* `ArgumentSchemaValidatorTest` refuses a `pattern` without `maxLength` (a catastrophic pattern on a hostile string included, under a time limit), verifies a conforming string within `maxLength`, and shows that a string over `maxLength` is refused by `maxLength` without the pattern being evaluated; `VerifyNotResolveAdversarialTest` refuses the unbounded pattern constraint over the whole pipeline, with its positive control.
* An enrolled schema with a `pattern` but no `maxLength` refuses every string for that property; the operator adds `maxLength` to such a schema.
* The developer guide (`pm-runtime/doc/developer/runtime-job.adoc`, Stage 3) states both scopes, the interpreter rule, the `maxLength` rule and the lock scope.
* A host tool that should not accept a given flag must be restricted by its enrolment, not by the flag list of this package.
