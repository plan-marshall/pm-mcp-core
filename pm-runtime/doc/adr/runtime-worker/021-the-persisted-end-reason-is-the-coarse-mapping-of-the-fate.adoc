= ADR 021: The persisted end reason is the coarse mapping of the job's fate
:nofooter:

== Status

Accepted

== Date

2026-11-21

== Context

The settlement writes the terminal worker block with the job's fate (ADR 017), and `WorkerTermination.endReason`
derives the block's `end_reason` from that fate and the worker's connection: a worker that never called is a
`start_failure` when its role class is not `zero_tool` (a `zero_tool` worker has no connection, so a succeeded one
records `task_done`), `succeeded` is `task_done`, `timed_out` is `budget`, `killed` is `drain`, `cancelled` is `withdrawn`,
and every other fate is `exited`. A forced end of the supervisor reaches the runner as `SUPERVISOR_END` and settles as
`cancelled`, so a worker lost to a missed acknowledgement or to silence, recycled or restarted after an off-track
action is recorded `withdrawn`.

The timeouts specification promised `end_reason: ack_missed` and `end_reason: silence` for the acknowledgement deadline
and the silence limit. Code and specification disagreed; the question was which of the two to change.

== Decision

The record keeps the coarse mapping of the fate: `WorkerTermination.endReason` stays as it is, and the specification
says what the code records (link:../../../../doc/specification/timeouts/01-job-budgets-and-waits.adoc#ack-deadline[Timeouts,
Acknowledgement deadline] and link:../../../../doc/specification/timeouts/01-job-budgets-and-waits.adoc#silence-limit[Silence
limit]). The end path names a loss only as far as the cause: the attempt's end of the task is `worker_lost` for a missed
acknowledgement and for silence (a process that exited after its first call ends `exited_without_submit`, ADR 020), and
the log record `WORKER_GENERATION_ENDED` names the end cause (`lost`), not the loss reason. The loss reason itself,
`ack_missed` or `silence`, reaches only the worker state the supervisor writes for a record the
settlement has not settled; a settled record carries the coarse mapping of the fate and no loss reason.

== Alternatives considered

* **Carrying the request's reason into the terminal block**: the supervisor's requested cause and loss reason would
  travel to the settlement and replace the fate's mapping. Rejected: the settlement would depend on a value the job
  runtime does not observe, and the record would no longer be derived from the fate alone.

== Consequences

* The record's `end_reason` of a forced end names the fate, not the cause; the attempt's end (`worker_lost`) and the
  end log (`lost`) say that the worker was lost, not whether it missed an acknowledgement or fell silent.
* `WorkerTerminationTest` pins the mapping per reason, so a change of one arm of `WorkerTermination.endReason` turns a
  test red.
* A later change that wants the fine-grained reason in the record supersedes this ADR and changes the specification
  with it.
