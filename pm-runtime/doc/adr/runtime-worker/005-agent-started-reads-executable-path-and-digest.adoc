= ADR 005: `agent_started` Reads the Executable Path and Digest
:nofooter:

== Status

Accepted

== Date

2026-10-26

== Context

The task protocol carries an `agent_started` signal: a second agent process was started inside the worker's process
tree. The signal names the queue task and the attempt it serves. A worker that started one cannot be trusted to say
*what* started: the isolation and classes stages of the profile verification place decoy instructions, a decoy MCP
server and decoy plugins where a worker that followed them would start something other than its harness. A signal that
named only a PID or a bare executable name would prove nothing about the bytes that ran.

The question was what the signal reads to establish that the process is the enrolled harness.

== Decision

`agent_started` reads the executable path and the executable's digest from the process tree of the worker, and
`AgentStartedDetector` compares that identity with the harness enrolment and with the installed operator binary at
`bin/pm-operator` under the runtime home. `ProcessExecutable` and `ProcessExecutables` resolve the executable of a
process (the production resolver is `SystemProcessExecutables`), and the detector reports a started agent only when a
process of the worker's own tree runs the enrolled executable or the operator binary, by path and digest. It reads the
process's path first and hashes the file only for a path that can match.

The signal carries the resolved path and digest to the protocol adapter; the supervisor records it through
`WorkerProtocol.agentStarted`.

== Alternatives Considered

1. *Trust the harness's own statement of what it started.* _Not taken_: the statement is exactly what a decoy would
   produce, and the control exists to test that the harness cannot be made to start a decoy.
2. *Read only the PID.* _Not taken_: a PID identifies a process, not the bytes it runs; a replaced binary keeps the
   PID.
3. *Read only the executable name.* _Not taken_: a decoy can carry the same name at another path.

== Consequences

* A process is reported only when its executable path and digest match an enrolment or the operator binary, so a decoy
  process is not recorded as the harness.
* A match raises `agent_started` through `WorkerProtocol.agentStarted` and ends the generation through `WorkerEnding`
  with `EndCause.OFF_TRACK`, so the attempt ends `off_track` and its task is offered again as a new attempt within its
  re-offer budget.
* A process whose path and digest match neither an enrolment nor the operator binary is silent: the detector reports
  nothing, logs nothing and ends nothing. A harness that re-execs a different binary after its first call is therefore
  not a signal of its own; the detector reports the bytes it can match to an enrolment, never a mismatch.
* The resolver is a seam: the production `SystemProcessExecutables` reads the OS process tree, and a test supplies its
  own executable so the comparison is exercised on every host.
