= ADR 010: The Activity Recorder Evaluates the Signals at the Entry
:nofooter:

== Status

Accepted.

== Date

2026-10-26

== Context

Model Work § A Worker Off Track requires the four activity signals to be evaluated at every activity entry, in the
transaction that appends it, and each signal to hold at most once per attempt and plan task. The journal appends under its
own leaf lock, outside the queue's transaction (ADR `core-queue/006`), and the task protocol records a signal under the
queue lock. The runtime must compute the signals; the workflow's task protocol owns the record and the action.

== Decision

`ActivityRecorder` is the one write path: it appends the entry under the journal's leaf lock, then reads the attempt's
entries and asks `OffTrackDetector` for the signals that hold, and reports each to the `WorkerProtocol` boundary. The
protocol stays the owner of the queue record's `signals[]`, the journal's `signal` entry, the action and the re-offer.
The recorder keeps the signals it reported per task and attempt, so a second entry of the same attempt does not report
the same signal again; the protocol's own once-per-attempt check is the second guard.

An unmeasurable signal is not evaluated: `over_size` without a predicted cost, and `outside_footprint` outside an
envelope task, both come from `WorkerTaskActivity` as absent, never as a fabricated zero.

== Alternatives Considered

1. *Evaluate inside `TaskProtocol`.*
   _Rejected_: the detector is runtime code and the protocol lives in `pm-workflow`, which the runtime may not reference;
   the boundary already carries the protocol's reports.
2. *Evaluate in the task protocol's off-track call alone.*
   _Rejected_: the call happens after the entry is written and after the lock is released; the specification places the
   evaluation at the entry.
3. *A background evaluator over the journal.*
   _Rejected_: it would see an attempt after it ended and could take an action on the next attempt.

== Consequences

* The two locks are not nested: the journal lock is released before the protocol takes the queue lock.
* A signal is reported once per attempt even if two entries arrive concurrently.
* The plan task's figures (`predicted_cost_tokens`, unplanned changes) arrive through `WorkerTaskActivity`, which the
  assembly adapts; the runtime reads no queue record or envelope.
