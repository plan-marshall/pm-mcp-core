= ADR 016: The Sweep Removes Pending Entry Residue by the End of the Entry
:nofooter:

== Status

Accepted

== Date

2026-11-22

== Context

The periodic sweep removed pending entry records older than a compiled maximum age (24 hours). Store Schemas § Pending
Entry and Timeouts § Pending Entry no longer give an entry a maximum age: an entry never expires and stays among the
project's open entries until its scope is created, the operator abandons it, or the release of its project deletes it.
The sweep's residue is now the directory of an entry whose removal a stop cut off
(link:../../../../doc/specification/runtime-lifecycle/01-startup-recovery-drain.adoc#periodic-sweep[Runtime Lifecycle §
Periodic Sweep]).

== Decision

* `PeriodicSweep` carries no maximum age. `runOnce(now)` passes the instant of the run to every step as the instant its
  records carry, never an age to compare.
* `PendingEntryRecordsSweep` decides by the end of the entry, not by its age: a directory whose record `entry.json`
  exists is an open entry and is never removed, however old it is; a directory whose four stores are absent from the
  workspace's sidecar and from the filesystem is residue — a removal a stop cut off, or a creation that never committed
  its first transaction — decided under the workspace lock by `PendingEntryStore.verify` (refined by PLAN-V2-167).
* The residue of a run is removed in one transaction of the workspace scope. Every candidate is re-judged under the
  workspace lock before it is removed, so an entry opened between the listing and the lock is kept. The delete targets
  are the entry's four stores, and the record is the first of them: `remove` deletes all four in one transaction the
  journal completes, whereas the creation's move deletes the record last, where it is the evidence the creation passed.
  The transaction owes one `pending_entry_removed` record per directory, and the directories are deleted after the
  commit.
* The step reports every entry it keeps and every directory it removed in one report: the count is the directories
  left gone, each of them is named, an unreadable record and a held entry are both named, and a directory the discard
  cannot remove — the record is present again, or the delete failed — is named as kept, so a completed removal never
  drops a kept entry from the report. A fault of the removal itself is a fault of one of the five types the step
  catches — `UncheckedIOException`, `IllegalArgumentException`, `IllegalStateException`, `InternalFaultException` and
  `StoreRefusal` — and is reported with what the run had staged for removal, the directories it had already removed and
  every entry it kept, as they stood when the fault struck, beside the unreadable entries the listing collected before
  it, so that fault drops none of them. A fault of another type leaves `run` uncaught: only these five types are the
  faults a removal carries as its state. A refusal of the discard is no fault of the run, because its two named
  refusals are caught per entry. The report says how far the faulted removal got: staged before the commit is called,
  so nothing is committed and the next run re-judges every entry; owed with the commit entered and its journal
  durable, so the recovery completes the removals; undecided with the commit entered and no journal present — the
  commit deletes the journal as it closes, and a commit that fails before writing it leaves none, so its absence
  decides nothing — and the next run re-judges the directories; or committed once the transaction's commit returned,
  so the removals are applied and only the directories remain for the next run. The reach is read from
  the phase the removal had reached and, while the commit was entered, from the workspace's journal — never from the
  fault's type (amended 2026-11-23 by `PLAN-V2-178`, which made the report carry this state). The discard's two
  refusals are caught per entry, so only a fault outside them reaches the committed arm, and a fault of the lock's own
  release carries the same state, because it is kept outside the lock transaction. A fault of that release beside a
  fault the attempt had already built keeps that fault's message, entries and reach and reports the release fault
  beside it (amended 2026-11-24 by `PLAN-V2-181`; amended 2026-11-24 by `PLAN-V2-183`: a fault with no message is
  named by its exception type, never printed as `null`; amended 2026-11-24 by `PLAN-V2-184`: the naming covers a first
  fault as well as the release fault, and only `UncheckedIOException`, `IllegalArgumentException` and
  `IllegalStateException` can carry no message — `InternalFaultException` and `StoreRefusal` compose a non-null one in
  their constructors): the release comes after another writer may have left the
  workspace's journal, so re-reading the journal after it would turn an undecided removal into one the report calls
  owed. A test reaches the staged arm
  (`PendingEntryRecordsSweepTest.faultBeforeTheCommitRollsBackTheStagedRemovals`), the owed arm
  (`PendingEntryRecordsSweepTest.auditSinkFaultInsideTheCommitLeavesTheRemovalOwed`, an audit sink that throws inside
  the commit) and the undecided arm (`PendingEntryRecordsSweepTest.aCommitThatCannotWriteItsJournalLeavesTheReachUndecided`,
  a workspace journal directory that refuses the write, and `PendingEntryRecordsSweepTest.aFaultedLockReleaseKeepsTheFirstFaultsReach`,
  the same refusal beside a lock whose release faults after another writer left a journal, and
  `PendingEntryRecordsSweepTest.aReleaseFaultWithoutAMessageIsNamedByItsType`, the release fault that carries no
  message). `PendingEntryRecordsSweepTest.aFirstFaultWithoutAMessageIsNamedByItsType` reaches no reach of its own: the
  acquisition faults before anything is staged, so its report carries none, and what it proves is the naming of a
  first fault that carries no message. The committed arm has no seam — the discard's two refusals are caught per
  entry — so it stays untested, as the test class's Javadoc states.
* An entry whose record cannot be read is kept and reported as a failure of the step, so a tampered entry is held for
  its operator instead of being swept.
* The log record `PM_RUNTIME-23` (`PENDING_ENTRY_RECORDS_SWEPT`) is retired, and the sweep owes the audit record
  alone.

== Alternatives Considered

1. *Keep a maximum age beside the evidence.*
_Not taken_: the specification says an entry never expires; an age would delete an open entry.
2. *Mark the entry as started or abandoned in its record and sweep the marked ones.*
_Not taken_: a marker is a second form of the end that the removal's own transaction already expresses, and a record
written before the deletion would be a store the sweep must trust.
3. *Delete the directory inside the transaction.*
_Not taken_: a transaction deletes stores, not directories, and the transcript and source files are not stores; the
record's absence is the durable evidence, and the directory is the last act.

== Consequences

* An open entry older than a day is still offered; no run removes it.
* A stop after the removal transaction leaves a record-less directory, which the next run removes; a stop before the
  commit leaves the entry as it was, and the recovery of the workspace completes the journal. A candidate is re-judged
  under the workspace lock before it is removed, so an entry opened between the listing and the lock is kept.
* A tampered entry is never cleaned away: the step reports it and keeps it until the operator accepts the edit or
  abandons the entry.
* A creation cut between the new scope's commit and the workspace's is not recovered by this step: the record still
  exists, and the new scope does not carry the entry id, so no evidence can derive it. The new scope holds the stores,
  so a repeated move is refused by their create targets, and the operator ends that entry by abandoning it.
