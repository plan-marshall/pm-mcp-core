== Purpose

_Requirements:_ link:{req}/07-credentials.adoc#PM-CRED-2[PM-CRED-2], link:{req}/07-credentials.adoc#PM-CRED-3[PM-CRED-3], link:{req}/07-credentials.adoc#PM-CRED-4[PM-CRED-4]

Package `de.planmarshall.runtime.credentials` of `pm-runtime` holds the credential stores of the runtime. The machine
uses exactly one store, the one the operator recorded in `credentials.store` of `machine-config.json`: `os`, the
macOS login Keychain or the Linux Secret Service, or `file`, the permission-guarded file store below
`<PM_MCP_BASE>/credentials/`. The runtime makes no automatic choice and has no fallback: before a store is recorded no
credential is entered, and an unavailable recorded OS store makes the credentials unavailable without a file being
written in its place (link:../adr/runtime-credentials/001-the-recorded-store-replaces-the-automatic-choice.adoc[ADR
001]).

The first recording of a store reconciles the enrolment integrity key of both stores and brings it into the store it
records. Changing the store later is a move of every entry, in either direction. Both operations write the same record
`state/credential-store-move.json` and both are finished by the next start where a stop cut them
(link:../adr/runtime-credentials/007-the-first-recording-reconciles-both-stores.adoc[ADR 007],
link:../adr/runtime-credentials/008-the-first-recording-is-resumable.adoc[ADR 008]).

== Core Types

_Requirements:_ link:{req}/07-credentials.adoc#PM-CRED-2[PM-CRED-2]

[horizontal]
`SecretStore`:: One store: `name()` (`keychain`, `secret-service` or `file`), `put`, `get`, `delete`, `entries()` and
the resolution of a project entry before its global entry (`resolve`).
`CredentialAccount`:: The account of an entry: `<credential_key>` (global) or `<project>/<credential_key>`.
`CredentialStoreChoice`:: The recorded store: reads and writes `credentials.store`, gives the active store, either
store for the move, and the store of the integrity key before the choice.
`CredentialStoreChoice.Store`:: `OS` (`os`) or `FILE` (`file`).
`CredentialStoreChoice.Writer`:: The closed set of writers of the machine configuration: `CREDENTIAL_STORE_ASPECT`,
`STORE_MOVE`, `OTHER_CONFIGURATION`; only the first two own `credentials.store`.
`CredentialStoreChoice.Refusal`:: A request refused although no store failed: `onboarding_incomplete` or
`aspect_owned`.
`SecretStoreException`:: A store that failed: `credential_store_locked`, `credential_store_unavailable`,
`credentials_file_insecure`, `credentials_file_invalid`, `credential_store_failed`.
`CredentialStoreCheck`:: The check of the OS store before it is recorded.
`CredentialStoreMove`:: The move of every entry between the two stores, and the resume of both operations.
`IntegrityKeyCarry` (package-private):: The part the move and the first recording share: compare the key the target
holds with the source (`targetKey`: none, held, or another key), copy the integrity key without ever overwriting a key
the target holds, read it back from the target, verify every sidecar under the key read back (`verifySidecars`), and
answer under which of two candidate keys the sidecars verify, for the reconcile of the first recording
(`failureUnder`).
`CredentialStoreMoveRecord`:: The codec of the record `state/credential-store-move.json` of an open operation: its
`operation` (`move` or `first_recording`), `from`, `to`, `started_at`, `phase`, `target_held_key` and
`transaction_id`.
`FileSecretStore`, `KeychainSecretStore`, `SecretServiceStore`:: The three stores.

== The Recorded Store

_Requirements:_ link:{req}/07-credentials.adoc#PM-CRED-2[PM-CRED-2], link:{req}/07-credentials.adoc#PM-CRED-4[PM-CRED-4]

`CredentialStoreChoice.recorded()` reads `credentials.store` of `<PM_MCP_BASE>/machine-config.json` without a lock:
the file is replaced by one atomic rename, so a read sees it before or after a write. An absent file or an absent key
means that no store is recorded; any other value than `os` or `file`, another format version, or an unreadable
document is a `StoreRefusal`.

The two `record` methods are the only writes of the key
(link:../adr/runtime-credentials/002-credentials-store-written-only-through-credential-store-choice.adoc[ADR 002]):
`record(locks, user, store)` for the credential-store aspect, in a transaction of its own, and
`record(transaction, store, writer)` for the switch inside the transaction of an operation: writer `STORE_MOVE` for the
move, writer `CREDENTIAL_STORE_ASPECT` for the aspect's first recording, each accepted only while the record of its own
operation exists, which the call re-reads under `locks/credentials.lock`. The transactional call refuses a writer that
does not own the key with `aspect_owned`, the aspect outside its first recording with an `IllegalArgumentException`, and
the store move outside a move with an `IllegalStateException`, all before anything is acquired or written, so a caller
that names itself the store move records nothing outside a move. Both take `locks/credentials.lock` first, then
`locks/machine-config.lock`; inside
it the document is re-read, every other member kept verbatim, `revision` incremented and the file replaced in one
atomic write, so two writers never interleave and no check-then-act window opens outside the lock. An absent document
is created with `format_version` 1, `revision` 1 and the other required keys at their schema defaults
(`max_build_slots` 2, `lsp_idle_timeout_seconds` 900). Every write logs `PM_RUNTIME-26` with the store, the writer
and the revision.

While the record `state/credential-store-move.json` of an operation exists, only that operation records a store: the
aspect and the move are refused with `aspect_owned` and an `IllegalStateException` respectively. The check is taken
under `locks/credentials.lock`, which the operation holds for its whole duration, so no other writer records a store
between the check and its write, nor while an operation runs
(link:../adr/runtime-credentials/004-move-copies-the-key-last-and-switches-once.adoc[ADR 004],
link:../adr/runtime-credentials/008-the-first-recording-is-resumable.adoc[ADR 008]).

The aspect records a store the first time only. Once a store is recorded, a change to the other store is a move, which
carries every entry and the key: `record(locks, user, store)` refuses the other store with `aspect_owned` and writes
nothing, and the recorded store again is a no-op that writes, carries and deletes nothing. The recorded store is read
under `locks/credentials.lock` as well, so a call that waits for a running move sees the store the move switched to.

=== The First Recording Reconciles the Key of Both Stores

Before a store is recorded, the integrity key lives in the store the runtime found (`integrityKeyStore()`, below) —
but it can also lie in the other store: a key file written while the OS store was unavailable, or a keyring entry a
recording whose deletion failed left behind. `record(locks, user, store)` therefore reads both stores and keeps the key
every HMAC sidecar verifies under
(link:../adr/runtime-credentials/007-the-first-recording-reconciles-both-stores.adoc[ADR 007]):

. Read the key of the store being recorded and of the other one. Where the store being recorded cannot be read and the
   other one holds a key, the recording is refused with the reason of that store; where neither holds a key, the store
   is recorded as it is and the work below is skipped.
. Decide the key to keep: the only key there is; the same key in both stores; or, where the two differ, the one whose
   run of `IntegrityKeyCarry.failureUnder` verifies every sidecar. Two different keys that the sidecars do not decide
   between (none exists, so both verify, or neither verifies) refuse the recording with `credential_store_failed`,
   naming both stores and what each key verifies; nothing is written or deleted then.
. Write the record `state/credential-store-move.json` with `operation: first_recording`, `from` the other store, `to` the
   store being recorded, `phase: copying`, `target_held_key` and a new `transaction_id`
   (link:../adr/runtime-credentials/009-the-transaction-id-of-the-operation.adoc[ADR 009]).
. Bring the kept key into the store being recorded, unless it holds it already: a differing key of that store is deleted
   first, then the key is copied and read back (`IntegrityKeyCarry`), and every HMAC sidecar is verified under the key
   read back where the other store holds a key too.
. Switch `credentials.store` in one write, rewrite the record to `phase: switched`, delete the key from the other store,
   and delete the record last.

A key that does not read back, a sidecar that does not verify or cannot be read, or a machine file that is not in its
format fails with `credential_store_failed`; a store that fails while the key is read or written fails with its own
reason (`PM_RUNTIME-133`). Before the switch nothing is recorded, the copy is removed from the store being recorded and
the record is deleted; where the copy cannot be removed the record is kept, and the next start removes it and records
again. After the switch the recording stands, the key is in both stores and the record stays: the next start deletes the
key from the other store (`PM_RUNTIME-32`). That deletion is guarded by durable evidence, not by the record's flag: the
store being recorded must hold a key, and where that key differs from the other store's the sidecars must verify under
it; otherwise the deletion refuses with an `IllegalStateException` and keeps the record, so the only key the sidecars
verify under is never deleted. While the record exists the aspect is refused with `aspect_owned`, so the operator cannot
record another store until the resume ended it — the same discipline as that of a move.

A store that cannot be read counts as holding no key (`PM_RUNTIME-134`): the operator records the file store exactly
when the OS store is broken, and a store the recording does not touch may not block it. That is a temporary
unreadability, not a key conflict: a key the unreadable store holds stays there, and a later move into that store
accepts it where it is the same key — a duplicate is not written again and stays — and refuses it only where it
differs from the old store's key (a target that holds the same key, or a key while the old store holds none, is no
conflict).

The recorded store therefore holds the key every sidecar was signed under, whichever store the key was created in, and
no second key is created there.

== The Active Store

_Requirements:_ link:{req}/07-credentials.adoc#PM-CRED-2[PM-CRED-2], link:{req}/07-credentials.adoc#PM-CRED-4[PM-CRED-4]

`activeStore()` reads the recorded store at every call, so the switch of a move takes effect for the next operation:

* No store recorded: `Refusal` with `onboarding_incomplete`, naming the store step `store` of the onboarding.
* `file`: the `FileSecretStore` below `<PM_MCP_BASE>/credentials`.
* `os`: the OS store of the platform, the Keychain on macOS and the Secret Service on Linux, behind a wrapper that
  probes it before every operation. An OS store unavailable at start or later fails a read with
  `credential_store_unavailable` and a write with `credential_store_locked`, logged as `PM_RUNTIME-128`; a locked
  collection or item met by a read is unavailable as well. No other store serves in its place. The Secret Service is
  probed afresh before every operation; the `KeychainSecretStore` is loaded at most once per `CredentialStoreChoice`
  instance, since loading it looks up Security.framework through `Arena.global()`, which is never released. A load
  that fails is not kept and is tried again at the next operation, and a locked Keychain is still reported by the
  store at every operation.

`backendOf(Store)` (package-private) gives either store whether it is recorded or not, for the move and the first
recording; an unavailable OS store given so is named as the OS store, never as the recorded one, and logs no
`PM_RUNTIME-128`.
`integrityKeyStore()` gives the store of the enrolment integrity key: the active store once a store is recorded, and
before that the OS store where one is available, else the file store, for which the key is the key file below
`state/` (link:runtime-enrolment.adoc[`runtime.enrolment`]). The store before the choice is found at the first call
and kept for the lifetime of the instance: a later probe never moves the key from the OS store to the key file or
back, so a transient outage of the OS store fails an operation on the key and never creates a second key in the other
store. The first recording reconciles the key of that store with the key of the other one (above).

The OS keyrings are reached through the package-private seam `CredentialStoreChoice.Keyrings`, which the tests
replace; `CredentialStoreChoice.of(MachinePaths)` uses the real ones. The Secret Service is bounded by
`SecretServiceStore.BUS_TIMEOUT` (2 seconds).

=== The Two Kinds of Refusal

`SecretStoreException.Reason` names failures of a store only. The two refusals that are not store failures, no store
recorded yet and a writer that does not own the key, are the nested `CredentialStoreChoice.Refusal` with its own
`Reason` (`ONBOARDING_INCOMPLETE`, `ASPECT_OWNED`), so that a caller that maps a store failure to its error code never
meets them there (link:../adr/runtime-credentials/002-credentials-store-written-only-through-credential-store-choice.adoc[ADR
002]).

== The Check of the OS Store

_Requirements:_ link:{req}/07-credentials.adoc#PM-CRED-2[PM-CRED-2]

Before the OS store is recorded, `CredentialStoreCheck.check(choice)` writes one test entry under the fixed global
account `credential-store-check`, reads it back and compares it, and deletes it. Each step is one `CheckLine`: the
step (`write`, `read_back`, `delete`), `ok` or `failed`, the message key `credential_store_check.<step>.<what>` with
the store and the account as arguments, and the store's own answer where there is one (its reason code and message).
A failed step ends the check, deletes what was written, and the check records nothing. An unavailable OS store fails
the write step. The test value is random and never logged or put into a line. The consent `check_credential_store`
and the states of the store step stay with the onboarding in the assembly.

== The Credential-Store Aspect

_Requirements:_ link:{req}/07-credentials.adoc#PM-CRED-2[PM-CRED-2], link:{req}/08-security.adoc#PM-SEC-8[PM-SEC-8]

`CredentialStoreAspect` runs the states of the credential-store aspect (`store.detect`, `store.choose`, `store.consent`,
`store.check`, `store.confirm-move`, `store.move`, `store.record`) over the delivered store: the check stays
`CredentialStoreCheck`, the move stays `CredentialStoreMove`, and the aspect is the order between them. The units that
call it are the onboarding's, in `plan-marshall-mcp`; this class is the engine half, and it is provable without a
workflow (link:../adr/runtime-credentials/010-the-aspect-runs-the-delivered-store.adoc[ADR 010]).

Each state answers a `Transition`: the next state, the reason of an unavailable store, the check lines, the count of
entries a move would carry and the consent to record. The order is the specification's:

* `detect` offers the OS store where it is available now and the file store always, and reports a move an earlier run
  began (`move_interrupted`).
* `choose` sends an OS store through `store.consent`; the file store lies in the machine's own directory, so it reaches
  `store.check` without a consent. An OS store that is not available now reaches `store.unavailable` with
  `os_unavailable`.
* `consent` asks the consent `check_credential_store` through `ConsentGate`: a `no` stays in `store.consent` and writes
  nothing, a `yes` or `yes_remember` reaches `store.check`, and a remembered kind passes without a question.
* `check` writes, reads back and deletes one test entry in the chosen store. A passed check with no store recorded, or
  with the chosen store recorded, reaches `store.record`; a passed check with another store recorded reaches
  `store.confirm-move`; a failed check reaches `store.unavailable` with the failed line's message key.
* `confirmMove` answers the number of Token Lane entries the recorded store holds.
* `move` runs `CredentialStoreMove`, which switches `credentials.store` last; a failure before the switch keeps the old
  store recorded and untouched, and the aspect reports `store.unavailable` with `credential_store_failed`.
* `record` records the store through `CredentialStoreChoice.record` and reaches `store.done`.

`resume()` finishes an operation a stop cut, which `store.detect` reported as `move_interrupted`.

== Provider Verification

_Requirements:_ link:{req}/07-credentials.adoc#PM-CRED-1[PM-CRED-1]

`ProviderVerification` checks one provider on the consent `verify_providers` (`ConsentGate`): the origin is reachable;
the credential authenticates and as whom; its permissions and its expiry; and, for the CLI variant, the tool's version
and that it is logged in as the same identity as the credential. Each check is one line with its name, `ok` or
`failed`, the message key `provider_verification.<check>.<ok|failed>`, the arguments and the provider's or the tool's own
answer.

The checks reach the providers through two seams, `ProviderVerification.ProviderProbe` and
`ProviderVerification.ToolProbe`, which the assembly implements over the provider modules and the enrolled CLI tools:
the CI contract has no module of this repository yet, and no provider module here answers `ci.whoami`, so the
verification is specified against the seam. A `no` to the consent runs no check and answers `ran: false`; a
`yes_remember` hands the consent back for the store. The verification records nothing: `providers.record` writes the
machine's provider defaults from it, and a provider whose checks failed is recorded only on the operator's word, and then
as not available.

== Enumeration

_Requirements:_ link:{req}/07-credentials.adoc#PM-CRED-2[PM-CRED-2], link:{req}/07-credentials.adoc#PM-CRED-3[PM-CRED-3]

Every store lists its entries through `SecretStore.entries()`: every account of `PM-MCP` it holds, global and project
entries, the account `enrolment-integrity-key` included where the key lives in the store, ordered by account; entries
of another service name are never listed (link:../adr/runtime-credentials/003-every-store-enumerates-its-entries.adoc[ADR
003]).

[horizontal]
`FileSecretStore`:: Lists `<dir>/<key>.json` and `<dir>/<project>/<key>.json` without following a link and skips the
temporary files `~tmp-*` of an atomic write, also one a crash left behind. `~` is outside the alphabet of an account,
so no legal name is skipped: an entry or a project named `.tmp-ci` is listed and moved. An absent directory is an
empty store. A directory that fails the
private-mode check or a symbolic link is `credentials_file_insecure`; an entry whose name is no account is
`credentials_file_invalid`.
`KeychainSecretStore`:: `SecItemCopyMatching` with `kSecReturnAttributes` and `kSecMatchLimitAll` under the service
name, reading `kSecAttrAccount` of each result dictionary (`MacSecurity`: `CFArrayGetCount`,
`CFArrayGetValueAtIndex`, `CFDictionaryGetValue`, `CFStringGetCString`). `errSecItemNotFound` is an empty store.
The new downcalls are registered in
`META-INF/native-image/de.planmarshall/pm-runtime-credentials/reachability-metadata.json`; the native build of
`pm-mcpd` in plan-marshall-mcp verifies them.
`SecretServiceStore`:: `SearchItems` on `service=<service name>` alone and the `Attributes` property of each item
(`credential_key`, optional `project`). A locked matching item is `credential_store_locked`; an item without
`credential_key` is no entry and is not listed.

== The Move Between the Stores

_Requirements:_ link:{req}/07-credentials.adoc#PM-CRED-2[PM-CRED-2], link:{req}/07-credentials.adoc#PM-CRED-3[PM-CRED-3], link:{req}/08-security.adoc#PM-SEC-5[PM-SEC-5]

`CredentialStoreMove.move(to)` moves every entry from the recorded store into the other one under
`locks/credentials.lock`, the lock every credential write takes, held for the whole move, and re-reads its record
inside the lock before every phase
(link:../adr/runtime-credentials/004-move-copies-the-key-last-and-switches-once.adoc[ADR 004]):

. Write the record `state/credential-store-move.json` in phase `copying` with `operation: move`
  (`PM_RUNTIME-27`), with `target_held_key`: whether the target held the integrity key already, and a new
  `transaction_id`.
. Copy every Token Lane entry the old store enumerates into the target and read each back.
. Copy the enrolment integrity key last, into the keyring entry of the target or the key file below `state/`, unless
  the target holds the same key already, read it back from the target, and verify every HMAC sidecar under the key read back: the enrolment files, `harnesses.json`
  and `logs/audit.head` (`EnrolmentSidecars` of link:runtime-enrolment.adoc[`runtime.enrolment`];
  link:../adr/runtime-credentials/005-the-move-verifies-every-sidecar-in-the-runtime.adoc[ADR 005]). Where the old store
  holds no key there is nothing signed and nothing to verify. The recorded store holds the key every sidecar was signed
  under, since the first recording reconciled it into the store before the choice (above).
. Switch `credentials.store` in one write through `CredentialStoreChoice` (writer `STORE_MOVE`), then rewrite the
  record in phase `switched`.
. Delete every entry and the key from the old store.
. Append the `operator` audit record `credential_store_moved` with the details `from`, `to`, `entries` (the number
  of Token Lane entries in the new store) and `transaction_id` (the id of the record), then delete the record and log
  `PM_RUNTIME-28`. The audit record goes first, so a stop or a failing audit sink leaves the record in phase
  `switched`, and the next start finishes the move again and appends the audit record then: at least once, with the
  same transaction id, so a reader that drops a duplicate counts the move once
  (link:../adr/runtime-credentials/009-the-transaction-id-of-the-operation.adoc[ADR 009]).

A failed copy, read-back or sidecar verification before the switch logs `PM_RUNTIME-129` and fails with
`credential_store_failed`; the old store stays recorded and untouched. The clean-up never deletes from the recorded
store: it deletes the copies only while `credentials.store` names the old store. The record stays exactly while the
next start has a clean-up left that it may do:

[cols="2,2,3"]
|===
| Recorded store at the failure | Copies | Record

| the old store
| removed from the target
| deleted

| the old store
| not all removed (the failure of the removal added to the cause)
| kept: the next start removes the copies and moves again from the first entry

| unreadable
| kept in the target
| kept: the next start resumes once the machine configuration reads again

| the target, which the lock discipline excludes
| kept in the target, the recorded store
| deleted: a resume would read the state as the switch of the move and delete the entries from the old store
|===

The log record and the failure say which of these happened. Until the switch the recorded store is the old one, so
the active store reads no other store while the move runs, and no other writer records a store while the record
exists. A move is refused before anything is written when no store is recorded (`onboarding_incomplete`), when the
target is the recorded store, when a move is open already, or with `credential_store_failed` when the target holds a
Token Lane entry already: a secret never exists in two stores, so such a target is inconsistent, and the move
neither overwrites what it holds nor deletes it in a clean-up. The message names the store and the number of entries,
never a secret.

The integrity key is no Token Lane entry, and a key can stay outside the recorded store (above), so before the record
is written the target is compared with the old store through `IntegrityKeyCarry.targetKey`, the comparison the first
recording uses as well. A target that holds another key than the old store is refused with `credential_store_failed`,
naming both stores, and nothing is written or deleted: the copy would overwrite a keyring entry, the clean-up of a
failure would delete a key file the move never wrote, and every sidecar signed under that key could never be verified
again. A target that holds the same key, or a key while the old store holds none, is no conflict: the move runs, does
not write the key again, and keeps it. The record says whether the target held the key (`target_held_key`), and the
clean-up of a failed move, the one of a resume included, deletes the key from the target only where it did not, so it
deletes only a key the move copied.

=== Lock Order

The move holds `locks/credentials.lock` and takes `locks/machine-config.lock` inside it for the switch, which sorts
after it. The sidecars are verified in a transaction of their own while the move's transaction holds the credentials
lock: the verification takes the enrolment locks, `locks/harnesses.lock` and the audit leaf lock last, after which a
transaction may acquire nothing, and the move still has to take the machine configuration lock for the switch.

=== The Record and the Resume

`CredentialStoreMoveRecord` is the strict codec of
`{"format_version": 1, "from", "to", "started_at", "phase", "target_held_key", "operation", "transaction_id"}`
(mode `0600`, one atomic rename, every field once, no other field, the two stores different, a transaction id of the
one written form; every refusal a `StoreRefusal` naming the file). `operation` says which operation it drives: `move`,
whose `from` is the store recorded when it started, or `first_recording`, whose `from` is the store that is not being
recorded. It names stores only and holds nothing secret.

`credentials.store` is switched before the record is marked `switched`, and only after every entry and the key were
copied and verified. A stop between the two leaves a record in phase `copying` although the target is recorded; since
only the operation that owns the record records a store while it exists, that state can only be its own switch.
`resume()` therefore decides the phase from the recorded store as well as from the record: in phase `switched`, or in
phase `copying` while `credentials.store` names the target, it marks the record `switched`, finishes the deletion from
the old store and ends the record, and deletes or copies nothing in the recorded target; in phase `copying` with the
old store recorded it deletes the copies from the target, the key only where `target_held_key` is `false`, and runs
the move again from the first entry, the old store holding every entry; without a record it does nothing. A record in phase `switched` while `credentials.store` does
not name its target is refused with an `IllegalStateException`: nothing is deleted from either store and the record
is kept. A stop never deletes the only copy of an entry. It returns the record as found.

A record with `operation: first_recording` is dispatched to
`CredentialStoreChoice.resumeFirstRecording` before those branches: in phase `copying` with the store being recorded
recorded already (the stop between the switch and the rewrite), or in phase `switched` with it recorded, it finishes
the deletion of the key from the other store and ends the record; in phase `copying` with no store recorded it removes
the copy from the store being recorded and runs the recording again; in phase `switched` without that store it is
refused and deletes nothing. A second resume on the finished state finds no record and does nothing.
The start calls it through `CredentialStoreMoveResume` of `runtime.start`
(link:runtime-start.adoc#_store_move_resume[Store Move Resume]), which logs `PM_RUNTIME-29` for a move and
`PM_RUNTIME-32` for a first recording.

The audit record is built directly as an `AuditEvent` with the category `operator`; `pm-core` gained no factory for
it.

== The D-Bus Client (`credentials.dbus`)

_Requirements: link:{req}/07-credentials.adoc#PM-CRED-2[PM-CRED-2]_

The package `de.planmarshall.runtime.credentials.dbus` is the minimal D-Bus client the Linux Secret Service backend needs;
it holds no credential logic of its own. It exists because the JDK has no D-Bus API and the store must speak the wire
protocol to the session bus.

[cols="1,3",options="header"]
|===
|Type |What it does

|`DbusConnection`
|A connection over the JDK's `UnixDomainSocketAddress` channel to the session bus named by the environment, with SASL
`EXTERNAL` authentication.

|`DbusWriter`, `DbusReader`, `DbusMessage`
|The wire format: a message is its fixed header, its header fields and its body; the reader and the writer align every
value to its natural boundary relative to the message start, as the specification requires.

|`Signatures`, `Variant`
|The type signatures and the variant wrapper: `y b n q i u x t s o g v`, arrays (with `byte[]` for `ay`, a `Map` for a
dictionary and a `List` otherwise) and structs as a `List`.

|`DbusException`
|A malformed message, a refused authentication or a bus error.
|===

The client is deliberately small: it implements the subset of the type system the Secret Service calls and no object
mapping, no introspection and no signal subscription beyond what those calls need. A new Secret Service call that needs a
type outside the subset adds it to `Signatures` and to both the reader and the writer, with a round-trip test.

The client is created per connection and closed with it; a connection failure is a `SecretStoreException` of the caller's
kind, never a `DbusException` that escapes the store. The bus address is read from the process environment, and the SASL
`EXTERNAL` identity is the process's own uid; neither comes from the configuration of the product.

== Pitfalls

_Requirements:_ link:{req}/07-credentials.adoc#PM-CRED-2[PM-CRED-2], link:{req}/07-credentials.adoc#PM-CRED-4[PM-CRED-4]

1. **Never a file write in place of an unavailable OS store**: an unavailable recorded store fails the operation; it
   is never a reason to use the other store.
2. **Write `credentials.store` only through `CredentialStoreChoice.record`**: the aspect through
   `record(locks, user, store)`, which reconciles the integrity key at the first recording, the move through the
   transactional call; never write `machine-config.json` around it, never record a store while a record is open, and
   never change a recorded store but by the move.
3. **The key moves last**: after every Token Lane entry, and the sidecars are verified under the key read back from
   the target, never under the key held in memory, before the store is switched.
4. **Switch before marking the record**: the record says `switched` only once the target is recorded, so a resume
   never deletes from the old store what the target does not hold; a record in phase `copying` with the target
   recorded is a switched operation, and the recorded store is never cleaned up.
5. **Decide the key once, in the record, then never again**: the reconcile of the first recording picks the key from
   the sidecars and writes `target_held_key` and `from` into the record before a copy; the resume never re-decides
   from the two stores, which cannot tell a copy from a key the machine already had (ADR 007, ADR 008).
6. **Delete the record last**: after the switch, the key deletion and the audit record. A record deleted earlier
   leaves a key in two stores with nothing that names the operation (ADR 008).
7. **No secret in a message**: no log record, exception message, check line or audit record names a secret; the tests
   put a marker-bearing key and a marker-bearing credential value through every path and scan the log for it.
