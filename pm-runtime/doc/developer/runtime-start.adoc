== Purpose

_Requirements:_ link:{req}/01-architecture.adoc#PM-ARCH-7[PM-ARCH-7], link:{req}/13-client-profiles.adoc#PM-CLIENT-1[PM-CLIENT-1], link:https://github.com/plan-marshall/plan-marshall-documentation/blob/9b54d54/doc/requirements/16-model-work.adoc#PM-WORK-5[PM-WORK-5], link:{req}/08-security.adoc#PM-SEC-6[PM-SEC-6], link:{req}/07-credentials.adoc#PM-CRED-2[PM-CRED-2]

Package `de.planmarshall.runtime.start` of `pm-runtime` holds the start, the drain, the per-project recovery and the
periodic sweep of the runtime; they are described in link:{docs}/developer/runtime-lifecycle.adoc[Developer Guide §
Runtime Lifecycle]. This guide covers what the work package `session-log-and-generations` added to it: the step of the
periodic sweep, which removes what has aged out of the store the package added in `pm-core`. It also covers the
stalled-scope detection of the work package `removed-concepts`. It further covers what the work package `audit-trail`
changed in it: the audit chain seam of the bounded
verification, whose broken outcome now carries a reason and the first broken line (<<_the_audit_chain_seam>>), and the
one `transaction_id` per record the pending-record step owes. Last, it covers what the work package
`credential-store-choice` added: the resume of a move between the credential stores that a stop cut
(<<_store_move_resume>>).

* `PendingEntryRecordsSweep` removes the pending entry records of the workspace scope older than the pending entry
  record maximum age.

The periodic sweep has no seam factory any more: the steps are real classes, and the assembly `pm-mcp-server`
must register `PendingEntryRecordsSweep` when it builds the `PeriodicSweep` — it still calls
`SweepStep.notImplemented` and does not build against the current snapshot until its registration pull request lands
(link:../adr/runtime-start/002-sweep-seam-factory-removed.adoc[ADR 002]).

The work package `job-runner` added the jobs part of recovery step 3 (<<_jobs_recovery_step>>), whose worker part stays
a seam, and the drain participant of the job runner (<<_job_drain_participant>>).

== Core Types

_Requirements:_ link:{req}/01-architecture.adoc#PM-ARCH-7[PM-ARCH-7]

[horizontal]
`PeriodicSweep`:: Runs every step for every enrolled project whose recovery has finished, once per `INTERVAL` (3600
seconds), handing each step the instant `PENDING_ENTRY_MAX_AGE` (86400 seconds) before the run. The duration is a
compiled constant. A failed step is logged at WARN as `PM_RUNTIME-115` (`PERIODIC_SWEEP_STEP_FAILED`) and stops neither
the other steps nor the other projects.
`SweepStep`:: The contract of a step: its `Name` and `run(projectId, olderThan)`, which reports a
`RecoveryStep.Outcome` (`Done` with a report, or `Failed` with a reason it can name), never an exception for a failure
it can name.
`SweepStep.Name`:: The closed set of steps: `PENDING_ENTRY_RECORDS`.
`PendingEntryRecordsSweep`:: The step `PENDING_ENTRY_RECORDS`, over `PendingEntryStore` of `core.store`.

=== Component Interaction

[source]
----
PeriodicSweep.runOnce(now)            olderThan = now - PENDING_ENTRY_MAX_AGE
  for each enrolled, recovered project:
    ├─ PendingEntryRecordsSweep.run(projectId, olderThan)
    │    PendingEntryStore.entryIds()                      (lock-free, only names that parse as entry ids)
    │    workspace lock ─► ScopeTransaction of the workspace
    │      for each record created before olderThan:
    │        PendingEntryStore.remove(transaction, id)     (delete target)
    │        transaction.owe(pending_entry_removed)        (one audit record per record)
    │      commit (journal, apply, digests, close: owed records handed over)
    │    ──► Done("removed N pending entry records") | Failed(unreadable records kept, or the write failed)
    │
    └─ (the further steps the target adds, in their order)
----

== The Pending-Record Step

_Requirements:_ link:{req}/13-client-profiles.adoc#PM-CLIENT-1[PM-CLIENT-1], link:{req}/01-architecture.adoc#PM-ARCH-7[PM-ARCH-7]

The only evidence that nobody will come back for a pending entry record is its age, the creation instant the record
states. The step lists the candidates without a lock, then opens one lock transaction on the workspace lock and one
`ScopeTransaction` of the workspace, and decides on each record as it reads it under that lock, so a record created or
replaced meanwhile is judged as it is now.

* A record created before the instant is removed as a delete target of that transaction, and the transaction owes one
  `pending_entry_removed` record (category `store`, details `entry_id`, `store`, `created_at` and `transaction_id`)
  for it (link:../adr/runtime-start/001-pending-entry-sweep-through-a-workspace-delete-transaction.adoc[ADR 001]). The
  `transaction_id` is the record's own, issued by `ScopeTransaction.recordId()`, never the id of the transaction: two
  records removed in one run carry two ids, and a record handed over again after a stop keeps its id, the key by which
  the reader of the audit log drops the duplicate
  (link:../../../pm-core/doc/adr/core-store/025-one-transaction-id-per-audit-record.adoc[`core-store` ADR 025]).
* A younger record is kept, and so is one created exactly at the instant.
* A file of `pending/` whose name does not parse as an entry id is never listed, so it is never selected.
* A record that cannot be read states no age: it is kept, and the step reports a failure naming it after the readable
  old records were removed.
* All removals of a run are one transaction, committed only if a record is removed. A stopped removal is completed by
  the recovery of the workspace, which hands the owed records over again.
* A workspace whose journal still waits for its recovery cannot be written: the step fails and removes nothing.

A run that removed records logs `PM_RUNTIME-23` (`PENDING_ENTRY_RECORDS_SWEPT`) with the count and the project.

[#_the_stalled_scope_detection]
== The Stalled-Scope Detection

_Requirements:_ link:https://github.com/plan-marshall/plan-marshall-documentation/blob/9b54d54/doc/requirements/01-architecture.adoc#PM-ARCH-8[PM-ARCH-8]

`StalledScopeDetector` decides on read whether a plan or an epic is held `stalled`
(link:../../../doc/specification/runtime-lifecycle/02-plan-pause-and-stalled-plans.adoc#stalled-plans[Runtime
Lifecycle Specification, Stalled Plans]). It takes a `View` of the scope: the project id, the `WorkflowStatus`, and
whether the scope is paused, rests in an operator wait, or is held for another kind. The workspace scope and an ended
scope never stall.

[horizontal]
`THRESHOLD`:: The compiled `600` seconds of
link:../../../doc/specification/timeouts/02-runtime-leases-operator-web.adoc#stalled-threshold[Timeouts & Budgets
Specification, Stalled Threshold]; the test reads the value from the specification.
`StalledHold`:: The hold: its kind `stalled`, the closed cause `NO_PROGRESS` (`no_progress`), the scope, the state the
scope rests in, the instant of the last transition or task progress and the idle seconds.
`Activity`:: What the detection found: the hold, or nothing, and its `needs_operator()` count (1 with a hold, 0
without), which a `needs_operator` summary counts on read.
`OperatorPort`:: Where the hold is announced: `holdOpened` when an episode begins, `holdReleased` when it clears by
itself, with the report `plan.hold_released`.

A scope is stalled when it has no pending condition, no active job, no active task, and has been idle at least the
threshold. The detector keeps the open episodes in memory, keyed by project, scope type and scope id: the first
detection of an episode hands one `AuditEvent.planStalled` record (`transition`, `warning`,
`details{scope_type, scope_id, state, cause, idle_since, idle_seconds}`,
link:../../../doc/specification/store-schemas/12-machine-stores.adoc#audit-log[Store Schemas Specification, Audit Log,
Stall records]) to the `AuditSink` and announces the hold; every further detection of the episode appends nothing. A
detection that finds the scope moved on ends the episode and announces the hold as released. The detector writes no
store: the status document gains no member, so the stall never reaches a stored or model-facing representation. The
acts a hold offers are `plan-and-epic-control`'s
(link:../adr/runtime-start/014-stall-derived-on-read-one-record-per-episode.adoc[ADR 014]).

[#_the_audit_chain_seam]
== The Audit Chain Seam

_Requirements:_ link:{req}/08-security.adoc#PM-SEC-6[PM-SEC-6], link:{req}/01-architecture.adoc#PM-ARCH-7[PM-ARCH-7]

Step 4 of `StartupSequence`, the bounded verification, verifies the audit chain through the seam
`AuditChainVerification`. Its implementation is `AuditVerification` of `runtime.audit`
(link:runtime-audit.adoc[Audit Trail (`runtime.audit`)]); the assembly passes `AuditChainVerification.NONE`, which
answers `NotVerified` for every start, until it wires that one.

[horizontal]
`Outcome.Intact`:: The chain is intact from its last checkpoint.
`Outcome.Broken(reason, firstBrokenLine, diagnostic)`:: The chain is broken. `reason` is one `BreakReason` of the closed
set of the specification, by wire name `link_broken`, `missing`, `reset`, `truncated` or `head_mismatch`.
`firstBrokenLine` (an `OptionalLong`, counted from 1 in the file the diagnostic names: the current log, the audit index
or a rotated file) is present exactly for `link_broken`; the record's constructor refuses a line for any other reason,
a missing one for `link_broken` and a line below 1. The factories are `Broken.linkBroken(line, diagnostic)` and
`Broken.withoutLine(reason, diagnostic)`. The diagnostic names the file and the position, never a key or a hash
secret.
`Outcome.NotVerified(reason)`:: The chain was not verified, for example because no chain or no key exists yet.

On a broken chain the start goes on. `StartupSequence` logs `PM_RUNTIME-108` (`AUDIT_CHAIN_BROKEN`,
`Audit chain broken (reason '%s', first broken line %s): %s; the start goes on`) with the reason, the first broken
line, `none` for every reason but `link_broken`, and the diagnostic, which names the file the line is counted in. It
hands one `audit_chain_broken` record to the audit sink (`category: security`, `outcome: failed`) with the details
`reason`, `first_broken_line` (for `link_broken` only) and `os_principal`, the running user, since the record is
machine-level. The diagnostic is not recorded: it may name more than the specification lets the record carry, and the
specification gives the record no detail for the file, so a recorded `first_broken_line` does not say which file it
counts in; only the log does. The outcome is carried in `Outcome.Ready`, and the status text of the verification
(`PM_RUNTIME-14`) names the reason, the line and the diagnostic. A sink that refuses the record never stops the start.

`Outcome.Broken` was changed in place from a record with one diagnostic, without a compatibility constructor
(link:../adr/runtime-start/011-broken-chain-outcome-carries-reason-and-line.adoc[ADR 011]).

[#_store_move_resume]
== Store Move Resume

_Requirements:_ link:{req}/07-credentials.adoc#PM-CRED-2[PM-CRED-2]

A move between the credential stores (`CredentialStoreMove` of
link:runtime-credentials.adoc[`runtime.credentials`]) or the first recording of a store that a stop cut leaves its
record `state/credential-store-move.json` (the record's `operation` says which). `CredentialStoreMoveResume.run()`
completes it through `CredentialStoreMove.resume()`:

* a first recording: phase `copying` with no store recorded removes the copy from the store being recorded and records
  again; phase `copying` with that store recorded (a stop between the switch and the rewrite of the record) and phase
  `switched` with it recorded finish the deletion of the key from the other store; phase `switched` without it is
  refused and deletes nothing (link:../adr/runtime-credentials/008-the-first-recording-is-resumable.adoc[ADR 008]);
* phase `copying` with the old store recorded: the copies are deleted from the target and the move runs again from the
  first entry, the old store holding every entry;
* phase `copying` with the target recorded (a stop between the switch and the rewrite of the record): the move is
  treated as switched, nothing is deleted from or copied into the recorded target, and the deletion from the old store
  is finished;
* phase `switched` with the target recorded: the deletion from the old store is finished and the record ended;
* phase `switched` with another or no store recorded: the resume is refused with an `IllegalStateException`, nothing
  is deleted from either store and the record is kept;
* no record: no move is open, nothing happens.

`run()` returns the record it resumed from, as it was found, and logs `PM_RUNTIME-29`
(`CREDENTIAL_STORE_MOVE_RESUMED`) for a move and `PM_RUNTIME-32` (`CREDENTIAL_STORE_FIRST_RECORDING_RESUMED`) for a
first recording, with their stores and that phase; the move itself appends its `credential_store_moved` audit record,
then ends the record and logs `PM_RUNTIME-28`, so a move whose audit record a stop or a failing sink lost is finished
and audited again by the next start. A move that fails again before the switch fails with `credential_store_failed`
and leaves the old store recorded; a copy that cannot be removed from the target, or a deletion the old store refuses,
fails with the store's reason and leaves the record for the next start.

The resume is machine-wide and runs once after the bind; it is no
`RecoveryStep`, and `StartupSequence`, `RecoveryStep` and `ProjectRecovery` are unchanged
(link:../adr/runtime-start/012-store-move-resumed-machine-wide-after-the-bind.adoc[ADR 012]). The assembly builds it
from the move and calls it:

[source,java]
----
var move = new CredentialStoreMove(base, choice, lockManager, auditSink, user, clock);
new CredentialStoreMoveResume(move).run();     // once, after the bind
----

[#_jobs_recovery_step]
== The Jobs Part of Step 3

_Requirements:_ link:{req}/01-architecture.adoc#PM-ARCH-7[PM-ARCH-7], link:{req}/06-execution.adoc#PM-EXEC-4[PM-EXEC-4]

Step 3 of the per-project recovery, `RecoveryStep.Name.JOBS_AND_WORKERS`, settles the jobs and workers a previous
runtime instance left. `JobRecoveryStep` is its jobs part: it reads every record of the project's job records
(`JobRecordStore.ofProject`) without a lock and settles every one left `queued` or `running` as `ended`/`killed` by
outcome row 4. A job is never adopted and never executed again. A record left `queued` never started: nothing is
signalled. A record left `running` is settled by the first matching rule:

[cols="1,2,2"]
|===
|Rule |When |What is signalled

|(a) |its `execution` is `in_process`: the operation died with the previous runtime |nothing; no orphan note
|(b) |its `spawned_at` lies before the boot time of the system: the process cannot have survived the reboot |nothing
|(c) |its `pid` is `null`: the runtime ended between the spawn and the post-spawn replace |nothing; the step hands the
audit sink one `job_recovered` record (category `store`, outcome `succeeded`, details `project_id`, `job_id` and
`note: orphan unidentifiable`), which it builds itself
|(d) |otherwise |the group is probed with `kill(-pgid, 0)`; a live group, which within one boot is the job's group, is
terminated with steps 1 to 3 of the `TerminationProtocol`; a group that no longer exists needs no termination
|===

The settled record carries the signal `runtime_restart` for a job nothing was sent to, the signal the termination
ended with for a terminated group (`SIGTERM` for a group that exited, `SIGKILL` for one that was killed, `runtime_restart`
when no signal reached it or one was refused), and none for an in-process operation. The settlement runs through
`JobSettlement`: the fate first, then the release of the slot that the caller's `JobRecoveryStep.Slots` names for the
job; `Slots.NONE` names none. Every signal goes through `ProcessGroupSignals`, so a test asserts at the lowest signalling
call that rules (a) to (c) send none.

The step reports the jobs settled per rule, the groups terminated and the workers among them. The *worker part* of the
step (the fence of a worker's generation, the revocation of its token, the release of its task lease and the removal of
its job-private directory) belongs to the launch of workers and is a seam: a worker's record is settled like every
other, and the report names the part `not implemented in this runtime`
(link:../adr/runtime-start/013-jobs-recovery-step-worker-part-a-seam.adoc[ADR 013]).

The step fails, and the recovery of its project stops there, when the job records cannot be read, an orphan note
cannot be handed over, or a fate cannot be recorded; a job whose fate was not recorded is settled by the next recovery.

`ProjectRecovery.withEnrolment` has an overload that takes the `JobRecoveryStep`: it places the step as step 3 in place
of any step named `JOBS_AND_WORKERS` in the list, as the two enrolment steps are placed. The overload without it is
unchanged and keeps the step the list holds, a seam included:

[source,java]
----
var signals = ProcessGroupSignals.system();
var jobs = new JobRecoveryStep(base, lockManager,
        new JobRecoveryStep.Signalling(signals, new TerminationProtocol(signals)), auditSink, bootTime,
        JobRecoveryStep.Slots.NONE, clock);
var recovery = ProjectRecovery.withEnrolment(store, check, enrolments, lockManager, jobs, otherSteps, executor);
----

The boot time of the system and the slots of the jobs are the caller's: this package reads neither.

[#_job_drain_participant]
== The Job Drain Participant

_Requirements:_ link:{req}/01-architecture.adoc#PM-ARCH-7[PM-ARCH-7], link:{req}/06-execution.adoc#PM-EXEC-4[PM-EXEC-4]

`JobDrainParticipant` (name `jobs`) is the `DrainParticipant` of `SubprocessJobRunner`:

[horizontal]
`stopAdmitting()`:: The runner stops admitting jobs under its admission lock, the lock every admission decision takes;
from now on a job whose start is asked for is recorded `queued` and never spawned.
`endIdle()`:: Nothing: a job is never idle.
`awaitQuiet(deadline)`:: Waits for every running job until the drain timeout's deadline and answers whether none runs
any more.
`terminateRemaining()`:: Cancels every job still running with the cause `DRAIN`, which the runner carries out with the
termination protocol and settles `killed` (row 4), and waits for each settlement at most the grace period and 10 seconds
(`TERMINATION_WAIT`). It answers the jobs it terminated.
`close()`:: Settles every job still `queued` as `killed` by row 4, without a signal; a queued job holds no slot.

Because the stop and every admission decision take one lock, a job admitted before the stop is among the running jobs
the drain waits for, and a job created after it is among the queued jobs `close()` settles.

== Registering the Steps

_Requirements:_ link:{req}/01-architecture.adoc#PM-ARCH-7[PM-ARCH-7]

The package ships no seam factory and no default list of steps. The caller, the assembly `pm-mcp-server` of
`plan-marshall-mcp`, builds the steps from the runtime's base directory, lock manager, audit sink and clock and hands
them to the sweep in the order they run:

[source,java]
----
List<SweepStep> steps = List.of(
        new PendingEntryRecordsSweep(base, lockManager, auditSink, clock));
var sweep = new PeriodicSweep(enrolledProjects, projectRecovery::isRecovered, steps, clock);
sweep.start(executor);     // first run one INTERVAL from now; stop() for the drain
----

`RecoveryStep.notImplemented` stays: the per-project recovery still has steps that are named seams. Only the sweep side
lost its factory.

== Pitfalls

_Requirements:_ link:{req}/01-architecture.adoc#PM-ARCH-7[PM-ARCH-7]

1. **Age is the only evidence**: never select a record because its name does not parse or its content is odd; an
   unreadable record is kept and reported. A name that is no entry id is not an entry.
2. **Decide under the lock**: the lock-free listing names candidates only; the age is read again under the workspace
   lock before a record is removed.
3. **Remove through the journal**: a record removed outside the workspace transaction leaves its sidecar entry behind
   and is reported as tampered; the delete target drops both together.
4. **One audit record per removed record, owed by the transaction**: append nothing to the audit log after the commit;
   the owed record is handed over at least once, also after a crash. Give it `transaction.recordId()`, never
   `transaction.transactionId()`.
5. **A stall is derived, never stored**: the detection writes no status member and no store; its one record per episode
   is appended inside the per-scope computation, and detection with its announcements is serialized on the detector, so
   two racing reads append one record and announce no transition twice. A refused record leaves the episode open for the
   next read.
6. **Never signal a job nobody can identify**: an in-process operation, a job spawned before the boot and a job whose
   record carries no PID are settled without a signal. Only a group probed live within this boot is terminated; a
   recorded PID of an earlier boot may belong to anyone now.
7. **Never adopt a job of a previous runtime**: every unsettled job is settled `killed`, never resumed or started again.
