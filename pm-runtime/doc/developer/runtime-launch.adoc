= Worker Launch and Harness Enrolment (`runtime.launch`)
:toc: left
:toclevels: 2
:nofooter:

link:../../README.adoc[`pm-runtime`] » Worker Launch

== What the package is for

`de.planmarshall.runtime.launch` composes the launch of a worker, the job of kind `llm`: the argument vector, the
environment, the working directory, the per-call MCP configuration and the `worker` block of its job record. It also
owns the machine's harness enrolment store and the launch-time verification of the enrolled executable. It never
starts a process of its own: the job runner starts the composed vector, and the supervisor decides when.

The package is the one place that reads the shape of a profile's `headless` block. Everything a launch contains is
server-owned; no element is read from a file a model can write.

== Main types

`HeadlessBlock`::
The launch contract of one harness profile, projected out of its `headless` block: the executable, the argument-vector
template with its typed slots, the per-class templates, the agent mode, the MCP delivery, the launch environment, the
model tiers and efforts, the supported version range, the update evidence, the resource tools, the per-worker data
home, the session residue, the resumability and the writable sub-paths.

`LaunchComposer`::
Composes a `WorkerLaunch` from a `LaunchRequest`. It renders a tier of the default assignment into the model the
harness maps it to (`HeadlessBlock.tierModel`), narrows an effort the harness does not accept to the nearest accepted
lower value, fixes the working directory (the plan worktree, the project checkout, or the empty `cwd/` of a
`zero_tool` worker), fills only the slots the template declares, withholds the ephemeral flag for a role that may
resume, writes the prompt file and the result schema into the job-private directory, mints the job token and composes
the `worker` block.

`PromptComposer`::
Renders the launch prompt in the specification's order: the shim paragraph, the core conduct skill, the task-protocol
skill, the role skill and its further skills — the shared prefix, byte-identical for every launch of a role on the same
skill digests — then, per launch, the task's skills and the contract envelope of a fresh worker. The writing skill is
owned here and added from the link schemas alone. A skill that does not resolve fails the composition; no worker ever
runs with a required skill missing.

`FreeTextDerivation`::
Derives whether a task writes free text from its entity's link schemas: a parameter of type `text`, or a named
parameter schema with a `string` field that has neither `enum` nor `pattern`. A closed value never triggers the writing
skill.

`HarnessEnrolmentStore`::
The machine-wide `harnesses.json` and its HMAC sidecar. Every read verifies the pair under the enrolment integrity key
first; every write holds `locks/harnesses.lock` and writes the canonical file and its sidecar owner-only. One API
serves the onboarding's `harness.enrol` and `pm-operator enrol-harness`. A file that fails its check is re-baselined by
the next enrolment with the named client only. Every entry names a serving program by its executable path, digest and
version; an entry that carries an undeclared member is refused `harness_store_unreadable`. A document whose top-level
`harnesses` member is missing, `null` or not an object is refused the same way, so a reader never sees such a document
as an empty store; only the re-baseline of a new enrolment treats it as empty, as it does a tampered file, and an empty
`harnesses` object stays a valid empty store
(link:../adr/runtime-launch/011-a-store-without-a-top-level-harnesses-object-is-unreadable.adoc[ADR 011]).

`HarnessVerifier`::
Verifies the harness before every spawn: the store's integrity, the enrolment, the digest of the executable, and,
where the digest changed, the update evidence and then the version probe. An accepted self-update rewrites the store
and is audited `harness_updated`; every other case returns a `HarnessVerification.Refused` carrying a `LaunchRefusal`.

`JobTokenStore`::
Resolves a presented token's SHA-256 to the generation it was minted for, and revokes the token with the job's fate (the runner revokes it once the settlement has recorded the fate, and the supervision pass revokes it once more). The
token itself is never stored.

`WorkerStart` (in `runtime.job`)::
The supervisor's start of a composed launch: the launch, the verified enrolment, the scope, the budget and the
writable sub-paths. `SubprocessJobRunner.startWorker` writes the record with the `worker` block, starts the composed
argument vector and revokes the token once the settlement has recorded the fate. `refuseWorker` records a launch the runtime refused with the
fate `refused`, the reason and the block, in one write and without a process.

`ModelSlotScheduler`::
The admission of the machine model slots. Every running worker, warm or fresh, holds one of the `model_slots` slots of
`model-slots.json` from its spawn to its exit; a warm worker holds it for its whole generation, idle or not. The cap is
`model_slots` of `machine-config.json`, its compiled default `2` and its bounds `1` to `16`. `request` answers
`Granted`, `Queued` (in the FIFO of the store) or `Deferred` (another writer worker of the plan holds a slot or waits);
`release` and `releasePlan(projectId, planId)` free what a settled worker or a paused plan held and return the leases
the freed slots admitted. Admission decides in one transaction of `ModelSlotStore` (`core.store`), so two claims never
see the same free slot.

`HarnessVerification` (this package)::
The outcome of the launch-time verification, `Accepted` or `Refused`. It shares its simple name with
`de.planmarshall.core.profile.HarnessVerification`, the admission precondition of a verification of an unknown harness;
`WorkerSupervisor` imports this package's type. The collision is recorded and deliberately not renamed: the rename
package renamed the harness identifier and the fields that carry it, and named neither class.

== How the parts work together

[source,text]
----LaunchRequest ──> LaunchComposer ──> WorkerVectorCheck ──> WorkerLaunch ──> job runner (kind llm)
      │                  │
      │                  ├── PromptComposer ──> prompt file, prompt digest, delivered skills
      │                  ├── HeadlessBlock  ──> argv, env, MCP configuration
      │                  └── JobTokens      ──> token (returned), SHA-256 (worker block)
      │
HarnessVerifier ──> HarnessEnrolmentStore ──> harnesses.json + harnesses.json.hmac
      │
      └── update evidence ──> version probe ──> supported range ──> accepted self-update
----

A caller verifies the harness first and passes the accepted `HarnessEnrolment` into the `LaunchRequest`; the composer
therefore never trusts an unverified build. The job record's `worker` block is composed from the same values as the
argument vector, so the two cannot disagree, and the vector the composition made is parsed back before the launch is
built (§ The Composed-Vector Check).

== The Composed-Vector Check

`WorkerVectorCheck` is the last step of the composition. `LaunchComposer.composeArgv` calls it on the vector it has
filled and prefixed with the enrolled executable, after the ephemeral flag was withheld from the template and before
the `WorkerLaunch` is built; a violation throws `CompositionException.argumentRejected`, whose `refusal()` is
`LaunchRefusal.ARGUMENT_REJECTED` (`argument_rejected`). The supervisor records the refusal through the `refuseWorker`
path it already uses, with the fate `refused`, and needs no change of its own (ADR
link:../adr/runtime-launch/010-the-composed-vector-is-parsed-back.adoc[runtime-launch/010]).

The check **parses the rendered vector back** against the template it was rendered from. It splits each template element
into its literal fragments and its slot markers, requires every fragment at the position the previous one ended, and
reads the text between two fragments as the value of the slot the template names. It never renders again: re-running
`fill` would compare the composition with itself. The answer is the first violated rule and the position of the element,
never the value, so the refusal can be recorded and shown without the vector in it.

[cols="1,2,3"]
|===
|Rule |Requires |Refuses

|(a) |element 0 is the enrolled executable path |another executable, or an empty vector
|(b) |every element corresponds to one template element; the literal parts are reproduced exactly |an altered literal, a dropped or inserted element, an unreproducible gap
|(c) |every typed slot value matches the closed grammar of its slot |see the grammar table below
|(d) |no element outside the two JSON slots contains a shell metacharacter |`\|`, `;`, `&`, `$`, `` ` ``, `>`, `<` outside `{{mcp_config}}` and `{{agent}}`
|(e) |no element that is neither a template element nor a slot value |an element a profile edit or a composer defect added
|===

The closed grammar of each typed slot:

[cols="1,3"]
|===
|Slot |Grammar

|`{{model}}` |the model the composer resolved after rendering the tier — a value the effective catalogue already allowed
|`{{effort}}` |one of the efforts the profile's `model_efforts` accepts for that model
|`{{prompt_file}}`, `{{result_schema}}` |an absolute normalized path below the job-private directory
|`{{cwd}}` |the working directory the composer fixed for the launch
|`{{session_id}}` |a harness session id, `[A-Za-z0-9._-]{1,128}`
|`{{tools}}` |a comma list whose every element is one of the role's tools, the harness's resource tools included
|`{{mcp_config}}` |a JSON object of the composed shape, `\{"mcpServers":\{"pm-job":\{…\}\}}`; exempt from rule (d)
|`{{agent}}` |a JSON object of the composed shape, `\{"pm-job":\{…\}\}`; exempt from rule (d)
|===

A gap in rule (b) is admitted for exactly one reason: a slot with no value removes its template element, and the flag
element before it is removed with it (`--json-schema` and its value, `--mcp-config` and its value). The ephemeral flag a
role that may resume must not receive is withheld from the **template** before it is rendered, not from the rendered
vector: the template and the vector therefore correspond element for element, no gap is left to explain, and a slot value
that happens to contain the flag's text is never mistaken for the flag.

Tested by `WorkerVectorCheckTest` (the four template shapes of the fixture profile, one refusing vector per rule, a slot
grammar per slot, a metacharacter per character, and the path through a real `LaunchComposer` and a recording starter) and
`LaunchComposerTest` (the `argument_rejected` refusal of a template that renders a metacharacter into a slot, the files a
refused composition leaves behind, and the digest of the conforming fixture vector).

== The Model Slots

[source,text]
----
caller ──> ModelSlotScheduler.request(request)
              └─ ModelSlotStore.update(document -> …)         one transaction on locks/model-slots.lock
                   1. reap: drop every slot and waiting worker whose runtime is not alive
                   2. already granted or waiting? answer that place
                   3. writer of a plan that holds or waits? Deferred("writer_holds_plan")
                   4. append the waiting entry (with its form) and admit from the head while slots < cap
                   5. return Granted, Queued or Deferred
----

* *The cap holds under concurrent claims*: every admission reads the slots and writes the one it adds in the same
  transaction, so the document never holds more than `model_slots` leases.
* *FIFO*: a request is appended to `waiting` and admission takes from its head only; a release or a pause admits the
  head first, and never a worker behind it.
* *One writer per plan*: at most one `writer` worker of a plan of one project holds a slot or waits for one — the
  identity is the project together with the plan. A second writer is `Deferred` and its task stays `queued`; `read_only`
  and `zero_tool` workers of the plan run beside it within the cap.
* *Warm holds the slot*: a slot is released by its worker's fate, not by an idle wait; `releasePlan` is the one act that
  releases a live plan's slots early, and it drops the plan's waiting workers too.
* *Stale slots are reaped first*: a slot or waiting entry whose runtime died is dropped in the admission transaction,
  before the cap is applied, so a slot a killed daemon left never keeps a worker out. The recovery of the runtime
  settles the instance's jobs before an admission runs, so the worker of a reaped slot has ended.
* *The budget starts at the spawn*: the time a worker waits for a slot is outside its budget. The metrics row that
  records it as `queued_ms` is the settlement's; no class of this package writes it.

The design is recorded in link:../adr/runtime-launch/005-model-slot-admission-in-one-store-transaction.adoc[ADR
runtime-launch/005]. Tested by `ModelSlotSchedulerTest` (the FIFO, eight concurrent claims against a cap of two, the
one-writer rule beside a `read_only` worker and across two projects, a stale slot reaped, a paused plan releasing its
held slots and dropping its waiting workers, the bounds of the cap) and `ModelSlotStoreTest` (the document round trip,
the refused duplicates and a writer without a plan).

== Invariants

* A launch never runs with a required skill missing: a skill that does not resolve, renders empty, or whose digest
  changed after the role was read fails the composition (`prompt_composition_failed`).
* A launch never runs a vector the composition cannot account for: every element corresponds to a template element, each
  typed slot value matches the grammar of its slot, and no element outside the two JSON slots carries a shell
  metacharacter (`argument_rejected`).
* The shared prefix contains nothing per launch: the job token, an identifier, a time and a fact of a task follow it.
* A `zero_tool` worker has no tool, no MCP configuration, no `job_token_sha256`, and runs in the empty `cwd/` of its
  job-private directory.
* A changed executable is never its own witness: the update evidence is checked before the version probe runs.
* The job token exists only in the composed launch and in the relay's MCP configuration; the record holds its SHA-256.
* The model slots never exceed their count, a plan holds at most one writer slot, and a paused plan holds none.

== Failure modes

|===
|Failure |Result

|The harness is not enrolled |`harness_not_enrolled`
|The store fails its per-use check or its HMAC |`harness_tampered` (audited `enrolment_tampered`)
|The store is verified but unreadable |`harness_store_unreadable`
|The executable changed without evidence, or the evidence failed |`harness_update_unverified`
|The probed version lies outside the supported range |`harness_version_unsupported`
|The prompt cannot be composed |`prompt_composition_failed`
|The composed vector does not conform to its template and the slot grammars |`argument_rejected` (rule and element position, never the value)
|The machine's cap lies outside `1` to `16` |the scheduler's constructor refuses it (`IllegalArgumentException`)
|A writer requests a slot while its plan's writer holds one |`Deferred("writer_holds_plan")`; the task stays `queued`
|===

A refusal names the act that resolves it (`LaunchRefusal.resolvingAct`): a new enrolment for every harness refusal, a
restored skill or schema for the composition failure, and a corrected profile template or a new enrolment for a vector
the check rejects.

== Extending it

* A new launch slot is added to `HeadlessBlock`'s projection and filled in `LaunchComposer.composeArgv`; it must also
  reach the profile validator's slot set and the closed grammar of `WorkerVectorCheck`. A slot the check does not know is
  refused, which is the fail-closed direction.
* A new harness profile needs no code: the profile's `headless` block is data. A harness whose MCP configuration is not
  exclusive declares no worker class.
* The update-evidence port (`HarnessVerifier.EvidenceCheck`) is where a platform check for `code_signature` or
  `package_provenance` plugs in. The default refuses every change, which is the fail-closed direction.
* A new class of worker (a fourth `class`) is added to the profile's class block and to `ModelSlotStore.WorkerClass`;
  the one-writer rule applies to `writer` alone.

== The Activity Projection and Its Verification

`HeadlessBlock.of` projects the profile's `usage` pointers and its `events` mapping beside the launch contract, so the
runtime maps a worker's output line and a turn's usage without reading the profile document
(link:../../../pm-core/doc/adr/core-queue/007-the-events-mapping-is-projected.adoc[core-queue ADR 007]).

`HarnessEventVerification.verify(mapping, usagePointers, recordedOutput)` computes the `events` stage of the profile
verification: it maps a recorded output through the same mapper the stream reader uses and records per declared kind
`reported` or `missing`; a kind that never appears fails the stage, and a harness whose profile declares no event stream
is not measured by it (link:../adr/runtime-launch/006-the-events-stage-maps-a-recorded-output.adoc[ADR 006]). The
recorded output is a fixture written for the test. No class writes the computed result into the verification record and
the enrolment (<<_not_implemented_here>>).

== Not Implemented Here

* *The events stage is computed, not recorded*: the computation here returns a `Result`; recording it in
  `VerificationRecord.stages` and `HarnessEnrolment.events` is the verification path's, which runs the profile
  verification and writes its record. The recorded outputs per shipped harness version are written where the shipped
  profiles live.
* *A refused launch is not counted as a start failure*: a refused launch (a `HarnessVerification.Refused` from
  `HarnessVerifier`, which `SubprocessJobRunner.refuseWorker` turns into a refused `JobId`) is a start failure the
  supervisor counts per role and harness through `StartFailureGuard`, closing the tasks of the role `lost` with
  `role_unavailable` after the compiled count; no production code calls `StartFailureGuard.startFailed`
  (link:runtime-worker.adoc[`runtime.worker`] records the same). The warm offer, the re-delivery, the offer bound,
  harness activation and the `skills_not_loaded` submit refusal of Model Work § Skill Delivery Record & Re-Delivery are
  the task protocol's.
* *Output and usage reading*: the mapping of the output stream to activity, the per-turn usage and the result parsing
  are not this package's (Model Work § Output Read While the Worker Runs).
* *The Linux child subreaper* of the launcher (`PR_SET_CHILD_SUBREAPER` in `pm-exec`, a binary of `pm-mcp-clients`) is
  not part of this repository; the runtime's descendant recording, sweep and audit are implemented
  (ADR runtime-launch/003).

== The Usage Report and the Start Context
_Requirements: link:../../../doc/Traceability.adoc#PM-CLIENT-5[§ PM-CLIENT-5], link:../../../doc/Traceability.adoc#PM-WF-14[§ PM-WF-14]_

`HarnessEnrolment.UsageReport` carries the harness's per-figure usage results and, for a verified profile, the start
context per class and model: the first-turn input, cache read and cache creation, an integer or `unmeasured`.
`HarnessEnrolmentStore` reads and writes the optional `start_context` array beside `source` and `figures`, and refuses an
unknown class or a token value that is neither an integer nor `unmeasured`; its figure keys are the report's
(`input`, `output`, `cache_read`, `cache_creation`, `reasoning`, `tool_uses`). The harness list of the onboarding and of
the machine's settings (`pm-mcp-clients`) renders the report as complete, partial with the missing figures, or
not reported, and the start context beside it.

link:../adr/runtime-launch/007-the-usage-report-keeps-the-start-context.adoc[ADR 007]: the usage report kept with an
enrolment carries the start context.

== Installing a Verified Usage Report

_Requirements: link:../../../doc/Traceability.adoc#PM-CLIENT-5[§ PM-CLIENT-5]_

`VerifiedUsage` is the seam the install path calls when a verified profile's `usage_report` is written into the enrolment.
`install` takes the evaluations of one harness and version in the order they ran and returns the
`HarnessEnrolment.UsageReport`: the figures of the first run mapped through `UsageReport.of` (the boundary that names
`input_tokens` as `input` and `output_tokens` as `output`, and refuses any figure outside the store's closed set —
including the cost, which the seam therefore leaves out before it calls `of`), the start context converted from
`ProfileStages.StartContext` to the enrolment's own type, and the source `verified`.

The figures are trusted only after the evaluation was repeated. `trusted` answers the condition — at least
`REQUIRED_EVALUATIONS` (`2`) runs that agree on every report figure's status **and on the start context** (the worker
class, the model and the first-turn tokens) — and `install` refuses an untrusted list with `harness_usage_not_repeated`
or `harness_usage_disagrees` instead of writing a number one run produced. What must agree about the figures is which
ones the harness reports, not their values: two runs of different prompts legitimately count different tokens. A start
context only one run measured is not a repeated measurement, so it is refused too.

The operator verb that writes the enrolment, the profile and the report under the store's lock stays in
`plan-marshall-mcp`; what is built here is the seam it calls. An accepted self-update drops a **verified** report
measured on the previous build (`HarnessEnrolment.updated`), so a list never shows an old version's coverage beside a
new build; a `DECLARED` report is the profile's own declaration, not a measurement of a build, so it stays.
`VerifiedUsageTest` covers the mapping, the cost left out, the start context across the seam and both refusals.

link:../adr/runtime-launch/008-a-verified-usage-report-is-installed-from-a-repeated-evaluation.adoc[ADR 008]: a verified
usage report is installed only from a repeated evaluation.

== The Rename and Its Compatibility

The harness side is named harness throughout the code: `HarnessEnrolment.harnessId()` and the store's parameters, the
launch refusal's resolving act, the eligibility refusal and the supervisor's records. The store's file format did not
change: `harnesses.json` is keyed by the harness id value and no entry member was ever named `client_id`, so a file
written before the rename reads as before, and the next enrolment rewrites it in the same shape. The audit detail key is
`harness_id` for records written now; records already written keep `client_id`, which nothing in this module reads as a
key. The two carriers with a former member name are the profile document and the verification record: each reader
accepts `client_id` where `harness_id` is absent, writes only `harness_id`, and refuses a document that carries both.
