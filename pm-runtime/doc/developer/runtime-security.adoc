== Purpose
_Requirements: link:{docs}/Requirements.adoc#PM-SEC-4[PM-SEC-4]_

Package `de.planmarshall.runtime.security` of `pm-runtime` holds what the authentication of the daemon resolves a
presented credential through: the kinds of token it accepts, the registries that resolve a token's hash to the job or
the paired device it was minted for, and the constant-time comparison and digest of secrets. The package holds no
listener and no request path; the assembly `pm-mcp-server` authenticates a request and asks these seams.

== Main Types
_Requirements: link:{docs}/Requirements.adoc#PM-SEC-4[PM-SEC-4]_

[cols="1,3",options="header"]
|===
|Type |What it is

|link:{src}/CredentialKind.java[`CredentialKind`]
|The closed kinds of token the runtime accepts, each with its own identity provider: `RUNTIME` (the runtime token of
`run/runtime.token`), `JOB` (a worker's job token, header `PM-MCP-Job-Token`) and `DEVICE` (a paired browser's device
secret, `pmw_…`).

|link:{src}/JobTokenRegistry.java[`JobTokenRegistry`]
|`resolve(tokenSha256)` → the `JobBinding(jobId)` the token was minted for, or empty for an unknown token. Only the hash is
stored (in the job record); a revoked token still resolves, so its calls are answered by the tool handler, never `401`.

|link:{src}/DeviceRegistry.java[`DeviceRegistry`]
|`resolve(secretSha256)` → the device id, or empty for an unknown, revoked or expired secret. The secret has the prefix
`pmw_`; the registry is checked on every request without a cache (the web device store).

|link:{src}/Secrets.java[`Secrets`]
|`sha256(secret)` over the UTF-8 bytes, and `constantTimeEquals(expected, presented)` through `MessageDigest.isEqual`.
|===

== Which Kind Counts Where

The listener a request arrived on fixes which kinds count:

* the runtime token everywhere on the Unix socket;
* the job token on `/mcp` of the Unix socket only;
* the device secret on the web listener only.

A credential of the wrong kind for the listener is not resolved at all. The three kinds are a closed set: a new kind is
a new constant here and a new branch in the assembly's authenticator, never an open string.

Only a hash of a secret is persisted. The job token's SHA-256 is in the job record, and the device secret's SHA-256 is in
the web device store; neither store holds the secret itself. A presented secret is hashed with `Secrets.sha256` and
compared with `Secrets.constantTimeEquals`, so the time a comparison takes does not say where two values differ.

== Invariants and Failure Modes

* *Resolution answers empty, not an exception.* An unknown token is an empty `Optional`; the caller answers `401` and
  nothing is logged with the presented value.
* *A revoked job token resolves.* The job record keeps the hash after a revocation so a call still reaches the tool
  handler, which answers that the job is no longer active. Treating a revoked token as unknown would turn that answer
  into a transport error.
* *The device registry is uncached.* Each request asks the store, so a revocation or an expiry takes effect on the next
  request.
* *No secret reaches a log, an exception or an audit detail.* Neither registry, nor `Secrets`, logs its input. A message
  names the kind and the outcome, never the value or its hash.
* *Comparison is constant-time.* Never use `String.equals` or `Arrays.equals` on a secret or a digest of one.

== Extending the Package

* A new credential kind: add the constant to `CredentialKind`, add the resolution path to the assembly's authenticator,
  and state on which listener the kind counts.
* A new resolution source: implement `JobTokenRegistry` or `DeviceRegistry` behind the seam and wire it in the assembly.
  The interface stays two methods; the store behind it is not this package's.
* A new digest: use `Secrets`, not a local `MessageDigest`, so one spelling of the algorithm and one comparison rule
  exist.

== Testing

The package has no unit test of its own in this module's test tree yet: `CredentialKind`, the two registries and
`Secrets` are exercised through the assembly's authentication path, which implements the registries. A test added here
should cover:

* the three constants and the listener each one counts on;
* a resolved and an unknown token for both registries, and a revoked job token that still resolves;
* the UTF-8 digest of `Secrets.sha256` and the equal and unequal cases of `constantTimeEquals`, with an equal prefix and
  equal length.
