== Purpose

_Requirements:_ link:{req}/16-model-work.adoc#PM-WORK-6[PM-WORK-6], link:{req}/06-execution.adoc#PM-EXEC-5[PM-EXEC-5], link:{req}/06-execution.adoc#PM-EXEC-6[PM-EXEC-6]

Package `de.planmarshall.runtime.corpus` of `pm-runtime` holds the two HTTP parts of the fetch of the corpus sources, each through `cui-http`: the HTTPS source repository and the Git LFS object download.
The HTTPS source repository is link:{src}/HuggingFaceSourceRepository.java[`HuggingFaceSourceRepository`], which implements `SourceRepository` of `pm-core` for a manifest whose fetch is the HTTPS one; the Git LFS part is link:{src}/LfsBatchClient.java[`LfsBatchClient`], which implements `LfsObjectSource` of `pm-core` (see link:../../../pm-core/doc/developer/core-role-corpus.adoc[`core-role-corpus.adoc`]).
The git part reads an LFS file as its pointer; `LfsBatchClient` downloads the object the pointer names over HTTP, never through a git filter driver, and `HuggingFaceSourceRepository` reads a Hugging Face dataset at its pinned commit, never through a git client.
`pm-mcp-server` composes them with `JGitSourceRepository` of `pm-provider-git` into a `CorpusImport` (link:../../../doc/adr/006-corpus-fetch-split-across-pm-core-pm-provider-git-and-pm-runtime.adoc[ADR 006], as amended for the HTTPS fetch).

== HTTPS Source Repository

_Requirements:_ link:{req}/16-model-work.adoc#PM-WORK-6[PM-WORK-6], link:{req}/06-execution.adoc#PM-EXEC-5[PM-EXEC-5]

`HuggingFaceSourceRepository` implements `SourceRepository` for a source whose manifest states the `huggingface` fetch: a Hugging Face dataset read at its pinned commit over HTTPS. It sits beside `LfsBatchClient`.

. `prepare(cacheRoot, manifest)` answers `SourceFetch.done` and makes no request and creates nothing: the files are read over HTTPS, so there is no cache repository to prepare.
. `fetchCommit(cacheRoot, manifest)` confirms the pin with one `GET` of the dataset's revision, `<host>/api/datasets/<owner>/<name>/revision/<commit>`, and stores nothing. A `200` is the pinned commit (`done`); a `404` is a commit the dataset does not have (`PIN_MISSING`); any other status, a request that got no answer and a refused request are `UNREACHABLE`. This is the amended `fetchCommit` contract: the commit it confirms is made readable by `readFile` and by `prepare`, and the step may create and store nothing, so a source fetched over HTTPS answers `prepare` and `fetchCommit` without a cache repository.
. `readFile(cacheRoot, manifest, path)` reads one file at the pinned commit with one `GET` of `<repository>/raw/<commit>/<path>`, which serves the file as it is stored, a file in Git LFS as its pointer; the pointer's object comes from an `LfsObjectSource` (`LfsBatchClient`) exactly as for a git source. The delivered bytes are `FETCHED`; the import's hash check decides whether they are the file's SHA-256, so bytes that are not are `hash_mismatch` and the run `FAILED`.

=== URL and Timeout Rules

Every URL is built from the repository: the dataset is the path below `/datasets/`, so the repository URL must be `<host>/datasets/<owner>/<name>`, and a repository that is not such a URL is `UNREACHABLE` before anything is sent.
Every request goes to an `https` URL without user information; a repository URL without scheme or host, or a repository that is not `https`, is refused before anything is sent.
The package-private constructor admits plain `http` to a loopback address as well, for the mock web server of the tests.
Every request is bounded by the compiled connect timeout `CONNECT_TIMEOUT_SECONDS` (10 s) and read timeout `READ_TIMEOUT_SECONDS` (60 s).

=== Outcomes of the HTTPS Fetch

_Requirements:_ link:{req}/16-model-work.adoc#PM-WORK-6[PM-WORK-6]

[cols="3,1",options="header"]
|===
|What happens |`SourceFetch.Outcome`

|the URL names no scheme or no host, is not `https`, carries user information, or is not a Hugging Face dataset URL; the dataset API does not answer, times out or is interrupted; the revision API answers a status other than 200 and 404; the raw endpoint answers a status other than 200 and 404
|`UNREACHABLE`

|the revision API answers 404 (the dataset has no such commit); the raw endpoint answers 404 (the file is absent at the pin)
|`PIN_MISSING`

|`prepare`, a revision confirmed with 200 (each without content), and the raw endpoint having delivered bytes
|`FETCHED`
|===

Every `UNREACHABLE` and `PIN_MISSING` outcome is logged as WARN `PM_RUNTIME-127` `CORPUS_HTTPS_SOURCE_UNAVAILABLE` with the repository without user information, query or fragment, and the detail; a repository URL without scheme or host is named `<a URL without scheme or host>` and none of its parts is logged, so writing the WARN never fails on what the caller handed in.

== Batch Request and Download

_Requirements:_ link:{req}/06-execution.adoc#PM-EXEC-5[PM-EXEC-5], link:{req}/06-execution.adoc#PM-EXEC-6[PM-EXEC-6]

`object(repository, pointer)` sends two requests, each through its own `cui-http` `HttpHandler`:

. The batch request, `POST <repository>.git/info/lfs/objects/batch` (`batchUri` appends `.git` unless the path ends with it and drops a trailing slash), with `Accept` and `Content-Type` `application/vnd.git-lfs+json` (`MEDIA_TYPE`) and the body `{"operation":"download","transfers":["basic"],"objects":[{"oid","size"}],"hash_algo":"sha256"}`, its size written with `Locale.ROOT` in ASCII digits whatever the default locale.
. The download, `GET` of the `href` of the answer's `actions.download`, with the string values of its `header` object. These values may carry a token; they are sent but never logged, and the query of the URL is cut from every detail.
A header the request builder refuses (a value with a control character, a restricted name) ends the fetch before anything is sent; the detail names the header (its name when that is an HTTP token, otherwise a fixed text) and never its value, and no exception message is carried, since the JDK's message quotes the value.

Every request goes to an `https` URL without user information; a repository URL without scheme or host, or a repository or download URL that is not `https`, is refused before anything is sent.
The package-private constructor admits plain `http` to a loopback address as well, for the mock web server of the tests.
Every request is bounded by the compiled connect timeout `CONNECT_TIMEOUT_SECONDS` (10 s) and read timeout `READ_TIMEOUT_SECONDS` (60 s).

== Outcomes

_Requirements:_ link:{req}/16-model-work.adoc#PM-WORK-6[PM-WORK-6]

[cols="3,1",options="header"]
|===
|What happens |`SourceFetch.Outcome`

|the URL names no scheme or no host, is not `https` or carries user information; the endpoint does not answer, times out or is interrupted; the batch API answers an error status other than 404; the batch answer is no JSON; the download action names no URL or a header the request refuses; the download answers an error status other than 404 and 410; the pointer's size exceeds what a byte array holds
|`UNREACHABLE`

|the batch API answers 404 (the repository has no LFS endpoint); the batch answer names no entry for the oid, an object `error`, or no download action; the download answers 404 or 410
|`PIN_MISSING`

|the download delivered bytes
|`FETCHED`
|===

Every `UNREACHABLE` and `PIN_MISSING` outcome is logged as WARN `PM_RUNTIME-126` `CORPUS_LFS_OBJECT_UNAVAILABLE` with the oid, the repository without user information, query or fragment, and the detail; a repository URL without scheme or host is named `<a URL without scheme or host>` and none of its parts is logged, so writing the WARN never fails on what the caller handed in.

The client does not decide whether delivered bytes are the object.
It reads the download up to one byte beyond the pointer's size and stops there (`BoundedBody`), so a longer body is never held in full.
Whatever it read is `FETCHED`, also when it has another size or another SHA-256 than the pointer; the detail then says the bytes are not the object.
`CorpusImport` checks every delivered object against the manifest's SHA-256, so such bytes are `hash_mismatch` and the run `FAILED`: a mismatch is never mistaken for a missing pin (link:../../../pm-core/doc/adr/core-role-corpus/003-missed-source-partial-and-hash-mismatch-failed.adoc[ADR 003 of `core-role-corpus`]).

== Testing

_Requirements:_ link:{req}/06-execution.adoc#PM-EXEC-6[PM-EXEC-6], link:{req}/16-model-work.adoc#PM-WORK-6[PM-WORK-6]

link:{test}/LfsBatchClientTest.java[`LfsBatchClientTest`] runs against the mock web server of `cui-test-mockwebserver-junit5` (`@EnableMockWebServer`, a test dependency of `pm-runtime`; link:../../../doc/adr/002-cui-http-and-the-mock-web-server-for-http.adoc[ADR 002]) with its own dispatcher: canned responses by method and target, each answering one request, anything else 404.
The client under test is built with the loopback admitted, a connect timeout of 2 s and a read timeout of 1 s.

* The delivered object: the batch request (method, path, media type, body) and the download with the action's header.
* Delivered bytes that are not the object, and a body longer than the pointer's size, read only up to one byte beyond it: both `FETCHED`.
* Every way the endpoint does not deliver (404, 503, object error, another object, no JSON, no download action, download 404 and 500): `UNREACHABLE` or `PIN_MISSING`, the WARN logged, the action's header value absent from the detail.
* A download action whose header value carries a line break: `UNREACHABLE` with only the batch request sent, the WARN logged, and neither the detail nor any log line holding the value.
* A refused download action: an `http` download URL to a host other than loopback, a download URL with user information (`http` or `https`, even to the loopback test server), a pointer larger than a byte array holds, and an `href` that is no URL. Each is `UNREACHABLE` with only the batch request sent, so nothing is downloaded and the action's `Authorization` header reaches no server; the WARN is logged and neither the detail nor any log line holds the header value or the user information. The test client admits `http` to loopback only, so the refusal of an `http` download to another host is the rule that refuses every `http` URL in the production client.
* A stalled response (headers delayed beyond the read timeout): `UNREACHABLE`, the WARN logged.
* A repository that is not `https`, and one with user information: refused with nothing sent.
* A repository URL without scheme or host (a relative path, `mailto:`, `https:/path`, `file:///`, `//host/path`): `UNREACHABLE` with nothing sent and the WARN logged, never an exception.
* `batchUri` for the URL forms of a repository.
* Under the default format locale `fa-IR`, whose digits are not ASCII: the batch request body exactly, its size in ASCII digits, and a status in a detail in ASCII digits.
* Within `CorpusImport`, with a manifest whose `https` repository is redirected to the mock web server: the delivered object yields the item, and bytes with another SHA-256, fewer bytes or more bytes fail the run with `hash_mismatch`.

link:{test}/HuggingFaceSourceRepositoryTest.java[`HuggingFaceSourceRepositoryTest`] runs the HTTPS source repository against the same mock web server (`@EnableMockWebServer`), with the repository URL redirected to it and the loopback admitted, a connect timeout of 2 s and a read timeout of 1 s:

* `prepare` creates nothing and makes no request.
* `fetchCommit` on a `200` of the revision API is `FETCHED`, on a `404` is `PIN_MISSING`, and on a server error or a stalled response is `UNREACHABLE`; `readFile` on a delivered plain file and on a delivered LFS pointer is `FETCHED`, on a `404` is `PIN_MISSING`, and on a server error or a stalled response is `UNREACHABLE`.
* A repository URL that is not `https`, is without a host or carries user information is refused with nothing sent, and the WARN is logged; under `fa-IR` a status in a detail is in ASCII digits.
* Within `CorpusImport`, a manifest whose repository is redirected to the mock web server yields the item `COMPLETE`, and delivered bytes that are not the pinned SHA-256 fail the run `FAILED`.

== Pitfalls

_Requirements:_ link:{req}/06-execution.adoc#PM-EXEC-5[PM-EXEC-5], link:{req}/06-execution.adoc#PM-EXEC-6[PM-EXEC-6]

1. **Never log a header value of the download action**: it may be a token. The WARN carries the oid, the repository and the detail only, and no detail carries the message of an exception the request builder throws, which quotes the value it refuses.
2. **Do not refuse delivered bytes here**: returning `PIN_MISSING` for a mismatch would turn a failed run into a partial one.
3. **Keep the read bounded**: do not read the download into memory with an unbounded body handler.
4. **Every request through `cui-http`**: no other HTTP client, and the timeouts stay compiled.
5. **Numbers in ASCII digits**: `%d` of `String.format` takes the digits of the default format locale; under `fa-IR` a status in a detail would not be ASCII. Format with `Locale.ROOT`.
6. **The HTTPS source reads raw bytes**: `HuggingFaceSourceRepository.readFile` returns the file at the pin as stored, a file in Git LFS as its pointer; the pointer's object comes from `LfsBatchClient`, so do not resolve LFS in the source repository.
