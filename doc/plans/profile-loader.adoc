== What

* The loader reads the whole profile documents that are resources of `pm-api` and validates them against the profile schema (with the `headless` members `install_locations`, `install_hint`, `auth_probe`, `models_probe`, `model_tiers`, `events`, and `resumability`, and the top-level `icon`); a failing profile is refused as a whole. The usage block and its rule that `input_tokens` and `output_tokens` are never `not_applicable` are link:token-usage.adoc[`token-usage`]'s.
* *The installed profile sets*: the machine set `<PM_MCP_BASE>/profiles/` and the project set `<PM_MCP_BASE>/projects/<project_id>/profiles/` beside the shipped one, the nearest set winning as a whole document and never merged; a project profile only for a `client_id` the machine or shipped set defines, with equal `detection`, `identity`, and `headless.executable`. A machine or project profile counts only with its verification record: `profile_digest` equal to the SHA-256 of the canonical JSON (RFC 8785) of the document and the HMAC sidecar verified with the key of the enrolment store; otherwise it is refused `profile_unverified` and the next set stays in force. A record whose harness version or digest differs from the enrolled harness within the supported range marks the profile `verified_on_other_build` and launches go on. Writing the sets is the onboarding's (link:machine-onboarding-unit.adoc[`machine-onboarding-unit`]); this package reads them and reports the state it found.
* Build test: every shipped profile validates.
* *The update and isolation declarations*: `headless.update_evidence` (its `method` `code_signature` with the `signer` the signature must name, `package_provenance` with the source repository the provenance must name, or `none`; validation refuses `code_signature` or `package_provenance` without a signer and `none` with one), the supported version range `headless.supported_versions`, the `headless.endpoints` a worker's egress proxy admits, and the capability `extension_isolation`; a profile whose `mcp_config.exclusive` is `false` declares `writer`, `read_only` and `zero_tool` all `null`, so no worker class is runnable while a harness's MCP configuration is not exclusive. The stage `isolation` settles `mcp_config.exclusive` and `capabilities` (`project_settings_control`, `extension_isolation`: no decoy tool, no canary file, no request to the decoy endpoint or proxy, the canary variable absent, and the project instruction and skill loaded) and the stage `egress` settles `headless.endpoints`; the stage `usage` cross-checks the profile's usage pointers against what the harness reports and records each figure `reported`, `not_applicable` or `missing`, so a declared pointer that does not resolve fails the stage. The loader validates these values and the classes they gate; the stages are the verification's (link:../specification/client-profiles/01-profile-schema.adoc#update-evidence[Client Profiles § Update Evidence]; link:../specification/client-profiles/01-profile-schema.adoc#role-classes[§ Role Classes of a Harness]; link:../specification/client-profiles/01-profile-schema.adoc#profile-verification[§ Profile Verification]).

== Done When

Every shipped profile loads and validates; for each hardening rule that concerns the parts read here, and for each pattern-constrained new member (`install_locations`, `install_hint`, `icon.source` with https and SVG or PNG only, `resumability.resume.argv` with its session-id slot exactly once), there is a fixture profile that the loader refuses as a whole, with the document and the JSON Pointer of the failing value asserted; a machine profile of a `client_id` the release does not ship is loaded; a machine or project profile without a record, edited after its record, or with a failing HMAC is refused `profile_unverified` and the next set's profile is in force; a project profile whose `detection` differs from the machine one is refused; a record of another harness build yields `verified_on_other_build`; a build test fails when a class of the loader names a harness, proven by a control fixture. A profile that declares `code_signature` or `package_provenance` without a `signer`, or `none` with one, is refused as a whole; a profile whose `mcp_config` is not exclusive and declares a class is refused, and one with an exclusive configuration loads every class it declares; a `supported_versions` range is validated; the `isolation` and `egress` stages record `mcp_config.exclusive`, `project_settings_control`, `extension_isolation` and `headless.endpoints`, and the `usage` stage records each figure `reported`, `not_applicable` or `missing` and fails for a pointer that does not resolve.
