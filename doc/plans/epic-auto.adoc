== What

* *Specification first*: the package writes the change An Epic Runs by Itself into `plan-marshall-documentation` as part of its own work, once it and UC-CTL-2 are agreed (link:../../../plan-marshall-documentation/doc/discussions/client-specification-changes.adoc#slicing[Specification Changes for the Clients, Packages]): the epic workflow, launchable rows, staging-time surface disjointness and runtime drift, the epic header, the queue row's wait reasons, and the project and machine keys, each building on what epic coordination already states and never stating it twice.
* *The setting*: `epic.auto_start` (`true` or `false`), a project key with the machine default `true`, so the specified behaviour stays the default; each epic carries its own value in its header, taken from the project at the start and never asked there (UC-STA-2 shows it on the ready step as the value in force). `parallelization_scope` stays the upper limit of plans of the epic running at once (machine default 1, raised by the operator, link:plan-and-epic-control.adoc[`plan-and-epic-control`]).
* *The toggle*: _Automatic: on/off_ among the epic's actions in every state that has not ended (UC-CTL-2, the actions by state of link:plan-and-epic-control.adoc[`plan-and-epic-control`]), an operator endpoint of both clients, a ledger write of the header, audited and told in the epic's events; switched on, the epic runs `epic.next-work` at once.
* *On*: whenever a place frees or a row becomes launchable, `epic.next-work` starts every launchable row up to the limit by itself. *Off*: the epic starts nothing by itself; the operator starts the next plan with _Next plan_ (link:plan-and-epic-control.adoc[`plan-and-epic-control`]); every reaction below still runs.
* *Too many common changes*: a launchable row is admitted beside the running plans only while its declared surface shares at most `epic.overlap_max_files` files with each running plan's declared surface and realized changes (a project key with a compiled upper bound, machine default 0: any common file; held in the epic header like `auto_start`, taken from the project at the start, and changeable from the epic's actions, an audited header write like the toggle; `epic.pmwf` stays compiled-only). Over it, the row waits with the reason `waits: overlap with <plan>` beside dependency, lock, and scope, until that plan has ended; it is never started in parallel, in either mode, also not by _Next plan_.
* *Overlap found while running*: a running plan whose realized changes come to overlap another running plan's beyond the limit is recorded in the ledger and the epic is told; neither plan is stopped (runtime drift never blocks); the one that lands second meets the base-advanced trigger of re-planning (PM-WF-17). The report of it to the operator is link:operator-reports.adoc[`operator-reports`]'s.
* *Reacting on a finished plan*: every end of a plan of the epic reaches its inbox (the landing, and the operator's acts of link:plan-and-epic-control.adoc[`plan-and-epic-control`]); the epic workflow then:
** for a landed plan: records the landing and runs the landing task's downstream impact judgment; a change of staged rows it proposes goes through `epic.recut`: one that only re-orders rows or amends a staged row's surface or prerequisites is applied once the server's checks pass; one that adds, drops, or re-scopes a plan waits for the operator in `decomposition.review` (link:epic-decomposition.adoc[`epic-decomposition`]), in both modes;
** for a plan that ended without landing (cancelled, abandoned, handed back, released, aborted): holds the rows that depend on it with that reason and asks the operator as specified;
** then `epic.next-work`: with automatic on it starts the next launchable rows up to the limit; with it off it records what is launchable now for the epic's view and _Next plan_ (reported as `epic.launchable`, link:operator-reports.adoc[`operator-reports`]).
* *Through*: the epic is through when every row is shipped or ended; with automatic on it then runs the completion review and records it; archiving stays the operator's act (link:plan-and-epic-control.adoc[`plan-and-epic-control`]).
* *A restart*: the epic's mode and its waiting rows are read back from the ledger; an epic with automatic on runs `epic.next-work` once recovered, starting nothing twice.

== Done When

The specification of the change is merged in `plan-marshall-documentation`; a new epic takes `auto_start` and `overlap_max_files` from the project, the project's values from the machine defaults `true` and 0, a value over the compiled upper bound is refused, and its start asks for neither; with automatic on, a freed place or a newly launchable row starts every launchable row up to `parallelization_scope` and no more, also after a restart and without starting a row twice; with it off nothing starts by itself while every reaction still runs and what is launchable is recorded; the toggle and a change of the overlap limit are audited header writes told in the epic's events and refused on an ended epic; a row whose surface overlaps a running plan's beyond `epic.overlap_max_files` waits with `waits: overlap with <plan>` in both modes and through _Next plan_, and is admitted once that plan has ended; an overlap found between running plans is recorded and told and stops neither; a landing's re-order or amendment of staged rows is applied after the checks pass, an added, dropped, or re-scoped plan waits in `decomposition.review`; a plan ended without landing holds its dependants with the reason; an epic through with automatic on runs its completion review and is not archived by itself.
