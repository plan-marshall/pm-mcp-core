== What

* *Implements* link:../specification/model-work/08-epic-coordination.adoc#epic-auto[Model Work § An Epic Runs by Itself], with the header fields of link:../specification/store-schemas/04-epic-and-change-ledger.adoc#epic-header[Store Schemas § Epic Header], the wait reason and `overlap_found` of link:../specification/store-schemas/04-epic-and-change-ledger.adoc#epic-queue-row[§ Queue Row], and the project's operator values of the `epic` object of link:../specification/store-schemas/08-project-configuration-local.adoc#local-config[§ Operator Local Configuration] (`PM-WF-15`, `PM-WF-23`, `PM-WF-21`).
* *The setting*: `epic.auto_start` (`true` or `false`), a project's operator value in `local-config.json`, never in the team file, with the machine default `true`, so the specified behaviour stays the default; each epic carries its own value in its header, taken from the project at the start and never asked there (UC-STA-2 shows it on the ready step as the value in force). `parallelization_scope` stays the upper limit of plans of the epic running at once (machine default 1, raised by the operator, link:epic-resource-and-release.adoc[`epic-resource-and-release`]).
* *The toggle*: _Automatic: on/off_ among the epic's actions in every state that has not ended (UC-CTL-2, the actions by state of link:epic-resource-and-release.adoc[`epic-resource-and-release`]), an operator endpoint of both clients, a ledger write of the header, audited and told in the epic's events; switched on, the epic runs `epic.next-work` at once.
* *On*: whenever a place frees or a row becomes launchable, `epic.next-work` starts every launchable row up to the limit by itself. *Off*: the epic starts nothing by itself; the operator starts the next plan with _Next plan_ (link:epic-resource-and-release.adoc[`epic-resource-and-release`]); every reaction below still runs.
* *Too many common changes*: a launchable row is admitted beside the running plans only while its declared surface shares at most `epic.overlap_max_files` files with each running plan's declared surface and realized changes (a project's operator value in `local-config.json` with a compiled upper bound of 20, machine default 0: any common file; held in the epic header like `auto_start`, taken from the project at the start, and changeable from the epic's actions through `PUT …/settings`, an audited header write like the toggle; `epic.pmwf` stays compiled-only). Over it, the row waits with the reason `overlap` naming that plan, beside `dependency`, `lock`, and `scope`, derived on read like them, until that plan has ended; it is never started in parallel, in either mode, also not by _Next plan_.
* *Overlap found while running*: at the re-planning checkpoint after each deliverable's build, a running plan whose realized changes come to overlap another running plan's declared surface or realized changes beyond the limit is recorded on both queue rows (`overlap_found`: the other plan, the paths, the time) and the epic is told; neither plan is stopped (runtime drift never blocks); the one that lands second meets the base-advanced trigger of re-planning (PM-WF-17). The report of it to the operator is link:operator-reports.adoc[`operator-reports`]'s.
* *Reacting on a finished plan*: every end of a plan of the epic reaches its inbox (the landing, and the operator's acts of link:plan-and-epic-control.adoc[`plan-and-epic-control`]); the epic workflow then:
** for a landed plan: records the landing and runs the landing task's downstream impact judgment; a change of staged rows it proposes goes through `epic.recut`: one that only re-orders rows or amends a staged row's surface or prerequisites is applied once the server's checks pass; one that adds, drops, or re-scopes a plan waits for the operator in `decomposition.review` (link:epic-decomposition.adoc[`epic-decomposition`]), in both modes;
** for a plan that ended without landing (cancelled, abandoned, handed back, aborted): holds the rows that depend on it with that reason, and `coordinate` raises a decision for the operator (a release ends the epic with its plans, link:epic-resource-and-release.adoc[`epic-resource-and-release`]);
** then `epic.next-work`: with automatic on it starts the next launchable rows up to the limit; with it off it records what is launchable now for the epic's view and _Next plan_ (reported as `epic.launchable`, link:operator-reports.adoc[`operator-reports`]).
* *Through*: the epic is through when every row is shipped or ended; with automatic on it then runs `epic.review-completion` and reports the result (`epic.through`), with it off it reports that it is through and the completion review runs at the operator's _archive_; archiving stays the operator's act (link:epic-resource-and-release.adoc[`epic-resource-and-release`]).
* *A restart*: the epic's mode and its waiting rows are read back from the ledger; an epic with automatic on runs `epic.next-work` once recovered, starting nothing twice.

== Done When

A new epic takes `auto_start` and `overlap_max_files` from the project, the project's values from the machine defaults `true` and 0, a value over the compiled upper bound is refused, and its start asks for neither; with automatic on, a freed place or a newly launchable row starts every launchable row up to `parallelization_scope` and no more, also after a restart and without starting a row twice; with it off nothing starts by itself while every reaction still runs and what is launchable is recorded; the toggle and a change of the overlap limit are audited header writes told in the epic's events and refused on an ended epic; a row whose surface overlaps a running plan's beyond `epic.overlap_max_files` waits with the reason `overlap` naming that plan in both modes and through _Next plan_, and is admitted once that plan has ended; an overlap found between running plans is recorded and told and stops neither; a landing's re-order or amendment of staged rows is applied after the checks pass, an added, dropped, or re-scoped plan waits in `decomposition.review`; a plan ended without landing holds its dependants with the reason; an epic through with automatic on runs its completion review and is not archived by itself.
