== What

* *Implements* link:../specification/workflow-dsl/02-units-jobs-decisions.adoc#clients-only[Workflow DSL § All Interaction in the Operator's Clients]; link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc#start-from-clients[State Catalogue § Starting from the Clients] with the bootstraps link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-bootstrap[`bootstrap-plan`] and link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-bootstrap-epic[`bootstrap-epic`], the link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-source[Source Units], link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc#issues[Issues by Number or URL], and link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc#options-when-needed[Asked When Needed] (`PM-WF-10`, `PM-ARCH-11`).
* *The operator's clients only*: the bootstraps of a plan and an epic run as units of operator waits that the clients drive; the session-driven units, the entry session, and the channel `session` of answers go from the code (`OutcomeClass`, the static verifier's rules for session units and their fixtures), the channels of an answer being `web`, `cli`, and `quorum`.
* *The setup gate*: `start.open`, `start-epic.open`, and the re-check of `start.create-scope` call the machine-onboarding guard of link:operator-wait-and-machine-scope.adoc[`operator-wait-and-machine-scope`] first, so no plan or epic starts while the machine's first onboarding has not reached `onboard.completed` (`machine_not_onboarded`, naming the terminal client and the web app), beside the rest of the setup gate of `start.open`. The move at creation of link:start-source-intake.adoc[`start-source-intake`] builds on these steps.
* *Sources as a list*: `start.sources` and `start-epic.sources`, offering only the kinds that combine with those already listed (a pull request or the local changes only with descriptions and documents, never both); the description stored by the main workflow; the source units `source-documents`, `source-issue` (number or URL, always stored as its URL, the structured fields; another repository on the operator's grant, whose _no_ goes to `source-issue.failed`; without a credential for the forge a public issue is read and another fails naming the credential), and the existing ones of lesson, local changes, pull request, and epic row, each writing into the source directory. The rate limits, documents copy or move, the source directory, the screening, and failing closed of link:start-source-intake.adoc[`start-source-intake`] build on these source units.
* *The other sources* (UC-STA-7 to UC-STA-9): pull request, lesson, and local changes as sub-workflows storing into the source directory; an issue's and a pull request's URL stored. A pull request's changed files are stored as its head and marked untrusted unless the operator authored it, never read by a model as instructions, the plan's own gates applying to them; its title and body screened as an issue's. A lesson: `source-lesson.resolve` with the premise check; a lesson claimed meanwhile, retired, or in a damaged store back to `source-lesson.choose` with the cause; a premise that no longer holds to the operator wait `source-lesson.premise` with the evidence, where _use it anyway_ stores the lesson with the evidence for the plan, _retire_ retires it in the lesson store, and _remove_ leaves it as it is, both adding nothing. The local changes: `source-local-changes.confirm` with _not now_ back to `start.sources`, a checkout without changes failing the source with that cause; the plan takes the land lane and lands them by the project's landing. The rate limits, the source directory, the screening, failing closed, and the claimed lesson of link:start-source-intake.adoc[`start-source-intake`] build on these sub-workflows (`source-lesson.*`, `source-local-changes.*`).
* *The start's end*: the landing is not asked at the start; while the project's landing in force is `landing.files`, `start.sources` does not offer the local changes and shows the reason naming the project's setting `landing` (the landing variants are link:machine-onboarding-unit.adoc[`machine-onboarding-unit`]'s); `start.create` re-checks what creation needs (`landing.files` refused for a plan from local changes) and returns to `start.ready` with the cause where something changed meanwhile.
* *Chat while starting*: `start.sources` and `start-epic.sources` leave room for the choice Chat that link:chat.adoc[`chat`] adds on top of this package, and the entry's `chat/` keeps its transcript (moved at the creation, deleted with an abandoned entry, never a source the plan reads); the chat itself and its one change, the description through `start.store-description`, are that package's.
* *Asked when needed*: posture and base branch leave the start: where neither the plan's own settings, the project (`plan_defaults.posture`), nor the machine sets them, `init.classify` asks both in the one operator wait `init.options`; whether the outline is reviewed is the plan's asking variant's (`outline_review`). `parallelization_scope` becomes the project's operator value `epic.parallelization_scope` in link:../specification/store-schemas/08-project-configuration-local.adoc#local-config[`local-config.json`] (machine default 1), which a new epic takes and which is never asked; it is raised through _Next plan_ (link:epic-resource-and-release.adoc[`epic-resource-and-release`]) or the project's settings.
* Where `entity-addressing`, `plan-instance`, or `project-units-and-invariants` have already implemented the session-driven bootstrap, this package restructures them.

== Done When

No unit is driven by a session, and no answer has the channel `session`; a test per source kind stores it in the source directory; a plan and an epic start from several sources and keep them after creation; a pull request's changed files are never read as instructions; a start of a plan and of an epic is refused `machine_not_onboarded` while the machine's onboarding is not complete; each branch of a lesson, unavailable and a premise that no longer holds, ends as specified; posture and base branch are asked in `init.options` only where no level sets them, and `parallelization_scope` never; `start.sources` does not offer the local changes while the project's landing is `landing.files`, with the reason, and `start.create` refuses `landing.files` for a plan from local changes.
