== What

* `pm-scenario` scenarios of the worker faults, recycling, the start-failure guard, consultation, fencing, and a runtime crash with a leased task.
* A worker off track, from a scripted output stream of the fixture harness: one scenario per signal (`repeating`, `no_progress`, `over_size`, `outside_footprint`), raised at its threshold and never before, and per action (`show`, `nudge`, `yield`, `restart`), taken and recorded with its signal without ending the plan or waiting for the operator (link:worker-activity.adoc[`worker-activity`]).
* A pause at once of a plan with a leased task, and the missing answer acknowledgement of a continuing worker (link:question-continuation.adoc[`question-continuation`]).
* Operator acts at operator waits are given by the scenario script; where `scenario-replay-harness` has no directive for one, the trace matrix names it and this package adds it.
* The same faults against real processes are link:../../../plan-marshall-mcp/doc/plans/worker-integration-tests.adoc[`plan-marshall-mcp` / `worker-integration-tests`].
* *The behavioural conformance harness*: the scenarios of `pm-conformance` (`PM-TEST-6`) run against a live model as a worker of a role on a fixture repository, and this package builds their runs and baselines on top of the shipped `scenario-replay-harness`: _Control First_ (a rule enters model-facing content, or is changed there, only with a scenario whose run against the version without the rule or the change scores `violated` in the same harness run; when that control holds, the rule is not added, because nothing shows it is needed, and the run report records both verdicts of the pair), _Combined Pressure_ (a scenario for a rule that is broken under pressure combines at least three pressures in its `pressure`: time, sunk cost, authority, exhaustion, or the plan's own instruction to violate it), and _Read Matches_ (before the first baseline of a new scenario is accepted, a person reads every sample its observation predicate matched and every sample it did not, and records the result with the baseline; a predicate that matched wrongly is corrected first). Every scenario declares its `rule_ref`, `situation`, `pressure`, `observation`, `binding_context`, `enforcement_class`, `tolerance_band`, `population` and `negative_control`, and a `violated` or `indeterminate` verdict is resolved by a recorded operator decision, never by the harness (link:../specification/workflow-dsl/07-loop-back-diagrams-verification.adoc#behavioural-conformance-harness[Workflow DSL § Behavioural Conformance Harness]).
* *The comparison footprint*: a run that compares two versions of model-facing content or of a role configuration runs both versions over the same tasks, several times each, and reports per version, beside the verdicts, the tokens and the revisits of every run (the navigation figures of link:../specification/model-work/09-completion-usage-and-spend.adoc#navigation-figures[Model Work § Navigation Figures]) with their spread, split into focused tasks and tasks that span several modules; a difference is reported `measured` only when the runs of both versions were drawn from the same tasks at random within the one run, and `estimated` otherwise; a single run per version is never a comparison, because runs of the same task with the same version differ by more than twice in tokens (link:../specification/workflow-dsl/07-loop-back-diagrams-verification.adoc#comparison-footprint[Workflow DSL § Comparison Footprint]).

== Done When

One scenario per fault of the fault matrix and per off-track signal and action, each replayed twice to the same stores; no scenario relies on a session or a session generation. A rule that enters model-facing content has a control scenario that scores `violated` against the version without it, both verdicts in the run report; a pressure scenario combines at least three pressures; a new baseline records the reading of every matched and unmatched sample; a comparison of two versions reports tokens and revisits per run with their spread over several runs of the same tasks each, split into focused tasks and tasks that span several modules, `measured` only for a randomised same-run draw and `estimated` otherwise, and never from a single run per version; every scenario declares the nine fields of the scenario record and a `violated` or `indeterminate` verdict is resolved by a recorded operator decision, never by the harness.
