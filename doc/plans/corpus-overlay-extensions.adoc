== What

A prototype of the question corpus of link:../../../plan-marshall-mcp/doc/plans/question-corpus-public-datasets.adoc[`plan-marshall-mcp` / `question-corpus-public-datasets`] ran the import of `corpus-sources` over the real rows of its three sources and showed three limits of it.

* *Sources on Hugging Face, fetched over HTTPS.* All three sources are dataset repositories on `huggingface.co`, and their licences are declared there only (their copies on GitHub carry none). JGit cannot fetch from that host: the ref listing already fails (`TransportException: Short read of block.`; with protocol v0 `Starting read stage without written request data pending is not supported`), while the same repositories answer JGit on GitHub and the git command line on `huggingface.co`. Such a source is fetched over HTTPS through cui-http instead of git:
** The manifest gets the member `fetch`, `git` or `huggingface`; the codec, the record and the schema resource change together, and every existing manifest states `git`.
** A second implementation of `SourceRepository` in `runtime.corpus`, on cui-http like `LfsBatchClient`: `prepare` creates nothing; `fetchCommit` confirms the pin through `<host>/api/datasets/<owner>/<name>/revision/<commit>` (200: `done`, 404: `pin_missing`; measured on 2026-10-15) and stores nothing, so the contract of `SourceRepository.fetchCommit` changes from "places the pinned commit in the cache repository" to "makes the pinned commit readable by `readFile`", in its Javadoc and the developer guide; `readFile` reads `<repository>/raw/<commit>/<path>`, which serves a file at the pinned commit as stored, the pointer of an LFS file included, so `CorpusImport` checks it and fetches the object through `LfsBatchClient` exactly as for a git source (both measured against the three sources on 2026-10-15: the plain files match their pinned SHA-256, the `input-bouncer` pointer names its object, the batch API of `<repository>.git/info/lfs/objects/batch` answers with a download action, and an unknown commit answers 404). A 404 is `pin_missing`; no answer, a server error, or a refused request is `unreachable`; the timeouts and the URL rules are those of `LfsBatchClient`.
** The composition chooses the implementation per manifest by its `fetch` member, never by the host name.
* *Several items per row.* One HumanEvalComm row is one problem with its original description and every modified variant; the corpus needs the variant, its control, and the answer applied from one row. `SourceOverlay` refuses a row selected twice; that refusal goes, the refusal of an item id generated twice stays. Each overlay row still generates one item, whose `provenance.origin` names the row's `path` and `line`.
* *An answer schema in the overlay row.* An open answer (the interpretation of an operator's own words, a decision with its rationale) needs `input.answer_schema`; the overlay row has no such member, so such an item is generated without one. The row gets `answer_schema` (a JSON Schema object, or `null`), literal, not a template, written into the generated item.
* *Formats changed together*: record, codec and schema resource of the manifest, the overlay and the imported item; the validator's rules follow; an ADR of `core.role.corpus` records the three changes against link:../../pm-core/doc/adr/core-role-corpus/001-source-manifest-overlay-and-imported-item-formats.adoc[ADR 001]. `ProductCorpusValidationTest` stays green on the product corpus.

Not in this package: the cause of the JGit failure on `huggingface.co` (git sources on other hosts keep JGit); a CSV file whose header names one field twice stays refused (`bouncerbench-lite/test.csv`, not used by the corpus).

== Done When

The HTTPS source repository's tests on a mock web server cover a plain file, an LFS pointer with its object, a 404 (`pin_missing`), and no answer or a server error (`unreachable`); `CorpusImportTest` imports one row selected three times into three items with distinct ids and one origin line, still fails an overlay that generates one id twice, and writes an overlay row's `answer_schema` into its item; the codec and schema tests cover `fetch` and `answer_schema`; and one import of every source the table of `question-corpus-public-datasets` pins, with `fetch: huggingface`, against `huggingface.co`, run by hand and its output recorded in the pull request, is `COMPLETE` with every file verified.
