== What

* *Implements* the engine side of UC-ONB-1 to UC-ONB-10 (`PM-WF-26`, `PM-WF-25`, `PM-SEC-8`): link:../specification/state-catalogue/14-machine-onboarding.adoc[State Catalogue § Machine Onboarding] and link:../specification/state-catalogue/19-onboarding-aspects-models-providers.adoc[§ Onboarding Aspects]; link:../specification/store-schemas/12-machine-stores.adoc#consent[Store Schemas § Consent Before Acting], link:../specification/store-schemas/12-machine-stores.adoc#model-catalogue[§ Model Catalogue], link:../specification/store-schemas/12-machine-stores.adoc#provider-defaults[§ Machine Provider Defaults], link:../specification/store-schemas/12-machine-stores.adoc#machine-config[§ Machine Configuration Store]; link:../specification/client-profiles/01-profile-schema.adoc#harness-scan[Client Profiles § Harness Scan], link:../specification/client-profiles/01-profile-schema.adoc#login-probe[§ Login Probe], link:../specification/client-profiles/01-profile-schema.adoc#unknown-harness[§ Unknown Harness], link:../specification/client-profiles/01-profile-schema.adoc#harness-icons[§ Harness Icons]; link:../specification/model-work/01-roles-and-configuration.adoc#role-assignment[Model Work § Role Assignment], link:../specification/model-work/01-roles-and-configuration.adoc#default-assignment[§ Default Role Assignment], link:../specification/model-work/01-roles-and-configuration.adoc#steward-role[§ Steward Role]; link:../specification/credentials-and-enrolment/01-provider-credentials.adoc#credential-store-choice[Credentials & Enrolment § Credential Store as an Operator Choice], link:../specification/credentials-and-enrolment/01-provider-credentials.adoc#provider-verification[§ Provider Verification], link:../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#auto[§ Automatic Onboarding], link:../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#concurrent-changes[§ Concurrent Changes of a Setting]; link:../specification/workflow-dsl/09-plan-instance.adoc#plan-axes[Workflow DSL § Plan Behaviour Axes], link:../specification/workflow-dsl/09-plan-instance.adoc#plan-overrides[§ Plan Overrides]. The client side is `onboarding-contract` of `pm-mcp-clients`.
* The onboarding's sub-workflows in the machine scope of the Workflow DSL: languages, harnesses (one scan, a default), models, roles, credentials, providers, plan defaults; each aspect a compiled sub-workflow with the parameter `onboard_run` (`first_run`, `reconfigure`); the first run from `onboard.entry` through `onboard.mode` (guided or automatic), a later run of one aspect from the machine's settings (`settings.choose`) with its current values as the proposal, returning there.
* The consent store `consents.json` and its closed list of kinds, among them `check_credential_store` (asked in `store.consent`, only for an OS store; the file store is checked without one) and `verify_providers` (asked in `providers.verify-consent`); a project's kind with its project, and `run_checkout_scripts` with the digest of each script, in this store only, never in an enrolment; the consent state before every action: each action state is reached only through its consent state (`<sub-workflow>.consent` or `<sub-workflow>.<action>-consent`) answered `yes` or `yes_remember`, or passed without a question where the kind is remembered in the store, and `no` records nothing and leaves the scope in the consent state, an optional action going on without the action; an act of the operator's own, a credential the operator types, stored without a consent.
* The harness scan, the login and model probes, and the verification of an unknown harness, as confined jobs of the kind `probe`; the verification runs only from `harness.verify-profile` after `harness.add-consent` answered `yes` with the expected tokens of its stages shown, the kind `verify_harness_profile` never remembered and so asked before every verification, in a first run and in a reconfiguration alike, and the draft validated as a profile before anything runs; the profile fields they read. The harnesses are listed in the order of their `client_id`, every supported worker-eligible one preselected and the first of them the default; the same order serves `auto.run` and the first enrolled harness of `roles.default`. The step needs one usable harness: the last chosen one cannot be left out, and when none is found or every chosen one fails its probe the step goes to `harness.none` (an operator wait with `recheck` and `add`, naming each known harness's install hint, the onboarding resting there until the operator acts).
* *The recorded runs, the repeated evaluation and the install-path handoff.* Three remainders of the closed usage package are owed here: the recorded output of each shipped harness and version, the turns of a warm worker included, as a parsing fixture with its expected row (link:../specification/client-profiles/01-profile-schema.adoc#token-usage[Client Profiles § Tokens, Not Money]); the repeated usage evaluation for every new harness and harness version before its figures are trusted (link:../../../plan-marshall-documentation/doc/specification/evaluation.adoc#results[Evaluation Reference § Results]); and the install path that hands a verification stage's `UsageResult` to the enrolment's `UsageReport`, whose `of` is the mapping boundary: it renames `input_tokens`/`output_tokens` to `input`/`output`, carries each `UsageStatus` as its wire name (`reported`, `not_applicable`, `missing`), and copies the `startContext` list unchanged (link:../specification/store-schemas/11-enrolment-store.adoc#harness-enrolment-store[Store Schemas § Harness Enrolment Store]).
* The model catalogue, the default and the operator's role assignment; the steward role outside both: not among the roles `roles.load` lists, always on the default harness with that harness's default model, outside the catalogue (`model_not_allowed` never applies to it), exempt from qualification, and its submits.
* The credential-store aspect (`store.choose`, `store.consent`, `store.check`, `store.confirm-move`, `store.move`), a failed move going to `store.unavailable` with `credential_store_failed` and the old store kept, over the delivered store of `pm-runtime` (`CredentialStoreChoice`, which records the operator's choice, and `CredentialStoreMove`, which moves the entries; the automatic selection is removed); the machine's provider defaults and their verification.
* The automatic onboarding with its consent and its result (reasons, items); _change_ on `auto.result` calls that one aspect as a later run (`onboard_run: reconfigure`, its current values as the proposal) through `onboard.next` and returns to the result; a state it cannot decide alone (a login, a token, no harness found, the model ids of a harness that cannot list its models) shown as in the guided run.
* *The machine's settings* (UC-ONB-10), states of the onboarding unit reached from `onboard.completed`: `settings.choose` (the recorded aspects, the remembered consents, the documents mode, the cleanup's durations, the credentials with their status, the paired devices, which are acted on through their own endpoints); reconfigure an aspect as a later run of its sub-workflow; withdraw a consent (`settings.withdraw`, `settings.remove-consent`, audited, asked again at its next action); the documents mode (`settings.documents-mode`, `settings.record`: the machine key `sources.documents_mode`, `copy`, `move`, or `ask`, the default, which link:start-source-intake.adoc[`start-source-intake`] reads); the cleanup's durations (`settings.cleanup-durations`, `settings.record`: the machine's `cleanup.*` durations per kind and the reminder's days, which link:cleanup.adoc[`cleanup`] reads); the providers checked again on request (`settings.verify-providers`, `call providers` at its entry `verify` over every chosen provider); a credential rotated or replaced (`settings.credential`, `settings.store-credential`, every token derived from the old secret dropped), verified again through `providers.verify-consent`, `providers.verify`, and `providers.failed`, after which a plan held by the expired credential goes on.
* *Concurrent changes of a setting* (link:../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#concurrent-changes[CLI & Security § Concurrent Changes of a Setting]): every change of a recorded value, of the machine's settings here, of a project's operator values in link:project-onboarding-unit.adoc[`project-onboarding-unit`], and of a plan's own values in link:plan-and-epic-control.adoc[`plan-and-epic-control`], carries the revision of the settings it was made against; the first change wins, a later one against an older revision is refused with `conflict` (`409`) and the current value, which the operator may change again on top of it; nothing is merged and nothing is overwritten unseen.
* The plan behaviour axes and plan overrides in the composition: each variant a sub-workflow named with its axis as prefix, an axis's variants a closed list; the method variant (`method.test-first`, `method.tests-after`) called by `plan.order-tasks` of `phase-4-plan`, the asking variant (`ask.every-phase`, `ask.key-points`, `ask.questions-only`) by the plan unit's `phases.ask`; a landing variant composed into the step list of `phase-6-finalize` at its landing orders, which keeps its checks and reviews, with `landing.pull-request` (push, pull request, its reviews, merge), `landing.main` (commit and push on the base branch), and `landing.files` (no commit, the changes written into the main checkout's working tree, the plan handed back), apart from the land lane; the binding of each axis at the plan's start; the composition event `override`, the prune reasons `plan_default` and `merge_by_operator`, and the removal of the shipped rule `auto-merge-off` are implemented (link:../../pm-workflow/doc/developer/workflow-plan.adoc#_the_plan_behaviour_axes[Plan Instance Developer Guide § The Plan Behaviour Axes]); `overrides.json` with a role's harness, model, and effort, the variant of each axis and of an integration, and the optional providers.
* *Validation of the landing*: `defaults.validate` checks only what the machine provides (a provider for `landing.pull-request`), never a repository; a landing variant is validated where a project is known (its setup, a plan's start, a plan's settings), refusing `landing.pull-request` without a provider and `landing.main` on a protected base branch with the reason, also a machine default that does not fit the project.

== Done When

The onboarding runs from its first state to `onboard.completed` and as a later run of each aspect, against the scenarios of `onboarding-contract` replayed on the runtime; no action runs without its consent, the store check and the provider verification included, an unknown harness's verification asked every time and never remembered, a `no` leaving the scope in its consent state with no job started, and a typed credential is stored without one; a run with every chosen harness failing rests in `harness.none`; the harness list shows for each harness and version the usage coverage its verification recorded; the steward runs outside the catalogue and the assignment; the automatic run reports each value it chose, and a _change_ on its result runs that aspect and returns to the result; the harnesses are listed and preselected in the order of their `client_id`; a failed store move keeps the old store and reports `credential_store_failed`; each branch of the machine's settings is tested, the cleanup's durations and the providers checked on request included, a withdrawn consent asked again, a rotated credential verified and a plan held by the old one going on; of two changes of a setting made against the same revision the first is recorded and the second refused with `conflict` and the current value; a landing variant is refused with its reason where it does not fit a project, and the machine default is never checked against a repository; each shipped harness and version has its recorded output as a parsing fixture with its expected row, the usage evaluation is repeated for every new harness and version, and a verified profile's usage report reaches its harness enrolment through `UsageReport.of`.
