== What

* *Specification first*: the package writes the engine side of the onboarding's changes into `plan-marshall-documentation` as part of its own work, once UC-ONB is agreed (link:../../../plan-marshall-documentation/doc/discussions/client-specification-changes.adoc#slicing[Specification Changes for the Clients, Packages]); `onboarding-contract` of `pm-mcp-clients` writes the client side beside it.
* The onboarding's sub-workflows in the machine scope of `operator-wait-and-machine-scope`: languages, harnesses (one scan, a default), models, roles, credentials, providers, plan defaults; a later run of one aspect through `onboard.entry` (`reconfigure`).
* The consent store `consents.json` and its closed list of kinds, among them `check_credential_store` (asked in `store.consent`, only for an OS store; the file store is checked without one) and `verify_providers` (asked in `providers.verify-consent`); a project's kind with its project, and `run_checkout_scripts` with the digest of each script, in this store only, never in an enrolment; the consent state before every action; an act of the operator's own, a credential the operator types, stored without a consent.
* The harness scan, the login and model probes, and the verification of an unknown harness, as confined jobs; the profile fields they read. The step needs one usable harness: the last chosen one cannot be left out, and when none is found or every chosen one fails its probe the step goes to `harness.none` (an operator wait: recheck, add one, or later, the onboarding resting there).
* The model catalogue, the default and the operator's role assignment; the steward role outside both: not among the roles `roles.load` lists, always on the default harness with that harness's default model, outside the catalogue (`model_not_allowed` never applies to it), exempt from qualification, and its submits.
* The credential store choice and its move; the machine's provider defaults and their verification.
* The automatic onboarding with its consent and its result (reasons, items); a state it cannot decide alone (a login, a token, no harness found, the model ids of a harness that cannot list its models) shown as in the guided run.
* *The machine's settings* (UC-ONB-10), states of the onboarding unit reached from `onboard.completed`: `settings.choose` (the recorded aspects, the remembered consents, the documents mode, the credentials with their status); reconfigure an aspect as a later run of its sub-workflow; withdraw a consent (`settings.withdraw`, `settings.remove-consent`, audited, asked again at its next action); the documents mode (`settings.documents-mode`, `settings.record`: the machine key `sources.documents_mode`, `copy`, `move`, or `ask`, the default, which link:start-from-clients.adoc[`start-from-clients`] reads); a credential rotated or replaced (`settings.credential`, `settings.store-credential`, every token derived from the old secret dropped), verified again through `providers.verify-consent`, `providers.verify`, and `providers.failed`, after which a plan held by the expired credential goes on.
* *Concurrent changes of a setting* (link:../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#concurrent-changes[Concurrent Changes of a Setting]): every change of a recorded value, of the machine's settings here, of a project's operator values in link:project-onboarding-unit.adoc[`project-onboarding-unit`], and of a plan's own values in link:plan-and-epic-control.adoc[`plan-and-epic-control`], carries the revision of the settings it was made against; the first change wins, a later one against an older revision is refused with `conflict` (`409`) and the current value, which the operator may change again on top of it; nothing is merged and nothing is overwritten unseen.
* The plan behaviour axes and plan overrides in the composition: each axis a call site, each variant a sub-workflow named with its axis as prefix; the landing axis a call site inside the phase `finalize`, which keeps its checks and reviews, with `landing.pull-request` (push, pull request, its reviews, merge), `landing.main` (commit and push on the base branch), and `landing.files` (no commit, the plan handed back), apart from the land lane; `method.*` and `ask.*`; the prune reason `plan_default`, the composition event `override`, their binding where the plan first needs them; `overrides.json` with a role's harness, model, and effort, the variant of each axis and of an integration, and the optional providers.
* *Validation of the landing*: `defaults.validate` checks only what the machine provides (a provider for `landing.pull-request`), never a repository; a landing variant is validated where a project is known (its setup, a plan's start, a plan's settings), refusing `landing.pull-request` without a provider and `landing.main` on a protected base branch with the reason, also a machine default that does not fit the project.

== Done When

The specification is merged in `plan-marshall-documentation`; the onboarding runs from its first state to `onboard.completed` and as a later run of each aspect, against the scenarios of `onboarding-contract` replayed on the runtime; no action runs without its consent, the store check and the provider verification included, and a typed credential is stored without one; a run with every chosen harness failing rests in `harness.none`; the steward runs outside the catalogue and the assignment; the automatic run reports each value it chose; each branch of the machine's settings is tested, a withdrawn consent asked again, a rotated credential verified and a plan held by the old one going on; of two changes of a setting made against the same revision the first is recorded and the second refused with `conflict` and the current value; a landing variant is refused with its reason where it does not fit a project, and the machine default is never checked against a repository.
