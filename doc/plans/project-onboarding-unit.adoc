== What

* *Implements* link:../../../plan-marshall-documentation/doc/specification/cli-and-security/02-credentials-and-operator.adoc#project-onboarding[CLI & Security § Onboarding a Project as One Process], link:../../../plan-marshall-documentation/doc/specification/state-catalogue/15-project-onboarding.adoc[State Catalogue § Project Onboarding], link:../../../plan-marshall-documentation/doc/specification/state-catalogue/06-setup-epic-other.adoc#state-catalogue-setup[§ Project Setup], link:../../../plan-marshall-documentation/doc/specification/store-schemas/08-project-configuration-local.adoc#project-levels[Store Schemas § Project Values over Machine Values], and link:../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#project-explorer[Runtime Model § The Projects of the Machine] with its store link:../../../plan-marshall-documentation/doc/specification/store-schemas/12-machine-stores.adoc#explorer-store[Store Schemas § The Operator's Projects] (`PM-EXT-8`, `PM-SEC-8`).
* *The gate*: the start of a project's onboarding calls the machine-onboarding guard of link:operator-wait-and-machine-scope.adoc[`operator-wait-and-machine-scope`] first and is refused while the machine's first onboarding has not reached `onboard.completed` (`machine_not_onboarded` in the setup gate, `onboarding_incomplete` (`409`) over the local API, naming the missing step and both clients).
* *The unit*: `project.checkout` to `project.enrol` in a scope of its own per project being onboarded (several at once, the machine scope untouched), then the project setup; detection after the consent kind `inspect_checkout` (it reads the checkout and runs the host tools' version probes, and changes nothing): the remote, base branch, build wrappers, host tools, language servers, and scripts with a check line each; the id proposed from the remote; the enrolment written as `pm-operator enrol` writes it.
* *The checkout's scripts*: `project.run-consent` (consent kind `run_checkout_scripts`) answered `yes`, `yes_remember` (for this project), or `no`; a remembered yes kept in the machine's `consents.json` keyed by the project and each script's digest (the store of link:machine-onboarding-unit.adoc[`machine-onboarding-unit`]), never in the enrolment: the entry lists every script it covers with its digest, and `project.run-consent` computes the digest of each script it would run from the checkout and is passed without a question only when every one is listed for this project with that digest, so a script not listed, a changed script, or an entry of another project asks again, and a `yes_remember` replaces the list; a `yes_remember` given before the project has its id is held with the onboarding's entry and written under the confirmed `project_id` in the transaction of `project.enrol`, an onboarding that does not reach its enrolment remembering nothing; the scripts run confined like a job, never without one of the two yes links; _no_ goes on to `project.identity` with what needs the scripts unknown, not asked again in that run.
* *The setup in the specification's order*, its choices operator waits served to both clients, no session driving it: `project.setup` calls the setup (`first_run`): `setup.entry`, `setup.prepare-workspace`, `setup.check-operator-files`, which ends with its exit `operator_values`; `project.operator`; the setup called again at its entry that starts at `setup.probe-integration-variants` and `setup.verify-credentials` (an invalid variant back to `project.operator` with its findings); `setup.project-settings` (base branch, branch prefix, lanes); `setup.detect-domains`; `setup.discover-modules`; `setup.seed-build-map` (derived from the modules); `setup.select-providers` (the team's: the CI provider from the remote or overridden, code analysis, review bots); `setup.configure-finalize` (the finalize steps and the project's landing variant, one of the variants link:machine-onboarding-unit.adoc[`machine-onboarding-unit`] defines, validated against the project there, a machine default that does not fit refused with the reason); `setup.probe-merge-queue` with `setup.merge-queue` where one could be enforced; `setup.qualify-consent` and `setup.qualify-roles`; `setup.enrich-consent` and `setup.enrich-architecture`; `setup.commit-changes` (commit, or leave to commit) and `setup.land-changes`; `project.completed`. A step that cannot pass waits in `setup.needs-repair`, whose retry runs it again.
* *Consents of model use*: `setup.qualify-consent` and `setup.enrich-consent` (consent kind `model_cost`), their expected use shown in tokens, never as money (link:token-usage.adoc[`token-usage`]), asked only where roles need grading or modules a description; _no_ skips the step with its reason, to be run later, and the setup goes on (the project ready without descriptions).
* *The project's values over the machine's*: `project.operator` shows the operator's values only (the model language, the allowed models, the role assignment, the method and asking axes, the integration variant and credential of each provider, the commit identity), each proposed from the machine and recorded for the project only when changed; the team's values (the landing axis, the providers' declaration) stay in the setup and `.marshall/config/`; `project_defaults` as the machine's value of the project's operator keys, one rule for all. A change of an operator value carries the revision it was made against and is refused with `conflict` and the current value when another change came first (the rule of link:machine-onboarding-unit.adoc[`machine-onboarding-unit`], link:../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#concurrent-changes[CLI & Security § Concurrent Changes of a Setting]).
* *The projects of the machine*: favourites and their order in the machine store `explorer.json`, recent and most used from the operator's acts in a project.

== Done When

A test onboards a fixture checkout from `project.checkout` to a ready project without a session, and one shows its start refused while the machine's onboarding is not complete; a test shows a refused consent leaving the checkout unread, a refused script consent going on without the scripts and not asked again in the run, and a remembered one kept in `consents.json` only and written at `project.enrol`, none remembered by an onboarding that does not reach it; a remembered script consent passes the state only for the same project and the same digests, a changed script, an added script, and the entry of another project each asked again; a test walks the setup's states in their order, refuses a landing variant that does not fit the project at `setup.configure-finalize`, and skips the qualification and the description on _no_ with their reasons; a test shows an accepted machine proposal recording nothing for the project and a changed one recorded, and a change against an older revision refused with `conflict` and the current value; `pm-operator enrol` still enrols as a direct verb with its arguments as the answers.
