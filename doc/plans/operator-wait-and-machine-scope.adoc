== What

* *Implements* link:../specification/workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL § Waiting for the Operator] and link:../specification/workflow-dsl/01-grammar.adoc#machine-scope[§ Machine Scope] (`PM-WF-20`, `PM-WF-26`).
* *The operator wait*: a state of any unit and any scope may wait for the operator, in its three forms (a link state, the operator states of the decision unit, the waiver wait); it offers the operator's links to both clients, the first act winning, holds no worker and no model slot, has no time limit, and ends by an operator act through a link or by an engine-owned transition that ends the scope; its awaited events and the static verifier's rules on resting states and operator links (Rules 10, 11b) follow. *Holding nothing* is structural, not a release of its own: an operator wait is no model-job state, so the engine opens no task in it and offers none to a worker, and the scope reaches it only after the tasks of the state before have settled, each closed task having released its lease and its model slot where they are held (link:slots-usage-and-budgets.adoc[`slots-usage-and-budgets`]); the one exception is a worker holding its task for the answer to its own question within its role's hold limit, which suspends or falls back after it (link:../specification/model-work/06-envelopes-questions-deadlines.adoc#continuation[Model Work § Continuing after a Question]). Consent states (`<sub-workflow>.consent`, links `yes`, `yes_remember`, `no`) are operator waits of this form; their store is link:machine-onboarding-unit.adoc[`machine-onboarding-unit`]'s. The question modes `auto` and `none`, the question wait, the deadline, the class fallbacks, and the expiry of a waiver request go; a waiver request ends by `waive` or `decline`.
* *What halts*: an operator wait halts its own scope only, shown as waiting for the operator, never as stalled; the machine scope's onboarding halts the system: while its first run has not reached `onboard.completed`, the setup gate refuses to start a plan, an epic, or a project onboarding. This package builds that guard once, reading the machine scope's state: the setup gate's reason `machine_not_onboarded` and, for an act over the local API that needs a step of the onboarding not done yet, `onboarding_incomplete` (`409`), each naming the missing step and both clients; the onboarding itself and the operator's verbs stay open. Its callers are the starts of link:start-from-clients.adoc[`start-from-clients`] (`start.open`, `start-epic.open`, `start.create-scope`) and the start of a project's onboarding of link:project-onboarding-unit.adoc[`project-onboarding-unit`], which build those entry points.
* *The machine scope*: the fourth top-level scope, one per machine (`scope_type: machine`, `scope_id` null, `NO_PLAN` for its workers), its workflow state in `<PM_MCP_BASE>/machine/mcp/status.json`, its states of the phase `machine`, and its resident unit `onboarding.pmwf` compiled into the binary; a condition of the machine scope retried at the compiled backoff and shown as a hold.
* Where `waits` or `operator-and-question-stores` have already implemented question deadlines and fallbacks, this package removes them, and so the mention of a deadline in the Javadoc of `EngineEvent.QuestionResolved` of `workflow-engine`.
* *Schema parity*: the scope `machine` and the phase `machine` of the status store, and `WorkflowStatusSchemaParityTest.phasesEqualSchema` and `scopeTypesEqualSchema` re-enabled.
