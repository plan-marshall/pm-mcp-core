== What

* The job kind `llm`: the launch composed from the role's effective `harness`, `model`, and `effort` (link:role-sets-and-model-caller.adoc[`role-sets-and-model-caller`]) and the client profile, a model tier rendered into the model `headless.model_tiers` maps it to; the job-private directory, the MCP configuration delivered as the profile says; `harness_version` in the job record, the version in force at the spawn, probed again where the executable's digest changed.
* The job token: minted at spawn, only its hash in the job record, revoked with the job's fate; the registry over the job records. A worker's identity in the audit rows is its `job_id`, role, and generation; the delivery record and skill delivery are per worker generation.
* The harness enrolment store and the confinement exceptions of `llm` jobs: the `client_id` an open pattern of the effective profile set; the required `usage_report` and the `events` stage results kept with the entry (their values are link:token-usage.adoc[`token-usage`]'s and link:worker-activity.adoc[`worker-activity`]'s); one store API for `pm-operator enrol-harness` and the onboarding's `harness.enrol`. Launch refusals carry their reason and name the act that resolves it in both clients.
* The ephemeral flag withheld, the session stored, and the job-private directory kept for a role that may resume after a question, and the launch of a resumed generation with `headless.resumability.resume.argv`, are link:question-continuation.adoc[`question-continuation`]'s; this package composes the launch they parameterise.
* *The launch prompt's shared prefix and the launch refusals*: the writing skill `skill://pm/writing/SKILL.md` is required for every task whose links carry free text, derived by the server from the link schemas (a parameter of type `text`, or a named parameter schema with a `string` field that has neither `enum` nor `pattern`) when the offer or the launch is composed, never from the role artifact; the shim paragraph, the core conduct skill, the task-protocol skill and the role skill with its further skills are rendered byte-identically for every launch of a role on the same skill digests and client profile and come first, with nothing that varies per launch before or between them, so a harness's prompt cache can serve the shared part. The class's launch loads the project's instruction files and skill directories and no plugin, hook, MCP server, endpoint or environment value from any settings file of the project, the checkout or the user (the capability `extension_isolation`). The harness is an enrolled host tool (`harness.enrol`, `pm-operator enrol-harness`), and before every launch the runtime re-digests the executable; a changed digest is accepted only on the profile's `update_evidence` and then only when the version probe reports a version inside `headless.supported_versions`, audited `harness_updated` with the new version and digest written to `harnesses.json`, and every other case refuses the launch before spawn with `harness_not_enrolled`, `harness_update_unverified` or `harness_version_unsupported` in the job record's `refusal_reason` (link:../specification/model-work/04-worker-launch.adoc#job-prompt[Model Work § Launch Prompt & Contract Envelope]; link:../specification/model-work/04-worker-launch.adoc#skill-delivery[§ Skill Delivery Record & Re-Delivery]; link:../specification/model-work/04-worker-launch.adoc#job-working-directory[§ Working Directory, Project Files & Zero-Tool Isolation]; link:../specification/model-work/04-worker-launch.adoc#harness-selection[§ Harness Eligibility & Launch Refusals]; link:../specification/store-schemas/11-enrolment-store.adoc#harness-enrolment-store[Store Schemas § Harness Enrolment Store]; link:../specification/store-schemas/10-job-and-lesson-records.adoc#job-record[§ Job Record]).

== Done When

A launch-vector test per role class against a fixture profile; a tampered harness enrolment refuses the launch; a `zero_tool` launch has no tool, no MCP entry and no loaded setting; a launch under a role assignment or plan override uses the effective values, a tier rendered to the profile's model; the job record carries `harness_version`, probed again after a digest change; a harness the operator added from a verified profile is enrolled and launched like a shipped one. A task whose links carry free text is launched with the writing skill derived from the link schemas and one whose links do not is not; two launches of one role for two tasks agree byte for byte up to the end of the role skill; a worker loads the project's instruction files and skill directories and no plugin, hook, MCP server, endpoint or environment value from any settings file; before every launch the executable is re-digested; a launch of a changed executable without passed update evidence is refused `harness_update_unverified`, one outside the supported range `harness_version_unsupported`, one of an unenrolled harness `harness_not_enrolled`, each recorded in the job record's `refusal_reason`, and an accepted self-update rewrites `harnesses.json` with the new version and digest and is audited `harness_updated`.
