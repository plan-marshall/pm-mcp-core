== What

The packages link:runtime-lifecycle.adoc[`runtime-lifecycle`] and link:service-unit.adoc[`service-unit`] are done and stay as they are: they built the drain on a signal, the recovery that resumes work after it, the version mismatch, and the unit file. This package adds the lifecycle as acts of the operator in both clients on top of them; it is a package of its own because those two are closed, and because its acts need the operator endpoints, the consent store, and the jobs, workers, and tasks they stop, none of which existed when they were cut.

* *Specification first*: the package writes the change The Runtime's Lifecycle into `plan-marshall-documentation` as part of its own work, once it and UC-SYS-1 are agreed: the requirement the change drafts or extends (link:../../../plan-marshall-documentation/doc/requirements/01-architecture.adoc#PM-ARCH-7[PM-ARCH-7], the inspection and lifecycle verbs); the sections it names: Drain, Stop & Upgrade (stop now, the withdrawable drain, restart, the upgrade from a client), the Local API (the operator endpoints of the lifecycle; drain stops being a signal only), Installation Layout (where versions come from, the switch done by the runtime), the consent kind `check_updates` in the closed list of consents, and the texts of the use case.
* *Stop*: one act with two modes. `drain`: nothing new starts, what runs finishes its current task or job, then the runtime stops as the drain of link:runtime-lifecycle.adoc[`runtime-lifecycle`] does, bounded by the drain timeout. `now`: running tasks are withdrawn, jobs stopped, worker generations fenced, and everything resumes from its last committed state at the next start through the per-project recovery. The answer names what runs (plans, epics, jobs, workers), so the client can ask its confirmation with it.
* *The drain as a state*: a drain started through the API is visible (`facts.runtime: draining`, the status, the event stream) and can be withdrawn while it runs, before its final step; a withdrawn drain leaves every participant running as before. A running drain can be turned into a stop now (the bound passed, or the operator's choice). `pm-operator drain` stays a signal for a runtime that does not answer.
* *Restart*: a stop (now or drain) followed by a start of the same installation, without a terminal: the runtime hands its successor start to a detached start of `<PM_MCP_HOME>/bin/pm-mcpd` that waits for the singleton lock of the stopping runtime; under the service unit the service manager's own start is used. The change fixes the mechanism; a stopped runtime is started only from the terminal client (on demand, or `pm-operator runtime start`).
* *Version and the update check*: the installed version and build from the runtime itself, a local read without consent; whether a newer release is available from the place the release comes from (the organisation's registry, `PM-DIST-1`), a network read that needs the consent kind `check_updates`, rememberable, asked before the first check and never repeated while remembered.
* *Upgrade*: on the operator's choice, the runtime fetches the release, verifies it, unpacks it into a new versioned installation directory, switches the two `PATH` symlinks, drains (or stops now, the operator's choice), and its successor starts from the new directory; running work resumes after it like after a restart. The old directory stays until the drain completed. A failure before the switch leaves the installed version running and unchanged; a failure after it (the new runtime does not reach its authenticated round trip within the start timeout) switches the symlinks back and starts the previous version; both say why. A stop requested while an upgrade runs is refused with the upgrade's state, a second upgrade likewise. Pre-1.0: no store migration beyond what the specification defines.
* *The endpoints*: the lifecycle acts as operator endpoints under `/api/v1/operator/` (stop with its mode, withdraw a drain, turn a drain into a stop now, restart, the update check, the upgrade), accepted from `pm-operator` and from a paired web device and audited with their channel; the version and the upgrade state as part of `GET /api/v1/status`; the lifecycle events (draining, drain withdrawn, stopping, upgrading, upgraded, upgrade failed) on the runtime-wide event stream, so every open client sees the runtime stopping.

== Done When

The requirement and the specification of the change are merged in `plan-marshall-documentation`; with a killed-runtime fixture and fixture jobs and workers: a stop now ends every job and fences every worker at once and the next start resumes each plan from its last committed state; a drain lets the running task and job finish and starts nothing new; a withdrawn drain leaves everything running; a drain turned into a stop now behaves like a stop now; a restart comes back on the same installation without a terminal; the update check runs only with `check_updates` given and never asks again while it is remembered; an upgrade from a staged release switches to the new directory and resumes the running work; a failure before and one after the switch each leave the previous version running with the reason; a stop during an upgrade is refused; every act is audited with its channel, and every open event stream sees the runtime stopping.
