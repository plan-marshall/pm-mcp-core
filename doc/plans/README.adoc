= Work Packages of `pm-mcp-core`
:toc: left
:toclevels: 2
:nofooter:

One plan file per work package. A work package is what one session takes up and lands as one pull request here, with its documentation pull request in `plan-marshall-documentation`. The files hold the tasks; what the tasks mean and require is stated in the documentation repository and linked by relative paths. The links assume the repositories checked out beside each other (`../plan-marshall-documentation`, `../pm-mcp-clients`, `../pm-mcp-core`, `../plan-marshall-mcp`); they do not resolve in the web view of a single repository.

The modules of this repository, their packages and their dependency rules are listed only in the link:../../../plan-marshall-documentation/doc/specification/module-structure.adoc[Module Structure Specification]; each package file names where it lands.

[#packages]
== Packages

The packages listed serve roadmap Milestones 2 to 4; later milestones are not cut into packages yet, and a package that names one of them as the home of something says what is left out here. This table is the only place that states the status of a package and what it depends on; the package files do not repeat either. A package is *ready* when its status is `open` and everything in its _Depends on_ column is `done`. Ready packages can be worked in parallel, also across the repositories. A dependency that has no work package yet keeps a package `blocked`; it is replaced by the package when that is planned.

[#how]
== How to Work a Package

* *Take it.* A package is claimed by a pull request, opened as a draft before any other work, whose first commit sets the package to `in progress` in the table above and names the package in its title. Before opening it, list the open pull requests of this repository: one that names the package holds the claim, and the package is then not yours to start. This is a convention and nothing enforces it: two sessions can pass the check at the same moment. When two pull requests name the same package, the one created later is closed by hand, by its own session or by the operator, and its session takes another package. The same pull request sets it to `done` when it finishes. A package whose dependency lies in another repository is ready when that dependency is merged there and its `SNAPSHOT` is deployed.
* *Trace first.* The packages are cut from the roadmap items, with the requirements, sections, and watch documents the roadmap names. Before code, build the trace matrix of the project skill `traced-implementation` (`../plan-marshall-documentation/.claude/skills/traced-implementation/SKILL.md`) for the package: every requirement bullet, every specification section, and every watch item anchored to them, each with its destinations. Split or extend the package where the matrix shows it; a row left out is recorded `out of slice` with its reason.
* *Present and remaining.* The roadmap item a package serves states what the code already covers. Read it first: a package delivers the remainder, never a second form of what exists.
* *Dependencies are the order.* The roadmap milestone a package serves says for which exit it is needed, not when it may start. Add a dependency you discover, and a new package, to the table above.
* *Done.* A package is done with its guarding tests, `verify`, `verify -Ppre-commit` (its rewrites reviewed and committed), `verify -Pcoverage`, and `verify -Pintegration-tests` green, and the native build where it touches a binary.
* *Documents.* A statement of a requirement or specification that a package proves wrong is corrected in the documentation repository, never worked around in code. The concept, developer, and user documentation of the package, the deletion of the implemented specification sections and watch items, and the update of the roadmap item go into one pull request in `plan-marshall-documentation` that names the code pull request and merges after it.
