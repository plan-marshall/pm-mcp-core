= Work Packages of `pm-mcp-core`
:toc: left
:toclevels: 2
:nofooter:

One plan file per work package. A work package is what one session takes up and lands as one pull request here, with the specification, the implementation watch and the traceability of this repository (link:../Specification.adoc[Specification], link:../ImplementationWatch.adoc[Implementation Watch], link:../Traceability.adoc[Traceability]) as part of the same work. The files hold the tasks; what the tasks mean and require is stated in those documents and in the requirements, use cases and roadmap of `plan-marshall-documentation`, and linked by relative paths. The links assume the repositories checked out beside each other (`../plan-marshall-documentation`, `../pm-mcp-clients`, `../pm-mcp-core`, `../plan-marshall-mcp`); they do not resolve in the web view of a single repository.

The modules of this repository, their packages and their dependency rules are listed only in the link:../../../plan-marshall-documentation/doc/specification/module-structure.adoc[Module Structure Specification]; each package file names where it lands.

[#packages]
== Packages

The packages listed serve roadmap Milestones 2 to 4, and the packages the client work of `pm-mcp-clients` needs, which serve items of later milestones named in their _Serves_ column; the rest of the later milestones is not cut into packages yet, and a package that names one of them as the home of something says what is left out here. This table is the only place that states the status of a package and what it depends on; the package files do not repeat either. The table lists the packages not yet done: a done package leaves the table and its file is deleted, so its implementation, its developer documentation and its ADRs are what remain of it. A package is *ready* when its status is `open` and its _Depends on_ column names no package of this table (a dependency in another repository is done when its row there says so). Ready packages can be worked in parallel, also across the repositories. A dependency that has no work package yet keeps a package `blocked`; it is replaced by the package when that is planned. A package that depends on a `blocked` package is `blocked` too.

[#how]
== How to Work a Package

* *Take it.* A package is worked in the usual plan-marshall flow: a branch, the commits of the plan, and a pull request opened at finalize. The pull request of the package removes its row from the table above and deletes its package file, within its commits, and drops the package from the _Depends on_ column of every row that names it. Nothing marks a package as taken before that pull request is open, so list the open pull requests of this repository for one that names the package before starting. A package whose dependency lies in another repository is ready when that dependency is merged there and its `SNAPSHOT` is deployed.
* *Trace first.* The packages are cut from the roadmap items, with the requirements, sections, and watch documents the roadmap names. Before code, build the trace matrix of the project skill `traced-implementation` (`../plan-marshall-documentation/.claude/skills/traced-implementation/SKILL.md`) for the package: every requirement bullet, every specification section, and every watch item anchored to them, each with its destinations. Split or extend the package where the matrix shows it; a row left out is recorded `out of slice` with its reason.
* *Present and remaining.* The roadmap item a package serves states what the code already covers. Read it first: a package delivers the remainder, never a second form of what exists.
* *Dependencies are the order.* The roadmap milestone a package serves says for which exit it is needed, not when it may start. Add a dependency you discover, and a new package, to the table above.
* *Log messages.* A package adds a log record to the holder of the module it changes (`CoreLogMessages`, `RuntimeLogMessages`, `WorkflowLogMessages`, or the provider's `<X>LogMessages`, created with its first record), at the next free identifier of the level: INFO 001–099, WARN 100–199, ERROR 200–299. There are no identifier blocks per workstream, and no holder is declared as shared surface of a plan (link:../adr/005-one-log-message-holder-per-module.adoc[ADR 005]).
* *Done.* A package is done with its guarding tests, `verify`, `verify -Ppre-commit` (its rewrites reviewed and committed), `verify -Pcoverage`, and `verify -Pintegration-tests` green, and the native build where it touches a binary.
* *Documents.* The code documentation of a package (Javadoc and `package-info.java`), its work package file with the index, its developer documentation, and one architectural decision record (ADR) per design decision live here: `{module}/README.adoc` describes the module, `{module}/doc/developer/{package}.adoc` holds the developer documentation of a package, `{module}/doc/adr/{package}/NNN-{slug}.adoc` its ADRs, and `doc/adr/NNN-{slug}.adoc` the ADRs of the whole repository. The specification, the implementation watch and the traceability of this repository live here as well (link:../adr/007-specifications-of-the-engine-in-this-repository.adoc[ADR 007]): the pull request of the package deletes the implemented specification sections and watch items, corrects a specification statement it proves wrong (never working around it in code), and adds the `Implementation:`, `Verified by:` and `Documentation:` lines of the requirements it implements to link:../Traceability.adoc[Traceability]. The requirements, the roadmap, `implementation-watch/cross-cutting.adoc` and the specifications every repository shares live in `plan-marshall-documentation`: a package opens a pull request there only to correct a requirement or to change one of those; the concept and user documentation of the package and the check-off of its roadmap item are written there at the milestone exit, from the rows its pull request body lists as owed.
