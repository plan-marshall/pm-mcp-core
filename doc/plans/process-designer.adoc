== What

* *Specification first*: the package writes the change Designing a Process into `plan-marshall-documentation` as part of its own work, once it and UC-PLN-3 are agreed: the requirement the change drafts in the link:../../../plan-marshall-documentation/doc/requirements/02-workflow.adoc[workflow requirements] (today no requirement lets the operator change the process of a plan); the machine level of workflow units and its precedence; the validation endpoint with its dry-run composition; the place and remove endpoints and their audit; the project-level placing as a short landing; the catalogue of building blocks served to the client.
* *What can be designed*: a unit the operator may own, the project-owned units of the state catalogue (the phase units, `remediation.*`, `replan`, `adjudicate.decisions`, `git.commit_and_push`), the variants of the plan behaviour axes (`landing.*`, `method.*`, `ask.*`), and recipes; a compiled-only unit (epic, setup, bootstrap, source units, `chat`, …) is served read-only as a building block, and placing one, or a unit of its name, is refused.
* *The axis variants as owned units*: each variant of `landing.*`, `method.*`, and `ask.*` becomes an owned unit with the compiled invariants of the part of the process it takes over (a landing variant those of the landing part of `finalize`, a method variant those of the order of tasks in `execute`, an asking variant those of the phase transitions it waits at). An axis's variants are a closed list: a variant can be changed, never added; placing a variant name the axis does not list is refused.
* *Recipes at project level only*: a recipe's workflow lives beside its recipe, `.marshall/recipes/<id>.pmwf`, and is designed and placed only there; the machine level holds workflow units, never recipes, and placing a recipe at machine level is refused.
* *The machine level*: a new level of workflow units, `<PM_MCP_BASE>/workflows/<unit>.pmwf` (the operator's, never committed), in force for every project of the machine that has no copy of its own. The loader of link:project-units-and-invariants.adoc[`project-units-and-invariants`] resolves a unit by the precedence project copy › machine copy › compiled default, an absent unit deferring to the next level; a unit present but unparsable or violating a declaration bound or an invariant never falls back to the next level: it refuses the lifecycle of every project it is in force for, naming the file and line. The plan's own choice of an axis variant stays as the change Plan Behaviour Axes defines (link:../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#change-plan-axes[Use Cases, Plan Behaviour Axes]). A machine unit is held to the same declaration bounds and compiled invariants as a project unit.
* *No copies at setup*: the setup no longer copies every default unit into `.marshall/config/` (`setup.prepare-workspace`); a project holds only the units it changes. The package changes this in the specification (link:../../../plan-marshall-documentation/doc/specification/workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL § Project-Owned Workflow Units], items 1 and 2; link:../../../plan-marshall-documentation/doc/specification/domain-extensions/04-setup-state-machine.adoc#project-setup-state-machine[Domain Extensions § Setup State Machine]; link:../../../plan-marshall-documentation/doc/specification/state-catalogue/06-setup-epic-other.adoc[State Catalogue § Setup]; link:../../../plan-marshall-documentation/doc/specification/filesystem-layout/03-project-store.adoc[Filesystem Layout § Project Store]; link:../../../plan-marshall-documentation/doc/specification/store-schemas/07-project-configuration.adoc[Store Schemas § Project Configuration]) and in the code (the setup unit, and the loader of link:project-units-and-invariants.adoc[`project-units-and-invariants`] where it is already implemented). The plan instance's header digests name the level and file each unit came from, so a changed machine unit is adopted through the existing `config_drift` like a changed project unit.
* *The installed units*: for a project, each designable unit in force with its level, and the text of each level present (project copy, machine copy, compiled default), so the designer can start from any of them; a compiled default only as text to copy.
* *Validation*: one endpoint takes the unit's text, its kind and name, and a target project, and validates it exactly as the loader would load it: the parse, the static verification rules, the compiled invariants of a project-owned unit, and a composition dry-run, a plan instance composed with the unit against the project's effective configuration, roles, and providers, started nowhere and stored nowhere. The answer lists the findings, each with its rule, line, and column; the parsed structure of the unit (its states, calls, outcomes, and transitions) whenever the text parses, also when other rules find problems, so the web app keeps its structure view in step without a parser of its own; and, when there are no findings, the composed process in the structure the plan view shows (UC-PLN-1). The validation runs nothing of the unit. The text, pasted or from an uploaded file, must be UTF-8 within a size limit the runtime declares as a bound; a text that is not, or exceeds it, is refused before the parse.
* *The catalogue of building blocks*: for a project, the primitives, the roles of its effective role set, the reusable sub-workflows, and the compiled units, each with what the designer inserts as text.
* *Placing*: at machine level, writing the machine copy; at project level, writing `.marshall/config/<unit>.pmwf` in the project's checkout and landing it as a short landing like `git.land-removal` and the epic's ledger (one commit, landed by the project's landing: `landing.pull-request` or `landing.main`; with `landing.files` it stays uncommitted in the working tree). A project unit is in force for a plan when the plan's checkout or worktree has it: a new plan takes it once it has landed on the base branch; a running plan adopts it through `config_drift`, where the composition rules allow it, once its worktree gets it at its next sync with the base; with `landing.files` it stays in the operator's checkout and no plan takes it until it is committed. A machine placing or removing validates against every enrolled project the unit would reach (for a removal, the unit of the next level) and is refused while any of them fails, naming each such project. Every placing validates again in the same request and refuses a unit with a finding; it carries the digest of the unit it replaces (none for a new one) and is refused with the current one where that changed meanwhile, so the difference the client showed is the one confirmed. Removing a placed unit returns to the next level, the project's copy through the same short landing.
* *Audit*: every placing and removing as an audit record of link:audit-trail.adoc[`audit-trail`]: who, when, the channel, the level, the project, the unit, and the digests before and after.
* *The endpoints* (the change fixes their names; proposed): `GET /api/v1/projects/{project_id}/workflows` (the installed units), `GET /api/v1/projects/{project_id}/workflows/catalogue` (the building blocks), `POST /api/v1/workflows/validate` (text, kind, name, target project → findings, the parsed structure, and the composed process), `PUT` and `DELETE /api/v1/workflows/{unit}` (machine level), `PUT` and `DELETE /api/v1/projects/{project_id}/workflows/{unit}` (project level); placing and removing accepted from a paired web device and the loopback listener, audited with their channel. Downloading needs no endpoint: the client writes the text it holds.
* Out of this package: a unit designed for one plan only and its promotion, and a model's help in designing (open points of the use case).

== Done When

The requirement and the specification of the change are merged in `plan-marshall-documentation`; a fixture unit at each level shows the precedence project copy › machine copy › compiled default, and removing a copy returns to the next level; a set-up project holds no copied default unit; an unparsable and a violating unit at project and at machine level each refuse the lifecycle with file and line and never fall back to the next level; a changed machine unit is adopted by a running plan through `config_drift`; the validation of a fixture with a parse error, a rule violation, and an invariant violation returns each with its rule, line, and column, the parsed structure for every fixture that parses, and for a valid one its composed process without starting or storing anything; a text that is not UTF-8 or exceeds the declared size bound is refused before the parse; a machine placing and a machine removal that fail for one enrolled project are refused naming it; a new axis variant and a recipe at machine level are refused, and a changed variant is held to the invariants of its part of the process; a new plan takes a project unit only once it is on the base branch, a running plan at its next sync with the base, and with `landing.files` no plan until it is committed; placing a unit with a finding, a compiled-only unit, or over a unit whose digest changed meanwhile is refused; a project-level placing lands as one commit through `landing.pull-request` and `landing.main` and stays uncommitted with `landing.files`; every placing and removing is audited with its channel and both digests.
