== Plans Started from an Epic's Row

[#PM-WATCH-CLI-1]
=== PM-WATCH-CLI-1: A plan started from its epic row is linked to its epic

Anchor:: link:../specification/model-work/08-epic-coordination.adoc#server-started-plans[Model Work § Server-Started Plans] (Start transaction, Single Epic Pointer)
Hazard:: A plan whose source was a staged specification file of its epic was detected as epic-linked by one probe
and reported `not_epic_pointer` by every transition probe.
Guard:: Linkage test for a plan the server started through `source-epic-row` (the staged spec section of the queue row
as request): `origin.epic_id` is set by the start transaction alone, and every surface (`pm-operator status`, the
web app, the epic ledger, `outbox:send`, the landing step) reports the plan as linked from that one field; a start of a
plan from other sources whose new `plan_id` equals a non-terminal queue row returns to `start.ready` with
`epic_pointer_mismatch`, so only its epic starts that row's plan; a start whose row is unknown or not launchable
creates no plan and marks the row `held`.
Fixture:: ledger-decomposition `source_id` = `.plan/orchestrator/orchestrator-refactor/plans/PLAN-02-…md`: detection
true, transition probe `not_epic_pointer` ×3.
Source:: plan-marshall lesson 2026-09-23-15-001.

== Token-Lane Credential Architecture & OS Keyring Integration

[#PM-WATCH-CLI-2]
=== PM-WATCH-CLI-2: Repository identity is the remote, never the checkout path

Anchor:: link:../specification/credentials-and-enrolment/01-provider-credentials.adoc#_token_lane_credential_architecture_os_keyring_integration[CLI & Security § Token-Lane Credential Architecture],
link:../specification/credentials-and-enrolment/01-provider-credentials.adoc#derived-tokens[§ Short-Lived Derived Tokens],
link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-2[PM-SEC-2], link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CRED-1[PM-CRED-1]
Hazard:: A foreign repository was identified by its checkout path. A renamed repository kept working for git and REST
reads through the provider's redirect, but the App installation-token mint did not follow the rename, so
credential lookups broke silently.
Guard:: The cross-project grant identifies its target project by remote owner and name, never by a checkout path,
and the credential entry's `<project>` is the enrolment identifier, never derived from a remote URL or a checkout
path, so a remote rename leaves the credential lookup unchanged. A derived installation token is dropped exactly on
the specified triggers: its credential entry rotated, removed or re-set, a request with it failing `auth_failed`, and
the runtime stopping (test per trigger: the next request mints a new token); the native transport's origin check
(`remote_origin_mismatch`) compares origins, never checkout paths.
Fixture:: `pr-agent-settings` → `cuioss-review-bot` (cuioss-organization 0.30.0, plan-marshall #1603).
Source:: plan-marshall lessons 2026-09-24-12-001 and 2026-09-24-12-007.

[#PM-WATCH-CLI-4]
=== PM-WATCH-CLI-4: The upstream filing credential is proven before any filing job exists

Anchor:: link:../specification/credentials-and-enrolment/01-provider-credentials.adoc#_token_lane_credential_architecture_os_keyring_integration[CLI & Security § Token-Lane Credential Architecture],
link:../specification/store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas § Lesson Record] (Upstream Release),
link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-ARCH-2[PM-ARCH-2], link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CRED-5[PM-CRED-5]
Hazard:: An upstream route was built before anyone proved that a consumer's credential can write to the vendor
tracker.
Guard:: The operator-confirmed filing job is offered only after a write-permission probe on the target tracker with
the enrolled credential passed; without a passed probe the release action only renders the issue body for the
operator to file (test: a failed or missing probe offers no filing job; matched control: a passed probe offers it).
Source:: plan-marshall lessons-routing PLAN-LR-03 D0.

[#PM-WATCH-CLI-5]
=== PM-WATCH-CLI-5: A derived installation token never outlives its secret and never leaks

Anchor:: link:../specification/credentials-and-enrolment/01-provider-credentials.adoc#derived-tokens[CLI & Security § Short-Lived Derived Tokens],
link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CRED-5[PM-CRED-5]
Hazard:: An in-memory cache of App installation tokens keeps acting after the App key was rotated or revoked, or a
cached token reaches a log, an audit record, a job output, or a tool result unredacted, because it never passed the
stored-secret resolution path that registers redaction.
Guard:: Tests rotate, remove, and re-set the `github` entry and answer a request with `auth_failed`: each drops every
cached token of the entry, and the next operation mints a new one; no token is used later than 5 minutes before its
expiry; every token is registered for redaction at mint, and a canary token value echoed in a recorded provider error
body is absent from `daemon.log`, `audit.jsonl`, job logs, and every tool result; no derived token is written to a
store or exported.
Source:: design review.

[#PM-WATCH-CLI-6]
=== PM-WATCH-CLI-6: The origin check sees the effective URL, whatever rewrites it

Anchor:: link:../specification/credentials-and-enrolment/01-provider-credentials.adoc#native-confinement[CLI & Security § Native Operation Confinement]
Hazard:: A repository-controlled rewrite (`url.<base>.insteadOf`, `pushInsteadOf`, `remote.<name>.pushurl`, a file
included through `includeIf`) or an HTTP redirect in the JGit transport sends the agent credential to a host other
than the origin of the credential entry.
Guard:: Adversarial fixture repositories whose remote is redirected to a foreign host by each of `insteadOf`,
`pushInsteadOf`, `pushurl`, and an `includeIf`-included file inside the repository, plus a recorded redirect from the
provider origin to a foreign host: every fetch and push refuses with `remote_origin_mismatch`, appends one `security`
audit record, and a listener on the foreign host counts zero connections; an `includeIf` target outside the
repository is ignored (its rewrite never applies, the foreign listener counts zero connections); matched control: the
same rewrites onto the credential origin pass.
Source:: design review.

[#PM-WATCH-CLI-7]
=== PM-WATCH-CLI-7: The GitHub API and web origins are paired, never confused

Anchor:: link:../specification/credentials-and-enrolment/01-provider-credentials.adoc#agent-credentials[CLI & Security § Agent Credentials of the Native Variant],
link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CRED-5[PM-CRED-5]
Hazard:: For `github.com` the API origin (`https://api.github.com`) differs from the web and transport origin
(`https://github.com`); an origin pin that takes one for the other sends the credential to the wrong origin or
refuses a valid request.
Guard:: Table test over a `github.com` entry, a GitHub Enterprise entry, and a GitLab entry: REST and GraphQL go to
the derived API origin and git transport to the `url` origin, each authenticated; a request to any other origin (for
example `api.github.com` with an Enterprise entry) carries no authentication header and is refused; GitLab uses the
`url` origin for both.
Source:: design review.

[#PM-WATCH-CLI-8]
=== PM-WATCH-CLI-8: No agent token and no askpass helper reach a CLI-variant job

Anchor:: link:../specification/credentials-and-enrolment/01-provider-credentials.adoc#cli-variant-credentials[CLI & Security § Credentials of the CLI Variant]
Hazard:: A token variable (`GH_TOKEN`, `GITHUB_TOKEN`, `GITLAB_TOKEN`) or an askpass or credential helper served by
a PM-MCP binary reaches the environment of a CLI `git`, `gh`, or `glab` job, where every descendant, repository hooks
included, and every same-user process can read it.
Guard:: CLI-variant job fixtures with a hook that records its environment and argument vector, run while the
runtime's own environment contains the forbidden variables: no token variable, no `GIT_ASKPASS` or `SSH_ASKPASS`, no
credential helper naming a PM-MCP binary (`pm-mcp`, `pm-operator`, `pm-mcpd`, `pm-exec`), and no secret canary value
appear, while the operator's ambient rows of the Job
Environment are present; the job's audit record carries `identity: operator_ambient`.
Source:: design review.

[#PM-WATCH-CLI-9]
=== PM-WATCH-CLI-9: A native operation never starts a process

Anchor:: link:../specification/credentials-and-enrolment/01-provider-credentials.adoc#native-confinement[CLI & Security § Native Operation Confinement]
Hazard:: JGit has several process entry points (hooks, filter drivers, `core.fsmonitor`, commit signing,
`FS.runInShell`); an `FS` subclass that covers only some of them leaves a repository value able to start a process
inside the runtime.
Guard:: Native-selected fixture repositories with a hook in `.git/hooks/`, a `core.hooksPath` hook, a clean/smudge
filter driver, `core.fsmonitor`, `commit.gpgSign` with `gpg.program`, and `core.sshCommand`: every native operation
that would reach one refuses with `capability_missing` or ignores the non-allowlisted key, and a sentinel file each
program would write stays absent; a build test enumerates the process call sites of the pinned JGit version, so an
upgrade that adds one fails until the `FS` subclass covers it.
Source:: design review.

[#PM-WATCH-CLI-30]
=== PM-WATCH-CLI-30: A lost rotation of the user refresh token locks the App out

Anchor:: link:../specification/credentials-and-enrolment/01-provider-credentials.adoc#user-access-token[CLI & Security § Agent Credentials of the Native Variant] (User access token)
Hazard:: Every refresh of a GitHub App user access token rotates both tokens: the old access token is revoked at
once and each refresh token is accepted once. Two concurrent refreshes, a new access token used before the new
refresh token is stored, or a holder that keeps the old access token each end in `401` for running plans, and a
refresh token lost between the provider's answer and the store makes every write fail until the operator logs in
again.
Guard:: Provider fake that rotates on refresh and revokes the old tokens: concurrent writes of several plans cause
exactly one refresh per entry, and every write after it carries the new access token; a crash injected after the
provider's answer and before the store write leaves the entry `credential_check_failed` naming
`pm-operator credentials set github`, never a silent retry with the spent refresh token and never a write under
an installation token; the new refresh token is in the active backend, read back, before the first use of the
new access token; no token appears in a log, an audit record (`user_token_refreshed` carries the expiry only), or
a model-facing representation; the refresh sends no client secret.
Fixture:: GitHub App device flow: access token valid 8 h, refresh token about 6 months, both rotated on every
refresh, the old access token revoked at once, refresh without `client_secret`.
Source:: link:../../../plan-marshall-documentation/doc/specification/evaluation.adoc#results[Evaluation Reference], Review-bot triggers and pull-request authorship.

[#PM-WATCH-CLI-31]
=== PM-WATCH-CLI-31: An organisation read cut by a cap is taken for the whole population

Anchor:: link:../specification/credentials-and-enrolment/01-provider-credentials.adoc#cross-repository-reads[CLI & Security § Cross-Repository Reads],
link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXEC-5[PM-EXEC-5]
Hazard:: A repository list or code search over an organisation ends at a page bound, at the provider's cap on
search results, or at the repositories the credential can see; a consumer that reads the cut result as complete
reports "no other repository uses this" for a population it never saw. Without the grant check the same reads
give a plan the whole organisation the credential reaches.
Guard:: Provider fakes for both providers: a list beyond the page bound, a search with the provider's
incomplete-results flag, and an organisation with repositories outside the App's installation each return
`completeness: incomplete` with the bound (`page_cap`, `provider_result_cap`, `not_visible`), and a consumer that
needs the whole population treats it as unknown; each of the four operations is refused `grant_missing` without a
grant naming its organisation, group, or repository, a `--org` grant does not open another organisation, and a
grant is refused for any access but `read`; file contents and search excerpts pass the level-1 validator before
they reach a model; matched control: `ci.labels` of the project's own repository needs no grant.
Source:: design review (migration inventory: organisation-wide reads had no surface).

== Operator Channel Isolation & Privileged CLI (`pm-operator`)

[#PM-WATCH-CLI-23]
=== PM-WATCH-CLI-23: Unenrol never strands live work, and a store never changes its root

Anchor:: link:../specification/credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#enrolment-lifecycle-release[CLI & Security § Enrolment, Lifecycle Gate & Release],
link:../specification/store-schemas/11-enrolment-store.adoc#project-store-identity[Store Schemas § Project Store Identity]
Hazard:: A re-enrolment from a different root silently adopts another checkout's plans, ledger, and findings. (The
unenrol half is guarded: link:../../../plan-marshall-documentation/doc/developer/enrolment-store.adoc#pitfalls[Developer Guide § Enrolment Store, Pitfalls].)
Guard:: Re-enrolling the same `project_id` from a different root is refused with `project_store_root_mismatch`;
control: re-enrolling from the recorded root reuses the store.
Source:: design review.

[#PM-WATCH-CLI-25]
=== PM-WATCH-CLI-25: The lifecycle gate is a release constant, and only a pilot passes a closed gate

Anchor:: link:../specification/credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#enrolment-lifecycle-release[CLI & Security § Enrolment, Lifecycle Gate & Release] (Lifecycle gate)
Hazard:: A scope creation that bypasses the gate, or reads an enrolment that was not verified, lets a pre-Stage-4
release create plans everywhere. (The gate decision, its compiled position and the HMAC over `pilot` are guarded:
link:../../../plan-marshall-documentation/doc/developer/enrolment-store.adoc#pitfalls[Developer Guide § Enrolment Store, Pitfalls].)
Guard:: With the gate constant closed: `start.create-scope` in a project enrolled without `--pilot` is refused
`lifecycle_closed` and creates nothing, and in a project enrolled with `--pilot` it creates the scope; re-running
`enrol` without `--pilot` refuses later scope creations while the project's live plans continue. With the gate
constant open: both projects create scopes.
Source:: design review.

[#PM-WATCH-CLI-29]
=== PM-WATCH-CLI-29: A project release ends its scopes `released`, and re-enrolment reopens it

Anchor:: link:../specification/credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#enrolment-lifecycle-release[CLI, Coordination & Security § Enrolment, Lifecycle Gate & Release]
Hazard:: A released project keeps plans and epics running that nobody follows any more, or a re-enrolled project stays
closed for good.
Guard:: Test: `pm-operator project release` with a running plan, a paused plan, an active epic, and a pending entry
writes `released_at`, ends both plans with the outcome `released` (archived like a completed plan) and the epic with
the `terminal_reason` `released` (archived in the machine store only, its ledger bytes unchanged and no commit),
deletes the pending entry with its sources, touches no branch, and appends an `operator` audit record; then the
opening of a start entry for a plan or an epic and `start.create-scope` refuse with `lifecycle_closed` while the
workspace scope stays available; a release while a short landing of the project runs past its bound is refused
`release_landing_pending` and ends nothing. Matched control: `pm-operator enrol` clears `released_at` (audited) and the lifecycle
is offered again under the lifecycle gate.
Source:: design review.
