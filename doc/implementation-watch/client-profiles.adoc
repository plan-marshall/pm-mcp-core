== Normative Client Profile JSON Schema

[#PM-WATCH-CLIENT-8]
=== PM-WATCH-CLIENT-8: A writable harness path never covers a managed settings, command, or skill file

Anchor:: link:../specification/client-profiles/01-profile-schema.adoc#_normative_client_profile_json_schema[Client Profiles § Normative Client Profile JSON Schema] (Writable paths)
Hazard:: A `headless.writable_paths` entry that names a harness home as a whole, or a directory holding the settings,
command, or skill file the bundle installed, puts that file into the Landlock write set of every worker: a worker
rewrites the host's deny rules or shim skill, and the host runs without them from then on.
Guard:: Profile validation refuses a `headless.writable_paths` entry that equals, contains, or lies under a settings,
command, or skill file the client's bundle manifest manages, or a shared configuration file in which the bundle owns
an `enforcement` element; a build-time test runs the rule over every shipped profile against its own bundle
manifest; negative fixture: a profile with the entry `~/.claude` and one with the path of the managed settings file
are each refused naming the entry and the managed file; runtime control: a worker's write to the managed settings
file fails.
Hazard:: The `claude` harness cannot run headless without rewriting `~/.claude.json`, the harness's
own state file; were an element the bundle owns held there, a worker with the file in its write set could change or
remove it, and the host's enforcement would change without the operator.
Guard:: The bundle owns nothing in a writable shared configuration file, `~/.claude.json` included (build-time test over
every shipped profile and manifest); a fixture worker that rewrites a recorded owned element elsewhere is reported `bundle_modified`
with that element by `pm-operator client status`; a confined `claude` writer worker
runs with exactly the declared entries (not `~/.claude` as a whole) before the _(provisional)_ marker of its
sub-paths is removed.
Fixture:: Claude Code 2.1.291 under Landlock ABI 8: writes to `~/.claude.json` (a file rule; `$HOME` not needed),
5 files under `~/.claude` (session transcript, synced plugin and skill manifests), 1 MCP log under
`~/.cache/claude-cli-nodejs`; unconfined also `~/.claude/backups/` and `~/.claude/sessions/<pid>.json`.
Source:: design review; link:../../../plan-marshall-documentation/doc/specification/evaluation.adoc#results[Evaluation Reference], Gate 13.

[#PM-WATCH-CLIENT-11]
=== PM-WATCH-CLIENT-11: A harness that cannot restrict its workers

Anchor:: link:../specification/client-profiles/01-profile-schema.adoc#role-classes[Client Profiles § Role Classes of a Harness],
link:../specification/client-profiles/01-profile-schema.adoc#worker-block[Client Profiles § Worker Block] (`worker.eligible`),
link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2]
Hazard:: Antigravity runs every worker with all its host tools and beside the MCP servers of the operator's own
configuration (`tool_set: advisory`, `mcp_config.exclusive: false`). That is accepted for `writer` and `read_only`
roles and fatal for the screener: a profile that declared `zero_tool` for it would hand untrusted text to a model
with a shell. Beside that, three things were seen in its measurement and not yet tested under target conditions:
the operator's global configuration may hold an MCP entry named `plan-marshall`, so a worker would start it beside
its job relay under the same server name; all `agy` processes share a tool schema cache per
server name, while the tool list differs per role; and task inputs of 8,000 characters and more were read back with
the host's `view_file` from its own step output, outside the server's resource tools. Its fault matrix passed only as
a three-trial smoke run with unconfined workers on macOS.
Guard:: Profile validation refuses a non-null `zero_tool` on a profile whose `mcp_config.exclusive` is `false`, and
a fixture profile proves it. `worker.eligible` of `antigravity` becomes `true` only after: the ten-trial fault matrix
with confined workers on Linux, with a global `plan-marshall` MCP entry present in the operator's configuration (no tool of it is listed to the
worker); two workers of roles with different tool sets running at once, each listing exactly its own
tools; and its writable paths under Landlock, the step output it reads back included, recorded in
`headless.writable_paths`.
Source:: link:../../../plan-marshall-documentation/doc/specification/evaluation.adoc[Evaluation Reference] (Gates 13 and 16), design review.

[#PM-WATCH-CLIENT-12]
=== PM-WATCH-CLIENT-12: A harness that cuts a tool result loses the task

Anchor:: link:../specification/client-profiles/01-profile-schema.adoc#headless-tool-result-limit[Client Profiles § Normative Client Profile JSON Schema] (Tool-result limit),
link:../specification/model-work/02-task-protocol.adoc#offer[Model Work § Offer]
Hazard:: A harness truncates an MCP tool result above its own limit and keeps the full text in a file that a
worker restricted to the server's tools cannot read. An offer whose task identifiers lie in the cut part leaves
the worker without its task: it acknowledges and submits with guessed ids, every call is refused, and the task
ends unsubmitted.
Guard:: Table test per harness with a declared `tool_result_limit_chars` over task inputs below, at, and above the
limit (8 000, 32 000, 128 000 characters): no tool result the server returns exceeds the limit, the task id and the
`ack` link are in the first part of every offer, and the worker completes the task by reading the parts as
resources; negative control: with the limit unset the largest input reproduces the loss; the exact threshold of
`opencode` is measured and replaces the provisional `32000`; a profile with a limit and no `resource_tools` is
refused.
Fixture:: OpenCode 1.18.34: 8 000 and 32 000 characters completed, 128 000 failed ("…128402 bytes truncated…",
full output saved under `~/.local/share/opencode/tool-output/`); the worker's `pull_ack` calls with the guessed ids
`h128000`, `128000`, `gate13` and a `pull_submit` with `task_id` `test` were all refused, and it ended with
`{"task_id":"unknown"}`. Claude Code 2.1.291 completed all three sizes.
Source:: link:../../../plan-marshall-documentation/doc/specification/evaluation.adoc#results[Evaluation Reference], Gate 13.

== On-the-Fly Placeholder Rendering Rules

[#PM-WATCH-CLIENT-1]
=== PM-WATCH-CLIENT-1: Format-accuracy evidence is secondhand

Anchor:: link:../specification/client-profiles/02-placeholders.adoc#_rendering_invariants[Client Profiles § Rendering Invariants],
link:../specification/client-profiles/02-placeholders.adoc#calibration-decision[Client Profiles § Calibration Decision],
link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-TOOL-5[PM-TOOL-5], link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-IMPL-2[PM-IMPL-2],
link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-TEST-6[PM-TEST-6]
Hazard:: The TOON wire form is a settled design decision, but its parse fidelity per client runtime is unmeasured;
the only format-accuracy figures in circulation are secondhand (an up-to-40% drop from generic Markdown, a
model-specific optimal format, parsing accuracy YAML 51.9% / JSON 43.1% / XML 33.8%). A runtime that parses TOON
poorly degrades silently.
Guard:: Keep the decision. Before revisiting TOON or the Calibration Decision, read the primary source (Ouyang et al.
2026, _SkCC_, arXiv 2605.03353) and record what it measured; never cite the figures in a specification before
that. The `PM-TEST-6` baseline of every client includes a TOON representation-parsing scenario (the model extracts
`links` and `facts` from a `pm_state` result), link:../specification/workflow-dsl/07-loop-back-diagrams-verification.adoc#behavioural-conformance-harness[Workflow DSL § Behavioural Conformance Harness].
Fixture:: the figures above, marked unverified.
Source:: plan-marshall defect instrumentation-substrate PLAN-03 deliverable 5 and § Folded finding — `next-level-006`.

== Embedded Client Bundle `bundle-manifest.json` Schema

[#PM-WATCH-CLIENT-6]
=== PM-WATCH-CLIENT-6: Every artifact an emitted instruction references is emitted too

Anchor:: link:../specification/client-profiles/02-placeholders.adoc#_rendering_invariants[Client Profiles § Rendering Invariants],
link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SKILL-2[PM-SKILL-2], link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2]
Hazard:: A target emitter shipped a routing table whose referenced documents were not part of that target's unit.
Guard:: Build-time test: every template is rendered for every built-in profile and fails on
any unresolved or missing form (Profile Completeness); a `{{...}}` token that fails to resolve fails the rendering

Fixture:: an opencode unit whose routing table referenced 8 `workflow/` documents that were not emitted (also
`phase-5-execute`).
Source:: plan-marshall defect process-compliance inbox module-budget-campaign-completion-008.

== Endpoint Harness

[#PM-WATCH-CLIENT-14]
=== PM-WATCH-CLIENT-14: An endpoint's defaults and silent acceptance never decide a verdict

Anchor:: link:../specification/client-profiles/03-endpoint-harness.adoc#endpoint-harness[Client Profiles § Endpoint Harness],
link:../specification/client-profiles/03-endpoint-harness.adoc#weights-identity[Client Profiles § Weights Identity],
link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2], link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-6[PM-WORK-6]
Hazard:: A local model server that speaks the OpenAI chat format is not the OpenAI service: it may stream by default
where the client library expects one JSON document, accept a `tools` member and answer with an invented tool result
and no tool call, accept a response schema and not hold to it, refuse in prose instead of an error status, and load
other weights under the same model name after an operating system update or on another chip. Each of these returns a
well-formed answer, so a screener verdict or a grade can rest on an answer the request never asked for, and a
qualification record can outlive the weights it graded. Any program can listen on a loopback port.
Guard:: The request sets every value the endpoint has a default for (streaming off among them) and never sends
`tools`; the server validates every answer against the result schema whatever `result_schema` says; a refusal, a
non-validating answer, an HTTP error, and a timeout each end the attempt without a result, and a screening stays
`unscreened`. Fixtures: a stub endpoint that streams unless told not to, one that returns prose under a schema, one
that answers a `tools` request with an invented result (recorded `tools_ignored`), one whose weights identity changes
between two runtime starts (the record goes stale, `harness_updated` audited), and a stub listening on the profile's
port from an executable other than the enrolled one (refused before any task text is sent).
Source:: Article analysis `macos27-on-device-llm` of plan-marshall-documentation (the measurements of a local model server it records).

[#PM-WATCH-CLIENT-15]
=== PM-WATCH-CLIENT-15: A remote endpoint is addressed by a versioned id, holds a key for one origin, and logs no body

Anchor:: link:../specification/client-profiles/04-judgment-endpoint.adoc#system-one-request[Client Profiles § The Request and the Answer],
link:../specification/client-profiles/04-judgment-endpoint.adoc#remote-form[§ Remote Form],
link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2], link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CRED-5[PM-CRED-5]
Hazard:: A hosted service moves its alias (`latest`, `preview`) to a new release without a change of the caller, so a
qualification record and a decision calibration outlive the model they graded. The request body carries the facts of a
task, and a client library's debug logging or an error report quotes it. A redirect, a proxy setting, or an
operator-edited `base_url` can send the key to another origin. A service that is overloaded (`429`, `529`) invites a
client library to retry inside an attempt, past the deadline of the vote. The answer's `confidence` member reads like
a probability.
Guard:: The verification sends the role's model id and refuses an id the service answers with another id
(`model_alias`); every answer is checked for the requested id, so a silent re-route ends the attempt. A request to an
origin other than the credential entry's, and a redirect to another origin or to `http`, sends no secret and ends the
attempt (matched control: the entry's own origin succeeds). No log, audit line, or error text holds a request body or
the key (a fixture whose answer echoes the body). The runtime retries nothing inside an attempt; the task's re-offer
budget decides. Fixtures: a stub that answers an alias request with a versioned id, one that answers `429` with a
`retry-after`, one that redirects to another origin, and one whose probabilities do not sum to `1`.
Source:: Article analysis `first-level-thinker` of plan-marshall-documentation.

[#PM-WATCH-CLIENT-16]
=== PM-WATCH-CLIENT-16: A worker's isolation covers the operator's own instruction files and skills

Anchor:: link:../specification/client-profiles/01-profile-schema.adoc#user-level-files[Client Profiles § Nothing of the Operator's Own],
link:../specification/client-profiles/01-profile-schema.adoc#profile-verification[§ Profile Verification],
link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2]
Hazard:: A harness reads user-level instruction files and skills from several places (its own home directory, a shared
`~/.agents/skills/`, another harness's skill directory it also supports), and some of these lookups use the home
directory even when the launch redirects the harness's data home. A settings switch that turns off user settings may
leave the user's instruction file and skills loaded. A worker then carries the operator's personal skills and
instructions: its behaviour and start context differ per machine, and a qualification graded on one machine does not
hold on another. A decoy placed only in the redirected data home passes the stage while the real locations still load.
Guard:: The isolation stage places its decoy user instruction file and decoy user skill in every user-level location
the harness documents or is observed to read, at the real home directory, not only below the data home of the launch,
and fails `extension_isolation` when the worker follows the instruction or knows the skill. Matched control: the same
worker knows the project's instruction file and skill. Fixtures: a harness stub that reads skills from the home
directory whatever its data-home variable says (the stage fails), and one that reads them only below the data home
(the stage passes).
Source:: Article analysis `claude-code-killer-six-months-goose` of plan-marshall-documentation (goose resolves its global
skill directories from the home directory, not from its data-home root).
