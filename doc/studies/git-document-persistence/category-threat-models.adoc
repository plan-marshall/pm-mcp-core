Threat model reports are a second category of information on the same engine. Recipes for threat modelling guide
the filling in, by people or assisted by a model; the result is a structured report that is maintained over the life
of the application.

No existing system known to this study maintains threat models across many applications, evaluates them and
detects that they are outdated, without additional operation. That gap is the place of this approach.

== Where a Threat Model Lives

A threat model describes one application and has to change with its architecture. That raises the question of
place:

* *A: in the application's repository* (`threat-model/` beside the code), recommended as the source of truth. It is
  versioned with the code and reviewed in pull requests; a release has its threat model. Outdated models become
  detectable: the architecture changed since the last commit of the threat model (new interfaces, dependencies,
  infrastructure files), so a review is due. This works through Git diffs, and only when model and code share the
  repository. The application reads many repositories, which the repository layer does anyway, and writes through
  pull requests in the user's name (Token Sheriff), because the `main` of the applications is protected.
* *B: a central repository `threat-models`*, like link:category-samm.adoc[SAMM]. Simpler where teams allow no writes
  into their repositories or the applications are not in Git; outdated models are then detected only through references
  to the applications' repositories.

Both are supported by configuration over the same repository layer.

== What the Application Contributes

Not a diagram editor; Threat Dragon has one. The value lies in the life cycle:

. *Recipes* guide the filling in; the result is a structured report in an open format.
. *Format*: OTM or the JSON of Threat Dragon instead of an own schema, so teams can go on editing the diagram in
  Threat Dragon and the application reads the same file.
. *Maintenance*: detection of outdated models, due dates, review by pull request, approval trailers.
. *Evaluation across applications*: open threats per application, untreated risks, age of the models.
. *Links*: threat modelling is a stream of the SAMM practice _Threat Assessment_ (business function _Design_), so
  maintained threat models are direct evidence for that maturity level in a SAMM assessment; accepted or untreated
  threats become entries of the ISMS risk register (`isms-register:risk/…`), countermeasures become issues.

== What to Observe

* *Confidentiality*: threat models describe attack paths. In the application's repository everyone with read access
  to the code sees them; internally that is mostly intended, for public repositories it is excluded, and variant B
  with a restricted repository applies.
* *Personal data*: hardly any, apart from owners; roles instead of names, as elsewhere.
* *Diagrams* are stored as data (OTM or JSON); images are generated, so diffs stay readable.
