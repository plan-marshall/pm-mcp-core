== Existing Solutions

No finished Java library provides this shape: drafts per user, merge on save, local or remote by configuration,
the same API for both. There are building blocks and reference designs:

[cols="1,2,1"]
|===
|Candidate |What it is |Use

|JGit
|Git in pure Java. Builds commits without a working tree (`ObjectInserter`, in-core `DirCache`), merges in core,
updates references atomically; pluggable object storage (DFS, `InMemoryRepository`).
|Foundation

|Gerrit NoteDb
|Gerrit keeps all review metadata in Git references and writes them with atomic multi-reference `BatchRefUpdate`.
|Architectural reference, not a library

|CrafterCMS
|A Java CMS on Git with two repositories per project: _Sandbox_ for drafts, _Published_ for released content,
optionally with a remote upstream.
|Functional reference, but a whole product

|Spring Cloud Config _(unverified)_
|Reads configuration from Git through JGit.
|Read-only, unsuitable

|Dolt, Irmin, Gollum, Decap CMS
|Git-like databases or Git-based content tools outside Java.
|Comparison only
|===

The pattern is proven (Gerrit, CrafterCMS); a reusable persistence module for it does not exist.

== Decision on a Library

Building the Git-based interaction as a library of its own is recommended. The application logic of SAMM, of the
threat models and of the ISMS is domain logic; the Git layer underneath is generic and is needed identically by all
of them. Separating it keeps the
domains free of JGit, makes the layer testable on its own against an in-memory or local repository, and lets
further domains reuse it.

=== Scope (`git-entity-store`, working title)

* *Repositories*: local or remote mode by configuration; bare clone as disposable cache; a registry of several
  repositories (confidentiality and retention classes) with stable aliases.
* *Writing*: in-core commits (blob, tree, commit) without working trees; compare-and-swap reference updates with
  retry; in-core merge; deterministic file content through a codec interface.
* *Drafts and saving*: draft references per user and entity; intermediate save; save as merge, compare-and-swap,
  fetch, push, retry on rejection; conflict results per path; expiry and garbage collection of drafts.
* *Identity*: author and committer per save; a credentials strategy per push (technical user or user token); commit
  trailers for approvals.
* *Reading*: snapshots of a reference or a commit (reporting dates), change history per path, diff of two states,
  an index interface the domain fills.
* *Post-commit processing*: an outbox over the new commits, idempotent by hash, with its progress kept in a
  reference; the hook for timestamps, mirror and index.
* *Notes*: reading and writing `git notes` for timestamps and other annotations.
* *Results instead of exceptions* for the expected outcomes (saved, conflict, rejected, credentials expired).

=== Not in Scope

The UI, the domain schemas (SAMM model, threat model format, ISMS entities), the OAuth flows (Token Sheriff; the
library only consumes credentials),
the identity provider, the issue-tracker and ticket integrations, and the timestamp authority client (an optional
module of its own).

=== Parts of the Engine

* `foundation`: the generic JGit layer shared with `pm-provider-git` (`git-core`, `git-worktrees`; see below).
* `store`: drafts, saving, identity, index and outbox on top of the foundation.
* `forms`: schema-driven documents (schema, template, workflow, deadlines, links) on top of the store.
* `timestamp` (optional): RFC 3161 anchoring through the post-commit outbox.
* `crypto` (optional): the encrypted keyring (a DEK per data subject, the KEK from a key source behind an interface:
  configuration value, Vault or KMS), rotation of the KEK on erasure, the evidence of erasure as a commit.
* `signing` (optional): the commit signature of the application through an exchangeable key source (KMS, HSM, file),
  the trailer schema of the user's claims, the registration of WebAuthn keys, approval notes and the signature check
  for the application and CI (see link:identity-and-signing.adoc[Identity and Signing]).
* `directory` (optional): the directory of persons and the catalogs of roles, teams and services, the first-login
  form and the resolution of references (see link:directory-and-catalogs.adoc[Directory and Catalogs]).
* `testing`: fixtures for local and in-memory repositories and a local remote for push and fetch tests.

The categories (SAMM, threat models, incident reports, ISMS) are configuration of `forms` (schemas, templates,
workflows), not parts of the engine.

=== Packaging: a Core Repository with Modules

An earlier version of this study recommended one module to start, with the parts as packages, and named three
triggers to split: the shared foundation for `pm-provider-git`, optional dependencies that would become mandatory,
and a layering that one module does not enforce. The owner has since decided for the cut those triggers lead to:
a core repository `git-foundation` with the extended JGit functionality and its helper classes, and the aspects as
modules of their own beside it.

* `git-core`, `git-worktrees` and `git-testing` hold the JGit level, taken over from `pm-provider-git`.
* `git-store`, `git-forms`, `git-crypto`, `git-signing`, `git-timestamp` and `git-directory` hold the aspects of the
  document store.
* Each module is an artifact of its own, released together with the others; a consumer of `git-core` pulls none of
  the third-party dependencies of the optional modules, and the module boundaries enforce the layering.
* The application with its categories and its UI lives outside the core repository; the categories are
  configuration of `git-forms`.

The cut, the inventory of `pm-provider-git` it rests on and the changes in `pm-mcp-core` are described in
link:extraction-from-pm-mcp-core.adoc[Extraction from `pm-mcp-core`].

=== Relation to `pm-mcp-core`: a Shared Foundation

`pm-provider-git` and the document store stand on one shared foundation instead of each carrying its own copy. The
inventory shows that all of `pm-provider-git` is generic except the adapter to the corpus interface of `pm-core`
(`JGitSourceRepository`) and the digest format `git.worktree-sha` of the job runtime specification
(`WorktreeShaDigest`); both stay in `pm-provider-git`, together with the contract `GitOperations` as a facade.

Gains: the hardening and the transport exist once, so a security fix reaches both products; one test base runs
against real local remotes; `pm-provider-git` shrinks to facade, adapter and digest.

Constraints:

* *The foundation does not live in `pm-mcp-core`.* That repository is proprietary, publishes only to the
  organisation's registry and deploys `SNAPSHOT` versions that are never released; another project must not hang on
  that life cycle. The foundation lives in a repository of its own and is released with real versions.
* *Two life cycles are coupled.* PM-MCP is pre-1.0 and changes contracts without deprecation cycles; the foundation
  stays small and stable and carries no domain term of either side.
* *Formal steps in `pm-mcp-core`*: dependency decision, Module Structure Specification, enforcer rules, ADRs and the
  native build of `pm-mcpd`; listed in link:extraction-from-pm-mcp-core.adoc[Extraction from `pm-mcp-core`].
* *Licence.* If the foundation is published as open source, the code taken over from `pm-provider-git` has to be
  released for it. The other direction is unproblematic: a proprietary product may depend on an open-source library.

== Risks and Limits

* Many concurrent writers on one branch cause retries; for assessments maintained by few people over days this is
  uncritical.
* Several application instances: safe through compare-and-swap on push, but each index is only as fresh as its last
  fetch; use webhooks.
* A conflict in the same file is resolved per question in the YAML structure; a real conflict goes to the UI.
* Removing data from the history stays expensive; hence the rules of link:data-protection.adoc[Data Protection].
* Using the Git server's content API instead of a clone would be simpler but binds to one vendor and runs into rate
  limits; a JGit clone works with any Git server.
* JGit's LFS support is limited _(unverified)_; evidence stays a link.
