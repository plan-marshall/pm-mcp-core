= Study: Git as the Persistence of Versioned Documents (OWASP SAMM, ISMS)
:nofooter:
:toc: macro
:toclevels: 2

A preliminary study for a project outside PM-MCP. It records the conclusions of an exploratory discussion held on
2026-11-12: whether a server-side Git repository can serve as the persistence of an application in which users
maintain versioned documents, first OWASP SAMM assessments and, as an extension, an ISMS. Nothing in this document
binds `pm-mcp-core`; the repository only hosts it. Statements marked _(unverified)_ come from general knowledge and
were not checked against a current source; they need verification before a decision rests on them.

toc::[]

== Question and Assumptions

The application is always server-based: one server manages the Git repositories; no client holds a clone. Git is
the persistence only, not a user-facing tool. The organisations that use the application are development
organisations that already operate a maintained Git server (GitHub, GitLab, Gitea, Bitbucket) with backups. Every
additional database brings operating effort; reusing the existing Git server avoids it.

Two scenarios are in scope:

. *OWASP SAMM*: users maintain SAMM assessments per scope (organisation, team, application) and date; the
  assessments are versioned, released and compared over time. This is the core.
. *ISMS*: an information security management system on the same foundation. This is an extension.

The questions were: does a finished Java module for Git-based persistence exist, is building one a good idea, how
do drafts, multiple users, local and remote operation and user identities work, what does the GDPR demand, which
gaps remain and how they are closed, and how the approach compares with an established ISMS product (verinice).

== Existing Solutions

No finished Java library provides this shape: drafts per user, merge on save, local or remote by configuration,
the same API for both. There are building blocks and reference designs:

[cols="1,2,1"]
|===
|Candidate |What it is |Use

|JGit
|Git in pure Java. Builds commits without a working tree (`ObjectInserter`, in-core `DirCache`), merges in core,
updates references atomically; pluggable object storage (DFS, `InMemoryRepository`).
|Foundation

|Gerrit NoteDb
|Gerrit keeps all review metadata in Git references and writes them with atomic multi-reference `BatchRefUpdate`.
|Architectural reference, not a library

|CrafterCMS
|A Java CMS on Git with two repositories per project: _Sandbox_ for drafts, _Published_ for released content,
optionally with a remote upstream.
|Functional reference, but a whole product

|Spring Cloud Config _(unverified)_
|Reads configuration from Git through JGit.
|Read-only, unsuitable

|Dolt, Irmin, Gollum, Decap CMS
|Git-like databases or Git-based content tools outside Java.
|Comparison only
|===

The pattern is proven (Gerrit, CrafterCMS); a reusable persistence module for it does not exist.

== Why Git Fits SAMM

An OWASP SAMM assessment is a self-contained document at a date: answers per question of the model, comments,
evidence, and scores computed from them. Its value is the comparison over time. It is edited as a draft, then
released and frozen as audit evidence. It refers to the SAMM model version it was taken with; since version 2 the
model itself is published as YAML files with semantic versioning. The data volume is small, and the only personal
data are the assessors, whom the Git server already knows.

Git therefore fits: the model is already YAML in Git, an assessment as YAML diffs well, release maps to a merge and
a tag, and the history, rights, reviews and backups come from the existing infrastructure.

== Architecture

----
 UI ──► application server ──► repository layer (JGit, in process)
                                 │
                                 ├─ local bare clone (disposable cache in remote mode)
                                 │     └─ in-memory index (built from the references)
                                 │
                                 └─ sync ──► remote Git server   ← source of truth and backup
----

=== Two Modes, One API

* *Local*: no remote; the bare repository on the server's disk is the source of truth. The operator backs up the
  directory. JGit creates it; no `git` installation is needed.
* *Remote*: the remote repository is the source of truth; the local bare clone is a cache that can be deleted and
  re-cloned. Saving adds a fetch and a push.

Both modes run the same code; the configuration says `remote: none` or names the remote. A remote can be added later
with one push.

=== No Working Trees

A Git branch is no working area; it is a reference, a pointer to a commit. Any number of them can exist for any
number of users at the same time. A working tree is a checked-out state on disk, and only one exists per branch.
`pm-mcp-core` needs linked working trees because agents and build tools work on files on disk (`LinkedWorktrees` of
`pm-provider-git`; JGit only reads linked working trees, since 7.0). The application here holds the content in
memory anyway, so it writes blobs, trees and commits directly into the object database and moves the reference.

[source,java]
----
// Set answers/governance-strategy.yaml on the assessment branch to `content` (sketch, untested)
Ref ref = repo.exactRef("refs/heads/assessments/" + id);
try (ObjectInserter ins = repo.newObjectInserter();
     ObjectReader reader = repo.newObjectReader();
     RevWalk walk = new RevWalk(reader)) {
    RevCommit parent = walk.parseCommit(ref.getObjectId());
    DirCache index = DirCache.read(reader, parent.getTree());     // in-core index, no files
    ObjectId blob = ins.insert(Constants.OBJ_BLOB, content);
    DirCacheEditor editor = index.editor();
    editor.add(new DirCacheEditor.PathEdit(path) {
        @Override public void apply(DirCacheEntry e) {
            e.setFileMode(FileMode.REGULAR_FILE);
            e.setObjectId(blob);
        }
    });
    editor.finish();
    CommitBuilder cb = new CommitBuilder();
    cb.setTreeId(index.writeTree(ins));
    cb.setParentId(parent);
    cb.setAuthor(userIdent);          // the logged-in user
    cb.setCommitter(serviceIdent);    // the technical user
    cb.setMessage("Update " + path);
    ObjectId commit = ins.insert(cb);
    ins.flush();
    RefUpdate ru = repo.updateRef(ref.getName());
    ru.setExpectedOldObjectId(parent);   // compare-and-swap
    ru.setNewObjectId(commit);
    RefUpdate.Result result = ru.update(walk);   // LOCK_FAILURE: someone was faster, retry
}
----

The last step carries multi-user operation: *compare-and-swap*. The reference moves only if it still points to the
commit the change was built on. Of two concurrent writers one wins; the other reloads and applies its operation
("set file X to content Y") again on the new state, a rebase of one operation without a textual merge.

=== Two Levels of Saving

[cols="1,2,1,1"]
|===
|Level |What happens |Where it lives |Secured

|Intermediate save (automatic)
|Commit on `refs/drafts/<user>/<assessment>`
|The server's repository only
|No

|Save (explicit)
|Merge the draft in core into the assessment branch (optionally squashed), compare-and-swap; in remote mode fetch,
merge onto the remote state, push, retry on rejection; delete the draft reference
|Locally and remotely
|Yes, in remote mode
|===

Draft references are never pushed; the push refspec carries `refs/heads/*` only. A user who logs in again finds the
drafts under `refs/drafts/<user>/` and continues. Conditions:

* The repository directory needs persistent storage (a persistent volume in a container platform); without it a
  restart loses every unsaved draft, not only a crash.
* With several application instances a draft lives on the instance that wrote it: one instance, sticky sessions or
  a shared volume (JGit's lock files keep the compare-and-swap safe).
* Abandoned drafts expire after a configured period; a garbage collection removes their objects.
* On a real conflict (the same question changed in parallel) nothing is pushed; the UI shows the conflict and the
  draft is kept.

=== Branch Granularity

* *A: one branch per assessment, shared by all editors* (recommended for SAMM, which is mostly filled in jointly in
  workshops). Every save is a small commit with compare-and-swap; the UI remembers the blob id it loaded (like an
  ETag) to detect a concurrent change of the same file.
* *B: one draft reference per user and assessment, merged on save.* Drafts stay private until submitted.

Release is a merge of the assessment branch into `main` and a tag `assessment/<id>`; protected branches and tags of
the Git server make it immutable. Optionally release opens a pull or merge request whose review is the four-eyes
approval.

=== Repository Layout for SAMM

----
samm.yaml                              # pinned SAMM model version(s)
scopes/<scope-id>/scope.yaml           # team / application / organisation
scopes/<scope-id>/assessments/<assessment-id>/
    assessment.yaml                    # header: date, model version, status, assessors
    answers/<practice-id>.yaml         # one file per practice: parallel editing without conflicts
    evidence.yaml                      # evidence as links, not as files
scopes/<scope-id>/targets.yaml         # target maturity, roadmap
----

* One file per practice keeps concurrent edits of different practices conflict-free.
* Deterministic serialisation (fixed key order, stable formatting) makes diffs show real changes only.
* Evidence as links (wiki, ticket, pipeline) avoids large files and Git LFS.

=== Reading and Queries

At start and after every fetch the application reads `main` and the open assessment branches into an in-memory
index; even hundreds of assessments with about ninety answers each are a few megabytes. Dashboards, trends and heat
maps are computed from it. A periodic fetch or a webhook of the Git server refreshes it. A database is not needed;
if one is ever wanted, it is a disposable cache (embedded SQLite or H2).

== Identity: Technical User or the Logged-in User

[cols="1,3"]
|===
|Level |Meaning

|a) Technical user pushes, the author is the user
|The commit carries `author = alice`, `committer = samm-bot`. The author is metadata the Git server does not check;
the application checks the rights. The simplest start.

|b) Push with the user's token
|JGit takes the token per push (`UsernamePasswordCredentialsProvider`). The token comes from an OAuth login against
the Git server (GitHub App or OAuth App, GitLab OAuth), which can be the application's own login; with another
identity provider the user authorises the Git server once in addition. The server stores tokens encrypted and
refreshes them (GitHub App user tokens: eight hours plus refresh token _(unverified)_). Gain: the Git server
enforces the rights and its audit log names the real pusher. A protected `main` usually rejects a user's direct
push; the user then pushes the assessment branch and release runs as a pull or merge request.

|c) Verified commits as the real user
|Not feasible server-side through a JGit push, because it would need the user's signing key. The bot can sign
(JGit `org.eclipse.jgit.gpg.bc`), or commits are created through the Git server's API, which signs them itself, at
the price of binding to one vendor.
|===

Start with a) and build the identity as an exchangeable strategy (credentials per save), so b) follows without a
rebuild. One push per save keeps every push to the commits of exactly one user.

[cols="1,1,1,1"]
|===
| |Local |Remote, bot |Remote, real user

|Drafts survive logout |yes |yes |yes
|Drafts survive restart |with persistent volume |with persistent volume |with persistent volume
|Secured after save |operator's backup |remote |remote
|Rights checked by |application |application |Git server and application
|Audit "who" |author |author |author and pusher
|===

== GDPR

Declaring the persistence "not deletable" does not exempt it from the GDPR. As soon as personal data lie in the
repository, the right to erasure (Art. 17) applies, and Art. 25 (privacy by design) demands a system that can serve
the data subjects' rights. Exceptions exist (Art. 17(3)), above all statutory retention duties, but only for the
data they cover and only for their period; afterwards storage limitation (Art. 5(1)(e)) requires deletion. During
retention, restriction of processing (Art. 18) replaces erasure.

Commits themselves are personal data when the author is a named person. The design therefore keeps personal data
out of the history:

* *Pseudonymous commits*: the author is an opaque user id or the Git server's user name; the mapping to the person
  lives outside Git and is deletable.
* *Roles instead of persons* in documents (`owner: role:it-security-lead`); the identity provider resolves the role.
* *Crypto-shredding* for personal fields that must be in a document: encrypted with a key per data subject held
  outside Git; destroying the key erases the data in effect. Whether this counts as erasure is not settled; agree it
  with the data protection officer.
* *No personal interview notes* in free-text fields; the UI says so.
* *Repositories per retention period* (see below): after the period the whole repository is deleted; no history is
  rewritten.

This is a technical assessment, not legal advice.

== Repositories per Confidentiality and Retention Class

Git grants rights per repository only. Cutting the data into repositories by confidentiality turns that into an
advantage; cutting them by retention period solves deletion:

----
isms-core            → policies, scope, statement of applicability   (widely readable)
isms-register        → assets, risks, controls                       (restricted)
isms-incidents-2026  → incidents of one year                         (strongly restricted, retention period)
samm-assessments     → SAMM                                           (development and security)
----

With pushes in the user's name (identity level b) the Git server enforces the rights itself. References across
repositories use stable ids (`isms-register:risk/R-042`, `samm:assessment/team-a-2026-q4`); the application checks
on save that the target exists, and a CI pipeline on the pull request can validate schemas (JSON Schema) and
references with the existing infrastructure.

== The ISMS on Git

ISO 27001 clause 7.5 asks for the control of documented information: versioning, review and approval, availability,
protection against change, traceable changes. Git maps onto it directly:

[cols="1,1"]
|===
|Clause 7.5 |Git

|Versioning, change history |commits, diff
|Review and approval |pull or merge request with review, protected `main`
|Protection against unauthorised change |repository rights, protected branches and tags
|Availability and retention |the Git server and its backup
|===

The ISMS artefacts sort into three groups:

. *Documents, very well suited*: policies, scope, risk methodology, statement of applicability, internal audit and
  management review reports. Rarely changed, approval-centred, diffable.
. *Registers, well suited*, with the SAMM pattern (one file per entry, in-memory index, compare-and-swap): assets,
  risks, controls, suppliers, nonconformities. Even a mid-sized ISMS holds a few thousand entries.
. *Operational data, referenced instead of stored*: tasks and deadlines (issue tracker of the Git server or Jira),
  incidents (ticket system, or a repository with a retention period), training records per employee (learning
  platform or HR system), persons and owners (identity provider).

Additional mechanisms:

* *Portable approvals*: approvals of a pull request live in the Git server's database. On merge the application
  writes them as commit trailers (`Approved-by: role:ciso (u-7f3a)`, `Review: <url>`), so the evidence survives a
  change of Git server.
* *Running numbers* (R-042) under concurrent creation: a ULID as file name; the readable number is assigned on save
  through a counter file in the same commit, made unique by the compare-and-swap.
* *Reporting dates*: "statement of applicability and risk register as of the audit on 1 March" is a tag or the
  commit of that date; the index is built from it.
* *Deadlines and reminders* are computed from the index; notifications are runtime state of the application, not
  persistence.

The bridge to SAMM: a released assessment becomes evidence for the secure-development controls (Annex A 8.25 ff.)
by a reference to its tag; target maturity levels become measures in the issue tracker. Both domains run on one
engine.

Limits: real-time incident handling with escalation is no case for Git (connect a ticket system); queries across
many repositories need an instance that may read all of them, or queries run with the user's rights and show only
what the user may see; Git replaces no document management system an auditor knows as such, so the process
description of the control of documented information has to be written once.

== Closing the Remaining Gaps without a Database

Every store beside Git falls into one of three classes:

. *Derived*: rebuildable from Git at any time (index, search, dashboards); local, volatile, no backup.
. *Complementary*: data that must not be in Git (mutable, deletable, personal); they belong in a system the
  organisation already operates, not in a new store.
. *Assuring*: an independent append-only proof about Git ("these commits existed at this time"); it must lie
  outside the control of the Git administrator.

[cols="2,3,1"]
|===
|Gap |Solution |New infrastructure

|History rewritten (force push by an administrator)
|Hash journal: every new state of `main` anchored externally with a timestamp
|no or minimal

|Approvals live in the Git server's database
|Commit trailers on merge
|no

|Personal, deletable data
|Identity provider, ticket system, or encrypted in Git with keys in Vault or a KMS
|only without Vault or KMS

|Read-access log (who read a confidential risk, logins)
|The organisation's existing logging or SIEM (ISO 27001 A.8.15)
|no

|Unsecured drafts
|Accepted risk, or drafts pushed as restricted private references
|no

|Search, evaluations, reporting-date views
|In-memory index, optionally SQLite or Lucene as a cache
|no, disposable
|===

=== The External Anchor

A copy of all commits in a second store adds nothing; Git already is an append-only, hash-chained store. Value comes
from an independent proof, the external anchor of the hash chain:

. *Mirror* to a second Git server under another responsibility, pushed after every save; a force push on the main
  server shows at the mirror at once.
. *RFC 3161 timestamps*: the hash of every new state of `main` is signed by a timestamp authority and stored as
  `git notes` (`refs/notes/timestamps`) in the repository itself; the proof travels with the repository. Qualified
  timestamps under eIDAS carry legal weight. *Recommended*, optionally together with 1.
. *WORM storage* (object storage with object lock), only where the organisation already has it.
. *Public transparency logs* (Sigstore/Rekor): elegant but public; not recommended for internal ISMS data.

=== Consistency between Git and the Other Systems

* Git first; everything else afterwards and derived from Git: after every successful push the application walks the
  new commits and writes journal, timestamps and index from them (an outbox whose outbox is Git).
* Idempotent by commit hash; after a failure the application resumes from the last processed hash, remembered in a
  reference (`refs/notes` or `refs/meta`), again in Git.
* Complementary data by reference only: Git holds `incident: TICKET-4711`, never Git content in the ticket system.

----
Git (truth: documents, registers, assessments, approval trailers, timestamps as notes)
 ├─ derived:        index, search (volatile, rebuildable from Git)
 ├─ complementary:  identity provider (persons), issue and ticket system (operations),
 │                  Vault/KMS (keys), SIEM (read-access log)
 └─ assuring:       RFC 3161 timestamps (+ optional mirror)
----

== Comparison with verinice

verinice (SerNet) is an established ISMS product. The classic product is a desktop client (Eclipse RCP) with the
server verinice.PRO and a database, strong in BSI IT-Grundschutz, ISO 27001 and data protection. verinice.veo is
the new web application: microservices on PostgreSQL, Keycloak and RabbitMQ, orchestrated by Kubernetes, offered as
SaaS or on premise.

[cols="1,2,2"]
|===
|Criterion |Git approach |verinice / verinice.veo

|Domain content
|Built by the project. The Grundschutz compendium is free; the texts of ISO 27001 are copyrighted and may not be
shipped, only own wording and numbers
|Catalogues, methodology and modelling logic included, matured over years

|Reports (statement of applicability, Grundschutz check, risk report)
|Built by the project
|Available, widely used in audits

|Operation
|Application and existing Git server; backup, rights and reviews exist
|veo: Kubernetes, PostgreSQL, Keycloak, RabbitMQ, or SaaS with the data at the vendor

|Versioning, diff, reporting dates
|Native and complete
|Rather status and release attributes on objects than a full history with diff _(unverified)_

|Approval, four eyes
|Pull request review, protected branches, commit trailers
|Workflow functions of the application (scope to verify)

|Tamper evidence
|Hash chain and RFC 3161 timestamps, verifiable externally
|Depends on the database and the administrators' rights

|Rights
|Coarse per repository, enforced by the Git server; cut by confidentiality
|Fine-grained per object and role in the application

|Audience
|Development organisations working with pull requests; editing also directly in the repository (YAML and CI checks)
|Security officers and business units without Git

|Data sovereignty
|Plain YAML or Markdown, readable without any software
|Database, export through exchange formats or REST API

|Integration
|Everything is files: CI pipelines, scripts, SAMM, issue tracker

|Acceptance by auditors

|Introduction in weeks
|===

Positioning: do not compete with verinice as a complete ISMS; complement it.

. *Core*: the SAMM tool on Git; no established competitor follows this approach.
. *Extension*: a lean "ISMS as code" for development organisations: policies, statement-of-applicability extracts
  for secure development, risks from SAMM gaps.
. *Bridge*: where an organisation already runs verinice, the tool delivers released SAMM assessments as evidence
  through the REST API of veo, a supplier to the main ISMS rather than a competitor.

== Decision on a Library

Building the Git-based interaction as a library of its own is recommended. The application logic of SAMM and of the
ISMS is domain logic; the Git layer underneath is generic and is needed identically by both. Separating it keeps the
domains free of JGit, makes the layer testable on its own against an in-memory or local repository, and lets
further domains reuse it.

=== Scope (`git-entity-store`, working title)

* *Repositories*: local or remote mode by configuration; bare clone as disposable cache; a registry of several
  repositories (confidentiality and retention classes) with stable aliases.
* *Writing*: in-core commits (blob, tree, commit) without working trees; compare-and-swap reference updates with
  retry; in-core merge; deterministic file content through a codec interface.
* *Drafts and saving*: draft references per user and entity; intermediate save; save as merge, compare-and-swap,
  fetch, push, retry on rejection; conflict results per path; expiry and garbage collection of drafts.
* *Identity*: author and committer per save; a credentials strategy per push (technical user or user token); commit
  trailers for approvals.
* *Reading*: snapshots of a reference or a commit (reporting dates), change history per path, diff of two states,
  an index interface the domain fills.
* *Post-commit processing*: an outbox over the new commits, idempotent by hash, with its progress kept in a
  reference; the hook for timestamps, mirror and index.
* *Notes*: reading and writing `git notes` for timestamps and other annotations.
* *Results instead of exceptions* for the expected outcomes (saved, conflict, rejected, credentials expired).

=== Not in Scope

The UI, the domain schemas (SAMM model, ISMS entities), the OAuth flows (the library only consumes credentials),
the identity provider, the issue-tracker and ticket integrations, and the timestamp authority client (an optional
module of its own).

=== Possible Module Cut

* `foundation`: the generic JGit layer shared with `pm-provider-git` (see below).
* `document-store`: drafts, saving, identity, index and outbox on top of the foundation.
* `timestamp` (optional): RFC 3161 anchoring through the post-commit outbox.
* `testing`: fixtures for local and in-memory repositories and a local remote for push and fetch tests.

=== Relation to `pm-mcp-core`: a Shared Foundation

`pm-provider-git` as it stands is no dependency for the new library: its contract is cut for PM-MCP (cache
repositories, fetch of single commits, linked working trees). About half of it is generic, though, and the
document store needs exactly that half. Both therefore stand on one shared foundation instead of each carrying its
own copy:

[cols="1,1"]
|===
|Generic, needed by the document store as well |Specific to PM-MCP

|Hardened opening of repositories (`RefusingFS`: no hooks, no process starts)
|Linked working trees on disk (`LinkedWorktrees`, `worktreeAdd`, `worktreeList`, `worktreeRemove`)

|The policy of permitted remotes (`RemotePolicy`) and its check before fetch and push
|`WorktreeShaDigest`

|Fetch and push with credentials, mapped to result types (`GitResult`, `GitOutcome`)
|The contract `GitOperations` with inputs cut for PM-MCP

|Opening a bare cache, reading a file at a commit, the log
|`fetchCommit` for the corpus cache, `JGitSourceRepository`

|Resolution of references and commit ids (`GitIdentity`)
|
|===

The document store adds what PM-MCP has not needed so far: in-core commits, compare-and-swap reference updates,
in-core merge, draft references and `git notes`.

----
git-foundation                         (repository of its own, own releases)
  ├─ hardened repository factory (RefusingFS), RemotePolicy
  ├─ transport: fetch and push with a credentials strategy → result types
  ├─ reading: blob at commit, log, reference resolution
  └─ writing: in-core commits, compare-and-swap, in-core merge, notes
        ▲                                   ▲
pm-provider-git                      git-document-store
  (working trees, PM-MCP contract,     (drafts, save and push, identity,
   corpus cache)                        index, outbox, timestamps)
----

Gains: the hardening and the transport exist once, so a security fix reaches both products; one test base runs
against real local remotes; `pm-provider-git` shrinks to working trees and the PM-MCP contract.

Constraints:

* *The foundation does not live in `pm-mcp-core`.* That repository is proprietary, publishes only to the
  organisation's registry and deploys `SNAPSHOT` versions that are never released; another project must not hang on
  that life cycle. The foundation gets a repository of its own with real versions.
* *Two life cycles are coupled.* PM-MCP is pre-1.0 and changes contracts without deprecation cycles; the foundation
  stays small and stable and carries no domain term of either side.
* *Formal steps in `pm-mcp-core`.* The new dependency needs the owner's explicit decision; the allowed dependencies
  of the modules are stated in the Module Structure Specification in the documentation repository and change there;
  the switch is a work package of its own with an ADR; the native-image metadata of JGit travels with the module
  that uses JGit and moves along, verified by the native build of `pm-mcpd`.
* *Licence.* If the foundation is published as open source, the code taken over from `pm-provider-git` has to be
  released for it. The other direction is unproblematic: a proprietary product may depend on an open-source library.

Order:

. Build `git-foundation` and `git-document-store` in a repository of their own. Take over the generic code of
  `pm-provider-git` and cut it so that `pm-provider-git` can later use it one to one.
. Once the foundation is stable and a first version is released, a work package in `pm-mcp-core` switches
  `pm-provider-git` onto it, with the dependency decision, the change of the specification and an ADR.

The new project never depends on PM-MCP, and PM-MCP gets the shared foundation once it has proven itself. The
extraction also fits the wish to move parts of `pm-mcp-core` into repositories of their own; it reduces the size of
the repository only slightly, though (`pm-provider-git` holds about 2,000 of more than 150,000 lines of production
Java), because the weight lies in `pm-core`, `pm-runtime` and `pm-workflow`.

== Risks and Limits

* Many concurrent writers on one branch cause retries; for assessments maintained by few people over days this is
  uncritical.
* Several application instances: safe through compare-and-swap on push, but each index is only as fresh as its last
  fetch; use webhooks.
* A conflict in the same file is resolved per question in the YAML structure; a real conflict goes to the UI.
* Removing data from the history stays expensive; hence the GDPR rules above.
* Using the Git server's content API instead of a clone would be simpler but binds to one vendor and runs into rate
  limits; a JGit clone works with any Git server.
* JGit's LFS support is limited _(unverified)_; evidence stays a link.

== Open Points and Next Steps

. Prototype of the store: concurrent saves against one branch, measuring conflicts and retries.
. Verify the JGit API used in the sketch (`DirCache.read`, `DirCacheEditor`, in-core merge, `RefUpdate` results) and
  the `git notes` support (`NoteMap`) against the JGit version in use.
. Push and fetch with token credentials against GitHub, GitLab and Gitea; token lifetimes and refresh of the hosts
  _(unverified)_.
. Choose a timestamp authority (qualified under eIDAS or internal).
. Agree the GDPR rules (pseudonymisation, crypto-shredding, retention classes) with the data protection officer.
. Verify the verinice statements (versioning, approval, licence of veo, catalogue coverage) with a demo instance.
. Draft the library API and the SAMM repository schema.
