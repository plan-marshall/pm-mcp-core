== Task Completion & Return Evaluation
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-5[PM-WF-5: Model Work as Role Tasks & Single-Level Leaf Constraint], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-14[PM-WF-14: Task Envelopes, Model Slots & Usage per Task], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-2[PM-WORK-2: Task Protocol]_

The server observes every worker's process, exit, output, and usage itself, and evaluates every task only from persisted records. Neither the worker's exit status nor its final output decides what a task produced.

[#model-job-lifecycle]
=== Worker Job Record, Status & Fate

A worker has a `job_id` of the kind `llm` (link:../identifiers/01-general-rules-and-registry.adoc#id-job-id[Identifier Registry, `job_id`]), which is also its `generation_id`, and a job record like every job (link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]), which adds the launch contract (xref:04-worker-launch.adoc#launch-contract[Launch Contract]), the SHA-256 of its job token, `connected_at`, the worker state (xref:02-task-protocol.adoc[Task Protocol]), the skill delivery record (xref:04-worker-launch.adoc#skill-delivery[Skill Delivery Record]), and the `queue_task_id` values it served. The job record carries no usage: usage lives in the metrics rows of <<job-result-schema>>.

* *Status*: `queued` (waiting for a model slot, xref:04-worker-launch.adoc#model-slots[Model Slots & One Writer per Plan]) -> `running` (spawned) -> `ended`. The worker's budget starts at spawn.
* *Connection*: `connected_at` is the instant of the first request the daemon accepted with the worker's token. It is a fact, never a state: a worker that never connected ends like any other job; one that exits before its first call is a start failure (xref:03-supervision-and-recycling.adoc[Supervision & Recycling]).
* *Fate*: `succeeded`, `failed`, `timed_out`, `killed`, `cancelled`, `indeterminate`, or `refused`, derived by the job runtime from the evidence it observed (link:../job-runtime/01-pipeline-and-subprocesses.adoc#outcome-derivation[Job Runtime Specification, Outcome Derivation]); the fate is never taken from the worker's own report. A worker the supervisor ends is `killed`. A record left `running` by a previous runtime instance is settled `killed` in the per-project recovery.
* *Budget*: A `timed_out` worker is `no_verdict` in every roll-up (link:../timeouts/01-job-budgets-and-waits.adoc#no-verdict-rule[Timeouts & Budgets Specification, Timed-Out Outcomes Are No-Verdict]).
* *Token revocation*: The fate revokes the job token; every later request with it is refused `job_ended`.

[#job-completion]
=== Task Completion & the `job_incomplete` Condition
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-32[PM-WATCH-DISP-32], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-42[PM-WATCH-DISP-42]_

A task ends in one of its closed outcomes `submitted`, `asked`, `infeasible`, or `lost` (xref:02-task-protocol.adoc[Task Protocol]). When a task ends, the engine evaluates its `job llm` state in the transaction that records the outcome (link:../workflow-dsl/02-units-jobs-decisions.adoc#model-job-states[Workflow DSL Specification, Model Job States]):

1. *Recorded*: When the task entity recorded its required submission (`submitted`), its question (`asked`), or its infeasibility with evidence (`infeasible`), the return-evaluation primitive of the entity kind decides the outcome (<<return-evaluation>>), whatever the worker's fate: a worker killed after its `submit` delivered its work.
2. *Incomplete*: Otherwise the attempt ended incomplete, and the server never synthesizes the missing submission. It logs an attribution defect in the audit log and raises the `job_incomplete` condition on the job state (link:../state-catalogue/01-conventions-generic-conditions.adoc#condition-job_incomplete[State Catalogue, Conditions]; the state and `call_stack` stay unchanged), which the server remedies itself: it offers the task again, with the observed partial progress in its facts (for example the completed and pending plan tasks of an envelope, the worktree's `worktree_sha`), within the task re-offer budget (link:../timeouts/01-job-budgets-and-waits.adoc#task-reoffer-budget[Timeouts & Budgets Specification, Task Re-Offer Budget]; xref:02-task-protocol.adoc#re-offer[Task Protocol, Re-Offer]); a replaced worker's task goes to its successor exactly once per attempt. Only when the budget is spent does the task close `lost` (`attempts_spent`), and the state takes its conservative fallback with the incomplete task recorded as the gap. On a fan-out state (`job llm … each …`) the condition is raised once, when the last task of the state has ended, and the offers cover only the unfinished entities.
3. *Closed without an attempt*: A task the model caller closes (`role_undefined`, `class_mismatch`, `role_unqualified`, `role_unavailable`) is never offered; it ends `lost` with that reason and the state takes its conservative fallback at once (xref:01-roles-and-configuration.adoc#conservative-fallback[Roles & Configuration, Conservative Fallback]).

[#return-evaluation]
=== Return Evaluation (Job State Outcomes)
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-27[PM-WATCH-DISP-27]_

The outcome transitions of a `job llm` state belong to the task's completion: when the task ends with its required records (<<job-completion>> item 1), the engine runs the *return-evaluation primitive* that the entity kind registers; its closed outcome set is checked by Rule 2 like every other primitive's (link:../workflow-dsl.adoc[Workflow DSL Specification]), and it reads only the persisted entity, plan task, question, and findings records, never the worker's fate beyond the item above and never its output. A loop-back is decided only by a remediation policy or triage.

[cols="2,3,4"]
|===
|Entity kind |Return-evaluation primitive and outcomes |Rule

|Envelope task (`envelope-M`, role `implement`)
|`execute.evaluate-envelope-return`: `question_pending` -> `execute.task-question`; `infeasible_pending` -> `execute.replan` (trigger `infeasible`); `chain_tail` -> `execute.chain-tail-commit`; `remediation_chain_tail` -> `execute.remediation-commit`; `continue` -> `execute.envelope-ready`; `all_complete` -> `execute.verify-sweep`
|Serial envelope tasks (xref:06-envelopes-questions-deadlines.adoc#envelope-early-end[Early End of an Envelope Task]). When several outcomes apply, the first in the order `question_pending`, `infeasible_pending`, `chain_tail`, `remediation_chain_tail`, `continue`, `all_complete` wins. The remaining plan tasks of an envelope task that ended early, the asking plan task included, form the next envelope task `envelope-(M+1)`; after `execute.task-question` closes the record it carries the answer in its facts.

|Q-Gate validation (`refine.qgate`, `outline.qgate`, `plan.qgate`, role `qgate`)
|The phase's Q-Gate verdict primitive: `clean` -> the phase exit; `blocking` -> `call remediation.qgate-findings`
|A `read_only` task that submits assessments and findings on its entity; the primitive runs the compiled mechanical checks of the phase and decides the verdict from the persisted findings alone (link:../phase-workflows/03-q-gate-and-execute.adoc[Phase Workflows Specification, Q-Gate Validation]).

|Single-submit entities (refine and outline authoring, the triage groups of a gather firing, architecture enrichment (kind `enrich-module`, entity `enrich-<module_id>`), the finalize reviews and `lessons-author`, epic `reground`, the epic `landing` entities)
|Declared by the job state's unit, for example `submitted` -> the next state, and for refine and outline authoring `ask` -> the phase's question state
|The entity runs the generic entity unit (<<entity-units>>); refine and outline authoring keep their open questions in the optional `decision` of their one `submit`, and the phase's question state serves the records it created.

|Multi-submit entities (epic `decompose`, `message`, and `completion`, the task revision, the pull-request body, `lessons-review`)
|Declared by the job state's unit: `submitted` -> the next state
|The entity runs the multi-submit entity unit `entity-multi.pmwf` (<<entity-units>>): the repeatable submits are each validated and persisted on their own, and the required submission is the closing submit (for example `submit:decompose`, `submit:message`, `submit:completion`, `submit:review`; every kind's closing submit: link:../state-catalogue/10-entity-units.adoc#state-entity-multi.active[State Catalogue, `entity-multi.active`]). A task that ended without it is `lost`; the next offer continues from what is persisted.

|Screener (`screen`, role `screener`)
|The verdict validation of xref:07-untrusted-text-screening.adoc#screener[Screener]: `clean` -> the step's next state; `suspicious` -> the step's withheld or acceptance route
|No entity and no connection; the structured `screen-verdict` output is the only evidence, fail-closed.
|===

[#entity-units]
==== Entity Units & the Entity Phase Value

Every task except a `zero_tool` worker's (the screener's, the judge's) works in a real entity state, which the task-protocol unit `worker-task` wraps (xref:02-task-protocol.adoc[Task Protocol]). Envelope tasks keep their own unit (`envelope.task.active`, `envelope.completed`); every other entity kind runs one of two generic entity units (`scope entity`). A kind that submits once runs `entity.pmwf`: `entity.active`, which offers the kind's `submit` link (and nothing that waits), and the terminal `entity.completed` (`submitted success`). A kind that submits several times (epic decomposition, message processing, and completion, task revision, pull-request body, lesson review) runs `entity-multi.pmwf`: its active state offers the kind's repeatable submits, each validated and persisted on its own while the entity stays active, and one closing submit that ends the entity (`submitted` -> its completed terminal; link:../state-catalogue/10-entity-units.adoc#state-catalogue-other[State Catalogue, Entity Units]). An entity unit declares no phase, like every unit; an entity state's phase is derived from the call stack (link:../workflow-dsl/01-grammar.adoc#state-phase[Workflow DSL, Phase of a State]), so an entity representation carries the phase of the job state that hosts it. No entity state waits on a question: a refine or outline entity carries its questions in its `submit`, and an envelope task's `ask:TASK-NNN` records the question and ends the entity (xref:06-envelopes-questions-deadlines.adoc#task-questions[Task Questions]).

[#job-result-schema]
=== Worker Result & Usage Parsing
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-3[PM-WATCH-DISP-3], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-40[PM-WATCH-DISP-40], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-43[PM-WATCH-DISP-43]_

*Result*: A fresh `writer` or `read_only` worker ends with the structured output `job-result`, validated by the server; it is display text and evidence, never the route and never a deliverable. A warm worker ends when the server answers its wait with `end` and has no final result.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://cuioss.de/plan-marshall-mcp/schemas/job-result-v1.json",
  "title": "JobResult",
  "type": "object",
  "required": ["status", "display_detail"],
  "additionalProperties": false,
  "properties": {
    "status": { "type": "string", "enum": ["success", "error"], "description": "The worker's own report; evidence only." },
    "display_detail": {
      "type": "string",
      "minLength": 1,
      "maxLength": 80,
      "pattern": "^[\\x20-\\x7E]+(?<!\\.)$",
      "description": "Concise single-line ASCII summary (1..80 chars) without a trailing period."
    }
  }
}
----

*Deliberate change vs. `plan-marshall`*: the shape mirrors the `plan-marshall` `execution-context` return (`status`, and `display_detail` of at most 80 ASCII characters on a single line without a trailing period; `plan-marshall` `marketplace/bundles/plan-marshall/agents/execution-context.md:141-152`), but results travel through the entity-scoped `submit` links, the harness's cancellation is observed by the server as the worker's fate, and `blocked` and `loop_back` are not statuses: a worker that cannot proceed follows `ask`, `infeasible:TASK-NNN`, or `yield:envelope-N`, or records its result through its `submit`; loop-backs are decided by the remediation policies and triage.

*Usage*: The server parses the usage from the harness output through the client profile's `headless.usage` declaration, read per turn, whose pointers map the harness's output fields to the columns `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`, `reasoning_tokens`, `tool_uses`, and `cost_usd` (link:../client-profiles/01-profile-schema.adoc#token-usage[Client Profiles Specification, Tokens, Not Money]). Every figure the harness reports is kept raw, as reported. A column the harness does not report is recorded as `unmeasured` with the reason `not_reported_by_harness`, never as `0`; a column whose figure does not exist for the harness by design (its pointer `"not_applicable"`, such as Antigravity's cache creation) is recorded as `"not_applicable"` and counts `0`; `"not_applicable"`, `unmeasured`, and a measured `0` are three distinct values. `headless.usage` has no pointer for the total: `total_tokens` is the sum of the five token components (input, output, cache read, cache creation, reasoning), a not-applicable one counting `0`, when every applicable one is measured, otherwise `unmeasured`; it is unweighted and the same for every harness. The component names mirror the per-dispatch usage columns of `plan-marshall` (`manage-metrics`), each optional and never defaulted to `0`; re-verify them against the latest `plan-marshall` version before implementing. A derived total keeps its lower bound of `1`, because a worker that ran consumed tokens; a measured `0` is legal only for a component, and a derived total of `0` is recorded `unmeasured`. `cost_usd` is recorded data only where the harness reports one: no view shows it, no figure the operator sees sums it, and no rule reads it. Beside the figures every row keeps what they depend on: `role`, `harness`, `harness_version` (the version the harness's probe reported at its worker's spawn, xref:04-worker-launch.adoc#launch-contract[Launch Contract]), `model`, `effort`, `form`, `phase`, and `attempt`.

*Rows per task and per job*: Usage is recorded in metrics rows of the task's scope (link:../store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Store Schemas Specification, Metrics Store]):

* *Fresh worker*: one row per job, keyed by its `job_id` and its `queue_task_id`, population `model_job`, holding the usage of the whole run (duration measured from spawn to exit).
* *Warm worker*: one row per task it served, keyed by its `queue_task_id` and the `job_id`, population `model_task`, holding the sum of the per-turn usage of the turns from the offer to the task's end; and one row per job, population `worker_idle`, holding the turns that served no task (the start and the idle wake-ups), with its `harness_version` like every row.
* *Consultation*: the usage of a consultation is the row of the consulted role's task, linked to the asking task (xref:05-consultation.adoc[Consultation]).

A run-total record of a warm worker is never read as its context size: the supervisor takes the context from the per-turn usage of the last turn (xref:03-supervision-and-recycling.adoc[Supervision & Recycling]). A worker ended by a signal reports no run usage: its run usage is recorded `unmeasured`, while the per-turn usage of the turns it completed stays accounted to their tasks (xref:03-supervision-and-recycling.adoc#ending[Supervision & Recycling, Ending a Worker]).

[#post-completion-invariants]
=== Post-Completion Integrity Invariants
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-6[PM-WATCH-DISP-6], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-7[PM-WATCH-DISP-7], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-8[PM-WATCH-DISP-8], link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-5[PM-WATCH-GEN-5], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-40[PM-WATCH-DISP-40]_

The workflow engine enforces six invariants when a task ends or a worker settles:

1. *Unmeasured Usage Never Fabricates Zero*: An unreported usage column is persisted as `"unmeasured"` in the metrics row (`metrics.json`), never as `0`, because a zero token count corrupts the token aggregations and masks missing telemetry; a not-applicable column is persisted as `"not_applicable"`, which counts `0` and still lets the row be measured. Every token total aggregated over workers is published as a population-stamped aggregate (`rows`, `rows_unmeasured`, `population_count`, per population `model_job`, `model_task`, and `worker_idle`; link:../store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Store Schemas Specification, Metrics Store]); when `rows_unmeasured > 0` the total is marked `total_is_floor: true`, is shown as at least its value with its coverage ("3 of 41 tasks unmeasured", with the reasons), and never wins a reconciliation against another source; a figure without a measured row is shown as unmeasured, never as `0`.
2. *No Synthesized Submissions*: A task that ended without its entity's required submission is never completed by the server (<<job-completion>> item 2), whatever the worker wrote to files or reported in its `job-result`.
3. *No Blind Re-Offer*: A task is offered again only through the `job_incomplete` remedy, after the server inspected the entity store and the worktree on disk; the next offer carries the observed partial progress in its facts and only the remaining work.
4. *Citations-Only Results for Read-Only Roles*: `read_only` tasks (Q-Gate validation, triage, enrichment, re-grounding, the reviews) persist their findings, component assessments, and proposals through entity-scoped `submit` links. The server computes the aggregate counts from the submitted records and renders them as facts of the next representation; `display_detail` is never read as evidence of a count.
5. *One Row per Attempt*: Every attempt that ran yields one row keyed by `queue_task_id` and `attempt`; a task closed without an attempt yields one row with every usage column `unmeasured` and `cause_class: refused` (<<job-result-schema>>); every warm worker job yields one `worker_idle` row, which belongs to no plan and lies in the workspace's `metrics.json`; every task row lies in the `metrics.json` of the task's scope: a plan's, an epic's (`epics/<epic_id>/`), or the workspace's (`workspace/`); outside a plan the row's `phase` is null. Each row carries `attempt_end`, the end of its attempt as the queue task record holds it, so that the share of attempts that ended with a clean exit and no submission (`exited_without_submit`, the end of a worker whose turn ended with text and no further call) is read per role, harness version, model, and effort, and a change of model or effort shows in it; it is a figure, and no rule reads it. `record-metrics` publishes, per divergence class (`row_absent_from_metrics`, `row_without_task_record`, `phase_re_entered`), the row count and the token mass the divergence hides.
+
[#cause-class]
*Cause Classes*: Every task row carries exactly one `cause_class` from the closed set `benign`, `returned_with_findings`, `retryable`, `stall`, `terminal_error`, `refused` (metrics row field, link:../store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Store Schemas Specification, Metrics Store]), derived from the task's outcome and its worker's fate, never from a `job-result`: `refused` for a task closed without an attempt (every role reason, `role_undefined`, `role_unqualified`, `role_unavailable`, and `class_mismatch`, and `withdrawn`) or whose worker's launch was refused; `benign` when its entity recorded the required submission, its question (`asked`), or its infeasibility with evidence (`infeasible`) without filing a finding; `returned_with_findings` when it filed at least one finding; `retryable` when the task ended `lost` and was offered again; `stall` when its worker ended `timed_out` without the submission; `terminal_error` for `failed`, `killed`, `cancelled`, or `indeterminate` without the submission; the first matching class in this order applies. The per-class populations sum to the task population of the phase and of the plan with an asserted residual of `0`; a row left unclassified fails the assertion and is never dropped from the total.
6. *Per-Column Usage Persistence & Measured Duration*: The total, each token component, `tool_uses`, and `cost_usd` are persisted independently, each as a measured value, `"not_applicable"`, or `"unmeasured"`; a column is never derived from another (the total is never split, the components are never summed into a missing total), except the total, which is the sum of the five token components when every applicable one is measured and `"unmeasured"` otherwise (<<job-result-schema>>); a partial sum is never recorded. The split a view shows, `tokens_in` (input, cache read, cache creation) and `tokens_out` (output, reasoning), is derived on read and never persisted. `duration_ms` is measured by the server: for a fresh worker from spawn to exit (`duration_basis: process`), for a warm worker's task from the offer to the task's end (`duration_basis: task`); the time in the slot queue is recorded apart as `queued_ms`. When every usage column of every row in a phase is `"unmeasured"`, `record-metrics` reports `instrument_dark: true` for that phase instead of a total.

[#spend-accounting-budget-anchors]
== Usage Reporting & Spend Classes
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-14[PM-WF-14: Task Envelopes, Model Slots & Usage per Task], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation]_

_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-2[PM-WATCH-DISP-2], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-3[PM-WATCH-DISP-3]_

The usage of the models is recorded and reported in tokens, never in money, and nothing limits it: no plan is re-planned, held, or handed back for what it used, no gate compares a plan's usage with a threshold, and no figure is projected against a budget. Limits can be added later, each by a change of its own, on the recorded data.

* *What the operator sees*: wherever usage is shown (a plan's completion report and its running process, an epic's resource, the system view; link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#reports[Runtime & Interaction Model Specification, Reports to the Operator], link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#process-resource[Process Resource], link:../runtime-lifecycle/03-runtime-metrics.adoc#runtime-metrics[The Runtime's Metrics]) it is `total_tokens` with its split, `tokens_in` and `tokens_out`, and its coverage (<<post-completion-invariants>> item 1), never a cost and never `priced_units`. `priced_units` stays the internal figure of the migration trigger _Priced units_ (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#migration-trigger-evaluation[Phase Workflows Specification, Migration Trigger Evaluation]).
* *A plan's tokens*: the section _tokens_ of a plan's completion report gives the total with its split and the plan's wall time; per phase; per role (a role pins harness, model, and effort); per model and harness; the waste, the tokens of tasks that produced nothing (class `no_product` below) and of retries and remediation per cause class (<<cause-class>>); and the coverage. `worker_idle` rows belong to no plan and are reported apart as idle usage.

[[navigation-figures]]*Navigation Figures*: Beside the tokens, the server derives from a task's records what the work cost to navigate, each figure with its population (the turns, the reads, or the lookups it counts over) and `indeterminate` where that population cannot be read:

* *Cache-read share*: the cache-read tokens over the context tokens (input, cache read, cache creation) of the task's turns; `unmeasured` where the harness does not report cache reads.
* *Skill residency*: per skill of the task's required set, the bytes delivered in-band at launch and the sections the worker read later through `pm_skill` with a `section` (or `resources/read` of a section anchor), so the skill content that is resident without being needed, and the sections read on demand, are visible per role and per skill.
* *Most expensive turns*: the five turns of the task with the most context tokens, each with its tokens and the tool calls it made.
* *Largest tool results*: the ten largest `tool_result` entries of the task's activity, each with its size and the tool and target of its call, so the first thing to cut is visible.
* *Revisits*: the reads of a file the worker had already read earlier in the same plan task, from the targets of the `tool_call` entries of its activity whose tool is a file-reading tool of the harness, over all such reads.
* *Language-server use*: the share of `pm_lsp` read operations among all code lookups of the task, `pm_lsp read operations / (pm_lsp read operations + calls of the harness's own search tools)`; `indeterminate` where the task made no lookup.
* *Fallback-to-read rate*: the `pm_lsp` lookups followed, in the same plan task, by a whole-file read of the file the lookup answered with, over all lookups; a read of a part of that file is the expected next step and does not count.

The section _tokens_ of a completion report shows them per task, per role, and per plan; they are evidence for the evaluation of a skill or a role configuration (link:../workflow-dsl/07-loop-back-diagrams-verification.adoc#comparison-footprint[Workflow DSL Specification, Comparison Footprint]), never a limit.

*Spend Classes*: The spend classes report what the tokens were spent on. Every task row is classified by what its task produced, from the entity and findings records the server holds, never from a worker's fate or its `job-result`:

[cols="1,4"]
|===
|Class |Condition

|`submitted`
|The task's entity recorded its required `submit` transition.

|`findings_only`
|No required `submit` was recorded, but the task filed at least one finding (`FindingRecord.queue_task_id`).

|`no_product`
|The task ended without a submit and without a filed finding.

|`unmeasured`
|The row's token usage is unmeasured, whatever the task produced (its product is still shown in the cross-tabulation); it is counted by rows, never summed as `0`.
|===

Every task row belongs to exactly one class, and every `worker_idle` row is reported apart as idle usage; the class token sums add up to the measured total with an asserted residual of `0`, and `unmeasured` rows are reported as a row count beside the sums. The worker's fate (`succeeded`, `failed`, `timed_out`, `killed`, `cancelled`, `indeterminate`, `refused`) is a separate dimension, rendered as a cross-tabulation with the classes, so a task whose worker `failed` after filing real findings is `findings_only`, never waste.
