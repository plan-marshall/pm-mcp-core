[#two-level-guard]
== Two-Level Guard for External Text
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-5[PM-WF-5: Model Work as Role Tasks & Single-Level Leaf Constraint]_

Fetching, extracting, and guarding external content is server work; a model only judges content the server has already fetched, validated, and marked untrusted. External text passes two guards before it reaches a model as content:

1. *Level 1, the deterministic ingestion validator* of the server, which is the containment boundary (link:../job-runtime/03-parsers-and-gates.adoc#ingestion-validator[Job Runtime Specification, Ingestion Validator]).
2. *Level 2, the screener*: a fresh `zero_tool` worker of the role `screener` that receives the cleaned text in-band and returns a closed verdict per item (<<screener>>). It can only restrict, never grant: it is defence in depth, never the boundary, and screened text is still delivered marked untrusted.

*Surfaces*: Level 2 screens all externally authored free text: issue and pull-request titles and bodies, every review comment and bot finding text, analysis-provider messages, and upstream MCP results entering a store. CI logs and build excerpts are the server's own job output and pass level 1 only. What the operator wrote and what is on this machine is trusted and passes neither guard (<<local-trusted>>).

There is no model that extracts from external text: no reader role exists, and a worker never fetches external content itself.

[#local-trusted]
=== What Is on This Machine Is Trusted
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-58[PM-WATCH-STORE-58]_

The guards separate what comes from outside the machine from what the operator and the project hold:

* *Trusted*: what the operator wrote in a client (a description, an answer, the operator's own words in a decision, a reason) and what is on this machine (the project's checkout, documents the operator chose, a lesson not derived from untrusted text, a recipe, the captured local changes). They are never screened and never marked untrusted; a model reads them as the operator's and the project's own, as it reads the code. A description is not searched for pasted third-party text: what the operator puts into a client is the operator's.
* *Untrusted until screened*: what comes from outside the machine: issues, pull requests, review comments and bot findings, analysis-provider messages, and results of upstream MCP servers. They pass both guards (<<screen-stored>>), and stay marked untrusted after the screening.
* *A lesson derived from untrusted text*: a lesson whose writing task read text marked untrusted (`derived_from_untrusted`, link:../store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Lesson Record]) can carry an injection the screener missed into later work as the project's own words. It is not trusted: chosen as the source of a start, it passes level 1 and the screener like an external source (link:../state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-source[State Catalogue, Source Units]) and stays marked untrusted; every other model that reads it (the lesson review among them) reads it marked untrusted.
* *A pull request's changed files*: code from outside the machine, possibly from a fork. A pull request's source stores its head and marks its changed files untrusted unless the operator authored the pull request (the provider's author of the pull request is the operator's identity on that provider); no model reads them as instructions, they are never part of a screening batch, and the plan's own gates (its review, its integrity checks) apply to them.

[#screen-stored]
=== Screened Once Stored
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_

Every external source of a start (an issue, a pull request, link:../state-catalogue/09-bootstrap-and-lessons.adoc#start-from-clients[State Catalogue, Starting from the Clients]) takes one order, the same for every source kind:

. *Fetch*: a bounded job fetches it through the provider (link:../job-runtime.adoc[Job Runtime Specification]).
. *Level 1*: the ingestion validator cleans its text (link:../job-runtime/03-parsers-and-gates.adoc#ingestion-validator[Job Runtime Specification, Ingestion Validator]).
. *Store*: the server stores it in the entry's source directory and enters it in the manifest marked `unscreened` (link:../filesystem-layout/03-project-store.adoc#source-directory[Filesystem Layout Specification, The Source Directory]); a stored source is never changed.
. *Screen*: the screener runs over the batch built from the stored files (<<batch-v1>>, <<screener>>), and the verdict (`clean` or `suspicious` with its spans) is written into the manifest beside the source.

No model but the screener reads a source before its verdict is `clean` or the operator accepted it; a start offers its chat only once every external source of the entry is screened (link:../state-catalogue.adoc#chat[State Catalogue, Chat]). A source stored and not yet screened when the runtime stopped is screened from its stored copy at the next start of the runtime, never fetched again.

*Fail closed*: a screener that fails (no valid output, a fate other than `succeeded`), and a role `screener` without a qualified configuration, leave the source `unscreened` with the cause, never marked `suspicious` in its place, so a failure never looks like a flagged source. The source's state of the source sub-workflow (`source-<kind>.unscreened`, link:../state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-source[State Catalogue, Source States]) is an operator wait that shows the cause and offers _retry_, _remove_, and _accept as untrusted_; an acceptance is recorded with the operator's reason like an accepted flagged source, and the text stays marked untrusted.

[#batch-v1]
=== Batch Format (`batch-v1`)
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-36[PM-WATCH-DISP-36]_

Every source step and every gather firing that ingests external text gathers its new items first and writes them, after level 1, as one server-built batch. The batch is the unit of screening and of batched judgment:

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://cuioss.de/plan-marshall-mcp/schemas/batch-v1.json",
  "title": "Batch",
  "type": "object",
  "required": ["batch_id", "items"],
  "additionalProperties": false,
  "properties": {
    "batch_id": { "type": "string", "pattern": "^BT-[0-9]+$", "description": "Scope-unique identifier of the batch, assigned by the server (identifiers.adoc, record counters)." },
    "items": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "required": ["item_id", "kind", "source", "fields", "text", "sha256"],
        "additionalProperties": false,
        "properties": {
          "item_id": { "type": "string", "pattern": "^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$", "description": "Batch-unique item identifier; for a finding its finding_id." },
          "kind": { "type": "string", "enum": ["issue", "pull_request", "review_comment", "bot_finding", "analysis_message", "upstream_result"] },
          "source": { "type": "string", "description": "Provider, bot kind, analysis provider, or upstream server that authored the text." },
          "fields": { "type": "object", "description": "The item's structured fields (author, file, line, rule_id, domain); never free text." },
          "text": { "type": "string", "description": "The level-1-cleaned text, enclosed in the spotlighting delimiters of the validator." },
          "sha256": { "type": "string", "pattern": "^[0-9a-f]{64}$", "description": "SHA-256 of the cleaned text; the key of the verdict cache." }
        }
      }
    }
  }
}
----

The batch is persisted with the records it came from (the source manifest of an entry for a source of a start, built from the stored files; the findings records of a gather firing with their `batch_id`, link:../store-schemas/03-findings-and-review-records.adoc[Store Schemas Specification, Findings & Review Records]); it is never rendered into `facts` as a whole.

[#screener]
=== Screener (role `screener`)
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-25[PM-WATCH-DISP-25], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-35[PM-WATCH-DISP-35]_

* *One task per batch part*: The screen state after a source or gather step screens the batch's items that have no cached verdict. It is declared with the fan-out of a model state, `job llm screen role screener each screen.batch-parts` (link:../workflow-dsl/02-units-jobs-decisions.adoc#model-job-states[Workflow DSL Specification, Model Job States]), over the server-computed list of the batch's parts: a batch within the compiled screening split bound (link:../timeouts/03-retention-host-config.adoc#screening-split-bound[Timeouts & Budgets Specification, Screening split bound]) is one part, a batch above it is split into consecutive parts. The state queues one task per part; each is served by its own fresh screener worker through the model slots, and the state completes when every part has its verdict. The shipped role artifact `screener` is `fresh` and `zero_tool` (xref:01-roles-and-configuration.adoc[Roles & Configuration]); a warm screener would carry injected text to the next batch (link:../../../../plan-marshall-documentation/doc/specification/evaluation.adoc#results[Evaluation Reference], E9).
* *Verdict cache*: Verdicts are cached per scope by the `sha256` of the cleaned text, so a re-gather screens only new texts. A cached verdict is reused, never re-decided; a fail-closed verdict (no valid screener output) is never cached (link:../store-schemas/15-screening-and-grants.adoc#screen-verdict-cache[Store Schemas Specification, Screening Verdict Cache]).
* *Isolation*: The screener is a `zero_tool` worker (xref:04-worker-launch.adoc#harness-selection[Harness Eligibility & Launch Refusals]): no tools, no MCP connection, one turn where the harness offers the limit, the server-fixed screener prompt (compiled, never a skill and never project-overridable) with the items in-band inside their spotlighting delimiters, the empty `cwd/` subdirectory of its job-private directory as working directory, and project and user settings off (xref:04-worker-launch.adoc#job-working-directory[Working Directory, Project Files & Zero-Tool Isolation]). It has no entity unit and takes no part in the task protocol: its task is leased to it at spawn, and the server ends the task `submitted` from a validated `screen-verdict` and `lost` otherwise (xref:02-task-protocol.adoc[Task Protocol]).
* *Result*: The structured output `screen-verdict`, validated by the server:
+
[source,json]
----
{
  "$id": "https://cuioss.de/plan-marshall-mcp/schemas/screen-verdict-v1.json",
  "type": "object",
  "required": ["items"],
  "additionalProperties": false,
  "properties": {
    "items": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["item_id", "verdict", "spans"],
        "additionalProperties": false,
        "properties": {
          "item_id": { "type": "string", "pattern": "^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$" },
          "verdict": { "type": "string", "enum": ["clean", "suspicious"] },
          "spans": {
            "type": "array",
            "items": {
              "type": "object",
              "required": ["start", "end", "reason"],
              "additionalProperties": false,
              "properties": {
                "start": { "type": "integer", "minimum": 0 },
                "end": { "type": "integer", "minimum": 0 },
                "reason": { "type": "string", "maxLength": 200 }
              }
            }
          }
        }
      }
    }
  }
}
----
* *Fail closed*: A missing, extra, duplicate, or unparseable item counts as `suspicious`. A screener worker that ends with any fate other than `succeeded`, or whose output does not validate, leaves every item of its part without a verdict: a source of a start stays `unscreened` with the cause (<<screen-stored>>), and a gathered item of a plan is withheld like a `suspicious` one. On a harness without schema output the final message is parsed against the same schema, with the same rule.
* *Effect of `suspicious`*: In a source of a start, the source sub-workflow enters an operator wait that shows the flagged spans and offers _accept_ (the text is used, still marked untrusted, the acceptance audited with the operator's reason) or _remove_ (the source leaves the entry's list), and the screening of a stored source writes the report `source.flagged` (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#reports[Runtime & Interaction Model Specification, Reports to the Operator]). Inside a plan the text is withheld: only the item's structured fields and `withheld: flagged by screener` are delivered; a withheld finding stays pending, its unit ends through its budget and fallback, the hand-back report lists the withheld items, and a `met` waiver of that finding lets the plan proceed (link:../state-catalogue.adoc[State Catalogue]).

[#batched-triage]
=== Batched Triage (`triage-groups`)
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-36[PM-WATCH-DISP-36]_

Model judgment of findings is batched like screening: one triage task per gather firing, never one per finding.

* *Grouping*: The server groups the batch's findings that are not withheld by `(domain, rule_id)` and renders the groups, each with its findings' structured fields, cleaned texts, and the evidence each judgment rests on (xref:06-envelopes-questions-deadlines.adoc#decision-evidence[Evidence in Facts]), as the entity of one triage task of the triage role the unit's state names (`triage-review` / `triage-analysis` in the default units) in the triage state of its remediation unit (link:../state-catalogue/08-remediation-units.adoc[State Catalogue, Remediation Units]); batched dispositions are for review-bot and plugin-doctor findings only. Analysis-provider findings get no batched triage: they are judged as failure envelopes by the role `triage-analysis` in `remediation-analysis.choose` (link:../state-catalogue/08-remediation-units.adoc#state-remediation-analysis.choose[State Catalogue, `remediation-analysis.choose`]).
* *Submission*: The task submits `submit:triage-groups` once: per group one disposition (`FIX`, `SUPPRESS`, or `ACCEPT`, with its `confidence` `0..100`, the decision confidence of the group's decision record, link:11-decision-records.adoc#decision-confidence[Decision Confidence of a Task]; `reply_text`; for `FIX` its `population` and for `SUPPRESS` its `suppress_reason`, link:../store-schemas/03-findings-and-review-records.adoc[Store Schemas Specification, Findings Ledger Record], Closed Suppression Reason; optional `requirement_refs`), and per finding an optional exception that overrides the group's disposition for that finding.
* *Server writes per finding*: The server expands the groups and writes one disposition per finding, validating each like a single disposition (a disposition that contradicts the finding's class is refused, `invalid_link_args` naming the finding); a finding the submission does not cover stays untriaged. Withheld findings are never part of a triage batch.
