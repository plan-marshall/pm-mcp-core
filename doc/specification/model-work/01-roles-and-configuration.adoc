[#roles]
== Roles as Configuration Artifacts
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-1[PM-WORK-1: Roles as Configuration], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-14[PM-WF-14: Task Envelopes, Model Slots & Usage per Task], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SKILL-5[PM-SKILL-5: Skill Extensions]_

Every piece of model work is a task of a role (xref:02-task-protocol.adoc[Task Protocol]). A role is one JSON artifact; the server knows no fixed role. A workflow state names a role by its name, and the one model caller (<<model-caller>>) reads the role's effective configuration (its artifact, with the harness, model, and effort of <<role-assignment>>) and acts on it. Changing or adding a role is an edit of a role set, and moving a role to another harness or model an edit of a role set or of a role assignment, never a code change.

[#role-artifact]
=== Role Artifact Schema

A role artifact is the file `<name>.json` of a role set (<<role-sets>>). Its schema is closed; an unknown member makes the artifact invalid (<<role-validation>>). The schema is the file `role-artifact-v1.schema.json` in `pm-core/src/main/resources/de/planmarshall/core/role/`, beside `RoleArtifact` and its reader `RoleArtifactValidator`:

* *`class`* decides what the role may do: a `writer` changes the plan worktree and runs builds, a `read_only` role reads and submits, a `zero_tool` role has no tool and no PM-MCP connection. The class bounds the tool set: the tools a class allows and the capabilities it needs from its harness are specified in xref:04-worker-launch.adoc#job-tool-sets[Worker Launch, Tool Sets]. `tools` names exactly the tools the role gets, the `PM-MCP` tools and the harness tools by the names of its `harness`, all within that bound. Every non-`zero_tool` role names `pm_wait`, `pm_state`, `pm_do`, `pm_skill`, and `pm_skill_file`.
* *`form`*: a `fresh` role gets one worker per task, which ends after the task; a `warm` role gets supervised workers that take task after task and are recycled (xref:03-supervision-and-recycling.adoc[Supervision & Recycling]). A `zero_tool` role is always `fresh`.
* *`count`*: for `fresh`, the most fresh workers of the role that run at once in the project; for `warm`, the most warm workers the supervisor keeps. Both are bounded further by the machine's model slots and by one writer per plan (xref:04-worker-launch.adoc[Worker Launch]).
* *`recycling`*: `idle_wakeups` lowers the harness's value (`worker.idle_wakeups` of the harness profile, link:../harness-profiles/01-profile-schema.adoc[Harness Profiles Specification, Profile Schema]) and never raises it; `token_budget` and `tasks_per_generation` hold for the role alone.
* *`skills`*: a compiled skill, among them the shipped role skills `skill://pm/role/<role>/SKILL.md`, or an extension skill of the machine or project skill directory (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/02-service-and-skill-tools.adoc#skill-extensions[MCP Tools Specification, Skill Extensions]). A role that the shipped set does not define takes its contract from an extension skill, so adding a role needs no code change; an artifact of the machine set that names a project extension skill is valid only in the projects whose directory holds that skill (<<role-validation>>).
* *`budget_floor_seconds`*: the floor of the job budget that the runtime learns per role, at least the compiled minimum of the link:../timeouts/01-job-budgets-and-waits.adoc#model-job-budget[Timeouts & Budgets Specification, Worker Budget]; the shipped floors are in <<default-roles>>.
* *`context_budget_tokens`*: the context budget of a worker of the role, which depends on the model the artifact names; the per-envelope packing budget is derived from it (xref:06-envelopes-questions-deadlines.adoc[Task Envelopes, Envelope Budget]). Where the artifact does not set it, the harness fallback `headless.context_budget_tokens` of the harness profile applies (link:../harness-profiles/01-profile-schema.adoc[Harness Profiles Specification, Profile Schema]).

* *`questions`*: whether a task of the role continues after it asked, and how long (xref:06-envelopes-questions-deadlines.adoc#continuation[Continuing after a Question]). It is set per role because a role names its harness and model: a continuation pays off where the work before the question is large and the model keeps it reliably, which differs per model. Each value is cut to what the role's harness declares in `headless.resumability`; a harness that declares neither form makes the member ineffective, which `pm-operator roles show` reports. The member is invalid on a `zero_tool` role, which never asks.
* *`off_track`*: per off-track signal of the role's workers a threshold below the compiled one and the action the server takes when the signal holds (xref:03-supervision-and-recycling.adoc#worker-off-track[A Worker Off Track]). A threshold above the compiled one makes the artifact invalid (`schema_invalid`); the member is invalid on a `zero_tool` role, which has no activity to watch.

The *configuration digest* of a role is the SHA-256 of the canonical JSON (RFC 8785) of its effective artifact with `description` removed and its `harness`, `model`, and `effort` replaced by the role's effective values (<<role-assignment>>), together with the digests of its skills as the project resolves them (an extension skill with the digests of its files at that read) and the major.minor of the enrolled harness version (link:../store-schemas/11-enrolment-store.adoc#harness-enrolment-store[Store Schemas Specification, Harness Enrolment Store]). It identifies the configuration a worker generation is started with: task offers and recycling compare it (xref:02-task-protocol.adoc#offer[Offer], xref:03-supervision-and-recycling.adoc[Supervision & Recycling]).

The *qualification digest* of a role is the SHA-256 of the canonical JSON (RFC 8785) of exactly the values the grading measures: the effective `harness`, `model`, and `effort` (<<role-assignment>>) and the artifact's `tools` and `class`, together with the digests of its skills as the project resolves them, the major.minor of the enrolled harness version, and, where the harness reports one, the weights identity of the model as the enrolment records it (link:../harness-profiles/03-endpoint-harness.adoc#weights-identity[Harness Profiles Specification, Weights Identity]). It identifies the configuration a qualification record is bound to (<<qualification-records>>); the form is measured per form within one record. A changed assignment or plan override of the harness, the model, or the effort changes both digests, so the role's qualification is stale in every project it applies to, as an edited artifact makes it. An edit of any other member (`count`, `recycling`, `budget_floor_seconds`, `context_budget_tokens`, `questions`, `off_track`, `form`) changes the configuration digest and leaves the qualification digest, and so the record, valid; an edit of `description` changes neither digest.

[#role-sets]
=== Role Sets & Precedence

The roles that exist are exactly the artifacts of the effective role set of a project. Three sets contribute, from lowest to highest precedence:

[cols="1,3,3"]
|===
|Set |Location |Owner

|Shipped
|`classpath:/roles/<name>.json`, compiled into the release; qualification records under `classpath:/roles/qualification/`
|The release (<<default-roles>>)

|Machine
|`<PM_MCP_BASE>/roles/<name>.json`; no qualification records
|The operator, for every project of the machine

|Project
|`<PM_MCP_BASE>/projects/<project_id>/roles/<name>.json`; every qualification record the operator makes under `<PM_MCP_BASE>/projects/<project_id>/roles/qualification/`
|The operator, for one project
|===

An artifact replaces the artifact of the same name in a lower set as a whole; members are never merged. A role's `harness`, `model`, and `effort` are further overlaid by the role assignments and a plan's override (<<role-assignment>>), which change only these three members. The paths are listed in the link:../filesystem-layout.adoc[Filesystem Layout Specification]. Role sets, role assignments, and plan overrides are operator files (link:../domain-extensions/06-configuration.adoc[Domain Extensions Specification, Configuration]): the runtime never reads a role, a harness, or a model from git-tracked configuration, and no job can write them (job confinement, link:../job-runtime/02-confinement-and-environment.adoc[Job Runtime Specification]).

The runtime reads the effective configuration at every composition (<<role-composition>>), at every task creation (<<model-caller>>), and at every offer (xref:02-task-protocol.adoc#offer[Offer]), so an edited artifact or a changed assignment applies to every queued task and to the next worker generation. A running generation keeps the configuration it was started with and its configuration digest (<<role-artifact>>); a generation whose digest is outdated is offered no new task, and a warm worker whose configuration changed is recycled after its current task (xref:03-supervision-and-recycling.adoc[Supervision & Recycling]).

[#role-assignment]
=== Role Assignment
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-1[PM-WORK-1: Roles as Configuration], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-14[PM-WF-14: Task Envelopes, Model Slots & Usage per Task], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-25[PM-WF-25: Plan Behaviour Axes & Plan Overrides], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)]_

A role is still defined by one artifact, which replaces a lower one as a whole, but the harness, model, and effort a role runs on are its *effective values*, taken in this order, each later level overriding the earlier ones:

. the shipped artifact;
. the machine artifact (`<PM_MCP_BASE>/roles/<name>.json`);
. the machine's role assignment (`<PM_MCP_BASE>/role-assignments.json`);
. the project artifact (`<PM_MCP_BASE>/projects/<project_id>/roles/<name>.json`);
. the project's role assignment (`<PM_MCP_BASE>/projects/<project_id>/role-assignments.json`);
. the plan's override (link:../workflow-dsl/09-plan-instance.adoc#plan-overrides[Workflow DSL Specification, Plan Overrides]).

An artifact level supplies its three members only where it holds the role's artifact; an assignment or an override changes only the `harness`, `model`, and `effort` it names of the artifact it lands on, and a role it does not name keeps the value of the level below. The role's other members (class, tools, form, skills, budgets) come from its effective artifact alone.

* *The assignment store*: a role assignment is a JSON object of the machine (`<PM_MCP_BASE>/role-assignments.json`) or of one project (`<PM_MCP_BASE>/projects/<project_id>/role-assignments.json`) with `format_version` and, per role name, `harness` and `model` (required), `effort` (optional and nullable) and `escalation` (optional); its schema is owned by the link:../store-schemas/12-machine-stores.adoc[Store Schemas Specification, Machine Stores]. It is written only by the sub-workflow `roles.write` of the onboarding, run for the machine (link:../workflow-dsl/01-grammar.adoc#machine-scope[Workflow DSL Specification, Machine Scope]) or for one project (link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-onboarding[Credentials & Enrolment Specification, Project Onboarding]), with the operator's choices from either client; the operator may still write whole artifacts of the machine or project set.
* *Validated as set*: `roles.write` and a plan's override validate every value they write as the role's effective configuration (<<role-validation>>), the enrolled harness, the allowed model of the effective catalogue, and the effort the harness accepts for the model, and refuse it with the validation reason; a value that a later change makes invalid (an unenrolled harness, a model the catalogue no longer allows) makes the role invalid at its next read, as an invalid artifact does.
* *Qualification follows the effective values*: both digests (<<role-artifact>>) are computed over the effective values, so a changed assignment or override makes the role's qualification stale per project; the role is graded again by the project setup (<<install-grading>>) or by `pm-operator roles qualify`. An override to a configuration without a current qualification record is shown to the operator as unqualified when it is set, and its tasks take the conservative fallback (<<conservative-fallback>>) until the project grades it.
* [[escalation-assignment]]*Escalation assignment*: a role's assignment may name, beside its own values, an `escalation` configuration (`harness`, `model`, `effort`), set by the operator like the role's values and resolved through the same levels (the project's over the machine's; a plan override does not set it). It is validated as set like the role's own values and has its own qualification digest and record: the escalation configuration of a role is graded on the role's corpus topics like any configuration (<<qualification>>). The last round of a fix budget whose work is a task of this role runs on it, while it is qualified (xref:../phase-workflows/01-planning-phases-1-2.adoc#_remediation_policy_calls[Phase Workflows Specification, Remediation Policy Calls]); a role without one, or with an unqualified one, runs that round on its own values, and the task records which it used.
* *Advisory beside the value*: wherever a role's assignment is shown or changed (the onboarding, the machine's and the project's settings, a plan override), the clients show the role's advisory of the default assignment (<<default-assignment>>) beside it, also after the operator changed the value.


[#role-validation]
=== Validation against Schema and Harness Profile

Every artifact is validated when it is read, first against its schema, then, with the role's effective `harness`, `model`, and `effort` (<<role-assignment>>), against the harness profile of that harness (link:../harness-profiles/01-profile-schema.adoc[Harness Profiles Specification, Profile Schema]) and the effective model catalogue. An invalid role counts as undefined; it does not fall back to an artifact of a lower set. The reason is reported to the operator in both clients (the role views of the machine's and the project's settings), in `pm-operator roles list` and `show` (<<operator-roles>>), and in the audit log.

[cols="2,5"]
|===
|Reason |Rule

|`schema_invalid`
|The artifact fails its schema, its `name` differs from its file name, or `recycling` is missing for `warm` or present for `fresh`.

|`harness_unknown`
|No harness profile has the `harness_id` `harness`, or the harness is not enrolled on the machine.

|`harness_not_eligible`
|The profile's `worker.eligible` is `false`.

|`harness_class_not_runnable`
|The profile's `headless.classes` entry for the role's class is `null`; for a `zero_tool` role (the screener, the judge) this is every harness that cannot be started without tools.

|`model_restricted`
|No entry of `worker.restricted_models` matches `model` (exact name or a `*` glob): the model refuses a restricted tool set on that harness.

|`effort_unsupported`
|`effort` is below every value `headless.model_efforts` lists for the model, or `effort` is not `null` while that list is empty for the model.

|`model_not_allowed`
|The effective model catalogue (the project's, else the machine's, link:../store-schemas/12-machine-stores.adoc#model-catalogue[Store Schemas Specification, Model Catalogue]) does not allow `model` on the role's harness. Never applies to the `steward` (<<steward-role>>).

|`tool_not_permitted`
|`tools` names a tool outside the tool set of the class, a harness tool that starts sub-agents or asks the user, or omits a PM-MCP tool every role of the class names; a `zero_tool` role names any tool.

|`form_not_permitted`
|A `zero_tool` role is `warm`.

|`skill_unresolved`
|A skill does not resolve in the project's skill catalogue (compiled skills and the accepted extension skills of the machine and project skill directories; a refused extension skill does not resolve), or the first skill is neither a compiled role skill (`skill://pm/role/…`) nor an extension skill (`skill://pm/ext/…`). Validity is per project, because the extension skills are.
|===

A role listed by a quorum declaration of the question adjudication whose artifact fails only with `harness_not_eligible` or `harness_unknown` is reported with that reason and counts as unavailable to the adjudication, not undefined (xref:10-decision-quorum.adoc#decision-declarations[Ask or Quorum, Decision Declarations]).

[#role-composition]
=== Composition Check (`role_undefined`, `class_mismatch`)
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-49[PM-WATCH-DISP-49]_

A workflow unit names roles freely by name: in a model state (`job llm <entity_kind> role <role>`) and in a consultation clause (`consult role <role>`, xref:05-consultation.adoc[Consultation]); the grammar is the link:../workflow-dsl.adoc[Workflow DSL Specification]'s. When the runtime composes a plan instance, an epic workflow, or the project setup workflow of a project (link:../workflow-dsl/09-plan-instance.adoc[Workflow DSL Specification, Plan Instance]), it resolves every named role in the project's effective set. A role that is absent or invalid refuses the composition with `role_undefined`, naming the role, the state, and the validation reason where there is one (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/04-errors-and-testing.adoc[MCP Tools Specification, Errors]); the scope is not created, and no state is reached that names the role.

[#role-class-fit]
The same check fits each named role's class to its use. Every entity kind declares, with its registration, the role class its tasks require: the task envelope `writer`, the screener's kind `screen` and the judge's grading kind `zero_tool`, the vote kind `vote` `read_only`, the commit message's kind `commit-message` and the change type's kind `change-type` `read_only` or `zero_tool`, a chat's reply `chat-reply` `read_only`, every other kind `writer` or `read_only` as its work needs (a kind that changes the plan worktree or runs builds `writer`, a kind that reads and submits `read_only`). A model state whose role's class differs from the class its entity kind requires, and a `consult role` clause that names a `zero_tool` role, refuse the composition with `class_mismatch`, naming the role, its class, the state, and the required class (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/04-errors-and-testing.adoc#rejection-reasons[MCP Tools Specification, Rejection Reasons]). The one exception is `chat-reply`, whose role the chat routes to at run time: a `writer` role it routes to (`implement` for a decision its task asked) is not refused but runs the chat with its tools narrowed to those of `read_only` (xref:04-worker-launch.adoc#job-tool-sets[Worker Launch, Tool Sets]), so a chat never changes the worktree, never runs a build, and never waits behind the plan's one writer (link:../state-catalogue.adoc#chat-context[State Catalogue, What a Chat Knows]).

A role that becomes undefined after composition (an artifact removed or invalidated by an edit) is found at task creation: the task closes without an attempt with the reason `role_undefined`, and its state takes the conservative fallback (<<conservative-fallback>>). A role whose class an edit changed so that it no longer fits is found at task creation the same way and closes the task with the reason `class_mismatch`.

[#closed-task-in-band]
*A closed task without tools*: the commit message and the change type are small closed tasks over evidence the server holds, so a model without tools, a model on this machine among them (link:../harness-profiles/03-endpoint-harness.adoc#endpoint-harness[Harness Profiles Specification, Endpoint Harness]), can take them. A `zero_tool` role of either kind receives in-band what a `read_only` worker reads with its tools (xref:06-envelopes-questions-deadlines.adoc#decision-evidence[Task Envelopes, Evidence in Facts]): the commit message the staged diff beside `git.diff-summary`, the change type the rendered clarified request. The shipped `commit-message` and `classify` are `read_only`; a machine or project artifact of either role may set `zero_tool`, and it is graded on the role's topics like every changed class (<<qualification-records>>).

[#model-caller]
== The Model Caller
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-1[PM-WORK-1: Roles as Configuration], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-5[PM-WF-5: Model Work as Role Tasks & Single-Level Leaf Constraint]_

The runtime has exactly one model caller. Every model step of every workflow goes through it, and no other part of the runtime knows what a role is for. When a model state creates a task (xref:02-task-protocol.adoc#queue-task[Queue Task]), the caller acts in this order:

. *Resolve*: It reads the effective configuration of the state's role (<<role-assignment>>). An absent or invalid artifact closes the task with `role_undefined`, and a class that does not fit the entity kind, or a `zero_tool` role consulted, with `class_mismatch` (<<role-composition>>).
. *Qualify*: It looks up a valid qualification record for the role's qualification digest (<<qualification-records>>). Without one, the task closes with `role_unqualified` and the state takes its conservative fallback (<<conservative-fallback>>). When only the fresh form of a `warm` artifact qualifies, the caller runs the role `fresh` and records `form_downgraded` on the task. A task of the `judge` (<<grading>>) or the `steward` (<<steward-role>>) skips this step.
. *Available*: When the start-failure guard of the role on its harness holds (xref:03-supervision-and-recycling.adoc#start-failure-guard[Start-Failure Guard]), the task closes with `role_unavailable` and the state takes its conservative fallback, except the probe task after the probe backoff, which starts its worker and waits for it (xref:03-supervision-and-recycling.adoc#start-failure-guard[Start-Failure Guard], _Clear_).
. *Fit*: For a `zero_tool` role it estimates the tokens of the launch prompt and the task's in-band input as a screening batch is packed (link:../harness-profiles/03-endpoint-harness.adoc#endpoint-request[Harness Profiles Specification, The Request]); when they exceed the role's context budget on its harness (on an endpoint harness `context_tokens` less `answer_reserve_tokens`), the task closes with `input_too_large` and the state takes its conservative fallback. The input is never cut to fit: a commit message written for part of a diff, or a judge's score for part of an answer, validates and is wrong.
. *Queue*: It queues the task for the role; the offer matches it to a generation of the role's current configuration (xref:02-task-protocol.adoc#offer[Offer]).
. *Serve*: The supervisor serves it with a warm worker of the role or starts a fresh worker for it (xref:03-supervision-and-recycling.adoc[Supervision & Recycling]), launched by the launch contract (xref:04-worker-launch.adoc[Worker Launch]).

[#role-model-effort]
=== Model & Effort

The harness, model, and effort of a worker come only from its role's effective values (<<role-assignment>>): its artifact, the role assignments, and the plan's override. There are no effort levels, no ladder, and no agent file installed per role or per level; how the launch fills the harness's model and effort slots and narrows an effort the harness does not accept is specified in xref:04-worker-launch.adoc#model-and-effort[Worker Launch, Model & Effort]. An effort below every value the harness accepts for the model, and any non-null effort for a model whose effort list is empty, makes the artifact invalid (`effort_unsupported`, <<role-validation>>). A changed artifact, assignment, or override applies to the next worker generation, without a restart.

[#default-roles]
=== Default Role Set

The shipped set defines every role the default workflow units name, the two quorum roles the quorum declarations of the default adjudication unit list among them, the grading judge `judge` (<<grading>>), the interpreting role `interpret` (xref:06-envelopes-questions-deadlines.adoc#own-words[Answers in the Operator's Own Words]), and the machine's advisor `steward` (<<steward-role>>). Every default role runs `fresh`, with `count` `2` (`screener` and `enrich` `4`). The column `Floor s` is the artifact's `budget_floor_seconds`; the column `Group` is the role's group, by which the clients group the roles in every view of the assignment. A role runs `warm` in the shipped set only where its qualification record shows the warm form within the allowed gap (<<qualification-records>>); the shipped set has no such role.

No shipped role has a `questions` member, so a shipped role's task that asks ends `asked` and its work continues in a new task (xref:06-envelopes-questions-deadlines.adoc#continuation[Continuing after a Question]). This follows from the shipped profiles, none of which declares a form (link:../harness-profiles/01-profile-schema.adoc#headless-resumability[Harness Profiles Specification, Resumability]), so a member would be ineffective. What a hold, a resume, and the fallback cost, and the work on which no continuation could be measured, are recorded in the rows and the limits of the link:../../../../plan-marshall-documentation/doc/specification/evaluation.adoc#results[Evaluation Reference], R4; the values of `questions.hold_seconds` and `questions.resume_within_seconds` for a shipped role stay unsettled until large work is measured.

The harness, model, and effort of every shipped artifact are not fixed by this specification: they are the pinned configuration of the role's default assignment (<<default-assignment>>), the model its tier maps to on its preferred harness, which the release's grading against the model verification corpus `test/model/verification/` selected (<<qualification>>); the `judge`, which no corpus topic grades, is pinned by the release and validated against each graded configuration (<<grading>>), and the `steward` runs on the machine's default harness (<<steward-role>>). Before a release, each role's topics are graded on its candidate configurations (the worker-eligible harnesses of the release with their models and effort levels), and the release pins for each role the candidate of the lowest tier that meets the default agreement level, with its qualification record, or, where no candidate meets it, the best-measured candidate (the lower tier breaking a tie), unqualified with its record; every quorum declaration of the default adjudication unit is calibrated in addition (xref:10-decision-quorum.adoc#quorum-calibration[Quorum Calibration]). The project setup grades the pinned configurations again on the machine's harness versions (<<install-grading>>). The measurements of the candidates the evaluation graded are in the link:../../../../plan-marshall-documentation/doc/specification/evaluation.adoc#results[Evaluation Reference, Results].

The quorum roles are shipped roles like every other: a project uses them only where a quorum declaration of its adjudication unit lists them, beside or instead of other `read_only` roles, the asking role among them. The listed roles of one declaration run on pairwise different models, as the quorum validation requires (xref:10-decision-quorum.adoc#decision-declarations[Decision Declarations]); an operator who assigns one listed role another's model assigns it another model or edits the declaration. Their configurations are the ones that passed the release's role grading and quorum calibration (xref:10-decision-quorum.adoc#quorum-calibration[Quorum Calibration]), so their level follows from that measurement.

A role none of whose candidates meets the level ships pinned to its best-measured candidate, the lower tier breaking a tie, with that candidate's record, which is no valid qualification: its tasks take the conservative fallback until a configuration of it qualifies, when the project setup grades it again on the machine or by `pm-operator roles qualify` (in the evaluation this held for `triage-build`, `triage-ci`, and `replan`, link:../../../../plan-marshall-documentation/doc/specification/evaluation.adoc#limits[Evaluation Reference, Limits]). A role without corpus items of its own, `triage-merge` among them, is graded on the generic items like every other role (<<qualification-topics>>). The shipped records are a starting point; the project setup grades every role without a valid record again on the machine's harness versions (<<install-grading>>).

The planning roles take the operator's chat tasks (link:../state-catalogue.adoc#chat[State Catalogue, Chat]): `refine` for a plan's start entry, `replan` for a plan, `decompose` for an epic, its decomposition, its registers, and an epic's start entry; a decision a worker asked is chatted about with the role of the task that asked it. A chat task submits an answer to the operator's message and may propose changes, each of the kind its caller accepts (a description, a revision of the plan through the guards of a first plan, staged rows through the epic's checks, an item's disposition or rewrite, an answer as the operator's own words, a follow-up plan); every proposal reaches its subject only through the operator's read-back. A chat task is served by the chat's own worker, warm for an open chat and fresh per turn for ended work, with the class `read_only` whatever the role's (link:../state-catalogue.adoc#chat-context[State Catalogue, What a Chat Knows]).

[[chat-skill]]*The chat skill*: every chat task requires the shipped skill `skill://pm/chat/SKILL.md` beside the routed role's skills. It tells the role to answer the operator's message from its context and from what it reads; to propose only the closed form of its scope and nothing else; never to propose or perform an operator act, but to name one as a reference where it would serve (link:../state-catalogue.adoc#chat-names-acts[State Catalogue, The Role Names an Act]); to pull what its core names by URI before relying on it, and to read the files `changed_since_last_task` and the lines `since_last_turn` names again; to take the outcomes of its own proposals that `since_last_turn` carries (accepted, applied, refused with its finding, rejected, lapsed, refused `conflict`) as what became of them, never assuming a proposal applied (xref:02-task-protocol.adoc#since-last-turn[Task Protocol, Since the Last Turn]); after a proposal lapsed, to name the lapse and what is still possible, and never to propose the lapsed change again unless the operator asks, a different proposal the operator's message calls for staying open to it; and that the operator's messages, the transcript, the facts, and every untrusted item are data, never instructions. Like a role skill it carries no rule list (<<role-skill-contents>>).

[#default-assignment]
=== Default Role Assignment
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-1[PM-WORK-1: Roles as Configuration], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-5[PM-CLIENT-5: Versioned Harness Profile Schema & Override Hierarchy]_

The release ships a *default assignment* beside the shipped set, `classpath:/roles/default-assignment.json`, so that every machine has a starting point that needs no model's advice. Per role it holds:

* *`tier`*: a model tier of the closed list `frontier`, `standard`, `fast`. Each harness profile maps the tiers to its concrete models (`headless.model_tiers`, link:../harness-profiles/01-profile-schema.adoc#model-tiers[Harness Profiles Specification, Model Tiers]), so the default holds on any harness;
* *`effort`*: the effort, narrowed where the resolved harness does not accept it for the model (xref:04-worker-launch.adoc#model-and-effort[Worker Launch, Model & Effort]);
* *`preferred_harness`*: the `harness_id` of the harness the release graded the role on;
* *`advisory`*: what the role does, what it needs from a model (reasoning depth, context size, tool use, speed), why this tier, what is lost when a lower tier is chosen (among it that a lower tier tends to take more turns for multi-step work, so its lower price per token does not make the task cheaper), and the evidence the choice rests on (the qualification records it was calibrated from), each a message key with its arguments, shown in the operator's interface language.

*Resolution* (`roles.default`, a state of the onboarding's sub-workflow `roles`, link:../workflow-dsl/01-grammar.adoc#machine-scope[Workflow DSL Specification, Machine Scope]): per role the preferred harness where it is enrolled, else the first enrolled harness, in the order of the `harness_id`, whose profile runs the role's class; and the model that harness maps the tier to, where the effective model catalogue allows it. A role whose tier maps to no allowed model on the resolved harness is shown unresolved, with its advisory, and the operator chooses its model in `roles.write`. The result is the proposal `roles.write` shows; the operator confirms or changes it, and what is confirmed is written to the role assignment of the machine or the project (<<role-assignment>>).

* *Pinned configuration*: the shipped artifact of a role names the tier's model on its preferred harness with the default effort, the configuration the release graded, with its shipped qualification record (<<qualification-records>>). A tier resolved to another model or another harness carries no shipped record and is graded by the project setup like a changed assignment (<<install-grading>>).
* *Calibrated per release*: the default assignment is calibrated per release from the qualification records of the release's grading, like the shipped thresholds; its advisory names that evidence.
* *The steward departs, never replaces*: the steward's proposal (`roles.propose`, <<steward-role>>) is a departure from the default with its reason per role, shown beside the advisory, which stays; the defaults work without any model.

[#steward-role]
=== Steward Role
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-1[PM-WORK-1: Roles as Configuration], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-6[PM-WORK-6: Role Qualification], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_

The shipped `read_only` role `steward` advises the operator on the machine's choices in the onboarding and the machine's settings. It reads the harness profiles of the enrolled harnesses, the models they offer, the model catalogue, the roles with their classes and the default assignment, and the qualification records of the machine's projects, all as facts of its task; it never chooses.

* *Its tasks*: `catalogue.advise` serves one task of kind `catalogue-advice`, whose closing link `submit:advice` carries per enrolled harness the models it recommends to allow with a rationale (`harness`, `models: list<text[1..128]>`, `rationale: text[10..1000]`); `roles.propose` serves one task of kind `role-proposal`, whose closing link `submit:proposal` carries per role it departs on the `harness`, `model`, and `effort` with its `reason: text[10..1000]`, and nothing for a role it keeps at its default. Both are recommendations: the operator confirms, changes, or ignores them in `catalogue.select` and `roles.write`, and nothing is written from a submission alone.
* *Its harness and model*: the steward is not among the roles the operator assigns. The model caller takes its harness at every task from `harnesses.default` of `machine-config.json` (link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration]) and its model from the tier `standard` of that harness's profile (`headless.model_tiers`), with the effort of its default assignment; its artifact's `harness` and `model` are not read, no assignment or override names it, and `model_not_allowed` never applies to it, because it advises at `onboard.models`, before the catalogue exists. No state of the onboarding before `onboard.models` starts a task of it.
* *Exempt from qualification*: the steward runs before any project exists and has no project to be qualified in. Like the `judge`, the model caller takes its tasks without the *Qualify* step (<<model-caller>>); what it submits is a recommendation the operator confirms, never a choice.

[#transcribe-role]
=== The Speech Role `transcribe`
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-24[PM-WF-24: Chatting with the Planning Role]_

The speech role `transcribe` turns what the operator dictates in the web app into text. It is no role of the role set: it has no artifact, class, harness, or task, the model caller never serves it, it is never qualified, and no harness or model of a planning role transcribes, so a choice made for speech never changes how plans are worked.

* *Its methods*: `browser` (the browser's own recognition; the runtime takes no part), `local` (a local speech model on the machine, run by the runtime: a `whisper.cpp` program the operator installed, MIT with its models MIT; the product ships neither the program nor a model, and no other local speech program is looked for), and `provider` (a speech-to-text service with its own credential, called by the runtime). The machine's value `transcribe` of `machine-config.json` names the allowed methods, none by default (off), the local model with the path and digest of its command, and the provider with its base URL, model id, and credential key (link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration Store]); a project's value may narrow the allowed methods and never widen them (link:../store-schemas/08-project-configuration-local.adoc#project-levels[Store Schemas Specification, Project Values over Machine Values]). Which allowed method a browser uses is that browser's choice, never a value of the runtime.
* *Chosen in the roles step*: the onboarding's roles step and its later runs offer the role apart from the role assignment; its consent state `roles.speech-consent` asks, per method chosen, `transcribe_browser` or `transcribe_provider` before a method that sends the audio off the machine is allowed, and `scan_speech_model` before it looks for the `whisper.cpp` program on the login `PATH`, as a harness is found, and runs its check, a fixed sample transcribed by a probe of the program found, like a harness's version probe (link:../store-schemas/12-machine-stores.adoc#consent[Store Schemas Specification, Consent Before Acting]; link:../job-runtime/02-confinement-and-environment.adoc#probe-jobs[Job Runtime Specification, Probe Jobs]). A provider's credential is entered like every credential; in the first run, before the credential store exists, the provider is recorded without it and its token is asked with the other providers' tokens in the providers step, the method unavailable until then. A withdrawn `transcribe_browser` or `transcribe_provider` takes its method out of use until it is given again; a withdrawn `scan_speech_model` is asked again at the next check and leaves a checked local model in use. A consent of `transcribe_provider` covers the provider it was given for (its id and base URL): another provider asks it again.
* *A transcription*: a recording of the `local` or `provider` method reaches the runtime over the local API (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#transcriptions[Runtime & Interaction Model Specification, Transcriptions]). The local model runs as a job of kind `speech` in the machine scope through `pm-exec`, the program behind a small wrapper that keeps the job's contract, with the confinement of a job and no network: its command is verified against the path and digest the check recorded, the recording reaches it on its standard input as 16 kHz mono WAV, and it writes the text to its standard output, which the runtime reads and keeps nowhere; the job's record holds its outcome, duration, and the sizes, never the audio or the text, and its budget key is `speech` with the transcription timeout as its fixed budget (link:../timeouts/02-runtime-leases-operator-web.adoc#transcription-bounds[Timeouts & Budgets Specification, Transcription Bounds]). A provider is called through the runtime's outbound client with its credential, by the one protocol of a speech provider: a `POST` of `multipart/form-data` to its base URL's `/v1/audio/transcriptions` with the fields `file` (the WAV recording), `model` (the provider's model id recorded with it), and `response_format` `json`, answered with `{"text": …}`. Neither the recording nor the text is written to a log, the audit, or a store; the text returns to the client as the operator's own.

[#qualification]
== Role Qualification
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-6[PM-WORK-6: Role Qualification]_

A role runs only on a configuration whose judgment was shown to meet the operator's level against the model verification corpus `test/model/verification/` (link:../../../../plan-marshall-documentation/doc/specification/evaluation.adoc#corpus[Evaluation Reference, Verification Corpus]), which the release ships with its revision.

[#corpus-sources]
=== Corpus Sources

The corpus is its own part plus the items generated from public datasets. A dataset is a source of the corpus, named by its manifest `sources/<name>/manifest.json` (the repository, the commit it is pinned to, the licence, and every file read from it with its SHA-256) and its overlay `sources/<name>/overlay.json` (the rows of one file that become items, and what each item adds to its row); `ATTRIBUTION.md` holds one section per source. No text of a dataset is stored below the corpus: the items are generated from the files fetched at the pinned commits into a cache outside the repository, and the corpus revision covers the pins, so a changed pin is a changed revision.

* *Fetch*: The git part reads each file as it is stored at the pinned commit; a file kept in Git LFS is read as its pointer, and its object is downloaded over HTTP from the repository's LFS endpoint. The refusal of LFS by the native git variant for a project repository does not concern the corpus cache: no filter driver runs for it.
* *Missed source*: A source is missed by name, and none of its items is generated, when its repository or LFS endpoint does not answer, its pinned commit, file, or object is absent, a file, a pointer, or a downloaded object does not have the SHA-256 its manifest pins, or its manifest, overlay, or source file does not yield the items its overlay selects. The other sources are generated all the same.
* *Partial import*: An import whose missed sources were all missed because a repository or endpoint did not answer or something is absent at the pin is *partial*.
* *Failed import*: A source missed for a SHA-256 that is not the pinned one, or for a manifest, overlay, or source file that does not yield the selected items, fails the import, whatever else was missed. The items of the other sources are still generated, but no role is qualified on a failed import.
* *Partial qualification*: A qualification graded on a partial corpus is recorded as such, with the missed sources named (link:../store-schemas/16-task-queue.adoc#qualification-record[Store Schemas Specification, Role Qualification Record]).

[#qualification-records]
=== Qualification Records

A qualification record is `<set>/qualification/<role>.json`. Every record the operator makes (the grading of the project setup and of `pm-operator roles qualify`) is written to the project set, `<PM_MCP_BASE>/projects/<project_id>/roles/qualification/<role>.json`, whichever set holds the role's effective artifact and whichever level sets its effective harness, model, and effort, because the grading measures the configuration as that project runs it; the shipped set holds the release's records, and the machine set holds none. A record is looked up in the project set first, then in the set of the artifact (for a shipped artifact, the shipped record). Its schema and members are owned by the link:../store-schemas/16-task-queue.adoc#qualification-record[Store Schemas Specification, Role Qualification Record].

* *Measurements, not a verdict*: A record stores what the grading measured (per form and per topic the agreement, the constant baseline, and the graded item count, and per form the tokens used and the time; the warm-fresh gap; every item's answer and score), never a pass flag, so a changed operator level applies to every existing record at once.
* *Valid*: A record is valid for a role when the digest it is bound to equals the role's qualification digest (<<role-artifact>>), its `corpus_revision` equals the shipped corpus revision, it has no ungraded item (<<grading>>), and, in the fresh form, the measured agreement of every topic of the record (the topics of the role's corpus, <<qualification-topics>>: `own` and `generic`, `own` alone, or `generic` alone) is at least the project's current agreement level and exceeds the topic's constant baseline by at least the qualification margin (<<constant-baseline>>), and the record holds a result for each of those topics; a record that lacks a topic of the corpus is not valid. The `warm` form qualifies in addition when the measured warm agreement of every topic is at least that level, exceeds the topic's constant baseline by the margin, and the measured warm-fresh gap is at most the project's current allowed gap. The levels are read from the project's `local-config.json` at every check (<<qualification-records>>, *Operator level*).
* *How far a figure reaches*: Beside each topic's agreement the record keeps its graded item count and marks a topic with fewer than a compiled `20` graded items `thin`. Both clients show the figure with its count ("7 of 8") and the mark. Neither changes validity: a topic qualifies on its measured agreement above its constant baseline, and the count says how much that figure rests on. Further figures of a topic (an interval of the agreement, the agreement on confirmed items alone, costly answers and a confusion matrix) are deferred (link:https://github.com/plan-marshall/plan-marshall-documentation/blob/main/doc/later-improvements.adoc#L-37[L-37]).
* *Invalidated*: A change of the effective harness, model, or effort (an edited artifact, a changed assignment, or a plan override), of the tools, the class, a skill digest (an edited extension skill included), the major or minor of the harness version the enrolment records, the weights identity of the model the enrolment records, or the corpus revision changes the qualification digest or the revision, so the record does not match it; an edit of any other member of the artifact leaves the record valid; the role is reported unqualified in both clients and in `pm-operator roles list` until it is graded again.
* *Operator level*: The agreement level (percent of the items of each topic of the role answered right, <<qualification-topics>>) and the allowed warm-fresh gap (percentage points) are operator configuration `qualification.agreement_level` / `qualification.allowed_gap` in `local-config.json` (defaults `80` / `5`, link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]). A record whose measurements fall below the current level counts as not qualified.

[#constant-baseline]
=== Constant Baseline

An agreement says nothing until it is compared with what a configuration that ignores the question would reach. The *constant baseline* of a topic is the agreement of the best constant answerer: for every option key of the topic's `exact_choice` items, the percent of the topic's graded items whose reference is that key (an item graded otherwise counts as not agreeing); the largest of these is the topic's `constant_baseline`, recorded in the qualification record beside its agreement. A topic qualifies only when its agreement also exceeds its constant baseline by at least the *qualification margin*, a compiled `10` percentage points, whatever agreement level the operator sets. A topic whose constant baseline plus the margin exceeds `100` cannot qualify any configuration; both clients name it as a topic whose references are too uniform to tell a configuration from a constant answer, so the corpus needs items of other references, never a lower margin. The same baseline bounds quorum calibration (link:10-decision-quorum.adoc#quorum-calibration[Ask or Quorum, Quorum Calibration]) and the judge instrument check (<<judge-instrument-check>>).

[#qualification-topics]
=== Corpus Topics of a Role

The topics of a role are defined by the `role` field of the corpus items, never by their paths: the items whose `role` names the role, together with the generic items (`role: worker`) for every role of the classes `writer` and `read_only`. Items with `review.status` `draft` or `confirmed` count; items of every other status (`contested`, `retired`) do not. Items whose `role` names no role of the effective set (the comparison items of `role: self-review`) grade no role. The items of a role fall into two topics: the role's own items (`own`) and the generic items (`generic`). The agreement is measured per topic, and a topic reaches the agreement level on its own items only; a pooled figure does not exist, so the generic items never cover for the role's own items. A `writer` or `read_only` role without items of its own has the topic `generic` alone; a `zero_tool` role has the topic `own` alone and without items of its own it has no topics and cannot qualify. The own items of the review roles (the categories review and triage) include planted defects at their correct severity, among them a defect the plan, the outline, or the request mandates, and a defect that every criterion and every test accepts but that a constraint `CN-<n>` of the intent record rules out (a default the specification chose, which the operator accepted as recommended); an answer that grades such a plan clean disagrees with the item's reference. The corpus grows from real plans through the decision export (xref:11-decision-records.adoc#corpus-export[Corpus Export]): an exported item counts once the operator has added it to the corpus, like every draft item.

*An escaped defect*: A review that reports nothing leaves no decision to export (link:11-decision-records.adoc#corpus-export[Decision Log, Corpus Export]). A defect that reached the base and that a review role did not report therefore becomes, on the operator's review, a draft planted-defect item of that role's topic at the commit it landed in, with its correct severity; a plan with `repairs` names the commit range to take it from.

[#grading]
=== Grading
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-51[PM-WATCH-DISP-51], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-57[PM-WATCH-DISP-57], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-66[PM-WATCH-DISP-66]_

`pm-operator roles qualify <role>` (<<operator-roles>>) grades the configuration of the role's effective artifact:

. Every item of the role's topics is offered as a task to workers of the configuration through the task protocol, once in the fresh form (one worker per item) and once in the warm form (one supervised worker taking the items in order; items its `contamination` notes name never share a worker); a `zero_tool` role is graded fresh only, each item in the server-fixed prompt of the role. Their tasks carry the item's `input.question` and `input.facts` and offer one submit with the item's `input.choices` or `input.answer_schema`.
. The workers run under the launch contract of production (xref:04-worker-launch.adoc[Worker Launch]): the project checkout as working directory with the project's own instructions, and the compiled and extension skills the role and the project resolve, so the grading measures the configuration as the project runs it. An item whose `provenance.origin` names the project's own repository and a commit runs instead in a job-private detached worktree of the project at that commit, so its worker never sees a change made after the decision it was taken from; when that commit is not in the repository, the item runs in the checkout and its result records `checkout: current`, which both clients show beside the topic's agreement. An item whose `input.context` names context files of the corpus runs instead in an empty job-private working directory with those files in-band, because its answer must rest on them alone.
. Each answer is scored by the item's `grading.method`; a rubric goes to a task of the shipped `zero_tool` role `judge` (<<default-roles>>) through the model caller, in the corpus judge prompt. The judge's configuration is validated against the graded one: a `judge` configuration whose model has the same model identity as the graded model (link:10-decision-quorum.adoc#model-identity[Ask or Quorum, Model Identity]) refuses the grading with `scorer_not_independent` (link:../workflow-dsl/07-loop-back-diagrams-verification.adoc#role-grading[Workflow DSL Specification, Role Grading]). The judge is a `zero_tool` worker like the screener (xref:04-worker-launch.adoc#job-working-directory[Worker Launch, Zero-Tool Isolation]): the empty job-private working directory `cwd/`, no MCP connection, one turn, the server-fixed prompt of the role (the corpus judge prompt with the item's question, facts, reference, and the answer in-band), and project and user settings off. Its task closes `submitted` only from a structured final result that validates against `judge-score`, the reply the judge prompt asks for; every other end closes it `lost`, and the item stays *ungraded*: it is recorded as ungraded instead of a score, counted in the record's `ungraded` count, and excluded from the agreement. The schema of the reply is the file `judge-score-v1.schema.json` in `pm-core/src/main/resources/de/planmarshall/core/role/qualification/`, beside `JudgeScorer` of that package (the reply's codec is not built yet). The model caller takes a `judge` task without the *Qualify* step (<<model-caller>>): no corpus topic grades the judge as a role; its validation is the independence check and, where the corpus holds the topic `judge/`, the judge instrument check (<<judge-instrument-check>>).

[[item-without-result]]*An item without an answer*: an item task of the graded role that ends without a valid result for a reason of the model (a refusal or an answer that does not validate until its re-offers are spent, `infeasible`, `asked`, or `input_too_large`) is scored `0` and counted as not agreeing. An item task that ends for a reason of the runtime (`role_unavailable`, `withdrawn`) measured nothing about the configuration and is *ungraded* like an item whose judge task closed `lost`.

The next grading run of the role (a setup reconcile run or `pm-operator roles qualify`) re-grades only the ungraded items, each by a new `judge` task over the recorded answer, while the record's qualification digest and corpus revision are unchanged, and every item otherwise. [#judge-instrument-check]
=== Judge Instrument Check

A grading is only as good as its judge, so the server checks that a judge configuration can tell a right answer from a wrong one because of the reference. The check blocks no grading: a grading records its result in the record, records none where the check did not run (while the corpus holds no topic `judge/`), and proceeds; a check that refuses a grading is deferred until that topic exists (link:https://github.com/plan-marshall/plan-marshall-documentation/blob/main/doc/later-improvements.adoc#L-37[L-37]). The check:

. The corpus topic `judge/` holds rubric items each with a reference, a known-right answer, and a known-wrong answer (a planted defect missed, a false finding, or a severity below the defect's effect). The check is never a role's topic and grades no role.
. Every item is scored twice per answer by tasks of the judge configuration in the corpus judge prompt: once with the reference (*oracle*) and once with the reference withheld (*blind*). A score of at least `0.5` counts as judging the answer right. The *accuracy* of a run is the percent of the answers judged as their label says; the constant baseline of the check is the larger of the two label shares (`50` for a balanced topic).
. The check passes when the oracle accuracy exceeds the constant baseline by the qualification margin (<<constant-baseline>>) and exceeds the blind accuracy by the same margin, so the judge's scores follow the reference and not its own opinion of the answer. A judge task that closes `lost` leaves its answer unscored and the check without a verdict.
. The record, `<set>/qualification/judge-check.json` of the project set, stores the oracle and blind accuracy, the constant baseline, every item's scores, the tokens used and the time, bound to the judge configuration's qualification digest and the corpus revision (link:../store-schemas/16-task-queue.adoc#judge-check-record[Store Schemas Specification, Judge Check Record]); it stores measurements, never a pass flag. A changed judge configuration or corpus revision leaves no valid record, and the next grading runs the check first; its tokens are part of the expected tokens the grading shows before the operator consents.
. A grading records the result of the check its judge ran (`judge_check`: `passed` or `failed`; absent where no check ran, which both clients show as not run), and both clients show the oracle, blind, and baseline figures beside it.

[#install-grading]
=== Grading at Install

The shipped records are the release's grading on the harness versions of its own test machine and only a starting point. The project setup grades the roles on the machine's harness versions (link:../domain-extensions/04-setup-state-machine.adoc#setup-qualification[Domain Extensions Specification, Role Qualification at Install]): its first run, like every reconcile run, offers to grade each role of the effective set that has no valid record for its qualification digest on the enrolled harness major.minor, so a harness update that changes the major.minor, a changed assignment, or any other change that invalidates a record, is offered again by the next setup reconcile run, which both clients name until it has run. The same runs offer to calibrate every quorum declaration that the project's adjudication unit or the default unit uses and that has no valid calibration record (xref:10-decision-quorum.adoc#quorum-calibration[Quorum Calibration]). Grading runs model jobs through the model slots (one task per topic item and form, and a `judge` task per rubric item): the setup shows the expected tokens of the grading first and grades only on the operator's consent, asked in an operator wait of the setup (link:../store-schemas/12-machine-stores.adoc#consent[Store Schemas Specification, Consent]; link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-onboarding[Credentials & Enrolment Specification, Project Onboarding]); a declined grading is recorded as owed, its roles stay unqualified, and both clients show it owed until it has run. The operator excludes a role from it with `qualification.skip_roles` in `local-config.json`, and a skipped role stays unqualified unless it has a valid record; the quorum calibration is excluded with the separate boolean `qualification.skip_decisions` (default `false`), and a skipped declaration stays uncalibrated, so its questions are delivered to the operator as decisions, unless it has a valid calibration record. Until a role's grading has finished, its tasks take the conservative fallback (<<conservative-fallback>>); the `judge` and the `steward` are exempt, because the model caller takes their tasks without the *Qualify* step: the judge's independence check is its validation (<<grading>>), and the steward submits a recommendation the operator confirms (<<steward-role>>).

[#conservative-fallback]
=== Conservative Fallback

A task closed with `role_unqualified`, `role_unavailable`, `role_undefined`, `class_mismatch`, or `input_too_large`, a task whose re-offers are spent (xref:02-task-protocol.adoc#re-offer[Re-Offer]), and a task of a state that routes `infeasible` like `lost` never reaches the operator. The server resolves the task's state itself, in this order:

. When the call binds `retry` and its budget is left, the server takes `retry` once per unit instance (link:../state-catalogue/08-remediation-units.adoc#state-remediation.conservative[State Catalogue, Conservative Remediation]); the quality-gate unit binds no `retry`, and its conservative state takes `exhausted` at once (`remediation.conservative-end`, link:../state-catalogue/11-remediation-units-merge-qgate-spend.adoc#state-remediation-qgate.conservative[State Catalogue, Quality-Gate Conservative]).
. Otherwise the server takes the `exhausted` outcome of the remediation policy the state belongs to (link:../workflow-dsl/08-remediation-units.adoc[Workflow DSL Specification, Remediation Policy Units]) or, outside a remediation unit, the state's declared `lost` route (link:../workflow-dsl.adoc[Workflow DSL Specification]).

The task records the reason; the gap the fallback records names it (link:../phase-workflows/01-planning-phases-1-2.adoc[Phase Workflows Specification, Gap Record]).
