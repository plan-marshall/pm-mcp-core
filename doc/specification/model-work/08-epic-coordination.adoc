== Epic Coordination & Server-Started Plans
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-5[PM-WF-5: Model Work as Role Tasks & Single-Level Leaf Constraint], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-15[PM-WF-15: Epic Creation, Server-Started Plans & Cross-Plan Merge Mutex], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-23[PM-WF-23: Operator Acts on Plans and Epics]_

An epic (`scope = "epic"`) decomposes a multi-plan initiative into workstreams and staged plan specifications, has the operator review that cut, starts its plans when they are launchable (by itself or on the operator's word), tracks cross-plan dependencies, keeps the declared surfaces of its own unordered plans disjoint, reacts to every ended plan, keeps the findings and watches its work surfaces, reconciles landing outcomes, and coordinates shared repository locks. The server drives the epic like a plan: every step that needs judgment is a task of a role, every step that needs the operator is an operator wait (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]), every other step is server logic, and the operator's acts on an epic are operator endpoints of its resource in both clients (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#epic-resource[Runtime & Interaction Model Specification, The Epic as a Resource]). The states of the epic workflow are catalogued in the link:../state-catalogue/06-setup-epic-other.adoc#state-catalogue-epic[State Catalogue, Epic Workflow: `epic`].

[#epic-workflow]
=== Epic Workflow (`epic.pmwf`)
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-38[PM-WATCH-DISP-38], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-39[PM-WATCH-DISP-39], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-50[PM-WATCH-DISP-50], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-54[PM-WATCH-DISP-54]_

The epic workflow is the compiled-only DSL unit `epic.pmwf` (`scope epic`); its states carry the prefix `epic.` and the phase value `epic`, and its terminal states are `epic.archived` (phase value `completed`) and `epic.aborted` (phase value `aborted`). An epic comes into existence only through a start of kind `epic`, an entry the operator opens in either client (link:../state-catalogue/09-bootstrap-and-lessons.adoc#start-from-clients[State Catalogue, Starting from the Clients]): its operator waits gather the epic's sources (a description is one) into the entry's source directory and the title proposed from them, and its creation transaction `start.create-scope` creates the epic scope (the machine store `epics/<epic_id>/`, `status.json`, the ledger directory in the shared epic worktree), writes `epic.json` with the title, the list of sources (kind, reference, digest), and `parallelization_scope`, `auto_start`, and `overlap_max_files` taken from the project's values (`epic.parallelization_scope`, `epic.auto_start`, `epic.overlap_max_files`, link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Operator Local Configuration]), none of them asked at the start, moves the source directory into the ledger as `.marshall/epics/<epic_id>/sources/`, places the epic at its start state `epic.decompose`, and ends the start; an abandoned start leaves no epic. The epic's sources are committed and landed with its ledger, so that another machine that adopts the epic, and every later decomposition, reads them; an external source lies there in its level-1-validated form with its verdict (link:07-untrusted-text-screening.adoc#screen-stored[Screened Once Stored]), and the epic's machine store keeps none. An existing git-tracked ledger without machine scope (`epics/<epic_id>/` absent, for example after a clone) is adopted, never re-created: the start of an epic offers `adopt:<epic_id>` (or routes a requested id that names it directly), and the adoption's `start.create-scope` transaction (outcome `adopted`) creates only the machine scope (`status.json`) from the ledger, the durable truth, which it never rewrites, at `epic.decompose` when the ledger has no queue row, otherwise `epic.next-work`; an unreadable or invalid ledger ends in a failure state with the reason (link:../state-catalogue/09-bootstrap-and-lessons.adoc#state-start-epic.adopt[State Catalogue, `start-epic.adopt`]).

After its creation the epic runs by itself. `epic.decompose` calls the sub-workflow `decomposition`, in which the role `decompose` drafts the workstreams and the staged plan sections from the epic's sources and the operator reviews the draft (<<decomposition-review>>); nothing is committed before the operator agrees. `epic.next-work` starts launchable plans while the epic's automatic mode is on (<<epic-auto>>, <<server-started-plans>>) and routes to the epic's other tasks when their trigger holds; `epic.active` is the watch where the epic rests between epic events, a `composite_job` without a model turn; every ledger write commits through `epic.commit-ledger`, the decomposition's through its own commit state (<<decomposition-review>>); the server lands the ledger itself (<<epic-landing>>). No task ends the epic, and no task archives it: archiving is the operator's act (<<epic-actions>>), which runs `epic.archive-check` and, when it passes, `epic.archive`, which moves the ledger to the archive and sets the epic's archive flag; the move is committed through `epic.commit-ledger`, which while the flag is set stages `.marshall/archived-epics/**` beside `.marshall/epics/**`, and landed through `epic.landing` like every ledger write, and only the landed archive ends the epic in `epic.archived` (`terminal_reason` `completed`); a landing failure takes the landing's own routes, and the next ledger commit or default-branch advance resumes it. The operator's cancel (`terminal_reason` `cancelled`, <<epic-actions>>) takes the same path: in its next transaction, after the epic's open tasks are withdrawn and their workers ended, an engine-owned scope-wide transition under the on-entry rule (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security.adoc[CLI, Coordination & Security Specification]) enters `epic.archive` with the reason, and the landed archive ends the epic in `epic.aborted`; an unreadable ledger keeps its condition with a server retry at the condition retry delay (link:../timeouts/01-job-budgets-and-waits.adoc#server-retry-backoff[Timeouts & Budgets Specification, Server retry backoff]), without a budget, and ends the same way. The release of the project ends the epic otherwise (<<epic-actions>>, *Released*). Excerpt (the landing's git internals are abbreviated):

---
name: Epic
description: Decomposes an initiative into workstreams and plans, has the operator review the cut, starts and follows the plans, and lands its ledger until the operator archives the epic.
type: workflow
modification_date: 2026-10-14
version: 1.0.0
author: plan-marshall
---
workflow epic version 1 format 1
scope epic
start epic.decompose

state epic.decompose
  phase epic
  call decomposition
    done                -> epic.next-work    # agreed by the operator and committed
    held                -> epic.active       # the draft task fell back; held until the next epic event re-enters it

state epic.next-work
  phase epic
  auto epic.next-work            # operator requests first; with automatic on starts launchable plans; while archiving only the archive's outcomes and idle
    decomposition_pending -> epic.decompose
    decompose_requested -> epic.decompose
    review_requested    -> epic.review
    archive_requested   -> epic.archive-check    # epic.review-completion first where no completion review ran since the epic was through
    settings_changed    -> epic.commit-ledger
    rows_ungrounded     -> epic.reground
    rows_stale          -> epic.recut
    message_pending     -> epic.ingest
    landing_unanalyzed  -> epic.analyze-landing
    watch_fired         -> epic.recheck-watches
    ledger_unlanded     -> epic.landing
    through             -> epic.review-completion
    archive_uncommitted -> epic.commit-ledger
    archive_landed      -> epic.archived
    cancel_landed       -> epic.aborted
    idle                -> epic.active

state epic.active
  phase epic
  composite_job epic.await-event   # the watch: settles on the first epic event, no model turn
    inbox_appended      -> epic.next-work
    plan_outcome        -> epic.next-work
    landing_recorded    -> epic.next-work
    base_advanced       -> epic.next-work
    overlap_found       -> epic.next-work
    role_set_changed    -> epic.next-work
    operator_action     -> epic.next-work
    cancelled           -> epic.next-work

state epic.reground
  phase epic
  job llm reground role reground
    submitted           -> epic.commit-ledger
    infeasible          -> epic.active    # the item held
    lost                -> epic.active    # the item held

state epic.recut
  phase epic
  job llm decompose role decompose
    applied             -> epic.commit-ledger    # only re-orders and amendments, every check passing
    review              -> epic.decompose        # adds, drops, or re-scopes a plan: the proposal is the draft's input
    infeasible          -> epic.active           # the item held
    lost                -> epic.active           # the item held

state epic.ingest
  phase epic
  job llm message role coordinate each epic.pending-messages
    submitted           -> epic.commit-ledger
    infeasible          -> epic.active    # the item held
    lost                -> epic.active    # the item held

state epic.analyze-landing
  phase epic
  job llm landing role landing each epic.unanalyzed-landings
    submitted           -> epic.commit-ledger
    infeasible          -> epic.active    # the item held
    lost                -> epic.active    # the item held

state epic.recheck-watches
  phase epic
  job llm watch-recheck role coordinate
    submitted           -> epic.commit-ledger
    infeasible          -> epic.active    # the item held
    lost                -> epic.active    # the item held

state epic.review
  phase epic
  call review                  # the register the operator chose; its dispositions written to the ledger in one write
    done                -> epic.next-work

state epic.review-completion
  phase epic
  job llm completion role coordinate
    continue            -> epic.commit-ledger
    complete            -> epic.commit-ledger    # recorded and reported epic.through; epic.archive-check instead when an archive request is pending
    infeasible          -> epic.active    # the completion review held
    lost                -> epic.active    # the completion review held

state epic.archive-check
  phase epic
  auto epic.check-through    # no plan running or paused, every row shipped or ended, no open finding, ledger landed, completion review done
    through             -> epic.archive
    not_through         -> epic.active    # the operator's archive is answered with what is open

state epic.commit-ledger
  phase epic
  call git.commit_and_push (message_mode=step_or_fallback, push_mode=never)   # while archiving also archived-epics/**
    done                 -> epic.next-work   # result {commit?, pushed, clean, landed}
    stepped_out          -> epic.active      # the ledger write stays uncommitted

state epic.landing
  phase epic
  job epic.land-ledger       # git steps: Epic Landing items 2, 6, 7
    succeeded           -> epic.next-work
    failed              -> epic.next-work
    refused             -> epic.next-work
    cancelled           -> epic.next-work
    timed_out           -> epic.next-work
    killed              -> epic.next-work
    indeterminate       -> epic.next-work

state epic.archive
  phase epic
  auto epic.archive-ledger   # moves the ledger, sets lifecycle terminal and archived_at
    archived            -> epic.commit-ledger

state epic.archived terminal archived success
  phase completed

state epic.aborted terminal aborted failure    # the end of the archive path of a cancel, or the integrity resolution
  phase aborted
----

*Next work*: The `auto` state `epic.next-work` first takes a pending operator request on the epic, in the order received (`decompose_requested`, `review_requested`, `archive_requested`, which runs `epic.review-completion` first where no completion review ran since the epic was through, and `settings_changed`, whose header write `epic.commit-ledger` commits); it then starts, while the epic's `auto_start` is on, every launchable row its admission allows (<<server-started-plans>>, <<epic-auto>>), and, while it is off, reports each row that became launchable since its last run (`epic.launchable`, link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#reports[Runtime & Interaction Model Specification, Reports to the Operator]); it reconciles every shipped row without a landing record (<<server-derived-landing-facts>> item 1), then takes the first outcome that holds, in the order of the excerpt, skipping `held` items: `decomposition_pending` when no decomposition is committed and none is `held`; `rows_ungrounded` when a start candidate (a `staged` row whose prerequisites have shipped) has a specification written or last re-grounded before the current `HEAD`; `rows_stale` when a row is judged `stale`, or the landing analysis judged that staged rows must be re-ordered or re-cut; `message_pending` when the inbox holds a `pending` message; `landing_unanalyzed` when a landing record has no landing analysis; `watch_fired` when a watch's trigger fired (<<findings-watches>>); `ledger_unlanded` when the epic branch holds commits the default branch lacks and the last landing did not fail on the same epic-branch head; `through` when the epic is through (every row shipped or ended, no message pending, every landing analyzed, the ledger landed), `auto_start` is on, and its completion review has not run since; otherwise `idle`. While the archive flag is set it starts and serves nothing and takes only the archive's outcomes: `archive_uncommitted` while the move is not committed, `ledger_unlanded` while it is not landed, then `archive_landed` (or `cancel_landed` for a cancelled epic), and `idle` while none of them holds (a landing that failed on the current epic-branch head waits in `epic.active` for the next ledger commit or default-branch advance). These remaining archive steps (commit, land, archived) are the progress measure of `epic.next-work` while archiving, which bounds the engine-chained cycle through `epic.commit-ledger` (link:../workflow-dsl/04-ast-node-model.adoc#static-verification-rules[Workflow DSL Specification, Rule 11a]). On `idle` the epic rests in the watch `epic.active` (`composite_job epic.await-event`), which settles on the first epic event and re-enters `epic.next-work`: an inbox append (`inbox_appended`, the operator's acts on its plans among them, <<epic-informed>>), a plan outcome of one of its rows (`plan_outcome`), a landing record (`landing_recorded`), an observed advance of the default branch (`base_advanced`), an overlap found between running plans (`overlap_found`, <<epic-auto>>), a change of the effective role set (an artifact edit, a changed role assignment, a new valid qualification record, or a cleared start-failure guard; `role_set_changed`), or an operator act on the epic (`operator_action`: next plan, decompose again, the automatic switch, a changed `overlap_max_files` or `parallelization_scope`, a review, archive, cancel).

*Epic tasks*: Every judgment of the epic is a task of a `read_only` role (xref:01-roles-and-configuration.adoc[Roles & Configuration]), whose entity offers `submit` links with the same checks as the ledger requires; no task writes the ledger directly.

* *`decompose`* (entity `decompose`, multi-submit unit `entity-multi.pmwf`, xref:09-completion-usage-and-spend.adoc#entity-units[Entity Units]): the draft of the sub-workflow `decomposition` (<<decomposition-review>>), and in `epic.recut` the proposal of the changes of staged rows. It offers `submit workstream`, `submit spec_section`, and `submit stage`, each validated and persisted into the draft (in a re-cut, into the proposal) on its own while the entity stays active, and the closing `submit:decompose`, which is refused (`invalid_link_args`, `detail: decomposition_not_ready`) until `epic.decomposition-ready` holds: at least one row is staged in the draft and every staged section parses. Its facts carry the epic's sources from its ledger, the committed rows, and, for a rewrite, the operator's instruction and the draft it rewrites; in a re-cut the `stale` rows, their verdict records, and the landing analyses that affect staged rows; its closing submit is refused while a row it serves is still `stale`, and the return evaluation of `epic.recut` splits the proposal (<<decomposition-review>>, *Applied without the review*). The same role drafts in the review of a register (<<epic-review>>) and answers in the operator's chat about the epic (link:../state-catalogue.adoc#chat[State Catalogue, Chat]).
* *`landing`* (entity `landing-<plan_id>` per landing without analysis): `submit_landing`, the semantic landing analysis and the downstream impact judgment, including whether staged rows must be re-ordered or re-cut after an overlap the landing notes (<<epic-surface-disjointness>> item 5), and the repeatable `submit register_item` (<<findings-watches>>).
* *`reground`* (entity `reground`): one task over every start candidate whose specification predates the current `HEAD`, which submits through `submit:reground` a verdict record per claim and a row verdict per row (<<server-derived-landing-facts>> item 2).
* *`coordinate`*: entity `message-<message_id>` per pending inbox message (multi-submit: `submit ingest` with `kind: enum[transferred|re-scoped|left_alone]` and `note: text[1..2000]?`, the repeatable `submit stage`, `submit spec_section`, `submit mailbox_send`, `submit transfer_offer`, and `submit register_item`, and the closing `submit:message`, which records the message `processed`); one task `watch-recheck` over the watches whose trigger fired, which submits per watch whether it becomes a finding or is closed, with its rationale; and entity `completion` once the epic is through, whose closing `submit:completion` carries `verdict: enum[complete|continue]` (`continue` is refused, `detail: nothing_staged`, unless the entity staged at least one row).

*Fallback of an epic task*: When an epic task takes its conservative fallback (exhausted re-offers, or a role reason: `role_undefined`, `role_unqualified`, `role_unavailable`, or `class_mismatch`, xref:09-completion-usage-and-spend.adoc#job-completion[Task Completion]) or ends `infeasible`, which routes like `lost`, the item it served is marked `held` with the reason (a message, a landing analysis, a stale row, a fired watch, the completion review, the decomposition), shown as a hold of the epic in both clients (link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue, Holds and Their Acts]), and skipped by `epic.next-work` until a change of the effective role set (an artifact edit, a changed assignment, a new valid qualification record, or a cleared start-failure guard) or an operator act on the epic; the task state continues at the watch `epic.active`, whose settling on one of those events re-enters the held item's state through `epic.next-work`. A `held` decomposition leaves the epic without rows until it is re-entered; a `held` re-grounding keeps its rows from starting. Every epic task has its metrics row in the epic's `metrics.json` (xref:09-completion-usage-and-spend.adoc#post-completion-invariants[Post-Completion Integrity Invariants], item 5).

`stage` takes `plan_slug: text[3..64]`, `spec_section: text[1..128]`, `surface_paths: list<text[1..512]>`, `surface_modules: list<text[1..128]>?`, `prerequisites: list<text[1..64]>?`, and `workstream_id: text[2..64]?`: `plan_slug` becomes the new row's `plan_id` (same grammar and phantom-ID checks as a plan's, link:../phase-workflows/01-planning-phases-1-2.adoc#_plan_id_derivation_phantom_id_refusal_guard[Phase Workflows Specification, Plan ID Derivation]), `spec_section` is the anchor of the row's section in `spec.md` (grammar: link:../identifiers/02-registry-stores-to-web.adoc#id-spec-section[Identifier Registry, Epic specification section anchor]), which must exist, `surface_paths` and `surface_modules` form the declared surface, `prerequisites` lists `plan_id` values of rows of the same epic, and `workstream_id` names the row's workstream; the server assigns the display-only `ordinal`. `workstream` (`workstream_id: text[2..64]`, `title: text[3..200]`, `order: int[1..999]`) writes one workstream definition of `epic.json`; `spec_section` (`anchor: text[1..128]`, `text: text[1..65536]`) writes one staged plan section of `spec.md` under `anchor`, which takes the same grammar and is unique within the `spec.md`, whose claim sections are parsed at once (<<server-derived-landing-facts>> item 2) by the link's content validator, which refuses the payload with `invalid_link_args` and names the cause in `detail`: `claim_section_unreadable` for an `unreadable` claim section, `section_too_large` for a section with more than six deliverables (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/04-errors-and-testing.adoc#rejection-reasons[MCP Tools Specification, Closed Rejection Reasons & Failure Classes]). In a decomposition these submits write the draft, never the ledger (<<decomposition-review>>); a `coordinate` task's `stage` and `spec_section` write the ledger under the same checks. The refusals `surface_overlap` and `surface_undeclared` of `stage` are `rejected` representations of the offering task entity (<<epic-surface-disjointness>>). The landing job settles `succeeded` only on the observed `merged` outcome; `ejected`, `closed`, and `timed_out` settle it `failed` and leave worktree and branch unchanged (<<epic-landing>> item 8).

[#decomposition-review]
=== The Decomposition Is Reviewed
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-15[PM-WF-15: Epic Creation, Server-Started Plans & Cross-Plan Merge Mutex], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-20[PM-WF-20: Waiting for the Operator], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-24[PM-WF-24: Chatting with the Planning Role]_

The cut of an initiative into plans shapes all of an epic's work, so the operator sees and shapes it before anything is committed. The compiled-only sub-workflow `decomposition` of the epic (its states `decomposition.<state>`, link:../state-catalogue/06-setup-epic-other.adoc#state-catalogue-epic[State Catalogue, Epic Workflow]) holds the draft, the server's checks, and the review:

. *Draft*: one task of the role `decompose` writes the draft (<<epic-workflow>>, *Epic tasks*): its `stage`, `spec_section`, `workstream`, and, in a re-cut, `drop` and `reorder` submits are persisted into the draft, never into the ledger. A task that falls back holds the decomposition (outcome `held`).
. *Checks*: the server checks the draft as it would check ledger writes: the surface disjointness of every staged row against every other non-terminal row of the epic (<<epic-surface-disjointness>> items 1 and 2), dependencies without a cycle, a workstream for every plan, and the section checks of `spec_section`. A failing check is shown on the draft with its row and cause; it never discards the draft.
. *Review* (`decomposition.review`, an operator wait): both clients show the draft as rows (plan, workstream, surface, prerequisites, section) with the checks' results and, for a later run, each change against the committed row it replaces. The operator keeps, edits (the title, the surface, the prerequisites, the section), drops, or adds plans; chats with the role over the draft through the sub-workflow `chat` (link:../state-catalogue.adoc#chat[State Catalogue, Chat]), whose accepted changes enter the draft through the operator's read-back; has it draft again with an instruction, which serves a new `decompose` task over the draft; or agrees. _Agree_ is offered only while every check passes.
. *Agreed*: the draft's rows, sections, and workstreams (with the epic's sources on the first run) are written to the ledger in one write under the epic lock and committed by the sub-workflow's own commit state (`git.commit_and_push`, staging only `.marshall/epics/**`), the draft cleared; the ledger is landed by `epic.landing` like every ledger write, and the sub-workflow exits `done`.

* *Kept until committed*: the draft and the operator's edits are kept in the epic's machine store, `epics/<epic_id>/decomposition.json` (link:../store-schemas/04-epic-and-change-ledger.adoc#epic-decomposition-draft[Store Schemas Specification, Decomposition Draft]), until the ledger write; leaving the review and a restart of the runtime resume it where it stopped, and while it is open the epic's resource serves the draft (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#epic-resource[Runtime & Interaction Model Specification, The Epic as a Resource]). It is deleted with the ledger write.
* *Runs*: `epic.decompose` calls it for the first decomposition, for the operator's _decompose again_ with its instruction (<<epic-actions>>), and for a re-cut that adds, drops, or re-scopes a plan, with the re-cut's proposal as the draft's input. A later run keeps what shipped, what runs, and what is paused: it changes only staged rows, and shows each change against the row it replaces.
* *Applied without the review*: `epic.recut` serves one task of `decompose` that proposes the changes of the staged rows for a `stale` row or a landing analysis that asked for them; its return evaluation applies a proposal that only re-orders staged rows or amends a staged row's declared surface or prerequisites once the server's checks pass (the staging check, dependencies without a cycle), without the review (outcome `applied`, committed by `epic.commit-ledger`), and reports it (`epic.recut_applied`); a proposal that adds, drops, or re-scopes a plan (a changed section) goes to `epic.decompose` and waits in `decomposition.review` (outcome `review`), whatever the epic's automatic mode.
* *No plan before the first commit*: the epic starts no plan before its first decomposition is committed; while the first review waits, `epic.next-work` serves nothing else that would stage a row, and the epic shows the review as what needs the operator (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#needs-operator[Runtime & Interaction Model Specification, What Needs the Operator], kind `operator_wait`).

[#epic-informed]
=== The Epic Is Told
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-15[PM-WF-15: Epic Creation, Server-Started Plans & Cross-Plan Merge Mutex], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-23[PM-WF-23: Operator Acts on Plans and Epics]_

An epic learns a plan's outcome from the plan's events once the plan ends, and it learns of every operator act on a plan of its own as well:

* *An inbox record per act*: every operator act on a plan whose `origin.epic_id` names a live epic appends, in the act's transaction, one server record to the epic's inbox (link:../store-schemas/04-epic-and-change-ledger.adoc#epic-inbox-record[Store Schemas Specification, Epic Inbox Record]) of the kind `paused`, `started`, `cancelled`, `abandoned`, `revised` (a revision the operator accepted in a chat), or `settings_changed` (a change of the plan's settings, link:../workflow-dsl/09-plan-instance.adoc#plan-overrides[Workflow DSL Specification, Plan Overrides]), with the operator's reason and channel.
* *The row follows the plan*: the queue row's status follows the plan's state: `pausing`, `paused`, and back to `running` on start; `cancelled` for a plan the operator cancelled; `abandoned` for a paused plan the operator abandoned, as for a pull request closed after hand-back and the plan outcome `aborted`. A plan's outcome `released` changes no queue row: the release of the project leaves the epic's ledger untouched and records the outcome in the machine's archive only (link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-release[Credentials & Enrolment Specification, Releasing a Project]).
* *The epic decides*: the epic's `coordinate` task decides on every such record as on every inbox message (`submit ingest`): re-stage the row as a new row, hold the rows that depend on it, leave it, or raise a decision for the operator; the epic never ends a plan itself.
* *A pausing or paused plan keeps its place*: its row counts toward the epic's `parallelization_scope` like a `running` one, so the epic starts no plan in its stead; to stop new starts the operator switches automatic off (<<epic-auto>>).
* The release of the project is no act on one plan: it ends the epic with its plans (<<epic-actions>>), so nothing is left to tell it.

[#epic-actions]
=== An Epic's Actions
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-23[PM-WF-23: Operator Acts on Plans and Epics], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-15[PM-WF-15: Epic Creation, Server-Started Plans & Cross-Plan Merge Mutex]_

The operator acts on an epic in either client through operator endpoints of the epic's resource (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#epic-resource[Runtime & Interaction Model Specification, The Epic as a Resource]), each validated like every operator act, answered with the epic's new state, audited, and re-entering `epic.next-work` as an `operator_action`:

* *Next plan*: has `epic.next-work` start the next launchable row now, in the queue's order, under the same admission tests (prerequisites, surfaces and their overlap, locks, `parallelization_scope`; <<server-started-plans>>); starting it creates its plan. With no launchable row it answers why, per row (`dependency`, `lock`, `scope`, `overlap` with the plan it waits for, `stale`, `held`); with `parallelization_scope` full it offers to raise it by one, a ledger write of the header, landed like every ledger write. It works in both automatic modes.
* *Decompose again*: the operator's instruction (a text) starts the sub-workflow `decomposition` over the staged rows (<<decomposition-review>>).
* *Automatic: on/off* and *overlap*: switch `auto_start`, or change `overlap_max_files` or `parallelization_scope` (<<epic-auto>>).
* *Review*: opens the review of the findings or the watches (<<epic-review>>).
* *Archive*: runs `epic.review-completion` first where it has not run since the epic was through (an epic with automatic off), then the archive check `epic.archive-check`: no plan of the epic running, pausing, or paused, every row shipped or ended, no `open` finding, the ledger landed, and the completion review done; it archives through `epic.archive` only when the check passes, and otherwise answers what is open. Only an `open` finding, one not decided yet, holds the archive; kept findings and the watches go into the archive with the epic, and the check lists them as carried.
* *Cancel*: an operator act of both clients with the operator's reason (`pm-operator abort epic <epic_id> --reason …` is its shell form), with the operator's choice for the epic's plans: cancel them too, each with its own outcome `cancelled` (link:../state-catalogue/04-plan-finalize-terminal.adoc#plan-end[State Catalogue, Cancelling and Abandoning]), or let them run on detached (<<server-started-plans>>, *Children of a Terminal Epic*). The epic ends through its archive path in `epic.aborted` with `terminal_reason` `cancelled`. A hold of the epic offers this cancel beside its own acts; for an integrity pause of the epic the cancel is its resolution _abort_ (link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue, Holds and Their Acts]).

*How an epic ends*: its `terminal_reason` is `completed`, set by the archive; `cancelled`, set by the cancel, the same word as a plan ended while it runs; or `released`, set by the release of the project, which ends the epic and its plans together (each plan `released`). *Released*: the release ends the epic by an engine-owned transition into `epic.aborted` that bypasses `epic.archive`: its open tasks are withdrawn, its machine scope is archived in the project's machine store, and its ledger stays in `.marshall/epics/<epic_id>/` untouched, without a ledger commit or an epic landing, so the release touches no repository (link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-release[Credentials & Enrolment Specification, Releasing a Project]). Every end is told in the epic's events and reported (`epic.ended`).

[#epic-auto]
=== An Epic Runs by Itself
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-15[PM-WF-15: Epic Creation, Server-Started Plans & Cross-Plan Merge Mutex], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-23[PM-WF-23: Operator Acts on Plans and Epics], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-21[PM-WF-21: Reports to the Operator]_

* *The epic's mode*: the epic header carries `auto_start` (boolean), taken at the epic's creation from the project key `epic.auto_start` (machine default `true`) and never asked at the start; the start shows the value in force. The operator switches it at any time with the epic's action _Automatic: on/off_; the switch is a ledger write of the header, landed like every ledger write, told in the epic's events, and an `operator_action` that re-enters `epic.next-work`. `parallelization_scope` stays the upper limit of the epic's running plans, a pausing or paused plan counted as running.
* *On*: whenever a place frees or a row becomes launchable, `epic.next-work` starts every launchable row up to the limit; pausing a plan frees no place (<<epic-informed>>).
* *Off*: `epic.next-work` starts nothing by itself and reports each row that became launchable (`epic.launchable`); the operator's _next plan_ (<<epic-actions>>) starts the next launchable row under the same admission. Every other step of the epic (its tasks, its landings, the reactions below) runs in both modes.
* *Overlap at admission*: a launchable row is admitted beside the running plans of the epic only while its declared surface shares at most `overlap_max_files` files with each running plan's declared surface and with that plan's realized changes (its realized footprint, link:../phase-workflows/03-q-gate-and-execute.adoc#_task_envelope_execution_independent_server_verification[Phase Workflows Specification, Task Envelope Execution]). Over it, the row waits with the reason `overlap` naming that plan, beside `dependency`, `lock`, and `scope`, derived on read like them, until that plan has ended; it is never started in parallel, by the epic or by _next plan_. The staging check between declared surfaces stays as it is (<<epic-surface-disjointness>>).
* *`overlap_max_files`*: the header's value, taken at the epic's creation from the project key `epic.overlap_max_files` (machine default `0`: any common file makes the row wait), bounded by a compiled upper bound; it is no unit declaration, since the epic unit is compiled only. The operator changes the epic's value at any time from the epic's settings, a ledger write of the header, told in the epic's events and re-entering `epic.next-work`.
* *Overlap found while running*: at the re-planning checkpoint after each deliverable's build (link:../phase-workflows/08-dynamic-re-planning.adoc#replan-triggers[Phase Workflows Specification, Triggers & Detection]), the server compares the running plan's realized changes with every other running plan's declared surface and realized changes in the epic; beyond `overlap_max_files` it records the overlap on both queue rows (`overlap_found`: the other plan, the paths, the time; link:../store-schemas/04-epic-and-change-ledger.adoc#epic-queue-row[Store Schemas Specification, Queue Row]), tells the epic in its events, and reports it (`epic.overlap_found`). Neither plan is stopped, since drift never blocks: the plan that lands second meets the base-advanced trigger of re-planning (`PM-WF-17`) where the overlap reaches its threshold `base_overlap_min_files`, otherwise its rebase and `remediation.merge-conflict`. A row that starts to wait for an overlap is reported once (`epic.waits_overlap`).
* *An ended plan*: reaches the epic's inbox (its landing, its merge, and the operator's acts, <<epic-informed>>), and the epic reacts in both modes: for a landed plan it records the landing and runs the landing task's downstream impact judgment, and staged rows it affects are re-ordered or re-cut through `epic.recut`, applied without the review where the re-cut only re-orders or amends rows (<<decomposition-review>>); for a plan that ended without landing (cancelled, abandoned, handed back, aborted) the rows that depend on it are held with that reason and the `coordinate` task raises a decision for the operator. Then `epic.next-work` runs: with automatic on it starts the next launchable rows up to the limit; with it off it reports each row that became launchable, and the epic's view and events show what is launchable now.
* *Through*: the epic is through when every row is shipped or ended. With automatic on it then runs `epic.review-completion` and reports the result (`epic.through`, its detail the completion review); with it off it reports that it is through, and the completion review runs at the operator's _archive_, before the archive check. A completion review with `complete` records the review, never archives: archiving is the operator's act (<<epic-actions>>).

[#findings-watches]
=== An Epic's Findings and Watches
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-15[PM-WF-15: Epic Creation, Server-Started Plans & Cross-Plan Merge Mutex]_

The epic keeps what its work surfaces in two registers of its ledger (<<git-distributed-epic-ledger>>):

* *Findings*: a problem no plan owns yet, to be fixed.
* *Watches*: an observation to check again, with the trigger that checks it: `landing` (the next landing of the epic, or the landing of a named row) or `base_advanced` (the next advance of the default branch, optionally only one that touches named paths).

Each item (link:../store-schemas/04-epic-and-change-ledger.adoc#epic-registers[Store Schemas Specification, Findings and Watches Registers]) has its id (epic-scoped, never reused), its statement, its rules (the paths, modules, or requirements it concerns), its origin (a landing, a plan's message, an observation of a task), when it was opened, the task that opened it, and its state: `open` (not decided yet), `kept` (kept as a finding, or moved to the watches), `dropped` (with the reason), or `promoted` (with the row it became). The epic's tasks add items with the repeatable submit `submit register_item` (`register: enum[findings|watches]`, `statement: text[10..2000]`, `rules: list<text[1..512]>`, `origin`, and for a watch its `trigger`): `epic.analyze-landing` and `coordinate` add them instead of only routing a message. A watch whose trigger fires is re-checked by a task of `coordinate` (`epic.recheck-watches`), which turns it into a finding or closes it. Only the epic's tasks and the review (<<epic-review>>) write the registers, each write a ledger write under the epic lock, committed and landed like every ledger write.

New findings, those `open` since the operator last reviewed the register, are a kind of what needs the operator of the epic (`findings`, link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#needs-operator[Runtime & Interaction Model Specification, What Needs the Operator]), so the operator learns of them in Running Work.

[#epic-review]
=== The Review
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-15[PM-WF-15: Epic Creation, Server-Started Plans & Cross-Plan Merge Mutex], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-24[PM-WF-24: Chatting with the Planning Role]_

The operator decides an epic's items in the compiled-only sub-workflow `review` over one register, the findings or the watches, opened from the epic's view and run by `epic.review`:

* *Proposal per item*: a task of the epic's planning role `decompose` proposes a disposition per `open` item (`keep`, `drop`, `promote`, `move_to_watches`), with its rationale.
* *The operator's dispositions* (`review.item`, an operator wait): per item the operator takes the proposal or chooses `keep`, `drop` (with a reason), `promote`, `edit`, or moves a finding to the watches; _promote_ has the role draft a staged plan for the item (a `stage` and its `spec_section`), and _edit_ has it rewrite the item's statement and rules; _chat_ calls the sub-workflow `chat` with the item or the whole register as its scope (link:../state-catalogue.adoc#chat[State Catalogue, Chat]). Every change a model proposes, a draft, a rewrite, or a chat's proposal, reaches the register only through the operator's read-back (xref:06-envelopes-questions-deadlines.adoc#own-words[Answers in the Operator's Own Words]).
* *One write*: _done_ writes the dispositions to the ledger in one write, committed by the review's own commit state and landed like every ledger write; a promoted item stages its row under the same surface checks as a decomposition (<<epic-surface-disjointness>>), and a promotion whose row fails them stays a disposition the operator corrects before _done_ is offered. Leaving the review keeps what was decided so far in the epic's machine store (`epics/<epic_id>/review.json`) and resumes it where it stopped.

[#server-started-plans]
=== Server-Started Plans
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-22[PM-WATCH-DISP-22], link:../../implementation-watch/credentials-and-enrolment.adoc#PM-WATCH-CLI-1[PM-WATCH-CLI-1], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-53[PM-WATCH-DISP-53], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-59[PM-WATCH-DISP-59]_

A plan is a top-level workflow, never a task: under the single-level leaf constraint (`PM-WF-5`) no worker starts a plan and no plan runs inside a task. The server starts every plan of an epic itself, by `epic.next-work` while the epic's automatic mode is on and on the operator's _next plan_ in both modes (<<epic-auto>>, <<epic-actions>>); a plan runs once it exists, so an epic's plans are never created to wait.

* *Launchable*: A row is launchable when it is `staged`, every prerequisite row (`prerequisites[]`) is in the partition `terminal.shipped` (`merged` or `completed`: the prerequisite's code is on the default branch, so a dependent may start before the prerequisite's post-run steps finish), its row verdict is not `stale`, its specification was last re-grounded at the current `HEAD` (`epic.next-work` serves the re-grounding first), and none of its claim sections is `unreadable` (<<server-derived-landing-facts>> item 2). A `parked` row is never launchable, and a `stale` row becomes launchable again only after its section was re-submitted through `spec_section`. Surface disjointness between declared surfaces is not checked here: it is a modelling invariant checked when a row is staged (<<epic-surface-disjointness>>); the overlap with running plans is checked at admission.
* *Admission*: a launchable row is started in staging order (`ordinal`) while fewer than `parallelization_scope` rows of the epic are `running`, `pausing`, or `paused` (`epic.json`, taken at the epic's creation from the project key `epic.parallelization_scope`, machine default `1`, never asked at the start; raised by the operator through _next plan_ or the epic's settings), and only while its declared surface overlaps no running plan of the epic beyond `overlap_max_files` (<<epic-auto>>). A row that is launchable and not admitted waits with its reason, derived on read: `dependency`, `lock`, `scope`, or `overlap` with the plan it waits for. Starting a plan takes no model slot; the plan's tasks are bounded by the model slots like every task (xref:04-worker-launch.adoc#model-slots[Model Slots & One Writer per Plan]).
* *Start transaction*: The server creates the plan through the `epic_row` source of a start, without an operator wait: it opens a pending entry of kind `plan` with the row's `plan_id` and `from_epic` (the directory `pending/<entry_id>/`, link:../filesystem-layout/03-project-store.adoc#source-directory[Filesystem Layout Specification, The Source Directory]), and runs the start's `epic_row` path, every state of which is server logic. The source unit `source-epic-row` reads the queue row under the epic lock: it must exist in that epic and be launchable, else the start fails (`row_unknown`, `row_not_launchable`, `spec_unreadable`) and the row is marked `held` with the reason. `start.launch` stores the row's staged spec section as the plan's source of kind `epic_row` (`sources/epic-row.md`, its claim sections parsed as in <<server-derived-landing-facts>> item 2), which `origin` names like every source; the plan's `request.md` is composed from it, its `plan_id` is the row's (no slug), and `origin.epic_id` is set. The start's `start.create-scope` commit writes the new plan first, the authoritative store, and then sets the row `running` (with `started_at`) under the epic lock; a plan with `origin.epic_id` whose row is not `running` after a crash between the two writes is reconciled by the project's startup recovery, which sets the row (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/01-core-workflow-tools.adoc[MCP Tools Specification, Core Workflow Tools, Commit in the `start.create-scope` transaction]). The plan then runs like every plan and is reported once (`plan.started`, naming the epic); its decisions are delivered to both clients of the operator (xref:06-envelopes-questions-deadlines.adoc#question-delivery[Delivery to the Operator]).
* *Single Epic Pointer, Fail Loud*: Epic membership of a plan has one carrier, `origin.epic_id`, set only by the start transaction (link:../store-schemas/02-workflow-state-store.adoc[Store Schemas Specification, Workflow State Store]); no tool parameter carries it. Every consumer reads membership only from there. A start of a plan from other sources whose new `plan_id` equals a non-terminal queue row of some epic returns to `start.ready` with the reason `epic_pointer_mismatch`: that row's plan is started only by its epic. A plan with `origin.epic_id` set never skips `default:emit-landing`; an unresolvable epic yields `landing_delivery: pending`, never a dropped step and never a refusal after the merge.
* *Children of a Terminal Epic*: The epic linkage is derived by one resolver, which reads the active and the archived epic root (link:../store-schemas/02-workflow-state-store.adoc#epic-linkage[Store Schemas Specification, Origin and Epic Linkage]). A plan whose `origin.epic_id` names a terminal epic (archived or aborted) resolves to `detached`, which every consumer treats like `not_orchestrated`: its landing is emitted to no inbox, its late findings are seeded as lessons, and its task entities offer no outbox link. The plan runs to its own outcome: an epic the operator cancels with its plans left running leaves them untouched (<<epic-actions>>; link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-abort[CLI, Coordination & Security Specification, Abort]).
* *Staleness in the view*: The epic's view (the epic's resource in both clients, `pm://epic/{epic_id}/ledger`) shows per staged row `regrounded_at_sha` (the commit the row's specification was last re-grounded against, <<server-derived-landing-facts>> item 2) and `main_commits_since` (commits on the default branch since then, with the count of those touching the row's expected surface).

[#epic-surface-disjointness]
=== Staging-Time Surface Disjointness (Epic Modelling Invariant)
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-16[PM-WATCH-DISP-16], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-21[PM-WATCH-DISP-21]_

Disjointness of plan surfaces is an invariant the epic establishes when it cuts its work into plans, not a property the server re-evaluates at runtime. The server enforces it once, when a plan is staged, and only within one epic:

1. *Declared Surface*: Every staged plan declares its expected surface in its queue row (`declared_surface: {paths: [...], modules: [...]}`, <<git-distributed-epic-ledger>>). Paths may be files, directories (prefix-matched) or globs (expanded); every entry must name a git-tracked path or glob inside the workspace, and modules are resolved to their directories through module discovery (the derived fact `module_discovery` of the project's `derived-facts.json`, link:../domain-extensions.adoc[Domain Extensions Specification]). A plan whose surface cannot be declared (an empty surface, an entry under a git-ignored tree such as `.marshall/local/**` or outside the workspace, or an entry that cannot be evaluated) is refused with `surface_undeclared` naming the offending entries. There is no `indeterminate` path: a surface is either declared and comparable, or the staging is refused.
2. *Staging Check*: When a task writes a queue row (staging a plan with its specification, or amending the declared surface or `prerequisites[]` of a `staged` row), the server compares the declared surface under the epic lock against the declared surface of every other non-terminal row of the same epic (every `live` state, `parked` included). An overlap is admitted only when the two rows are ordered through prerequisites: one depends, transitively over `prerequisites[]`, on the other, so it can only start after the other reached `terminal.shipped`. An unordered overlap refuses the write with `surface_overlap`, naming the overlapping plans and paths; the task re-cuts the plans or declares the ordering. The queue row is written only when the check passes.
3. *Start*: Starting a plan compares no declared surfaces, because the invariant already holds for every staged row; its admission compares the row's declared surface with the running plans' declared surfaces and realized changes against `overlap_max_files` (<<epic-auto>>).
4. *Scope*: The check covers one epic. There is no cross-epic comparison and no comparison against plans started without an epic; conflicts with those surface at rebase or merge: a rebase conflict in `sync-baseline` or `finalize.merge-sync` calls the plan's `remediation.merge-conflict` policy, and a pull request the provider refuses to merge ends the plan `handed_back`.
5. *Runtime Drift Is Recorded, Never Blocking*: A running plan of the epic may change files beyond its declared surface inside its worktree; the server records `realized − declared` as unplanned changes with their provenance (link:../phase-workflows/03-q-gate-and-execute.adoc#_task_envelope_execution_independent_server_verification[Phase Workflows Specification, Task Envelope Execution]). When unplanned paths overlap the declared surface of another non-terminal row of the same epic that is not ordered with it, the overlap is noted in the plan's landing record, naming the plans and paths, and the landing analysis handles it; an overlap with another running plan beyond `overlap_max_files` is recorded and reported while both run (<<epic-auto>>, *Overlap found while running*). The overlap never blocks a running plan; a row that would start into it waits at admission. The `landing` task of the landing judges whether the affected staged rows are re-ordered or re-cut, which `epic.recut` applies (<<decomposition-review>>).

[#git-distributed-epic-ledger]
=== Git-Distributed Epic Ledger & Per-File Store Layout
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-13[PM-WATCH-DISP-13], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-14[PM-WATCH-DISP-14], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-15[PM-WATCH-DISP-15], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-16[PM-WATCH-DISP-16], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-30[PM-WATCH-STORE-30], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-37[PM-WATCH-DISP-37], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-54[PM-WATCH-STORE-54]_

To allow epic state to merge cleanly across worktrees and machines via Git without monolithic file conflicts, the daemon persists epic state under `.marshall/epics/<epic_id>/` using a strict per-concern file split:

[cols="2,2,3"]
|===
|Path |Writer Discipline |Contents & Invariants

|`epic.json`
|Daemon only (atomic write-and-rename under epic lock).
|Epic header (link:../store-schemas/04-epic-and-change-ledger.adoc#epic-header[Store Schemas Specification, Epic Header]): `epic_id` (the epic's identity, kept unchanged when the epic is archived to `.marshall/archived-epics/<epic_id>-<YY-MM-DD>/`, link:../filesystem-layout/03-project-store.adoc#archives[Filesystem Layout Specification, Plan & Epic Archives]; the dated suffix and the title are never identities), title, the list of its sources (kind, reference, digest), workstream definitions, the per-epic `parallelization_scope`, `auto_start`, and `overlap_max_files`, the coarse `lifecycle`, the `terminal_reason` once it ended (`completed`, `cancelled`, `released`), and `format_version`. It carries no FSM state: the workflow state (`epic.*`) lives only in the epic's `status.json` in the per-project machine store, so the two files never share a name.

|`queue/<plan_id>.json`
|Daemon only (exclusive create `CREATE_NEW` on addition; row-local read-modify-write on update).
|One file per staged plan (schema: link:../store-schemas/04-epic-and-change-ledger.adoc#epic-queue-row[Store Schemas Specification, Queue Row]), keyed by the child plan's `plan_id` in the canonical plan grammar (link:../identifiers/01-general-rules-and-registry.adoc#id-plan-id[Identifier Registry]; derivation in link:../phase-workflows/01-planning-phases-1-2.adoc#_plan_id_derivation_phantom_id_refusal_guard[Phase Workflows Specification, Plan ID Derivation]), which is allocated and phantom-ID checked when the row is staged. The epic-local ordinal (`PLAN-03`, `PLAN-PR-025B`) is kept only as the display-only field `ordinal`; no link, envelope, resource, or lookup addresses a row by it, and the write side and the read side of every epic↔plan address (plan start, `origin.epic_id`, inbox, landings) use `plan_id`. Each row tracks the closed 16-state plan vocabulary partitioned into `live` (`staged`, `running`, `pausing`, `paused`, `handed_back`, `parked`), `terminal.shipped` (`merged`, `completed`), and `terminal.closed_unshipped` (`abandoned`, `cancelled`, `superseded`, `split`, `retired`, `transferred`, `resolved`, `returned`). A row follows its plan's activity (`pausing`, `paused`, and `running` again, <<epic-informed>>), and its plan outcome maps onto it when it ends or its landing is reconciled: `merged` -> `merged`; `no_change` -> `completed`; `cancelled` -> `cancelled`; `abandoned` and `aborted` -> `abandoned`; `returned` -> `returned` (the work may be staged again as a new row); `released` changes no row (the release leaves the ledger untouched); `handed_back` -> `handed_back`, a live status awaiting a human merge, which the landing reconciliation settles from the observed pull request (merged -> `merged`, closed -> `abandoned`), so a dependant of a handed-back row starts only after its pull request merged. Launchability is derived on a `staged` row (<<server-started-plans>>), never a status. A row the server cannot start, whose task closed `lost` or ended `infeasible`, or that depends on a plan ended without landing, carries `held {reason, at}` until the effective role set changes or the operator acts on the epic; a running row on which an overlap was found carries `overlap_found` (<<epic-auto>>). `parked` is an operator hold: a parked row is never started, but its declared surface still takes part in the staging-time disjointness check (<<epic-surface-disjointness>>). Each row carries `prerequisites[]` (the `plan_id` values of rows of the same epic it depends on; the start waits until all are in `terminal.shipped`) and `declared_surface{paths[], modules[]}` (its expected surface, written only when the staging check passes). The closed-unshipped members mirror `plan-marshall` (`orchestrator.py`, `CLOSED_UNSHIPPED_PLAN_STATUSES`): `superseded` (the work was absorbed by a named successor row), `transferred` (the row moved to another epic's ledger, <<cross-epic-transfer>>), `retired` (withdrawn, no successor carries it), `resolved` (the defect closed with no plan work at all); `abandoned`, `cancelled`, `split`, `returned`, and the live `pausing`, `paused`, and `handed_back` are `PM-MCP` members. A row staged by intake carries `intake{source_epic, source_plan_id, source_location, message_id}`; a row whose work left carries `disposition` (`transferred`, `re-scoped`, or `left_alone`) with the confirming message. Executing child plans **never** write to `queue/` directly.

|`inbox.jsonl`
|Strictly append-only event log (link:../store-schemas/04-epic-and-change-ledger.adoc#epic-inbox-record[Store Schemas Specification, Epic Inbox & Plan Mailbox Records]), appended under the epic lock by the plan-scope outbox link (<<plan-scope-outbox-link>>), by `default:emit-landing`, by the server for every operator act on a plan of the epic (<<epic-informed>>), by the server on entry of a plan's `refine.hypothesis-refuted` (link:../state-catalogue/02-plan-phases-1-3.adoc#state-refine.hypothesis-refuted[State Catalogue, `refine.hypothesis-refuted`]), by other epics (<<cross-epic-transfer>>), and by the owning epic's own claim and processing transitions; no line is ever rewritten.
|Structured cross-scope messages from executing child plans (blocker reports, process findings, landing notifications, the server-appended `hypothesis_refuted` of a plan whose open hypothesis was refuted twice, and the server-appended records of the operator's acts on a plan: `paused`, `started`, `cancelled`, `abandoned`, `revised`, `settings_changed`) and from other epics (`transfer_offer`, `intake_confirmed`); an overlap of a plan's unplanned changes with a sibling's surface arrives with the plan's landing notification (<<epic-surface-disjointness>>). Each `message` event carries a store-assigned, never-reused `message_id` (`msg-NNNN`); `claimed` and `processed` events reference it, and a message's current state (`pending`, `claimed`, `processed`) is the fold of its events. Distinguishes the three empty states (`no_file`, `empty_file`, `all_processed`) from `unreadable` (reported with the failing line), which is never read as empty. Plan-side writes resolve through the epic ledger resolution seam to the shared epic worktree copy, never the primary checkout.

|`landings.jsonl`
|Append-only under epic lock when a landing notification is reconciled.
|Structured landing history records for completed or closed child plans (<<server-derived-landing-facts>>; record schema by reference to the landing envelope: link:../store-schemas/04-epic-and-change-ledger.adoc#landing-record[Store Schemas Specification, Landing Record]). Each landing carries the plan's whole findings ledger as `findings[]`, so the epic never depends on the archived plan directory to read them.

|`spec.md`
|Written only through the `submit` links of the epic's task entities.
|The epic specification: workstream and staged-plan sections, including each staged plan's claim sections and expected surface (the authoritative, checked copy is the queue row's `declared_surface`). Served as `pm://epic/{epic_id}/spec/{section}` (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools.adoc[MCP Tools Specification]).

|`register.jsonl`
|Written under the epic lock by the server, from the submits of the epic's tasks and the dispositions of the review.
|The two registers, findings and watches (<<findings-watches>>; schema: link:../store-schemas/04-epic-and-change-ledger.adoc#epic-registers[Store Schemas Specification, Findings and Watches Registers]). Read whole by the epic's tasks as facts and by the epic's resource; carried into the archive with the epic.

|`sources/`
|Moved in by the epic's creation; never changed.
|The epic's source directory with its manifest `sources.json` (link:../filesystem-layout/03-project-store.adoc#source-directory[Filesystem Layout Specification, The Source Directory]), read by every decomposition on every machine.

|`resume_anchor.md`
|Daemon-rendered markdown artifact.
|Human- and clone-readable queue overview and resumption summary. Regenerated automatically on merge conflict; regeneration refuses with an explicit diagnostic if any `queue/<plan_id>.json` source file is unreadable.
|===

The ledger directory is fully git-tracked. The epic's non-tracked scope state (the FSM `status.json`, `digests.json`, the transaction journal, an open decomposition draft `decomposition.json`, an open review `review.json`, and the transcripts of chats about the epic) is not part of it; it lives in `epics/<epic_id>/` of the per-project machine store (link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]).

[#plan-scope-outbox-link]
==== Plan-Scope Outbox Link (`outbox:send`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-32[PM-WATCH-STORE-32], link:../../../../plan-marshall-documentation/doc/implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-1[PM-WATCH-TOOL-1]_

Every task entity of a plan whose `mcp/status.json` carries `origin.epic_id` and whose epic linkage is not `detached` (<<server-started-plans>>, *Children of a Terminal Epic*) offers `outbox:send` (rel `submit`, form `submit`, free `kind:enum[blocker_report|process_finding|landing_notification],summary:text[1..200],body:text[1..16384]`). The target inbox is derived by the store from `origin.epic_id` and the sending `plan_id`; the caller supplies no path or epic identifier. `landing_notification` is emitted only by `emit-landing`; an overlap of the plan's unplanned changes with a sibling's declared surface is noted in its landing record, never sent as a message (link:../store-schemas/04-epic-and-change-ledger.adoc[Store Schemas Specification, Epic Inbox]). Following the link appends one `message` event, returns its store-assigned `message_id`, and never changes the plan's state or the task's.

*Read Access*: The inbox is served as `pm://epic/{epic_id}/inbox` and the per-message resource `pm://epic/{epic_id}/inbox/{message_id}`. The epic's representation points at every message of its inbox; a plan's representation and its task entities point at the messages the plan sent, with their current delivery state (`pending`, `claimed`, `processed`). The resources carry no per-scope read restriction: every scope of the project may read them, and the project boundary (`PM-SEC-2`) is the access boundary (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/03-resource-uris.adoc#_normative_resource_uri_templates[MCP Tools Specification, Read Access Within the Project]).

[#plan-mailbox]
==== Plan Mailbox (Epic → Plan Channel)
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-26[PM-WATCH-DISP-26]_

The epic → plan direction is a per-plan mailbox `mcp/mailbox.jsonl` in the plan directory, mirroring `plan-marshall`'s addressee mailbox (`plan-orchestrator` `inbox write --target-plan`, `inbox mailbox`). It lives in the plan directory of the per-project machine store, which never moves except on archival, when the mailbox moves with it (link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]), and follows the same strictly append-only event model with store-assigned, never-reused `message_id` values as the epic inbox (link:../store-schemas/04-epic-and-change-ledger.adoc#epic-inbox-record[Store Schemas Specification, Epic Inbox & Plan Mailbox Records]):

* *Write*: A `coordinate` task of the owning epic submits `mailbox_send` (`plan_id`, `kind:enum[advisory|spec_amendment|coordination]`, `summary:text[1..200]`, `body:text[1..16384]`), for a queue row whose child plan exists. Within the epic transaction, which holds the epic lock, the server takes the mailbox's own leaf lock (like the leaf lock of `audit.jsonl`, link:../store-schemas/13-leases-integrity-testing.adoc#lock-free-snapshot-reads[Store Schemas Specification]), reads the last `message_id`, and appends one `message` event, addressed by the child `plan_id` (the queue key); the caller supplies no path, and the plan lock is not taken. Only the epic named in the plan's `origin.epic_id` may write the mailbox.
* *Target Resolution*: A target plan that does not exist (a `staged` row not yet started) or is archived is refused at write time with `target_undeliverable`, and the message is never written elsewhere. For an existing plan the write succeeds and reports the target's liveness (`running`, `not_running`, or `indeterminate` when its `mcp/status.json` is unreadable); `not_running` and `indeterminate` never withhold delivery, because the plan reads its mailbox when it resumes.
* *Read*: A plan reads only its own mailbox: every task entity of the plan whose mailbox holds unconsumed messages carries `facts.mailbox` (`unconsumed_count`), and the resource `pm://plan/{plan_id}/mailbox` (and `…/mailbox/{message_id}`) serves the messages with their consumption and the mailbox's `delivery_state` (`never_delivered`, `delivered_unconsumed`, `consumed`, or `unmeasured`), which is not rendered in `facts` because only unconsumed messages call for an action (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]). Reading is fail-open: an unreadable mailbox renders `facts.mailbox` with `mailbox_state: unreadable` (its `delivery_state` is recorded `unmeasured`) and never blocks the plan. `mailbox_ack:<message_id>`, offered on those task entities, appends a `consumed` event under the same mailbox leaf lock. A reader ignores a torn last line.
* *Advisory Only*: A mailbox message never changes the plan's state, scope, or tasks; a running plan's scope changes only by the operator's acts on it (<<server-derived-landing-facts>> item 2, *Running Rows Are Not Re-Scoped*). Because its content is advisory, the mailbox is not covered by the plan's digest sidecar (`mcp/digests.json`).

[#cross-epic-transfer]
==== Cross-Epic Intake & Transfer

A row moves from one epic to another only as a recorded transfer over the two inboxes; only the owning epic's own tasks ever change its queue rows:

1. *Offer*: A `coordinate` task of the source epic submits `transfer_offer` (`plan_id`, `target_epic:epic_id`, `rationale:text[1..2000]`), which appends a `message` event of kind `transfer_offer` (`source_epic`, `source_plan_id`, `source_location`) to the target epic's inbox under the target epic lock. An offer is not a transfer: the source row stays unchanged.
2. *Intake*: The target epic's `coordinate` task for the `transfer_offer` message stages its own row from the offer, subject to the staging-time surface check (<<epic-surface-disjointness>>); the new row carries `intake{source_epic, source_plan_id, source_location, message_id}`, and the server appends `intake_confirmed` to the source epic's inbox.
3. *Source Disposition*: The source epic's `coordinate` task for the `intake_confirmed` message sets the source row's `disposition` (`transferred`, which moves the row to `terminal.closed_unshipped` status `transferred`; `re-scoped`; or `left_alone`). A source row stays live until its own epic records the disposition, and the epic's view lists pending offers and unanswered confirmations.

[#epic-landing]
=== Epic Landing (`land-ledger`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-15[PM-WF-15: Epic Creation, Server-Started Plans & Cross-Plan Merge Mutex]_

Ledger changes are edited in the shared epic worktree (link:../filesystem-layout/01-repository-workspace.adoc#shared-epic-worktree[Filesystem Layout Specification]) and reach the default branch only through the landing, which `epic.next-work` enters as the state `epic.landing` when the epic branch holds unlanded commits (<<epic-workflow>>):

1. *One Landing for All Epics*: A landing covers every pending change in the shared epic worktree, whatever epic made it, in one pull request from the epic branch. There are never concurrent per-epic landing pull requests.
2. *Repository-Wide Serialization*: The landing holds the repository-wide epics-worktree lock for its git steps; a concurrent landing of another epic waits for the lock or is answered with the open pull request. The landing never joins the per-repository plan merge FIFO or takes the plan merge lease (link:../phase-workflows.adoc[Phase Workflows Specification], Cross-Plan Merge Mutex): its diff is confined to `.marshall/epics/**` and `.marshall/archived-epics/**`, disjoint from every plan surface by construction, so plan merges and epic landings never block each other.
3. *Ledger Paths Only*: The landing stages and commits only `.marshall/epics/**` and `.marshall/archived-epics/**`, even though the worktree holds nothing else; a diff touching any other path refuses the landing.
4. *Pull-Request Reuse & Composition*: A repeated landing reuses the open pull request of the epic branch and never opens a duplicate; title and body are composed from the landing snapshot (epics touched, queue rows changed, landings and inbox records added), never from plan artifacts.
5. *Gate*: Required CI checks only. The plan pre-merge review barrier (link:../phase-workflows.adoc[Two Fail-Closed Barrier Predicates]) does not apply: a ledger-only diff draws no review-bot participation (`.marshall/**` is excluded from review bots), so Predicate 2 could never be satisfied.
6. *Merge Confirmation*: The landing's git steps are the primitives of the plan merge: `git.stage-and-commit` and `git.push` in the epic worktree, `ci.pr-create` (or the reused pull request), and `ci.merge` or, when the derived fact `merge_queue_enforced` holds, `ci.enqueue`, both bound to the expected head SHA (the landing snapshot's commit; a moved head refuses the merge and the landing stops as in item 8). The landing waits for a terminal outcome (`merged`, `ejected`, `closed`, or `timed_out`) and is stamped `landed` only from the provider's observed pull-request state (`ci.pr-observe` or `ci.queue-membership`: `merged`, with the merge commit on the base branch), never from a merge command's return value or exit code. A queue wait is bounded by stall as `finalize.merge-queue-wait` is (link:../phase-workflows/06-finalize-re-entry-and-merge.adoc#_cross_plan_merge_mutex_fifo_admission_queue[Phase Workflows Specification, Cross-Plan Merge Mutex item 5]): observed progress restarts the clock, `timed_out` follows only after no progress for twice the queue's check-response timeout (or the compiled fallback, link:../timeouts/01-job-budgets-and-waits.adoc#merge-queue-wait[Timeouts & Budgets Specification, Merge-Queue Landing Wait]) and is a no-verdict outcome, never a landing verdict.
7. *Post-Merge*: The server never moves the primary checkout: when its default branch is checked out and behind the merged landing, the epic's view carries the fact `primary_checkout_behind` naming `git pull` for the operator to run. The epic branch is resynced by `git.fetch` and a merge commit of the new default branch into it (`git.stage-and-commit` of a non-fast-forward merge) inside the epic worktree, without removing the worktree; ledger writes committed after the landing snapshot stay on the branch. A reset of the epic branch to the default branch, a rebase, and a recreation of the branch are forbidden, because each could discard post-snapshot writes.
8. *Failure*: CI failure, queue ejection, or wait timeout stops the landing and shows it as a hold of the epic (`landing_failed`, link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue, Holds and Their Acts]) in both clients; worktree and branch are left exactly as they were (no reset). The server does not land the same epic-branch head again; the next ledger commit or a default-branch advance resumes the landing.

[#server-derived-landing-facts]
=== Server-Derived Landing Facts, Spec Re-Grounding & Cross-Plan Locks
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-17[PM-WATCH-DISP-17], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-18[PM-WATCH-DISP-18], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-19[PM-WATCH-DISP-19], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-20[PM-WATCH-DISP-20], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-22[PM-WATCH-DISP-22], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-23[PM-WATCH-DISP-23], link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-42[PM-WATCH-GEN-42], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-38[PM-WATCH-PHASE-38], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-15[PM-WATCH-DISP-15]_

[[_server_derived_landing_facts_spec_re_grounding_cross_plan_locks]]
1. *Server-Derived Landing Facts (`n/a` vs. `unknown`)*: When a child plan reaches `completed` and merges, the daemon derives objective landing facts directly from the git commit history, plan audit log, and realized footprint store (commits merged, files changed, tasks completed, loop-back count, test/coverage deltas). Values that do not apply to the plan's profile are recorded as `"n/a"`, while values that could not be read due to missing artifacts are recorded as `"unknown"`—degraded answers are never folded into `"n/a"`. A `landing` task (entity `landing-<plan_id>`) submits only the semantic landing analysis and the downstream impact judgment through `submit_landing`.
** *Landing Shape*: A landing record is the landing envelope that `emit-landing` writes, defined once in link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#_landing_envelope_emit_landing[Phase Workflows Specification, Landing Envelope] (identity and merge facts, figures, step record, review facts, `findings[]`, narrative and amendments, completeness, one landing per `plan_id`, and the non-landing record written when nothing merged); `landings.jsonl` stores it unchanged.
** *Squash-Aware Landing Commit*: The landing commit is located as the base-branch commit whose subject ends with `(#<pr_number>)`; a two-parent merge-commit lookup is never the only tier.
** *Fact States*: Every landing is plan-typed: `"n/a"` is never legal at the pull-request and merge keys and is legal at the deliverable and task keys only for landings of `local_changes` plans (`plan_sources`, whose land lane has no deliverables or tasks) and of `pr` plans (no deliverables; tasks only from a loop-back), and every `"n/a"` names the rule, derived from plan data, that made the fact inapplicable. A fact whose source question no longer applies after the observed event (for example the provider's mergeable state after the pull request merged) is recorded as `"not_applicable_after_merge"`, distinct from both `"n/a"` and `"unknown"`; a genuinely failed read stays `"unknown"` and keeps the landing incomplete. A fact that is `"unknown"` on every landing of an epic is surfaced as a detector defect.
** *No Partial Landing*: A landing without its fact block is refused at write time as an internal write refusal (`landing_facts_missing`, failure class `server_fault`; never a `rejected` reason of a link); it is never persisted partially.
** *Shipped-Without-Landing Reconciliation*: Every epic representation compares the queue rows in `terminal.shipped` with `landings.jsonl`. Rows without a landing record are listed in the epic's view as `unlanded_shipped` (count and `plan_id` values; the count is always stated, zero included), and `epic.next-work` reconciles each itself, deriving the landing facts from the child plan's archived stores and git history. A shipped row is never treated as landed without a landing record.
2. *Specification Corpus Re-Grounding*: Before a start candidate is started, `epic.next-work` enters `epic.reground`, which serves one task of the `read_only` role `reground` over every start candidate whose specification was written or last re-grounded before the current `HEAD` (<<epic-workflow>>); its entity exposes only the `submit:reground` link, so the task never writes the ledger directly. Every persisted re-grounding claim verdict is explicitly labeled `observed` or `hypothesis`, where every `hypothesis` must name the specific repository file or artifact that confirms or refutes it. Per row the job submits a row verdict `current | stale`: `stale` means the section no longer holds against `HEAD` and must be re-written; a row with a `contradicted` claim cannot be `current`. The row verdict is kept in the queue row (`reground_verdict`, with `regrounded_at_sha`); a `stale` row is not started until its section is re-submitted through `spec_section` (`epic.recut`), which clears the verdict.
** *Claim-Section Parse States*: Every claim section of a staged specification (`spec.md`) parses to exactly one of `absent`, `empty`, `unreadable` (a table or prose where a bullet list is expected, or a heading that matches only case-insensitively), or `parsed`. `unreadable` blocks the start of that row (the reason is stated in the epic's view) and never passes vacuously; `absent` and `empty` are reported as distinct states.
** *Verdict Record*: A persisted re-grounding verdict record carries `claim` (section and claim index), `label` (`observed` | `hypothesis`), `verdict` (`corroborated` | `contradicted` | `partially_exercised` | `unverifiable`), `checked_at` (the commit SHA the claim was checked against), `by` (the `queue_task_id` of the task that produced it), `scope_change` (`none` | `rescoped`), `exercised_path` (the components actually tested, for example `reader -> classifier`), and `evidence` (text). `contradicted` is admissible only when `exercised_path` covers every component the claim names; otherwise the verdict is `partially_exercised`.
** *Archived Snapshots Are Not Siblings*: Cross-checks against sibling epics read the active root and the archived root (link:../filesystem-layout/03-project-store.adoc#archives[Filesystem Layout Specification, Plan & Epic Archives]) and identify an epic only by the `epic_id` in its `epic.json`; an archived snapshot whose `epic_id` equals the checking epic's own is never a sibling candidate, and a distinct epic is still enumerated and compared.
** *Running Rows Are Not Re-Scoped*: No epic task offers a spec-editing or re-scoping link for a queue row in `running`; a re-grounding verdict that would re-scope such a row is recorded as pending and applied only after the row reaches a terminal state. Overlapping work waits for the running plan to land.
3. *Fixed Lock Hierarchy & Cross-Plan Coordination Primitives*: All representation and resource reads execute against atomic filesystem snapshots without holding scope locks during long-running script or build jobs, and whenever an operation mutates multiple scopes, short transaction locks are acquired in a strict global order (`workspace` lock -> `plan` lock -> `epic` lock -> `machine` lock), while long-lived claims are leases (link:../store-schemas.adoc[Store Schemas Specification], `PM-IMPL-7`). The server serializes PR merge execution across concurrent plans via a fair per-repo FIFO admission queue and merge lease in `<PM_MCP_BASE>/state/merge-queue.json`, while shared review-bot rate-window claims (e.g., CodeRabbit hourly windows) are leases in `<PM_MCP_BASE>/state/review-bot-windows.json`. Machine-wide build concurrency is bounded by the slot cap in `<PM_MCP_BASE>/machine-config.json` (workers by their own cap, xref:04-worker-launch.adoc#model-slots[Model Slots & One Writer per Plan]), where stale slot reaping (`ProcessHandle.of(pid)`) executes inside the same atomic state transition as new job admission and the FIFO queue never drops a submitted build.
