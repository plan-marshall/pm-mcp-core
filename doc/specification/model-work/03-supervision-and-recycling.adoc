[#host-values]
=== Values per Host and per Role

The supervisor takes its timing from the client profile of the worker's harness (link:../client-profiles/01-profile-schema.adoc[Client Profiles Specification, Worker Block]) and its recycling rules from the role's artifact (xref:01-roles-and-configuration.adoc#role-artifact[Role Artifact Schema]). No value is compiled per role or per harness into the supervisor.

[cols="2,2,3"]
|===
|Value |Source |Use

|Bounded wait, progress frames
|`connection.bounded_wait_seconds`, `connection.progress_resets_timeout`
|How long a `pm_wait` is held, and whether progress frames are sent (xref:02-task-protocol.adoc#pm-wait[`pm_wait`]).

|Acknowledgement deadline, informational
|`worker.ack_deadline_seconds`, `worker.ack_informational`
|<<detection>>

|Silence grace
|`worker.silence_grace_seconds`
|<<detection>>

|Idle wake-ups
|`worker.idle_wakeups`, lowered by the artifact's `recycling.idle_wakeups`
|<<recycling>>

|Token budget, tasks per generation
|The artifact's `recycling.token_budget` and `recycling.tasks_per_generation`
|<<recycling>>
|===

The measured basis of the host values is in the link:../../../../plan-marshall-documentation/doc/specification/evaluation.adoc#parameters[Evaluation Reference, Substantiated Values].

[#detection]
== Detection
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-3[PM-WORK-3: Supervision & Recycling]_

* *Missing answer acknowledgement*: A worker that continues after its question (xref:06-envelopes-questions-deadlines.adoc#continuation[Continuing after a Question]) does not acknowledge the representation that carries the answer within the host's acknowledgement deadline, where the host's acknowledgement is not informational. The acknowledgement tells the server that the worker received the answer and continues; without it a worker that took the answer and then stopped would hold its task until its silence limit.
* *Silence*: A worker that makes no call and holds no bounded wait for longer than the host's silence limit — the bounded wait plus the host's silence grace — is silent. A held wait is an open call and suppresses the signal; the answer re-arms it.
* *Exit*: The supervisor observes the exit of the worker's process itself, never by polling a call. An exit after the first call is a loss whose task is offered again; for a role with a connection, an exit before the first call is a start failure, which the start-failure guard counts (<<start-failure-guard>>) and which is no loss. A `zero_tool` worker has no first call, so its exit is always the exit loss.

A `zero_tool` worker (the screener, the judge) has no MCP connection and makes no call, so none of these signals applies to it: it receives no offer to acknowledge, it is never silent, and it is never counted by the start-failure guard (<<start-failure-guard>>). Its fate is decided by its exit and its worker budget alone (link:../timeouts/01-job-budgets-and-waits.adoc#model-job-budget[Timeouts & Budgets Specification, Worker Budget]): an exit with a structured final result that validates against the result schema of its role (`screen-verdict`, `judge-score`) closes its task `submitted`, every other exit and the expiry of its budget close it `lost` (xref:07-untrusted-text-screening.adoc#screener[Screener]; xref:01-roles-and-configuration.adoc#grading[Grading]).

[#worker-off-track]
== A Worker Off Track
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-7[PM-WORK-7: Worker Activity & Off-Track Signals], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-3[PM-WORK-3: Supervision & Recycling], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-1[PM-WORK-1: Roles as Configuration]_

Detection decides only whether a worker is alive. A worker that is alive and busy but makes no progress (it repeats one call, works for many turns without following a link of its task, spends far more on a plan task than its size predicts, or changes files outside the plan task's footprint) is noticed by the *off-track signals*, which the runtime computes from the worker's activity journal (link:../client-profiles/01-profile-schema.adoc#worker-activity[Client Profiles Specification, What a Worker Does]) and the task's records, never by a model. A signal is not a limit: it never ends a plan, and it never becomes a decision or waits for the operator.

[cols="1,4"]
|===
|Signal |Holds when

|`repeating`
|The worker made the same tool call with the same target `N` times in a row (a `tool_call` entry of the activity: tool name and target). A repeat is not counted when, between the two calls, the target was written (a `file_changed` entry for it), the harness compacted the worker's context (a compaction the profile maps), or the earlier call failed or was rejected: then the repeat has a cause, and the counting starts again.

|`no_progress`
|The worker completed `N` turns (`turn` entries) without following a link of its task (a server entry of the activity: `ack`, a `submit`, `ask`, `consult:<role>`, `yield`, `infeasible`).

|`over_size`
|The tokens spent on the current plan task of an envelope task (the `total_tokens` of its turns since the plan task was yielded) exceed `N` times its `predicted_cost_tokens` (xref:06-envelopes-questions-deadlines.adoc#cost-sizing[Cost Sizing]). Only for envelope tasks.

|`outside_footprint`
|The unplanned changes already recorded for the current plan task of an envelope task (changes inside the worktree beyond its declared footprint, link:../phase-workflows/03-q-gate-and-execute.adoc#_task_envelope_execution_independent_server_verification[Phase Workflows Specification, Task Envelope Execution]) reach `N` files. Only for envelope tasks.
|===

* *Thresholds*: every `N` is a compiled threshold (link:../timeouts/01-job-budgets-and-waits.adoc#off-track-thresholds[Timeouts & Budgets Specification, Off-track signal thresholds]); a role artifact may lower it in its `off_track` member and never raise it (xref:01-roles-and-configuration.adoc#role-artifact[Role Artifact Schema]). The compiled values are set from the activity of real plans once it is recorded.
* *When it is evaluated*: at every activity entry of the worker's current task, in the transaction that appends it; a signal holds at most once per attempt and plan task, so one cause never takes its action twice.
* *What the server does*: per signal the action the role artifact chooses from the closed list below, `show` where the artifact names none. Every action is recorded with the signal, its measured value, and its threshold in the queue task's `signals[]` (link:../store-schemas/16-task-queue.adoc#queue-task-record[Store Schemas Specification, Queue Task Record]) and as a `signal` entry of the activity journal (link:../store-schemas/16-task-queue.adoc#activity-journal[Store Schemas Specification, Activity Journal]).

[cols="1,4"]
|===
|Action |Effect

|`show`
|The task and its plan say so: the plan's process and the task's activity carry the signal, and the overview shows the plan off track (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#overview-resource[Runtime & Interaction Model Specification, Overview Resource]); nothing else changes.

|`nudge`
|The worker's next tool result of `PM-MCP` carries a server note naming the signal and the expected next step of its task protocol, within the worker's own task protocol (link:../hypermedia-format/01-representation-and-link-forms.adoc[Hypermedia Format Specification]); the note never changes the task's links.

|`yield`
|The worker's next call is answered with the end of its attempt: for an envelope task the server takes the envelope's yield as `yield:envelope-M` does, with the `yield_reason` `off_track`, so the remaining plan tasks go to the next envelope task (link:../phase-workflows/03-q-gate-and-execute.adoc#_task_envelope_execution_independent_server_verification[Phase Workflows Specification, Task Envelope Execution]); for any other task it acts as `restart`.

|`restart`
|The worker is ended as in <<ending>>, the attempt ends with `end: off_track`, and its task is offered again as a new attempt within its re-offer budget (xref:02-task-protocol.adoc#re-offer[Re-Offer]).
|===

* *Told, not asked*: a `yield` or a `restart` the server took is a report to the operator of the kind `task.off_track`, whose detail is the task's activity (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#reports[Runtime & Interaction Model Specification, Reports to the Operator]); no signal adds to what needs the operator.
* *Verified by scenarios*: each signal and each action is a scenario of the fixture harness with a scripted output stream (a looping worker, a busy worker without links, a worker far over its size, a worker changing an unplanned file), beside the fault matrix of link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-TEST-4[PM-TEST-4].

A model that watches the activity and judges whether a worker is on track is a later improvement (link:../../../../plan-marshall-documentation/doc/later-improvements.adoc#L-17[Later Improvements, L-17]).

[#start-collisions]
=== Starts of One Harness

A harness that keeps its local state in one per-user store shares it between all its processes: a stalled worker that holds the store's lock makes every other start of the harness fail, and the operator's own sessions of it with them. Such a harness declares a per-worker data home in its client profile, so that no two workers and no worker and the operator's session share that store (`opencode`; link:../job-runtime/02-confinement-and-environment.adoc#worker-data-home[Job Runtime Specification, Per-Worker Data Home]). _Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-60[PM-WATCH-DISP-60]_

[#warm-slots]
== Model Slots & Warm Workers
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-14[PM-WF-14: Task Envelopes, Model Slots & Usage per Task]_

Every worker holds a machine-wide model slot from its spawn to its exit, a warm worker for its whole generation, idle or not; the slot rules and one writer per plan are specified in xref:04-worker-launch.adoc#model-slots[Worker Launch, Model Slots & One Writer per Plan]. The supervisor adds two rules:

* *Idle recycle returns slots*: The idle recycle (<<recycling>>) is what returns the slot of an unused warm worker.
* *Idle yields*: When a task of another role waits for a slot and every slot is held, the supervisor recycles the longest-idle warm worker that holds no lease, so idle warm workers never starve queued work.
