[#model-job-launch]
== Worker Launch
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-5[PM-WF-5: Model Work as Role Tasks & Single-Level Leaf Constraint], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-14[PM-WF-14: Task Envelopes, Model Slots & Usage per Task], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SKILL-4[PM-SKILL-4: Skill Delivery to Workers & State through Representations], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation]_

Every worker of `PM-MCP` is a job of kind `llm` that the server starts itself through the headless command line of an enrolled harness (`claude -p`, `opencode run`), like a build. The model caller reads the effective configuration of the role a task names (xref:01-roles-and-configuration.adoc[Roles & Configuration]) and starts a worker of that role: one per task for a `fresh` role, a supervised worker that takes task after task for a `warm` role (xref:03-supervision-and-recycling.adoc[Supervision & Recycling]). This part specifies how one worker is launched: its launch contract, tool set, connection, working directory, model slot, launch prompt, skill delivery, environment, and budget, and how its output is read while it runs. How a worker receives, acknowledges, and submits tasks is the task protocol (xref:02-task-protocol.adoc[Task Protocol]).

[source,text]
----
pm-mcpd (workflow engine, supervisor)                                  harness CLI (worker)
 task queued for role R (queue_task_id qt-…)
 model caller reads role R:
   harness, model, effort  <- effective values (artifact, assignments, plan override)
   template                <- client profile `headless` block of the harness
   tool set                <- role artifact `tools` (within its class)
   cwd                     <- plan worktree | project checkout | private `cwd/` (zero_tool)
   launch prompt           <- shim + core conduct + task protocol + role skill
                              (+ task skills + contract envelope for a fresh worker)
   mcp config              <- `<PM_MCP_HOME>/bin/pm-mcp serve --job`; job token and generation in its environment
 model slot lease (machine cap, one writer worker per plan)
 pm-exec (process group, confinement, environment) ------------------> claude -p … / opencode run …
                                                                          |
 job-bound connection <---------------- pm_wait / ack / pm_state / pm_do -+ tools of the role
 activity and per-turn usage read from the output stream                  |
 fate: succeeded | failed | timed_out | killed | … <---------------------- + exit
 task outcome evaluated on persisted records (09)
----

A worker is a leaf (`PM-WF-5`): its connection never follows a link that starts a model, so a worker never starts another worker, and the harness tool that starts sub-agents is never in its tool set (<<job-tool-sets>>). A worker that needs another model's judgment consults through the server (xref:05-consultation.adoc[Consultation]).

[#launch-contract]
=== Launch Contract

Implemented by `runtime.launch` (`HeadlessBlock`, `LaunchComposer`, `WorkerStart`), and recorded in the job record
(`worker`, `argv_digest`): the server composes the launch of every worker from server-owned inputs only, and no element
is read from a file the model can write (link:../../../pm-runtime/doc/developer/runtime-launch.adoc[Worker Launch
Developer Guide]; link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job
Record]). A change of the role's effective configuration applies to the next worker generation; a running generation
keeps the contract it was launched with. Remaining: the verify-not-resolve argument-schema validation of the composed
vector, which the worker start path does not run yet.

[#harness-selection]
=== Harness Eligibility & Launch Refusals
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-33[PM-WATCH-DISP-33]_

*Eligibility*: A harness hosts workers only when its client profile's `worker` block declares `eligible: true` (link:../client-profiles/01-profile-schema.adoc[Client Profiles Specification, Worker Block]), which a profile does only after the worker behaviour has been measured on that harness under the target conditions, with every fault of the fault matrix passed (link:../../../../plan-marshall-documentation/doc/specification/evaluation.adoc#limits[Evaluation Reference, Limits]). A role whose effective configuration names an ineligible harness, a model outside the harness's `restricted_models`, a model the effective catalogue does not allow, or a harness that lacks a capability of the role's class is invalid when it is read and counts as undefined (xref:01-roles-and-configuration.adoc[Roles & Configuration]); the launch therefore never meets an unsupported combination of a valid role.

*Capabilities per class*: Every role belongs to one class, and a class needs a fixed set of the capabilities a `headless` block declares:

[cols="1,3,3"]
|===
|Class |Harness tools |Required of the harness (`headless.classes`)

|`writer`
|The harness's file-reading, file-writing and shell tools and its MCP resource-reading tools (`headless.resource_tools`)
|A non-null `writer` entry; its `tool_set` may be `enforced` or `advisory`

|`read_only`
|The harness's file-reading and search tools and its MCP resource-reading tools
|A non-null `read_only` entry; `enforced` gives a read-only tool set, `advisory` leaves the worker every tool of the harness

|`zero_tool`
|None, and no MCP connection (the screener, xref:07-untrusted-text-screening.adoc#screener[Screener]; the judge, xref:01-roles-and-configuration.adoc#grading[Grading])
|A non-null `zero_tool` entry: the harness starts with no tool and no MCP connection
|===

Only the `zero_tool` class depends on the harness restricting the worker; for `writer` and `read_only` an advisory tool set is accepted (link:../client-profiles/01-profile-schema.adoc#role-classes[Client Profiles Specification, Role Classes of a Harness]).

*Harnesses*:

[cols="1,1,4,3"]
|===
|Harness |Eligible |Launch |Notes

|`claude`
|yes
|Inline agent (`--agents '<json>'`, `--agent pm-job`), `--mcp-config` with `--strict-mcp-config`, `--json-schema`, `--no-session-persistence`, `--output-format stream-json`; `zero_tool` with `--tools ""`, `--setting-sources ""`, `--max-turns 1`, `--system-prompt-file`
|Its output stream carries one event per model message, tool call, tool result, and turn.

|`opencode`
|yes, with its per-worker data home
|Inline agent in `OPENCODE_CONFIG_CONTENT` with a local MCP command; `read_only` with every permission denied except the read tools; the result parsed from the final message against the schema, fail-closed; its own data directory per worker (`XDG_DATA_HOME`, with the harness's login file copied in)
|Only the models in `restricted_models` accept a restricted agent; unreliable exit codes (`exit_reliable: false`); a tool-result limit, above which the server delivers a task's input in parts (`tool_result_limit_chars`); a process stopped while a model request is open may never continue after it is resumed, and is then replaced by silence at its silence limit (xref:03-supervision-and-recycling.adoc#detection[Detection]).

|`codex`
|no
|Per-call flags (`agent_mode: flags`)
|Not measured as a worker host.

|`antigravity`
|no, until its fault matrix has passed with confined workers
|Per-call flags, the MCP configuration as the file `.agents/mcp_config.json` in the worker's working directory
|No class is runnable: its MCP configuration is not exclusive, so neither `writer` and `read_only` nor `zero_tool` can be held to their isolation (link:../client-profiles/01-profile-schema.adoc#role-classes[Client Profiles Specification, Role Classes]).

|===

*Harness enrolment*: A harness executable is an enrolled host tool of the machine: the onboarding's `harness.enrol`, for a candidate its scan found (link:../client-profiles/01-profile-schema.adoc#harness-scan[Client Profiles Specification, Harness Scan]) or a harness verified from a draft (link:../client-profiles/01-profile-schema.adoc#unknown-harness[Unknown Harness]), and `pm-operator enrol-harness <client>` record its absolute path, the version its version probe reports, and its SHA-256 digest (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-enrol-harness[CLI, Coordination & Security Specification, Harness Enrolment]; store: link:../store-schemas/11-enrolment-store.adoc#harness-enrolment-store[Store Schemas Specification, Harness Enrolment Store]). Before every launch the runtime verifies it without resolving (link:../job-runtime/01-pipeline-and-subprocesses.adoc#_verify_not_resolve_execution_pipeline[Job Runtime Specification, Verify-Not-Resolve Execution Pipeline]). Because harnesses update themselves, a changed digest is accepted only on the profile's update evidence, checked before the changed file runs, and then only when its version probe reports a version within the profile's `headless.supported_versions`; it is audited and the new digest is recorded (link:../client-profiles/01-profile-schema.adoc#update-evidence[Client Profiles Specification, Update Evidence]). The enrolment records path, version, and digest only: `PM-MCP` never stores or exports a harness's authentication. The harness must already be logged in by its own login (cached under its home); the onboarding checks it with the profile's login probe before the first worker starts (link:../client-profiles/01-profile-schema.adoc#login-probe[Client Profiles Specification, Login Probe]).

*Launch refusals*: Implemented by `HarnessVerifier`, `LaunchRefusal` and `SubprocessJobRunner.refuseWorker`
(link:../../../pm-runtime/doc/developer/runtime-launch.adoc[Worker Launch Developer Guide]): a launch is refused before
spawn, with fate `refused` and a reason, when the harness is not enrolled (`harness_not_enrolled`), its executable changed
without the update evidence of its profile (`harness_update_unverified`), its version lies outside the supported range
(`harness_version_unsupported`), the harness enrolment store `harnesses.json` fails its HMAC check (`harness_tampered`,
audit `security` record `enrolment_tampered`; `pm-operator enrol-harness <client>` shows path, version, and digest and
rewrites the file and its sidecar), the prompt cannot be composed (`prompt_composition_failed`,
<<job-prompt>>), or a verify-not-resolve check fails. Each refusal carries the act that resolves it in both clients.
Remaining: the start-failure guard. For a `zero_tool` role a refusal closes the task `lost` and is not counted
(xref:03-supervision-and-recycling.adoc#detection[Detection]); for every other role it counts as a start failure of the
role on that harness: the supervisor stops starting workers there after the compiled number of consecutive start
failures, reports the reason and the act that resolves it in both clients and the audit log, and the role's waiting tasks
take their conservative fallback (xref:03-supervision-and-recycling.adoc[Supervision & Recycling]). A harness that is not
logged in starts and fails before its first call, which is a start failure by the same rule.

[#model-and-effort]
=== Model & Effort

Implemented by `LaunchComposer` (link:../../../pm-runtime/doc/developer/runtime-launch.adoc[Worker Launch Developer
Guide]): the role's effective `model` and `effort` fill the `{{model}}` and `{{effort}}` slots of the harness's
template; a `null` value fills neither slot; a model tier of the default assignment is rendered into the model the
harness's profile maps it to (`headless.model_tiers`); and an effort the harness does not accept for the model narrows
to the nearest accepted lower value, recorded as `effort_narrowed_from` in the job record. No other configuration names
a model or an effort for a worker, and no agent file is installed per model or per client.

[#agent-composition]
=== Agent Composition per Harness (`agent_mode`)

Implemented by `HeadlessBlock` and `LaunchComposer` (link:../../../pm-runtime/doc/developer/runtime-launch.adoc[Worker
Launch Developer Guide]): the `headless` block declares `agent_mode: inline | flags`, the typed slots `{{prompt_file}}`,
`{{model}}`, `{{effort}}`, `{{mcp_config}}`, `{{result_schema}}`, `{{tools}}`, `{{cwd}}`, and `{{agent}}` (the rendered
inline agent definition), the per-class entries `classes` with their argument templates, the delivery of the MCP
configuration `mcp_config`, the launch environment `env`, and the capabilities; the server fills only the slots a
template declares and drops an element whose slot has no value. The `inline` mode renders a per-worker named agent into
the `{{agent}}` slot; `flags` turns the same slots into per-call flags. The ephemeral flag is withheld for a role that
may resume after a question, and a resumed generation is launched with `headless.resumability.resume.argv` in place of
the start of a new session (the continuation itself is `question-continuation`'s,
link:06-envelopes-questions-deadlines.adoc#continuation[Continuing after a Question]).

[#job-tool-sets]
=== Tool Sets

The tool set of a worker is exactly its role artifact's `tools`: the `PM-MCP` tools and the harness tools by their names on the role's harness, each by exact name, never by a pattern. The class bounds what the artifact may name, which the role set's validation checks (`tool_not_permitted`, xref:01-roles-and-configuration.adoc#role-validation[Roles & Configuration, Validation]): the harness tools of the class (<<harness-selection>>) and these `PM-MCP` tools:

* *`writer`*: `pm_wait`, `pm_state`, `pm_do`, `pm_skill`, `pm_skill_file`, `pm_build`, and `pm_lsp`.
* *`read_only`*: `pm_wait`, `pm_state`, `pm_do`, `pm_skill`, `pm_skill_file`, and `pm_lsp` limited to its read operations: `rename` is refused with `invalid_arguments`. `pm_build` is not in the set.
* *`zero_tool`*: none.

`pm_wait` is the worker's only wait tool (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/01-core-workflow-tools.adoc[MCP Tools Specification, Core Workflow Tools]; semantics xref:02-task-protocol.adoc[Task Protocol]); `pm_state` and `pm_do` reach only the worker's own task entities (<<job-token>>). The set is rendered into `{{tools}}` and enforced a second time by the daemon on the job-bound connection. The harness tools of `writer` and `read_only` include the harness's MCP resource-reading tools (`headless.resource_tools`; an empty list means the harness offers none and its workers read no resources). Never in a tool set: the harness's sub-agent tool (`Agent`, `task`, `spawn_agent`), a tool that asks the user, the web tools, and every operator action or scope-creating link. The harness allowlist is defence in depth; the containment is the daemon's per-request binding.

[#job-token]
=== Job Token, Generation & Connection Binding
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-10[PM-WATCH-DISP-10], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-30[PM-WATCH-DISP-30], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-34[PM-WATCH-DISP-34]_

A worker never receives the runtime token (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#runtime-token[Runtime & Interaction Model Specification, Runtime Token]). It connects back through a capability of its own:

1. *Job token and generation*: Implemented by `JobTokens`, `LaunchComposer` and `JobTokenStore`
(link:../../../pm-runtime/doc/developer/runtime-launch.adoc[Worker Launch Developer Guide]): at spawn the server mints a
random 256-bit job token, stores only its SHA-256 in the job record (`job_token_sha256`), and revokes it with the job's
fate (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#job-token[Runtime
& Interaction Model Specification, Job Token]). The worker's MCP configuration starts the relay `pm-mcp serve --job` by the
absolute path `<PM_MCP_HOME>/bin/pm-mcp` of the running runtime's installation
(link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#installation-layout[CLI,
Coordination & Security Specification, Installation Layout]), never through a `PATH` lookup, because a job's `PATH` holds
only the enrolled tool directories (link:../job-runtime/02-confinement-and-environment.adoc#_job_environment_pm_sec_5[Job
Runtime Specification, Job Environment]) and the relay must be the release of the daemon it connects to;
`PM_MCP_JOB_TOKEN` and `PM_MCP_JOB_ID` are in the relay's environment and the daemon's socket path is a relay argument;
`PM_MCP_JOB_ID` is the worker's `generation_id`. The relay sends both on every request and removes identity and generation
arguments from the tool schemas it passes to the harness
(link:../../../../plan-marshall-documentation/doc/specification/runtime-model/03-relay.adoc[Runtime & Interaction Model
Specification, Relay]), so the model never sees, passes, or invents them.
2. *Per-request binding*: The daemon resolves the job from the token's digest on every request (stateless; no connection state) and enforces: `pm_state` and `pm_do` address only the task entities leased to the worker's generation, else `job_scope_mismatch`; a fenced generation is refused `generation_fenced`; a token of an ended job is refused `job_ended`; `tools/list` and every call are limited to the worker's tool set (<<job-tool-sets>>); `resources/list` and `resources/read` work read-only for every resource of the worker's own project and `skill://pm/…` (the project boundary is the only read boundary, link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/03-resource-uris.adoc[MCP Tools Specification, Resource URIs]); `pm_do` never admits a link that starts a model, and a consultation only through a `consult` link of the task's state (xref:05-consultation.adoc[Consultation]). The first accepted request records `connected_at` in the job record.
3. *A worker's identity*: A worker connection takes its client profile from the job record, which names the harness of its role's effective configuration and the harness version probed at its spawn, and every audit row it causes carries the `job_id`, the role, and the generation.
4. *MCP configuration*: The server delivers the worker's MCP configuration as the profile's `headless.mcp_config` says: rendered into a slot of the launch, or written to the file the harness reads in the worker's working directory. On a harness whose configuration is exclusive only the job relay connects (`--strict-mcp-config`; OpenCode an inline configuration that replaces `mcp`). A harness whose configuration is not exclusive (`antigravity`) would also connect the worker to the MCP servers of the operator's own harness configuration, so it runs no worker class at all: neither `writer` and `read_only`, which require extension isolation, nor `zero_tool` (link:../client-profiles/01-profile-schema.adoc#role-classes[Client Profiles Specification, Role Classes]).

[#job-working-directory]
=== Working Directory, Project Files & Zero-Tool Isolation

Implemented by `LaunchComposer` and the confinement of every job
(link:../../../pm-runtime/doc/developer/runtime-launch.adoc[Worker Launch Developer Guide]; link:../job-runtime/02-confinement-and-environment.adoc[Job Runtime Specification, Confinement and Environment]):

* *`writer` and `read_only` workers*: the process working directory is the plan worktree when the plan has one, else the enrolled project checkout; the confinement of the job grants the harness its declared `headless.writable_paths` and its own data directory and nothing of the runtime base beyond the worker's job-private directory. The harness loads the project's own instructions and skills natively from there and nothing else of its extension mechanisms: the class is runnable only where the profile declares the capability `extension_isolation`, so no plugin, hook, MCP server, endpoint or environment value of a settings file reaches the worker, and no instruction file or skill of the user (link:../client-profiles/01-profile-schema.adoc#user-level-files[Client Profiles Specification, Nothing of the Operator's Own]), and it connects to no MCP server but its job relay.
* *`zero_tool` workers (the screener, the judge)*: run always in the empty `cwd/` subdirectory of their job-private directory, which they can read and never write, with project and user settings off where the harness offers it (`--setting-sources ""`), so no project file and no project skill reaches them; the prompt is the server-fixed prompt of the role only (xref:07-untrusted-text-screening.adoc#screener[Screener]; xref:01-roles-and-configuration.adoc#grading[Grading]).

Remaining: the supervisor's choice of a working directory per warm worker (xref:03-supervision-and-recycling.adoc[Supervision & Recycling]).

[#model-slots]
=== Model Slots & One Writer per Plan
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-31[PM-WATCH-DISP-31]_

* *Machine cap*: Every running worker, warm or fresh, holds a lease of the machine lease store `model-slots.json` beside `build-slots.json` (link:../store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Store Schemas Specification, Machine Lease Stores]), with the cap `model_slots` in `machine-config.json` (link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration]; default and bounds: link:../timeouts/02-runtime-leases-operator-web.adoc#model-slot-lease[Timeouts & Budgets Specification, Model slot lease]). A warm worker holds its slot for its whole generation, idle or not. Admission is FIFO in request order; stale slots are reaped in the admission transaction as build slots are.
* *Queued*: A task waiting for a worker is `queued` (xref:02-task-protocol.adoc[Task Protocol]); a launch waiting for a slot has the job record status `queued`, and the worker's budget starts at spawn, so the time in the slot queue never counts against it (link:../timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets]).
* *One writer per plan*: At most one worker of a `writer` role runs or waits for a slot per plan at a time (serial envelope tasks: they share one worktree, one chain-tail commit, and one module build, xref:06-envelopes-questions-deadlines.adoc#envelope-early-end[Early End of an Envelope Task]); `read_only` and `zero_tool` workers of the plan run beside it within the machine cap.
* *Fan-out*: A `job llm … each …` state (link:../workflow-dsl/02-units-jobs-decisions.adoc#model-job-states[Workflow DSL Specification, Model Job States]) queues one task per element of its server-computed list (architecture enrichment: one task per module; a screening batch above the split bound: one task per part) at once; the slots and the role's `count` bound how many workers serve them.

[#job-prompt]
=== Launch Prompt & Contract Envelope
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-9[PM-WATCH-DISP-9], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-10[PM-WATCH-DISP-10], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-24[PM-WATCH-DISP-24]_

Implemented by `PromptComposer` and `LaunchComposer` (link:../../../pm-runtime/doc/developer/runtime-launch.adoc[Worker Launch
Developer Guide]): the server hands a worker what it needs to start in one prompt file and decides exactly what the worker
knows. The runtime creates `<PM_MCP_BASE>/run/jobs/<job_id>/` (mode `0700`, files `0600`) before the spawn, and it holds
the prompt file, the rendered result schema, the per-call MCP configuration (none for a `zero_tool` worker) and, for a
`zero_tool` worker, the empty working directory `cwd/`; the prompt file's SHA-256 is the job record's `prompt_digest`. The
launch prompt is composed in this order: (1) the shim paragraph (<<shim-paragraph>>); (2) the core conduct skill
`skill://pm/core/SKILL.md`; (3) the task-protocol skill `skill://pm/task-protocol/SKILL.md`; (4) the role skill and the
role's further skills. Items (1) to (4) are byte-identical for every launch of a role on the same skill digests, and
nothing that varies per launch precedes or interleaves them, so a harness's prompt cache can serve the shared part. A
fresh worker's prompt then adds (5) the state's `skill` clauses, the writing skill where the task writes free text, the
project's domain skills and, for an envelope task, the union of its plan tasks' `skills[]`; and (6) the task's contract
envelope. Above the in-band bound the remaining task skills are rendered as their section index with their URIs. A skill
that does not resolve, renders empty or changed its digest fails the launch with `prompt_composition_failed`; no worker
runs with a required skill missing. Project-level instructions and harness-native skills load natively from the working
directory (<<job-working-directory>>), and the project's `PM-MCP` skills are the extension skills of `.marshall/skills/`,
delivered like compiled skills.

Remaining: the job-bound checks of the contract envelope in the relay's per-request binding (<<job-token>>).

[#skill-delivery]
=== Skill Delivery Record & Re-Delivery
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-24[PM-WATCH-DISP-24], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-44[PM-WATCH-DISP-44]_

For every task the server computes the required skill set: core conduct, task protocol, the role's skills, the skills of the task's state, the writing skill when the task writes free text, and the project's domain skills with the extension skills whose `domains` name an active domain of the project, each identified by URI and digest (`PM-SKILL-4`).

The launch-time part is implemented by `PromptComposer` and `FreeTextDerivation`
(link:../../../pm-runtime/doc/developer/runtime-launch.adoc[Worker Launch Developer Guide]): the writing skill is derived
from the schemas of the entity's links, never from the role artifact, and is delivered only where a task writes free text;
the skills of the launch prompt are recorded per generation in the job record's `delivered_skills`. Remaining: the offer
of a warm worker, the re-delivery to a generation whose record holds an older digest, the offer bound, host activation
and the `skills_not_loaded` refusal at submit — all of them the task protocol's
(xref:02-task-protocol.adoc[Task Protocol]).

* *Free text*: A task writes free text when a link of its entity carries a parameter of type `text` (link:../hypermedia-format/02-link-grammar.adoc[Hypermedia Format Specification, Link Grammar]) or a named parameter schema with a `string` field that has neither `enum` nor `pattern` (link:../hypermedia-format/02-link-grammar.adoc#named-parameter-schemas[Named Parameter Schemas]). The server derives this from the schemas of the links when it composes the offer or the launch, never from the role artifact, so no role can leave the writing skill out.
* *Writing skill*: `skill://pm/writing/SKILL.md` (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/02-service-and-skill-tools.adoc#writing-skill[MCP Tools Specification, Writing Vocabulary]) is rendered with the project's effective model language (link:../store-schemas/08-project-configuration-local.adoc#project-levels[Store Schemas Specification, Project Values over Machine Values]). It is the only place a worker is told the language to write in: a changed model language changes the skill's digest, and the skill is delivered again to every generation that received the old digest. Extension skills (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/02-service-and-skill-tools.adoc#skill-extensions[MCP Tools Specification, Skill Extensions]) are read when the launch prompt or the offer is composed and carry the digest of that read; an extension skill that the role artifact or a state's `skill` clause names and that is refused at that read does not resolve, so the launch is refused with `prompt_composition_failed` and no offer is made, and a role that names it is invalid (`skill_unresolved`) and takes the path of an undefined role (xref:01-roles-and-configuration.adoc#role-composition[Composition Check]). A refused domain-bound skill is absent from the catalogue and is not required. The server delivers the set; it never waits for a model to fetch a skill.

* *Delivery record*: The server keeps one delivery record per generation (a worker's `job_id`): per skill its URI, its digest, and the instant of delivery. The launch prompt's in-band skills are recorded at spawn, the in-band skills of an offer with the offer, and every skill the generation loads through `pm_skill` (or, under host activation, through the host's read of the skill resource) at the load, with the digest it was served. A new generation starts with an empty record, so a successor receives everything again; nothing depends on what a predecessor knew. The record is kept with the job record of the worker (link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]).
* *Offer*: An offer to a warm worker carries in-band every required skill whose URI and digest its generation's record lacks, and names the others by URI only, their digests in `_meta` (offer format: link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/01-core-workflow-tools.adoc[MCP Tools Specification, Core Workflow Tools]); the in-band skills are recorded with the offer.
* *Re-delivery*: A skill is delivered again (1) to every new generation and (2) whenever the skill's digest changed (a new release, project configuration, or an edited extension skill), because the record holds the old digest. A compaction of a warm worker's context stays invisible to the server; the shim covers it (<<shim-paragraph>>).
* *Offer bound*: The server never offers a task whose skills missing from the generation's record exceed the compiled prompt in-band bound; such a task goes to a fresh worker of the role, whose launch prompt carries them.
* *Host activation*: When a connection declares the client capability of the MCP Skills Extension (`io.modelcontextprotocol/skills`), the server switches that connection to host activation: offers name the required skills by URI only, their digests in `_meta`, and the host loads them through its own skill path. The client profile records the verified support (`skills_extension`, link:../client-profiles/01-profile-schema.adoc[Client Profiles Specification, Profile Schema]).
* [[skills-loaded-at-submit]]*Loaded before submit*: A submit of a task is accepted only when every skill the task requires is in the generation's delivery record with its current digest. Otherwise the submit is refused `skills_not_loaded` and its `detail` lists the missing `skill://` URIs (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/04-errors-and-testing.adoc#rejection-reasons[MCP Tools Specification, Rejection Reasons]); the task stays executing, the worker loads them, and submits again. A `pm_skill` call that fails with a server fault ends the attempt like every server fault (xref:02-task-protocol.adoc#re-offer[Re-Offer]).
* *Results against the contract*: What the server receives is checked against the link and schema the contract names, whatever the model made of a skill. Whether a model applies a skill is measured (link:../../../../plan-marshall-documentation/doc/specification/evaluation.adoc#results[Evaluation Reference], E13) and qualified per role (xref:01-roles-and-configuration.adoc[Roles & Configuration]), never assumed.

[[shim-paragraph]]*Shim paragraph*: Every launch prompt of a `writer` or `read_only` worker starts with the paragraph that the shim skill of the client bundle carries (link:../../../../plan-marshall-documentation/doc/specification/host-integration/02-bundle-manifest.adoc#shim-skill[Host Integration & Bundle Manifest Specification, Bundle Manifest, Shim Skill]): skills of `plan-marshall` arrive in-band or are named by a `skill://pm/` URI; a named skill is binding and is read through `pm_skill`, sections through their anchors; a skill is never reconstructed from memory; a skill of the same name from elsewhere does not replace it. The paragraph never chooses skills.

[#worker-output]
=== Output Read While the Worker Runs
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-7[PM-WORK-7: Worker Activity & Off-Track Signals], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation]_

The runtime reads a worker's output stream (`headless.output.format` `stream_json` or `jsonl`) line by line while the worker runs, never only after its exit, and never scrapes a terminal or reads the harness's session transcript:

* *Activity*: each line is mapped through the profile's `headless.events` onto the closed activity kinds and appended to the task's activity journal (link:../store-schemas/16-task-queue.adoc#activity-journal[Store Schemas Specification, Activity Journal]; the mapping: link:../client-profiles/01-profile-schema.adoc#worker-activity[Client Profiles Specification, What a Worker Does]); the server adds its own entries for the links the worker follows on its job-bound connection. A harness whose profile declares `headless.events: null` contributes no entries of its own.
* *Usage per turn*: the usage pointers are read from every `turn` line and accounted to the task the worker holds at that turn (xref:09-completion-usage-and-spend.adoc#job-result-schema[Worker Result & Usage Parsing]); the same figures give the supervisor a warm worker's context size (xref:03-supervision-and-recycling.adoc#recycling[Recycling]).
* *Signals*: every appended entry is the evaluation point of the off-track signals of the worker's current task (xref:03-supervision-and-recycling.adoc#worker-off-track[A Worker Off Track]).
* *The job log*: every line stays in the job log as well, which no client reads; after a failed start its last lines are the harness's error text (xref:03-supervision-and-recycling.adoc#start-failure-guard[Start-Failure Guard]).

[#job-environment-and-budget]
=== Environment, Confinement & Budget

A worker is confined like every job of its project (link:../job-runtime/02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Job Runtime Specification, Linux Filesystem Confinement]): no access to `<PM_MCP_BASE>` beyond read access to its own job-private directory (<<job-prompt>>) and, for a harness with a per-worker data home (`headless.data_home`), write access to its own data directory below it, and writes only to the write set of every job and the harness sub-paths its profile declares (`headless.writable_paths`), with network access for the harness's model provider. `headless.writable_paths` lists only what a headless harness must write to run (its login or credential file, caches, the session directory) and never a settings, skill, or command file that the bundle manifest manages (link:../client-profiles/01-profile-schema.adoc#headless-block[Client Profiles Specification, Profile Schema]), so a worker cannot change the host's `PM-MCP` integration. Its environment holds the rows of every job, the harness switches of `headless.env`, and `PM_MCP_JOB_TOKEN` and `PM_MCP_JOB_ID` as the only `PM-MCP` values (link:../job-runtime/02-confinement-and-environment.adoc#_job_environment_pm_sec_5[Job Runtime Specification, Job Environment]); no variable of a host session of the operator reaches it, and no harness authentication variable is captured, stored, or exported by `PM-MCP`. The worker uses the harness's own login, cached under the harness home or, for a harness with a per-worker data home, copied by the runtime into the worker's data directory for the job's lifetime; a copy that a dead runtime left behind is removed by the recovery of its project (link:../job-runtime/02-confinement-and-environment.adoc#worker-data-home[Job Runtime Specification, Per-Worker Data Home]).

Every worker runs under the worker budget of its role, learned per role above the floor of the role artifact's `budget_floor_seconds` (link:../timeouts/01-job-budgets-and-waits.adoc#model-job-budget[Timeouts & Budgets Specification, Worker Budget]): for a fresh worker it runs once, from its spawn to its exit; for a warm worker it runs per task, from the offer to the end of the attempt, so an idle warm worker never runs out of budget (xref:03-supervision-and-recycling.adoc[Supervision & Recycling]). An expiry ends the held attempt with the end `budget`. Budget expiry, the supervisor's end of a worker, and drain end it through the termination protocol of every job (link:../job-runtime/01-pipeline-and-subprocesses.adoc#_process_termination_cancellation_protocol[Job Runtime Specification, Process Termination & Cancellation Protocol]).
