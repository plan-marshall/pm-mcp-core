[#state-catalogue-bootstrap]
== Start of a Plan: `bootstrap-plan`
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-10[PM-WF-10: Phase 1–4 Planning Invariants, Lane Ratchet & Artifact Gates]_

[[start-from-clients]]Every plan is created by a start; there is no creation tool. The operator opens a start in either client of a project with `POST /api/v1/projects/{project_id}/entries` (kind `plan`); the entry is then addressed at the top level by its `entry_id` (`/api/v1/entries/{entry_id}`, its events at `/api/v1/entries/{entry_id}/events`, link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#event-streams[Runtime & Interaction Model Specification, Events per Scope]). The entry is a directory of the project's machine store, `pending/<entry_id>/` with its record `entry.json`, its source directory `sources/`, and the transcript of a chat about it, `chat/` (link:../store-schemas/01-format-and-session-log.adoc#pending-entry-record[Store Schemas Specification, Pending Entry Record]; link:../filesystem-layout/03-project-store.adoc#source-directory[Filesystem Layout Specification, The Source Directory]). `bootstrap-plan.pmwf` (state prefix `start`) is a compiled-only unit run on the entry: one instance per entry, its state kept in the record; its operator waits are served to both clients, the first valid act wins, and no harness, session, or model relays the operator's choices (link:../workflow-dsl/02-units-jobs-decisions.adoc#clients-only[Workflow DSL Specification, All Interaction in the Operator's Clients]). An entry never expires: it has no time limit, is never discarded by time, and stays among the project's open entries, offered to continue in both clients, until it is started, abandoned, or deleted with the release of its project. Nothing exists under `plans/` before `start.create` succeeds, so an abandoned entry leaves no scope; abandoning deletes the entry with its sources and its transcript. A breach of an entry's record (`integrity_breach`) ends only by `accept-edit` or by abandoning the entry.

The start gathers the plan's sources into its source directory: the operator adds them one by one, each through its source unit, which stores it and, for an external one, screens the stored copy (<<state-catalogue-source>>), and removes any of them; the start itself stores a description (`start.store-description`), since it needs nothing gathered. Only the kinds that combine with those already in the list are offered: a pull request or the local changes only with descriptions and documents, never both, and the local changes not while the project's landing in force is `landing.files`, whose reason names the project's setting `landing`. A recipe is no source: choosing one starts a plan whose process is the recipe's own workflow (`recipe`, <<state-catalogue-recipe>>). Once a source is stored and every external one screened, `start.sources` offers a chat about the entry with the role `refine` (link:../state-catalogue.adoc#chat[Chat]); its one change is a description, stored after its read-back, and starting never waits for it. A plan of an epic is started by the epic itself: the server opens its entry with `from_epic` when it starts the epic's row (`epic.next-work`) and runs the start without an operator, from `start.open` through `start.source-epic-row` to `start.launch`.

[[options-when-needed]]*Asked when needed*: The start asks only what the plan starts from, and its title and id, proposed from the sources. The landing is not asked at the start (a project whose landing in force is `landing.files` is not offered the local changes as a source). Every other option of the plan is an operator wait at the state that first needs it, with its proposal, and is not asked at all where the plan's own settings, the project, or the machine set it (link:../workflow-dsl/09-plan-instance.adoc#plan-axes[Workflow DSL Specification, Plan Behaviour Axes]): the posture where the plan's lane is chosen and the base branch before the plan's base stamp, in `init.options` (xref:02-plan-phases-1-3.adoc#state-init.options[`init.options`]); the outline review where the outline is ready, by the plan's asking variant (xref:02-plan-phases-1-3.adoc#state-outline.gate[`outline.gate`]). A value the operator sets in the plan's settings before it is asked is the same plan value (composition event `override`). An epic's `parallelization_scope` is never asked: a new epic takes the project's `epic.parallelization_scope` (machine default `1`), and the operator raises it through the epic's _next plan_, which offers to raise it by one when the scope is full, or in the project's settings; a raise of an epic is a ledger write of its header (link:../model-work/08-epic-coordination.adoc#epic-actions[Model Work Specification, An Epic's Actions]). An epic's automatic mode and `overlap_max_files` are taken from the project likewise and shown, never asked.

*Creation*: `start.create` writes outside the entry, so it never claims one transaction over several stores: each write is journaled in its own store (link:../store-schemas/01-format-and-session-log.adoc#transaction-journal[Store Schemas Specification, Transaction Journal, Writes outside the scope]) in a fixed order: the new plan scope first, the authoritative write, into which the entry's source directory moves (`plans/<plan_id>/sources/`) together with the transcript of a chat about the entry (`plans/<plan_id>/chat/`, after a chat still open was ended, its transcript complete; no source and read by no model of the plan); then the epic queue row (`running`, `started_at`) of a plan of an epic; then the lesson claim of a plan from a lesson; and last the deletion of the entry. A crash between the writes is completed by the startup recovery from the existing plans: a plan with `origin.epic_id` whose row is not `running` sets it, a plan created from a lesson whose lesson is unclaimed claims it, and an entry whose plan exists is deleted (link:../runtime-lifecycle/01-startup-recovery-drain.adoc#per-project-recovery[Runtime & Interaction Model Specification, Per-Project Recovery]). `origin` of the plan's `mcp/status.json` names the sources by their ids in the manifest, and `request.md` composes its original input from the descriptions and a reference to each other source.

[#state-catalogue-source]
=== Source Units

A source unit (`scope subworkflow`, compiled only) gathers, stores, and checks one source of a start before any scope exists; its exit contract is `done {source record | none}` (`none`: nothing added, for example a retired lesson) or `stepped_out` (the operator's _remove_, the implicit `step_out` of its operator waits; for `source-epic-row`, which the server runs without an operator, the server step-out of `source-epic-row.refused`). The server gathers every source; a model works with a source only once it is stored, and an external one only once it is screened. *One order for every external source* (an issue, a pull request): a bounded job fetches it, the deterministic level-1 validator cleans its text (every change reported), it is stored in the source directory marked untrusted and unscreened, and then the screener reads the stored copy, one `batch-v1` batch built from the stored files per firing; the verdict is written into the manifest (link:../model-work/07-untrusted-text-screening.adoc#screen-stored[Model Work Specification, Screened Once Stored]). The screening fails closed: a screener that fails, or a role `screener` without a qualified configuration, leaves the source unscreened with the cause, and no model reads it until it is screened again or the operator accepts it explicitly as untrusted, recorded with its reason like an accepted flagged source. What is on this machine (the operator's description, documents the operator chose, a lesson, the local changes, an epic's row) is trusted and never screened (link:../model-work/07-untrusted-text-screening.adoc#local-trusted[Model Work Specification, What Is on This Machine Is Trusted]). A source is never changed once stored. A new way to start is one more source unit and one more link of `start.sources`.

[[documents-source]]*Documents* (`source-documents`, source kind `documents`): the operator picks files or a directory of the checkout or of the operator's home directory, the checkout's files first: the web app through a listing of the server confined to those two roots, the terminal client by paths resolved against its working directory. The listing, a move, and the choice of documents outside the checkout are accepted only from the terminal client and from a browser on the loopback listener, never from a device on the network. The server checks each (a regular file, readable, within the compiled bounds of size and count, no link followed out of a chosen directory; refusals `not_found`, `not_readable`, `too_large`, `outside_allowed`) and copies or moves them into `sources/documents/<n>/`, a directory with its tree, recording each with where it came from, its size, and its digest. Copy or move follows the machine key `sources.documents_mode` (`copy`, `move`, or `ask`, by default `ask`; link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration Store]); with `ask` the choice is an operator wait with _copy_ preselected, whose _always_ stores the answer as the machine's value. A copy is not managed: nothing keeps it and its original in step. A move deletes a file outside git where it was and removes a file git tracks from git by the short landing `git.land-removal`, started once the source is stored and running on while the work starts (xref:18-plan-unit-axes-short-landings.adoc#state-catalogue-short-landings[Short Landings]); a move is the only deletion of the operator's files the runtime makes, and only on the operator's choice.

[[issues]]*Issues by number or URL* (`source-issue`, source kind `issue`): the operator names a number (the project's own repository) or a URL; the server resolves the forge (GitHub, GitLab, or a Forgejo forge such as Codeberg), the repository, the provider, and the credential from it, and a number becomes the issue's URL in the project's repository before anything is fetched. The URL is the issue's reference in the manifest, in `origin`, and wherever the issue is named later; the same holds for a pull request. Another repository is read only under the operator's grant, once or for the project, recorded like the cross-repository reads (link:../credentials-and-enrolment/01-provider-credentials.adoc#cross-repository-reads[CLI, Coordination & Security Specification, Cross-Repository Reads]), with the credential of that forge, or without one for a public issue. The fetch is a bounded `ci.issue-view` of the forge's provider: title and body as text through the guard, labels, milestone, assignees, state, and URL as structured fields in `issue.json`, never as text for a model to follow; links to the issue's own forge keep their targets, because the level-1 allowlist gains the origin of the source's forge. A fetch the forge refuses for its rate limit fails with the cause `rate_limited` and the time the limit resets (`resets_at`); it is not retried by itself. Writing back (`ci.issue-comment`: the clarified request after Phase 2, the approved outline after Phase 3) goes only to an issue of the project's own repository and only where the team key `issues.write_back` enables it (link:../store-schemas/07-project-configuration.adoc#project-configuration-store[Store Schemas Specification, Project Configuration]).

[#state-catalogue-bootstrap-epic]
== Start of an Epic: `bootstrap-epic`
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-15[PM-WF-15: Epic Creation, Server-Started Plans & Cross-Plan Merge Mutex]_
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-38[PM-WATCH-DISP-38]_

The operator opens the start of an epic in either client with `POST /api/v1/projects/{project_id}/entries` (kind `epic`), addressed like a plan's start. `bootstrap-epic.pmwf` (state prefix `start-epic`) is compiled only and runs like `bootstrap-plan` (<<start-from-clients>>): it gathers the epic's sources (descriptions, documents, issues, through the same source units), offers a chat about the entry with the role `decompose`, and proposes the epic's title and id from the sources. Its creation writes in a fixed order: first the ledger, the durable truth (the ledger directory `.marshall/epics/<epic_id>/` in the shared epic worktree with `epic.json`: title, `parallelization_scope`, `auto_start`, and `overlap_max_files` taken from the project's values, the list of its sources with kind, reference, and digest, and the lifecycle), into which the entry's source directory moves (`.marshall/epics/<epic_id>/sources/`, an external source in its level-1-validated form with its verdict); then the machine store `epics/<epic_id>/` with `status.json` at `epic.decompose` and the transcript of a chat about the entry (`epics/<epic_id>/chat/`, never in the ledger); and last the deletion of the entry. The epic's first ledger commit (`decomposition.commit`) commits the ledger and its sources, and `epic.landing` lands them, so that every machine that adopts the epic and every later decomposition reads them. A crash after the ledger write leaves a ledger without machine scope, which the start adopts. An epic whose git-tracked ledger exists (`.marshall/epics/<epic_id>/` with `epic.json`, read through the Epic Ledger Resolution Seam, link:../filesystem-layout/01-repository-workspace.adoc#shared-epic-worktree[Filesystem Layout Specification, Shared Epic Worktree]) but has no machine scope (for example after a clone on another machine) is offered for adoption instead of a new epic: the ledger is the durable truth, and the adoption creates only the machine scope from it and never rewrites it.
