[#state-catalogue-onboarding]
== Machine Onboarding: `onboard` (machine)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-26[PM-WF-26: Machine Onboarding & the Machine Scope]_

Declared in `onboarding.pmwf` (`scope machine`, compiled only, frontmatter type `system` without entries and exits), the unit of the machine's one scope, whose state is `<PM_MCP_BASE>/machine/mcp/status.json` (link:../workflow-dsl/01-grammar.adoc#machine-scope[Workflow DSL Specification, Machine Scope]); phase value `machine`. Like the project's workspace unit it is resident: it has no terminal state and rests in `onboard.completed`, which every state reaches and to which every state reached from it returns. Each aspect of the machine (the languages, the harnesses, the model catalogue, the role assignment, the credential store, the providers, the plan defaults) is a compiled sub-workflow, called in the first run with `onboard_run: first_run` and called again alone from `settings.choose` with `onboard_run: reconfigure` and its current values as the proposal; the first run and a later change are one process (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-1[UC-ONB-1]). Every choice is an operator wait served to both clients, the first act winning; a change of a recorded value carries the revision it was made against and is refused with `conflict` against a newer one (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#two-channels[CLI, Coordination & Security Specification, Operator Choices in the Web App and the Terminal]). Every action that looks at the machine or acts on it is preceded by a consent state of its kind (link:../store-schemas/12-machine-stores.adoc#consent[Store Schemas Specification, Consent Before Acting]); an act of the operator's own, such as a typed credential, needs none. No state before `onboard.models` starts a role task, since no harness is enrolled before it; a role task of the machine scope runs on an enrolled harness like any worker task. In a later run the aspect units' operator waits offer the implicit `step_out`, which returns to `settings.choose` with nothing more recorded; the first run offers none, and the operator who leaves a state finds it again at the next entry.

*The halt*: the onboarding's wait is the one operator wait that halts the system: while the onboarding is not complete, the setup gate of every start and of every project onboarding refuses with the reason `machine_not_onboarded`, naming the terminal client and the web app, while the onboarding itself and the operator's verbs work (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]).

*The automatic run* (`onboard_run: auto`, link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#auto[CLI, Coordination & Security Specification, Automatic Onboarding]): after the one consent of `auto.consent`, each aspect runs with its proposal accepted: an operator wait whose proposal is complete is answered by the server with it, recorded with its reason (detected, default, the only option), and its consent is covered by the run's one consent; a wait without a complete proposal (a login, a secret, no harness found, the model ids of a harness that cannot list them, a failed check) waits for the operator as in the guided run, and the run continues after it. The run starts no role task, and `auto.result` ends it with every value, its reason, and the check that confirmed it.

[#state-catalogue-onboarding-aspects]
== The Onboarding's Aspects

Each aspect is a compiled sub-workflow of the machine scope (`scope subworkflow`, phase value `machine`; `workspace` where a project's onboarding calls `catalogue` or `roles` for the project), with the entry `start`, the exit `done` (its terminal `<unit>.done`, `terminal done success`), and in a later run the operator's `stepped_out`. A consent state is an operator wait with `yes`, `yes_remember` where the kind can be remembered, and `no`; `no` leaves the scope in the state, except where the row names the optional action it skips (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#consents[Consents]).

[#state-catalogue-harness]
=== Harnesses: `harness`

The scan, the probes, and a verification run the found programs as jobs, through the job launcher with the confinement of a job, never in the runtime's own process (link:../client-profiles/01-profile-schema.adoc#harness-scan[Client Profiles Specification, Harness Scan]). The step cannot finish without one usable harness; a later run scans again, offers a harness found and not enrolled, shows an enrolled one no longer found as missing and offers its removal, and refuses to remove the default before another is chosen or a harness roles use before they are reassigned.
