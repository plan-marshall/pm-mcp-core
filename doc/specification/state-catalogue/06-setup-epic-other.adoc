== Project Setup: `setup` (workspace)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-3[PM-EXT-3: Module Discovery, Build Map & Architecture Enrichment]_

Declared in `project-setup.pmwf` (`scope subworkflow`, compiled only, never designable: it must be able to repair a project whose units fail verification), run in the project's workspace scope as the last part of the project's onboarding, which calls it from `project.setup` (xref:15-project-onboarding.adoc#state-catalogue-project-onboarding[Project Onboarding]); phase value `workspace`. Entries: `first_run`, `integrations` (the first run continued after the project's operator values, at `setup.probe-integration-variants`, its recorded `setup_run` kept), `reconcile`, and `aspect` (one of `team_settings`, `build_map`, `providers`, `finalize`, `qualification`, `architecture`); exits: `done` (`setup.completed`), `operator_values` (`setup.operator-values`: in the first run after `setup.check-operator-files`, so that the caller shows `project.operator` before the integrations are probed, and whenever the project's operator values need the operator), and the operator's `stepped_out`. The first run thus runs `setup.entry`, `setup.prepare-workspace`, and `setup.check-operator-files`, then the operator values of the project (`project.operator`), then the rest of the setup from `setup.probe-integration-variants` (link:../../../../plan-marshall-documentation/doc/use-cases/04-projects.adoc#UC-PRJ-1[UC-PRJ-1]). The start state `setup.entry` records `setup_run: first_run | reconcile | aspect:<name>` from server facts and the call, and every later fork of the run follows the recorded run, so an interrupted first run keeps its first-run path. The first run creates `.marshall/` and `.marshall/config/` and copies no workflow unit: the project takes the machine's or the default unit of every designable unit until its team places one (link:../workflow-dsl/04-ast-node-model.adoc#process-designer[Workflow DSL Specification, Designing a Process]). Every choice of the setup is an operator wait served to both clients, the first act winning; a team choice is written to the team configuration, a question the setup raises is a decision of the workspace scope (class `setup`, link:../domain-extensions/04-setup-state-machine.adoc#setup-questions[Domain Extensions Specification, Setup Choices by Owner]). Every server-raised question state is preceded by an `auto` probe state that enters it only when something needs an answer. Every setup failure enters `setup.needs-repair`, never a condition (link:../domain-extensions/04-setup-state-machine.adoc#setup-probe-states[Domain Extensions Specification, Probe States]). A role task of the setup (the qualification, the enrichment) runs only after the operator's consent to its expected tokens (consent kind `model_cost`), whose _no_ skips the step with its reason and records it as owed for a later run. In a reconcile run or an aspect run the setup's operator waits offer the implicit `step_out`, which returns to the caller with the changes already written left uncommitted for the next `setup.commit-changes`; the first run offers none. In an aspect run, the state that ends the aspect's part exits `aspect_done` to `setup.commit-changes` (to `setup.completed` for the qualification, whose records are operator files).

|[[state-setup.enrich-architecture]]`setup.enrich-architecture`
|`workspace`
|`job`
|`setup.enrich-consent` (`yes`, `yes_remember`).
|`job llm enrich-module role enrich each setup.enrichment-modules`: a fan-out over the server-computed list of the modules to enrich (link:../workflow-dsl/02-units-jobs-decisions.adoc#model-job-states[Workflow DSL Specification, Model Job States]), one task per module, served within the role's count and the model slots, each with its own entity `enrich-<module_id>` closed by the kind's single `submit` link (`responsibility`, `purpose`, `key_packages`, reasoning fields). The re-offers cover only the unfinished modules (xref:01-conventions-generic-conditions.adoc#condition-job_incomplete[Condition job incomplete]).

[#state-catalogue-epic]
== Epic Workflow: `epic`
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-15[PM-WF-15: Epic Creation, Server-Started Plans & Cross-Plan Merge Mutex]_

Declared in `epic.pmwf` (`scope epic`, compiled only, start `epic.decompose`); the epic scope is created by its start (xref:09-bootstrap-and-lessons.adoc#state-catalogue-bootstrap-epic[Start of an Epic]); phase value `epic` for every non-terminal state. The DSL excerpt is in link:../model-work/08-epic-coordination.adoc#epic-workflow[Model Work Specification, Epic Workflow (`epic.pmwf`)]. `epic.next-work` decides the epic's next work, `epic.active` is the watch state where the epic rests between epic events, every judgment is a task of a `read_only` epic role (`decompose`, `reground`, `coordinate`, `landing`), every ledger write commits through a `git.commit_and_push` call, and every operator step is an operator wait of the epic's sub-workflows `decomposition` and `review` (xref:17-epic-decomposition-and-review.adoc#state-catalogue-decomposition[Decomposition & Review]), which halts the epic's own scope while its plans run on in theirs. The operator acts on an epic (next plan, decompose again, automatic on or off, its `overlap_max_files`, a review, archive, cancel) are operator endpoints of the epic resource; each is validated, audited, and recorded as a request the watch settles on (`operator_action`), and `epic.next-work` takes it (link:../model-work/08-epic-coordination.adoc#epic-actions[Model Work Specification, An Epic's Actions]). When an epic task closes `lost` (its re-offers spent, `role_unqualified`, or `role_unavailable`) or ends `infeasible`, the item it served is marked `held` with the reason, shown as the hold `held` in both clients (xref:01-conventions-generic-conditions.adoc#holds[Holds and Their Acts]), and skipped by `epic.next-work` until a change of the effective role set (an artifact or assignment change, a new valid qualification record, or a cleared start-failure guard) or the hold's `retry`; the state continues at the watch `epic.active`. *Automatic mode*: with the header's `auto_start` on, `epic.next-work` starts every launchable row the admission allows; with it off it starts a row only on the operator's _next plan_ and reports each row that became launchable (`epic.launchable`); every other step of the epic runs in both modes (link:../model-work/08-epic-coordination.adoc#epic-auto[Model Work Specification, An Epic Runs by Itself]). *Ends*: archiving is the operator's act, after the completion review and the archive check (`terminal_reason` `completed`); the operator's cancel takes the archive path with `terminal_reason` `cancelled`; the integrity abort ends the epic as `cancelled` at once; the release of the project ends it as `released`, archived on the machine only, its ledger untouched.

|[[state-epic.next-work]]`epic.next-work`
|`epic`
|`auto`
|`epic.decompose` (`done`), `epic.commit-ledger`, `epic.landing`, `epic.review` (every outcome); `epic.active` (every outcome); `start-epic.adopt` (`adopted`, for an adopted ledger that has a queue row).
|`auto epic.next-work`, the epic's next work: it first takes a pending operator request (in the order received), then, with automatic on, starts every launchable row the admission allows through the start of a plan without the operator (xref:09-bootstrap-and-lessons.adoc#state-start.launch[`start.launch`]), and with automatic off starts the next launchable row only on a _next plan_ request and appends a report `epic.launchable` for each row that became launchable; it reconciles every shipped row without a landing record, then takes the first outcome that holds, skipping `held` items. *Admission*: a row is launchable when its prerequisites shipped and it is re-grounded at the current `HEAD` and not `stale`; it is admitted beside the running plans only within `parallelization_scope` (a pausing or paused row keeps its place) and while its declared surface shares at most `overlap_max_files` files with each running plan's declared surface and realized changes, otherwise it waits with the reason `dependency`, `lock`, `scope`, or `overlap` (naming the plan), derived on read. A _next plan_ request with no launchable row is answered with the reason per row, and with the scope full it offers to raise the scope by one. The epic starts no plan before its first decomposition is committed. While the epic archives (its archive flag `archived_at` set by `epic.archive`) it starts and serves nothing and takes only the archive's outcomes and `idle`. `facts`: the queue rows, `unlanded_shipped` (count and `plan_id` values, zero included), the pending messages and requests, the `held` items, `primary_checkout_behind`.
|`decomposition_pending` (no decomposition committed and none `held`), `decompose_requested` (the operator's _decompose again_, with its instruction) -> `epic.decompose`; `review_requested` (the operator's findings or watches review) -> `epic.review`; `archive_requested` (the operator's _archive_): -> `epic.review-completion` when no completion review ran since the epic was through, otherwise -> `epic.archive-check`; `settings_changed` (a switch of the automatic mode or of `overlap_max_files`: the header written) -> `epic.commit-ledger`; `rows_ungrounded` (a start candidate's specification predates `HEAD`) -> `epic.reground`; `rows_stale` -> `epic.recut`; `message_pending` -> `epic.ingest`; `landing_unanalyzed` -> `epic.analyze-landing`; `watch_fired` (a watch whose trigger fired: a landing, an advance of the default branch) -> `epic.recheck-watches`; `ledger_unlanded` (the epic branch holds commits the default branch lacks, and the last landing did not fail on the same head) -> `epic.landing`; `through` (every row shipped or ended, no pending message, every landing analyzed, the ledger landed, automatic on, and no completion review run since) -> `epic.review-completion`; archiving: `archive_uncommitted` (the ledger's move is not committed) -> `epic.commit-ledger`, `ledger_unlanded` (the committed move is not yet on the default branch) -> `epic.landing`, `archive_landed` -> `epic.archived`, `cancel_landed` (the archive of a cancelled epic landed) -> `epic.aborted`; `idle` (also with automatic off when the epic is through: a report `epic.through` once; and while the epic archives when nothing of the archive can advance, for example after a failed landing) -> `epic.active`.

|[[state-epic.landing]]`epic.landing`
|`epic`
|`job`
|`epic.next-work` (`ledger_unlanded`).
|`epic.land-ledger`: one pull request from the epic branch for all pending ledger changes, landed by the project's landing: `landing.pull-request` as one pull request, `landing.main` as a push of the epic branch's commits onto the base branch, and for a project whose landing is `landing.files` as one pull request, since a ledger is never left uncommitted; repository-wide epics-worktree lock; ledger paths only; required CI checks only; waits for `merged`, `ejected`, `closed`, or `timed_out`; post-merge epic-branch resync.
