== Overview

This document is the central catalogue of every workflow state of *plan-marshall-mcp* (`PM-MCP`). Every state identifier used anywhere in the requirements, the specifications, the roadmap, or the implementation watch is defined here exactly once, in one row of one table, with its phase value, its kind, where it is entered from, what it offers, where it exits to, and the section that specifies its behaviour. Other documents describe behaviour; they name a state only by its identifier and link to its row here (anchor `state-<state id>`, xref:state-catalogue/01-conventions-generic-conditions.adoc#_state_identifier_grammar[State Identifier Grammar]).

The catalogue is normatively equal to the state table that the diagram generator produces from the workflow definitions (`renderAsciiDocTables`, link:workflow-dsl/07-loop-back-diagrams-verification.adoc#_automated_mermaid_asciidoc_table_and_ascii_diagram_generation[Workflow DSL Specification, Diagram Generation], `PM-IMPL-5`). Once the `*.pmwf` definitions exist, a build test (`StateCatalogueDriftTest`) compares the generated columns (state identifier, phase, kind, entered from, offered links and outcomes, exits to) with this catalogue and fails the build when they differ, beside the `WorkflowDiagramDriftTest` (link:workflow-dsl/07-loop-back-diagrams-verification.adoc#_build_time_drift_gate[Workflow DSL Specification, Build-Time Drift Gate]). The *Defined in* column is maintained by hand; the same test verifies that every link in it resolves. Until the definitions exist, this catalogue is the reference the definitions are written against: a state that is not in the catalogue does not exist, and a new state is added here before any other document uses it.

*Default units*: The phase units, the sub-workflow units `git.commit_and_push`, `remediation.*`, `replan`, and `adjudicate.decisions`, and the variants of the plan behaviour axes (`landing.*`, `method.*`, `ask.*`) are designable: each resolves by level, the project's copy (`.marshall/config/<unit>.pmwf`) over the machine's copy (`<PM_MCP_BASE>/workflows/<unit>.pmwf`) over the compiled default, a missing copy resolving to the next level, and a project holds a copy only of the units its team placed or changed (link:workflow-dsl/04-ast-node-model.adoc#process-designer[Workflow DSL Specification, Designing a Process]). Every other unit is compiled only, never designable, and calls the binary's default sub-workflows: the plan unit, the machine onboarding with its aspects and settings, the project onboarding and the setup, the starts with their source units and the recipe choice, the epic units (`epic`, `decomposition`, `review`), `decision`, `chat`, the short landings `git.land-removal` and `git.land-unit`, the entity units, and the task-protocol unit `worker-task`. This catalogue documents the *default* units the binary ships, and `StateCatalogueDriftTest` compares it with the default units only. A machine's or a project's copy may differ within the compiled invariants (for example by omitting an optional finalize step or adding a project step's state); its states are published with the project's effective configuration (`pm://project/config`, `units[]` with the level of each unit), never added to this catalogue. A recipe's workflow (a unit of type `recipe`) is documented with its recipe (link:domain-extensions/05-recipes-and-extension-points.adoc#recipe-workflow[Domain Extensions Specification, A Recipe Is a Workflow]).

The server drives every scope: each state is server logic, a task of a named role (`job llm`), or an operator wait, defined once in the workflow language (link:workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]); the kind `link` exists only on the entity states of a task, which its worker follows. The operator acts only in the two clients, the terminal client and the web app, over the operator endpoints of the local API: a harness is a worker only and never relays the operator's words or choices (link:workflow-dsl/02-units-jobs-decisions.adoc#clients-only[Workflow DSL Specification, All Interaction in the Operator's Clients]). An operator wait halts its own scope and nothing else, and has no time limit; the machine's onboarding is the one wait that halts the system. Every blocking situation of a plan that needs no operator has a bounded self-remedy and a defined fallback to the plan outcomes `handed_back` or `returned` (link:state-catalogue/01-conventions-generic-conditions.adoc#exits-and-fallbacks[Exits, Step-Outs & Fallbacks]); what holds a scope without a decision is a hold, which both clients show with its acts (link:state-catalogue/01-conventions-generic-conditions.adoc#holds[Holds and Their Acts]). Every row is fully specified; a behaviour without a specification is not catalogued.

== Chatting with the Planning Role: `chat`
_See Requirement link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-24[PM-WF-24: Chatting with the Planning Role]_

[[chat-unit]]One compiled sub-workflow `chat` (`chat.pmwf`, compiled only, never designable) lets the operator talk over a plan, an epic, the decomposition's draft, an epic's register or one of its items, a decision, a start's entry, or an ended plan or epic with the role that plans it, and steers the work only through changes the operator accepts (link:../../../plan-marshall-documentation/doc/use-cases/06-controlling-work.adoc#UC-CTL-1[UC-CTL-1]). It runs in one of two ways:

* *Called by a state that offers it*, on the call stack, with the caller's subject and scope: `decision.chat` (a decision), `start.chat` and `start-epic.chat` (a start's entry), `decomposition.chat` (the draft), `review.chat` (one item or the whole register). Its exits are `ended` and `proposed`: an accepted proposal is carried to the caller, whose own path applies it (an answer as the operator's own words, a description as a new source, a change into the draft and its checks, an item's disposition or rewrite). It has the phase of its caller.
* *Hosted by its subject scope*, opened by the operator's act _chat_ on a plan or an epic in every state, and on an ended plan or epic: an instance with its own state, like a task entity, that never moves the subject's current state and never stands on its call stack; one chat at a time per subject. An accepted change is applied by `chat.apply`. A chat of a plan has the phase of the phase sub-workflow on the plan's call stack; a chat about ended work runs in the project's workspace scope. The server never starts a chat.

*Routing*: the chat goes to the subject's planning role: for a plan `replan`, whose context is the plan's (<<chat-context>>); for an epic, its decomposition, and its review `decompose`; for a decision a worker asked, the role of the task that asked, and for one a server rule raised or a quorum escalated, the subject's planning role; for a workspace decision a worker asked, that role, while a question the setup's workflow raised has no planning role and _chat_ is offered disabled with that reason; for a start `refine` (a plan's entry) or `decompose` (an epic's); for ended work `replan` for a plan and `decompose` for an epic. Every caller and every subject offers _chat_ disabled with its reason while no configuration of the routed role qualifies.

*Data, never instructions*: the chat's context gives the role its subject as data (<<chat-context>>), an untrusted item still marked untrusted; the operator's messages are not interpreted, the role answers them. Nothing changes without the operator's acceptance of each proposed change in a read-back (link:model-work/06-envelopes-questions-deadlines.adoc#own-words[Model Work Specification, Answers in the Operator's Own Words]).

[[chat-context]]*What a chat knows*: a chat's turns are one conversation, so an open chat is served by a worker of its own that keeps what it read, and is told what changed:

* *The chat worker*: the chat of a plan (running, pausing, or paused), of an epic with its decomposition and its review, of a decision, and of a start's entry is served by one warm generation of the routed role bound to the chat, started with its first turn, offered that chat's `chat-reply` tasks and no other task (link:model-work/03-supervision-and-recycling.adoc#chat-worker[Model Work Specification, The Chat Worker]); a chat about ended work, whose archive never changes, gets a fresh worker per turn and holds no slot between turns. The worker runs with the class `read_only` whatever the routed role's class, the kind `chat-reply` declaring it (link:model-work/01-roles-and-configuration.adoc#role-class-fit[Model Work Specification, Composition Check]), in the subject's working directory: the plan worktree where the plan has one, else the project checkout.
* *A turn's offer*: each turn's task carries the operator's message, the subject's narrative lines since the generation's previous turn (`since_last_turn`, <<chat-narrative>>), the core's counts as they are now (the tasks by status, the footprint's counts, the open decisions and holds), which the narrative's context-only events change without a line, and the files changed since its last task (`changed_since_last_task`, link:model-work/02-task-protocol.adoc#changed-since-last-task[Model Work Specification, Changed since the Last Task]); the worker keeps the rest in its own context.
* *Re-prime*: a new generation (the first turn, the worker released when idle or for a slot, the role's token budget reached, a lost or replaced generation) is primed with the skills of its launch, the chat skill `skill://pm/chat/SKILL.md` among them (link:model-work/01-roles-and-configuration.adoc#chat-skill[Model Work Specification, The Chat Skill]), the pushed core of its subject, and the transcript window, and pulls the rest by URI. The core is rendered from the structured store when the generation is primed, never kept from `chat.open`. The transcript goes on unchanged for the operator.
* *Pulled by URI*: everything the core does not hold is named in it by its `pm://` URI and read by the worker through the resource reads of its job connection (a configuration whose harness declares no `headless.resource_tools` does not qualify for a chat, and _chat_ is offered disabled with that reason while no other does), read-only and within its own project (link:model-work/04-worker-launch.adoc#job-token[Model Work Specification, Job Token, Generation & Connection Binding]), or with the harness's read tools in its working directory. Beside the resources every worker reads, a chat reads the older turns of its transcript (`pm://chat/{chat_id}/turns{?before}`), the narrative of a plan or an epic from a point on (`pm://plan/{plan_id}/history{?since}`, `pm://epic/{epic_id}/history{?since}`), an entry's sources (`pm://entry/{entry_id}/sources`, `pm://entry/{entry_id}/sources/{source_id}`, an untrusted source still marked), and the archived record of ended work (`pm://archive/{plan_id}/record`, `pm://epic/{epic_id}/record`), which replaces the archive's read access by id (link:../../../plan-marshall-documentation/doc/specification/mcp-tools/03-resource-uris.adoc#chat-resources[MCP Tools Specification, Resource URIs]).
* *Budgets*: at a re-prime the core holds at most the chat core budget and the transcript window the newest turns, verbatim, up to the chat transcript window (link:timeouts/02-runtime-leases-operator-web.adoc#chat-page[Timeouts & Budgets Specification, Chat Transcript Page]); the older turns are read by URI, and no model writes a summary of them. Over the core budget a list becomes its count with its URI, never cut text. A warm worker's own context is bounded by its role's token budget, after which it is recycled and the next turn re-primes a new generation.
* *Idle*: the worker is released after the chat idle release without a turn, and at once where queued work waits for a slot (idle yields, link:model-work/03-supervision-and-recycling.adoc#warm-slots[Model Work Specification, Model Slots & Warm Workers]); the chat itself never ends by time, and the operator's next message starts a new generation, re-primed.
* *The context summary*: the chat carries `context: {knows: [{key, args}], as_of}`, what the last core given holds as message keys `chat.knows.*` (`description`, `tasks {count}`, `phase {phase}`, `version {version}`, `sources {count}`, `rows {count}`, `items {count}`, `decision {id}`, `record {outcome}`) with the instant it was rendered; the clients show it as what the role knows.
* *A paused plan*: a paused plan's chat is offered, and its `chat-reply` task is offered to the chat's worker, which holds its own model slot, since a reply changes nothing (link:model-work/02-task-protocol.adoc#offer[Model Work Specification, Offer]); a revision accepted there waits for the plan's start.
* *The transcript as data*: the transcript window reaches the chat's own worker only, the operator's messages in it as data, never as instructions; no other task of the subject reads it.

*Apply paths*: an accepted change goes through the caller's own path and its checks:

* *A plan*: a revision through the guards of a first plan (the outline validation, the derivation dry-run, the task graph, the Q-Gate's mechanical checks), applied at the plan's next task boundary (what runs finishes, the revision is applied, the plan runs on) as `replan.apply` applies one (`replan.apply-revision`), composing a plan instance version of the event `replan` whose re-planning record names the operator's chat as who decided (link:phase-workflows/08-dynamic-re-planning.adoc#replan-apply[Phase Workflows Specification, Apply, Re-Entry & Instance Version]; link:store-schemas/17-re-planning.adoc#replan-record[Store Schemas Specification, Re-Planning Record]). The revision is the operator's own act: it does not spend `replan_budget`, and re-planning still never asks the operator mid-plan (`PM-WF-17`). A question never touches the plan. An epic is told of a revision of a plan it started (inbox record `revised`, link:model-work/08-epic-coordination.adoc#epic-informed[Model Work Specification, The Epic Is Told]). While an accepted revision waits for its boundary, the plan's status and its resource carry `queued_revision: {chat_id, turn_id, applies}`, `applies` the point it waits for as a message key (`chat.applies.after_task {task_id}`, or `chat.applies.on_start` while the plan is paused), until it is applied or lapses.
* *An epic*: staged rows through the epic's checks (surfaces disjoint, dependencies without a cycle); a chat changes only staged rows, never a plan that runs.
* *A decision*: the chat never answers; an answer it proposes is offered as the operator's own words and passes `decision.interpret` and `decision.read-back` unchanged, the interpretation never seeing the recommendation or the votes, which the chat may explain. A revision of the plan it proposes goes through the plan's path; the decision stays open, unless the applied revision removes the task or state that asked it, which closes it `withdrawn` with the reason. The scope waits during the chat as for any decision; an answer in another channel closes the decision and ends the chat. A waiver request offers no chat.
* *A start*: the one change is a description, a rewrite of one or an addition, stored as a new source; starting never waits for the chat.
* *Ended work*: read-only over the archived record (outcome, reason, history, decisions, re-planning records, events), read by its URI (`pm://archive/{plan_id}/record`, an epic's `pm://epic/{epic_id}/record`, <<chat-context>>); it never changes the archive. Its one proposal is a follow-up plan: a description that, once read back, opens the start of a new plan in the project with that description stored and the ended plan or epic named in it, from where the operator goes on at `start.sources` (xref:state-catalogue/09-bootstrap-and-lessons.adoc#state-start.open[`start.open`], `follow_up`).

[[chat-proposal-states]]*A proposal's states*: a proposal is `open` until it is answered; `replaced` by a later proposal of the same chat; `rejected`; `refused` where a check of its path failed, the finding shown; `accepted` where a plan's revision passed its guards and waits for the next task boundary (`queued_revision` above); `applied` at that boundary, or at once where its path has no boundary (staged rows, a draft, an item, a description, a follow-up start); and `lapsed` where the plan left the window of a revision (a phase change out of execute or finalize before the merge, the merge itself) before the proposal was answered or applied, which changes nothing and is told by a notice. An accept naming a proposal made against an older instance version of the plan than the current one is refused `conflict` and told by a notice; the proposal stays visible and can be rejected.

[[chat-origin]]*Origin*: every change a chat leads to records its origin `origin: {kind: chat, chat_id, turn_id}` (the chat and the turn of the accepted proposal) beside the operator's channel and device: a plan's revision in its re-planning record (link:store-schemas/17-re-planning.adoc#replan-record[Store Schemas Specification, Re-Planning Record]), staged rows of an epic, a change of the decomposition's draft and an item's disposition or rewrite (link:store-schemas/04-epic-and-change-ledger.adoc#epic-drafts[Store Schemas Specification, Epic Drafts]), a description stored in a start's entry (xref:state-catalogue/09-bootstrap-and-lessons.adoc#state-start.store-description[`start.store-description`]), and a decision's answer after a chat (`after_chat`, link:model-work/11-decision-records.adoc#decision-record-content[Model Work Specification, Decision Log, Content]). The clients show such a change as the operator's own, made from the chat.

[[chat-names-acts]]*The role names an act, never proposes or performs one*: a chat changes its subject only through the content proposals of its scope; it never proposes, triggers, or performs an operator act (pausing or starting a plan, a plan setting, cancelling, abandoning, the next plan, an epic's automatic mode, decomposing again, archiving, a hold's act, a waiver). Where an act would serve the operator's question, the role names it: its reply carries the act as a reference of the kind `act` (`{kind: act, act, subject}`; a hold it names is a reference of the kind `hold`, `{kind: hold, id}`, as in the narrative's lines), the act one of those the clients offer on that subject, checked by the server at submit (an act the subject does not offer refuses the submit `invalid_arguments`); the clients show it with the way to the view where the operator acts, and nothing in the chat carries it out. This keeps the operator's acts in the operator's two clients (link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-ARCH-11[PM-ARCH-11]) and the MCP surface free of them (link:../../../plan-marshall-documentation/doc/specification/mcp-tools/01-core-workflow-tools.adoc#_architectural_constraints[MCP Tools Specification, Architectural Constraints], 10): no tool, resource, or link of the chat's worker reaches an operator act (link:model-work/04-worker-launch.adoc#job-tool-sets[Model Work Specification, Tool Sets]).

[[chat-reply-stream]]*The reply as it is written*: the operator's message is recorded as a turn of its own the moment `message` is taken, and the client's request is answered with its id before the role answers (link:../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#chat-routes[Runtime & Interaction Model Specification, The Chat's Routes]). `chat.reply` then writes the role's reply into a turn of its own while the job runs: each piece of the reply's text, as the worker's activity reports what the model writes (link:harness-profiles/01-profile-schema.adoc#worker-activity[Harness Profiles Specification, What a Worker Does]), masked like the activity over the joined text of the reply, a piece held back until no secret pattern can still span its end, and not cut to the activity's bound, is appended to the turn and announced as `chat.turn.delta`, each step the runtime derives from that activity (a target read, a check run) as `chat.turn.progress`, a message key and never the model's words, and the turn's end as `chat.turn.completed` with its status and the reply as the role submitted it, which replaces the pieces (link:../../../plan-marshall-documentation/doc/specification/runtime-model/06-event-catalogue.adoc#chat-events[Event Catalogue, Chat]). While `chat.reply` runs, the operator's link `stop` is offered, the one link that ends a job (link:workflow-dsl/02-units-jobs-decisions.adoc#workflow-definition-units[Workflow DSL Specification, Workflow Definition Units]): it withdraws the reply's task from its worker and stops the job, the state takes `cancelled`, and the turn keeps the text written so far with the status `stopped`. An `infeasible` or `lost` reply keeps its text so far with the status `failed` and its reason. A proposal is a turn of its own after the reply that made it. While it is open the operator may write on (`message` in `chat.read-back`); a reply that proposes again replaces the open proposal, which is recorded `replaced`, and _end_ drops it. A harness whose profile maps no events (`headless.events: null`) sends no pieces: its reply appears whole at its end. When the task is offered again to a new worker (a lost generation replaced), the turn's text so far is cleared and announced again with `chat.turn.started`, so two attempts never read as one reply. A reply longer than the chat reply bound (link:timeouts/02-runtime-leases-operator-web.adoc#chat-page[Timeouts & Budgets Specification, Chat Transcript Page]) ends its job, the state takes `too_long`, and the turn keeps its text so far with the status `failed` and the reason `too_long`. A role's reply, its pieces included, is the one text of a model the clients render as the chat's Markdown subset (link:../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#web-chat-text[CLI, Coordination & Security Specification, The Chat's Text]); the operator's messages, untrusted items, and notices stay plain text.

[[chat-narrative]]*The subject's narrative*: the runtime derives from its subject's events (a plan's history and its records, link:store-schemas/02-workflow-state-store.adoc#plan-history[Store Schemas Specification, The Plan's History]; an epic's rows and settings; an entry's sources) one closed catalogue of lines, each `{key, args, refs, at}`: a message key `chat.line.*` with its arguments and the references it names, never a model's words, and never untrusted text (a flagged source is named by its id and kind). The same lines have three readers: the transcript, where the runtime writes them as a turn of the kind `notice` carrying `lines[]` between the role's replies, never inside a reply being written (a line that arises meanwhile is held until the reply ends), the lines that arise together in one turn, which the clients fold; the role's next turn, whose offer carries the lines since the generation's previous turn as `since_last_turn`, while a new generation gets the core instead (<<chat-context>>); and the history resources `pm://plan/{plan_id}/history{?since}` and `pm://epic/{epic_id}/history{?since}`, the same lines from a point on. A chat about ended work has no narrative, since its archive never changes; a decision's chat follows its decision's subject.

What changes without a line is counted in the core when a generation is primed: a task started, steps, checks, the footprint, tokens, progress. Left out of the narrative altogether: the workers' activity, metrics, runtime and device events, other subjects, reports, and the chat's own events, which are turns already. The subject's end ends the chat as before.

*Transcript*: kept turn by turn with its subject for the audit and sent nowhere else (what the operator dictates is turned into text before it is a message, link:model-work/01-roles-and-configuration.adoc#transcribe-role[Model Work Specification, The Speech Role `transcribe`]): a plan's in `plans/<plan_id>/chat/`, an epic's in `epics/<epic_id>/chat/`, a decision's with the decision, an entry's in `pending/<entry_id>/chat/` (moved into the plan's or the epic's machine store at its creation, deleted with an abandoned entry), ended work's beside the archived record (`archive/<plan_id>/chat/`, an epic's `epics/<epic_id>/chat/`); never in a ledger, and never read by a model of the plan as a source.
