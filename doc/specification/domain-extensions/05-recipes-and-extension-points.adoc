[#recipe-workflow]
== A Recipe Is a Workflow
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-4[PM-EXT-4: Recipes as Workflows]_

Recipes are repeatable, structured campaigns for recurring engineering work (such as `recipe-code-review`, `recipe-security-audit`, `recipe-simplify-codebase`, `recipe-agentfile-hygiene`, `recipe-lesson-cleanup`, `recipe-doc-verify`, `recipe-verify-ascii-diagrams`, `recipe-cui-logging-enforce`). [[recipe-workflow-definition]]A recipe is a named workflow of its own: a declarative descriptor beside its workflow, a unit of type `recipe` without entries and exits that starts at its starting point and ends the plan in its stop points (link:../workflow-dsl/01-grammar.adoc#unit-types[Workflow DSL Specification, Unit Types]). Its phases are sub-workflows: its own where it differs from a plan's (the harvest of its targets and the outline derived from them), and the plan's shared ones (`plan`, `execute`, `finalize` with the landing) where it does not (link:../workflow-dsl/04-ast-node-model.adoc#process-designer[Workflow DSL Specification, Designing a Process]). The operator chooses a recipe at the start of a plan (link:../../../../plan-marshall-documentation/doc/use-cases/05-starting-work.adoc#UC-STA-5[UC-STA-5]; link:../state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-recipe[State Catalogue, Recipe Choice]); starting it creates a plan whose process is the recipe's workflow with the parameters given. No state of a plan's general workflow routes into a recipe, and no recipe is chosen for the operator. A recipe plan runs under the same server boundaries and gates as any plan; like the finalize `simplify` step (link:../phase-workflows/04-finalize-step-bands.adoc#_normative_step_catalogue_across_ordering_bands[Phase Workflows Specification, catalogue row `5`]), `recipe-simplify-codebase` has no delete boundary of its own: a deleted test file or test method is part of the plan's diff and is verified by the gates that follow (pre-push quality gate, CI, review). `recipe-lesson-cleanup` maintains the lesson corpus (merging duplicates, retiring and superseding lessons, routing stalled ones) under the Corpus Routing Campaign rules of the lesson store (link:../store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Lesson Record]): one recorded disposition per lesson, idempotent re-runs, population deltas reported; a claimed lesson is refused.

*Where recipes come from*: the recipes of the project's domains (compiled into their bundles), of the machine (`<PM_MCP_BASE>/recipes/<recipe_id>.json` with its workflow `<recipe_id>.pmwf`, offered in every project on the machine), and of the project (`.marshall/recipes/<recipe_id>.json`, `.marshall/recipes/<recipe_id>.md`, and its workflow `.marshall/recipes/<recipe_id>.pmwf`); a project's recipe takes the place of one of the same key in that project. A duplicate key of a built-in or domain recipe fails the build, and the operator's placing of a machine or project recipe with such a key is refused (link:../workflow-dsl/04-ast-node-model.adoc#process-designer[Workflow DSL Specification, Designing a Process]). A recipe's workflow is verified like every unit of its level against the compiled invariants of the parts of the process it takes over.

=== Declarative Recipe Descriptor Schema
_Implementation watch: link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-12[PM-WATCH-EXT-12]_

Built-in recipes (`classpath:/recipes/<recipe_id>.json` with `<recipe_id>.pmwf`), machine recipes, and project-local recipes are defined as declarative data structures beside their workflow.

*Domain recipes (`provides_recipes`)*: `plan-marshall`'s `provides_recipes()` hook becomes packaging: a domain recipe (such as `pm-dev-java-cui`'s `cui-logging-enforce`) is part of its domain bundle, compiled into the classpath next to the domain descriptor, and registered under the bundle's `domain_id` (its descriptor's `domain` field equals that `domain_id`). The recipe registry is assembled at build time; two recipes with the same `recipe_key` (built-in or domain) fail the build, so a collision never reaches a runtime registry and no registration order decides a winner.

=== Recipe Workflows: Harvest, Deliverables & Parameters
_Implementation watch: link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-12[PM-WATCH-EXT-12], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-9[PM-WATCH-PHASE-9]_

The harvest and deliverable rules mirror `plan-marshall`'s recipe engine (`script-shared/scripts/recipe_scoring.py`, `phase-1-init/SKILL.md`, verified at commit `1d4a1da37`; re-verify against the latest `plan-marshall` version before implementing), without its scoring and routing: a recipe is the operator's explicit choice.

1. *Explicit Choice*: A recipe runs only when the operator chose it at the start; nothing scores the registry against a request, and no plan is routed into a recipe.
2. *The Recipe's Workflow*: The plan of a recipe runs the recipe's unit in place of the plan unit: its own phases first (the harvest of the targets, their confirmation, and the outline derived from them, `confidence = 100`, `planning_lane = deep`, `track = complex`), then the plan's shared phases `plan`, `execute`, and `finalize`, which it calls like the plan unit does (link:../state-catalogue/18-plan-unit-axes-short-landings.adoc#state-catalogue-plan-unit[State Catalogue, Plan Unit]). Its plan instance is composed from its unit and the shared phases like every plan's, with the plan behaviour axes bound the same way.
3. *Request-Scoped Recipes*: A recipe whose harvester kind is `request_scoped` (`surgical-fix`) takes the sources of a request: the start gathers them like a plan's (`start.sources`), and its deliverables come from the pre-diagnosed request (the named files, root cause, and exact change; one deliverable per affected file or one for the whole cohesive edit); a request that names no file or crosses a module boundary is refused by the recipe's fit gate rather than widened.
4. [[recipe-plan-id]]*Recipe Plan ID*: A recipe plan's `plan_id` is `recipe-{recipe_key}-{yyyy-mm-dd-hh-mm-ss}` (UTC), so every run gets a fresh branch name, and it is not changeable at the start, the title is; its grammar and the 37-character bound of `recipe_key` that keeps it within the `plan_id` grammar are in the link:../identifiers/01-general-rules-and-registry.adoc#id-recipe-plan-id[Identifier Registry]. *Deliberate change vs. `plan-marshall`*: `plan-marshall` uses hour precision (`{yyyy-mm-dd-hh}`), which collides when the same recipe runs twice within an hour.
5. *Server-Side Target Harvesting & Deliverable Generation*: The recipe's harvest phase executes the recipe's deterministic `target_harvester` (e.g., enumerating packages per module, scanning `.md`/`.adoc` files for misaligned ASCII box diagrams, or invoking an enrolled `project_script` harvester) and populates the solution outline's deliverables from the `deliverable_template`. The workflow asks for model judgment only where it is required: confirming or pruning the harvested targets (`confirm_recipe_targets`, a task of the role `outline` before the server outline gate) and verifying coverage at completion.
6. *Auditable, Idempotent Harvest Runs*: A recipe run records one disposition per harvested target; for `recipe-lesson-cleanup` over `stalled_lessons` the dispositions are `routed`, `reclassified`, and `retired` (through the lesson's in-file retirement with its mandatory `reason` and `verdict`, link:../store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Lesson Record, Retirement]); the `stalled_lessons` population is the lessons with a stale claim (link:../store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Lesson Record, Claim]). Re-running on unchanged input is a no-op keyed on the target's duplicate key (for lessons: link:../store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Lesson Record, Upstream Release, Duplicates]). If the population differs between harvesting and action, the run reports the delta (added and removed target ids) and never adopts it silently.
7. *Empty Harvest Is a No-Op, Never an Empty PR*: When the harvester (after `confirm_recipe_targets` pruning) yields zero targets, the plan creates no deliverables, no commit, and no pull request: the recipe's workflow composes a post-run-only version of the plan instance (composition event `empty_harvest`; every step below order `900` pruned with prune reason `empty_harvest`, xref:06-configuration.adoc#config-snapshot[Plan Instance]) and calls the phase `finalize` at its entry `post_run`; the post-run band runs, and `finalize.archive-plan` ends the plan in the terminal `completed` with `outcome: no_change`, `merge_outcome: no_pr` (link:../store-schemas.adoc[Store Schemas Specification, `merge_outcome`]) and the fact `empty_harvest` (harvester kind and the population it scanned) in its landing envelope. It is the same post-run-only form the `returned` fallback uses.
8. [[recipe-parameters]]*Recipe Parameters*: `recipe_params` are gathered before the plan exists, by the start's recipe choice (link:../state-catalogue/09-bootstrap-and-lessons.adoc#state-recipe.parameters[State Catalogue, `recipe.parameters`]), and kept with the entry; nothing is written to a plan before `recipe.create` creates it. With a non-empty `parameters_schema` the operator wait renders the schema together with the resolved option lists and a proposal per parameter, and the server validates the answer against the recipe's own `parameters_schema` (a violation is refused `invalid_link_args` naming the parameter and the rule); without one the choice passes on at once. A parameter without an option (no module the recipe can work on, no domain of it in the project) is shown with its reason, and the recipe cannot run. There is no global parameter vocabulary such as a fixed scope × thoroughness matrix.
** *Server-resolved options (`x-pm-options`)*: An `enum` of the schema may declare `x-pm-options` with one value of the closed set `domains` (the project's active domains), `profiles` (the execution profiles), `skills:<domain>` (the skills of that domain), `modules` (the discovered modules), and `base_branches` (the push remote's branches); the server computes the options, renders them, and validates the submitted value against them. Dependent choices (for example the skills of every chosen domain) are resolved in one step, because the server computes the option lists of every domain up front.
** *Audit recipes*: A recipe that audits a scope declares `scope` and `base_branch` in its `parameters_schema`, so the audited scope is an input the server validates, never an assumption.
9. *Request-Aspect Classification*: For every plan other than a recipe's, the server classifies the request aspect (`analysis`, `planning`, `implementation`) over the plan's sources in `init.classify` by keyword-table token overlap (`plan-marshall`'s `aspect-classify`): the higher of `analysis` and `planning` is accepted only when its overlap confidence is at least `0.7` and beats the `implementation` overlap; otherwise the aspect is `implementation`. The result is persisted as `status.metadata.request_aspect` with its confidence, silently (no question), and records intent only; it never decides whether a build is needed. *Deliberate change vs. `plan-marshall`*: `plan-marshall` offers a bounded model fallback for an ambiguous aspect; `PM-MCP` computes it deterministically, with zero model calls.
10. [[agentfile-hygiene]]*Agent-File Hygiene*: `recipe-agentfile-hygiene` harvests the project's always-on instruction files (`CLAUDE.md` at every level, `AGENTS.md`), which `writer` and `read_only` workers load natively (link:../model-work/04-worker-launch.adoc#job-working-directory[Model Work Specification, Worker Launch, Working Directory]), and classifies every section as kept, demoted to a skill or document loaded on demand, or deleted. Its rubric judges each line by the wrong action it prevents: a line that names none (a general appeal to clean code or best practice, a description of what the checkout shows) is deleted. A structural overview is deleted when a model derives it cheaply from the checkout or the architecture enrichment covers it (xref:04-setup-state-machine.adoc#setup-enrichment[Project Setup, Enrichment]), and kept when deriving it costs more than the lines it takes, across the sessions that need it. A rule a machine can check is reported as a candidate for a check, in the remedy kinds `check` and `wire_check` of a lesson (link:../store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Lesson Record, Remedy]), and stays a line only until that check runs before the task ends. A line that states a general capability of a model rather than a fact about the project is marked as a removal candidate when the effective model of a role that loads the file changes; a fact about the project (a generated file, a build entry point, two places that must change together) is never marked by a change of model.

11. [[review-history]]*Review History* (_Implementation watch: link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-40[PM-WATCH-EXT-40]_): `recipe-review-history` turns what reviewers caught on a project's merged pull requests into draft review rules of that project. Its parameters name the number of merged pull requests, newest first. Before any model reads them, the server sets aside the newest fifth (at least five) as held out, records their numbers in the recipe's record, and never hands them to a task. It ingests the review comments of the rest through the provider, human and bot alike, each screened and marked untrusted like every review comment (link:../model-work/07-untrusted-text-screening.adoc#screen-stored[Model Work Specification, Screened Once Stored]). A task of the read-only role `review-code` submits per recurring catch one draft rule: the mistake it prevents, the check a reviewer makes, and the pull requests and comments it comes from; a rule without at least one comment that names a real defect is refused, and a rule a machine can check is reported as a candidate for a check (the remedy kinds `check` and `wire_check`). The operator takes or rejects each draft; no draft becomes a rule without that act. The rules taken are written in the operator's words or the task's, as an extension skill of the project (`.marshall/skills/`) that the operator binds to `review-code`, and land through the plan's pull request. The held-out pull requests are the tasks on which a comparison of the role with and without that skill may grade it (link:../workflow-dsl/07-loop-back-diagrams-verification.adoc#comparison-held-out[Workflow DSL Specification, Comparison Footprint]). A run with no comment to read ends `no_change` like every empty harvest.

[[self-review-surfacer]]
== Pre-Submission Self-Review Surfacer Extension Point (`ext-self-review-*`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-5[PM-EXT-5: Out-of-Process Project Script Jobs & Domain Workers]_

_Implementation watch: link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-13[PM-WATCH-EXT-13], link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-14[PM-WATCH-EXT-14], link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-15[PM-WATCH-EXT-15], link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-16[PM-WATCH-EXT-16], link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-17[PM-WATCH-EXT-17], link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-18[PM-WATCH-EXT-18], link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-19[PM-WATCH-EXT-19], link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-24[PM-WATCH-EXT-24], link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-26[PM-WATCH-EXT-26], link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-38[PM-WATCH-EXT-38], link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-45[PM-WATCH-GEN-45]_

The self-review surfacer is a domain extension point, not a recipe: a domain bundle registers at most one compiled surfacer `ext-self-review-<domain_id>` (in `plan-marshall`: `pm-plugin-development:ext-self-review-plan-marshall`), declaring the content classes it covers and its detectors. During `phase-6-finalize`, the pre-submission structural self-review step (link:../phase-workflows/04-finalize-step-bands.adoc#_normative_step_catalogue_across_ordering_bands[Phase Workflows Specification, catalogue row `8`, `pre-submission-self-review`]) runs the surfacers registered for the plan's domains as deterministic candidate detectors over the plan's realized diff to surface high-risk patterns (unvalidated boundary inputs, asymmetric function pairs, description-vs-body mismatches, stale ordinal prose, unguarded flags) as structured facts for model review.

*Outcomes*: every round records exactly one of three outcomes, carried into the landing facts as `self_review` (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#_landing_envelope_emit_landing[Phase Workflows Specification § Landing Envelope]):

* `reviewed`: at least one applicable surfacer ran and the model submitted its verdict over the surfaced candidates.
* `not_covered`: a surfacer is registered for the plan's domains but does not apply to the footprint; the surfacer names the reason (`no_covered_content_class` with the uncovered content classes, or `zero_detectors`).
* `not_run`: no surfacer is registered for any of the plan's domains; the reason is `no_domain_surfacer`.

Neither `not_covered` nor `not_run` is ever recorded or rendered as `clean` or `passed`. The contract rules:

* **AsciiDoc Content Class**: `*.adoc` paths form their own content class `asciidoc` (never `other`), covered at least by the stale-count and ordinal-prose detector: a count or ordinal stated in prose ("the five bands", "the third item", "13-state vocabulary") that no longer matches the enumeration, table, or list it describes, including one in a file the plan did not edit, is a candidate. PM-MCP's own documentation is AsciiDoc, so its changes are reviewed rather than reported `not_covered`.
* **Applicability by Content Class**: A surfacer is applicable when its declared content classes cover at least one content class of the realized footprint; a footprint whose paths all fall in content class `other` has no applicable surfacer. An inapplicable surfacer is never run: the step records `not_covered` with the surfacer's reason and the uncovered content classes and completes non-blocking, never as `clean`. The reasons `no_domain_surfacer`, `no_covered_content_class`, and `zero_detectors` are round-invariant at an unchanged `HEAD`.
* **Not Run Is Not Clean Invariant**: When no self-review surfacer is registered for the plan's domains, the server records `"status": "not_run"` with `"reason": "no_domain_surfacer"` in the finalize ledger—never `"clean"` or `"passed"`. Every active surfacer records its `scope_statement`, `structural_limit`, and `delta_coverage`; a detector class with zero matching files in the diff is recorded as `unapplicable`, never counted toward measured clean coverage.
* **Which Zero Coverage**: Per content class the surfacer records `files`, `files_with_candidates`, and `detectors`; a class with `files > 0` and `detectors == 0` is recorded as `gap`, never as clean. The reach map is derived from the registered detectors. Every realized path with no applicable detector is listed as `not_scanned` in the step facts and the landing facts, and a round over only `not_scanned` paths is `not_covered`. Per-file candidate counts distinguish `examined_zero` (an applicable detector ran on the file and found nothing) from `not_scanned`.
* **Removed Guards**: Every surfacer that covers a content class of code carries a removed-guard detector: a guard construct of the domain (validation of input at a trust boundary, escaping of output, a permission, containment, or signature check, error handling that prevents the loss of data, a test) that the plan's base commit has in a file of the realized footprint and `HEAD` no longer has is a candidate, with the removed lines and the step or task whose change removed it. The detector compares guards per file by construct, never by count alone, so a guard moved within the footprint is not a candidate and a guard replaced by a weaker one is. A candidate is judged by `review-code` like any other and is never a refusal: a guard the plan removes on purpose (a check made unreachable, a duplicate merged into one) is confirmed with its reason. It covers the change of every writer, the applied proposals of `simplify` among them, because the never-simplify list is guidance and a deleted guard passes the tests that never exercised it. A candidate whose removed lines an earlier security fix of the project added is filed as a security finding (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#security-audit-calibration[Phase Workflows § Security Audit Calibration], Removed Security Guards).
* [[self-review-consumers]]**Consumers Outside the Footprint** (_Implementation watch: link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-39[PM-WATCH-EXT-39]_): A change can keep a symbol's declaration and change what it does; its consumers in files the plan did not touch then pass the build and are reviewed by nobody. For every symbol that the realized diff declares or changes, that exists at `HEAD`, and that is visible outside its file (the domain's language decides: in Java `public` and `protected` members and types), the step derives its direct consumers through `pm_lsp` (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/02-service-and-skill-tools.adoc#_pm_lsp_warm_language_server_operations[MCP Tools, `pm_lsp`]): `call_hierarchy` incoming at depth 1 for a member, `references` for a type or a field. The consumers in files outside the realized footprint go into the round's facts as `external_consumers[]` (the changed symbol, the consumer's path and range, and `test` from the owning build system's source set, never from a name pattern). They are context for `review-code`, never candidates the round must clear: the task judges whether the change holds for them, and a finding it raises on one is an ordinary finding. For a changed symbol with no consumer in a test source set, the step also names the nearest test reached through one of its direct consumers (`tested: via_caller`, with the consumer); a symbol with a test consumer is `tested: direct`, one with neither `tested: none`. `via_caller` is a pointer for the reviewer, never evidence that the change is tested, and never lowers the attention a symbol gets. Bounds: at most `20` consumers per symbol and `200` per round, ordered by path and line, with `consumers_total` and `consumers_omitted` per symbol, so a truncated list never reads as complete. A symbol whose consumers could not be derived (an answer with `index: incomplete` or `index: unknown`, no language server enrolled for its language, `lsp_unavailable`, a timeout) is recorded `consumers: not_derived` with the reason, never with an empty list, and the round's facts count those symbols.
* **Run-Emitted Diagnostics**: Diagnostics emitted by the plan's own run (build, validator, or gate output) whose subject overlaps the plan footprint are surfaced as candidates alongside the detector findings.
* **Target-Class Seeding**: When the plan's approved outline names the defect class the plan exists to remove (its target defect class), the surfacer also seeds candidates of that class over the plan footprint in every round, because a fix for a class is the likeliest place to re-commit it; the seeded candidates are counted in the round's `cohort_size` like any other.
* **Out-of-Surface Findings**: Findings identified outside the surface go into a non-blocking `observed_out_of_surface` list whose count reaches the step summary, so `clean`, `nothing_found`, and `suppressed` stay distinct outcomes.
* **Round Accounting**: `cohort_size` is published per round and cumulatively. A finding at a file and line of a prior round's finding is marked `repeat_site` with its repeat count. A finding classified `self_seeded` (introduced by the previous round's fix) records that classification at WARNING level; its remedy is the deletion of the added clause, gated on that recorded classification. Each round records `findings_total` and `findings_self_seeded`; from round 2 the step's facts state the self-seeded share, the vocabulary skill prescribes deleting the added text or replacing it with a pointer as the default remediation, and the share of every round is rendered in the `choose` task's facts of the `remediation.review-findings` policy unit that self-review findings call and, when its fix budget is exhausted, in the hand-back gap comment. The share is a signal only: the unit's `fix_budget` (link:../workflow-dsl/07-loop-back-diagrams-verification.adoc#loop-back-bounds[Workflow DSL Specification]) remains the loop's only automatic bound.
* **Delta Round Narrowing Invariant**: On subsequent finalize iterations after a fix, delta self-review rounds narrow only the candidate file set to files modified since the previous reviewed `worktree_sha`, never narrowing the hunk basis against the plan's base commit. Every fix hunk is reviewed together with its full enclosing passage (the enclosing section, list, table, or code block), never as the bare hunk. The plan's base commit is the footprint `base_ref` defined in link:../store-schemas.adoc[Store Schemas Specification] (§ Three-Way File Footprint Reconciliation). Before computing candidates the step fetches `origin/<base_branch>` itself; the fail-closed refusal applies only when the base commit or the previous `worktree_sha` is still unresolvable after that fetch, and then the step fails with an explicit error rather than silently widening or skipping. The delta candidate set also includes the reference closure: every file of the plan footprint that references a path or a declared symbol changed since the previous reviewed `worktree_sha` (a document line made stale by an edit in another file is therefore a candidate in the next delta round, not only in the closing full round). When the previous round's `worktree_sha` is not an ancestor of `HEAD` (the branch was rebased), delta resolution is skipped, open findings stay pending, and a full round is required: an endpoint diff across an upstream advance never marks a finding fixed. A delta round can never close the step: a clean delta round is followed by exactly one full-surface round over the whole plan diff, and only a clean full-surface round records `done` (`may_close = true`). A delta round that surfaces findings calls `remediation.review-findings` (its `fix` in the `loop_back` form) without a confirmation round.

[[retrospective-aspects]]
== Retrospective Aspect Extension Point (`provides_retrospective_aspects`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-5[PM-EXT-5: Out-of-Process Project Script Jobs & Domain Workers]_

`plan-marshall`'s `provides_retrospective_aspects()` hook lets a domain bundle attach deterministic, script-backed analysis fragments to `plan-retrospective` for plans of its domain (`pm-plugin-development` is the only bundle declaring one). In `PM-MCP` it becomes an extension point of the post-run quality report (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#post-run-quality-report[Phase Workflows Specification § Post-Run Quality Report]):

* *Registration*: A domain bundle registers each aspect as a compiled instrument keyed `(domain_id, aspect)`; the report engine runs it only when the plan's domains include that `domain_id`. There is no script path and no model job: the aspect is part of the in-process report engine.
* *Instrument Contract*: A domain aspect is an instrument like any built-in one and obeys the report's Instrument Contract (populations, declared `proves` / `falsifiable_preconditions` / `self_included`, `zero_reason`, clean rendered). An aspect that cannot read its inputs renders `unmeasured`, never `0`.
* *Observability Only*: Every domain aspect declares `gates_merge: false`; its verdicts are INFO decisions in `quality-report.json` and never enter the pre-merge barrier.

== Out-of-Process Project Script Jobs (`project_script`) & Domain Workers
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-5[PM-EXT-5: Out-of-Process Project Script Jobs & Domain Workers]_

To support repository-specific automation (`finalize-step-*` skills that ship executable checks, custom `recipe-*` target harvesters) and third-party/organization domain workers (custom build-log parsers, marker scanners, or module discovery for languages not compiled into `pm-mcpd`) without compromising the GraalVM native-image closed world, `PM-MCP` provides a permanent **`project_script`** job type in the Job Runtime (see link:../job-runtime.adoc[Job Runtime Specification]).

=== Division of Authority: Server vs. `project_script`

[source,text]
----
┌─────────────────────────────────────────────────────────────────────────┐
│ PM-MCP Daemon (Authoritative State & Security Boundary)                 │
│  • Owns workflow state machine, step ordering, gating, and locks        │
│  • Verifies script path, interpreter hash, and SHA-256 against enrolment│
│  • Serializes closed JSON input payload; spawns isolated process group  │
│  • Validates stdout against strict output JSON Schema                   │
│  • Persists findings/facts into the per-project machine store atomically│
└───────────────────┬─────────────────────────────────▲───────────────────┘
                    │ stdin: ProjectScriptInput JSON  │ stdout: ProjectScriptOutput JSON
                    ▼                                 │
┌─────────────────────────────────────────────────────────────────────────┐
│ Out-of-Process `project_script` Subprocess (Stateless Fact Producer)    │
│  • Runs in sanitized environment (no provider credentials)              │
│  • Reads worktree files read-only; NEVER writes to .marshall/ stores    │
│  • Returns structured facts, candidate findings, or parsed log records  │
└─────────────────────────────────────────────────────────────────────────┘
----

1. *No Direct Store Mutation*: A `project_script` subprocess is a stateless fact producer. It **must never** write directly to the per-project machine store (`<PM_MCP_BASE>/projects/<project_id>/`, outside its Landlock write set anyway), `.marshall/epics/`, or `.marshall/config/`. All persistence is performed by the daemon after validating the script's JSON output.
2. *Operator Enrolment Precondition*: Every `project_script` (and its runtime interpreter, such as a pinned `python3` binary) must be enrolled by the operator in the project's enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` (`project_scripts.<project_script_id>`, link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]) with its repository-relative script path, expected SHA-256 content hash, interpreter, maximum timeout (`max_timeout_seconds`, the budget of every run, link:../timeouts/01-job-budgets-and-waits.adoc#project-script-budget[Timeouts & Budgets Specification]), its binding (`worker_kind` ∈ `finalize_step`, `recipe_harvester`, `log_parser`, `module_discovery`, `edge_resolver`, and `target`, the step id, recipe key, or build system it serves), and its `argument_schema` (an inline JSON Schema, validated as a schema at enrolment, against which the runtime validates the arguments of every run, `PM-EXT-5`). A job that uses a script for another worker kind or target than its binding is refused. If a script file is modified in the working tree without re-enrolment, the verify-not-resolve digest check rejects execution with job outcome `refused`.
3. *Project Finalize Steps Route Like Default Steps*: A `finalize_step` script runs in the project step's `project.run-step` state of the plan instance (the step exists only when the project unit, the `workflow.json` descriptor, and the enrolment binding agree). Its findings go to the findings ledger and are triaged like every producer's; a job fate other than `succeeded` enters the shared `finalize.step-failed` state (one automatic re-fire, then `finalize.hand-back` before order `70`, an owed item after it), never an operator decision (link:../state-catalogue/04-plan-finalize-terminal.adoc[State Catalogue, finalize steps]).

[#log-parser-output]
==== `log_parser` Output: Failure Records

A remediation policy hands the model structured failures, never raw logs: the evidence job of a failure class records one failure envelope per failure in the plan's evidence directory (link:../store-schemas/14-plan-instance-waivers-questions.adoc#evidence-directory[Store Schemas Specification, Evidence Directory & Failure Envelope]). For a CI log the compiled log parser of the build domain, or an enrolled `project_script` with `worker_kind: log_parser`, produces the parsed part of these envelopes; a log no parser claims is parsed by the generic tail parser, which yields one failure of kind `unknown`. A `log_parser` script returns its failures in `facts.failures` and leaves `findings` empty (a CI failure is evidence for a remediation decision, not a finding of the findings ledger):

[source,json]
----
{
  "$id": "https://cuioss.de/plan-marshall-mcp/schemas/log-parser-facts-v1.json",
  "title": "LogParserFacts",
  "type": "object",
  "required": ["failures"],
  "additionalProperties": false,
  "properties": {
    "failures": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["kind", "message"],
        "additionalProperties": false,
        "properties": {
          "kind": { "type": "string", "enum": ["compile", "test", "lint", "policy", "unknown"], "description": "The check's failure_kind; infra is set by the server for a failed gather constituent, and a timed-out check is failure_class timed_out, never a kind." },
          "file": { "type": ["string", "null"], "description": "Repository-relative path; a path outside the repository is dropped by the server." },
          "line": { "type": ["integer", "null"], "minimum": 1 },
          "message": { "type": "string", "minLength": 1, "maxLength": 400, "description": "One line; redacted by the server." },
          "log_line_from": { "type": ["integer", "null"], "minimum": 1, "description": "First log line of the excerpt that shows the failure." },
          "log_line_to": { "type": ["integer", "null"], "minimum": 1 }
        }
      }
    }
  }
}
----

The server completes each envelope and never takes these fields from the script: `failure_id`, `class` (`ci`), `source` (the check name), the `excerpt_uri` of the excerpt it cuts from the reported log lines (`pm://plan/{plan_id}/evidence/{evidence_id}`, an untrusted resource, never inlined beyond `message`), the `fingerprint` (class, kind, file, and the normalized message), which recognises a repeated failure across remediation rounds, and the baseline, gate, and waivability fields. `message` is untrusted external content: it passes the ingestion validator before it reaches a representation. A script output that violates the schema is a job failure; the evidence job then falls back to the generic tail parser, so an unparsed log never hides a failure.
