[#planning-lanes]
== Planning Lanes & One-Way Ratchet (`light` -> `deep`)

`PM-MCP` routes the planning pipeline (Phases 2–4) along one of two structural lanes stored in `status.metadata.planning_lane`, which deterministically drives the `track` field (`light => simple`, `deep => complex`). The lane is the structural selector for the whole Phase 2–4 pipeline, mirroring `plan-marshall` (`plan-marshall/workflow/planning.md` § Planning-lane dispatch and `phase-3-outline/workflow/light-lane.md`; re-verify before implementing): a `light` plan runs one collapsed light envelope, a `deep` plan runs the full refine loop -> outline -> plan pipeline.

[cols="1,2,4"]
|===
|Lane |Target Scope |Discovery & Execution Contract

|`light`
|Bounded, localized changes (`scope_estimate` in `{surgical, single_module}` with known target files)
|Skips the Phase 2 states. After the server-side light gate (<<light-gate>>) passes, runs *one* collapsed light envelope (`outline.light`) that folds refine without the confidence loop (clarified request, `pr_title`, minimal premise check over the bounded read set, no clarification iteration, no confidence scores), the Simple outline, and deliverable derivation. The envelope reads only the bounded read set the server computed: the declared affected files plus their one-hop neighbours (*Total Read Set Cap* `cap = 25`, *Declared-File Band* `band = 8`). No Q-Gate runs.

|`deep`
|Codebase-wide, multi-module, architectural, or uncertain changes
|Runs the full Phase 2 refine loop (`refine.analyze`, the confidence loop, the Q-Gate of lesson-derived plans), then full domain discovery, ADR progressive-disclosure scan (`manage-adr scan`), consumer sweeps for symbol renames/deletions, and full Q-Gate verification (`outline.deep`).
|===

The closed `planning_lane` enumeration also holds the lanes `land` (source `local_changes`, <<land-lane>>) and `adopt` (source `pr`, <<adopt-lane>>). Both are fixed at plan creation by the source, skip the planning pipeline, and stand outside the ratchet below.

[#light-gate]
=== Light Gate: Deterministic Budget Trigger

The budget trigger is the primitive `lane.budget-check`, computed by the server before the light envelope's task is created. Two `auto` states run it: `init.light-gate` (in `phase-1-init`, entered from `init.ready` for a `light` plan only) and `outline.light-regate` (in `phase-3-outline`, the light lane's rework entry `rework_light`, entered on every rework of a `light` plan's outline, before every new `outline.light` task); a revision never re-enters a Phase 1 state (link:../state-catalogue/02-plan-phases-1-3.adoc#state-outline.light-regate[State Catalogue]). It never reads a worker's file-read counter: the server does not observe the harness's own reads, so the bound is decided over the declared and resolved file set before any model work.

1. *Declared Affected Files `A`*: On the first run, the explicit repository-relative paths named in the request (the same path extraction the initial lane router uses; the gate never discovers files the request did not name). On a relaunch after revision, the `Affected files` of the current `outline.md`.
2. *One-Hop Neighbours*: For each file of `A`, the server reads the file-level neighbours resource `pm://architecture/files/{+path}/neighbours` (link:../domain-extensions/03-module-discovery.adoc#_architecture_query_resources_pmarchitecture[Domain Extensions Specification, Architecture Query Resources]: the file's own resolved imports, its paired test or production file, and its owning module), and adds the owning module's descriptor; exactly one hop, never transitive, never a content search. `neighbours` is the resolved set minus `A`.
3. *Budget*: The plan escalates to `deep` when `|A| + |neighbours| > 25` (cap) or `|A| > 8` (band); `escalation_trigger` records `budget_cap` or `budget_band` with both counts.
4. *Fail Toward the Safe Lane*: When the neighbours of any file of `A` cannot be resolved (architecture inventory absent, file not attributed to a module, or a resource answering `indeterminate` or an error), the plan goes `deep` with `escalation_trigger: neighbours_indeterminate` and `facts` naming the unresolved files and the reason. An unresolved neighbour set is never counted as empty, and an empty `A` is unresolved, not bounded.
5. *Baseline Probe*: Because a light plan never enters `refine.baseline-reconcile`, the gate runs the same non-mutating probe (xref:01-planning-phases-1-2.adoc#_phase_entry_baseline_reconciliation[Phase Entry & Baseline Reconciliation], probe variants and overlap population unchanged). `overlap_with_content_conflict` sends the plan `deep` (`escalation_trigger: baseline_conflict`), since content conflicts are absorbed during refinement, which only the deep lane runs; the other outcomes are recorded as on the deep lane.
6. *Record*: The gate records `A`, `neighbours`, both counts, and its outcome in `audit.jsonl` (`lane_budget`) and appends a `lane.budget` decision record with both counts against the cap and the band (link:../model-work/11-decision-records.adoc#decision-points[Model Work Specification, Decision Points]); a later ratchet to `deep` appends a correction of cause `reverted` to the plan's last `light` decision. On pass, `A ∪ neighbours` is handed to the envelope in `facts.light_read_set` as its read bound.

[#light-envelope]
=== Collapsed Light Envelope (`outline.light`) & Artifact Gates

When the light gate passes, the plan moves to `phase-3-outline` with `phase-2-refine` recorded as collapsed (`status.metadata.phase_2_mode = collapsed_light`, not yet `done`), so the envelope's token usage is attributed to `phase-3-outline`. The light lane's own `outline.light-detect-change-type` runs the change-type detection of the deep lane (the heuristic scores `original_input`, since no clarified request exists yet) and continues only into the light lane, then the server creates the `outline.light` task (a `job llm` state of role `outline`, xref:01-planning-phases-1-2.adoc#phase-roles[Model Work per State]). The phase artifact gates apply to light plans unchanged; the collapsed envelope satisfies them as follows:

* *Clarified Request and `pr_title` (Phase 2 exit gate)*: The envelope's `submit:outline` carries the intent record `intent:schema[intent-record]` (xref:01-planning-phases-1-2.adoc#intent-record[Intent Record], with the same server checks), `pr_title` (conventional commit, `<= 72` characters), and `outline:schema[outline-record]`. A light submission missing `intent` or `pr_title` is refused with `invalid_link_args`. On acceptance the server writes `intent.json`, the rendered `request.md` `## Clarified Request`, `status.metadata.pr_title`, and `outline.md` in one transaction and records `phase-2-refine` `done`. The light envelope is thereby the `pr_title` producer on its own path (link:../workflow-dsl/04-ast-node-model.adoc#static-verification-rules[Workflow DSL Specification, rule 8]); the Phase 3 arrival requirement for `pr_title` is evaluated on this submission.
* *Validated `outline.md` (Phase 3 exit gate)*: The submission passes `OutlineValidator` exactly as on the deep lane (<<outline-validation-gate>>), after the widen-only domain merge over the declared files and followed by the single narrowing pass.
* *Server Outline Gate*: `outline.gate` follows unchanged (§ 4); the light lane never approves its own outline. A `revise` answer of the outline review ends the phase with its exit `rework`, on which the plan unit's light call states call the phase again at its entry `rework_light`, `outline.light-regate` (link:../state-catalogue/18-plan-unit-axes-short-landings.adoc#state-catalogue-plan-unit[State Catalogue, Plan Unit]); that state re-runs the budget check over the outline's `Affected files` and creates a new `outline.light` task on pass (a failing check ratchets the plan to `deep`).
* *Judgment Escalation*: Instead of an outline, the envelope task may submit `outcome = escalate_to_deep` with `escalation_trigger` (`premise`, `cross_module_ripple`, or `public_symbol_deletion`) and a rationale; nothing of the envelope is persisted besides the escalation record.

=== Lane Ratchet Rules

1. *Unknown Scope Bias*: At initial routing, an unknown or unresolved `scope_estimate` biases fail-safe to `deep`. Conversely, an unset `change_type` does **not** force `deep` when `scope_estimate` and target files are bounded.
2. *One-Way Escalation (`light -> deep`)*: The engine ratchets a `light` plan to `deep` (locking `planning_lane = "deep"`, `track = "complex"`, `lane_escalated = true`, and `escalation_trigger` permanently for the plan) whenever the *Deterministic Budget Trigger* fires in the light gate (<<light-gate>>, including `neighbours_indeterminate` and `baseline_conflict`), the *Scope-Lane Consistency Check* finds a recorded `scope_estimate` of `broad` or `multi_module` on the `light` plan (`escalation_trigger: scope_lane_mismatch`), or the *Judgment Escalation Trigger* fires (the envelope submits `outcome = escalate_to_deep` because it found a false request premise, cross-module ripple effects, or public symbol deletions requiring a full consumer sweep). The escalation is a first-class engine transition into `refine.baseline-reconcile`: from `init.light-gate` the plan enters Phase 2 normally; from `outline.light` or `outline.light-regate` the collapsed Phase 2 record is superseded (`phase_2_mode = full`), the phase is set back to `phase-2-refine`, and the deep pipeline runs fresh.
3. *No Down-Ratchet*: No transition exists from `deep` to `light`. Even if Phase 3 discovery later narrows `scope_estimate` from `multi_module` to `surgical` (which may enable the Q-Gate surgical bypass), `planning_lane` remains `deep`.
4. *Minimum Lane (team configuration)*: The only lane setting is the team key `plan.phase-1-init.minimum_lane` in `.marshall/config/workflow.json` (`light` default: the initial router decides; `deep`: every plan runs the deep lane, `plan-marshall`'s `deep_lane: always`). *Deliberate change vs. `plan-marshall`*: a forced `light` lane (`deep_lane: never`) and switching off the escalation ratchet (`plan.phase-1-init.escalation`) do not exist, because they can only skip a check the router or the ratchet would run; the ratchet always applies. A `deep` minimum is recorded in `audit.jsonl` as the lane decision's reason.

[#land-lane]
== Land Lane (`local_changes`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-77[PM-WATCH-PHASE-77], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-89[PM-WATCH-PHASE-89]_

A plan started with `local_changes` lands changes the operator already made; it has no model implementation work. Its lane `land` stands next to `light` and `deep` but is not part of the planning lane ratchet: it is fixed at plan creation and never converts to `light` or `deep`, and no plan converts into it. Its states are catalogued in the link:../state-catalogue/03-plan-phases-4-5-land.adoc#state-catalogue-land[State Catalogue, Land Lane: `land`].

1. *Init*: `init.classify` runs the sibling collision detector over the captured paths and resolves the workflow settings; the planning-lane router does not run. The plan's landing commits: while the project's landing in force is `landing.files`, `start.sources` does not offer the local changes and shows the reason naming the project's setting `landing` (xref:01-planning-phases-1-2.adoc#_plan_source_contracts[Plan Source Contracts]). `status.metadata.pr_title` is set from the source's `summary`; without a `summary` it is derived from the `plan_id` and marked `pr_title_stale`, so `create-pr` requires the retitle submission. The plan instance is composed at plan creation (<<plan-instance-composition>>) over the captured footprint, with no tasks, and with the land composition rules applied (item 4).
2. *Skipped Work*: The plan unit calls no `refine`, `outline`, or `plan` phase, and its `execute` phase runs no task work (no deliverables, tasks, envelopes, or chain-tail commits): it calls the `land` sub-workflow instead (xref:01-planning-phases-1-2.adoc#plan-unit-phases[The Plan Unit as a Workflow of Phases]).
3. *Verification*: `land.worktree-init` creates the plan's branch at the capture's snapshot commit and its worktree as `execute.worktree-init` does, restores the main checkout's captured paths where their digest still matches, and re-records `entry_baseline` (the capture mechanic of the `local_changes` source, xref:01-planning-phases-1-2.adoc#_plan_source_contracts[Plan Source Contracts]). `land.verify-sweep` then runs the verification of execute's exit over the captured footprint: the Phase 5 verification steps of the plan instance with the footprint-driven scope and relocation override (xref:03-q-gate-and-execute.adoc#_whole_tree_verification_gates_triage_required_routing[Whole-Tree Verification Gates & `triage_required` Routing]), the baseline-red server rule, and the footprint check that the realized footprint of the worktree equals the captured `declared_files`. The `land.*` states form the sub-workflow `land`, called within the phase sub-workflow `execute`, so their phase is `phase-5-execute` (`mcp/status.json` `phase`). `land.exit-barrier` evaluates the Phase 5 exit barrier (xref:03-q-gate-and-execute.adoc#_phase_5_exit_barrier_dual_freshness_pending_tasks_gates[Phase 5 Exit Barrier: Dual Freshness & Pending-Tasks Gates]) with zero tasks; the clean-tree and freshness gates apply unchanged. The plan then enters `phase-6-finalize` with every guarantee: step verdicts and verdict currency, the pre-merge barrier, the merge record, and the landing.
4. *Failures Without Model Authorship (Composition Rules)*: The model never authors the landed change. The restriction is data of the plan-instance composition, not a special state family: the shipped default composition rule file (versioned like the templates) binds every remediation policy call of a `land` plan with `actions: [retry]` (its `decide` is server logic: `retry` within the budget, then `exhausted`; no task decides, and neither the `loop_back` form of `fix` nor an in-branch fix is offered), and prunes task allocation with prune reason `land_lane`; the same rules prune `simplify` and run `security-audit` findings-only. A failed verification therefore calls `remediation.build-failure` with the land budgets (retry `1`, fix `0`), and every exhausted policy takes `finalize.hand-back`: the pull request (or branch) carries the operator's change with the failure documented, and the operator fixes it on the branch after the run, outside any plan guard. The capture is one-shot and never repeated (xref:01-planning-phases-1-2.adoc#_plan_source_contracts[Plan Source Contracts], `local_changes`). Team overrides of the composition rules are a later improvement; the shipped rule file applies.
5. *Capture Ref Retention*: On `merged`, the post-merge actions of `finalize.merge-dispatch` and `finalize.merge-queue-wait` (or, with `landing.main`, of the base push, xref:06-finalize-re-entry-and-merge.adoc#landing-variants[Landing Variants]) compare the tree of the `declared_files` at the capture snapshot with that tree at the merged plan head, ignoring paths the base changed: when they are equal, `refs/pm-mcp/captures/<plan_id>` is removed; otherwise the ref is kept and the owed item `capture_ref_retained` is written. The server never moves the main checkout: local commits the plan carried that landed squashed stay on the operator's branch and are written as an owed `cleanup` item naming the operator command. Every other ending (`handed_back`, `cancelled`, `abandoned`, `released`, `aborted`, and `delete-plan`) keeps the ref and writes the owed item `capture_ref_retained` (link:../store-schemas/03-findings-and-review-records.adoc#owed-item-record[Store Schemas Specification, Owed Item Record]), so the operator's captured changes stay recoverable. The operator removes a retained ref with `pm-operator drop-capture <plan_id>` (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-drop-capture[CLI, Coordination & Security Specification]); the recovery sweep never touches it.

[#adopt-lane]
== Adopt Lane (`pr`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-76[PM-WATCH-PHASE-76], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-84[PM-WATCH-PHASE-84]_

A plan started with `pr` repairs an existing pull request; it has no planning work. Its lane `adopt` is, like `land`, fixed at plan creation, outside the planning lane ratchet: it never converts to `light` or `deep`, and no plan converts into it.

1. *Init*: `init.classify` runs the sibling collision detector over the pull request's changed paths (`declared_files`) and resolves the workflow settings; the planning-lane router does not run. The plan unit calls `init` and then `finalize`, entered at `finalize.adopt-pr`. The plan instance is composed at plan creation (<<plan-instance-composition>>) over `declared_files`, with no tasks; the composition prunes `create-pr` with reason `adopt`, because the pull request already exists.
2. *Verification*: the plan's verification is the finalize pipeline itself: `pre-push-quality-gate` (`10`) over the whole tree and the push freshness gate of `default:push` (`11`, applied when a push is required).
3. *Baseline Sync Checks Only*: `sync-baseline` (`3`) never rebases an adopted branch: it fetches, records `upstream_commit_count`, and completes with `action` `noop` or `check`. A rebase happens only in `finalize.merge-sync` under the rule of xref:06-finalize-re-entry-and-merge.adoc#merge-path[Merge Path (`branch-cleanup`)], item 3, with the explicit lease and the handling of item 3 there.
4. *Ending*: the plan's own steps never close the pull request; every run that ends without a merge is `handed_back` through `finalize.hand-back`, which leaves the pull request open with the gap comment (xref:01-planning-phases-1-2.adoc#plan-outcomes[Plan Outcomes & Fallback Routes]); only the operator, cancelling or abandoning the plan, may choose to close it. The adopt lane lands only by `landing.pull-request`.

[#outline-validation-gate]
== Phase 3 (`outline`): Validation Rules & `outline.gate`
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-4[PM-WATCH-PHASE-4]_

When the outline task submits the solution outline in `outline.light` or `outline.deep`, it submits it as the *outline record* `outline:schema[outline-record]` (link:../store-schemas/06-task-and-references.adoc#outline-record-store[Store Schemas Specification, Outline Record]), never as prose; the server keeps the record in `outline.json` and renders `outline.md` from it for the operator, the pull request, and the issue write-back. The submit primitive validates the record before accepting the transition; validation is not a state of its own, and a rejected submission leaves the plan in the submitting state with `rejected.reason = "invalid_link_args"`. The schema decides the structure: every deliverable carries its fields, and every list member its parts, so a missing or misspelled field is refused at its JSON pointer and nothing is parsed from text. The server-side `OutlineValidator` then enforces four structural invariants, validates each deliverable's `added_dependencies` (§ 5), its `satisfies` against the intent record (§ 6), its `interfaces` (§ 7), and its `key_links` (§ 8), and runs the *derivation dry-run*: the Phase 4 profile mapping, the `TaskGraphValidator` over the would-be task graph, and the verification-command coverage (Phase 4, items 1–2). A non-derivable outline is refused like any other invalid one, so a derivation failure surfaces where the model can fix it.

=== 1. Per-File Intent Marker Validation
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-3[PM-WATCH-PHASE-3], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-65[PM-WATCH-PHASE-65]_

Every member of a deliverable's `affected_files` carries an intent from a closed 5-value enum (shown here in its rendered form):

[cols="1,2,3"]
|===
|Intent Marker |Syntax Example |Pre-Execution `files_exist` Gate Semantics

|`read`
|``- `src/main/java/Foo.java` (read)``
|Consulted as read-only reference. The `files_exist` gate is satisfied when the path (after glob expansion) exists on disk, or when a deliverable in the transitive `depends:` closure declares it `write-new`; a glob is judged on its expansion, never on the literal. Recorded in `references.json` under read-only references, disjoint from expected modifications.

|`write-new`
|``- `src/main/java/Bar.java` (write-new)``
|Created fresh by the deliverable; file **must not exist** on disk prior to execution (flags a Q-Gate finding if already present).

|`write-replace`
|``- `src/main/java/Baz.java` (write-replace)``
|Modified in place; file exists on disk and is recorded in the declared modification footprint.

|`write-conditional`
|``- `src/test/resources/baseline.json` (write-conditional)``
|Modified only if a gate named in the deliverable fires (for example a snapshot baseline refreshed only when the snapshot test turns red). The file must exist on disk (same rule as `read`). Stored in `references.json -> derived_files.conditional_modifications`: excluded from the footprint coverage denominator and never reported as `modify_shortfall` when untouched, but inside the declared write set, so a touch is never recorded as an unplanned change.

|`delete`
|``- `src/main/java/Old.java` (delete)``
|Removed by the deliverable; file **must exist** on disk prior to execution (with the same glob-expansion and `depends:`-closure rule as `read`) and triggers the whole-tree verification gate in Phase 5.
|===

Every `affected_files` member carries its `path` and exactly one `intent` from the closed enum `read`, `write-new`, `write-replace`, `write-conditional`, `delete`; a member without one, or with another value, is refused by the schema. The rendered `outline.md` shows each member as ``- `<path>` (<intent>)`` under `**Affected files:**`, the form of `plan-marshall`. Furthermore, if a deliverable changes a default value, constant, or enum member, the *value-change test-sweep rule* requires all existing test files asserting the old value (discovered identifier-first) to be listed in `Affected files` with `(write-replace)`.

=== 2. Six-Bucket File-Type Classifier & `module_testing` Profile Requirement

For each deliverable, the server classifies its write-intent `Affected files` via the domain build extensions into one of six closed file-type buckets and validates the deliverable's declared `profiles[]`:

[cols="1,2,3"]
|===
|File-Type Bucket |Path Composition |Mandatory `profiles[]` Assignment

|`production_only`
|Production source files only
|`[implementation, module_testing]` — `module_testing` is **mandatory**.

|`test_only`
|Test source files only
|`[module_testing]` only.

|`mixed_code`
|Production and test source files (no docs)
|`[implementation, module_testing]` — `module_testing` is **mandatory**.

|`mixed_with_docs`
|Production/test source files plus documentation files
|`[implementation, module_testing]`, with `module_testing` scoped strictly to the code/test paths.

|`documentation_only`
|Documentation or markdown files only
|`[implementation]` only — `module_testing` is **prohibited**.

|`unknown`
|Unclaimed file extension or path
|*Blocks Deliverable*: Emits a blocking finding requiring path correction or build-extension mapping; never silently falls back to `documentation_only`. A path the build map routes as build-neutral (for example `.github/**`) is not `unknown`: it is `no_module` (xref:03-q-gate-and-execute.adoc#_whole_tree_verification_gates_triage_required_routing[Whole-Tree Verification Gates & `triage_required` Routing], Footprint-Driven Scope) and neither blocks the deliverable nor widens a gate.
|===

=== 3. Single Domain Narrowing Pass

Immediately after `outline.md` passes structural validation, the server re-derives the plan's active domain set from the union of all deliverables' declared footprints (`Affected files`) and narrows `metadata.domains` **exactly once**. This removes any temporary over-provisioned domains introduced during Phase 2's widen-only union before Phase 4 resolves task skills. A narrowing that removes a domain sets `status.metadata.pr_title_stale` (the title was authored for the wider scope). The pass appends an `outline.domain-narrowing` decision record with the domains it removed.

[#outline-gate]
=== 4. Server Outline Gate (`outline.gate`) & Outline Review
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-58[PM-WATCH-PHASE-58]_

Outline approval is a server gate, not an operator decision. After the outline passes validation and its Q-Gate (deep lane), or directly after validation where no Q-Gate runs on the path (light lane, surgical bypass), the plan enters the `auto` state `outline.gate` *while remaining in `phase-3-outline`* (Phase 3 is never marked `done` before the gate passes). The gate passes when the outline Q-Gate policy returned `resolved` or `waived` (or no Q-Gate runs on the path), the derivation dry-run passes against the current inputs, and no `3-outline` finding is pending; it then enters `plan.derive-tasks`. Every evaluation appends an `outline.gate` decision record with the pending `3-outline` findings, the dry-run, and the Q-Gate outcome (link:../model-work/11-decision-records.adoc#decision-points[Model Work Specification, Decision Points]). No configuration key removes the gate (a compiled invariant of the `outline` unit, link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Compiled Invariants]).

* *Outline Review*: Where the plan's asking variant waits at the outline (link:../workflow-dsl/09-plan-instance.adoc#plan-axes[Workflow DSL Specification, Plan Behaviour Axes]), the passed gate raises a server decision `outline.review` (class `review`) with the outline as context and the options `approve` and `revise` (free `text`, recorded as an intent amendment), delivered to both clients as an operator wait without a time limit (xref:07-questions-waivers-operator-influence.adoc#questions-waivers-operator-influence[Questions, Waivers & Operator Influence]); where the asking variant does not wait there, nothing is asked (link:../state-catalogue/09-bootstrap-and-lessons.adoc#options-when-needed[State Catalogue, Asked When Needed]). `approve` enters `plan.derive-tasks`; `revise` ends the phase with its exit `rework`, on which the plan unit's call states of the plan's lane call the phase again at the lane's authoring entry (`outline.deep`, or `outline.light-regate` for a light plan, <<light-gate>>; link:../state-catalogue/18-plan-unit-axes-short-landings.adoc#state-catalogue-plan-unit[State Catalogue, Plan Unit]) with the revision text in `facts`, charged to the `fix` budget of `remediation.qgate-findings` because the revised outline passes the outline Q-Gate again. The decision and the current state are persisted.
* *Issue Write-Back*: For a plan from an issue of the project's own repository with the team configuration's `issues.write_back` set, the passed gate posts the approved outline to the issue (`ci.issue-comment`; xref:01-planning-phases-1-2.adoc#_plan_source_contracts[Plan Source Contracts], `issue`), after the outline review where one is asked.
* *Dependency Approval*: `outline.gate` renders the union of all deliverables' `Added dependencies` sections in `facts` as `added_dependencies[]` (each coordinate with its deliverable; an explicit empty list when the outline adds none). The gate's pass fixes exactly these coordinates as the plan's approved dependency set (§ 5), which the pre-merge Dependency Delta Check (xref:05-finalize-review-metrics-descriptor.adoc#dependency-delta[Dependency Delta Check (Pre-Merge)]) verifies.
* *No Silently Carried Q-Gate Findings*: Blocking `3-outline` findings are settled by the Q-Gate policy (fixed, or accepted-by-waiver under `qgate_findings:outline`). Non-blocking `3-outline` findings still `pending` when the gate evaluates are dispositioned `ACCEPT` by the server with the recorded reason `non_blocking_at_gate` and listed in `facts` and in the pull-request body; the gate never passes with a pending `3-outline` finding (Blocking Findings Guard).
* *Residual Derivation Failure*: When `plan.derive-tasks` nevertheless fails (an input changed between the gate and derivation, for example the skill registry), the phase is set back to `phase-3-outline`, the failure is filed as a blocking `3-outline` Q-Gate finding, and the plan enters the outline Q-Gate remediation (xref:03-q-gate-and-execute.adoc#_q_gate_validation_loop[Q-Gate Validation Loop]), whose exhaustion ends `returned`.
* *Deliberate change vs. `plan-marshall`*: its `plan_without_asking` flag is generalised by the asking axis, and its `AskUserQuestion` outline approval does not exist; the gate is always evaluated, and the operator's review is the decision above, asked where the asking variant waits at the outline.

=== 5. `Added dependencies` Section
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-60[PM-WATCH-PHASE-60]_

A deliverable that introduces a new third-party dependency names it in its `added_dependencies`. Each entry is one ecosystem-qualified `coordinate` from a closed ecosystem set, without a version, with its justification: `why` the plan needs it and the simpler `rejected_alternative` (the standard library, a facility already in the tree, a dependency already installed) and why it was rejected. Both justification parts are required; the Q-Gate judges whether they hold, the server only that they are there. The coordinates:

* `maven:<groupId>:<artifactId>` for Maven and Gradle build files (for example ``- `maven:org.jspecify:jspecify` ``);
* `npm:<name>` for `package.json`, including scoped names (``- `npm:@scope/name` ``);
* `pypi:<name>` for `pyproject.toml`, compared in its PEP 503 normalized form.

An entry with an unknown ecosystem prefix or a coordinate that does not match its ecosystem's grammar, and a coordinate named twice in the outline (within one deliverable or across deliverables), is rejected with `rejected.reason = "invalid_link_args"` naming its JSON pointer. A deliverable with an empty list adds no third-party dependency; the section never lists the project's own modules. A version change of an existing dependency is not an addition and is not listed.

The union of the `added_dependencies` of the outline record that passed `outline.gate` is the plan's *approved dependency set*; `outline.gate` shows each coordinate with its justification. Like `declared_files` it is immutable after the gate passed; adding a coordinate later requires an outline revision through `loop_back_outline` (xref:03-q-gate-and-execute.adoc#_task_envelope_execution_independent_server_verification[Task Envelope Execution], Loop-Back to the Outline).

[#outline-satisfies]
=== 6. `satisfies` Coverage
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-110[PM-WATCH-PHASE-110]_

A deliverable names the parts of the plan's intent record it implements in its `satisfies` (xref:01-planning-phases-1-2.adoc#intent-record[Intent Record]); each entry is one identifier of the record's `criteria` (`AC-<n>`) or `decisions` (`DC-<n>`). `OutlineValidator` refuses the outline with `invalid_link_args`, naming the JSON pointer or the identifier, when:

* an entry names an identifier the current record does not hold, or names a `deferred` item (`DF-<n>`), which no deliverable may implement;
* a criterion of the record is named by no deliverable (every criterion is covered);
* a deliverable has an empty `satisfies`;
* a deliverable that satisfies an `unchanged` criterion verified by `test` depends, directly or through others, on a deliverable that satisfies a `new` or `fix` criterion and no `unchanged` one: the guard of behaviour that must not change comes before the change it guards. The refusal names both deliverables and the criterion. A deliverable that satisfies both kinds is not refused: the check does not look inside a deliverable.

*Outline role skill*: where the intent record marks a `riskiest` assumption that is `unverified`, the outline's first deliverable (one without a dependency) carries the assumption's test, so a wrong premise fails before the work that rests on it; the role skill states this as guidance (class `guidance`), and the Q-Gate judges it with the other outline findings. A risk the outline sees is stated the same way, never as prose of a deliverable: as the verification of a deliverable that satisfies an `unchanged` criterion, or as the test of an assumption; a risk that fits neither goes back to the record through the outline review's `revise`.

The coverage is computed, never judged: the Q-Gate judges whether a deliverable does what its list claims (the validator `Task description fidelity` and the outline review), not whether the list is complete. A plan with no intent record (a recipe workflow that does not call refine) submits empty `satisfies`, and § 6 does not apply to it. The union of the lists is carried into the derived tasks of each deliverable and listed in the pull-request body, each criterion with the deliverables that satisfy it.

[#outline-interfaces]
=== 7. `interfaces`

A deliverable that shares a contract with another deliverable or with code in the tree may declare it in its `interfaces`: each member names its `direction` (`produces` or `consumes`), the `symbol` (a fully qualified name), and its exact `signature`. The list is optional; where it is given, `OutlineValidator` refuses the outline with `invalid_link_args`, naming the member, when a consumed symbol is neither produced by a deliverable in the consumer's transitive `depends:` closure (same symbol, same signature) nor found in the tree by `pm_lsp workspace_symbol` with that signature (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/02-service-and-skill-tools.adoc[MCP Tools Specification, `pm_lsp`]). While the language server of the module is not ready, a symbol of the tree is reported `unverified` in `facts` and the outline is not refused for it. The produced and consumed signatures are carried into the descriptions of the deliverable's derived tasks.

[#outline-key-links]
=== 8. `key_links`
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-108[PM-WATCH-PHASE-108]_

A deliverable may declare how its new code is wired into the system in its `key_links`: each member names the file the link lives in (`from`, a path of the deliverable's write set), what it connects to (`to`, a symbol or a path), and a `pattern` (a regular expression of at most `500` characters) that matches in `from` when the link exists. The server evaluates patterns with a linear-time matcher (no backreferences, no lookaround) and refuses at submission a pattern it cannot compile in that dialect, so a model-supplied pattern cannot stall the runtime. The list is optional. In the verification sweep of Phase 5 (xref:03-q-gate-and-execute.adoc#_whole_tree_verification_gates_triage_required_routing[Whole-Tree Verification Gates]) the server checks every key link of every completed deliverable against the worktree, in-process and without a model: a pattern that does not match in its `from` file is a failure `key_link_missing` naming the deliverable and the link, ingested and remediated like a failed verification step. A green build proves that the code compiles; a key link proves that it is called.

== Phase 4 (`plan`): Task Derivation, DAG Validation & Instance Composition

Phase 4 transforms the structured deliverables of the gated `outline.md` into executable `TASK-NNN.json` files and task envelopes, and composes the plan instance version of event `plan` (<<plan-instance-composition>>).

=== Deterministic Task Derivation & DAG Cycle Detection
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-7[PM-WATCH-PHASE-7], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-8[PM-WATCH-PHASE-8], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-16[PM-WATCH-PHASE-16]_

1. *Profile-to-Task Mapping*: For each deliverable $D_i$ in `outline.md`, the engine generates one task per declared profile in fixed intra-deliverable order (`implementation` $\rightarrow$ `module_testing` $\rightarrow$ `verification`), copying the deliverable's `intent_gloss` verbatim into each derived task's description. A verification command the deliverable declares is copied verbatim into `verification.commands` of its tasks (placeholders are substituted at execute); a deliverable that declares a command whose tasks would receive none is a derivation failure, never a silent fallback to a module-level command.
2. *Dependency DAG Construction & Cycle Rejection*: Inter-deliverable `depends:` declarations map the head task of $D_i$ to the tail task of each prerequisite deliverable $D_j$, and each task of a deliverable depends on its predecessor in the fixed intra-deliverable order; the edges are persisted in each task's `depends_on` (link:../store-schemas/06-task-and-references.adoc#_task_record_schema_taskstask_nnn_json[Store Schemas Specification, Task Record]). `TaskGraphValidator` runs Kahn's topological sort and depth-first cycle detection over the complete task graph; any self-dependency, unresolved task or deliverable reference, or cycle (`TASK-A -> ... -> TASK-A`) fails validation before any task file is written. The same check runs server-side on every later task creation or amendment and refuses the write (`invalid_link_args` with `task_dependency_unresolved` or `task_dependency_cycle`).
3. *Two-Tier Skill Resolution*: Each task is assigned `skills[]` (`skill://pm/...` URIs) by combining system persona skills (`skill://pm/core/SKILL.md`, profile vocabulary skill) with domain-resolved skills for the deliverable's `(domain, module, profile)` tuple. A `verification` task resolves only the core skills and no domain skills; its steps are the verification commands (as `plan-marshall` `phase-4-plan/SKILL.md`, profile `verification`).
4. *Atomic Non-Idempotent Task Creation*: All derived tasks are persisted in a single atomic batch (`batch-add`). Task creation is strictly non-idempotent: once `tasks/TASK-*.json` files exist for the plan, the engine omits the task-creation link on any re-entry into Phase 4, preventing duplicate task generation. The outline gate's derivation dry-run makes a failure here residual; it is handled as in § 4 of Phase 3 (Residual Derivation Failure). Q-Gate findings on the task bundle are remediated only through *Targeted Task Revision*: the `fix` of `remediation.qgate-findings` returns `fix_requested`, which enters `plan.revise-tasks`, a `job llm` state of role `plan` whose task carries the findings in `facts.qgate_findings`. Its entity offers `revise:TASK-NNN` for each task that carries a blocking finding, with the free parameters of `plan.describe-tasks` for that task (`description`, `steps`, `target_files`, `depends_on`) and the same validations (declared-path discipline, dependency graph check), and `revalidate`, which re-enters `plan.qgate`; a `revalidate` with no revision since the last verdict is refused with `fix_unchanged`. A revision changes only the named task, never the task set: no task is added or deleted. A finding that needs a structural change (a different task split, a missing or superfluous deliverable) is resolved only by the task's `loop_back_outline` submit from `plan.revise-tasks` to Phase 3 (xref:03-q-gate-and-execute.adoc#_task_envelope_execution_independent_server_verification[Task Envelope Execution], Loop-Back to the Outline), or ends in the Q-Gate policy's `exhausted` (`returned`). *Deliberate change vs. `plan-marshall`*: its Phase 4 Q-Gate auto-loop clears the existing task set and re-runs task creation from scratch (clear-and-replan); `PM-MCP` keeps the task set and revises only the tasks named by blocking findings.
5. *Server-Side Cost Sizing, Envelope Bin-Packing & Instance Composition*: Upon `plan.describe-tasks` submission, the server automatically executes three deterministic passes in-process (without exposing separate LLM-driven `pack-envelopes` or `compose-manifest` states):
** `TaskCostEstimator` computes `cost_size` (`XS | S | M | L | XL | XXL`) for each task from its step count, profile, skill count, and target file count, and stamps `predicted_cost_tokens`, the size-to-token table value of that size, labelled `uncalibrated` until the server has recalibrated the table from measured metrics (link:../model-work/06-envelopes-questions-deadlines.adoc#cost-sizing[Model Work Specification, Cost Sizing]); the prediction sizes the envelopes and is the reference of the worker signal `over_size` (link:../model-work/03-supervision-and-recycling.adoc#worker-off-track[Model Work Specification, A Worker Off Track]), never a limit of the plan.
** `EnvelopePacker` groups the tasks, topologically ordered over `depends_on` (ties broken by `task_id`), Next-Fit into task envelopes (`envelope-1..M`) bounded by the configured per-envelope budget, merges an envelope below the minimum envelope work of `10K` into an adjacent compatible one, and stamps `envelope_id` on each `TASK-NNN.json`. Tasks share an envelope only when they target the same module and the execute unit names the same role for them (the execution profile is not a sharing criterion), so a deliverable's `implementation` and `module_testing` pair shares one envelope task's context.
** The server composes the plan instance version of event `plan` (tasks and steps known; provider and footprint prunes, each with its prune reason and source fact; policy budgets bound with provenance).
6. *Declared-Path Discipline in Task Descriptions*: A task description or step submitted via `plan.describe-tasks` or `revise:TASK-NNN` that names a path outside its deliverable's `affected_files` is rejected with `invalid_link_args` naming the path; the outline must be revised or the path declared, and the step is never silently dropped. (During execution an envelope task may still change further files inside the worktree; those are recorded as unplanned changes, xref:03-q-gate-and-execute.adoc#unplanned-changes[Unplanned Changes].)

[#plan-instance-composition]
=== Plan Instance Composition (Posture, Prunes & Budgets)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-99[PM-WATCH-PHASE-99]_

Every plan executes its own *plan instance*: real DSL units the server composes from the templates (the plan unit, the phase sub-workflows it calls, the variants of the plan's axes, and the remediation policy units, each resolved by level: the project's copy, else the machine's, else the compiled default, link:../workflow-dsl/04-ast-node-model.adoc#process-designer[Workflow DSL Specification, Designing a Process]; for a recipe's plan the recipe's workflow in place of the plan unit) and the plan's facts (link:../workflow-dsl/09-plan-instance.adoc#plan-instance[Workflow DSL Specification, Plan Instance]; storage in link:../store-schemas/14-plan-instance-waivers-questions.adoc#plan-instance[Store Schemas Specification, Plan Instance]). The facts stay where they are owned and are never duplicated (configuration in its stores, waivers in `waivers.jsonl`, lane, deliverables, footprint, and tasks in the plan stores); the instance carries their *effect* with provenance: the phases the plan unit calls (a phase it does not call is a pruned call with its reason), the chosen variant of each axis (the others pruned with reason `plan_default`), the units used with their level, every pruned step with its prune reason and source fact, every policy call with its bound budgets and their source, gates marked waived with the waiver id, and a header with the digests of every input. The step list *is* the instance, and the header binds the configuration.

* *Versions & Events*: The instance is immutable and versioned, one file per unit and version (`instance/plan.v<N>.pmwf` for the plan unit with the instance header, `instance/<unit>.v<N>.pmwf` for each phase sub-workflow and axis variant it composes, such as `instance/phase-6-finalize.v<N>.pmwf`), with an append-only `instance/composition.jsonl`, `instance_version` in `mcp/status.json`). A new version is composed on exactly the closed `composition_event` set: `start` (version 1 at plan creation: the phase calls of the source's lane, both planning lanes open, the axes' variants bound, posture prunes where a posture is set), `override` (a plan's own value set where the plan first needs it or later, the asked posture among them, link:../workflow-dsl/09-plan-instance.adoc#plan-overrides[Workflow DSL Specification, Plan Overrides]), `outline` (lane known: the states of the other lane pruned with reason `other_lane`, link:../workflow-dsl/09-plan-instance.adoc#composition-rules[Workflow DSL Specification, Composition Rules]), `plan` (tasks and steps known; provider and footprint prunes; budgets bound), `config_adopted`, `waiver` (a `met` waiver, a `raise`, or an `unwaive`), `fallback` (the post-run-only form of `plan.return` and `finalize.hand-back`), `empty_harvest` (the post-run-only form of a recipe's workflow whose harvest yielded no targets), and `replan` (a re-planning or a revision the operator accepted in a chat, xref:08-dynamic-re-planning.adoc#replan-apply[Dynamic Re-Planning]). A loop-back to Phase 3 re-runs the `outline` and `plan` events; completed history and firings are never rewritten.
* *Position Rule*: A new version takes effect at the next transition, never mid-state, and is valid only if it contains the current state and every state of the `call_stack` (state ids are stable across versions). A version triggered by the operator (a configuration change, a waiver, a plan setting) that fails the rule is refused; a server event (fallback, empty harvest) is composed in the transaction that enters its target state. The compiled invariants are checked on every version.
* *Posture Lattice*: `minimal` $\sqsubset$ `standard` $\sqsubset$ `full`. The posture is a plan fact, the plan's, the project's, or the machine's value, or asked where the plan's lane is chosen (xref:01-planning-phases-1-2.adoc#_deterministic_init_classifiers_workflow_settings[Init Classifiers], item 5); its effect is the set of steps pruned with reason `posture`, composed into the version that binds it, so the posture preview is the diagram of that version.
* *Posture Resolution*: Every lane-participating step has an effective tier on the lattice `off` $\sqsubset$ `minimal` $\sqsubset$ `standard` $\sqsubset$ `full`: the `lane` of its `workflow.json` entry (`plan.phase-6-finalize.steps` for an optional step, `project_steps` for a project step) when one is set, which replaces the tier; else `off` for a step whose catalogue default is off; else the tier its catalogue row states (xref:04-finalize-step-bands.adoc#_normative_step_catalogue_across_ordering_bands[Step Catalogue], for example `full` for `security-audit` and `plan-retrospective`); else its class default (`minimal` for `core` and `derived-state`, `standard` for `adversarial` and `prunable`). A step is kept iff its effective tier $\sqsubseteq$ the plan's posture, so an `off` step is never kept and a `minimal` step runs under every posture; every other step is pruned with reason `posture`. A `core` or `derived-state` step always resolves at its class default: an `off` never applies to it, because `workflow.json` cannot set its lane (Floor Immunity). *Deliberate change vs. `plan-marshall`*: `plan-marshall` resolves the same lattice and class defaults, but also takes a plan-local override ahead of the project's and ignores a weakening `off` of a floor step with an informational note; `PM-MCP` has the team's `workflow.json` as its one override source and refuses a floor-step entry at validation.
* *Floor Immunity*: Steps whose lane class is `core` or `derived-state` carry floor immunity (currently `sync-baseline`, `pre-push-quality-gate`, `push`, `create-pr`, `ci-verify`, `branch-cleanup`, `record-metrics`, `print-phase-breakdown`, `emit-landing`, `archive-plan`, and `architecture-refresh`): these are the mandatory steps, whose presence in the project's `phase-6-finalize.pmwf` unit is a compiled invariant (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Compiled Invariants]) and which `workflow.json` cannot configure (a `steps` entry for one is refused with `mandatory_step_not_configurable`). Steps without a `lane` block are not lane-participating and are always kept. Only the composition rules `local_only` and `adopt` (`create-pr` alone) and the post-run-only forms override floor immunity; the `land` rules prune no floor-immune step.
* *Local-Only Runs*: When the project has no push remote (derived fact `push_remote` empty, link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas Specification, Derived Facts Store]), the composition prunes every step that needs a remote or a pull request (`push`, `create-pr`, `ci-verify`, `automatic-review`, `analysis-roundtrip`) with reason `local_only`, and keeps `pre-push-quality-gate` and `pre-submission-self-review`, since no CI verifies the finalize mutations. `merge.gate-entry` then ends with `local_only` and enters `finalize.hand-back` in its local form; the plan ends `handed_back` with `merge_outcome: local_only`. *Deliberate change vs. `plan-marshall`*: the local-only outcome is derived from the repository, never chosen (`plan-marshall`'s `commit_and_push: false` does not exist), and `plan-marshall` also drops the two local gates; with a push remote every plan pushes, opens a pull request, and passes CI and the merge barrier. A `stale` or `failed` `push_remote` fact makes the composition `indeterminate`, never local-only.
* *Merge Left to the Operator*: When the plan's asking variant leaves the merge to the operator (link:../workflow-dsl/09-plan-instance.adoc#plan-axes[Workflow DSL Specification, Plan Behaviour Axes]), the composition prunes the merge execution of `landing.pull-request` (the states `finalize.merge-dispatch`, `finalize.merge-queue-wait`, and `finalize.merge-queue-exit`) with reason `merge_by_operator`; every gate and the pre-merge barrier stay, and a passing barrier hands the plan back with its pull request ready for review (`merge_outcome: awaiting_human_merge`, xref:06-finalize-re-entry-and-merge.adoc#merge-path[Merge Path], item 8).
* *Composition Rules as Data*: Lane-specific restrictions are declarative rules of a shipped default rule file, versioned like the templates, which prune steps, links, and policy actions (the `land` rules: <<land-lane>>, item 4). Team overrides of the composition rules are a later improvement.
* *Prune Predicates & Prune Reasons*: The provider, footprint, and change-type prunes are one composition rule each: an unset `integrations.sonar` (no code analysis provider configured; Sonar is the one shipped analysis adapter) prunes `default:analysis-roundtrip` with reason `provider_unconfigured`; a declared footprint disjoint from the code and build globs (the source files of the supported languages and the build files `pom.xml`, `package.json`, `pyproject.toml`, `Dockerfile`, and `Containerfile`) prunes `default:finalize-step-simplify` and `default:adr-propose` with reason `footprint_disjoint`; and a `change_type` of `analysis` or `verification` prunes `default:finalize-step-simplify` with reason `change_type_exempt`. None of the three prunes a floor-immune step or binds a policy argument. An unresolved `ask` seed is pruned only when its backing provider is unconfigured. Every pruned step is recorded in the instance with its reason from the closed prune-reason set (`posture`, `plan_default`, `provider_unconfigured`, `footprint_disjoint`, `change_type_exempt`, `local_only`, `land_lane`, `adopt`, `other_lane`, `merge_by_operator`, `empty_harvest`, `returned`, `handed_back`) and its source fact. A `footprint_disjoint` prune evaluates the structured-derived footprint (`references.json -> derived_files.expected_modifications`); an absent, unreadable, or empty footprint is `indeterminate` and keeps the step (never pruned, never reported clean), mirroring `VerdictCurrencyEvaluator`: absence of a footprint never means "disjoint from everything".
* *Sub-Process Calls*: The instance header lists its sub-units (`git.commit_and_push`, the `remediation.*` units) by id and digest; each call site carries its bound arguments with provenance (the template file, or the `raise` waiver id), so one sub-unit serves every call site.
* *Display*: `pm://plan/{plan_id}/diagram` renders the instance in force phase by phase (active state, pruned phases and steps with their reason, waived gates with the waiver id); `pm://plan/{plan_id}/instance[/{version}]` returns the DSL text and header; both clients of the operator show the version and the last composition event with the plan's process (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#process-resource[Runtime & Interaction Model Specification, The Plan's Process as a Structure]).

== Planning Transition Guards & Real-World Invariants
_Implementation watch: link:../../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-5[PM-WATCH-FS-5], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-58[PM-WATCH-PHASE-58], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-59[PM-WATCH-PHASE-59]_

Every phase transition out of Phases 1, 2, 3, and 4 executes a deterministic server-side guard pipeline:

[cols="2,1,4"]
|===
|Guard / Invariant |Scope |Enforcement Rule

|*Artifact Gate*
|Exits from Phases 2, 3, 4
|Refuses transition unless the phase's mandatory artifacts exist and pass schema validation: Exit Phase 2 requires a valid intent record in `intent.json` and `request.md` containing the `## Clarified Request` rendered from it; every arrival at Phase 3 requires a non-empty `status.metadata.pr_title` (a recipe's workflow that calls the phase renders it from the recipe's `pr_title_template`, link:../domain-extensions/05-recipes-and-extension-points.adoc#recipe-workflow[Domain Extensions Specification, A Recipe Is a Workflow]); on the light lane both Phase 2 requirements are evaluated on the collapsed envelope's submission, which must carry the clarified request and `pr_title` before `phase-2-refine` is recorded `done` and `outline.md` is accepted (<<light-envelope>>); Exit Phase 3 requires `outline.md` passing `OutlineValidator` and `outline.gate` passed; Exit Phase 4 requires $\ge 1$ `tasks/TASK-*.json`, an acyclic DAG, and a composed plan instance version of event `plan`. The artifacts are server-produced and every path has a producer (link:../workflow-dsl/04-ast-node-model.adoc#static-verification-rules[Workflow DSL Specification, rule 8]), so no bypass exists. *Recurring Waivers*: the server counts waived gates across plans from the `waiver_waived` records mirrored into the audit log (gate and `reason_class`, link:../store-schemas/12-machine-stores.adoc#audit-log[Store Schemas Specification, Audit Log]): a gate identifier waived in three or more plans within the `waiver_waived` records of the last 90 days, whatever the cleanup has deleted since (link:../timeouts/03-retention-host-config.adoc#cleanup[Timeouts & Budgets Specification, One Cleanup]), triggers the `lessons-capture` signal gate (catalogue row `991`) and is listed in the project's status as a recurring waiver, so a gap that is repeatedly absorbed by waivers becomes a recorded defect.

|*Clean Main Checkout Guard* (`git status --porcelain`)
|All planning transitions (Phases 1–4), and every later transition
|A plan writes its state only through server links into its directory in the per-project machine store (`<PM_MCP_BASE>/projects/<project_id>/plans/<plan_id>/`), and server-owned repository writes happen only in worktrees (the plan worktree and the shared epic worktree), so the plan has no legitimate write in the main checkout in any phase. The plan's creation transaction records `entry_baseline` (the main checkout's porcelain paths with their content digests, link:../store-schemas.adoc[Store Schemas Specification], Workflow State Store) in `mcp/status.json`. Before completing any planning transition, the daemon runs `git status --porcelain` on the main checkout; a path outside the git-ignored `.marshall/local/` that is absent from `entry_baseline` or whose digest changed violates the plan's rules: it is a hard error that refuses the transition and raises the `footprint_violation` condition on the current state (link:../state-catalogue/01-conventions-generic-conditions.adoc#condition-footprint_violation[State Catalogue, Conditions]), attributed to the plan. Baseline dirt present at entry is listed in `facts.baseline_dirty`, never blocks, and is never offered for revert. Server-owned writes never land in the main checkout (the epic ledger is written in the shared epic worktree), so a sibling plan's landing or outbox write cannot trip this guard. *Deliberate change vs. `plan-marshall`*: `plan-marshall`'s handshake refuses on any main-checkout dirt, including operator dirt the phase could not have authored.

|*`.marshall/config/` Recovery Guard*
|Plan creation and all planning transitions
|If a file under `.marshall/config/` (a team file or a workflow unit) changed in the main checkout since `entry_baseline` during a planning phase, the server **never** silently discards or commits it. The transition is refused and the condition `precondition_unmet` (reason `config_changed`) is raised on the current state (state unchanged; link:../state-catalogue/01-conventions-generic-conditions.adoc#state-catalogue-conditions[State Catalogue, Conditions]) whose `facts` name the file and the operator's two remedies (commit the config change or restore the file); its bounded `retry` re-checks after the operator acted, and a spent budget takes the fallback of the current position (xref:01-planning-phases-1-2.adoc#plan-outcomes[Plan Outcomes & Fallback Routes]). No plan starts on an uncommitted or invalid configuration: the setup gate of the start refuses while `.marshall/config/` is dirty (`config_dirty`), a team file or workflow unit fails validation (`config_invalid`), or one is at another format (`format_outdated`, `format_newer`), each with its reason and file, and creates nothing; the creation transaction re-checks the same predicates and returns the entry to `start.ready` with the reason (link:../state-catalogue/09-bootstrap-and-lessons.adoc#start-from-clients[State Catalogue, Starting from the Clients]). A `local_changes` plan is exempt from `config_dirty`: a dirty file under `.marshall/config/` is part of its captured change set, shown in `request.md` and the pull request, and its verification runs with the changed configuration (which must still verify).

|*Outside-World Invariants* (`main_sha`, `worktree_path`, instance header)
|Phase entries (Phases 2–6)
|Reports `main_sha` baseline drift (informational before Phase 5, never refusing), verifies the configuration digest of the effective configuration (compiled defaults, derived facts, team files, operator file, and the process DSL units of the project and the machine, link:../store-schemas/07-project-configuration.adoc#project-configuration-store[Store Schemas Specification, Project Configuration]; `PM-EXT-7`), and worktree consistency keyed on the plan's worktree presence in `mcp/status.json`: a non-null `worktree_path` must resolve to a live git worktree of `branch_name`; `worktree_path` must be `null` in Phases 1–4, except for a plan that returned from Phase 5 through `loop_back_outline`, whose worktree is kept and adopted again by `execute.worktree-init`, and in Phase 6 steps after `branch-cleanup` at order `> 70`, which therefore never refuse on the removed worktree (link:../filesystem-layout/01-repository-workspace.adoc#worktree-lifecycle[Filesystem Layout Specification, Worktree Lifecycle]). A plan executes against the configuration bound in the header of its plan instance version. When the current configuration digest differs (after a binary upgrade that changed a compiled default or a compiled default unit, a changed derived fact, a placed or removed machine unit, or a committed edit of a team file, the operator file, or a project workflow unit, including an edit the plan's own deliverable made), the engine composes a candidate instance version: an identical candidate is adopted and the new digest recorded; a differing candidate raises the `config_drift` condition on the phase entry state, which the server resolves itself (link:../state-catalogue/01-conventions-generic-conditions.adoc#condition-config_drift[State Catalogue, Conditions]): it adopts the candidate (event `config_adopted`) when the candidate verifies and contains the current state and every call-stack state (the position rule, <<plan-instance-composition>>), and otherwise keeps the bound version; the instance diff and the decision are in `facts`, and the decision is recorded in `audit.jsonl` and `instance/composition.jsonl`. *Deliberate change vs. `plan-marshall`*: an upgrade never re-composes an in-flight plan silently, and no handshake or baseline drift override exists. Worktree refusal errors are never bypassed.

|*Store Integrity & Digest Guard*
|Every `pm_state` / `pm_do` read
|Every server write to the plan's stores in the per-project machine store (`status.json`, `references.json`, `findings.jsonl`, `TASK-*.json`) records a SHA-256 content digest. If a host shell edits these files directly (host file tools are denied `<PM_MCP_BASE>/**`), the digest mismatch is detected on the next MCP call that takes the scope lock, which, after transaction-journal recovery, raises the `integrity_breach` condition (`kind: store_tampered`) on the current state: the integrity pause, the hold `integrity_pause` ended only by the operator's act `accept-edit` or `cancel` (the integrity abort) (link:../store-schemas/13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification]; xref:01-planning-phases-1-2.adoc#plan-outcomes[Plan Outcomes & Fallback Routes]); it is a condition, not a state change and not a `rejected.reason`. A lock-free read (`pm_state`, `pm://` resources) never decides it and reports `digest_unverified` instead.

|*Blocking Findings Guard* (`pending_findings_blocking_count == 0`)
|Exits from Phases 2, 3, 4, 5
|Refuses phase exit while any Q-Gate or verification finding with `blocking == true` remains in `resolution == "pending"` (the server-written resolution, link:../store-schemas.adoc[Store Schemas Specification], Findings Ledger Record). The exit from Phase 3 is stricter: it requires every Q-Gate finding of phase `phase-3-outline`, blocking or not, to carry a terminal disposition; `outline.gate` dispositions the non-blocking ones (Phase 3, § 4). A finding addressed to a phase the plan has already left is refused at the findings write seam with `phase_closed` (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/04-errors-and-testing.adoc#rejection-reasons[MCP Tools Specification, Closed Rejection Reasons]); only Phase 6 findings filed after the merge are carried out instead (below). In Phase 6 the pre-merge review barrier (Predicate 1) is the last findings guard; after the merge no step refuses on findings, and a blocking finding filed later is carried out and recorded in the landing (catalogue rows `1000` and `1100`). A refusal lists each blocking finding (`finding_id`, `source`, `severity`, age since `created_at`, failing predicate) in `facts`, never only a count. Independently of refusals, every phase-transition representation (including Phase 6 entry) carries `pending_findings: {blocking: N, non_blocking: M}` in `facts`.

== Direct In-Band Text Submissions (`PM-WF-2`, `PM-WF-6`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-16[PM-WATCH-STORE-16]_

Text reaches `PM-MCP` as a structured tool argument over JSON-RPC 2.0 and reaches a child tool in memory through `stdin` (`PM-EXEC-5`). No workflow operation stages text in a scratch file, writes it through a host tool, or passes it on a command line:

[cols="2,3"]
|===
|Workflow Operation |PM-MCP Direct In-Band Contract

|*Git Commit Message* (`git.commit_and_push`)
|A task of role `commit-message` submits `message: text[1..2000]` in `pm_do` `args` (or the engine uses the deterministic template). Server validates Conventional Commits, appends `Co-Authored-By` trailer, and pipes UTF-8 bytes via `stdin` to `git -C <tree> commit -F -`.

|*PR / MR & Issue Bodies and Replies* (`create-pr`, `submit:triage-groups`, issue write-back)
|The `pr-author` task submits `body: text[1..32768]` and the `triage-review` task `reply_text: text[1..4000]` directly in `pm_do` `args`. Server injects deterministic sections (`## Unplanned Changes`, `## Waivers`, `## Gaps`, `## Not Verified`, `## Builder Questions`, and `## Amendments` from the plan's records) in memory and streams to `gh pr create --body-file -` / `glab` via `stdin`; the issue write-back (the clarified request, the approved outline) is composed by the server from the plan's artifacts and streamed the same way through `ci.issue-comment`. Server-owned sections are delimited by `<!-- pm-mcp:section:<name> -->` … `<!-- /pm-mcp:section:<name> -->` markers; every render (`create-pr`, a later recorded unplanned change, waiver consumption, or amendment, and a `HEAD` advance) reads the current body first, replaces only the delimited blocks (never appending a second copy), and preserves model-authored text outside the markers. A budgeted server section is truncated only at a paragraph or list-item boundary with an explicit `… (truncated, N chars)` marker, or dropped whole with a marker, never mid-token.

|*Clarified Request Document* (`phase-2-refine`)
|The refine task submits the intent record `intent:schema[intent-record]` (xref:01-planning-phases-1-2.adoc#intent-record[Intent Record]), `pr_title`, and the six confidence dimension scores as separate `int[0..100]` parameters (`correctness`, `completeness`, `consistency`, `non_duplication`, `ambiguity`, `module_mapping`) in `submit:refine`. Server validates the record and writes `intent.json` and the rendered `request.md` + SHA-256 digest atomically. On the light lane the collapsed envelope submits `intent` and `pr_title` (no confidence scores) together with the outline in `submit:outline` (<<light-envelope>>).

|*Solution Outline Document* (`phase-3-outline`)
|The outline task submits the outline record `outline:schema[outline-record]` directly in `submit:outline`. Server validates the schema and runs `OutlineValidator` (intent markers, 6-bucket profile classifier, `added_dependencies` grammar and justification, `satisfies` coverage, `interfaces`, the derivation dry-run) in-process before persisting `outline.json`, rendering `outline.md`, and narrowing `metadata.domains`.

|*Task Creation & Descriptions* (`phase-4-plan`)
|Engine derives task skeletons in-process (`plan.derive-tasks`), the `plan` task submits enriched descriptions via `plan.describe-tasks` `args`, and server writes `tasks/TASK-NNN.json` atomically.

|*Lesson Creation & Body* (`lessons-capture`)
|The `lessons` task's single `submit` passes `title`, `component`, `category: enum[bug\|improvement\|anti-pattern\|arch-constraint]` (mirroring `plan-marshall` `manage-lessons`; re-verify before implementing), `rule` (required for `arch-constraint`, absent otherwise), `provenance: enum[run_artifact\|tool_return\|operator_action]` (set by the server where the creating transition determines it), and full markdown `body: text[1..16384]` in `args`; the server writes the lesson file (YAML front matter plus Markdown body, link:../store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Lesson Record]) atomically as revision 1, whose `sources[]` the server records from the creating transition (the plan, and the findings, jobs, or landing it names; every `ref` resolved by the server, never a caller path). A later body change replaces the body wholesale as a new revision with its own sources. The server stamps the lesson's `tool_version` from its own release version (`PM-DIST-1`) and derives its `audience` (link:../store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Audience Classification]); neither is a submit parameter. No submit parameter chooses a store or a route, so a lesson is never stored anywhere by fallback.

|*ADR Authoring* (`adr-propose`)
|The `adr-author` task submits `title`, `tags`, `affects`, and `adr_body: text[1..32768]` in the `adr` link of its `finalize.adr-author` entity; server runs `AsciiDocValidator` in-process and writes the numbered ADR file atomically.
|===
