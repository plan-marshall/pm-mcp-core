== Sanity Check (Phase between Execute and Finalize)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-13[PM-WF-13: Finalize Step Ordering Bands, Verdict Currency & Pre-Merge Barrier]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-10[PM-WF-10: Phase 1–4 Planning Invariants, Lane Ratchet & Artifact Gates]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-20[PM-WF-20: Waiting for the Operator]_

A change can pass its build, its tests, and every review and still bring what nobody reading the diff notices: a new third-party dependency resolved three levels down, a suppression comment, a character a reviewer cannot see, a credential copied from a file the worker read, a fix whose test never failed. The sanity check lists these as facts, from what the plan's change and its build produced, and the operator decides each once. Nothing in it predicts, judges, or reads text a model wrote about the change.

* *Placement*: The plan unit calls the phase `sanity-check` (unit `phase-sanity-check.pmwf`, phase value `phase-sanity-check`) between `execute` and `finalize`: after the verify sweep and the exit barrier passed, before any push and before any pull request exists. It runs for every plan whose plan unit calls `execute`, the `land` lane and a plan of a project without a push remote (local-only) included; the `adopt` lane, which calls no `execute`, meets it first before its landing (<<sanity-check-rerun>>). The phase's entry is `start`; it ends `passed`, on which the plan unit calls `finalize` at its entry `start`, or `hand_back`, on which it calls `finalize` at its entry `hand_back` (link:../state-catalogue/20-sanity-check.adoc#state-catalogue-sanity-check[State Catalogue, Sanity Check]).
* *Two Units*: The phase unit is one call of the sub-workflow `sanity-check` (`sanity-check.pmwf`, `scope subworkflow`), which holds the steps, the question, and the fix. `sanity-check.pmwf` is a designable unit: the project's copy `.marshall/config/sanity-check.pmwf` lists the steps the project runs, in their order (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Designable Workflow Units]); finalize calls the same unit again before the landing (<<sanity-check-rerun>>), so one list of steps serves both runs.
* *Scope*: A run reads the plan's change against its base: the commits of `base_ref..HEAD`, their messages, and the worktree at `HEAD`, read from git objects, together with the change ledger and the output of the plan's last build; never a model's account of the change.

[[sanity-check-steps]]
=== Steps & the Extension Point `ext-point-sanity-check-step`
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-60[PM-WATCH-PHASE-60], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-122[PM-WATCH-PHASE-122], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-123[PM-WATCH-PHASE-123], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-124[PM-WATCH-PHASE-124]_

A step is a deterministic check registered at the extension point `ext-point-sanity-check-step`: a compiled step or one a domain build extension contributes. It reads only git, the change ledger, and what the build tool states offline about the build that ran; it calls no model and uses no network. It returns *items*, each with a stable key (the step id and the item's identity in the step, never a line number, which a later commit shifts), its evidence (file and line, commit, coordinate), and whether the step supports `accept_kind` for it. A step that returns no item adds nothing to the question. A step that cannot read what it needs (a file unreadable at `HEAD` or `base_ref`, a build tool's listing that fails, an unreadable change ledger) is never clean: the run ends `indeterminate`, re-runs within the compiled server-rule retry budget (link:../timeouts/01-job-budgets-and-waits.adoc#server-rule-retry[Timeouts & Budgets Specification, Server-Rule Retry Budget]), and a spent budget takes the fallback with the cause named.

The shipped steps, in the order of the shipped unit:

. [[sanity-step-dependencies]]*`dependencies`*: the resolved dependencies and build plugins of each module, read offline from the build that ran, by the build tool of its domain: `mvn -o dependency:list` with `mvn -o dependency:resolve-plugins` for the plugins, `gradle --offline dependencies` with `gradle --offline buildEnvironment` for the plugins, `npm ls`, and `pip list` of the project's virtual environment. The step compares them with the baseline `.marshall/sanity/dependencies.json` (<<sanity-check-storage>>); every resolved coordinate with its version that the baseline does not hold for that module is an item (added), and a transitive one is grouped under the direct dependency that brings it, so the operator reads one entry per direct dependency with its transitive ones below it. A coordinate the baseline holds for that module and the build no longer resolves is an item as well (removed), answered like an added one. `accept_kind` writes every item of the run into the baseline, an added coordinate added and a removed one removed, which is how a project without a baseline sets its first one. The added, removed, and replaced coordinates (a removed and an added coordinate of the same module and scope) are what the change map shows (xref:05-finalize-review-metrics-descriptor.adoc#change-map[Change Map]); the change map reads them for the build at the current `HEAD`, so the step's offline read runs again, without a question, whenever the change map is recomputed (`finalize.settle-commit`).
. [[sanity-step-markers]]*`markers`*: a literal list over the lines the plan adds against `base_ref`: `TODO`, `FIXME`, `@SuppressWarnings`, `NOSONAR`, `noinspection`, `noqa`, `type: ignore`, `pylint: disable`, `eslint-disable`, `@ts-ignore`, `@ts-expect-error`. Each occurrence is an item (its key: the file, the marker, and the digest of the added line's text). `accept_kind` accepts the marker for the project (`.marshall/sanity/markers.json`): an occurrence of an accepted marker is no item in any later run.
. [[sanity-step-added-lines]]*`added-lines`*: mandatory (<<sanity-check-units-invariant>>). Every later plan reads the checkout as the project's own, unscreened (link:../model-work/07-untrusted-text-screening.adoc#local-trusted[Model Work Specification, What Is on This Machine Is Trusted]), so text a writer adds that a reviewer does not see but a model reads is carried on by the next plan. The step reads every text file's lines added at `HEAD` against `base_ref` (a file git classifies as binary is not read and is listed):
.. *Hidden characters*: the hidden characters (link:../job-runtime/03-parsers-and-gates.adoc#hidden-character-classes[Job Runtime Specification, Hidden Characters]), detected and never removed, except a variation selector or a zero-width joiner inside an emoji sequence and a byte-order mark at the start of a file. Each added line that holds one is an item of kind `hidden_characters`, naming the code points and their positions. An escape sequence that spells such a code point in source text is no item (matched negative control).
.. *Instructions to a model*: in a plan that read text marked untrusted (a source marked untrusted, a finding of source `github_pr`, `gitlab_mr`, or `analysis` in its findings store, third-party content a worker of the plan read, link:../model-work/07-untrusted-text-screening.adoc#third-party-content[Model Work Specification, Third-Party Content on This Machine], or, for the follow-up of a re-planning, the same of the plan it follows, xref:08-dynamic-re-planning.adoc#replan-follow-ups[Follow-Up Plans]), the rule table of the ingestion validator (stage 4) runs over the NFKC copy of the added lines; each hit is an item of kind `model_instruction` naming the rule. A plan that read no untrusted text runs no rule table, since skills, agent files, and prompts address models by design.
.. [[sanity-credential-shaped]]*Credential-shaped values*: a worker reads what its confinement allows, the project's own files (an untracked `.env`) and its harness's login included, and a value it copies into a file or a commit message is published by the push; the redaction registry cannot catch it, because the runtime never held it. This stage therefore reads the lines each commit of `base_ref..HEAD` adds and each commit's message, so that a value one commit adds and a later one removes is still found. A hit is a token of a provider prefix of the compiled credential pattern table (for example `ghp_`, `github_pat_`, `glpat-`, `sk-ant-`, `AKIA`, each with the length and alphabet of its format), the header line of a PEM private key, or an exact value of the redaction registry (link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/specification/cli-and-security/02-operator-channel.adoc#operator-credential-cli[CLI, Coordination & Security Specification, Runtime Secret Redaction]): an item of kind `credential_shaped` naming the pattern, the file and line or the commit, never the value, and a `security` audit record. A prefix without a value of its format (`ghp_` in a sentence) and a value of the pattern table's documented example set are no item (matched negative control).
. [[sanity-step-fix-proof]]*`fix-proof`*: a test that passes after a fix proves the bug is gone only if it failed before the fix, and only if it still is the test that failed. The writer role of a `fix` criterion verified by `test` writes the test first and runs it with `pm_build` (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/02-service-and-skill-tools.adoc[MCP Tools Specification, `pm_build`]); `expect: red` is an optional hint of that intent and proves nothing. Every build row of the change ledger records every test file the plan changed against `base_ref`, each path with the digest of the plan's own diff of that file against `base_ref`, and the identities of the failed tests of its parsed result. The server finds a criterion's red run in the change ledger: a run that ended `failed` before the last green run of the plan, with at least one failed test of its parsed result in a test file its row records, run by a task of a deliverable whose `Satisfies` names the criterion (xref:02-planning-lanes-phases-3-4.adoc#outline-satisfies[Phase 3, `Satisfies` Coverage]). A failure only in other files, a compile error, `failed_unparsed`, or a run that went green proves nothing. The role's task facts name the criteria that still owe a red run. Items: a `fix` criterion verified by `test` without such a red run (kind `fix_red_missing`; its `fix` is a task of the writer role that reverts the production change in the plan's worktree, takes the red run, and restores the change), and every test file holding a failed test of a criterion's red run whose diff of the plan at `HEAD` against `base_ref` differs from the digest that run's row recorded (kind `fix_test_changed`, with the difference as evidence, because a later edit may strengthen the test as well as weaken it); a rebase that brings a change of the base to the file without changing the plan's own diff of it raises no item. The `fix_red_missing` task commits nothing: its revert of the production change stays uncommitted, and whatever way the task ends (`submitted`, `infeasible`, `lost`, a spent budget), the server restores the plan's worktree to `HEAD` before the unit continues or steps out, so a hand-back never settles the reverted code. A plan whose intent record has no such criterion has no item.

A step a domain build extension contributes follows the same contract; a project adds it to its copy of the unit and removes or reorders every step but `added-lines`. Each run records its result per step (`{step, state: clean | items | indeterminate, items[], cause}`) in the plan's records and the facts of the next state.

[[sanity-check-question]]
=== The One Question

* *Nothing to Ask*: Only an `accept` and an `accept_kind` decision (<<sanity-check-storage>>) filter an item out of a run's result. A run whose items all carry such a decision passes without asking; an item answered `fix` that the run still finds stays in the result and goes to the next fix task (*`fix`* below).
* *One Question per Run*: Otherwise the unit enters one operator wait, `sanity.question` (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]), that shows every item without a decision, grouped by step, with its evidence. The wait offers per item the operator links `accept`, `accept_kind` where the step supports it, and `fix`; each answer is kept as it is given and may be changed until the wait closes, which it does when every item has an answer; `sanity.apply` then records the answers. `accept_kind` is recorded only after a confirmation that states its consequence (for `markers`: every later occurrence of the marker in this project passes unasked; for `dependencies`: every listed coordinate becomes part of the baseline that later plans trust). The plan's asking variant neither adds nor removes this wait, no quorum answers it, and it has no time limit.
* *Decided Once*: An answered item is never asked again: not in a later run of this plan, and, for an `accept_kind` or an accepted dependency, not in a later plan of the project. An item answered `fix` is not asked again either, but it is not filtered out: while the run still finds it, it drives the next fix task or the spent budget.
* *`accept`*: the item stays as it is; the decision is recorded with the item's key and evidence.
* *`fix`*: the unit creates one task of the writer role `implement` (`sanity.fix`) whose facts carry every item answered `fix` with its evidence (`fix_red_missing` items in a task of their own, which runs first and commits nothing, <<sanity-step-fix-proof>>; the other items go to the next fix task), commits its change through `git.commit_and_push`, and runs the steps again. An item answered `fix` that the run still finds is not asked again: the next fix task receives it again, bounded by the unit's `fix_budget` call argument (shipped `2`, bounded by the compiled hard cap of the link:../timeouts/01-job-budgets-and-waits.adoc#fix-budget[fix budget]). A spent budget, and a fix task that ends `infeasible` or `lost`, end the unit `stepped_out`, and the caller takes its fallback (the phase's exit `hand_back`; `finalize.hand-back` in finalize) with the open items in the gap. A `credential_shaped` item has no fix task, because a later commit that removes the value leaves it in the history the push would publish: its `fix` ends the unit `stepped_out` with the cause `credential_shaped`, and the hand-back takes its local form, which keeps the branch on the machine for the operator to remove the value from the history.
* *Land Lane*: A `land` plan's composition binds the unit with `fix_budget=0` (xref:02-planning-lanes-phases-3-4.adoc#land-lane[Land Lane], item 4): the model never authors the landed change, so a `fix` hands the plan back with the item in the gap.
* *Credential Barrier*: Independently of the question, the push stage of `git.commit_and_push` runs the credential stage of `added-lines` before every push of the plan (`default:push`, the base push of `landing.main`, every later push, and the commit the hand-back settles; link:../state-catalogue/05-git-commit-and-push.adoc#state-git.check-branch-parity[State Catalogue, `git.check-branch-parity`]): while a `credential_shaped` item has no `accept`, the push is refused and the call steps out with the cause `credential_shaped`, which its caller routes to `finalize.hand-back` in its local form.

[[sanity-check-storage]]
=== Storage

* *Team Files*: One team file per check that accepts beyond the plan, `.marshall/sanity/<check>.json` (git-tracked, owner class *team*, link:../store-schemas/07-project-configuration.adoc#project-configuration-store[Store Schemas Specification, Project Configuration]): `dependencies.json`, the baseline (per module, the accepted coordinates with their versions), and `markers.json`, the accepted marker kinds. An absent file holds nothing; a file that fails validation refuses like every invalid team file (`config_invalid`).
* *Written by the Plan's Own Commit*: On an `accept` of a dependency and on an `accept_kind`, the server writes the team file in the plan's worktree and commits it through `git.commit_and_push` with the plan's other changes, so the update lands with the plan's pull request and the team reviews it there like code. This write is the server's, on the operator's act: the protected-path check of `.marshall/**` admits exactly this file and this content (xref:03-q-gate-and-execute.adoc#protected-paths[Protected Paths]), and nothing else of a plan writes under `.marshall/sanity/`.
* *Per-Occurrence Decisions*: Every other decision (an `accept` of one marker occurrence, of a hidden character, of a `model_instruction`, of a `credential_shaped` false match or test fixture, of a `fix-proof` item) is a record of the plan: a decision-log record at the decision point `sanity.item` with the decider `operator`, the item's key, its evidence, and the answer (link:../model-work/11-decision-records.adoc#decision-points[Model Work Specification, Decision Points]). It never leaves the plan.
* *Reading*: The pull-request body lists every accepted item in the server-owned section `## Sanity Check` (xref:05-finalize-review-metrics-descriptor.adoc#pr-body-sections[Pull-Request Body Sections]), each with its step, its evidence (never a credential's value), and whether it was accepted for the occurrence or for the kind; the landing record carries the same list.

[[sanity-check-rerun]]
=== Run before the Landing

What finalize changes after the phase (an applied simplification, a remediation fix, an ADR, a rebase that needed a conflict resolution) has not been checked. Finalize therefore calls `sanity-check` again in `finalize.sanity-recheck` before every landing (link:../state-catalogue/07-plan-finalize-merge-post-run.adoc#state-finalize.sanity-recheck[State Catalogue, `finalize.sanity-recheck`]): with `landing.pull-request` on every `ready` of the merge gate `finalize.merge-gate`, which every entry of the merge path passes, so every `HEAD` the barrier evaluates passed this run; with `landing.main` and `landing.files` before every entry of their order-`70` state `finalize.land-main` or `finalize.land-files`.

* *Changes Since*: The run reads the change since the `HEAD` the last run evaluated (the whole change against the base for an `adopt` plan, whose plan unit calls no phase `sanity-check`); `dependencies` reads the latest build again. Only items without a decision are asked, in one question as in the phase.
* *Outside the Merge Lease*: The run precedes the lease request of the merge path, so the plan holds no lease while the question waits.
* *Its Commits*: A team-file update or a fix task's change commits with `push_mode=post_pr_conditional`, and the run then ends `passed_committed`, because its commit moved `HEAD`.
* *Ends*: `passed_committed` re-enters `finalize.next-step`, where Phase-Exit Completeness and verdict currency re-fire what the new `HEAD` invalidates before the lease is requested or the landing state is entered, and the order-`70` entry runs this check again; `passed`, a run that committed nothing, continues to the bound landing variant's state; `stepped_out` enters `finalize.hand-back`.

[[sanity-check-units-invariant]]
=== Compiled Invariants & Accepted Consequence

* *Invariants*: Every path of a plan that calls `execute` passes the phase `sanity-check` between the exit barrier and Phase 6, and every path to a landing passes `finalize.sanity-recheck`; the step `added-lines` is present in every copy of `sanity-check.pmwf`, and the credential barrier of the push stage holds whatever the unit lists (`INV-SANITY-1`, link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Compiled Invariants]).
* *Checked Here Only*: No earlier phase asks which dependencies a plan will add: the outline names none, no build is refused before it runs because of a dependency, no build file is parsed for dependencies, and a task's submit is not scanned for markers. The checks of what a plan changed are items the operator decides, never findings that a model triages and a waiver accepts.
* *Accepted Consequence*: a substituted package name that a worker writes into a build file is resolved and its hooks run by the plan's own builds before any review reads it; the confinement of a build job (link:../job-runtime/02-confinement-and-environment.adoc[Job Runtime Specification, Confinement]) bounds what it reaches, and the item stops it before it leaves the machine.
