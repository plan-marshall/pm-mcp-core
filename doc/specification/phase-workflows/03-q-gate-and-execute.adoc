== Q-Gate Validation, Change-Type & Unplanned-Change Contracts
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-11[PM-WF-11: Q-Gate Validation Loop, Change-Type & Unplanned-Change Recording]_

=== Q-Gate Validation Loop
_Implementation watch: link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-52[PM-WATCH-GEN-52], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-6[PM-WATCH-PHASE-6], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-10[PM-WATCH-PHASE-10], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-12[PM-WATCH-PHASE-12], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-5[PM-WATCH-PHASE-5]_

Quality Gate (`Q-Gate`) validation runs at the tail of Phase 3 (deep lane only; the light lane never runs it), at the tail of Phase 4, and in Phase 2 only for lesson-derived plans on the deep lane (narrative-vs-code validation; a light lesson-derived plan never enters Phase 2, and its premise contradictions surface through the light envelope's premise check as a judgment escalation to `deep`); the Phase 3 and Phase 4 validator populations are the table below. *Deliberate change vs. `plan-marshall`*: its Phase 2 Q-Gate runs on every plan and adds module-mapping completeness, track-scope consistency, scope realism, and confidence justification; here module-mapping existence is a server check of every refine submission and scope-lane consistency a ratchet trigger (xref:01-planning-phases-1-2.adoc#quality-dimensions[Six Quality Dimensions], Server Checks on Every Submission), while scope realism and confidence justification are dropped as covered by the `ConfidenceAggregator`. It catches structural defects (narrative-vs-code drift, missing consumer sweeps, invalid command flags, tier and architecture mismatches, and unresolved lesson citations) before advancing to the next phase.

*Task and Server Verdict*: `refine.qgate`, `outline.qgate`, and `plan.qgate` are `job llm` states of role `qgate` (xref:01-planning-phases-1-2.adoc#phase-roles[Model Work per State]) whose task submits findings from its entity. The task's completion runs the return-evaluation primitive, which executes the compiled mechanical checks of the table below and decides the verdict from the persisted findings alone: `clean` (no blocking finding pending) continues within the phase (`refine.ready`, `outline.gate`) or, in Phase 4, ends the phase with its exit `ready`, on which the plan unit calls the execute phase, `blocking` calls `remediation.qgate-findings`. The task files findings; the server decides. The task's submit carries `confidence:int[0..100]`, and the verdict appends a `qgate.verdict` decision-log record with the task as decider and the blocking findings against `0` (link:../model-work/11-decision-records.adoc#decision-points[Model Work Specification, Decision Points]). A task that ends without a valid submit takes the state's `lost` route; while `qgate` is unqualified no verdict exists, and the phase takes its fallback (`returned`).

==== Remediation Budget, `fix_unchanged` & Surgical Bypass

[cols="1,3"]
|===
|Parameter / Rule |Normative Specification

|*No Mode*
|The Q-Gate has no configurable mode in any phase: validation and remediation continue until the verdict is `clean` or the remediation budget is spent. *Deliberate change vs. `plan-marshall`*: its `q_gate_validation` knob (`off` skips validation, `once` leaves known findings open) does not exist, because both only weaken the gate; the presence of the Q-Gate states in the deep-lane `outline` and in the `plan` unit is a compiled invariant (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Compiled Invariants]).

|*Remediation Policy* (`remediation.qgate-findings`, retry `0`, fix `3`, actions `[fix]`)
|A `blocking` verdict calls the unit, whose evidence is the phase's blocking findings. Whether a task of the role `qgate` decides the remedy follows from the bound remedies: with the shipped bindings (`fix` only) the server takes `fix` without a task; a phase unit that also binds `request_waiver` (the gate `qgate_findings:<phase>` is waivable) hands the choice to the decision task (xref:01-planning-phases-1-2.adoc#_remediation_policy_calls[Remediation Policy Calls]). Its `fix` returns `fix_requested`, which the caller routes to the authoring state with the findings in `facts.qgate_findings`: `refine.analyze` (Phase 2), the outline phase's exit `rework` (Phase 3, on which the plan unit calls the phase again at the authoring entry of the plan's lane, `outline.deep` or `outline.light`, link:../state-catalogue/18-plan-unit-axes-short-landings.adoc#state-catalogue-plan-unit[State Catalogue, Plan Unit]), or the task state `plan.revise-tasks` (Phase 4, targeted task revision). The next accepted submission re-enters `<phase>.qgate`, whose `blocking` verdict calls the unit again on the same per-plan counter. An outline-review `revise` (xref:02-planning-lanes-phases-3-4.adoc#outline-gate[Outline Review]) is charged to this counter of the outline's call on the deep lane; on the light lane, where no Q-Gate runs, it is never charged to the Q-Gate budget but to the plan's own counter `outline_review_revisions`, with the same default and hard cap. The hard cap is `5`, and the operator raises the ceiling only with `--raise fix_budget:qgate-findings=N`.

|*`fix_unchanged` instead of a Content-Hash Gate*
|A remediation submission whose target artifact (the intent record in Phase 2, the outline record in Phase 3, the `TASK-*.json` bundle in Phase 4) is identical in its canonical JSON form to the one the last verdict evaluated is refused with `fix_unchanged` and charges nothing: unchanged content cannot produce a different verdict.

|*Surgical Bypass Predicate*
|In Phase 3 (`outline`), Q-Gate validation is automatically bypassed (logging `(phase-3-outline:qgate-bypass)` to the audit log) if and only if all three conditions hold on the accepted outline: `deliverable_count == 1`, its `Affected files` name at most `3` paths, and the plan's derived `change_type` (<<change-type-derivation>>) $\in \{\text{"bug\_fix"}, \text{"tech\_debt"}, \text{"verification"}\}$. *Deliberate change vs. `plan-marshall`*: `plan-marshall` applies a surgical-scope bypass of its own to its Phase 4 Q-Gate (its "B2": a surgical scope estimate and at most 2 paths in the deliverables' declared file surface); in `PM-MCP` the bypass is limited to Phase 3 and `plan.qgate` runs on every path into Phase 5 (`INV-PLAN-1`, link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Compiled Invariants]).

|*Exit Semantics*
|`resolved` continues to the phase exit; `waived` (operator waiver `qgate_findings:<phase>`) continues to the phase exit with the open blocking findings dispositioned accepted-by-waiver; `exhausted` and `stepped_out` end the phase with its exit `returned`, which the plan unit routes to `plan.return` (xref:01-planning-phases-1-2.adoc#plan-outcomes[Plan Outcomes & Fallback Routes]).

|*Convergence Record*
|Each remediation round records `findings_raised`, `findings_self_seeded` (findings located in lines changed by the previous round's fix, from the server's fix attribution, link:../store-schemas/03-findings-and-review-records.adoc#fix-attribution[Store Schemas Specification, Fix Attribution], which records `findings_cleared` and `findings_introduced` for the remediation rounds of every class) and, on exhaustion, `findings_at_ceiling` (raised in the last round, whose fixes no round reviews). The exit renders `converged` vs `oscillating` from these figures, never from the last count alone.

=== `change_type` Contract
_Implementation watch: link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-21[PM-WATCH-GEN-21]_

`change_type` classifies the intent of a plan and its deliverables using a closed 6-value enumeration orthogonal to `domain` and `profile`:

[source,java]
----
package de.planmarshall.workflow.classification;

public enum ChangeType {
    ANALYSIS("analysis", 1),
    FEATURE("feature", 2),
    ENHANCEMENT("enhancement", 3),
    BUG_FIX("bug_fix", 4),
    TECH_DEBT("tech_debt", 5),
    VERIFICATION("verification", 6);

    private final String wireName;
    private final int priorityOrder;

    ChangeType(String wireName, int priorityOrder) {
        this.wireName = wireName;
        this.priorityOrder = priorityOrder;
    }

    public String wireName() { return wireName; }
    public int priorityOrder() { return priorityOrder; }
}
----

The priority order is `plan-marshall`'s documented order (`ref-workflow-architecture/standards/change-types.md`, Priority Ordering Rationale). *Deliberate change vs. `plan-marshall`*: its planning-lane routing also knows the value `feature_breaking`, which does not exist here; whether a change breaks compatibility is the separate `compatibility` field (`breaking`, `deprecation`, `smart_and_ask`; Phase 2), never a change type.

[#change-type-derivation]
==== Server-Derived `change_type`
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-9[PM-WATCH-PHASE-9]_

Every deliverable of the outline declares its own `change_type`. The plan's `status.metadata.change_type` has one writer, the server, which derives it when the outline is accepted (`outline.deep`, `outline.light`) and again whenever an accepted revision changes the deliverables (an outline rework, a re-planning): the first mutating type of the deliverables in the priority order above (`feature`, then `enhancement`, `bug_fix`, `tech_debt`); only when every deliverable is read-only, `analysis` if one deliverable is `analysis`, else `verification`. No model classifies the plan and no heuristic reads the request text; every later reading of the plan's kind of work (the surgical bypass, the composition) reads this derived value. The derivation appends an `outline.change-type` decision-log record with the deliverables' types (link:../model-work/11-decision-records.adoc#decision-points[Model Work Specification, Decision Points]).

* *Read-Only Deliverables*: a deliverable with `change_type: verification` or `analysis` is read-only by definition; if any of its `Affected files` carries a mutating intent (`write-new`, `write-replace`, `delete`), `OutlineValidator` refuses the submit with `invalid_link_args`, detail `change_type_scope_disagreement`, before the outline is accepted, and the plan instance composition never meets such an outline.
* *Deliberate change vs. `plan-marshall`*: its keyword heuristic over the request and its model fallback classify the plan before any deliverable exists; here the plan's type follows from the deliverables it was planned with.

[#unplanned-changes]
=== Unplanned Changes (Recorded, Not Reviewed)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-14[PM-WATCH-PHASE-14]_

The declared footprint (`declared_files`, fixed when `outline.gate` passes) is the plan's statement of intent, not a fence inside the worktree. An envelope task that needs to change a file beyond its deliverable's `Affected files` changes it in the plan worktree without asking: there is no deviation request, no task blocking, and no review state.

* *Recording*: The server records every path of `realized − declared` (the realized footprint minus the declared write intents; a modified `(read)` entry included) as an *unplanned change* with its provenance (`task_id` and deliverable, or the loop-back round that produced it) from the Task Diff Records and the change ledger. The unplanned changes are listed in the pull-request body (`## Unplanned Changes`, xref:05-finalize-review-metrics-descriptor.adoc#pr-body-sections[Pull-Request Body Sections]), in the landing record, and in the retrospective's footprint reconciliation; they never extend `declared_files`.
* *Boundaries Stay Hard*: Only a boundary breach is refused, by the non-waivable guards: a write outside the plan worktree, a change of the main checkout where the platform confines no job (Clean Main Checkout Guard), or a change of a protected path the operator does not accept (<<protected-paths>>). A breach raises `footprint_violation` (xref:02-planning-lanes-phases-3-4.adoc#_planning_transition_guards_real_world_invariants[Planning Transition Guards & Real-World Invariants]), whose bounded self-remedy ends in the fallback.
* [[protected-paths]]*Protected paths* (the matcher and its first family are described in the link:../../../pm-core/doc/developer/core-store.adoc#_protected_paths[Scope Stores Developer Guide, Protected Paths]): `.marshall/**` and a pinned wrapper file, which no plan changes (the one exception is the server's own write of a sanity-check team file on the operator's accept, xref:09-sanity-check.adoc#sanity-check-storage[Sanity Check, Storage]), and the project configuration of every harness, as the link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/specification/harness-integration/01-harness-detection.adoc#harness-integration-table[Harness Integration Table] lists it (its settings, command, hook and MCP configuration files and its project skill directories), the CI configuration of the forges (`.github/workflows/**` and `.github/actions/**`, `.gitlab-ci.yml` and `.gitlab/ci/**`), and the files an editor or a shell runs when the operator opens the checkout (`.vscode/tasks.json`, `.vscode/settings.json`, `*.code-workspace`, `.devcontainer/**`, `.envrc`), and the hook definitions git runs from tracked files (`.husky/**`, `.githooks/**`, `lefthook.yml`, `.lefthook.yml`, `lefthook-local.yml`, `.pre-commit-config.yaml`, and every tracked file in the directory that the effective `core.hooksPath` names, set in the repository, global, or system configuration). The harness configuration is what the operator's own harness sessions and later workers load once the change is merged, so a rule, hook or skill that a worker adds there unasked would act outside the plan; the CI configuration runs with the repository's secrets as soon as the plan's branch is pushed, before any review reads it; the editor files run outside every confinement when the operator opens the checkout; and a hook definition runs at the next commit, in a `git` job of the CLI variant with the operator's identity and in the operator's own commits once merged (the untracked git metadata is kept out of a worker's reach by its confinement, link:../job-runtime/02-confinement-and-environment.adoc#git-metadata[Job Runtime Specification, Git Metadata]). A commit whose realized change touches a path of these four families waits for one operator decision (link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-1[PM-SEC-1]): the footprint check holds the commit in the condition `footprint_violation` of kind `protected_path`, whose `facts` carry the diff of exactly those paths, and only the operator ends the hold (link:../state-catalogue/01-conventions-generic-conditions.adoc#condition-footprint_violation[State Catalogue, Conditions]). `accept` lets the commit proceed and covers exactly that diff, so a later different change of such a path asks again; `refuse` keeps it a footprint violation, whose bounded `fix` task of `implement` reverts the paths. The decision is no waiver, and a path the outline declares lifts no protection: what the commit changes is decided when it is made. A path is matched ignoring case and after Unicode NFC normalisation, on every platform, because a case-insensitive file system (the default on macOS) opens `.CLAUDE/settings.json` as the protected `.claude/settings.json`. The project's instruction files (`CLAUDE.md`, `AGENTS.md`) are not protected. _Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-130[PM-WATCH-PHASE-130], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-131[PM-WATCH-PHASE-131], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-48[PM-WATCH-JOB-48]_
* *Epic Plans*: When an unplanned path overlaps the declared surface of a sibling plan of the same epic, the overlap is noted in the landing record for the epic's landing reconciliation; it never blocks.
* *Deliberate change vs. `plan-marshall`*: the batched deviation question (`hold` / `accept` / `split`), the `ScopeDeviationRequest` record, the deviation review state, the `approved_widening` approval path, and the loop-back footprint review do not exist; the recorded provenance replaces them.

[#own-calls]
=== Own Calls of a Writer (Recorded, Judged at Self-Review)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-113[PM-WATCH-PHASE-113]_

A writer settles choices that the intent record, the outline, and its plan task leave open: which of two remedies, a replaced dependency, a bounded buffer instead of an unbounded one, a deliberate shortcut. Nobody reads them in the diff of a large change, so the writer states them, and the server keeps them where the operator reads the plan.

* *Submission*: `submit:TASK-NNN` carries the required parameter `own_calls:list<schema[own-call]>` (link:../hypermedia-format/02-link-grammar.adoc#named-parameter-schemas[Hypermedia Format Specification, Named Parameter Schemas]), at most `10` items; an empty list states that the task settled nothing the plan left open. Each item carries `call` (`10..500` characters: what was chosen), `options` (one to four alternatives weighed, each `1..200` characters; one alternative is the choice not to do it), `reason` (`10..500` characters, naming the evidence), `touches` (the identifiers of the intent record and the outline it concerns: `AC-<n>`, `CN-<n>`, `NG-<n>`, `DC-<n>`, a deliverable number; may be empty), and `kind`: `design`, or `shortcut` with `site` (a path of the task's changed paths, with a line), `limit` (what the shortcut accepts), and `ends_when` (the condition that ends it).
* *Server checks* (a violation is refused with `invalid_link_args`, `rejected.detail` naming the item): every identifier of `touches` exists in the plan's current intent record or outline; a `shortcut`'s `site` is a path of the task's Task Diff Record; and a call may not choose against a decision of the intent record whose decider is `operator` or `quorum`: such a choice is a task question (`ask:TASK-NNN`), never an own call.
* *Records*: in the transaction that accepts the submit, each item becomes a decision-log record at the decision point `execute.own-call` (link:../model-work/11-decision-records.adoc#decision-points[Model Work Specification, Decision Points]) with the decider `role`, its `options`, its `choice` (the `call`), and its `rationale` (the `reason`). A task that ends without its submit records no own call; a re-offer submits its own.
* *What an own call is*: the skill of the `implement` role states it as guidance: a choice between alternatives that a reader of the plan could not predict and would otherwise find only in the diff; never a naming choice or a step the plan task names. A shortcut is always an own call.
* *Reading*: the pull-request body lists every own call in the server-owned section `## Own Calls` (shortcuts first, each with its limit and ending condition; xref:05-finalize-review-metrics-descriptor.adoc#pr-body-sections[Pull-Request Body Sections]), the landing record and the completion report carry them, and the self-review names an own call that works against the intent record in its `conflicts[]` (xref:05-finalize-review-metrics-descriptor.adoc#self-review-submission[Self-Review Submission]). The `simplify` review receives the shortcuts as facts and proposes the removal of none whose `ends_when` has not occurred.
* *Deliberate change vs. `plan-marshall`*: its writers note such choices in the prose of the decision log (in 61 of 291 archived plans), which no step reads.

==== Task Envelope Execution & Independent Server Verification
_Implementation watch: link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-47[PM-WATCH-GEN-47], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-1[PM-WATCH-DISP-1], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-6[PM-WATCH-PHASE-6], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-11[PM-WATCH-STORE-11]_

1. *Serial Envelope Tasks*: `execute.envelope-ready` is a `job llm` state of the writer role `implement` (`job llm envelope role implement`, xref:01-planning-phases-1-2.adoc#phase-roles[Model Work per State]): entering it allocates the next envelope `envelope-M` in dependency order and creates its task; the task's worker runs in the plan worktree, and at most one writer worker runs per plan (link:../model-work/04-worker-launch.adoc#model-slots[Model Work Specification, Model Slots & One Writer per Plan]), so the worktree has one writer. The worker receives the entity `envelope-M` with only the current active plan task (`TASK-NNN`); the skills its plan tasks require come with the offer (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]). The entity's submits move only the entity; the plan state reacts only to the end of the task, whose return-evaluation primitive `execute.evaluate-envelope-return` decides one closed outcome from the persisted plan-task and question records, in this precedence when several apply: `question_pending` -> `execute.task-question`; `infeasible_pending` -> `execute.replan` (only when no runnable plan task remains, item 5); `chain_tail` -> `execute.chain-tail-commit`; `remediation_chain_tail` (the finished plan tasks are remediation tasks) -> `execute.remediation-commit`; `continue` -> `execute.envelope-ready`; `all_complete` -> `execute.verify-sweep`. A task that ended without the submits its entity requires is offered again for the remaining plan tasks within the compiled re-offer budget (link:../timeouts/01-job-budgets-and-waits.adoc#task-reoffer-budget[Timeouts & Budgets Specification, Re-Offer Budget]); once they are spent it closes `lost`, and the state takes the Phase 5 fallback (the exit `hand_back`, on which the plan unit calls `finalize.hand-back`). A task the operator's pause _now_ withdrew is no loss: it is offered again for its remaining plan tasks when the operator starts the plan, and a pause after the current task lets the running envelope task end and creates no next one until the start (link:../runtime-lifecycle/02-plan-pause-and-stalled-plans.adoc#plan-pause[Runtime Lifecycle Specification, Pausing and Starting a Plan]). The `submit` of a chain-tail plan task ends the entity and yields the envelope's remaining plan tasks to `envelope-(M+1)`.
2. *Independent Verification on `submit:TASK-NNN`*: The server never trusts a task's self-reported completion. When `submit:TASK-NNN` is invoked, the daemon independently verifies: (a) *Non-Empty Diff & Boundary Check* — for write-intent tasks, verifies that `git status --porcelain` in the worktree contains changes and that no path outside the worktree, of the main checkout, or of a protected path was touched (a boundary breach raises `footprint_violation`), forbidding batched destructive `git checkout` commands; paths beyond the deliverable's declared write intents, a modified `(read)` entry included, are recorded as unplanned changes (<<unplanned-changes>>); and (b) *Independent Command Re-Run* — executes the task's declared verification command via the daemon's build runner and verifies a passing verdict artifact. Markers and suppressions in the added lines are no submit check: the sanity-check phase lists them once for the whole change (xref:09-sanity-check.adoc#sanity-check-steps[Sanity Check, Steps]). When the verification passes, the server appends (c) a *Task Diff Record* to `change-ledger.jsonl`: `kind: "task_diff"` with `task_id`, `deliverable_id`, the `worktree_sha` of the worktree at submit, `changed_paths` (the paths changed since the previous task's recorded snapshot, present and possibly empty), and `commit_sha: null`, because tasks never commit. This is the only producer of per-task change attribution.
3. *Context Yield, Task Questions & Infeasibility*: If the worker approaches its context limit before finishing all plan tasks in `envelope-M`, it follows `yield:envelope-M` (no free parameters). Every early end of an envelope completes the entity (`envelope.completed`), and the server hands the remaining unstarted plan tasks to `envelope-(M+1)`, a new task; the server records [[yield-reason]]`yield_reason` from the exit taken, a closed enum `chain_tail | question | context | off_track` persisted beside the task's classification in the metrics store; this is the only list of its values. *A worker off track*: where the role artifact chose the action `yield` for an activity signal the server computed (`repeating`, `no_progress`; link:../model-work/03-supervision-and-recycling.adoc#worker-off-track[Model Work Specification, A Worker Off Track]), the worker's next call is answered with the end of the attempt, and the envelope ends as on `yield:envelope-M` (`yield_reason: off_track`); with the action `restart` the worker is ended and its envelope task offered again within its re-offer budget. Either action is recorded with its signal in the activity and the task's record and reported to the operator (kind `task.off_track`, link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#reports[Runtime & Interaction Model Specification, Reports to the Operator]); a signal never ends the plan, never becomes a decision, and is no limit of the tokens it uses. An envelope task that needs an answer calls `ask:TASK-NNN` (`decision:schema[decision-envelope]`), which records a question record of class `task`. Where the task continues after its question (link:../model-work/06-envelopes-questions-deadlines.adoc#continuation[Model Work Specification, Continuing after a Question]), the envelope rests in `envelope.task.awaiting_answer` within the role's hold limit and continues the same plan task once the answer is acknowledged; where the task does not continue, the question ends the task with outcome `asked` (`yield_reason: question`), and the remaining plan tasks, the asking one included, go to `envelope-(M+1)`, whose task receives the answer in `facts`. `execute.task-question` is an operator wait for the decision, unless the adjudication's quorum decides it (xref:07-questions-waivers-operator-influence.adoc#questions-waivers-operator-influence[Questions, Waivers & Operator Influence]). The answer is recorded as an `amendments[]` entry and listed in the pull-request body and the landing record. If a plan task is genuinely impossible as specified, the envelope task submits `infeasible:TASK-NNN` with evidence (task outcome `infeasible`); the server sets the task to `infeasible` with the evidence as its disposition, `infeasible` is terminal for that task, and substituting a weaker deliverable under the same name is strictly prohibited. Envelope tasks continue for every plan task that does not depend, transitively through `depends_on`, on the infeasible deliverable.
4. *Dependency-Ordered Creation*: A plan task is yielded to its envelope's task only when every plan task in its `depends_on` is `completed`; an envelope's task is created only when its first plan task is yieldable. A task whose dependency is `infeasible` or `removed` is never yielded.
5. *Infeasible Deliverables (Re-Planning)*: When no runnable plan task remains and a deliverable is infeasible, the plan is re-planned with the trigger `infeasible` (`execute.replan`, xref:08-dynamic-re-planning.adoc#dynamic-re-planning[Dynamic Re-Planning]): the `replan` task's facts carry the infeasible deliverables with their evidence and their server-computed transitive dependents, and it re-integrates (new or amended deliverables and plan tasks, or the loop-back to the outline below), defers or removes the infeasible part (an `infeasible` task keeps its evidence; the other tasks of the moved deliverables and their dependents become `removed`, `disposition.by: model`; removing the last deliverable is refused), waits for a prerequisite, or hands the plan back. While `replan` is unqualified the plan is handed back with the reason `role_unqualified`.
+
[[loop-back-outline]]*Loop-Back to the Outline*: a decision of a re-planning (`reintegrate_in_plan` with `reentry: outline`) and of the `plan.revise-tasks` task. The calling phase ends with its exit `loop_back_outline`, and the plan unit's call state of the plan's lane calls the outline again at that lane's authoring entry (`deep` -> `outline.deep`, `light` -> `outline.light`, whose new outline passes the light gate again; no state reads the lane, link:../state-catalogue/18-plan-unit-axes-short-landings.adoc#state-catalogue-plan-unit[State Catalogue, Plan Unit]), with the evidence as an amendment. The loop-back budget is a compiled `1` per plan, raised only as `fix_budget:outline-loop-back` (link:../timeouts/01-job-budgets-and-waits.adoc#loop-back-outline-budget[Timeouts & Budgets Specification, Outline Loop-Back Budget]); a spent budget takes the fallback (`handed_back` when Phase 5 committed work, else `returned`). A loop-back from Phase 5 or finalize keeps the worktree: the `outline` task's worker runs in it (a worker's working directory is the plan worktree when it exists, link:../model-work/04-worker-launch.adoc#job-working-directory[Model Work Specification, Working Directory]), and `execute.worktree-init` adopts it; a fallback taken in Phases 3–4 after such a loop-back reaches `plan.return`, which forwards the committed work to `finalize.hand-back`. The re-authored outline and the re-derived tasks compose new instance versions at the `outline` and `plan` events; a deliverable the revised outline drops has its tasks set `removed` (`disposition.by: outline_gate`), Phase 4 derives the tasks of the revised deliverables additively, and `completed` tasks are never reopened (`PM-WF-7`). The loop-back counter is never reset.

=== Per-Deliverable Chain-Tail Commit & Module Build (`git.commit_and_push`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-17[PM-WATCH-PHASE-17]_

Individual tasks never run `git commit`. When the last task belonging to deliverable $D_i$ (the *chain tail*) passes independent verification:

1. *Chain-Tail Commit via `call git.commit_and_push`*: `execute.chain-tail-commit` invokes the reusable compound sub-workflow `call git.commit_and_push (message_mode=auto_deliverable, push_mode=never)` (`PM-WF-16`, see link:../workflow-dsl.adoc[Workflow DSL Specification]). The sub-workflow cleans untracked build/temp artifacts against the compiled artifact pattern table of `pm-core` (respecting `.gitignore` and excluding `.marshall/**`), formats the conventional commit message (`feat(<module>): complete deliverable <N> - <title>`) with the configured `Co-Authored-By` trailer, streams the message over `stdin` to `git -C <worktree> commit -F -`, and appends a `kind = "change"` entry to `change-ledger.jsonl` stamped with the new `commit_sha` and git-sourced `changed_paths`. It returns `done` with the result `{commit?, pushed, clean, landed}` (a read-only deliverable returns `clean` without a commit), or `stepped_out`, which the caller routes to the phase's exit `hand_back`.
2. *Per-Deliverable Module Build*: `done` enters the `job` state `execute.deliverable-build`, which runs the per-deliverable verification verbs of the effective configuration (`workflow.json` `plan.phase-5-execute.per_deliverable_verbs`, default `compile` and `module-tests`, as `plan-marshall`'s `per_deliverable_build`; link:../store-schemas/07-project-configuration.adoc#config-workflow-json[Store Schemas Specification, `workflow.json`]) scoped to the modules that claim the `changed_paths` of $D_i$'s chain-tail entry in the change ledger, by the rules of the end-of-phase sweep (<<footprint-driven-scope>>: the build map assigns each path, a build-neutral path is `no_module` and widens nothing, a deleted or renamed path a module claims widens the build to the whole tree; the declared `deliverables[].module` plays no part), and records a `kind = "build"` entry in `change-ledger.jsonl`. `succeeded` continues at the re-planning checkpoint `execute.replan-check` and then at `execute.envelope-ready` (xref:08-dynamic-re-planning.adoc#replan-triggers[Dynamic Re-Planning, Triggers]). Every other fate (`failed`, `failed_unparsed`, `refused`, `cancelled`, `timed_out`, `killed`, `indeterminate`) enters `execute.remediate-build`, writing the status field `remediation_cause: deliverable` (link:../store-schemas/02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Store Schemas Specification, Workflow State Store]), which calls `remediation.build-failure`, because an absent verdict is never admitted as a pass: its `retry` re-runs the build, its `fix` returns `fix_requested`, which allocates remediation tasks whose commit (`execute.remediation-commit`, routing `done` and `stepped_out`) continues through the router `execute.route-commit-cause` by `remediation_cause` (`deliverable` -> `execute.deliverable-build`, `sweep` -> `execute.verify-sweep`). `resolved` (the unit's own re-run passed) continues through the router `execute.route-build-cause` by the same field: `deliverable` -> `execute.envelope-ready` (the deliverable's build is green, so the next envelope follows), `sweep` -> `execute.verify-sweep`. A build failure is not waivable, so the unit has no `waived` outcome; `exhausted` enters `execute.replan` (trigger `ceiling`) and `stepped_out` ends the phase with its exit `hand_back`.

=== Whole-Tree Verification Gates & `triage_required` Routing
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-15[PM-WATCH-PHASE-15], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-66[PM-WATCH-PHASE-66], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-117[PM-WATCH-PHASE-117]_

Once all task envelopes reach completion, the transaction that enters `execute.verify-sweep` composes the plan instance version of the event `realized`, whose prunes read the change the plan made (link:../workflow-dsl/09-plan-instance.adoc#_versions_composition_events[Workflow DSL Specification, Versions & Composition Events]), and `execute.verify-sweep` (a `composite_job`) runs the end-of-phase verification steps of that instance (ordered by the `ext-point-build-verify-step` descriptors: `module-tests`, `quality-gate`, `coverage`, and domain `arch-gate`):

* [[footprint-driven-scope]]*Footprint-Driven Scope & Relocation Override*: The server compares the realized git footprint (`references.json:realized_footprint`) against project modules to scope build executions. However, if the realized footprint holds a deleted (`D`) or renamed (`R`) path that a module claims, the server unconditionally forces a **whole-tree build and verification sweep** across all modules to catch broken cross-module imports or references; a declared `delete` intent does not widen the scope, the change the plan made does. A realized path claimed by no module but routed by the build map as build-neutral (for example `.github/**`) is classified `no_module`: it neither blocks nor widens a module-scoped gate to whole-tree, and the scope decision lists it.
* [[mutation-step]]*Mutation Step (opt-in)*: A project that lists `default:mutation` in `final_verification` (link:../store-schemas/07-project-configuration.adoc#config-workflow-json[Store Schemas Specification, `workflow.json`]) runs, after the other steps passed, the build verb `mutation` of the domain's build system (for Java PIT through the canonical template of the build extension), scoped to the production classes the plan changed: the test set is the module's tests, and the build tool's own mutation run selects for each mutant the tests that cover it (for PIT its coverage analysis); the server selects no tests. The step is non-blocking: it never fails the sweep and never calls a remediation policy; its parsed result, each surviving mutant with its class, line, and mutator, is filed as non-blocking findings of class `surviving_mutant`, given to the `review-code` half of the self-review as evidence (xref:04-finalize-step-bands.adoc#_normative_step_catalogue_across_ordering_bands[Step Catalogue], `pre-submission-self-review`) and listed in the pull-request body (`## Surviving Mutants`, xref:05-finalize-review-metrics-descriptor.adoc#pr-body-sections[Pull-Request Body Sections]). It is pruned with reason `no_production_delta` when the realized footprint holds no production source, and a domain without a `mutation` verb records it `not_run`.
* *`triage_required` -> Build Remediation*: Whenever an end-of-phase verification step fails or a constituent ends without a verdict, the engine ingests the parsed build/test/arch-gate failures into `findings.jsonl` (the evidence of the unit) and enters `execute.remediate-build` with `remediation_cause: sweep` (routing as in the per-deliverable build above); its `fix` allocates remediation tasks that commit via `call git.commit_and_push (message_mode=interactive, push_mode=never)` and re-enter `execute.verify-sweep`.
* *Baseline-Red Server Rule*: Before a failing gate reaches the remediation policy, the server proves whether it is red only through failures already present on the base, by the proof of link:../job-runtime/03-parsers-and-gates.adoc#_gate_honesty_verification[Job Runtime Specification, Gate Honesty Verification] (item 4, Baseline Separation). When every failure is baseline-only, the server writes a `baseline_red` build row into `change-ledger.jsonl` bound to the `worktree_sha`, the merge base, and the digest of the accepted diagnostics, and the gate passes: the freshness gate counts that row as passing for the same `worktree_sha` only, a finalize gate step completes `done` with `assurance_verdict: degraded`, and the pull-request body (`## Gaps`, xref:05-finalize-review-metrics-descriptor.adoc#pr-body-sections[Pull-Request Body Sections]) and the landing record list the baseline failures. Coverage debt in untouched modules is a non-blocking `baseline_debt` finding. A red that is not provably baseline-only is plan-caused and calls the build (or, in finalize, the CI) remediation policy. There is no baseline-red state and no operator acceptance; the plan is never looped back to remediate a baseline failure.
* [[sweep-culprit]]*Culprit Localisation*: A plan-caused red of the sweep whose failing step also ran per deliverable and passed there for every deliverable is an interaction of commits, which no per-deliverable build localises. Before such a red reaches the build remediation policy, the job `execute.localise-sweep` runs the failing step's verb, scoped as in the sweep, in a job-private detached worktree at the plan's commits after the merge base (the chain-tail commits and the remediation commits in `change-ledger.jsonl`, in commit order), by bisection: it finds the first commit at which the step's failure fingerprints appear, in at most $\lceil \log_2 n \rceil + 1$ builds for $n$ commits, bounded by the compiled cap of link:../timeouts/01-job-budgets-and-waits.adoc#sweep-localisation-cap[Timeouts & Budgets Specification, Sweep Localisation Builds]. Every probe build is recorded in `change-ledger.jsonl` like every build, bound to its commit. The result is a fact of the remediation decision, `sweep_culprit`: `found` with the commit, its deliverable or remediation round, and the failure fingerprints that first appeared there; `not_reproduced` when the failure does not appear at `HEAD` in the job-private worktree (the policy's `retry` then has that evidence); or `indeterminate` when a probe ends without a verdict or the cap is spent. Localisation never changes the plan's worktree, never reverts a commit, and never decides: the policy's decide step reads the result as evidence. It is skipped, with the reason recorded, for a plan with fewer than two commits after the merge base and for a red the relocation override widened to whole-tree (its per-deliverable builds did not cover the failing scope).

=== Phase 5 Exit Barrier: Dual Freshness & Pending-Tasks Gates
_Implementation watch: link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-25[PM-WATCH-GEN-25], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-17[PM-WATCH-PHASE-17], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-96[PM-WATCH-PHASE-96]_

Leaving `phase-5-execute` (to the phase `sanity-check`, xref:09-sanity-check.adoc#sanity-check[Sanity Check], and then `phase-6-finalize`) is governed by an atomic dual-gate barrier in `execute.exit-barrier`. **Both gates are always evaluated together before acting on either** so a single diagnostics payload surfaces all reasons if both fail:

1. *Pending-Tasks & Clean-Tree Gate*: Every `tasks/TASK-*.json` record in the plan must be in a terminal status (`completed`, `infeasible`, or `removed`), every `infeasible` or `removed` task must carry its recorded `disposition` (link:../store-schemas/06-task-and-references.adoc#_task_record_schema_taskstask_nnn_json[Store Schemas Specification, Task Record]), and no task may be open (`pending_count == 0`, `in_progress_count == 0`); the gate reports the counts of every status and lists each non-`completed` task with its disposition. The worktree must have zero uncommitted modifications (`git status --porcelain` is empty). A dirty tree is handled first: it enters `execute.remediation-commit`, whose artifact review separates build leftovers from real changes; real changes are committed and recorded as unplanned changes, and the route continues to `execute.verify-sweep` because `HEAD` changed; only a boundary breach raises `footprint_violation`. A barrier failing on open tasks routes to `execute.envelope-ready` while runnable tasks remain, and otherwise to `execute.replan` (trigger `infeasible`) (link:../state-catalogue/03-plan-phases-4-5-land.adoc#state-catalogue-execute[State Catalogue]).
2. *Worktree Freshness Gate (`worktree_sha`)*: Freshness is keyed strictly on `worktree_sha` — the SHA-256 digest over the `HEAD` commit id plus, for every path the status reports as changed, deleted, or untracked (sorted by path), the path and either the file's bytes read from disk or a deletion marker, computed by the single git contract operation `git.worktree-sha` for both variants (link:../job-runtime/03-parsers-and-gates.adoc#worktree-sha[Job Runtime Specification, Working-Tree Hash]) — never on `HEAD` commit SHA alone (which would misclassify an unbuilt dirty tree as fresh). The gate queries the change ledger (`change-ledger.jsonl`) and reads the explicit closed-enum `status` member (`fresh`, `exempt`, `stale`, `undecidable`), never inferring freshness from a process exit code or from `"not stale"`: `fresh` requires that every required build notation for the realized footprint has a passing `kind = "build"` ledger entry whose recorded `worktree_sha` equals the current live `worktree_sha` and every ledger row matches a registered build notation of the project; [[build-neutral-since-build]]without such an entry the gate observes what changed since the latest succeeded build of the notation: that build row records the `HEAD` it built (`head`), and the changed paths are `git diff --name-only <head>..HEAD`, the paths the status reports as changed now, and, when the build ran on a dirty tree, every path that was dirty then; when the build map routes every one of them as build-neutral, the notation is `fresh` with the basis `build_neutral_since_build`, otherwise the gate is `stale` with `tree_modified_since_build` naming the paths; `exempt` applies when the `build-decision` verdict over the build map and the realized footprint is `not_necessary` (every realized path is build-neutral); the `documentation_only` file-type bucket is a file role for `profiles[]` assignment and is never read as a build verdict (as in `plan-marshall` ADR-004); `stale` / `undecidable` fails the barrier with an explicit `stale_reason` (`tree_modified_since_build`, `last_build_failed`, `no_successful_build`, `missing_module_build`, `unrecognized_build_notation`, `ledger_unreadable`, or `worktree_sha_unavailable`). A reason a build clears routes back to `execute.verify-sweep`; `unrecognized_build_notation`, `ledger_unreadable`, and `worktree_sha_unavailable`, which no sweep clears, raise the `guard_indeterminate` condition on the barrier (link:../state-catalogue/01-conventions-generic-conditions.adoc#condition-guard_indeterminate[State Catalogue Specification, Conditions]), whose bounded re-evaluation and spent-budget fallback replace an unbounded sweep loop. A live or recorded `worktree_sha` that is `unavailable` (a failed git invocation) makes the gate `undecidable` with `worktree_sha_unavailable`, never `fresh`, and ledger rows of another `worktree_sha_version` never match the live digest (link:../job-runtime/03-parsers-and-gates.adoc#worktree-sha[Job Runtime Specification, Working-Tree Hash], rules 4 and 5).
+
`last_build_failed` (the latest build row for a required notation is not `succeeded`) is a different operator action than `tree_modified_since_build` (a path the build map does not route as build-neutral changed after a passing build) and is never reported as it; when no successful build exists at all the reason is `no_successful_build`. Where the step records show that `HEAD` is a finalize-internal commit, the refusal names the committing step. The same derivation serves every later reader of a build's currency (the push freshness gate of `git.commit_and_push` and the verdict currency of an `open_ended` step, xref:06-finalize-re-entry-and-merge.adoc#verdict-input-scope[Verdict Input Scope]); no commit records a reconciliation of its own.
