== Automatic Review: Registry, Participation, Refusals & Ingestion
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-24[PM-WATCH-PHASE-24], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-25[PM-WATCH-PHASE-25], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-26[PM-WATCH-PHASE-26], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-27[PM-WATCH-PHASE-27], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-28[PM-WATCH-PHASE-28], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-29[PM-WATCH-PHASE-29], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-30[PM-WATCH-PHASE-30], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-105[PM-WATCH-PHASE-105]_

`default:automatic-review` (order `30`) and the composite wait `finalize.concurrent-wait` work from one server-owned review-bot registry and write one participation record per `(pr_number, round, bot_kind)` into the plan's append-only `review-participation.jsonl` at review time (a change appends the full record again; the last readable line of a key is current), each stamped with the `HEAD` it observed (link:../store-schemas/03-findings-and-review-records.adoc#review-participation[Store Schemas Specification, Review Participation Record]). The rules mirror `plan-marshall` `automatic-review` (`SKILL.md`, `standards/*.md`), verified at `plan-marshall` commit `f3de0e14f`; re-verify against the latest `plan-marshall` version before implementing. The comment fetch and the reply transmission are the findings contract of `pm-core` (`FindingSource`, `FindingResponder`), the pull-request and check reads contracts of the CI contract (no module of this repository yet), both implemented by `pm-provider-github` and `pm-provider-gitlab` (link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-IMPL-1[PM-IMPL-1]).

=== Review-Bot Registry

The registry holds one compiled-in record per `bot_kind`; a project may add records.

[cols="1,4"]
|===
|Field group |Content

|Identity & trigger
|`bot_kind` and `author_login` (the identity used for author binding). One `trigger_token`: the server posts only this token, never one chosen per call; `trigger_verbs{incremental, full}` (CodeRabbit `@coderabbitai review`; no compiled-in record declares a `full` verb). `trigger_events`: the PR events the bot subscribes to (pr-agent does not subscribe to `synchronize`). The server opens the pull request and posts every trigger as the operator via the App (the user access token of a GitHub App credential, link:../credentials-and-enrolment/01-provider-credentials.adoc#user-access-token[Credentials & Enrolment Specification, User Access Token]), never under the App's bot identity, and with a personal access token credential as that token's user: CodeRabbit skips a pull request authored by a bot and ignores triggers posted by a bot, and a user trigger does not rescue a bot-authored pull request, because the author of the pull request decides. A CodeRabbit review seat assigned to the bot by an organisation administrator is an untested alternative and no part of this design. `trigger_semantics` (`comment_trigger`, the default, or `auto_on_push`): a bot that acts on no trigger comment is configured to review every push on its own and registered as `auto_on_push`; the server then never posts a trigger for it, its waits are satisfied only by a review of the pushed `HEAD`, and a remedy that needs a trigger (re-trigger after a window, the `full` verb) is unavailable for it, so the bot resolves `unproven` instead.

|Publish shapes
|`publish_shapes` ⊆ `{conversation, inline_thread, pr_review}` and `participation_evidence` (which shapes prove a review). Participation markers are anchored patterns (start of block or structural element, never a bare substring), and each marker records the sample (PR count) it was validated on. Observed shapes the registry does not declare raise a `registry_drift` finding; a missing optional shape is not non-participation.

|Currency
|`participation_requires_update` (mirrored from `plan-marshall`, where it opts a bot into the currency test; `sourcery` declares `false`, `coderabbit` and `cuioss-review-bot` declare `true`). In `PM-MCP` it exempts no bot: the currency test is unconditional (xref:06-finalize-re-entry-and-merge.adoc#_two_fail_closed_barrier_predicates[Two Fail-Closed Barrier Predicates]). `reviewed_sha_carrier` (`structured`, `body_pattern`, or `none`) with `reviewed_sha_pattern` (cuioss-review-bot: body "Review updated until commit `<sha>`"); `completion_check_name` (nullable).

|Refusal recognition
|`refusal_patterns`, `refusal_size_patterns`, `refusal_wrapper_markers` (CodeRabbit `<details><summary>⚠️ Action not completed</summary>`), and `rate_limit_eta_patterns` (including "reset in 57 minutes"; the CodeRabbit reset notice may omit its trailing phrases). `no_new_commits_patterns` (CodeRabbit "Review skipped" together with "No new commits to review"; its bot-author skip notices "Review skipped … Bot user detected" and "authored by a bot without an assigned CodeRabbit review seat" are `refusal_patterns` instead: a refusal of mode `unknown` that no trigger remedies, met only on an adopted pull request that a bot authored) and, for a bot without `trigger_verbs.full`, `no_new_commits_class` (`refused` or `declined`). Sourcery phrasings: "your pull request is larger than the review limit of", "reached your weekly rate limit of", "you've used your own review budget of N diff characters".

|Rate class & caps
|`rate_limit_class` (`awaitable_window`, `hard_quota`, or `unknown`), `rate_interval_seconds`, `attempt_ceiling` (compiled default: link:../timeouts/01-job-budgets-and-waits.adoc#review-bot-windows[Timeouts & Budgets Specification, Review-Bot Rate Windows]), and `structural_caps{max_files, max_diff_chars}` (null in every compiled-in record; declared only by a team record that knows its bot's plan).

|Content classification
|`actionable_content_markers`, `contentless_review_markers`, `ignore_patterns`, `severity_map`, and dated per-bot `config_verdicts[]` (for example CodeRabbit `enable_prompt_for_ai_agents`).
|===

Compiled-in data (re-verify before implementing): `coderabbit` (one review per hour, `awaitable_window`; reviews a user-authored pull request on its own within seconds of its opening and accepts a user's trigger); `sourcery` (`hard_quota`, an account-level diff-character quota over a rolling 7-day window, and per-pull-request size and file-count ceilings); `cuioss-review-bot` (`unknown`, reviewed SHA in the body only). No compiled-in record encodes a ceiling or quota as a number: the ceiling is read from the bot's own notice (link:../store-schemas/03-findings-and-review-records.adoc#review-bot-registry[Store Schemas Specification, Review-Bot Registry Record]). The provider cap for a GitHub comment body is 65,536 characters.

* *One Shared Reader*: Required, optional, and enabled populations are resolved only from `required_bots` / `optional_bots` against the registry through one shared reader. An unregistered token fails loud (`unregistered_kind`) with the same disposition everywhere and is never counted in a ratio denominator.
* *Review Bots Are Not CI*: `ci_status` evaluation excludes check-runs owned by registered review bots. On a bot timeout the engine first checks that the bot's trigger workflow or app is installed for the repository (`not_wired`) before reporting `unproven`.
* *Size Cap at Fetch Time*: A bot whose structural cap is below the PR's measured diff is classified `refusal_candidate` when comments are fetched; an unmatched comment from it is checked against its refusal phrasings before any participation verdict.

=== Per-Bot Participation States

Per round, every bot of the roster resolves to exactly one per-bot `state` of the closed enumeration defined in link:../hypermedia-format/03-composite-wait-and-encoder.adoc#_closed_status_enumerations_in_finalize_concurrent_wait[Hypermedia Format Specification, Closed Status Enumerations] (with a `refusal_mode` for `refused`); the composite `bot_status` of `finalize.concurrent-wait` is the aggregate of these states over the required bots through the closed per-bot mapping table defined there (satisfied, `running` when a run is observed, `pending` when none is observed and then `unproven` when the poll budget is spent, fail-fast `unproven`, and `refused` by mode), and its outcomes route the finalize excerpt (link:../workflow-dsl.adoc[Workflow DSL Specification]). `unproven` for a required bot calls `remediation.review-findings` with the failure kind `evidence_missing`, whose `retry` is a window-gated re-trigger that is never offered for `unregistered_kind` and `not_wired`; their only ends are a `review_evidence` waiver or the fallback. The rules below decide which state applies.

* *Review Evidence*: Completion requires a review verdict object (a review, an inline comment of that review, or a completed check-run) authored by the bot's registered `author_login`; per-bot completion waits match `author_login`, because a SHA match proves which commit was reviewed, not who reviewed it. Rate-limit meta-comments, re-served prior-round comments, "Review completed" placeholders without a review, inline comment or check-run, and thread acknowledgements never count. A declared clean verdict ("No major issues detected", "No code suggestions found") counts as `participated_but_empty`.
* *Refusal Precedence*: A refusal outranks a later edit timestamp, and a refusal observed in the same pass as a clean review of the same bot resolves `refused`. A refusal never sets the covered commit and never advances the `head_at_completion` of `automatic-review`.
* *Declined vs Unproven*: `declined` requires a named commit that is not the merge candidate; evidence that names no commit resolves `unproven` for a bot with `reviewed_sha_carrier: none`.
* *Nobody-Reviewed Shapes*: `not_triggered`, `rereview_silent_failure`, and `run_stuck` stay distinct; workflow runs are queried unfiltered by branch. An exhausted poll yields `unproven`, never `absent`.
* *Opposite Claims*: `unreadable` (the read failed) and `silent` (the read succeeded and nothing was published) are opposite claims; a prediction is recorded as `unrecorded`, never as an observation. A fetch returning zero comments resolves to exactly one of: no review covering `HEAD` (`absent` or `unproven`), reviewed clean (`participated_but_empty`), or fetch unreachable (`unreadable`).
* *Per-State Remedies*: Each non-participating state carries its own remedy in the evidence of `remediation.review-findings` (the kind of re-trigger its `retry` performs, or none), never a shared generic `retry`, and a `reopens` axis (`awaitable` or `hard`) derived from the refusal mode. A roster question that was never put renders "question never put"; an awaitable refusal's representation names the governing config key and value.
* *Partitioned Reporting*: Unproven and blocking sets are reported partitioned by `roster_class` (`required`, `optional`, `unclassified`); only the required partition gates. The roster aggregate is `reviewed`, `incomplete`, `vacuous` (empty required set, answered: `review.required_bots` present in `project.json` as `[]`), or `unestablished` (never answered: the key is absent; there is no separate provenance bookkeeping, the presence of the key is the answer); an empty roster never renders `reviewed` or `clean`.
* *Per-Bot Facts*: `facts.bots` renders per bot `state`, `completion_check`, and `at_head` as separate columns (hypermedia-format.adoc), because "participated", "completion check finished", and "CI check green" prove different things. The participation summary renders per class `required k/|required|`, `optional j/|optional|` (with each silence's state), and `roster r/|roster|`; a bare N-of-M is never emitted.

=== Refusals & Rate Windows

1. *Derived Recognition*: Refusals are recognised by a derived rule (wrapper marker plus registry patterns), tested with controls in both directions. An unrecognised refusal-shaped notice resolves `refused` with mode `unknown`; an unmatched bot comment is never counted as participation.
2. *Capture on Sight*: The body and `observed_at` of a refusal are captured when first seen; a later absence of the notice is not a refutation, and a body divergence on re-read is reported. Every refusing bot is reported, never only the first.
3. *Wake on Edits*: Waiters order comments by `max(created_at, updated_at)`.
4. *Currency of a Notice*: A notice is current only if it answers a trigger this run posted (by trigger id) or its stated window is still open; otherwise it is `stale`. A rate-limit refusal is bound to the request it answered and to its reset time; a window already waited out is never restarted by re-reading the same refusal.
5. *Window Derivation*: A window's `reset_at` is the bot-stated reset ETA when one is published and parsed (a floor to re-check, which beats every derived value); otherwise `claimed_at + rate_interval_seconds` of the bot's registry record; otherwise the compiled rate-window floor. The re-review timeout is the `reset_at` of the bot's open window, or, without an open window, the registered interval plus a compiled completion allowance. Values, floor, and allowance are defined only in link:../timeouts/01-job-budgets-and-waits.adoc#review-bot-windows[Timeouts & Budgets Specification, Review-Bot Rate Windows] (compiled, not configurable). Waiting past the ETA records a reason. A detected but unparsed ETA records `eta_unparsed` (a drift signal), never "no ETA", and falls back to the interval. Wait budgets derive from the registered interval, never from a flat timeout. The triggers per `(repository, pr_number, bot_kind)` are bounded by the registry's `attempt_ceiling`; at the ceiling no further trigger is posted and the bot resolves `unproven`.
6. *Closed Windows*: A trigger is never posted inside a closed window (a trigger extends the window, close and reopen do not reset it, and windows are organisation-scoped); `retry` is offered only while the window is open.
7. *Mode Routing*: `size` files a structural finding that `remediation.review-findings` triages (`ACCEPT` accepts, `SUPPRESS` disables the bot for this PR; a split of the change is a re-planning, item 12), never a wait; `weekly_quota` and `hard_quota` resolve `unproven` at once with no `retry`, never a wait; `rate` waits for the window and then triggers; `no_unreviewed_commit` routes to `finalize.review-full-trigger`, which posts the registry's `full` trigger verb once for the current `HEAD` (a repeated notice after that trigger resolves `unproven`). A stale bot with a declared comment trigger gets the trigger posted once and a bounded wait, then resolves `unproven` (never re-triggered for a quota refusal).
8. *Satisfying Event*: Every wait names its satisfying event and its producer; if the bot's `trigger_events` cannot fire on this retry path, the wait fails fast with `no_satisfying_event`.
9. *Re-Trigger Target*: The re-trigger target is the unproven set (including bots that never published), selected after the round's own fetch, never by comment recency. The wait and trigger target set is the unproven part of `required ∪ optional`; the gating set is the required bots only.
10. *Per-PR Counters*: Rate-window claims (the cross-plan leases in `review-bot-windows.json`) and attempt counters are kept per repository, PR, and bot.
11. *No-New-Commits Notice*: A bot notice matching the registry's `no_new_commits_patterns` ("Review skipped: No new commits") is never participation and never a neutral acknowledgement. For a bot whose registry declares a `full` trigger verb it resolves `refused` with mode `no_unreviewed_commit`, whose remedy is that verb (no compiled-in record declares one; a team record may). For a bot without a `full` verb the registry's `no_new_commits_class` decides: `refused` (mode `no_unreviewed_commit`, resolving `unproven` because no remedy verb exists) or `declined` (the `plan-marshall` classification). *Deliberate change vs. `plan-marshall`*: `plan-marshall` classifies the notice as `declined`, accepts the decline, and never re-triggers; `PM-MCP` re-triggers with the `full` verb wherever one exists, so no stale credit stands for an unreviewed `HEAD`.
12. *Pre-Wait Cap Gate*: Before entering `finalize.concurrent-wait`, the engine measures the diff (files and diff characters) against the `structural_caps` a team record declares for a required bot; a bot without declared caps is not gated here, and its size refusal is read from its notice (item 7). An exceeded cap of a required bot first raises the re-planning trigger `downstream_limit` (once per `HEAD` and bot, xref:08-dynamic-re-planning.adoc#replan-triggers[Dynamic Re-Planning, Triggers]), because splitting the change is a re-planning; when a path partition (for example test sources vs the rest) brings each part under the cap, the trigger's facts propose that concrete split. An exceeded cap that is not re-planned (an optional bot, or a judged `HEAD`) records `refused` with mode `size` pre-emptively, names the cap and the measurement, and calls `remediation.review-findings` instead of waiting, whose `triage-review` task dispositions each structural refusal as a finding of its firing (`ACCEPT` accepts, `SUPPRESS` disables the bot for this PR). Under every cap the flow is unchanged.

=== Comment Ingestion

1. *Every Firing*: Comments are re-ingested on every firing of `automatic-review` and on every re-entry of `finalize.concurrent-wait`. All three surfaces (conversation, inline threads, PR review bodies) are fetched and classified.
2. *Own Comments by Provenance*: Own comments are recognised by provenance (server-recorded posted comment ids and trigger ids); headings are secondary. Repository-owner comments are genuine reviews unless provenance matches. Posted triggers are excluded and counted with a reason; a bot comment quoting a trigger is still ingested.
3. *Noise Filter*: Fenced code, blockquotes, and `<details>` blocks are stripped first; a comment is noise only if an acknowledgement pattern covers the whole remainder; length is an outer bound only. Drops are recorded distinguishably from genuine acknowledgements.
4. *Actionable Content*: A bot comment becomes a finding only if it matches the registry's `actionable_content_markers` (when declared) after noise stripping; enumerated refusal patterns are the secondary guard.
5. *Status Line then Remainder*: A `review_body` yields finding candidates only from the text after the bot's status line ("Actionable comments posted: N"). A body consisting only of a status line, an approval notice, or a "Review finished" header is a status record, never a finding, and never enters Predicate 1.
6. *Complete Fetches*: Every connection is paginated (`pageInfo`) or reports `observed` vs `cap`; a clipped fetch is never success.
7. *Comment Identity*: A comment's identity is `(bot_kind, comment_id)` plus its edit marker (`updated_at != created_at`); an edited comment is new information.
8. *Fetch Freshness*: The merge barrier re-fetches immediately before merge; a review newer than the last fetch blocks.
9. *Summary-Card Overflow*: Overflow folded into a summary card ("Outside diff range comments (N)") is ingested as findings.
10. *Participation-Only Artifacts*: A persistent summary card or a trigger acknowledgement is participation-only: no finding, no reply. Refusals, rate-limit notices, own comments, and other participation-only artifacts are never filed as findings; they update the participation record only.
11. *Agent Prompt Blocks*: The bot's "Prompt for AI Agents" block is stripped once, when the firing's batch is built, and never by length clamping; the stored body keeps it, quarantined as untrusted content.
12. *Two-Level Guard per Firing*: The texts a firing ingests (every new comment and bot finding text, and the analysis providers' issue messages) pass the deterministic level-1 validator and then, as one server-built batch (`batch-v1`) of the firing, the level-2 screening of the items whose cleaned text has no cached verdict (SHA-256 verdict cache per scope; one `screener` task per batch part, a batch above the screening split bound being split into parts), fail-closed (link:../model-work/07-untrusted-text-screening.adoc#two-level-guard[Model Work Specification, Two-Level Guard for External Text]). An item flagged `suspicious` is withheld from every model: only its structured fields (author, file, line, kind) and `withheld: flagged by screener` are delivered, its finding stays pending, and its unit ends through its budget and fallback unless a `met` waiver of that finding lets the plan proceed; the hand-back report lists the withheld items. CI log and build excerpts are the server's own job output and pass level 1 only.

`record-metrics` (`998`) composes the plan's figures once. `print-phase-breakdown` (`999`, an operator view) and the landing envelope of `emit-landing` (`1000`) render that composition and never re-derive a figure; the terminal `completed` representation carries only its outcome facts (`merge_outcome`, `landing_delivery`, `owed[]`), not the figures. === Metric Aggregates (`record-metrics`)

* *Priced Units*: `priced_units = input + 5 × output + 0.1 × cache_read + 1.25 × cache_creation` is the internal figure of the migration trigger _Priced units_ only (<<migration-trigger-evaluation>>): no view of the operator, `print-phase-breakdown` included, shows it, and no rule other than that trigger reads it. It is computed from the persisted raw token components (link:../store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Store Schemas Specification, Metrics Store]) with the weights taken from one named constant table (`PricingWeights`; output at 5× input follows list prices), never persisted per job or per phase; a row lacking one of `input`, `output`, `cache_read`, or `cache_creation` contributes to `rows_unmeasured` (the rows of the priced population missing one of those priced inputs; a `not_applicable` one counts as zero) of the priced figure, which is then a floor, and a row that reports only a total makes the priced figure `not_derivable` for that row. A cost the harness reports is recorded data that no figure sums and no view shows (link:../client-profiles/01-profile-schema.adoc#token-usage[Client Profiles Specification, Tokens, Not Money]). *Deliberate change vs. `plan-marshall`*: `plan-marshall` computes `billing_weighted_total` with output at 1×, which understates generation (about 1.1% of the column against about 5.3% of spend); `plan-marshall` baselines are re-derived from their raw components under `PricingWeights` before any comparison.
* *Task & Worker Accounting*: Per phase and role, the tasks are recorded with their outcomes (`submitted`, `asked`, `infeasible`, `lost`), their attempts, the generation of every attempt, and the reason `role_unqualified` where a fallback replaced them; the workers are recorded with their fates (`succeeded`, `failed`, `timed_out`, `killed`, `refused`). A task offered again after it ended without its required submission is a recorded gate signal. Spawn-to-exit duration is measured by the server (`duration_basis: process`).
* *Phase Time Monotonicity*: Every phase block with both timestamps is validated (`end >= start`; start, end, and duration agree when all three exist), and `phase_blocks_checked` and `phase_time_violations[]` are recorded beside `any_phase_missing_end_time`.
* *Stall Rate & Ledger Divergence*: An envelope task that ends with plan tasks remaining and no recorded `yield_reason` (outcome `lost`) counts as `stall`; the stall rate and the `yield_reason` counts (`chain_tail`, `question`, `context`, `off_track`) are published per plan. When two ledgers can diverge (task rows vs audit rows), `record-metrics` publishes `union_rows` and a non-blocking `reconciliation{findings_count}` warning instead of picking one ledger.
* *Spend Classes*: Token usage is published per spend class (`submitted`, `findings_only`, `no_product`, `unmeasured`) cross-tabulated with the termination `status`, with the residual asserted `0` (link:../model-work/09-completion-usage-and-spend.adoc#spend-accounting-budget-anchors[Model Work Specification, Spend Classes]); spend is never classified by `status`.
* [[caller-drift-rate]]*Caller-Drift Rate*: Per plan, the count of link calls rejected per `rejected.reason` and the count of repeated identical rejected calls (same link and same argument digest), with the three failure classes `caller_drift`, `precondition`, and `server_fault` kept apart, and within `caller_drift` the kinds `shape` and `content` kept apart (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/04-errors-and-testing.adoc#rejection-reasons[MCP Tools Specification, Closed Rejection Reasons]). The rate counts only the `shape` rejections and the repeated identical rejected calls. The `content` rejections are counted beside it with how many of them were followed by an accepted call of the same link on the same entity within the state's self-remedy budget, because a stricter content validator refuses more first attempts by construction while the accepted results get better; they are evidence of what the validators catch, not of drift. `PM-MIG-5` compares the rate with the `plan-marshall` baseline of argument-shape failures per plan, which has no content validation (<<migration-trigger-evaluation>>).
* *Per-Document Consumption*: From the served-content ledger (link:../store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Store Schemas Specification, Metrics Store]), per served URI and section the read count, the bytes served, and the repeat reads within one job, together with the per-phase document residency. The skills delivered with an offer are recorded as served to the worker generation that received them. Harness `Read`/`Grep` bytes of a worker are outside the server and are never estimated into these figures.
* *Terminal Phase Boundary*: Phase 6 is recorded with `boundary: provisional`, `measured_until`, and `excluded_steps` (catalogue row `998`); every consumer (the landing, `print-phase-breakdown`, the quality report) renders the label with the figure, never a provisional total as a final one. Every earlier phase carries `boundary: closed` once its close row exists (labelled `re_entered` when rows follow its close).
* *Build Figures*: `build_count` and build time come from the plan's change ledger (`kind = "build"` rows). An unreadable ledger renders `unavailable`; when the runtime job journal shows build jobs for the plan while the ledger is unavailable or empty, a finding is filed.
* *No-Verdict Jobs*: A `timed_out` job, a worker included, counts as `no_verdict` in every roll-up (link:../timeouts/01-job-budgets-and-waits.adoc#no-verdict-rule[Timeouts & Budgets Specification, Timed-Out Outcomes Are No-Verdict]).
* *Wait Lapses*: `wait_lapses` are recorded per lapsed bot wait, keyed by the bot status that ended it (`unproven`, `refused_awaitable`, `refused_hard`; the `finalize.concurrent-wait` outcomes `review_evidence_missing` and `bot_refused_awaitable`, link:../hypermedia-format/03-composite-wait-and-encoder.adoc#_closed_status_enumerations_in_finalize_concurrent_wait[Hypermedia Format Specification, Closed Status Enumerations]), together with whether the awaited operation later settled green. CI waits never lapse (they are re-polled), so they have no lapse kind. The counts enter the landing envelope as policy evidence.
* [[planning-weight]]*Planning Weight*: Per plan, the size of what it planned against the size of what it changed: the intent record's item counts (criteria, non-goals, constraints, decisions, assumptions), the rendered `## Clarified Request` and `outline.md` in non-empty lines, and the lines the plan added and removed between `base_ref` and `HEAD`, with the ratio of planned to changed lines and the plan's lane. A plan without a measured realized footprint has the ratio `unmeasured`. The figure blocks nothing; it shows whether the records of small changes stay in proportion to them (xref:01-planning-phases-1-2.adoc#intent-record[Intent Record], Proportion).
* *Rendering*: `print-phase-breakdown` renders absent or unmeasured figures as `unmeasured`, never `0`, a total over unmeasured rows as at least its value, and the coverage whenever it is decidable (rows and total persisted together, for example "3 of 41 tasks unmeasured" with the reasons), including when rows exist but the sum is zero.

=== Landing Envelope (`emit-landing`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-101[PM-WATCH-PHASE-101]_

The landing envelope carries:

* *Identity & Merge Facts*: `plan_id`, `outcome` (`merged`, `handed_back`, `returned`, or `no_change`; the outcomes of a plan ended through `plan.aborted` are recorded as there, link:../state-catalogue/04-plan-finalize-terminal.adoc#plan-end[State Catalogue, Cancelling and Abandoning Archive]), `landing` (the landing variant in force), `plan_sources` (the kinds of the plan's sources from its manifest: `description`, `documents`, `issue`, `lesson`, `local_changes`, `pr`, or `epic_row`), `recipe` (the recipe key of a recipe's plan, else `null`), `prs[]` (all PRs of the plan, re-recorded when a PR is replaced or split), `merged_pr_numbers`, `merge_commit_sha` (required when merged), `merge_state` (`landed`, `open`, `closed`, `enqueued_not_landed`, `not_applicable`, or `unknown`), derived from the same observation as the plan's `merge_outcome` through the one merge outcome mapping (link:../store-schemas/02-workflow-state-store.adoc#merge-outcome-mapping[Store Schemas Specification, Merge Outcome Mapping]); `unknown` is recorded only when the observation failed and is counted in `missing_facts`, and `owed[]`, the plan's owed items (link:../store-schemas/03-findings-and-review-records.adoc#owed-item-record[Store Schemas Specification, Owed Item Record]), as an explicit empty list when nothing is owed.
* *Figures*: `total_tokens` with its split and its population count (omitted when that count is `0`), `total_wall_seconds`, the `wait_lapses`, and the realized footprint; the Phase 6 figures carry their `boundary: provisional` label, `measured_until`, and `excluded_steps`.
* *Step Record*: `steps[]` with, per finalize step, `step_id`, its firings, the final outcome, `head_at_completion`, `work_performed`, and the dropping or pruning gate, taken from the step records.
* *Waivers & Gaps*: every waiver of the plan with its consumptions (`HEAD`, covered items), every waiver request with its outcome (`waived`, `raised`, `declined`, or `cancelled`), the gap record of a fallback (gate, policy, `cause`, reason or spent budget), the unplanned changes with their provenance, the deliverables removed as infeasible, and the baseline failures a `baseline_red` row accepted.
* *Review Facts*: `review_state` of the merge (`reviewed`, `vacuous`, `unreviewed_by_waiver` with the waiver id, or `not_applicable` for `landing.main`, which has no review), `self_review` (`reviewed`, `not_covered`, or `not_run`, never collapsed into a clean result), and `review_yield` per review bot and for self-review (`findings` and the count per `resolution`, every member stated, zeros included).
* *Fix Balance*: `fix_balance[]`, per remediation round of every class (and per loop-back iteration) with a landed fix commit, `remediation_class`, `round`, `commit_sha`, `findings_cleared`, `findings_introduced`, and `net_worse` (`findings_introduced` greater than `findings_cleared`), `lines_added`, and `lines_removed`, from the server's fix attribution (link:../store-schemas/03-findings-and-review-records.adoc#fix-attribution[Store Schemas Specification, Fix Attribution]); an explicit empty list when no fix landed. Beside it `size_before_fix` and `size_at_landing` (link:../store-schemas/03-findings-and-review-records.adoc#fix-size[Store Schemas Specification, Fix Size]), so that a change that grew through its fixes is visible even when every round cleared more findings than it introduced.
* *Late Findings & Quality Report*: `late_findings[]` (`finding_id`, `source`, `severity`, `carried_to`) for every blocking finding carried out after the merge, as an explicit empty list when there is none; and `quality_report`, the persisted `quality-report.json` when `plan-retrospective` ran, else `not_run`.
* *Findings*: `findings[]`, every `FindingRecord` of the plan (all statuses and dispositions), not a curated subset, so the epic never depends on the archived plan directory to read them.
* *Narrative & Amendments*: `narrative`, a Markdown string field written in the same atomic record as the server-derived facts (`PM-IMPL-2`), with its producer named (the PR body submitted in `create-pr` plus the server-rendered sections; without a PR it is `n/a` with a reason), the plan's `amendments[]`, and the answered question records.
* *Completeness*: `complete` and `missing_facts[]`, computed at emission. Each fact is a typed value, `"n/a"`, or `"unknown"`; `complete: false` is emitted only with a non-empty `missing_facts` (the facts that are `unknown`) and is surfaced as a fact on the epic representation; `unknown` and `n/a` are counted separately. Every fact carries `provenance` (`derived`, or `recovered_by_hand` with a required `verified_by`); a correction is appended as an `annotation` event referencing the original record (link:../store-schemas/04-epic-and-change-ledger.adoc#epic-inbox-record[Store Schemas Specification, Epic Inbox & Plan Mailbox Records]), never a rewrite. The epic representation reports `facts_outstanding` (landings with `unknown` facts) separately from `messages_outstanding` (inbox messages not yet processed).

Rules:

* *One Landing per Plan*: Every landing is plan-typed, and exactly one landing exists per `plan_id`; `n/a` is never legal at the pull-request and merge keys, and at the deliverable and task keys only for `local_changes` landings, whose land lane has no deliverables or tasks, and `pr` landings, which have no deliverables and tasks only from a loop-back (fact states: link:../model-work/08-epic-coordination.adoc#_server_derived_landing_facts_spec_re_grounding_cross_plan_locks[Model Work Specification, Fact States]). When nothing merged, the step emits a non-landing record naming the outcome (`enqueued_not_landed`, `declined`, `no_pr`, `dequeued`, `local_only`, `handed_back`, or `awaiting_human_merge`), never a landing with `n/a` values.
* *Delivery Verification*: After appending, `emit-landing` reads the record back from the epic inbox, validates it against the landing schema (the closed JSON Schema of the fields above, `$id` `https://cuioss.de/plan-marshall-mcp/schemas/landing-envelope.json`, referenced by the `landings.jsonl` record of link:../store-schemas/04-epic-and-change-ledger.adoc#landing-record[Store Schemas Specification, Landing Record]), and records `landing_delivery` (`verified`, `incomplete`, or `failed`) in its step record and in `facts`. A read-back that ends `incomplete` or `failed` routes like a failed append: the server appends, reads back, and validates again within the compiled server-rule retry budget (link:../timeouts/01-job-budgets-and-waits.adoc#server-rule-retry[Timeouts & Budgets Specification, Server-Rule Retry Budget]), and a spent budget records `pending`. An envelope that cannot be delivered (`landing_delivery: pending`: the plan's epic linkage is `indeterminate`, or the retry budget was spent while the linkage is `orchestrated`) is kept in the plan directory as `landing-envelope.json` (the landing schema); later late findings are appended to it, and the epic's landing reconciliation delivers it unchanged and skips it once `landings.jsonl` records its `plan_id`. No writer deletes it; it travels with the plan directory into the archive (link:../store-schemas/04-epic-and-change-ledger.adoc#kept-landing-envelope[Store Schemas Specification, Kept Landing Envelope]).
* *Completion Report*: The completion report of an ended plan (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#reports[Runtime & Interaction Model Specification, Reports to the Operator]) is a view built on the plan's archive and records, the landing record among them; it adds nothing to the envelope.
* *No Landing without an Orchestrating Epic*: A plan whose epic linkage is `not_orchestrated` or `detached` (its epic terminal, archived or aborted; link:../store-schemas/02-workflow-state-store.adoc#epic-linkage[Store Schemas Specification, Origin and Epic Linkage]) appends nothing to an inbox and keeps no envelope: `emit-landing` records `work_performed=false` and `landing_delivery: null`, and its late findings are seeded as lessons.

[[post-run-quality-report]]
== Post-Run Quality Report (`plan-retrospective`)
_Implementation watch: link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-1[PM-WATCH-GEN-1], link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-12[PM-WATCH-GEN-12], link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-60[PM-WATCH-GEN-60], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-38[PM-WATCH-PHASE-38], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-47[PM-WATCH-PHASE-47], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-48[PM-WATCH-PHASE-48], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-49[PM-WATCH-PHASE-49], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-50[PM-WATCH-PHASE-50], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-51[PM-WATCH-PHASE-51], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-52[PM-WATCH-PHASE-52], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-53[PM-WATCH-PHASE-53]_

`default:plan-retrospective` (`995`) runs the server's report engine over the plan's persisted stores (findings, review participation, step records, plan instance versions and composition events, assessments, references, change ledger, waivers, question records) and the metrics snapshot labelled `measured_until` (<<_usage_measurement_window>>), and writes `quality-report.json` (link:../store-schemas/05-metrics-and-quality-report.adoc#quality-report[Store Schemas Specification, Quality Report Record]). The engine is deterministic and in-process: it creates no task, reads no model-authored text as evidence, and every figure it publishes is derived from records. It is observability only: every instrument declares `gates_merge: false`, the step never refuses, and no step reads the report as a precondition. The report is computed before the landing, and `emit-landing` carries it (<<post-run-metrics-and-landing>>).

=== Instrument Contract

* *Populations*: Every published count is `{value, population}`; a rate is published with its numerator and denominator populations, so `2/2` and `40/40` stay distinguishable. A population of `0` renders `unmeasurable`, never a rate; `withheld` (with `withheld_reason`), `unmeasured`, and `0` are distinct values. Populations are rendered as explicit lists, empty lists included.
* *Declared Preconditions*: Every instrument declares what it proves (`proves`), whether any precondition it evaluates can be falsified by the condition it audits (`falsifiable_preconditions`), and whether its own output is inside the population it measures (`self_included`). `self_included: false` requires a reason. The instrument census iterates over all instruments and the report's own meta blocks, so it counts itself.
* *Why Zero*: Every zero carries `zero_reason` (`structural`, `starved`, `gated`, `no_count`, `disciplinary`, `no_block`, or `fired`). A plan or store the engine cannot read contributes `floor` (a lower bound, never healthy). A figure scanned across several stores (for example contradiction incidence across the findings stores of a corpus) carries `records_scanned` and `stores_reached` of `stores_expected`; a zero over fewer stores than expected renders `none reachable`, never `0`, so an honest zero exists only when every expected store was reached.
* *Clean Is Rendered*: A section with zero findings renders its populations and its zeros; no section is dropped because it is empty. An instrument whose status is `unmeasured` still renders every finding it holds.
* [[instrument-stratum]]*One Instrument Version per Population*: Every instrument records the version of what produces its input and its verdict (the engine version, the parser of a build output, the prompt digest of a judging role, the reviewer charter of a review bot); records produced under different versions form separate populations, each sized, and a figure is never pooled across them, in one plan and in corpus mode alike. A change of version within the measurement window splits the figure at the change and renders both halves.
* *Domain Aspects*: Domain bundles extend the report with retrospective aspects (link:../domain-extensions/05-recipes-and-extension-points.adoc#retrospective-aspects[Domain Extensions Specification § Retrospective Aspect Extension Point]); each is an instrument under this contract with `gates_merge: false`, run only for plans of its domain.

=== Quality Chain

* *Derived Step Set*: The finding-filing steps are derived from the registered `FinalizeStepDescriptor` roster (`filesFindings`, validator rule 8), never from a list. Per step the report records `presence`: `not_admitted`, `admitted_not_fired`, `fired`, or `fired_but_refused`, with admission taken from the plan instance version in force when the step would have fired (`not_admitted` = pruned, with its prune reason). A firing is counted per step from its step record, never per audit line. Steps ordered after `plan-retrospective` are `after_window`, never `not_admitted`. A plan whose records lack a plan instance is `indeterminate` on presence and forms its own, separately sized population.
* *Examination*: A fired step reports its `assurance_verdict` (`checked`, `degraded`, `not_reached`, `never_performed`, `attempted_over_empty_scope`); `degraded` (curable by a re-run) and the step's declared `cannotReach` class (a structural limit) are reported separately.
* *Coverage and Yield*: `coverage` is fired over admitted steps, with every not-admitted step named. `yield` is computed over the fired set only and split by `resolution`, `source`, and `severity` with every enum member tallied. Yield scores `fixed` and `rejected`; `accepted`, `taken_into_account`, and `suppressed` count as recorded decisions, never as points; `pending` never scores. Committed findings are `{fixed, accepted, taken_into_account}`, released findings `{rejected, suppressed}`. Coverage and yield are rendered side by side, never as one product.
* *Second Reading Yield*: Where a plan ran two code readings (xref:04-finalize-step-bands.adoc#second-code-reading[Second Code Reading]), the committed findings of the second reading that no finding of the first duplicates, over all committed findings of the two. A figure over a project's plans shows whether the second reading pays for its task.
* *Escape Distance*: The stage that caught each finding is a separate figure, ordered by cost: build < self-review < automatic review < human. It is never folded into yield.

=== Review Retrospective

The checks of `plan-marshall`'s project step `finalize-step-review-retrospective` are one section of the report, read from `review-participation.jsonl` and the findings store. All its verdicts are observability only (`gates_merge: false`, `proves: reviewer_quality_only`) and are recorded as INFO decisions; none enters the pre-merge barrier.

* *Rows*: The rows are the enabled roster (`required_bots ∪ optional_bots`); the required set is a column, never a filter, and a silent reviewer still gets a row. Metrics and participation follow every PR of the plan in `prs[]`, including superseded and split PRs.
* *Review Deficit*: `review_deficit` is one of `clean`, `required_absent`, `unassessable`, `vacuous`, or `unestablished`, with precedence `unassessable` > `vacuous`/`unestablished` > `required_absent` > `clean`. No roster baseline yields `unassessable`; a configured empty roster yields `vacuous` and an omitted roster `unestablished`; `required_absent` needs a non-empty baseline, a non-empty roster, and no required reviewer that reviewed. `clean` requires at least one required reviewer that reviewed and is graded on the actionable count. Participation per reviewer is `measured`, `reviewed_silent`, or `unmeasurable`, persisted with its populations.
* *Coverage Denominator*: Reviewer coverage is anchored to the configured roster baseline. An omitted, empty, or non-superset baseline withholds the figure with its cause; a roster that is a proper subset of the baseline is reported as `roster_narrowed`.
* *Gate Escapes*: A gate escape is a finding raised by a later stage for a defect an earlier gate could see. `rejected` and `suppressed` findings are not escapes (their count is published), and the escape numerator counts only roster reviewers. When the gates ran on different commits the verdict is `gate_tree_unsubstantiated`; when every gate commit precedes the last loop-back it is `gates_did_not_cover_reviewed_tree`.
* *False Positives per Reviewer*: The per-reviewer false-positive figure is the reviewer's `rejected` count over its findings; contradicting records are disclosed, never resolved into a confident zero.
* *Reviewed Tree*: The report asserts that the newest `reviewed_commit_sha` equals the merged head; otherwise it records `reviewed_tree_stale` with both commits.
* *Bypass Audit*: For a merged PR, every required bot must have a participation record covering the merge candidate; otherwise the merge is classified `bypass` as `barrier_skipped`, `refusal_misread`, or `merged_outside_finalize`, unless a consumed `review_evidence` waiver covers the bot, which is reported as `unreviewed_by_waiver` with the waiver id.

=== Footprint & Assessments

The report publishes the three-way footprint reconciliation of the persisted capture (link:../store-schemas/13-leases-integrity-testing.adoc#three-way-footprint[Store Schemas Specification, Three-Way File Footprint Reconciliation]) and compares it with the component assessments. The comparison is `measured` only with a resolved footprint and more than zero assessments read, `no_assessments` when the assessment store is empty, and `inconclusive` otherwise; include and exclude verdicts are withheld unless it is `measured`, and `touched_but_unassessed` paths are always reported.

=== Usage & Measurement Window

The report reads token usage only from the metrics snapshot the metrics reader composes at the report's own call (validator rule 5). The snapshot is the composition of `record-metrics` (<<post-run-metrics-and-landing>>) over the records present at that instant, labelled `measured_until` with that instant; the report never reads `metrics.json`, which `record-metrics` (`998`) writes later.

* *Window Named*: The usage section renders `measured_until` and names the steps outside the window (the report's own step and every step of the plan instance ordered after it), so the report's own usage and the terminal steps are visibly absent, never silently zero. Phase 6 figures carry `boundary: provisional`.
* *Figures*: Tokens per phase with their split, population stamps, and floor labels, tokens per spend class cross-tabulated with the termination `status`, and tokens per finding-filing step and per firing cause (from the step records' `firings[]`). Every figure is a `count` with its population; an unmeasured channel renders `unmeasured`, and a derived ratio over an empty population renders `not_derivable`.
* *Yield per Usage*: Where the quality chain and the usage share a step, the report places the step's yield beside its tokens; it never divides yield by tokens into one score.

=== Corpus Mode

`pm-operator quality-report <plan_id>|--corpus` takes exactly one of the two: with `<plan_id>` it returns the plan's persisted `quality-report.json` (`not_run` when `plan-retrospective` did not run for it); with `--corpus` it computes the report over the archived and active plans of the project. It returns `quality-report.json` of the same schema (`mode: corpus`), folded from the per-plan results of the same engine; a corpus of one plan equals that plan's report. Plans are grouped into populations (with and without a plan instance), and every population is sized. *Deliberate change vs. `plan-marshall`*: the archived-plan auditor (`audit-archived-plan-retrospectives`) is a second implementation; `PM-MCP` has one engine for both modes.

[[repaired-landings]]*Repaired Landings*: The quality chain ends at the merge; what a landed plan did afterwards is visible only when a later plan says so. The corpus report publishes `repaired_landings`: the plans whose landed work a later plan names in `repairs` of its intent record (xref:01-planning-phases-1-2.adoc#intent-record[The Intent Record]) over the plans that landed, as counts with their population. The figure blocks nothing, and it is a lower bound, because a defect repaired without the link is not counted.

== Finalize Commit Instrumentation, Freshness Reconcile & Post-PR Re-Push (`PM-WF-16`)

Whenever any Phase 6 step declaring `mutatesSource == true` (`order < 70`) completes, the finalize engine routes through `finalize.settle-commit`, which invokes `call git.commit_and_push (message_mode=step_or_fallback, push_mode=post_pr_conditional)` (see link:../workflow-dsl.adoc[Workflow DSL Specification]):

1. *Conditional Auto-Commit & Ledger Recording*: If `git status --porcelain` in the worktree is clean, `git.commit_and_push` returns `done` with `clean: true` immediately and the finalize pipeline advances to the next step; a `stepped_out` return enters `finalize.hand-back`. If uncommitted modifications exist, `git.commit_and_push` runs `.gitignore`-aware artifact cleanup, resolves the step's commit message (or deterministic fallback `chore(finalize): apply <step_id> changes`) with the `Co-Authored-By` trailer, pipes the message via `stdin` to `git -C <worktree> commit -F -`, and appends a `kind = "change"` entry (`commit_sha`, `changed_paths`, `worktree_sha`) to `change-ledger.jsonl`.
2. *`head_at_completion` Re-Stamping*: If the completed `mutatesSource == true` step also declares `headDependent == true` (such as `simplify`, `security-audit`, `pre-push-quality-gate`, `automatic-review`, `analysis-roundtrip`; the in-branch fixes of the remediation units re-stamp the step whose class they fixed), `git.commit_and_push` atomically updates that step's persisted `head_at_completion` in `mcp/status.json` to the newly created `commit_sha` without emitting a duplicate step completion event. This prevents the step's own commit from self-invalidating its verdict on a subsequent re-entry check.
3. *`freshness_reconcile` for Commits after the Latest Successful Build*: If any `mutatesSource == true` step produces a commit after the latest successful build (not only steps at `order >= 10`, `PRE_PUSH_QUALITY_GATE_ORDER`; for example `architecture-refresh` at `9` committing on re-entry), `git.commit_and_push` records a `freshness_reconcile` entry in `mcp/status.json` containing `(commit_sha, step_id, prior_build_worktree_sha)` where `prior_build_worktree_sha` is read from the latest `outcome == "succeeded"` build entry in `change-ledger.jsonl`. When the `git.pre-commit-verify-freshness` gate runs before pushing, it consults `freshness_reconcile` so a known non-build-affecting finalize commit (such as an ADR addition in `adr-propose`) is recognized as reconciled, whereas any modification to buildable source paths invalidates `pre-push-quality-gate` and re-runs the Settle quality gate first. A commit whose changed paths are all build-neutral per the build map (for example generated architecture metadata) is reconciled without a rebuild.
4. *Post-PR Conditional Re-Push (`order > 20`)*: The transition entering `finalize.settle-commit` persists `settle_trigger {step_id, order}`; a caller that is not a step (`execute.exit-barrier`, `land.exit-barrier`, `finalize.adopt-pr`) writes order `0`, so a commit after a loop-back is never pushed before the Settle band re-runs. When the trigger's `order > 20` (after `default:create-pr`, such as `default:adr-propose` at `62`) and the project has a push remote (derived fact `push_remote`), `push_mode=post_pr_conditional` evaluates `push_required`, verifies freshness and `branch-sync-state` parity, pushes the new commit to `origin/<branch>`, and returns `done` with `pushed: true`, routed by the guard `result.pushed` to `finalize.review-cap-check`, whose `within_caps` outcome enters `finalize.concurrent-wait` so CI and review bots re-evaluate the updated PR `HEAD`. The in-branch fixes of the remediation units commit inside the unit with `push_mode=always` and await their own class at the new `HEAD` (link:../workflow-dsl/03-reference-excerpt.adoc#_reference_workflow_dsl_excerpt_finalize_pmwf[Workflow DSL Specification, `phase-6-finalize.pmwf` Excerpt]).

[[realized-footprint-capture]]
== Realized Footprint Capture & Footprint-Scoped Steps
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-64[PM-WATCH-PHASE-64], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-36[PM-WATCH-STORE-36]_

Finalize steps obtain the realized footprint (link:../store-schemas.adoc[Store Schemas Specification], Three-Way File Footprint Reconciliation) through one resolver:

* *Reconcile Before Footprint-Scoped Steps*: At Phase 6 entry and after every `finalize.settle-commit`, the engine re-captures `realized_files` and runs the three-way reconciliation before any step whose scope is the footprint (`simplify`, `security-audit`, `pre-submission-self-review`, `pre-push-quality-gate`) runs.
* *One Resolver for Diff-Fed Steps*: Every diff-fed step reads the footprint through this resolver, which resolves only from the plan's own worktree. Without a resolvable footprint the step takes an outcome of class `INDETERMINATE` that names the cause and completes `failed` (`pending` when the worktree is not yet materialised, `disabled` when the plan runs without a worktree), never a clean `done` and never another tree's footprint.
* *Capture Before Destruction*: `branch-cleanup` persists the realized footprint in `references.json` before it removes the worktree; every post-merge consumer reads the persisted capture.
* *Only `measured` Is Evidence*: The three-way reconciliation, the scope-creep and coverage checks, the pre-merge footprint checks inside `branch-cleanup`, and every post-merge footprint consumer compare against `realized_files` only when `realized_state.state == measured`. `unresolved` and `not_captured` (link:../store-schemas/13-leases-integrity-testing.adoc#three-way-footprint[Store Schemas Specification]) make each of them record `indeterminate` with the state and cause named, never a clean or empty result.

[#dependency-delta]
== Dependency Delta Check (Pre-Merge)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-60[PM-WATCH-PHASE-60]_

The server verifies that every third-party dependency the plan adds was approved when `outline.gate` passed (Phase 3, § 5). The check is part of the footprint reconciliation: it runs with the three-way reconciliation at Phase 6 entry and after every `finalize.settle-commit` (<<realized-footprint-capture>>), and again inside `default:branch-cleanup` after its rebase, against the re-derived `base_ref`, immediately before the Pre-Merge Review Barrier is evaluated.

1. *Changed Build Files*: From the realized footprint (only when `realized_state.state == measured`), the server selects every path claimed as a build file by the build-file dependency parser of a build domain (link:../domain-extensions/03-module-discovery.adoc#_server_owned_module_discovery_enrolled_discovery_jobs[Domain Extensions Specification, Build-File Dependency Parser]): Maven `pom.xml`, Gradle build files, `package.json`, `pyproject.toml`.
2. *Added Coordinates*: Each changed build file is parsed at `base_ref` and at `HEAD` (a file absent at `base_ref` contributes an empty base set). The added coordinates are the ecosystem-qualified coordinates declared at `HEAD` and not at `base_ref`, over every dependency scope the parser reports (including test, development, and optional dependencies). Coordinates of the project's own modules (module discovery snapshot) are not third-party and are excluded; a version change is not an addition. The removed coordinates are those declared at `base_ref` and not at `HEAD`, by the same rules; they are no finding of this check, and the self-review judges each that no own call and no deliverable names (<<change-map>>).
3. *Blocking Finding per Undeclared Coordinate*: For every added coordinate the approved dependency set does not name, the server files one blocking finding (`source: dependency_delta`, finding type `undeclared_dependency`, `severity: major`, `file_path` the build file, `summary` naming the coordinate and the build file; link:../store-schemas.adoc[Store Schemas Specification], Findings Ledger Record). A coordinate the approved outline names is not reported (matched negative control). A repeated run files no duplicate for a coordinate that already has a finding. The model may triage the finding only with `FIX` (remove the dependency); it is accepted otherwise only by an operator waiver (`findings:dependency_delta`), because accepting it approves a dependency the outline gate never saw, and without one the plan is handed back.
4. *Never Clean without Evidence*: The check records `indeterminate`, never clean, when the realized footprint is not `measured`, when a changed build file has no build-file dependency parser, or when a parser fails on either side (the parse diagnostic and file are named). An `indeterminate` check blocks like a finding: the server files one blocking finding (`source: dependency_delta`, finding type `dependency_delta_indeterminate`, `file_path` the unparsed build file or null, `summary` naming the cause), so the Pre-Merge Review Barrier (Predicate 1) refuses the merge; the same triage restriction as for `undeclared_dependency` applies.
5. *Result*: The check publishes `dependency_delta: {state: clean | findings | indeterminate, build_files_checked, added[], removed[], undeclared[], cause}` in the finalize facts and in the merge record; `clean` requires at least one parsed changed build file or an empty set of changed build files, stated as `build_files_checked: 0`.

[#capability-test-guard]
== Capability Test Guard (Pre-Merge)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-119[PM-WATCH-PHASE-119]_

A capability requirement states what the system does; the tests named in its `verified_by` keep the code saying the same (xref:01-planning-phases-1-2.adoc#capability-specs[Capability Specs]). The server checks that no plan removes such a test without stating the change of the requirement it verifies. The check runs with the Dependency Delta Check (<<dependency-delta>>): at Phase 6 entry, after every `finalize.settle-commit`, and inside `default:branch-cleanup` after its rebase, immediately before the Pre-Merge Review Barrier is evaluated.

1. *Guarded Tests*: The capability specs at `base_ref` give, per requirement, its `verified_by` paths.
2. *Removed Tests*: From the realized footprint (only when `realized_state.state == measured`), a guarded path present at `base_ref` and absent at `HEAD` is removed, unless git's rename detection between `base_ref` and `HEAD` pairs it with a new path; a renamed path is followed, and `architecture-refresh` writes the new path into `verified_by`.
3. *Blocking Finding per Unstated Removal*: For every removed path whose requirement the intent record neither `modified` nor `removed` (its `capability` binding), the server files one blocking finding (`source: capability_tests`, finding type `capability_test_removed`, `severity: major`, `file_path` the removed test, `summary` naming the capability, the requirement, and the test). A removed test of a requirement the record changes is not reported (matched negative control); a repeated run files no duplicate. The model may triage the finding only with `FIX` (restore the test, or move its assertions into a file that git pairs with it); it is accepted otherwise only by an operator waiver (`findings:capability_tests`), because accepting it leaves a stated behaviour without the test that held it.
4. *Never Clean without Evidence*: The check records `indeterminate`, never clean, when the realized footprint is not `measured` or a capability spec at `base_ref` does not parse; an `indeterminate` check files one blocking finding (`source: capability_tests`, finding type `capability_tests_indeterminate`, `summary` naming the cause) under the same triage restriction.
5. *Result*: `capability_tests: {state: clean | findings | indeterminate, guarded, removed[], renamed[], unstated[], cause}` in the finalize facts and in the merge record; `clean` with `guarded: 0` when no requirement names a test.

[#fix-proof]
== Fix Proof Guard (Pre-Merge)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-124[PM-WATCH-PHASE-124]_

A test that passes after a fix proves the bug is gone only if it failed before the fix, and only if it still is the test that failed. The server checks both from the change ledger. The check runs with the Capability Test Guard (<<capability-test-guard>>).

1. *The Red Run*: The writer role of a `fix` criterion verified by `test` writes the test first and runs it with `pm_build(expect: red, criterion: AC-<n>)` (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/02-service-and-skill-tools.adoc[MCP Tools Specification, `pm_build`]). A run counts as the criterion's red run only when it ended `failed` with at least one failed test in its parsed result: a compile error, `failed_unparsed`, or a run that went green proves nothing. The ledger row records the criterion and, in `red_tests`, the path and blob of every test file the worktree changed against `base_ref`. The role's task facts name the criteria that still owe a red run.
2. *Blocking Finding per Missing Proof*: For every `fix` criterion verified by `test` without a red run that precedes the last green run of the plan, the server files one blocking finding (`source: fix_proof`, finding type `fix_red_missing`, `severity: major`, `summary` naming the criterion). The model may triage it only with `FIX`: a task of the writer role reverts the production change in the plan's worktree, takes the red run, and restores the change; a fix that cannot be reproduced by a test is accepted only by an operator waiver (`findings:<class>`).
3. *Non-Blocking Finding per Changed Test*: Every path of a `red_tests` whose blob at `HEAD` differs from the recorded one files one non-blocking finding (`source: fix_proof`, finding type `fix_test_changed`, `file_path` the test), which the code review of the self-review judges with the difference in its facts, because a later edit may strengthen the test as well as weaken it.
4. *Never Clean without Evidence*: The check records `indeterminate`, never clean, when the change ledger is unreadable; an `indeterminate` check files one blocking finding (`source: fix_proof`, finding type `fix_proof_indeterminate`) under the same triage restriction.
5. *Result*: `fix_proof: {state: clean | findings | indeterminate, owed, proven[], missing[], changed[], cause}` in the finalize facts and in the merge record; `clean` with `owed: 0` when the record has no such criterion.

[#added-line-scan]
== Added-Line Scan (Pre-Merge)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CRED-5[PM-CRED-5: Outbound Domain Scoping & Output Secret Redaction]_
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-122[PM-WATCH-PHASE-122], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-123[PM-WATCH-PHASE-123]_

The checkout is trusted (link:../model-work/07-untrusted-text-screening.adoc#local-trusted[Model Work Specification, What Is on This Machine Is Trusted]): every later plan reads it as the project's own, unscreened. A writer that read an injection can write text into it that a reviewer does not see but a model reads, and the next plan that reads the file carries it on. The server checks the lines a plan adds before they reach the base branch. The check runs with the Dependency Delta Check (<<dependency-delta>>): at Phase 6 entry, after every `finalize.settle-commit`, and inside `default:branch-cleanup` after its rebase, immediately before the Pre-Merge Review Barrier is evaluated.

1. *Added Lines*: From the realized footprint (only when `realized_state.state == measured`), every text file's lines added at `HEAD` against `base_ref`, read from git objects; a file git classifies as binary is not read and is listed in the result.
2. *Hidden Characters, Blocking*: The code points the Unicode stage of the ingestion validator removes (link:../job-runtime/03-parsers-and-gates.adoc#ingestion-validator[Job Runtime Specification, Ingestion Validator], stage 1), detected and never removed, except a variation selector or a zero-width joiner inside an emoji sequence and a byte-order mark at the start of a file. For every added line that holds one, the server files one blocking finding (`source: added_lines`, finding type `hidden_characters`, `severity: major`, `file_path` and `line`, `summary` naming the code points and their positions). An escape sequence that spells such a code point in source text (`\uE0001`) is no hit (matched negative control). A repeated run files no duplicate for a line that already has a finding. The model may triage the finding only with `FIX` (remove the characters); it is accepted otherwise only by an operator waiver (`findings:added_lines`), because a reviewer cannot see what it accepts.
3. *Instructions to a Model, Non-Blocking*: In a plan that read text marked untrusted (a source marked untrusted, or a finding of source `github_pr`, `gitlab_mr`, or `analysis` in its findings store), the rule table of the ingestion validator (stage 4) runs over the NFKC copy of the added lines. Each hit is one non-blocking finding (`source: added_lines`, finding type `model_instruction`, `file_path` and `line`, `summary` naming the rule), given to the `review-code` half of the self-review as evidence (xref:04-finalize-step-bands.adoc#_normative_step_catalogue_across_ordering_bands[Step Catalogue], `pre-submission-self-review`) and listed in the hand-back report. A plan that read no untrusted text runs no rule table, since skills, agent files, and prompts address models by design.
4. *Credential-Shaped Values, Blocking*: A worker reads what its confinement allows, the project's own files (an untracked `.env`) and its harness's login included, and a value it copies into a file or a commit message is published by the push; the redaction registry cannot catch it, because the runtime never held it. This stage therefore reads, unlike items 1 to 3, the lines each commit of `base_ref..HEAD` adds and each commit's message, so that a value one commit adds and a later one removes is still found. A hit is a token of a provider prefix of the compiled credential pattern table (for example `ghp_`, `github_pat_`, `glpat-`, `sk-ant-`, `AKIA`, each with the length and alphabet of its format), the header line of a PEM private key, or an exact value of the redaction registry (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-credential-cli[CLI, Coordination & Security Specification, Runtime Secret Redaction]). For each hit the server files one blocking finding (`source: added_lines`, finding type `credential_shaped`, `severity: major`, `file_path` and `line` or the commit, `summary` naming the pattern and the commit, never the value) and records a `security` audit record. A prefix without a value of its format (`ghp_` in a sentence) and a value of the pattern table's documented example set are no hit (matched negative control). No model triage resolves the finding: a later commit that removes the value leaves it in the history the push would publish. No push of the plan (`default:push`, the base push of `landing.main`) happens while one is open, and the plan waits for the operator, who waives it (`findings:added_lines`, for a test fixture or a false match) or ends the plan at its hand-back, which keeps the branch local and names the finding in the landing record, so that the operator removes the value from the history before anything leaves the machine; the stage also runs over the commit the hand-back settles, before the hand-back chooses its form (xref:06-finalize-re-entry-and-merge.adoc[Finalize Re-Entry & Merge], Hand-Back).
5. *Never Clean without Evidence*: The check records `indeterminate`, never clean, when the realized footprint is not `measured` or a file at `HEAD` or `base_ref` cannot be read; an `indeterminate` check files one blocking finding (`source: added_lines`, finding type `added_lines_indeterminate`, `summary` naming the cause) under the triage restriction of item 2.
6. *Result*: `added_lines: {state: clean | findings | indeterminate, files_checked, lines_checked, commits_checked, binary_skipped[], hidden[], instructions[], credentials[], rule_table_ran, cause}` in the finalize facts and in the merge record; an entry of `credentials[]` names the pattern, the file and line or the commit, never the value.

[[outbound-text-credential-check]]*Outbound Text*: The pattern table of item 4 also runs over every free-text value the server sends to a provider on a plan's behalf (a pull-request or merge-request title and body, a comment, a review reply), immediately before it is sent. A hit refuses the write with `credential_shaped_text`, naming the field and the position, never the value; nothing is sent, a `security` audit record is written, and the task that composed the text receives the refusal and writes it again within its budget.

[#change-map]
== Change Map
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-114[PM-WATCH-PHASE-114]_

The operator of a large change reads its structure before its lines: which modules it adds or removes, which dependencies between modules it adds or removes, and which third-party dependencies it adds, removes, or replaces. The server computes this *change map* without a model, with the Dependency Delta Check (<<dependency-delta>>), at Phase 6 entry and after every `finalize.settle-commit`.

1. *Two Trees*: The in-process crawl of module discovery (link:../domain-extensions/03-module-discovery.adoc#_server_owned_module_discovery_enrolled_discovery_jobs[Domain Extensions Specification, Module Discovery]) runs over the tree at `base_ref`, read from git objects and never checked out, and over the worktree at `HEAD`. Enrolled discovery jobs are not run for the map; a module whose edges only such a job provides is drawn without them and marked `edges_partial`.
2. *Delta*: `modules_added[]`, `modules_removed[]`, `edges_added[]` and `edges_removed[]` (`from` module, `to` module), and the third-party coordinates of the dependency delta, `added[]` and `removed[]`, where a removed and an added coordinate of the same module and scope form a `replaced[]` pair. A module whose descriptor failed to parse on either side is named with its diagnostic, and the map is `partial`, never complete.
3. *Rendering*: a fixed-width text diagram of at most `20` boxes: the modules the delta names and those with a path in the realized footprint, each with its direct neighbours; an added edge drawn `+-->`, a removed edge `--x`, a removed or replaced third-party dependency named under its module. A larger map is rendered as the lists alone. The diagram is shown in the server-owned section `## Change Map` of the pull-request body, in the landing record, in the completion report, and as the resource of the plan (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/03-resource-uris.adoc[MCP Tools Specification, Resource URIs], `pm://plan/{plan_id}/change-map`). For the web app the same boxes and edges are laid out as data (link:../workflow-dsl/07-loop-back-diagrams-verification.adoc#diagram-layout[Workflow DSL Specification, Positioned Layout]), which the web app draws in place of the text diagram.
4. *Judged at Self-Review*: The facts of `review-requirement` carry the map; every removed or replaced third-party coordinate that no own call (xref:03-q-gate-and-execute.adoc#own-calls[Own Calls of a Writer]) and no deliverable names is judged there (xref:04-finalize-step-bands.adoc#_normative_step_catalogue_across_ordering_bands[Step Catalogue], `pre-submission-self-review`). An added coordinate stays the Dependency Delta Check's.
5. *Result*: `change_map: {state: complete | partial | indeterminate, modules_added[], modules_removed[], edges_added[], edges_removed[], replaced[], cause}` in the finalize facts; `indeterminate` when the realized footprint is not `measured`. The map blocks nothing by itself.

[#merge-danger]
== Merge Danger
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-13[PM-WF-13: Finalize Step Ordering Bands, Verdict Currency & Pre-Merge Barrier]_

Before the operator merges, the pull request says what would be hard to undo and how far the change reaches. The server composes this from the plan's records, without a model, whenever it renders the server sections of the body:

1. *Hard to Undo*: every decision of the plan whose reversibility is `costly` or `irreversible` (link:../model-work/06-envelopes-questions-deadlines.adoc#decision-structure[Model Work Specification, The Decision Structure]), `irreversible` first, each with its title, the option taken, who took it (the operator, a quorum, or a server rule), and its `pm://` URI. With none recorded the section says `No costly or irreversible decision recorded`; it never states that the change is safe to undo.
2. *Reach*: the modules with a path in the realized footprint and the modules that depend on them directly, both from the change map's crawl at `HEAD` (<<change-map>>), as two counts and the module names up to `20`; with a map that is `partial` or `indeterminate` the reach is named as not computed, never as empty.
3. *Rendering*: the server-owned section `## Merge Danger` of the pull-request body, rendered with the other server sections (xref:04-finalize-step-bands.adoc#_normative_step_catalogue_across_ordering_bands[Step Catalogue], `create-pr`), and the same lists in the landing record. The section blocks nothing.

[#code-scanning-provider]
== Code Scanning Alerts as a Code Analysis Provider
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-9[PM-WF-9: Composite Wait States & Short-Circuit Failure Handling]_

_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-120[PM-WATCH-PHASE-120]_

GitHub code scanning holds the results of every tool that uploads SARIF to it: CodeQL, Semgrep, and model-driven review pipelines that must run outside the operator's machine, in an isolated CI job or virtual machine with credentials of their own. PM-MCP reads those results; it never runs such a tool. The adapter `github-code-scanning` of `pm-provider-github` implements the code-analysis contract of `pm-core` (link:../../../../plan-marshall-documentation/doc/specification/module-structure.adoc[Module Structure, Code analysis]) and is polled by `default:analysis-roundtrip` like every code analysis provider.

1. *Configuration*: `project.json` `integrations.github-code-scanning` with `tools`, the non-empty list of SARIF tool names whose alerts count; an alert of another tool is ignored. The adapter uses the effective variant and credential of the `github` integration (native REST or `gh api`), so it needs no credential of its own.
2. *Status* (`analysis.status`, target the pull request and its head commit): `running` while a configured tool has no analysis of the head commit and the head's CI is not complete; `findings` when an issue of step 3 is open; `passed` when every configured tool has an analysis of the head commit and no issue is open; `undecidable`, naming the tool, when the head's CI completed and a configured tool uploaded no analysis of the head commit, when an analysis reports errors, or when code scanning is not enabled for the repository. The adapter never reports `not_run`: a configured tool that did not report is never read as clean.
3. *Issues* (`analysis.issues`): the open alerts of the configured tools on the pull request that the base branch does not have. Each is a finding `source: analysis` of provider `github-code-scanning`: `rule_id` is `<tool>/<rule id>`, `file_path` and `line` those of the alert's most recent instance, `severity` mapped from the alert's security severity (`critical` to `critical`, `high` to `major`, `medium` to `minor`, `low` to `info`), else from the rule's level (`error` to `major`, `warning` to `minor`, `note` to `info`), and `external.issue_key` the alert number. The alert's message and its rule's help are external text, screened before any model receives them (<<_comment_ingestion,Comment Ingestion>> applies the same screening). GitHub keys an alert on the tool's fingerprint of the result, so a re-run of the tool keeps the alert number and a repeated ingestion files no duplicate.
4. *Responses*: only a finding resolved `SUPPRESS` is transmitted, as a dismissal carrying the plan id and the reason: `claim_refuted` as `false positive`; `rule_exception`, `generated_code`, and `tool_limitation` as `won't fix`; `duplicate` is not transmitted. A dismissal closes the alert for the whole repository, so the responder dismisses only an alert whose first instance lies on the plan's pull request; an alert that the base branch also has is never in the issue set of step 3. A `FIX` transmits nothing: the alert closes when the tool's next analysis no longer reports it.
5. *Severity as Reported*: the findings of this provider enter `remediation.analysis` and are waivable as `findings:github-code-scanning`; the security calibration (<<security-audit-calibration>>) caps the findings of the plan's own security review and leaves a tool's mapped severity as it is.

[#security-audit-calibration]
== Security Audit Calibration: Ingress, Severity Caps & History
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-13[PM-WF-13: Finalize Step Ordering Bands, Verdict Currency & Pre-Merge Barrier]_

_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-121[PM-WATCH-PHASE-121]_

The security audit (xref:04-finalize-step-bands.adoc#_normative_step_catalogue_across_ordering_bands[catalogue row `7`]) is a model's review whose findings are never waivable, so an inflated severity costs a loop-back and a finding without a path to it costs a fix of nothing. The following rules keep its findings grounded, cap their severity from facts the server checks, and give the review the project's own security history.

1. *Scope*: a finding names a weakness that attacker-controlled data reaches, and carries `security.ingress`, the file and line where that data enters, checked like the finding's own location (link:../store-schemas/03-findings-and-review-records.adoc#located-finding-grounding[Store Schemas § Located Finding Grounding]). The review does not report misuse that needs an actor the system already trusts and no path from untrusted input, missing defence in depth without such a path, exhaustion of a resource unless the threat model marks the asset's availability critical, or hygiene without an exploit path. An intrinsically weak construct (a broken hash used for a security purpose, a secret in the source) is a finding without a caller.
2. *Calibration Facts*: with each finding the task submits `attacker_position`, `privileges_required`, and `evidence_level`. `test_reproduced` is accepted only with `evidence.ref` naming a build job of the plan's run whose failing test reproduces the weakness; otherwise the server records `reasoned`.
3. *Severity Caps*: at filing the server sets `severity` to the lowest of the submitted severity and every cap whose condition holds, writes the rule of the lowest cap into `security.cap_rule`, and keeps the submitted value in `submitted_severity`. The cap table is the declaration `security_severity_caps` of the finalize phase unit `phase-6-finalize` (link:../workflow-dsl/02-units-jobs-decisions.adoc#unit-declarations[Workflow DSL § Unit Declarations]); its shipped value is the table that passed the calibration of `review-security`:
+
[cols="2,1",options="header"]
|===
|Condition |Highest severity

|`evidence_level: reasoned` |`major`
|`privileges_required: low` |`major`
|`privileges_required: high` |`minor`
|`attacker_position: adjacent` or `local` |`major`
|`attacker_position: trusted_operator` |`minor`
|===
+
Compiled bounds: a cap never raises a severity, a condition names only fields and values of the `security` object, and a cap is a value of the severity enumeration; a project's unit may lower, raise, or remove a cap within these bounds.
4. *Threat Model*: the team may keep `.marshall/config/threat-model.adoc`: the trust boundaries with their entry points, the exposure of each deployed component (`exposed`, `internal`, `privileged`), and the assets with their availability tier (`critical`, `standard`, `low`). The task receives it when present; absent, its facts state `threat_model: absent`, and the review takes every component as exposed.
5. *Security History*: without a model, the server gives the task, for the files of the plan footprint, the `security_audit` findings of the project's archived plans resolved `fixed` on those files (summary, file, line, plan, and fix commit), newest first, at most `20` with the remainder counted; an archive that cannot be read is named in the facts, never rendered as no history.
6. *Removed Security Guards*: when a removed-guard candidate of the pre-submission self-review (link:../domain-extensions/05-recipes-and-extension-points.adoc#self-review-surfacer[Domain Extensions § Removed Guards]) has removed lines that the fix commit of such an earlier finding added (git blame at the plan's base commit), the server files it as a blocking `self_review` finding of type `security_guard_removed`, naming the earlier finding and its plan, with the earlier finding's severity; it is triaged like a security finding, never waivable, and a plan that removes the guard on purpose answers it with `FIX` or with `SUPPRESS` on refuting evidence.

== Java `FinalizeStepDescriptor` Record Schema & Static Checks

*Status: IN PROGRESS.* Every built-in, bundle, or project-local finalize step is represented in `pm-workflow` by the immutable record link:../../../pm-workflow/src/main/java/de/planmarshall/workflow/finalize/FinalizeStepDescriptor.java[`FinalizeStepDescriptor`] with its nested types `Lane`, `LaneClass`, `InputScope`, and `ConfigurableKey` and its order constants (link:../../../pm-workflow/doc/developer/workflow-finalize.adoc[Finalize Pipeline Developer Guide]); `pm-workflow` holds no table of the default steps, whose roster is part of the assembly.

A gate step declares in `cannotReach` the defect class it cannot detect (for example `ci-verify`: unreviewed semantics and untested paths), which is rendered with its verdict. An empty examined scope renders "NONE — this pass analysed no dimension; it certifies nothing".

=== Build-Time & Startup Static Invariant Verification (`FinalizePipelineValidator`)
_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-3[PM-WATCH-DSL-3], link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-20[PM-WATCH-GEN-20], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-39[PM-WATCH-PHASE-39], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-55[PM-WATCH-PHASE-55]_

`FinalizePipelineValidator` validates the complete registered `List<FinalizeStepDescriptor>` at build time (via JUnit tests, over the default roster) and on every load of a project's finalize unit (over the project's roster: the default descriptors of the steps its `phase-6-finalize.pmwf` contains plus its project step descriptors), failing closed on any violation; a violation in a project roster refuses the project's plan lifecycle with the file and line (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units & Compiled Invariants]).

The validator, link:../../../pm-workflow/src/main/java/de/planmarshall/workflow/finalize/FinalizePipelineValidator.java[`FinalizePipelineValidator`] with its closed rule set link:../../../pm-workflow/src/main/java/de/planmarshall/workflow/finalize/PipelineRule.java[`PipelineRule`], implements rules 1 to 5, the input-scope part of rule 6, and the derivation of the finding-filing steps of rule 8 over a roster it takes as input, and the loader of the project-owned units runs it over the project roster on every load (link:../../../pm-workflow/doc/developer/workflow-finalize.adoc#_the_rules[Finalize Pipeline Developer Guide § The Rules]). The build-time run over the default roster belongs to the assembly and is not implemented yet. What a descriptor cannot decide stays here, a named hook of `PipelineRule`, not implemented yet:

* *Runtime guards of rules 3 and 5*: the post-run source guard checks `git status --porcelain` after every post-merge step to detect stray tracked writes. The engine has one metrics reader, the composition function of `record-metrics`: for a consumer ordered after `998` it returns the recorded `metrics.json`, and for a consumer ordered before it a snapshot composed at the consumer's call and labelled `measured_until`, never the unwritten store. A consumer before `998` that renders a snapshot figure without its `measured_until` label violates the rule at runtime.
* *Rule 6, `work_performed`*: every step whose `done` outcome is reachable through a no-op/skipped branch as well as a work-performing branch must include `"work_performed"` in `recordsFacts` and emit `work_performed=true|false`.
* *Rule 7, No Guard After the Irreversible Move*: No step with $\text{order} > \text{MERGE\_GATE\_ORDER}$ (`70`) may declare an outcome that refuses on its inputs; post-merge steps record degraded results (`indeterminate` facts, `landing_delivery: pending`, carried late findings, owed items) instead. An I/O failure of a post-merge step routes to a bounded `retry` state or `finalize.step-failed`, never to a refusal that strands the merged plan. There is no exception: `archive-plan` holds no open pull request.
* *Rule 8 at runtime*: the findings store refuses a write from a step whose `filesFindings` does not contain the finding's `source`.
