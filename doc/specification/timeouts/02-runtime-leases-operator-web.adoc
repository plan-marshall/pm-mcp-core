[#runtime-lifecycle]
== Runtime Lifecycle

[cols="2,3,2,2,2,3,2"]
|===
|Name |Value / derivation |Configurable? |Floor / cap |Applies to |Behaviour on expiry |Defined for

|[[runtime-start-timeout]]Runtime start timeout
|`5` for a runtime started on demand to answer an authenticated round trip.
|fixed
|—
|every `pm-operator` command that starts the runtime on demand, which holds `locks/runtime-start.lock` until its authenticated round trip succeeds or this timeout expires; `pm-operator status` waiting for a live runtime's answer; a worker's relay waiting for the socket to accept connections; an exiting runtime waiting for the successor it started after a restart or an upgrade
|The command fails with a diagnostic naming `logs/daemon.log`; `pm-operator status` reports "not responding"; the relay answers pending requests with the JSON-RPC error `runtime_unavailable` and retries on the next request; after an upgrade the exiting runtime terminates the successor, switches the links back, and starts the previous version (link:../runtime-lifecycle/01-startup-recovery-drain.adoc#runtime-lifecycle-operations[Runtime Model, The Runtime's Lifecycle]).
|link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#_start_modes[Runtime Model, Start Modes]; link:../../../../plan-marshall-documentation/doc/specification/runtime-model/04-sessions-and-workers.adoc#_failure_semantics[Runtime Model, Failure Semantics]

|[[runtime-http-idle-timeout]]Runtime HTTP idle timeout
|Derived: strictly above the larger of the caps of the xref:01-job-budgets-and-waits.adoc#bounded-wait[Bounded wait window] and the xref:01-job-budgets-and-waits.adoc#progress-wait[Progress wait upper bound], so no held `pm_wait` or `pm_build` call reaches it.
|derived (compiled into `quarkus.http.idle-timeout` and `quarkus.mcp.server.connection-idle-timeout`)
|—
|connections on the runtime's socket listener (`/mcp` and `/api/v1`)
|The runtime closes the idle connection; a held call never expires by it, since every wait answers within its window.
|link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#_transport_endpoint[Runtime Model, Transport Endpoint]

|[[project-recovery-wait]]Project recovery wait
|`10` for a call addressing a project whose per-project recovery (lazy or background pass) has not finished.
|fixed
|—
|every MCP call addressing a project (by the scope of the worker's leased task) after a runtime start, and every Local API request addressing a project
|The call returns the retryable error `runtime_recovering` (`isError: true`; a Local API request: the same code of the `pm-api` error codes); the recovery continues, and a repeated call is served once it has finished. Nothing of the call is executed.
|link:../runtime-lifecycle/01-startup-recovery-drain.adoc#per-project-recovery[Runtime Model, Per-Project Recovery]; link:../../../../plan-marshall-documentation/doc/specification/mcp-tools.adoc[MCP Tools] (closed error codes); link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#local-api[Runtime Model, Local API]; implemented: link:../../../pm-runtime/src/main/java/de/planmarshall/runtime/start/ProjectRecovery.java[ProjectRecovery] (`RECOVERY_WAIT`), link:../../../../plan-marshall-documentation/doc/concepts/runtime-lifecycle.adoc#per-project-recovery[Concepts § Per-Project Recovery]

|[[drain-timeout]]Drain timeout
|`600`
|`drain_timeout_seconds` in `machine-config.json`
|minimum `0` (`0` terminates running jobs at once), maximum `3153600000` (100 years of 365 days, so the deadline of the drain can always be represented); a negative, non-integer or larger value, and a `machine-config.json` that cannot be read or does not parse as one JSON object, is invalid: the default `600` applies and a warning names the file and the reason; the start and the drain never fail for it
|running jobs at `SIGTERM`/`SIGINT` / `pm-operator drain` and at the operator's stop with `when: drain`, for which a stop with `when: now` cuts it to `0`; the wait of `pm-operator drain` for the runtime's exit
|Remaining job groups are terminated (xref:01-job-budgets-and-waits.adoc#grace-period[Grace period]) and recorded `killed`, their build and model slots released, their job tokens revoked, the generations of workers fenced and their task leases released (the tasks stay `queued` for the next start), and `queued` jobs recorded `killed`; at the start of the drain no task is offered any more and every waiting worker is answered `end`, so only workers holding a task run into the drain timeout; warm language servers are shut down; merge-queue and review-bot leases are left in place and handled at the next start like those of a crash (<<leases>>); the runtime exits. `pm-operator drain` waits for the exit up to the drain timeout plus the xref:01-job-budgets-and-waits.adoc#grace-period[Grace period] plus a fixed `10`, then reports that the runtime is still draining.
|link:../runtime-lifecycle/01-startup-recovery-drain.adoc#runtime-lifecycle-operations[Runtime Model, The Runtime's Lifecycle]; implemented on the runtime side: link:../../../pm-runtime/src/main/java/de/planmarshall/runtime/start/DrainTimeout.java[DrainTimeout], link:../../../../plan-marshall-documentation/doc/user/operator.adoc#drain-timeout-seconds[User Guide § drain_timeout_seconds]

|[[stalled-threshold]]Stalled threshold
|`600` since the last transition or task progress of a non-terminal scope that is neither paused nor in an operator wait, has no pending condition, and awaits no event (the definition: link:../runtime-lifecycle/02-plan-pause-and-stalled-plans.adoc#stalled-plans[Runtime Model, Stalled Plans]).
|fixed (compiled constant; the `plan_stalled` record feeds metrics, which must stay comparable across machines)
|—
|plans and epics
|The scope is shown as the hold `stalled` in both clients of the operator, and one `plan_stalled` audit record is appended per episode; nothing changes in a model-facing representation.
|link:../runtime-lifecycle/02-plan-pause-and-stalled-plans.adoc#stalled-plans[Runtime Model, Stalled Plans]

|[[pending-entry-max-age]]Pending entry
|No maximum age: a pending entry of a start or a project onboarding never expires and is never discarded by time; it stays among the project's open entries until it is started or abandoned, or deleted with the release of its project.
|—
|—
|`<PM_MCP_BASE>/projects/<project_id>/pending/<entry_id>/`
|Nothing expires; the periodic sweep removes only the directory of an entry already started or abandoned whose removal a stop cut off (link:../runtime-lifecycle/01-startup-recovery-drain.adoc#periodic-sweep[Runtime Model, Periodic Sweep]).
|link:../state-catalogue/09-bootstrap-and-lessons.adoc#start-from-clients[State Catalogue, Starting from the Clients]

|[[periodic-sweep-interval]]Periodic runtime sweep interval
|`3600` between two runs of the runtime's periodic sweep over all enrolled projects.
|fixed (compiled constant)
|—
|the removal of technical residue, the measurement of the machine store's disk use, and the cleanup's check (its first pass after the start and the first of each new UTC day)
|Each run removes the residue whose retention passed, one audit record each, under the evidence rules of the removal sweeps, records the disk use, and runs the cleanup's check where it is due (link:../runtime-lifecycle/01-startup-recovery-drain.adoc#periodic-sweep[Runtime Model, Periodic Sweep]).
|link:../runtime-lifecycle/01-startup-recovery-drain.adoc#periodic-sweep[Runtime Model, Periodic Sweep]; implemented: link:../../../pm-runtime/src/main/java/de/planmarshall/runtime/start/PeriodicSweep.java[PeriodicSweep] (`INTERVAL`), link:../../../../plan-marshall-documentation/doc/concepts/runtime-lifecycle.adoc#periodic-sweep[Concepts § Periodic Sweep]

|[[event-buffer]]Event buffer
|The last `1000` events of each event stream are held for a reconnecting client.
|fixed (compiled constant)
|—
|the event streams of the local API (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#event-streams[Runtime Model, Events per Scope])
|A client whose `Last-Event-ID` is older than the buffer receives `reset` and reads the scope's resources again; every runtime start begins with an empty buffer.
|link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#event-streams[Runtime Model, Events per Scope]

|[[metrics-event-interval]]Metrics event interval
|At most one `system.metrics` event per second, and one `tokens.changed` event per scope per second, each carrying what changed since the last.
|fixed (compiled constant)
|—
|the runtime-wide stream and the plan and epic streams
|—
|link:../runtime-lifecycle/03-runtime-metrics.adoc#runtime-metrics[Runtime Model, The Runtime's Metrics]

|[[update-check-interval]]Update check interval
|At most one check for a newer release per `86400`, only while the consent `check_updates` is remembered for the machine; the operator's _check_ runs at once.
|fixed (compiled constant)
|—
|the runtime's check of the organisation's registry (link:../runtime-lifecycle/01-startup-recovery-drain.adoc#runtime-lifecycle-operations[Runtime Model, The Runtime's Lifecycle])
|The next check runs; a failed check is recorded with its reason in the version state and never retried before the next interval.
|link:../runtime-lifecycle/01-startup-recovery-drain.adoc#runtime-lifecycle-operations[Runtime Model, The Runtime's Lifecycle]

|[[lsp-idle-timeout]]Language server idle timeout
|`900` without a request to the instance.
|`lsp_idle_timeout_seconds` in `machine-config.json`
|minimum `60`
|warm LSP pool instances
|Clean eviction (`shutdown` → `exit` → `SIGTERM` after xref:01-job-budgets-and-waits.adoc#grace-period[Grace period]); the next request starts a new instance lazily.
|link:../job-runtime/01-pipeline-and-subprocesses.adoc#_warm_language_server_pool_orthogonal_service_access_pm_svc_2_pm_svc_4_pm_tool_2[Job Runtime, Warm Language Server Pool]; link:../../../../plan-marshall-documentation/doc/specification/mcp-tools.adoc[MCP Tools] (Warm LSP Pool Lifecycle)

|[[lsp-start-timeout]]Language server start timeout
|`120` from spawn to the `initialize` response.
|`lsp_start_timeout_seconds` in `machine-config.json`
|minimum `10`
|warm LSP pool instances
|The instance is terminated; `pm_lsp` reports the failure and an Axis C resolver reports `NOT_RUN` with `FAILED_TO_START`.
|link:../domain-extensions.adoc[Domain Extensions] (Explicit Non-Run Reporting)

|[[lsp-restart-cap]]Language server restart cap
|`2` automatic restarts per instance after an unexpected exit (an attempt budget, not a duration).
|fixed (compiled constant)
|—
|warm LSP pool instances
|No further restart: `pm_lsp` returns `lsp_unavailable` for the instance until its idle eviction or a runtime restart.
|link:../job-runtime/01-pipeline-and-subprocesses.adoc#_warm_language_server_pool_orthogonal_service_access_pm_svc_2_pm_svc_4_pm_tool_2[Job Runtime, Warm Language Server Pool]

|[[lsp-request-timeout]]Language server request timeout
|`60` per request.
|`lsp_request_timeout_seconds` in `machine-config.json`
|minimum `5`
|`pm_lsp` operations and Axis C symbol-edge queries
|The request is cancelled (`$/cancelRequest`); `pm_lsp` reports a timeout, never an empty result, and an Axis C resolver reports `NOT_RUN` with `TIMEOUT`.
|link:../domain-extensions.adoc[Domain Extensions] (Explicit Non-Run Reporting)

|[[lock-wait-threshold]]Transaction lock acquisition
|No timeout: transaction locks are held for one transaction only (link:../store-schemas/13-leases-integrity-testing.adoc#lock-free-snapshot-reads[Store Schemas, Transaction Locks]); long-lived claims are leases (<<leases>>). A reporting threshold of `30` watches every wait without aborting it.
|fixed (the threshold feeds a `PM-MIG-5` trigger, which must not vary per machine)
|—
|runtime
|The wait continues; the lock manager appends one `lock_wait_exceeded` audit record (lock, holder, waited time), which counts as a `PM-MIG-5` integrity trigger event.
|link:../../../../plan-marshall-documentation/doc/developer/locks-and-leases.adoc#lock-manager[Developer Guide § The Lock Manager]

[#leases]
== Leases & Heartbeats

[cols="2,3,2,2,2,3,2"]
|===
|Name |Value / derivation |Configurable? |Floor / cap |Applies to |Behaviour on expiry |Defined for

|[[merge-lease]]Merge holder lease
|`lease_expires_at = heartbeat_at + 900`; every transition of the holding plan inside the rebase-to-merge critical section is a heartbeat and refreshes `heartbeat_at`.
|fixed
|—
|`holder` of `state/merge-queue.json`
|The holder is reclaimed in the next admission transaction (stale-holder reclaim); an orphaned holder whose expiry passed without adoption is released.
|link:../phase-workflows/06-finalize-re-entry-and-merge.adoc#_cross_plan_merge_mutex_fifo_admission_queue[Phase Workflows, Cross-Plan Merge Mutex]; link:../store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Store Schemas, Machine Lease Stores]

|[[merge-mutex-admission-wait]]Merge-mutex admission wait
|No deadline of its own (like the xref:01-job-budgets-and-waits.adoc#model-slot-wait[Model slot wait]): a plan in `finalize.merge-lease` rests in FIFO order until it holds the lease. The wait is bounded by the holder's lease (<<merge-lease>>) and the stale-holder and orphan reclaim rules, which end every held lease.
|fixed
|—
|`merge.acquire-lease` of `finalize.merge-lease`
|—; the lease job's generic fate routes (`failed`, `refused`, `cancelled`, `timed_out`, `killed`, `indeterminate`) enter `finalize.merge-lease-interrupted`.
|link:../phase-workflows/06-finalize-re-entry-and-merge.adoc#_cross_plan_merge_mutex_fifo_admission_queue[Phase Workflows, Cross-Plan Merge Mutex]; link:../state-catalogue/07-plan-finalize-merge-post-run.adoc#state-finalize.merge-lease[State Catalogue, `finalize.merge-lease`]

|[[build-slot-lease]]Build slot lease
|`lease_expires_at = acquired_at + t + 5` (the job's allocated budget plus the termination grace period).
|derived
|—
|`state/build-slots.json`
|The slot is released once its job has settled; a slot whose job was recorded `killed` at a runtime restart is released at once.
|link:../store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Store Schemas, Machine Lease Stores]

|[[model-slot-lease]]Model slot lease
|No time expiry (`lease_expires_at: null`): a running worker holds its slot from the transaction that turns it `running` until its fate, a warm worker for its whole generation, idle or not; the supervisor's bounds (xref:01-job-budgets-and-waits.adoc#model-job-budget[Worker budget], xref:01-job-budgets-and-waits.adoc#worker-supervision[Worker Supervision & Recycling]) end every worker. The machine cap is `model_slots` (compiled default `2`), at most one writer worker per plan.
|cap: `model_slots` in `machine-config.json`
|cap `1`..`16`
|`state/model-slots.json`
|The slot is released once its worker has settled; a slot whose worker was recorded `killed` at a runtime restart is released at once; the next `queued` worker is admitted (xref:01-job-budgets-and-waits.adoc#model-slot-wait[Model slot wait]).
|link:../store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Store Schemas, Machine Lease Stores]

|[[task-lease]]Task lease
|No time expiry of its own: from the offer to the attempt's outcome or the fence of the holding generation. The acknowledgement deadline, the silence limit, and the worker budget end a worker that keeps a lease without progress (xref:01-job-budgets-and-waits.adoc#worker-supervision[Worker Supervision & Recycling]).
|—
|—
|`lease` of a queue task record
|Released at once in the fence transaction; the task is offered to the successor exactly once within the xref:01-job-budgets-and-waits.adoc#task-reoffer-budget[Task re-offer budget].
|link:../store-schemas/16-task-queue.adoc#queue-task-record[Store Schemas, Queue Task Record]

|[[job-token-lifetime]]Job token and worker generation lifetime
|From the worker's spawn to the transaction that records its fate; no time expiry of its own. A generation is a worker's `job_id`; there is no other kind.
|fixed
|—
|the job token of a worker (`PM-MCP-Job-Token`) and every `generation_id`
|The token is revoked and the worker's generation fenced with the fate; every later request with the token is refused `job_ended`, and every call of a fenced generation `generation_fenced`.
|link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas, Job Record]; link:../identifiers/02-registry-stores-to-web.adoc#id-job-token[Identifier Registry, Job Token]

|[[review-bot-window-claim]]Review-bot window claim
|`reset_at` of the window (xref:01-job-budgets-and-waits.adoc#review-bot-windows[Review bot windows]).
|—
|—
|`state/review-bot-windows.json`
|—
|link:../store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Store Schemas, Machine Lease Stores]

|[[orphaned-lease-release]]Orphaned lease release
|Positive evidence only: owning scope terminal, archived, or gone; or `lease_expires_at` passed without adoption; or (build or model slot) its job recorded `killed`. Task leases are never orphaned: the restart releases them (<<task-lease>>).
|—
|—
|every lease marked `orphaned_at`
|Released and audited.
|link:../runtime-lifecycle/01-startup-recovery-drain.adoc#per-project-recovery[Runtime Model, Per-Project Recovery]

[#operator-waivers-questions]
== Operator, Waivers & Questions

[cols="2,3,2,2,2,3,2"]
|===
|Name |Value / derivation |Configurable? |Floor / cap |Applies to |Behaviour on expiry |Defined for

|[[operator-wait]]Operator wait
|No time limit: a state that waits for the operator (a decision, a waiver request, a consent, an option asked when needed, a choice of a start, of a setup, or of the onboarding) ends only by an act of the operator through one of its operator links, or by an act that ends its scope.
|—
|—
|every operator wait of every unit and scope
|Nothing expires and nothing is decided by time; the wait halts its own scope only.
|link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL, Waiting for the Operator]

|[[waiver-expiry]]Waiver
|No time expiry and not bound to `HEAD`: a `met` waiver can be set until the gate's fallback is taken and applies to every later evaluation of its gate until the plan ends or `unwaive` revokes it (refused once consumed); a revoked `raise` lowers the ceiling from the next budget check.
|—
|—
|`waivers.jsonl`
|—
|link:../store-schemas/14-plan-instance-waivers-questions.adoc#waiver-record[Store Schemas, Waiver Record]

|[[waiver-request-expiry]]Waiver request
|No expiry: an open waiver request is an operator wait (xref:01-job-budgets-and-waits.adoc#waiver-wait[Waiver request]) until `waive` or `decline`.
|—
|—
|`waiver_requests[]`
|—; an act that ends the plan closes it `cancelled`.
|link:../store-schemas/14-plan-instance-waivers-questions.adoc#waiver-request-record[Store Schemas, Waiver Request Record]

|[[integrity-pause]]Integrity pause
|No expiry: an `integrity_breach` hold ends only by `accept-edit` (re-baseline and re-verification) or, for a plan or epic scope, by its cancel, the abort that ends a plan with the outcome `aborted` and an epic as `cancelled`; a workspace breach and a lesson breach end only by `accept-edit`; a breached pending entry record ends by `accept-edit` or by abandoning the entry.
|—
|—
|plan, epic, and workspace scopes, single lessons, and single bootstrap entities (a tampered enrolment pauses every running plan of the project)
|—; the deadline of a prerequisite wait is held and processed after the pause ends.
|link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-integrity-pause[CLI & Security, Integrity Pause]

|[[access-grant-lifetime]]Access grant
|No time expiry: a grant holds until the plan ends.
|—
|—
|`grants.jsonl` of a plan
|—
|link:../store-schemas/15-screening-and-grants.adoc#grant-record[Store Schemas, Access Grant Record]

|[[credential-expiring-window]]Credential expiry warning window
|`14` days before `expires_at`.
|fixed
|—
|credential entries with a known `expires_at`, for a `github_app` entry the expiry of its user refresh token (`pm-operator credentials status`, the project setup credential verification)
|Not an expiry: the entry is reported `expiring` to the operator; it is never refused and never reported in a model-facing representation, since an expiring credential still works.
|link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-credential-cli[CLI & Security, Operator Credential CLI]; link:../store-schemas/12-machine-stores.adoc#credential-store[Store Schemas, Credential Store]; link:../domain-extensions/04-setup-state-machine.adoc#setup-verify-credentials[Domain Extensions, Setup Credential Verification]
