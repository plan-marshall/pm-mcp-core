== Native Build Output Parsers
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-11[PM-WATCH-JOB-11]_

When a build completes with a non-zero exit code or compiler warnings, the runtime extracts structured diagnostics without calling external Python scripts (`PM-IMPL-6`). Each compiled parser ports one `plan-marshall` parser module (`marketplace/bundles/plan-marshall/skills/build-*/scripts/`, plus the domain-owned OpenRewrite parser) and is verified by Java tests whose test data and expected values are derived from that module and its pytest suite (`PM-TEST-2`):

Implemented by `pm-core` package `core.build` (link:../../../pm-core/doc/developer/core-build.adoc[`core.build` Developer Guide]) for the JVM tools: the parsers `MavenOutputParser`, `GradleOutputParser` and `OpenRewriteLogParser` over the result model `ParsedBuild` with its `Diagnostic` and `TestCounts`, each verified by ported Java tests whose data and expected values are derived from the original module and its pytest suite (`PM-TEST-2`; link:../store-schemas/13-leases-integrity-testing.adoc#ported-tests[Store Schemas Specification, Ported-Primitive Tests]). The rules they carry bind every parser of this section: test counts are aggregated over every summary block of a multi-module run; a successful build whose summaries cannot be aggregated reports `tests_population: unmeasured` and no test count, never `tests_run: 0`; a `no_tests_ran` verdict requires the tool's positive marker, never a zero count; failure-trailer advice lines (`Re-run Maven using the -X switch…`, `[Help 1] http…`, `After correcting the problems, you can resume the build…`, `mvn <args> -rf :<module>`) are dropped, each matched whole against a compiled pattern table, so a reworded line is filed again rather than a genuine diagnostic being dropped silently; and an unrecognised `[ERROR]` line is categorised `unrecognized`, never assigned a real category. The trailer drop and the passing-count skip are the `plan-marshall` parsers' own behaviour, held by the port rather than changed. Five behaviours are deliberate changes against those parsers, each verified by its own fixture and listed in link:../../../pm-core/doc/adr/core-build/002-deliberate-changes-against-the-ported-parsers.adoc[ADR `core-build/002`]: `unrecognized` for an unmatched `[ERROR]` line, an unmeasured test population that carries no number, a `no_tests_ran` verdict only from the tool's positive marker, the Gradle counts summed over every block, and an OpenRewrite format drift reported as `parse_error` rather than as zero findings. Remaining: nothing in this section; `BuildOutputParser` of `runtime.job` dispatches these parsers for a build job (see § Unparseable Output Fallback).

The text a parser reads is bounded (PM-ARCH-8, PM-IMPL-5). The log is read through `BuildLogText.read` of `pm-core`, which takes at most the cap of the module's limits resource, counted from its end and from the first line beginning inside it:

include::../../../pm-core/src/main/resources/de/planmarshall/core/build/build-limits.properties[tag=log-max-bytes]

A log longer than that cap reaches a parser as its tail, because the count lines, the summary and the failure tail are at its end. Before any pattern runs, every one of the nine parsers cuts every line at the per-line bound of the same resource:

include::../../../pm-core/src/main/resources/de/planmarshall/core/build/build-limits.properties[tag=max-line-length]

The cut bounds every expression of a parser at once, a pattern that would backtrack over a line of repeated tokens included. A log inside both bounds reads as it was written, so no result changes for it. The dispatcher `BuildOutputParser` of `runtime.job` cuts the stripped log the same way before its dispatch patterns, and none of its multi-line patterns lets a repetition cross a line end. The pipeline's job log is cut the same way and keeps its first line, the launch report, whose launcher-failure decision it carries (`JobLog.readWhole`; link:../../../pm-runtime/doc/developer/runtime-job.adoc#_job_log[`runtime.job` Developer Guide § Job Log]). The decisions are link:../../../pm-core/doc/adr/core-build/007-the-read-and-the-patterns-are-bounded.adoc[ADR `core-build/007`] and link:../../../pm-core/doc/adr/core-build/009-the-redactor-shapes-the-diagnostic-redaction-and-the-input-bounds.adoc[ADR `core-build/009`].

The six JavaScript and Python parsers — npm errors, TypeScript, ESLint, Jest, TAP and the pyproject log of pytest, ruff and mypy — are implemented by `NpmErrorParser`, `TypeScriptOutputParser`, `EslintOutputParser`, `JestOutputParser`, `TapOutputParser` and `PyprojectOutputParser` in the same package and over the same result model, each ported from its module and verified by ported Java tests of the same convention. They hold the rules above and add the changes link:../../../pm-core/doc/adr/core-build/003-the-six-remaining-parsers-and-their-deliberate-changes.adoc[ADR `core-build/003`] records, each with its own fixture: one npm diagnostic per error block, under either the `npm ERR!` prefix of npm up to 11 or the `npm error` prefix of npm 12 on; both `tsc` forms scanned over every line; the ESLint problem summary reported beside the rows it cannot place; every Jest, TAP and pytest summary block summed; a contradictory summary reported `unmeasured`; and, for pytest, the location taken from the deepest traceback frame and the xdist `@<group>` suffix stripped before the block lookup. The passing summary the tool prints is its positive success marker: Jest's `Tests:` summary and TAP's summary block when they report at least one passed test and no failed test, and the npm install family's completion line for a job whose verb is `install` or `clean-install` of the xref:02-confinement-and-environment.adoc#canonical-build-verbs[Canonical Build Verb Set]; under any other verb the line is printed by an `npm ci` before the job's own tool and is no marker, so a runner no scanner reads stays `indeterminate` (ADR link:../../../pm-runtime/doc/adr/runtime-job/018-the-install-marker-needs-an-install-verb.adoc[`runtime-job/018`]). A TAP summary is no marker either when a run did not finish the plan it announced: the plan is checked per run, a run starting at every line that starts with `TAP version` (the lines before the first such line, or the whole log without one, are one run), and a run whose summed top-level plan lines `1..N` differ from its own number of top-level test points makes the log no marker, so a later run of concatenated runs cannot supply a point an earlier run is missing; a plan count too large for a `long`, or plan counts whose sum overflows a `long`, leave the run unfinished (no passing summary), because an announced plan that cannot be verified never reads as finished; the summary counts are still summed over all runs, and an indented subtest plan and a run without a plan line change nothing. The summary counts follow the same rule: a TAP or Jest summary count too large for a `long`, or summary counts whose sum overflows a `long`, leave the population `unmeasured` and the passing summary is no marker, because a wrapped sum never reads as a measured population; a failing count too large for a `long` is still a printed failing count, so the status is red; and an ESLint problem summary whose count or sum cannot be represented is reported as no summary. A clean `tsc` or ESLint run prints none, so its zero exit stays `indeterminate` (ADR link:../../../pm-runtime/doc/adr/runtime-job/016-the-npm-passing-summary-is-the-success-marker.adoc[`runtime-job/016`]). Every message of the npm error parser, its `ERESOLVE` and `E404` messages included, is redacted through `SecretRedactor` before it is cut to its stored length (ADR link:../../../pm-core/doc/adr/core-build/009-the-redactor-shapes-the-diagnostic-redaction-and-the-input-bounds.adoc[`core-build/009`]). The developer guide carries the parser-by-parser detail (link:../../../pm-core/doc/developer/core-build.adoc[`core.build` Developer Guide]).

Coverage reports are parsed separately (<<Native Coverage Report Parsers>>).

=== Unparseable Output Fallback (`failed_unparsed`)
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-7[PM-WATCH-JOB-7], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-14[PM-WATCH-JOB-14]_

Implemented by `BuildOutputParser` in `pm-runtime` package `runtime.job`, which selects the native parser by the build system of the job's budget key and hands the parsed build to the outcome derivation, and by `UnparsedEvidence` in `pm-core` package `core.build` — the raw log with its ANSI escapes stripped and each carriage-return spinner frame run reduced to its last frame, then the last 50 lines, each cut to its last characters at the per-line bound before it is redacted through `SecretRedactor`, at most 4 KB, with the resource URI `pm://plan/{plan_id}/builds/{job_id}/log` and no invented diagnostic. The full raw log stays at `<PM_MCP_BASE>/projects/<project_id>/jobs/<job_id>.log`, next to the job record. The developer guides are link:../../../pm-runtime/doc/developer/runtime-job.adoc[`runtime.job`] and link:../../../pm-core/doc/developer/core-build.adoc[`core.build`]; the decisions are link:../../../pm-runtime/doc/adr/runtime-job/015-the-parser-seam-carries-the-job-and-settlement-replacements.adoc[ADR `runtime-job/015`] and link:../../../pm-core/doc/adr/core-build/004-the-unparsed-excerpt-is-bounded-redacted-and-diagnostic-free.adoc[ADR `core-build/004`], with the line cut before the redaction in link:../../../pm-core/doc/adr/core-build/009-the-redactor-shapes-the-diagnostic-redaction-and-the-input-bounds.adoc[ADR `core-build/009`].

== Adaptive Build Timeouts, Coverage Parsers & Gate Honesty (`PM-EXEC-6`)

=== Adaptive Timeout Learning
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-15[PM-WATCH-JOB-15], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-16[PM-WATCH-JOB-16], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-33[PM-WATCH-JOB-33]_

The runtime (`pm-mcpd`) persists observed execution durations per project in `<PM_MCP_BASE>/projects/<project_id>/build-timings.json` (link:../store-schemas/09-derived-facts-and-build-timings.adoc#build-timings-store[Store Schemas Specification, Build Timings Store]), keyed by budget key (for build jobs the canonical command: build system, canonical verb of the xref:02-confinement-and-environment.adoc#canonical-build-verbs[Canonical Build Verb Set], and module; a build profile is named literally in the verb's template, so it needs no key component; for `git` and `ci` operations the operation key `<kind>:<operation>`, the same for an in-process operation of the native variant and a job of the CLI variant, xref:01-pipeline-and-subprocesses.adoc#in-process-operations[In-Process Operations (Native Variant)]; for workers the key `llm:<role>`, the role name, one key per role whatever the harness); there is no repository-local and no machine-level timeout store, so a moved checkout keeps its budgets. The blend formula, the engine floors, the allocation rule, the escalation budget and its cap, operator budgets, and the no-verdict rule for `timed_out` are defined only in link:../timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets]; this section defines which runs feed the learned baseline $L$:

* *Finished Runs Feed $L$*: Every finished run (any exit code) feeds $L$ with its duration; `killed` and `cancelled` runs never do. A worker (key `llm:<role>`) feeds $L$ only with successful work: a fresh worker with its spawn-to-exit duration when it ended `succeeded`, a warm worker with the duration of each of its attempts that closed its task with a submission (attempt `end: closed`, link:../store-schemas/16-task-queue.adoc#queue-task-record[Store Schemas Specification, Queue Task Record]), from the task's offer to the attempt's end (its idle time between tasks never counts); a run or attempt that ended any other way says nothing about the time the role's work takes. An in-process operation has finished when it returned a result of its contract; the time it spent deferred by a provider rate limit is excluded from the duration.
* *Timed-Out Runs Never Feed $L$*: A `timed_out` run is a non-finish, so its duration is unknown. It never feeds $L$; it sets the one-shot escalation budget of link:../timeouts/01-job-budgets-and-waits.adoc#escalation-budget[Timeouts & Budgets Specification] for the next run of the same key, which the next finished run clears. *Deliberate change vs. `plan-marshall`*: `plan-marshall` blends its doubled timeout into $L$, so one residue-slowed timeout inflates every later budget.
* *Residue-Poisoned Runs*: A finished run whose worktree held build residue above the hygiene threshold at its start (the count of git-ignored build output files measured at job start, beside the <<worktree-sha>> scan; the threshold is a named engine constant recorded with the observation) is stored as `poisoned` and not blended while clean observations exist. The learned value's hygiene (`observations`, `poisoned`, `cold`, `escalation_seconds`) is recorded in the build timings store (link:../store-schemas/09-derived-facts-and-build-timings.adoc#build-timings-store[Store Schemas Specification, Build Timings Store]), the job record carries only its `budget_derivation` (kind and, for `learned`, the observation count), and both clients of the operator show both; it is never rendered in the job facts (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).
* *Budget Derivation*: Every allocated budget records `budget_derivation` (`learned` with its observation count, `escalated`, `operator`, or `floor_default`; link:../timeouts/01-job-budgets-and-waits.adoc#budget-allocation[Timeouts & Budgets Specification, Allocated Budget]) in the job record, never in the representation: the model acts on the offered links, not on the derivation. Every `timed_out` outcome is `no_verdict`, whatever the derivation; the derivation selects only the retry offer, server-side (link:../timeouts/01-job-budgets-and-waits.adoc#no-verdict-rule[Timeouts & Budgets Specification]).
* *Budget Scope & Measurement*: Every budget states the statistic it came from and the scope it applies to (link:../timeouts/01-job-budgets-and-waits.adoc#no-verdict-rule[Timeouts & Budgets Specification], Budget statistic). Its scope is the budget key, so a figure measured under one key is never applied to another.
* *Runner-Dependent Verdicts*: When the same test population is red under one canonical command and green under another (for example a real-tree test that times out under a module-scoped test run but passes under `verify`), the job facts report both keys with their verdicts (the budgets stay in the job records); the difference is never left implicit.
* *Cold Rebuilds*: A finished run that starts after a dependency sync or a build-cache invalidation since the key's previous observation (a changed resolved-dependency set or a cleared build cache) is stored as `cold`. Like a `poisoned` run it is not blended into $L$ while warm observations exist, and it is never read as a regression of $L$.
* *Seeded Wait Budgets*: The expected duration of a CI wait (link:../hypermedia-format/03-composite-wait-and-encoder.adoc#_deterministic_evaluation_immediate_short_circuit_matrix[Hypermedia Format Specification, Short-Circuit Matrix]) is seeded from the project's known-slow ceilings (the operator budgets in the enrolment) when no learned figure exists. CI waits are re-polled and never lapse, so a seeded figure sets only the expected duration recorded with the wait (shown in both clients of the operator, never rendered), never a failure deadline (link:../timeouts/01-job-budgets-and-waits.adoc#ci-wait[Timeouts & Budgets Specification, CI Wait]). Review-bot waits are bounded by the bot's rate window, re-review timeout, and attempt ceiling, never by a learned or seeded figure (link:../timeouts/01-job-budgets-and-waits.adoc#review-bot-windows[Timeouts & Budgets Specification, Review-Bot Rate Windows]).
* *No Inherited Baselines*: Every learned value starts from the project's own finished runs under `PM-MCP`; learned timeouts of `plan-marshall` are never read or imported (`PM-MIG-2`).

=== Native Coverage Report Parsers

Implemented by `JacocoReportParser`, `CoberturaReportParser`, `LcovReportParser` and `IstanbulSummaryParser` in `pm-core` package `core.build` (link:../../../pm-core/doc/developer/core-build.adoc#_the_coverage_reports[`core.build` Developer Guide § The Coverage Reports]) over the model `CoverageReport` with its `CoverageMetrics`, `CoverageItem` and `CoverageVerdict`, each parser returning a `CoverageParseResult` — a parsed report or a refusal that names the format, never a report of zeros. The parser tests are ported from `plan-marshall`'s `_coverage_parse.py` and its pytest suite (link:../store-schemas/13-leases-integrity-testing.adoc#ported-tests[Store Schemas Specification, Ported-Primitive Tests]); the model is recorded in link:../../../pm-core/doc/adr/core-build/005-the-coverage-model-and-the-xml-hardening.adoc[ADR `core-build/005`], and the XML hardening, the zero-denominator rule and the read bounds in link:../../../pm-core/doc/adr/core-build/008-the-coverage-parsers-read-with-dtd-off-and-bounded.adoc[ADR `core-build/008`]. The rules stated below stay binding: the threshold verdict (`passed`) and the low-coverage list compare the **line** percentage only, every other metric is parsed and rendered and never feeds a threshold, and an XML report is read by a parser with DTD support off: a `DOCTYPE` is tolerated and never resolved or fetched, an entity reference in element content is refused, never expanded, and an undeclared entity reference in an attribute value is dropped from the value, never expanded or resolved.

A counter with a zero denominator measured nothing, so its metric is absent rather than a measured `0.0`: an item whose line counter is `0/0` is no item, a branch, function or instruction counter of `0/0` leaves that metric absent, and a report whose overall line counter is `0/0` is refused (`no lines measured`). An Istanbul metric object that carries no `total` is refused, never read from its `pct` alone. The percentages compared with a threshold are the ones already rounded to two decimals.

A report is read as a stream, never whole, and the read is bounded (PM-ARCH-8, PM-IMPL-5). A report file larger than the cap of the module's coverage limits resource is refused, naming the cap:

include::../../../pm-core/src/main/resources/de/planmarshall/core/build/coverage-limits.properties[tag=coverage-max-bytes]

An LCOV line longer than the line limit of the same resource is refused, naming the limit:

include::../../../pm-core/src/main/resources/de/planmarshall/core/build/coverage-limits.properties[tag=coverage-max-line-length]

A repeated counter is refused, so a later value never overrides an earlier one: a JaCoCo report that carries a counter type twice at the report root or twice within one class, an LCOV record that carries one of the counter lines `LF`, `LH`, `BRF`, `BRH`, `FNF` or `FNH` twice, and an Istanbul summary that carries a key twice in one object. A report file that cannot be read is refused naming its file name, never its directory. A refusal echoes at most 256 characters of report content after its format prefix, so a hostile long type name, counter value or file name is cut in the reason. A limit above the range of the quantity it sizes is refused by name when the module loads, never narrowed by overflow, and an XML report is read by a factory that also allows no protocol for an external DTD or schema where the implementation accepts it, the JDK's built-in StAX implementation being the supported one (link:../../../pm-core/doc/adr/core-build/009-the-redactor-shapes-the-diagnostic-redaction-and-the-input-bounds.adoc[ADR `core-build/009`]).

Remaining: the runtime wiring that evaluates a coverage report after test execution and renders its figures in the job facts.

=== Changed Lines without Coverage
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXEC-6[PM-EXEC-6: Adaptive Build Timeouts, Coverage Parsing & Gate Honesty]_

_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-49[PM-WATCH-JOB-49]_

A threshold names a percentage of a module; the worker that has to meet it needs the lines it wrote that no test ran. For a coverage evaluation of a plan the server joins the parsed report with the plan's own change and records the result as the gate fact `uncovered_changes`, beside the other `gate_facts` of the job record:

1. *The changed lines*: per file, the lines the plan added or changed against its merge base, read from the diff of the plan's worktree at the `worktree_sha` of the job. A file or a line the plan did not change never appears, so the coverage debt of the base stays `baseline_debt` (Baseline Separation, <<_gate_honesty_verification>>).
2. *The uncovered ones*: of those lines, the executable lines the report marks as not run, read from the line records of the format (JaCoCo `sourcefile` lines with no covered instruction, Cobertura and LCOV lines with zero hits). A changed line the report does not list (a comment, a blank line, a declaration) is neither covered nor uncovered. The report names a file by the format's own name (a package path, a path relative to a source root), which the server maps to the repository path through the module's source roots.
3. *Never an empty list by default*: an empty list is recorded only when the report names every changed file and marks every executable changed line as run. A changed file the report does not name (`file_not_reported`), a format without line data (the Istanbul summary, `no_line_data`; the same run's LCOV report is read when it exists), and a report file older than the job that was to produce it (`stale_report`) are recorded as `not_derived` with that cause.
4. *Rendering and bounds*: the list is rendered to the model only when the line verdict failed for a module of the plan's realized footprint, per file as ranges of consecutive lines, bounded in files and in ranges per file, with the remainder counted. It is a pointer, never evidence that a line can or should be tested (unreachable code, generated source); it never feeds the verdict, which compares the line percentage alone, and it blocks nothing.

=== Gate Honesty Verification
_Implementation watch: link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-2[PM-WATCH-GEN-2], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-8[PM-WATCH-JOB-8], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-17[PM-WATCH-JOB-17], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-25[PM-WATCH-JOB-25], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-39[PM-WATCH-JOB-39]_

Before marking a module or pre-push quality gate as `fresh` in `change-ledger.jsonl` (`PM-SVC-1`), the runtime applies five honesty checks. The freshness gate reads a row's `gate_kind`, the canonical build verb of the gate or `ci_check:<name>` (link:../store-schemas/04-epic-and-change-ledger.adoc#_change_ledger_record_change_ledger_jsonl[Store Schemas Specification, Change Ledger Record]), and matches it against the gate it checks:

1. *Examined Population*: The set of modules and source files actually compiled and tested in the build log must be non-empty and must cover every module mapped from the plan's realized file footprint.
2. *Gate Coverage*: The gate scope of a build is computed from its `module` argument, never from its verb: an absent `module` is the whole tree, a present `module` is that module only. A module-scoped run of any verb never satisfies a whole-tree gate, and a whole-tree gate (`quality-gate`, `verify`, `coverage`, `arch-gate` of the xref:02-confinement-and-environment.adoc#canonical-build-verbs[Canonical Build Verb Set]) is satisfied only by a whole-tree run of that verb. Every gate result carries server-derived coverage facts in `plan-marshall`'s terms (`script-shared/scripts/build/_gate_coverage.py`, verified at plan-marshall commit `88fcfc9ef`), which the server derives from the parsed build and the gate definition and the model never supplies:
** `gate_coverage`: `COMPLETE` (at least one dimension checked over its full scope and none degraded), `PARTIAL` (the degraded dimensions are named with their reason; a clean exit is then not a full pass), or `UNKNOWN` (nothing checked and nothing degraded recorded; the run certifies nothing). A dimension attempted over an empty scope is recorded as `empty_scope`, neither a pass nor a gap.
** `structural_limits`: per checked analysis kind, what the analysis cannot evaluate however wide its scope (for example type checking cannot decide whether a well-typed value is correct, tests are silent on inputs no test supplies); an analysis kind without a registered limit is recorded `UNKNOWN`, never omitted.
** `uncovered`: the dimensions the run did not cover, split into `not_at_this_scope` (the gate performs them, but not at this scope) and `not_by_this_gate` (no invocation of this gate performs them); without a declared scope the split is `undeclared`, never an empty list.
** `parity_population`: the recorded dimensions along which the local gate is compared with CI, each `equal`, `subset`, or `closed`; the population is asserted non-empty, because a parity table over nothing reads as perfect parity.
+
All four are persisted in the gate's job record (`gate_facts`, link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]) and step record. The representation of a gate result renders only what the model acts on: `gate_coverage` with, for `PARTIAL`, the degraded dimensions and their reasons, and `uncovered`, so a clean exit is never reported as a full pass. `structural_limits` (a static, registered property of each analysis kind) and `parity_population` (local-versus-CI parity evidence for metrics and the quality report) are never rendered (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).
3. *Test-Scope Divergence Detection*: Detects and rejects runs where test filtering flags or skipped-test properties excluded tests belonging to modified modules. A test that skips itself at run time (an assumption, a skip marker, a missing fixture) is not excluded by the run and is not a divergence: the server records it in the gate's `skipped_tests` (per module of the realized footprint, each skipped test with the reason the parser reads, `null` where the log gives none), persisted with the other gate facts in the job record. The record blocks nothing, changes no `gate_coverage`, and is not rendered to the model.
4. *Baseline Separation*: A red gate is checked for failures already present on the base before any routing, as a server rule (no model judgment, no operator decision, no `<phase>.baseline-red` state). The failures are compared by their fingerprints (<<evidence-gathering>>):
** *Primary proof, the provider's CI result on the base*: For a CI check, and for a local gate that CI also runs, the proof is the provider's result of the same check on the base: on the merge base (`merge-base(HEAD, origin/<base_branch>)`), or on the latest base-branch commit that contains it and has a result. `remediation.ci-failure`'s gathering job fetches this base result in the same job, so a baseline-only red never reaches the unit's `decide`.
** *Fallback, a local build of the merge base*: For a local gate CI does not run (for example the pre-push quality gate) or when the provider has no result for the base, the gate is re-run on the merge base in the plan's baseline scratch worktree. The baseline worktree is a detached worktree at the merge base, created natively with `git.worktree-add` at `.marshall/local/worktrees/baseline-<plan_id>-<sha12>` (`<sha12>` the first 12 hex digits of the merge-base SHA), never the primary checkout and never the plan's worktree; it is reused by every base run of the plan while the merge base is unchanged, replaced (the old one removed, a new one created) when the merge base moves, and removed when the plan leaves `finalize`, is archived, or is aborted; the recovery sweep removes one whose plan is gone or terminal (link:../filesystem-layout/01-repository-workspace.adoc#worktree-lifecycle[Filesystem Layout Specification, Worktree Lifecycle]). Before each reuse it must be clean (`git.status` empty); a dirty baseline worktree is replaced, never used. A quality-gate or format job run there (or in any fresh worktree of the base) must leave `git.status` empty; a job that rewrites committed files there is reported as dirtying the base, never silently accepted, and the worktree is replaced before the next base run.
** *Verdict*: Located diagnostics present on both sides are `baseline` and never become plan findings; for coverage, a threshold failure in a module whose main sources the plan did not change is `baseline_debt` (one non-blocking finding of severity `info` per module, never fanned out into build-error or Q-Gate findings). When every failure of the gate is baseline-only, the server writes a `baseline_red` row into `change-ledger.jsonl`, bound to the gate's `worktree_sha`, the merge base, the base commit and proof source, and the digest of the accepted diagnostics (link:../store-schemas/04-epic-and-change-ledger.adoc#_change_ledger_record_change_ledger_jsonl[Store Schemas Specification, Change Ledger Record]); the freshness gate accepts that row as passing for the same `worktree_sha` only, the gate step completes `done` with `assurance_verdict: degraded`, and the PR body and the landing record list the baseline failures. Both build jobs keep their own outcomes. A red that is not provably baseline-only is plan-caused: its failures (the remaining diagnostics) go to the build or CI remediation policy. A base run or base result that cannot be obtained or parsed leaves every diagnostic attributed to the plan (fail-closed) and says so in `facts`.

5. [[side-state]]*Untracked Side State*: A gate that passes in the plan's worktree may rest on a file the branch does not carry: the realized footprint is read from `git status` and leaves out what `.gitignore` matches, so a fixture, a link, or a configuration file a worker created under an ignored path is in no commit, yet the build of the worktree reads it. Before a whole-tree gate is marked `fresh`, the server lists, through a `git` job in the plan's worktree (`git status --porcelain --ignored`, ignored directories reported collapsed), the ignored paths that match no entry of the compiled artifact pattern table of `pm-core` (build output, dependency and tool caches) and lie outside `.marshall/**`, and records them in the gate's `side_state` (at most `100` paths, with the total count). Since the worktree was created from the base, every such path appeared during the plan. The record blocks nothing, changes no `gate_coverage`, and is not rendered to the model. A pushed plan is checked again by CI on a clean checkout; a plan that lands without CI (`landing.main`, `landing.files`) or is handed back in the local form has no such check, and for it the plan's completion report lists the `side_state` of its last whole-tree gate, so a local green is never shown without the files it may have rested on.

_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-26[PM-WATCH-JOB-26]_

[#provenance-provider]
=== Snippet Provenance Provider
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-9[PM-WF-9: Composite Wait States & Short-Circuit Failure Handling]_

_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-37[PM-WATCH-JOB-37]_

A worker can reproduce licensed code it has seen without saying so, and no other gate looks at where a change's lines come from. The provenance provider is a code analysis provider behind the code-analysis contract, with the provider id `provenance`, that asks a snippet-matching service whether the lines a plan adds match a known open-source component.

* *Off unless the operator enables it, per project*: the provider runs only for a project whose operator file `local-config.json` holds `integrations.provenance` (link:../store-schemas/08-project-configuration-local.adoc[Store Schemas Specification, Project Configuration (Local)]): the service's HTTPS `url` and its `credential_key`, `null` for a service on the operator's own network that takes no credential. The operator act that writes it shows what leaves the machine (the added lines of every plan of the project, with their file paths) and to which origin, and records `consented_at`. No team file and no machine default can enable it, because the decision to send a repository's code to a service is the operator's for each project.
* *What is sent*: the lines the plan's branch adds against its merge base, per file, never an unchanged file, a deleted line, or a file outside the plan's footprint. The request goes only to the configured origin, through the outbound HTTPS stack, with the credential of its key (link:../credentials-and-enrolment/03-audit-and-outbound-https.adoc[Credentials & Enrolment Specification, Audit & Outbound HTTPS]).
* *When*: once per pushed `HEAD` of the plan branch, as one constituent of `finalize.concurrent-wait` with target kind `commit`; it needs no CI and no pull request, so it also runs for a local-only plan. A result is current only for its `HEAD`.
* *Result*: the provider has no quality gate. Every match becomes one finding of source `analysis` and provider `provenance`, kind `issue`, with the file, the added line range, the matched share in percent, the component and its version, the licences the service names, and the service's URL for the match; the analysis result record's `status` is `findings` when one match exists, `passed` when none, and `undecidable` when the service refused, failed, or answered outside its schema (rate limit, quota, timeout). The service's text is external text: it passes the ingestion validator and the screening batch like every analysis message (<<evidence-gathering>>).
* *Remediation*: `findings` and `undecidable` call `remediation.analysis` like every provider: `retry` asks again, `fix` rewrites the matched lines in the branch, and `request_waiver` asks the operator, who may waive `findings:provenance` for the plan with a reason.

[#ingestion-validator]
=== Ingestion Validator (Level 1, `PM-SEC-1`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-27[PM-WATCH-JOB-27], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-29[PM-WATCH-JOB-29]_

Every surface that admits external text into a server store or a representation runs it through one deterministic validator first: issue and pull-request titles and bodies (the structured fields of an issue, its labels, milestone, assignees, state, and URL, are validated against their closed schema and never delivered as text for a model to follow), review comments and bot findings, analysis-provider messages, upstream MCP results, and CI log and build excerpts; the files of extension skills pass stages 1 to 3 in refusing mode, where any change a stage would make refuses the skill (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/02-service-and-skill-tools.adoc#skill-extensions[MCP Tools Specification, Skill Extensions]). The validator is the containment boundary of the two-level guard (link:../model-work/07-untrusted-text-screening.adoc#two-level-guard[Model Work Specification, Two-Level Guard]); it runs in-process on the JDK and `org.commonmark:commonmark` (0.30.0), the one library added for it, and uses the URL validation pipelines of `cui-http` (`de.cuioss.http.security`). Its stages run in this order:

1. *Unicode, to a fixpoint*: removes the Unicode tag block (`U+E0000`–`U+E007F`), variation selectors, every code point of the general categories `Cf`, `Co`, and `Cn`, the `Cc` controls except line feed and tab, lone surrogates, and ANSI escape sequences; normalizes the content to NFC and keeps an NFKC copy for detection only (never delivered). The stage repeats until a pass changes nothing, bounded by a compiled pass limit; a text that does not settle within it is refused.
2. *Markdown AST*: parses the text with `commonmark` and renders it back from the tree: images are removed; a link whose target lies outside the allowlist (the origins of the project's push remote provider and of its configured analysis providers, and, for a source fetched from another forge, the origin of that forge, all server-derived; link:../state-catalogue/09-bootstrap-and-lessons.adoc#issues[State Catalogue Specification, Issues by Number or URL]) is neutralized to inert text; raw HTML blocks, inline HTML, and HTML comments are removed; a collapsed section (a `<details>` block) is removed together with its content, and so are the known disclosure footers of review bots (a compiled pattern table per registered review bot); without this, the screener flagged 23 to 27 % of real review comments falsely (link:../../../../plan-marshall-documentation/doc/specification/evaluation.adoc#parameters[Evaluation Reference, Substantiated Values]); URLs shaped for exfiltration (long encoded query or path segments, a path or query that holds a placeholder for the data to be sent (`[DATA]`, `{{secret}}`), a host given as an IP address, a host of a tunnel or out-of-band interaction service from a compiled host table, `data:` and non-`https` schemes, credentials in the authority) are flagged; every URL extracted from the tree passes the `cui-http` URL validation pipelines (encoding and traversal attacks), and a failing URL is neutralized.
3. *Bounds*: the per-field length, line, and item bounds of the record's closed schema; an over-long value is clamped, never truncated silently.
4. *Rule table*: a compiled table of injection-shaped patterns evaluated on the NFKC detection copy (instructions addressed to a model, role and tool-call markers, prompt and chat-template delimiters, concealment from the user or the operator, persistence into later sessions or stored rules, references to credential paths). It runs as well over what stages 1 and 2 removed from a text that a registered review bot did not author: a run of tag-block code points decoded to the ASCII it encodes, and the text of a removed HTML block, HTML comment, or collapsed section. A hit there is recorded as an instruction in removed content, because removing a hidden instruction must not hide that the author tried to address a model; the removed text still reaches no model. A review bot's collapsed sections and footers address agents by design; scanning them would bring back the false flags that stage 2 removes them to prevent. It runs as well over encoded text in the detection copy: the first ten runs of at least 32 characters of the Base64 alphabet (standard or URL-safe, padding optional) that decode to valid UTF-8, each decoded once and never recursively. A hit there is recorded as an instruction in encoded content, because an encoded instruction is invisible to every other pattern of the table; the text is delivered as it is, encoded. A hit is a risk signal recorded as a finding of the item and handed to the screener as context; it never blocks the text on its own.
5. *Spotlighting at delivery*: wherever the cleaned text reaches a model (a representation, a task's facts, a screener prompt), it is enclosed in delimiters with a per-delivery random nonce that the text is checked not to contain, and marked untrusted.

*Every change is reported*: each stage appends to the item's change report what it removed, neutralized, clamped, or flagged, with counts and positions; nothing is dropped silently, and an item whose report is not empty says so wherever it is delivered. The structured fields of every ingested record are validated against their closed schema (`additionalProperties: false`, `maxLength`, `maxItems`, `pattern`); a structural violation refuses the record. A `pattern` is matched only against a string whose length the same schema's `maxLength` has already bounded: the `maxLength` check runs first, and a `pattern` on a schema without `maxLength` is refused before any regular expression is compiled or evaluated, because an enrolled expression is matched by a backtracking engine with no time budget. An enrolled `maxLength` is itself bounded: a schema that matches a string by a `pattern` admits a `maxLength` of at most 256 code points, and an enrolment of a schema above that ceiling is refused as `enrolment_invalid`, so the string handed to the engine is bounded by the schema's admission and not only by the enrolling project's choice. The rule governs both the closed schemas of ingested records and the `argument_schema` enrolled for a project script (link:01-pipeline-and-subprocesses.adoc[Job Runtime § Argument Schema Validation]). The validator detects no semantic injection: that is the screener's task (level 2), and a local classifier is deferred.

[#worktree-sha]
== Working-Tree Hash (`worktree_sha`, `PM-SVC-1`)
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-24[PM-WATCH-JOB-24]_

`worktree_sha` stamps every build and change entry in `change-ledger.jsonl` and keys every freshness gate. It is a PM-MCP-native, variant-neutral digest computed by one operation of the git contract, `git.worktree-sha` (budget class link:../timeouts/01-job-budgets-and-waits.adoc#git-local-budget[Timeouts & Budgets Specification, `git` local operation class]), which both variants serve from the same status information and which returns the digest together with its hash version; a workflow uses it as a single node (link:../workflow-dsl.adoc[Workflow DSL Specification]). The digest follows these rules:

1. *Inputs*: The `HEAD` commit id, and every path the working-tree status of the worktree root reports as changed (in the index or the working tree), deleted, or untracked; ignored paths are not included. The native variant reads the status with JGit `StatusCommand` (untracked files listed individually, no rename detection); the CLI variant runs `git status --porcelain -z --untracked-files=all --no-renames` and `git rev-parse HEAD` with the worktree root as working directory, so that both variants report the same path set.
2. *Framing*: `sha256(HEAD ‖ NUL ‖ Σ entry)`, where `HEAD` is the lower-case hex commit id and the entries are sorted by the bytes of their UTF-8 path. An entry is the path, `NUL`, and then either the tag byte `F`, the content length as 8-byte big-endian integer, and the file's bytes read from disk, or, for a path that no longer exists on disk, the tag byte `D` (the deletion marker). A symbolic link contributes the tag byte `L`, the length, and its target path (never the target's content). A path the status reports that is a directory on disk (a nested repository or a submodule, which the status reports as one path) contributes the tag byte `D` as well: the digest covers the files of the worktree's own repository, never the content of a repository nested in it.
3. *Configuration independence*: The digest reads no textual diff output, so settings that shape it (`diff.noprefix`, `color.diff`, external diff and textconv drivers, `diff.renames`, `core.quotePath`) have no effect, and no configuration-neutralising options are passed. The status itself honours the repository's ignore rules in both variants.
4. *Hash version*: Every record that carries a `worktree_sha` also carries `worktree_sha_version` (currently `1`, the inputs of rule 1 with the framing of rule 2): the `change-ledger.jsonl` rows and the `freshness_reconcile` record, whose version is that of its `prior_build_worktree_sha` (link:../store-schemas.adoc[Store Schemas Specification]). Any change of the inputs or the framing is a new version. Freshness gates compare digests only of equal versions: a row of another version never matches the live digest and never makes a gate `fresh`; the gate reports it like an absent row for that notation.
5. *Fail-closed on failure*: If the status, the `HEAD` resolution, or a file read fails (in the CLI variant a non-zero exit, termination by a signal, or its timeout; in the native variant an exception or the timeout), no digest is produced. The value is `unavailable`, recorded with the failing step and its failure (`exit_code`, `signal`, `timed_out`, or the exception class) as `worktree_sha_failure`; an unresolvable `HEAD` is such a failure. Every freshness gate keyed on it evaluates indeterminate, never `fresh`: the gate status is `undecidable` with `stale_reason: worktree_sha_unavailable` (link:../phase-workflows.adoc[Phase Workflows Specification], Worktree Freshness Gate), and an `unavailable` value never equals another `unavailable`. *Deliberate change vs. `plan-marshall`*: its `worktree_sha.py` ignores the exit codes of `git diff` and `git ls-files` and hashes the empty output of a failed call into an ordinary digest.
6. *Variant parity (`PM-TEST-2`)*: The native and the CLI variant must produce byte-identical digests on every successful fixture of the equality-behaviour tests.

== Security Boundary & Confinement Adversarial Testing (`PM-TEST-5`, `PM-SEC-1`, `PM-SEC-2`, `PM-SEC-5`)

The `pm-core` and `pm-mcp-server` verification suite enforces automated adversarial tests (`PM-TEST-5`) across every job and ingestion boundary:

1. *Workspace & Symlink Escape Rejection (`PM-SEC-2`)*: Adversarial fixtures containing `..` segments, URL-encoded path traversal, and intra-worktree symlinks pointing outside `<workspace-root>` must be rejected (`path_traversal_rejected`: job outcome `refused` for a job, `rejected.reason` for a `pm_do` argument) before any file descriptor or subprocess is opened.
2. *Tampered Binary & Wrapper Rejection (`PM-EXEC-2`, `PM-EXEC-3`, `PM-EXT-5`)*: Modifying 1 byte of an enrolled `mvnw`, `gradlew`, `pw`, one of a wrapper's `pinned_files` (wrapper jar, wrapper properties, `.mvn/maven.config`, `.mvn/jvm.config`, `gradle.properties`), host binary, or `project_script` without operator re-enrolment, or adding a pinned build configuration file after enrolment, must fail the SHA-256 preflight check with `refused` and emit a `security` event in `audit.jsonl`.
3. *Argument Vector Injection & Environment Sanitization (`PM-EXEC-1`, `PM-SEC-5`)*: Passing shell metacharacters (`; rm -rf`, `$(...)`, backticks) or non-allowlisted flags (`-Dexec.executable=...`, `--init-script`) in job parameters must be rejected at schema validation, and spawned child environments must never contain `GITHUB_TOKEN` or `SONAR_TOKEN`.
4. *Ingestion Validator & Worker Containment (`PM-SEC-1`, `PM-SEC-5`)*: The ingestion validator (<<ingestion-validator>>) is run as JUnit fixtures over the attack generators of `cui-http`, over prompt-injection corpora (garak, promptfoo), and over matched pairs written in the shapes of an incident-response detection pack (an MCP-style tool description carrying an instruction block, an HTML text with instructions hidden by CSS once as a block and once inline, a rules-file text with coercive directives, a URL template that carries data and a typosquatted package name), each with the clean control of the same document: hidden text is either removed with its block or left visible, never hidden, a rule hit is recorded on the attack and none on its control, and the control passes unchanged; every tag-block, variation-selector, bidirectional, and ANSI payload is removed within the pass limit, every image, raw HTML fragment, HTML comment, collapsed section, and known review-bot disclosure footer is removed and every non-allowlisted link neutralized, and each change appears in the change report. A screener worker is launched with zero tools and no MCP configuration, and an unparseable or incomplete verdict makes its items `suspicious`. A request with a job token for an entity not leased to its generation is refused `job_scope_mismatch`, a request of a fenced generation `generation_fenced`, and a request with the token of an ended job `job_ended`. On a Landlock-capable kernel a worker cannot read `<PM_MCP_BASE>` (the runtime token included) apart from its own job-private directory `run/jobs/<job_id>/`, which it cannot write and which no other job can read, and writes only its project root, the system temporary directory, and its declared harness paths, never a settings, command, or skill file of the installed harness bundle; its environment holds no runtime token and no credential variable, a harness authentication variable set in the runtime's environment included (matched positive controls as in item 5).
5. *Landlock Read and Write Sets (`PM-SEC-5`)*: On a Landlock-capable kernel, a job that reads a credential file under `<PM_MCP_BASE>/credentials/` (or any other path under `<PM_MCP_BASE>`, `run/runtime.token` included) fails with a permission error, while a matched positive control reads a file of its own project root and a binary of `<PM_MCP_HOME>/bin/`. A job that writes its project's enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json` (and any other path under `<PM_MCP_BASE>` or `~/.plan-marshall/`) fails with a permission error and leaves the file unchanged, and so does a job that writes into the root of a second enrolled project; a matched positive control writes inside the job's own project root.
6. *Enrolment Tampering (`PM-EXEC-2`)*: Editing a project's enrolment file out of band without the operator CLI makes the next job of that project refuse with `enrolment_tampered` and an `audit.jsonl` `security` record, while a job of a second enrolled project on the same runtime still runs (matched control); the same edit re-baselined through the operator CLI is accepted.
