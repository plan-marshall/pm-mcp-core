== Linux Filesystem Confinement (Landlock)
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-20[PM-WATCH-JOB-20], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-21[PM-WATCH-JOB-21], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-28[PM-WATCH-JOB-28]_

On Linux (`PM-SEC-5`, `PM-TECH-4`), the `pm-exec` launcher (xref:01-pipeline-and-subprocesses.adoc#_process_group_creation_via_the_pm_exec_launcher[Process-Group Creation via the `pm-exec` Launcher]) confines every job before `execve`:

. `prctl(PR_SET_NO_NEW_PRIVS, 1)`: the job and all its descendants can never gain privileges (setuid/setgid binaries, file capabilities).
. A Landlock ruleset (Landlock ABI >= 2, Linux >= 5.19, applied via FFM) that grants read and execute access to the whole filesystem except `<PM_MCP_BASE>` (see *Read set* below), for a worker only to its listed read set (<<worker-read-set>>), and write access only to:
** the job's own project root (which contains all of that project's worktrees under `.marshall/local/worktrees/` and its `.marshall/local/temp/`); never the root of another enrolled project and never the per-project machine store under `<PM_MCP_BASE>`,
** the build toolchain caches declared per project in the enrolment field `write_paths` (for example `~/.m2/repository`, `~/.gradle`, `~/.npm`, `~/.cache/pip`); for a worker without an entry that holds a credential location (<<worker-read-set>>),
** the system temporary directory (`/tmp`; the JVM ignores `TMPDIR` for `java.io.tmpdir`) and device nodes under `/dev`; nothing the runtime reads back or trusts lies there,
** for a `ci` job of the CLI variant only, the configuration directory of its CLI (`gh` or `glab`: `GH_CONFIG_DIR` or `GLAB_CONFIG_DIR` as captured at enrolment, else the CLI's default location below `XDG_CONFIG_HOME`), which the CLI writes while it runs (token refresh, state files; <<_job_environment_pm_sec_5,Job Environment>>),
** for a `build` or `project_script` job, and a CLI-variant `git` job that runs repository hooks, the project's daemon store (<<build-daemons>>),
** for a worker (kind `llm`) only, the paths the client profile of its role's harness declares in `headless.writable_paths`: only the sub-paths below the harness home that the headless harness must write to run (its login or credential file, its caches, and its session directory), never the harness home as a whole and never a settings, command, or skill file that the bundle manifest manages; a profile rule forbids such an entry (link:../client-profiles/01-profile-schema.adoc#headless-writable-paths[Client Profiles Specification, Writable Paths]), and, for a harness whose profile declares a per-worker data home (`headless.data_home`), the worker's data directory `<PM_MCP_BASE>/run/jobs/<job_id>/data/` (<<worker-data-home>>). The concrete paths per harness are listed in the client profile; a path stays _(provisional)_ there until a writer worker has run in confinement with exactly the declared set.

The write set never contains `<PM_MCP_BASE>` (enrolments, machine configuration, credentials, logs, the machine stores, and the job-private directories under `run/jobs/` stay out of every job's write reach) apart from two places that hold nothing the runtime reads or trusts: the project's daemon store and a worker's own data directory. It never contains `~/.plan-marshall/`.

*Consequence for the harness configuration*: A worker cannot change the host configuration its harness loads: the settings and skill files of the installed client bundle (the permission rules, the shim skill) lie outside its write set, so a worker cannot weaken the deny rules or rewrite what the next worker of that harness, or a coding agent the operator runs, loads. The restriction applies to the Landlock write set of jobs only; the bundle installer, which runs inside `pm-mcpd`, is unaffected (`PM-SEC-5`).

*Read set*: The whole of `<PM_MCP_BASE>` is outside every job's read set: the runtime token in `run/` (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#runtime-token[Runtime & Interaction Model Specification, Runtime Token]), the credential files, the enrolments and their HMAC sidecars, the machine stores, and the logs. The one exception is the own job-private directory `<PM_MCP_BASE>/run/jobs/<job_id>/` of a worker or a probe (<<probe-jobs>>) (link:../filesystem-layout/02-machine-runtime.adoc#job-private-directories[Filesystem Layout Specification, Job-Private Directories]): the ruleset of that job, and of no other, grants read access to it and never write access, so nothing the daemon composes for a launch lies in a job-writable place; only its `data/` subdirectory, where one exists (<<worker-data-home>>), is also writable, and the project's daemon store (<<build-daemons>>) is readable and writable for the jobs that use it. Besides `<PM_MCP_BASE>`, the read set leaves out the user's session bus socket (<<session-bus>>) and, for a project without the container-engine opt-in, the container engine's socket paths (<<container-engine>>); leaving a socket out of the read set refuses a `connect(2)` to it from Landlock ABI 9 only (<<pathname-sockets>>). The installation directory `<PM_MCP_HOME>` (the four binaries) lies apart from it and stays readable. Because Landlock rules only grant access, the runtime builds the read set as read and execute rules on `/` minus the path to `<PM_MCP_BASE>`: for each directory from `/` down to the parent of `<PM_MCP_BASE>`, a rule for every entry except the next directory on that path. The entries are enumerated at job start; an entry created later on that path (for example a new file directly in the home directory) is not readable by the job, which is accepted. A consequence of the same construction: a job can traverse the directories on that path and `stat` `<PM_MCP_BASE>` itself, but cannot list them (`ls /`, `ls $HOME`, and a listing of `<PM_MCP_BASE>` fail with `EACCES`), while every subtree below them stays readable; no build of the verification needed such a listing. On macOS and on Linux without Landlock a job can read `<PM_MCP_BASE>`, the token included, like any process of the user; this lies within the same-user boundary accepted for the operator channel (link:../../../../plan-marshall-documentation/doc/later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]). The runtime token and every other runtime secret are never passed in a job's argument vector or environment (<<Job Environment (`PM-SEC-5`)>>). A worker's read set is not built by this enumeration but listed (<<worker-read-set>>); `<PM_MCP_BASE>`, the session bus socket, and the container engine's sockets lie outside it because nothing grants them, and the job-private directory and the runtime socket keep their own read rules.

The ruleset is inherited across `fork`/`execve` and cannot be removed by the job. The runtime passes the read and write sets to the launcher as an argument vector computed from the project's enrolment file at job start, so enrolment changes take effect for the next job without restarting anything.

Properties and limits:

* *Warm build daemons*: A Gradle daemon or `mvnd` keeps the ruleset of the job that started it, and a job reaches only the daemons of its own project's daemon store (<<build-daemons>>). Enrolling a project needs no daemon restart.
* *Container engine*: Docker, Docker Compose, and Testcontainers hand their work to the container daemon, which runs outside every job's confinement; a project's jobs reach it only under the enrolment opt-in (<<container-engine>>).
* *Not covered*: Landlock does not restrict network address families and does not provide a private `/tmp`. `RestrictAddressFamilies` and `PrivateTmp` are therefore not enforced, and no loopback connection is restricted (a build tool reaches its daemon over loopback TCP). A worker reaches the network only through its egress proxy (<<worker-egress>>); the other job kinds keep the network their operation needs (`PM-SEC-5`).
* [[pathname-sockets]]*Unix sockets*: Up to Landlock ABI 8 the filesystem rules do not govern a `connect(2)` to a pathname Unix socket: every such socket stays reachable for a job, whatever the read set says. ABI 9 adds the right `LANDLOCK_ACCESS_FS_RESOLVE_UNIX`, which `pm-exec` handles and grants with the read and write sets wherever the kernel offers it; a pathname socket outside both sets is then unreachable. Two consequences follow. First, a confined worker's job relay connects to the runtime socket `<PM_MCP_BASE>/run/runtime.sock`, which lies outside the read set (link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]): the runtime names that socket as a read rule of its own for every worker and for no other job, so the connection holds on every ABI. Second, the session bus socket and, without the opt-in, the container engine's sockets are refused from ABI 9 on; below ABI 9 the withheld environment is the only guard against a job that names such a socket by its path (<<session-bus>>, <<container-engine>>), an accepted residual risk (`PM-SEC-5`), verified on Landlock ABI 8, that ends without any change of configuration on a kernel offering ABI 9. The applied ABI is in every job record (`landlock_abi`), which thereby states which of the two holds; a job record never claims a socket guard below ABI 9.
* *ABI Floor*: ABI 1 denies every cross-directory rename and link (`LANDLOCK_ACCESS_FS_REFER` arrives with ABI 2), which breaks Gradle, npm, and Java `Files.move` with `EXDEV`. On a kernel offering only ABI 1 the runtime applies no ruleset and records `confinement: partial(abi=1)`; it never reports a job as confined unless ABI >= 2 was applied. Rights that later ABIs add (for example `LANDLOCK_ACCESS_FS_TRUNCATE`, ABI 3) are handled as best effort, and the applied ABI is recorded in every job record (`landlock_abi`).
* *Unavailable Landlock*: On kernels without Landlock (older kernels, some WSL2 kernels), jobs run with `PR_SET_NO_NEW_PRIVS` only; the runtime records `confinement: unavailable` in each job record and in the runtime status both clients show, and this is an accepted residual platform risk (`PM-SEC-5`).

[#worker-read-set]
=== Worker Read Set
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-5[PM-SEC-5: Subprocess Environment Sanitization & Linux Filesystem Confinement]_ +
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-38[PM-WATCH-JOB-38]_

A worker runs what its model asks for through its harness's shell, and nothing the runtime can check shows whether a model's weights carry behaviour that only a trigger fires. The egress proxy keeps what a worker reads from leaving through its shell (<<worker-egress>>), but not through its model: whatever a worker reads enters its conversation, goes to its model provider, and can end up in what it writes. A worker (kind `llm`) therefore reads only what it works on and what its harness needs to run:

* *Listed, not enumerated*: the read set of a worker is a list of grants, and nothing outside the list and the worker's write set is readable. The runtime passes the list to `pm-exec`, which then builds no read rule on `/` and enumerates nothing; every other job kind keeps the read set above.
* *The grants*, read and execute:
** the system locations of the platform, a list compiled into the runtime and changed only by a release: on Linux `/usr`, `/bin`, `/sbin`, `/lib`, `/lib32`, `/lib64`, `/etc`, `/opt`, `/proc`, and `/sys`; on macOS `/System`, `/usr`, `/bin`, `/sbin`, `/Library`, `/private/etc`, and `/opt`; a location that does not exist is left out;
** the installation of the harness executable and of every host tool and interpreter the project enrolled: the enrolled absolute path with symbolic links resolved, and the parent of the directory that holds it (the installation prefix, for example `~/.sdkman/candidates/java/21` for its `bin/java`); a prefix that is the home directory, contains it, or contains a credential location is reduced to the directory that holds the executable;
** the files and directories the client's bundle manifest manages for the harness (its settings with the deny rules, the shim skill), so that the harness always loads the rules that restrict it; they stay outside the write set (*Consequence for the harness configuration* above);
** the paths the client profile of the harness declares in `headless.readable_paths` (link:../client-profiles/01-profile-schema.adoc#headless-readable-paths[Client Profiles Specification, Readable Paths]);
** the root of another enrolled project, only while the worker's plan holds a cross-project grant for it (link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-2[PM-SEC-2]), read only.
* *Credential locations are never granted*: no grant, and no entry of a worker's write set, may be the home directory itself or equal, contain, or lie in a credential location of the compiled list: `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.azure`, `~/.config/gcloud`, `~/.kube`, `~/.docker`, `~/.netrc`, `~/.git-credentials`, `~/.npmrc`, `~/.pypirc`, `~/.m2/settings.xml`, `~/.m2/settings-security.xml`, `~/.gradle/gradle.properties`, `~/.config/gh`, `~/.config/glab-cli`, and on macOS `~/Library/Keychains`. The runtime leaves such an entry out when it composes the sets, with an activity entry of the worker that names it; a declared toolchain cache such as `~/.gradle` therefore stays in the write set of a `build` job and is not readable for a worker. Profile validation refuses a `headless.readable_paths` or `headless.writable_paths` entry of that kind.
* *What a worker still reads*: the project root with its worktrees is its work, so a file there that holds a secret (an `.env`, an untracked key file) stays readable, and what a worker reads reaches its model provider; an accepted residual risk (`PM-SEC-5`). Neither Landlock nor the macOS sandbox profile restricts the walk of a path or its `stat` (the profile allows `file-read-metadata` everywhere for the same effect), so a worker learns that a path outside its read set exists, never its content.
* *Built at every start*: the runtime composes the list at every worker start from the profile, the bundle manifest, the project's enrolment, and the plan's grants, like the write set, so a changed enrolment or grant takes effect for the next worker.
* *Platforms*: the macOS sandbox profile grants a worker exactly this read set (<<macos-confinement>>). Where the platform confines no job (`confinement: unavailable`), nothing restricts what a worker reads.

[#build-daemons]
=== Build Daemons
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-34[PM-WATCH-JOB-34]_

A Landlock domain confines a process and its descendants, never the processes it talks to. A warm build daemon serves every client that finds it in its registry, with the ruleset of whichever process started it: a daemon started outside confinement writes wherever a confined client asks, and a daemon started under one write set fails the writes of a client with another. Whether a build uses a daemon is decided by the project's build configuration (for example `org.gradle.daemon` in `gradle.properties`) and the enrolled command templates (`mvnd` or `mvn`, `--no-daemon`), never by `PM-MCP`; where it does, the runtime keeps the daemons of one project and one write set apart from every other daemon (`PM-EXEC-4`):

* *Daemon store*: `<PM_MCP_BASE>/projects/<project_id>/daemons/<write_set_digest>/` (mode `0700`; link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]), where `<write_set_digest>` is the first 16 hex characters of the SHA-256 over the job's sorted write set. The runtime creates the directory at job start. It holds only the registries and logs of the build daemons; the runtime reads nothing from it and trusts nothing in it. It is readable and writable for the `build` and `project_script` jobs of the project and for a CLI-variant `git` job that runs repository hooks, and for no other job.
* *How the build tools find it*: `mvnd` through `MVND_DAEMON_STORAGE=<store>/mvnd` in the job environment (<<_job_environment_pm_sec_5,Job Environment>>); Gradle through its daemon registry directory, which the server appends to the composed argument vector of a Gradle wrapper (`-Dorg.gradle.daemon.registry.base=<store>/gradle`; the flag-injecting `GRADLE_OPTS` is never exported) _(provisional until a confined Gradle build is verified with it)_. `GRADLE_USER_HOME` and the other declared toolchain caches (`write_paths`) stay shared between the projects and with the operator.
* *Effect*: A job finds only daemons that jobs of the same project started under the same write set, so every daemon carries exactly the ruleset of its clients, and a job never drives a daemon of the operator or of another project. A changed write set (an enrolment change) gives the next job a new store directory; the daemons of the old one end by their own idle timeout, and the periodic sweep removes the store directories of other digests by itself, as technical residue, once no daemon process recorded in them lives (`pm-operator sweep` lists them) (link:../store-schemas/13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Store Schemas Specification, Evidence-Based Removal Sweeps]).
* *Limit*: The store separates daemons by registry; it is no network confinement (Properties and limits, _Not covered_). The rule applies on every platform, so that a job never drives the operator's daemons where no confinement exists either.

[#container-engine]
=== Container Engine
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-35[PM-WATCH-JOB-35], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-36[PM-WATCH-JOB-36]_

Docker, Docker Compose, and Testcontainers hand their work to the container daemon over its socket. That daemon runs with root authority outside every job's Landlock domain, so a job that reaches the socket holds the authority of the Docker group: it can mount any host path into a container, `<PM_MCP_BASE>` with the runtime token and the credential store included. Access to the container engine is therefore an opt-in of the project's enrolment, the field `container_engine` (link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]; `PM-EXEC-4`, `PM-SEC-5`):

* *Without the opt-in* (`container_engine: null`, the default): no job of the project receives `DOCKER_HOST`, `DOCKER_CONFIG`, or a `TESTCONTAINERS_*` variable, and the read set leaves out the engine's socket paths: `/var/run/docker.sock`, `/run/docker.sock`, `$XDG_RUNTIME_DIR/docker.sock`, and the path of a `unix:` `DOCKER_HOST` found at enrolment, which refuses a connection from Landlock ABI 9 on (<<pathname-sockets>>). A build that needs the engine fails with the tool's own error; the failure envelope names the opt-in of the project's enrolment.
* *With the opt-in* (`container_engine: "docker"`): the `build` jobs of the project receive the container variables as captured at enrolment, and the socket paths stay in the read set. Every process job of the project then records `confinement: partial(container_engine)` in place of `confined` (link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]), and both clients of the operator show it for the project: the job's own writes stay confined, the engine's do not.
* *Operator confirmation*: The opt-in is set only at the project's enrolment, in its onboarding or by `pm-operator enrol --container-engine docker`, which tells the operator that the project's jobs then hold the authority of the Docker group, reaching every host path including `<PM_MCP_BASE>`, and requires the confirmation; the write is audited (`container_engine_enabled`; link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#enrolment-lifecycle-release[Credentials & Enrolment Specification, Enrolment Lifecycle]). `docker` is the only engine value.

[#session-bus]
=== Session Bus
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-36[PM-WATCH-JOB-36]_

The Linux Secret Service has no per-application access control: every process of the user that reaches the session bus can read an unlocked collection, and with it the Token Lane secrets (link:../credentials-and-enrolment/01-provider-credentials.adoc#os-keyring-backends[Credentials & Enrolment Specification, Credential Stores]). Every job is therefore cut off from the user's session bus:

* No job receives `DBUS_SESSION_BUS_ADDRESS` or `XDG_RUNTIME_DIR` (<<_job_environment_pm_sec_5,Job Environment>>), so no D-Bus client library of a job finds the bus.
* The read set leaves out the bus socket `$XDG_RUNTIME_DIR/bus` of the runtime's user (`/run/user/<uid>/bus`); from Landlock ABI 9 that refuses a deliberate `connect(2)`, below it the withheld variables are the only guard (<<pathname-sockets>>).
* *Consequence for the CLI variant*: A CLI-variant `git` or `ci` job cannot use a login that lives only in the Secret Service (the `libsecret` git credential helper, the keyring storage of `gh` or `glab`). The tool then reports its own authentication error, and the readiness check of the integration names it (link:../credentials-and-enrolment/01-provider-credentials.adoc#cli-variant-credentials[Credentials & Enrolment Specification, Credentials of the CLI Variant]): the operator keeps that login in the tool's file storage or an SSH agent, or selects the native variant.
* *Residual risk*: An unconfined process of the same user (the operator's shell, a coding agent the operator runs) reaches the bus like any desktop application, and so does a job on a kernel below Landlock ABI 9 that connects to the socket by its path (verified on Landlock ABI 8: with both variables withheld a client that looks the bus up does not find it, while a connect naming `/run/user/<uid>/bus` succeeds); both are accepted residual risks (`PM-SEC-5`). On macOS the Keychain's per-application access control guards the same secrets, and no session bus exists.

[#worker-data-home]
=== Per-Worker Data Home
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-60[PM-WATCH-DISP-60], link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-61[PM-WATCH-DISP-61]_

A harness that keeps its local state in one per-user store shares it between all its processes: a stalled worker that holds the write lock of that store blocks every other worker of the harness and the operator's own interactive sessions of it. A client profile therefore declares a per-worker data home for such a harness (`headless.data_home`, link:../client-profiles/01-profile-schema.adoc#headless-data-home[Client Profiles Specification, Per-Worker Data Home]; `opencode`: `XDG_DATA_HOME`):

* The runtime creates `<PM_MCP_BASE>/run/jobs/<job_id>/data/` (mode `0700`) with the job-private directory and sets the declared variable to it in the worker's environment.
* It copies the harness's own login file (the profile's `data_home.login_file`, relative to the operator's data home) into the same relative place below it with mode `0600`. The file is copied as bytes: the runtime never parses it, logs it, or keeps it anywhere else, and `PM-MCP` still stores and exports no harness authentication (`PM-EXEC-1`). A harness without a login file fails its worker's start like every harness that is not logged in.
* The directory is readable and writable for that worker alone, the only job-writable place below `run/jobs/`; the runtime reads nothing back from it.
* It is removed with the job-private directory after the job's fate is recorded, the login copy included; a login the harness refreshed inside it is not copied back. A worker of such a harness therefore leaves no session residue.
* A runtime that dies while workers run leaves their data directories, login copies included, behind. The recovery of the project at the next runtime start settles those workers and removes their job-private directories with the data directories (link:../runtime-lifecycle/01-startup-recovery-drain.adoc[Runtime Lifecycle Specification, Per-Project Recovery]), so no login copy outlives the recovery of its project.

The rule applies on every platform. With it, the write set of such a worker needs no path of the harness's shared data directory (`headless.writable_paths`).

[#probe-jobs]
=== Probe Jobs
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-8[PM-EXT-8: Project Onboarding as One Process]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-8[PM-SEC-8: Consent Before Acting]_

Every probe of a program the runtime found and did not enrol yet runs as a job of kind `probe`, through `pm-exec` with the confinement of a job, never in the runtime's own process, and only after the operator's consent of its kind (link:../store-schemas/12-machine-stores.adoc#consent[Store Schemas Specification, Consent Before Acting]): the version probe of a harness the scan found and the harness's login and models probes (link:../client-profiles/01-profile-schema.adoc#harness-scan[Client Profiles Specification, Harness Scan]), and in a project's onboarding the version probes of the host tools found and the checkout's own scripts (link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-onboarding[Credentials & Enrolment Specification, Onboarding a Project as One Process]). Its verification against the candidate record is step 0 of its pipeline (xref:01-pipeline-and-subprocesses.adoc#_verify_not_resolve_execution_pipeline[Verify-Not-Resolve Execution Pipeline]).

* *Working directory*: the checkout root for a probe of a checkout; the empty subdirectory `cwd/` of its job-private directory `<PM_MCP_BASE>/run/jobs/<job_id>/` for a probe of a harness or of a tool found on the machine.
* *Read set*: that of every job (<<_linux_filesystem_confinement_landlock,Read set>>): the whole of `<PM_MCP_BASE>` stays out of it, except the probe's own job-private directory, read-only.
* *Write set*: the system temporary directory and device nodes for every probe; for a probe of a harness additionally the paths its profile declares in `headless.writable_paths` and its data directory where the profile declares one (<<worker-data-home>>), since a login probe may refresh the harness's own login; for a checkout's script the write set of a build job of that checkout, its root and the toolchain caches the detection proposes as its write paths. A version probe writes nothing else; no probe writes `<PM_MCP_BASE>` or another enrolled project's root.
* *Environment*: the rows of the job environment that name all job types (<<_job_environment_pm_sec_5,Job Environment>>), its `enrolment` rows taken from the login environment the terminal client sent with the request, or last captured on the machine; `PATH` holds only the directories of the probed executable and its interpreter. A probe receives no job token, no MCP connection, no credential variable, and no session bus. A login probe of a harness without one (one minimal headless call, its expected tokens shown in the consent) runs the profile's headless template with no tool and no MCP connection.
* *Budget, outcome, and record*: The fixed budget of its kind, a probe never retried by itself, its fate by rows 1 to 4 of the outcome derivation or by an exit code it declares, and its job record and log in the store of its scope, the machine scope's (`<PM_MCP_BASE>/machine/jobs/`) or the onboarding entry's (`<PM_MCP_BASE>/onboardings/<entry_id>/jobs/`; link:../filesystem-layout/02-machine-runtime.adoc#machine-scope-home[Filesystem Layout Specification, Machine Scope & Onboarding Entries]), are implemented (link:../../../pm-runtime/doc/developer/runtime-job.adoc#_probe_jobs[Job Runtime Developer Guide § Probe Jobs]). Remaining: any other end leaves its exit code and output to the step that asked for it, which reads them and shows a failure with the harness's or tool's own output and its acts (xref:01-pipeline-and-subprocesses.adoc#outcome-derivation[Outcome Derivation]).

[#macos-confinement]
== macOS Confinement (Seatbelt)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-5[PM-SEC-5: Subprocess Environment Sanitization & Linux Filesystem Confinement]_

On macOS the `pm-exec` launcher confines every job before `execve` with a sandbox profile of the platform (Seatbelt, applied with `sandbox_init` before the job's image starts), which every descendant inherits and which the job cannot remove:

* *The same sets*: the profile denies by default and allows reading the whole filesystem except `<PM_MCP_BASE>` (its own job-private directory excepted, as on Linux), for a worker only its listed read set (<<worker-read-set>>), and writing exactly the write set of the Linux ruleset (<<_linux_filesystem_confinement_landlock>>), computed from the same enrolment at job start. `PR_SET_NO_NEW_PRIVS` has no macOS counterpart; the profile denies `process-exec` of setuid and setgid files instead.
* *Network*: for a worker the profile allows outbound connections to the loopback port of its egress proxy and to the runtime socket only (<<worker-egress>>); for the other job kinds it allows the network.
* *Verified per release*: the profile language is a platform interface Apple does not document. The release verifies the profile on every macOS version it supports with the confinement tests of the Linux ruleset (a write outside the set, a read of `<PM_MCP_BASE>`, a connection that bypasses the proxy, each refused); a macOS version on which the profile cannot be applied runs jobs unconfined and records `confinement: unavailable` in every job record and the runtime status.
* *Recorded*: a confined job records `confinement: seatbelt` in its job record.

[#worker-egress]
== Worker Egress Proxy
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-5[PM-SEC-5: Subprocess Environment Sanitization & Linux Filesystem Confinement]_

A worker needs the network only for its harness's model provider; its builds run as `build` jobs through `pm_build`. The runtime therefore serves each worker an egress proxy and admits nothing else:

* *The proxy*: an HTTP `CONNECT` proxy of the runtime on a loopback port, one per worker generation, that admits a tunnel only to a host and port of the profile's `headless.endpoints` (link:../client-profiles/01-profile-schema.adoc[Client Profiles Specification, Profile Schema]) and refuses every other one; it reads no content of a tunnel. Every refused destination is an activity entry of the worker and counts toward an audit record `egress_refused` per worker generation.
* *The environment*: the worker's `HTTPS_PROXY` and `HTTP_PROXY` name the proxy and `NO_PROXY` is empty (<<_job_environment_pm_sec_5>>); a harness whose profile verification did not measure that it works through the proxy is not eligible as a worker host.
* *Enforcement*: the proxy is the worker's only route out, enforced by the platform, never only configured. On macOS the sandbox profile admits outbound connections to the proxy's loopback port and the runtime socket only. On Linux the launcher starts the worker in a network namespace of its own (a new user and network namespace, unprivileged), which holds only a loopback interface; inside it the launcher forwards the proxy's loopback port to the runtime's proxy over a Unix socket, so a direct connection to any other host has no route. Both record `egress: enforced` in the job record.
* *Where it cannot be enforced*: on a Linux whose kernel or policy refuses unprivileged user namespaces, or a platform without either mechanism, egress is `unenforced`. No worker is admitted there unless the operator accepted unenforced egress for the machine, an operator act of both clients that shows what it means (a worker's shell reaches every host), is recorded in the audit log, and is shown in the runtime status for as long as it holds; every job record then states `egress: unenforced`.

== Job Environment (`PM-SEC-5`)

The runtime builds every job environment from scratch; nothing is inherited from the runtime's own environment, which belongs to whichever `pm-operator` command, service manager, or restarting predecessor started it (link:../../../../plan-marshall-documentation/doc/specification/runtime-model.adoc[Runtime & Interaction Model Specification]). Each variable has one provenance: `enrolment` values are captured by the terminal client from the operator's login environment and sent with the project's onboarding or `pm-operator enrol` (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#client-environment[CLI, Coordination & Security Specification, What the Terminal Client Sends]), recorded in the project's `build_environment` (enrolment file `enrolments/<project_id>.json`), and refreshed only by a later enrolment; `runtime` values are computed at job start. The harness enrolment captures no environment value.

*Write paths of CLI-variant jobs*: The Landlock write set of a `ci` job additionally contains the `gh` or `glab` configuration directory (token refresh rewrites `hosts.yml`). `~/.ssh/known_hosts` stays read-only for every job: an unknown host key fails the job and is never accepted (no `accept-new`). Repository hooks and signing programs are started by `git` inside the CLI `git` job and inherit its environment, write set, and budget (the hook-running `git` class, link:../timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets]); there is no separate hook or filter job type.

[#canonical-build-verbs]
== Canonical Build Verb Set

This is the one closed set of canonical build verbs of PM-MCP. `pm_build.command` (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/02-service-and-skill-tools.adoc#_pm_build_enrolled_build_execution[MCP Tools Specification]), `PM-TOOL-2`, the canonical argument templates of link:../domain-extensions.adoc[Domain Extensions Specification] (Tier 2), the budget keys of link:../timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts & Budgets Specification], and the link:../identifiers/02-registry-stores-to-web.adoc#id-build-verb[Identifier Registry] use exactly this set. It equals `plan-marshall`'s `ALL_CANONICAL_COMMANDS` (`script-shared/scripts/extension/_extension_constants.py`, verified at plan-marshall commit `88fcfc9ef`; re-verify before implementing), in the same order:

[cols="1,2,3"]
|===
|Verb |`plan-marshall` constant |Meaning

|`clean` |`CMD_CLEAN` |Remove build output.
|`compile` |`CMD_COMPILE` |Compile production sources (build class `compile`).
|`test-compile` |`CMD_TEST_COMPILE` |Compile test sources.
|`module-tests` |`CMD_MODULE_TESTS` |Run the unit tests (build class `module-tests`).
|`integration-tests` |`CMD_INTEGRATION_TESTS` |Run the integration tests.
|`e2e` |`CMD_E2E` |Run the end-to-end tests.
|`coverage` |`CMD_COVERAGE` |Run the tests with coverage measurement and thresholds (xref:03-parsers-and-gates.adoc#_native_coverage_report_parsers[Native Coverage Report Parsers]).
|`benchmark` |`CMD_BENCHMARK` |Run the benchmarks; never a gate.
|`quality-gate` |`CMD_QUALITY_GATE` |Static checks, formatting, and lint.
|`arch-gate` |`CMD_ARCH_GATE` |Architecture rules through a domain-owned engine.
|`verify` |`CMD_VERIFY` |Full verification including tests (build class `verify`).
|`install` |`CMD_INSTALL` |Install the artifacts into the local repository (a toolchain cache of the enrolment's `write_paths`).
|`clean-install` |`CMD_CLEAN_INSTALL` |`clean` followed by `install`.
|`package` |`CMD_PACKAGE` |Package the artifacts.
|===

* *Scope is not a verb*: Every verb runs whole-tree without `module` and module-scoped with it, through the optional module-argument group of its template (link:../domain-extensions/06-configuration.adoc#module-argument-group[Domain Extensions Specification, Optional Module-Argument Group]); gate scope follows from `module` alone (xref:03-parsers-and-gates.adoc#_gate_honesty_verification[Gate Honesty Verification], Gate Coverage).
* *Resolution*: A verb resolves through the project's enrolled template or the domain's compiled default template; a verb without either is refused (`refused`, reason `verb_not_supported`), never approximated by another verb.
* *Deliberate deviations*: None against `plan-marshall`'s set. PM-MCP adds no verb of its own: module tests run as `module-tests`, and format checking is part of `quality-gate`.
