== Verify-Not-Resolve Execution Pipeline
_Implementation watch: link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-59[PM-WATCH-GEN-59]_

Before spawning any subprocess, the runtime reads the enrolment file of the job's project, `<PM_MCP_BASE>/enrolments/<project_id>.json` (link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]), verifies its integrity (<<enrolment-integrity>>), and then validates the job request through a deterministic three-stage verification pipeline (`PM-EXEC-1`..`PM-EXEC-3`, `PM-SEC-2`). A probe job, which runs before a project is enrolled or for the machine, is verified against its candidate record instead of an enrolment (*Probe Jobs* below):

[source,text]
----
  Job Request (Scope, Executable, Argv, WorkingDir)
                       │
                       ▼
       ┌───────────────────────────────┐
       │ 0. Enrolment HMAC Check       │ ──► REFUSED (enrolment_tampered, enrolment_insecure,
       │                               │              enrolment_invalid, not_enrolled)
       └───────────────┬───────────────┘
                       │ Valid (HMAC matches file content)
                       ▼
       ┌───────────────────────────────┐
       │ 1. Working Directory Check    │ ──► REFUSED (path_traversal_rejected)
       └───────────────┬───────────────┘
                       │ Valid (Root or linked worktree)
                       ▼
       ┌───────────────────────────────┐
       │ 2. Executable & Digest Check  │ ──► REFUSED (executable_not_enrolled,
       │                               │              executable_digest_mismatch, build_config_changed;
       │                               │              a worker also harness_tampered,
       │                               │              harness_update_unverified, harness_version_unsupported)
       └───────────────┬───────────────┘
                       │ Valid (Exact path & SHA-256 match)
                       ▼
       ┌───────────────────────────────┐
       │ 3. Argument Schema Validation │ ──► REFUSED (argument_rejected, verb_not_supported)
       └───────────────┬───────────────┘
                       │ Valid
                       ▼
             Spawn Subprocess (Direct)
----

* *Working Directory Confinement (`PM-SEC-2`)*: The working directory must resolve canonically via `Path.toRealPath()` to the project's enrolled root or a live linked git worktree verified through the git contract's `worktree-list` operation, served by the project's configured variant. Arbitrary paths or symlink escapes are rejected with outcome `refused` and reason `path_traversal_rejected`.
* *Working Directory Selection (`PM-ARCH-5`)*: The working directory is derived from the plan's persisted worktree presence at job start, never from the phase: jobs for plans whose `worktree_path` is set run in the plan's worktree root; jobs for plans whose `worktree_path` is `null` and plan-less jobs run in the main checkout (link:../filesystem-layout/01-repository-workspace.adoc#worktree-lifecycle[Filesystem Layout Specification, Worktree Lifecycle]). A job that removes a worktree never runs with a working directory inside that worktree. A worker's working directory is fixed at its launch (link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]). The exceptions are the `zero_tool` workers (the screener and the grading judge `judge`) and the graded workers of a qualification item whose corpus context travels in-band: each runs in the empty subdirectory `cwd/` of its job-private directory `<PM_MCP_BASE>/run/jobs/<job_id>/`, which it can read and never write (link:../model-work/01-roles-and-configuration.adoc#grading[Model Work Specification, Grading]); no other job's working directory lies outside the enrolled tree.
* *Verify-Not-Resolve Executable Resolution (`PM-EXEC-1`, `PM-EXEC-2`, `PM-EXEC-3`, `PM-EXT-5`)*: The runtime *never* searches the system `PATH`:
** *Wrapper Jobs (`mvnw`, `gradlew`, `pw`)*: The wrapper must sit at the root of the tree, must match an enrolled wrapper name in the project's enrolment file (a wrapper name that is not enrolled refuses the job with reason `executable_not_enrolled`), and its SHA-256 content hash must match the enrolled digest; whether git tracks or has committed the wrapper is not checked. The digest check also covers every file that decides which tool runs and with which flags, recorded at enrolment as the wrapper's `pinned_files`: the wrapper jar and wrapper properties (`gradle/wrapper/gradle-wrapper.jar`, `gradle/wrapper/gradle-wrapper.properties`, `.mvn/wrapper/maven-wrapper.properties`) and the repository build configuration (`.mvn/maven.config`, `.mvn/jvm.config`, `gradle.properties`) where present; a pinned file that appears after enrolment counts as changed. Enrolment of `mvnw` or `gradlew` requires `distributionSha256Sum` in the wrapper properties, so the downloaded distribution is pinned as well. A mismatch refuses the job with `refused`, reason `build_config_changed`, and the changed paths. The refusal names no operator act (link:../hypermedia-format/01-representation-and-link-forms.adoc#operator-command-relay[Hypermedia Format Specification, No Operator Relay]): the changed files are re-baselined by a later run of the project's enrolment (`pm-operator enrol`, `PM-EXEC-2`), which the operator's clients offer. The interpreter-based wrapper `pw` is never started through its `#!/usr/bin/env` shebang: the runtime invokes the enrolled interpreter host tool (the wrapper's `interpreter`) with the wrapper as its first argument. What a wrapper runs is decided by the enrolled canonical template of the build verb (`build.canonical_templates`) or its compiled default; there is no per-wrapper goal allowlist.
** *Host Tools (`git`, `gh`, `glab`, `python3`, `ruby`, `npm`, `npx`, `asciidoctor`)*: The runtime invokes the exact absolute `executable_path` recorded in the project's enrolment file after verifying that the file's current SHA-256 matches the enrolment record. A host tool that is a script (`asciidoctor`, a Ruby script) records its `interpreter`, itself an enrolled host tool (`ruby`): the runtime verifies both digests and invokes the interpreter's `executable_path` with the script's `executable_path` as its first argument, never the script's shebang (`PM-EXEC-3`). A host tool or interpreter that is not enrolled refuses the job with reason `executable_not_enrolled`; a file whose SHA-256 differs from the record refuses it with reason `executable_digest_mismatch`.
** *Worker Jobs (`llm`)*: The harness executable of a worker (`claude`, `codex`, `opencode`, or a harness the operator added) is enrolled per machine by the harness step of the machine's onboarding or by `pm-operator enrol-harness <client>`, which records its absolute path, the version its version probe reports, and its SHA-256, and nothing else: no environment value and no credential (link:../store-schemas/11-enrolment-store.adoc#harness-enrolment-store[Store Schemas Specification, Harness Enrolment Store]). The runtime invokes exactly that path, never a `PATH` lookup. Before every worker spawn it verifies the HMAC sidecar of `harnesses.json`; a mismatch refuses the job (`refused`, reason `harness_tampered`, a `security` audit record `enrolment_tampered`). Harnesses update themselves, so a digest that differs from the record is accepted only on the update evidence of the harness's client profile, checked without running the file (link:../client-profiles/01-profile-schema.adoc#update-evidence[Client Profiles Specification, Update Evidence]); without it the job is refused with `harness_update_unverified` and the changed file never runs. After passed evidence, the version probe of the file must report a version within the supported version range of the profile: the new digest and version are recorded and audited. A version outside the range, or a probe that fails, refuses the job with `harness_version_unsupported`. A refused spawn is no model call and no question: it counts as a start failure of the role on that harness (link:../model-work/04-worker-launch.adoc#harness-selection[Model Work Specification, Launch Refusals]); once the start-failure guard holds, the supervisor starts no further worker of the role on that harness, reports the reason to the operator in both clients and the audit log, where the clients offer the harness's enrolment again, and the role's tasks close `lost` with `role_unavailable` and take their conservative fallback (link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]). There is no pause and no `accept-edit` form for it. The argument vector is the one the server composed from the role artifact and the profile's `headless` template (link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]), validated like every other.
** *Project Script Jobs (`project_script`, `PM-EXT-5`)*: Both the script file (`script_path`) and its interpreter (`interpreter`, an enrolled host tool) must match their enrolled SHA-256 digests (`project_scripts.<project_script_id>` of the project's enrolment file), the job's use must match the script's `binding` (`worker_kind` and `target`), and the job arguments must validate against the script's enrolled `argument_schema`; the budget is the script's `max_timeout_seconds`. A script that is not enrolled, or a job whose use does not match its `binding`, is refused with reason `executable_not_enrolled`; a script or interpreter whose digest differs, with reason `executable_digest_mismatch`; arguments that violate the schema, with reason `argument_rejected` (stage 3). The arguments are a typed JSON value and are not appended to the argument vector. There is no job kind for `plan-marshall` scripts.
** *Probe Jobs (`probe`)*: A probe runs a program found on the machine or in a checkout that is not enrolled yet: the version probe of a harness or host tool the scan found, the login or models probe of a harness, and the version probes and scripts of a checkout in a project's onboarding (link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-onboarding[Credentials & Enrolment Specification, Onboarding a Project as One Process]). The refusal of a probe without the operator's consent of its kind and its step 0, the verification against the probe's candidate record in place of the enrolment check (both digests, `executable_digest_mismatch`; the working directory, the canonical git top-level of the onboarding's checkout root or the probe's own job-private directory, `path_traversal_rejected`), are implemented (link:../../../pm-runtime/doc/developer/runtime-job.adoc#_probe_jobs[Job Runtime Developer Guide § Probe Jobs]). The verification also compares a requested argument vector with the declared one (`argument_rejected`), but the runner launches the declared vector of the candidate by construction, so that refusal can fire only for a caller of the verification that supplies another vector; it is a property of the verification, not a control of the runner path. Remaining: the candidate record, which the scan or the detection writes with the absolute path and the SHA-256 of the executable (and of its interpreter, for a script), and its declared vector, the profile's or the host-tool table's probe vector, or a script with exactly the arguments the consent named. Confinement and environment: xref:02-confinement-and-environment.adoc#probe-jobs[Probe Jobs].
* *Argument Schema Validation (`PM-EXEC-1`, `PM-EXEC-5`)*: The argument vector (`argv`) is checked against a closed allowlist schema per tool type. Shell meta-characters (`|`, `;`, `&`, `$`, `` ` ``, `>`, `<`) are never evaluated: the runtime spawns every job without a shell, and the `#!/bin/sh` wrappers `mvnw` and `gradlew` receive the validated vector as positional arguments. This validation guards only against injection through link parameters; flags that come from repository content (the build configuration files above) are governed by their enrolled digests, not by the argument schema. It runs last, after the enrolment, the working directory and the executable passed, and refuses the job with reason `argument_rejected` for a shell meta-character in any caller-supplied argument of any job kind, for a forbidden free flag in a canonical build job (link:../domain-extensions/06-configuration.adoc#enrolled-argument-templates[Domain Extensions Specification, Enrolled Argument Templates]), for a module that is not a discovered module of the project, and for project script arguments that violate the script's `argument_schema`; it refuses a build verb with reason `verb_not_supported` when it has neither an enrolled nor a default template, or when the job is module-scoped and the template has no module-argument group.

[#enrolment-integrity]
=== Enrolment Integrity Check (`PM-EXEC-2`)

Step 0 of the pipeline runs the enrolment check of the job's project, which verifies the sidecar record `<PM_MCP_BASE>/enrolments/<project_id>.json.hmac` (size, SHA-256 and HMAC-SHA-256) against the current enrolment file (link:../../../../plan-marshall-documentation/doc/concepts/enrolment.adoc#check[Concepts § Enrolment, The Check]), before every verify-not-resolve check, in addition to the check in the project's recovery after a runtime start. A failed check blocks only this project's jobs. The runtime (`pm-mcpd`) computes and writes every HMAC with a key that only it reads. Key handling and the accepted residual risks (hosts without a keyring; a same-user process that re-baselines through the operator endpoint with the runtime token) are documented in link:../../../../plan-marshall-documentation/doc/concepts/enrolment.adoc#integrity[Concepts § Enrolment, Integrity] and link:../../../../plan-marshall-documentation/doc/concepts/enrolment.adoc#residual-risk[§ Residual Risk]; operator re-baselining is specified in link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#enrolment-integrity[Credentials & Enrolment Specification, Enrolment Integrity].

* *Mismatch*: The job is refused with reason `enrolment_tampered` (outcome `refused`) and a `security` record is appended to `audit.jsonl`; the runtime never repairs or re-signs the file and trusts no enrolment until the operator re-baselines it through the operator CLI.
* *Other refusals of the check*: an enrolment file or sidecar that fails a per-use check (owner, mode, file type) refuses the job with reason `enrolment_insecure`; an enrolment that cannot be read strictly (an unreadable file or sidecar, an outdated or newer format) or that violates an enrolment rule refuses it with reason `enrolment_invalid`; a project with neither an enrolment file nor a sidecar refuses it with reason `not_enrolled`. Each blocks only this project's jobs.
* *Write Protection*: Jobs can neither read nor write `<PM_MCP_BASE>` on Linux (xref:02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Linux Filesystem Confinement (Landlock)]); the HMAC is the control against writers that are not jobs, such as a model-driven host shell.

== Subprocess Lifecycle & Process-Group Isolation

Every job runs as a direct child of the always-on runtime (`pm-mcpd`), started through the launcher `pm-exec`, independent of any host connection (link:../../../../plan-marshall-documentation/doc/specification/runtime-model.adoc[Runtime & Interaction Model Specification]), inside its own isolated operating system process group (`PM-EXEC-4`, `PM-EXEC-5`, `PM-IMPL-1`).

*Job identity and files*: The `job_id` (link:../identifiers/01-general-rules-and-registry.adoc#id-job-id[Identifier Registry]) with its kind prefix, and the job record (link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]) with the job log beside it in the `jobs/` of the store of its scope (a project, the machine scope, or an onboarding entry for a probe), are implemented (link:../../../pm-core/doc/developer/core-store.adoc#_job_records[Scope Stores Developer Guide § Job Records], link:../../../pm-runtime/doc/developer/runtime-job.adoc#_job_log[Job Runtime Developer Guide § Job Log]). Language servers are no jobs (<<_warm_language_server_pool_orthogonal_service_access_pm_svc_2_pm_svc_4_pm_tool_2,Warm Language Server Pool>>).

[#job-status]
*Job status*: The statuses `queued`, `running`, `refused`, and `ended` (with its fate, <<outcome-derivation>>), a queued job cancelled without any signal, and a job created while the runtime drains recorded `queued`, whatever its kind, and settled `killed` at exit are implemented (link:../../../pm-runtime/doc/developer/runtime-job.adoc#_drain[Job Runtime Developer Guide § Admission and the Drain]; link:../runtime-lifecycle/01-startup-recovery-drain.adoc#_drain_stop_upgrade[Runtime Lifecycle Specification, Drain, Stop & Upgrade]). Remaining: `queued` as the wait before spawn for a slot of its machine lease store, a build slot for a `build` job or a model slot for a worker (link:../store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Store Schemas Specification, Machine Lease Stores]), without a process, a `pid`, or a running budget; admission moves the job to `running` in the transaction that takes the slot, and a job that needs no slot is `running` from its creation.

[#job-wall-times]
*Wall times*: The two wall times of the settled job record, the job's own from `spawned_at` to `ended_at` and the child's `child_wall_ms` from the reported process start to the observed exit, never longer than the job's and `null` without an observed exit, are implemented (link:../../../pm-runtime/doc/developer/runtime-job.adoc#_outcome_derivation[Job Runtime Developer Guide § Outcome Derivation]). Their difference is the runtime's overhead on the job (launcher, confinement, pipeline, and settling), the source of the build-overhead trigger of `PM-MIG-5` (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#migration-trigger-evaluation[Phase Workflows Specification, Migration Trigger Evaluation]).

=== Process-Group Creation via the `pm-exec` Launcher
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-2[PM-WATCH-JOB-2]_

Java's `ProcessBuilder` cannot place a child into a new process group or session (`setpgid`/`setsid`); a child started directly would inherit the runtime's own process group, and signalling that group would hit the runtime and every other job. The runtime therefore starts every job through the launcher `pm-exec`, a separate tiny native binary of the release (plain GraalVM native image with FFM, no Quarkus, module `pm-modules/pm-exec`), started by its path in the runtime's own installation directory `<PM_MCP_HOME>/bin/`, never through `PATH`. The runtime's side is implemented (link:../../../pm-runtime/doc/developer/runtime-job.adoc#_launch_and_launch_report[Job Runtime Developer Guide § Launch and Launch Report]): it starts `<PM_MCP_HOME>/bin/pm-exec -- <verified absolute executable> <args…>` of a verified job with `ProcessBuilder` and its I/O handling (the cleared environment filled from the caller's allowlist, `stdin` from `/dev/null` or an in-memory payload, the output redirected to the job log), takes the PID of the started process as the job PID and process-group ID, reads the launch report from the first line of the job log, records its fields in the job record, and strips it from the job's output, and derives the fate of a launcher that failed before `execve` from its exit. The launcher itself:

. The launcher calls `setpgid(0, 0)` via FFM, so its PID becomes the process-group ID, and then replaces itself with the target via `execve` (never `execvp`: no `PATH` search, `PM-EXEC-1`). The job's PID recorded by the runtime is therefore both the job PID and its process-group ID. For a worker and a probe on Linux the launcher instead stays as the job's process and starts the target as its child with the same `execve` rules (<<_process_termination_cancellation_protocol>>, step 3a); its PID is the job PID and process-group ID all the same, and its launch report is written right before it starts that child.
. [[launch-report]]*Launch report*: Right before `execve` the launcher writes exactly one launch report to `stderr`: a single line holding one JSON object (its PID after `setpgid`, the process start instant `process_started_at`, the applied `confinement`, and `landlock_abi`). `stderr` is the only channel the launcher has (it receives the job's output redirection and nothing else), so the report is the first line of the job log. A launcher that fails before `execve` writes no report and exits `64` (usage), `126` (confinement could not be applied), or `127` (`execve` failed). The runtime waits for the report only for the launch report wait (link:../timeouts/01-job-budgets-and-waits.adoc#launch-report-wait[Timeouts, Launch Report Wait]), never for the job's budget, and a cancel ends the wait at once; a job whose launcher wrote no report in that time keeps the job record without a `pid` (step 6) and is settled by its exit, a cancel or its budget.
. Cancellation and timeouts signal exactly that group (`kill(-pid, …)`). Warm build daemons that detach themselves into their own session (Gradle daemon, `mvnd`) are intentionally not affected (`PM-EXEC-4`).
. `pm-exec` is not a user command and not a verb of `pm-mcp` or `pm-operator`; only the runtime starts it: it accepts only an absolute executable path, an argument vector, and (on Linux) the confinement sets, performs no verification of its own, reads no file of `<PM_MCP_BASE>`, and holds no secret.

*Alternative for later implementations (macOS only)*: Start jobs directly via FFM `posix_spawn` with `POSIX_SPAWN_SETPGROUP` (the mechanism already used for the detached runtime start, link:../../../../plan-marshall-documentation/doc/specification/runtime-model.adoc[Runtime & Interaction Model Specification]). This removes the extra `execve` hop but replaces `ProcessBuilder` completely: pipes, `stdin` streaming, output capture, and exit-status reaping (`waitpid`) must then be implemented on FFM as well. The job contract (process group = job PID, outcome classification) is identical, so the runtime can switch implementations without changing any other specification. On Linux the `pm-exec` launcher (or an equivalent restricted spawner thread) stays mandatory: `PR_SET_NO_NEW_PRIVS` and the Landlock ruleset must be applied between `fork` and `execve`, and `posix_spawn` offers no hook for that.

=== In-Memory `stdin` Streaming (`PM-EXEC-5`)

When a workflow primitive served by the CLI variant (link:../credentials-and-enrolment/01-provider-credentials.adoc#cli-variant-credentials[Credentials & Enrolment Specification, Credentials of the CLI Variant]) passes multi-line text to an enrolled `git` or `ci` tool, the job carries the validated UTF-8 bytes as its in-memory `stdin` payload. The runtime's side, the payload written by a virtual thread and the stream closed right after it, so the tool sees EOF and never waits for interactive input and the text never enters the argument vector, a file, or a shell, is implemented (link:../../../pm-runtime/doc/developer/runtime-job.adoc#_launch_and_launch_report[Job Runtime Developer Guide § Launch and Launch Report]). The native variant runs in process and passes the same text as an in-memory request payload; it has no job and no `stdin`.

The `stdin` forms of the CLI variant are closed:

* `git`: `git -C <tree> commit -F -`.
* `gh`: `gh pr create|edit|comment --body-file -`, `gh issue create|comment --body-file -`, and `gh api graphql --input -` for the fixed GraphQL documents.
* `glab`: the operations whose `glab` subcommand has no `stdin` form (`mr create`, `mr note`, `issue note`) are sent as `glab api <endpoint> --input -` with a server-composed JSON body, which `glab` reads from `stdin` (link:../../../../plan-marshall-documentation/doc/specification/evaluation.adoc#results[Evaluation Reference, `glab` bodies on `stdin`]). An operation for which no form reads its body from `stdin` returns `unsupported_by_variant{reason: no_stdin_form}` in the CLI variant; free text is never moved to the argument vector or a file to work around it.

For every form the server never writes commit messages or PR/issue bodies to a scratch file, in the worktree or in `/tmp/`, and never places multi-line text in the argument vector, avoiding OS `ARG_MAX` limits and `ps` command-line inspection.

[#worker-output]
=== A Worker's Output While It Runs

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-7[PM-WORK-7: Worker Activity & Off-Track Signals]_

A worker's harness writes its structured output stream (`headless.output.format`) to the job log like every job. The runtime reads that log while the worker runs, line by line as it grows, never a terminal and never the harness's session transcript:

* *Activity*: For a harness whose profile maps its stream (`headless.events`, link:../client-profiles/01-profile-schema.adoc#worker-activity[Client Profiles Specification, What a Worker Does]), each line is mapped onto the closed list of activity kinds; a line that matches no mapping is counted, not shown. Every text and target of an entry passes the `SecretRedactor` before the entry is appended to the task's activity journal, so the journal never holds a secret the job log could carry (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-credential-cli[CLI, Coordination & Security Specification, Runtime Secret Redaction]); the activity is untrusted data (`PM-SEC-1`). A harness that declares `headless.events: null` yields no harness entries; the server's own entries are written for every worker.
* *Usage and failure*: The usage of each turn is read through the profile's usage pointers (link:../client-profiles/01-profile-schema.adoc#headless-usage[Client Profiles Specification, Usage Pointers]); after a failed start the last lines of the log are read for the start-failure guard (link:../model-work/03-supervision-and-recycling.adoc#start-failure-guard[Model Work Specification, Start-Failure Guard]).
* *Redaction of every read-out*: Whatever leaves a job log toward an operator or a model, an activity entry, an excerpt, the harness's error text, or a log resource, passes the `SecretRedactor` first; the job log file itself lies under `<PM_MCP_BASE>`, outside every job's read set.

=== Process Termination & Cancellation Protocol
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-3[PM-WATCH-JOB-3]_

When a job exceeds its allocated budget (`PM-EXEC-4`, link:../timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts & Budgets Specification, Job Budgets]), when the engine cancels it (a cancel is an engine event, never a model link), when the supervisor ends a worker (link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]), or when the runtime drains, the runtime terminates the job's process group in numbered steps. Steps 1 to 4 and 6, and the fate of a terminated job derived by <<outcome-derivation>>, are implemented (link:../../../pm-runtime/doc/developer/runtime-job.adoc#_termination[Job Runtime Developer Guide § Termination], link:../../../pm-runtime/doc/developer/runtime-job.adoc#_the_runner[§ The Runner], link:../../../pm-runtime/doc/developer/runtime-start.adoc#_jobs_recovery_step[Runtime Start Developer Guide § The Jobs Part of Step 3]):

* *Step 1*: `SIGTERM` to the job's process group (`kill(-pgid, SIGTERM)` via Java FFM, `PM-TECH-4`), whose ID equals the job PID.
* *Step 2*: the termination grace period (link:../timeouts/01-job-budgets-and-waits.adoc#grace-period[Timeouts & Budgets Specification]) for all processes in the group to exit.
* *Step 3*: `kill(-pgid, SIGKILL)` when any process of the group remains alive after the grace period. Steps 1 to 3 address the group, never only its leader, also when the leader has already exited and only descendants remain.
* *Step 4*: a cancel that reaches a job before the launcher called `setpgid` signals the PID directly, retries against the group, and records `cancel_before_group: true`.
* *Step 6*: the job record written before spawn and replaced right after it with `pid` and `process_started_at` from the launch report (<<launch-report>>), the job counting as running only once that replace is persisted, and in the project's recovery after the next runtime start every record left `queued` or `running` settled `killed` by the first matching rule, (a) an in-process operation (<<in-process-operations>>), (b) a spawn before the system boot, (c) a `pid` that is `null`, with the audit note `orphan unidentifiable`, or (d) a live process group probed and terminated with steps 1 to 3, and never adopted or re-executed (link:../runtime-lifecycle/01-startup-recovery-drain.adoc#per-project-recovery[Runtime Lifecycle Specification, Per-Project Recovery]).

Remaining:

* *Step 3a, A Worker's Descendants Outside the Group*: For a worker (`llm`) and a probe, which start no process that may outlive them (a worker's builds run as `build` jobs, whose warm daemons outlive them by design, xref:02-confinement-and-environment.adoc#build-daemons[Build Daemons]), a descendant that left the process group or started a new session (`setsid`) is ended with the job as well. On Linux the launcher does not replace itself with the command for these two kinds: it marks itself child subreaper (`PR_SET_CHILD_SUBREAPER`), starts the command as its child in its own process group, and stays the job's process (its PID is the job's PID and process-group ID, and its exit status is the command's). The kernel reparents every orphaned descendant of the command to the launcher, whatever group or session it moved to, so none can leave its reach. When the command exits, or on the runtime's `SIGTERM`, the launcher signals all its remaining children with `SIGTERM`, then within the grace period with `SIGKILL`, and repeats until it has no child left (`waitpid` returns `ECHILD`), before it exits; a child that appears during the sweep is its child too, so the sweep is race-free. The runtime sends its `SIGKILL` to the group (step 3) only after the grace period, so the sweep completes first. On macOS, which has no subreaper, the runtime records the job's process tree while it runs (refreshed on every activity entry of a worker and at least once per second) and signals every recorded member still alive at the job's end; a descendant that detaches and loses its parent between two refreshes escapes the sweep. That residual risk is bounded: it keeps the job's sandbox profile, and its only network route, the worker's egress proxy, closes with the worker (xref:02-confinement-and-environment.adoc#worker-egress[Worker Egress Proxy]). A descendant found alive after the sweep is written as a `security` audit record `job_descendant_survived` with its PID and executable, and the runtime status shows it.
* *Step 5, Worker Fence*: For a worker, the fence follows step 3: its job token is revoked, its generation fenced, and its lease released at once. Relay termination never affects a job, and a `timed_out` job is `no_verdict` in every roll-up (link:../timeouts/01-job-budgets-and-waits.adoc#no-verdict-rule[Timeouts & Budgets Specification, Timed-Out Outcomes Are No-Verdict]).

[#in-process-operations]
=== In-Process Operations (Native Variant)
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-3[PM-WATCH-JOB-3]_

A `git` or `ci` operation of the native variant (JGit, provider HTTP clients) runs inside the runtime: no argument vector, no environment, no process group, no Landlock ruleset, and no `pm-exec` launcher exist for it. It is still a job of the runtime, so waits, cancellation, metrics, and recovery treat it like any other job:

* *Job Record*: Every in-process operation gets a job record of its kind (`git` or `ci`, job id prefix `g` or `c`) with `execution: in_process`, its budget key `<kind>:<operation>`, `budget_seconds`, and `budget_derivation`; the process fields (`argv_digest`, `pid`, `process_started_at`, `spawned_at`, `exit_code`, `signal`) are `null` and `confinement` is `not_applicable` (link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]). It writes no job log file.
* *Budget & Cancellation*: The operation runs under the budget of its operation class; at budget expiry, on a cancel by the engine, and at the expiry of the drain timeout it is cancelled cooperatively (JGit `ProgressMonitor`, interruption of the HTTP exchange), every HTTP request carries the compiled per-request connect and read timeout, and an operation that does not return within the grace period is abandoned with its late result discarded (link:../timeouts/01-job-budgets-and-waits.adoc#in-process-operations[Timeouts & Budgets Specification, In-Process Operations]). A partial result is never used.
* *Outcome*: Rows 1 to 4 of <<outcome-derivation>> apply unchanged (`refused` before the operation starts, `cancelled`, `timed_out` as `no_verdict`, `killed` at drain or for a record left `running` by a previous runtime instance; nothing is probed or adopted). Otherwise rows 11 to 13 decide: `succeeded` for a domain outcome of its closed contract enumeration, `failed` for a transport outcome, `indeterminate` for an end outside its contract. A provider rate limit (`rate_limited{reset_at}`, or a `Retry-After`) is neither a failure nor a timeout: the operation is re-issued after the stated instant, the time until then does not count against its budget, and the wait records `provider_rate_limit` (<<_bounded_long_poll_progress_reset_waiting_primitives_pm_wf_8_pm_impl_4>>).

[#git-identities]
=== Git Identities (`PM-EXEC-5`)
_Implementation watch: link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-59[PM-WATCH-GEN-59]_

Every operation of the git contract, in the native variant over JGit and in the CLI variant over `git`, treats a pinned commit as an identity that is checked, never as a name that is looked up:

* *Commits are object ids*: a commit the server pins (the entry baseline and the capture snapshot, the `head_sha` of a pull request, the merge base, an epic's landing, `head_at_completion`) is passed and compared as its full 40-character object id, never abbreviated and never as a ref name.
* *Refs by their full name*: a branch is addressed as `refs/heads/<name>`, a ref of the runtime as `refs/pm-mcp/<…>`, a remote branch as `refs/remotes/<remote>/<name>`; the CLI variant passes the full name and, where `git` would also accept a commit, the `--end-of-options` form, so a branch named like a commit hash is never taken for the commit.
* *Ambiguity is an error*: a name that resolves both as a ref and as an object id, or as two refs, is refused (`git_identity_ambiguous`, naming the name), never resolved by one reading.
* *Checked after it arrives*: after every fetch, checkout, reset, rebase, and worktree creation, the commit reached is compared with the pin the operation was meant to reach; a mismatch refuses the operation (`git_identity_mismatch`, with both ids) before anything runs on the result.

=== Bounded Long-Poll & Progress-Reset Waiting Primitives (`PM-WF-8`, `PM-IMPL-4`)
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-5[PM-WATCH-JOB-5], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-6[PM-WATCH-JOB-6], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-19[PM-WATCH-JOB-19], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-30[PM-WATCH-JOB-30]_

Every job is awaited by the engine, never by a model: a job state advances on the job's completion as an engine event, a composite wait settles or short-circuits on the events of its members, and a cancel terminates the job's process group (<<Process Termination & Cancellation Protocol>>). No representation offers a link to wait for or cancel a job; the plan representation shows the job's progress as a view (`PM-WF-8`).

Two waiting primitives serve the only calls a model holds open: a worker's `pm_wait` (a consultation's wait included; semantics in link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]) and a running `pm_build` (`PM-SVC-1`, `PM-SVC-4`). The server selects between them without model involvement:

* *Bounded Wait*: The server holds the call open for at most the bounded wait window of the calling connection's client profile (`connection.bounded_wait_seconds`; for a worker the profile of its role's harness; value and bounds in link:../timeouts/01-job-budgets-and-waits.adoc#bounded-wait[Timeouts & Budgets Specification, Bounded Wait Window]). A `pm_wait` returns an offered task, `wait_again`, or `end` within the window; a `pm_build` returns its result once the build completes, otherwise the running build with its `job_id` to continue the call with. Neither ever fails with an MCP transport timeout.
* *Progress Wait*: When the profile declares `progress_resets_timeout: true` and the request supplies a `_meta.progressToken`, the runtime emits periodic `notifications/progress` frames over the calling connection (relayed to the harness by `pm-mcp serve --job`) at the interval of link:../timeouts/01-job-budgets-and-waits.adoc#progress-interval[Timeouts & Budgets Specification], never with a gap the host could read as idle. A `pm_wait` keeps its bounded window and is held through it by the frames (the per-host rule in link:../client-profiles/01-profile-schema.adoc#worker-block[Client Profiles Specification, Worker Block]); a `pm_build` waits up to the progress wait upper bound (link:../timeouts/01-job-budgets-and-waits.adoc#progress-wait[Timeouts & Budgets Specification]).
* *Wait Attribution*: The engine records for every interval a plan spends waiting its `wait_reason` and `deliberate` (`true` for an operator wait, a pause, a prerequisite wait, or a rate window). The closed enum maps every wait of a plan to exactly one reason:
** `build`: a build or `project_script` job, its wait for a build slot included;
** `git`: a `git` job or in-process `git` operation;
** `ci`: a `ci` job or operation and a CI wait (link:../timeouts/01-job-budgets-and-waits.adoc#ci-wait[Timeouts & Budgets Specification, CI Wait]);
** `model_job`: the tasks of a `job llm` state, the wait of its workers for a model slot (link:../timeouts/01-job-budgets-and-waits.adoc#model-slot-wait[Timeouts & Budgets Specification, Model Slot Wait]) and the re-offers of its tasks included;
** `review_bot_window`: a review-bot rate window or re-review wait (link:../timeouts/01-job-budgets-and-waits.adoc#review-bot-windows[Timeouts & Budgets Specification, Review-Bot Rate Windows]);
** `operator_wait`: every operator wait of the plan (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]): an open decision, the votes of its quorum included, an open waiver request of a remediation unit, a consent, and a choice;
** `paused`: the time the plan holds paused by the operator, from the point its pause names until it is started again (link:../runtime-lifecycle/02-plan-pause-and-stalled-plans.adoc#plan-pause[Runtime Lifecycle Specification, Pausing and Starting a Plan]);
** `merge_queue`: the merge-queue landing wait;
** `merge_mutex`: the admission wait of the cross-plan merge mutex (link:../timeouts/02-runtime-leases-operator-web.adoc#merge-mutex-admission-wait[Timeouts & Budgets Specification, Merge-Mutex Admission Wait]);
** `server_retry`: the backoff before a server retry, of a bounded server rule or of a condition's self-remedy retry (link:../timeouts/01-job-budgets-and-waits.adoc#server-retry-backoff[Timeouts & Budgets Specification, Server Retry Backoff]);
** `provider_rate_limit`: the time a provider's API rate limit (`Retry-After` or a rate-limit reset instant) deferred the next observation of a `ci`, review-bot, or merge-queue wait (link:../timeouts/01-job-budgets-and-waits.adoc#ci-repoll-cadence[Timeouts & Budgets Specification, Provider Re-Poll Cadence]); it is never a timeout and never a failure;
** `prerequisite`: the time a plan holds in `replan.await-prerequisite` for a named prerequisite to land;
** `integrity_pause`: the time the plan's scope holds under an integrity pause (link:../store-schemas/13-leases-integrity-testing.adoc#store-digest-verification[Store Schemas Specification, Store Digest Verification]), `deliberate: false`.
+
`record-metrics` sums wait time per reason and reports deliberate waits separately from poll misses, never as one "waste" figure.

[#engine-deadlines]
=== Engine Deadline: Prerequisite Wait

One wait of a plan ends by time without any model call: the prerequisite wait of a re-planning (value in link:../timeouts/01-job-budgets-and-waits.adoc#replan-budget[Timeouts & Budgets Specification, Re-planning budget & prerequisite wait]). Its deadline is a persisted instant (`prerequisite.deadline_at` of the re-planning record, link:../store-schemas/17-re-planning.adoc[Store Schemas Specification, Re-Planning]), never an in-memory timer alone. An operator wait has no deadline: a decision, a waiver request, a consent, and every other wait for the operator end only by an act of the operator or an override, never by the passing of time (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]).

* *Prerequisite Wait*: A server-side `composite_job` of the re-planning (`replan.await-prerequisite`), bound as `active_job`; its constituents are the deadline and a watch of the prerequisite (the provider's pull-request state or the prerequisite plan's outcome). The prerequisite landing settles it `landed`, its closing unlanded `closed`, the deadline `expired` (link:../phase-workflows/08-dynamic-re-planning.adoc#replan-actions[Phase Workflows Specification, Actions & Guards]). It needs no model turn.
* *Timer*: The runtime keeps one deadline timer over the persisted instants of every enrolled project; it fires at the earliest instant and after every runtime start, where the per-project recovery (link:../runtime-lifecycle/01-startup-recovery-drain.adoc#per-project-recovery[Runtime Lifecycle Specification, Per-Project Recovery]) processes every deadline that passed while the runtime was down, before the project is served. A deadline fires at most once; its transaction re-checks that the wait is still open (a prerequisite that landed in the race wins).
* *Holds and pauses*: While the scope is under an integrity pause, or the plan is paused, a passed deadline is held and processed after the pause ends or the plan is started again. The ends of a plan close the re-planning's wait in their own transaction, so no timer fires on it.

=== Warm Language Server Pool & Orthogonal Service Access (`PM-SVC-2`, `PM-SVC-4`, `PM-TOOL-2`)

The Job Runtime manages the runtime's bounded pool of warm Language Server Protocol (LSP) processes (`max_lsp_instances` in `machine-config.json`, link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration]) spoken via Eclipse `LSP4J` over `stdio` (`PM-TECH-2`, `PM-TECH-3`):

* *Verify-Not-Resolve Launch*: Each language server binary (for example `jdtls`, `pyright-langserver`, `typescript-language-server`, `rust-analyzer`, or any other language server a domain declares) is verified against `language_servers` of the project's enrolment file `enrolments/<project_id>.json` before launch.
* *Pool Processes, Not Jobs*: A language server is started through `pm-exec` like a job, in its own process group and, on Linux, with the same confinement as a job of its project (xref:02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Linux Filesystem Confinement (Landlock)]), but it gets no job record, no `job_id`, and no outcome (there is no job kind for it). After a runtime crash it ends when its `stdin` closes.
* *Lifecycle & Eviction*: Instances are keyed by `(canonical_worktree_path, language_id)` (the plan worktree, or the main checkout at the enrolled `project_root`), initialized lazily on the first `pm_lsp` call (`PM-TOOL-2`, `PM-SVC-4`), evicted cleanly (`shutdown` -> `exit` -> `SIGTERM`) after the language server idle timeout (`lsp_idle_timeout_seconds`; start, request, and idle timeouts in link:../timeouts/02-runtime-leases-operator-web.adoc#runtime-lifecycle[Timeouts & Budgets Specification, Runtime Lifecycle]), when the plan worktree it serves is removed, or when the runtime drains or stops, and restarted automatically on unexpected exit, within the language server restart cap (link:../timeouts/02-runtime-leases-operator-web.adoc#lsp-restart-cap[Timeouts & Budgets Specification]). After the retries are exhausted, `pm_lsp` returns `lsp_unavailable` for that instance until its idle eviction or a runtime restart (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools.adoc[MCP Tools Specification], closed error codes).

[#outcome-derivation]
== Outcome Derivation
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-1[PM-WATCH-JOB-1], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-23[PM-WATCH-JOB-23]_

The closed table of 13 rows by which the runtime derives every job outcome itself, at the boundary, from evidence it observed (whether it refused the job before spawn, which signal it sent and why, the wait status of the process, and the state and parse of the job log), evaluated top to bottom with the first matching row deciding, is implemented, with the derived `fate`, the deciding `outcome_row`, the exit code or signal, and `cancel_before_group` recorded in the job record (link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]): its rows are those of link:../../../pm-runtime/src/main/java/de/planmarshall/runtime/job/OutcomeDerivation.java[`OutcomeDerivation`] (link:../../../pm-runtime/doc/developer/runtime-job.adoc#_outcome_derivation[Job Runtime Developer Guide § Outcome Derivation]; `PM-EXEC-4`, `PM-SVC-1`). A status that a job reports about itself (the `status` field of a `project_script` output payload, the final message of a worker) is evidence to check, never the outcome. Remaining is the evidence that the parts of the runtime still to be built supply to the rows:

* *Refusals (row 1)*: besides the reasons of the verify-not-resolve pipeline (<<Verify-Not-Resolve Execution Pipeline>>), a worker job is refused with `harness_tampered`, `harness_update_unverified`, or `harness_version_unsupported`, and a job may be refused by its admission.
* *Success markers (row 7)*: build — the engine's terminal success marker (`BUILD SUCCESS`, `BUILD SUCCESSFUL`) or the tool's passing summary (xref:03-parsers-and-gates.adoc#_native_build_output_parsers[Native Build Output Parsers]); `git` — exit `0` plus the post-condition read where the primitive declares one; `ci` — a parseable `--json` payload of the expected shape; `project_script` — a schema-valid output payload whose `status` agrees; `probe` — its output read by the scan, the detection, or the probe's step; `llm` — the harness's final result event after the server ended the worker (`end` through `pm_wait`, or a fresh worker's task reaching a closed task outcome); the result of model work is the task's submission, validated on its submit link, never the job's output (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]). For a `zero_tool` worker, which has no connection, a structured final result that validates against the result schema of its role's task (`screen-verdict` for the screener, `judge-score` for the judge, link:../model-work/01-roles-and-configuration.adoc#grading[Model Work Specification, Grading]). For a harness whose profile declares `exit_reliable: false`, the final result event is parsed from its JSONL output. The success markers for `git` and `ci` apply to the jobs of the CLI variant.
* *Diagnostics (rows 9 and 10)*: the located diagnostics a parser extracts become findings; the fallback of a `build` job without a parsed diagnostic is xref:03-parsers-and-gates.adoc#_unparseable_output_fallback_failed_unparsed[Unparseable Output Fallback (`failed_unparsed`)].
* *In-process operations (rows 11 to 13)*: the domain outcome of its closed contract enumeration is the operation's result, never a failure of the job. A provider's refusal of the requested change is a domain outcome, never a transport outcome: an HTTP `405`, `406`, `409`, or `422` answer (a merge refusal, a head mismatch), and every other `4xx` answer whose body carries the provider's reason (for example GitLab's `400` "Merge trains are not enabled for this project"), except `401` and `403` (transport outcomes) and `404` (the domain outcome `not_found`). The outcome is the operation's own refusal outcome where its enumeration has one (the merge's `not_mergeable{reason}` and `head_moved`), otherwise `rejected{reason}`, which every mutating operation's enumeration contains; the CLI variant derives the same outcome from the tool's output. The transport outcomes are `auth_failed` for `401`, `permission_denied` for `403`, `provider_unavailable`, `malformed_response` (which includes a `4xx` answer without a reason in its body), `unsupported_by_variant`, and `capability_missing`, recorded with the fate; for an end outside the contract the exception class is recorded (<<in-process-operations>>).

*Write order at job end*: The fixed order of the settlement, in which the first step that fails stops every later one, with the job record's fate first and the release of the build or model slot the job held after it, is implemented (link:../../../pm-runtime/doc/developer/runtime-job.adoc#_settlement[Job Runtime Developer Guide § Settlement]). Its other steps are seams and remain, each in its place of the order: with the fate, for a worker, the revocation of its token and the fence of its generation (the job record carries no usage); then for a worker the queue task record (attempt end, lease release; link:../store-schemas/01-format-and-session-log.adoc#transaction-journal[Store Schemas Specification, Transaction Journal], Worker end), then the metrics row of the attempt that ended with the job, if any, with its usage parsed (every other attempt's row is written when that attempt ends; `metrics.json` of the task's scope, link:../store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Store Schemas Specification, Metrics Store]), then the change-ledger row (`change-ledger.jsonl`, for jobs that stamp one), then the timing observation (link:../store-schemas/09-derived-facts-and-build-timings.adoc#build-timings-store[Store Schemas Specification, Build Timings Store]), and after the slot release, last, the removal of a worker's job-private directory. A crash in between loses at most a task's metrics row (reported by `record-metrics` as the divergence `row_absent_from_metrics`, never read as `0`), a freshness mark (the build re-runs), or a timing sample; a task lease left on an ended generation is released by the recovery, and the recovery removes a job-private directory whose job has settled.

Language server instances of the warm LSP pool are not classified by this table; their failures are reported as the non-run reasons of link:../domain-extensions.adoc[Domain Extensions Specification] (Explicit Non-Run Reporting) and the timeouts of link:../timeouts/02-runtime-leases-operator-web.adoc#runtime-lifecycle[Timeouts & Budgets Specification, Runtime Lifecycle].
