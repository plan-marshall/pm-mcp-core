=== Closed Link Relations (`rel`)

Every link's `rel` column is drawn from a closed enumeration of 9 relation identifiers, shared by the model-facing links and the operator links of the operator's clients (xref:01-representation-and-link-forms.adoc#operator-links[Operator Links]). Waiting on a job and cancelling it are engine events, never relations (xref:01-representation-and-link-forms.adoc#link-forms[Link Forms]):

[cols="1,1,3"]
|===
|`rel` Value |Allowed Forms |Semantic Meaning

|`next`
|`noop`, `submit`
|Default forward transition along the primary workflow path (for example the task acknowledgement `ack`).

|`alt`
|`noop`, `submit`
|Alternative forward transition (for example the `no` of a consent or the `skip` of an optional step an operator wait offers, or an alternative submission of a task entity). The planning lane is never a model-selected link: it is computed by the server.

|`retry`
|`noop`, `submit`
|Repeat the last failed deterministic operation (build, push, CI fetch, re-scan, bot re-trigger) without changing code. The `retry` of a remediation decision task is a `submit` link carrying `reason:enum[flaky\|infra\|timeout]`, bounded by the policy's retry budget; as an operator link it is the retry an operator wait or a hold offers.

|`fix`
|`noop`, `submit`
|Choose an in-branch fix for a failed build, check, or gate finding; the `fix` of a remediation decision task is bounded by the policy's fix budget, and a worker of the plan's writer role does the fix.

|`loop_back`
|`noop`, `submit`
|Return from `finalize` to `execute` in the plan's worktree by allocating fresh remediation tasks (the `loop_back` form of a remediation policy's `fix`, which returns `fix_requested` to its caller and is bounded by the policy's fix budget), or re-author the outline (`loop_back_outline`, bounded by the loop-back budget).

|`submit`
|`submit`
|Deliver judgment output to the server: model-authored from a worker for its leased task entity, or the operator's answer or choice as an operator link.

|`escalate`
|`submit`
|File a request for operator action (`request_waiver`, xref:01-representation-and-link-forms.adoc#question-waiver-and-exit-links[Task, Question & Waiver-Request Links]). The request starts an operator wait that the operator ends with `waive` or `decline` in either client; the model never waits on the operator inside the call.

|`consult`
|`submit`
|Ask another role through the server (`consult:<role>`, one link per `consult role` clause of the task's state, `PM-WORK-4`); the answer arrives through the asker's next `pm_wait`.

|`abort`
|`submit`
|Leave a sub-workflow through the implicit `step_out`, an operator link of an operator wait of the sub-workflow, which unwinds one frame and returns the control outcome `stepped_out` to its caller (`PM-WF-16`); no model-facing link has this relation. Ending a plan or epic is never a link: it is an operator act (cancel, abandon, the integrity abort) or the release of its project.
|===

[#link-identifier-grammar]
=== Link Identifier Grammar (`<action>`, `<action>:<entity_id>`, `submit:<kind>`, `consult:<role>`)

Link identifiers (`link` column) are server-derived, stateless tokens of the form `<action>` or `<action>:<qualifier>`. Their grammar and length bounds (action name, qualifier, and the whole link identifier) are defined in the link:../identifiers/01-general-rules-and-registry.adoc#id-link-id[Identifier Registry]; the four forms have the following semantics, and an operator link's `id` uses the scope-wide or the entity-addressed form:

1. *Scope-Wide Link (`<action>`)*: An action name alone (for example `ack`, `submit`, `ask`, `infeasible`, `retry`, `fix`, `loop_back`, `request_waiver`, or an operator link such as `yes`, `waive`, or `step_out`); it applies to the addressed task entity or state as a whole.
2. *Entity-Addressed Link (`<action>:<entity_id>`)*: An action name, `:`, and a link:../identifiers/01-general-rules-and-registry.adoc#id-entity-id[entity identifier] (for example `submit:TASK-004`, `ask:TASK-004`, `revise:TASK-004`); it is validated against both the addressed state and the addressed `<entity_id>`'s state under the scope lock (`PM-WF-4`).
3. *Kind-Addressed Submit (`submit:<kind>`)*: The action `submit`, `:`, and the name of a submission the task entity's kind registers (for example `submit:answer` of a consultation, `submit:vote` of a vote, `submit:triage-groups`, `submit:reground`, the closing `submit:decompose` of the epic decomposition); it addresses the task entity as a whole and names which of its registered submissions the call delivers, with that submission's closed parameter schema. The kind is registered with the entity kind (link:../workflow-dsl/02-units-jobs-decisions.adoc[Workflow DSL Specification, Entity Units]), never derived from the call, and a kind the entity's current state does not offer is `link_not_available`.
4. *Role-Addressed Link (`consult:<role>`)*: The action `consult`, `:`, and a role name of the effective role set (link:../identifiers/01-general-rules-and-registry.adoc[Identifier Registry, role name]), for example `consult:review-security`; it exists exactly once per `consult role <role>` clause of the task's state.

=== Free Parameter Descriptor Grammar (`free` Column)
_Implementation watch: link:../../implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-10[PM-WATCH-HYP-10]_

The `free` column specifies the closed schema for `pm_do(..., args)` in compact human- and model-readable form:

[source,ebnf]
----
free_spec     = "" | param_decl , { "," , param_decl } ;
param_decl    = param_name , ":" , param_type , [ "?" ] ;
param_name    = lowercase_alpha , { lowercase_alpha | digit | "_" } ;
param_type    = scalar_type
              | "list<" , scalar_type , ">" ;
scalar_type   = "text" , [ int_range ]
              | "int" , [ int_range ]
              | "enum[" , enum_val , { "|" , enum_val } , "]"
              | schema_ref ;
schema_ref    = "schema[" , schema_name , "]" ;
schema_name   = lowercase_alpha , { lowercase_alpha | digit | "-" } ;   (* identifiers.adoc, named parameter schema *)
int_range     = "[" , int , ".." , int , "]" ;
enum_val      = alpha , { alpha | digit | "_" | "-" } ;
int           = "0" | nonzero_digit , { digit } ;
alpha         = lowercase_alpha | uppercase_alpha ;
lowercase_alpha = ? ASCII "a".."z" ? ;
uppercase_alpha = ? ASCII "A".."Z" ? ;
digit         = "0" | nonzero_digit ;
nonzero_digit = ? ASCII "1".."9" ? ;
----

`param_name` is bounded as registered in the link:../identifiers/01-general-rules-and-registry.adoc#id-param-name[Identifier Registry]. `param_type` mirrors the DSL `type_spec` (link:../workflow-dsl.adoc[Workflow DSL Specification]): lists use the single syntax `list<…>` (for example `paths:list<text>?`), enum values may contain upper case (`enum[FIX|SUPPRESS|ACCEPT]`), and there is no free-form object type: the only object-valued type is the named schema reference `schema[<schema_name>]` (<<named-parameter-schemas>>), also as a list element (`list<schema[<schema_name>]>`).

[#named-parameter-schemas]
==== Named Parameter Schemas

A parameter of type `schema[<schema_name>]` takes a JSON object as its value; the server validates it against the closed JSON Schema (`additionalProperties: false` at every object level) registered under `<schema_name>`, in the same in-process validation as every other parameter (link:../workflow-dsl/05-primitives.adoc#independent-transition-validation[Workflow DSL Specification, Independent Server-Side Transition & Parameter Validation], step `P`). A violation is rejected with `invalid_link_args`, and `rejected.detail` names the parameter and the JSON pointer of the offending member. `schema_name` follows the link:../identifiers/01-general-rules-and-registry.adoc#id-schema-name[Identifier Registry, named parameter schema] grammar. Named schemas are compiled into the binary beside the workflow definitions and are closed: a new name, or a change of a registered schema, ships only with a workflow version. A `schema[…]` type naming an unregistered schema fails DSL validation (Rule 1, link:../workflow-dsl/04-ast-node-model.adoc#static-verification-rules[Workflow DSL Specification, Static Verification Rules]). A named schema describes only model-supplied members; server-owned fields are never part of it, and a payload carrying one is rejected by `additionalProperties: false`.

[cols="1,3,2"]
|===
|`schema_name` |Content |Used by

|`decision-envelope`
|The model-supplied part of a decision (link:../model-work/06-envelopes-questions-deadlines.adoc#decision-structure[Model Work Specification, The Decision Structure]), without the server-owned `question_id`, revision, class, origin, and source entity: `title`, `header`, `description`, its `evidence[]` (`pm://` URIs of files, diffs, findings, and records), `blocks` (`plan`, `task`, `nothing`), `reversibility` (`reversible`, `costly`, `irreversible`), the optional `revisits` (the `decision_id` of the standing decision it reopens), and `parts[]` (one to six), each of the schema `question-envelope`
|`ask` and `ask:TASK-NNN` (`decision:schema[decision-envelope]`); the optional `decision:schema[decision-envelope]?` parameter of the `submit` link of a refine or outline task entity

|`question-envelope`
|One part of a decision: the optional `part_key` (named by another part's dependency), its `question_text`, `decision_kind`, `answer_type` (`one`, `several`, `value`) with the `value_schema` of a value, `options` as objects `{branch_key, label, description, consequences, preview?}` (the description states the option's trade-off), the optional `depends_on` (options of another part), its `recommendation` `{branch_key, confidence, rationale}`, never part of an option's label, and whether own words, a note, and a delegation are allowed (`own_words`, `note`, `delegation`); definition in link:../model-work/06-envelopes-questions-deadlines.adoc#question-envelope-schema[Model Work Specification, The Model-Supplied Schema]
|The `parts[]` of `decision-envelope`

|`intent-record`
|The intent record of a plan: `why`, `goal`, `criteria` (`AC-<n>` in EARS form with `kind` and `verified_by`), `current_behaviour`, `non_goals`, `constraints`, `decisions` (with `decider`), `assumptions`, `open_questions`, `deferred`, `source_claims`; definition in link:../store-schemas/06-task-and-references.adoc#intent-record-store[Store Schemas Specification, Intent Record]
|`submit:refine` and the light `submit:outline` (`intent:schema[intent-record]`), and the re-planning action that changes intent

|`outline-record`
|The solution outline of a plan: `summary`, `overview`, `scope_estimate`, and its `deliverables` with their fields (`number`, `title`, `intent_gloss`, `change_type`, `execution_mode`, `domain`, `module`, `depends`, `design_notes`, `profiles`, `affected_files` with intents, `change_per_file`, `verification`, `satisfies`, `added_dependencies` with justification, `interfaces`, `key_links`); definition in link:../store-schemas/06-task-and-references.adoc#outline-record-store[Store Schemas Specification, Outline Record]
|`submit:outline` (`outline:schema[outline-record]`), deep and light

|`epic-intent`
|The intent of an epic: `destination`, `done_when` (three to six checks), `non_goals`, `not_yet_specified`; definition in link:../store-schemas/04-epic-and-change-ledger.adoc#epic-header[Store Schemas Specification, Epic Header]
|`submit intent` of the `decompose` entity (`intent:schema[epic-intent]`)

|`question-answer`
|The operator's answer to one decision: the `revision` it answers and per part the chosen `branch_key` values or the `value`, the operator's own words, and a note, or for the whole decision `none_fits` (where offered) or `later`; the channel and device are taken from the request, never from the body; definition in link:../model-work/06-envelopes-questions-deadlines.adoc#decision-structure[Model Work Specification, The Decision Structure]
|The body of the answer endpoint of the local API, from either client (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]); never a model-facing link

|`vote-answer`
|One listed role's vote on one part of an adjudicated decision: `question_id`, `choice` (one `branch_key` for a part of the answer type `one`, a set of `branch_key` values for `several`, a value of the part's `value_schema` for `value`), `confidence` (integer `0..100`), and `rationale` (`10..500` characters), with the dissent from an option it rejects named in the rationale; definition in link:../model-work/10-decision-quorum.adoc#blind-input[Model Work Specification, Blind Input]
|`submit:vote` of a vote task (`answers:list<schema[vote-answer]>`, one item per question of the task's entity)

|`triage-groups`
|The triage of one gather firing: one entry per finding group `(domain, rule_id)` of the firing's batch with its disposition (`FIX`, `SUPPRESS`, `ACCEPT`), `confidence` (`0..100`, the group's decision confidence), `reply_text` (`1..4000` characters), optional `requirement_refs`, and `population` for `FIX`, plus per-finding exceptions (`finding_id` with its own disposition and reply); a finding withheld by the screener is never part of it; definition in link:../model-work/07-untrusted-text-screening.adoc#batched-triage[Model Work Specification, Batched Triage]
|`submit:triage-groups` of the triage task of a gather firing (`triage:schema[triage-groups]`)

|`simplify-proposal`
|One simplification the read-only simplify task proposes: `file` (a repository-relative path of the plan footprint), `change` (`1..4000` characters, what to change), `rationale` (`1..2000` characters); the server records it as a proposal record with its `proposal_id` (link:../identifiers/02-registry-stores-to-web.adoc#id-proposal-id[Identifier Registry, `proposal_id`]) and never applies it itself
|`submit:simplify` of the simplify task (`proposals:list<schema[simplify-proposal]>`)
|===

NOTE: Boolean parameters are prohibited in workflow transitions and operator links to preserve explicit closed-enum intent (e.g., `decision:enum[approve|reject]` rather than `approved:bool`). A trailing `?` marks an optional parameter (such as `paths:list<text>?` or `decision:schema[decision-envelope]?`).

[#decision-confidence-parameter]
==== Decision Confidence Parameter

Every closing link of a task entity whose state is a decision point of a role (link:../model-work/11-decision-records.adoc#decision-confidence[Model Work Specification, Decision Confidence of a Task]: `outline.classify-change-type`, `<phase>.qgate`, `replan.review`, `remediation-<class>.choose`) carries `confidence:int[0..100]` in its `free` list after its own parameters; the server records it in the decision record and refuses a submit without it `invalid_link_args`. The implicit `infeasible` link carries no `confidence`: it reports evidence, not a decision. A vote carries its confidence per question inside `schema[vote-answer]` instead, and a triage submit per finding group inside `schema[triage-groups]`. The actions of `replan.review` also carry `corrects:list<text>?` (at most ten `decision_id` values the revision departs from).

=== Direct In-Band Multi-Line Text Payloads (`PM-WF-2`, `PM-WF-6`)

Because `pm_do(scope_id, link, args)` is transported as a structured JSON-RPC 2.0 request over `stdio`, parameters of type `text[min..max]` accept arbitrary multi-line UTF-8 strings (including Markdown headings `#`, fenced code blocks, quotes, shell metacharacters, and Unicode) directly in `args`:

* *No Scratch-File Staging*: The model never invokes host `Write` or `Edit` tools on `.marshall/` files and never creates staging files of the kind `plan-marshall` needed (`.plan/temp/*-commit-msg.txt`, `work/ci-bodies/*.md`, `work/pending-tasks/*.json`, `work/lesson-body-*.md`). This is a model-facing rule, not a prevention: host file tools can still write `.marshall/`. The runtime detects such a write after the fact, on the next transition that reads a digest-protected store (the `integrity_breach` condition with kind `store_tampered`, which pauses the scope; link:../store-schemas.adoc[Store Schemas Specification], § Store Digest Verification); writes to files outside the digest-protected set are not detected.
* *Single-Turn Atomic Validation & Persistence*: When the model follows a `submit` link such as `commit` (`message:text[1..2000]`), `submit:outline` (`outline:schema[outline-record]`), the closing `submit` (`body:text[1..32768]`) of the `pr-body` entity, or `retitle` (`pr_title:text[1..72]`), the server validates both the parameter bounds and the domain content grammar in-process before persisting the target store or streaming the payload to a child tool via `stdin` (`PM-EXEC-5`).
* *Self-Correcting Validation Feedback*: If a submitted multi-line payload violates a structural rule (for example, an `outline` missing a `(read|write-new|write-replace|write-conditional|delete)` file-intent suffix, or a `message` violating Conventional Commits syntax), the server leaves the state unmutated and returns `rejected.reason = "invalid_link_args"` with exact line-level `detail` alongside the current TOON representation so the model can resubmit immediately in the next turn. `rejected.detail` names the offending parameter or token, the expected shape (the schema fragment), and one corrected example.
