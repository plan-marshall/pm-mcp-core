_Implementation watch: link:../../implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-1[PM-WATCH-HYP-1]_

Every representation is serialized as a top-level TOON object with a fixed canonical field ordering. The server drives every plan and epic itself, so a representation offers links only where a model acts (`PM-WF-1`).

[#representation-kinds]
=== Representation Kinds
_Implementation watch: link:../../implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-9[PM-WATCH-HYP-9]_

[cols="1,2,3"]
|===
|Kind |Addressed as |Links

|Task entity
|`scope: entity` with the `plan_id` or `epic_id` of its scope (neither for a task of the workspace scope or of the machine scope, which the worker addresses with `plan_id: "NO_PLAN"`) and the `entity` of the task (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]). It is served only to the worker whose generation holds the task's lease.
|While the task is offered, only `ack`. After the acknowledgement, the links of the entity unit of the task's kind, the `infeasible` link (evidence required) on every task entity except the consultation entity (link:../model-work/05-consultation.adoc#consult-serving[Model Work Specification, Serving the Consultation]), the `ask` link where its state declares one, the `request_waiver` link of a remediation decision for a waivable gate, and one `consult:<role>` link per `consult role` clause of its state (<<question-waiver-and-exit-links>>).

|View
|`scope: plan` or `scope: epic`, read by a worker of the plan or epic as the resource `pm://plan/{plan_id}/state` or `pm://epic/{epic_id}/state`; the engine moves the scope.
|None: `links: []`. A view never offers a transition of the scope. The operator's clients read the scope over the local API in the operator representation (<<operator-representation>>), never as a view.
|===

The representation of a task entity is the result of every `pm_do` on it, so each followed link returns the next representation of the entity it addressed. A worker addresses only the task entities leased to its generation (link:../workflow-dsl/05-primitives.adoc#independent-transition-validation[Workflow DSL Specification, Transition Validation], step 2).

[#canonical-top-level-fields]
=== Canonical Top-Level Fields
_Implementation watch: link:../../implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-2[PM-WATCH-HYP-2], link:../../implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-3[PM-WATCH-HYP-3]_

[cols="1,1,1,3"]
|===
|Field |Presence |Type |Normative Definition

|`scope`
|Required
|Closed enum
|`"plan"`, `"epic"`, `"workspace"` (the project's workspace scope, which hosts `project-setup`; a call addresses it with `plan_id: "NO_PLAN"`, link:../identifiers/01-general-rules-and-registry.adoc#id-no-plan[Identifier Registry, `NO_PLAN`], never with a `scope` input), `"machine"` (the machine's one scope, which hosts its onboarding, link:../workflow-dsl/01-grammar.adoc#machine-scope[Workflow DSL Specification, Machine Scope]), or `"entity"` (a task entity, <<representation-kinds>>).

|`plan_id` / `epic_id`
|Required (one of), except for `scope: workspace`, `scope: machine`, and a task entity of the workspace or machine scope
|String
|The addressed plan identifier (`plan_id`) or epic identifier (`epic_id`); a task entity carries the identifier of the scope its task belongs to. A `workspace` or `machine` representation and a task entity of the workspace or machine scope carry neither (not even the `NO_PLAN` sentinel that addresses them): the absence tells the worker to address the scope with `plan_id: "NO_PLAN"`. Their scope is the one of the worker's job record.

|`entity`
|Conditional
|String
|Present iff `scope == "entity"`: the entity a task works on (for example `envelope-2` or `enrich-http`), the task's `queue_task_id` where its state names no entity of its own, or, for a task of a start's entry (the screening of a stored source), the `entry_id` of the entry (for example `ent-3f9a2c41`).

|`state`
|Required
|Dotted enum
|Closed-enum state name (`<phase>.<step>[.<substate>]`; every state is catalogued in the link:../state-catalogue.adoc[State Catalogue]). In a view, the scope's current state (a `job llm` state also while its tasks run, for example `refine.analyze`; while a sub-workflow is active, the active sub-workflow state, for example `git.compose-message`). For a task entity, the state of the task: `task.offered` before the acknowledgement, afterwards the state of the entity unit of its kind (for example `entity.active` or `envelope.task.active`). Never a boolean.

|`condition`
|Conditional
|Closed enum
|Present iff the scope's `pending_condition` is set (link:../store-schemas.adoc[Store Schemas Specification]): the condition kind (`footprint_violation`, `job_incomplete`, `config_drift`, `guard_indeterminate`, `precondition_unmet`, `integrity_breach`; link:../state-catalogue/01-conventions-generic-conditions.adoc#state-catalogue-conditions[State Catalogue, Conditions]). `state` stays the current state id and `facts` carry the condition (link:../workflow-dsl/04-ast-node-model.adoc#condition-overlays[Workflow DSL Specification, Condition Overlays]). The self-remedy is server logic (a server retry, or a task of the role whose work raised the condition), so a view offers no link for it; a condition that needs the operator is a hold, shown to the operator's clients with its acts (link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue Specification, Holds and Their Acts]), never to a model. Under `integrity_breach` a view renders `links: []`, no task of the scope is offered, and every `pm_do` on the scope is rejected with `integrity_paused` until the operator resolves the hold.

|`phase`
|Required
|Closed enum
|Lifecycle phase (`init`, `refine`, `outline`, `plan`, `execute`, `finalize`, `completed`, `aborted`, `epic`, `workspace`, or `machine`, mapped 1:1 to the persisted values of `status.json`; link:../identifiers/01-general-rules-and-registry.adoc#id-phase[Identifier Registry, `phase`]). A plan's phase is the phase sub-workflow on its call stack, also within a sub-workflow called inside the phase (link:../store-schemas/03-findings-and-review-records.adoc#phase-sub-workflows[Store Schemas Specification, Phases as Sub-Workflows]). A task entity carries the phase of the state that created its task.

|`summary`
|Required
|String
|Single-line human-readable status summary (`1..160` ASCII characters).

|`skill`
|Optional
|URI String
|URI of the vocabulary skill guiding model judgment in this state (`skill://pm/<path>/SKILL.md`; the DSL clause `skill pm/<path>` maps to `skill://pm/<path>/SKILL.md`). A task entity carries the `skill` of the state that created its task. Omitted in views and in purely deterministic states.

|`rejected`
|Optional
|Object
|Present only when the immediately preceding `pm_do` transition was rejected (`link`, closed-enum `reason`, and diagnostic `detail`; link:../../../../plan-marshall-documentation/doc/specification/mcp-tools.adoc[MCP Tools Specification], § Rejected Transition Representation). A condition the start re-checks when it creates the scope is no rejection of a model call: the entry returns to its ready state with the reason, shown to the operator's clients (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/01-core-workflow-tools.adoc#bootstrap-commit-recheck[MCP Tools Specification, Start Commit Re-Check]).

|`facts`
|Required
|Object
|Minimal key-value map of domain facts required to exercise judgment in `state`, restricted to fields with a declared operational purpose (<<model-facing-minimality>>). Large payloads are referenced via `pm://` resource URIs.

|`links`
|Required
|Tabular TOON array
|`links[N]{rel,link,form,free}:` listing every transition valid for the caller (<<representation-kinds>>). Empty (`links: []`, the official form of an empty array) in a view, in terminal states, and under the `integrity_breach` condition, whose only resolutions are operator acts.
|===

[#facts-content-rules]
=== Facts Content Rules
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-TOOL-5[PM-TOOL-5: Tool Schema Stability & Context Budget Discipline]_
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-14[PM-WATCH-JOB-14]_

_Implementation watch: link:../../../../plan-marshall-documentation/doc/implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-12[PM-WATCH-TOOL-12]_

The server renders `facts` under seven general rules. Rules 1 to 4 apply to every representation and every resource derived from the same stores; rules 5 to 7 apply to every representation, tool result, and error payload:

1. *Server-Derived Counts Name Their Population*: Every count in `facts` (deliverables, files, tasks, findings) is derived by the server from the structured store at render time, never copied from authored text, and names its population in the key (for example `files_realized`, `files_declared`, `files_declared_unrealized`), so realized and declared-but-unrealized members are never mixed in one number.
2. *Population-Checked Aggregates*: A server-aggregated count or coverage figure (findings, reviewed comments, tokens, examined modules) is computed together with its population size. A zero over a non-empty population that structurally cannot be zero, or a figure whose population cannot be read, is rendered `indeterminate`, never `0` or "clean".
3. *Closed-Vocabulary Rule*: Every closed enumeration that classifies observed or judged input (statuses, dispositions, buckets, verdicts, linkage) contains an explicit out-of-set member (`unknown`, `indeterminate`, `not_applicable`, or `out_of_scope`, as fits). No member doubles as a stand-in for an unclassifiable case, and a malformed input is classified differently from an absent one.
4. *Truncation Is Reported*: Any server-side clamp of text (pull-request body sections, comment bodies against a provider's size cap such as 65,536 characters) reports `truncated: true` with the original and the kept length and cuts at a sentence or line boundary; text is never cut mid-sentence silently. Where the full text is kept (a job log, a stored source, a record), a truncation in a model-facing result also names where it is read in full (`full: <resource URI>`, for example `pm://plan/{plan_id}/builds/{job_id}/log`); a clamp whose full text is not kept says `full: none`, so a reader never takes the kept part for the whole.
5. [[model-facing-minimality]]*Model-Facing Minimality*: A representation (its top-level fields and `facts`), a tool result (`pm_wait`, `pm_build`, `pm_lsp`, `pm_skills`, `pm_skill`, `pm_skill_file`), and an error payload (`rejected`, the `isError: true` envelope, JSON-RPC `error.data`) carry only information that changes what the model does next: the offered links and their parameters, the facts its judgement in the current state needs (for a decision, the evidence the decision rests on: the code at the commit, the log line, the standing decision, link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Envelopes, Questions & Deadlines]), the error it must correct, the identifiers it must pass back (`question_id`, `finding_id`, `entity`), and the one-line `summary`. A model never relays anything to the operator: the operator is never its reader. Everything else is recorded, never returned: the implementation variant that served an operation; derivation and provenance sources (`budget_derivation`, the `source` of a configuration value or a resolved limit, a build template's source); internal versions (`format_version`, `worktree_sha_version`, binary and relay versions) unless the model must act on them; confinement and sandbox details; lease and holder internals (`holder_instance`, the lease of a task, the worker's generation and job token, queue positions, attempt counts); digests and hashes the model makes no decision on (`worktree_sha`, `config_hash`, `input_digest`); calibration bases (`predicted_cost_basis`); timing internals (elapsed seconds, `derived_at`, `recorded_at`, job durations, learned-budget hygiene); retry bookkeeping; the internal job identifiers of a composite wait; the role configuration and launch contract of a worker (harness, model, effort, form, argument vector, prompt file, job token digest, model-slot lease) and its parsed usage and cost; screener verdicts beyond the `withheld` marker of a withheld item; tallies and populations that serve only metrics; and `audit_id`, except on the errors an operator must look up (`internal_fault`, `file_unreadable`). Such data goes to `audit.jsonl`, the metrics store, the job record, the queue task record, or the server log, and where the operator needs it, it is served to the operator's clients over the local API (the terminal client `pm-operator` and the web app, link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]), never pushed in a representation or tool result. Web listener, pairing, and paired-device details (listener, certificate fingerprint, `device_id`, device labels, the channel of an operator act), the supervisor state of a worker, holds, `needs_operator`, reports, and the `stalled` state of a plan are operator data only and never model-facing. When the model's judgement needs a count (for example the open blocking findings), the count is rendered and its population list is not; rules 1 and 2 name and check a population, they do not require rendering it. A build-time test (`ModelFacingFieldAuditTest`) walks every representation, tool-result, and error-payload record type and fails on any field that is not in the registry of model-facing fields, in which every entry declares its operational purpose (`link_parameter`, `pass_back`, `judgement`, or `error_correction`); a new model-facing field is a registry change with a stated purpose.
6. [[operator-command-relay]]*No Operator Relay*: No representation, tool result, or error payload carries an operator command or asks a model to relay anything to the operator; there is no `facts.operator_command`. What the next step needs from the operator (an integrity pause, a waiver request, a condition that needs a setting, a grant, an enrolment, or a credential) is an operator wait or a hold of the scope, served to the operator's clients with its acts as operator links (<<operator-links>>; link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue Specification, Holds and Their Acts]); a task entity shows at most that its scope waits, and a worker never answers, waives, or confirms for the operator (`PM-WF-12`, `PM-SEC-3`).
7. [[options-defined-once]]*Options Are Defined Once, in the Representation*: Where a judgment chooses among options (the remedy links of a remediation decision, the dispositions of a triage), the representation that offers the choice states each offered option's definition exactly once, as `facts.options[N]{option,definition}` keyed by the link identifier or the enum value it defines, rendered from the one compiled definition of that option. Only offered options are listed. The options of a decision are defined by the decision itself, not compiled: they are stated once, with the part they belong to, in the operator representation of the decision (link:../model-work/06-envelopes-questions-deadlines.adoc#decision-structure[Model Work Specification, The Decision Structure]) and, for a worker that continues after it, in `facts.answers` (<<answers-facts>>), never in `facts.options`. A role skill refers to the options by name and never redefines them, because a model follows the literal definition it reads over a differing one elsewhere.

[#call-path-breadcrumb]
==== Call-Path Breadcrumb (`facts.call_path`)

While a sub-workflow is active (a `call` has made the sub-workflow's first state current, link:../workflow-dsl/06-reusable-sub-workflows.adoc#_call_stack_execution_persistence_semantics[Workflow DSL Specification, Call-Stack Execution]), a view carries `facts.call_path`, the call-site state ids of the scope's call stack from the root frame outward (for example `call_path[2]: plan.finalize, finalize.push-barrier`); it is absent at the root frame. A task entity never carries it: the task's own `skill` and `facts` frame its one judgment. The operator representation names the same path as its state's `node_id` (<<operator-representation>>).

[#answers-facts]
==== Answers to Earlier Questions (`facts.answers`)

A task that continues after its question (link:../model-work/06-envelopes-questions-deadlines.adoc#continuation[Model Work Specification, Continuing after a Question]) receives its answer, and a task that continues the work of a task that ended `asked` may be served by another generation, harness, or model, which never saw the question. Both therefore carry every closed question they continue from as `answers[N]{question_id,plan_task_id,question_text,branch_key,label,text,kind}`, one item per answered part of the decision: a continued task its own question, the task of `<state>` re-entered from `<state>.asked` the questions its state's earlier tasks asked in the same entry of the state, the envelope task after `execute.task-question` the questions of its plan tasks. `branch_key` and `label` are the chosen option (for a part that takes several, the keys joined by `+`; for a value, `value`; for words that fit no option, `own`), `text` the operator's own words and note, quoted as data and never an instruction, `plan_task_id` is set for class `task` only, and `kind` is how the answer was taken (`chosen`, `interpreted`, `own_option`, `delegated`, or `none_fits`; `delegated` where the operator left the choice to the asking role and its recommendation was taken, as the part allowed it). Every item is of a question closed `answered`. Nothing is ever answered by default. The answer's channel, the answering device, the interpretation of own words, and a quorum's votes are recorded, never rendered (link:../model-work/06-envelopes-questions-deadlines.adoc#answer-in-next-task[Model Work Specification, The Answer in the Next Task]).

[#remediation-evidence-facts]
==== Remediation Evidence (`facts.failures`)

The decision task of a remediation policy unit (`remediation-<class>.choose`, link:../workflow-dsl/08-remediation-units.adoc#remediation-units[Workflow DSL Specification, Remediation Policy Units]) renders the server-gathered failure envelopes as `failures[N]{failure_id,class,kind,file,line,message,excerpt_uri}`, the budgets left per offered remedy, and the definitions of the offered remedies (rule 7). `excerpt_uri` points at an untrusted evidence resource (`pm://plan/{plan_id}/evidence/{evidence_id}`, link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/03-resource-uris.adoc[MCP Tools Specification, Resource URI Surface]); log text is never inlined beyond `message`. The envelope's `source` and `fingerprint` (class, kind, file, normalized message), the provider run and job ids, log URLs, and the provider variant are recorded in the evidence record and the job record, never rendered: the server, not the model, compares fingerprints (<<model-facing-minimality>>). A failure the operator cannot waive carries `waivable: false`.

=== Canonical Representation Examples

The decision task of `remediation.ci-failure` after its acknowledgement, as its `triage-ci` worker reads it; the remedies the call site binds and the budgets leave are its links, each defined once in `facts.options`:

----

plan_id: plan-2026-042
entity: qt-5d0e7a1c9b3f2468
state: entity.active
phase: finalize
summary: "1 required CI check failed at HEAD, choose the remedy"
skill: "skill://pm/finalize/ci-triage/SKILL.md"
facts:
  failures[1]{failure_id,class,kind,file,line,message,excerpt_uri}:
    FL-7,ci,test,src/test/java/HeaderParserTest.java,42,"expected null but was empty","pm://plan/plan-2026-042/evidence/EV-3"
  fix_budget_left: 3

  retry_budget_left: 2
links[4]{rel,link,form,free}:

[#link-forms]
== The Two Normative Link Forms
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-2[PM-WF-2: Closed Link Relation Grammar & Link Forms]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-8[PM-WF-8: Asynchronous Job Links & Wait Transitions]_

Every row in `links[N]{rel,link,form,free}:` belongs to one of two closed link forms (`submit`, `noop`). The `form` column defines the interaction mechanics expected from the caller. Waiting on a job and cancelling it are engine events, never links: a job's completion moves its state, and a view shows the job's progress (`PM-WF-8`). The only waits a model holds are a worker's `pm_wait` (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/01-core-workflow-tools.adoc[MCP Tools Specification, Core Workflow Tools]) and a running `pm_build`. No model-facing form requests an operator decision: what needs the operator is an operator wait whose operator links are endpoints of the local API (<<operator-links>>), and the operator's other acts (waivers, pause and start, cancel and abandon, the holds' acts) are endpoints of the same API. No form starts a model: every model step is a task of a role (<<model-job-states>>).

[cols="1,2,2,3"]
|===
|Link Form |Target Tool |`free` Column |Execution Semantics

|`submit`
|`pm_do(scope, link, args)`
|Non-empty typed parameter list (e.g., `"outline:text[1..65536]"`, `"disposition:enum[FIX\|SUPPRESS\|ACCEPT],reply_text:text[1..4000]"`)
|Submits model judgment artifacts to the server from a worker for its leased task entity. The server validates `args` against the link's closed schema before executing the backing primitive.

|`noop`
|`pm_do(scope, link, {})`
|`""` (empty)
|Triggers a deterministic server-side transition that requires zero free judgment parameters from the model (for example the task acknowledgement `ack`).
|===

[#question-waiver-and-exit-links]
=== Task, Question & Waiver-Request Links
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-12[PM-WF-12: Question Records vs Operator Overrides]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-18[PM-WF-18: Question Recommendation Score & Decision Quorum]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-4[PM-WORK-4: Consultation through the Server]_

_Implementation watch: link:../../implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-7[PM-WATCH-HYP-7]_

These links are ordinary `submit` or `noop` links; their relation and form satisfy the closed relation table (xref:02-link-grammar.adoc#_closed_link_relations_rel[Closed Link Relations (`rel`)]):

[cols="2,1,1,5"]
|===
|Link |`rel` |`form` |Semantics

|`ack`
|`next`
|`noop`
|The only link of an offered task entity (`task.offered`), and of a task entity that carries the answer to the question its worker held or resumed for (link:../model-work/06-envelopes-questions-deadlines.adoc#answer-acknowledgement[Model Work Specification, Answer Acknowledgement]: the worker received the answer and continues). The worker's explicit acknowledgement of the offer, within its host's acknowledgement deadline; it returns the task entity in the first state of its entity unit (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]).

|`ask` (`decision:schema[decision-envelope]`)
|`submit`
|`submit`
|Offered on a task entity only by states that declare it. Creates a server-owned question record (`origin: model`) from the model-supplied envelope (xref:02-link-grammar.adoc#named-parameter-schemas[Named Parameter Schemas]). Where the task continues, its representation moves to `awaiting_answer`, whose only next step is `pm_wait` (hold), or tells the worker to end (resume), and the answer returns to the same task in `facts.answers` (link:../model-work/06-envelopes-questions-deadlines.adoc#continuation[Model Work Specification, Continuing after a Question]); otherwise it ends the task with the outcome `asked`, the state waits on the record in its question state and offers a new task with the answer in its `facts` (link:../workflow-dsl/02-units-jobs-decisions.adoc#question-states[Workflow DSL Specification, Question States]). The question becomes a decision of the scope, delivered to the operator's clients as an operator wait (link:../model-work/06-envelopes-questions-deadlines.adoc#decision-structure[Model Work Specification, The Decision Structure]). Server-raised questions (init classifiers, the outline review where the plan's asking axis asks it) are created by their primitive, never through `ask`.

|`ask:<task_id>` (`decision:schema[decision-envelope]`)
|`submit`
|`submit`
|The task-question link of a task envelope entity (`envelope.task.active`). Records the question for the plan task. Where the envelope task continues, it rests in `envelope.task.awaiting_answer` and returns to the same plan task with the answer; otherwise it ends the envelope task (`yield_reason: question`, server-recorded), and the envelope's remaining plan tasks, the asking one included, go to the next envelope task, which receives the answer in `facts`. Only a held continuation keeps a worker waiting, within its hold limit.

|`infeasible` (`evidence:text[1..2000]`)
|`submit`
|`submit`
|Implicit link of every task entity except the consultation entity, after the acknowledgement (link:../model-work/05-consultation.adoc#consult-serving[Model Work Specification, Serving the Consultation]). Ends the task with the outcome `infeasible` and its evidence (required); the calling state routes the outcome (link:../model-work/02-task-protocol.adoc#task-outcomes[Model Work Specification, Closed Task Outcomes]). It carries no `confidence` (xref:02-link-grammar.adoc#decision-confidence-parameter[Decision Confidence Parameter]).

|`consult:<role>` (`question:text[1..4000]`)
|`consult`
|`submit`
|One per `consult role <role>` clause of the task's state, and no other (link:../workflow-dsl/01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification, Grammar]). Submits a question to a task of the named role and moves the asking task to `consulting`; the answer arrives as the answer to the worker's next `pm_wait`, and the task's final submit must refer to it. A consulted task offers no `consult` link of its own (link:../model-work/05-consultation.adoc[Model Work Specification, Consultation]).

|`request_waiver` (`rationale:text[1..2000]`)
|`escalate`
|`submit`

Files a waiver request (link:../store-schemas/14-plan-instance-waivers-questions.adoc#waiver-request-record[Store Schemas Specification, Waiver Request Record]) and ends the task; the unit then rests in an operator wait without a time limit, which the operator ends by `waive` or `decline` in either client (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]). No model ends a plan or an epic, and no model leaves a sub-workflow early: a task ends only in its closed outcomes `submitted`, `asked`, `infeasible`, and `lost` (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]). A scope ends through `plan.aborted` or `epic.aborted` only by an operator act (cancel, abandon, the abort that resolves an integrity pause, link:../state-catalogue/04-plan-finalize-terminal.adoc#plan-end[State Catalogue Specification, Cancelling and Abandoning]), the release of its project, or `delete-plan`; the implicit `step_out` of a sub-workflow (relation `abort`) is an operator link of an operator wait (<<operator-links>>).

[#model-job-states]
=== Task States (`job llm`)

A state that needs a model (refine analysis, outline authoring, the Q-Gate, task envelopes, triage, remediation decisions, the screener, and every other task site of link:../model-work.adoc[Model Work Specification]) is a task state (DSL `job llm <entity_kind> role <role> [each <primitive_id>]`, link:../workflow-dsl/02-units-jobs-decisions.adoc#model-job-states[Workflow DSL Specification, Task States]). Entering it creates one queue task per entity for the named role; a worker of that role receives the task as the answer to its `pm_wait` and works on the task entity. The plan representation stays a view: it carries `state`, `summary`, and `facts.task_status` (the furthest task protocol state its tasks reached: `queued`, `offered`, `executing`, or `consulting`), and never a launch instruction, a link, or anything of the worker's configuration (<<model-facing-minimality>>).

* *Completion Is the Awaited Event*: When every task of the state has ended, the server runs the return-evaluation primitive of the entity kind over the persisted records the tasks submitted and takes the transition of its closed outcome. A worker's own final output never carries a deliverable: deliverables reach the server only through `submit` links.
* *The Worker's Connection*: A worker reaches PM-MCP only through its job relay (`pm-mcp serve --job`) with its job-bound capability and generation (link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]); its representations follow this format with the links of its leased task entity, and a link that would start a model is never offered to it (single-level leaf rule, `PM-WF-5`). The skills and the contract of an offered task are rendered from the same link and schema definitions as its representations, so one definition drives both.
* *Missing Submission*: When a worker ends or is fenced without the task's required submission, the worker's attempt ends; the server offers the task again within the self-remedy budget of the state, and only when it is spent does the task close `lost` and the state take its conservative fallback (link:../workflow-dsl/02-units-jobs-decisions.adoc#model-job-states[Workflow DSL Specification, Task States]). No link resumes a task. A call that carries the token of an ended worker is refused `job_ended`, a call of a fenced generation `generation_fenced`.

[#operator-representation]
== Operator Representation
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-ARCH-11[PM-ARCH-11: The Operator's Two Clients & Their Contract]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-20[PM-WF-20: Waiting for the Operator]_

The operator's two clients read every state and resource over the local API (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]) in a representation of their own, never in a model-facing one: JSON (or TOON where a client asks for it), with a closed schema per resource in `pm-api`. Both clients receive the same representation and render it each as its design says; neither reads a store, a ledger, or a model-facing representation. Model-facing minimality does not apply to it; its own rule is that it carries what a client shows and what its acts need, and never a secret.

* *State*: the representation of a scope's current state carries `scope` (`kind`: `plan`, `epic`, `workspace`, `machine`, or `entry`; `id`; `project_id` with its `display_name`, absent for the machine), `state` (`state_id`, `node_id`, the path of state ids from the scope's unit, the state's kind, among them `operator_wait`, and the `level` it writes where it writes configuration: `machine`, `project`, or `plan`), `progress` where the unit counts its steps (`done`, `of`), `title` and `texts` (<<runtime-texts>>), `facts` (typed values the state shows, each a value, a message key with its arguments, or verbatim text), `proposal` (the values preselected for the operator, each with its origin), `items` (the rows of a list the state shows, such as the check lines of a probe or the sources of an entry, each with its own `id`, facts, and links), `holds` and `needs_operator` where the scope has them, `revision` (the revision of the state's decision or setting that an act must name), and `links`, the operator links (<<operator-links>>).
* *Resources*: every other resource (the overview, a project, a plan's process, an epic, ended work, reports, the system view) is a JSON object of its schema, whose references to other resources are links with a relation (`self`, `project`, `epic`, `plan`, `process`, `activity`, `detail`, `next`, `prev`) and an `href` of the local API, so a client leads from one to another in one step.
* *Identifiers*: identifiers, state ids, link ids, store keys, and option keys are the same for both clients and in every language (link:../../../../plan-marshall-documentation/doc/specification/module-structure.adoc#i18n[Module Structure Specification, Languages and Internationalisation]).

[#operator-links]
=== Operator Links

An operator link is an act the state offers the operator: an object `{id, rel, method, href, params, preselected, confirm}`.

* `id` follows the link identifier grammar (link:../identifiers/01-general-rules-and-registry.adoc#id-link-id[Identifier Registry, Link Identifier]) and is unique within the state (for example `yes`, `yes_remember`, `no`, `answer`, `waive`, `decline`, `step_out`, `accept_edit`, `cancel`, `retry`); `rel` is one of the closed relations of link:02-link-grammar.adoc#_closed_link_relations_rel[Closed Link Relations] (`step_out`, the early exit of a sub-workflow, has `abort`). A client and a mock scenario key a link by its `id`, never by its relation, which several links share.
* `method` and `href` are the local API request that takes the act (`POST /api/v1/entries/ent-3f9a2c41/links/yes`, `POST /api/v1/plans/plan-2026-042/decisions/Q-007/answer`); `params` is the closed schema of its body, in the free parameter grammar of link:02-link-grammar.adoc#_free_parameter_descriptor_grammar_free_column[Free Parameter Descriptor Grammar], with the named schemas of link:02-link-grammar.adoc#named-parameter-schemas[Named Parameter Schemas]; `preselected` marks the link the state proposes; `confirm` names the message key of a confirmation the client shows before it follows the link, where the state asks for one (an act that ends work names what it ends).
* Following a link is an operator act: validated against the state's current revision under the scope lock, audited with its channel and device, and answered with the new state; a link of a state left meanwhile is refused `act_not_available`, an act against an older revision `conflict`, and the first valid act of the two clients wins. An operator link never reaches a worker, and no model-facing link reaches a client of the operator.

[#runtime-texts]
=== Texts of the Runtime

Every text the runtime gives a client to show is a *message key* with its arguments (link:../identifiers/02-registry-stores-to-web.adoc#id-message-key[Identifier Registry, Message Key]), rendered by the client from the message catalogue of its interface language (link:../../../../plan-marshall-documentation/doc/specification/module-structure.adoc#i18n[Module Structure Specification, Languages and Internationalisation]): `{"key": "check.login.missing", "args": {"harness": "claude"}}`. A state's title, a check's cause and fix, a reason, an error's detail, and a report's subject and body are message keys. Text that does not come from the runtime is never a key and is carried *verbatim*, marked with its source: `{"verbatim": "…", "source": "provider" | "harness" | "model" | "operator" | "repository"}`, for example a provider's answer, a harness's error text, the content of a question or an option, a title drawn from a request, or the reason the operator wrote. A client shows verbatim text as plain text, never as markup or a link it follows; text of a model, a provider, a harness, or a repository is untrusted (`PM-SEC-1`). An argument of a message key is a value or such a verbatim object, never a key of its own.
