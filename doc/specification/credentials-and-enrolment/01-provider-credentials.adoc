*Proven Write Credential for Upstream Filing*: A credential that an operator-confirmed filing job would use to write to a vendor tracker (the lesson Upstream Release, link:../store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Lesson Record]) is proven by a write-permission probe on the target tracker before the filing job is offered; without a passed probe the release action only renders the issue body for the operator to file.

=== Two-Lane Provider Architecture

External provider integrations are strictly partitioned into two authentication lanes. The provider operations of both lanes are contracts of the provider modules `pm-provider-git` and `pm-provider-ci` and the findings and code-analysis contracts of `pm-core`, implemented by `pm-provider-github`, `pm-provider-gitlab`, `pm-provider-forgejo`, and `pm-provider-sonar` (link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-IMPL-1[PM-IMPL-1]; Forgejo: link:../../../../plan-marshall-documentation/doc/specification/module-structure.adoc#forgejo[Module Structure Specification, Codeberg and Forgejo]). For the integrations `git`, `github`, and `gitlab` each contract has two implementations, the *native variant* (in process) and the *CLI variant* (jobs of the enrolled `git`, `gh`, `glab`); `forgejo` and `sonar` have only the native variant. The lane of an integration follows its variant:

1. *System Lane (CLI variant of `git`, `github`, `gitlab`)*: Executed as verified subprocess jobs (`PM-EXEC-5`) that inherit the developer's existing CLI authentication (`~/.gitconfig`, credential helpers, SSH agent, `gh auth`, `glab auth`), by design (<<cli-variant-credentials>>). `PM-MCP` never reads, extracts, or stores CLI-lane tokens and never injects a Token Lane secret into such a job.
2. *Token Lane (SonarQube/SonarCloud, Forgejo, authenticated upstream MCP servers, and the native variant of the git HTTPS transport, GitHub, and GitLab)*: Executed directly by the runtime (`pm-mcpd`) in process: REST and GraphQL through `de.cuioss:cui-http`, git transport through JGit over HTTPS. Tokens are resolved per request by credential key (`PM-CRED-1`) from the credential store the operator chose (<<credential-store-choice>>): `<project>/<credential_key>` (project-scoped override) -> `<credential_key>` (global fallback), and sent only to the origin of the entry's `url` and, for `github` and `gitlab`, the API origin derived from it (<<agent-credentials>>, `PM-CRED-5`). That `url` belongs to the operator-owned credential entry, and the credential key a project uses is an operator value too (the machine's provider defaults, or the project's `local-config.json`, link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Local Configuration]); no team file names a credential or decides where a token is sent. The native variant authenticates with the agent credential, never with the operator's ambient CLI login: for a GitHub App every write acts as the operator via the App (its user access token, <<user-access-token>>) and every read-only query as the App installation (<<agent-credentials>>).

*Variant selection*: The machine records per provider whether it is available, its default variant, and the credential key it uses (`providers` of `machine-config.json`, with the CLI tools enrolled for the machine in `host-tools.json`; link:../store-schemas/12-machine-stores.adoc#provider-defaults[Store Schemas Specification, Machine Provider Defaults]). A project takes them unless its own setup sets them: its onboarding shows the integration variant and the credential of each provider with the machine's value as the proposal, and records a value for the project only when the operator changes it (link:../store-schemas/08-project-configuration-local.adoc#project-levels[Store Schemas Specification, Project Values over Machine Values]; link:../domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]). The CLI variant needs the integration's host tool enrolled for the machine or for the project; where the effective variant cannot serve the repository (the derived fact `git_native_capability`), the choice is an operator wait of the project's setup (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]), answered in either client, never by a model and never a decision of a plan; no git or provider operation runs before the variant is set. A project's own choice is stored in the operator's `local-config.json` (link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Local Configuration]), never in a team file, because it decides whose credentials act. One integration of a project uses exactly one variant for all its operations; different integrations may differ (for example the CLI variant of `git` with the native variant of `github`). The operator's ambient identity, with all of the operator's rights, therefore acts only where the operator chose the CLI variant with an enrolled tool, an operator act. No operation falls back from one variant to the other, and the variant changes only through an operator act that reports and audits the change. The variant that served an operation, the credential key and origin, and for the CLI variant `identity: operator_ambient` are written to the operation's audit record, never into a model-facing result (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

* *No refusal by credential kind*: Every listed credential kind is accepted on equal footing; neither the kind nor a missing expiry is refused or warned about in a workflow. Entering and verifying a credential determine the token kind from the provider and record it with the entry (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-credential-cli[Operator Credential Acts & Runtime Secret Redaction]).
* *Check visibility*: A credential that cannot read check runs (a GitHub fine-grained personal access token cannot call the Checks API) is detected up front by the derived network fact `checks_visible` (link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas Specification, Derived Facts]); `ci.checks` then reads what the credential can see (commit statuses, check suites) and reports `completeness: incomplete`, which never counts as a green check.
* *Installation tokens*: For a `github_app` entry the runtime signs an RS256 JWT with the JDK (`iat` back-dated and `exp` bounded by the GitHub App JWT validity window, link:../timeouts/03-retention-host-config.adoc#github-app-jwt-window[Timeouts & Budgets Specification]; `iss` the `client_id`) and mints an installation token for the read-only query classes, narrowed to the one repository (or, for a granted cross-repository read, to the granted repositories, <<cross-repository-reads>>) and to the read-only permission set of the operation class, through `POST /app/installations/{id}/access_tokens`; every write operation uses the user access token instead (<<user-access-token>>). The App needs at most the repository permissions `contents: write`, `pull_requests: write`, `checks: read`, `actions: read`, `statuses: read`, `issues: write`, and `metadata: read`; a comment on a pull request needs `pull_requests: write` (`issues: write` alone is refused for it), and `issues: write` serves issue comments only. Administrative permissions are never required, because repository administration (such as enabling a merge queue) stays with the operator.
* [[user-access-token]]*User access token (writes)*: A `github_app` entry also holds a user refresh token of the App, obtained once by the device flow when the operator enters the credential (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-credential-cli[Operator Credential Acts & Runtime Secret Redaction]; the App must have the device flow enabled). Every write operation (push, pull-request creation and edit, comments and review replies, review triggers, thread resolution, merge and merge-queue enqueue, branch delete) runs with the user access token, which acts as the operator via the App (shown by the provider as the operator's login "via" the App) with the intersection of the App's and the operator's permissions; so the pull requests and review triggers the server writes are user-authored, which review bots that skip bot-authored pull requests and bot triggers require (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#automatic-review[Phase Workflows Specification, Automatic Review]). The access token (valid 8 hours) is held in memory only, like an installation token (<<derived-tokens>>). Before it expires (link:../timeouts/03-retention-host-config.adoc#user-token-refresh-margin[Timeouts & Budgets Specification, User token refresh margin]) the runtime refreshes it with the refresh token and the `client_id`, without a client secret; the provider rotates both tokens on every refresh, revokes the old access token at once, and accepts each refresh token (valid about six months) once. The refresh is therefore atomic under `<PM_MCP_BASE>/locks/credentials.lock`: one refresh at a time per entry; the new refresh token is written to the recorded store and read back before the new access token is used, and every in-memory holder switches to the new access token in the same step. A refresh whose answer is lost, or a refused or expired refresh token, makes the entry `credential_check_failed`, held for the operator with the act that enters the credential again (a new device flow; link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue Specification, Holds and Their Acts]); there is no fallback to the installation token for a write. A personal access token credential (GitHub, GitLab, or Forgejo) authors as its own user and needs none of this. _Implementation watch: link:../../implementation-watch/credentials-and-enrolment.adoc#PM-WATCH-CLI-30[PM-WATCH-CLI-30], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-105[PM-WATCH-PHASE-105]_
* *Committer identity*: The committer of agent commits is the identity resolved from the agent credential through `ci.whoami` (a GitHub App: `<app-slug>[bot]` with the address `<id>+<app-slug>[bot]@users.noreply.github.com`; a token: the token's user), recorded as the operator-only derived fact `agent_identity`; without a Token Lane provider credential the committer is the fixed `plan-marshall-mcp` noreply identity. The author stays the operator (`commit_identity`, link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Local Configuration], proposed from the machine's `project_defaults.commit_identity` where set, else the global git identity). The identity appears in the operator's clients and the audit log, never in a model-facing representation.

[#derived-tokens]
=== Short-Lived Derived Tokens
_Implementation watch: link:../../implementation-watch/credentials-and-enrolment.adoc#PM-WATCH-CLI-2[PM-WATCH-CLI-2], link:../../implementation-watch/credentials-and-enrolment.adoc#PM-WATCH-CLI-5[PM-WATCH-CLI-5]_

A stored secret is read per request and never cached (`PM-CRED-5`). A token derived from it that expires by construction, a GitHub App installation token (valid one hour) or a GitHub App user access token (valid 8 hours, <<user-access-token>>), is the second named exception of `PM-CRED-5`:

* It is held in memory only, an installation token keyed by installation and permission set and reused until the derived token reuse margin before its expiry (link:../timeouts/03-retention-host-config.adoc#derived-token-reuse-margin[Timeouts & Budgets Specification]), then a new one is minted; a user access token keyed by its credential entry and refreshed at the user token refresh margin (link:../timeouts/03-retention-host-config.adoc#user-token-refresh-margin[Timeouts & Budgets Specification]). The user refresh token is the stored secret of that derivation: it is read only for a refresh and replaced in the store by its successor in the same refresh.
* It is registered with the redaction registry when minted (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-credential-cli[Operator Credential Acts & Runtime Secret Redaction]).
* It is never persisted, never exported to a subprocess environment or log, and never passed to the CLI variant.
* It is dropped when its credential entry is rotated, removed, or re-set, when a request with it fails with `auth_failed` (revocation), and when the runtime stops; a user access token is also replaced at once by its successor when it is refreshed.

[#cross-repository-reads]
=== Cross-Repository Reads & Issues
_Implementation watch: link:../../implementation-watch/credentials-and-enrolment.adoc#PM-WATCH-CLI-31[PM-WATCH-CLI-31]_

The CI provider contract (`pm-provider-ci`) has four read operations beyond the project's own repository, served by both variants and in the `ci` query operation class (link:../timeouts/01-job-budgets-and-waits.adoc#ci-query-budget[Timeouts & Budgets Specification]):

* `ci.org-repos`: the repositories of an organisation (GitHub, Forgejo) or group (GitLab);
* `ci.code-search`: a code search restricted to an organisation or group;
* `ci.repo-file`: one file of a repository outside the project, at a named ref;
* `ci.labels`: the label list of a repository.

Two issue operations serve the issue source of a start (link:../state-catalogue/09-bootstrap-and-lessons.adoc#issues[State Catalogue Specification, Issues by Number or URL]): `ci.issue-view` reads one issue by its URL (title and body as text, labels, milestone, assignees, state, and URL as structured fields), of the project's own repository or of another repository; `ci.issue-comment` posts a comment to an issue of the project's own repository only, and only while the team key `issues.write_back` enables it (link:../store-schemas/07-project-configuration.adoc[Store Schemas Specification, Project Configuration]).

Each read outside the project's own repository runs only under an operator grant that names its target: for a plan `pm-operator grant-access <plan_id> --org <owner> read` or `--repo <owner>/<name> read` (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-grant-access[operator-grant-access]), and for an issue named at a start the grant the source state asks for, once (for this start and the plan it creates) or for the project (every later read of that repository by the project's plans, until the operator withdraws it in the project's settings); `ci.labels` of the project's own repository needs none, and a public issue of another forge is read without a credential, every other with the credential of that forge. Without the grant the operation is refused with `grant_missing`: in a plan's step as the `precondition_unmet` condition, held for the operator with the grant as its act (link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue Specification, Holds and Their Acts]), like every cross-project access (`PM-SEC-2`). In the native variant a GitHub App reads with an installation token narrowed to `metadata: read` and `contents: read` on the granted repositories; a repository outside the App's installation is not visible to it. Every result carries `completeness`: `complete`, or `incomplete` with the bounds that cut it (`page_cap`, the server's compiled page bound; `provider_result_cap`, for example the provider's cap on search results or its `incomplete_results` flag; `not_visible`, repositories the credential cannot see, where the provider reports them). An `incomplete` result is never read as "absent": a consumer that needs the whole population treats it as unknown. A read that the forge refuses for its rate limit fails with the cause `rate_limited` and the instant the limit resets (`resets_at`, from the forge's answer) and is not retried by itself. File contents, issue texts, and search excerpts are external text and pass the level-1 validator before they reach a model (`PM-SEC-1`).

[#native-confinement]
=== Native Operation Confinement
_Implementation watch: link:../../implementation-watch/credentials-and-enrolment.adoc#PM-WATCH-CLI-6[PM-WATCH-CLI-6], link:../../implementation-watch/credentials-and-enrolment.adoc#PM-WATCH-CLI-9[PM-WATCH-CLI-9], link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-28[PM-WATCH-EXT-28]_

A native operation runs inside the runtime process: it has no argument vector, no environment, and no Landlock ruleset. What it can do is bounded by the following rules, each enforced in the provider modules:

* *Paths*: It writes only inside the enrolled project root and its linked worktrees; every path it derives, including the `gitdir` targets of worktree administration files, passes the `PM-SEC-2` checks.
* *Origin check*: HTTP requests go through `cui-http` with origin pinning. The git transport resolves the effective fetch and push URL of the remote with every `url.<base>.insteadOf`/`pushInsteadOf` rewrite and `remote.<name>.pushurl`, maps an SSH remote of a known provider host (`github.com`, `gitlab.com`, `codeberg.org`, and hosts whose `ci_provider` is established) to its HTTPS form without changing the configured remote, and requires `https` and an origin equal to the credential entry's origin. A mismatch refuses the operation with `remote_origin_mismatch`, appends a `security` record to `audit.jsonl`, and sends nothing; every other SSH remote is `capability_missing{reason: ssh_only_remote}`. Its connection factory refuses every other host, so a redirect cannot carry the credential elsewhere.
* *Configuration allowlist*: From the repository configuration and the user's global configuration it reads only content-shaping keys: `core.autocrlf`, `core.eol`, `core.safecrlf`, `core.excludesFile`, `core.ignoreCase`, `core.precomposeUnicode`, `remote.<name>.url|pushurl|fetch`, `url.<base>.insteadOf|pushInsteadOf`, `branch.<name>.*`, `init.defaultBranch`, and, for capability detection only, `core.hooksPath`, `filter.<driver>.*`, `lfs.*`, `submodule.*`, and `extensions.*`. Every other key is ignored, among them `credential.*`, `core.sshCommand`, `core.fsmonitor`, `http.*` proxy settings, and `include.*`/`includeIf.*` targets outside the repository. A proxy is an operator setting, never a repository value or an environment variable: the closed object `proxy` of `machine-config.json` (`https_proxy`, a URL without embedded credentials, and `no_proxy`, a list of hosts; link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration Store]), set as an operator configuration value and applied to every `cui-http` call and to the JGit transport of the native variant. Authenticated proxies are deferred (link:../../../../plan-marshall-documentation/doc/later-improvements.adoc#_l_8_authenticated_proxies[Later Improvements, L-8]).
* *No process execution*: A native operation never starts a process. JGit's process entry points (`FS.runInShell`, `FS.runHookIfPresent`, filter-driver execution) are served by a `pm-provider-git` subclass of JGit's `FS` that refuses with `capability_missing` instead of running anything, so no repository value can start a process in the runtime.
* *Selection criterion instead of fallback*: Repository hooks (non-sample files in `.git/hooks/`, `core.hooksPath`, `.husky/`, `lefthook.yml`, `.pre-commit-config.yaml`), required commit signing (`signed_commits_required`), filter drivers including LFS, submodules, SHA-256 object format, partial clone, sparse checkout, split index, and SSH-only remotes are detected by the derived fact `git_native_capability` (link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas Specification, Derived Facts]). An operation that needs a missing capability is refused with `capability_missing{reason}` naming the feature and the operator act that enrols the integration's host tool and selects the CLI variant; no operation falls back on its own. A new capability finding invalidates an effective native variant, and the project's setup requires the operator's act for that integration.

[#cli-variant-credentials]
=== Credentials of the CLI Variant
_Implementation watch: link:../../implementation-watch/credentials-and-enrolment.adoc#PM-WATCH-CLI-8[PM-WATCH-CLI-8]_

The CLI variant runs the operator's enrolled `git`, `gh`, or `glab` with the operator's ambient authentication, by design: it is the variant of a project whose operator chose it with an enrolled tool, it needs no credential held by `PM-MCP`, and it serves the operator's own setup (signing, SSH remotes, hooks, special hosts).

* *Operator choice, audited*: The choice of the integration variant (link:../domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]) shows on selection that the CLI variant of that integration acts with the operator's identity; every CLI job's audit record carries `identity: operator_ambient`.
* *No token injection*: An agent token is never passed to a CLI job, neither as `GH_TOKEN`, `GITHUB_TOKEN`, `GITLAB_TOKEN`, or another token variable, nor through a `GIT_ASKPASS` or `SSH_ASKPASS` helper, nor through a credential helper served by `PM-MCP`: every descendant of the job, including repository hooks, and every same-user process reading `/proc/<pid>/environ` could read it, which breaks `PM-CRED-5`.
* *Environment, write paths, `stdin`*: The job environment rows of CLI-variant `git` and `ci` jobs (configuration discovery, SSH agent socket, provider CLI configuration directories, non-interactive guards, committer variables), their additional write paths, and their `stdin` forms are specified in link:../job-runtime.adoc[Job Runtime Specification] (Job Environment; In-Memory `stdin` Streaming). `known_hosts` stays read-only: an unknown host key fails the job, it is never accepted.
* *Hooks and signing*: Repository hooks and signing programs run only here, started by `git` itself inside the CLI `git` job and therefore under that job's environment and Landlock confinement (`PM-SEC-5`).
* *No session bus*: A job never reaches the user's session bus (link:../job-runtime/02-confinement-and-environment.adoc#session-bus[Job Runtime Specification, Session Bus]), so on Linux a CLI job cannot use a login kept only in the Secret Service (the `libsecret` git credential helper, the keyring storage of `gh` or `glab`). The verification command of the integration (`gh auth status`, `glab auth status`, `git ls-remote`) then fails as a job, and the setup names the cause; the operator keeps that login in the tool's own file storage or an SSH agent, or selects the native variant.

[#os-keyring-backends]
=== Credential Stores
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CRED-3[PM-CRED-3: Permission-Guarded File Credential Store]_

Within the store the operator recorded (<<credential-store-choice>>; the recorded store and its move are implemented, link:../../../pm-runtime/doc/developer/runtime-credentials.adoc[Developer Guide § Credential Stores]), the project entry `<project>/<credential_key>` is resolved before the global entry `<credential_key>` (`PM-CRED-2`). `<project>` is the project's enrolment identifier (`PM-CRED-3`), never derived from a remote URL or a checkout path. [[keyring-service-name]]Every keyring entry of `PM-MCP`, Token Lane credentials and the enrolment integrity key alike, is stored under one *service name* (`PM-CRED-2`): `de.planmarshall.mcp` for the default `PM_MCP_BASE`, and `de.planmarshall.mcp/<instance_hash>` for any other, where `<instance_hash>` is the first 16 hex characters of the SHA-256 of the canonical absolute path of `<PM_MCP_BASE>` (`PM-DIST-5`), so two instances never share an entry. The stores are:

* *macOS Keychain (`os` on macOS)*: Invokes macOS Security framework APIs (`SecItemAdd`, `SecItemCopyMatching`, `SecItemUpdate`, `SecItemDelete`) directly via Java 25's Foreign Function & Memory (FFM) API (`java.lang.foreign.Linker`). Items are stored under the <<keyring-service-name,service name>> with account `<credential_key>` or `<project>/<credential_key>` and a trusted-application ACL restricting unprompted read access to the runtime binary `pm-mcpd`, the only process that reads or writes credentials (neither CLI binary touches the credential store); another reader raises the OS access dialog. The ACL identifies the binary by its code signature: `pm-mcpd` of a macOS release is signed with a Developer ID and notarised in the macOS release job, so the ACL holds the designated requirement of that signature (the team identifier) and an upgraded `pm-mcpd` reads the items of its predecessor without a prompt. A locally built `pm-mcpd` is ad-hoc signed and trusted by its code-directory hash, so every rebuild loses unprompted access to the items the previous build stored (the OS asks once per item). The items live in the login keychain; the data-protection keychain refuses a binary without an entitlement and is not used.
* *Linux Secret Service (`os` on Linux)*: Communicates with `org.freedesktop.secrets` over the user session D-Bus (`gnome-keyring` / `KWallet`) storing attributes `service=<service name>` (<<keyring-service-name>>), `credential_key=<credential_key>`, and optional `project=<project>`. It is available while the session bus is reachable and the default collection is unlocked; a locked collection is never prompted for. The Secret Service has no per-application access control: every process of the user that reaches the session bus can read an unlocked collection. Jobs therefore never reach the session bus (link:../job-runtime/02-confinement-and-environment.adoc#session-bus[Job Runtime Specification, Session Bus]); an unconfined process of the user, such as a coding agent the operator runs, can, which is an accepted residual risk (`PM-SEC-5`).
* *Permission-Guarded File Store (`file`)*: Secrets are stored in the `PM-MCP` credential file format (`format_version`, closed schema, written only by the runtime on the operator's entry of a secret, a store move, or the token refresh of a `github_app` entry, `PM-CRED-3`) at `<PM_MCP_BASE>/credentials/<credential_key>.json` and `<PM_MCP_BASE>/credentials/<project>/<credential_key>.json` (directory mode `0700`, file mode `0600`, see link:../filesystem-layout.adoc[Filesystem Layout Specification] and link:../store-schemas.adoc[Store Schemas Specification]).

*A credential a step cannot use*: If the recorded store is unavailable (`credential_store_unavailable`), if ownership or permission checks on a credential file fail (`credentials_file_insecure`), if the credential is missing (`credential_missing`), if a credential file was not written by the runtime in the current format (`credentials_file_invalid`), or if a resolved credential's check against its provider fails (the step's provider call, or `ci.whoami` where the step verifies the identity, answers that the credential is rejected, revoked, or lacks a required permission: `credential_check_failed`), the runtime holds only the step that needs that credential: the engine raises the `precondition_unmet` condition on the step's current state with `facts.reason` set to the cause, held for the operator as a hold whose acts set, replace, or move the credential (link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue Specification, Holds and Their Acts]; `PM-CRED-4`); its `retry` re-checks within the condition budget (link:../timeouts/01-job-budgets-and-waits.adoc#condition-budget[Timeouts & Budgets Specification, Condition Budget]), after which the phase's fallback is taken with the credential as the gap. The runtime itself keeps running; it exits with code `77` only for the causes of step 3 of the startup sequence (link:../runtime-lifecycle/01-startup-recovery-drain.adoc#_startup_sequence[Runtime Lifecycle Specification, Startup Sequence]).

* *No Legacy Credential Access*: The `CredentialStore` never reads `plan-marshall` credentials (its keyring entries, `~/.plan-marshall/credentials/`, `PLAN_MARSHALL_CREDENTIALS_DIR`, `PLAN_MARSHALL_HOME`), and no act imports them (`PM-MIG-2`). Credentials enter the `PM-MCP` stores only through the operator's entry of a secret (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-credential-cli[Operator Credential Acts & Runtime Secret Redaction]), each entry operator-owned, including its allowed `url`.

[#credential-store-choice]
=== Credential Store as an Operator Choice
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CRED-2[PM-CRED-2: Operator-Chosen Credential Store & Native Access]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CRED-3[PM-CRED-3: Permission-Guarded File Credential Store]_

The operator chooses once for the machine which store holds the Token Lane secrets (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-7[UC-ONB-7]). The recorded store, its writers, the refusal before the choice, the integrity key before the choice and its carry at the first recording, the refusal of every other store and the move with its resume are implemented (link:../../../pm-runtime/doc/developer/runtime-credentials.adoc[Developer Guide § Credential Stores], link:../../../pm-runtime/doc/developer/runtime-enrolment.adoc[Developer Guide § Integrity Key and Sidecars]); what remains is the part of the onboarding and the clients:

* *The setting*: `credentials.store` of `machine-config.json` (`os` or `file`; link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration Store]) is aspect-owned: the plain configuration endpoint refuses it (`aspect_owned`, xref:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#two-channels[Operator Choices in the Web App and the Terminal]).
* *What each store protects against*: The choice shows it: the macOS Keychain lets only `pm-mcpd` read without a prompt; the Linux Secret Service lets every process of the user read an unlocked collection; the file store lets every process of the user read its files (`0600`). The residual risks of `PM-SEC-5` stay as they are. Before the OS store is recorded, the aspect checks it on the consent `check_credential_store` (link:../store-schemas/12-machine-stores.adoc#consent[Store Schemas Specification, Consent Before Acting]).
* *One store, never another*: When the recorded OS store is unavailable at start or later (a locked collection, a session without the user's session bus), both clients report it with the cause, a step that needs a credential is held with `credential_store_unavailable` (<<os-keyring-backends>>), and a request that writes an entry is answered `423` (`credential_store_locked`).
* *The first recording*: Before a store is recorded the enrolment integrity key lives in the store the runtime finds (the OS store where one is available, else the key file). The first recording of the other store carries the key into it before `credentials.store` is written: the key is copied and read back, every HMAC sidecar is verified under the key read back, the store is switched in one write, and only then is the key deleted from the store it was found in. A sidecar that does not verify records nothing, and the key stays where it was found. Only the first recording writes `credentials.store` from the aspect: while a store is recorded, recording a different store is refused (`aspect_owned`), since a change of the recorded store is the move below, and recording the recorded store again changes nothing.
* [[credential-store-move]]*The move*: Changing the store, a move of every entry in either direction, is an operator act of the credential-store aspect or of `pm-operator credentials migrate os|file`. It runs under `locks/credentials.lock` from its record `state/credential-store-move.json` (link:../store-schemas/12-machine-stores.adoc#credential-store-move-record[Store Schemas Specification, Machine State Records]): every Token Lane entry is copied and read back, the integrity key last, every sidecar is verified under the key read back from the target, `credentials.store` is switched once, the old store is emptied, the move is audited and the record ends; the audit record is appended before the record ends, so a stop or a failing audit sink leaves the record and the next start finishes the move and appends it. A target that holds a Token Lane entry already is refused before the record is written (`credential_store_failed`, naming the store and the number of entries), since a secret never exists in two stores; nothing is written or deleted then. A failure before the switch leaves the old store recorded and untouched and removes the copies from the target; where a copy cannot be removed, or the recorded store cannot be read, the record stays and the next start resumes the move. While the record exists only the move records `credentials.store`, and the move records it only while its record exists. A move a stop cut is resumed at the next start from the record and the recorded store, as the record's schema states; a stop never deletes the only copy of an entry.

[#provider-verification]
=== Provider Verification
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CRED-1[PM-CRED-1: Dual-Lane Credential Separation (System vs Token Lane)]_

A provider is verified as a whole when the operator configures it for the machine and again on the operator's request (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-8[UC-ONB-8]):

* *The checks*: The providers aspect of the machine's onboarding runs, per selected provider and on the consent `verify_providers`, the checks of its kind, each reported as a check line: the origin is reachable; the credential authenticates (`ci.whoami`) and as whom; its permissions and its expiry; for the CLI variant the tool's version and that it is logged in as the same identity as the credential. A check line carries the check's name, `ok` or `failed`, a message key with its arguments, and the provider's or the tool's own answer verbatim where there is one.
* *A failed provider*: A provider whose checks fail is recorded only on the operator's word, and then as not available; it never serves a project in that state.
* *Again later*: The same verification runs from the machine settings on request (`pm-operator config providers --verify`) and after a credential is rotated or replaced there; it changes nothing unless a check fails. Its last result with its time is kept with the machine's provider defaults (link:../store-schemas/12-machine-stores.adoc#provider-defaults[Store Schemas Specification, Machine Provider Defaults]) and shown with each provider in both clients. Checks that need a repository (the permissions on it, check runs visible) stay in the project's setup (link:../domain-extensions/04-setup-state-machine.adoc#setup-verify-credentials[Domain Extensions Specification, Credential Verification]).
* `pm-operator credentials verify <credential_key>` checks one credential alone and records nothing of the provider (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-credential-cli[Operator Credential Acts & Runtime Secret Redaction]).
