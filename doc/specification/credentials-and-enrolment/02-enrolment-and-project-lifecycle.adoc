== Enrolment Integrity
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-5[PM-SEC-5: Subprocess Environment Sanitization & Linux Filesystem Confinement]_

The enrolment file, its sidecar record with the HMAC under the enrolment integrity key, the key, the per-use checks, the check with its refusals, and the residual risk are implemented and documented in link:../../../../plan-marshall-documentation/doc/concepts/enrolment.adoc[Concepts § Enrolment] and link:../../../../plan-marshall-documentation/doc/developer/enrolment-store.adoc[Developer Guide § Enrolment Store] (link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXEC-2[PM-EXEC-2], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-5[PM-SEC-5]). This section keeps what is not implemented yet.

* *Harness Enrolment*: The machine-wide `<PM_MCP_BASE>/harnesses.json` has its own sidecar `harnesses.json.hmac`, a record in the format of the sidecar of a project enrolment (a closed, versioned record with exactly `format_version` `1`, `size`, `sha256` and `hmac`, the HMAC over the exact canonical bytes; link:../../../../plan-marshall-documentation/doc/concepts/enrolment.adoc#integrity[Concepts § Enrolment, Integrity]), under the same key, and its own lock `locks/harnesses.lock`; it is verified before every worker launch, and a mismatch is resolved by enrolling the harness again, never by `accept-edit` (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-enrol-harness[operator-enrol-harness]).
* *Verification Points*: The runtime runs the enrolment check in the project's recovery after a runtime start, before the project is first served (link:../runtime-lifecycle/01-startup-recovery-drain.adoc#per-project-recovery[Runtime & Interaction Model Specification, Per-Project Recovery]), and before every verify-not-resolve check of the project's jobs (`PM-EXEC-2`, link:../job-runtime/01-pipeline-and-subprocesses.adoc#enrolment-integrity[Job Runtime Specification]); the runtime also runs it before it serves a start or an operator act that uses the file. The check in the project's recovery is implemented (link:../../../../plan-marshall-documentation/doc/concepts/runtime-lifecycle.adoc#per-project-recovery[Concepts § Per-Project Recovery]); the other points are not wired yet. The operator is shown the refusal `enrolment_tampered` as a hold of the project with its act, and re-baselines the file interactively (accepting the edit, `pm-operator accept-edit enrolment <project_id>`, after reviewing the displayed recorded and current size and SHA-256 from the sidecar record, link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-accept-edit[operator-accept-edit]).

== Enrolment, Lifecycle Gate & Release
_Implementation watch: link:../../implementation-watch/credentials-and-enrolment.adoc#PM-WATCH-CLI-23[PM-WATCH-CLI-23], link:../../implementation-watch/credentials-and-enrolment.adoc#PM-WATCH-CLI-25[PM-WATCH-CLI-25], link:../../implementation-watch/credentials-and-enrolment.adoc#PM-WATCH-CLI-29[PM-WATCH-CLI-29]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-MIG-1[PM-MIG-1: Six-Stage Build-Out & Per-Project Plan Lifecycle]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-MIG-5[PM-MIG-5: Quantitative Triggers & Project Release]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXEC-2[PM-EXEC-2: Operator Enrolment & Verify-Not-Resolve Contract]_

`PM-MCP` and `plan-marshall` keep separate state trees (`PM-MIG-2`, link:../filesystem-layout/03-project-store.adoc#coexistence-lifecycle[Filesystem Layout Specification]). There is no crossing: `PM-MCP` imports nothing from `plan-marshall` (no configuration, lessons, `project-architecture/`, credentials, or learned build timeouts) and never reads or writes `.plan/` or `~/.plan-marshall/`. A project is taken into use as follows; each step is an operator act and writes an `audit.jsonl` record:

* *Enrolment*: The project's onboarding (<<project-onboarding>>) ends its detection and identity in `project.enrol`, which has the runtime write the project's enrolment (link:../../../../plan-marshall-documentation/doc/concepts/enrolment.adoc#enrolment-file[Concepts § Enrolment], link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]) with the fields the onboarding detected and the operator confirmed: the project root (refused with `enrolment_root_conflict` when another enrolment file already names it, and with `project_store_root_mismatch` when the machine store of this `project_id` records a different `project_root`), wrappers with their `pinned_files` and interpreter, host tools (the machine's enrolled CLI tools of `host-tools.json` serve unless the project enrols its own), the canonical and discovery command templates it overrides, provider `verify_argv` overrides, project scripts with binding, argument schema (validated as a schema), and maximum timeout, command budgets, write paths, the captured build environment, language servers, `container_engine` (`docker` only after the operator has been told that the project's jobs then hold the authority of the Docker group, which reaches every host path including `<PM_MCP_BASE>`, and has confirmed it; audited as `container_engine_enabled`; link:../job-runtime/02-confinement-and-environment.adoc#container-engine[Job Runtime Specification, Container Engine]), and `pilot`. On first enrolment it creates the project's machine store `<PM_MCP_BASE>/projects/<project_id>/` (link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]) with its workspace scope. `pm-operator enrol [--pilot] [--container-engine docker]` stays the direct verb: a later run of `project.identity` to `project.enrol` with its arguments as the answers, run from the checkout's working directory.
* *Setup*: The project setup in the workspace scope (link:../domain-extensions/04-setup-state-machine.adoc#project-setup-state-machine[Domain Extensions Specification, Project Setup State Machine]) creates, on its first run, `.marshall/` with its `.gitignore` partition (link:../filesystem-layout/01-repository-workspace.adoc#repository-layout[Filesystem Layout Specification]) and `.marshall/config/`, which holds no copy of a default workflow unit: a project holds a copy only of the units its team placed or changed, and a unit absent there resolves to the machine's level, then to the compiled default (link:../workflow-dsl/04-ast-node-model.adoc#process-designer[Workflow DSL Specification, Designing a Process]); the JSON team files are sparse and start absent, and no `plan-marshall` input exists.
* *Lifecycle gate*: The compiled gate and its decision per project are implemented (link:../../../../plan-marshall-documentation/doc/concepts/enrolment.adoc#lifecycle-gate[Concepts § Enrolment, The Lifecycle Gate and Pilots]). Where the gate refuses a project, the opening of a start entry for a plan or an epic and `start.create-scope` refuse with `lifecycle_closed` and create nothing, while the orthogonal services and the workspace scope stay available; since the gate is asked at each start, enrolling again without `--pilot` refuses only later starts, and the project's live plans and epics continue.
* *Unenrolment* (`pm-operator project unenrol <project_id>`, or the act of either client, confirmed with what it ends): refused with `scope_active` while the project has non-terminal plans or epics or running jobs, naming them; it removes the enrolment file and its sidecar and records `unenrolled_at` in the project store's `store.json` (link:../store-schemas/11-enrolment-store.adoc#project-store-identity[Store Schemas Specification, Project Store Identity]), leaving the store otherwise untouched. The store is then an item of the operator's cleanup, deleted as a whole only by it (link:../timeouts/03-retention-host-config.adoc#cleanup[Timeouts & Budgets Specification, One Cleanup]), and never a candidate of the periodic sweep, which removes only its technical residue. The store records its `project_root`; enrolling the same `project_id` again reuses the store only for the same root, removing `unenrolled_at`, and is refused otherwise (`project_store_root_mismatch`, a refusal naming both roots, not an MCP tool error).
* *Release*: the operator's switch-off for the `PM-MIG-5` triggers (<<project-release>>).

== Onboarding a Project as One Process
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-8[PM-EXT-8: Project Onboarding as One Process]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-26[PM-WF-26: Machine Onboarding & the Machine Scope]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-8[PM-SEC-8: Consent Before Acting]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-3[PM-EXT-3: Module Discovery, Build Map & Architecture Enrichment]_

A project is onboarded by one compiled unit, never project-owned, that runs from its checkout through detection, identity, and enrolment into the project setup (link:../../../../plan-marshall-documentation/doc/use-cases/04-projects.adoc#UC-PRJ-1[UC-PRJ-1]). Its states and their facts are in link:../state-catalogue/15-project-onboarding.adoc#state-catalogue-project-onboarding[State Catalogue Specification, Project Onboarding]; what the process guarantees:

* *A scope of its own*: Each onboarding runs in a scope of its own, an entry like a plan's start until `project.enrol` and then the project's workspace scope, so that several projects are onboarded at once and the machine scope's state is never touched. It starts only while the machine's onboarding is complete (`onboarding_incomplete` otherwise). Its choices are operator waits served to both clients, whichever answers first wins; no coding-agent session drives it (link:../workflow-dsl/02-units-jobs-decisions.adoc#clients-only[Workflow DSL Specification, All Interaction in the Operator's Clients]).
* *Where it starts*: `POST /api/v1/project-onboardings` (body: the checkout path; from the terminal client also its login environment, xref:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#client-environment[What the Terminal Client Sends]) opens the onboarding's entry, addressed like every entry at the top level as `/api/v1/entries/{entry_id}` with its events (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#event-streams[Runtime & Interaction Model Specification, Events per Scope]) and kept in its home `<PM_MCP_BASE>/onboardings/<entry_id>/` (link:../filesystem-layout/02-machine-runtime.adoc#machine-scope-home[Filesystem Layout Specification, Machine Scope & Onboarding Entries]), until `project.enrol` moves it into the project's workspace scope. `pm-operator project add [<path>]` opens it from the terminal, the working directory the proposed checkout. The checkout path must resolve canonically to a git top-level that no enrolment names (`enrolment_root_conflict`) and that lies under no project's `.marshall/local/worktrees/`.
* *Detection*: After the operator's consent `inspect_checkout` (link:../store-schemas/12-machine-stores.adoc#consent[Store Schemas Specification, Consent Before Acting]), the server reads the checkout and changes nothing: the remote with its owner and name, the base branch, the build wrappers with their pinned files, the host tools the project uses, the language servers, and the project scripts, each reported with a check line. What can be read is read (a build wrapper's version from its pinned properties); only host tools found in the directories of the operator's login `PATH` run their version probe, each as a probe job (link:../job-runtime/02-confinement-and-environment.adoc#probe-jobs[Job Runtime Specification, Probe Jobs]), never in the runtime's own process.
* *The checkout's own scripts*: Running them needs the operator's consent per project, `run_checkout_scripts`, asked in `project.run-consent` with every script and its arguments named, before any of them runs. It is the trust the enrolment grants anyway, since the enrolled wrapper runs in every build of the project's plans. Each script runs as a probe job with the confinement of a build job of the checkout. A _no_ goes on without the scripts, what needs them recorded as unknown, and is not asked again in that run. A remembered _yes_ is kept in `consents.json`, keyed by the project and the digest of each script, never in the enrolment, and a later run asks again only for a script that changed.
* *A consent remembered before enrolment*: Both checkout consents are asked before the project has its id. A remembered _yes_ is held with the onboarding's entry and written to `consents.json` under the project's `project_id` at `project.enrol`, the id the operator confirmed; an onboarding that does not reach `project.enrol` remembers nothing.
* *Identity*: The project's id is proposed from the remote's name, made valid by the identifier grammar (link:../identifiers.adoc[Identifier Registry]) and unique on the machine (a taken id gains the suffix `-2`, `-3`, …); the display name is proposed from the remote's owner and name. The operator may change both before the enrolment, the display name also later.
* *The build environment*: It is the operator's login environment as the terminal client captures and sends it, never the runtime's own (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#runtime-environment[Runtime & Interaction Model Specification, Environment]). An onboarding run from the web app takes the build environment the terminal client last captured on the machine and says so with its time; with none, the state names the terminal command that captures it (`pm-operator project add`, or `pm-operator project setup <project_id>`), and the enrolment waits for it.
* *Enrolment, then the setup*: `project.enrol` writes the enrolment the detection proposed and the operator confirmed (<<enrolment-lifecycle-release>>) and calls the project's setup, whose first states prepare the workspace and check the operator files; the operator's values of the project follow in `project.operator`, each with the machine's value as the proposal (link:../store-schemas/08-project-configuration-local.adoc#project-levels[Store Schemas Specification, Project Values over Machine Values]), and the setup then goes on from its integration variants (link:../domain-extensions/04-setup-state-machine.adoc#project-setup-state-machine[Domain Extensions Specification, Project Setup State Machine]).
* *Model cost asked first*: After the setup's qualification probe reports `grade`, and after its enrichment probe reports `enrich`, a consent state of kind `model_cost` (`setup.qualify-consent`, `setup.enrich-consent`) shows the expected tokens; _no_ skips the step with its reason and records it as owed for a later run, and the project is ready without it (link:../domain-extensions/04-setup-state-machine.adoc#setup-qualification[Domain Extensions Specification, Role Qualification at Install]).
* *A later run of one aspect*: The setup takes an optional aspect (the operator values, the team settings, the build map, the providers, the finalize steps, the qualification, the architecture) and runs only that aspect's states, with the current values as the proposal; without an aspect it takes its reconcile path. `pm-operator project setup <project_id> [<step>]` starts it, or continues an onboarding still open.

== Releasing Ends Work as the Operator Ends It
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-MIG-5[PM-MIG-5: Quantitative Triggers & Project Release]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-23[PM-WF-23: Operator Acts on Plans and Epics]_

The release is the operator's switch-off for the `PM-MIG-5` triggers: an operator act of both clients (`POST /api/v1/projects/{project_id}/release` with the operator's reason; `pm-operator project release <project_id>` its terminal form), confirmed with what it ends, listed before the confirmation: every non-terminal plan and epic of the project, its pending entries, and a running onboarding (link:../../../../plan-marshall-documentation/doc/use-cases/04-projects.adoc#UC-PRJ-3[UC-PRJ-3]). It runs in this order:

. *A short landing finishes first*: Before it ends anything, the release lets a running short landing of the project (`git.land-removal`, `git.land-unit`; link:../workflow-dsl/06-reusable-sub-workflows.adoc[Workflow DSL Specification, Reusable Sub-Workflows]) finish, within the compiled bound `release.landing_wait_seconds` (link:../timeouts/01-job-budgets-and-waits.adoc[Timeouts & Budgets Specification]). While it waits, the project admits no new start and no new short landing (each refused `lifecycle_closed`). When the landing does not finish within the bound, the release is refused (`release_landing_pending`, `409`, naming the landing), ends nothing, and the project admits starts again.
. *The release is recorded*: The runtime writes `released_at` (the release instant) into the project's enrolment file (link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]) and appends an `operator` audit record.
. *Every plan ends `released`*: Every plan of the project that has not ended, whatever its state (running, pausing, paused, waiting for the operator, or held), ends through `plan.aborted` with the outcome `released` and the operator's reason, never `cancelled` or `abandoned`, and is archived like a completed plan (link:../state-catalogue/04-plan-finalize-terminal.adoc#plan-end[State Catalogue Specification, Cancelling and Abandoning Archive]); its open decisions and waiver requests are closed `cancelled`, and its lesson claims are released.
. *Every epic ends `released`*: Every epic of the project that has not ended ends with the `terminal_reason` `released` and is archived in the project's machine store only (link:../filesystem-layout/03-project-store.adoc#archives[Filesystem Layout Specification, Archives]): its ledger stays in `.marshall/epics/<epic_id>/` untouched, without `epic.archive`, a ledger commit, or an epic landing. Its plans end with the release, so nothing is left to tell it.
. *Entries and onboarding*: The project's pending entries are deleted with their sources, and a running onboarding or setup run of the project is ended.
. *The report*: The runtime writes the report `project.released` (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#reports[Runtime & Interaction Model Specification, Reports to the Operator]).

The release touches no repository: branches, worktrees, and pull requests stay as they are, the archived records stay readable in the project's machine store, nothing is converted, and the project can continue on `plan-marshall`, whose `.plan/` `PM-MCP` never touched. While `released_at` is set, the plan lifecycle is not offered: the opening of a start entry for a plan or an epic and `start.create-scope` refuse with `lifecycle_closed`; the workspace scope and the orthogonal services stay available. Enrolling the released project again clears `released_at` (audited), and the lifecycle is offered again under the lifecycle gate.
