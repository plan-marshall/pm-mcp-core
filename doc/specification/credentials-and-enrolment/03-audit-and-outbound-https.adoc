== Security Audit Trail
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-6[PM-SEC-6: Security Audit Trail & Tamper-Evident Logging]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_

Every MCP tool call, state transition, job execution, credential lookup, consent, and operator act appends a structured JSONL record to `<PM_MCP_BASE>/logs/audit.jsonl` (mode `0600`, appended under the audit lock on the log file itself, a leaf of the lock order, schema defined in link:../store-schemas/12-machine-stores.adoc#audit-log[Store Schemas Specification, Audit Log]):

* *Identity per record*: A record carries the identity of the operation it audits, and no call is checked against an environment: an operator act its channel (`cli`, or `web` with the `device_id` of the paired device), a worker's operation its `job_id`, role, harness, and generation, and a machine-level record (runtime start, a sweep, a machine-scope transition) the operating system principal running the runtime (`System.getProperty("user.name")` / `geteuid()`).
* *Tamper Evidence*: The hash chain of `logs/audit.jsonl` (each record's `prev_hash` is the lowercase hex SHA-256 of the previous record's canonical line; the first record after a rotation chains to the checkpoint line that closed the rotated log, and only the first record of a log never rotated to the genesis value), the anchored head `logs/audit.head` under the HMAC-SHA-256 of the enrolment integrity key (link:../../../../plan-marshall-documentation/doc/concepts/enrolment.adoc#integrity[Concepts § Enrolment, Integrity]), the rotation at `audit_rotation.max_bytes` or `audit_rotation.max_days` with its `checkpoint` record, the rename to `audit-<first_event_id>.jsonl` and the hash-chained index `logs/audit-index.jsonl`, and the verification with the reasons `link_broken` (with the first broken line), `missing`, `reset`, `truncated`, and `head_mismatch`, incremental from the last checkpoint and full across every rotated file, are implemented and documented in link:../../../pm-core/doc/developer/core-store.adoc[Scope Stores Developer Guide § The Audit Log] and link:../../../pm-runtime/doc/developer/runtime-audit.adoc[Audit Trail Developer Guide] (`PM-SEC-6`; schemas: link:../store-schemas/12-machine-stores.adoc#audit-log[Store Schemas Specification, Audit Log]). The chain alone proves only that the records present are consistent; the anchored head makes a deleted log, a reset to the genesis value, a truncated tail, and a consistently rewritten chain detectable. Records are appended under the audit lock, the leaf of the lock order; the head and the rotation only read the integrity key and never create it, so while no key exists (no enrolment yet) no head is written, no rotation happens, and the verification reports the chain as not verified. The following stays open:
* *Wiring*: `pm-mcpd` hands its audit records to the production sink and passes the verification to the bounded verification of its start (link:../runtime-lifecycle/01-startup-recovery-drain.adoc#_startup_sequence[Runtime Lifecycle Specification, Startup Sequence], step 4.1), and it reads the rotation limits from `audit_rotation` of `machine-config.json` (link:../timeouts/03-retention-host-config.adoc#audit-rotation-age[Timeouts & Budgets Specification]); until then the runtime rotates at the defaults (64 MiB, 30 days).
* *Removal of Rotated Files*: The periodic sweep removes rotated files older than `audit_rotation.retain_days` (`machine-config.json`, link:../timeouts/03-retention-host-config.adoc#rotated-audit-files[Timeouts & Budgets Specification, Rotated Audit Files]) by itself, as technical residue (link:../store-schemas/13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Store Schemas Specification, Evidence-Based Removal Sweeps]), as whole files and never their index entries, one audit record each, so a removed file stays accounted for; `pm-operator sweep --machine` lists them and `--apply` runs that pass at once.
* *Reporting & `pm-operator audit verify`*: The full chain across all rotated files is verified on demand by `pm-operator audit verify`. The same reporting rules apply to every result: on `stderr`, in both clients of the operator, and as an `audit_chain_broken` security record (`details.reason`, `details.first_broken_line` for `link_broken`, `details.os_principal`); the log is never rewritten or silently repaired, and the next record chains to the last line as found.
* *Residual Risk*: The anchoring is tamper-evident, not tamper-proof: a process that holds the integrity key (on macOS, anything that runs the `pm-mcpd` binary; with the file store or the key file, any process of the user) can forge a consistent head. This is accepted and documented with the enrolment integrity risk (link:../../../../plan-marshall-documentation/doc/concepts/enrolment.adoc#residual-risk[Concepts § Enrolment, Residual Risk]; `PM-SEC-6`).
* *Error Sanitization*: Unhandled exceptions or protocol errors return only a closed-enum error code to the MCP caller, plus the `audit_id` (a UUIDv7, link:../identifiers/02-registry-stores-to-web.adoc#id-audit-id[Identifier Registry]) only where the operator must look the error up (`internal_fault`, `file_unreadable`; link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]); stack traces and host filesystem paths are written exclusively to `<PM_MCP_BASE>/logs/daemon.log`.

== Outbound HTTPS Security (`cui-http`) & Native Runtime Stack
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-TECH-1[PM-TECH-1: Java 25+ & Quarkus MCP Runtime Foundation]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-TECH-2[PM-TECH-2: Outbound HTTPS Client, LSP Client & McpAssured Testing Libraries]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-TECH-3[PM-TECH-3: GraalVM Native Executable & Startup/Memory Bounds]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-TECH-4[PM-TECH-4: Operating System Platform Integration (macOS & Linux)]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SVC-3[PM-SVC-3: Selective Upstream MCP Proxy & Provenance Tagging]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-TEST-5[PM-TEST-5: Security Boundary & Confinement Adversarial Testing]_

* *Outbound HTTPS Hardening (`de.cuioss:cui-http`)*: All outbound REST and GraphQL calls (SonarQube/SonarCloud, the native GitHub, GitLab, and Forgejo clients), remote upstream MCP calls, and the runtime's own fetches (a release from the organisation's registry, on the operator's upgrade or the consent `check_updates`; a harness icon, on the consent `fetch_icons`) use `de.cuioss:cui-http`'s `HttpHandler` and `ResilientHttpAdapter` with TLS 1.2+, mandatory certificate/hostname verification, HTTPS-only redirect following, and origin-pinned bearer token transmission (stripping `Authorization` headers on any cross-origin redirect). All URL/path/header parameters composed into outbound requests are validated through `de.cuioss.http.security` pipelines. The native git transport (JGit) uses a connection factory with the same TLS rules that connects only to the credential entry's origin (link:01-provider-credentials.adoc#native-confinement[Native Operation Confinement]). Both honour the operator's `proxy` setting of `machine-config.json` and no other proxy source (link:01-provider-credentials.adoc#native-confinement[Native Operation Confinement], Configuration allowlist). An upstream MCP server is always a remote HTTPS server reached this way, and it is called by the runtime only, never re-exposed to a worker; no upstream server runs as a `stdio` subprocess (`PM-TECH-2`). Nothing about the machine is sent beyond the request itself (`PM-ARCH-2`).
* *GraalVM Native Image & Resource Bounds*: The runtime `pm-mcpd` is compiled as a standalone Quarkus native executable (`Java 25+`, `quarkus-mcp-server-http`, Virtual Threads); the two CLI binaries `pm-mcp` (the relay) and `pm-operator` and the launcher `pm-exec` are plain native images without Quarkus (xref:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#cli-implementation[CLI Implementation]). Startup and memory bounds for the runtime, the relay, and the operator CLI are defined in `PM-TECH-3` and verified as described in the link:../../../../plan-marshall-documentation/doc/specification/runtime-model/04-sessions-and-workers.adoc#_verification[Runtime & Interaction Model Specification, Verification].
* *STDIO & Confinement Adversarial Verification (`PM-TEST-5`)*: Integration tests (`*IT`) using `McpAssured` (`McpStdioTestClient`) verify the transport isolation properties listed in the link:../../../../plan-marshall-documentation/doc/specification/runtime-model/04-sessions-and-workers.adoc#_verification[Runtime & Interaction Model Specification, Verification], that insecure permissions (`0755`) on `<PM_MCP_BASE>/enrolments/` trigger fail-closed termination at runtime start (exit code `77`), that insecure permissions (`0644`) on one project's enrolment file block only that project (`enrolment_insecure`), that a project's enrolment file edited outside the operator acts is refused with `enrolment_tampered` for that project while a second enrolled project is still served, that a job writing `<PM_MCP_BASE>/enrolments/<project_id>.json` or into another enrolled project's root fails under the Linux Landlock write set while a write into its own project root succeeds, that a job cannot read `<PM_MCP_BASE>/run/runtime.token` or a credential file under `<PM_MCP_BASE>/credentials/` under the Linux Landlock read set while a read outside `<PM_MCP_BASE>` succeeds (positive control), that a request without the runtime token is refused on `/mcp` and `/api/v1`, that an operator verb run without a terminal or with an agent environment marker is refused before any request is sent, that an insecure file-store credential file blocks only the step that needs it (`credentials_file_insecure`), that a request on the LAN listener that needs the loopback listener (a credential secret, a file listing, a move of documents) is refused (`loopback_only`) also when it names a loopback address, that a revoked device's open event streams end with their reason, that no secret registered with the redaction registry appears in a job log excerpt or an activity journal, that path-traversal or command-injection payloads are deterministically rejected and logged to `audit.jsonl`, and that hostile repository configuration against the native git variant is contained: a `url.<base>.insteadOf` or `pushInsteadOf` rewrite and a `remote.<name>.pushurl` to a foreign host yield `remote_origin_mismatch` with a `security` audit record and no credential-bearing request to that host, while `core.sshCommand`, `core.fsmonitor`, a `.gitattributes` filter driver, and a hook in a native-selected repository start no process and yield `capability_missing`; CLI-variant `git` and `ci` jobs are shown to carry no token variable or askpass helper in their environment.
