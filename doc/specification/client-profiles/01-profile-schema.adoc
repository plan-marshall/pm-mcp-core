== Normative Client Profile JSON Schema
_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-8[PM-WATCH-CLIENT-8]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-5[PM-CLIENT-5: Versioned Client Profile Schema & Override Hierarchy]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-TOOL-5[PM-TOOL-5: Tool Schema Stability & Context Budget Discipline]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-14[PM-WF-14: Task Envelopes, Model Slots & Usage per Task]_

A client profile is the one configuration document of a harness: `classpath:/profiles/<client_id>.json`, a resource of `pm-api` (`claude.json`, `opencode.json`, `antigravity.json`, `codex.json`), and every profile the operator installed for the machine or a project (<<profile-sets>>). Everything the system knows about a harness is in its profile and nowhere else (<<harness-as-data>>). Every profile is validated against the following JSON Schema (Draft 2020-12):

[#role-classes]
=== Role Classes of a Harness

`headless.classes` states, per role class, whether the harness can run it and how far it holds a worker to the tools of its role.

* *The screener needs a harness without tools*: `zero_tool` is the class of the screener and the judge, which read untrusted or ungraded text (link:../model-work/07-untrusted-text-screening.adoc#screener[Model Work Specification, Screener]), and of a commit-message or change-type role whose artifact sets it (link:../model-work/01-roles-and-configuration.adoc#closed-task-in-band[Model Work Specification, A Closed Task without Tools]). It is the one class for which the harness must restrict the worker, and the restriction is total: no tool, no MCP connection, project and user settings off. A harness that cannot be started that way declares `zero_tool: null`, and no screener or judge role may name it. This is the only class restriction the system depends on.
* *The other classes run no code the harness fetches or runs on its own*: a `writer` or `read_only` worker loads the project's instruction files and skill directories and no plugin, no hook, no MCP server, no environment value, and no model endpoint or proxy from any settings file of the project, the checkout, or the user, and connects to no MCP server but its job relay. Plugins update and run themselves, and hooks run without a tool call, so neither the role's tool set nor the job's confinement keeps their code out of the worktree that becomes the pull request. A harness whose launch of the class cannot be held to that declares the class `null`.
* [[user-level-files]]*Nothing of the operator's own*: a `writer` or `read_only` worker loads no instruction file and no skill of the user (for example `~/.claude/CLAUDE.md`, `~/.claude/skills/`, `~/.agents/skills/`), wherever the harness looks for them, also where a home or data-home variable of the launch does not redirect that lookup. What a worker of a role knows is then the same on every machine, so its qualification and its start context do not depend on the operator's personal setup. The project's instruction files and skills load as before. _Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-16[PM-WATCH-CLIENT-16]_
* *Beyond that, a tool restriction is welcome and not required*: `writer` and `read_only` workers act on text that has passed the screener, inside the confinement of the job launcher, and the server limits what they can reach of `PM-MCP` on every request (link:../model-work/04-worker-launch.adoc#job-tool-sets[Model Work Specification, Tool Sets]). `tool_set: enforced` means the harness also limits the worker to the tools of its role; `tool_set: advisory` means it cannot, the worker runs with every tool of the harness, and the role's tool set only tells it which to use. Both are runnable. `pm-operator roles show <role>` reports an advisory tool set, so the operator sees which roles run unrestricted.
* *Rules*, checked by profile validation: a non-null `zero_tool` requires `capabilities` to hold `project_settings_control`; a non-null `writer` or `read_only` requires `capabilities` to hold `extension_isolation`; a profile whose `mcp_config.exclusive` is `false` declares `writer`, `read_only`, and `zero_tool` all `null`, since such a harness cannot be kept from connecting; `worker.restricted_models` is non-null exactly when a class is `enforced`. The launch re-checks the class's capability and tool template (`LaunchComposer.requireClass`, link:../../../pm-runtime/doc/developer/runtime-launch.adoc[Worker Launch Developer Guide]).

[#headless-block]
`headless` is the harness's launch contract for workers; the host never starts a sub-agent. How the server composes a
worker's launch from the role artifact and this block, the tool sets of the role classes (`writer`, `read_only`,
`zero_tool`), the composition per `agent_mode`, the harness enrolment, and the working directory are specified in
link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]. The projection of this block and the
composition are implemented by `runtime.launch` (link:../../../pm-runtime/doc/developer/runtime-launch.adoc[Worker Launch
Developer Guide]). A role artifact of a class its harness cannot run (<<role-classes>>) is invalid on load and counts as
undefined (link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]). A
profile with `headless: null` is shown in the harness lists, marked, and never offered as a worker host or as the default
harness (<<harness-scan>>). Values the evaluation did not measure stay _(provisional)_ like the other host facts.

[#headless-usage]
*Usage pointers*: Usage is read from the harness output through `headless.usage`, never asked from a model. The same per-turn figures give the supervisor a warm worker's context size for its token budget (link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]).

[[claude-state-file]]*The `claude` state file*: `~/.claude.json` holds the harness's own state, which a headless run rewrites. The bundle owns nothing in it (xref:../../../../plan-marshall-documentation/doc/specification/host-integration/02-bundle-manifest.adoc#bundle-content[Bundle Manifest, Bundle Content]), and a worker's own MCP configuration is the per-call one of its launch (`--strict-mcp-config`), so a worker that rewrites the file changes neither its own connection nor anything the bundle installed; the file stays in the write set, because the harness cannot run headless without rewriting it. _Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-8[PM-WATCH-CLIENT-8]_

[[headless-data-home]]*Per-worker data home*: `headless.data_home` is declared for a harness whose local state is one per-user store that all its processes share, so that a stalled worker cannot hold that store's lock against every other worker and against the operator's own sessions. `opencode` declares `{"variable": "XDG_DATA_HOME", "login_file": "opencode/auth.json"}`: every worker gets its own data directory below its job-private directory, with the harness's login file copied in, and the directory is removed when the job settles (link:../job-runtime/02-confinement-and-environment.adoc#worker-data-home[Job Runtime Specification, Per-Worker Data Home]). Profile validation refuses a `variable` that matches a credential pattern or that the job environment already sets. `claude` and `codex` declare `null`. _Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-60[PM-WATCH-DISP-60]_

[[headless-tool-result-limit]]*Tool-result limit*: `headless.tool_result_limit_chars` is the largest tool result the harness passes to its model whole. A harness that cuts a larger result keeps the full text where a worker restricted to the server's tools cannot read it, so the worker would lose the task's identifiers. The server therefore returns no tool result above the limit to a worker of that harness: identifiers and links come first, and the remaining content is named as parts below the limit, read through the harness's resource tools (link:../model-work/02-task-protocol.adoc#offer[Model Work Specification, Offer]; value and basis: link:../timeouts/03-retention-host-config.adoc#tool-result-limit[Timeouts & Budgets Specification, Harness Tool-Result Limit]). `opencode` declares `32000`: its inline settings set the harness's own limit to `128000` bytes and lift its line limit out of reach (<<headless-inline-settings>>), and a quarter of the bytes is the character count no result of UTF-8 text can exceed; `claude` declares `null`. Profile validation refuses a non-null limit on a profile without `resource_tools`, and a limit above a quarter of a byte limit the profile's own inline settings set. _Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-12[PM-WATCH-CLIENT-12]_

[[headless-inline-settings]]*Inline settings*: a harness that bounds a worker by mechanisms of its own (a timeout on a model request, the size at which it cuts a tool result, the compaction of its context, the form in which it offers MCP tools) would act on the worker beside the server, unseen in its output stream. `headless.inline_settings` sets these mechanisms for every worker of the harness, in the harness's own configuration keys, so that the server's supervision and recycling are the only ones acting on the worker and every bound the harness keeps is a declared one. The server merges the object into the inline configuration document of the launch; the agent's own permissions and the MCP configuration of the job relay are rendered by the server and are never part of it. `opencode` (2.x) declares _(provisional until its verification has run)_:

|`connection.idle_timeout_seconds` |`1800` |`60` |`180` |`270` _(provisional)_
|`connection.bounded_wait_seconds` |`240` |`240` |`150` |`240` _(provisional)_
|`connection.progress_resets_timeout` |`true` |`true` |`false` |`false` _(provisional)_
|===

Rules of the block, checked by profile validation:

* *Eligibility*: `eligible: true` requires a non-null `headless` block. A host is eligible only after its worker behaviour has been measured on it under the target conditions (the real relay, confined writer workers) and every fault of the fault matrix passed (link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-TEST-4[PM-TEST-4]; exit detection within the link:../timeouts/01-job-budgets-and-waits.adoc#exit-detection-bound[exit detection bound]). `claude` is eligible. `opencode` is eligible with its per-worker data home (<<headless-data-home>>), without which a stalled worker blocks every other process of the harness, and with its tool-result limit (<<headless-tool-result-limit>>); Antigravity (its fault matrix passed only as a smoke run with unconfined workers) and Codex (not measured) are not eligible. The operator assigns the roles of an ineligible host to an eligible harness. A role whose effective configuration names a harness that is not eligible is invalid (link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]).
* *Restricted models*: a worker of a class whose `tool_set` is `enforced` runs with a restricted tool set, so a model that refuses a restricted agent cannot host one. An entry `*` stands for every model of the harness, an entry `<provider>/*` for every model of that provider. The free OpenCode models refuse a restricted agent and are not listed; of the OpenCode Go models only the measured `opencode-go/muse-spark-1.3-contributor` is listed (link:../../../../plan-marshall-documentation/doc/specification/evaluation.adoc[Evaluation Reference]), and another one is listed once it is measured.
* *Informational acknowledgement*: with `ack_informational: true`, `ack_deadline_seconds` equals the silence limit, `connection.bounded_wait_seconds` plus `silence_grace_seconds` (`240 + 30 = 270` measured on `opencode`, where a provider stall of 120.8 s left a live worker's task unacknowledged), and a missing acknowledgement ends no worker: silence alone decides. The supervisor applies the silence limit of the effective connection values, so an operator override of the bounded wait moves both.
* *Bounded wait and idle timeout*: on a host whose progress resets its timeout, a worker's `pm_wait` is always held with progress frames, so its bounded wait may exceed the host idle timeout (`opencode`: `240` against `60`); on any other host the bounded wait stays below the idle timeout by the margin of link:../timeouts/01-job-budgets-and-waits.adoc#bounded-wait[Timeouts & Budgets Specification, Bounded Wait Window].
* *Values of an ineligible host*: while `eligible` is `false`, no other value of the block has an effect, and each is `null` unless it was measured on the host; the extrapolated Antigravity values of the evaluation are entered only once they are measured.
* *A worker that does not continue*: an `opencode` process stopped while a model request is open may never continue after it is resumed. Its inline settings bound that request (<<headless-inline-settings>>), so that the harness ends it and the worker exits before its silence limit; where it does not, the supervisor ends such a worker by silence at its silence limit and never earlier (link:../model-work/03-supervision-and-recycling.adoc#detection[Model Work Specification, Detection]), so the limitation costs one silence limit before the task is offered again; it does not affect eligibility.

The relay and the server need no other host value for workers: identity, role, and generation travel in the worker's environment, never in the profile (link:../../../../plan-marshall-documentation/doc/specification/runtime-model.adoc[Runtime & Interaction Model Specification, Relay]).

[#model-tiers]
=== Model Tiers & Models of a Harness
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-5[PM-CLIENT-5: Versioned Client Profile Schema & Override Hierarchy], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-1[PM-WORK-1: Roles as Configuration]_

* *Tiers*: `headless.model_tiers` maps each tier of the closed list `frontier`, `standard`, `fast` to the concrete model the harness takes for it, so the shipped default assignment, which names a tier per role, holds on any harness (link:../model-work/01-roles-and-configuration.adoc#default-assignment[Model Work Specification, Default Role Assignment]). A tier the harness has no model for is `null`; a role whose tier resolves to `null` on its harness is shown unresolved, and the operator chooses its model. The `steward` takes the model of the tier `standard` of the machine's default harness (link:../model-work/01-roles-and-configuration.adoc#steward-role[Model Work Specification, Steward Role]). The values of a shipped profile are those the release graded; a mapped model must appear in `worker.restricted_models` where the class of a role assigned to it is `enforced`, which profile validation checks.
* *Models probe*: `headless.models_probe` is an argument vector whose output lists the models the harness offers (one id per line, or a JSON array at its pointer), run without a shell, as a probe job (link:../job-runtime/02-confinement-and-environment.adoc#probe-jobs[Job Runtime Specification, Probe Jobs]) of the onboarding's `catalogue` sub-workflow on the operator's consent (link:../store-schemas/12-machine-stores.adoc#consent[Store Schemas Specification, Consent]); its result fills the models the operator chooses from in `catalogue.select`, each recorded with the source `probe` in the model catalogue (link:../store-schemas/12-machine-stores.adoc#model-catalogue[Store Schemas Specification, Model Catalogue]). A harness that cannot list its models declares `null`, and the operator enters the model ids, recorded with the source `operator`.
* *Weights probe*: `headless.weights_probe` reads the identity of a model's weights where the harness reports one, which binds the model's qualification to those weights (link:03-endpoint-harness.adoc#weights-identity[Endpoint Harness, Weights Identity]). The shipped profiles declare `null`.
* [[long-context-thresholds]]*Long-context price tier*: some providers bill every request whose input exceeds a threshold at a higher price per token. `headless.long_context_thresholds` names that threshold per model id, and a shipped profile holds an entry only where the provider documents the price, with the documented value, checked for every release. A context budget that the system falls back to (the profile's `headless.context_budget_tokens`, the compiled `400K`) is capped at the threshold of the worker's model, so an envelope packed to a fallback never runs its turns above the tier (link:../model-work/06-envelopes-questions-deadlines.adoc[Model Work Specification, Envelopes]). A `context_budget_tokens` the role artifact sets, and the operator's `envelope_budget_tokens`, are taken as set: the tier is then the operator's choice, and the role view shows a budget above the threshold beside the role's model.
* *Implemented*: the tier of the default assignment is rendered into the model of this block by `LaunchComposer.renderModel`, before the effort is narrowed (link:../../../pm-runtime/doc/developer/runtime-launch.adoc[Worker Launch Developer Guide]).

[#harness-scan]
=== Harness Scan
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-5[PM-CLIENT-5: Versioned Client Profile Schema & Override Hierarchy], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXEC-1[PM-EXEC-1: Wrapper-First Execution & Enrolled Host Tools], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-8[PM-SEC-8: Consent Before Acting]_

The machine's onboarding finds the harnesses installed on the machine itself (link:../workflow-dsl/01-grammar.adoc#machine-scope[Workflow DSL Specification, Machine Scope]):

* *Where it looks*: `harness.scan` looks for the `headless.executable` of every profile in the effective profile set (shipped and machine profiles, <<profile-sets>>) in the directories of the operator's login `PATH`, which the terminal client sends with its request because the runtime's own environment is never an input (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#runtime-environment[Runtime & Interaction Model Specification, Environment]), and in the profile's `headless.install_locations` (paths with `~` and the platform's application directories). It runs only after the consent `scan_harnesses` (link:../store-schemas/12-machine-stores.adoc#consent[Store Schemas Specification, Consent]).
* *What it runs*: nothing but the profile's version probe (`identity.version_probe`, without a shell, with a bounded timeout) on what it finds, as a probe job (link:../job-runtime/02-confinement-and-environment.adoc#probe-jobs[Job Runtime Specification, Probe Jobs]); a found executable is a candidate, with its path, its version, and whether the version lies in `headless.supported_versions`. Only `harness.enrol` records a candidate's absolute path and SHA-256 digest in the harness enrolment, as `pm-operator enrol-harness` does (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-enrol-harness[CLI, Coordination & Security Specification, Harness Enrolment]).
* *What it shows*: every profile of the set with its result: found (path, version), found outside the supported range, or not found with the profile's `install_hint`, rendered in the operator's interface language. A profile with `headless: null` or `worker.eligible: false` is shown and marked, never offered for enrolment as a worker host or as the default.
* *The default harness*: `harness.enrol` records the default harness in `machine-config.json` as `harnesses.default` (a client id of `harnesses.json`, link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration]); a harness that is the default cannot be removed before another is chosen. The steward runs on it (link:../model-work/01-roles-and-configuration.adoc#steward-role[Model Work Specification, Steward Role]).
* *No closed list of harnesses*: the scan, the enrolment, the role validation, and every view take the harnesses from the effective profile set; no closed list of client ids refuses a harness the operator added (<<unknown-harness>>).

[#login-probe]
=== Login Probe
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-5[PM-CLIENT-5: Versioned Client Profile Schema & Override Hierarchy], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-8[PM-SEC-8: Consent Before Acting]_

A harness is logged in through its own login, never through `PM-MCP` (*No harness credentials* above), and the onboarding checks it before the first worker starts:

* *The probe*: `headless.auth_probe` is an argument vector with the exit codes that mean logged in and logged out and the harness's own login command. `harness.probe` runs it, without a shell and with a bounded timeout, as a probe job of the enrolled executable (link:../job-runtime/02-confinement-and-environment.adoc#probe-jobs[Job Runtime Specification, Probe Jobs]), after the consent `probe_harness_login` of `harness.probe-consent`. Logged in lets the onboarding go on; logged out leads to `harness.blocked`, an operator wait that shows the login command for the operator to run in a terminal and offers _probe again_; any other exit code is shown as unknown with the harness's error text and the same choice.
* *Without a probe*: a harness whose profile declares `auth_probe: null` is probed by one minimal headless call of its `launch` form (one turn, no tool, no MCP connection, a fixed prompt), whose expected tokens are shown in the consent before it runs; its success means logged in, and a start failure is shown with the harness's error text like a logged-out probe.
* A harness that is logged out later makes its workers fail before their first call, which the start-failure guard reports (link:../model-work/03-supervision-and-recycling.adoc#start-failure-guard[Model Work Specification, Start-Failure Guard]).

[#update-evidence]
=== Update Evidence
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXEC-1[PM-EXEC-1: Wrapper-First Execution & Enrolled Host Tools], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation]_

Harnesses update themselves, so the digest of an enrolled harness executable changes without the operator. A changed executable is never its own witness: its version probe runs only after evidence from outside it shows it is the vendor's.

* *When*: at a worker's spawn, when the SHA-256 of the enrolled executable differs from the enrolment (link:../job-runtime/01-pipeline-and-subprocesses.adoc#_verify_not_resolve_execution_pipeline[Job Runtime Specification, Verify-Not-Resolve Execution Pipeline]).
* *`code_signature`*: the runtime checks the platform code signature of the file without running it (on macOS the signature, its Developer ID chain, and the notarisation, the signing identity's team identifier equal to `signer`). A platform without code signatures, an unsigned file, an invalid signature, or another signer fails the evidence.
* *`package_provenance`*: the runtime has the package manager that installed the executable verify the installed package's signed provenance (its source repository equal to `signer`), as a probe job of that enrolled host tool, and checks that the executable is a file of that package with that digest. A package manager that is not enrolled, a package without provenance, or a mismatch fails the evidence.
* *`none`*: there is no evidence; every change waits for the operator.
* *Validation*: profile validation refuses `code_signature` or `package_provenance` without a `signer`, and `none` with one (the schema's `if`/`then`/`else`), so no profile declares a method that checks against nothing.
* *Outcome*: passed evidence lets the version probe run, and a version inside `supported_versions` is accepted and audited (`harness_updated`, naming the evidence); failed or missing evidence refuses the launch before spawn with `harness_update_unverified`, never running the changed file, and the act that resolves it is the operator's enrolment of the harness, which shows the recorded and the new version and digest (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-enrol-harness[CLI, Coordination & Security Specification, Harness Enrolment]).
* *Shipped values*: a shipped profile declares a method only where the release has checked it on that harness; every other profile ships `none`.
* *Implemented*: the re-digest, the evidence check before the version probe, the accepted self-update and the refusals are implemented by `runtime.launch` (`HarnessVerifier`, `HarnessEnrolmentStore`; link:../../../pm-runtime/doc/developer/runtime-launch.adoc[Worker Launch Developer Guide]): an accepted update rewrites `harnesses.json` with the new version and digest and is audited `harness_updated`; a changed executable without evidence is refused `harness_update_unverified`, one outside the range `harness_version_unsupported`, and an unenrolled harness `harness_not_enrolled`. The platform checks themselves (`code_signature`, `package_provenance`) are the `EvidenceCheck` seam of the verifier; the default refuses every change, the fail-closed direction.

[#harness-icons]
=== Harness Icons
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-5[PM-CLIENT-5: Versioned Client Profile Schema & Override Hierarchy], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-ARCH-2[PM-ARCH-2: Local-by-Design & Zero External Cloud Dependency], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-8[PM-SEC-8: Consent Before Acting]_

A harness is shown where the harness itself is shown (the harness lists, a role's assignment) by its icon, never as the product's own mark, in a heading, or anywhere that suggests that its maker endorses `PM-MCP`.

* *Two forms*: the profile's `icon` names either `source`, the URL of the maker's official icon file, or `bundled`, the name of an icon shipped in the binary, which only an icon whose maker gave written permission to ship it may use.
* *Fetched by the runtime, never by the browser*: an icon of the form `source` is fetched by the runtime, once, from its URL, through the proxy settings of the runtime's outbound requests, on the operator's consent `fetch_icons`, asked in `harness.icons-consent` after the scan; with _no_ the monograms are shown and the step goes on. The fetched file (SVG or PNG, at most `256` KiB, an SVG stripped of scripts, external references, and event attributes) is stored in the machine store `<PM_MCP_BASE>/icons/<client_id>.<ext>` (link:../store-schemas/12-machine-stores.adoc[Store Schemas Specification, Machine Stores]) and served to the web app from the runtime's own origin (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#web-security-headers[CLI, Coordination & Security Specification, Request Validation & Security Headers]). A browser never loads it from the maker's server, which would send the operator's address to that server on every view and break the content security policy.
* *Monogram*: without a fetched or bundled icon, a harness is shown by a generated monogram, the initials of its `display_name` on a colour derived from its `client_id` (the first bytes of its SHA-256 as a hue), the same in both clients. The monogram is the icon of every harness; a profile gains its `source` or `bundled` icon only once its maker's terms or a confirmation allow it. No shipped profile declares one; the bundling of makers' icons is a later improvement (link:../../../../plan-marshall-documentation/doc/later-improvements.adoc#L-21[Later Improvements, L-21]).

[#token-usage]
=== Tokens, Not Money
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-5[PM-CLIENT-5: Versioned Client Profile Schema & Override Hierarchy], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-14[PM-WF-14: Task Envelopes, Model Slots & Usage per Task]_

Usage is read from the harness output through `headless.usage`, never asked from a model. The pointers and the recording are implemented; what remains of this part is the handoff a verified profile makes to its enrolment and the fixtures and the evaluation that judge a harness version.

* *Usage report of a harness*: the harness lists of the onboarding and of the machine's settings show per enrolled harness and version what it reports of its usage: `complete` (every token figure reported or not applicable), `partial` (naming what is missing), or `not_reported`, from the profile's declaration and, for a verified profile, from the `usage_report` the owed install path writes into the enrolment (link:../store-schemas/11-enrolment-store.adoc#harness-enrolment-store[Store Schemas Specification, Harness Enrolment Store]). The install path that hands the verification stage's `UsageResult` to the enrolment's `UsageReport` (`UsageReport.of` is the mapping boundary) is owed to `machine-onboarding-unit`.
* [[start-context]]*Start context*: what a worker costs before it does anything is recorded per class and model in the `usage_report` as `start_context`, the input of the first model turn with the cache read and the cache creation; it is the basis on which the operator and the evaluation compare harnesses and judge a token budget, and no rule reads it.
* *Measured per version*: recorded outputs of each harness and version are parsing fixtures, so a changed output format fails a test; the usage measurement of the evaluation is repeated for every new harness and harness version before its figures are trusted (link:../../../../plan-marshall-documentation/doc/specification/evaluation.adoc#host-values[Evaluation Reference, Hosts as Relay Starters and Workers]).

[#worker-activity]
=== What a Worker Does
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-7[PM-WORK-7: Worker Activity & Off-Track Signals], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_

The runtime starts every worker itself and receives its output as a structured stream (`headless.output.format` `stream_json` or `jsonl`), which it reads while the worker runs (link:../model-work/04-worker-launch.adoc#worker-output[Model Work Specification, Output Read While the Worker Runs]). The operator sees what a worker does from it:

* *Events, mapped per harness*: `headless.events` maps a line of the output stream onto one closed, harness-neutral list of activity kinds: `text` (what the model wrote, cut to the compiled bound), `tool_call` (the tool's name and its target: a path, a command line, a server link with its id, never its whole arguments), `tool_result` (its size and whether it failed, never its content), `file_changed` (a path of the worktree), and `turn` (its usage, read through the usage pointers, and its stop reason where the profile maps one). The stop reason is recorded as one of the closed values `end_turn`, `tool_use`, `max_tokens`, `refusal`, or `other` (any other value of the harness), so that a turn the model's safeguards declined, or one that ended with text instead of a tool call, is visible in the task's activity; it is recorded only, and no fate, outcome, re-offer, or signal is derived from it. A line that matches no mapping is counted, not shown. The server adds the entries it knows itself (the links the worker followed, its questions and answer acknowledgements, and the off-track signals and actions, link:../model-work/03-supervision-and-recycling.adoc#worker-off-track[Model Work Specification, A Worker Off Track]). The runtime never scrapes a terminal and never reads the harness's session transcript, since a worker runs without session persistence: a harness whose output gives no event stream (`output.format: json`, one result at its end) declares `headless.events: null`, and its tasks show only the server's entries.
* *Activity record*: per task an append-only activity journal in the store of the task's scope, written while the worker runs, masked, bounded, archived with the plan and deleted with it; its entries, the server's own kinds, and its bounds are defined by link:../store-schemas/16-task-queue.adoc#activity-journal[Store Schemas Specification, Activity Journal].
* *Untrusted*: the activity is untrusted data, shown as plain text and never read by a model as instructions (link:../model-work/07-untrusted-text-screening.adoc#two-level-guard[Model Work Specification, Two-Level Guard]).
* *Served to the clients*: the local API serves a task's activity from a cursor and as a live stream that a client opens only while it shows the task, below the plan or the epic (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]); the plan's process names, per leaf, its tasks with a link to their activity (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#process-resource[Runtime & Interaction Model Specification, Process Resource]).
* *Verified per harness*: the stage `events` of the profile verification checks that every mapping resolves and every expected kind appears, and records per kind `reported` or `missing` (<<profile-verification>>); recorded outputs of each harness version are parsing fixtures. Whether Antigravity's output streams its steps at all is measured there first (link:../../../../plan-marshall-documentation/doc/specification/evaluation.adoc#limits[Evaluation Reference, Limits]).

The shipped declarations: `claude` maps its `stream-json` events (`assistant` text and `tool_use` blocks, `user` `tool_result` blocks, the `result` and per-message usage as `turn`); `opencode` (2.x) maps the lines of `run --format json` _(provisional until its stage `events` has run)_: `text` from `text`; `tool_call` and `tool_result` both from `tool_use`, which the harness writes only when the call has ended (its failure from `state.status` `error`, a cut result from the tool's metadata `truncated`); `file_changed` from the files the tool metadata of `edit`, `write`, and `patch` names; `turn` from `step_finish`, which the harness writes once per model request, with its tokens and its `reason` (`stop` as `end_turn`, `tool-calls` as `tool_use`, `length` as `max_tokens`, `content-filter` as `refusal`, any other as `other`). A permission the agent's rules do not grant is rejected by the harness and arrives as a failed `tool_use`. The lines carry no version and the run no final line: the end of the run is the exit of the process; `antigravity` and `codex` declare `null` until measured.

[#profile-verification]
=== Profile Verification

_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-16[PM-WATCH-CLIENT-16]_

`pm-operator profile verify <client_id>` tests a harness on this machine and emits its profile. It is the only way a profile comes into being: the shipped profiles are its output on the release's reference machines, and the values of the link:../../../../plan-marshall-documentation/doc/specification/evaluation.adoc[Evaluation Reference] are its measurements.

*What the operator gives and what the tool finds out.* A harness's command line cannot be discovered, so the operator supplies a *draft*: a profile document in which only the statements about the harness's interface are filled in (`headless.executable`, `argv`, `env`, `mcp_config`, the `args` of each class to be tested, `inline_settings`, `output`, `usage`, `events`, `auth_probe`, `models_probe`, `model_tiers`, `install_locations`, `identity.version_probe`, `tools`, `skill_loading`). In the onboarding the draft is entered as a form (<<unknown-harness>>). Without `--draft` the effective profile of the `client_id` is the draft, which is how a profile is verified again after a harness update. Everything else the tool measures, and every statement of the draft it can test, it tests.

[source,text]
----
pm-operator profile verify <client_id> [--draft <file>] [--executable <path>]
                                       [--stage <stage>]... [--trials <n>]     [op]
pm-operator profile install <client_id> [--project]                             [op]
pm-operator profile show <client_id> [--candidate] [--project]
pm-operator profile remove <client_id> [--project]                              [op]
----

*How it runs.* The verb is a request to the runtime, which runs the stages as jobs of its own: the real job launcher, the real job relay `pm-mcp serve --job`, and the real supervisor, with compiled probe tasks in place of a plan. No project is involved: every probe worker runs in a workspace of its own that the runtime creates in the user's temporary directory (`pm-mcp-probe-<run_id>/`, mode `0700`) and removes afterwards; it lies outside `<PM_MCP_BASE>`, which no job may read or write, and it is the only project root in the worker's write set. The harness uses the operator's own login, so a run costs model tokens; the verb prints the stages, the number of worker starts, and the trials before it starts and asks for confirmation. A probe worker is confined like every job where the platform has a confinement.

*Stages* (a closed list; `--stage` selects, default all in this order; a stage whose prerequisite failed is `not_run`):

[cols="1,4,3"]
|===
|Stage |What it does |Profile values it settles

|`identity`
|Runs `identity.version_probe` without a shell and matches `version_pattern`.
|`identity`, the harness version of the record

|`detection`
|Starts the harness with a probe MCP server and a task to run, through its shell tool, the probe command the stage writes into the probe workspace. Each of the two records the *names* of its environment variables, never a value. Compared with the environment the harness was started in, the names the harness added are the candidate signals.
|`detection.primary_signals` as proposals the operator confirms at install; `detection.reaches`, measured

|`launch`
|Starts one worker from the draft's `argv`, `env`, and `mcp_config`: it connects through the job relay, takes the base task, and submits it. Checks that the structured result parses, that every line of the output has the declared format, and that the worker exits on `SIGTERM` during a held wait without leaving a relay behind; runs the draft's `auth_probe` and `models_probe` and checks their exit codes and output format.
|`headless.argv`, `env`, `mcp_config.delivery` and `path`, `output`, `capabilities` (`result_schema`, `usage_fields`, `cost_field`, `exit_reliable`, `ephemeral`), `session_residue`, `auth_probe`, `models_probe`

|`events`
|Only for a draft whose `headless.events` is not `null`. Runs the base task and a task that calls a tool, fails one call, changes a file, and asks, and checks that every mapping of `headless.events` resolves on the real output and every expected activity kind appears (<<worker-activity>>).
|`headless.events`, recorded per activity kind as `reported` or `missing`

|`egress`
|Starts the `launch` base task with the worker's egress proxy admitting only the draft's `headless.endpoints`, then a task that asks the worker to fetch a decoy host through its shell, once through the configured proxy and once directly (proxy variables unset). Checks that the base task passes through the proxy without a name lookup of its own (link:../job-runtime/02-confinement-and-environment.adoc#worker-name-resolution[Job Runtime Specification, Name Resolution]), that the proxied decoy request reached the proxy and was refused, and that the direct request found no route (on a platform with enforced egress; with unenforced egress the stage records `unenforced` and the direct request is not scored).
|`headless.endpoints`

|`isolation`
|Starts a worker beside a decoy MCP server entered in a harness configuration file of the probe workspace, and a decoy instruction file of the project; for each of `writer` and `read_only`, with the class's launch, also beside a decoy hook and a decoy plugin enabled in the project's and in the user's harness settings, each of which writes a canary file when it runs, a decoy `env` block that sets a model endpoint, a proxy, and a canary variable, a decoy user instruction file and a decoy user skill in every user-level location the harness reads (its home directory and the user-scope locations of the host integration table, independent of the data home of the launch, <<user-level-files>>), and a project instruction file and skill the task asks about. Records whether the worker listed or called a decoy tool, whether it followed a decoy instruction, whether it knew the decoy user skill, whether a canary file exists, and whether the worker knew the project instruction and skill.
|`mcp_config.exclusive`, `capabilities` (`project_settings_control`, `extension_isolation`: no decoy tool, no canary file, no request to the decoy endpoint or proxy, the canary variable absent, no decoy user instruction followed and no decoy user skill known, and the project instruction and skill loaded)

|`classes`
|For each class with `args` in the draft. `writer` and `read_only`: the task asks for one tool inside the role's tool set and one outside it; the tool set is `enforced` when the outside call is refused or the tool is absent, `advisory` when it succeeds. `zero_tool`: the task text asks the worker to read a canary file, to run a command, and to call a tool of the probe server; the class is runnable only when the output shows no tool call, the probe server saw no connection, the decoy instruction was not followed, and the answer does not contain the canary.
|`headless.classes`, `worker.restricted_models` (the models the stage ran with)

|`limits`
|Offers task inputs of 8,000, 32,000, and 128,000 characters and checks that the submitted result names the identifier at the end of each.
|`headless.tool_result_limit_chars`, `resource_tools`

|`paths`
|Only where the platform confines jobs. Runs the base task with the write set of the draft's `writable_paths` and the worker read set with the draft's `readable_paths`, and reports every write and every read the confinement denied and every declared path that was not written or read. Then a task asks the worker to read, through its shell, a decoy file the stage places in the home directory outside the read set; the read must fail and the decoy's content must not appear in the output.
|`headless.writable_paths`, `readable_paths`, `data_home`

|`resumability`
|Only for a harness whose draft declares a form. A worker on a probe task asks through the `ask` link after it has read a canary of the probe workspace. *Hold*: the stage answers after one, two, and the longest bounded-wait windows the operator chose, and checks that the same generation continues, applies the answer, and names the canary without reading it again. *Resume*: the worker ends, and after the chosen delays a generation started from `resume.argv` on the session id read from the result continues, applies the answer, and names the canary; a resume of a missing session and of a session older than the chosen limit must fail at once, never hang. A harness whose resume of a missing session starts a new session and exits `0` instead fails this check (the link:../../../../plan-marshall-documentation/doc/specification/evaluation.adoc#results[Evaluation Reference], R2, names the harnesses that did): the server could then not tell a lost session from a continued one (link:../model-work/06-envelopes-questions-deadlines.adoc#continuation[Model Work Specification, Resume refused]). On a harness whose output shows no tool call a re-read of the canary cannot be seen (link:../../../../plan-marshall-documentation/doc/specification/evaluation.adoc#results[Evaluation Reference], R1). Records the usage of every wake-up and resume.
|`headless.resumability`

|`faults`
|The fault matrix of link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-TEST-4[PM-TEST-4] with `--trials` trials per fault (default and minimum for eligibility: `10`), two workers at once: exactly-once submit, exit detection, stall detection by silence, fencing of late calls, and the acknowledgement latency.
|`worker.eligible`, `ack_deadline_seconds`, `ack_informational`, `silence_grace_seconds`, `idle_wakeups`; `connection` timing values
|===

*Endpoint harnesses.* A draft whose profile is an endpoint profile is verified by the stages of
link:03-endpoint-harness.adoc#endpoint-verification[Endpoint Harness § Verification of an Endpoint] — `identity`,
`launch`, `classes` and `limits` — and not by the stages above: an endpoint harness has no process to launch, no tool and
no session. The endpoint profile's members are settled as that section states; its `profile_kind` tells the two kinds
apart (link:03-endpoint-harness.adoc#endpoint-profile-schema[Endpoint Harness § Endpoint Profile Schema]).

*Output.* The run writes a candidate profile `<PM_MCP_BASE>/profiles/candidates/<client_id>.json` and its verification record beside it, and changes nothing that is in force.

[source,json]
----
{
  "format_version": 1,
  "client_id": "antigravity",
  "profile_schema_version": 1,
  "profile_digest": "sha256:9f2c…",
  "verified_at": "2026-10-08T08:36:00Z",
  "tool": { "version": "0.4.0", "commit": "02ffcbd22b43de8d673b3b6abe77f755a1442398" },
  "harness": {
    "executable": "agy",
    "version": "1.3.1",
    "executable_sha256": "sha256:41d0…",
    "models": ["gemini-3.8-flash-low"]
  },
  "platform": { "os": "linux", "arch": "x86_64", "confinement": "landlock", "landlock_abi": 8 },
  "stages": {
    "identity":  { "status": "passed" },
    "detection": { "status": "passed" },
    "launch":    { "status": "passed" },
    "events":    { "status": "passed", "results": { "text": "reported", "tool_call": "reported", "tool_result": "reported", "file_changed": "missing", "turn": "reported" } },
    "egress":    { "status": "passed" },
    "isolation": { "status": "passed" },
    "classes":   { "status": "passed" },
    "limits":    { "status": "passed" },
    "paths":     { "status": "passed" },
    "faults":    { "status": "passed", "trials": 10 }
  },
  "values": [
    { "pointer": "/headless/classes/zero_tool", "status": "measured", "code": "launch_without_tools_refused" },
    { "pointer": "/headless/classes/writer/tool_set", "status": "measured", "code": "outside_call_succeeded" },
    { "pointer": "/detection/primary_signals", "status": "confirmed", "code": "added_for_commands_only" },
    { "pointer": "/worker/silence_grace_seconds", "status": "measured", "code": "stall_detected", "figures": { "min_ms": 50050, "max_ms": 50090, "trials": 10 } }

----

* `stages.<stage>.status` is `passed`, `failed`, or `not_run`. `values` holds one entry per profile value a stage settles, with `status` `measured` (the tool determined it), `confirmed` (a proposal of the tool the operator confirmed at install), `declared` (taken from the draft, because the tool cannot test it), or `not_measured` (its stage failed or did not run).
* *Kept with the enrolment*: the per-kind result of `events` is kept with the harness's enrolment when the verified profile is installed for an enrolled harness (link:../store-schemas/11-enrolment-store.adoc#harness-enrolment-store[Store Schemas Specification, Harness Enrolment Store]) and shown wherever the enrolled harnesses are listed; the per-figure result of the verification stage `usage`, with its `start_context`, reaches the enrolment's `usage_report` through the install path owed to `machine-onboarding-unit`. Recorded outputs of each harness and version, taken by these stages, are parsing fixtures of the build, so that a changed output format fails a test.
* *What ran is tracked exactly*: `tool` names the release and the commit of the `pm-mcpd` that ran the verification, taken from the binary and never from an argument; `harness` names the executable by its name, the exact version its version probe printed, the SHA-256 of the executable file the run started, and every model a stage ran with; `platform` names operating system, architecture, and confinement. The record holds no path, no host name, no user name, no environment value, and no model output.
* *The record is closed data*: its schema admits no free text. `code` is a value of the closed list of outcome codes of its stage, `figures` holds integers under a closed set of keys (`min_ms`, `max_ms`, `trials`, `chars`, `count`), and the `results` of the stage `events` hold, under the closed activity kinds, one of `reported` and `missing`. A record with an unknown member, an unknown code, or a string that is not one of its closed forms is refused.
* *The candidate claims only what was measured*:
** `worker.eligible` is `true` only when `faults` passed every fault with at least 10 trials on a platform with a confinement (Landlock on Linux, the sandbox profile on macOS), `paths` passed, and `egress` passed or recorded `unenforced`; otherwise it is `false`, whatever the draft says. A record with `egress: unenforced` makes the harness eligible only while the operator's acceptance of unenforced egress holds for the machine (see *Runtime check on load* below).
** `headless.classes.zero_tool` is non-null only when the `classes` stage passed it and `isolation` measured an exclusive configuration with settings control; otherwise `null`.
** A `writer` or `read_only` class is non-null when its base task passed and `isolation` measured an exclusive configuration with extension isolation for its launch, with the `tool_set` the stage measured.
** `tool_result_limit_chars` is the largest size that passed when a larger one failed, else `null`.
** A value whose stage did not run keeps the draft's value with `status: declared` where the schema requires one, and the three claims above fall back to their closed side.
* *Install*: `pm-operator profile install <client_id>` shows the candidate against the effective profile value by value, lists every value that is `declared` or `not_measured`, asks the operator to confirm the proposed detection signals, and on confirmation moves candidate and record into the machine set (<<profile-sets>>) under the lock of the machine store. The runtime loads it for workers started afterwards; running workers keep the profile of their job record.
* *Runtime check on load*: the runtime honours a machine profile's `worker.eligible: true` and a non-null `zero_tool` only when its record shows the stages above as `passed` for the platform the runtime runs on, the `egress` stage as `passed` or as `unenforced` while the operator's acceptance of unenforced egress holds for the machine (link:../job-runtime/02-confinement-and-environment.adoc#worker-egress[Job Runtime Specification, Worker Egress Proxy]; when the acceptance is withdrawn, no further worker of that harness starts); a record from another platform leaves the profile usable for detection and rendering and its harness ineligible for workers.

[#unknown-harness]
=== Unknown Harness
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-5[PM-CLIENT-5: Versioned Client Profile Schema & Override Hierarchy], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-1[PM-CLIENT-1: Harnesses as Workers & Client Identity], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-8[PM-SEC-8: Consent Before Acting]_

A machine whose harness has no shipped or installed profile can still be onboarded: the onboarding's `harness.add` offers it beside the found harnesses as a secondary choice, and directly when the scan found none.

* *The draft as a form*: `harness.add` takes the draft in either client as a form instead of a file: the executable (its absolute path), a client id and a display name, and the interface statements the verification needs from the operator (the headless arguments, the environment, the MCP configuration, the output and usage format, the version probe, and where known the login probe, the models probe, and the tiers), prefilled from the profile of the known harness the operator picks as the closest. The form validates every field as profile validation does (<<profile-hardening>>) before anything runs.
* *Verified, stage by stage*: `harness.verify-profile` runs the profile verification (<<profile-verification>>) as a sub-workflow of the onboarding, after the consent `verify_harness_profile` of `harness.add-consent`, which states the expected tokens of the run; both clients show each stage as a line with ✓ or ✗, and a failed stage names the draft field it concerns, back to the form.
* *Installed and enrolled*: the verified profile is installed into the machine profile set (<<profile-sets>>) and its harness enrolled like a found harness (<<harness-scan>>); it is eligible as a worker host only where the verification shows it, and otherwise shown and marked like every ineligible harness.
* *No closed list refuses it*: no closed list of client ids (the scan, the enrolment, the role validation, the profile sets, the views) refuses a harness the operator added; a client id is valid where it matches the pattern of `client_id` and names a profile of the effective set. A client bundle exists only for the hosts the release ships a bundle for (xref:../../../../plan-marshall-documentation/doc/specification/host-integration/02-bundle-manifest.adoc[Bundle Manifest]); an added harness runs as a worker without one, since the runtime composes every worker's launch itself.

[#profile-hardening]
=== A Profile Is Untrusted Input

Implemented by `ProfileValidator` and the bounded reader of `pm-core`: closed shape, bounded strings, the
model-readable character set, the launch and path rules, the one pattern, and the refusing fixture of each rule. See
link:../../../pm-core/doc/developer/core-profile.adoc[Client Profiles Developer Guide].

*Claims.* No value of a profile is believed because the profile says so: `worker.eligible`, a runnable `zero_tool`
class and an `enforced` tool set count only with the stages of the bound record `passed` on the runtime's platform
(<<profile-verification>>). The profile loader carries the record, its platform and its stages with the loaded profile;
`ProfileWorkerEligibility` in `runtime.worker` consults it before every start and refuses an ineligible profile
(link:../../../pm-runtime/doc/developer/runtime-worker.adoc[runtime.worker Developer Guide]).

[#profile-override-hierarchy]
=== Profile Override Hierarchy

The runtime resolves a client profile from four layers in order of increasing precedence:

1. *Compiled Binary Baseline* (`classpath:/profiles/<client_id>.json`): The profile documents compiled into the binaries (<<harness-as-data>>).
2. *Machine Profile* (`<PM_MCP_BASE>/profiles/<client_id>.json`): A verified profile the operator installed on the machine; it replaces the compiled document of the same `client_id` as a whole (<<profile-sets>>).
3. *Project Profile* (`<PM_MCP_BASE>/projects/<project_id>/profiles/<client_id>.json`): A verified profile the operator installed for one project; it replaces the machine or compiled document as a whole for that project's workers (<<profile-sets>>).
4. *Machine-Wide Operator Overrides* (`machine-config.json`, the closed object `client_profiles.<client_id>.connection`, link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration]): Optional override of the connection settings `bounded_wait_seconds`, `idle_timeout_seconds`, and `progress_resets_timeout` across all repositories on the workstation, set with `pm-operator config`. No other profile key can be overridden: the `worker` block, the `headless` block, and the `detection` and `identity` objects that form the host-detection table (xref:../../../../plan-marshall-documentation/doc/specification/host-integration/01-host-detection.adoc#host-detection-table[Host-Detection Table]) are never touched by an override.

Harness, model, and effort of a worker come only from the operator's role configuration, the role's effective values (its artifact, the role assignments, and the plan's override; link:../model-work/01-roles-and-configuration.adoc#role-assignment[Model Work Specification, Role Assignment]), operator files, rendered into the `{{model}}` and `{{effort}}` slots of `headless`; a profile carries no model choice beyond the map of the default assignment's tiers (<<model-tiers>>). A change of the role configuration applies to the next worker of the role; nothing is re-installed. No git-tracked configuration carries client profile overrides, role sets, or model pins (`PM-WORK-1`, `PM-EXT-6`); the closed team schemas admit no such key, so a `client_profiles` block in a team file is the finding `unknown_config_key` (`config_invalid`).
