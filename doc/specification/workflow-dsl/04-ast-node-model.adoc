== AST Node Model
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-16[PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-IMPL-1[PM-IMPL-1: Decoupled Plain-Java Core Engine & Quarkus Assembly]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-IMPL-5[PM-IMPL-5: Declarative Workflow DSL & Automated Diagram Generation]_

The tree a unit is parsed into is implemented in link:../../../pm-workflow/src/main/java/de/planmarshall/workflow/ast/package-info.java[`de.planmarshall.workflow.ast`]: immutable Java records, sealed interfaces, and enums, from `WorkflowDefinition` down to `OutcomeTransition`, every node the parser reads carrying its `SourceLocation`, among them every `declare` line, recorded in `WorkflowDefinition.declarations` as a `ValueDeclaration` (the value with its location), and every `decide` line, a `DecisionDeclaration.Ask` or `DecisionDeclaration.Quorum` with its location; the tree, the parser, and the printer are documented in link:../../../../plan-marshall-documentation/doc/developer/workflow-dsl.adoc[Developer Guide § The Workflow Language]. The tree checks only its own immutability. The following constraints on its values are checked by the static verification (<<static-verification-rules>>), the loader of the machine's and the project's units (<<project-owned-units>>), and the composition of a plan instance (xref:09-plan-instance.adoc#plan-instance[Plan Instance]):

* *Definition*: every unit is one file and declares one DSL format (`formatVersion`); `derivedFrom` is filled only for a copy held at machine or project level that was taken from another level, with the revision it was taken from; `declarations` occur only in a unit with a compiled declaration schema and `decisions` only in the unit `adjudicate.decisions` (xref:02-units-jobs-decisions.adoc#unit-declarations[Unit Declarations]).
* *Frontmatter*: every definition carries the frontmatter of its file, its entry bindings, and its start state when it has no entries (link:../../../pm-workflow/doc/developer/workflow-ast.adoc[Workflow AST Developer Guide]).
* *Values*: a `CallValue.EnumList` holds distinct members; a `DecisionDeclaration.Quorum` lists `1` to `3` distinct roles with a score of `50` to `100`.
* *States*: a state carries no phase (xref:01-grammar.adoc#state-phase[Phase of a State]); `terminalOutcome` is present exactly when the state is terminal. A `ModelJob` of the form `role each` occurs only in the unit `adjudicate.decisions`; for a state that declares `ask`, the loader adds the engine-made question state `<state>.asked` of class `ask` with the transition `asked -> <state>.asked` (xref:02-units-jobs-decisions.adoc#model-job-states[Task States], item 8). A `QuestionWait` declares no links.
* *Links*: the relation `ESCALATE` names only the `request_waiver` link, which files a request and never awaits an answer; `CONSULT` is rendered from a `consult role` clause and never declared; `ABORT` is only the implicit `step_out` the operator follows in an operator wait of a sub-workflow (Rule 12); every declared `link` clause is an operator link (Rule 10).
* *Scopes*: `WorkflowScope` has the members `PLAN`, `EPIC`, `WORKSPACE`, `MACHINE`, `ENTITY`, and `SUBWORKFLOW` (xref:01-grammar.adoc#machine-scope[Machine Scope]).
* *Instance header*: the parser checks the structure of the instance header schema (link:../store-schemas/14-plan-instance-waivers-questions.adoc#plan-instance[Store Schemas Specification, Plan Instance]); its remaining checks run where the version is composed.

[#guard-results]
==== Three-Valued Guard Results

The three guard values, their propagation through `and`, `or`, and `not`, the `guard_indeterminate` condition that a guard which could not be evaluated raises on the current state (<<condition-overlays>>), and the result guards that always decide are implemented in the workflow engine and documented in link:../../../pm-workflow/doc/developer/workflow-engine.adoc#_guards[Workflow Engine Developer Guide § Guards]. A guard cannot be evaluated when a built-in guard's input cannot be read, a `predicate:` primitive fails or times out, or a configuration key cannot be read. A link is offered, and its transition fires, only on `HELD`; `NOT_HELD` omits the link (`PM-WF-3`); an undecided link is neither offered nor refused silently.

[#condition-overlays]
=== Condition Overlays (Engine-Owned)
_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-14[PM-WATCH-DSL-14]_

A condition is an engine-owned overlay on the scope's current state, not a state: `integrity_breach`, `footprint_violation`, `job_incomplete`, `config_drift`, `guard_indeterminate`, and `precondition_unmet` (link:../state-catalogue/01-conventions-generic-conditions.adoc#state-catalogue-conditions[State Catalogue, Conditions]). The engine raises it where the condition arises (a digest check of a plan, epic, workspace, or lesson store, of a pending entry, or of an enrolment file, the footprint check of `git.stage-and-commit` (xref:06-reusable-sub-workflows.adoc#_six_stage_execution_contract_of_git_commit_and_push[Six-Stage Execution Contract of `git.commit_and_push`], Stage 4) or of a task `submit` (xref:05-primitives.adoc#independent-transition-validation[Independent Server-Side Transition & Parameter Validation (`PM-WF-6`)] item 6), a planning transition guard, a task attempt that ended without its required submission (xref:02-units-jobs-decisions.adoc#model-job-states[Task States]), an indeterminate derived fact, a phase handshake, a missing credential, a guard that could not be evaluated (<<guard-results>>)) and records it in `mcp/status.json` as `pending_condition` (`kind` from the closed `ConditionKind` enumeration, `facts`, `raised_at`, `remedy_attempts`, link:../store-schemas.adoc[Store Schemas Specification]). How the engine raises a condition without changing the scope's position, and unwinds the call stack when a budget is spent, is documented in link:../../../pm-workflow/doc/developer/workflow-engine.adoc#_guards[Workflow Engine Developer Guide § Guards] and link:../../../pm-workflow/doc/developer/workflow-engine.adoc#_call_stack_and_exit_contracts[§ Call Stack and Exit Contracts]. A condition is no operator wait: it has its bounded self-remedy and fallback; where only the operator can remove its cause, both clients show it as a hold with its acts (link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue, Holds and Their Acts]).

* *Rendering*: While a condition is set, the representation keeps `state` as the current state id, carries the field `condition` naming the kind (link:../hypermedia-format/01-representation-and-link-forms.adoc#canonical-top-level-fields[Hypermedia Format Specification]) and the condition's `facts`. The self-remedy is server logic in every scope, so the view offers no link for it, and every task entity of the scope keeps its own links. While a condition is set on an operator wait, the wait's operator links are answered with `link_not_available`; the operator sees the hold and its acts instead.
* *Integrity pause*: `integrity_breach {kind: store_tampered | enrolment_tampered, store, recorded_size, current_size, recorded_digest, current_digest}` offers no link at all, and every `pm_do` of the paused scope is rejected with `integrity_paused`; a tampered plan, epic, or workspace store, lesson, or pending entry record pauses that scope (or the lesson source), a tampered enrolment file every running plan of the project. Both clients show it as the hold `integrity_pause`, whose act accepts the edit (the engine re-verifies the digests before it clears the condition); a plan or an epic also offers cancel (the engine-owned transition into `plan.aborted` or `epic.aborted`), and a pending entry its abandonment (link:../state-catalogue/01-conventions-generic-conditions.adoc#state-catalogue-conditions[State Catalogue, Conditions]). The pause has no bound and no fallback (xref:02-units-jobs-decisions.adoc#waivers-and-integrity[Waivers, Waiver Requests & the Integrity Pause]).
* *Bounded self-remedy*: Every other condition is bounded by the compiled self-remedy budget of `3` attempts per condition instance (`remedy_attempts`); the operator may fix the cause at any time. In a plan or an epic the server runs the self-remedy itself: it retries where a retry can clear the condition (`guard_indeterminate` re-evaluates every guard of the state, `precondition_unmet` re-checks its precondition after the compiled backoff (link:../timeouts/01-job-budgets-and-waits.adoc#server-retry-backoff[Timeouts & Budgets Specification, Server Retry Backoff]), `job_incomplete` re-offers the task, xref:02-units-jobs-decisions.adoc#model-job-states[Task States]), and where clearing it needs work, it creates a task of the role whose work raised it (`footprint_violation`: a task of the plan's writer role that reverts the offending changes, after which the check runs again); `config_drift` is resolved by the server: it adopts when the re-composed instance version verifies and contains the scope's position, and keeps the version in force otherwise (item 4 of <<project-owned-units>>), recording the choice in the audit log and the composition log (link:../store-schemas/14-plan-instance-waivers-questions.adoc#plan-instance[Store Schemas Specification, Composition Log]). A self-remedy that succeeds clears the condition and re-renders the current state. When the budget is spent, the engine takes the phase's fallback route with the condition recorded as the gap (`cause: condition`, with the condition kind): at plan scope the unwind of every call frame above the phase's frame to the phase's fallback (xref:01-grammar.adoc#sub-workflow-exits[Sub-Workflow Exit Contract]) records the server step-out `stepped_out {by: server, cause: condition}`; `handed_back` degrades to a local branch when the fallback itself needs what is missing (a push credential). After the merge there is no fallback: the condition's step is re-fired or owed (xref:03-reference-excerpt.adoc#_reference_workflow_dsl_excerpt_finalize_pmwf[Reference Workflow Excerpt], shared failure state). The epic, workspace, and machine scopes and the entries have no fallback end: a condition of theirs is retried by the server at the compiled backoff until its cause clears, shown to both clients as a hold with its acts, and ends by the operator removing the cause or, for an epic, by its cancel, and for an entry by the operator abandoning it; workspace setup failures are routed by `setup.needs-repair` (link:../domain-extensions/04-setup-state-machine.adoc[Domain Extensions Specification, Project Setup State Machine]).
* *Not Declared in DSL Units*: Conditions are never declared in a `*.pmwf` unit and are never a transition target. A DSL transition whose target names a condition or one of the reserved state ids `<phase>.blocked`, `<phase>.footprint-violation`, and `<phase>.config-drift` fails validation (Rule 3).

[#static-verification-rules]
=== Static AST Verification Rules (Build Time & Every Unit Load)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-5[PM-WF-5: Model Work as Role Tasks & Single-Level Leaf Constraint]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-16[PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-IMPL-5[PM-IMPL-5: Declarative Workflow DSL & Automated Diagram Generation]_

_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-1[PM-WATCH-DSL-1], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-3[PM-WATCH-DSL-3], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-4[PM-WATCH-DSL-4], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-5[PM-WATCH-DSL-5], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-8[PM-WATCH-DSL-8], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-9[PM-WATCH-DSL-9], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-11[PM-WATCH-DSL-11], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-15[PM-WATCH-DSL-15], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-16[PM-WATCH-DSL-16], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-29[PM-WATCH-DSL-29], link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-32[PM-WATCH-DSL-32]_

`WorkflowValidator` verifies every `WorkflowDefinition` in JUnit build tests (the default units), on every load of the machine's and a project's units (<<project-owned-units>>), on every validation the operator asks for and before every placing of a unit (<<process-designer>>), and on every composed plan instance version (xref:09-plan-instance.adoc#plan-instance[Plan Instance]), failing closed if any rule is violated; a unit of the machine or project level and an instance version are additionally checked against the compiled invariants. A `WorkflowDefinition` is always a complete definition unit, one file (xref:02-units-jobs-decisions.adoc#workflow-definition-units[Workflow Definition Units]): the plan unit, a phase, a plan instance's composed unit, another top-level workflow, or one sub-workflow. Rules 8, 9, and 11, which follow paths, follow them through the calls of a unit into its callees (the plan unit into its phases, a phase into the axis variants and sub-workflows it calls), so a path that a call splits across units is checked as one.

The parts of Rules 1, 2, 3, 5 and 6 stated as implemented below are checked by `WorkflowValidator` in the package link:../../../pm-workflow/src/main/java/de/planmarshall/workflow/verify/package-info.java[`de.planmarshall.workflow.verify`] and documented in link:../../../../plan-marshall-documentation/doc/developer/workflow-dsl.adoc#verification[Developer Guide § Static Verification]; every statement that remains below is not implemented yet:

1. *Primitive Binding & Parameter Equivalence*: Implemented: primitive binding of `do`, `auto`, `job`, `composite_job`, `facts`, and `predicate:`, and the free-parameter match of every `LinkSpec` (see above). Every `job llm` entity kind must resolve to a registered entity kind with its entity unit and return-evaluation primitive, and every `each` primitive of a `job llm` state to a registered read-only list primitive; the form `role each <primitive_id>` is admitted only in the unit `adjudicate.decisions`, and its primitive must be a registered read-only primitive that returns role names. The `ask` declaration (`ModelJob.ask`) is refused on a `role each` state (a vote task never asks) and on a state whose entity kind has no entity unit (the zero-tool kind `screen`); its role's class is checked at composition (Rule 13). Every role name of a `job llm` state and of a `consult role` clause must match the role-name grammar of the link:../identifiers/01-general-rules-and-registry.adoc[Identifier Registry]; whether the role exists is checked at composition (Rule 13), never at unit load, because the role set is operator configuration. Every `ParamType.SchemaRef` (`schema[<schema_name>]`, in a link's free parameters or a sub-workflow's `result` declaration) must name a schema registered in the Named Parameter Schemas (link:../hypermedia-format/02-link-grammar.adoc#named-parameter-schemas[Hypermedia Format Specification]); an unknown schema name fails validation with the source file and line. Every question clause names a registered question class. Every primitive that declares `enqueuesJob()` must declare its job-starting outcomes (at least one, for example `started`, `rerun_started`, or `concurrent_restarted`), and every transition of a declared job-starting outcome must target a `job` or `composite_job` state, which binds the returned job id instead of starting a job (xref:02-units-jobs-decisions.adoc#job-state-binding[Job State Entry & Binding (`JobStep`)]); no other outcome of such a primitive may target a job state.
2. *Exhaustive Outcome Coverage*: Implemented: the bijection of the transitions of every `auto`, `job`, `composite_job`, and `link` action with the outcomes of its primitive, `cancelled` of a job included (see above); `cancelled` is the outcome of a cancellation by the engine (xref:02-units-jobs-decisions.adoc#implicit-job-links[Implicit Links]). A `job` state's constants are exactly the `PM-EXEC-4` set. The transitions of a `job llm` state form the bijection with the outcomes of the entity kind's return-evaluation primitive, which the task's completion runs, plus the reserved outcome `lost` (no `cancelled` transition; in a fan-out state the evaluation runs at every task's end, and the state takes its outcome over the whole list once every task has ended); `lost` may be left undeclared only in a unit of `scope plan` and in a sub-workflow only plan-scope units call (the phases among them), where the engine routes it to the phase's fallback (xref:02-units-jobs-decisions.adoc#model-job-states[Task States] item 4); on a state that declares `ask`, the outcome `asked` is covered by the engine-made transition `asked -> <state>.asked` and declaring it fails validation, and on a state without `ask` the evaluation has no `asked` outcome; the transitions of a question clause form the bijection with the closed resolution outcomes of its class (xref:02-units-jobs-decisions.adoc#question-states[Question States & Decisions]). For these, too, a missing outcome and an unknown outcome name fail validation with the source file and line number.
3. *Graph Integrity*: Implemented: the graph reachability of every `StateNode` from the unit's start state or from its entry-bound states, the abort terminals `plan.aborted` and `epic.aborted` counting as reachable from every state; the path of every non-terminal state to a `terminal` state, the implicit `step_out` of an operator wait of a sub-workflow and the default `lost` route of a task state counting as such a path, and in a `scope workspace` unit the path of every state back to `startState`; not implemented yet: in a `scope machine` unit the path of every state to its resting state `onboard.completed` and back to it from every state reached from it (xref:01-grammar.adoc#machine-scope[Machine Scope]); the uniqueness of the declared link identifier patterns within a state, the implicit `step_out` included (see above). State identifiers must be unique across all files of the definition unit, the engine-made question states `<state>.asked` of the states that declare `ask` included. `startState` and every `OutcomeTransition.targetStateId` must exist in the unit's `states` (a cross-file target within the plan workflow is valid; a target inside another unit or inside a sub-workflow is not). Reachability is checked for every combination of the values of the configuration keys that the unit's guards declare in `depends_on_config` (every enum value, `true` and `false` for a boolean): a state or outcome transition that no combination reaches fails validation, and one that some combinations do not reach is reported with those combinations. Reachability is graph reachability under those combinations only; it never evaluates the feasibility of a primitive outcome or of a bound call parameter. The abort terminals are entered by the engine-owned operator transition: no transition may target `plan.aborted`, and `epic.aborted` is targeted by exactly one declared transition, `abort_landed` of `epic.next-work`, which ends the epic's archive path after the epic's cancel. The implicit `step_out` is rendered only on an operator wait of a sub-workflow a workspace, machine, or entry unit calls, and the workspace and machine units declare no terminal state because they are resident. Implemented: the interface rules of the frontmatter and the type check (link:../../../pm-workflow/doc/developer/workflow-verify.adoc#interface-rules[Workflow Verification Developer Guide § Interface Rules and Unit Types]), except the machine unit (xref:01-grammar.adoc#interface-rules[Interface Rules]). Every `skill` clause must resolve to a vocabulary skill in the compiled corpus, and the implicit links `ack`, `consult:<role>`, and `infeasible` count in the uniqueness of the link identifier patterns of their state. Condition overlays (<<condition-overlays>>) are engine-owned and need no target in `states`: a transition whose target names a condition kind or one of the reserved state ids `<phase>.blocked`, `<phase>.footprint-violation`, and `<phase>.config-drift` fails validation.
4. *Single-Level Leaf Task Constraint (`PM-WF-5`, `PM-WORK-4`)*: No unit a worker acts in (the entity unit of every entity kind a `job llm` state names, `worker-task`, and every sub-workflow such a unit calls) contains a `StateBehavior.ModelJob` state or a link whose transitions enter one. A consultation task offers no `consult` link (consultation depth one), and a `consult role` clause never names a role whose class is `zero_tool` (checked with the role's existence, Rule 13). At runtime a worker's connection is refused every link outside the task entities leased to its generation. Workers are leaves and never start a model, each task of a fan-out state included; a consultation is a task the server creates.
5. *Backwards-Compatible State Migration*: Implemented: every state name of the released-states baseline the verifier is given exists in `states` or appears as `oldStateId` in a `migrate <old> -> <new>` declaration whose target exists in `states` (see above). The baseline is the committed `released-states.txt`. The rule applies to the default units; an in-flight plan of a project whose unit dropped or renamed a state keeps executing its instance version in force (xref:09-plan-instance.adoc#plan-instance[Plan Instance], position rule). The baseline and its gate: xref:07-loop-back-diagrams-verification.adoc#state-name-migration[State-Name Migration Registry].
6. *Sub-Workflow Entries, Exit Contract & Parameter Binding (`PM-WF-16`)*: Implemented: the entry a call names and the exit contract of its callee, the exits the callee's frontmatter declares plus the control outcome `stepped_out` (link:../../../pm-workflow/doc/developer/workflow-verify.adoc#interface-rules[Workflow Verification Developer Guide § Interface Rules and Unit Types], link:../../../pm-workflow/doc/developer/workflow-verify.adoc#_the_exit_contract[§ The Exit Contract]). Every `StateBehavior.SubWorkflowCall` must reference a registered `WorkflowDefinition` whose `scope == WorkflowScope.SUBWORKFLOW` (xref:01-grammar.adoc#sub-workflow-exits[Sub-Workflow Exit Contract]). Every call site routes each outcome of the contract: exactly once, or twice with the complementary result guards `guard result.<f>` and `guard not result.<f>` over a boolean or optional field `<f>` of the callee's result schema; a result guard on any other transition, or on an outcome other than `done`, fails validation. `stepped_out` targets, at a phase's call site in the plan unit, the plan's fallback (`plan.return`, or the call of `phase-6-finalize` through its entry `hand_back`; xref:01-grammar.adoc#sub-workflow-exits[Sub-Workflow Exit Contract]); inside a phase, the phase's fallback state (`finalize.hand-back`) or a terminal of the phase that ends it with `stepped_out`; inside a `scope epic`, `scope workspace`, or `scope machine` unit, an entry's unit, or a bootstrap unit (which have no fallback end) a resting state of the calling unit (for example `epic.active`, `setup.commit-changes`, `project.completed`, `settings.choose`, or the entry's choice of its sources); or, inside another sub-workflow, a state of the same unit that handles the failure: one that continues the unwinding (a server step-out terminal, or an operator wait whose own `step_out` continues it), the unit's budget re-check in a remediation unit (`INV-REM-4`, xref:08-remediation-units.adoc#remediation-invariants[Compiled Invariants of Remediation Units]), or a domain terminal of class `failure`; never a terminal state of class `success` and never a state that continues the flow as if the call had succeeded. The outcome id `stepped_out` is declared only by a terminal of class `stepped_out`, and every other outcome id of a sub-workflow terminal is a domain outcome its callers continue on differently. The `paramBindings` of every `call` site are checked against the target's `params` (`param` declarations): every declared parameter must be bound exactly once, no binding may name an undeclared parameter, and every bound value must match the declared type (membership in the `enum[…]` value set, an integer within the declared `int` range, or a non-empty list of distinct members of a `list<enum[…]>`). *Guided step-in*: a task state takes its skill from its `skill` clause or, where it declares none, from its entity kind; an operator wait asks the operator, never a model, and declares no `skill` clause.
7. *Acyclic Call-Graph DAG & Bounded Depth (`PM-WF-16`)*: Across all registered `WorkflowDefinition` instances, the static `call` graph must form a strict directed acyclic graph (DAG) with zero cycles and a maximum static call-stack depth $\le 5$, the plan unit's phase calls being the first level (a recipe's workflow likewise for its phases, the machine unit for its aspects).
8. *Gate Artifact Producer Coverage*: For every guard or gating primitive that declares a required artifact (`requiredArtifacts()`, for example `pr_title` or `outline.md`), every path from the unit's `startState` to that guard or state, including recipe and lane shortcuts, must pass a state whose primitive declares the artifact in `producedArtifacts()`. A path without a producer fails validation, so a gate can never refuse for an artifact its lane could not produce.
9. *Step Completion Once per Firing & Failure Outcomes Never Map to Success*: Every outcome constant of every primitive and `composite_job` outcome set declares an `OutcomeClass` (xref:05-primitives.adoc#primitive-outcome-classes[Outcome Classes & Step Records]), and every terminal state declares its class in `terminal <outcome_id> <outcome_class>`; a sub-workflow's terminal class is the class of the matching outcome at its `call` sites, and `stepped_out` has the class `STEPPED_OUT`. A step is completed only by a `completes <step_id> as done|skipped|failed|waived` clause (xref:01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Formal EBNF Grammar for the Workflow DSL]). The rule checks:
** *Once per firing*: A firing of a finalize step opens on entry into the step's beginning state (the state `finalize.next-step` selects for it, the region entry state for steps that share one, such as `finalize.review-cap-check` for the `22..40` wait region, and `finalize.merge-evidence-wait` for the wait-region steps with the cause `input_changed`) while the step has no open firing; a re-entry while it is open continues it. Every path from an opening to the next opening of the same step, to the state of order `70` (`finalize.merge-gate`), or to a terminal state carries exactly one completion of that step; a remediation call on the path belongs to the firing. A path ends early at an `UNSETTLED` outcome (`fix_requested`, the re-planning's `reentered` or `reauthor`, a task's `asked`) or a `STEPPED_OUT` outcome, which hands the step back without a completion. Entering `plan.aborted`, `plan.return`, or `finalize.hand-back` records every begun step whose firing is still open as `failed`, in the transaction of the entering transition; a path into one of them therefore carries no `completes` clause for such a step. No completion on a path, or two, fails validation.
** *Class admits the completion*: `as done` is admitted only on an outcome of class `SUCCESS`; `as skipped` only on `SUCCESS` or `SKIP`, and on the reserved `lost` (`INDETERMINATE`) or a task's `infeasible` (`FAILURE`) on the declared conservative route of an optional step, or of the optional enrichment judgment of a mandatory step (`finalize.architecture-judgment`, whose route commits the unenriched inventory through `finalize.settle-commit`) (the step settles `skipped` with `work_performed=false` and the gap recorded); `as failed` on any class except `UNSETTLED` and `STEPPED_OUT`; `as waived` only on the transition of the outcome `waived` of a `call` to a remediation unit (the step is settled by a consumed waiver, whose id the step record references). A `FAILURE`, `INDETERMINATE`, or `STEPPED_OUT` outcome never completes a step `done` or `waived`, and never `skipped` outside that conservative route, and a composite primitive whose sub-operations report any `FAILURE` outcome yields a `FAILURE` outcome itself.
** *Cycle measures* (Rule 11a): a `STEP_LIST` measure is admitted only on the dispatch hub of a unit with a step list, which every pass settles one step of; an `ARCHIVE_STEPS` measure only on the next-work primitive of an epic unit whose archive path commits, lands, and ends in the terminal; an `ATTEMPT_CAP` measure only with a declared exhaustion outcome of class `FAILURE` whose transition leaves every cycle through the state.
10. *Operator Links and Model Links Apart (`PM-WF-1`, `PM-WF-20`)*: A declared `link` clause is an operator link: a resting link state is an operator wait (xref:02-units-jobs-decisions.adoc#operator-wait[Waiting for the Operator]), admitted in every unit and scope, whose links are rendered only as operator endpoints of the local API and never in a model-facing representation; a question state declares no links. A model acts only through the links of its task entity (registered with the entity kind) and the implicit worker links (`ack`, `consult:<role>`, `infeasible`), so in a plan or an epic a model acts only through a task. A violation fails validation with the source file and line.
11. *No Cycle Without an Awaited Event*: Every primitive declares the external event it waits for (`Primitive.awaitedEvent()`, xref:05-primitives.adoc#primitive-spi-contract[`Primitive<P, R>` SPI Contract]).
** *11a (engine-chained cycles)*: A cycle that consists only of engine-chained transitions (the outcomes of `auto` states, the entry of `call` states, and sub-workflow terminal returns, including those of a sub-workflow called on the cycle) fails validation unless a state on it declares a finite measure that strictly decreases on every pass: `pm_do` chains such transitions inside one transaction, so an unmeasured cycle would never yield. A server retry therefore waits in a `composite_job` state that awaits `TIME` (the retry backoff) or `EXTERNAL_STATE` (the re-observation), and a scope that rests between events rests in a watch `composite_job` whose closed outcomes are those events. The measure is declared by the primitive of a state on the cycle (`cycleMeasure()`, xref:05-primitives.adoc#primitive-spi-contract[`Primitive<P, R>` SPI Contract]) and checked by Rule 9, in one of two forms; a cycle without one fails validation naming the cycle:
*** *Progress measure*: a finite set of work that every pass reduces. The dispatch hub `finalize.next-step` (`STEP_LIST`) fires exactly one step and settles it per pass, measured by the unsettled steps of the instance's step list (the cycles `finalize.next-step` -> a step's `auto` state -> `finalize.next-step`, for example `finalize.adr-propose` `no_signal`, and `finalize.merge-gate` `incomplete` -> `finalize.next-step`, which re-fires the lowest-order unmet step). `epic.next-work` (`ARCHIVE_STEPS`) is measured, while the epic archives, by the remaining archive steps (commit, land, archived) (the cycle `epic.next-work` `archive_uncommitted` -> `epic.commit-ledger` -> `epic.next-work`).
*** *Compiled attempt cap* (`ATTEMPT_CAP`): a compiled number of passes per counting frame, after which the primitive takes its declared exhaustion outcome, which leaves the cycle. The sync loop of `git.commit_and_push` (`git.execute-push` or `git.push-with-lease` `rejected_non_ff` / `rejected_lease` -> `git.sync-required` -> `git.verify-freshness` -> `git.check-branch-parity` -> the push) is bounded by the sync attempt cap of `git.sync-required` (`attempts_exhausted`, link:../timeouts/01-job-budgets-and-waits.adoc#commit-attempt-caps[Timeouts & Budgets Specification, Commit Sub-Process Attempt Caps]); the re-probe of the setup (`setup.probe-integration-variants` `current` -> `setup.verify-credentials` `variant_invalidated` -> `setup.probe-integration-variants`) by the variant re-probe cap of `setup.verify-credentials` (`reprobe_exhausted`, link:../timeouts/01-job-budgets-and-waits.adoc#setup-reprobe-cap[Timeouts & Budgets Specification, Setup Variant Re-Probe Cap]).
** *11b (cycles through a resting state)*: A self-loop or cycle that passes a resting state (a `link`, question, `job`, `composite_job`, or `job llm` state) must contain an awaited event. Link actions count by kind: the operator links of an operator wait await `OPERATOR_ACT`, a worker's `submit`-form link of a task entity awaits `MODEL_SUBMIT`, and a `noop`-form link counts through its primitive's `awaitedEvent()`; a `job` or `composite_job` state awaits `JOB_SETTLED` (the waiver wait `OPERATOR_WAIVER`); a `job llm` state awaits `TASK_SETTLED` of its task (in a fan-out state of each of its tasks), whose completion runs the return evaluation; a question state awaits the decision unit's `OPERATOR_ACT` and `QUESTION_ANSWER`. A cycle all of whose events are `NONE` fails validation: it would re-run without any event that could change its outcome.
12. *Link Relation & Form Compatibility*: For every `LinkSpec`, the form (the declared `[form]`, or `LinkRelation.defaultForm()` when it is omitted) must be one of `rel.allowedForms()` (<<_ast_node_model>>, link:../hypermedia-format/02-link-grammar.adoc#_closed_link_relations_rel[Hypermedia Format Specification, Closed Link Relations]). The form must also fit the link: `submit` declares a non-empty parameter list; `noop` declares none; a link of rel `escalate` is the `submit` closing link of a remediation unit's decision task whose primitive files a waiver request (the unit's waiver wait then waits for the operator); the rels `consult` and `abort` are never declared in a `link` clause (the engine renders `consult:<role>` from a `consult role` clause and the operator's implicit `step_out`). A violation fails validation with the source file and line.
13. *Every Named Role Exists and Fits Its Use (composition, `PM-WORK-1`)*: When the runtime composes a plan instance version, an epic workflow, or the project setup workflow of a project, every role named by a `job llm` state or a `consult role` clause of the composed unit and of every unit it calls must be defined by the project's effective role set (the listed roles of the `adjudicate.decisions` unit's quorum declarations, which a `role each` state reads, are checked instead by the quorum validation at the same compositions and again at every adjudication, link:../model-work/10-decision-quorum.adoc#decision-declarations[Model Work Specification, Decision Declarations]; a listed role whose harness is not eligible or not enrolled is unavailable there, not undefined) (link:../model-work/01-roles-and-configuration.adoc#role-composition[Model Work Specification, Composition Check]); a missing or invalid role refuses the composition with `role_undefined`, naming the role and the state, so no state that names it is ever reached. Every entity kind declares with its registration the role class its tasks require (link:../model-work/01-roles-and-configuration.adoc#role-class-fit[Model Work Specification, Composition Check, class fit]), and a consulted role is never `zero_tool`: a role named by a `job llm` state whose class differs from the class its entity kind requires, a `consult role` clause that names a `zero_tool` role, or an `ask` declaration on a state whose role is `zero_tool`, refuses the composition with `class_mismatch`, naming the role, the state, and the required class; task creation repeats the check against the role set in force, and a mismatch there closes the task without an attempt (reason `class_mismatch`). The shipped default role set defines every role the default units name, which `DefaultUnitInvariantTest` verifies at build time.
14. *Every Named Skill Resolves (composition, `PM-SKILL-5`)*: At the same compositions, every skill named by a `skill` clause of the composed unit and of every unit it calls must resolve in the project's skill catalogue: a compiled skill, or an extension skill under `skill://pm/ext/` that is present and accepted at that read (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/02-service-and-skill-tools.adoc#skill-extensions[MCP Tools Specification, Skill Extensions]). A skill that does not resolve (absent, or an extension skill that is missing or refused) refuses the composition with `skill_unresolved`, naming the skill and the state, so no state renders a skill the server cannot deliver; the launch-time `prompt_composition_failed` remains only as a defence against a skill that changed after the composition (link:../model-work/04-worker-launch.adoc#job-prompt[Model Work Specification, Launch Prompt]). The default units name only compiled skills, which `DefaultUnitInvariantTest` verifies at build time.

=== Designable Workflow Units, Levels & Compiled Invariants
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-IMPL-5[PM-IMPL-5: Declarative Workflow DSL & Automated Diagram Generation]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-7[PM-EXT-7: Configuration Versioning, Validation & Zero-CoT Upgrades]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-22[PM-WF-22: Designing a Process]_

*Status: IN PROGRESS.* The loader of the default and the project-owned units, their verification on load, and the tree-checkable part of the compiled invariants are implemented in link:../../../pm-workflow/src/main/java/de/planmarshall/workflow/unit/package-info.java[`de.planmarshall.workflow.unit`] and link:../../../pm-workflow/src/main/java/de/planmarshall/workflow/verify/package-info.java[`de.planmarshall.workflow.verify`] and documented in the link:../../../pm-workflow/doc/developer/workflow-unit.adoc[Workflow Units Developer Guide] and the link:../../../pm-workflow/doc/developer/workflow-verify.adoc#_compiled_invariants[Workflow Verification Developer Guide § Compiled Invariants]; the items below state what remains.

The process a plan runs is made of units at three levels: the compiled default, the machine's copy, and the project's copy. A unit the project's team placed or changed is a file in the repository, seen and reviewed by the team like code; a unit of the machine level is the operator's own and is never committed. The guarantees of the process stay server-enforced at every level, because every unit and every plan instance composed from it is verified against rules and invariants compiled into the binary, and a unit can only compose compiled primitives and enrolled scripts.

1. *Which Units Are Designable, and Their Levels*: The designable units are the phase sub-workflows `phase-1-init.pmwf` to `phase-6-finalize.pmwf` and the `land` lane's `land.pmwf`, the sub-workflow units `git-commit-and-push.pmwf`, `remediation-*.pmwf` (the remediation policy units, xref:08-remediation-units.adoc#remediation-units[Remediation Policy Units]), the re-planning unit `replan.pmwf`, and the adjudication unit `adjudicate-decisions.pmwf` (the units that take a decision with declared parameters, xref:02-units-jobs-decisions.adoc#unit-declarations[Unit Declarations]), the variants of the plan behaviour axes (`landing.*`, `method.*`, `ask.*`, xref:09-plan-instance.adoc#plan-axes[Plan Behaviour Axes]), each verified against the compiled invariants of the part of the process it takes over, and the recipes' workflows (type `recipe`, link:../domain-extensions/05-recipes-and-extension-points.adoc#recipe-workflow[Domain Extensions Specification, A Recipe Is a Workflow]). An axis's variants are a closed list: a variant is changed, never added. The plan unit `plan.pmwf` is compiled; what a plan runs is chosen by its phases, the variants, and the sub-workflows they call. A designable unit resolves by level: the project's copy (`.marshall/config/<unit>.pmwf`, git-tracked, owner class *team*, link:../store-schemas/07-project-configuration.adoc#project-configuration-store[Store Schemas Specification, Project Configuration]; a recipe's workflow `.marshall/recipes/<id>.pmwf`) over the machine's copy (`<PM_MCP_BASE>/workflows/<unit>.pmwf`; a recipe's workflow `<PM_MCP_BASE>/recipes/<id>.pmwf`, link:../filesystem-layout/02-machine-runtime.adoc#machine-layout[Filesystem Layout Specification, Machine-Wide Runtime Layout]) over the compiled default (`classpath:/workflows/`); the plan's own choice of an axis variant stays as Plan Behaviour Axes defines it. A unit absent from a level resolves to the next level and is no finding; a unit present at a level but unparsable or violating is never replaced by another level (no silent fallback). A project holds a copy only of the units its team placed or changed, and the setup copies no unit into it; a copy taken from the machine level or the default carries `derived_from <n>` (the revision of the unit it was taken from) in its header, for the offered changes of item 6. The *compiled-only* units are never designable and never resolved by level: the machine unit `onboarding.pmwf` with its aspect sub-workflows, the project onboarding unit and the workspace unit `project-setup.pmwf`, the bootstrap units with their source units `source-*.pmwf`, the epic unit `epic.pmwf`, the entity units, the task protocol unit `worker-task.pmwf`, the decision unit `decision` (its declarations `interpret_role` and `clarify_max` keep their shipped values, xref:02-units-jobs-decisions.adoc#question-states[Question States & Decisions]), the chat unit `chat`, and the short landings `git.land-removal` and `git.land-unit`. They call the binary's default sub-workflows (and their question states run the default adjudication unit), never a machine's or a project's copy, so a failing unit of the machine or project level never blocks the setup that repairs it, the epic ledger, the start of a plan, a decision, or a chat. The composition rule file is shipped data, not a designable unit; team overrides of the composition rules are deferred (link:../../../../plan-marshall-documentation/doc/later-improvements.adoc[Later Improvements, L-5]).
2. *Load & Verification*: The load of a project's units and its verification (the parse, the format refusal, Rules 1–12 without Rule 5, the declaration bounds, `FinalizePipelineValidator` over the project roster, the compiled invariants of item 5, every finding with its file and line, the lifecycle refusal `config_invalid`, and no fallback to a default unit) are implemented by link:../../../pm-workflow/src/main/java/de/planmarshall/workflow/unit/ProjectUnitLoader.java[`ProjectUnitLoader`] (link:../../../pm-workflow/doc/developer/workflow-unit.adoc#_loading_the_project_units[Workflow Units Developer Guide § Loading the Project Units]). Not implemented yet: the machine level, loaded and verified the same way from `<PM_MCP_BASE>/workflows/` and `<PM_MCP_BASE>/recipes/`, a refused machine unit refusing the plan lifecycle of every project it reaches; the resolution of an absent unit to the next level; every computation of the effective configuration runs the load (the entry's scope creation, every phase handshake, `setup.reconcile-config`; cached by the units' digests); a refused load is a verification finding in the workspace scope and refuses the project's plan lifecycle until the unit verifies (the entry's scope creation returns to `start.ready` and every phase handshake refuses with `config_invalid`, naming the file and line of the load's refusal); Rules 13 and 14 run when an instance or workflow is composed from the units; and the verification outcome and the level of every unit are published in `pm://project/config` (`units[]`), whose digests include the machine's units.
3. *Project Steps Bind to Enrolled Scripts*: A unit never introduces executable code: every primitive it names must be registered in the binary (Rule 1). A project finalize step exists only when three owners agree: the unit contains the step (a transition completes it with `completes project:<name>`, leaving the state that runs the compiled primitive `project.run-step` for its step id), `workflow.json` `plan.phase-6-finalize.project_steps` declares its descriptor (`order`, `lane`, `project_script_id`), and the operator's enrolment binds the `project_script` with `worker_kind: finalize_step` and `target` equal to the step id (link:../domain-extensions/05-recipes-and-extension-points.adoc#_out_of_process_project_script_jobs_project_script_domain_workers[Domain Extensions Specification, `project_script`]). The check of the agreement over the declared descriptors and the bound step ids, each disagreement the finding `project_step_unbound` with file and line, is implemented by `ProjectUnitLoader` (link:../../../pm-workflow/doc/developer/workflow-unit.adoc#_project_step_binding[Workflow Units Developer Guide § Project Step Binding]); reading the descriptors from `workflow.json` and the bindings from the enrolment, and the primitive `project.run-step`, are not implemented yet.
4. *Plan Instance*: A plan never executes the units directly: in the transaction that creates the plan (`start.create-scope`, run by the `create` link of `bootstrap-plan`) the server composes the plan's first instance version from the verified units, each resolved by level, the sub-units they call, the composition rules, and the plan's facts, and every later composition event composes a new version (xref:09-plan-instance.adoc#plan-instance[Plan Instance]). A changed unit of the machine or project level raises `config_drift` at the next phase handshake of every plan it reaches (link:../domain-extensions/06-configuration.adoc#config-snapshot[Domain Extensions Specification, Three-Surface Synchronization]); the server adopts it, composing a new version (event `config_adopted`), only when it verifies and still contains the plan's current state and every state of its `call_stack`, and keeps the version in force otherwise (<<condition-overlays>>).
5. *Compiled Invariants*: The following invariants are compiled into the binary; no configuration key, composition rule, and unit edit can switch one off, and every one of them is checked over every unit of the machine and project level on every load, on every validation and placing (<<process-designer>>), and over every composed instance version (`INV-*` identifiers name the invariant in findings). The invariants of the remediation units, `INV-REM-*`, are listed with the units (xref:08-remediation-units.adoc#remediation-invariants[Compiled Invariants of Remediation Units]). The check on every load is implemented for the part of each invariant the syntax tree of a unit decides, against the default unit of the same id as reference, by link:../../../pm-workflow/src/main/java/de/planmarshall/workflow/verify/CompiledInvariants.java[`CompiledInvariants`] over the list link:../../../pm-workflow/src/main/java/de/planmarshall/workflow/verify/InvariantId.java[`InvariantId`] (link:../../../pm-workflow/doc/developer/workflow-verify.adoc#_compiled_invariants[Workflow Verification Developer Guide § Compiled Invariants]); the bounds of the declarations by link:../../../pm-workflow/src/main/java/de/planmarshall/workflow/verify/DeclarationBounds.java[`DeclarationBounds`]. Not implemented yet: the check over every composed instance version and the composition checks the rows name (Rules 13 and 14, `quorum_invalid`, `quorum_not_diverse`, the role class of `INV-REPLAN-1`, the prunes of `INV-FIN-1`), the runtime parts named as hooks on `InvariantId` (`INV-GEN-2`: only the operator API writes waiver records and every lookup logs a consumption; `INV-GEN-4`: the removed options a primitive reads from configuration at runtime), and the behaviour of the primitives the rows name, which the tree only places. The table stays the definition these checks implement.

At every composition, every listed role of a quorum declaration is defined (or unavailable only for its harness) and `read_only` (`quorum_invalid`), and the listed roles of one declaration name pairwise different models (`quorum_not_diverse`); either refusal is a rejection of class `precondition` (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/04-errors-and-testing.adoc#rejection-reasons[MCP Tools Specification, Closed Rejection Reasons]), and the bootstrap commit re-check repeats both checks (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/01-core-workflow-tools.adoc#bootstrap-commit-recheck[MCP Tools Specification, Bootstrap Commit Re-Check]).

|`INV-REPLAN-1`
|`replan`
|The unit's states, primitives, transitions, and terminals equal those of the default unit, except the role its `job llm` state names, which must be a `read_only` role at composition; it differs otherwise only in its declarations, each within its compiled bounds (link:../phase-workflows/08-dynamic-re-planning.adoc#replan-constants[Phase Workflows Specification, Declared Thresholds]); every trigger keeps its conservative fallback, and the re-planning task never offers a question link.

|`INV-AXIS-1`
|`landing.*`, `method.*`, `ask.*`
|Plan behaviour axes: a variant takes over only the part of the process its axis names and keeps every invariant of that part: a landing variant lands only through `git.commit_and_push` (`landing.pull-request` through the push barrier, the pull request, and the pre-merge barrier; `landing.main` by one commit pushed onto the base branch with the push freshness gate and no force push; `landing.files` by no commit, ending the plan `handed_back`) and runs after every check and review of the finalize phase; a method variant only orders the plan's implementing and testing tasks, every task of the plan still run and every footprint check of `INV-EXEC-2` kept; an asking variant only adds operator waits at the plan's phase transitions and declares whether the outline is reviewed and whether the plan merges itself, never skipping a gate, a barrier, or a review (xref:09-plan-instance.adoc#plan-axes[Plan Behaviour Axes]).

|`INV-GIT-1`
|`git.commit_and_push`
|The six stages run in order on every path: worktree inspection, `.gitignore`-aware artifact detection, message resolution with Conventional Commit validation and the operator's trailer, stage-and-commit with the footprint check, the push-policy evaluation with the freshness gate and branch parity, and the push; the exit contract is `done {commit?, pushed, clean, landed}` plus `stepped_out`; `pushed` holds only when the remote branch holds `HEAD`, an unknown remote state steps out (`push_state_unknown`), and every model loop of the unit is capped; the unit has no override state and no force push other than `git.push-with-lease` after a server rebase of the plan's own branch.
|===
+
The invariants are defined against the default units: every invariant holds for them, and `DefaultUnitInvariantTest` verifies that at build time together with a fixture set of weakened units that each invariant must refuse.
6. *Offered Changes*: A new binary never changes a unit of the machine or project level, and a changed machine unit never changes a project's copy. The changes of the unit a held copy was taken from are offered as a three-way diff from the copy's `derived_from` revision to the current revision of that unit: a project's copy in `setup.offer-new-steps`, a machine's copy in the machine's settings (link:../domain-extensions/06-configuration.adoc#config-upgrades[Domain Extensions Specification, Upgrade Path]); a copy whose `derived_from` is older is valid and runs unchanged as long as it verifies.

[#process-designer]
=== Designing a Process
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-22[PM-WF-22: Designing a Process]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-IMPL-5[PM-IMPL-5: Declarative Workflow DSL & Automated Diagram Generation]_

The operator changes the process a plan runs by designing a unit in the web app (link:../../../../plan-marshall-documentation/doc/use-cases/03-plans.adoc#UC-PLN-3[UC-PLN-3]): starting from an uploaded file, a pasted text, or an installed unit, validated on demand and before every placing exactly as the runtime loads it, and placed at machine or at project level. What may be designed is the closed set of designable units of <<project-owned-units>>, item 1; a compiled-only unit is never placed.

1. *Building blocks, in two scopes*: `GET /api/v1/projects/{project_id}/workflows/catalogue` serves what a unit can use in that project, as the project resolves it (its copies over the machine's over the compiled defaults, its effective role set); `GET /api/v1/workflows/catalogue` serves the machine scope (the compiled and the machine-level units and the machine's role set), so that a machine-level unit is designed with no project chosen. `GET /api/v1/projects/{project_id}/workflows` lists the designable units of a project with, per level, whether a copy exists, its text and digest, and which level is in force; `GET /api/v1/workflows` lists the machine level's units with the compiled defaults.
2. *The catalogue is complete and has one source*: The catalogue lists every element the language can use, each with the text the designer inserts and what it needs: the primitives of `do`, `auto`, `job`, and `guard` with their parameter records and outcomes (xref:05-primitives.adoc#primitive-spi-contract[`Primitive<P, R>` SPI Contract]); the guards; the link relations and their forms (xref:01-grammar.adoc#dsl-reserved-keywords[Grammar], Link relations and forms); the condition kinds of a guard (`in_worktree`, `has_open_findings`, `all_tasks_completed`, `predicate`, combined with `and`, `or`, `not`); the reusable and compiled sub-workflows with their parameters, entries, and exits, the phases among them; the roles of the effective role set with their class; the declarable parameters of each unit with their compiled bounds (xref:02-units-jobs-decisions.adoc#unit-declarations[Unit Declarations]); and the keywords and clauses of the language (`state`, `skill`, `link`, `call`, `declare`, `migrate`, …) with a template each. It is generated from the registries the parser, the static verification, and the composition use (the primitive registry, the role sets, the unit loader), never from a list kept apart, so it offers exactly what validation accepts. It carries the runtime's version and a digest; a client loads it again when the digest changes, after an upgrade or a placing. Each unit is shown by the name and description of its frontmatter, with its entries and exits, and a building block for a `call` offers one template per entry of the callee.
3. *Validation*: `POST /api/v1/workflows/validate` takes the unit's text, its kind and name, and the target (a project, or the machine), and checks it exactly as the units of that level are loaded: the frontmatter's format, fields, and interface (link:../../../pm-workflow/doc/developer/workflow-dsl.adoc#unit-frontmatter[Workflow DSL Developer Guide § The Unit Frontmatter], link:../../../pm-workflow/doc/developer/workflow-verify.adoc#interface-rules[Workflow Verification Developer Guide § Interface Rules and Unit Types]), the parse, Rules 1–12 of the static verification (<<static-verification-rules>>), the compiled invariants (<<project-owned-units>>, item 5), and a dry-run composition of a plan instance with the unit in place against the project's effective configuration, roles, skills, and providers (Rules 13 and 14). For a machine target the dry run runs against every enrolled project the unit would reach, each finding naming its project. The answer lists the findings, each with its rule or invariant, its line, and its column, and for a valid unit the composed process in the form of the plan's process resource (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#process-resource[Runtime & Interaction Model Specification, The Plan's Process as a Structure]), its nodes `planned` or `not_in_plan` with their prune reasons. The dry run starts nothing and stores nothing. With no enrolled project, validation runs everything but the dry run, which it reports `not_run` with the reason `no_project`.
4. *Placing and removing*: `PUT` and `DELETE /api/v1/workflows/{unit}` at machine level, `PUT` and `DELETE /api/v1/projects/{project_id}/workflows/{unit}` at project level; a recipe's workflow is placed and removed under the recipe's key (`<PM_MCP_BASE>/recipes/<id>.pmwf`, `.marshall/recipes/<id>.pmwf`). Placing and removing are operator acts. Each request re-validates in the same request: at machine level against every enrolled project in which the unit would be in force, refused with `unit_invalid` and the findings of each project that fails, and refused with `no_project_to_compose` while no project is enrolled; a removal validates the unit of the next level the same way. Each request carries the digest of the unit it replaces and is refused with `conflict` when that unit changed meanwhile, and the client shows the difference against the unit it replaces before it places. It is refused with `unit_not_designable` for a compiled-only unit or a unit outside the designable set, for a variant name an axis does not list, and for a recipe key of a built-in or domain recipe, and with `unit_invalid`, with its findings, when it fails validation (item 3), among them when its author is `plan-marshall` or when its type, entries, or exits differ from those of the unit it replaces (`INV-GEN-1`). A machine recipe is offered in every project on the machine, and a project's recipe of the same key takes its place in that project.
5. *Project level as a short landing*: A unit placed or removed at project level is written to `.marshall/config/` (a recipe's workflow to `.marshall/recipes/`) and landed by one commit through the compiled sub-workflow `git.land-unit` (xref:06-reusable-sub-workflows.adoc#short-landings[Short Landings]), by the project's landing: through `landing.pull-request` or `landing.main`, and left uncommitted in the working tree with `landing.files`. Until it has landed it shows in the project's running work, and a failed landing waits for the operator. A project unit is in force for a plan when the plan's own checkout or worktree holds it: a new plan starts from the base branch and takes it once it has landed there; a running plan adopts it through `config_drift` once its worktree has it, at its next sync with the base branch (link:../domain-extensions/06-configuration.adoc#config-snapshot[Domain Extensions Specification, Three-Surface Synchronization]); with `landing.files` the file is only in the operator's checkout, and nothing takes it until it is committed. A machine unit is in force from its placing: the effective configuration's digests include it, so it reaches a running plan only through the `config_drift` adoption of item 4 of <<project-owned-units>>.
6. *Path confinement*: Every route that names a unit, at machine and at project level, accepts only a name of the canonical unit-name grammar (link:../identifiers/01-general-rules-and-registry.adoc#id-state-id[Identifier Registry, `state_id`]: no path separator, no `..`, no absolute path) and writes or deletes only after checking that the resolved path lies inside its target directory (`<PM_MCP_BASE>/workflows/`, `<PM_MCP_BASE>/recipes/`, `.marshall/config/`, `.marshall/recipes/`); a name outside the grammar or a path outside its directory is refused with `unit_name_invalid`, a well-formed name the catalogue does not list as designable for that level with `unit_not_designable` (item 4).
7. *The web listeners, no audit record*: Every designer endpoint is on the runtime's own `/api/v1/` and reached by the web app through the loopback or the LAN listener (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#two-listeners[CLI, Coordination & Security Specification, Loopback and LAN Listeners Side by Side]) with its device secret (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#web-proxy[CLI, Coordination & Security Specification, API Access & Device Secret]); none of them is `cli_only`, and a paired device and the browser on the loopback listener read, validate, place, and remove. Placing and removing write no audit record: the origin of a unit is its frontmatter (author, modification date, release), which the signature reserved there will make verifiable (xref:01-grammar.adoc#unit-frontmatter[Unit Frontmatter]).
8. *Validation and the catalogue from the terminal*: A unit is also written outside the designer, in the project's repository, by a person or by a coding agent working for the operator. The terminal client reaches the validation (item 3) and the catalogue (items 1 and 2) through the same endpoints over the local API (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]) for a unit file it names, and prints each finding with its rule or invariant, its line, and its column, both for a person and machine-readable, and the building blocks with their templates, so that such a unit is checked by the runtime's own rules before it is committed, instead of failing at the next phase handshake with `config_invalid` (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/04-errors-and-testing.adoc#rejection-reasons[MCP Tools Specification, Closed Rejection Reasons]). Both change nothing and write no audit record; placing and removing stay in the web app.
