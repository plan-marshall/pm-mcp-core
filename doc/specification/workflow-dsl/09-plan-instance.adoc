[#plan-instance]
== Plan Instance (`instance/plan.v<N>.pmwf` per Plan)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-IMPL-5[PM-IMPL-5: Declarative Workflow DSL & Automated Diagram Generation]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-7[PM-EXT-7: Configuration Versioning, Validation & Zero-CoT Upgrades]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-25[PM-WF-25: Plan Behaviour Axes & Plan Overrides]_

Every plan executes its own *plan instance*: real DSL units that the server composes from the templates (the plan unit, or for a recipe's plan the recipe's workflow; the phase sub-workflows and the variants of the plan behaviour axes it calls; each resolved by level, xref:04-ast-node-model.adoc#project-owned-units[Designable Workflow Units, Levels & Compiled Invariants]), the sub-units they call (`git.commit_and_push`, the `remediation.*` units, xref:08-remediation-units.adoc#remediation-units[Remediation Policy Units], `replan`, `adjudicate.decisions`, and the compiled-only units `decision` and `chat`), the composition rules (<<composition-rules>>), and the plan's facts. A version consists of one composed file per unit the plan composes, the plan unit's file `instance/plan.v<N>.pmwf` (`scope plan`, `id` `plan`) with the version's header, and `instance/<unit>.v<N>.pmwf` for each phase sub-workflow and each bound axis variant; the other sub-units are bound by id, level, and digest in the header. Facts stay where they are owned and are never copied into the instance: configuration in its stores, waivers in the plan's waiver record, the plan's own values in its overrides (<<plan-overrides>>), plan facts (lane, posture, deliverables, footprint, tasks) in the plan stores. The instance carries their *effect* with provenance, which makes the process in force visible per plan:

* the lane's route: the phase calls the lane does not make are pruned calls, and the states of the sources the plan cannot take are absent;
* the bound variant of each plan behaviour axis, the variants not chosen pruned with the reason `plan_default` (<<plan-axes>>);
* the pruned template elements (phase calls, steps, states, links, and policy actions), each with its prune reason and source fact in the header;
* the policy calls with their effective bound arguments; the header names each argument's source (the template's call argument, a composition rule, or the `raise` waiver id);
* the gates marked waived, with the waiver id;
* the header with the digests and levels of every input (template units of every level, sub-units, composition rule file, effective configuration, the plan's overrides, plan facts).

The step lists are the instance (the dispatch hubs select the next unsettled step of the version in force), and its header binds the configuration. Its storage, header schema, and composition log are specified in link:../store-schemas/14-plan-instance-waivers-questions.adoc#plan-instance[Store Schemas Specification, Plan Instance].

=== Versions & Composition Events
_Implementation watch: link:../../implementation-watch/workflow-dsl.adoc#PM-WATCH-DSL-21[PM-WATCH-DSL-21]_

The instance is immutable and versioned; each version has exactly one composition event from the closed enum: `start` (version 1, composed in the transaction that creates the plan, `start.create-scope` of the `create` link of `bootstrap-plan`, or of `start.launch` for a plan the server starts for its epic (link:../state-catalogue/09-bootstrap-and-lessons.adoc#state-start.launch[State Catalogue, `start.launch`]): init and refine routes, both lanes open, the posture prunes where a level sets the posture, every axis variant a level sets bound), `outline` (lane known: the other lane pruned with reason `other_lane`, <<composition-rules>>), `plan` (steps and tasks known; provider and footprint prunes; budgets bound), `config_adopted` (an adopted configuration or unit change of any level, `adopt` of the `config_drift` condition), `waiver` (a `met` waiver, a `raise`, or an `unwaive`), `override` (the operator set or changed one of the plan's own values, <<plan-overrides>>, including an option asked where the plan first needs it, such as the posture and the base branch in `init.options`), `fallback` (the post-run-only form of the `returned` and `handed_back` routes), `empty_harvest` (the post-run-only form of a recipe's plan whose harvest is empty), and `replan` (a re-planning of a running plan revised its outline or its plan tasks, composed by `replan.apply` with footprint prunes and policy bindings evaluated again over the revised plan, link:../phase-workflows/08-dynamic-re-planning.adoc#replan-apply[Phase Workflows Specification, Dynamic Re-Planning]; a revision the operator accepted in a chat composes the same event). A loop-back to the outline re-runs `outline` and `plan`.

1. *When a version is in force*: A version composed by a server event (`outline`, `plan`, `fallback`, `empty_harvest`, `replan`) is in force for the rest of its composing chain, from the transition that enters its target state on, so the states that chain on (for example `finalize.next-step` after `finalize.hand-back`) already select from it. A version composed by an operator or configuration event (`config_adopted`, `waiver`, `override`) is in force from the next transition. `instance_version` of `mcp/status.json` names the version in force; a version never takes effect mid-state.
2. *Position rule*: A version is valid only if it contains the scope's current state and every state of its `call_stack`, the phase sub-workflow's call state among them. State ids are stable across versions, so the current position maps onto the new version unchanged. A server event is composed in the transaction that enters its target state and always contains it; an operator-triggered event whose version fails the rule is refused (a configuration change is then kept, a waiver or an override refused with `position_not_contained`).
3. *Verified per version*: Every composed unit of a version passes Rules 1–14 (xref:04-ast-node-model.adoc#static-verification-rules[Static AST Verification Rules]) and every compiled invariant before the version is written; a version that fails is never written. Rule 13 resolves every role the version names in the effective role set, with the plan's overrides applied, and Rule 14 every skill its `skill` clauses name in the project's skill catalogue, at that moment: a role that is missing or invalid refuses the composition with `role_undefined`, a role whose class does not fit its use with `class_mismatch`, a skill that does not resolve with `skill_unresolved` (at event `start` the plan is not created; at a server event the composing transition raises `precondition_unmet` with that reason and its server retry; an operator-triggered event is refused, a configuration change kept).
4. *History*: Completed firings, step records, and the audit trail always refer to the version in force when they happened; history is never rewritten, and a counter (policy budgets, the loop-back budget) is never reset by a re-composition.
5. *Units reach a running plan only through adoption*: A changed unit of the machine or project level, or a changed composition rule file, raises `config_drift` at the next phase handshake; only `adopt` composes it into the plan (event `config_adopted`).

[#instance-header-grammar]
=== Instance Header Grammar

The plan unit's file of an instance version is a `.pmwf` file of the workflow grammar (xref:01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Formal EBNF Grammar]) with one additional line after the `workflow` header, which only the server writes:

[source,ebnf]
----
instance_decl        = "instance" , instance_header , EOL ;
instance_header      = ? one line of canonical JSON, valid against the plan instance
                         header schema (store-schemas/14-plan-instance-waivers-questions.adoc,
                         Plan Instance) ? ;
----

Its frontmatter (xref:01-grammar.adoc#unit-frontmatter[Unit Frontmatter]), written by the server, declares `type: instance`, no entry and no exit, the name `Plan <plan_id>, version <N>`, the composition event as its description, the day of the composition as `modification_date`, the release of the runtime that composed it as `version`, and the author `plan-marshall`; a file outside the plan's `instance/` directory that declares `type: instance` fails validation. The `workflow` header of the plan unit's file is `workflow plan version <N> format <f>`, where `<N>` is the plan's `instance_version` (the instance header's `version`), which the file name `instance/plan.v<N>.pmwf` repeats. The file of a composed phase or variant keeps the frontmatter, id, type, entries, and exits of its template, carries no `instance` line, and repeats `<N>` in its file name. Every body is the composed state list; it never contains an element that no template declares, and every call site carries the effective values it binds. Pruned elements are absent from the bodies and listed in the header (`pruned[]`), so the verification rules and invariants run over exactly what the plan executes. A unit outside the plan's `instance/` directory that contains an `instance` line fails validation.

[source,text]
----
---
name: Plan header-parser, version 3
description: Composed at the event plan.
type: instance
modification_date: 2026-10-14
version: 1.0.0
author: plan-marshall
---
workflow plan version 3 format 1
instance {"format_version":1,"plan_id":"header-parser","version":3,"event":"plan", …}
scope plan
…
----

In `instance/phase-6-finalize.v3.pmwf` of the same version the call `finalize.remediate-ci` binds `call remediation.ci-failure (retry_budget=2, fix_budget=4, actions=[retry,fix,loop_back])`; the header records `fix_budget=4` with the source of a `raise` waiver (`fix_budget:ci-failure`), while the template binds `3`.

[#composition-rules]
=== Composition Rules

The land restriction, the local-only prunes, the merge prune of the asking axis, the binding of the axis variants, and every other prune predicate are *data*: one declarative composition rule file, shipped with the binary and versioned like the templates, whose rules map a plan fact or an effective configuration value to prunes (element, id, prune reason) and policy bindings (a call site and the argument it fixes). The rule shape and the shipped rules are specified in link:../store-schemas/14-plan-instance-waivers-questions.adoc#composition-rules[Store Schemas Specification, Composition Rules]; the DSL-relevant effects are:

* *Lanes*: from the `outline` event on, the states of the other lane are pruned with reason `other_lane`; a `light` version keeps the deep route of its escalation, a `deep` version holds no state of the light route. Implemented: what exactly is pruned, and the shared states before the split at `init.ready` that never are, is documented in link:../../../pm-workflow/doc/developer/workflow-plan.adoc#_lane_pruning[Plan Instance Developer Guide § Lane Pruning]; the per-lane routes it rests on are those of the plan unit (link:../phase-workflows/01-planning-phases-1-2.adoc#plan-unit-phases[Phase Workflows Specification, The Plan Unit as a Workflow of Phases]).
* *`land` lane*: every policy call is bound with `actions=[retry]`, so `remediation.offer-actions` offers neither `loop_back` nor an in-branch `fix` and `decide` takes the `retry` without a task (xref:08-remediation-units.adoc#unit-template[Unit Template]); task allocation is pruned with reason `land_lane`; exhaustion ends in `finalize.hand-back`.
* *`adopt` lane*: `create-pr` is pruned with reason `adopt`, because the adopted pull request exists; `finalize.push-barrier` continues at the landing's dispatch hub, which selects the next step the instance keeps.
* *Axis variants*: at each axis call site the variant chosen by the nearest level that sets one is bound, and every other variant of the axis is pruned with the reason `plan_default` (<<plan-axes>>). Implemented as far as the composition reads the levels and the declarations: link:../../../pm-workflow/doc/developer/workflow-plan.adoc#_the_plan_behaviour_axes[Plan Instance Developer Guide § The Plan Behaviour Axes].
* *No push remote*: `push`, `create-pr`, `ci-verify`, `automatic-review`, and `analysis-roundtrip` are pruned with reason `local_only`; `pre-push-quality-gate` and `pre-submission-self-review` stay; `finalize.merge-gate` routes `local_only` to the local form of `finalize.hand-back`, and the plan ends `handed_back`.
* *The merge left to the operator*: where the bound asking variant declares that the plan does not merge itself (`self_merge = false`, <<plan-axes>>), the merge execution of `landing.pull-request` (`finalize.merge-dispatch`, `finalize.merge-queue-wait`, `finalize.merge-queue-exit`) is pruned with reason `merge_by_operator` (implemented: the shipped rule `merge-by-operator`, link:../../../pm-workflow/doc/developer/workflow-plan.adoc#_the_rule_file[Plan Instance Developer Guide § The Rule File]); the gate, lease, sync, evidence wait, and barrier stay, and `finalize.merge-barrier`, reading that the instance prunes the merge execution, settles `pass_hand_back` instead of `pass`, completes `default:branch-cleanup` as `done`, and enters the ready form of `finalize.hand-back` (the pull request marked ready for review, never a draft), so the plan ends `handed_back` with `merge_outcome: awaiting_human_merge`. The prune never removes a gate or a barrier predicate.
* *The outline review*: where the bound asking variant declares no outline review (`outline_review = false`), the outline review state is pruned with reason `plan_default`, and `outline.gate` continues to Phase 4.
* *Posture, providers, footprint, change type*: steps pruned with the reason `posture` (at event `start` where a level sets the posture, else at the event `override` that records the posture asked in `init.options`); an unset `integrations.sonar` prunes `default:analysis-roundtrip` with reason `provider_unconfigured`; a declared footprint disjoint from the code and build globs prunes `default:finalize-step-simplify` and `default:adr-propose` with reason `footprint_disjoint`; a `change_type` of `analysis` or `verification` prunes `default:finalize-step-simplify` with reason `change_type_exempt`; floor immunity protects the mandatory steps (`INV-FIN-1`).
* *Post-run-only forms*: `finalize.hand-back` and a recipe's empty harvest compose a version in which every step below order `900` is pruned with the reason `returned`, `handed_back`, or `empty_harvest`, so `finalize.next-step` runs the post-run band and `finalize.archive-plan` without a special mode.

A rule never adds an element, never raises a budget, and never names a gate; the compiled invariants are checked on its result.

*Outcomes settled by a prune*: pruning a state removes the state and every transition into it; it never re-routes the outcome that led there. An outcome of a kept state whose every transition led into a state the composition pruned with a prune record (a reason of the closed prune-reason set and its source fact) is settled by that record: Rule 2 counts it as routed in that version, because the version's own facts exclude it. The lane router `init.ready` of a `deep` version never returns `light`, since the light route is pruned with `other_lane`; `finalize.merge-barrier` of a version that prunes the merge execution with `merge_by_operator` reads the prune and settles `pass_hand_back`, never `pass`. Only the composition settles an outcome this way: a unit verified without the prune records of its composition, and a transition into a state removed without a prune record, still fails Rule 2. Implemented in the composer and the verifier (link:../../../pm-workflow/doc/developer/workflow-plan.adoc#_outcomes_settled_by_a_prune[Plan Instance Developer Guide § Outcomes Settled by a Prune]); the barrier's reading of the prune at run time is not.

The templates are the designable units of each level; team overrides of the composition rules are deferred (link:../../../../plan-marshall-documentation/doc/later-improvements.adoc[Later Improvements, L-5]); until then the shipped rule file applies.

[#plan-axes]
=== Plan Behaviour Axes
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-25[PM-WF-25: Plan Behaviour Axes & Plan Overrides]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)]_

How a plan lands, the order in which it works, and how often it waits for the operator are choices of workflow units: each *axis* is a call site of the plan's workflow, and each *variant* a sub-workflow of it, designable like a phase (xref:04-ast-node-model.adoc#project-owned-units[Designable Workflow Units], item 1) and named with its axis as prefix. An axis's variants are a closed list: a variant is changed, never added.

[cols="1,2,3,5"]
|===
|Axis |Call site |Variants |What the variant does

|landing
|Inside `phase-6-finalize`, at the landing orders of its step list (`11` to `70`), after the phase's checks and reviews; the phase keeps them and its post-merge and post-run bands, and the variant is what lands (link:../phase-workflows/06-finalize-re-entry-and-merge.adoc#landing-variants[Phase Workflows Specification, Landing Variants])
|`landing.pull-request`, `landing.main`, `landing.files`
|`landing.pull-request` pushes the branch and lands it through the pull request, its reviews, and the merge; `landing.main` commits and pushes onto the base branch through `git.commit_and_push`, with no pull request; `landing.files` makes no commit: the changes are written, uncommitted, into the main checkout's working tree, the plan branch is kept, and the plan ends `handed_back`; where a path the plan changed is modified in the checkout, nothing is written and the plan is handed back in the local form with the gap cause `files_not_applicable`. The landing axis is never the `land` lane, a plan that calls no outline and no plan phase.

|method
|Inside `phase-4-plan`, at `plan.order-tasks`, before the task descriptions and the envelope packing
|`method.test-first`, `method.tests-after`
|Orders the plan's implementing and testing tasks (declared `order = tests_first` or `tests_after`): test-first runs each deliverable's testing tasks before its implementing ones, tests-after the reverse.

|asking
|In the plan unit, between two phase calls
|`ask.every-phase`, `ask.key-points`, `ask.questions-only`
|Decides which phase transitions wait for the operator (declared `wait_after`, a list of the phases after which the plan waits in an operator wait before its next call), whether the outline is reviewed (`outline_review`), and whether the plan merges itself (`self_merge`): `ask.every-phase` waits after `init`, `refine`, `plan`, and `execute`, reviews the outline, and leaves the merge to the operator; `ask.key-points` waits only at the outline review and leaves the merge to the operator; `ask.questions-only` waits at no transition, reviews no outline, and merges by itself. Decisions are asked under every variant.
|===

1. *Binding is composition*: The method and asking variants are called at their call sites like every sub-workflow (the method variant by the plan phase's `plan.order-tasks`, so the order is fixed before the envelopes are packed; the asking variant by the plan unit's `phases.ask`). A landing variant holds the step states of the landing orders; the instance composes the bound variant's states into the composed file of `phase-6-finalize` at those orders, so the phase's dispatch hub `finalize.next-step` fires them like the phase's own steps and the states keep their `finalize.` identifiers (`landing.pull-request`: the push barrier, `create-pr`, the wait region, and the merge path; `landing.main`: `finalize.land-main`; `landing.files`: `finalize.land-files`). A landing variant is therefore verified composed into the phase: its transitions may target the phase's dispatch hub, its fallback `finalize.hand-back`, and the phase states a landing continues in (`finalize.settle-commit`, `finalize.allocate-remediation`, `finalize.replan`, `finalize.self-review`).
+
 The plan instance binds the chosen variant of each axis where the plan first needs it (at its start where a level sets it; otherwise where the plan reaches the axis's first call site, asking the operator there), from the plan's own value, else the project's, else the machine's, and prunes the variants not chosen with the reason `plan_default`, so the process in force shows the choice (<<composition-rules>>). A later change composes a new instance version (event `override`, <<plan-overrides>>), under the position rule; a variant whose call site the plan has already passed changes nothing for that pass.
2. *Three levels*: The nearest level that sets an axis wins, and a level that says nothing defers to the next: the plan's own value (<<plan-overrides>>), the project's (the landing a value of the team, kept in the team's configuration in `.marshall/config/`, because how a repository lands is a convention of the repository; the method and the asking the operator's, kept in the project's `local-config.json`), and the machine's default (`machine-config.json` `plan_defaults`; link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration Store], link:../store-schemas/08-project-configuration-local.adoc#project-levels[Project Values over Machine Values]). Where no level sets one, the shipped `plan_defaults` apply: `landing.pull-request`, `method.tests-after`, and `ask.questions-only`.
3. *Validation*: A landing variant is validated where a project is known: at the project's choice in its setup and at a plan's start, `landing.pull-request` without a provider of the project and `landing.main` on a base branch the provider reports as protected are refused with the reason. The machine default is never validated against a repository: the onboarding's `defaults.validate` checks only what the machine itself provides (a provider for `landing.pull-request`), and a machine default that does not fit a project is refused for that project, with the reason, at its setup or at the plan's start, where the project or the plan chooses another. A plan from local changes needs a landing that commits: while the project's landing in force is `landing.files`, the start does not offer the local changes as a source and shows the reason, naming the project's setting (link:../state-catalogue/09-bootstrap-and-lessons.adoc#options-when-needed[State Catalogue, Asked When Needed]); a plan from local changes refuses `landing.files` as its own value.
4. *What the variants declare*: The method and asking variants carry their choices as declarations of a compiled declaration schema (xref:02-units-jobs-decisions.adoc#unit-declarations[Unit Declarations]): `order: enum[tests_first|tests_after]` for a method variant; `wait_after: list<enum[init|refine|outline|plan|execute]>`, `outline_review: enum[true|false]`, and `self_merge: enum[true|false]` for an asking variant; the composition rules read them. A designed variant keeps its axis's interface and the invariants of the part it takes over (`INV-AXIS-1`, xref:04-ast-node-model.adoc#project-owned-units[Compiled Invariants]).
5. *The asking wait*: Where the bound asking variant waits after a phase, the called variant rests in an operator wait (`ask-every-phase.confirm`) (xref:02-units-jobs-decisions.adoc#operator-wait[Waiting for the Operator]) that shows the ended phase's result and offers the link `continue`; the operator's scope-wide acts stay available there. Where the variant sets the outline review, the plan does not ask it again elsewhere.

[[plan-posture]]*Posture and base branch*: The posture is no axis (it prunes steps, it calls no variant), but it resolves by the same levels: the plan's own value (`overrides.json` `posture`), else the project's, else the machine's (`plan_defaults.posture`, an optional key of the operator at project and at machine level, set in the project's or the machine's settings and never asked during an onboarding; link:../store-schemas/08-project-configuration-local.adoc#project-levels[Store Schemas Specification, Project Values over Machine Values], link:../store-schemas/12-machine-stores.adoc#machine-config[Machine Configuration Store]). The key ships unset, so while no level sets it, `init.options` asks the posture in every plan. The base branch is the project's unless the plan's own value (`overrides.json` `base_branch`), asked in `init.options` or set in the plan's settings before the base is stamped, names another. Both answers are the plan's own values and compose the event `override` (link:../state-catalogue/02-plan-phases-1-3.adoc#state-init.options[State Catalogue, `init.options`]).

[#plan-overrides]
=== Plan Overrides
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-25[PM-WF-25: Plan Behaviour Axes & Plan Overrides]_

A plan's own values are its *overrides*, kept in the plan store `overrides.json` (link:../store-schemas/14-plan-instance-waivers-questions.adoc#plan-instance[Store Schemas Specification, Plan Instance Store]), which only the operator writes, in either client:

* per role `harness`, `model`, and `effort` (link:../model-work/04-worker-launch.adoc#harness-selection[Model Work Specification, Harness Selection]);
* the variant of each plan behaviour axis (<<plan-axes>>);
* the posture (`minimal`, `standard`, or `full`) and the base branch, asked in `init.options` where no level sets them (<<plan-posture>>);
* the variant of an integration;
* the optional providers (code analysis, review bots) the plan uses.

1. *Where they are set*: An override is set where the plan first needs the value (link:../state-catalogue/09-bootstrap-and-lessons.adoc#options-when-needed[State Catalogue, Asked When Needed]), or later from the plan's settings (link:../../../../plan-marshall-documentation/doc/use-cases/06-controlling-work.adoc#UC-CTL-5[UC-CTL-5]). Setting one is an operator act, audited, and the epic of the plan, if it has one, is told that the plan's settings changed.
2. *Composition*: An override set or changed after the plan's start composes a new instance version with the composition event `override`, under the position rule (<<plan-instance>>, item 2); the write answers with the new instance version, and an override whose version would not contain the plan's position is refused with `position_not_contained` and not written.
3. *Validation*: An override passes the same validation as the machine's values: the harness enrolled, the model allowed by the model catalogue (`model_not_allowed` otherwise), the provider available, a landing variant validated as for the project (<<plan-axes>>, item 3).
4. *Qualification*: An override to a role configuration without a current qualification record is shown as unqualified when it is set, and its tasks take the qualification fallback of `PM-WORK-6` until the project grades it (link:../model-work/01-roles-and-configuration.adoc#conservative-fallback[Model Work Specification, Conservative Fallback]).
5. *Never a decider*: An override changes how the plan runs, never what a decision decided; it is no answer to a question and never passes a gate.

=== Display

The diagram generator renders the instance, not the templates: `pm://plan/{plan_id}/diagram` shows the version in force with the active state, the pruned elements with their reason, and the waived gates with their waiver id; `pm://plan/{plan_id}/instance[/{version}]` returns the DSL text with its header (xref:07-loop-back-diagrams-verification.adoc#_automated_mermaid_asciidoc_table_and_ascii_diagram_generation[Diagram Generation]). The operator's clients show the composed process of the version in force as the plan's process resource: a tree of the plan, its phases, every unit's states in their order, and every call with the sub-workflow it calls, expanded down to the leaves, each node with its derived state and the plan's current position, the pruned phase calls and variants as _not in this plan_ with their prune reason (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#process-resource[Runtime & Interaction Model Specification, The Plan's Process as a Structure]). Version 1, composed when the plan is created, is also the preview of the plan's process (for example of its posture and its bound variants).
