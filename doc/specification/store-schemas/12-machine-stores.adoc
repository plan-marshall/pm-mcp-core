== Machine Configuration, Operator Files, Credentials & Security Audit Stores

*Operator files and their revision*: The operator files of the machine (`machine-config.json`, `consents.json`, `role-assignments.json`, `model-catalogue.json`, `host-tools.json`, `explorer.json`) and of a project (`local-config.json`, `role-assignments.json`, `model-catalogue.json` in its machine store) are written only by the runtime, on an act of the operator in either client over the local API (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]), never by a model, a job, or a client process. Each carries `revision`, an integer the runtime increments with every write. A change names the revision it was made against; the first change wins, and a change against an older revision is refused with `conflict` (`409`), nothing merged and nothing overwritten unseen (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#two-channels[CLI, Coordination & Security Specification, Operator Choices in the Web App and the Terminal]). Every write is audited with its channel (`cli` or `web`) and, for a paired device, its `device_id` (<<audit-log>>).

[#machine-config]
=== Machine Configuration Store (`<PM_MCP_BASE>/machine-config.json`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)]_

Configures machine-wide build and worker concurrency limits, warm LSP pool sizing, the machine-level timeouts and budgets (drain timeout, escalation cap, progress wait bound, language server timeouts, audit rotation age, rotated audit file retention), the machine-wide connection overrides of the harness profiles (`harness_profiles.<harness_id>.connection`, link:../harness-profiles/01-profile-schema.adoc[Harness Profiles Specification], Machine-Wide Operator Overrides), the outbound proxy (`proxy`), web access with its two listeners (`web`), the interface and model languages (`language`), the default harness (`harnesses.default`), the credential store (`credentials.store`), the provider defaults (`providers`, <<provider-defaults>>), the plan defaults (`plan_defaults`), how documents are taken as a source (`sources.documents_mode`), the cleanup durations (`cleanup`), the speech role's methods with its local model and provider (`transcribe`, link:../model-work/01-roles-and-configuration.adoc#transcribe-role[Model Work Specification, The Speech Role `transcribe`]), the console preferences (`console`), and `project_defaults`, the machine's value of the per-project operator keys of `local-config.json` (xref:08-project-configuration-local.adoc#local-config[Operator Local Configuration (`<PM_MCP_BASE>/projects/<project_id>/local-config.json`)]). Every value the onboarding records here is the default of every project (xref:08-project-configuration-local.adoc#project-levels[Project Values over Machine Values]); only the interface language, the default harness, and the credential store are facts of the machine with no project value. The lock-wait report threshold is a compiled constant (link:../timeouts/02-runtime-leases-operator-web.adoc#runtime-lifecycle[Timeouts & Budgets Specification, Runtime Lifecycle]).

Written only by the runtime under `locks/machine-config.lock`, on the operator's acts: the sub-workflows of the machine's onboarding and their later runs from the machine settings (link:../workflow-dsl/01-grammar.adoc#machine-scope[Workflow DSL Specification, Machine Scope]), a value set or unset over the local API, `pm-operator config` and the direct verbs that run one aspect, and `pm-operator web enable|disable`, which take no port option. A key the machine's onboarding has not recorded yet is absent, and its compiled default applies where one exists; `credentials.store` has none (<<credential-store>>). `pm-operator` reads the file directly only for the drain timeout that bounds `pm-operator drain` (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#cli-file-reads[CLI, Coordination & Security Specification, Direct File Reads]). The timeout values, their bounds, and their expiry behaviour are defined in link:../timeouts/03-retention-harness-config.adoc#configuration-keys[Timeouts & Budgets Specification]; the `default`, `minimum`, and `maximum` values below equal them. The variants of the plan behaviour axes are the units of link:../workflow-dsl/09-plan-instance.adoc#plan-axes[Workflow DSL Specification, Plan Behaviour Axes]; the machine's landing default is validated only against what the machine itself provides (a provider for `landing.pull-request`), never against a repository.

[#consent]
=== Consent Before Acting (`<PM_MCP_BASE>/consents.json`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-8[PM-SEC-8: Consent Before Acting]_

The server asks before it looks at the machine or a checkout, runs a program it found, or spends model tokens on its own initiative. Every such action has a consent kind from the closed list below, and its state is preceded by a consent state, an operator wait (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]) named `<sub-workflow>.consent`, or `<sub-workflow>.<action>-consent` where a step asks several, with the operator links `yes`, `yes_remember` (only for a kind that can be remembered), and `no`. One consent state may ask several kinds, each answered separately. `no` records nothing and leaves the scope in the consent state, which offers the same links again; only an optional action (column _With no_) goes on without it. The server never takes the action without one of the two yes links, and a consent covers its kind and never a wider one: `scan_harnesses` runs no login or model probe. An act of the operator's own needs no consent: a secret the operator enters is stored on that act.

A grant is not a consent: reading another repository is a cross-repository read grant (xref:15-screening-and-grants.adoc#grant-record[Access Grant Record]).

*The store*: `consents.json` is the only place a remembered consent lives; a project's enrolment holds none. The runtime writes it under `locks/consents.lock` in the transaction of the consent state answered `yes_remember`, and on the operator's withdrawal in the machine settings of either client (link:../workflow-dsl/01-grammar.adoc#machine-scope[Workflow DSL Specification, Machine Scope], `settings.withdraw`) or over the local API; a consent state whose kind (and, for a project kind, project and scripts) is remembered is passed without a question. Withdrawing changes nothing recorded with the consent; its state asks again the next time its action runs. The consents of the speech role (`transcribe_browser`, `transcribe_provider`) gate a method the clients use later, not an action of a state: they are offered with `yes_remember` and `no` only, a `transcribe_provider` consent covers the provider it was given for (another provider asks it again), they are never asked by `auto_run`, and a withdrawn one takes its method out of use at once (a transcription by it refused `transcription_not_allowed`) until the method is allowed again in the roles step. Both a remembered and a withdrawn consent append an `operator` audit record (`consent_remembered`, `consent_withdrawn`, `details{kind, project_id}`). A consent of a project is asked before the project has its id in its onboarding: a `yes_remember` is held with the onboarding's entry and written here under the confirmed `project_id` in the transaction of `project.enrol`; an onboarding that does not reach its enrolment remembers nothing (link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-onboarding[Credentials & Enrolment Specification, Onboarding a Project as One Process]). For `run_checkout_scripts` the entry lists every script it covers with its digest; a later run asks only for a script that is not listed or whose digest changed, and its `yes_remember` replaces the list. The entries of a project go with its machine store when the cleanup deletes it.

[#model-catalogue]
=== Model Catalogue (`model-catalogue.json`, Machine and Project)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-1[PM-WORK-1: Roles as Configuration]_ +
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)]_

Which models plans may use, per enrolled harness. The machine's catalogue `<PM_MCP_BASE>/model-catalogue.json` is written by the catalogue step of the machine's onboarding and its later runs: the models a harness lists through its profile's `headless.models_probe` (source `probe`, after the consent `probe_harness_models`), or, where the harness cannot list them, the model ids the operator enters in `catalogue.select` (source `operator`); the operator keeps or drops each (link:../harness-profiles/01-profile-schema.adoc[Harness Profiles Specification, Profile Schema]). A project may allow its own: `<PM_MCP_BASE>/projects/<project_id>/model-catalogue.json`, of the same schema, chosen in the project's operator values from the models the enrolled harnesses offer (xref:08-project-configuration-local.adoc#project-levels[Project Values over Machine Values]), replaces the machine's catalogue for that project as a whole; without one the machine's applies. The *effective catalogue* of a project is its own, else the machine's. Role validation refuses a role whose effective model is not allowed on its harness by the effective catalogue (`model_not_allowed`, link:../model-work/01-roles-and-configuration.adoc#role-assignment[Model Work Specification, Role Assignment]); the steward, which advises before the catalogue exists, is outside it (link:../model-work/01-roles-and-configuration.adoc#steward-role[Model Work Specification, Steward Role]). The machine file is written under `locks/model-catalogue.lock`, the project file under the project's `locks/local-config.lock`. An entry of a harness that is no longer enrolled is ignored and dropped by the next write.

[#provider-defaults]
=== Machine Provider Defaults (`providers`, `<PM_MCP_BASE>/host-tools.json`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)]_ +
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXEC-5[PM-EXEC-5: Git & Provider Operations: Native and CLI Variants]_

The machine provides the providers every project starts from:

* *`providers` of `machine-config.json`* (<<machine-config>>): per provider (`git`, `github`, `gitlab`, `forgejo`, `sonar`) whether it is available, its default variant, and the credential key it uses; written by the provider step of the machine's onboarding and its later runs. A provider is recorded available only after its checks passed (link:../credentials-and-enrolment/01-provider-credentials.adoc#provider-verification[Credentials & Enrolment Specification, Provider Verification], which keeps the last result and the check lines); one whose checks failed is recorded only on the operator's word, and then as not available.
* *Machine host tools*: the CLI tools of the providers (`git`, `gh`, `glab`) are enrolled once for the machine in `host-tools.json`, with resolved absolute path, digest, version, and the instant of enrolment, like a harness: the runtime resolves the path once (no `PATH` lookup at job time), runs the tool's version probe, and records path, digest, version and the instant of enrolment, and nothing else. Written only by the runtime under `locks/host-tools.lock` on the provider step and its verb, with an HMAC sidecar `host-tools.json.hmac` in the format of the harness enrolment's sidecar under the enrolment integrity key (xref:11-enrolment-store.adoc#harness-enrolment-store[Harness Enrolment Store]), verified before every use. A project's enrolment uses these tools unless it enrols its own (`host_tools[]`, xref:11-enrolment-store.adoc#enrolment-store[Project Enrolment Store]); a tool of either file is checked on every use like an enrolled host tool, and a changed digest refuses the job with the reason and the act that enrols it again.
* *A project* still derives its CI provider from its remote (derived fact `ci_provider`, xref:09-derived-facts-and-build-timings.adoc#derived-facts[Derived Facts Store]); it takes the variant and the credential key from the machine's provider defaults unless its own operator values set them (xref:08-project-configuration-local.adoc#local-config[Operator Local Configuration]).

[#icon-store]
=== Harness Icon Store (`<PM_MCP_BASE>/icons/`)

The icons of harnesses whose profile declares the `source` form (link:../harness-profiles/01-profile-schema.adoc#harness-icons[Harness Profiles Specification, Harness Icons]). The runtime fetches an icon once, on the consent `fetch_icons`, through its outbound HTTPS client and the `proxy` setting, and stores it as `icons/<harness_id>.<ext>` (`svg` or `png`, mode `0600`) with `icons/index.json` (`format_version`, and per `harness_id` the source URL, the SHA-256 and size of the file, the media type, and `fetched_at`), written under `locks/icons.lock`. It serves the file to both clients from its own origin; a browser never loads an icon from its maker. A harness without a stored or bundled icon is shown with the monogram of its harness id. A file that differs from its index entry, or is larger than the compiled icon size bound, is not served and is fetched again only on a new consent. No shipped profile declares the `source` form (link:../../../../plan-marshall-documentation/doc/later-improvements.adoc#L-21[Later Improvements, L-21]), so the store stays empty.

[#explorer-store]
=== The Operator's Projects (`<PM_MCP_BASE>/explorer.json`)

The operator's favourite projects and their order, and per project when the operator last acted in it and how often over a rolling window, for the projects of the machine (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#project-explorer[Runtime & Interaction Model Specification, The Projects of the Machine]). Written by the runtime under `locks/explorer.lock` on the operator's acts in either client: a favourite set, moved, or removed; and, as activity, opening a project, starting a plan or an epic, answering a decision, and changing the project's configuration. An act counts on the UTC day it happened; days older than the compiled activity window are dropped by the next write. An entry of a project no longer enrolled is dropped by the next write. Explorer data is operator data only and never reaches a model.

[#credential-store]
=== Permission-Guarded File Credential Store (`<PM_MCP_BASE>/credentials/<credential_key>.json`, `PM-CRED-3`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CRED-3[PM-CRED-3: Permission-Guarded File Credential Store]_

The file store serves the Token-Lane credentials when the operator chose it (`credentials.store: file`, link:../credentials-and-enrolment/01-provider-credentials.adoc#credential-store-choice[Credentials & Enrolment Specification, Credential Store as an Operator Choice]); it is never a fallback. With `os` recorded, the OS store (service `de.planmarshall.mcp`) holds every entry, and an unavailable OS store makes the credentials unavailable (`credential_store_unavailable`) without a file being written in its place; before a store is recorded no credential is entered. The files are user-only `0600` JSON files inside `<PM_MCP_BASE>/credentials/` (`0700` directory; only `PM_MCP_BASE` relocates it), in `PM-MCP`'s own format with `format_version` and a closed schema (xref:01-format-and-session-log.adoc#format-versioning[Format Versioning & Atomic Write Discipline]); the naming keeps the project-scoped tier `<PM_MCP_BASE>/credentials/<project>/<credential_key>.json`, resolved before the global file, and files are named by credential key (`github`, `gitlab`, `forgejo`, `git-https` for the native git and provider integrations, `mcp-<server_id>` for an upstream MCP server, otherwise the key the operator's provider configuration names, for example `sonar`; `PM-CRED-1`, link:../identifiers/02-registry-stores-to-web.adoc#id-credential-key[Identifier Registry, `credential_key`]). No entry holds a harness's authentication: a harness CLI uses its own login, which `PM-MCP` neither stores nor exports.

A credential file is written only by the runtime under `locks/credentials.lock`: on the operator's act of entering a secret (the `pm-operator credentials` verbs, the secret read from the terminal with echo disabled, or the credential form of a paired device on the loopback listener, never on the LAN listener), stored on that act without a consent; on the move between the stores, which the operator's change of `credentials.store` runs in either direction and which carries the enrolment integrity key last; and, for the rotated user refresh token of a `github_app` entry, in the token refresh (link:../credentials-and-enrolment/01-provider-credentials.adoc#user-access-token[Credentials & Enrolment Specification, User Access Token]). The file is written atomically with mode `0600` and is never a template for hand editing. A file with a missing or different `format_version`, an undeclared field, or a field its `auth_type` does not allow is refused with a reason naming the file and the field, and holds only the step that needs the credential (`credentials_file_invalid`, held for the operator with the act that rewrites it). `PM-MCP` never reads `~/.plan-marshall/credentials/`, `PLAN_MARSHALL_CREDENTIALS_DIR`, or legacy keyring entries (`PM-MIG-2`).

The allowed origin for a credential is the origin of the `url` of its operator-owned entry (`PM-CRED-5`), plus, for `github` and `gitlab`, the API origin the provider module derives from it by its compiled rule (`https://github.com` -> `https://api.github.com`; every other host: the `url` origin; link:../credentials-and-enrolment/01-provider-credentials.adoc#agent-credentials[Credentials & Enrolment Specification, Agent Credentials of the Native Variant]); the native git transport sends the credential only when the effective remote URL has that origin (`remote_origin_mismatch` otherwise). No team file names a credential or decides where a token is sent.

`pm-runtime/src/main/resources/de/planmarshall/runtime/credentials/`, beside the credential store that holds the
entries: `FileSecretStore` writes the `format_version` and `value` subset today, and the codec of the full record is the
remaining work of `runtime.credentials`:

A file exists only for a complete credential: an empty secret is refused, so no placeholder state exists. The `auth_type` values `none` and `system` of `plan-marshall` have no file: a provider without authentication needs no credential, and the System Lane (the CLI variant of `git`, `github`, `gitlab`) uses the operator's ambient CLI authentication by design (link:../credentials-and-enrolment/01-provider-credentials.adoc#cli-variant-credentials[Credentials & Enrolment Specification, Credentials of the CLI Variant]). A GitHub App installation token is derived from the `private_key`, and a user access token from the `refresh_token`, at run time; neither is stored in any backend (link:../credentials-and-enrolment/01-provider-credentials.adoc#derived-tokens[Credentials & Enrolment Specification, Short-Lived Derived Tokens]).

[[credential-store-move-record]]*`state/credential-store-move.json`*: the open operation on the credential store, a move between the credential stores or the first recording of one (link:../credentials-and-enrolment/01-provider-credentials.adoc#credential-store-move[Credentials & Enrolment Specification, The Move]), written only by the runtime under `locks/credentials.lock`, which the operation holds for its whole duration: written with `phase: copying` at the start of the operation, before the first entry or the key is copied; rewritten once to `phase: switched` right after the write that switches `credentials.store` (<<machine-config>>); and deleted when the operation ends, last: after the last entry was deleted from the old store (a move), the key was deleted from the store the operation did not record, and, for a move, the `credential_store_moved` audit record was appended (so a stop or a failing audit sink before then leaves it, and the next start appends the audit record: at least once, with the same `transaction_id`), or when an operation that failed before the switch has deleted its copies from the target. An operation that failed before the switch keeps it where a copy could not be deleted from the target or `credentials.store` cannot be read, so the next start resumes it as below; where `credentials.store` names the target at that failure, which the lock discipline excludes, it is deleted and the copies stay, since the target is the recorded store and a resume would read the state as the switch. A move is refused before it is written when the target holds a Token Lane entry already, since a secret never exists in two stores, or holds another integrity key than the old store, since the move would overwrite it or delete it in a clean-up and the sidecars signed under it could never be verified again. `target_held_key` records whether the target held the integrity key the operation keeps when it started: the key of the old store for a move, and the key the sidecars verify under for a first recording, so a target that holds a key while `from` holds none holds that key and not the key of `from`; the clean-up of a failed operation and the resume delete the key from the target only where it did not, so they delete only a key the operation copied. `operation` says which operation the record drives: `move`, the move of every Token Lane entry and the key between the stores, or `first_recording`, the credential-store aspect's first recording of a store, which moves the integrity key alone and copies no entry. `transaction_id` is the id of the operation, issued once when the record is written and kept across a resume, so a re-delivered audit record of the operation carries the same id and a reader drops the duplicate. Its absence means that no operation is open. While it exists only the operation that owns it records `credentials.store`, and each of the two records it only while its own record exists; every other writer, the credential-store aspect included, is refused (`aspect_owned`), and the check is taken under `locks/credentials.lock`, so no writer records a store between the check and its write. After a stop the next start reads it and resumes the move:

* with `operation: move`, `phase: copying` and `credentials.store` still naming the old store, the stop fell before the switch: it deletes the copies from the target and starts again from the first entry;
* with `phase: copying` and `credentials.store` already naming the target, the stop fell between the switch and the rewrite of the record, so the switch has happened: it rewrites the record to `switched` and finishes the deletion from the old store, and never deletes from or copies into the recorded target;
* with `operation: first_recording` and `phase: copying` while no store is recorded, the stop fell before the switch: it deletes the copy from the store being recorded and records again; with that store recorded (in either phase) it deletes the key from the other store and ends the record;
* with `phase: switched` and `credentials.store` naming the target it finishes the deletion from the old store; with `phase: switched` and `credentials.store` naming another store or none the resume is refused, deletes nothing from either store and keeps the record.

It names stores only and holds nothing secret; it is read only by the runtime, never by a job or a model.

A scope in an operator wait or paused is never stalled. The record is operator and metrics data only and never appears in a model-facing representation.

*Hash chain (`PM-SEC-6`)*: The canonical line of a record is its exact UTF-8 byte sequence in `audit.jsonl`, excluding the terminating newline. A writer appends only under the audit lock (`LockKey.auditLog`, the leaf of the lock order), after reading the current last line to compute `prev_hash`; the append goes through the JSONL append path, which releases the lock of the operating system with its channel after each append, so the in-process lock of the one runtime serializes the appends and the runtime lock excludes a second runtime. A line chains to the last complete line of the log, the first line of a log after a rotation to the checkpoint line that closed the rotated log, and only the first line of a log that was never rotated to the genesis value. The writer also maintains the HMAC-anchored head `logs/audit.head` (<<audit-head>>) and, on rotation, a `checkpoint` record plus an entry in the hash-chained index `logs/audit-index.jsonl` (<<audit-index>>; link:../credentials-and-enrolment/03-audit-and-outbound-https.adoc#_security_audit_trail_three_tier_identity_verification[Credentials & Enrolment Specification, Security Audit Trail]). The runtime verifies incrementally from the last checkpoint at startup; a mismatch, unparsable line, missing log, reset, truncation, or head mismatch is reported to the operator and recorded as an `audit_chain_broken` record (`category: security`, `details.reason` `link_broken | missing | reset | truncated | head_mismatch`, and `details.first_broken_line` for `link_broken`), and no complete record of the log is ever rewritten or repaired; only a torn tail after the anchored head is truncated by the next writer (xref:01-format-and-session-log.adoc#format-versioning[Format Versioning & Atomic Write Discipline] item 6).
