== Machine Configuration, Operator Files, Credentials & Security Audit Stores

*Operator files and their revision*: The operator files of the machine (`machine-config.json`, `consents.json`, `role-assignments.json`, `model-catalogue.json`, `host-tools.json`, `explorer.json`) and of a project (`local-config.json`, `role-assignments.json`, `model-catalogue.json` in its machine store) are written only by the runtime, on an act of the operator in either client over the local API (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]), never by a model, a job, or a client process. Each carries `revision`, an integer the runtime increments with every write. A change names the revision it was made against; the first change wins, and a change against an older revision is refused with `conflict` (`409`), nothing merged and nothing overwritten unseen (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#two-channels[CLI, Coordination & Security Specification, Operator Choices in the Web App and the Terminal]). Every write is audited with its channel (`cli` or `web`) and, for a paired device, its `device_id` (<<audit-log>>).

[#machine-config]
=== Machine Configuration Store (`<PM_MCP_BASE>/machine-config.json`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)]_

Configures machine-wide build and worker concurrency limits, warm LSP pool sizing, the machine-level timeouts and budgets (drain timeout, escalation cap, progress wait bound, language server timeouts, audit rotation age, rotated audit file retention), the machine-wide connection overrides of the client profiles (`client_profiles.<client_id>.connection`, link:../client-profiles/01-profile-schema.adoc[Client Profiles Specification], Machine-Wide Operator Overrides), the outbound proxy (`proxy`), web access with its two listeners (`web`), the interface and model languages (`language`), the default harness (`harnesses.default`), the credential store (`credentials.store`), the provider defaults (`providers`, <<provider-defaults>>), the plan defaults (`plan_defaults`), how documents are taken as a source (`sources.documents_mode`), the cleanup durations (`cleanup`), the console preferences (`console`), and `project_defaults`, the machine's value of the per-project operator keys of `local-config.json` (xref:08-project-configuration-local.adoc#local-config[Operator Local Configuration (`<PM_MCP_BASE>/projects/<project_id>/local-config.json`)]). Every value the onboarding records here is the default of every project (xref:08-project-configuration-local.adoc#project-levels[Project Values over Machine Values]); only the interface language, the default harness, and the credential store are facts of the machine with no project value. The lock-wait report threshold is a compiled constant (link:../timeouts/02-runtime-leases-operator-web.adoc#runtime-lifecycle[Timeouts & Budgets Specification, Runtime Lifecycle]).

Written only by the runtime under `locks/machine-config.lock`, on the operator's acts: the sub-workflows of the machine's onboarding and their later runs from the machine settings (link:../workflow-dsl/01-grammar.adoc#machine-scope[Workflow DSL Specification, Machine Scope]), a value set or unset over the local API, `pm-operator config` and the direct verbs that run one aspect, and `pm-operator web enable|disable`, which take no port option. A key the machine's onboarding has not recorded yet is absent, and its compiled default applies where one exists; `credentials.store` has none (<<credential-store>>). `pm-operator` reads the file directly only for the drain timeout that bounds `pm-operator drain` (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#cli-file-reads[CLI, Coordination & Security Specification, Direct File Reads]). The timeout values, their bounds, and their expiry behaviour are defined in link:../timeouts/03-retention-host-config.adoc#configuration-keys[Timeouts & Budgets Specification]; the `default`, `minimum`, and `maximum` values below equal them. The variants of the plan behaviour axes are the units of link:../workflow-dsl/09-plan-instance.adoc#plan-axes[Workflow DSL Specification, Plan Behaviour Axes]; the machine's landing default is validated only against what the machine itself provides (a provider for `landing.pull-request`), never against a repository.

[#consent]
=== Consent Before Acting (`<PM_MCP_BASE>/consents.json`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-8[PM-SEC-8: Consent Before Acting]_

The server asks before it looks at the machine or a checkout, runs a program it found, or spends model tokens on its own initiative. Every such action has a consent kind from the closed list below, and its state is preceded by a consent state, an operator wait (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]) named `<sub-workflow>.consent`, or `<sub-workflow>.<action>-consent` where a step asks several, with the operator links `yes`, `yes_remember` (only for a kind that can be remembered), and `no`. One consent state may ask several kinds, each answered separately. `no` records nothing and leaves the scope in the consent state, which offers the same links again; only an optional action (column _With no_) goes on without it. The server never takes the action without one of the two yes links, and a consent covers its kind and never a wider one: `scan_harnesses` runs no login or model probe. An act of the operator's own needs no consent: a secret the operator enters is stored on that act.

[cols="2,4,2,2"]
|===
|Kind |What the operator allows |Remembered |With _no_

|`scan_harnesses` |look for the executables of the profiles' harnesses and run their version probe |for the machine |stays
|`fetch_icons` |download the makers' icons of the found harnesses once, through the runtime (<<icon-store>>) |for the machine |goes on with monograms
|`probe_harness_login` |run the login probe of each chosen harness, its command or one minimal headless call with its token cost |for the machine |stays
|`verify_harness_profile` |run a harness the binary does not know to verify its draft profile, with the token cost of its stages |never |stays
|`probe_harness_models` |run the model probe of each enrolled harness |for the machine |stays
|`model_advice` |a task of the steward with its expected tokens |for the machine |goes on without the advice
|`check_credential_store` |write, read, and delete one test entry in the chosen OS credential store |for the machine |stays
|`scan_providers` |look for the providers' CLI tools and the credentials already stored |for the machine |stays
|`verify_providers` |call each chosen provider with its credential and run its CLI tool |for the machine |stays

A grant is not a consent: reading another repository is a cross-repository read grant (xref:15-screening-and-grants.adoc#grant-record[Access Grant Record]).

*The store*: `consents.json` is the only place a remembered consent lives; a project's enrolment holds none. The runtime writes it under `locks/consents.lock` in the transaction of the consent state answered `yes_remember`, and on the operator's withdrawal in the machine settings of either client (link:../workflow-dsl/01-grammar.adoc#machine-scope[Workflow DSL Specification, Machine Scope], `settings.withdraw`) or over the local API; a consent state whose kind (and, for a project kind, project and scripts) is remembered is passed without a question. Withdrawing changes nothing recorded with the consent; its state asks again the next time its action runs. Both a remembered and a withdrawn consent append an `operator` audit record (`consent_remembered`, `consent_withdrawn`, `details{kind, project_id}`). A consent of a project is asked before the project has its id in its onboarding: a `yes_remember` is held with the onboarding's entry and written here under the confirmed `project_id` in the transaction of `project.enrol`; an onboarding that does not reach its enrolment remembers nothing (link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-onboarding[Credentials & Enrolment Specification, Onboarding a Project as One Process]). For `run_checkout_scripts` the entry lists every script it covers with its digest; a later run asks only for a script that is not listed or whose digest changed, and its `yes_remember` replaces the list. The entries of a project go with its machine store when the cleanup deletes it.

[#model-catalogue]
=== Model Catalogue (`model-catalogue.json`, Machine and Project)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-1[PM-WORK-1: Roles as Configuration]_ +
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)]_

Which models plans may use, per enrolled harness. The machine's catalogue `<PM_MCP_BASE>/model-catalogue.json` is written by the catalogue step of the machine's onboarding and its later runs: the models a harness lists through its profile's `headless.models_probe` (source `probe`, after the consent `probe_harness_models`), or, where the harness cannot list them, the model ids the operator enters in `catalogue.select` (source `operator`); the operator keeps or drops each (link:../client-profiles/01-profile-schema.adoc[Client Profiles Specification, Profile Schema]). A project may allow its own: `<PM_MCP_BASE>/projects/<project_id>/model-catalogue.json`, of the same schema, chosen in the project's operator values from the models the enrolled harnesses offer (xref:08-project-configuration-local.adoc#project-levels[Project Values over Machine Values]), replaces the machine's catalogue for that project as a whole; without one the machine's applies. The *effective catalogue* of a project is its own, else the machine's. Role validation refuses a role whose effective model is not allowed on its harness by the effective catalogue (`model_not_allowed`, link:../model-work/01-roles-and-configuration.adoc#role-assignment[Model Work Specification, Role Assignment]); the steward, which advises before the catalogue exists, is outside it (link:../model-work/01-roles-and-configuration.adoc#steward-role[Model Work Specification, Steward Role]). The machine file is written under `locks/model-catalogue.lock`, the project file under the project's `locks/local-config.lock`. An entry of a harness that is no longer enrolled is ignored and dropped by the next write.

[#credential-store]
=== Permission-Guarded File Credential Store (`<PM_MCP_BASE>/credentials/<credential_key>.json`, `PM-CRED-3`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CRED-3[PM-CRED-3: Permission-Guarded File Credential Store]_

The file store serves the Token-Lane credentials when the operator chose it (`credentials.store: file`, link:../credentials-and-enrolment/01-provider-credentials.adoc#credential-store-choice[Credentials & Enrolment Specification, Credential Store as an Operator Choice]); it is never a fallback. With `os` recorded, the OS store (service `de.planmarshall.mcp`) holds every entry, and an unavailable OS store makes the credentials unavailable (`credential_store_unavailable`) without a file being written in its place; before a store is recorded no credential is entered. The files are user-only `0600` JSON files inside `<PM_MCP_BASE>/credentials/` (`0700` directory; only `PM_MCP_BASE` relocates it), in `PM-MCP`'s own format with `format_version` and a closed schema (xref:01-format-and-session-log.adoc#format-versioning[Format Versioning & Atomic Write Discipline]); the naming keeps the project-scoped tier `<PM_MCP_BASE>/credentials/<project>/<credential_key>.json`, resolved before the global file, and files are named by credential key (`github`, `gitlab`, `forgejo`, `git-https` for the native git and provider integrations, `mcp-<server_id>` for an upstream MCP server, otherwise the key the operator's provider configuration names, for example `sonar`; `PM-CRED-1`, link:../identifiers/02-registry-stores-to-web.adoc#id-credential-key[Identifier Registry, `credential_key`]). No entry holds a harness's authentication: a harness CLI uses its own login, which `PM-MCP` neither stores nor exports.

A credential file is written only by the runtime under `locks/credentials.lock`: on the operator's act of entering a secret (the `pm-operator credentials` verbs, the secret read from the terminal with echo disabled, or the credential form of a paired device on the loopback listener, never on the LAN listener), stored on that act without a consent; on the move between the stores, which the operator's change of `credentials.store` runs in either direction and which carries the enrolment integrity key last; and, for the rotated user refresh token of a `github_app` entry, in the token refresh (link:../credentials-and-enrolment/01-provider-credentials.adoc#user-access-token[Credentials & Enrolment Specification, User Access Token]). The file is written atomically with mode `0600` and is never a template for hand editing. A file with a missing or different `format_version`, an undeclared field, or a field its `auth_type` does not allow is refused with a reason naming the file and the field, and holds only the step that needs the credential (`credentials_file_invalid`, held for the operator with the act that rewrites it). `PM-MCP` never reads `~/.plan-marshall/credentials/`, `PLAN_MARSHALL_CREDENTIALS_DIR`, or legacy keyring entries (`PM-MIG-2`).

The allowed origin for a credential is the origin of the `url` of its operator-owned entry (`PM-CRED-5`), plus, for `github` and `gitlab`, the API origin the provider module derives from it by its compiled rule (`https://github.com` -> `https://api.github.com`; every other host: the `url` origin; link:../credentials-and-enrolment/01-provider-credentials.adoc#agent-credentials[Credentials & Enrolment Specification, Agent Credentials of the Native Variant]); the native git transport sends the credential only when the effective remote URL has that origin (`remote_origin_mismatch` otherwise). No team file names a credential or decides where a token is sent.

[[credential-store-move-record]]*`state/credential-store-move.json`*: the open move between the credential stores (link:../credentials-and-enrolment/01-provider-credentials.adoc#credential-store-move[Credentials & Enrolment Specification, The Move]), written only by the runtime under `locks/credentials.lock`, which the move holds for its whole duration: written with `phase: copying` at the start of a move, before the first entry is copied; rewritten once to `phase: switched` right after the write that switches `credentials.store` (<<machine-config>>); and deleted when the move ends, after the last entry was deleted from the old store and the `credential_store_moved` audit record was appended (so a stop or a failing audit sink before then leaves it, and the next start appends the audit record: at least once), or when a move that failed before the switch has deleted its copies from the target. A move that failed before the switch keeps it where a copy could not be deleted from the target or `credentials.store` cannot be read, so the next start resumes the move as below; where `credentials.store` names the target at that failure, which the lock discipline excludes, it is deleted and the copies stay, since the target is the recorded store and a resume would read the state as the switch. A move is refused before it is written when the target holds a Token Lane entry already, since a secret never exists in two stores, or holds another integrity key than the old store, since the move would overwrite it or delete it in a clean-up and the sidecars signed under it could never be verified again. `target_held_key` records whether the target held the integrity key (then the key of the old store) when the move started; the clean-up of a failed move and the resume delete the key from the target only where it did not, so they delete only a key the move copied. Its absence means that no move is open. While it exists only the move records `credentials.store`, and the move records it only while it exists; every other writer, the credential-store aspect included, is refused (`aspect_owned`), and the check is taken under `locks/credentials.lock`, so no writer records a store between the check and its write. After a stop the next start reads it and resumes the move:

* with `phase: copying` and `credentials.store` still naming the old store, the stop fell before the switch: it deletes the copies from the target and starts again from the first entry;
* with `phase: copying` and `credentials.store` already naming the target, the stop fell between the switch and the rewrite of the record, so the switch has happened: it rewrites the record to `switched` and finishes the deletion from the old store, and never deletes from or copies into the recorded target;
* with `phase: switched` and `credentials.store` naming the target it finishes the deletion from the old store; with `phase: switched` and `credentials.store` naming another store or none the resume is refused, deletes nothing from either store and keeps the record.

It names stores only and holds nothing secret; it is read only by the runtime, never by a job or a model.

[#web-access-records]
=== Runtime Token & Web Access Records (`run/runtime.token`, `state/web-devices.json`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-7[PM-SEC-7: Optional Web Access, Device Pairing & Browser Channel Hardening]_

_Implementation watch: link:../../../../plan-marshall-documentation/doc/implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-16[PM-WATCH-CLI-16]_

The records of local trust and browser access (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#runtime-token[Runtime & Interaction Model Specification, Runtime Token]; link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#web-server[CLI, Coordination & Security Specification, Web Access & Pairing]). None of their content reaches a model-facing representation (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

*`run/runtime.token`*: not JSON and without `format_version`: the file content is exactly the runtime token, 43 base64url characters without padding and without a trailing newline (256 bits, link:../identifiers/02-registry-stores-to-web.adoc#id-runtime-token[Identifier Registry, runtime token]). Mode `0600` in the `0700` directory `<PM_MCP_BASE>/run/`; written atomically by the runtime at every start before the socket is bound, replacing the previous token; read by every local client after its owner, mode, and no-symlink check; outside every job's read set on Linux with Landlock ABI >= 2; on macOS and on Linux without Landlock a job can read it like any process of the user (link:../job-runtime/02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Job Runtime Specification, Linux Filesystem Confinement]). A token file that is absent, of another length, or outside the alphabet makes a client refuse with a diagnostic naming the path, never guess.

*`state/web-devices.json`*: the web device store, mode `0600`, written only by the runtime under `locks/web-devices.lock` (pairing, rename, revocation, idle expiry, and the `last_used_at` update at most once per write interval per device, link:../timeouts/02-runtime-leases-operator-web.adoc#device-last-used-granularity[Timeouts & Budgets Specification]). A device secret is never stored, only its SHA-256. A revocation ends the device's open event streams with its reason, which the web app shows (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#devices[CLI, Coordination & Security Specification, Devices in Both Clients]). *Pairing code (in memory only)*: The open pairing is held in the runtime's memory, never persisted: the SHA-256 of the normalized code, the label, `expires_at` (issue plus the pairing code lifetime, link:../timeouts/02-runtime-leases-operator-web.adoc#pairing-code-ttl[Timeouts & Budgets Specification]), and the failure count (at most the pairing failed-attempt limit, link:../timeouts/02-runtime-leases-operator-web.adoc#pairing-attempt-limit[Timeouts & Budgets Specification]). At most one pairing is open; a new one replaces it, and a redemption or the failure that reaches the limit removes it, after which, while the terminal client is open, the runtime issues a fresh code that reaches only the terminal client (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#fresh-code[CLI, Coordination & Security Specification, A Fresh Code after a Redemption]). A runtime restart discards it, so a pairing code never survives a restart and nothing about it is recoverable from disk.

*No process record*: The web listeners are part of the runtime and have no record and no lock of their own. Their setting is the `web` object of `machine-config.json` (<<machine-config>>); the live state of each (open or closed, port, and for the LAN listener the SHA-256 fingerprint of the DER certificate) is part of the runtime status (`GET /api/v1/status`, link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]), from which both clients take it.

The generated certificate and its private key live in `<PM_MCP_BASE>/web/tls/` (`cert.pem`, `key.pem`; directory `0700`, files `0600`), written only by the runtime on the first opening of the LAN listener and reused afterwards.

A row: `format_version` (`1`), `day` (date), `project_id`, `model`, `role`, `calls`, `tokens_in`, `tokens_out`, `total_tokens` (integers or `unmeasured`), `tasks`, `tasks_unmeasured`, `total_is_floor` (boolean), `plan_id` (the deleted plan), and `added_at`. It holds tokens only, never a cost.

[#audit-log]
=== Security & Transition Audit Log (`<PM_MCP_BASE>/logs/audit.jsonl`, `PM-SEC-6`)

The record, the head and the index entry with the closed schemas below and their strict codec, the hash chain with its predecessor rule across a rotation, the append under the audit lock, the record of a torn tail of the log written into the log itself, and the production audit sink are implemented in `pm-core` (`PM-SEC-6`, `PM-IMPL-7`, link:../../../pm-core/doc/developer/core-store.adoc[Scope Stores Developer Guide § The Audit Log]); the head under the HMAC of the enrolment integrity key, the rotation with its checkpoint record and the index, and the incremental and the full verification with the reasons below are implemented in `pm-runtime` (link:../../../pm-runtime/doc/developer/runtime-audit.adoc[Audit Trail Developer Guide]). Every record a scope transaction owes carries a `transaction_id` of its own, the key by which a reader drops a record handed over twice. Not implemented yet: the wiring of the sink and the verification into `pm-mcpd`, which today passes no verification and refuses every record, the verb `pm-operator audit verify`, the removal of rotated files by the periodic sweep, and the reading of the rotation limits from `machine-config.json`; until the last one the runtime rotates at the defaults.

Every state transition, job execution, operator act (in either client), credential lookup, consent, and store deletion appends a structured JSONL record to `audit.jsonl` (with all Token-Lane secrets redacted):

----

  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://cuioss.de/plan-marshall-mcp/schemas/audit-record.json",
  "title": "AuditRecord",

  "required": ["format_version", "event_id", "prev_hash", "timestamp", "category", "event", "actor", "outcome"],
  "additionalProperties": false,
  "properties": {
    "format_version": { "type": "integer", "const": 1 },
    "event_id": { "type": "string", "format": "uuid", "pattern": "^[0-9a-f]{8}-[0-9a-f]{4}-7[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$" },
    "prev_hash": {
      "type": "string",
      "pattern": "^[0-9a-f]{64}$",
      "description": "SHA-256 (lowercase hex) of the previous record's canonical line; 64 '0' characters for the first record of the log."
    },
    "timestamp": { "type": "string", "format": "date-time" },
    "category": { "type": "string", "enum": ["transition", "job", "operator", "security", "credential", "store"] },

    "scope_type": { "type": ["string", "null"], "enum": ["plan", "epic", "workspace", "entry", "project", "machine", null] },
    "scope_id": { "type": ["string", "null"] },

    "details": { "type": "object", "description": "Event-specific fields.   }

----

*Identity*: No record carries an identity a client declared. An operator act is identified by its channel and device (`details{channel, device_id, os_principal}`), a worker's call by its job record (`details{job_id, role, harness, generation_id}`), and a machine-level record (runtime start, a sweep, a lease or audit-chain event) by `details.os_principal`.

*Transition records*: Every committed state transition of a plan, an epic, the workspace scope, an entry, or the machine scope appends a `transition` record with `event: transitioned` and `details{from_state, to_state, link, instance_version}`, the link the operator, a worker, or the server took. It is the security mirror of the transition; the record a client reads of a plan's process is the plan's own history (xref:02-workflow-state-store.adoc#plan-history[The Plan's History]), and no view of the clients reads the audit log.

*Checkpoint records*: A rotation appends a `security` record with `event: checkpoint`, `scope_type: machine`, and `details{record_count, head_hash, hmac}` (the number of records in the file before the checkpoint, the hash of the last canonical line before it, and the HMAC-SHA-256 over both under the enrolment integrity key).

*Enrolment records*: An enrolment HMAC mismatch appends a `security` record (`event: enrolment_tampered`), an operator re-baselining an `operator` record. An enrolment write that sets or clears `container_engine` appends an `operator` record (`event: container_engine_enabled` or `container_engine_disabled`, `details{project_id, engine}`), naming the Docker-group authority the operator confirmed. `pm-operator project unenrol` appends `project_unenrolled`, and the release of a project `project_released` (`operator`, `details{project_id, plans, epics}`).

*Consent records*: A remembered and a withdrawn consent append an `operator` record (`event: consent_remembered` or `consent_withdrawn`, `details{kind, project_id}`, <<consent>>); a consent answered `yes` or `no` for one run is part of the transition record of its state.

*Credential records*: Every refresh of a GitHub App user access token appends a `credential` record (`event: user_token_refreshed`, `details{credential_key, refresh_expires_at}`, never a token); a refresh that fails appends `event: user_token_refresh_failed` with the provider's reason, and the entry is `credential_check_failed` until the operator runs the device flow again. The choice and every move of the credential store append an `operator` record (`event: credential_store_chosen` or `credential_store_moved`, `details{from, to, entries}`).

*Waiver records*: Every line of a plan's `waivers.jsonl` is mirrored as an `operator` record (`event: waiver_waived` or `waiver_revoked`, `details{plan_id, waiver_id, gate, mode, reason_class}`, xref:14-plan-instance-waivers-questions.adoc#waiver-record[Waiver Record]); the recurrence count of a gate across plans (link:../phase-workflows.adoc[Phase Workflows Specification], Artifact Gate) and the lessons-capture signal are derived from the `waiver_waived` records of the last 90 days by `gate` and `reason_class`, whatever the cleanup has deleted since. No separate exemption record exists.

*Integration records*: Every git or provider operation, in-process (native variant) or as a job (CLI variant), appends a `job` record whose `details` carry `integration` (`git`, `github`, `gitlab`, `forgejo`, `sonar`), `variant` (`native` or `cli`), and `identity`: for the native variant the credential key that authenticated it (`github`, `gitlab`, `forgejo`, `git-https`, link:../identifiers/02-registry-stores-to-web.adoc#id-credential-key[Identifier Registry, `credential_key`]; never the secret or a derived token) and the resolved agent identity, for the CLI variant the value `operator_ambient` (link:../credentials-and-enrolment/01-provider-credentials.adoc#cli-variant-credentials[Credentials & Enrolment Specification, Credentials of the CLI Variant]). A native operation refused by the origin check appends a `security` record with `event: remote_origin_mismatch`, `outcome: refused`, and `details{integration, remote, effective_url_host, credential_origin}` (link:../credentials-and-enrolment/01-provider-credentials.adoc#native-confinement[Credentials & Enrolment Specification, Native Operation Confinement]). The operator's choice of a variant (a machine default, or a project's own value) is an `operator` record with `event: integration_variant_selected` and `details{integration, variant, project_id}`. These fields are operator and audit data only: they never appear in a model-facing representation, resource, or tool result (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

*Worker, grant, and source records*: A request over a worker's connection carries `details.job_id`, `details.role`, `details.harness`, and `details.generation_id` in every record it causes. The supervisor appends a `job` record `worker_started` and `worker_ended` (`details{job_id, role, form, end_reason}`) per worker; a refused call of a fenced generation a `security` record `generation_fenced` (`details{generation_id, tool}`); a stop of a role's starts after repeated start failures a `job` record `worker_starts_stopped` (`outcome: warning`, `details{role, harness, start_failures, harness_error}`, the harness's own error text, redacted); a task that ended `lost` and sent its state to the conservative fallback a `transition` record `task_fallback` (`details{queue_task_id, role, reason}`, reason `attempts_spent`, `role_undefined`, `class_mismatch`, `role_unqualified`, or `role_unavailable`); and the load of an invalid role artifact an `operator` record `role_invalid` (`details{role, set, reason}`). A harness enrolment (`harness.enrol` of the onboarding or `pm-operator enrol-harness`) appends an `operator` record `harness_enrolled` (also when it re-baselines a tampered file), an accepted self-update an `operator` record `harness_updated`, and a failed HMAC check of `harnesses.json` or `host-tools.json` a `security` record `enrolment_tampered` naming the file (xref:11-enrolment-store.adoc#harness-enrolment-store[Harness Enrolment Store]). Every access grant is mirrored as an `operator` record `access_granted` with `details{plan_id, entry_id, project_id, target, access, reason}` (the scope the grant is recorded in, and `target` the `project_id`, `org`, or `repo` of the grant) (xref:15-screening-and-grants.adoc#grant-record[Access Grant Record]). The operator's acceptance of a source of a start flagged by the screener or left unscreened appends a `security` record `screen_accepted` with `details{entry_id, source_id, sha256, verdict, reason}` (`verdict` `suspicious` or `unscreened`). A refused re-check of a start's `start.create-scope` transaction is scope-less (no plan or epic exists yet): it appends a `transition` record `bootstrap_refused` (`scope_type: entry`, `details{entry_id, reason}`) and is never counted per plan.

*Store deletions*: Every item the cleanup deletes appends one `store` record `cleanup_deleted` (`details{kind, id, project_id, job_id, channel, size_bytes}`, <<cleanup-journal>>); every removal of the periodic sweep one `store` record naming the residue and its evidence (xref:13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Evidence-Based Removal Sweeps]).

*Web access records*: A successful pairing appends an `operator` record with `event: web_device_paired`, `outcome: succeeded`, and `details{device_id, label, paired_from}`; a failed redemption a `security` record with `event: web_pairing_failed`, `outcome: refused`, and `details{failures, pairing_invalidated}` (never the submitted code); a rename an `operator` record `web_device_renamed` (`details{device_id, label}`); a revocation an `operator` record with `event: web_device_revoked`, `outcome: succeeded`, and `details{device_id, reason}` (`reason`: `operator` for a revocation by the operator in either client, `idle_expired` for the device idle expiry, link:../timeouts/02-runtime-leases-operator-web.adoc#device-idle-expiry[Timeouts & Budgets Specification]), one record per device when several are revoked at once. An act taken through a paired device carries `details.channel: web` and `details.device_id`; one through `pm-operator` `details.channel: cli`. Opening and closing a listener (`pm-operator web enable|disable`, turning the LAN listener off from a device) has no record form of its own: like every act that changes `machine-config.json` it appends one machine-level `operator` record. No record carries a device secret, its hash, or the runtime token (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#web-server[CLI, Coordination & Security Specification, Web Access & Pairing]).

*Runtime lifecycle records*: The operator's stop, its withdrawal, an upgrade, its withdrawal, and an update check append an `operator` record (`event: runtime_stop_requested`, `runtime_stop_withdrawn`, `runtime_upgrade_requested`, `runtime_upgrade_withdrawn`, `runtime_update_checked`, with `when`, `then`, or the version in `details`); an upgrade's result a `transition` record `runtime_upgraded` or `runtime_upgrade_failed` (`details{from_version, to_version, reason}`, <<upgrade-record>>).

*Stall records*: A plan (or epic) that becomes stalled (link:../runtime-lifecycle/02-plan-pause-and-stalled-plans.adoc#stalled-plans[Runtime Lifecycle Specification]) appends one `transition` record per stall episode with `event: plan_stalled`, `outcome: warning`, `scope_type: plan` (or `epic` for a stalled epic), and `details{state, cause, idle_since, idle_seconds}` (`cause` from the closed set of link:../runtime-lifecycle/02-plan-pause-and-stalled-plans.adoc#stalled-plans[Runtime Lifecycle Specification, Stalled Plans]: `no_progress`); the next transition of the scope ends the episode, and a later stall starts a new one. A scope in an operator wait or paused is never stalled. The record is operator and metrics data only and never appears in a model-facing representation.

*Hash chain (`PM-SEC-6`)*: The canonical line of a record is its exact UTF-8 byte sequence in `audit.jsonl`, excluding the terminating newline. A writer appends only under the audit lock (`LockKey.auditLog`, the leaf of the lock order), after reading the current last line to compute `prev_hash`; the append goes through the JSONL append path, which releases the lock of the operating system with its channel after each append, so the in-process lock of the one runtime serializes the appends and the runtime lock excludes a second runtime. A line chains to the last complete line of the log, the first line of a log after a rotation to the checkpoint line that closed the rotated log, and only the first line of a log that was never rotated to the genesis value. The writer also maintains the HMAC-anchored head `logs/audit.head` (<<audit-head>>) and, on rotation, a `checkpoint` record plus an entry in the hash-chained index `logs/audit-index.jsonl` (<<audit-index>>; link:../credentials-and-enrolment/03-audit-and-outbound-https.adoc#_security_audit_trail_three_tier_identity_verification[Credentials & Enrolment Specification, Security Audit Trail]). The runtime verifies incrementally from the last checkpoint at startup; a mismatch, unparsable line, missing log, reset, truncation, or head mismatch is reported to the operator and recorded as an `audit_chain_broken` record (`category: security`, `details.reason` `link_broken | missing | reset | truncated | head_mismatch`, and `details.first_broken_line` for `link_broken`), and no complete record of the log is ever rewritten or repaired; only a torn tail after the anchored head is truncated by the next writer (xref:01-format-and-session-log.adoc#format-versioning[Format Versioning & Atomic Write Discipline] item 6).
