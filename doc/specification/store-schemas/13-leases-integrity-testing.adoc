[#machine-lease-stores]
== Machine Lease Stores & Task Leases (`merge-queue.json`, `review-bot-windows.json`, `build-slots.json`, `model-slots.json`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-37[PM-WATCH-STORE-37], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-52[PM-WATCH-STORE-52]_

The four lease stores in `<PM_MCP_BASE>/state/` are updated only in short transactions under their machine store locks (<<lock-free-snapshot-reads>>; `PM-IMPL-7`, `PM-WF-15`). Every lease owner has the same shape, and every instant follows the one wire shape (xref:01-format-and-session-log.adoc#format-versioning[Format Versioning & Atomic Write Discipline] item 5), so a lease written by one component and reclaimed by another round-trips byte-identical instants.

*Ownership vs Liveness*: A lease is owned by its scope (`project_id`, `scope_type`, `scope_id`; a model slot by the project whose worker holds it, `scope_type: project`, or by the machine scope for a worker of the machine scope, `scope_type: machine` without a project), never by the runtime instance; the project's recovery after a runtime start selects the project's leases by `project_id`; `holder_instance` records only which runtime currently serves it. At runtime start, a lease whose `holder_instance` is no longer alive (PID plus start instant) is not released but marked `orphaned_at`; the next call addressing the owning scope adopts it (sets `holder_instance` to the new runtime, clears `orphaned_at`) under the machine store lock. An orphaned lease is released only on positive evidence of abandonment: the owning scope is terminal, archived, or no longer resolvable; its `lease_expires_at` passed without adoption; or, for a build or model slot, its job was recorded as `killed` at the restart (such a slot is therefore released at once). For the merge holder, provider-side evidence also counts: when the provider observation of the holder's pull request (`ci.pr-observe`) reports it merged or closed, the next admission transaction releases the holder lease, with an audit record naming the observation, whether or not the lease is orphaned or expired. An unobservable or failed provider observation is no evidence and releases nothing.

* *`merge-queue.json`*: `{"format_version": 1, "repositories": {"<repository key>": {"holder": <lease> | null, "waiting": [<entry>]}}}`. A `holder` lease carries `owner`, `acquired_at`, `heartbeat_at`, and `lease_expires_at` (heartbeat and expiry rule in link:../timeouts/02-runtime-leases-operator-web.adoc#merge-lease[Timeouts & Budgets Specification, Merge Holder Lease]); a `waiting` entry carries `owner` and `enqueued_at`, in FIFO order.
* *`build-slots.json`*: `{"format_version": 1, "slots": [<lease>], "waiting": [<entry>]}`, one lease per running build job keyed by `owner` and `job_id`, with `acquired_at` and `lease_expires_at` (link:../timeouts/02-runtime-leases-operator-web.adoc#build-slot-lease[Timeouts & Budgets Specification, Build Slot Lease]); a `waiting` entry carries `owner`, `job_id`, and `enqueued_at`, in FIFO order, for a build job recorded `queued` (its wait bounded as in link:../timeouts/01-job-budgets-and-waits.adoc#build-slot-wait[Timeouts & Budgets Specification, Build Slot Wait]). The slot count never exceeds `max_build_slots` (xref:12-machine-stores.adoc#machine-config[Machine Configuration Store (`<PM_MCP_BASE>/machine-config.json`)]).
* *`model-slots.json`*: `{"format_version": 1, "slots": [<lease>], "waiting": [<entry>]}`, one lease per running worker, warm or fresh, with `owner`, `job_id`, `role`, `class` (`writer`, `read_only`, `zero_tool`), `form` (`warm`, `fresh`), `plan_id` (the plan of a writer worker, else `null`), `acquired_at`, and `lease_expires_at: null` (link:../timeouts/02-runtime-leases-operator-web.adoc#model-slot-lease[Timeouts & Budgets Specification, Model Slot Lease]); a `waiting` entry carries `owner`, `job_id`, `role`, `class`, `plan_id`, and `enqueued_at`, in FIFO order, for a worker recorded `queued`. The slot count never exceeds `model_slots` (xref:12-machine-stores.adoc#machine-config[Machine Configuration Store (`<PM_MCP_BASE>/machine-config.json`)]), and at most one `writer` worker of a plan holds a slot or waits for one. A slot is acquired in the transaction that turns the worker `running` and released after its fate; a warm worker holds it for its whole generation, idle or not. Which worker the supervisor starts is decided from the task queue (xref:16-task-queue.adoc#queue-task-record[Queue Task Record]); this store holds only the slots and the workers waiting for one. The gauges of the runtime's metrics for slots and leases (in use, caps, held) are kept by the transactions that write these stores and set from them at the start (link:../runtime-lifecycle/03-runtime-metrics.adoc#runtime-metrics[Runtime Lifecycle Specification, The Runtime's Metrics]).
* *Task leases*: A queue task is leased to one worker generation, recorded as `lease` in its queue task record under the queue lock (xref:16-task-queue.adoc#queue-task-record[Queue Task Record]), never in a machine store. The lease is taken by the offer, has no time expiry of its own (link:../timeouts/02-runtime-leases-operator-web.adoc#task-lease[Timeouts & Budgets Specification, Task Lease]), and is released in the transaction that records the attempt's outcome, the fence of the holding generation, or a pause of the plan that withdraws the task (the task is offered again when the plan is started; link:../runtime-lifecycle/02-plan-pause-and-stalled-plans.adoc#plan-pause[Runtime Lifecycle Specification, Pausing and Starting a Plan]); a leased task is never offered to a second wait of the same generation. At runtime start every task lease is released by the project's recovery (xref:16-task-queue.adoc#task-queue[Task Queue], Recovery: the attempt ends `restart`, uncounted, and the task is queued again); a lease is never orphaned or adopted.
* *`review-bot-windows.json`*: `{"format_version": 1, "windows": {"<org>/<bot_kind>": <window>}}`. Rate windows are org-scoped, so a window claim is keyed by organisation and `bot_kind`; attempt counters inside a window are keyed by `(repository, pr_number, bot_kind)`, so one pull request never reports another's attempts. A window stores `owner`, `claimed_at`, the absolute `reset_at` (derived per link:../timeouts/01-job-budgets-and-waits.adoc#review-bot-windows[Timeouts & Budgets Specification, Review-Bot Rate Windows]), `attempts` (bounded by the bot's `attempt_ceiling`, xref:03-findings-and-review-records.adoc#review-bot-registry[Review-Bot Registry Record]), and `answers_trigger_id` (the review request the refusal answered). A wait on a window computes its remainder from `reset_at`, so a killed waiter or a runtime restart resumes the remainder; re-reading the same refusal never restarts a window that has already been waited out. A contended claim returns `reason`, `holder`, and `seconds_remaining`.

== Data Layer Integrity & Concurrency Invariants (`PM-IMPL-7`)

[#store-digest-verification]
=== Store Digest Verification Against Out-of-Band Edits

[[_store_digest_verification_against_out_of_band_edits]]
The digest sidecar of a scope, the recording of a digest only through the transaction journal, the verification of a store under the scope lock after the recovery of the scope, the lock-free report `digest_unverified`, and the re-baseline of a digest are implemented (`PM-IMPL-7`, link:../../../../plan-marshall-documentation/doc/concepts/store-integrity.adoc#out-of-band-edits[Concepts § Store Integrity, Out-of-Band Edits], link:../../../../plan-marshall-documentation/doc/developer/store-substrate.adoc#digests[Developer Guide § Store Substrate, Verifying and Re-Baselining Digests]). Which stores a sidecar covers, and what the runtime does with a decided mismatch, are specified here:

* The sidecar of a scope covers these stores, each written by a transaction of the scope: a plan's `mcp/status.json`, its history `mcp/history.jsonl`, `intent.json`, `outline.json`, `references.json`, `TASK-*.json`, the plan instance files `instance/plan.v<N>.pmwf`, `instance/<unit>.v<N>.pmwf`, and `instance/composition.jsonl`, `overrides.json`, the bound sub-unit copies `mcp/units/<digest>.pmwf`, `metrics.json`, `quality-report.json`, the findings, assessment, review-participation, change-ledger, `waivers.jsonl`, `waiver-consumptions.jsonl`, `grants.jsonl`, `questions.jsonl`, `screen-verdicts.jsonl`, `decisions.jsonl`, and `evidence/failures.jsonl` files, the evidence excerpt files `evidence/<evidence_id>.log`, the facts snapshots `decision-facts/<facts_digest>.toon`, the kept undelivered landing envelope `landing-envelope.json`, the source manifest `sources/sources.json` (whose entries carry the digest of every stored source file, verified on every read of the file), `outline.md`, and `request.md`, but not the plan mailbox `mcp/mailbox.jsonl`, which is advisory content under its own leaf lock (xref:04-epic-and-change-ledger.adoc#epic-inbox-record[Epic Inbox & Plan Mailbox Records (`inbox.jsonl`, `mcp/mailbox.jsonl`)]), and the activity journals `tasks/activity/<queue_task_id>.jsonl` of every scope, which are untrusted display data written while a worker runs, outside the transaction journal; the workspace scope's `mcp/status.json`, `questions.jsonl`, `screen-verdicts.jsonl`, `decisions.jsonl`, `grants.jsonl`, the facts snapshots `decision-facts/<facts_digest>.toon`, `metrics.json`, the findings and change-ledger JSONL files, and of every pending entry its record `pending/<entry_id>/entry.json`, its source manifest `pending/<entry_id>/sources/sources.json`, and its `grants.jsonl`; an epic scope's `status.json`, `decomposition.json`, `questions.jsonl`, `screen-verdicts.jsonl`, `decisions.jsonl`, the facts snapshots `decision-facts/<facts_digest>.toon`, and `metrics.json`; and the machine scope's `machine/mcp/status.json` and `machine/metrics.json`.
* On every read of a store inside a transition, the engine verifies it against the sidecar under the scope lock: any mismatch that remains after the recovery of the scope immediately raises the `integrity_breach` condition (`kind: store_tampered`, with the store and the recorded and current size and digest) on the scope's current state (link:../state-catalogue/01-conventions-generic-conditions.adoc[State Catalogue, Conditions]), which replaces any other condition, leaves `state` and `call_stack` unchanged, offers no link to a worker, rejects every `pm_do` with `integrity_paused`, and is held for the operator as a hold of kind `integrity_pause` (link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue Specification, Holds and Their Acts]). It has no time bound and no fallback; nothing of the paused scope waits on time meanwhile. A tampered enrolment file (`kind: enrolment_tampered`) raises the same condition on every running plan of the project. A breach of a pending entry's stores raises it only on that entry: the workspace scope's own state and its other entries continue, and the pause ends by `accept-edit` of the entry's store or by the operator's abandoning of the entry.
* A store that a transaction deleted has neither a file nor a sidecar entry: the delete target of the transaction journal removes the store and drops its entry together (xref:01-format-and-session-log.adoc#transaction-journal[Transaction Journal]), and the verification finds the two in agreement, so the removed store is consistent and never a breach. Only an entry that outlives its file, or a file that differs from its entry, is the evidence of an edit. This rule is implemented (`PM-IMPL-7`, link:../../../pm-core/doc/developer/core-store.adoc[Scope Stores Developer Guide § The Delete Mode of the Transaction Journal]).
* A lock-free snapshot reader (<<lock-free-snapshot-reads>>) serves a store reported `digest_unverified` with `facts.store_integrity: digest_unverified` naming the store; it never reports a breach.
* *Resolutions*: The acts of an `integrity_pause` are closed and are operator acts of both clients. `accept-edit` (`pm-operator accept-edit plan <plan_id> <store>`, `epic <epic_id> <store>`, `workspace <store>`, `lesson <lesson_id>` (the lesson store, last item), or `enrolment <project_id>` (a project's enrolment file, whose HMAC sidecar it re-baselines, xref:11-enrolment-store.adoc#enrolment-store[Enrolment Store]) in the terminal; link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-accept-edit[CLI, Coordination & Security Specification, Accept-Edit]) shows the tampered file with its path and its recorded and current size and SHA-256 before confirmation, restores nothing and shows no diff (the prior content is not kept), re-baselines that store's digest, and records the act in `audit.jsonl`; the engine then re-verifies every store of the scope before it clears the condition. The other way out is *cancel*, for a plan or epic scope: it is the resolution _abort_ of the pause and ends a plan through `plan.aborted` with the outcome `aborted` and an epic with the `terminal_reason` `cancelled` (link:../state-catalogue/04-plan-finalize-terminal.adoc#plan-end[State Catalogue Specification, Cancelling and Abandoning Archive]). The workspace scope has no cancel, so a workspace breach ends only by `accept-edit workspace <store>`, and the breach of a pending entry also by abandoning the entry.
* The durable intents of owed audit records, the transaction journal and the intent file `<store>.audit-intent` of a JSONL store, are no stores: the sidecar never covers them, and they exist only until the audit sink accepted the records they owe (xref:01-format-and-session-log.adoc#transaction-journal[Transaction Journal], Audit delivery). A journal kept for an owed record marks its scope `digest_unverified` for a lock-free reader like any journal, until the next recovery hands the record over.
* The project's lesson store keeps its own sidecar with the same format and rules, at lesson granularity (xref:10-job-and-lesson-records.adoc#lesson-record[Lesson Record (project lesson store)]): an out-of-band edit or deletion of one lesson blocks only that lesson.

[#three-way-footprint]
=== Three-Way File Footprint Reconciliation (`references.json`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-19[PM-WATCH-PHASE-19], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-21[PM-WATCH-STORE-21], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-22[PM-WATCH-STORE-22], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-23[PM-WATCH-STORE-23], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-24[PM-WATCH-STORE-24], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-33[PM-WATCH-STORE-33], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-36[PM-WATCH-STORE-36]_

[[_three_way_file_footprint_reconciliation_references_json]]
The `references.json` store tracks three distinct file-footprint sets for a plan:

* *Declared Footprint (`declared_files`)*: Files explicitly listed during refinement/outline, the plan's statement of intent. `declared_files` is immutable once `outline.gate` passed. A path changed later beyond it inside the plan worktree is accepted and recorded in `unplanned_changes[]` with its provenance (task or loop-back, phase, time), never appended to `declared_files` and never reviewed; every reconciliation result names whether a realized path was declared or unplanned. Only boundary breaches (outside the worktree, the main checkout, protected paths) are refused, by the non-waivable guards.
* *Structured-Derived Footprint (`derived_files`)*: Re-derived by set union over the solution outline's structured deliverables and partitioned into three disjoint keys:
** `expected_modifications`: Files the plan intends to create, modify, or delete.
** `conditional_modifications`: Files declared `(write-conditional)`, edited only if a named gate fires.
** `read_only_references`: Files inspected for context that must remain unmodified.
* *Realized Footprint (`realized_files`)*: Captured from the plan's own worktree via `git` jobs as the union of `git diff --name-status -M <base_ref>...HEAD` and `git status --porcelain=v1 -z`. A rename or copy contributes both its old and its new path to `realized_files` and is also recorded as a pair in `realized_renames[]`. *Deliberate change vs. `plan-marshall`*: `compute-footprint` uses `--name-only`, which drops the old path of a rename.

Resolution and capture rules:

* *Base Reference*: `<base_ref>` is `git merge-base HEAD origin/<base_branch>`, computed after the most recent fetch (after `sync-baseline`, the rebased-onto tip). It is never the SHA the plan was created against and never a local `<base_branch>` ref. Every footprint, scope, and self-review diff of the plan reads this one `base_ref`, recorded in `realized_state.base_ref`; after a `sync-baseline` or `branch-cleanup` rebase the realized footprint is re-derived against the new merge-base. When the local `<base_branch>` trails `origin/<base_branch>`, `realized_state.base_commits_behind` records by how many commits, so a stale local ref is visible although it is never used.
* *Own Tree Only*: The realized footprint resolves only from the plan's own worktree, through one resolver whose tiers (the live diff, then the persisted capture) apply identically to every consumer. A pending or absent worktree yields `realized_state.state: unresolved` with cause `pending` (not yet materialised; plans always execute in a worktree, so no other cause exists), never another tree's measured-empty set; `unresolved` and "measured, both sides empty" stay distinct. A diff-fed step without a resolvable footprint ends with an outcome of class `INDETERMINATE` naming the cause (the step completes `failed`), never a clean `done`.
* *Only `measured` Reconciles*: `realized_state` is always present; the plan's creation transaction writes it as `not_captured`. The three-way reconciliation, the footprint coverage, the scope-creep check, and every pre-merge or post-merge footprint check compare against `realized_files` only when `realized_state.state == measured`; for `unresolved` and `not_captured` each of them reports `indeterminate` with the state and cause named, never a clean or empty result.
* *Capture Before Destruction*: `realized_files` is captured and persisted (`realized_state.captured_at`) at the latest before `branch-cleanup` (order 70) removes the worktree. Post-merge consumers read the persisted set; a post-merge git-derived empty set is never evidence of no change, and a missing persisted set (`realized_state.state: not_captured`) makes the consumer report `indeterminate`. Steps that compute the footprint publish its size (`files_total`, `insertions_total`, and a source-vs-data split) as facts.
* *Consumer Scope and Provenance*: Every consumer that derives a scope from `references.json` names the set it reads. Footprint-scoped consumers (the self-review surfacer, `simplify`, `security-audit`) scope on `declared_files ∪ derived_files.expected_modifications ∪ realized_files`, re-read at each firing, and carry each path's provenance (`declared`, `derived`, `realized`, `unplanned`); a union is never passed on without it. `derive-verification` keeps reading the realized set only.

Pairwise reconciliation computes the **symmetric difference in both directions** ($A \setminus B$ and $B \setminus A$) across all three sets so that two equal-sized but disjoint file sets are reported as 100% disagreeing rather than matching by count. In addition:

* `derived_files \ realized_files` is reported split by intent: untouched `read_only_references` and untouched `conditional_modifications` are expected, while untouched `expected_modifications` are reported as `modify_shortfall`.
* *Coverage Populations*: Footprint coverage is $|\text{expected\_modifications} \cap \text{realized\_files}| / |\text{expected\_modifications}|$, published with both populations. Read-only references are a separate population (reported as touched or untouched, never in the coverage ratio), and conditional modifications are reported beside it (touched or not), never in the denominator. An empty `expected_modifications` makes coverage `not_derivable`, never `100%`.
* *Scope-Creep Allow Set*: A realized path is inside the plan's declared scope when it is in `declared_files ∪ derived_files.expected_modifications ∪ derived_files.conditional_modifications`; a realized path outside it (including one declared only as a read-only reference) is an unplanned change: recorded, listed in the PR body and the landing record, and never blocking.
* Paths from change-ledger entries with `change_origin: quality_gate_autofix` are reported separately from deliverable changes.
* Results are published per deliverable (from the deliverable's `Affected files` and its task and chain-tail change entries) beside the plan-level figures; a plan-level average never replaces them.
* *Dependency Delta*: The reconciliation also runs the pre-merge Dependency Delta Check over the changed build files of the realized footprint against the outline's approved dependency set (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#dependency-delta[Phase Workflows Specification, Dependency Delta Check]).

[#plan-deletion-lessons]
=== Plan Deletion and Lesson Claims

When the operator deletes a plan (`pm-operator delete-plan <plan_id>`, a live plan or one in the archive), the lesson store keeps every lesson; only the plan's claims are released. The deletion runs in this order:

. *End the plan*, if it is live: two transactions of their own stores, the plan first (xref:01-format-and-session-log.adoc#transaction-journal[Transaction Journal], Writes outside the scope, Plan end): under the plan lock the plan enters `plan.aborted` with the outcome `cancelled` and the fixed reason `plan_deleted`, and every open question record and waiver request is closed with the plan; then, under the lesson store lock, the claim of every lesson whose `claim.plan_id` names the plan is released (xref:10-job-and-lesson-records.adoc#lesson-claim[A Claimed Lesson Ends with the Landing]).
. *Remove*: the plan directory (`plans/<plan_id>/` or `archive/<plan_id>/`) is replaced by the tombstone `archive/<plan_id>/deleted.json`, the same tombstone the cleanup leaves (link:../filesystem-layout/03-project-store.adoc#archives[Filesystem Layout Specification, Plan & Epic Archives]), with one audit record.

A failure before the removal leaves an ended plan, which a repeated `delete-plan` removes; a claim it left set is released by the recovery rule of the plan end. Lessons resolved `present_unreadable` during the scan are listed in the deletion result by id, because their claims cannot be read; a claim among them surfaces later as a stale claim, and the deletion proceeds. The tombstone keeps the `plan_id` from being allocated again (link:../identifiers/01-general-rules-and-registry.adoc#id-plan-id[Identifier Registry, `plan_id`]); the deleted plan's branch, its pull request, and its capture ref `refs/pm-mcp/captures/<plan_id>` stay in the repository and on the provider until the operator removes them.

[#lock-free-snapshot-reads]
=== Lock-Free Snapshot Reads, Transaction Locks & Leases (`PM-IMPL-7`)
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-26[PM-WATCH-DISP-26], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-43[PM-WATCH-STORE-43]_

[[_lock_free_snapshot_reads_transaction_locks_leases_pm_impl_7]]
* *Lock-Free Snapshot Reads*: Because every store update uses atomic write-and-rename (`<file>.tmp.<uuid>` -> `<file>`), all read-only operations (`pm_state`, the `pm://` resources, and the reads of the local API) read the current inode snapshot directly without acquiring file locks. A snapshot reader never decides `store_tampered`; it reports `digest_unverified` (<<store-digest-verification>>).
* *Sibling Lock Files*: Every store that is replaced by atomic rename is guarded by a sibling lock file, never by a lock on the store file itself (a rename replaces the inode, so a lock on the old file excludes nobody). The machine stores and their lock files are:
** `<PM_MCP_BASE>/locks/build-slots.lock`: `state/build-slots.json`
** `<PM_MCP_BASE>/locks/consents.lock`: `consents.json`
** `<PM_MCP_BASE>/locks/credentials.lock`: the file store `credentials/` (every credential write), the move between the stores with its record `state/credential-store-move.json` (xref:12-machine-stores.adoc#credential-store-move-record[Machine State Records]), and the creation of the enrolment integrity key, taken before any enrolment lock
** `<PM_MCP_BASE>/locks/enrolments/<project_id>.lock`: `enrolments/<project_id>.json` and its sidecar `enrolments/<project_id>.json.hmac` (one lock per enrolment file)
** `<PM_MCP_BASE>/locks/explorer.lock`: `explorer.json`
** `<PM_MCP_BASE>/locks/harnesses.lock`: `harnesses.json` and its sidecar `harnesses.json.hmac`
** `<PM_MCP_BASE>/locks/host-tools.lock`: `host-tools.json` and its sidecar `host-tools.json.hmac`
** `<PM_MCP_BASE>/locks/icons.lock`: `icons/`
** `<PM_MCP_BASE>/locks/install-records.lock`: `state/install-records.json`
** `<PM_MCP_BASE>/locks/login-environment.lock`: `state/login-environment.json`
** `<PM_MCP_BASE>/locks/machine-config.lock`: `machine-config.json`
** `<PM_MCP_BASE>/locks/merge.lock`: `state/merge-queue.json`
** `<PM_MCP_BASE>/locks/model-catalogue.lock`: `model-catalogue.json`
** `<PM_MCP_BASE>/locks/model-slots.lock`: `state/model-slots.json`
** `<PM_MCP_BASE>/locks/review-bot.lock`: `state/review-bot-windows.json`
** `<PM_MCP_BASE>/locks/role-assignments.lock`: `role-assignments.json`
** `<PM_MCP_BASE>/locks/upgrade.lock`: `state/upgrade.json`
** `<PM_MCP_BASE>/locks/web-devices.lock`: `state/web-devices.json`
+
The per-project server and operator stores that are not guarded by a scope lock have their own lock files in the per-project machine store: `projects/<project_id>/locks/local-config.lock` guards the project's operator files `local-config.json`, `role-assignments.json`, and `model-catalogue.json`, `projects/<project_id>/locks/derived-facts.lock` guards `derived-facts.json` (xref:09-derived-facts-and-build-timings.adoc#derived-facts[Derived Facts Store]), `projects/<project_id>/locks/build-timings.lock` guards `build-timings.json` (xref:09-derived-facts-and-build-timings.adoc#build-timings-store[Build Timings Store (`<PM_MCP_BASE>/projects/<project_id>/build-timings.json`)]), and `projects/<project_id>/locks/queue.lock` guards the task queue `queue/` with its queue task records and the job records of the project's workers (xref:16-task-queue.adoc#task-queue[Task Queue]). The machine scope and a project's onboarding entry have their locks below their homes (link:../filesystem-layout/02-machine-runtime.adoc#machine-scope-home[Filesystem Layout Specification, Machine Scope & Onboarding Entries]).
+
The append-only `logs/audit.jsonl` is never replaced by rename (rotation renames it only under its own lock) and may be locked directly; `logs/audit.head` and `logs/audit-index.jsonl` are written under that audit lock. The append-only journals `state/reports.jsonl`, `state/cleanup.jsonl`, and `state/usage-aggregate.jsonl` are locked directly the same way, each its own leaf lock (a journaled rewrite of `state/reports.jsonl` runs under its lock as well). A plan's append-only mailbox `mcp/mailbox.jsonl` is locked directly the same way (xref:04-epic-and-change-ledger.adoc#epic-inbox-record[Epic Inbox & Plan Mailbox Records (`inbox.jsonl`, `mcp/mailbox.jsonl`)]).
* *Transaction Locks*: Short locks held only for one transaction, all taken by the runtime (the only lock of `pm-operator` is the process lock `runtime-start.lock`; `pm-mcp` takes none). They are acquired in one total order, and a transaction that needs several locks acquires them strictly in this order to prevent deadlocks:
. scope locks of the machine: the machine scope lock `<PM_MCP_BASE>/machine/locks/machine.lock` and the lock of a project's onboarding entry `<PM_MCP_BASE>/onboardings/locks/<entry_id>.lock`, lexicographic by entry; the transaction of `project.enrol` takes its entry's lock before the new project's workspace lock
. workspace lock: `<PM_MCP_BASE>/projects/<project_id>/locks/workspace.lock` (the project's one workspace scope)
. plan locks: `<PM_MCP_BASE>/projects/<project_id>/locks/plan-<plan_id>.lock`, lexicographic by `plan_id`
. epic locks: `<PM_MCP_BASE>/projects/<project_id>/locks/epic-<epic_id>.lock`, lexicographic by `epic_id`
. epic worktree lock: `<PM_MCP_BASE>/projects/<project_id>/locks/epics-worktree.lock` (git operations on the shared epic worktree)
. lesson store lock: `<PM_MCP_BASE>/projects/<project_id>/locks/lessons.lock` (lesson id allocation and every write, claim, release, or retirement in the lesson store)
. local configuration lock: `<PM_MCP_BASE>/projects/<project_id>/locks/local-config.lock` (`local-config.json`)
. derived facts lock: `<PM_MCP_BASE>/projects/<project_id>/locks/derived-facts.lock` (`derived-facts.json`; a refresh during a scope transaction takes it after the scope lock)
. build timings lock: `<PM_MCP_BASE>/projects/<project_id>/locks/build-timings.lock` (`build-timings.json`)
. queue lock: `<PM_MCP_BASE>/projects/<project_id>/locks/queue.lock`, or the machine scope's `<PM_MCP_BASE>/machine/locks/queue.lock` (the task queue and the worker job records; a transition that creates or settles tasks takes it after its scope lock, and the supervisor takes it before a machine store lock)
. machine store locks: `<PM_MCP_BASE>/locks/{build-slots,consents,credentials,enrolments/<project_id>,explorer,harnesses,host-tools,icons,install-records,login-environment,machine-config,merge,model-catalogue,model-slots,review-bot,role-assignments,upgrade,web-devices}.lock`, alphabetical by lock path (several enrolment locks lexicographic by `project_id`)
. leaf locks: the audit log lock (`<PM_MCP_BASE>/logs/audit.jsonl`), the journal locks of `state/reports.jsonl`, `state/cleanup.jsonl`, and `state/usage-aggregate.jsonl`, and the mailbox lock of a plan (`plans/<plan_id>/mcp/mailbox.jsonl`, taken by an epic transaction under its epic lock and by the plan's consumption events); nothing is acquired after a leaf lock. A digest sidecar takes no lock of its own: it is written only through the transaction journal under the lock of its scope or of the lesson store (<<store-digest-verification>>)
+
The runtime singleton lock (`locks/runtime.lock`, held for the process lifetime) and the on-demand start lock (`locks/runtime-start.lock`, the only lock of `pm-operator`, held by its command until its authenticated round trip with the started runtime succeeds or the runtime start timeout expires) are process locks, not transaction locks, and stay outside this order. The machine scope and onboarding entry locks live beside their homes, and workspace, plan, epic, epic worktree, lesson store, local configuration, derived facts, build timings, and queue locks in the per-project machine store, each outside the directories they protect (link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]), so archiving a plan directory or editing an epic in a worktree never splits a lock.
* *Order Assertion*: The lock manager asserts the order on every acquisition against the locks the current transaction already holds (re-entry of a held lock is allowed). An out-of-order acquisition is refused: the call fails with `internal_fault` (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools.adoc[MCP Tools Specification]), nothing is written, and an audit record `lock_order_violation` (`category: store`, `outcome: refused`, `details{held, requested}`) is appended. A unit test of the lock manager covers an out-of-order acquisition at every level boundary.
* *Leases*: Long-lived claims (merge holder in `merge-queue.json`, review-bot windows in `review-bot-windows.json`, build slots in `build-slots.json`, model slots in `model-slots.json`) are lease records owned by a scope (`project_id`, `scope_type`, `scope_id`), served by a runtime instance (`holder_instance`: PID and start instant), and bounded by an expiry (<<machine-lease-stores>>); a restart orphans a lease instead of releasing it, and the owning scope adopts it on its next transition. A lease is claimed or released inside a short transaction on the machine store lock and is never held as an OS lock, so holding a lease while taking a plan lock does not invert the lock order. Task leases are not machine leases: they live in the queue task records and are released, never orphaned, at a restart (<<machine-lease-stores>>, Task leases).
* *Lock Manager*: All acquisitions in the runtime go through one lock manager (`PM-IMPL-7`, link:../../../../plan-marshall-documentation/doc/developer/locks-and-leases.adoc#lock-manager[Developer Guide § The Lock Manager]).

[#evidence-based-removal-sweeps]
=== Evidence-Based Removal Sweeps
_Implementation watch: link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-39[PM-WATCH-GEN-39], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-46[PM-WATCH-STORE-46]_

Work history (archived plans, archived epics' machine stores, the logs of ended work, read reports, and the machine stores of unenrolled projects) is never a sweep candidate: only the one cleanup deletes it, on the operator's word (link:../timeouts/03-retention-host-config.adoc#cleanup[Timeouts & Budgets Specification, One Cleanup]). A removal sweep removes technical residue, which needs no judgement:

* *The periodic sweep* removes by itself, in every pass of the running runtime (fixed interval, link:../timeouts/02-runtime-leases-operator-web.adoc#runtime-lifecycle[Timeouts & Budgets Specification, Runtime Lifecycle]), each removal with its audit record: the workspace scope's technical rows older than `retention.workspace_rows_days` (closed findings, answered questions, decisions whose facts are no longer referenced together with their facts snapshots, screen verdicts; never the metrics rows of a plan, which go with the plan; each store is replaced without the swept rows in one journaled transaction of the workspace scope); retired lesson bodies (`retention.retired_lesson_bodies_days`); ended queue task records and the records of ended jobs of the workspace scope and of workers (`retention.task_records_days`); the daemon store directories of a write-set digest that is no longer the project's and in which no recorded daemon process lives (link:../job-runtime/02-confinement-and-environment.adoc#build-daemons[Job Runtime Specification, Build Daemons]); the job-private directories of ended jobs; stale leases (<<machine-lease-stores>>); temporary files and caches; and rotated audit files older than `audit_rotation.retain_days` of `machine-config.json` (whole files only, their index entries are never removed; link:../timeouts/03-retention-host-config.adoc#rotated-audit-files[Timeouts & Budgets Specification, Rotated Audit Files]). The retention keys are those of the project's `local-config.json`, else `project_defaults.retention` (link:../timeouts/03-retention-host-config.adoc#retention-days[Timeouts & Budgets Specification]). The pass also measures the disk use of the machine store for the runtime's metrics.
* *The recovery's sweeps*: the baseline worktree sweep of the recovery and the baseline worktree removal of every plan-worktree enumeration (link:../filesystem-layout/01-repository-workspace.adoc#worktree-lifecycle[Filesystem Layout Specification, Worktree Lifecycle]), whose evidence (a plan that no longer resolves or is terminal) needs no operator judgement.
* *`pm-operator sweep [<project_id>] [--machine] [--apply]`* (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-channel-isolation[CLI, Coordination & Security Specification, Operator Channel Isolation]) lists what the next periodic pass would remove, with its evidence (a dry run on demand), for that project or every enrolled project, `--machine` adding the machine category; with `--apply` it runs that pass at once, and only then also the quiet-window retirement of `arch-constraint` lessons under `retention.arch_constraint_quiet_days`, which is a verdict on a lesson, not residue (xref:10-job-and-lesson-records.adoc#lesson-record[Lesson Record]). It never lists or removes work history. The store of an unenrolled project is a cleanup item, never a sweep candidate (xref:11-enrolment-store.adoc#project-store-identity[Project Store Identity (`<PM_MCP_BASE>/projects/<project_id>/store.json`)]).

Every removal sweep:

* removes only technical residue, each removal with an audit record naming the item and its evidence; the listing of `pm-operator sweep` without `--apply` removes nothing;
* reports for every kept item the first keep-rule that fired, and for every removed item the trigger that fired;
* reports the origin (`default`, `derived`, `machine`, `team`, or `project`, xref:07-project-configuration.adoc#project-configuration-store[Project Configuration]) of every configuration value it used;
* reports an empty population as one of `root_absent`, `root_unreadable`, `nothing_listed`, or `all_kept`, never as a bare zero;
* never removes an item on absence of evidence: a missing marker, record, or audit tombstone keeps the item and reports it as `skipped_no_evidence`.

[#ported-tests]
=== Ported-Primitive Tests (`PM-TEST-2`)
_Implementation watch: link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-32[PM-WATCH-GEN-32], link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-57[PM-WATCH-GEN-57], link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-58[PM-WATCH-GEN-58]_

* *Per-Script Porting Tests (`PM-TEST-2`)*: Each `Ported` script is adapted one at a time. For each, JUnit 5 tests run the Java primitive in-process against fixture trees in a test sandbox (for Java the per-project machine store layout `<PM_MCP_BASE>/projects/<project_id>/`, where the plan stores live, `PM-ARCH-5`, link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]). The test data and the expected values are derived from the original script and its pytest suite as the guide, with the legacy -> target mapping applied when the data is derived, and are committed as plain files. A legacy format is re-verified against the pinned `plan-marshall` commit before its test data is derived or changed, and a target field or stored identifier the derived data cannot populate fails the test instead of being defaulted or guessed. The tests canonicalize the resulting JSON/JSONL store state (normalizing generated UUIDs and ISO-8601 timestamps) and assert the expected state for all canonical store read/write invariants; no stdout format and no exit code is asserted, because the `PM-MCP` store primitives have neither.
* *No Python at Test Time*: The build, CI, and every workflow need no Python interpreter and no checkout of `plan-marshall`; no run compares the Java result with a Python result, live or recorded.
* *Known-Defect Baseline*: A known defect of the original script is never taken as the expected value: it is recorded as a named *deliberate change* with its own fixture, for which the test asserts the corrected behaviour. The tests of a structural refactor are written only after every behaviour fix touching the same code has landed.
* *No Shadow Execution*: The tests never run on live stores, and the runtime has no routing seam, executor adapter, or automatic fallback to Python (`PM-MIG-2`). Behaviour on real work is measured by parallel runs: the same requests executed by legacy `plan-marshall` and by `PM-MCP` on separate clones or checkouts, compared by the server-computed metrics (`priced_units` as the internal figure of the migration trigger, discipline events, outline and triage quality; `PM-MIG-4`).
