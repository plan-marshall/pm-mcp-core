[#project-configuration-store]
== Project Configuration (`.marshall/config/`, `local-config.json`, Effective Configuration; `PM-EXT-6`, `PM-EXT-7`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)]_

_Implementation watch: link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-21[PM-WATCH-EXT-21], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-13[PM-WATCH-STORE-13], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-25[PM-WATCH-STORE-25]_

Configuration is split by owner class (link:../domain-extensions/06-configuration.adoc#config-split[Domain Extensions Specification, Configuration Split]): four git-tracked *team* files under `.marshall/config/` with the workflow units the team placed or changed, and the project's recipes under `.marshall/recipes/`; one machine-local *operator* file per project (xref:08-project-configuration-local.adoc#local-config[Operator Local Configuration (`<PM_MCP_BASE>/projects/<project_id>/local-config.json`)]) with the project's role assignment and model catalogue; and the machine's operator files, `machine-config.json` with `project_defaults` and the machine's aspect values (xref:12-machine-stores.adoc#machine-config[Machine Configuration Store (`<PM_MCP_BASE>/machine-config.json`)]) and the machine's workflow units and recipes (`<PM_MCP_BASE>/workflows/`, `<PM_MCP_BASE>/recipes/`). Which level wins is xref:08-project-configuration-local.adoc#project-levels[Project Values over Machine Values]. No file mixes owner classes and no key exists in two owner classes. Binary versions, fingerprints, migration ledgers, and "offered" lists never land in a team file. `PM-MCP` never reads a legacy `.plan/marshal.json` and imports nothing from it (`PM-MIG-2`); the project setup workflow creates `.marshall/config/` on its first run and copies no workflow unit into it.

[cols="2,1,2,3"]
|===
|File |Owner |Writer |Content

|`.marshall/config/project.json`
|team
|project-setup links (validated), committed edits
|Repository and collaboration policy: base branch, branch prefix, the `merge_method` and `ci_provider` overrides, integrations (Sonar coordinates), review bots, the project's review-bot registry records, review currency, and whether a source issue is written back to (`issues.write_back`).

|`.marshall/config/workflow.json`
|team
|project-setup links, committed edits
|Plan workflow policy: the project's landing axis (`landing`), minimum planning lane, refine compatibility and simplicity, per-deliverable verification verbs and final verification, lane and parameters of optional finalize steps, project finalize step descriptors. No team file names a role, a harness, a model, an effort, or a credential: those are the operator's (link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration], `PM-WORK-1`).

|`.marshall/config/domains.json`
|team
|project-setup links, committed edits
|Overrides of the derived domain detection: forced enable or disable, `always_on`, `file_globs`, disabled profiles.

|`.marshall/config/build-map.json`
|team
|`setup.seed-build-map` (write-once), `customize_routes`, `setup.reseed-build-map`, committed edits
|The file-to-build route table (link:../domain-extensions/03-module-discovery.adoc#build-map[Domain Extensions Specification, Build Map]); seeded, not sparse.

|`.marshall/config/*.pmwf`
|team
|the operator's placing and removing in the designer, landed by `git.land-unit` (link:../workflow-dsl/04-ast-node-model.adoc#process-designer[Workflow DSL Specification, Designing a Process]), `setup.offer-new-steps` (adopted default changes), committed edits
|Only the designable units the team placed or changed (the phase units, the remediation, re-planning, and adjudication units with their declared decision parameters, `git.commit_and_push`, and the variants of the plan behaviour axes; link:../workflow-dsl/02-units-jobs-decisions.adoc#unit-declarations[Workflow DSL Specification, Unit Declarations]), each verified on every load against the compiled invariants (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units & Compiled Invariants]). A unit resolves by level: the project's copy over the machine's copy (`<PM_MCP_BASE>/workflows/<unit>.pmwf`) over the compiled default; a unit absent here resolves to the next level and is no finding, while a unit present but unparsable or violating is never replaced by another level. A copy taken from the machine or the default carries `derived_from`.

|`.marshall/recipes/`
|team
|the operator's placing and removing in the designer (`git.land-unit`), committed edits
|The project's recipes, each descriptor with its workflow `<id>.pmwf` (type `recipe`); a project recipe takes the place of a machine recipe of the same key in this project (link:../domain-extensions/05-recipes-and-extension-points.adoc#recipe-workflow[Domain Extensions Specification, A Recipe Is a Workflow]).

|`<PM_MCP_BASE>/workflows/*.pmwf`, `<PM_MCP_BASE>/recipes/`
|operator
|the operator's placing and removing in the designer at machine level
|The machine's workflow units and recipes, offered in every project on the machine and never committed; their digests enter the `config_hash` of every project they reach.

|`<PM_MCP_BASE>/projects/<project_id>/local-config.json`
|operator
|the operator's acts in either client: `project.operator` of the project's onboarding and setup, a value set or unset over the local API, `pm-operator config --project <project_id>`
|The operator's values and machine-local bindings of one project (xref:08-project-configuration-local.adoc#local-config[Operator Local Configuration (`<PM_MCP_BASE>/projects/<project_id>/local-config.json`)]); beside it, in the same store, the project's `role-assignments.json` and `model-catalogue.json` (xref:12-machine-stores.adoc#role-assignments-store[Role Assignments], xref:12-machine-stores.adoc#model-catalogue[Model Catalogue]).
|===

. *Sparse Files*: A team file and `local-config.json` hold only deviations from the effective default; an absent file means "no deviation" (except `build-map.json`, whose absence is `build_map_unseeded`). There is no default seeding into files, no default sync, no key sorting, and no key normalization: a new compiled default reaches every project with the binary, while in-flight plans stay protected by the plan instance snapshot (item 6). A key whose value equals the effective default without it is reported as the advisory finding `redundant_config_key`; a key without a compiled default whose presence is itself the answer (`review.required_bots`) is never redundant.
. *Version*: Every JSON configuration file carries `format_version` and is accepted only at the binary's current version (xref:01-format-and-session-log.adoc#format-versioning[Format Versioning & Atomic Write Discipline]); an outdated or newer team file refuses the project's scope creations (re-checked in a bootstrap's `start.create-scope` transaction) and phase handshakes with `format_outdated` or `format_newer` naming the file, and is never rewritten by a reader.
. *Closed Schemas, Validated on Every Read*: The schemas below are closed at every level (`additionalProperties: false`). Every computation of the effective configuration validates the files against them and against the server-side rules named in their descriptions. An undeclared key is the finding `unknown_config_key` naming the file and JSON pointer, never a silently kept setting; a setup or configuration link that would write an undeclared key is refused (`invalid_link_args`). A team file or workflow unit that fails validation is a verification finding in the workspace scope and refuses the project's scope creations and phase handshakes with `config_invalid` naming the file and pointer (for a workflow unit: file and line); an operator file that fails validation is reported with source `invalid` and never folded into the defaults. A non-object root fails before any field access.
. *Effective Configuration and Sources*: The server computes the effective configuration; neither the model nor the operator reads raw files. A team key resolves *team file → derived value (xref:09-derived-facts-and-build-timings.adoc#derived-facts[Derived Facts Store (`<PM_MCP_BASE>/projects/<project_id>/derived-facts.json`)]) → machine value → compiled default*, where only `workflow.landing` has a machine value (`plan_defaults.landing`); an operator key resolves *`local-config.json` → the machine's value (`project_defaults`, or the machine's value of its aspect) → compiled default*; no key is resolvable from both chains. A plan's own value of a key it may override stands above both, in its plan instance. Every effective value carries its origin `source`: `default` (the compiled default), `derived`, `machine`, `team`, `project` (the project's operator value), or `plan` (with the file for `machine`, `team`, and `project`, and the fact `state` for `derived`) and the origin it overrides. The effective key of a value is `<file_stem>.<dotted path>` (for example `project.review.currency`, `workflow.plan.phase-2-refine.compatibility`, `workflow.landing`, `local-config.plan_defaults.asking`, `derived.push_remote`); workflow guards name configuration keys in this form (`depends_on_config`, link:../workflow-dsl/01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification]).
. *Published View*: The effective configuration is served as the read-only resource `pm://project/config` (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/03-resource-uris.adoc#_normative_resource_uri_templates[MCP Tools Specification]) and to both clients over the local API: `config_hash`; `entries[]` of `{key, value, source, file?, fact_state?, overrides?}`; `units[]` of `{unit, file, digest, origin: default|machine|project, default_revision, verification: verified|refused, findings[]}`, `origin` naming the level in force; and `findings[]` (every validation finding with file, pointer or line, and reason). Over the local API every operator value is set and unset per key and level, each change carrying the revision it was made against (xref:12-machine-stores.adoc#machine-config[Machine Configuration Store], Operator files and their revision); a key an onboarding aspect records with its checks is changed only by a run of that aspect (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#two-channels[CLI, Coordination & Security Specification, Operator Choices in the Web App and the Terminal]).
. *Snapshot of In-Flight Plans (`config_hash`)*: `config_hash` is the SHA-256 over the canonical serialization of the effective configuration: every effective value with its source, the digests of the process DSL units the project loads at every level (the project's copies, the machine's units, and the compiled defaults), the derived facts the values rest on (value and `input_digest`), the team files, the operator file, and the digest of the compiled defaults. It is never computed over raw file bytes alone, so a binary upgrade that changes a default, a changed derived fact, or an edited workflow unit changes it. The plan instance header records it in `inputs.config_hash` (xref:14-plan-instance-waivers-questions.adoc#plan-instance[Plan Instance]); a difference at a phase handshake raises `config_drift` (`adopt` / `keep`, link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#_planning_transition_guards_real_world_invariants[Phase Workflows Specification, Outside-World Invariants]).

The pinned compiled defaults (for example the review rate-window values) live in the compiled default table that every effective-configuration computation starts from; a test pins that table.

[#config-project-json]
=== Team File `project.json`

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://cuioss.de/plan-marshall-mcp/schemas/config-project.json",
  "title": "ProjectConfigFile",
  "description": "Sparse team file .marshall/config/project.json: only deviations from the derived and compiled defaults.",
  "type": "object",
  "required": ["format_version"],
  "additionalProperties": false,
  "properties": {
    "format_version": { "type": "integer", "const": 1 },
    "base_branch": {
      "type": "string",
      "pattern": "^[A-Za-z0-9_./-]+$",
      "maxLength": 128,
      "description": "Integration branch of plans. Default derived from origin/HEAD (derived fact base_branch_default), fallback main. Server rule: the branch exists on the remote (base_branch_unknown)."
    },
    "branch_prefix": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9/_-]*/$",
      "maxLength": 64,
      "default": "feature/",
      "description": "The server names every plan branch <branch_prefix><plan_id>."
    },
    "merge_method": {
      "type": "string",
      "enum": ["squash", "merge", "rebase"],
      "description": "Override of the derived merge method (one method allowed by the repository -> that one; several -> squash). Server rule: allowed by the repository settings (merge_method_not_allowed)."
    },
    "ci_provider": {
      "type": "string",
      "enum": ["github", "gitlab", "forgejo"],
      "description": "Override of the CI provider derived from the remote host (derived fact ci_provider), for self-hosted remotes. Server rule: the matching host tool is enrolled."
    },
    "integrations": {
      "type": "object",
      "additionalProperties": false,
      "properties": {
        "sonar": {
          "type": "object",
          "required": ["organization", "project_key"],
          "additionalProperties": false,
          "description": "Sonar coordinates of the project. The credential is the operator's (local-config.json integrations.sonar, else the machine's providers.sonar); its token is sent only to that entry's url origin (PM-CRED-5), never to a value of this file.",
          "properties": {
            "organization": { "type": "string", "minLength": 1, "maxLength": 255 },
            "project_key": { "type": "string", "minLength": 1, "maxLength": 400 }
          }
        }
      }
    },
    "issues": {
      "type": "object",
      "additionalProperties": false,
      "properties": {
        "write_back": {
          "type": "boolean",
          "default": false,
          "description": "When true, a plan started from an issue of the project's own repository posts the clarified request after Phase 2 and the approved outline after Phase 3 to it (ci.issue-comment); never to an issue of another repository."
        }
      }
    },
    "review": {
      "type": "object",
      "additionalProperties": false,
      "properties": {
        "required_bots": {
          "type": "array",
          "items": { "$ref": "#/$defs/bot_kind" },
          "uniqueItems": true,
          "description": "No default: the presence of the key is the roster answer (absent: never answered, roster aggregate unestablished; []: answered empty, vacuous), so the key is exempt from redundant_config_key. Server rule: every token resolves in the review-bot registry (unregistered_kind); disjoint from optional_bots."
        },
        "optional_bots": {
          "type": "array",
          "items": { "$ref": "#/$defs/bot_kind" },
          "uniqueItems": true,
          "description": "Default []."
        },
        "bot_registry": {
          "type": "array",
          "items": { "$ref": "https://cuioss.de/plan-marshall-mcp/schemas/review-bot-registry.json" },
          "description": "Project review-bot registry records (Review-Bot Registry Record); a bot_kind that collides with a compiled record is refused."
        },
        "currency": {
          "type": "string",
          "enum": ["exact_sha", "after_last_push"],
          "default": "after_last_push",
          "description": "Strictness of the review currency test of the pre-merge barrier (phase-workflows.adoc, Predicate 2)."
        }
      }
    }
  },
  "$defs": {
    "bot_kind": { "type": "string", "pattern": "^[a-z0-9][a-z0-9-]{0,31}$" }
  }
}
----

[#config-workflow-json]
=== Team File `workflow.json`

Which finalize steps exist is decided by the project's `phase-6-finalize.pmwf` unit, never by this file: `steps` only sets the lane and parameters of an optional step the unit contains, and a `steps` entry for a step the unit does not contain is the finding `config_step_not_in_unit`.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://cuioss.de/plan-marshall-mcp/schemas/config-workflow.json",
  "title": "WorkflowConfigFile",
  "description": "Sparse team file .marshall/config/workflow.json.",
  "type": "object",
  "required": ["format_version"],
  "additionalProperties": false,
  "properties": {
    "format_version": { "type": "integer", "const": 1 },
    "landing": {
      "type": "string",
      "enum": ["landing.pull-request", "landing.main", "landing.files"],
      "description": "The project's landing axis (Workflow DSL Specification, Plan Behaviour Axes), a convention of the repository; overrides the machine's plan_defaults.landing, overridden by a plan's own. Chosen in setup.configure-finalize and validated against the project there: landing.pull-request needs a provider, landing.main a base branch that the provider does not protect (derived fact base_branch_protected)."
    },
    "plan": {
      "type": "object",
      "additionalProperties": false,
      "properties": {
        "phase-1-init": {
          "type": "object",
          "additionalProperties": false,
          "properties": {
            "minimum_lane": {
              "type": "string",
              "enum": ["light", "deep"],
              "default": "light",
              "description": "deep: every plan runs the deep lane. light: the initial router decides and the light -> deep ratchet always applies. A forced light lane does not exist."
            }
          }
        },
        "phase-2-refine": {
          "type": "object",
          "additionalProperties": false,
          "properties": {
            "compatibility": { "type": "string", "enum": ["breaking", "deprecation", "smart_and_ask"], "default": "breaking" },
            "simplicity": { "type": "string", "enum": ["lean", "pragmatic", "defensive"], "default": "lean" }
          }
        },
        "phase-5-execute": {
          "type": "object",
          "additionalProperties": false,
          "properties": {
            "per_deliverable_verbs": {
              "type": "array",
              "minItems": 1,
              "uniqueItems": true,
              "items": { "$ref": "#/$defs/build_verb" },
              "description": "Default [\"compile\", \"module-tests\"]. Server rule: each verb renderable by the project's effective canonical template."
            },
            "final_verification": {
              "type": "array",
              "uniqueItems": true,
              "items": { "$ref": "#/$defs/step_id" },
              "description": "End-of-phase-5 verification steps; default derived from the build systems' verbs. Server rule: each id a shipped verification step or an enrolled project step."
            }
          }
        },
        "phase-6-finalize": {
          "type": "object",
          "additionalProperties": false,
          "properties": {
            "steps": {
              "type": "object",
              "propertyNames": { "$ref": "#/$defs/step_id" },
              "additionalProperties": {
                "type": "object",
                "additionalProperties": false,
                "properties": {
                  "lane": {
                    "type": "string",
                    "enum": ["off", "minimal", "standard", "full"],
                    "description": "Lowest execution posture at which the optional step runs, or off. Server rule: only optional steps; a mandatory step is refused (mandatory_step_not_configurable)."
                  },
                  "params": {
                    "type": "object",
                    "description": "Step parameters, validated by the server against the closed parameter schema of the step descriptor (FinalizeStepDescriptor.configurable)."
                  }
                }
              }
            },
            "project_steps": {
              "type": "object",
              "propertyNames": { "pattern": "^project:[a-z][a-z0-9-]{0,63}$" },
              "additionalProperties": {
                "type": "object",
                "required": ["order", "project_script_id"],
                "additionalProperties": false,
                "properties": {
                  "order": { "type": "integer", "minimum": 3, "maximum": 989, "not": { "enum": [11, 70] }, "description": "Band position: a gap of the Settle band (3..10), the post-push band (12..69), the post-merge band (71..899), or 900..989; 11, 70, and 990..1099 are reserved for default steps. A collision with a default step's order and a source-mutating step at 70 or above are refused by FinalizePipelineValidator with the rest of the roster." },
                  "lane": { "type": "string", "enum": ["off", "minimal", "standard", "full"] },
                  "project_script_id": {
                    "type": "string",
                    "pattern": "^[a-z][a-z0-9-]{0,63}$",
                    "description": "Server rule: enrolled with binding worker_kind finalize_step whose target is this step id; the step exists only when the unit, this descriptor, and the enrolment agree."
                  }
                }
              }
            }
          }
        }
      }
    }
  },
  "$defs": {
    "step_id": { "type": "string", "pattern": "^(default|project):[a-z][a-z0-9-]{0,63}$" },
    "build_verb": {
      "type": "string",
      "enum": ["clean", "compile", "test-compile", "module-tests", "integration-tests", "e2e", "coverage", "benchmark", "quality-gate", "arch-gate", "verify", "install", "clean-install", "package"]
    }
  }
}
