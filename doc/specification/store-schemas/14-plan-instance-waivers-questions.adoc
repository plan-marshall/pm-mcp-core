[#plan-instance]
== Plan Instance (`instance/plan.v<N>.pmwf`, `instance/<unit>.v<N>.pmwf`, `instance/composition.jsonl`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-13[PM-WF-13: Finalize Step Ordering Bands, Verdict Currency & Pre-Merge Barrier]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-7[PM-EXT-7: Configuration Versioning, Validation & Zero-CoT Upgrades]_

Every plan executes its own *plan instance*: DSL units, stored per version as one composed file per unit (the plan unit's file `instance/plan.v<N>.pmwf` with the version's header, and `instance/<unit>.v<N>.pmwf` for each phase sub-workflow and each bound axis variant), that the server composes from the templates (the plan unit, its phase sub-workflows, the variants of its behaviour axes, the `remediation.*` policy units, and the other sub-workflows it calls, each resolved by level: the project's `.marshall/config/*.pmwf`, the machine's `<PM_MCP_BASE>/workflows/`, the compiled default; link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units & Compiled Invariants], link:../workflow-dsl/04-ast-node-model.adoc#process-designer[Designing a Process]), the composition rules (<<composition-rules>>), and the plan's facts. Facts stay where they are owned and are never copied into the instance: configuration in its stores (xref:07-project-configuration.adoc#project-configuration-store[Project Configuration]), waivers in `waivers.jsonl` (<<waiver-record>>), the plan's own values in `overrides.json` (<<plan-overrides-store>>), plan facts (lane, deliverables, footprint, tasks) in the plan stores. The instance carries their *effect* with provenance. The step lists are the instance; the configuration snapshot (`config_hash`) is in its header.

* *Storage*: Each version is a set of immutable files in `plans/<plan_id>/instance/`: `plan.v<N>.pmwf`, the plan unit with the header, and `<unit>.v<N>.pmwf` per composed phase sub-workflow and bound axis variant (for example `phase-6-finalize.v3.pmwf`), all written in the transaction that composes the version (`N` from `1`, never rewritten, never deleted while the plan exists; link:../workflow-dsl/09-plan-instance.adoc#plan-instance[Workflow DSL Specification, Plan Instance]); the version is always referred to by the plan unit's file, and its header `version` is the plan's `instance_version` (link:../identifiers/02-registry-stores-to-web.adoc#id-instance-version[Identifier Registry, Plan Instance Version]). The version in force is `instance_version` of the plan's `mcp/status.json` (xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store]). A version composed by an operator or configuration event (`config_adopted`, `waiver`, `override`) is in force from the transition after the one that composed it, never mid-state; a version composed by a server event (`outline`, `plan`, `fallback`, `replan`) is in force for the rest of its composing chain, from the transition that enters its target state, so every `auto` state of that chain (for example `finalize.next-step` after `plan.return`) selects from the new version. Completed firings, step records, and history always refer to the version in force when they happened; history is never rewritten.
* *Header*: Every version has one instance header (schema below), which names every input by digest and the version's composed unit files. It is the single `instance` line after the `workflow` line of the plan unit's file `plan.v<N>.pmwf`, the DSL body follows it; the other unit files of the version carry no header. The header is serialized as one line of canonical JSON (keys sorted, no insignificant whitespace, UTF-8), so its digest is reproducible (link:../workflow-dsl/09-plan-instance.adoc#instance-header-grammar[Workflow DSL Specification, Instance Header Grammar]). `pm://plan/{plan_id}/instance[/{version}]` returns the DSL text with its header, `pm://plan/{plan_id}/diagram` renders the version in force (active state, pruned elements with reason, waived gates with waiver id), the plan's process resource serves it to both clients (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#process-resource[Runtime & Interaction Model Specification, The Plan's Process as a Structure]), and `pm-operator status` names the version and its last composition event (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/03-resource-uris.adoc#_normative_resource_uri_templates[MCP Tools Specification, Resource URI Templates]).
* *Invariants per Version*: The compiled invariants are checked on every composed version before it is written; a version that fails them is never written (the composing transition is refused, and for a server event the plan takes the phase's fallback route with the failed invariant as the gap).
* *Position Rule*: A version is valid only if it contains the current state and every state of the `call_stack` (the adopt rule of the bound unit copy, link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification]). State ids are stable across versions, so the current position maps onto the new version unchanged. An operator-triggered event whose version fails the rule is refused (a configuration candidate is then kept, a waiver or an override is refused with `position_not_contained`); a server event (`fallback`, `replan`, `outline`, `plan`) is composed in the transaction that enters its target state, so the version always contains it.
* *Sub-Units*: The phase sub-workflows and the bound axis variants are composed files of the version (Storage). The header lists every other sub-unit the composed units call (`git.commit_and_push`, the `remediation.*` units, `replan`) and the adjudication unit its decisions run (`adjudicate.decisions`) by id and digest; each call site carries its bound arguments with provenance, so one sub-unit serves every call site and is never expanded inline. The verified text of each bound sub-unit is kept as `plans/<plan_id>/mcp/units/<digest>.pmwf` (`<digest>` the SHA-256 of the unit text): content-addressed, written once in the transaction that composes the first version naming the digest, never rewritten, covered by the plan's digest sidecar, and read by the engine instead of the project copy while a version naming it is in force, so an edit of a project's or the machine's unit never changes a running call.
* *Readers*: Phase 5 and Phase 6 step selection, verdict currency, and the retrospective's step admission read the instance; the step admission reads the version in force when the step would have fired (`not_admitted` = pruned, with the prune reason).

*Composition Events*: The closed `composition_event` enum (link:../identifiers/02-registry-stores-to-web.adoc#id-composition-event[Identifier Registry]): `start` (version 1 in the plan's creation transaction: init and refine routes, both lanes open, each axis variant bound at the plan's start by the precedence of the plan behaviour axes (link:../workflow-dsl/09-plan-instance.adoc#plan-axes[Workflow DSL Specification, Plan Behaviour Axes]) and the others pruned with reason `plan_default`), `outline` (lane known: from this event on, the states of the other lane are pruned with reason `other_lane`, link:../../../pm-workflow/doc/developer/workflow-plan.adoc#_lane_pruning[Plan Instance Developer Guide § Lane Pruning]; the posture bound with its prunes), `plan` (tasks and steps known; provider and footprint prunes; budgets bound), `config_adopted` (an adopted configuration or template change), `waiver` (a `met` waiver, a `raise`, or an `unwaive`), `override` (a value of the plan's own set or changed in `overrides.json`, <<plan-overrides-store>>), `fallback` (the post-run-only form of the `returned` and `handed_back` routes, pruned steps with reason `returned` / `handed_back`), `empty_harvest` (the post-run-only form of a recipe's plan whose harvest is empty, pruned steps with reason `empty_harvest`), and `replan` (a re-planning that revised the outline or the plan tasks, a revision the operator accepted in a chat among them, link:../phase-workflows/08-dynamic-re-planning.adoc#replan-apply[Phase Workflows Specification, Dynamic Re-Planning]). [#composition-rules]
=== Composition Rules
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-89[PM-WATCH-PHASE-89]_

The land restriction (link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#land-lane[Phase Workflows Specification, Land Lane]), the local-only prunes, and every other prune predicate are *data*: one declarative rule file, versioned like the templates, whose rules map a plan fact or an effective configuration value to prunes and policy bindings. Its revision and digest are an input of every instance header.

* *Location*: Team overrides of the composition rules (and of units that are not project-owned) are deferred (link:../../../../plan-marshall-documentation/doc/later-improvements.adoc#_l_5_team_overrides_of_templates_and_composition_rules[Later Improvements, L-5]); until then the shipped rule file applies to every project.
* *Effects of the Shipped Rules at Run Time*: with `actions: [retry]` bound at every policy call of a `land` plan, the server takes `retry` without a task; an empty `derived.push_remote` keeps `pre-push-quality-gate` and `pre-submission-self-review` (*deliberate change vs. `plan-marshall`*, which drops them); where the merge execution is pruned with reason `merge_by_operator`, `finalize.merge-barrier` reads the prune and settles `pass_hand_back` instead of `pass` (its `pass` settled by the prune record, link:../workflow-dsl/09-plan-instance.adoc#composition-rules[Workflow DSL Specification, Composition Rules]), enters the ready form of `finalize.hand-back`, and the plan ends `handed_back` with `merge_outcome: awaiting_human_merge`.

[#plan-overrides-store]
=== Plan Overrides (`overrides.json`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-25[PM-WF-25: Plan Behaviour Axes & Plan Overrides]_

A plan's own values, nearest of the levels of its configuration (link:../workflow-dsl/09-plan-instance.adoc#plan-overrides[Workflow DSL Specification, Plan Overrides]): per role its `harness`, `model`, and `effort`; the variant of each plan behaviour axis; the plan's posture and base branch; the variant of an integration; and the optional providers (code analysis, review bots) the plan uses. `plans/<plan_id>/overrides.json` is absent until the first value is set. A key it does not hold defers to the project's and the machine's values.

* *Written only by the operator*, in either client: at the operator wait of the state that first needs the value (link:../state-catalogue/09-bootstrap-and-lessons.adoc#options-when-needed[State Catalogue, Asked When Needed]) or later from the plan's settings. A write names the `revision` it changes and is refused with `conflict` when the file has moved on; it replaces the file by the scope's transaction, is audited with its channel, composes a new plan instance version of the event `override` under the position rule (<<plan-instance>>; refused `position_not_contained` otherwise), and is answered with that version. For a plan of an epic it appends the inbox message `settings_changed` (xref:04-epic-and-change-ledger.adoc#epic-inbox-record[Epic Inbox Record]).
* *Validated like the machine's values*: an enrolled harness, a model the effective catalogue allows on it (`model_not_allowed`), an available provider, and an axis variant valid for the project; a refused value changes nothing.
* *Unqualified*: an override to a configuration without a current qualification record is shown as unqualified when it is set; its tasks take the qualification fallback of `PM-WORK-6` until the project grades it.

[#waiver-record]
== Waiver Record (`waivers.jsonl`, `waiver-consumptions.jsonl`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-3[PM-SEC-3: Operator Channel Isolation (Operator CLI & Paired Web Devices)]_
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-38[PM-WATCH-STORE-38]_

A waiver is the operator's only influence on the gates and budgets of a running plan: it declares a waivable gate met (`mode: met`) or raises a remediation budget ceiling (`mode: raise`). `plans/<plan_id>/waivers.jsonl` has exactly one writer, the runtime executing the operator's act from either client (`waive` / `unwaive`; in the terminal client `pm-operator waive` / `unwaive`, link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-waive[CLI, Coordination & Security Specification, Waivers]); no primitive has a write capability for it (compiled invariant `INV-GEN-2`). Every line is mirrored to `audit.jsonl`, and every `waived` or `revoked` line composes a new plan instance version (event `waiver`). The `reason_class` of a `waived` line is mirrored into the audit log with the gate, where the Artifact Gate recurrence count and the lessons-capture signal read it.

* *Plan-Scoped, not HEAD-Bound*: A `met` waiver applies to every evaluation of its gate after it is set, for the rest of the plan (a known-flaky check stays waived after a later push). It can be set at any time until the gate's fallback is taken, including before the plan's first transition and after a failing evaluation; once the fallback of the gate was taken or the plan has ended it is refused (`plan_ended`).
* *Raise*: `raise` sets the new absolute ceiling of `fix_budget:<policy>`, `retry_budget:<policy>`, or `fix_budget:outline-loop-back` (the per-plan counter `outline_loop_backs`). The consumed budget stays the per-plan counter of the status store, so a re-composition never resets it (xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store], `policy_counters`). A value at or below the effective ceiling, or above the compiled hard cap, is refused (`raise_out_of_range`). Revoking a `raise` (`unwaive`) lowers the ceiling from the next budget check on: a counter already above the restored ceiling reads exhausted there, and the unit takes its fallback; no refusal applies to the revocation.
* *Consumption*: A waivable gate admits a failure only through the primitive `waiver.lookup`, which appends one line per evaluation that relies on a `met` waiver to `plans/<plan_id>/waiver-consumptions.jsonl`. `waiver-consumptions.jsonl` has exactly one writer, `waiver.lookup`; the waiver store itself is never written by a primitive. Every consumption is listed in the pull request comment and the landing record.
* *Refusals*: `not_waivable` (an unknown gate or one on the non-waivable list: integrity breaches, the footprint and main-checkout guards, job confinement, credentials, security findings, the operator boundary, a build failure, a merge conflict, a provider refusal of the merge), `plan_ended`, `already_consumed` (`unwaive` of a waiver with at least one consumption), `raise_out_of_range`, `position_not_contained` (<<plan-instance>>, Position Rule).

[#waiver-request-record]
=== Waiver Request Record (`mcp/status.json` → `waiver_requests[]`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-40[PM-WATCH-STORE-40]_

The waiver request is the typed member `waiver_requests[]` of the plan's status document, with its closed outcomes and no time limit.

A worker's `request_waiver` in the decision task (`choose`) of a remediation unit (offered whenever the failing gate is waivable) files a request, and the remediation unit's state that awaits it is an operator wait of the plan (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]). A waiver request is never a question record and offers no chat: it is answered only by the operator's `waive` (a `met` waiver or a `raise`) or `decline`, in either client, and the decline records the outcome `declined` and lets the remediation unit take its next transition (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-waive[CLI, Coordination & Security Specification, Waivers]).

[#question-record]
== Question Record (`questions.jsonl`)
_See Requirements link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-12[PM-WF-12: Question Records vs Operator Overrides], link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-18[PM-WF-18: Question Recommendation Score & Decision Quorum]_
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-40[PM-WATCH-STORE-40]_

A decision is a set of questions, each question one of its parts (link:../model-work/06-envelopes-questions-deadlines.adoc#decision-structure[Model Work Specification, The Decision Structure]); it is named by the `question_id` of its first question and addressed across scopes as `<scope_id>/<question_id>`. Every question is a server-owned question record, created by a task (through the `ask` link, offered only where the task's state declares `ask` (link:../workflow-dsl/02-units-jobs-decisions.adoc#model-job-states[Workflow DSL Specification, Task States (`job llm`), item 8]), or through `ask:TASK-NNN` on a task envelope entity, after which the task ends with outcome `asked` unless it continues after the question; or as a part of the optional `decision` of a refine or outline `submit` (`decision:schema[decision-envelope]?`)) or by a server primitive (init classifiers, the outline review where the plan's asking variant asks it, the workspace setup's choices that write team configuration). Overrides (waivers, access grants, ending a plan or an epic, integrity resolutions), consents, choices that write operator configuration, and the other choices of an entry, of the project setup, and of the onboarding are operator waits without a question record (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]).

* *Decision and Parts*: what a decision blocks and how reversible it is are set by its creator: the asking task's submit, or for a server-raised question its primitive (model-work/06, The Decision Structure); a server-raised question carries the fields of its part from its primitive, its options server-owned. The support per option (counts, roles and models, dissent) is derived by the runtime from the votes of the adjudication's decision-log record and never stored here (link:../model-work/10-decision-quorum.adoc[Model Work Specification, Decision Quorum]).
* *Revision*: a change of an open decision is revised in the transaction of the change; an answer from a second client to an older revision is refused.
* *Delivery*: a decision is delivered to both clients of the operator as an operator wait of its scope, after its adjudication where a quorum is declared: the transaction that opens the wait appends a `delivered` line for every question of the set, whose `at` is the decision's `delivered_at` in the list of open decisions across scopes (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#needs-operator[Runtime & Interaction Model Specification, What Needs the Operator]). It has no deadline and no fallback by time; it ends only by an answer through a channel of this record, by its withdrawal, or by the end of its scope. A question never stops a worker: the asking task has ended `asked`, or holds its task for the answer within its role's hold limit (link:../model-work/06-envelopes-questions-deadlines.adoc#continuation[Model Work Specification, Continuing after a Question]). No channel is configured per project.
* *Answer Validation*: every channel passes the same validation, refused over the local API with its error codes (link:../model-work/06-envelopes-questions-deadlines.adoc#answers-and-amendments[Model Work Specification, Answers & Amendments]): an unknown option or an invalid value is refused `invalid_answer`, and so are own words, a note, a delegation, or _none fits_ where the part or the decision does not allow them, and an answer to a part whose dependency is unanswered is refused `dependency_unanswered`; the refusals `already_answered` and `conflict` of the store reach the channel with the same codes. A worker's vote in an adjudication is refused `invalid_link_args`. _Later_ records nothing: the decision stays open.
* *Own Words*: an answer in the operator's own words is recorded only after the operator confirmed its read-back (link:../model-work/06-envelopes-questions-deadlines.adoc#own-words[Model Work Specification, Answers in the Operator's Own Words]): `interpreted` with its interpretation, `own_option` for words that fit no option, never the closest option in their place, and `delegated` only where the decision allows a delegation. The words are the operator's own and never screened; a model that reads them later gets them as quoted data in its facts.
* *None Fits*: where it is offered, a worker's decision answered _none fits_ is closed by that answer and its asking role asks anew; a decision with a declared quorum is revised and voted on again.
* *Adjudication*: where the decision's declaration names a quorum, every record of a set gets exactly one `adjudicated` line per revision before it is delivered or answered, naming the revision's adjudication decision-log record, which holds the outcome, the reason, and the votes (xref:18-decision-records.adoc#decision-record[Decision-Log Record]; semantics in link:../model-work/10-decision-quorum.adoc#adjudication-record[Model Work Specification, Ask or Quorum, Record]). The `adjudicated` line of a `decided` set is followed by the `answered` line with `channel: quorum` in the same transaction; an escalated set is delivered as an operator wait.
* *Decision*: every `answered` line names the decision-log record of the decision finally taken, appended in the same transaction (link:../model-work/11-decision-records.adoc#question-decisions[Model Work Specification, Question Decisions & Quorum]).
* *Closure*: the server withdraws an open decision when a revision of the plan the operator accepted in a chat removes the task or state that asked it (reason `removed_by_revision`); the end of its scope (cancel, abandon, the release of the project, the integrity abort, `delete-plan`, the abandoning of an entry) cancels every open question (reason `scope_ended`), except while `questions.jsonl` holds a line refused when read: the store then refuses the cancel append `unreadable` and the open questions stay open (link:../../../pm-core/doc/adr/core-store/039-question-append-refused-while-the-log-holds-a-refused-line.adoc[ADR core-store/039]). An integrity hold holds an open decision; it never closes it.
* *Amendments*: an answer creates an `amendments[]` entry only when it changes intent (refine answers still go to `request.md`); the entry names the `question_id` (xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store]).

[#cli-answers]
=== Answers from the Terminal Client
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-12[PM-WF-12: Question Records vs Operator Overrides]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-3[PM-SEC-3: Operator Channel Isolation (Operator CLI & Paired Web Devices)]_

The terminal client is the channel `cli`, the second channel of content answers beside the web app's `web`; together with `quorum` they are the only channels of an answer.

* *Announced in both clients*: while it is open, the terminal client follows the runtime's events and announces every delivered decision and every pending waiver request of the operator's plans, epics, workspace scopes, and entries, as the web app does (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#event-streams[Runtime & Interaction Model Specification, Events per Scope]).
* *One answer endpoint*: both clients answer through the same scope-qualified answer endpoint of the local API, validated the same way (Answer Validation above); the first valid answer wins, and a later one from either client is refused `already_answered`.
* *The channel is the runtime's*: the runtime records the channel from the transport of the request, never from a field the client sends: a request over the runtime's socket that passes the operator checks of `pm-operator` is `cli`; a request on a web listener authenticated by a paired device's secret is `web` with that device's `device_id` (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-channel-isolation[CLI, Coordination & Security Specification, Operator Channel Isolation]).
* *Content, never override*: an answer from the terminal client is a content answer, never an override; a waiver request is answered by `waive` or `decline` (<<waiver-request-record>>), never by an answer. The terminal client keeps the operator checks of `pm-operator`.
* *Answered elsewhere*: when a decision is answered, withdrawn, or cancelled, the runtime announces its closing on the scope's event stream with the channel that closed it; every client then says that it was answered in another client, or withdrawn, and withdraws what it showed (the report `decision.closed_elsewhere`, link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#reports[Runtime & Interaction Model Specification, Reports to the Operator]).

== Evidence Directory & Failure Envelope (`evidence/`)

Each remediation unit's gather state gathers per failure class, either by one server-side gathering job (CI logs, provider observations) or, for a class read from the plan's own stores (build, review, qgate, merge conflict), inside the gather state's own transaction (link:../job-runtime/03-parsers-and-gates.adoc#evidence-gathering[Job Runtime Specification, Evidence Gathering]) and records its failures in the plan's evidence directory: the append-only `plans/<plan_id>/evidence/failures.jsonl` (one failure envelope per line) and one excerpt file `plans/<plan_id>/evidence/<evidence_id>.log` per stored log excerpt. Excerpts are untrusted content, redacted before they are written, exposed only as the resource `pm://plan/{plan_id}/evidence/{evidence_id}`, and never inlined into a representation beyond the envelope's `message`.
