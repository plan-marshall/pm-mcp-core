== Task Record (`tasks/TASK-NNN.json`) & References Record (`references.json`)

=== Task Record Schema (`tasks/TASK-NNN.json`)

*Task Status*: `pending` (not yet in an envelope) and `in_progress` (in the envelope of a queued or leased envelope task) are open; a change beyond the declared footprint never blocks a task (it is recorded as an unplanned change, <<_references_footprint_store_schema_references_json>>); a task whose dependencies are not yet satisfied stays `pending`. `completed`, `infeasible`, and `removed` are terminal; no task status `skipped` exists, and no verb skips a task:

* `completed`: the server's independent verification of `submit:TASK-NNN` passed (link:../phase-workflows/03-q-gate-and-execute.adoc#_task_envelope_execution_independent_server_verification[Phase Workflows Specification]).
* `infeasible`: set by the worker's `infeasible:TASK-NNN` with its evidence (`disposition.by: worker`, `disposition.evidence`).
* `removed`: the task's deliverable was removed by the outline gate or by a re-planning that removed or deferred the deliverable (`replan.apply`, link:../phase-workflows/08-dynamic-re-planning.adoc#replan-apply[Phase Workflows Specification, Dynamic Re-Planning]); `disposition.by` is `outline_gate` for removal by the outline gate, `model` for removal by a re-planning the server triggered, `operator` for removal by a revision the operator accepted in a chat (link:../state-catalogue.adoc#chat[State Catalogue, Chatting with the Planning Role]), with the reason.

A task in `infeasible` or `removed` carries a non-null `disposition`; a task in any other status carries none. Step status is `pending`, `completed`, `skipped`, or `failed`.

*Dependencies (`depends_on`)*: Phase 4 writes the task graph into `depends_on` (link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#_deterministic_task_derivation_dag_cycle_detection[Phase Workflows Specification]). At every task creation or amendment the server checks that every referenced task exists in the plan and that the graph stays acyclic; otherwise the write is refused (`invalid_link_args`, `detail` `task_dependency_unresolved` or `task_dependency_cycle`, naming the tasks) and no task file is written. A dependency is satisfied only by a task in status `completed`.

A deliverable may declare several verification command and criterion pairs; the task carries them all in `verification`. A task with profile `implementation`, `module_testing`, or `integration_testing` requires at least one command and at least one criterion. An empty or truncated criterion rejects task creation; it is never downgraded to a warning.

=== Intent Record (`intent.json`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-10[PM-WF-10: Phase 1–4 Planning Invariants, Lane Ratchet & Artifact Gates]_

The schema below is the normative shape for the assembly's submission endpoints.

The plan's intent record (link:../phase-workflows/01-planning-phases-1-2.adoc#intent-record[Phase Workflows Specification, The Intent Record]), written by the transaction that accepts a `submit:refine` or a light `submit:outline`, and by a re-planning that changes intent. `current` is the accepted record; every earlier revision moves to `history[]` in the same transaction and is never changed. The model-supplied record is the named parameter schema `intent-record`; the members around it are server-owned.

=== Outline Record (`outline.json`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-10[PM-WF-10: Phase 1–4 Planning Invariants, Lane Ratchet & Artifact Gates]_

The schema below is the normative shape for the assembly's submission endpoints.

The plan's solution outline (link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#outline-validation-gate[Phase Workflows Specification, Phase 3 Validation]), written by the transaction that accepts a `submit:outline` and by `replan.apply`. `current` is the accepted record and every earlier revision moves to `history[]`; `deliverable_status` is server-owned. `outline.md` is rendered from `current` in the model language, deliverable by deliverable, in the section form of `plan-marshall`'s solution outline (`**Metadata:**`, `**Intent gloss:**`, `**Profiles:**`, ``- `<path>` (<intent>)`` under `**Affected files:**`, `**Change per file:**`, `**Verification:**`, `**Satisfies:**`, `**Added dependencies:**`, `**Interfaces:**`, `**Key links:**`); it is never read back. The model-supplied record is the named parameter schema `outline-record`.
