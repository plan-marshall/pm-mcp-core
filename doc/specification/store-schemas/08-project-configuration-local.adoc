[#local-config]
== Operator Local Configuration (`<PM_MCP_BASE>/projects/<project_id>/local-config.json`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)]_

_Implementation watch: link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-29[PM-WATCH-EXT-29]_

The operator's values of one project and its machine-local bindings, written only by the runtime under the project's `locks/local-config.lock` on the operator's acts in either client: the operator values of the project's onboarding and setup (`project.operator`) and their later runs, a value set or unset over the local API, and `pm-operator config --project <project_id>`; never by a model. Sparse like the team files: a key holds only the project's own value, and accepting the machine's value as the proposal records nothing. The file carries `revision` like every operator file (xref:12-machine-stores.adoc#machine-config[Machine Configuration Store], Operator files and their revision). Which value of which level wins is <<project-levels>>.

* *Shared keys* (`$defs/settings`): each falls back to the same key of `machine-config.json` `project_defaults` and then to the compiled default; `$defs/settings` is the schema of both (xref:12-machine-stores.adoc#machine-config[Machine Configuration Store (`<PM_MCP_BASE>/machine-config.json`)]). Among them the commit author identity `commit_identity {name, email}`, the author of every server commit (the operator, who is responsible for the change); the committer is the agent identity resolved from the provider credential (derived fact `agent_identity`), else the fixed `plan-marshall-mcp` noreply identity (link:../domain-extensions/04-setup-state-machine.adoc#setup-verify-credentials[Domain Extensions Specification, Credential Verification]). Where neither the project nor the machine holds one, `project.operator` proposes the operator's global git identity, and accepting it records it for the project, since no level holds it; while no effective value exists, a commit refuses with `identity_missing`. The `commit_trailer` stays a separate key.
* *Aspect keys*: the project's value of an aspect the machine's onboarding records falls back to that aspect's machine value, never to `project_defaults`: `language.model` to the machine's `language.model`; `plan_defaults.method` and `plan_defaults.asking` to the machine's `plan_defaults` (link:../workflow-dsl/09-plan-instance.adoc#plan-axes[Workflow DSL Specification, Plan Behaviour Axes]); `plan_defaults.posture` to the machine's `plan_defaults.posture`, an optional key with no compiled default at either level: while neither sets it, a plan asks the posture in `init.options` (link:../workflow-dsl/09-plan-instance.adoc#plan-posture[Workflow DSL Specification, Posture and base branch]); `integrations.<integration>` to the machine's `providers.<integration>` (xref:12-machine-stores.adoc#provider-defaults[Machine Provider Defaults]); and `cleanup.plans_after_days`, `cleanup.epics_after_days`, `cleanup.logs_after_days` to the machine's `cleanup`. The landing axis of a project is no operator key: it is the team's (`workflow.json` `landing`, xref:07-project-configuration.adoc#config-workflow-json[Team File `workflow.json`]).
* *Integration variant and credential*: `integrations.<integration>` holds the project's `variant` (`native` or `cli`, for `git`, `github`, and `gitlab`) and its `credential_key`. The effective variant is the project's value, else the machine's default variant, else derived: `cli` where the integration's host tool is enrolled (in the project's enrolment or the machine's `host-tools.json`), `native` where not. A choice of the operator is required only while the effective variant is invalid (a `native` variant and a feature the derived fact `git_native_capability` reports): it is an operator wait of `project.operator` (link:../domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]), never a question record and never an answer a model relays. One value holds for every operation of the integration; there is no per-operation override. While the choice is required and absent, every operation of that integration refuses with `integration_variant_unset`. A `cli` value requires the integration's host tool enrolled for the project or the machine (`cli_tool_not_enrolled` otherwise). Sonar and Forgejo have only the native variant and take only a `credential_key`. The effective value carries its origin (`project` for the project's value, `machine` for the machine's default variant, `derived` otherwise), enters `config_hash`, and is served to the operator in both clients and in `pm://project/config`, never pushed into a representation or tool result (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).
* *`upstream_mcp`*: the upstream MCP allowlist of the project (`PM-SVC-3`, link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/02-service-and-skill-tools.adoc#_selective_upstream_mcp_proxy_meta_provenance_pm_svc_3[MCP Tools Specification, Selective Upstream MCP Proxy]): per `server_id` the server's HTTPS `url`, its credential key `mcp-<server_id>` where the server is authenticated, the tools the server may call, and the call timeouts. Upstream tools are called server-side only; no worker reaches one. Its only writer is the operator verb `pm-operator upstream allow|deny`; a plain set does not change it, and repository content never adds a server or a tool. Upstream servers are remote HTTPS servers reached through `cui-http`; there is no `stdio` subprocess variant. Absent means no upstream server.

*Remediation Budgets Are Not Configuration*: `retry_budget`, `fix_budget`, and the allowed `decide` actions of a remediation policy are call arguments of the project-owned phase units (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units]), bound with their source in the plan instance (xref:14-plan-instance-waivers-questions.adoc#plan-instance[Plan Instance]) and capped by the compiled hard limits (link:../timeouts/01-job-budgets-and-waits.adoc#remediation-budgets[Timeouts & Budgets Specification, Remediation Budgets]); no JSON configuration file holds them, and the operator raises one only by a `raise` waiver for one plan.

*Decision Parameters Are Not Configuration Keys*: The decision declarations (`ask` or a quorum with its listed roles and score per decision kind), the vote wait, and the calibration level of the question adjudication, and the trigger thresholds, budget, and prerequisite wait of the re-planning, are declarations of the units `adjudicate-decisions.pmwf` and `replan.pmwf` within compiled bounds (link:../workflow-dsl/02-units-jobs-decisions.adoc#unit-declarations[Workflow DSL Specification, Unit Declarations]). Whether a decision is taken by a quorum or by the operator is said only by its declaration; a decision the operator takes is an operator wait without a time limit (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]), and no key of this file changes who decides or how long a decision waits.

*Roles Are Not Configuration Keys*: The harness, model, and effort of a role are the effective values of its artifact overlaid by the role assignments of the machine and the project and a plan's override (link:../model-work/01-roles-and-configuration.adoc#role-assignment[Model Work Specification, Role Assignment]; xref:12-machine-stores.adoc#role-assignments-store[Role Assignments]); its form, count, and recycling belong to the role artifacts of the operator's role sets (`<PM_MCP_BASE>/roles/`, `<PM_MCP_BASE>/projects/<project_id>/roles/`, link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]). Neither this file nor `project_defaults` holds a key for them.

[#project-levels]
== Project Values over Machine Values
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-8[PM-EXT-8: Project Onboarding as One Process]_ +
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)]_

The machine sets defaults, not final values. Every value the machine's onboarding records is the default of every project, and a project may set its own; one rule decides for every key and aspect: *the nearest level wins, and a level that says nothing defers to the next*. The one exception is the speech role's methods, which a project may only narrow (the table below). The levels, from the farthest: the compiled default, the derived value (xref:09-derived-facts-and-build-timings.adoc#derived-facts[Derived Facts Store]), the machine's value, the team's value (`.marshall/config/`), the project's operator value, and a plan's own value (link:../workflow-dsl/09-plan-instance.adoc#plan-overrides[Workflow DSL Specification, Plan Overrides]). A key belongs to the team or to the operator, never to both, so the team and the project's operator level never compete for one key.

The interface language, the enrolled harnesses with the default harness, the credential store, the duration of read reports and of unenrolled projects, and the machine's host tools are facts of the machine and have no project value.

* *Where the project sets them*: the project's onboarding and setup show the operator's values of the project in one step, `project.operator`: every aspect above that is the operator's, each with the machine's value as its proposal (the integration variant and credential from the machine's provider defaults, the commit identity from `project_defaults.commit_identity`, else the global git identity). Accepting a proposal records nothing for the project; a changed value is recorded in `local-config.json` or in the project's own store (its role assignment, its model catalogue). The step takes over the operator's choices of `setup.select-integration-variants` and the operator posture of `setup.project-settings` (link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-onboarding[Credentials & Enrolment Specification, Onboarding a Project as One Process]). The team's values stay in the setup and in `.marshall/config/`. A later run of one aspect runs only that aspect's states with the current values as the proposal.
* *A machine value that does not fit*: a machine default that does not fit a project (`landing.main` on a protected base branch, `landing.pull-request` without a provider) is refused for that project, with the reason, at its setup or at a plan's start, and the project or the plan chooses another; the machine default itself is never validated against a repository.
* *Effective configuration*: the server computes every value with its source level and what it overrides, publishes it as `pm://project/config` and to both clients over the local API, and sets and unsets a value per key and level there (xref:07-project-configuration.adoc#project-configuration-store[Project Configuration], items 4 and 5). Every project and plan that follows the machine's value uses a changed machine value from its next read; a plan holds the values bound at its start in its plan instance (link:../workflow-dsl/09-plan-instance.adoc#plan-axes[Workflow DSL Specification, Plan Behaviour Axes]).
