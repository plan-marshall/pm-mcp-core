[#local-config]
== Operator Local Configuration (`<PM_MCP_BASE>/projects/<project_id>/local-config.json`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)]_

_Implementation watch: link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-29[PM-WATCH-EXT-29]_

The operator's values of one project and its machine-local bindings, written only by the runtime under the project's `locks/local-config.lock` on the operator's acts in either client: the operator values of the project's onboarding and setup (`project.operator`) and their later runs, a value set or unset over the local API, and `pm-operator config set|unset <key> [<level>]` at the project's level; never by a model. Sparse like the team files: a key holds only the project's own value, and accepting the machine's value as the proposal records nothing. The file carries `revision` like every operator file (xref:12-machine-stores.adoc#machine-config[Machine Configuration Store], Operator files and their revision). Which value of which level wins is <<project-levels>>.

* *Shared keys* (`$defs/settings`): each falls back to the same key of `machine-config.json` `project_defaults` and then to the compiled default; `$defs/settings` is the schema of both (xref:12-machine-stores.adoc#machine-config[Machine Configuration Store (`<PM_MCP_BASE>/machine-config.json`)]). Among them the commit author identity `commit_identity {name, email}`, the author of every server commit (the operator, who is responsible for the change); the committer is the agent identity resolved from the provider credential (derived fact `agent_identity`), else the fixed `plan-marshall-mcp` noreply identity (link:../domain-extensions/04-setup-state-machine.adoc#setup-verify-credentials[Domain Extensions Specification, Credential Verification]). Where neither the project nor the machine holds one, `project.operator` proposes the operator's global git identity, and accepting it records it for the project, since no level holds it; while no effective value exists, a commit refuses as `failed` with the reason `commit_failed` and a `detail` naming the missing `commit_identity` (the reason set is closed, link:../../../pm-providers/pm-provider-git/doc/adr/provider-git-primitive/005-one-failed-outcome-with-a-closed-reason.adoc[ADR provider-git-primitive 005]). The `commit_trailer` stays a separate key. Besides the constraints of its schema below (`$defs/settings`), neither half of `commit_trailer` may hold an unpaired UTF-16 surrogate, which has no UTF-8 encoding and so cannot reach a commit message; a surrogate pair, one supplementary character, is allowed, and the length bounds count code points. The schema's patterns refuse the Unicode line separators U+0085, U+2028 and U+2029 and every C0 and C1 control, so a value that passes the schema check carries none; the code applies the textual rule of the two halves to a stored value — a name without an angle bracket or a line break, an email of the form `local@domain` without an angle bracket or white space, which covers the three separators — and passes over the half when that rule refuses it. A stored half that breaks a constraint, this one included, is passed over like an absent one, per half: the next stored value of the half that keeps the constraints is used and the half reports `configured`; when none is left, the compiled default is used and the half reports `invalid_ignored` (link:../../../pm-providers/pm-provider-git/doc/developer/provider-git-primitive.adoc#_the_commit_message_and_the_trailer[Commit Primitives Developer Guide § The Commit Message and the Trailer]). [[epic-defaults]]The values a new epic copies into its header at its creation, never asked at its start, are `epic.parallelization_scope` (compiled default `1`), `epic.auto_start` (`true`), and `epic.overlap_max_files` (`0`, at most `20`, the compiled upper bound); the epic's own values are changed on the epic (xref:04-epic-and-change-ledger.adoc#epic-header[Epic Header]; link:../model-work/08-epic-coordination.adoc#epic-auto[Model Work Specification, An Epic Runs by Itself]).
* *Aspect keys*: the project's value of an aspect the machine's onboarding records falls back to that aspect's machine value, never to `project_defaults`: `language.model` to the machine's `language.model`; `plan_defaults.method` and `plan_defaults.asking` to the machine's `plan_defaults` (link:../workflow-dsl/09-plan-instance.adoc#plan-axes[Workflow DSL Specification, Plan Behaviour Axes]); `plan_defaults.posture` to the machine's `plan_defaults.posture`, an optional key with no compiled default at either level: while neither sets it, a plan asks the posture in `init.options` (link:../workflow-dsl/09-plan-instance.adoc#plan-posture[Workflow DSL Specification, Posture and base branch]); `integrations.<integration>` to the machine's `providers.<integration>` (xref:12-machine-stores.adoc#provider-defaults[Machine Provider Defaults]); and `cleanup.plans_after_days`, `cleanup.epics_after_days`, `cleanup.logs_after_days` to the machine's `cleanup`. The landing axis of a project is no operator key: it is the team's (`workflow.json` `landing`, xref:07-project-configuration.adoc#config-workflow-json[Team File `workflow.json`]).
* *Integration variant and credential*: `integrations.<integration>` holds the project's `variant` (`native` or `cli`, for `git`, `github`, and `gitlab`) and its `credential_key`. The effective variant is resolved as link:../domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants] states. A choice of the operator is required only while the effective variant is invalid (a `native` variant and a feature the derived fact `git_native_capability` reports): it is an operator wait of `project.operator` (link:../domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]), never a question record and never an answer a model relays. One value holds for every operation of the integration; there is no per-operation override. While the choice is required and absent, every operation of that integration refuses with `integration_variant_unset`. A `cli` value requires the integration's host tool enrolled for the project or the machine; a `cli` value without its enrolled tool is an invalid variant and refuses with `integration_variant_unset` as well (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/04-errors-and-testing.adoc#rejection-reasons[MCP Tools Specification, Closed Rejection Reasons]). Sonar and Forgejo have only the native variant and take only a `credential_key`. The effective value carries its origin (`project` for the project's value, `machine` for the machine's default variant, `derived` otherwise), enters `config_hash`, and is served to the operator in both clients and in `pm://project/config`, never pushed into a representation or tool result (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).
* *`upstream_mcp`*: the upstream MCP allowlist of the project (`PM-SVC-3`, link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/02-service-and-skill-tools.adoc#_selective_upstream_mcp_proxy_meta_provenance_pm_svc_3[MCP Tools Specification, Selective Upstream MCP Proxy]): per `server_id` of a server configured on the machine (xref:12-machine-stores.adoc#upstream-servers[Upstream MCP Servers]) that the project switched on, the tools the project allows, picked from the tools the machine fetched from that server. The server's URL, credential, and call timeouts are the machine's and are not repeated here. Upstream tools are called server-side only; no worker reaches one. Its only writer is the operator's act `pm-operator upstream allow|deny` or its form in the web app: `allow` is refused `server_not_configured` for a server the machine does not configure and `tool_not_offered` for a tool outside its fetched list, and `deny` removes the project's entry only, never the machine's server or its credential; a plain set does not change it, and repository content never adds a server or a tool. Absent means no upstream server.

*Remediation Budgets Are Not Configuration*: `retry_budget`, `fix_budget`, and the allowed `decide` actions of a remediation policy are call arguments of the project-owned phase units (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units]), bound with their source in the plan instance (xref:14-plan-instance-waivers-questions.adoc#plan-instance[Plan Instance]) and capped by the compiled hard limits (link:../timeouts/01-job-budgets-and-waits.adoc#remediation-budgets[Timeouts & Budgets Specification, Remediation Budgets]); no JSON configuration file holds them, and the operator raises one only by a `raise` waiver for one plan.

*Decision Parameters Are Not Configuration Keys*: The decision declarations (`ask` or a quorum with its listed roles and score per decision kind), the vote wait, and the calibration level of the question adjudication, and the trigger thresholds, budget, and prerequisite wait of the re-planning, are declarations of the units `adjudicate-decisions.pmwf` and `replan.pmwf` within compiled bounds (link:../workflow-dsl/02-units-jobs-decisions.adoc#unit-declarations[Workflow DSL Specification, Unit Declarations]). Whether a decision is taken by a quorum or by the operator is said only by its declaration; a decision the operator takes is an operator wait without a time limit (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]), and no key of this file changes who decides or how long a decision waits.

*Roles Are Not Configuration Keys*: The harness, model, and effort of a role are the effective values of its artifact overlaid by the role assignments of the machine and the project and a plan's override (link:../model-work/01-roles-and-configuration.adoc#role-assignment[Model Work Specification, Role Assignment]; xref:12-machine-stores.adoc#role-assignments-store[Role Assignments]); its form, count, and recycling belong to the role artifacts of the operator's role sets (`<PM_MCP_BASE>/roles/`, `<PM_MCP_BASE>/projects/<project_id>/roles/`, link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]). Neither this file nor `project_defaults` holds a key for them.

[#project-levels]
== Project Values over Machine Values
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-8[PM-EXT-8: Project Onboarding as One Process]_ +
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)]_

The machine sets defaults, not final values. Every value the machine's onboarding records is the default of every project, and a project may set its own; one rule decides for every key and aspect: *the nearest level wins, and a level that says nothing defers to the next*. The one exception is the transcription methods, which a project may only narrow (the table below). The levels, from the farthest: the compiled default, the derived value (xref:09-derived-facts-and-build-timings.adoc#derived-facts[Derived Facts Store]), the machine's value, the team's value (`.marshall/config/`), the project's operator value, and a plan's own value (link:../workflow-dsl/09-plan-instance.adoc#plan-overrides[Workflow DSL Specification, Plan Overrides]). A key belongs to the team or to the operator, never to both, so the team and the project's operator level never compete for one key.

[[machine-facts]]The interface language, the enrolled harnesses with the default harness, the credential store, the upstream MCP servers (a project only switches a configured server on, xref:12-machine-stores.adoc#upstream-servers[Upstream MCP Servers]), the duration of read reports and of unenrolled projects, and the machine's host tools are facts of the machine and have no project value.

* *Where the project sets them*: the project's onboarding (link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-onboarding[Credentials & Enrolment Specification, Onboarding a Project as One Process]) and setup show the operator's values of the project in one step, `project.operator`: every aspect above that is the operator's, each with the machine's value as its proposal (the integration variant and credential from the machine's provider defaults, the commit identity from `project_defaults.commit_identity`, else the global git identity). Accepting a proposal records nothing for the project; a changed value is recorded in `local-config.json` or in the project's own store (its role assignment, its model catalogue). The team's values stay in the setup and in `.marshall/config/`. A later run of one aspect runs only that aspect's states with the current values as the proposal.
* *A machine value that does not fit*: a machine default that does not fit a project (`landing.main` on a protected base branch, `landing.pull-request` without a provider) is refused for that project, with the reason, at its setup or at a plan's start, and the project or the plan chooses another; the machine default itself is never validated against a repository.
* *Effective configuration*: the server computes every value with its source level and what it overrides, publishes it as `pm://project/config` and to both clients over the local API, and sets and unsets a value per key and level there (xref:07-project-configuration.adoc#project-configuration-store[Project Configuration], items 4 and 5). Every project and plan that follows the machine's value uses a changed machine value from its next read; a plan holds the values bound at its start in its plan instance (link:../workflow-dsl/09-plan-instance.adoc#plan-axes[Workflow DSL Specification, Plan Behaviour Axes]).
