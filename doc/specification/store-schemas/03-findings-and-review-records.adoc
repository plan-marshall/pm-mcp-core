[#phase-sub-workflows]
== Phases as Sub-Workflows and the Phase of a Record
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-16[PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-IMPL-5[PM-IMPL-5: Declarative Workflow DSL & Automated Diagram Generation]_

A plan runs as a workflow of phases. Its plan unit calls each of the six phases, `init`, `refine`, `outline`, `plan`, `execute`, and `finalize`, as a sub-workflow, and a phase's outcome decides the plan unit's next call. Calls, frames, interfaces, and their checks are those of every sub-workflow (link:../workflow-dsl/01-grammar.adoc#interface-rules[Workflow DSL Specification, Interface Rules]; link:../workflow-dsl/06-reusable-sub-workflows.adoc[Workflow DSL Specification, Reusable Sub-Workflows]); this section fixes what is particular to the phases and the phase every store records.

* *The plan unit*: it starts at its starting point and ends in its stop points, with neither entries nor exits, and holds the calls of the phases and the routes between them, never a state of a phase. A loop-back is the plan unit calling an earlier phase again; a re-entry from finalize into execute is the finalize phase ending with that outcome, on which the plan unit calls execute.
* *A phase's interface*: each phase declares its interface in its frontmatter: an entry for each point at which it is entered (a phase entered again after a loop-back, finalize entered first and after a fix, each through an entry of its own) and an exit for each outcome on which the plan unit continues differently. No transition crosses from one phase into another.
* *A lane is a choice of phases*: the plan unit's choice of which phases it calls, never a phase of its own. The light and deep lanes call all six; the `land` lane calls no refine, outline, or plan phase, and its `land.*` states form a sub-workflow called within the phase `execute`; the `adopt` lane calls `init` and then `finalize`. A recipe's workflow calls phases the same way, its own where they differ and the plan's shared ones (finalize, the landing) where they do not (link:../domain-extensions/05-recipes-and-extension-points.adoc#recipe-workflow[Domain Extensions Specification, A Recipe Is a Workflow]); a plan behaviour axis is a call site inside a phase, the landing axis inside `finalize` (link:../workflow-dsl/09-plan-instance.adoc#plan-axes[Workflow DSL Specification, Plan Behaviour Axes]).
* *The phase of a plan*: the phase sub-workflow on its call stack, the bottom frame of `call_stack` (xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store]). A sub-workflow called within a phase (a remediation unit, `git.commit_and_push`, the `replan` unit, a decision, a chat) has that phase. No state declares a phase, and no table maps a state to its phase. At its end a plan takes the phase `completed` in each of its three delivery terminals, `completed`, `handed_back`, and `returned`, whose `outcome` tells them apart, and the phase `aborted` in `plan.aborted`; no call stack is left.
* *Composition*: the plan instance composes the plan unit and the phase sub-workflows; a pruned phase is a pruned call, with its reason (xref:14-plan-instance-waivers-questions.adoc#plan-instance[Plan Instance]). A phase is shown, replaced, and extended on its own, as a unit the composition resolves by level (link:../workflow-dsl/04-ast-node-model.adoc#process-designer[Workflow DSL Specification, Designing a Process]).
* *Depth*: the phase level adds one frame to every call path of a plan: `call_stack` holds at most five frames (`PM-WF-16`).

*The phase value of a record*: the stores record a phase by its phase value, one per phase sub-workflow:

[cols="1,1"]
|===
|Phase sub-workflow |Phase value

|`init` |`phase-1-init`
|`refine` |`phase-2-refine`
|`outline` |`phase-3-outline`
|`plan` |`phase-4-plan`
|`execute` |`phase-5-execute`
|`finalize` |`phase-6-finalize`
|===

Every `phase` field of a plan's record (the `phase` of `mcp/status.json`, a finding, an unplanned change of `references.json`, a metrics row, a gap record, a re-planning trigger, an amendment, a history line) holds the phase value of the phase sub-workflow on the call stack of the transition that writes it, taken by the server and never supplied by a caller; a configuration key that names a phase uses the same value (`workflow.plan.phase-5-execute.per_deliverable_verbs`). A record of an epic, the workspace, or the machine scope has no phase value of a plan.

== Owed Item Record (`mcp/status.json` → `owed[]`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-30[PM-WF-30: PR Body & Landing Record]_

An owed item is an obligation a plan incurred but did not discharge. It is written by the step that incurs it, never
derived from prose, and it stays in the plan's `mcp/status.json` through archival (`PM-WF-30`).

The schema of an owed item is the file `owed-item.schema.json` in `pm-core/src/main/resources/de/planmarshall/core/store/`, beside the codec of the status document, `WorkflowStatusCodec`:

----

* *Kinds*: The set is closed; each kind names the states that write it.
** `cleanup`: removal work the server leaves to the operator. Writers: `finalize.merge-dispatch` and `finalize.merge-queue-wait` (the operator's local commits a `land` plan carried that landed squashed stay on the operator's branch; the item names what remains to remove), and `finalize.hand-back` (a worktree or branch removal of a non-merging run it could not perform).
** `post_merge_cleanup`: the post-merge work of a plan handed back with its pull request still queued (`enqueued_not_landed`): branch removal and the post-merge band steps that did not run. Writer: `finalize.merge-queue-exit` (`closed` or `budget_spent` while the pull request is still queued). Discharged by the operator once the queue landed or dropped the entry.
** `capture_ref_retained`: the capture ref `refs/pm-mcp/captures/<plan_id>` of a `land` plan, kept as the operator's recovery point. Writers: `finalize.merge-dispatch` and `finalize.merge-queue-wait` (a `merged` plan whose captured tree differs from the merged head), `finalize.hand-back`, and the engine-owned abort `plan.aborted` (also as the first transaction of `delete-plan`). Discharged by the operator's drop of the capture (`pm-operator drop-capture <plan_id>` in the terminal client) (link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#land-lane[Phase Workflows Specification, Land Lane, item 5]).
** `post_merge_step_failed`: a finalize step that failed after the merge; `incurred_by_step` names it. Writer: `finalize.step-failed` (`after_merge`, the re-fire spent); the plan stays `merged`.
* *Dischargers*: `operator` (an act of the operator in either client) and `plan_step` (the step that incurred the item, on a later firing).
* *Explicit Empty Set*: `emit-landing` and `archive-plan` write `owed` explicitly; `[]` means the plan owes nothing, an absent or null field means the question was never asked and is rendered `unknown`, never as nothing owed.
* *Survives Archival*: Owed items stay readable from the archived plan (link:../filesystem-layout.adoc[Filesystem Layout Specification]) and are never folded into `completed`; an archived plan with an undischarged item is never due for the cleanup (link:../timeouts/03-retention-harness-config.adoc#cleanup[Timeouts & Budgets Specification, One Cleanup]).
* *Listable Without Prose*: For an epic plan the landing envelope carries `owed[]` to the epic inbox. For every plan, the project owed index `pm://project/owed` (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools.adoc[MCP Tools Specification]) lists the undischarged items of active and archived plans, derived from their `owed[]` (no separate store), with per-root coverage; a root that could not be read is reported, never read as zero.
* *Discharge*: An item is discharged only by recording `discharge_proof` and `discharged_at` through the discharger's transition: the step that incurred it on a later firing, or the operator's discharge in either client (in the terminal client `pm-operator discharge-owed --plan <plan_id> --owed <owed_id> --proof <ref>`, and `pm-operator drop-capture <plan_id>` for `capture_ref_retained`), which also serve archived plans; these two acts are the only writes to an archived plan's records, beside the transcript of a chat about it and the cleanup's deletion; a discharged item is kept, never deleted.

== Findings Ledger Record (`findings.jsonl`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-27[PM-WF-27: Findings & Triage]_
_Implementation watch: link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-16[PM-WATCH-GEN-16], link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-43[PM-WATCH-GEN-43], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-4[PM-WATCH-STORE-4], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-5[PM-WATCH-STORE-5], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-7[PM-WATCH-STORE-7], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-31[PM-WATCH-STORE-31], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-45[PM-WATCH-STORE-45], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-116[PM-WATCH-PHASE-116], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-126[PM-WATCH-PHASE-126]_

Each line in `findings.jsonl` (of a plan, or of the workspace scope for the findings of plan-less builds) is a standalone JSON object representing a finding from Q-Gate validation, code review, a code analysis provider, or PR review bots. External provider identifiers (`provider_ref`) are persisted as a typed sub-object rather than packed into free-text `detail` strings.

*Versioned lines*: The store is append-only and versioned (xref:01-format-and-session-log.adoc#format-versioning[Format Versioning & Atomic Write Discipline] item 6): every change of a finding (triage, resolution, transmission, carry-out) appends its full record again with a new `updated_at`. The current record of a finding is the last readable line with its `finding_id`; the earlier lines are its history and are never read as current.

----

* *Immutable Severity, Mutable Blocking*: `severity` is set at creation and never changed; for a `security_audit` finding the server sets it at creation from the submitted severity and the calibration cap (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#security-audit-calibration[Phase Workflows § Security Audit Calibration]), keeping the submitted value in `submitted_severity`. `blocking` is written from the producer's declared class for the finding type (each producer declares it per finding type in its descriptor, validated at write) and may later change only through triage. A waiver changes neither `blocking` nor `resolution`: a finding admitted at a gate by a `findings:<class>` or `qgate_findings:<phase>` waiver stays as it is and is listed in that waiver's consumption (accepted by waiver, xref:14-plan-instance-waivers-questions.adoc#waiver-record[Waiver Record]).
* [[located-finding-grounding]]*Located Finding Grounding*: A finding a model files (`self_review`, `security_audit`, `code_review`, `qgate`) with a `file_path` is refused at filing, with `invalid_link_args` naming the finding and the cause, when the file does not exist at its `raised_at_head` or its `line` lies beyond the file's last line there; a `security` `ingress` is checked the same way. The server reads the file from the git object of that commit, never from the working tree, so an edit after the finding was raised does not decide it. A refusal files nothing and counts toward the task's refused submissions; a cited location that disappears later is the stale re-anchor below, not a refusal (_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-57[PM-WATCH-STORE-57]_).
* *What Is Not a Finding*: Refusals, rate-limit or budget notices, the server's own posted comments and triggers, and participation-only artifacts (summary cards, trigger acknowledgements) are never filed as findings; they update the review participation record only (<<review-participation>>).
* *Structured Reviewer Identity*: `author` and `bot_kind` come from the provider's structured author field, never from comment text. A comment whose structured author and self-declared bot identity disagree is itself filed as a finding with the provider's `source`. A comment's identity is `(bot_kind, provider_ref.comment_id)` plus `edit_marker`; an edited comment is new information.
* *Screened External Text*: A gather firing that ingests external text (review comments, bot findings, analysis-provider messages) builds one screening batch over its new items; the server writes `batch_id` and `screen` per finding from the scope's screen verdict cache or the batch's screener job (xref:15-screening-and-grants.adoc#screen-verdict-cache[Screen Verdict Cache]) before any task receives the text. The triage task of the firing receives only findings whose `screen.withheld` is `false`; a withheld finding is delivered with its structured fields only and stays `pending`.
* *Server-Written Resolution*: The model submits only `disposition` (`FIX`, `SUPPRESS`, `ACCEPT`); the triage submission (`triage-groups`) has no resolution parameter. The server writes `resolution` from recorded evidence, so a refuted claim, a valid finding that was dismissed, and a finding that is not this plan's concern stay distinguishable:
+
[cols="1,3,1"]
|===
|Disposition |Recorded condition |`resolution`

|— |Finding created, or triaged but its effect not yet recorded |`pending`
|`FIX` |The fix landed: its fix task passed server verification, or the in-branch settle commit covering the fix's `population` is recorded |`fixed`
|`SUPPRESS` |`evidence.claim_refuted == true`: the `ext-point-verify` refutation sub-state refuted the claim (`evidence.class: verifier`), or, when that sub-state is unavailable, substitute evidence with a concrete `evidence.ref` (file:line, job id, or URL) |`rejected`
|`SUPPRESS` |Otherwise (the finding is valid but dismissed) |`suppressed`
|`ACCEPT` |`scope_class == out_of_footprint` (pre-existing or another owner's code), or the triage cites a standing decision of the plan (an `amendments[]` entry or an ADR id that the server resolves) |`taken_into_account`
|`ACCEPT` |Otherwise (a known, accepted gap) |`accepted`
|— |Stale re-anchor: the finding's cited location no longer exists at `HEAD` (link:../phase-workflows.adoc[Phase Workflows Specification], Step Records, Re-Fire & Loop-Back Rules) |`taken_into_account`
|===
+
`scope_class` is computed by the server at triage from `file_path` against the plan's effective footprint (`declared_files ∪ realized_files`, which includes the recorded unplanned changes, xref:13-leases-integrity-testing.adoc#three-way-footprint[Three-Way File Footprint Reconciliation (`references.json`)]). No operator triage exists: the operator's only lever over findings is a waiver of the gate. `pending` is the only non-terminal resolution: the Blocking Findings Guard and the pre-merge barrier count it, and a `FIX` whose fix has not landed is still `pending`. Every report and landing figure over findings is keyed by `resolution` with every member tallied (stated zeros); the false-positive count of a source is its `rejected` count and never includes `suppressed`. *Deliberate change vs. `plan-marshall`*: `plan-marshall` lets the model choose one of the six resolutions directly; `PM-MCP` keeps the three model dispositions and derives the six-value resolution from evidence the server holds.
* *Evidence Symmetry*: A resolution rests on evidence of the same kind whichever way it goes: `rejected` requires a concrete `evidence.ref` as a `FIX` requires a landed change, and a disposition that lowers severity cites an executed check.
* *Closed Suppression Reason*: A `SUPPRESS` disposition carries `suppress_reason` from a closed list, and the server refuses a `SUPPRESS` without one, or one whose reason contradicts the record, with `invalid_link_args` naming the finding: `claim_refuted` (the finding's claim is wrong; only with `evidence.claim_refuted`, and it is the only reason that resolves `rejected`), `duplicate` (another finding of the plan reports the same defect; `evidence.ref` names its `finding_id`, which the server resolves in the plan's findings store), `rule_exception` (a rule of a skill the plan resolves permits the case; `evidence.ref` names the skill file with its anchor, which the server resolves in the delivered skills), `generated_code` (the finding lies in a path that git does not track, or that `.gitattributes` marks `linguist-generated` or `linguist-vendored`, which the server checks at the finding's `raised_at_head`), and `tool_limitation` (the producing tool cannot see what makes the code correct; the `reply_text` says what). There is no reason "other": a valid finding that fits none is `FIX` or `ACCEPT`. Every report and landing figure over `suppressed` and `rejected` findings is keyed by `suppress_reason` as well, every member tallied. *Deliberate change vs. `plan-marshall`*: its `resolution_detail` is optional free text; `PM-MCP` keeps the reply text and adds the closed reason the reports count.
* [[fix-attribution]]*Fix Attribution*: When the server files a located finding, it compares the finding's `file_path` and `line` with the lines changed by every remediation fix commit of the plan in `change-ledger.jsonl` (a remediation task's commit, a settle commit covering a fix's `population`, a loop-back iteration's fix commit), mapped forward to the finding's `raised_at_head`, and writes `introduced_by` with the latest such fix; this one comparison is the source of every `findings_self_seeded` count (Q-Gate rounds, loop-back iterations, self-review rounds). Per remediation round of every class, the server records `findings_cleared` (findings the round's fix resolved `fixed`) and `findings_introduced` (findings whose `introduced_by` names the round), renders both in the facts of the next decision task of the same policy unit, and lists every fix whose `findings_introduced` exceeds its `findings_cleared` as `net_worse` in the landing record and the completion report; a round whose fix has no landed commit has no figures, never zeros. Attribution states a location, not a cause: a finding on a line a fix touched is attributed to that fix even when the defect predates it, and the facts say so.
* [[fix-size]]*Fix Size*: Per remediation round of every class with a landed fix commit, the server records `lines_added` and `lines_removed` of the round's fix commits from git, and per plan `size_before_fix` (the lines added and removed between the plan's merge base and the parent of its first fix commit) and `size_at_landing` (the same between the merge base and the landed `HEAD`). It renders the figures in the facts of the next decision task of the same policy unit. They are computed without a model, report what happened, and block nothing: no gate, budget, or re-planning trigger reads them. A binary file counts no lines and is named in `binary_files`; a figure that could not be read is `unknown`, never `0`; a plan with no fix commit has `size_before_fix` equal to `size_at_landing`.
* *Re-Disposition of a Transmitted Finding*: A finding whose `transmit_outcome` is `sent` may be re-dispositioned only together with a new `reply_text`; the server then resets `transmit_outcome` to `pending`, re-derives `resolution`, and transmits again. A bare re-disposition (same or no reply) is refused with `invalid_link_args`.
* *Late Findings Are Carried Out*: After the merge gate (order `> 70`) no step refuses on findings. A blocking finding still `pending` after the merge (filed after the barrier evaluated) is carried out by the server: appended to the parent epic inbox as a `process_finding` message, or, for a plan without an epic or whose epic linkage is `detached` (its epic terminal, xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store], Origin and Epic Linkage), seeded as a lesson (category `bug`, title from `summary`, body from `body`); while the epic linkage is `indeterminate` the message is appended to the kept landing envelope `landing-envelope.json` (xref:04-epic-and-change-ledger.adoc#kept-landing-envelope[Kept Landing Envelope]) and delivered with it. The finding is set to status `carried` with `carried_to` after the destination has accepted the record (write order and recovery: xref:01-format-and-session-log.adoc#transaction-journal[Transaction Journal], Writes outside the scope, Late findings); its `resolution` stays `pending`, so the carried debt remains visible (link:../phase-workflows.adoc[Phase Workflows Specification], rows `1000` and `1100`).
* *Transmit Reasons*: `transmit_reason` is one closed vocabulary shared by every provider: `no_provider_address` (no thread, comment id, or Sonar issue key to answer on), `pr_number_unrecorded` and `belongs_to_other_pr` (the finding cannot be shown to belong to this pull request; deferred, never dropped), `nothing_to_transmit` (the disposition carries no reply), `reply_failed` and `resolve_failed` (the provider call for the reply or for the thread resolution failed), `provider_unreachable`, and `provider_rejected`. Provider error text is never packed into the reason. *Deliberate change vs. `plan-marshall`*: the GitHub, GitLab, and Sonar integrations each report their own free-text skip reasons (`no_resolution_detail`, `no thread_id or resolution_detail`, `no issue key in detail`, `thread-reply failed: <error>`; verified at `plan-marshall` `b1a9a89fa`), so one condition has three spellings.
* *Transmission and Resolution Are Separate*: Before the provider call the server persists `transmit_outcome: pending` with the `transmit_disposition` it sends. `responded_at` is stamped after the provider accepted the reply and before the thread is resolved; `resolve_state` is persisted separately, so a resolve-only retry never re-sends the reply. After a crash, a `pending` transmission is reconciled by looking up the reply on the provider before any re-send.

[#analysis-result]
== Analysis Result Record (`analysis.jsonl`)

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-IMPL-1[PM-IMPL-1: Decoupled Plain-Java Core Engine & Quarkus Assembly]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-IMPL-2[PM-IMPL-2: Versioned JSON/JSONL Storage & TOON Wire Output]_

Each line of `analysis.jsonl` of a plan is one observation of one code analysis provider for one target: what the provider reported about a commit or a pull request, in the provider-neutral form of the code-analysis contract (link:../../../../plan-marshall-documentation/doc/specification/module-structure.adoc#findings-analysis-contracts[Module Structure Specification, Findings & Code-Analysis Contracts]). The record is the same for every provider; nothing in it is specific to one. The new issues of an observation are not part of this record: they are findings of the findings ledger with `source: analysis` and the same `provider`.

*Serialization*: one canonical JSON object per line, written through Jackson from a Java record of `de.planmarshall.core.analysis`, with the members in the order of the schema and no member omitted (an absent value is `null`). The log is append-only: a later observation of the same key appends the full record again. The key is (`provider`, `target.kind`, `target.commit_sha`, `target.pr_number`), and the current record of a key is its last readable line. A model never reads the file: the wire shows the aggregated `analysis_status` only, and the record is served on demand to the operator's clients.

The schema of an analysis result record is the file `analysis-result.schema.json` in `pm-core/src/main/resources/de/planmarshall/core/analysis/`, beside its codec `AnalysisResultCodec`:

[source,json]
----
include::../../../pm-core/src/main/resources/de/planmarshall/core/analysis/analysis-result.schema.json[]
----

* *Consistency*, checked on write: `status: passed` requires `count_status: measured`, `new_code_issue_count: 0`, and a `gate` that is `null` or `passed`; `gate_failed` requires `gate.result: failed`; `findings` requires `new_code_issue_count > 0` and no failed gate; `count_status: indeterminate` requires `status: undecidable` unless the status is `running` or `not_run`.
* *Strings from the provider* (`metric`, `threshold`, `actual`, `analysis_ref`) are untrusted: they are length-bounded, stored as data, and never rendered to a model.

[#component-assessments]
== Component Assessment Record (`assessments.jsonl`)
_Implementation watch: link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-40[PM-WATCH-GEN-40], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-8[PM-WATCH-STORE-8]_

Tasks of `read_only` roles persist component assessments through their entity `submit` (link:../model-work.adoc[Model Work Specification]). Assessments are a second schema beside findings: they are never written to `findings.jsonl`, and no finding histogram or count reads this store (`PM-WF-11`).

The schema of a component assessment record is the file `assessment-record.schema.json` in `pm-core/src/main/resources/de/planmarshall/core/findings/`, beside the findings ledger:

[source,json]
----
include::../../../pm-core/src/main/resources/de/planmarshall/core/findings/assessment-record.schema.json[]
----

* *Assessments Are Inputs, Never Back-Filled*: The server stamps `recorded_at` when it appends the record. A gate or coverage check that consumes assessments reads only records whose `recorded_at` is earlier than its own evaluation start and refuses those written after it; an empty assessment population is reported as a gap, and no link writes placeholder assessments.
* *Append-Only Supersession*: A line is never rewritten. A superseding record names the record it replaces in `supersedes`; the superseded record's validity window is `[effective_from, effective_from of the superseding record)`. Superseded assessments stay readable, never live.
* *Footprint Changes Supersede*: An outline revision that changes a deliverable's footprint appends superseding assessments for the affected components; a recorded unplanned change (`unplanned_changes`, xref:13-leases-integrity-testing.adoc#three-way-footprint[Three-Way File Footprint Reconciliation (`references.json`)]) supersedes nothing.
* *Grading Against the Judgement in Force*: A consumer that grades a recorded action against an assessment uses the assessment whose window contains the action's timestamp. A write to a path whose live assessment is `exclude` is `violated_live_exclusion`; it is recorded and graded, never blocking, since unplanned changes inside the worktree are accepted.

[#review-participation]
== Review Participation Record (`review-participation.jsonl`)
_Implementation watch: link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-29[PM-WATCH-PHASE-29], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-45[PM-WATCH-STORE-45]_

The plan's `review-participation.jsonl` holds one current record per `(pr_number, round, bot_kind)`, written by `automatic-review` at review time for every bot of `required_bots ∪ optional_bots` (`PM-WF-13`). It is versioned like the findings ledger: every change appends the full record again, and the current record of a key is the last readable line with that key. The pre-merge barrier and every post-merge reader take review participation only from these records.

The schema of a review participation record is the file `review-participation.schema.json` in `pm-core/src/main/resources/de/planmarshall/core/findings/`, beside the findings ledger:

[source,json]
----
include::../../../pm-core/src/main/resources/de/planmarshall/core/findings/review-participation.schema.json[]

* *Covered Commit from Evidence Only*: `covered_commit_sha` is taken only from provider evidence (the review's commit id, or the registry's `reviewed_sha_pattern` in the body) and `sha_source` keeps structured and body-derived values distinct. It is `null` when no evidence names a commit; a refusal never sets it. `head_at_observation` is stored separately and is never copied into it.
* *Currency Inputs*: The barrier's review currency test (link:../phase-workflows/06-finalize-re-entry-and-merge.adoc#_two_fail_closed_barrier_predicates[Phase Workflows Specification, Predicate 2]) reads `covered_commit_sha` and `evidence.created_at` of each record against `HEAD` and the branch's last push; it is evaluated per record for every required bot, never skipped for a bot by a registry field.
* *Per Round*: A looped-back pull request has no single reviewed tree. Participation is recorded per `round`; no single reviewed SHA is synthesised for a multi-round pull request.
* *Refusal Capture*: A refusal is recorded with its `body` and `observed_at` when first seen; a later absence of the notice is not a refutation.
* *No Backfill*: Missing records for already-merged pull requests are never synthesised. A post-merge reader treats an absent, unreadable, malformed, or stale record as `indeterminate` (never clean) and names the case.

== Review-Bot Registry Record
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-13[PM-WATCH-STORE-13]_

One record per `bot_kind` is compiled into the binary; a project may add records through its team configuration (`.marshall/config/project.json` `review.bot_registry`, xref:07-project-configuration.adoc#config-project-json[Team File `project.json`]). `required_bots` and `optional_bots` are resolved against the registry only through one shared reader. A bot token that matches no record fails loudly (`unregistered_kind`) with the same disposition everywhere and is never counted in a ratio denominator.

The compiled-in records carry the data derived from `plan-marshall` `automatic-review/standards/` at f3de0e14f, normative as written: `coderabbit` (one review per hour, `awaitable_window`, trigger verb `@coderabbitai review`, CodeRabbit refusal wrapper `<details><summary>⚠️ Action not completed</summary>`, and the bot-author skip notices "Bot user detected" and "authored by a bot without an assigned CodeRabbit review seat" among its `refusal_patterns`), `sourcery` (`hard_quota`, an account-level diff-character quota over a rolling 7-day window, and per-pull-request size and file-count ceilings), and `cuioss-review-bot` (`unknown`, reviewed SHA only in the body). No record encodes a bot's ceiling or quota as a number: the detection patterns are number-free and the ceiling is read from the bot's own notice (`refusal_size_cap_patterns`, `rate_limit_eta_patterns`), so a plan change of the bot needs no record change. `sourcery` declares `participation_requires_update: false`; `coderabbit` and `cuioss-review-bot` declare `true` (they edit their summary comment in place on re-review). The provider comment body cap (GitHub 65,536 characters) is a provider limit, not a bot record.
