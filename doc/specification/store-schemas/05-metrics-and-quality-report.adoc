[#metrics-store]
== Metrics Store (`metrics.json`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-26[PM-WATCH-STORE-26], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-35[PM-WATCH-STORE-35], link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-13[PM-WATCH-GEN-13]_

The plan's `metrics.json` holds the task and phase measurements that `default:record-metrics` aggregates (`PM-WF-14`, link:../model-work/09-completion-usage-and-spend.adoc#job-result-schema[Model Work Specification, Worker Result & Usage Parsing], which defines which row each worker and task yields). It extends the rule "unmeasured is never `0`" from token usage to every figure it publishes.

* *Scope*: One `metrics.json` exists per scope that runs model work: `plans/<plan_id>/metrics.json`, `epics/<epic_id>/metrics.json`, and `workspace/metrics.json` of the project's machine store (link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]). The epic and workspace files hold only the task rows and served-read rows of their scope, with `phase: null`; the workspace file also holds the `worker_idle` rows of the project's warm workers, which serve every scope of the project and are therefore reported apart, never in a plan's figures (link:../model-work/09-completion-usage-and-spend.adoc#spend-accounting-budget-anchors[Model Work Specification, Spend Accounting]); wait rows and phase-close rows exist only in a plan's file. Each file is written under its scope's lock and covered by the scope's digest sidecar.
* *Rows*: Task rows (kind `task`: `queue_task_id`, `attempt`, `role`, the worker's `job_id` and `generation_id`, `harness` with the `harness_version` probed at its worker's spawn, `model`, `effort`, `form`, `phase` (the phase value of the phase sub-workflow on the call stack of the creating state, xref:03-findings-and-review-records.adoc#phase-sub-workflows[Phases as Sub-Workflows]), `step_id` or null, `envelope_id` or null with its summed `predicted_cost_tokens` and their basis (`uncalibrated` or `calibrated`), the task's `outcome`, `cause_class`, `spend_class`, `population`, the usage columns (`input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`, `reasoning_tokens`, `tool_uses`, `cost_usd`) and the derived `total_tokens` (derived from the five token components of `headless.usage`, never one of its pointers), each a measured value, `"unmeasured"` (with `not_reported_by_harness` where the harness does not report the field, `output_unparsed` where its output could not be parsed, `terminated` for a run its worker did not finish), or, for a token component the harness's profile declares so, `"not_applicable"`, the server-measured `duration_ms` with its `duration_basis`, and the slot-queue time `queued_ms`): one per fresh worker's job (population `model_job`, the whole run) and one per task a warm worker served (population `model_task`, the turns from the offer to the task's end); worker idle rows (kind `worker_idle`, population `worker_idle`): one per warm worker's job, holding the turns that served no task (its start and its idle wake-ups); one row per wait slice (`phase`, `wait_reason`, `deliberate`, duration; link:../job-runtime.adoc[Job Runtime Specification], Wait Attribution), one row per phase close (`start_time`, `end_time`, `duration_ms`, `duration_clamped`, `boundary` (`closed`, `re_entered`, or `provisional` with `measured_until` and `excluded_steps`), `step_firings` as a map from step id to firing count), and one row per served document read (Served-Content Ledger below). A task that is offered again after a lost attempt yields one task row per attempt that ran, all keyed by its `queue_task_id`; a task closed without an attempt (its role undefined, unqualified, unavailable, or of a class that does not fit, or the task withdrawn before any attempt) yields one task row with every usage column `"unmeasured"` and `cause_class: refused`. A worker's protocol state stays in its job record and is never a row.
* *Consultations*: The usage of a consultation is the row of the consulted role's task, which names the asking task in `consultation_of` (`PM-WORK-4`); it is never added to the asker's row.
* *Continuations*: A row whose usage belongs to a continuation (link:../model-work/06-envelopes-questions-deadlines.adoc#continuation[Model Work Specification, Continuing after a Question], Accounting) carries `continuation` `hold` or `resume`: the wake-ups of a holding generation, or the generation started from a stored session. A task that never continued, and the fallback rows of one that did, carry `null`, so that the two populations are compared per role and harness and no figure is counted twice.
* *Served-Content Ledger*: Every `pm_skill`, `pm_skill_file`, and skill `resources/read` served in a plan, epic, or workspace scope appends `{uri, section?, bytes, plan_id, phase, queue_task_id?, served_at}` to the `metrics.json` of that scope (`plan_id` and `phase` null outside a plan); `bytes` is the rendered size served, `0` for an empty section. Every skill document or section the server renders in-band into a worker's launch prompt or into an offer is recorded the same way, against the offered task. `queue_task_id` is set for a read over a worker's connection while it holds the task and for an in-band rendering, and is otherwise null. A read without a scope is attributed to no plan. `record-metrics` publishes from these rows the per-document consumption (reads per URI and section, bytes, repeat reads within one task). It measures only what the server serves; a harness's own reads of project files are not observable.
* *Populations*: Every token figure carries its `population` stamp: `model_job`, `model_task`, or `worker_idle`. Relations (`=`, `<`, `>`) and sums are formed only between figures of one population. A derived ratio whose denominator population is empty is `not_derivable`, never `0`.
* *Re-Entry*: Re-entry is derived from observables (rows timestamped after the phase's recorded `end_time`), never from a close counter. A re-entered phase is labelled `re_entered` and accumulates across closes.
* *What the Operator Sees*: a plan's completion report takes its section _tokens_ from these rows (the total with its split, per phase, per role, per model and harness, the waste of spend class `no_product`, the retries and remediation per cause class, and the coverage; link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#reports[Runtime & Interaction Model Specification, Reports to the Operator]); an epic's figure sums its plans', the archived ones included, and its own rows.
* *The Runtime's Metrics*: the models' figures of the runtime's metric registry are counted where a task row is written and filled at the runtime's start from the task rows of the metrics stores, which stay the truth, and from the machine's usage aggregate of deleted plans (link:../runtime-lifecycle/03-runtime-metrics.adoc#runtime-metrics[Runtime Lifecycle Specification, The Runtime's Metrics]); a metric's name is distinct from every name of this store. Before the cleanup deletes a plan's rows, what the plan used is added to that aggregate (link:../timeouts/03-retention-host-config.adoc#cleanup[Timeouts & Budgets Specification, One Cleanup]).
* *Cause Classes*: `cause_class` (`terminal_error`, `retryable`, `returned_with_findings`, `benign`, `stall`, `refused`) is a total function over the task's outcome and its worker's fate (link:../model-work/09-completion-usage-and-spend.adoc#cause-class[Model Work Specification, Cause Classes]): every task closed without an attempt is `refused`, and a task closed `asked` or `infeasible` with its record is `benign`; the server observes every end of a worker, so no unconfirmed class exists. The per-class populations sum to the total task population with an asserted residual of `0`; the build-time exhaustiveness check (`PM-IMPL-5`) fails on an unclassified member. A spend decomposition sums to the phase total, with an explicit `unbucketed` class.
* *Spend Classes*: `spend_class` (`submitted`, `findings_only`, `no_product`, `unmeasured`) is derived by the server from what the task produced (link:../model-work/09-completion-usage-and-spend.adoc#spend-accounting-budget-anchors[Model Work Specification, Spend Accounting]); it is a separate dimension from `outcome` and `cause_class`, and waste is read only from `no_product`.
* *Stall Rate*: An envelope task that ends with `tasks_remaining > 0` and no blocked cause is `stall`. The stall rate and the `yield_reason` counts (`chain_tail`, `question`, `context`, `off_track`) are published per plan.
* *Ledger Divergence*: Where two ledgers can diverge (task rows vs queue task records and audit rows), `record-metrics` publishes `union_rows` and a non-blocking `reconciliation{findings_count}` warning. Each ledger states its counting unit.
* *One Writer per Name*: Every metric name has exactly one writer. A second producer over another population uses a different name.
* *Raw Components Only*: Rows persist the reported token components, their plain sum `total_tokens`, and the harness-reported `cost_usd`, never a weighted or priced figure of the server's own. `priced_units` is the internal figure of the migration trigger _Priced units_, derived from the rows and one named constant table (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#migration-trigger-evaluation[Phase Workflows Specification, Migration Trigger Evaluation]) and never shown; a change of the weights re-derives it from the persisted components, the stored baselines included.
* *The Open Phase*: a phase is recorded here once it closed (`phase_close`); when the plan's current phase began is `phase_entered_at` of its `mcp/status.json` (xref:02-workflow-state-store.adoc#phase-start[The Start of the Current Phase]).

Aggregates are never persisted; they are derived in views from `rows[]`.

[#quality-report]
== Quality Report Record (`quality-report.json`)

The plan's `quality-report.json` is written once per firing of `default:plan-retrospective` (`995`) by the server's report engine (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#post-run-quality-report[Phase Workflows Specification, Post-Run Quality Report]). It is derived only from persisted plan stores and from the metrics snapshot composed from them at the report's call (labelled `measured_until`); no model-authored text enters it. A re-fire replaces it atomically, and the store is covered by the digest sidecar (xref:13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification Against Out-of-Band Edits]).

* *Counts with Populations*: Every published count is a `count` object; a rate is published as numerator and denominator counts, never as a bare ratio. An empty population renders `unmeasurable`; `withheld`, `unmeasured`, and `0` are distinct values. A plan or store the engine cannot read contributes `floor` (a lower bound, never healthy).
* *Report Instruments Never Gate*: `gates_merge` is `false` for every instrument (schema constant); the report is written after the merge and no step reads it as a precondition.
* *One Schema for Both Modes*: A corpus report has exactly this schema; it is a fold over the per-plan results of the same engine.
