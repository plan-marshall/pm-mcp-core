[#task-queue]
== Task Queue (`<PM_MCP_BASE>/projects/<project_id>/queue/`)

Every piece of model work of a project is a queue task, persisted in the project's task queue until a worker of its role has served it (`PM-WORK-2`). The protocol that moves a task (offer, acknowledgement, execution, consultation, submit, fencing) is specified in link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]; this part holds its records. The queue directory holds one queue task record per task (<<queue-task-record>>); the activity of a task's worker is journaled in the plan's store (<<activity-journal>>).

* *One Queue per Project*: Tasks of every scope of the project (plans, epics, the workspace scope and the entries it hosts) share the queue, ordered per role: consultation tasks first, then work tasks in creation order (link:../model-work/02-task-protocol.adoc#queue-task[Model Work Specification, Queue Task]). The queue is per project because a worker serves one project (its job record's scope is `project`, xref:10-job-and-lesson-records.adoc#job-record[Job Record]). The tasks of the machine scope, which has no project, are kept the same way in the machine's own queue `<PM_MCP_BASE>/machine/queue/`, under its own queue lock (link:../workflow-dsl/01-grammar.adoc#machine-scope[Workflow DSL Specification, Machine Scope]).
* *Lock and Write*: Every write runs under the queue lock `locks/queue.lock` (xref:13-leases-integrity-testing.adoc#lock-free-snapshot-reads[Lock-Free Snapshot Reads, Transaction Locks & Leases (`PM-IMPL-7`)]) as an atomic write-and-rename of the one record it changes (xref:01-format-and-session-log.adoc#format-versioning[Format Versioning & Atomic Write Discipline]). A transition that creates or settles a task holds its scope lock and takes the queue lock after it; the offer, the acknowledgement, the consultation, and the fence take the queue lock alone. Queue records are not part of a scope's transaction journal and not covered by a digest sidecar, like the job records.
* *Two Authorities*: The scope store is authoritative for which tasks a model state owns and for how they ended (`active_tasks` of xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store (`mcp/status.json`)]); the queue task record is authoritative for the delivery (lease, attempts, consultations). A creating transition writes `active_tasks` first and the queue record after it; a settling transition records the outcome in the scope and then closes the queue record.
* *Recovery*: The project's recovery after a runtime start records every running worker `killed` and fences its generation (xref:10-job-and-lesson-records.adoc#job-record[Job Record]), then reconciles the queue: a held task's current attempt ends with `end: restart`, its lease is released, and the task is queued again without counting a re-offer; a task its scope lists closed is closed with the scope's outcome; a task its scope no longer lists is closed `lost` (reason `withdrawn`) without a re-offer; a task the scope lists without a queue record is created again `queued`. Each reconciliation appends one audit record.
* *Removal*: A closed queue task record that its scope no longer lists is technical residue: the periodic sweep removes it after `retention.task_records_days` (link:../timeouts/03-retention-harness-config.adoc#cleanup[Timeouts & Budgets Specification, One Cleanup]). Usage is never kept here: every task's usage is a metrics row of its scope keyed by its `queue_task_id` (xref:05-metrics-and-quality-report.adoc#metrics-store[Metrics Store (`metrics.json`)]).

[#queue-task-record]
=== Queue Task Record (`queue/<queue_task_id>.json`)

One record per task. A `job llm <entity_kind> role <role> [each <primitive>]` state creates one per entity in the transaction that enters it (kind `work`); a `consult:<role>` link creates one for the consulted role (kind `consultation`, whose `queue_task_id` is the `consultation_id`, link:../model-work/05-consultation.adoc[Model Work Specification, Consultation]). The semantics of every field are those of link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]; this section fixes the record.

* *Status*: `queued` (waiting for a generation of its role started with the role's current configuration digest; matching: link:../model-work/02-task-protocol.adoc#offer[Model Work Specification, Offer]; a task of a paused plan stays `queued` and is not offered until the operator starts the plan again), `offered` (leased, not yet acknowledged), `executing` (from the acknowledgement on, recorded as `lease.acknowledged_at`), `consulting` (an own consultation is open), `awaiting_answer` (its generation holds it for the answer to its question), `suspended` (no lease; the asking worker ended with its session stored, link:../model-work/06-envelopes-questions-deadlines.adoc#continuation[Model Work Specification, Continuing after a Question]), `closed`. An attempt that ends without a result returns the task to `queued`, released at once, and the task is offered again within its re-offer budget (link:../timeouts/01-job-budgets-and-waits.adoc#task-reoffer-budget[Timeouts & Budgets Specification, Task Re-Offer Budget]).
* *Outcome and Reason*: A closed task has exactly one of the outcomes `submitted`, `asked` (with its `question_id`), `infeasible`, or `lost`; a `lost` task names its `reason`: `attempts_spent` (its re-offers are spent), `role_undefined`, `class_mismatch`, `role_unqualified`, or `role_unavailable` (the model caller closed it before any attempt), `deadline_expired` (a vote task still open at the vote wait's expiry, link:../model-work/10-decision-quorum.adoc#adjudication[Model Work Specification, The Adjudication]), or `withdrawn` (its state or scope ended while the task was open). `form_downgraded` records that the caller ran a `warm` role `fresh` because only the fresh form qualifies.
* *Lease*: `lease` names the generation the task is leased to, set in the transaction of the offer (for a fresh worker: at its spawn) and cleared at the submit that closes the attempt, at the fence of the generation, and when the operator pauses the plan now. Every call on the task entity is checked against it.
* *Attempts*: One entry per offer, with its generation, its worker, the configuration digest the worker was started with, its instants, and how it ended. `counts` is `false` for an attempt ended by a restart, a drain, a start failure of a fresh worker, or the operator's pause of the plan now (link:../runtime-lifecycle/02-plan-pause-and-stalled-plans.adoc#plan-pause[Runtime Lifecycle Specification, Pausing and Starting a Plan]), which spend no re-offer; an attempt ended by the server's `restart` of a worker off track counts.
* *Continuation*: A task that asked and continues records it in `continuation` (`null` otherwise): the `question_id`, the `form` in force (`hold` or `resume`), when the hold ends (`hold_until`), the stored session (`session_id`, `suspended_at`, `resume_until`, the configuration digest and the worktree head at the suspension), and, where it fell back, `fallback_reason` (`not_allowed`, `hold_expired`, `resume_expired`, `session_missing`, `configuration_changed`, `harness_changed`, `worktree_moved`, `resume_unacknowledged`). The attempt of a suspended worker ends `suspended` and spends no re-offer; the resumed generation's offer is a new attempt.
* *Off-Track Signals*: every signal the runtime raised on the task's worker and the action it took (`show`, `nudge`, `yield`, `restart`) are listed in `signals[]` with the attempt, the measurement, and when (link:../model-work/03-supervision-and-recycling.adoc#worker-off-track[Model Work Specification, A Worker Off Track]); the same entry is written to the task's activity journal (<<activity-journal>>). A `yield` closes the attempt as the worker's own yield of its envelope would; a `restart` ends the attempt with `end: off_track`.
* *Consultations*: The asking task lists its consultations in `consultations[]` (their limits: link:../model-work/05-consultation.adoc[Model Work Specification, Consultation]); the consultation task names its asker in `consultation_of`. The answer is recorded on the asker's entry when the consultation closes and delivered once, to the asking generation's next wait, or to the successor in the task's facts after a fence (`delivered_to`).

[#activity-journal]
=== Activity Journal (`tasks/activity/<queue_task_id>.jsonl`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WORK-7[PM-WORK-7: Worker Activity & Off-Track Signals]_

What a worker does while it serves a task, one entry per activity, in an append-only journal per task in the store of the task's scope: `plans/<plan_id>/tasks/activity/<queue_task_id>.jsonl`, and the same below `epics/<epic_id>/`, `workspace/`, and the machine scope. The runtime maps each line of the worker's output stream onto one harness-neutral kind through the `headless.events` pointers of the harness's harness profile and adds what it knows itself (link:../harness-profiles/01-profile-schema.adoc#worker-activity[Harness Profiles Specification, What a Worker Does]); the off-track signals are computed from the journal (link:../model-work/03-supervision-and-recycling.adoc#worker-off-track[Model Work Specification, A Worker Off Track]).

* *Written while the worker runs*: the runtime appends each entry as its line arrives, under the journal's own leaf lock taken on the file (like the plan mailbox's), outside the scope's transaction journal and digest sidecar, like a job log; a torn last line is ignored by a reader and repaired by the next writer (xref:01-format-and-session-log.adoc#format-versioning[Format Versioning & Atomic Write Discipline], item 6). Every text and target is masked like every job log before it is written (link:../job-runtime/01-pipeline-and-subprocesses.adoc[Job Runtime Specification]).
* *Harness and server entries*: the harness's kinds are `text` (what the model wrote, cut to the compiled bound of 2,000 characters), `tool_call` (the tool's name and its target: a path, a command line, a server link with its id, never its whole arguments), `tool_result` (its size and whether it failed, never its content), `file_changed` (a path of the worktree), and `turn` (its usage, from the usage pointers, and its stop reason where the profile maps one). The server's kinds are `link` (a link of the task the worker followed: `ack`, `submit`, `ask`, `consult`, `yield`, `infeasible`), `question` (a question the worker asked), `answer_ack` (its acknowledgement of an answer), `signal` (an off-track signal with the action taken), and `attempt_end` (how the attempt ended, with the count of the output lines that matched no mapping, which are counted and never shown). A harness whose profile declares `headless.events: null` has only server entries.
* *Bounded per task*: a journal holds at most the compiled bound of 5,000 entries; an append beyond it rewrites the journal without its oldest `text` entries, never a server entry, by an atomic write-and-rename under the same leaf lock. `seq` is never reused, so a client's cursor stays valid and a gap in `seq` shows what gave way.
* *Untrusted*: a text or a target may come from the project, a review comment, or a tool result: the clients show it as plain text, never as markup or a link they follow, and no model reads the journal as instructions (`PM-SEC-1`).
* *Served to both clients*: the entries from a cursor and a live stream that a client opens only while it shows the task (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#process-resource[Runtime & Interaction Model Specification, The Plan's Process as a Structure]).
* *Kept with the plan*: the journal is archived with its plan and deleted with it, by `delete-plan` or by the cleanup (link:../timeouts/03-retention-harness-config.adoc#cleanup[Timeouts & Budgets Specification, One Cleanup]); an epic's go with its machine store.

[#qualification-record]
== Role Qualification Record (`<set>/qualification/<role>.json`)

The record of one grading of a role's configuration by the operator's grading in either client (`pm-operator roles qualify` in the terminal client) or the setup run's `setup.qualify-roles`, behind its consent to the model cost (`PM-WORK-6`; grading, validity, and invalidation: link:../model-work/01-roles-and-configuration.adoc#qualification[Model Work Specification, Role Qualification]). Every record the operator makes lies in the project role set (`<PM_MCP_BASE>/projects/<project_id>/roles/qualification/<role>.json`), whichever set holds the role's effective artifact; the shipped set carries the release's records, and the machine set holds none (lookup: project set first, then the set of the artifact; paths: link:../filesystem-layout/03-project-store.adoc#role-sets[Filesystem Layout Specification, Role Sets & Task Queue]). Written only by the runtime, by atomic write-and-rename; a new grading replaces the record. The record holds the measurements only and no pass flag: whether it qualifies a form is evaluated at every check against the project's current levels (`qualification.agreement_level`, `qualification.allowed_gap`, operator configuration, xref:08-project-configuration-local.adoc#local-config[Operator Local Configuration]). A record with an ungraded item (its judge task closed `lost`) qualifies no form; the next grading re-grades only those items while `qualification_digest` and `corpus_revision` are unchanged. A record graded on a partial corpus, one whose import of the corpus sources missed a source that did not answer or is absent at its pin, names the missed sources in `missed_sources` beside `corpus_revision`; the list is empty for a complete corpus (link:../model-work/01-roles-and-configuration.adoc#corpus-sources[Model Work Specification, Corpus Sources]). No record is graded on a failed import.

[#decision-calibration-record]
=== Decision Calibration Record (`qualification/decisions/<declaration-digest>.json`)

The record of one calibration of a quorum declaration by the operator's calibration in either client (`pm-operator roles qualify --decisions` in the terminal client) or the setup run's role grading (`PM-WORK-6`; run, measurements, and validity: link:../model-work/10-decision-quorum.adoc#quorum-calibration[Model Work Specification, Quorum Calibration]), one file per declaration digest, so identical declarations of the project's adjudication unit and of the binary's default unit share one record. It lies in the project role set (`<PM_MCP_BASE>/projects/<project_id>/roles/qualification/decisions/<declaration-digest>.json`); the shipped set carries the release's records for the quorum declarations of the default unit (`classpath:/roles/qualification/decisions/<declaration-digest>.json`). Adjudication reads the record of the declaration's digest from the project set, else from the shipped set. The subdirectory keeps the records apart from the role qualification records `qualification/<role>.json`. Written only by the runtime, by atomic write-and-rename; a new calibration of the declaration replaces the record. It holds measurements and no pass flag: whether the declaration decides is evaluated at every check against the declaration `max_false_auto_percent` of the unit whose declaration applies.
