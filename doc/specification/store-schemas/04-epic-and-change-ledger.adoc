[#epic-inbox-record]
== Epic Inbox & Plan Mailbox Records (`inbox.jsonl`, `mcp/mailbox.jsonl`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-32[PM-WATCH-STORE-32]_

The epic inbox (`.marshall/epics/<epic_id>/inbox.jsonl`, plan → epic and epic → epic) and the plan mailbox (`mcp/mailbox.jsonl` in the plan directory, epic → plan) share one record model: a strictly append-only event log. No line is ever rewritten or deleted; a message's current state is the fold of its events (link:../model-work.adoc[Model Work Specification], Git-Distributed Epic Ledger and Plan Mailbox).

The schema is the file `pm-core/src/main/resources/de/planmarshall/core/store/message-event.schema.json`.

* *Store-Assigned Identity*: The store allocates `message_id` as the next number above the highest ever written in that file, including ids of lines it cannot parse; an id is never reused, and a caller never supplies one. A `claimed`, `processed`, `consumed`, or `annotation` event for an unknown or already-folded-terminal message is refused.
* *Fold*: Inbox messages fold to `pending` (only `message`), `claimed`, or `processed`; mailbox messages fold to `unconsumed` or `consumed`, or `unknown` when a referencing line is unreadable. The empty states (`no_file`, `empty_file`, `all_processed`) and `unreadable` (with the failing line) are distinct and never read as each other.
* *Writers*: Inbox events are appended under the epic lock in the shared epic worktree copy (link:../filesystem-layout/01-repository-workspace.adoc#shared-epic-worktree[Filesystem Layout Specification]). The plan mailbox has its own leaf lock, whose OS lock is taken on the sidecar `mcp/mailbox.jsonl.lock` beside `mcp/mailbox.jsonl`, never on the mailbox itself (like the audit log's on `logs/audit.jsonl.lock`; xref:13-leases-integrity-testing.adoc#lock-free-snapshot-reads[Lock-Free Snapshot Reads, Transaction Locks & Leases (`PM-IMPL-7`)]): the epic's transaction holds the epic lock, then takes the mailbox leaf lock, reads the last `message_id`, and appends one line; the plan's `consumed` events are appended under the same leaf lock. The plan directory never moves except on archival, when it carries the mailbox with it. The mailbox is advisory content and is not covered by the plan's store digests; a reader ignores a torn last line (the next writer repairs it, xref:01-format-and-session-log.adoc#format-versioning[Format Versioning & Atomic Write Discipline], item 6). The git-tracked inbox is protected by its git history.
* *The Operator's Acts*: every operator act on a plan whose `origin.epic_id` names a live epic appends its message in the transaction of the act, its sender the plan; the epic's `coordinate` task decides on it as on every message (link:../model-work/08-epic-coordination.adoc#epic-informed[Model Work Specification, The Epic Is Told]). A plan's outcome `released` appends nothing: the release of a project ends its epics with their plans and never writes a ledger.
* *Read Scope*: Inbox and mailbox resources are readable by every scope of their project (`PM-SEC-2` is the boundary); a representation points each scope at its own messages (the epic at its inbox, a plan at its own inbox messages and its mailbox).

[#epic-ledger-records]
== Epic Ledger Records (`epic.json`, `queue/<plan_id>.json`, `landings.jsonl`, `register.jsonl`)

The git-tracked epic ledger `.marshall/epics/<epic_id>/` (link:../model-work/08-epic-coordination.adoc#git-distributed-epic-ledger[Model Work Specification, Git-Distributed Epic Ledger]) holds, beside the inbox (<<epic-inbox-record>>), the Markdown documents `spec.md` and `resume_anchor.md`, and the epic's source directory `sources/` (moved in from its entry at the epic's creation and never changed, xref:01-format-and-session-log.adoc#pending-entry-record[Pending Entry]; link:../filesystem-layout/03-project-store.adoc#source-directory[Filesystem Layout Specification, The Source Directory]), four JSON stores. All are written only by the server, under the epic lock, in the shared epic worktree (link:../filesystem-layout/01-repository-workspace.adoc#shared-epic-worktree[Filesystem Layout Specification]); their integrity is their git history. The epic's FSM state is not part of the ledger: it lives in `epics/<epic_id>/status.json` of the per-project machine store (xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store (`mcp/status.json`)]), and so do the transcripts of the chats about the epic (`epics/<epic_id>/chat/`) and its decomposition draft while it awaits the operator; no ledger holds a transcript.

[#epic-header]
=== Epic Header (`epic.json`)

The epic's identity and descriptive header. It carries no FSM state and no queue content. It is created by the `start.create-scope` transaction of the epic bootstrap (`bootstrap-epic`) from the title of `start-epic.ready`, the epic's sources, and the project's values of `epic.parallelization_scope`, `epic.auto_start`, and `epic.overlap_max_files` (machine defaults `1`, `true`, and `0`; xref:08-project-configuration-local.adoc#local-config[Operator Local Configuration]), none of which is asked at the start; adopting an existing ledger without machine scope (`start-epic.adopt`) only reads and validates it and never rewrites the header or a row; `workstreams` starts empty and is written when the operator agrees a decomposition draft (link:../model-work/08-epic-coordination.adoc#decomposition-review[Model Work Specification, The Decomposition Is Reviewed]). The operator changes `parallelization_scope` (through _Next plan_ or the epic's settings), `auto_start` (the epic's action _Automatic: on/off_), and `overlap_max_files` (the epic's settings) at any time; each change is a ledger write of the header, landed like every ledger write, told in the epic's events, and an `operator_action` that re-enters `epic.next-work` (link:../model-work/08-epic-coordination.adoc#epic-auto[Model Work Specification, An Epic Runs by Itself]).

[#epic-queue-row]
=== Queue Row (`queue/<plan_id>.json`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-53[PM-WATCH-STORE-53], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-54[PM-WATCH-STORE-54], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-55[PM-WATCH-STORE-55]_

One file per staged plan, created with `CREATE_NEW` and updated row-locally; the closed status vocabulary, the mapping of plan outcomes onto it, and the transfer rules are defined in link:../model-work/08-epic-coordination.adoc#git-distributed-epic-ledger[Model Work Specification, Git-Distributed Epic Ledger]. The row follows its plan's state: `pausing` and `paused` while the operator pauses it, `cancelled` when the operator cancels it, `abandoned` when the operator abandons it paused; a plan's outcome `released` changes no row (link:../model-work/08-epic-coordination.adoc#epic-informed[Model Work Specification, The Epic Is Told]).

* *What a Row Waits For* is derived on read and never stored: `dependency` (a prerequisite has not shipped), `lock`, `scope` (the epic's `parallelization_scope` is full), or `overlap` (its declared surface shares more than the header's `overlap_max_files` files with a running plan's declared surface or realized changes; it names that plan and holds until that plan has ended), each shown since the row's `updated_at` (its last write), so that no time of its own is recorded for a wait; the epic's resource serves it (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#epic-resource[Runtime & Interaction Model Specification, The Epic as a Resource]).
* *A Pausing or Paused Row Keeps Its Place*: it counts toward `parallelization_scope` like a `running` one.
* *A Row Staged from a Chat*: a row the operator accepted in the epic's chat records `origin: {kind: chat, chat_id, turn_id}` beside the operator's channel and device (link:../state-catalogue.adoc#chat-origin[State Catalogue, Origin]).

The schema is the file `pm-core/src/main/resources/de/planmarshall/core/store/queue-row.schema.json`.

[#epic-registers]
=== Findings and Watches Registers (`register.jsonl`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-15[PM-WF-15: Epic Creation, Server-Started Plans & Cross-Plan Merge Mutex]_

The epic keeps two registers in its ledger, in one versioned JSONL store `register.jsonl` (xref:01-format-and-session-log.adoc#format-versioning[Format Versioning & Atomic Write Discipline], item 6): *findings*, a problem no plan owns yet, to be fixed, and *watches*, an observation to check again when its trigger fires (link:../model-work/08-epic-coordination.adoc#findings-watches[Model Work Specification, An Epic's Findings and Watches]). Every change of an item appends its full record again; the current record of an item is the last readable line with its `item_id`. Keeping an item keeps it as a finding or moves it to the watches by a new record with the other `register`.

* *Writers*: the server, from the submits of the epic's tasks (`epic.analyze-landing`, `coordinate`, the re-check of a watch whose trigger fired) and from the operator's dispositions in the epic's review, under the epic lock in the shared epic worktree, committed and landed like every ledger write. No plan writes the registers.
* *Identity*: the store allocates `item_id` as the next number above the highest ever written in the file, like `message_id`; it is never reused.
* *New findings*: a finding in the state `open` is an item not decided yet; the epic's `needs_operator` summary counts the open findings as its kind `findings` (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#needs-operator[Runtime & Interaction Model Specification, What Needs the Operator]).
* *The archive*: only an `open` finding holds the epic's archive; kept findings and the watches go into the archive with the epic, and the archive check lists them as carried (link:../model-work/08-epic-coordination.adoc#epic-actions[Model Work Specification, An Epic's Actions]).

[#kept-landing-envelope]
=== Kept Landing Envelope (`landing-envelope.json`)

When `emit-landing` cannot deliver the landing envelope (`landing_delivery: pending`, xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store]), because the plan's epic linkage is `indeterminate` or because the append retry budget was spent while the linkage is `orchestrated`, the server keeps the undelivered envelope in the plan directory as `plans/<plan_id>/landing-envelope.json`: `{format_version, envelope}` with `envelope` of the landing schema (`landing-envelope.json#`, link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#_landing_envelope_emit_landing[Phase Workflows Specification, Landing Envelope]). A late finding carried out while the envelope is kept (xref:03-findings-and-review-records.adoc#_findings_ledger_record_findings_jsonl[Findings Ledger Record], Late Findings Are Carried Out) is appended to the envelope's carried messages by a replace of this file. The file is written only by the server under the plan lock, is covered by the plan's digest sidecar, is never deleted (it stays in the plan directory and travels with it into the archive), and is delivered unchanged by the epic's landing reconciliation, which skips an envelope whose `plan_id` `landings.jsonl` already records; it is never re-rendered from the plan's records. A plan whose linkage is `not_orchestrated` or `detached` emits no landing to an inbox and keeps no envelope.

[#epic-drafts]
== Epic Drafts (`epics/<epic_id>/decomposition.json`, `epics/<epic_id>/review.json`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-15[PM-WF-15: Epic Creation, Server-Started Plans & Cross-Plan Merge Mutex]_

An open decomposition and an open review of an epic's registers keep what is not committed yet in the epic's machine store, never in its ledger (link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]), so leaving and a restart of the runtime resume them where they stopped, in either client. Each is one JSON file replaced by the epic scope's transaction and covered by the scope's digest sidecar; it exists only while its sub-workflow runs and is deleted in the transaction that writes its result to the ledger (link:../model-work/08-epic-coordination.adoc#decomposition-review[Model Work Specification, The Decomposition Is Reviewed], link:../model-work/08-epic-coordination.adoc#epic-review[The Review]). The server's checks are computed on read and never stored. A change of the draft, and an item's disposition or rewrite, that the operator accepted in a chat records `origin: {kind: chat, chat_id, turn_id}` beside the operator's channel and device, in the draft and, through `review.commit` and the decomposition's commit, on the committed row as its `origin` and on the committed register item as the origin of that change (`disposition_origin`), never replacing the item's own origin (link:../state-catalogue.adoc#chat-origin[State Catalogue, Origin]).

== Change Ledger Record (`change-ledger.jsonl`)
_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-13[PM-WATCH-JOB-13], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-9[PM-WATCH-STORE-9], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-10[PM-WATCH-STORE-10]_

* *Per-Task Attribution*: `kind: "task_diff"` rows are appended by the server when `submit:TASK-NNN` passes independent verification (link:../phase-workflows.adoc[Phase Workflows Specification], Task Envelope Execution): `task_id`, `changed_paths` since the previous task's snapshot (present, possibly empty), and `commit_sha: null`. They are the only producer of `task_id` in this ledger.
* *Baseline-Red Rows*: A `baseline_red` row is written by the server only, in the transaction that proves a red gate baseline-only (every failing fingerprint present on the base); it is bound to its `worktree_sha`, merge base, and diagnostics digest. A freshness gate accepts it as passing for the same `worktree_sha` (and hash version) only, never for another tree, so the exit barrier does not reject the same tree as `last_build_failed`. The gate step completes `done` with `assurance_verdict: degraded`, and the PR body and the landing record list the baseline failures. A red gate that is not provably baseline-only never produces the row; it calls the build or CI remediation policy.
* *Attribution State*: Every per-task consumer first reads `change_attribution`, which the server derives: `measured` when every completed task has a `task_diff` row, otherwise `unavailable` (for example when a task snapshot could not be taken). Under `unavailable` the dependent per-task keys are absent, never empty or zero.
