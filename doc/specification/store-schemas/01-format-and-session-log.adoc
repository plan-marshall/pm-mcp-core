[#format-versioning]
== Format Versioning & Atomic Write Discipline
_Implementation watch: link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-17[PM-WATCH-GEN-17], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-25[PM-WATCH-STORE-25], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-37[PM-WATCH-STORE-37]_

[[_format_versioning_atomic_write_discipline]]
1. *Version Envelope*: Every persisted JSON root object and every JSONL header/record must declare `"format_version": 1` (positive integer, one sequence per file kind): the server-owned stores, the git-tracked team configuration files `.marshall/config/*.json` (xref:07-project-configuration.adoc#project-configuration-store[Project Configuration (`.marshall/config/`, `local-config.json`, Effective Configuration; `PM-EXT-6`, `PM-EXT-7`)]), and the operator files (`local-config.json`, `machine-config.json`, the project enrolments, the harness enrolment `harnesses.json`, credential files). A workflow unit (`*.pmwf`) declares its DSL format in its header (`workflow <id> version <n> format <f>`, link:../workflow-dsl/01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification]). Exempt are Markdown documents (checked by their parsers), plain-text logs, OS primitives, and the raw HMAC key.
+
*Accept exactly one, refuse, never rewrite*: Before 1.0 a binary accepts exactly the current `format_version` of each file kind; there is no migration chain and no startup migration. Beside the results of item 4 (a missing `format_version` is `unreadable`), a reader returns `format_outdated{file, found, current}` or `format_newer{file, found, current}`; no reader tolerates an older shape. An outdated or newer file is never modified by a reader: a scope store raises the `precondition_unmet` condition on its scope (reason `format_outdated` or `format_newer`), shown to the operator in both clients as a hold of kind `condition` with its acts (link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue, Holds and Their Acts]); a team configuration file or workflow unit refuses every scope creation of a bootstrap (re-checked in the bootstrap's `start.create-scope` transaction) and every phase handshake of the project with `format_outdated` or `format_newer` naming the file (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/04-errors-and-testing.adoc#rejection-reasons[MCP Tools Specification, Closed Rejection Reasons]); an operator file is refused naming the file and the changed keys, and the refusal reaches both clients of the operator. *Upgrade path*: a `format_version` bump is listed with the changed keys in the release notes; a live scope keeps the store format of the binary that runs it, so the operator finishes the live scopes before an upgrade that changes a format, and the upgrade of the runtime drains its live work first (link:../runtime-lifecycle/01-startup-recovery-drain.adoc#runtime-lifecycle-operations[Runtime Lifecycle Specification, The Runtime's Lifecycle]); a later run of the project's setup offers the new binary's default changes for the files the project holds as its own (a diff for a workflow unit of the project, a server-rendered rewrite for a JSON configuration file, link:../domain-extensions/06-configuration.adoc#config-upgrades[Domain Extensions Specification, Configuration Upgrades]). The migration mechanism for 1.0 and later is decided at 1.0.
2. *Atomic Write-and-Rename*: All JSON file updates are written to a sibling temporary file (`<filename>.tmp.<uuid>`), flushed to disk (`FileChannel.force(true)`), and atomically renamed over the target file (`StandardCopyOption.ATOMIC_MOVE`, `StandardCopyOption.REPLACE_EXISTING`); the parent directory is then forced to disk as well (`FileChannel.force(true)` on the directory), so that the rename itself survives a crash. A store replaced this way is guarded by a sibling lock file, never by a lock on the store file itself (xref:13-leases-integrity-testing.adoc#lock-free-snapshot-reads[Lock-Free Snapshot Reads, Transaction Locks & Leases (`PM-IMPL-7`)]). Every write to a plan, epic, or workspace store runs as a journaled transaction (<<transaction-journal>>).
3. *Single Writer Set*: Every writer of a `PM-MCP` store runs inside the one `PM-MCP` runtime and serializes through its own locks. Legacy `plan-marshall` never touches `.marshall/` or `<PM_MCP_BASE>`, and `PM-MCP` never writes `.plan/` or `~/.plan-marshall/` (`PM-MIG-2`), so no store is shared and no cross-runtime lock protocol exists.
4. *Absent vs Unparseable*: Every store and document reader returns one of `absent`, `empty`, `parsed`, or `unreadable` (with the failing line or offset), and a reader of a versioned file also `format_outdated` or `format_newer` (item 1). An input that yields no parsable content is `unreadable`, never an empty record and never `absent`. A JSONL record that is refused, because it is unreadable or declares another `format_version`, is reported with its line number. Consumers handle `unreadable` explicitly: they fail closed or report `indeterminate`.
5. *One Wire Shape per Instant*: Every persisted or exchanged instant is an RFC 3339 UTC string (`"format": "date-time"`, `Z` suffix); epoch numbers are never persisted. A process start instant is taken from the OS (`ProcessHandle.Info.startInstant()`) and stored in the same shape. Durations are integers whose field name carries the unit (`duration_ms`, `*_seconds`).
6. *JSONL Append Discipline*: A JSONL store of a plan, epic, or workspace scope is appended to through the scope's transaction under the scope lock; `audit.jsonl` under the audit lock, a plan's `mcp/mailbox.jsonl` under its mailbox leaf lock (xref:04-epic-and-change-ledger.adoc#epic-inbox-record[Epic Inbox & Plan Mailbox Records (`inbox.jsonl`, `mcp/mailbox.jsonl`)]), a task's activity journal under its own leaf lock outside the scope's transaction (xref:16-task-queue.adoc#activity-journal[Activity Journal]), and the machine journals `state/reports.jsonl`, `state/cleanup.jsonl`, and `state/usage-aggregate.jsonl` under their own leaf locks (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#reports[Runtime & Interaction Model Specification, Reports to the Operator], link:../timeouts/03-retention-harness-config.adoc#cleanup[Timeouts & Budgets Specification, One Cleanup], xref:12-machine-stores.adoc#usage-aggregate[Usage aggregate]). No JSONL store is ever rewritten, except by three rewrites, each under the store's lock: the periodic sweep's removal of the workspace scope's technical rows (xref:13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Evidence-Based Removal Sweeps]), the cleanup's deletion of the read reports of `state/reports.jsonl`, and the bound of a task's activity journal (xref:16-task-queue.adoc#activity-journal[Activity Journal]). A *versioned* JSONL store, whose records change (`findings.jsonl` keyed by `finding_id`, `review-participation.jsonl` keyed by `(pr_number, round, bot_kind)`, xref:03-findings-and-review-records.adoc#_findings_ledger_record_findings_jsonl[Findings Ledger Record]), appends the full record again at every change: the current record of a key is the last readable line with that key, and the earlier lines are its history. In `audit.jsonl` a torn tail lies after the anchored head (`audit.head` is updated only after a complete append), so the repair never touches a chained record.

[#transaction-journal]
=== Transaction Journal (`mcp/transaction-journal.json`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-2[PM-WATCH-STORE-2], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-44[PM-WATCH-STORE-44], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-47[PM-WATCH-STORE-47]_

Every write to the server-owned stores of a plan, epic, or workspace scope, and to the project's lesson store, runs as one transaction under the lock of its scope through the scope's transaction journal. A target replaces a store, appends to a JSONL store, or deletes a store. The path base of a scope also names a store in `pm-operator accept-edit`. When the recovery reports an invariant violation (a target that has neither its new digest nor its staged file), its caller raises the `integrity_breach` condition (kind `store_tampered`) for the violating stores (xref:13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification Against Out-of-Band Edits]).

*Audit delivery*: The audit record of a completed store mutation (`transaction_rolled_forward`, `jsonl_tail_repaired`, `cross_scope_reconciled`) is delivered at least once and never lost. A durable intent holds it from before the mutation that removes its cause until the audit sink accepted it (the journal for a roll-forward and for the records a transaction owes, the intent file `<store>.audit-intent` for a tail repair), and the next recovery of the scope or repair of the store replays it. Every such record carries a `transaction_id` of its own (a transaction that owes several records gives each its own identifier; a roll-forward record carries that of its journal), by which the audit log store, when it appends, and every reader drop a duplicate (xref:12-machine-stores.adoc#audit-log[Security & Transition Audit Log]). A sink that refuses a record never fails or undoes the data outcome of the mutation.

*Writes outside the scope*: A transition that also writes outside its scope (another scope, the lesson store, the job records, the task queue) never extends its journal. It writes in a fixed order, the authoritative store first, each further write as a transaction of its own store under that store's lock, and the runtime's startup recovery derives every later write from the authoritative store (link:../runtime-lifecycle/01-startup-recovery-drain.adoc#per-project-recovery[Runtime Lifecycle Specification, Per-Project Recovery], cross-scope reconciliation). The orders and recovery rules of the transitions are these:

* *`start.create-scope`*: the new scope (authoritative; a plan's directory is built complete in the sibling temporary directory `plans/.init-<entry_id>/`, with copies of the entry's source directory, transcript, question log, decision log, and grants (<<pending-entry-record>>, Creation), and published by one atomic directory rename to `plans/<plan_id>/`; for a new epic, its git-tracked ledger with a copy of the entry's source directory before its machine scope, so a crash between them leaves a ledger the epic bootstrap adopts), then for a `local_changes` plan the capture ref `refs/pm-mcp/captures/<plan_id>` at the recorded `captured_changes.snapshot_sha` (xref:06-task-and-references.adoc#_references_footprint_store_schema_references_json[References & Footprint Store Schema (`references.json`)]), then the epic queue row (`running`, `started_at`, xref:04-epic-and-change-ledger.adoc#epic-queue-row[Epic Queue Row]), then the lesson claim (xref:10-job-and-lesson-records.adoc#lesson-record[Lesson Record]), then the deletion of the pending entry directory (<<pending-entry-record>>). A plan is live when `plans/<plan_id>/mcp/status.json` exists; every enumeration of live plans lists only such directories. Recovery: a temporary init directory `plans/.init-*` is deleted (no transaction survives a restart); a non-terminal plan whose capture ref is missing gets it re-created at its `snapshot_sha`; a plan with `origin.epic_id` whose epic queue row is still unstarted (`started_at: null`) sets the row `running` with the plan's creation instant as `started_at`; a non-terminal plan created from a lesson whose lesson is unclaimed claims it; a pending entry directory whose plan or epic exists is deleted once the new scope carries the entry id it was created from — today it does not, so a creation cut between the new scope's commit and the workspace's leaves the entry's record in place and a repeated creation is refused by the creates of the new scope's stores, and the operator ends that entry by abandoning it (plan `PLAN-V2-22`, ADR `runtime-start/016`).
* *Job states*: the scope's `active_job` (authoritative for which job a state owns, xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store (`mcp/status.json`)]), then the job record in `jobs/` (authoritative for the job's fate, xref:10-job-and-lesson-records.adoc#job-record[Job Record]). Recovery: an `active_job` that names a job without a record is settled `killed` (the job never started).
* *Worker end*: the job record (fate and terminal worker block; authoritative for the generation; the runner revokes the token once the settlement has recorded the fate, and the supervision pass fences the generation once it reads the settled record), then the queue task record (the held task's attempt ended, its lease released). Recovery: a task leased to a generation whose job record has ended is released and queued again like a task held at a restart (xref:16-task-queue.adoc#task-queue[Task Queue], Recovery).
* *Queue tasks*: `active_tasks` first, then the queue task record (xref:16-task-queue.adoc#task-queue[Task Queue], Two Authorities and Recovery).
* *Plan end*: the plan's terminal transaction (authoritative for its `outcome` and its landing), then the lesson store transaction that retires or releases the plan's claimed lesson by whether the plan landed its changes; which ends retire and which release, and how the recovery settles a claim whose plan is terminal, archived, or no longer resolvable, is owned by xref:10-job-and-lesson-records.adoc#lesson-claim[A Claimed Lesson Ends with the Landing].
* *Late findings*: the carry-out of a blocking finding after the merge (xref:03-findings-and-review-records.adoc#_findings_ledger_record_findings_jsonl[Findings Ledger Record], Late Findings Are Carried Out) writes the destination first (the `process_finding` message under the epic lock, or the seeded lesson under the lesson store lock), because the destination assigns the `ref`; then the plan's transaction sets the finding `carried` with `carried_to`. A message appended to the kept landing envelope is part of the plan's own transaction. Recovery derives nothing: a crash between the two leaves the finding without the status `carried` and without `carried_to` (its `resolution` stays `pending` either way), and the resumed carry-out carries it again; the accepted cost is a duplicate notice of a debt that stays visible, never a lost one.

[#pending-entry-record]
== Pending Entry (`pending/<entry_id>/`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-10[PM-WF-10: Phase 1–4 Planning Invariants, Lane Ratchet & Artifact Gates]_

_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-42[PM-WATCH-STORE-42]_

A start of a plan or an epic is an *entry* until its scope exists (link:../state-catalogue/09-bootstrap-and-lessons.adoc#start-from-clients[State Catalogue, Starting from the Clients]). The operator opens one in either client (`POST /api/v1/projects/{project_id}/entries` with the kind `plan` or `epic`), and the server opens one itself for a plan it starts for a launchable epic row. An entry is the directory `pending/<entry_id>/` of the per-project machine store, whose files are listed there (link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]); its record `entry.json` holds the entry's kind and the state of its bootstrap (schema below).

The requirements of the entry are these, and the store, its transactions and its per-entry integrity hold are
implemented by `PendingEntryStore` of `core.store`
(link:../../../pm-core/doc/developer/core-store.adoc#_the_pending_entry[Scope Stores Developer Guide § The Pending
Entry], ADR `core-store/082`):

* The directory, its record, an empty source directory with its manifest, its question and decision stores, and its
  transcript are created in one transaction of the workspace scope when the entry is opened; every bootstrap transition
  replaces the record, and the sources are files of the source directory with their entries in the manifest
  (link:../filesystem-layout/03-project-store.adoc#source-directory[Filesystem Layout Specification, The Source
  Directory]), never members of the record.
* An entry never expires: it stays among the project's open entries, offered to continue in both clients, until its
  scope is created, the operator abandons it, or the release of its project deletes it
  (link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-release[Credentials & Enrolment
  Specification, Releasing Ends Work as the Operator Ends It]). The periodic sweep removes only the directory of an
  entry already started or abandoned whose removal a stop cut off (link:../runtime-lifecycle/01-startup-recovery-drain.adoc#periodic-sweep[Runtime
  Lifecycle Specification, Periodic Sweep]).
* The `start.create-scope` transaction creates the scope from the entry in the fixed write order of
  <<transaction-journal>>: the source directory, the transcript and the decision stores move into the new scope, the
  entry's directory is deleted last, and a deleted `entry_id` creates at most one scope.
* A digest mismatch of an entry's store holds only that entry, released by the operator's `accept-edit` of the store or
  ended by abandoning the entry; no other entry and no workspace workflow is affected
  (link:../store-schemas/13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification]).
* Both clients address an entry at the top level, `/api/v1/entries/{entry_id}`, with its event stream, and a worker task
  of the entry is a queue task of the workspace scope with the entity `<entry_id>`
  (link:../store-schemas/16-task-queue.adoc#queue-task-record[Queue Task Record]).
* The entry of a project onboarding, opened before the project has an id, is specified with the onboarding
  (link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-onboarding[Credentials & Enrolment
  Specification, Onboarding a Project as One Process]); it has no record of this schema.
* The `grants.jsonl` member of the layout belongs to the package `access-grants`: it is the grants given once for the
  start, and until that package lands an entry carries no grants store
  (link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine
  Store], ADR `core-store/082`).
