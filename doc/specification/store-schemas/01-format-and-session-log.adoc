[#format-versioning]
== Format Versioning & Atomic Write Discipline
_Implementation watch: link:../../../../plan-marshall-documentation/doc/implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-17[PM-WATCH-GEN-17], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-25[PM-WATCH-STORE-25], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-37[PM-WATCH-STORE-37]_

[[_format_versioning_atomic_write_discipline]]
1. *Version Envelope*: Every persisted JSON root object and every JSONL header/record must declare `"format_version": 1` (positive integer, one sequence per file kind): the server-owned stores, the git-tracked team configuration files `.marshall/config/*.json` (xref:07-project-configuration.adoc#project-configuration-store[Project Configuration (`.marshall/config/`, `local-config.json`, Effective Configuration; `PM-EXT-6`, `PM-EXT-7`)]), and the operator files (`local-config.json`, `machine-config.json`, the project enrolments, the harness enrolment `harnesses.json`, credential files). A workflow unit (`*.pmwf`) declares its DSL format in its header (`workflow <id> version <n> format <f>`, link:../workflow-dsl/01-grammar.adoc#_formal_ebnf_grammar_for_the_workflow_dsl[Workflow DSL Specification]). Exempt are Markdown documents (checked by their parsers), plain-text logs, OS primitives, and the raw HMAC key.
+
*Accept exactly one, refuse, never rewrite*: Before 1.0 a binary accepts exactly the current `format_version` of each file kind; there is no migration chain and no startup migration. A reader returns `absent`, `unreadable` (including a missing `format_version`), `format_outdated{file, found, current}`, `format_newer{file, found, current}`, or `parsed`; no reader tolerates an older shape. An outdated or newer file is never modified by a reader: a scope store raises the `precondition_unmet` condition on its scope (reason `format_outdated` or `format_newer`), shown to the operator in both clients as a hold of kind `condition` with its acts (link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue, Holds and Their Acts]); a team configuration file or workflow unit refuses every scope creation of a bootstrap (re-checked in the bootstrap's `start.create-scope` transaction) and every phase handshake of the project with `format_outdated` or `format_newer` naming the file (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/04-errors-and-testing.adoc#rejection-reasons[MCP Tools Specification, Closed Rejection Reasons]); an operator file is refused naming the file and the changed keys, and the refusal reaches both clients of the operator. *Upgrade path*: a `format_version` bump is listed with the changed keys in the release notes; a live scope keeps the store format of the binary that runs it, so the operator finishes the live scopes before an upgrade that changes a format, and the upgrade of the runtime drains its live work first (link:../runtime-lifecycle/01-startup-recovery-drain.adoc#runtime-lifecycle-operations[Runtime Lifecycle Specification, The Runtime's Lifecycle]); a later run of the project's setup offers the new binary's default changes for the files the project holds as its own (a diff for a workflow unit of the project, a server-rendered rewrite for a JSON configuration file, link:../domain-extensions/06-configuration.adoc#config-upgrades[Domain Extensions Specification, Configuration Upgrades]). The migration mechanism for 1.0 and later is decided at 1.0.
2. *Atomic Write-and-Rename*: All JSON file updates are written to a sibling temporary file (`<filename>.tmp.<uuid>`), flushed to disk (`FileChannel.force(true)`), and atomically renamed over the target file (`StandardCopyOption.ATOMIC_MOVE`, `StandardCopyOption.REPLACE_EXISTING`); the parent directory is then forced to disk as well (`FileChannel.force(true)` on the directory), so that the rename itself survives a crash. A store replaced this way is guarded by a sibling lock file, never by a lock on the store file itself (xref:13-leases-integrity-testing.adoc#lock-free-snapshot-reads[Lock-Free Snapshot Reads, Transaction Locks & Leases (`PM-IMPL-7`)]). Every write to a plan, epic, or workspace store runs as a journaled transaction (<<transaction-journal>>).
3. *Single Writer Set*: Every writer of a `PM-MCP` store runs inside the one `PM-MCP` runtime and serializes through its own locks. Legacy `plan-marshall` never touches `.marshall/` or `<PM_MCP_BASE>`, and `PM-MCP` never writes `.plan/` or `~/.plan-marshall/` (`PM-MIG-2`), so no store is shared and no cross-runtime lock protocol exists.
4. *Absent vs Unparseable*: Every store and document reader returns one of `absent`, `empty`, `parsed`, or `unreadable` (with the failing line or offset). An input that yields no parsable content is `unreadable`, never an empty record and never `absent`. A JSONL record that is refused, because it is unreadable or declares another `format_version`, is reported with its line number. Consumers handle `unreadable` explicitly: they fail closed or report `indeterminate`.
5. *One Wire Shape per Instant*: Every persisted or exchanged instant is an RFC 3339 UTC string (`"format": "date-time"`, `Z` suffix); epoch numbers are never persisted. A process start instant is taken from the OS (`ProcessHandle.Info.startInstant()`) and stored in the same shape. Durations are integers whose field name carries the unit (`duration_ms`, `*_seconds`).
6. *JSONL Append Discipline*: The append under the store's lock and the repair of a torn tail are implemented (`PM-IMPL-7`, link:../../../../plan-marshall-documentation/doc/developer/store-substrate.adoc#jsonl-stores[Developer Guide § Store Substrate, JSONL Stores]). A JSONL store of a plan, epic, or workspace scope is appended to through the scope's transaction under the scope lock; `audit.jsonl` under the audit lock, a plan's `mcp/mailbox.jsonl` under its mailbox leaf lock (xref:04-epic-and-change-ledger.adoc#epic-inbox-record[Epic Inbox & Plan Mailbox Records (`inbox.jsonl`, `mcp/mailbox.jsonl`)]), a task's activity journal under its own leaf lock outside the scope's transaction (xref:16-task-queue.adoc#activity-journal[Activity Journal]), and the machine journals `state/reports.jsonl` and `state/cleanup.jsonl` under their own leaf locks (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#reports[Runtime & Interaction Model Specification, Reports to the Operator], link:../timeouts/03-retention-host-config.adoc#cleanup[Timeouts & Budgets Specification, One Cleanup]). No JSONL store is ever rewritten, except by three rewrites, each under the store's lock: the periodic sweep's removal of the workspace scope's technical rows (xref:13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Evidence-Based Removal Sweeps]), the cleanup's deletion of work history (a deleted plan's rows of the workspace's metrics store, the read reports of `state/reports.jsonl`), and the bound of a task's activity journal (xref:16-task-queue.adoc#activity-journal[Activity Journal]). A *versioned* JSONL store, whose records change (`findings.jsonl` keyed by `finding_id`, `review-participation.jsonl` keyed by `(pr_number, round, bot_kind)`, xref:03-findings-and-review-records.adoc#_findings_ledger_record_findings_jsonl[Findings Ledger Record]), appends the full record again at every change: the current record of a key is the last readable line with that key, and the earlier lines are its history. In `audit.jsonl` a torn tail lies after the anchored head (`audit.head` is updated only after a complete append), so the repair never touches a chained record.

[#transaction-journal]
=== Transaction Journal (`mcp/transaction-journal.json`)
_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-44[PM-WATCH-STORE-44], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-47[PM-WATCH-STORE-47]_

Every write to the server-owned stores of a plan, epic, or workspace scope, and to the project's lesson store, runs as one transaction under the lock of its scope through the scope's transaction journal. The journal, its five steps (stage, journal, apply, digests, close), its roll-forward recovery with its audit record `transaction_rolled_forward`, its document, and the path base of each scope are implemented (`PM-IMPL-7`, link:../../../../plan-marshall-documentation/doc/concepts/store-integrity.adoc#crash-consistency[Concepts § Store Integrity, Crash Consistency], link:../../../../plan-marshall-documentation/doc/developer/store-substrate.adoc#scope-transaction[Developer Guide § Store Substrate, Writing a Scope Transaction] and link:../../../../plan-marshall-documentation/doc/developer/store-substrate.adoc#recovery[§ Recovery]). A target replaces a store, appends to a JSONL store, or deletes a store. The delete target, its document `{path, mode}` without a staged file or a digest, its apply that removes the store, its digests step that drops the store's sidecar entry, and its idempotent roll-forward (a delete is applied when its store is absent, so it never violates the invariant) are implemented, with the journal in `format_version` 3 and versions 1 and 2 refused as outdated (`PM-IMPL-7`, link:../../../pm-core/doc/developer/core-store.adoc[Scope Stores Developer Guide § The Delete Mode of the Transaction Journal]). The path base of a scope also names a store in `pm-operator accept-edit`. When the recovery reports an invariant violation (a target that has neither its new digest nor its staged file), its caller raises the `integrity_breach` condition (kind `store_tampered`) for the violating stores (xref:13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification Against Out-of-Band Edits]).

*Audit delivery*: The audit record of a completed store mutation (`transaction_rolled_forward`, `jsonl_tail_repaired`, `cross_scope_reconciled`) is delivered at least once and never lost. A durable intent holds it from before the mutation that removes its cause until the audit sink accepted it (the journal for a roll-forward and for the records a transaction owes, the intent file `<store>.audit-intent` for a tail repair), and the next recovery of the scope or repair of the store replays it. Every such record carries a `transaction_id` of its own (a transaction that owes several records gives each its own identifier; a roll-forward record carries that of its journal), by which the audit log store, when it appends, and every reader drop a duplicate (xref:12-machine-stores.adoc#audit-log[Security & Transition Audit Log]). A sink that refuses a record never fails or undoes the data outcome of the mutation. The intents, the replay and the identifiers are implemented (link:../../../../plan-marshall-documentation/doc/concepts/store-integrity.adoc#audit-delivery[Concepts § Store Integrity, Audit Records of a Store Change], link:../../../../plan-marshall-documentation/doc/developer/store-substrate.adoc#audit-records[Developer Guide § Store Substrate, Audit Records]); the deduplication by the audit log store is not.

*Writes outside the scope*: A transition that also writes outside its scope (another scope, the lesson store, the job records, the task queue) never extends its journal. It writes in a fixed order, the authoritative store first, each further write as a transaction of its own store under that store's lock, and the runtime's startup recovery derives every later write from the authoritative store (link:../runtime-lifecycle/01-startup-recovery-drain.adoc#per-project-recovery[Runtime Lifecycle Specification, Per-Project Recovery], cross-scope reconciliation). The ordered write and its reconciliation, with one audit record `cross_scope_reconciled` per derived write, owed by the transaction of that write, are implemented (link:../../../../plan-marshall-documentation/doc/developer/store-substrate.adoc#ordered-writes[Developer Guide § Store Substrate, Ordered Writes and Reconcilers]); the orders and recovery rules of the transitions are these:

* *`start.create-scope`*: the new scope (authoritative; a plan's directory is built complete in the sibling temporary directory `plans/.init-<entry_id>/`, with copies of the entry's source directory, transcript, and decision stores (<<pending-entry-record>>), and published by one atomic directory rename to `plans/<plan_id>/`; for a new epic, its git-tracked ledger with a copy of the entry's source directory before its machine scope, so a crash between them leaves a ledger the epic bootstrap adopts), then for a `local_changes` plan the capture ref `refs/pm-mcp/captures/<plan_id>` at the recorded `captured_changes.snapshot_sha` (xref:06-task-and-references.adoc#_references_footprint_store_schema_references_json[References & Footprint Store Schema (`references.json`)]), then the epic queue row (`running`, `started_at`, xref:04-epic-and-change-ledger.adoc#epic-queue-row[Epic Queue Row]), then the lesson claim (xref:10-job-and-lesson-records.adoc#lesson-record[Lesson Record]), then the deletion of the pending entry directory (<<pending-entry-record>>). A plan is live when `plans/<plan_id>/mcp/status.json` exists; every enumeration of live plans lists only such directories. Recovery: a temporary init directory `plans/.init-*` is deleted (no transaction survives a restart); a non-terminal plan whose capture ref is missing gets it re-created at its `snapshot_sha`; a plan with `origin.epic_id` whose epic queue row is still unstarted (`started_at: null`) sets the row `running` with the plan's creation instant as `started_at`; a non-terminal plan created from a lesson whose lesson is unclaimed claims it; a pending entry directory whose plan or epic exists is deleted.
* *Job states*: the scope's `active_job` (authoritative for which job a state owns, xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store (`mcp/status.json`)]), then the job record in `jobs/` (authoritative for the job's fate, xref:10-job-and-lesson-records.adoc#job-record[Job Record]). Recovery: an `active_job` that names a job without a record is settled `killed` (the job never started).
* *Worker end*: the job record (fate, fenced generation, revoked token; authoritative for the generation), then the queue task record (the held task's attempt ended, its lease released). Recovery: a task leased to a generation whose job record has ended is released and queued again like a task held at a restart (xref:16-task-queue.adoc#task-queue[Task Queue], Recovery).
* *Queue tasks*: `active_tasks` first, then the queue task record (xref:16-task-queue.adoc#task-queue[Task Queue], Two Authorities and Recovery).
* *Plan end*: the plan's terminal transaction (authoritative for its `outcome`), then the lesson store transaction: a plan ending `merged`, whose changes landed by the merge of `landing.pull-request` or the push of `landing.main`, retires its claimed lesson, every other outcome releases the claim (xref:10-job-and-lesson-records.adoc#lesson-claim[A Claimed Lesson Ends with the Landing]). Recovery: a lesson whose `claim.plan_id` names a terminal or archived plan is retired or released per that plan's recorded outcome, and released when the plan no longer resolves.
* *Late findings*: the carry-out of a blocking finding after the merge (xref:03-findings-and-review-records.adoc#_findings_ledger_record_findings_jsonl[Findings Ledger Record], Late Findings Are Carried Out) writes the destination first (the `process_finding` message under the epic lock, or the seeded lesson under the lesson store lock), because the destination assigns the `ref`; then the plan's transaction sets the finding `carried` with `carried_to`. A message appended to the kept landing envelope is part of the plan's own transaction. Recovery derives nothing: a crash between the two leaves the finding `pending` without `carried_to`, and the resumed carry-out carries it again; the accepted cost is a duplicate notice of a debt that stays visible, never a lost one.

[#pending-entry-record]
== Pending Entry (`pending/<entry_id>/`)
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-WF-10[PM-WF-10: Phase 1–4 Planning Invariants, Lane Ratchet & Artifact Gates]_

_Implementation watch: link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-42[PM-WATCH-STORE-42]_

A start of a plan or an epic is an *entry* until its scope exists (link:../state-catalogue/09-bootstrap-and-lessons.adoc#start-from-clients[State Catalogue, Starting from the Clients]). The operator opens one in either client (`POST /api/v1/projects/{project_id}/entries` with the kind `plan` or `epic`), and the server opens one itself for a plan it starts for a launchable epic row. An entry is a directory of the per-project machine store (link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]):

[source,text]
----
pending/<entry_id>/
├── entry.json        the pending entry record (schema below): the entry's
│                     kind and the state of its bootstrap
├── sources/          the source directory: every source as it came in,
│                     with its manifest sources.json
├── questions.jsonl   the entry's decisions (Question Record)
├── decisions.jsonl   their decision records (Decision Record)
└── chat/             the transcript of a chat about the entry
----

The record with its strict codec (the envelope, the state position, the call frames, the condition overlay, and `last_refusal` typed; `facts` and `recipe.params` kept as the JSON text they were read with and written back byte for byte), the allocation of a fresh `entry_id` checked against the entries present and the targets of the same transaction under the workspace lock, so concurrent entries never share a directory, the creation, replacement, and removal of a record as targets of a journaled transaction of the workspace scope under `locks/workspace.lock` (<<transaction-journal>>), its coverage by the workspace scope's digest sidecar (xref:13-leases-integrity-testing.adoc#store-digest-verification[Store Digest Verification Against Out-of-Band Edits]), and the listing of only the names that parse as an `entry_id` are implemented in the file form `pending/<entry_id>.json` (`PM-IMPL-7`, link:../../../pm-core/doc/developer/core-store.adoc[Scope Stores Developer Guide § The Pending Entry Record]). Not implemented yet: the directory form with its source directory, transcript, and decision stores, the schema below, its writers (the entry endpoint, the bootstrap transitions and terminals), the pause of one entry, and the addressing.

* *Opened by the server*: the directory, its record, and an empty source directory are created in one transaction of the workspace scope when the entry is opened; every bootstrap transition replaces the record. The sources are not part of the record: each source is a file of the source directory and an entry of its manifest (link:../filesystem-layout/03-project-store.adoc#source-directory[Filesystem Layout Specification, The Source Directory]); a source unit adds one, the operator removes one in `start.sources` or `start-epic.sources`, and a stored source is never changed. External text is kept only in its level-1-cleaned form with its screen verdict (xref:15-screening-and-grants.adoc#screen-verdict-cache[Screen Verdict Cache]); a `suspicious` item is used only after the operator's audited accept in its operator wait.
* *Never expires*: an entry has no time limit and is never discarded by time. It stays among the project's open entries, offered to continue in both clients, until its scope is created, the operator abandons it, or the release of its project deletes it (link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-release[Credentials & Enrolment Specification, Releasing Ends Work as the Operator Ends It]). Abandoning an entry deletes its directory with its sources and its transcript.
* *Bootstrap state*: `bootstrap` holds the entity's state position, its call frames (a called source unit, a chat), its condition overlay, the recipe chosen in `start.choose` with its parameters, the title and the id shown in `start.ready` or `start-epic.ready`, and the reason of the last refused re-check of the `start.create-scope` transaction. The options of a plan that are asked where the plan first needs them are not part of the entry (link:../state-catalogue/09-bootstrap-and-lessons.adoc#options-when-needed[State Catalogue, Asked When Needed]).
* *Server-started plans*: a plan the server starts for a launchable epic row has `from_epic` set; `start.launch` stores the row's staged section as the source of kind `epic_row` (`epic-row.md`), and its creation copies `from_epic` into `mcp/status.json` `origin.epic_id`, the single carrier of epic membership (xref:02-workflow-state-store.adoc#epic-linkage[Workflow State Store, Origin and Epic Linkage]).
* *Integrity*: a digest mismatch of a record pauses only that entry (`integrity_breach`, kind `store_tampered`), shown as a hold of kind `integrity_pause`; it ends by the operator's accept of the edit (`accept-edit workspace pending/<entry_id>/entry.json`) or by abandoning the entry. No other entry and no workspace workflow is affected.
* *Addressing*: both clients address an entry at the top level, `/api/v1/entries/{entry_id}`, with its event stream (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#event-streams[Runtime & Interaction Model Specification, Events per Scope]); its states are operator waits (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]). A worker task of the entry (the screener of a source, the chat task of the role `refine` or `decompose`) addresses its entity as `pm_state` / `pm_do` with `plan_id: NO_PLAN` and `entity: <entry_id>`; a call naming a deleted `entry_id` is `scope_not_found`.
* *Creation*: the `start.create-scope` transaction creates the scope from the entry: the source directory goes into `plans/<plan_id>/sources/`, or into the epic's ledger `.marshall/epics/<epic_id>/sources/`, committed and landed with it; the transcript into `plans/<plan_id>/chat/`, or into the epic's machine store `epics/<epic_id>/chat/`, never into a ledger; the decision stores into the new scope's stores (xref:14-plan-instance-waivers-questions.adoc#question-record[Question Record], xref:18-decision-records.adoc#decision-record[Decision Record]). For a plan, `origin` names the sources by their ids (xref:02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Workflow State Store]). The entry's directory is deleted last (<<transaction-journal>>, Writes outside the scope); a deleted `entry_id` no longer exists, so each entry creates at most one scope.
* *A project's onboarding*: the entry of a project onboarding, opened before the project has an id, is specified with the onboarding (link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-onboarding[Credentials & Enrolment Specification, Onboarding a Project as One Process]); it has no record of this schema.
