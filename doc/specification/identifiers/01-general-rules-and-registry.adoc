[#general-rules]
== General Rules

The following rules apply to every identifier in the registry; a table row states only what it adds.

1. *ASCII only*: Every identifier consists of printable ASCII characters (`0x21..0x7E`); none contains whitespace, a path separator other than the ones its grammar names, or a character that needs escaping in a file name, a URI path segment, a TOON scalar, or a host tool name. Unicode normalization never applies because no identifier admits non-ASCII input.
2. *Case*: Identifiers are lower case unless the grammar admits upper case explicitly (entity-addressed identifiers such as `TASK-001` and `F-12`, `module_id`, repository paths). An identifier is compared byte-exactly; the server never folds case to make two identifiers match.
3. *Separators*: `-` separates words inside one identifier, `_` separates words inside names that must also be valid tool or parameter names, `.` separates the segments of a dotted identifier (`state_id`, `primitive_id`), `:` separates the parts of a link identifier and a finalize step identifier, and `/` separates URI and path segments. No other separator is used, and an identifier never starts or ends with a separator unless its grammar says so.
4. *Maximum length*: Every identifier has a maximum length, stated in the table; a grammar whose regex is unbounded is bounded by the stated length (enforced as `maxLength` in a schema, or by the server's validator where the schema subset cannot express it). An identifier that exceeds its bound is refused, never truncated.
5. *Server-generated identifiers are opaque to the model*: The model copies a server-generated identifier verbatim from a representation, a worker's launch prompt or offer, or a tool result; it never composes, increments, or parses one. The server never derives meaning from the model's spelling of such an identifier beyond looking it up in the addressed scope.
6. *Model-supplied identifiers are validated server-side*: Every identifier that arrives from the model (tool arguments, link identifiers, `args` values that name an entity) is checked against its grammar by the server's argument validator before it is looked up, and a violation is answered as defined in link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/04-errors-and-testing.adoc#protocol-errors-vs-domain-workflow-failure-states[MCP Tools Specification, Protocol Errors] (`invalid_arguments` for tool arguments, `rejected` for link arguments). A grammatically valid identifier that names nothing in the addressed scope is `scope_not_found` or `link_not_available`, never an empty result.
7. *No identifier encodes another scope's identifier*: An identifier is resolved only within the scope that the same call addresses; it never embeds the `plan_id`, `epic_id`, or `project_id` of another scope (`message_id`, `job_id`, `queue_task_id`, `generation_id`, `waiver_id`, `question_id`, `decision_id`, and `batch_id` carry no scope). Composite storage addresses such as `plans/<plan_id>/`, `locks/plan-<plan_id>.lock`, the credential account `<project_id>/<credential_key>`, the archived epic directory `<epic_id>-<YY-MM-DD>`, the capture ref `refs/pm-mcp/captures/<plan_id>` of a `local_changes` plan (link:../phase-workflows/01-planning-phases-1-2.adoc#_plan_source_contracts[Phase Workflows, Plan Source Contracts]), the split ref `refs/pm-mcp/splits/<plan_id>/<n>` of a `split_change` re-planning (link:../store-schemas/17-re-planning.adoc#replan-record[Store Schemas, Re-Planning Record]), or the baseline scratch worktree `.marshall/local/worktrees/baseline-<plan_id>-<sha12>` (`<sha12>` the first 12 hex digits of the merge-base commit, link:../job-runtime/03-parsers-and-gates.adoc#_gate_honesty_verification[Job Runtime, Gate Honesty Verification]) are paths built from identifiers, not identifiers, and are never parsed back into one; so is the address of a decision across scopes, `<scope_id>/<question_id>` (<<id-question-id>>).
8. *Stability*: An identifier is immutable once allocated. An identifier marked _never reused_ is not allocated again after its entity is deleted, archived, or retired; one marked _re-derivable_ is computed from content and is equal whenever the content is equal.
9. *Schema subset*: A tool `inputSchema` expresses a grammar with a lookaround-free `pattern` plus `minLength`/`maxLength` (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools.adoc[MCP Tools Specification], Architectural Constraint 3). Stored schemas may use lookaround.
10. *Scope counters*: A numbered identifier allocated per scope takes the next value of a counter persisted in the scope's status store (`counters` of `mcp/status.json`, link:../store-schemas/02-workflow-state-store.adoc#_workflow_state_store_mcpstatus_json[Store Schemas, Workflow State Store]): counter + 1, counted in the allocating transaction. The counted kinds are `finding_id`, `task_id`, `envelope_id`, `question_id`, `decision_id`, `waiver_id`, and the record counters `amendment_id`, `assessment_id`, `owed_id`, `request_id`, `failure_id`, `evidence_id`, `batch_id`, `proposal_id`, `replan_id`, and `follow_up_id` (xref:02-registry-stores-to-web.adoc#id-record-counters[Record counters]). A counter never decreases, so _never reused_ holds after a record is removed or purged; it is never derived from the records present. `message_id` is the exception: it is counted per store file (link:../store-schemas/04-epic-and-change-ledger.adoc#epic-inbox-record[Store Schemas, Epic Inbox]).

[#registry]
== Registry

`Generated by` names the party that allocates the value: *server* (the runtime `pm-mcpd` computes it, also where a client of the operator requests it; no client allocates an identifier), *model* (supplied in a tool call or link argument, validated by the server), *operator* (set or confirmed through an act of either client of the operator, or an operator-owned file; a value the server proposes and the operator confirms is the operator's), or *build* (fixed in the compiled binary, a workflow definition, or a compiled-in catalogue).

There is no legacy `script` job kind (`PM-MIG-2`), and no job kind for language servers: they are pool processes without job records (link:../job-runtime.adoc[Job Runtime]). A review-bot poll is a `ci` job with the budget key `ci:<operation>`; it has no kind and no prefix of its own. `pm_build.job_id` accepts only the `b-` form; a worker's fields (its `generation_id`, the `job_id` of a task row, an attempt, or a lease) accept only the `l-` form; a reference to a non-worker job (the `active_jobs` entries, the `active_job` binding, a firing's job of the workflow state, the `gather_job_id` of a failure envelope, the `job_facts.job_id` of the derived facts, and the job reference of a change-ledger entry) accepts only the `[bcgpv]-` form. The `active_job` binding of a `composite_job` state or a `job llm` state holds the state's `state_id` (<<id-state-id>>) instead of a `job_id`. [[id-worker-id]]A worker has no identifier of its own: it is identified by its `job_id`.
|server (random; a collision with a record or log of the store that keeps the job draws again, implemented; remaining: the check against the existing job records of every project of the machine)
