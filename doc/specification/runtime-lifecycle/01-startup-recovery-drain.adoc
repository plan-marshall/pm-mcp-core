== Startup Sequence
_Implementation watch: link:../../implementation-watch/runtime-lifecycle.adoc#PM-WATCH-RUN-9[PM-WATCH-RUN-9], link:../../../../plan-marshall-documentation/doc/implementation-watch/runtime-model.adoc#PM-WATCH-RUN-14[PM-WATCH-RUN-14], link:../../../../plan-marshall-documentation/doc/implementation-watch/runtime-model.adoc#PM-WATCH-RUN-17[PM-WATCH-RUN-17]_

The steps run in this order; each later step runs only while the runtime holds the singleton lock. Steps 1 to 5 run in the runtime's `StartupEvent` observer, which Quarkus runs before its HTTP server binds the socket, so nothing can connect before the token exists; steps 6 and 7 follow the bind.

. *Singleton lock*: Acquire `<PM_MCP_BASE>/locks/runtime.lock` (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#_singleton_discovery[Singleton & Discovery]). A runtime that loses exits without writing anything, audit records included; the successor of a restart waits for the lock instead (<<runtime-lifecycle-operations>>).
. *Stale-socket cleanup*: While holding the singleton lock, and never before, remove a stale `run/runtime.sock` and the stale `state/runtime.json`. Holding the lock proves that no live runtime owns them; a runtime that removed them without the lock could unlink the live holder's socket.
. *Directory & permission verification (`PM-SEC-4`)*: First the runtime creates the directories `run/`, `enrolments/`, `state/`, and `logs/` of `<PM_MCP_BASE>` where they are absent (mode `0700`, under `umask 077`; a client's on-demand start has created `logs/` before the spawn, link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#_start_modes[Start Modes]); an existing directory is checked, never repaired. Then `<PM_MCP_BASE>`,`<PM_MCP_BASE>/enrolments/`, and `<PM_MCP_BASE>/run/` must be owned by the effective UID with mode `0700` and must not be symlinks, and `state/*` must be `0600`. Violations are written to `stderr` and `audit.jsonl` and the runtime exits with code `77` (`EX_NOPERM`). In the same step the length of the socket path is checked against the platform's `sun_path` limit; a path over it refuses the start like every other violation of this step (the diagnostic of link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#_singleton_discovery[Singleton & Discovery], Socket, Path length, on `stderr` and in `audit.jsonl`, exit code `77`), before a token is written or a socket bound. A single enrolment file is not part of this check: its permissions and integrity are verified per project (<<per-project-recovery>>), and a failure blocks only that project. Credential files under `<PM_MCP_BASE>/credentials/` are not part of this check: an insecure credential file blocks only the step that needs it (`PM-CRED-4`, link:../../../../plan-marshall-documentation/doc/specification/cli-and-security.adoc[CLI, Coordination & Security Specification]).
. *Bounded verification*: The step, with its seam for the audit chain, the `audit_chain_broken` record of a broken chain that is never repaired and never stops the start, and no store or unit work, is implemented (link:../../../../plan-marshall-documentation/doc/concepts/runtime-lifecycle.adoc#startup[Concepts § Startup]). So is the audit chain verification (`PM-SEC-6`) that fills the seam: it verifies the HMAC-anchored head `logs/audit.head`, the rotation index, and the `prev_hash` chain of `logs/audit.jsonl` from its last checkpoint (incremental; the full verification across every rotated file is what the operator command `pm-operator audit verify` requests), and the `audit_chain_broken` record carries `details.reason`, `details.first_broken_line` for `link_broken`, and `details.os_principal` (link:../../../pm-runtime/doc/developer/runtime-audit.adoc[Audit Trail Developer Guide]). Remaining: the wiring of that verification into `pm-mcpd`, which passes none yet, the verb `pm-operator audit verify`, and the report of a broken chain on `stderr` and in the runtime status. A project's workflow units are verified when they are loaded (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units], `PM-IMPL-5`), and a failure refuses only that project's plan lifecycle; every store's `format_version` is checked when it is read, and a mismatch refuses only what reads it (link:../store-schemas/01-format-and-session-log.adoc#format-versioning[Store Schemas Specification, Format Versioning]).
. *Runtime token*: Write a fresh runtime token to `run/runtime.token` (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#runtime-token[Local Trust: Runtime Token]), replacing the previous instance's token, before anything can connect.
. *Bind the socket*: Bind the socket path (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#_singleton_discovery[Singleton & Discovery], Socket), restrict the socket created under the process `umask` to mode `0600` and verify its owner, mode, and file type (a failed check exits with code `77` like step 3), and only then write `state/runtime.json` with it.
. *Ready*: Begin accepting connections, settle the result of an upgrade the previous instance recorded (<<runtime-lifecycle-operations>>, Upgrade), and start the background recovery pass over all enrolled projects (<<per-project-recovery>>) and over the machine scope. A project's supervisor starts workers only after its recovery has finished.
. *Web listeners*: Open each web listener the `web` object of `machine-config.json` records as open, the loopback listener on `web.port` and the LAN listener on `web.lan_port` (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#_transport_endpoint[Transport Endpoint], Web listeners). An occupied port leaves that listener closed, is reported in the runtime status, and never stops the start, the socket listener, or the other web listener; another port is never chosen.

The cold-start target of `PM-TECH-3` (≤ 50 ms) covers steps 1 to 7 on a clean state: socket bound and ready, without any per-project recovery and without the web listeners, which are off by default.

[#per-project-recovery]
=== Per-Project Recovery
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-61[PM-WATCH-DISP-61]_

The per-project crash recovery (`PM-ARCH-7`) with its two triggers after bind, its once-per-instance rule, its bounded wait, its restriction to enrolled projects, and its step order is implemented (link:../../../../plan-marshall-documentation/doc/concepts/runtime-lifecycle.adoc#per-project-recovery[Concepts § Per-Project Recovery]); the runtime wires it to the bind and to its calls. The answer on expiry of the wait is the retryable error `runtime_recovering` (link:../../../../plan-marshall-documentation/doc/specification/mcp-tools/04-errors-and-testing.adoc[MCP Tools Specification], closed error codes). A link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#local-api[Local API] request addressing the project waits the same way and is answered with the same retryable error code `runtime_recovering` of the `pm-api` error codes (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#api-error-codes[Local API, Error codes]). The per-project machine store an unenrolled project leaves behind is not touched by the recovery: it is an item of the cleanup from its unenrolment on (link:../timeouts/03-retention-host-config.adoc#cleanup[Timeouts & Budgets Specification, One Cleanup]), and it is used again only when the same `project_id` is enrolled again for the `project_root` the store records (link:../store-schemas/11-enrolment-store.adoc#project-store-identity[Store Schemas Specification, Project Store Identity]). The machine scope recovers the same way, without the steps that concern a project's enrolment and worktrees. The project's recovery comprises these steps; what a step states is still to be built unless it says otherwise:

. *Enrolment integrity verification (`PM-SEC-5`)*: The verification of the enrolment file and its sidecar, with the settlement of a stopped write of the pair before it and the audit record of every refusal, as a failed step that blocks only its project, is implemented (link:../../../../plan-marshall-documentation/doc/concepts/runtime-lifecycle.adoc#per-project-recovery[Concepts § Per-Project Recovery]). Remaining: the uniqueness of `project_root` among the enrolment files (`enrolment_root_conflict`), and the report of a failure on `stderr` and in the runtime status. Verify the project's enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json`: mode `0600` and owner, schema and exact `format_version`, its HMAC-SHA-256 sidecar `<project_id>.json.hmac` (link:../credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#enrolment-integrity[Credentials & Enrolment Specification]), and the uniqueness of its `project_root` among the enrolment files. On a failure the runtime records the audit record (`enrolment_tampered`, `enrolment_insecure`, `enrolment_invalid`, or `enrolment_root_conflict`), reports it on `stderr` and in the runtime status, and refuses every enrolment-dependent operation of this project with that reason until the operator repairs or re-baselines the file; the other projects and the runtime are unaffected.
. *Owed enrolment audit records*: The step, with the background pass for the intents of projects no longer enrolled, is implemented (link:../../../../plan-marshall-documentation/doc/concepts/runtime-lifecycle.adoc#per-project-recovery[Concepts § Per-Project Recovery]). Hand over the audit records an earlier enrolment write of the project still owes in `<PM_MCP_BASE>/enrolments/<project_id>.json.audit-intent` (a refused or stopped hand-over left them there), in their order and with their transaction ids, under the project's enrolment lock (link:../../../../plan-marshall-documentation/doc/concepts/store-integrity.adoc#audit-delivery[Concepts § Store Integrity, Audit Records of a Store Change]). The background pass does the same for an intent whose project is no longer enrolled, which an `unenrol` with a refused hand-over leaves behind. A record the audit log refuses again stays owed; the recovery is not refused for it.
. *Jobs and workers*: The jobs part of the step is implemented (link:../../../pm-runtime/doc/developer/runtime-start.adoc#_jobs_recovery_step[Runtime Start Developer Guide § The Jobs Part of Step 3]): every job record (`jobs/<job_id>.json`, link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]) of the project left `queued` or `running` by a previous runtime instance, workers included, is settled `killed` by the first matching rule, a live process group terminated first (link:../job-runtime/01-pipeline-and-subprocesses.adoc#_process_termination_cancellation_protocol[Job Runtime Specification, Process Termination], step 6), and the slot the caller names for a job is released after its fate. Remaining is the worker part, which the step reports as a seam: the generation of every worker settled here is fenced and its job token revoked; its usage is recorded `unmeasured`. The job-private directory `<PM_MCP_BASE>/run/jobs/<job_id>/` of every worker whose job record has `status: ended` is removed, whatever its fate, those settled here included (a crash between the recorded fate and the removal leaves it behind), and with it the data directory of a worker whose harness has a per-worker data home and the copy of the harness's login file in it, which a runtime that died while the worker ran left behind (link:../job-runtime/02-confinement-and-environment.adoc#worker-data-home[Job Runtime Specification, Per-Worker Data Home]) (link:../filesystem-layout/02-machine-runtime.adoc#job-private-directories[Filesystem Layout Specification, Job-Private Directories]). Jobs are never re-executed blindly.
. *Leases and the task queue*: The selection of the project's leases by the `project_id` of their `LeaseOwner`, the orphan marking of those whose holder is no longer alive, and the release of an orphaned lease only on positive evidence are implemented (link:../../../../plan-marshall-documentation/doc/concepts/runtime-lifecycle.adoc#per-project-recovery[Concepts § Per-Project Recovery]); the lease stores themselves (merge-queue holders, review-bot claims, build slots, model slots) come with their packages. Release a build or model slot at once (its job is recorded as `killed`). Release every task lease (recorded in its queue task record, never as a `LeaseOwner`), all of them held by worker generations, at once by the queue recovery rule (link:../store-schemas/16-task-queue.adoc#task-queue[Store Schemas Specification, Task Queue], Recovery: the attempt ends `restart`, uncounted, and the task is queued again); a late call of the earlier holder about that task is refused. The positive evidence of abandonment of any other orphaned lease is: owning scope terminal, archived, or gone, or lease expiry passed without adoption; the owning scope adopts its orphaned leases on its next transition (link:../store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Store Schemas Specification, Machine Lease Stores]).
. *Journal roll-forward*: The roll-forward of the interrupted journal of every scope given to the step is implemented (link:../../../../plan-marshall-documentation/doc/concepts/runtime-lifecycle.adoc#per-project-recovery[Concepts § Per-Project Recovery]); the per-project machine store supplies the scopes: the project's plan, epic, and workspace scopes and its lesson store (link:../store-schemas/01-format-and-session-log.adoc#transaction-journal[Store Schemas Specification, Transaction Journal]). Store digests are compared only after this step.
. *Cross-scope reconciliation*: Running the reconcilers registered for the project after the roll-forward is implemented (link:../../../../plan-marshall-documentation/doc/concepts/runtime-lifecycle.adoc#per-project-recovery[Concepts § Per-Project Recovery]). The orders and the recovery rule of each transaction that writes outside its scope (`start.create-scope`, job states, worker end, queue tasks, plan end, late findings) are listed once in link:../store-schemas/01-format-and-session-log.adoc#transaction-journal[Store Schemas Specification, Transaction Journal] and come with their stores as reconcilers; a job state whose `active_job` was settled `killed` routes that outcome. Each reconciliation appends one audit record `cross_scope_reconciled` (the same record as in the Transaction Journal); the task queue is reconciled by the same rule (link:../store-schemas/16-task-queue.adoc#task-queue[Store Schemas Specification, Task Queue], Recovery). A report a committed transition owed when the previous instance stopped is written here, with this instance's `sent_at` (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#reports[Reports to the Operator]); a cleanup deletion cut by the stop goes on from the cleanup journal (link:../timeouts/03-retention-host-config.adoc#cleanup[One Cleanup]).
. Reconcile the recorded worktree presence of every plan whose `worktree_path` is set, lazily on the first transition of that plan: a recorded worktree that no longer exists is cleared (`worktree_path: null`) with an audit record and never followed (link:../filesystem-layout/01-repository-workspace.adoc#worktree-lifecycle[Filesystem Layout Specification, Worktree Lifecycle]). Plan directories never move, so there is no directory move to complete or roll back.
. *Engine deadlines*: After the roll-forward, re-arm the deadline timer from the persisted `deadline_at` of every open prerequisite wait of a re-planning and the persisted failure instants of the server retry backoffs, and process every deadline that passed while no runtime ran (held while the scope is under an integrity pause or paused, link:../job-runtime/01-pipeline-and-subprocesses.adoc#engine-deadlines[Job Runtime Specification, Engine Deadlines]). An operator wait has no deadline and needs no re-arming (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]); a prerequisite wait has no process, so it is re-armed, never settled `killed`.
. *Resume the drive*: Every non-terminal plan and epic of the project continues from its persisted state: a job state whose job was settled `killed` routes that outcome, a state waiting on a task offers the requeued task (link:../workflow-dsl/02-units-jobs-decisions.adoc#job-state-binding[Workflow DSL Specification, Job State Entry & Binding]), an operator wait stays offered, a paused plan stays paused, and a pausing plan holds at the point its pause names (link:02-plan-pause-and-stalled-plans.adoc#plan-pause[Pausing and Starting a Plan]). The metrics' gauges of the project are set from the recovered state (link:03-runtime-metrics.adoc#runtime-metrics[The Runtime's Metrics]).
. *Baseline worktree sweep*: A baseline scratch worktree `.marshall/local/worktrees/baseline-<plan_id>-<sha12>/` whose plan no longer resolves or is terminal (archived or aborted) is removed from the main checkout (`git.worktree-remove`) and audited; one whose plan is live is kept (link:../filesystem-layout/01-repository-workspace.adoc#worktree-lifecycle[Filesystem Layout Specification, Worktree Lifecycle]; link:../job-runtime/03-parsers-and-gates.adoc#_gate_honesty_verification[Job Runtime Specification, Gate Honesty Verification], item 4).

*Sweep rule*: Every removal of technical residue (leases, jobs, the residue of the periodic sweep, baseline scratch worktrees) selects candidates only from positive evidence of abandonment (a dead owner identified by PID plus start instant, a terminal state, an expired lease, or a retention period of residue passed), never from a name that fails to parse as an identifier and never from the absence of evidence (link:../store-schemas/13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Store Schemas Specification, Evidence-Based Removal Sweeps]). Each swept directory declares its reserved entries (for example the shared epic worktree `_epics` under `.marshall/local/worktrees/`), which are excluded by construction. Work history is never residue: it goes only through the cleanup the operator confirms (link:../timeouts/03-retention-host-config.adoc#cleanup[One Cleanup]).

[#periodic-sweep]
=== Periodic Sweep
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-ARCH-10[PM-ARCH-10: One Cleanup of Work History & Automatic Removal of Residue]_

The periodic sweep over the enrolled projects and the machine at the fixed periodic sweep interval (link:../timeouts/02-runtime-leases-operator-web.adoc#periodic-sweep-interval[Timeouts & Budgets Specification]) is implemented as a schedule of steps (link:../../../../plan-marshall-documentation/doc/concepts/runtime-lifecycle.adoc#periodic-sweep[Concepts § Periodic Sweep], link:../../../pm-runtime/doc/developer/runtime-start.adoc[Sweep Steps Developer Guide]); its wiring into `pm-mcpd` and the steps below are still to be built. Each pass removes technical residue by itself, each removal in a transaction of its scope with one audit record, under the sweep rule above; `pm-operator sweep` lists what the next pass would remove, with its evidence, and runs that pass at once with `--apply` (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-channel-isolation[CLI, Coordination & Security Specification]):

. *Residue*: the pending entry directory of an entry already started or abandoned whose removal a stop cut off (the started scope or the abandonment is the evidence, never the entry's age: an open entry never expires); the workspace scope's technical rows older than `retention.workspace_rows_days`, the metrics rows of a plan excepted; retired lesson bodies older than `retention.retired_lesson_bodies_days`; ended queue task records older than `retention.task_records_days`; daemon store directories of a write-set digest no longer the project's; the job-private directories of ended jobs; stale leases; temporary files and caches; and rotated audit files older than `audit_rotation.retain_days`, their index entries kept (link:../timeouts/03-retention-host-config.adoc#retention[Timeouts & Budgets Specification, Retention & Rotation]).
. *Disk use*: the size of the machine store, recorded with when it was measured for the metric `runtime.disk.machine_store` (link:03-runtime-metrics.adoc#runtime-metrics[The Runtime's Metrics]).
. *The cleanup's check*: the first pass after the start and the first pass of each new UTC day compute the work history due and open a cleanup job where its rules say so (link:../timeouts/03-retention-host-config.adoc#cleanup[One Cleanup]).

The quiet-window retirement of `arch-constraint` lessons is a verdict on a lesson, not residue: it stays an act of `pm-operator sweep --apply` and never runs by itself.

== Drain, Stop & Upgrade
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-ARCH-7[PM-ARCH-7: Runtime & Relay Lifecycle, Crash Recovery & Job Drain]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-DIST-1[PM-DIST-1: Single Version Authority & Embedded Client Bundles]_

_Implementation watch: link:../../implementation-watch/runtime-lifecycle.adoc#PM-WATCH-RUN-6[PM-WATCH-RUN-6], link:../../implementation-watch/runtime-lifecycle.adoc#PM-WATCH-RUN-9[PM-WATCH-RUN-9], link:../../implementation-watch/runtime-lifecycle.adoc#PM-WATCH-RUN-13[PM-WATCH-RUN-13], link:../../implementation-watch/runtime-lifecycle.adoc#PM-WATCH-RUN-15[PM-WATCH-RUN-15]_

[[runtime-lifecycle-operations]]The operator stops, restarts, and upgrades the runtime from either client through operator endpoints of the local API; each is privileged (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-channel-isolation[CLI, Coordination & Security Specification, Operator Channel Isolation]), accepted from `pm-operator` and from a paired device, audited with its channel, and announced to every client (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/06-event-catalogue.adoc[Event Catalogue]).

* *Lifecycle state*: the runtime status (`GET /api/v1/status`) carries the runtime's version and its lifecycle state: `running`; `draining`, with who asked it (`operator`, `signal`, `service_manager`), whether it can be withdrawn, what follows (`exit`, `restart`), and when the drain timeout ends; `stopping`; or `upgrading`, with its step. Beside it the *version state*: the newest version known with when it was checked, a failed check with its reason, whether the installation can be upgraded by the runtime, and the link to the release notes (`GET /api/v1/system/release-notes`); and an upgrade's last result. The version state and an upgrade's result are machine state records (link:../store-schemas/12-machine-stores.adoc#machine-state-records[Store Schemas Specification, Machine State Records]).
* *Drain*: On the operator's stop with `when: drain`, on `SIGTERM`/`SIGINT` (sent by `pm-operator drain`, the service manager, or the OS), the runtime drains. The drain with its order, its drain timeout (`drain_timeout_seconds` in `machine-config.json`, link:../timeouts/02-runtime-leases-operator-web.adoc#drain-timeout[Timeouts & Budgets Specification]), the removal of `runtime.json`, `run/runtime.token`, and the socket, the release of the singleton lock, the exit code `0`, and the merge-queue and review-bot leases left in place is implemented, with jobs, workers, the LSP pool, and the web listeners joining it as participants (link:../../../../plan-marshall-documentation/doc/concepts/runtime-lifecycle.adoc#drain[Concepts § Drain]). The participant of the jobs is implemented (link:../../../pm-runtime/doc/developer/runtime-start.adoc#_job_drain_participant[Runtime Start Developer Guide § The Job Drain Participant]): a job a transition creates during drain is recorded `queued`, never admitted; running jobs finish up to the drain timeout; after it the remaining job process groups are terminated and recorded `killed`, and every job still `queued` is recorded as `status: ended`, `fate: killed` without signalling anything. The participants still to be built do this: a `pm_build` call during drain is answered with its queued job; a held `pm_wait` is answered `end`; idle warm workers end; the tasks in progress finish up to the drain timeout. After it the generations of the remaining workers are fenced, which revokes their job tokens (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#job-token[Local Trust: Job Token]). The task leases of the fenced generations are released (their tasks are offered again exactly once after the next start, <<per-project-recovery>>), warm LSP servers shut down, and the build and model slots released (their jobs are settled `killed`). The merge-queue and review-bot leases left in place become orphaned at the next start and are adopted or released there by the evidence rules of <<per-project-recovery>>, exactly as after a crash. The open event streams end with `stream.closed`, and the web listeners close last; their setting is unchanged, so the next start opens them again. Calls arriving during the drain receive a normal representation with `facts.runtime: draining`, and no new task is offered.
* *Stop*: `POST /api/v1/operator/runtime/stop` with `when` (`drain`, the default, or `now`) and `then` (`exit`, the default, or `restart`). `now` is the drain with its wait cut to zero: what still runs is stopped and settled as after the drain timeout (tasks offered again after the next start, jobs recorded `killed`), so the recovery resumes it; a stop with `now` during a drain cuts that drain's wait the same way. `DELETE /api/v1/operator/runtime/stop` withdraws a drain the operator asked while it runs: the runtime admits jobs and offers tasks again and returns to `running`; once the wait has ended and the runtime terminates what runs, the withdrawal is answered `409` (`not_withdrawable`). A drain that a signal started (`pm-operator drain`, the service manager, the OS) cannot be withdrawn.
* *`pm-operator drain`* stays a signal, never an API request, so it works whatever state the runtime is in: it reads `pid` and `start_instant` from `runtime.json`, confirms that the process with that PID has that start instant (never signalling a reused PID), sends `SIGTERM`, and waits for the process to exit, bounded by the wait of `pm-operator drain` defined with the drain timeout, which it reads from `machine-config.json` (link:../timeouts/02-runtime-leases-operator-web.adoc#drain-timeout[Timeouts & Budgets Specification, Drain Timeout]); it has no timeout option of its own. It reports the exit, or, when the bound passes first, that the runtime is still draining, with the recorded PID. Without a live `runtime.json` it reports that no runtime is running and exits `0`; it never starts the runtime.
* *Restart*: with `then: restart`, the runtime finishes its drain as above, starts its successor detached by the on-demand start procedure of `pm-api` (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#_start_modes[Start Modes]), and releases the singleton lock by exiting; the successor waits for the lock and starts. A runtime the service manager runs exits instead with the exit code `75` (`EX_TEMPFAIL`), on which the unit restarts the service (`RestartForceExitStatus=75` under `systemd`, `KeepAlive` with `SuccessfulExit: false` under `launchd`), so the successor runs under the service unit.
* *Update check*: `POST /api/v1/operator/runtime/upgrade/check`, and, while the consent `check_updates` is remembered for the machine, the runtime itself at most once a day (link:../timeouts/02-runtime-leases-operator-web.adoc#update-check-interval[Timeouts & Budgets Specification, Update Check Interval]), asks the organisation's registry of `PM-DIST-1` for the newest release of the machine's platform through its outbound HTTPS client, under the consent `check_updates` (link:../store-schemas/12-machine-stores.adoc#consent[Store Schemas Specification, Consent Before Acting]); with _no_ nothing is fetched. Nothing about the machine is sent beyond the request itself (`PM-ARCH-2`), and the result refreshes the version state. Which credential the runtime presents to the registry and the form of a release in it are open: see link:../../../../plan-marshall-documentation/doc/discussions/open-questions.adoc#registry-credential[Open Questions].
* *Upgrade*: `POST /api/v1/operator/runtime/upgrade` with the version and `when` (`drain` or `now`). The runtime fetches the release and its build attestation, verifies the attestation (signed provenance whose subject is the archive's digest and whose signer is the release workflow of `plan-marshall/plan-marshall-mcp`), checks that it was built from the tag of the requested version (`refs/tags/v<version>`) and that its subject is the archive of the machine's platform for that version, and verifies the archive against the digest the attestation states, never against a digest the registry states alone (a release without a valid attestation is refused with the reason `release_unattested`), unpacks it into a new versioned installation directory beside the current one (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#installation-layout[CLI, Coordination & Security Specification, Installation Layout]), rewrites the service unit where one is installed, records the upgrade (`from`, `to`, step `switching`) as a machine state record, switches both `PATH` links, and then stops with `then: restart`, so its successor is the new `pm-mcpd`. `DELETE /api/v1/operator/runtime/upgrade` withdraws it while the release is fetched and verified; once the links are switched it is answered `409` (`not_withdrawable`). A failure before the switch (fetch, verification, unpacking, or the service unit) is undone before it is reported: the staged installation directory is removed and the previous service unit restored and reloaded, so the installation in force is unchanged; the failure is the upgrade's result with its reason. The exiting runtime, after releasing the lock, waits for its successor's authenticated round trip, bounded by the runtime start timeout (link:../timeouts/02-runtime-leases-operator-web.adoc#runtime-start-timeout[Timeouts & Budgets Specification]); a successor that does not answer is terminated, the links and the unit are switched back, and the previous version is started the same way. The runtime that starts settles the recorded upgrade (Startup Sequence, step 7): the new version records `upgraded` and announces `runtime.upgraded`; the previous version, finding the upgrade still recorded `switching` to another version, records it failed and announces `runtime.upgrade_failed` with the reason. The previous installation directory stays as the way back until the next upgrade removes it. An installation not laid out in versioned directories with the two links, or reached through `PM_MCP_HOME`, is not upgraded by the runtime: the upgrade is refused (`upgrade_not_possible`) with its reason, and the steps by hand of the installation layout stay; there the old installation directory stays until the old runtime has exited, because it starts its jobs through its own `pm-exec` until then.
* *`pm-operator status`* is an API request (`GET /api/v1/status`, link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#local-api[Local API]): it reports `running` only from a successful authenticated round trip, never from the presence of `runtime.json`. When no live runtime is recorded (no `runtime.json`, or its `pid` and `start_instant` do not match a live process) it reports "not running" without starting the runtime; when a live runtime does not answer within the runtime start timeout it reports "not responding" with the recorded PID.
* *Versions apart*: A relay whose own version differs from `runtime.json -> version` forwards normally. The runtime's comparison of the relay's `PM-MCP-Relay-Version` header with its own version and its audit record with both versions are implemented (link:../../../../plan-marshall-documentation/doc/user/operator.adoc#relay-version-mismatch[User Guide § Relay Version Mismatch]); the status data of the mismatch recommends the restart of the runtime. The mismatch is operator-only (`PM-DIST-4`): it is shown in the runtime status to both clients, and no representation carries it (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]). A client of the operator compares its own version with the runtime's on its first request and says so when they differ.
