[#repository-layout]
== Repository Workspace Layout (`.marshall/`)
_Implementation watch: link:../../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-1[PM-WATCH-FS-1]_

Every repository checkout of an enrolled project contains a `.marshall/` directory structured into two distinct regions: git-tracked shared documents and the git-ignored technical directory `.marshall/local/`. It is created by the first run of the project setup workflow in the project's workspace scope, which copies no workflow unit into it: `.marshall/config/` holds a unit only once the team placed or changed it (link:../workflow-dsl/04-ast-node-model.adoc#process-designer[Workflow DSL Specification, Designing a Process]) (link:../domain-extensions/04-setup-state-machine.adoc#project-setup-state-machine[Domain Extensions Specification, Project Setup State Machine]) and is disjoint from the `.plan/` tree of `plan-marshall`, which may exist beside it and is never read or written by `PM-MCP`.

[source,text]
----
<workspace-root>/
├── .gitignore
├── .marshall/
│   ├── config/                          # Team configuration (git-tracked, sparse, Store Schemas § Project Configuration)
│   │   ├── project.json                 # Repository and collaboration policy
│   │   ├── workflow.json                # Plan workflow policy, optional finalize step lanes
│   │   ├── domains.json                 # Overrides of the derived domain detection
│   │   ├── build-map.json               # Seeded file-to-build route table
│   │   └── *.pmwf                       # Only the units the team placed or changed; absent units resolve to the machine, then the default
│   ├── recipes/                         # The project's recipes (git-tracked): each descriptor with its workflow <id>.pmwf
│   ├── skills/                          # Project skill directory: team extension skills (git-tracked, MCP Tools § Skill Extensions)
│   │   └── <name>/                      # One skill: SKILL.md and its supporting files, served as skill://pm/ext/<name>/
│   ├── project-architecture/            # Architecture module enrichment (git-tracked)
│   │
│   ├── epics/                           # Epics (git-tracked, edited only in the shared epic worktree)
│   │   └── <epic_id>/                   # Fully tracked; the epic's FSM state lives in the machine store
│   │       ├── epic.json                # Epic header: identity, workstreams, lifecycle, the list of its sources (no FSM state)
│   │       ├── sources/                 # The epic's source directory: sources.json and the stored sources (03 § The Source Directory)
│   │       ├── spec.md                  # Epic specification (workstream and plan sections)
│   │       ├── queue/                   # Staged per-plan spec definitions
│   │       │   └── <plan_id>.json       # Individual queued plan record and spec reference
│   │       ├── inbox.jsonl              # Append-only event log: messages from plans and epics
│   │       ├── landings.jsonl           # Verified plan landings and post-merge analysis
│   │       ├── register.jsonl           # Findings and watches registers of the epic
│   │       └── resume_anchor.md         # Human- and model-readable epic checkpoint summary
│   │
│   ├── archived-epics/                  # Archived epics (git-tracked, moved in the shared epic worktree)
│   │   └── <epic_id>-<YY-MM-DD>/        # Same per-concern layout; epic.json keeps epic_id
│   │
│   └── local/                           # Git-ignored technical data only, never state
│       ├── worktrees/                   # Worktree root (git checkouts, recreated from branches)
│       │   ├── _epics/                  # Shared epic worktree (one for all epics, fixed branch)
│       │   ├── baseline-<plan>-<sha12>/ # Baseline scratch worktree of plan <plan>, detached at the merge base
│       │   └── <plan_id>/               # Plan worktree: created for execute/finalize, removed afterwards
│       │       ├── .git                 # Git worktree pointer file
│       │       └── <repo-source-files>  # The branch's checkout, including its git-tracked .marshall/
│       │
│       └── temp/                        # Disposable temporary files of the runtime and its jobs
----

Nothing in `.marshall/local/` is state: deleting it loses no plan data. A plan worktree is recreated from the plan's branch by the next step that needs it (<<worktree-lifecycle>>), the shared epic worktree from its branch `pm-mcp/epics`, and `temp/` is never read across calls. All server-owned state of the project lives in the per-project machine store (xref:03-project-store.adoc#machine-store[Per-Project Machine Store]).

The repository `.gitignore` partitions `.marshall/`: `.marshall/*` is ignored as a blanket, `!.marshall/config/`, `!.marshall/recipes/`, `!.marshall/skills/`, `!.marshall/project-architecture/`, `!.marshall/epics/`, and `!.marshall/archived-epics/` are un-ignored, and `.marshall/local/` stays fully ignored. The epic trees are fully tracked; no re-ignore rule below them exists. The first run of the project setup workflow writes this partition and every later run verifies it; the entries for the `.plan/` tree of `plan-marshall` are left untouched.

[#worktree-lifecycle]
=== Worktree Lifecycle
_Implementation watch: link:../../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-5[PM-WATCH-FS-5], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-4[PM-WATCH-JOB-4], link:../../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-6[PM-WATCH-FS-6]_

A plan never moves (`PM-ARCH-5`). Its worktree is only a git checkout, created for execute and finalize and removed afterwards; the plan's `mcp/status.json` records the worktree's presence as `worktree_path` (link:../store-schemas.adoc[Store Schemas Specification], Workflow State Store):

* *Creation*: `execute.worktree-init` (or `land.worktree-init` of the `land` lane) creates the plan's feature branch and the git worktree (`finalize.adopt-pr` of the `adopt` lane creates the worktree on the adopted pull request's existing head branch) at `.marshall/local/worktrees/<plan_id>/`, then records the canonical absolute path of the worktree root (`Path.toRealPath()`) as `worktree_path` in one journaled transaction under the plan lock. The plan directory stays in the machine store; nothing is moved or copied into the worktree.
* *Use*: While `worktree_path` is set, the plan's jobs and the writer workers serving its tasks run with the worktree root as working directory (link:../job-runtime.adoc[Job Runtime Specification], Working Directory Selection), so project instructions and skills load natively in a worker; without a worktree they run in the project checkout. Every server-owned repository write of the plan happens in the worktree, never in the main checkout.
* *Removal*: `default:branch-cleanup` removes the worktree (`git worktree remove`, run by a job whose working directory is the main checkout, never inside the worktree) and sets `worktree_path` to `null` in the same transaction that records the removal. A removal that timed out is recorded only after the partial-removal re-check (link:../timeouts/01-job-budgets-and-waits.adoc#worktree-remove-recheck[Timeouts & Budgets Specification]) found positive evidence that it completed; it is never retried with `--force`. No store keeps pointing at a removed worktree: every post-merge step, and a resume after branch-cleanup, reads `worktree_path: null` and either runs against the main checkout or refuses fail-closed-clean, never on a stale path.
* *Crash Consistency*: Creation and removal are idempotent and reconciled under the plan lock on retry and on the first call after a runtime start: a recorded `worktree_path` whose worktree no longer exists is cleared with an audit record, never silently followed, and a worktree of the plan's branch that exists but is not recorded is adopted by the creating step. A plan whose worktree was deleted with `.marshall/local/` gets it recreated from its branch by the next step that needs one.
* *Baseline Scratch Worktrees*: Baseline re-runs of a failing whole-tree gate (link:../job-runtime/03-parsers-and-gates.adoc#_gate_honesty_verification[Job Runtime Specification, Gate Honesty Verification]) use one scratch worktree per plan and merge base, `.marshall/local/worktrees/baseline-<plan_id>-<sha12>/`, where `<sha12>` is the first 12 hex digits of the merge-base SHA. It never carries plan state and is never recorded in `worktree_path`:
** *Creation*: created on the plan's first base run by the native `git.worktree-add`, detached (no branch) at `merge-base(HEAD, origin/<base_branch>)`.
** *Reuse*: every later base run of the plan reuses it while the merge base is unchanged, after checking that it is clean (`git.status` empty and `HEAD` at the merge base); a dirty or moved one is removed and created again, never used.
** *Replacement*: when the merge base moves, the old baseline worktree is removed and one for the new merge base is created.
** *Removal*: removed (`git.worktree-remove`, from the main checkout) when the plan leaves `finalize`, is archived, or is aborted; a removal that times out follows the partial-removal re-check (link:../timeouts/01-job-budgets-and-waits.adoc#worktree-remove-recheck[Timeouts & Budgets Specification]).
** *Recovery Sweep*: the project's recovery after a runtime start, and every plan-worktree enumeration, removes a baseline worktree whose plan no longer resolves or is terminal (archived or aborted), with an audit record; it never removes one whose plan is live. A `baseline-*` directory is never mistaken for a plan worktree or adopted as one.

[#linked-worktree-recognition]
=== Recognition of a Linked Worktree by the Path Confinement

The path confinement of `PM-SEC-2` accepts a project path outside the enrolled repository root only inside a live linked git worktree of that root. The check reads the plain files git writes for a linked worktree and runs no git process. A directory of the live set counts as a linked worktree of the root only when all of the following hold:

* *Pointer*: Its `.git` is a file that names the git directory of the worktree after the prefix `gitdir:`.
* *Registration*: The canonical path of that git directory is a direct child of `<project_root>/.git/worktrees/`, and neither `<project_root>/.git` nor `<project_root>/.git/worktrees` is a symbolic link.
* *Common Directory*: The `commondir` file of the git directory names `<project_root>/.git`.
* *Back-Pointer*: The `gitdir` file of the git directory names the worktree back: the path it holds, resolved against the git directory when it is relative (the form git writes with `worktree.useRelativePaths`), is the `.git` file of that worktree.

Each of the three files is a regular file, never a symbolic link, that is not empty and not larger than 8192 bytes. A path inside any other directory outside the root is refused with `path_traversal_rejected`. This holds for a directory whose git directory carries a fitting `commondir` file but lies outside `<project_root>/.git/worktrees/`, and for a second directory that points at the git directory of a registered worktree.

A worktree directory moved by hand (with `mv`, not with `git worktree move`) keeps a `gitdir` record that names its old location. It is refused until `git worktree repair` has rewritten the record.

[#shared-epic-worktree]
=== Shared Epic Worktree
_Implementation watch: link:../../implementation-watch/filesystem-layout.adoc#PM-WATCH-FS-4[PM-WATCH-FS-4], link:../../implementation-watch/store-schemas.adoc#PM-WATCH-STORE-30[PM-WATCH-STORE-30]_

Git-tracked epic state (`.marshall/epics/**`) is edited only in one shared epic worktree and reaches the default branch only through the epic landing (`PM-ARCH-5`):

* *Location*: `.marshall/local/worktrees/_epics/`, beside the plan worktrees under the same git-ignored root. The key `_epics` lies outside the link:../identifiers/01-general-rules-and-registry.adoc#id-plan-id[plan ID grammar], so no plan can collide with it.
* *Branch*: One fixed, long-lived branch (`pm-mcp/epics`) created once off `origin/<default branch>`; the ledger changes of every epic are committed there.
* *Lifecycle*: Created on the first epic-ledger write and reused as-is afterwards (idempotent). No normal operation removes it, including the epic landing; only `pm-operator epic-worktree teardown` does. Plan-worktree enumeration, startup recovery, and any orphan sweep recognise it and never treat it as an orphaned plan worktree.
* *Concurrency*: The per-concern ledger layout lets concurrent epics write disjoint files in the one working tree. Ledger writes serialize per epic under the epic lock; git operations on the worktree serialize under the project-wide lock `<PM_MCP_BASE>/projects/<project_id>/locks/epics-worktree.lock`.
* *No Plan Mechanics*: The ledger is git-tracked, so the worktree is a second checkout of it: no per-scope executor and no plan-keyed merge lease apply. The epics' non-tracked FSM state lives in the machine store (`epics/<epic_id>/`, xref:03-project-store.adoc#machine-store[Per-Project Machine Store]) and the epic locks live there too, outside the tree (link:../store-schemas.adoc[Store Schemas Specification], § Lock-Free Snapshot Reads, Transaction Locks & Leases).
* *Epic Ledger Resolution Seam*: Every read and write of `.marshall/epics/**` (epic header `epic.json`, queue rows, inbox, landings, the findings and watches registers, spec documents, the epic's sources, `pm://epic/**` resources, and the epic resource of the local API) and every plan-side access (the `default:emit-landing` inbox append, a child plan's read of its specification, the `running` observation) resolves through one resolver to the shared epic worktree copy; nothing reads the primary checkout's copy. A specification staged in the worktree but not yet landed is served to the child plan through this seam.
* *Stranded-Change Guard*: Before the first ledger write is routed into the shared epic worktree, the runtime checks the primary checkout for uncommitted or unpushed changes under `.marshall/epics/**`. If any exist it refuses with `ledger_changes_stranded`, naming the paths, until the operator lands them or carries them into the worktree with `pm-operator epic-worktree adopt`; two diverging copies are never left behind silently.
