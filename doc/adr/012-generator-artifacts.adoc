= ADR 012: Generator Artifacts per Module
:nofooter:

== Status

Accepted, amended by ADR link:016-schemas-are-files-of-the-implementing-module.adoc[016] (`pm-core:tests` also carries `SchemaResource`),
and by the operator's decision of 2026-11-15 (`pm-core:tests` also carries the assertion-message scanner, PLAN-V2-103)

== Date

2026-10-31; amended 2026-11-06 by operator decision (PLAN-V2-92: the provider artifacts `pm-provider-ci:tests` and
`pm-provider-git:tests`); amended 2026-11-15 by operator decision (PLAN-V2-103: the shared assertion-message scanner).

== Context

The migration of about 400 test classes to `cui-test-generator` (PLAN-V2-85 to PLAN-V2-93) creates typed generators for
domain types such as findings, profiles, store records and queue tasks. Without a shared home every test class, and
every module, would build its own. `pm-runtime` already publishes a test JAR (`TestBases`, `FakeBus`,
`FakeSecretService`) that the assembly's tests consume, so the build already has a working pattern for a test-scope
artifact deployed with the `SNAPSHOT`.

The dependency rules of the repository decide who may consume which artifact: `pm-core`'s types are visible to
`pm-workflow`, `pm-runtime` and every provider; `pm-provider-http`'s types to `pm-provider-github`, `-gitlab` and
`-sonar`; `pm-workflow` and `pm-runtime` may not depend on each other, so only the assembly sees both.

== Decision

Each module that provides generators useful to another module, or that needs a generator for one of its own types in two
or more of its own test classes (the amendment of 2026-11-06 under Consequences), publishes its test scope as a
`tests`-classified test JAR, built by `verify` and deployed like every other artifact of the repository. The artifact holds the package
`de.planmarshall.<module>.testing.generators` with one `TypedGenerator<T>` per domain type, named `<Type>Generator`,
and one factory class per artifact (`CoreGenerators`, `WorkflowGenerators`, `RuntimeGenerators`, `HttpGenerators`,
`CiGenerators`, `GitGenerators`) that registers the generators in one place. The framework's `@GeneratorsSource` selects only the built-in `GeneratorType`
enum, so the factory is consumed through `@TypeGeneratorFactorySource(factoryClass = …, factoryMethod = …)`; the
factory is still the one registration point of the artifact.

The consumption matrix:

* `pm-core:tests` — `pm-workflow`, `pm-runtime` and every provider module.
* `pm-provider-http:tests` — `pm-provider-github`, `pm-provider-gitlab` and `pm-provider-sonar`.
* `pm-provider-ci:tests` — `pm-provider-github` and `pm-provider-gitlab`, the adapters of the CI contract.
* `pm-provider-git:tests` — no module of this repository; the assembly `plan-marshall-mcp` may consume it.
* `pm-workflow:tests` and `pm-runtime:tests` — the assembly `plan-marshall-mcp` only.

A consumer declares the artifact as a test-scope dependency of type `test-jar`; its version comes from the root POM's
`dependencyManagement`, never from a literal. The enforcer rules of the root POM keep their meaning for a test-scope
dependency: `pm-core:tests` is admitted for the modules that already depend on `pm-core`, and the tests of
`pm-workflow` and `pm-runtime` stay refused for each other, test scope included.

`pm-core:tests` carries a third kind of shared test support beside the generators and `SchemaResource`: the
assertion-message scanner of the `junit-core` rule that every assertion carries a message of 20 to 60 characters. The
operator decided on 2026-11-15 (PLAN-V2-103) that the scan logic is published once, in
`de.planmarshall.core.testing.assertions`, and that every module guards its own test tree with a thin test over
it—a per-module copy of the scanner class was the alternative, and a `pm-core` test reading a sibling module's
sources by relative path was the other. The scanner reads a package path and a source root, so a module's guard names
its own base package and reads its own `src/test/java`; nothing of a consumer's tree is compiled into the artifact.

The scanner of the assertion-message family (PLAN-V2-160, #532 to #534) is four parts behind the entry point
`AssertionMessages`: the lexer `CodeView` (code, comments, strings and text blocks apart), the argument splitter
`ArgumentSpans`, the constant resolver `ConstantScopes` and the verdict on one call `MessageMeasurement`. A message is
measured when it is one string literal, a supplier whose body is one string literal, or the name of a
`static final String` constant of the same file that the name binds to at the assertion. Every other message shape is
accepted unmeasured and listed in the scan's `unmeasured` report with its line and shape; the guards do not fail on
the report, which counts what the rule does not reach. The heading of an `assertAll` is exempt from the 20-to-60 rule:
it labels a group whose assertions carry their own messages, which are measured. The rewording of the family's
first pull request, #451, changed 45 message literals (measured at `19b0ae6b`); its merge message sums its table to 44
and its text to 29 plus 15, and neither figure is the measured one.

The rule for later work: **a test that needs a generator for a type of another module takes it from that module's
artifact; a new generator for a type of this module goes into this module's artifact, not into a test class.**

== Alternatives Considered

* **A single repository-wide generator module.** It would give every module one artifact, but it would have to depend
  on every module it generates for, turning the dependency direction and publishing the internal types of all modules
  in one place. Rejected.
* **Generators in the production source of each module.** Test data would then ship in the production JAR and a
  consumer's test scope would see the generators only through the compile classpath. Rejected.
* **Generators copied into each consuming test tree.** This is the duplication the plan exists to remove, and it
  would let two modules' generators for the same type drift apart. Rejected.

== Consequences

* A module that adds a generator publishes it with its own artifact; the artifact must be built by `verify` and
  deployed with the `SNAPSHOT`, so a consumer needs no local build of the producer.
* The five generator artifacts package only their generator package: the `test-jar` goal's `includes` narrows the artifact
  to it, so a module's own test classes, fixtures and fakes are not published. `pm-core:tests` adds the assertion-message
  scanner of PLAN-V2-103 to the artifact beside the generator package and `SchemaResource`; the scan's own controls
  (`AssertionMessagesTest`) stay unpublished, because the `*Test` exclusion removes them. `pm-runtime:tests` keeps its
  whole test scope, because the assembly already consumes `TestBases` and the fakes there; the generator package joins
  it.
  PLAN-V2-106 started the replacement of the hand-written fakes by EasyMock doubles; PLAN-V2-136 completed it and keeps
  `FakeBus`, `FakeSecretService` and `FakePmExec` as the closed list of ADR
  link:026-the-kept-hand-written-test-doubles-are-a-closed-list.adoc[026] (corrected 2026-11-14, PR #416).
* In this plan `pm-workflow` and `pm-runtime` declare `pm-core:tests` and consume it, and `pm-provider-github` and
  `pm-provider-gitlab` declare `pm-provider-http:tests` and consume it for the endpoint of their mock server.
  `pm-provider-sonar` may consume the shared-HTTP artifact but builds no shared-HTTP type by hand in its own tests, so
  it declares no dependency rather than an unused one.
* `BuildGuardsIT` proves with fixture projects that a test-scope dependency on `pm-core:tests` is admitted for
  `pm-workflow`, `pm-runtime` and a provider, and that a dependency of `pm-runtime` on the tests of `pm-workflow` (or
  the reverse) is still refused.
* A later plan that needs a generator for a type of its own module adds it to that module's artifact; it does not
  introduce a second generator module.
* The operator decided on 2026-11-06 (PLAN-V2-92) that a provider module that needs a generator for its own type in
  two or more of its own test classes publishes it. `pm-provider-ci` (`RepositoryRef`, factory `CiGenerators`) and
  `pm-provider-git` (`GitCredential`, factory `GitGenerators`) therefore publish `pm-provider-ci:tests` and
  `pm-provider-git:tests`. Like the other new artifacts, the two carry only their generator package. In PLAN-V2-92
  neither `pm-provider-github` nor `pm-provider-gitlab` declares `pm-provider-ci:tests`, and no module of this
  repository consumes `pm-provider-git:tests`.
* The "if cheap" sub-items of the scanner work (item 46(b) of PLAN-V2-114) are closed without a change (recorded
  2026-11-21, PLAN-V2-163): the class Javadoc of the schema helper `SchemaValidation` of `pm-core` no longer carries an
  upstream changelog statement, and its claim that the registry is thread-safe while its configuration is not modified
  is the library's own documented contract, which no test of this repository measures; the check count that
  ADR link:028-the-json-schema-validator-is-on-the-3-line.adoc[028] shipped was removed by #537 and is not restored.
