= ADR 024: The Duration of the Full Verify, Measured and Cut
:nofooter:

== Status

Accepted

== Date

2026-11-13

== Context

The operator reported on 2026-11-12 that a full `verify -Ppre-commit` of this repository takes about 22 minutes on the
local host, too long to run whole inside the build daemon's bound of 1120 s, so every plan splits it into per-module
runs. Earlier landings of the epic record gate lengths between 673 s and 1275 s on the same host; they corroborate the
figure but do not decompose it. The question is where the time goes, which share of it is test execution, and which
causes can be removed without lowering the quality of the tests.

[#baseline-verdict]
=== The Verdict on the 22 Minutes

The reported 22 minutes do not hold for `verify -Ppre-commit` on an idle host, which takes 650 s and 654 s (10:49 and
10:52 min), of which about 515 s (79 %) is the test phase; they match the coverage lane `verify -Pcoverage` (21:17 min,
1278 s), and a shared host adds about 29 % to the gate (run 1, 14:04 min).

The sum of the test times in the reports (331 s, measured with the coverage agent) is smaller than the test phase of the
gate (515 s): at least 184 s of the test phase is spent outside the test methods — in the start of the test JVM, class
loading, the extensions and the class-level setup the reports do not attribute to a test.

=== The Ranked Cost

cited by the decisions and by the test-level section, so row 8 (13.5 s, the root module) keeps its place before rows 9
and 10 (17.4 s and 15.3 s). The phase figures are those of the
reference run 3 and the two-part split above; the class figures come from the coverage lane and carry the JaCoCo agent,
so a class close to the cut-off (`JudgmentVerificationTest` 5.03 s above it, `GitHubCiProviderTest` 4.98 s below it)
is ranked on an upper bound. The decision names where the item is dealt with: *fix in 3* (a build-level change in the
repository's own configuration, kept only when the reference run shows the gain), *fix in 4* (a test-level change),
*finding for 5* (recorded as an input of the test-design findings), or *keep* with its reason.

Two configuration facts carry the largest items:

* The test JVM. The parent `pm-mcp-parent` 0.1.1 configures `maven-surefire-plugin` with `reuseForks` `false` and the
  default `forkCount` of 1, so Surefire starts one fresh JVM per test class, one after the other: 345 JVMs in
  `pm-core`, 202 in `pm-runtime`, 132 in `pm-workflow`. Each pays the start of the JVM, the loading of its classes and
  the warm-up of the JIT before its first test, and none runs beside another.
* The reactor. `.mvn/maven.config` holds `-T1`. It was set by `0e0d128a` (2026-10-08), the commit that split the engine
  modules into this repository; neither its message nor a later commit gives a reason. `.mvn/jvm.config` holds only
  `--enable-native-access=ALL-UNNAMED`. After `pm-core`, the modules `pm-workflow`, `pm-runtime` and the provider
  modules depend on nothing but `pm-core` and two provider modules, yet run one after the other.

== Decision

The reference of every figure in this ADR is the median of idle runs of the full reactor routed through the build
daemon, with the host load stated per run; a figure taken under load is marked and is not the reference. The target is
a full `verify -Ppre-commit` of at most 600 s on an idle host (median of three runs), inside the daemon's 1120 s bound
without a split, and the ranking covers every test class and build phase above a cut-off of 5 s (operator's decision of
2026-11-12 at refine).

Every item of the ranked cost carries the decision stated in its row. The fresh JVM per test class is removed in the
repository's own configuration; with that one change the gate takes 247 s (median of three consecutive green runs: 256 s,

[#operator-leads]
=== Leads for the Operator

Findings outside this repository's own configuration are not changed by this plan:

* *The parent's `reuseForks`.* `pm-mcp-parent` 0.1.1 configures `maven-surefire-plugin` with `reuseForks` `false`, which
  starts a fresh JVM for every test class. This repository overrides it (change A); every other repository built on the
  parent pays the same cost. Setting `reuseForks` `true` in the parent would give them the gain and let this
  repository drop its override.
* *The forked lifecycles of the `pre-commit` profile.* The parent's `rewrite:run` forks the lifecycle up to
  `process-test-classes` and `javadoc:javadoc` up to `generate-sources`, so the `validate` executions run up to three
  times per module, and both run on the `pom` modules (the root, `pm-providers`), where they process nothing; the root
  takes 13.5 s (ranked row 8). Binding the profile's goals without a forked lifecycle, or skipping them for `pom`
  packaging, is a change of the parent.
* *CI and dependencies.* The measurement names no CI workflow setting and no dependency as a cost above the cut-off.

== Alternatives Considered

* *Taking the operator's 22 minutes as the baseline without a measurement:* not taken, because the plan fixes only what
  the measurement shows; the measurement attributes the 22 minutes to the coverage lane, not to the pre-commit gate.
* *Taking the loaded run 1 as the reference:* not taken, because the host is shared and a loaded figure measures the
  other plans as much as this build.
* *Changing the parent's `reuseForks` instead of overriding it here:* not taken, because a parent change is outside
  this plan; it is a lead for the operator (<<operator-leads>>).
* *Applying all three build-level changes together:* not taken, because each change is kept only on its own measured
  gain; after change A the remaining two did not justify their risk (<<build-level-changes>>).

=== What Follows

* Every later figure of this plan is compared with the idle reference of 650 s and with the quality baseline per module;
  coverage per module may not fall below it.
* The per-class times above carry the coverage agent; a ranking that relies on them states so.
* Plain `verify` and the integration-test lane have no measured baseline in this ADR.
* The test classes of a module share one JVM. A new test class that changes process-global state (a static field, a
  system property, the default locale) restores it, because the class after it now runs in the same JVM.
* `.mvn/maven.config` keeps `-T1`; a parallel reactor (change B) and parallel test JVMs (change C) are the levers left
  if the gate grows towards the target again, each to be measured before it is kept.
