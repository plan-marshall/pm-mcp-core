## Objective

The role-name grammar `^[a-z][a-z0-9-]{1,31}$` (2 to 32 characters) is written out as a `Pattern` in twenty classes of `pm-core`, `pm-workflow` and `pm-runtime`, each with its own field, anchors and error text. The specification defines it once (`doc/specification/identifiers/01-general-rules-and-registry.adoc`, entry `id-role-name`, restated as the JSON-schema `pattern` in a dozen schema blocks of `store-schemas/` and in `model-work/01`), so a change of the grammar is a change in twenty places and a new record that carries a role copies the text again (the decision records of PLAN-V2-23 and PLAN-V2-60 will). Operator decision 2026-10-29 (decision 17 of 18, option 1): **a small refactor plan that gives the role-name pattern one definition and replaces the copies, with a test that fails if a copy is added.**

Five of the sites serve the identifier `client_id` (a harness name), which the registry gives the same text under its own entry `id-client-id`; they are given the same treatment under their own name, because a guard on the text cannot tell the two apart. The plan changes no behaviour: every class keeps its own null handling, its own error text and its own tests, unchanged.

## Deliverables

The pattern stays anchored: only `WorkflowStatus.requireMatch` prints the pattern in its refusal (line 491), so the anchored text keeps every message byte-identical; every caller uses it through `matcher(..).matches()`, so anchored and bare copies behave the same. Tests (JUnit 5, `@DisplayName`, AAA, `@ParameterizedTest` for the variants), `RoleNameTest` and `ClientIdTest`, with every edge case of the grammar: two characters accepted (`ab`), one refused (`a`), exactly 32 accepted and 33 refused, the empty string, a leading digit, a leading hyphen, upper case, `_` (a role name has no underscore; the registry's rule 3 gives `_` to names that must be tool names), `.`, `/`, a space, a trailing newline (`ab\n` refused: `matches()` is a full match), a trailing and a doubled hyphen (accepted today by every copy: the grammar admits them; pinned so a tightening is a decision), non-ASCII letters and full-width forms, `null` raising `NullPointerException`; the shipped role names and the examples of the registry (`implement`, `review-code`, `triage-review`) accepted. ## Standing Constraints

- **No behaviour change.** Every caller keeps its null handling (`Objects.requireNonNull` before the match, or the `NullPointerException` of `matcher(null)`), its exception type and its message text. - **The home is `core.id`, which depends on nothing.** `core.store`, `core.queue`, `core.role` and the other two modules depend on it; it depends on none of them. A new import from `core.id` into another `core` package fails the review.

- **Order.** The plan is sequenced after the plans that edit a replaced class or add a record carrying a role (Dependencies and Sequencing).
