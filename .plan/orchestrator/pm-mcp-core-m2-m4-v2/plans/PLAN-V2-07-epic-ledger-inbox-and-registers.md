## Objective

Build the second half of the epic ledger records that no package builds: the epic inbox `inbox.jsonl` and the findings and watches registers `register.jsonl` of `.marshall/epics/<epic_id>/` (`store-schemas/04-epic-and-change-ledger.adoc`, § Epic Inbox & Plan Mailbox Records, § Findings and Watches Registers). At `d95641dc` no class reads or writes either (`pm-workflow/.../workflow/epic/` holds `EpicTokens` and `package-info.java` only; `ChangeLedger` is `change-ledger.jsonl`), while `plan-and-epic-control` appends the operator's acts to the inbox in the act's transaction, `epic-resource-and-release` reads the registers for its archive check, and `epic-review` writes them. This plan builds the shared message-event record and its codec, the inbox store (append under the epic lock with a store-assigned never-reused `message_id`, the fold of a message's events, the distinct empty and unreadable states), the register item record and codec, and the register store (append-only, store-assigned `EI-<n>`, the current record of an item is the last readable line), with the parity tests that pin them to the specification's blocks. The plan mailbox `mcp/mailbox.jsonl` shares the message record but is another store in another scope and has no package: its store is left out, its fold is not. What the consumers add is behaviour (who appends which event and when), plus the members the register block lacks (Claim Labels).

## Deliverables

1. **The message event record, its codec and the fold** (`core.store`, new): `EpicMessageEvent` with every member of the `MessageEvent` block in schema order (`format_version` 1, `event` (`message`, `claimed`, `processed`, `consumed`, `annotation`), `message_id` `^msg-[0-9]{4,}$`, `at`, `sender` (`scope` `plan`/`epic`, `id` in the plan-id grammar), `kind` (the 16 values, each knowing whether it is an inbox or a mailbox kind from the block's description), `summary` 1 to 200, `body` at most 16384, `payload` (an object; kept as the parsed JSON object, not interpreted), `by`, `outcome`, `note` at most 2000). The members the block's descriptions restrict to an event type are refused on another type (`sender`, `kind`, `summary`, `body`, `payload` on `message` only; `outcome` on `processed` only; `note` on `annotation` only; `by` on the four later events); which of `sender`, `kind` and `summary` a `message` event must carry the block does not say: the outline reads Model Work § Plan-Scope Outbox Link (`outbox:send` offers `kind`, `summary` 1 to 200, `body` 1 to 16384) and decides, and the ADR records it. `EpicMessageEventCodec` as `EpicHeaderCodec` (public `MEMBERS` and `REQUIRED` in schema order, strict reading, writer in schema order). `EpicMessageFold` is a pure function from the events of one message to its state: for the inbox `pending` (the `message` event only), `claimed`, `processed`; for the mailbox `unconsumed`, `consumed`, and `unknown` when a referencing line is unreadable; the empty states of a whole file (`no_file`, `empty_file`, `all_processed`) and `unreadable` (with the failing line number) are distinct values and are never read as each other. **Done when:** every event type round-trips; a member on the wrong event type, an unknown member, a `message_id` outside the pattern and a body over 16384 are refused with the member named; the fold has a test per state and per empty state, and a file with one unparseable line is `unreadable` with its line number, never `empty_file` or `all_processed`.
2. **The inbox store** (`core.store`, new): `EpicInbox` appends one event at a time to `inbox.jsonl` of a ledger directory under the epic lock (`LockKey.epic`) through `JsonlStoreFile.append` (a torn tail is repaired first and its audit record handed to the caller's `AuditSink`), never rewrites or removes a line, and reads without a lock. The store assigns `message_id` as the next number above the highest ever written **including the ids of lines it cannot parse** (a shared helper `EpicLedgerIds`, package-private, which scans the raw lines and is also the register store's allocator, Deliverable 4); an id is never reused, and a caller never supplies one; the sender of a `message` event is derived from the calling scope (a `plan_id` or an `epic_id` the server passes from the scope that appended, never a field the model supplies). `claimed`, `processed`, `consumed` and `annotation` for an unknown message and for one already folded terminal are refused (the refusal is a value or a `StoreRefusal` as the existing logs do, named by the outline); a `message` event whose id exists is refused. A read reports the entries (accepted or refused with the line number), the fold per message, the empty states, and a duplicate `message_id` produced by a git merge of two ledgers as a refused line, not as a second message. The appends to another epic's inbox (a `transfer_offer`) take that epic's lock: the caller orders the epic locks by `LockOrder`; the store does not hold two. **Done when:** `PM-WATCH-STORE-32`'s inbox guard is a named test: two appends from one sender yield two distinct ids and two `message` events, also after a restart (a new store object over the same file) and after a merge (a file holding the lines of two branches), and a `message` event with an existing id is refused; the highest-id rule is tested with a refused line holding the highest id; a write without the epic lock is an internal fault and writes nothing; an append after an injected torn tail repairs it first and hands the audit record over; concurrent appends from two threads under the lock yield distinct ids and whole lines.
3. **The register item record and its codec** (`core.store`, new): `EpicRegisterItem` with every member of the `EpicRegisterItem` block in schema order (`format_version`, `item_id` `^EI-[0-9]+$`, `register` (`findings`, `watches`), `statement` 1 to 2000, `rules[]` of 1 to 400 characters, `origin` (`kind` `landing`/`message`/`observation`, `ref` nullable), `state` (`open`, `kept`, `dropped`, `promoted`), `trigger` (null or `kind` `landing`/`base_advanced`, `plan_id` nullable, `paths[]`), `promoted_to` nullable, `opened_at`, `updated_at`). Record invariants from the block's descriptions: `trigger` is set for a watch and null for a finding; `promoted_to` is set exactly when the state is `promoted`; `paths` only on a `base_advanced` trigger is **not** stated and is not enforced. `EpicRegisterItemCodec` as in Deliverable 1. The state transitions (which state moves to which, who may move it) are `epic-review`'s and `epic-resource-and-release`'s and are not built here. **Done when:** a finding and a watch of every state round-trip; a watch without a trigger, a finding with one, a `promoted` item without `promoted_to`, a `promoted_to` on another state, a statement over 2000 and an `item_id` outside the pattern are each refused with the member named.
4. **The register store** (`core.store`, new): `EpicRegisterStore` appends the full record of an item for every change to `register.jsonl` under the epic lock (the same `JsonlStoreFile` discipline as Deliverable 2), allocates `item_id` as the next number above the highest ever written including unparseable lines (`EpicLedgerIds`), and refuses a record for an `item_id` the file does not hold when the call is an update and a caller-supplied id when the call is an addition. A read returns the **current record of each item, the last readable line with its `item_id`**, in the order of the items' first appearance, the refused lines with their numbers, and the three file states of Deliverable 1; keeping an item as a finding or moving it to the watches is a new record with the other `register` (the store checks the record, not the move). The read exposes the one filter two consumers need: the open findings (state `open`, register `findings`), which the archive check counts and the operator's summary shows. **Done when:** an item changed three times reads as its third record; a torn or refused last line leaves the line before it current and is reported; ids are monotonic and never reused (also over a refused line holding the highest id and a restart); an item moved to the watches reads from the watches; the open-findings filter matches the definition above on a fixture of all four states in both registers; a write without the lock is an internal fault.
5. **Schema parity** (R10). `EpicMessageSchemaParityTest` reads the `MessageEvent` block (the first block after `[#epic-inbox-record]`) and `EpicRegisterSchemaParityTest` the `EpicRegisterItem` block (after `[#epic-registers]`), with `SpecificationDocument.jsonBlockAfter`, in the pattern of `TaskQueueSchemaParityTest` and of the first plan's `EpicHeaderSchemaParityTest`: the codec's `MEMBERS` and `REQUIRED` equal the block's `properties` and `required` in schema order, the enums (`event`, `kind`, `sender.scope`, `register`, `origin.kind`, `state`, `trigger.kind`), the patterns, the length bounds and the format version equal the code, and every event type and every item state the codecs write validates against the block (`networknt`, as that test does; no new dependency). The blocks stay byte-stable. The register block lacks three things the specification states in prose, and **this plan does not invent them**: (a) "the task that opened it" and the reason of `dropped` (`model-work/08-epic-coordination.adoc` line 251 states both of an item; the block has no member for either, and `additionalProperties` is `false`; the drop reason exists only in the review draft's `disposition.reason`), (b) the `rules` item length (the block says 400 characters, the `submit register_item` text at the same line says 512), (c) the annotation of a processed message (`store-schemas/04` line 56 refuses an `annotation` for an already-folded-terminal message, line 310 says a correction of a landing is an `annotation` event in the inbox). Each is recorded in the ADR and the package file's hand-over to `epic-review` / the operator, and a block is changed only if the operator decides it and the code and the test change with it. **Done when:** the two blocks are read by tests and equal the code; (a) to (c) are in the pull request body with the lines they cite; no `[source,json]` block of `store-schemas/04` changes unless code and test changed with it.

## Standing Constraints

Plan-specific constraints (the epic-wide rules are in `standing-rules.md`, named in the First Instruction above):

- **Log messages: none expected.** This plan is expected to add no INFO, WARN or ERROR message: the stores return values and throw the exceptions the existing stores throw. If the trace matrix shows one, it goes into `CoreLogMessages` at the next free identifier of its level (ADR `doc/adr/005-one-log-message-holder-per-module.adoc`), and the plan says so in its inbox message.
- **No consumer behaviour.** No epic task, no landing reconciliation, no `coordinate` decision, no `outbox:send` link, no endpoint and no commit to the shared epic worktree is built. The plan appends and reads; who appends what is the consumer's.
- **A log is append-only.** No method removes or rewrites a line; a correction is a later event or record. The only change of bytes the store makes is the cut of a torn tail by the next append (`JsonlStoreFile`).
- **The shared specification files are touched by section** (see the first plan); the register block and the message block are not edited unless the operator decides one of the gaps of Deliverable 5.
- **Sonar** (where the project analyses its pull requests: `runbook_lane resolve` reports `sonar: configured`): an open Sonar issue is fixed in a pushed commit, or dismissed with a stated reason recorded as `{issue-key}: {reason}` in the run's progress record; the merge gate reads the open-issue count at the head, `unknown` for a failed read and never `0`.
