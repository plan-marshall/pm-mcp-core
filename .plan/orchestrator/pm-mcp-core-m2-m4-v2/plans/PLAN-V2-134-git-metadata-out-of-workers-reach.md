## Objective

A worker's write set holds the whole project root, so it holds the repository's git directory and the `.git` link file of every worktree, and Landlock cannot leave out a path below a granted one. A value a worker writes there (`core.fsmonitor`, a hook, a filter driver, a link file that points a worktree at a git directory of its own) runs outside every confinement the next time the operator's shell prompt, editor or a `git` job of the CLI variant runs `git` in the checkout. The merged specification (`job-runtime/02#git-metadata`, `PM-WATCH-JOB-48`) closes this in four parts: the git metadata is not writable for a worker, the launch report states whether that held, a digest of it is compared when a worker ends and before every `git` job, and the tracked hook definitions are protected paths. None of it exists in the code: the confinement composer grants the project root and names no git path, the launch report has four members and refuses a fifth, the job record has no `git_metadata`, no digest is taken, and no protected-path matcher exists in any module of this repository.

This repository builds no binary. The mount and the sandbox rule are the work of the launcher `pm-exec` in `pm-mcp-clients` and are **owed outside this repository**; what `pm-runtime` and `pm-core` can do, and this plan does, is everything the runtime owns: find the paths, hand them to the launcher as one more option, read and record the launcher's statement (the honest value is `unenforced` until a report says `enforced`), take and compare the digest with the launcher as a test double that applies nothing, refuse the `git` job, audit it and signal the hold, and match the hook definitions as protected paths. It builds no enforcement, no hold of its own in the engine and no operator act.

## Standing Constraints

Plan-specific constraints (the epic-wide rules are in `standing-rules.md`):

- **No enforcement is built here.** The mount namespace and the macOS sandbox rule are `pm-exec`'s (`pm-mcp-clients`), outside this repository (`CLAUDE.md`: this repository builds no binary). The runtime composes, passes, reads and compares; a test launcher that applies nothing is the fixture. A review finding that asks for the mount is answered with the owed list.
- **The honest value is the safe value.** A record never says `enforced` unless a launch report says so; no code path writes `enforced` except the copy of a report's value.
- **The digest is read-only and runs no git.** It reads files, never writes or repairs one, starts no process and uses no JGit. An unreadable input is a difference (fail closed). The digest stores and logs part names, never file contents.
- **The launcher change and the runtime change are ordered.** The parser accepts `git_metadata` before any launcher emits it (the strict parser refuses an undeclared member, `LaunchReport.java:160`), and the runtime renders `--read-only` only when `pm-exec` accepts it (it answers exit 64 to an unknown option); Q1 settles how.
- **Default and its alternatives.** The defaults are the minimal reading of the specification: the inputs it lists, the two comparison points it names, the refusal reason it names. Every alternative is in Carried Open Items with a recommendation; a choice that adds a public type or a file the spec does not name is ask-at-refine (R07).
- **A baseline is decided once and persisted as the protocol requires (R14).** If Q2 persists it, the checklist item (4) (decide once, never re-derive from a probe that can flap), (1) (a resume decides from the pair record and recorded state) and (3) (the record that drives recovery is deleted last) apply and get a test per cell.
- **Scope-bloat guard (soft cap).** Seven deliverables exceed the soft cap of about six; the rationale is that 1 to 5 are one chain (one value, produced, carried and compared), 7 is the documentation the rules require, and 6 is independent and cuts out at the outline without rework.
- **Not here:** the system call filter and the `seccomp` report member (`job-runtime/02#seccomp-filter`, the package `exec-hardening`), the egress record (PLAN-V2-59), the other families of protected paths (`.marshall/**`, harness configuration, forge CI, editor files: `PM-WATCH-PHASE-130`/`131`), the engine's hold and the operator's act, the native variant's call, submodule link files and worktrees created after the spawn (Q8). Anything else the outline finds wrong is reported in the landing and the inbox message, not fixed here.
- **Where the project analyses its pull requests with Sonar** (read it over plain HTTP: `pullRequest=N`, never `branch=<feature>`): an open Sonar issue is fixed in a pushed commit, or dismissed with a stated reason recorded as `{issue-key}: {reason}` and transmitted through `plan-marshall:workflow-integration-sonar:sonar_rest transition --issue-key {key} --transition {falsepositive|wontfix}`.
