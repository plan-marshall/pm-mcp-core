## Objective

Build the first half of the epic ledger records that no package builds. The Store Schemas specification defines the epic header `.marshall/epics/<epic_id>/epic.json` and the queue row `queue/<plan_id>.json` with their JSON schemas (`store-schemas/04-epic-and-change-ledger.adoc`, § Epic Header, § Queue Row), and five staged packages (`plan-and-epic-control`, `epic-decomposition`, `epic-auto`, `epic-resource-and-release`, `epic-review`) each extend or read them, but at `d95641dc` `pm-workflow/.../workflow/epic/` holds `EpicTokens` and `package-info.java` only and no class in `pm-core`, `pm-workflow` or `pm-runtime` reads or writes `epic.json` or a queue row: "the first to land creates classes the others must adopt, and no order is stated" (epic Open Defects, 2026-10-25; the operator decided on 2026-10-29 to cut a package for them, ordered before their consumers). This plan creates the package `epic-ledger-records` (file and index row), the immutable records of the header and the queue row with **every member of the schema blocks** (so `terminal_reason`, `auto_start`, `overlap_max_files`, `parallelization_scope`, `intent`, `workstreams`, `sources`, `held`, `reground_verdict` and the 16-state status vocabulary exist from the start), strict codecs, the two stores that write them under the epic lock, and the parity tests that pin them to the specification's blocks. What the consumers add is behaviour (who writes which member, when, and with which check), plus one member the schema block lacks (`overlap_found`, Claim Labels), never a second type. The inbox and the registers are the second plan.

4. **The two stores.** `EpicHeaderStore` reads `epic.json` without a lock (an absent file is a distinct result from an unreadable one, as `QualificationSettingsStore.read` and the empty states of the inbox) and replaces it by atomic write-and-rename under the epic lock (`LockKey.epic`) through `AtomicStoreFile` and a `LockManager` transaction, creating it only when absent (`create`) and replacing it only when it exists and parses (`replace`, which refuses an absent or unreadable header and a changed `epic_id`). `EpicQueueStore` owns the `queue/` directory of the ledger: `create(row)` is an exclusive create (`CREATE_NEW`, forced to disk, the directory forced) that refuses an existing `plan_id`; `replace(row)` is the row-local read-modify-write under the epic lock (a changed `plan_id`, an absent row and an unreadable row are refused); `read(planId)` and `list()` take no lock and report an unreadable file with its name while the other rows stay readable; the file name is `<plan_id>.json` and the store's temporary-file names cannot be a legal row name (R14 (6): the plan-id grammar has no dot; a test). Both stores take the ledger directory (the directory `epics/<epic_id>/` of the shared epic worktree) and the epic's `LockKey` as parameters, and neither touches git, a transaction journal or a digest sidecar (the ledger's integrity is its git history, `store-schemas/04` § Epic Ledger Records); resolving that directory is the epic ledger resolution seam, which no package builds (Claim Labels). The classes sit in `core.store` because `SyncedFiles` and `StoreLockGuard`, which the exclusive create and the lock check need, are package-private there. **Done when:** write/read round trips; a second `create` of one `plan_id` is refused and leaves the first row byte-identical; `replace` of a changed key, of an absent row and of an unreadable row is refused; a write without the epic lock is an internal fault and writes nothing (the `StoreLockGuard` test pattern); a crash injected after the temporary file and before the rename (R14 (5), (8)) leaves the old content readable; `list()` over a directory with one torn row file returns the other rows and names the torn one.

## Standing Constraints

Plan-specific constraints (the epic-wide rules are in `standing-rules.md`, named in the First Instruction above):

- **Log messages: none expected.** This plan is expected to add no INFO, WARN or ERROR message: the stores return values and throw the exceptions the existing stores throw (`StoreRefusal`, `InternalFaultException`, `UncheckedIOException`). If the trace matrix shows one, it goes into `CoreLogMessages` at the next free identifier of its level (ADR `doc/adr/005-one-log-message-holder-per-module.adoc`), and the plan says so in its inbox message.
- **No consumer behaviour.** The plan writes no state of the epic workflow, no operator act, no landing, no endpoint, no commit to the shared epic worktree and no project configuration value. A member that a consumer package sets is a member of the record with a copy method, nothing more. A decision on a consumer's behaviour that the work seems to need is reported in the inbox message, not built.
- **The shared specification files are touched by section.** `store-schemas/04` and `model-work/08` are also edited by the five consumer packages and by the second plan of this package; this plan edits the header and queue-row sections of the former and one table cell of the latter, and the second plan edits the inbox and register sections. Condense and point (R05) keeps every anchor (other parts and watch items link to them).
- **Sonar** (where the project analyses its pull requests: `runbook_lane resolve` reports `sonar: configured`): an open Sonar issue is fixed in a pushed commit, or dismissed with a stated reason recorded as `{issue-key}: {reason}` in the run's progress record; the merge gate reads the open-issue count at the head, `unknown` for a failed read and never `0`.
