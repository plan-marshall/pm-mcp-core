## Objective

Today a sub-workflow declares its parameters in the BODY (`param <name> : <type>` after `scope subworkflow`) and its entries and exits in the FRONTMATTER; nothing declares what configuration or which facts the unit reads, and a parameter has no default, no optional form and no fallback. Move the INPUT interface to the frontmatter, in the style of `entry`/`exit` (repeated keys, order-sensitive, a description directly below), add what the unit reads, and check all of it statically:

- the body `param` declarations are REMOVED (one source; pre-1.0, no shim, no deprecation cycle); `result` stays in the body (see Deliverable 2, the reason is stated there);
- the frontmatter gains `reads_config`, `reads_fact` and `input` with `input_type`, `input_default`, `input_fallback`, `input_description`;
- the three namespaces stay apart: configuration keys (`project.…`, `workflow.…`, `local-config.…`), facts (`reads_fact` names a derived fact KIND; read-only, never overridable by a caller) and the per-call input (`input.<name>`, unit-local);
- Rule 6 checks the call sites against the declared inputs (a required input bound, an input with a default, a fallback or the optional form may be omitted, every bound value compatible), a new Rule 1 binding checks every `reads_config` key and `reads_fact` kind against a registry the verifier is given, and `INV-GEN-1` compares the inputs of a project copy with those of its default unit.

The types stay the three that exist (`enum`, `int` range, `list<enum>`): this plan moves the interface and adds the declaration forms; the new closed types for free text and paths, the call-time channel that fills them and `git.commit_and_push` as the first user are the second spec. The operator decided the shape on 2026-10-29; do not re-litigate it. This spec records the open points as questions (end of this section) and fixes the rest.

**Decisions this spec takes (each becomes an ADR, R06):**

1. *`result` stays in the body.* The typed result record is the OUTPUT of the unit; the decision concerns one source for the INPUT interface. Moving `result` would add an output key to the frontmatter and change `WorkflowDefinition.resultSchema()` for its five consumers (`WorkflowPrinter`, `WorkflowValidator`, `PlanInstanceComposer`, `SubWorkflowInvariants`, the fixtures) for no gain in the input channel. A later move to an `exit_result` line below `exit: done` is possible and is not blocked by this plan.
2. *`input_type` carries the optional form as a trailing `?`*, the notation the link parameters already use (`param_decl = param_name ":" type_spec ["?"]`, `01-grammar.adoc` line 170, `ParamSpec.optional`). `input_type: int[0..5]?` is an input whose absence is legal; an absent input has the semantics its description documents (for example an absent `files` means every changed path of the scope, in the second spec). An input with `input_default` or `input_fallback` is not required either and must not carry the `?` (refused: two ways to say the same).
3. *Order of resolution of an input at a call:* the value bound at the call site; else the value of the `input_fallback` configuration key; else `input_default`; else absent when the type carries `?`; else the call site is refused (statically if it is a literal site, at the call if it is not). `input_fallback` names a configuration key that the unit also lists in `reads_config` (one place that says what the unit reads) and whose domain is assignable to the input type.
4. *Registries are arguments of the verifier* (ADR `workflow-verify/015`: baseline and registry are arguments), not code of this repository: there is no closed-configuration-schema class and no fact-kind class at HEAD (Claim Labels). `ConfigKeyRegistry` and `FactKindRegistry` are new value objects of `workflow.verify`; the production wiring from the closed configuration schema and from the fact-kind enumeration is the assembly's and is listed under Dependencies as an external hand-off.
5. *A new Rule 1 binding, not a new rule number:* `CONFIG_KEY_BINDING`, `FACT_KIND_BINDING` and `INPUT_DECLARATION` are `VerificationRule` constants of specification rule 1 (the family of `SCHEMA_BINDING` and `ENTITY_KIND_BINDING`).
6. *Names:* an input name is a `param_name` (lowercase, digits, underscore; never a reserved keyword) and is addressed inside the unit as `input.<name>`; the prefix keeps it textually apart from a configuration key (which always has a dot and a file stem) and from a fact kind. Because the prefix already separates them, the collision rule is the shadowing rule: an input name equal to a `reads_fact` kind of the same unit is refused (an input `push_remote` beside the fact `push_remote` would read as the fact).
7. *`reads_config` never names a fact:* a key with the stem `derived.` is refused there and belongs to `reads_fact` (the kind without the stem). `depends_on_config` of a guard keeps accepting `derived.<kind>` unchanged (`01-grammar.adoc` line 243; out of scope).

**Decided by the operator on 2026-10-29** (do not re-litigate): (a) the address form is unit-local, `input.<name>`, and the owner of an input is the unit whose frontmatter declares it; the fully qualified form `<unit id>.input.<name>` is used for logs, provenance records and documentation, never for a registry (the second spec records it in the frame); a call binds explicitly, `callee_input = caller_value`, checked by Rule 6 at build time, and the runtime only copies the bound value once into the frame; (b) the one-line edit of `PlanInstanceComposer` is accepted, because this plan runs after PLAN-105; (c) `list<path>[..n]` is written `list<path>[0..n]` in the second spec because `int_range` has a mandatory low bound.

## Deliverables

1. **The frontmatter keys (test first).** `UnitFrontmatterReader` reads `reads_config` and `reads_fact` (repeated; each value once per key; a config key in the grammar `config_key` of `01-grammar.adoc` line 209, a fact kind an identifier) and `input` (repeated; an identifier-grammar name, each once) with, in this order and directly below it, `input_type` (exactly once; the existing three types, `[lo..hi]` ranges as in `int_range`, a trailing `?`), `input_default` (at most once; an enum value, an integer or `[]` of the type), `input_fallback` (at most once; a configuration key) and `input_description` (at most once; 1 to 500 characters). A key out of that order, a second one, a missing `input_type`, a default outside the type, a default or fallback beside `?`, more than 16 inputs, 32 `reads_config` or 32 `reads_fact` values is refused with the line and column; the closed format of ADR 005/007 holds (one field per line, plain or double-quoted value, 200 lines including delimiters, no new required key — so no fixture without an input changes, unlike #150's `icon`). `UnitFrontmatter` gains `readsConfig`, `readsFact` and `inputs` (`List<InputDecl>`); `WorkflowPrinter` writes them in that order and calls the reader's `isPlain` (R15 item 3); a CRLF twin fixture for the new lines (R15 item 2).
   **Done when:** `UnitFrontmatterReaderTest` and `WorkflowPrinterTest` hold a refusing case per rule above, a CRLF twin and a parse-print-parse round trip with every key; the 200-line bound and the three numbers `UnitFrontmatterReaderTest.constantsAreTheSpecificationValues` reads are unchanged.
2. **One source: the body `param` is removed (test first).** `WorkflowParser` no longer parses `param` (a `param` line after `scope subworkflow` is refused as an unexpected statement, naming the frontmatter key to use), `subworkflow_decl` keeps `result`; `WorkflowDefinition` loses `params` (and `ParamDecl` is deleted); the inputs are read from `frontmatter().inputs()`. The new `ast/InputType` (sealed: `Enumeration`, `IntRange`, `EnumList`) and `ast/InputDecl` carry the declaration. `RemediationInvariants` (`INV-REM-1`: the expected parameters; the `actions` set) and `WorkflowValidator.checkSchemaBinding` read the inputs; every fixture and test that declares a `param` migrates (the 6 `.pmwf` fixtures and the 7 Java test classes listed in the Expected Surface). `call_arg` and `call_value` of the grammar are unchanged in this plan.
