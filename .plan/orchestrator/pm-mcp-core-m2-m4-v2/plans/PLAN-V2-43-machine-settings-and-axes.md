2. (Task 1) The onboarding's sub-workflows in the machine scope of `operator-wait-and-machine-scope`: languages, harnesses (one scan, a default), models, roles, credentials, providers, plan defaults; each aspect a compiled sub-workflow with the parameter `onboard_run` (`first_run`, `reconfigure`); the first run from `onboard.entry` through `onboard.mode` (guided or automatic), a later run of one aspect from the machine's settings (`settings.choose`) with its current values as the proposal, returning there.
7. (Task 8) The automatic onboarding with its consent and its result (reasons, items); _change_ on `auto.result` calls that one aspect as a later run (`onboard_run: reconfigure`, its current values as the proposal) through `onboard.next` and returns to the result; a state it cannot decide alone (a login, a token, no harness found, the model ids of a harness that cannot list its models) shown as in the guided run.
8. (Task 9) The machine's settings (UC-ONB-10), states of the onboarding unit reached from `onboard.completed`: `settings.choose` (the recorded aspects, the remembered consents, the documents mode, the cleanup's durations, the credentials with their status, the paired devices, which are acted on through their own endpoints); reconfigure an aspect as a later run of its sub-workflow; withdraw a consent (`settings.withdraw`, `settings.remove-consent`, audited, asked again at its next action); the documents mode (`settings.documents-mode`, `settings.record`: the machine key `sources.documents_mode`, `copy`, `move`, or `ask`, the default, which `start-source-intake` reads); the cleanup's durations (`settings.cleanup-durations`, `settings.record`: the machine's `cleanup.*` durations per kind and the reminder's days, which `cleanup` reads); the providers checked again on request (`settings.verify-providers`, `call providers` at its entry `verify` over every chosen provider); a credential rotated or replaced (`settings.credential`, `settings.store-credential`, every token derived from the old secret dropped), verified again through `providers.verify-consent`, `providers.verify`, and `providers.failed`, after which a plan held by the expired credential goes on. Every writer of this deliverable carries the revision of the settings it was made against and raises the `SettingsConflict` PLAN-46 landed (`pm-core` `core.config`; Task 10, Concurrent Changes of a Setting: the first change wins, a later one against an older revision is refused with `conflict` (`409`) and the current value, nothing is merged and nothing is overwritten unseen); the project's operator values and a plan's own values are `project-onboarding-unit`'s and `plan-and-epic-control`'s.
10. (Task 11) The plan behaviour axes and plan overrides in the composition: each variant a sub-workflow named with its axis as prefix, an axis's variants a closed list; the method variant (`method.test-first`, `method.tests-after`) called by `plan.order-tasks` of `phase-4-plan`, the asking variant (`ask.every-phase`, `ask.key-points`, `ask.questions-only`) by the plan unit's `phases.ask`; a landing variant composed into the step list of `phase-6-finalize` at its landing orders, which keeps its checks and reviews, with `landing.pull-request` (push, pull request, its reviews, merge), `landing.main` (commit and push on the base branch), and `landing.files` (no commit, the changes written into the main checkout's working tree, the plan handed back), apart from the land lane; the binding of each axis at the plan's start; the composition event `override`, the prune reasons `plan_default` and `merge_by_operator`, and the removal of the shipped rule `auto-merge-off` are implemented (Plan Instance Developer Guide § The Plan Behaviour Axes); `overrides.json` with a role's harness, model, and effort, the variant of each axis and of an integration, and the optional providers.
11. (Task 12) Validation of the landing: `defaults.validate` checks only what the machine provides (a provider for `landing.pull-request`), never a repository (the engine half is landed: `MachineDefaultsValidation` of `pm-runtime` `runtime.config`, PLAN-46 #233; it is used here, not rebuilt); a landing variant is validated where a project is known (its setup, a plan's start, a plan's settings), refusing `landing.pull-request` without a provider and `landing.main` on a protected base branch with the reason, also a machine default that does not fit the project.
