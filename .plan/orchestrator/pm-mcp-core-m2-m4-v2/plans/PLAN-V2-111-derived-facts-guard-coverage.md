## Objective

PLAN-V2-05 (#272) deleted the watch item PM-WATCH-STORE-43 ("The derived-facts store has its own lock in the total order") because its three named test classes were said to cover the item's guard. The analysis of the landing read the merged code and found that they do not: `FileLockManager` asserts the lock order within one transaction only, and `DerivedFactStore.refresh` opens its own, so a refresh made inside a plan or workspace transaction is never order-checked by the manager; the lock test therefore calls the pure function `LockOrder.check` on a hand-built list, and its "a plan lock then a refresh" case would pass whatever the place of `DERIVED_FACTS` in the order. The "no update is lost" tests across keys race two threads with no forced interleaving and can pass on an implementation that writes from the pre-derivation snapshot. Separately, a schema violation of an enum or a const prints the offending value, the store copies the violations into `failure.reason`, and the reason travels into the guard result: for the operator-only kind `agent_identity` that is a path for the operator-only value to a model-facing guard reason. This plan closes these three gaps: tests that fail when the property they name is broken, the redaction of the operator-only value, and a restored, narrowed watch item with the specification and guide statements corrected to what the manager enforces. It changes no behaviour of a fact that is not operator-only.

## Deliverables

1. **Tests that can fail.** (a) `pm-core`, `DerivedFactStoreConcurrencyTest`: a deterministic cross-key case: the derivation of the first key refreshes the second key (a nested `refresh` inside the `Derivation`, the way `updateKeepsANewerStoredResult` does for one key); afterwards both entries are stored. It must fail against a `update` that writes the document it read before the derivation; show that by a mutation of a scratch copy (the failing run is reported, the production code is not changed for it). The racing two-key cases stay as the smoke test and say so in their display names. (b) `pm-runtime`, `DerivedFactStoreLockTest`, with the real `FileLockManager`: the guard of the watch item as it is worded — thread A holds a plan lock in its own transaction and refreshes a fact; thread B refreshes the same key while A holds the plan lock (latches force the overlap: B starts after A acquired the plan lock and before A's refresh returns); both calls return within the timeout (no deadlock), the stored entry is one of the two results and is consistent, and the `RecordingAuditSink` holds no `lock_order_violation`. The case `planLockThenRefresh` is kept only if its display name and message say what it shows (the refresh is permitted, no more); its order assertion is dropped, because `LockOrderTest` states it. Done when: both new cases pass, the failing run of (a) is reported, and no test of the plan claims to show the lock order by a refresh.
2. **No operator-only value in a reason.** `DerivedFactStore.validated` builds `Failed("The value violates its schema: " + join(violations))`; `SchemaSubset` writes the offending value into the violations of `enum` and `const` (`SchemaSubset.java` lines 103 and 106). For a kind whose `operatorOnly()` is true, the reason names the kind and the number of violations and never a violation text (so no value); for every other kind the reason is unchanged. Test first: in `DerivedFactRefreshTest` (the group "the validation of a derived value"), `agent_identity` with a schema that has an `enum`, a value that violates it, the reason does not contain the value, `reading` is `Indeterminate`, and `DerivedFactGuards.evaluate`'s input (`couldNotEvaluate()`) does not contain it; a second case with a non-operator kind shows its reason still names the violation. The failing run against the unchanged production code is reported. The Javadoc of `refresh` says that a consumer's own `Failed` reason is the consumer's text and must not carry an operator-only value, and the guide says so. Done when: the cases pass and the failing run is reported.
3. **The statements, the watch item, the ADRs.** (a) `doc/implementation-watch/store-schemas.adoc`: PM-WATCH-STORE-43 is restored under the **same id and anchor**, narrowed: *Hazard* — a refresh that runs inside a scope transaction is not order-checked, because the manager asserts the order within one transaction and the store opens its own; *Guard* — the store holds the derived-facts lock for the re-read and the write only, takes no other lock and calls no foreign code under it, and the derivation runs outside it (so it cannot take part in a lock cycle), proved by Deliverable 1; the order of a caller's transaction relative to the store's is a convention of the callers that no test of the store can enforce, which is why the item stays (R05: kept with a reason). Restoring the same id also repairs the one link `plan-marshall-documentation` `requirements/14-implementation.adoc` line 135 still has to it, so no documentation pull request is needed; if the outline finds a reason to use another id, the plan says so and lists the documentation pull request as owed. (b) `store-schemas/09-derived-facts-and-build-timings.adoc`, the paragraph before the first "Implemented by": the sentence that a refresh inside a plan, epic or workspace transaction "takes it after the scope lock the transaction already holds" is corrected to what is true (it takes it in its own transaction after the caller's lock is held; the lock manager does not see the caller's keys); the schema block, the kind table, the anchors and the *Provider derivations* bullet stay byte-stable (R10). (c) `pm-core/doc/developer/core-store.adoc`: the paragraph "A refresh made inside a scope transaction therefore takes" and the sentence "is a violation the lock manager refuses" say the same. (d) Two ADRs in `pm-core/doc/adr/core-store/`: the store's transaction is its own and the order across transactions is by convention (alternative: a `refresh` overload that takes the caller's `LockTransaction` so the manager checks it — recorded with its cost, a second public signature on every consumer, and why it is not chosen; the operator may choose it at refine, R07), and the operator-only value never enters a reason (alternative: `SchemaSubset` never echoes a value, which is the more general fix and touches `core.role.corpus`, the surface of PLAN-V2-65). (e) ADR `core-store/057` gives "keeps the last good digest so the retry is automatic" as its reason; the retry is guaranteed by the decision table (`stale` and `failed` derive again whatever the digest). Correct the reason there and in the Javadoc of `DerivedFactStore` (the paragraph *Failure*), and state in ADR `core-store/056` that the comparison of `derived_at` is made on the caller's start instants and that a failure started later wins over a success started earlier for the same digest (the entry is `failed` and the next call derives again). ## Standing Constraints

- **Where the project analyses its pull requests with Sonar** (`runbook_lane resolve` reports `sonar: configured`): an open Sonar issue is fixed in a pushed commit, or dismissed with a stated reason recorded as `{issue-key}: {reason}` in the run's progress record and transmitted through `plan-marshall:workflow-integration-sonar:sonar_rest transition --issue-key {key} --transition {falsepositive|wontfix}`. - **Do not touch** the build timings, `DerivedFactGuards`, the codec or the kind registry.
