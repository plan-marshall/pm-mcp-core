## Objective

`PLAN-V2-01` gives a primitive a place to say why it failed, skipped or could not decide: a closed `reason` on its result, declared per outcome and checked at registration. Nothing in the engine reads it yet. This plan makes the engine honest about it, and no more:

- **Check it.** The engine already checks that a returned outcome belongs to the primitive's declared set (`WorkflowEngine.java` line 820); it now checks the same of the reason, so a result that bypassed the record's invariant (a raw type) is a fault, not data.
- **Map it.** A reason may name an engine condition (`OutcomeReason.conditionKind()`, one of `footprint_violation` and `precondition_unmet`). When the result carries such a reason, the engine does not take the transition: it raises that condition on the current state, with the reason in the condition's facts. This is the mapping `PLAN-V2-20` hands off for `git.stage-and-commit`'s `failed` outcome with the reason `footprint_violation` (the catalogue row says it: "a breach raises the `footprint_violation` condition on this state … and nothing is committed", `state-catalogue/05-git-commit-and-push.adoc` line 84).
- **Never route on it.** A reason is data (decided on 2026-10-29). No grammar production, no guard, no transition of any unit reads a reason. The one verifier change is a diagnostic: a state that routes a reason's name as if it were an outcome is refused with a message that says so. Rule 9 needs no new rule: it admits a completion by the CLASS of the outcome, and a reason does not change a class; this plan proves that with tests and states it in the specification.
- **Carry it into what is already persisted.** The engine persists the status and nothing else: it appends no audit record, no step record (the `steps.<id>.firings` record is specification only; `WorkflowStatusCodec` keeps `steps` as an unread member), and `PLAN-105` is about to add the plan's history. The only data the engine persists about a primitive's failure today is the `facts` of a condition overlay; Deliverable 1 puts the reason there. Deliverable 2 adds it to the history line the engine appends when it leaves a state, if `PLAN-105`'s merged shape carries the outcome there; if not, the reason waits for the persisted command log (the follow-up).

**Decisions this spec takes (each becomes an ADR, R06):**

1. *A reason that maps to a condition raises it INSTEAD of taking the transition.* The transition of the outcome is not taken, the facts of the result are not merged into the call's result record (the step is interrupted, as the catalogue says: "the link or primitive that met the violation is not executed"), and the scope rests on the state that ran the primitive, exactly as for every other condition (`raise` leaves state, phase and call stack as they are; an advance of a scope with a condition returns it unchanged). When the condition clears the state is run again. The outcome is still routed by Rule 2, because the verifier does not know which result a run returns; the route is what the state takes when the reason maps to no condition.
2. *The facts of the raised condition are `primitive`, `outcome`, `reason` (wire names), and the facts of the result, rendered as text and bounded.* A condition's facts are a JSON object of text values (`EngineStep.ConditionRaised.raise` writes `Map<String,String>`); a text, number or boolean fact is its text; a collection fact (for example `offending_files`) is its elements joined by a comma; every value is cut at `MAX_FACT_LENGTH` (256 characters, a named constant) and a collection at 50 elements, with a `…` marker. A fact the result also names `primitive`, `outcome` or `reason` is dropped in favour of the engine's. The bound is a privacy and size bound: a condition is shown to the operator.
3. *Only the engine raises it; the reason's table is `PLAN-V2-01`'s.* The mapping reads `OutcomeReason.conditionKind()`; the engine holds no table of its own, so a new reason with a condition needs no engine change.
4. *A reason is not put into the sub-workflow result record.* The `results` map that `returnFromFrame` hands to the caller's result guards (`WorkflowEngine.java` line 825) carries facts only; routing on a reason through a fact would re-open the door `PLAN-V2-01` closed. The reason of a failure that a caller must act on is promoted to a named outcome by the primitive's author.
5. *The verifier names a reason mistaken for an outcome; it adds no rule.* In `coverOutcomes` (Rule 2), a routed name that is no outcome of the primitive but is the wire name of a reason of one of its outcomes is reported as "routes '<name>', which is a reason of the outcome '<o>' of the primitive '<p>': a reason is carried as data and never routed". The violation count is unchanged (the existing violation, a better message); the rule id stays; the class check of Rule 9 is untouched. An omitted per-reason edge is never reported: one transition of the outcome covers every reason of it.
6. *(Only if Deliverable 2 runs.) The reason is an optional member of the history line.* The wire name of the reason, present on the `left` record of a state whose primitive returned a reason, absent otherwise. No second record, no copy of the facts.

## Standing Constraints

- **Log messages: none expected.** A raised condition is a status value; a malformed result is a fault with an audit record, as the existing `UNDECLARED_OUTCOME` fault.
- **No behaviour change for a primitive without a reason.** An outcome that declares no `reasonType()` takes exactly the path of today: the same transition, the same status, the same facts merge. A test over the existing fixtures proves it by not changing.
- **Nothing routes on a reason.** No grammar production, no `GuardEvaluator` branch, no transition target and no result-record member reads or carries a reason (Decision 4).
- **Format versions stay 1** (R13), only if Deliverable 2 runs: the history line changes in place.
- **No generic `Exception`** is caught or thrown in production code.
- **Add no dependency and no plugin** (CLAUDE.md).
- **`EngineFixtures`, `ScenarioFixtures` and the other shared fixture files are read, not edited** (`PLAN-V2-15` and `PLAN-V2-13` change the first; `PLAN-V2-33` and `PLAN-V2-49` the second): new fixtures go into new files.
