## Deliverables

The bullets of `doc/plans/chat-plan-revision.adoc` § What, in its words (regenerated by cleanup at 99971f3 from the package file).

1. Implements Phase Workflows § Revision from a Chat and the plan's part of _Apply by subject_ of State Catalogue § Chatting with the Planning Role: `chat`, on top of `chat`, whose plan chat until then proposes no revision.
2. The proposal: a plan's chat proposes a revision only while the plan runs in Phase 5 or in finalize before the merge, the window of every re-planning, and otherwise answers and proposes none.
3. Apply: an accepted revision passes the guards of a first plan (outline validation, derivation dry-run, task graph, Q-Gate), is applied at the plan's next task boundary as `replan.apply` applies one (`replan.apply-revision`), what runs finishing first, a paused plan applying it when started again, and composes a plan instance version of event `replan`; its re-planning record names the operator's chat as the decider, and the report `plan.revised` is written. A chat's revision is the operator's own act: it spends nothing of the plan's re-planning budget. A change to a plan an epic started reaches the epic's inbox like every act.
4. Inside a decision: a revision the chat proposes goes through the same path; the decision stays open unless the applied revision removes the task or state that asked it, which closes it as withdrawn, with the reason.
5. A revision that changes intent: an accepted revision that changes the plan's intent record carries the record through the re-planning path — the named parameter schema `intent-record`, the `submit:refine`/`submit:outline` shape and `request.md` § Clarified Request rendered from it — and a revision whose record does not validate is refused before it reaches the next task boundary; the current record moves to `history[]` in the accepting transaction and is never changed, and the intent of an epic the plan started stays the epic's (`epic-intent`), never a plan revision's (Store Schemas § Intent Record; Phase Workflows § The Intent Record; § Apply, Re-Entry & Instance Version).

**Done when** (the package's own acceptance): A plan's chat proposes a revision in Phase 5 and in finalize before the merge and none outside that window; an accepted revision passes the guards of a first plan, takes effect at the next task boundary (a paused plan's when started again), composes an instance version of event `replan` whose record names the chat as the decider, writes `plan.revised`, and leaves the re-planning budget untouched; a change to a plan of an epic reaches the epic's inbox; in a decision, an applied revision that removes what asked it closes the decision as withdrawn with the reason, and one that does not leaves it open. A revision that changes intent carries the validated intent record through `submit:refine`/`submit:outline`, renders `request.md` § Clarified Request from it, and moves the current record to `history[]`; a record that does not validate is refused before the next task boundary. **Sonar:** the SonarCloud search of the pull request (`pullRequest=<N>&resolved=false`) lists no open issue other than one dismissed with its reason, and its quality gate is green, before the pull request is reported ready.
