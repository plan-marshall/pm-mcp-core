## Objective

The specification says no value of a profile is believed because the profile says so: `worker.eligible`, a runnable `zero_tool` class and an `enforced` tool set count only with the stages of the bound verification record `passed` on the platform the runtime runs on. `ProfileWorkerEligibility.evaluate` (`ProfileWorkerEligibility.java`, the claimed-stage lists `ELIGIBLE_STAGES` = faults and egress, `ZERO_TOOL_STAGES` = classes and isolation, and the `classes` stage for an enforced tool set) already refuses a claimed profile with no record, a record of another platform, a claimed stage absent from the record, and any recorded stage that is `failed` or `not_run`. **Compared with the specification it does not check:**

1. the stage **`paths`** for `worker.eligible` (the spec: `faults` passed every fault with at least 10 trials on a platform with a confinement, **`paths` passed**, and `egress` passed or recorded `unenforced`); a record without a `paths` stage is accepted today;
2. **at least 10 trials** of the `faults` stage (`VerificationRecord.Stage.trials`, `Integer`, set for `faults` only) and **a platform with a confinement** (`VerificationRecord.Platform.confinement`);
3. the stage **`isolation`** for a `writer` or `read_only` class with an `enforced` tool set (the spec: its base task passed and `isolation` measured an exclusive configuration with extension isolation for its launch; today only `classes` is required);
4. the **profile digest**: the record's `profileDigest` ("the canonical-JSON digest the profile had when it was verified", `VerificationRecord.java:37`) is never compared with the digest of the profile the record is bound to, so a record verified for another document of the same harness is believed;
5. the **`unenforced` egress** case: the spec honours `eligible: true` with an `egress` recorded `unenforced` only while the operator's acceptance holds for the machine; the code requires `egress` to be `passed` and says so on purpose (its Javadoc and ADR `runtime-worker/006`: "the egress owner holds the acceptance"), which is a refusal of a case the spec allows.

Also: the watch item PM-WATCH-CLIENT-13, which the owner register names for this gate, is absent from `doc/implementation-watch/harness-profiles.adoc` (the items present run 1 to 12 and 16 to 21), and the gate has no production caller in this repository (`SupervisorEnvironment.EligibilityGate` is offered; the assembly wires it, nothing here does).

## Standing Constraints

- **Fail closed.** Every input that is absent, unreadable, from another platform, bound to another digest or short of a stage or of a trial is a refusal with a closed reason; no default makes a harness eligible. A new refusal never widens what is honoured today.
- **No wiring.** The plan edits the gate and its tests and documents; it does not edit `SupervisorEnvironment`, `WorkerSupervisor`, the loader or the assembly.
- **The record is untrusted input:** the gate reads the closed, validated `VerificationRecord` and trusts no string of it beyond its closed forms; nothing of the record is logged beyond the stage name and the reason.
- No dependency or plugin; no hand-written test double (EasyMock only); where the project analyses its pull requests with Sonar, read it over plain HTTP (`pullRequest=N`, never `branch=<feature>`): an open issue is fixed in a pushed commit or dismissed with a stated reason `{issue-key}: {reason}` through `plan-marshall:workflow-integration-sonar:sonar_rest transition --issue-key {key} --transition {falsepositive|wontfix}`.
