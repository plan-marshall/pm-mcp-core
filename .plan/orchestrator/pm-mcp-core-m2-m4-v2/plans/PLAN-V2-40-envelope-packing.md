## Objective

The package `de.planmarshall.workflow.envelope` of `pm-workflow` holds only a `package-info.java` ("The task envelopes: the packing of plan tasks into envelopes by their predicted cost") and no plan builds it (PLAN-103 reported it to the operator; the operator decided on 2026-10-29, decision 4 of 18, to cut a package for it and to keep the package). Model Work § Task Envelope Bin-Packing specifies a pure, deterministic computation: the cost size of a plan task (`derive-cost-size`), the size-to-token table, the Next-Fit packing into envelopes with the module-and-role sharing rule and the below-minimum merge (`EnvelopePacker`), and the per-envelope budget derived from the context budget of the envelope role, whose two fallbacks are capped at the long-context threshold of the role's model. This plan builds that computation as inputs-to-outputs functions with no store, no queue and no profile type behind them, so that it runs free of the staged plans that edit `ProfileValidator`; the profile member that supplies the threshold (`headless.long_context_thresholds`) is the follow-up plan PLAN-V2-63 (`long-context-thresholds`), which depends on this one and on `machine-harness-verification`.

This plan also cuts the work package. Its first deliverable writes the package file `doc/plans/envelope-packing.adoc` and its row in the index `doc/plans/README.adoc`, which R01 requires to exist (a package that is worked removes its row and deletes its file, and none exists for the envelope). The row and the file stay when this plan merges: the package is finished by PLAN-V2-63 (`long-context-thresholds`), which removes them.

The row text of `own-calls` ("the task envelope with its `submit` link and the Task Diff Record (no work package)") is not changed by this plan; say in the pull request body that the task envelope with its `submit` link is still without a package.
2. **The cost sizing, `TaskCostEstimator` and `SizeTokenTable` (item 1 to 3 of § Cost Sizing).** `TaskCostEstimator` computes `score = 10 * steps + W_profile + 3 * skills + 4 * files` from the four signals of a task record (number of steps, profile, number of skills, number of distinct target files), with the profile weights `implementation` 12, `module_testing` 12, `verification` 4 and 8 for every other profile; the score maps through the monotone bands `XS < 30`, `S < 60`, `M < 150`, `L < 300`, `XL < 700`, `XXL >= 700` to `cost_size`. `SizeTokenTable` is the table of the compiled defaults (`XS` 5K, `S` 25K, `M` 60K, `L` 130K, `XL` 260K, `XXL` 520K, K = 1000) with its basis `uncalibrated`; `predicted_cost_tokens` is a lookup in the table, never a computation, and the estimate carries the basis of the table it used. The table is an object the caller passes in, so the later recalibration can supply a `calibrated` one; no configuration reads it. Tests (`TaskCostEstimatorTest`, JUnit 5, `@DisplayName`, AAA): each band edge (29/30, 59/60, 149/150, 299/300, 699/700) as a `@ParameterizedTest`; raising any one signal never lowers the size (a loop over the four signals); the profile weights including an unlisted profile; the table values and the basis.
3. **`EnvelopePacker` (§ Deterministic Envelope Packing Algorithm).** Implement the algorithm of the specification's code block: Next-Fit in task order, an envelope closes when the next task cannot share it (same module and same role; the execution profile is not a criterion) or would push it past the budget; a task whose predicted cost alone exceeds the budget sits alone; then the below-minimum merge (`MIN_JOB_TOKENS` 10 000: an envelope below it joins its adjacent compatible envelope, the preceding one first, otherwise the following, otherwise it stays alone); then the sealing into `envelope-1`, `envelope-2`, ... with the task ids, the sorted distinct union of the skill URIs and the summed predicted cost. The types are those of the specification (`PlannedTaskSummary`, `PackedEnvelope`, the enum `CostSize`, nested in `EnvelopePacker`); `PackedEnvelope` gets one derived method `belowMinimum()` (total below `MIN_JOB_TOKENS`) and no further component, so that the fact `below_minimum_task` can be built from it later and the specified signature `packEnvelopes(List<PlannedTaskSummary>, long)` stays. The packer never re-derives a cost and never reorders: every envelope is a contiguous slice of the ordered input. Tests (`EnvelopePackerTest`): empty input; one task; Next-Fit closes on the budget and on a module change and on a role change separately; an `XXL` task alone; a task exactly at the budget; the below-minimum merge into the preceding, then into the following neighbour, and the lone envelope with no compatible neighbour that stays and answers `belowMinimum()`; that a merge produces an envelope over the budget (the specification's consequence); contiguity and order over a generated input (cui-test-generator) with the property "concatenating the task ids of the envelopes gives the input order"; the skill union is sorted and distinct; the same input gives the same output (determinism).
4. **`EnvelopeBudget` with the long-context cap (§ Envelope Budget, item 4).** A pure resolution with the inputs `OptionalInt` role-declared `context_budget_tokens`, `OptionalInt` profile fallback (`headless.context_budget_tokens`), `OptionalInt` long-context threshold of the role's model, `OptionalInt` operator override (`envelope_budget_tokens`) and the compiled fallback `400_000`. Precedence: the operator override; else the role-declared value; else the profile fallback; else the compiled fallback. The profile fallback and the compiled fallback are capped at the threshold when one is given; the role-declared value and the operator override are taken as set. The result is a record (`tokens`, the source of the value `OPERATOR | ROLE | PROFILE | COMPILED`, `capped` for a fallback that the threshold lowered, `aboveThreshold` for a role-declared or operator value above a given threshold, which is what the role view shows later). The inputs are plain integers on purpose: this class does not read `RoleArtifact`, `HarnessProfile` or the profile document, and `headless.long_context_thresholds` is read by the follow-up plan. Tests (`EnvelopeBudgetTest`): every precedence step; the cap on the profile fallback and on the compiled fallback (threshold 200 000 against 400 000 gives 200 000 with `capped`); no cap without a threshold; a threshold above the fallback changes nothing and is not `capped`; a role value and an operator value above the threshold are kept and answer `aboveThreshold`; the compiled fallback is 400 000.
5. **Documentation (R05, R06).** The developer guide `pm-workflow/doc/developer/workflow-envelope.adoc` (new; the types and how they work together, the invariants, what the package does not do, the links to the specification sections) and `pm-workflow/doc/adr/workflow-envelope/001-...adoc` (and the next numbers) for the design decisions taken: the computation takes plain values and holds no store or profile type; `belowMinimum()` as a derived method; the precedence and the cap of the budget with the threshold as an input. The `package-info.java` of the package says what it holds now (cost sizing, packer, budget) and keeps its specification line.
