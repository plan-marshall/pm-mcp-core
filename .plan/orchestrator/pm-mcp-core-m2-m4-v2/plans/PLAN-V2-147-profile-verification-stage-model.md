## Objective

The profile verification (`doc/specification/harness-profiles/01-profile-schema.adoc` § Profile Verification, the stage table at about `:355-410`, the record at about `:418-469`) runs twelve stages (`VerificationRecord.STAGE_NAMES`: `identity`, `detection`, `launch`, `events`, `egress`, `isolation`, `classes`, `limits`, `paths`, `resumability`, `faults`, `usage`; the specification adds `settings`) and writes a closed record from which a profile's claims are derived ("the candidate claims only what was measured"). At the head the record has a reader (`VerificationRecord.read`, `:150`) and **no writer**; there is no stage order and no prerequisite in code; the evaluators that exist are partial (`ProfileStages.usage` `:407`, `:425`, `EndpointVerification` `:689`, the hand-fed `IsolationResult`, `HarnessEventVerification.verify`, `ResumabilityResult`); `running_total` accumulation is only in the schema (`harness-profile-v1.schema.json:~302`). This plan builds the pure part, in `pm-core`: the closed stage list with its order and prerequisites, the evaluators of every stage over closed observation values, the candidate and record writer, the expected-token computation shown at consent, and the recorded-fixture format. **It runs no harness, no process and no network; nothing it delivers claims that a real harness was verified** (Done-when). The runner that produces the observations is PLAN-V2-148.

## Standing Constraints

- **Pure logic.** No process, no file outside `@TempDir`, no network, no clock; observations are closed values built by the caller.
- **The draft, the observations and the record are untrusted input:** closed shapes, bounded strings, the model-readable character set; the record holds no path, host, user, environment value or model output; no credential enters a record or a fixture.
- **Existing behaviour stays:** `VerificationRecord.read` keeps accepting every record that is valid by the specification; the `ProfileStages` results keep their shapes (the evaluators feed them).
- **Synthetic until recorded:** every fixture is labelled synthetic; no test, document or commit message says a real harness was verified.
- No dependency or plugin is added; no hand-written test double (EasyMock only); where the project analyses its pull requests with Sonar, read it over plain HTTP (`pullRequest=N`, never `branch=<feature>`): an open issue is fixed in a pushed commit or dismissed with a stated reason `{issue-key}: {reason}` through `plan-marshall:workflow-integration-sonar:sonar_rest transition --issue-key {key} --transition {falsepositive|wontfix}`.
