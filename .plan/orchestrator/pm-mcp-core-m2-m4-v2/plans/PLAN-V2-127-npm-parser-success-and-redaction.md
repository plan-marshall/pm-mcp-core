## Objective

PLAN-V2-36 wired the nine native build parsers into the job settlement. Its analysis (`landings/PLAN-V2-36.md`) found that the wiring is sound for Maven, Gradle and pytest and wrong for the npm family: `JestOutputParser`, `TapOutputParser`, `TypeScriptOutputParser`, `EslintOutputParser` and `NpmErrorParser` build every `ParsedBuild` with `successMarker=false`, so a zero-exit `npm test` that printed `Tests: 5 passed, 5 total` ends `indeterminate` (row 8 of the outcome derivation) and never `succeeded`; the specification names "the tool's passing summary" as the marker (`job-runtime/01-pipeline-and-subprocesses.adoc` line 202), the code does not honour it, and the guide states the opposite as a fact. The same analysis found that the excerpt a `failed_unparsed` build will hand on is redacted on the raw tail, not on what a person reads: an ANSI escape inside a credential label defeats the redactor, and the redactor does not know the shapes an npm log carries (a token with the `npm_` prefix, a URL with user information, a `--password <value>` flag). The operator decided on 2026-11-09 that these functional defects of the npm family get their own plan. The fixes make the contract true; they add no parser and no new outcome row. All line numbers are those of `origin/main` at `d1fb719f`; this plan re-reads them at the head.

Not here (owned elsewhere or left open): test conformance of `BuildOutputParserTest`, `JobSettlementTest`, `SubprocessJobRunnerTest` (PLAN-V2-90: I3, I4, I5 of the analysis); the size cap of `BuildLogText.read` and the quadratic regexes (C4; PLAN-V2-131); the `RuntimeException` catch of `JobSettlement.run` (I1); the replacement map of the recovery path (PLAN-V2-51 and 55); the first scanner wins when an npm log carries markers of several tools (a recorded limit, see Carried Open Items); the coverage report parsers (PLAN-V2-18, which this plan follows).

## Deliverables

1. **A passing Jest or TAP run is a success (failing case first).** Today `JestOutputParser.java` lines 85 to 88 and `TapOutputParser.java` lines 99 to 101 pass `successMarker=false` to the `ParsedBuild`, and `OutcomeDerivation.java` lines 122 to 129 therefore answer row 8 (`indeterminate`) for exit code 0. Write the failing cases first: `BuildOutputParserTest` gets a zero-exit Jest log (`PASS src/a.test.ts`, `Tests:       5 passed, 5 total`) and a zero-exit TAP log (`# tests 5`, `# pass 5`, `# fail 0`) whose outcome is asserted `SUCCEEDED` at row 7; both fail against `d1fb719f` (report the failing run). Then set the marker in each parser from the tool's printed passing summary, defined once in the parser: the status is `SUCCESS`, the counts are `Measured`, the failed count is 0 and the passed count is above 0. A log whose summary is unreadable or `Unmeasured` (`Tests: 7 total`, `# tests 5` with two passing tests), a measured zero (`Tests: 0 total`, `# tests 0`), an all-skipped run, a failing count and a run with a filed diagnostic keep the marker `false`; `zeroCountIsNoMarker` (`BuildOutputParserTest` lines 240 to 250) stays and still passes. The ported fixtures that pin the old value change in their `success-marker` line only, and each says so in a comment: `npm-jest/deliberate-jest-two-test-blocks.txt`, `npm-tap/deliberate-tap-two-blocks.txt` and `npm-tap/npm-tap-success.txt` become `success-marker true`; `deliberate-jest-unmeasured-tests.txt`, `deliberate-tap-unmeasured-tests.txt` and `deliberate-tap-zero-tests.txt` stay `false` and are the negative controls. `noTestsRan` is unchanged: no npm tool prints a positive "no tests" marker. **Done when:** the two new outcome cases pass and failed before, every named negative control stays `indeterminate`, `ParsedBuildPortedTest` passes with the three changed fixtures, and the Javadoc of the two parsers states the marker.
2. **The npm tools that print no passing summary: decide and state it (R07: ask at refine).** `TypeScriptOutputParser.java` lines 70 to 72, `EslintOutputParser.java` lines 79 to 81 and `NpmErrorParser.java` lines 85 to 87 also pass `false`, and for `tsc` and ESLint that is right by the log: a clean run prints nothing the log can prove, and `BuildOutputParser.npm` (lines 100 to 118) dispatches them only on a marker a failing log carries (`error TS\d+`, an ESLint row or summary), so a clean run is `ParseResult.NOTHING`. The default of this plan: (a) the install family keeps its own completion line as its passing summary — `NpmErrorParser` (or a scanner beside it, the outline picks and records the choice) sets the marker for a log with no `npm ERR!` block and a line of the form `added|removed|changed|up to date ... packages` (the fixture `npm-success.txt` has `added 150 packages in 10s`), and `BuildOutputParser.npm` dispatches to it; `BuildOutputParserTest.unrecognisedLog` (lines 264 to 272, the log `up to date, audited 5 packages`) is changed deliberately from `NOTHING` to a success and says so; (b) a clean `tsc` or ESLint run stays `indeterminate` at row 8 and the specification says so in one sentence at `job-runtime/01-pipeline-and-subprocesses.adoc` line 202 ("the tool's passing summary" is read as "where the tool prints one"), recorded in an ADR of `runtime-job/` that supersedes in part the last bullet of ADR `runtime-job/015` (line 67: "the mapping keeps a zero exit of a tool without a positive success marker `indeterminate`") — the rule stays, its list of tools shrinks. The alternative the operator may choose instead is to let the job's verb carry the decision (`npm:quality-gate` with exit 0 and an empty log is a success); it changes the outcome table's premise that the log, not the exit code alone, proves a success, and it is not the default. **Done when:** the operator's answer is recorded in the ADR; under the default, a zero-exit install log ends `SUCCEEDED` at row 7, a clean `tsc` and a clean ESLint log (empty) end `INDETERMINATE` at row 8 in cases that name the limit, and the guide sentence at `core-build.adoc` lines 165 to 167 ("None of them prints a positive success banner") and the adapter paragraph at `runtime-job.adoc` line 283 are rewritten to the parser-by-parser truth.
3. **Read the prefix current npm prints (verify first).** `BuildOutputParser.NPM_MARKER` (line 66) and `NpmErrorParser` (`ERROR_PREFIX` line 43, `CONFLICT_MARKER` line 51, `ERROR_CODE` line 55, `E404_PACKAGE` line 57) recognise `npm ERR! ` only. The analysis (C7) reports that newer npm prints `npm error `; that is not shown by the code and is HYPOTHESIS until the lane records a real failing log of the npm release the project builds with (`npm --version` in the fixture's comment). **If it is shown:** a failing case first — a log `npm error code E404` / `npm error 404 'missing@1' is not in this registry` with a non-zero exit is today `NOTHING` and ends `failed_unparsed` (row 10) where the same log in the old prefix ends `failed` (row 9) — then accept both prefixes in the five places, with a fixture in each prefix (`ported/build/npm-errors/`, marked deliberate) and the adapter case. **If it is not shown:** the deliverable is dropped, the landing says so, and nothing else of it is done. **Done when:** the recorded log and the two cases exist and pass, or the landing reports the refutation.
4. **The unparsed excerpt is redacted on what a person reads (failing case first).** `UnparsedEvidence.of` (lines 76 to 83) takes `rawLog.lines()` (line 86) and redacts that text (line 88); it never strips ANSI, although `BuildOutputParser` does (line 80). Three effects, each with a failing case before the fix: (a) a credential label split by an escape (`ESC[1mpassword` `ESC[0m=<value of 14 characters with no provider prefix>`) is not matched by the label pattern of `SecretRedactor` (`assignment`, line 67 requires the separator right after the label) and the value is in the excerpt; (b) the escapes spend the 4 KB byte bound (line 43), so a colour-coded log keeps less than the text it shows and the cut can end inside an escape; (c) `String.lines()` treats `\r` as a line end, so an npm progress spinner that overwrites one line with `\r` frames counts every frame against the 50-line bound and pushes the failure out of the tail. Fix: strip ANSI through `BuildLogText.stripAnsi` and reduce each `\r` run to its last frame before the tail is taken, then redact, then cut by bytes (the order of ADR `core-build/004` line 46 stays). **Done when:** the three cases pass and failed before (the failing run is reported), `redactsASecret` and the bounds tests of `UnparsedEvidenceTest` pass unchanged, and ADR `core-build/004` and `core-build.adoc` line 269 name the stripped form.
5. **The redactor knows the shapes an npm log carries (failing case first; R07 for the shape list).** `SecretRedactor` (lines 42 to 64) redacts an authorization header, a bearer value, an explicit `label=value` assignment and the provider shapes `sk|ghp|gho|ghu|ghs|ghr|github_pat|xox[abprs]`. By reading the patterns, these shapes are returned unchanged today: (a) an npm access token `npm_` followed by its characters (the prefix is not in `TOKEN_SHAPE`, line 61; the length is HYPOTHESIS, verify against the npm documentation and record it in the fixture comment); (b) user information in a URL, `https://<user>:<secret>@registry.example/pkg` (a registry URL in an `npm ERR!` line); (c) a command-line flag with a space instead of a separator, `--password <value>` and `--token <value>` (the assignment pattern requires `:` or `=`); (d) a PEM block, `-----BEGIN ... PRIVATE KEY-----` to `-----END ... PRIVATE KEY-----` (the label `private[_-]?key` does not match the spaced words and the base64 lines carry no label). Default: mask (a) to (c) with patterns anchored to the shape so that prose cannot match (the user-information pattern needs the `scheme://...@` form; the flag pattern needs the leading `--`), keep the label and the scheme, and mask (d) inside one text only (a window that starts inside a block is carried, see Carried Open Items). The existing narrowness argument of the class Javadoc (lines 22 to 26: a false positive costs evidence) is kept: each new pattern gets a negative control (`https://github.com/org/repo`, `--password-file notes.txt` is a different flag and stays, a sentence with the word `token`). `SecretRedactor` also masks every activity entry (`ActivityJournal.java` line 208), so the new masks reach the journal; `ActivityJournalMaskingTest` stays green and the journal's specification sentence ("masked like every job log") is unchanged. **Done when:** each of (a) to (d) has a case that fails against `d1fb719f` and passes, each negative control and `redacting is idempotent` pass, and the class Javadoc lists the shapes.
6. **The npm error diagnostic is redacted at its source.** `NpmErrorParser.java` line 120 files `DiagnosticCollector.stored(code + ": " + firstLine(block))`, i.e. the first reportable line of the raw `npm ERR!` block, up to 500 characters (`DiagnosticCollector.java` line 72), unredacted; the located diagnostics of a build "become findings" (`job-runtime/01` row 9), so a `request to https://<user>:<secret>@registry.example/pkg failed` line would be stored as a finding message. Today `BuildOutputParser` keeps only the count (line 128), so no consumer reads the message yet (OBSERVED by search: no production class outside `core.build` names `de.planmarshall.core.build.Diagnostic`; the adapter reads `build.diagnostics()` only); the fix is made at the source because the consumer is a later plan. Redact `firstLine(block)` through `SecretRedactor.redactText` before the 500-character cut (a cut value must not leave a secret prefix that the redactor would have matched whole) and pin it with a case that uses the user-information shape of Deliverable 5(b). **Done when:** the case passes and failed before, the `ERESOLVE` and `E404` messages (built from the dependency names) are unchanged, and the guide says where the diagnostics of the npm parser are redacted. Whether the other parsers' messages (they carry source and test text) are redacted at `DiagnosticCollector.stored` for every parser is a decision with false-positive cost on compiler messages and is carried, not taken here.

**Done when:** Deliverables 1 to 6 (3 as its verify-first clause says); no outcome row of the table, no outcome name and no public signature of `OutputParser` or `ParsedBuild` changes; the specification sentence and the two guides state what the code does. **Sonar:** the SonarCloud search of the pull request (`pullRequest=<N>&resolved=false`) lists no open issue other than one dismissed with its reason, and its quality gate is green, before the pull request is reported ready. **Build:** `verify -Ppre-commit` (its rewrites reviewed and committed), then `verify` of `pm-core` and `pm-runtime` (where a full run does not finish inside the host's bound, the targeted `-Dtest` runs of the changed classes and the per-module run, each reported in the pull request body), `verify -Pcoverage` and the integration tests of `pm-core` and `pm-runtime` are green. **Links:** run the links check (R17) from the main checkout against the documentation checkout at its `origin/main` (`git -C ../plan-marshall-documentation fetch origin main` first; the sibling checkout lags).
