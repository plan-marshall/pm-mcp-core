## Objective

Today a sub-workflow receives only closed values bound once per `call` from literals (`call_value` = enum value, integer, enum list; the lexer has no string token), so a commit message and a list of paths — the two things `git.commit_and_push` needs from its caller — have no channel: the specification's `step_or_fallback` "uses a step-supplied commit message" (`06-reusable-sub-workflows.adoc` line 40) and names no carrier, and `GitOperations.commit` stages every change of the worktree. This plan builds the channel the operator decided on 2026-10-29, on top of the interface of the first spec:

- new closed, server-validated input types: `text[lo..hi]`, `commit_message[lo..hi]` (a text that is additionally a Conventional Commit without a `Co-Authored-By` line; the server alone appends the trailer), `path` and `list<path>[0..n]` (relative, no `..`, inside the worktree, a subset of the scope's staging set; a violation is refused), each also with the trailing `?`;
- the caller declares a typed SLOT in its frontmatter; a task submit or an operator answer fills it (a `fills` clause of the state that receives the value); the call site binds it (`call git.commit_and_push entry commit (message = slot.commit_message, files = slot.files)`);
- the value is validated at the call — at the bind — and never inside the sub-workflow, and is typed data only: it is never put on a command line;
- the provenance of every bound value (`literal`, `task_submit`, `operator_answer`, and — because the first spec's order of resolution makes them possible — `config` and `default`) is recorded in the `call_stack` frame;
- every call frame also carries the identity of the command it is: a `command_id` (one per call) and the `correlation_id` of the advance that pushed it (one per engine advance, shared by every frame the advance pushes and, in the later plans of the command-model groundwork, by every primitive command it runs), both drawn from a `RandomGenerator` that the engine's ports carry;
- `git.commit_and_push` is the first user: its `message_mode` and `push_mode` become inputs of its frontmatter, beside the new `message` and `files`; the rest of its six-stage contract is unchanged. Every other sub-workflow migrates in a later plan (inventory in Dependencies).

**Decisions this spec takes (each becomes an ADR, R06):**

1. *`commit_message` is a closed type of its own*, not an attribute on `text`: the validator is chosen by the type, so a project copy of a unit cannot drop it (and `INV-GEN-1` of the first spec compares the type). It runs the existing `ConventionalCommitValidator` of `pm-core` (`core.spi.validation`), whose `commit.co-authored-by` rule already refuses the trailer line. Bounds: `text` and `commit_message` at most 2000 characters, a `path` at most 1024, a `list<path>` at most 500 entries (compiled caps, the unit may narrow them).
2. *The bound of a path is the scope's STAGING SET, not the footprint.* The operator wrote "a subset of the scope's footprint"; the specification (Stage 4, `06-reusable-sub-workflows.adoc` lines 243 to 244) stages "paths inside the worktree beyond the declared footprint … and records them as unplanned changes", and derives the staging set from the scope (a plan: the dirty paths inside its worktree; an epic: `.marshall/epics/**`, with `.marshall/archived-epics/**` while it archives; the workspace: the setup call's set). A footprint bound would refuse what the specification stages. The staging set is also the only set that is a set of FILES, so a directory — which JGit's `addFilepattern` would expand — can never pass.
3. *The path rules, in two layers.* Pure and syntactic (`workflow.input`): relative, `/` only, no empty segment, no `.` or `..` segment, no NUL, control or format character (the character classes of ADR `workflow-dsl/007`), no leading `:` (git pathspec magic) or `-`, no `.git` segment in any case, at most 1024 characters, a `list<path>` without a duplicate. Environmental (the engine's bind): `PathConfinement.confine` against the worktree root (R09: the refusal is the value `ConfinementOutcome.Rejected`, no exception) and membership in the staging set.
4. *Where a slot lives:* a new member `slots` of `mcp/status.json` (scope level, not a frame: the epic, workspace and plan units that call `git.commit_and_push` have no frame of their own, `store-schemas/02` lines 124 to 128), an object keyed `<declaring unit id>:<slot name>` with `{value, source, source_ref, filled_at}`. A slot is CONSUMED by the call that binds it (cleared in the same transaction): a stale message is never reused.
5. *Where a slot is filled:* by a state-level clause between `facts` and the state body, `fills slot.<name> from <param>`: in a `job llm` state from the argument of the accepted submission, in an operator wait from the free parameter of the link the operator followed. The value is validated against the slot type at the submit or the act — the worker or the operator gets `invalid_link_args` and can correct it — and again at the bind (the staging set may have changed since). The submission reaches the engine through the new component `submissions` of `EngineEvent.TasksSettled` (entity → argument name → text; a list as the JSON array text of the link parameter — confirm at the outline how a `list<…>` link parameter is carried); the operator's act already carries `OperatorAct.parameters`.
6. *The bind lives in `WorkflowEngine.call`*, with a new port `InputBindingContext` in `Ports` (worktree root, staging set, configuration value by key — the last for the first spec's `input_fallback`). A refusal at the bind raises the condition `precondition_unmet` (reason `input_refused`, naming the input and the rule) with its bounded self-remedy, because its cause can clear (the dirty set changes); an input a unit forgot to fill is the same condition with reason `input_unbound`.
7. *`message_mode` and `push_mode` stay REQUIRED enum inputs of `git.commit_and_push` with no `input_fallback`.* The operator's example (`message_mode` falling back to `project.git.commit.message_mode`) cannot be built: no such key exists in `store-schemas/07`, the specification says "No configuration key suppresses a push" (`06-reusable-sub-workflows.adoc` line 44), and `INV-FIN-4` reads the literal `push_mode` of the call site (`FinalizeInvariants.java` line 225). The fallback mechanism is built and tested by the first spec and by this plan's fixtures; the unit does not use it yet.
8. *`message` is consulted by `step_or_fallback` only* (it is the "step-supplied message" that has no carrier today; `interactive` keeps its compose task; `auto_deliverable` and `none_assert_clean` stay deterministic and refuse a bound `message` at the bind). *`files` narrows the COMMIT set to a subset of the staging set*: the footprint check of Stage 4 (1) keeps judging the whole staging set, so a dirty path outside `files` but inside the scope's set is left unstaged and is no violation, and a dirty path outside the scope's set stays a violation. Absent `files` means every path of the staging set, as today.
9. *Literal text at a call site stays out of the grammar* (no string token in the lexer; the model never types text into a unit): text and paths arrive only through a slot. The provenance `literal` therefore covers enum, integer and enum-list values, as today.
10. *A call frame is a command and carries its identity.* `command_id` (`^cmd-[0-9a-f]{16}$`, 20 characters) and `correlation_id` (`^cor-[0-9a-f]{16}$`, 20 characters) are new required members of the `call_stack` frame (`CallFrame.commandId`, `CallFrame.correlationId`, of the new types `CommandId` and `CorrelationId` in `core.id`), written and read strictly by `WorkflowStatusCodec` and pinned in the frame block of `store-schemas/02`. The engine draws them from a new component `ids` (a `java.util.random.RandomGenerator`) of `WorkflowEngine.Ports`: one `correlation_id` per `Run` (that is, per engine advance), one `command_id` per pushed frame; a test seeds the generator, the assembly passes a `SecureRandom`. A unit call is a command whose input is `bound_args` and whose provenance is `arg_sources`; with the two ids the frame is the whole identity of that command while it is on the stack. Nothing else of the command model is in this plan: the `Command` value, the dispatch of primitives through it and the settlement are the plan `command-record-and-dispatch`, the reason of a failing outcome is `primitive-failure-reasons` and `engine-carries-reasons`, and the persisted command log is a later follow-up. The ids are not secrets and not capabilities; they are references (uniqueness within the scope that owns the status; never reused).

**Decided by the operator on 2026-10-29** (do not re-litigate): (a) the bound of a path is the staging set, not the footprint (Decision 2); (b) a slot is consumed by the call that binds it (Decision 4); (c) `message` is consulted by `step_or_fallback` only (Decision 8); (d) `commit_message` is a type name beside `text` (Decision 1); (e) the `fills` clause sits on the state, not on the link; (f) the address form is unit-local, `input.<name>`, with the declaring unit as its owner: the call site binds explicitly (`callee_input = slot.x`), and wherever a bound value is named outside the unit (the frame's provenance, a log or audit field, a refusal message) it carries the qualified form `<unit id>.input.<name>`, which is never a registry key; (g) the third plan (`PLAN-V2-10` registries and primitives, staged by the orchestrator) owns the production registries, the primitives `git.resolve-message` and `git.stage-and-commit` and the entity kind `commit-message`, so Deliverable 4 specifies their contract and that plan implements it; (h) the call frame carries `command_id` and `correlation_id` (Decision 10) so that the command model of `primitive-failure-reasons`, `engine-carries-reasons` and `command-record-and-dispatch` needs no second frame migration.

## Standing Constraints

- **Log messages: none expected.** A bind refusal is a condition and a `Violation`, not a log line.
- **Format versions stay 1** (R13): the frame and the status member change in place; no reader for the old frame.
- **No command line from a value.** A bound text or path is never concatenated into a command, a path of the filesystem outside `PathConfinement`, a log message beyond 80 characters, or an audit field unbounded; the commit message goes to the repository over the API or `stdin`, as `PM-EXEC-5` says.
- **No generic `Exception`** is caught or thrown in production code; the refusal values of `InputValidator` and `ConfinementOutcome` are returned.
- **Add no dependency and no plugin** (CLAUDE.md).
- **The existing call sites keep working unchanged**: every `call git.commit_and_push (message_mode=…, push_mode=…)` of the specification (about a dozen sites in `phase-workflows/03`, `04`, `05`, `state-catalogue/04`, `08`, `17`, `18`, `workflow-dsl/03`, `08`) still verifies.
