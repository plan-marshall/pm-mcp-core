## Objective

A harness can answer a turn with another model than the one the launch named (a router, a fallback after an overload or a quota, a preview the account cannot use). The merged specification (`harness-profiles/01 #served-model`, `store-schemas/05`, `store-schemas/16 #activity-journal`, watch item PM-WATCH-CLIENT-20) asks the runtime to read the model of every turn through a new required usage pointer `headless.usage.model`, to record the distinct models of a row's turns as `served_models` of the task row of `metrics.json`, and to write the server entry `model_differs` into the task's activity once per change, naming both models. A different model is recorded and shown, never acted on. #354 changed prose and the inline profile schema block only: the validator still closes `headless.usage` to the seven numeric figures and refuses `model`, and neither JSON schema file, the activity kind enum, the row record nor the shipped `claude` profile knows the member. This plan brings the code and the schema files to the specification: the pointer in the validator, `served_models` in the row, `model_differs` in the journal, and the pure reading and comparison the runtime's pump uses. The wiring of the pump in the daemon, the shipped profiles and the clients' display are owed outside this repository and are listed, not done.

## Carried Open Items

Open design questions are not decided silently. Each carries a recommendation and a confidence; items 1, 2, 3 and 6 are asked of the operator at refine (R07: they change the contract or the file set), the others are settled by the orchestrator at emit unless the operator objects. None adds a dependency or a plugin.

1. **Which lines carry the model (Claim 13).** The specification says the runtime reads the model "of every turn" and that `claude` declares the model of its `assistant` messages; the shipped `claude` maps its activity kind `turn` from `result` lines and `text` from `assistant` lines. Recommendation: apply the pointer to every parsed line of the stream, independent of the events mapping (D5). The alternative (map `assistant` lines as `turn`) changes the usage reading and the per-turn entries. Confidence 65%. The wording "of every turn" of `#served-model` is then corrected to "of every line of the output stream that carries one".
2. **The comparison rule for an alias (Claim 14).** `models_probe` lists identifiers and maps no alias, `claude` declares it `null`, and the watch guard demands that an alias launched against a turn that reports the full identifier writes no entry while a switch from one release to another is seen (PM-WATCH-CLIENT-20, hazard 2). Options: (a) exact string equality only: simple, fails the alias guard, writes one false entry per run for an alias; (b) exact, or the served identifier equals the launch model plus a trailing snapshot suffix of eight digits (or an ISO date) after a hyphen: keeps a release switch visible, is harness-shaped; (c) a new optional profile member for aliases: a schema change the specification does not make. Recommendation: (b) behind the seam of D5 with the rule stated once in the ADR, and the specification sentence corrected to say what is implemented; the alias resolution through a listing stays the assembly's. Confidence 55%. Operator decides: it changes what the specification promises.
3. **The wire members of the entry.** `model_differs: { "launch": "...", "served": "..." }`; the clients' text uses `{launched}` and `{served}`. Recommendation: `launch` and `served`. Confidence 75%.
4. **Does the `turn` entry's usage object carry `model`?** Recommendation: no; the usage object stays the seven numeric figures (ADR runtime-worker/013), the model is carried by the row and the entry. Confidence 75%.
5. **`served_models` of a refused row and of a row whose profile declares a pointer but no turn resolved it:** `"unmeasured"`; the `worker_idle` row has no member (the specification names task rows). Confidence 85% and 80%.
6. **The verification stage `usage` and `model` (Claim 15).** The stage text says every declared pointer must resolve; for `claude` the `model` pointer addresses an `assistant` line that the stage's one captured turn (the `result` line) does not carry. Recommendation: the stage does not check `model` in this plan; the specification statement is corrected to "every figure", and a stage check of the model pointer against the captured output is named as a follow-up. Confidence 70%.
7. **The shape of the pointer:** a string starting with `/`, at most 256 characters; `not_applicable` refused (a harness that does not report the model declares `null`). Confidence 80%.
