## Objective

After this plan `pm-core` tests its codecs against the schema files with the 3.x line of `com.networknt:json-schema-validator`, the nine test classes call the validator's current API, every positive check still proves the document valid and every negative control still proves a mutated document refused (so no check passed vacuously through the change of the result type), the transitive Jackson 3 libraries are on the test classpath only, the decision on them and on the parent POM is recorded, and the pull request that carries it is opened with the label `skip-bot-review`. Pull request #71 is superseded by it and closed.

Not here: a production use of the validator (ADR `core-profile/001` and `doc/adr/016`: it stays a test-scope dependency, a stored record is not validated at run time), a change to any schema file, specification block or codec to suit the new library, a move of the validator into the generator artifact `pm-core:tests`, and any other dependency bump.

## Deliverables

1. **The nine schema tests call the 3.x API.** The test classes that import `com.networknt.schema` at `d1fb719f` (re-grep at the head: PLAN-V2-119, 121, 122 and 123 land before this plan and may add or retire users) are `AnalysisResultSchemaTest`, `ConsentSchemaParityTest`, `ModelCatalogueSchemaParityTest`, `RoleAssignmentsSchemaParityTest` (all four under `pm-core/src/test/java/de/planmarshall/core/{analysis,config}`), `TaskQueueSchemaParityTest` (`queue`), `CorpusSchemaResourcesTest` and `ItemGeneratorTest` (`role/corpus`), `AuditSchemaParityTest` and `PlanHistorySchemaParityTest` (`store`). Every one imports `InputFormat`, `JsonSchemaFactory`, `SpecVersion` and (but `ItemGeneratorTest`) `JsonSchema`; every one builds the validator with `JsonSchemaFactory.getInstance(SpecVersion.VersionFlag.V202012).getSchema(<text>)` and validates a `String` with `validate(<text>, InputFormat.JSON)`. The pull request #71 fails to compile at exactly these imports (`cannot find symbol: class JsonSchema`, `JsonSchemaFactory`, `SpecVersion`, `location: package com.networknt.schema`, CI run 42371458088, 2026-11-07), so the class names of the 3.x line differ; the outline reads them from the library's own Javadoc and README (HYPOTHESIS: `Schema`, `SchemaRegistry`, `SpecificationVersion`, and a result of `Error` items in a `List`, not `ValidationMessage` items in a `Set`). **The trap is the result type.** Twelve assertions compare `assertEquals(Set.of(), <result>, ...)` (`AnalysisResultSchemaTest` 103, `ConsentSchemaParityTest` 113, `ModelCatalogueSchemaParityTest` 97, `RoleAssignmentsSchemaParityTest` 98, `TaskQueueSchemaParityTest` 112, `CorpusSchemaResourcesTest` 145, `ItemGeneratorTest` 151, 180 and 296, `AuditSchemaParityTest` 108, `PlanHistorySchemaParityTest` 119 and 121) and seven more assert `assertFalse(<result>.isEmpty())` (`AnalysisResultSchemaTest` 113, `CorpusSchemaResourcesTest` 158, 167, 176, 189 and 190, `PlanHistorySchemaParityTest` 131). If the result becomes a `List`, `Set.of()` never equals it, so every positive assertion fails (loud) — but a naive fix that turns the positive checks into `assertTrue(<result>.isEmpty())` is right only if the negative controls still fail for a reason: a validator that has silently stopped validating (a schema that did not load, a dialect that was not selected) makes **every** positive check pass and every `assertFalse(...isEmpty())` fail, so the negative controls are the proof and are kept. The two helper methods that declare `Set<?>` as their return type (`AnalysisResultSchemaTest` line 93 and `CorpusSchemaResourcesTest` line 88) take the new type. Whether the nine classes keep a private call each, or the call moves into one helper of `pm-core`'s tests that the nine share, is ask-at-refine (B5): the default is the minimal edit per class, because a helper in the `pm-core:tests` artifact changes the artifact's surface (ADR `doc/adr/012` and `016`) and a helper in the test tree alone would be a tenth file for a one-line call. **Done when:** the nine classes (plus any the head adds) compile and pass against the 3.x line with no schema file, specification block, codec or expected value edited, every `assertEquals(Set.of(), …)`-style positive check is replaced by the equivalent for the new result type and carries a message of 20 to 60 characters, and the negative controls of each class are shown, in the pull request body, to fail when the schema is replaced by `{}` in a scratch run (the failing run is reported, nothing of it is committed).
