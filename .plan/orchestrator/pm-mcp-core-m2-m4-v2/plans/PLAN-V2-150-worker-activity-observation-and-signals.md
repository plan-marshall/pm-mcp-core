## Objective

A harness reports a write only through the tools its mapping names, never one made by a command it runs, and a harness without a mapping reports none: so the specification says the runtime observes the files a worker changes itself (`01-profile-schema.adoc:306`): for a worker whose working directory is a git work tree, the runtime runs `git status --porcelain --untracked-files=all` and takes a digest of every path it lists when the attempt begins and again after every `tool_result` entry, without holding the worker, and appends one `file_changed` entry per path whose presence or digest differs, unless a harness `file_changed` named that path since the last observation; ignored paths are not observed; a `zero_tool` role, or a worker with no git work tree, has no observation. On top of those entries the off-track signals `failing_again` and `edit_churn` (`model-work/03-supervision-and-recycling.adoc`, the rows at about `:83` and `:86`) are computed from the `pm_build` results and the `file_changed` entries of the current plan task. At the head nothing observes (`ActivityRecorder.append` journals only entries it is given; the only `ProcessBuilder` in `pm-runtime/.../worker/` is `VerifyingBinaryCheck.java:154`), `ActivityEntry.Kind.FILE_CHANGED` is a harness-sourced kind (`ActivityEntry.java:~123`), `QueueTaskRecord.SignalName` has five signals (`repeating`, `no_progress`, `over_size`, `outside_footprint`, `agent_started`: `QueueTaskRecord.java:~408-420`) and `failing_again` and `edit_churn` appear only in `role-artifact-v1.schema.json:59-60`. This plan builds the observation and the two signals.

## Standing Constraints

- **The observation never executes anything a worker wrote:** no hook, no fsmonitor, no filter driver, no worker-controlled `git` configuration (Deliverable 1); a worker is not held while it runs.
- **A write is counted once:** a harness `file_changed` and the runtime's observation of the same path do not double count.
- **The schema files are the authority** for the task record and the activity entry; a member or a signal name is added to the file, the codec and the parity test in one commit.
- **No retry loops, no polling:** an observation is taken at the start of the attempt and after a `tool_result` entry, nothing else.
- No dependency or plugin; no hand-written test double (EasyMock only; a fixture `git` is a script in `@TempDir`); where the project analyses its pull requests with Sonar, read it over plain HTTP (`pullRequest=N`, never `branch=<feature>`): an open issue is fixed in a pushed commit or dismissed with a stated reason `{issue-key}: {reason}` through `plan-marshall:workflow-integration-sonar:sonar_rest transition --issue-key {key} --transition {falsepositive|wontfix}`.
- **Review lens:** `plan-marshall:persona-security-expert` is the lens of the deliverables that parse or confine untrusted input (read it as the R20 paragraph says); the `Persona:` lines name the work identity only (the persona grammar takes a plain name).
