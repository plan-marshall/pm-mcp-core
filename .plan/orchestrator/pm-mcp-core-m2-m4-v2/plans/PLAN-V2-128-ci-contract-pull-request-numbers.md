## Objective

The CI contract keeps an issue and a pull request apart by their types: `CiProvider.issueView` and `issueComment` take an `IssueRef`, `prView` takes a `PullRequestRef`, and `ForgeUrl.pullRequest()` is present exactly for a pull-request URL (ADR `provider-ci/009`, PLAN-V2-62). Reading the merged code at `d1fb719f`, the split is closed on one side only and leaks in three places that are all about the number a person names:

- a pull-request URL copied from the browser's tab of the pull request (`/pull/7/files`, `/-/merge_requests/7/diffs`) is `INVALID`, so the number cannot be read from it at all;
- `ForgeUrl` offers `pullRequest()` but no `issue()`, so the only way to an `IssueRef` from a resolved URL is `new IssueRef(url.repository(), url.number())`, which is also what a consumer writes for a pull-request URL;
- `issueComment` of an `IssueRef` whose number names a pull request is unguarded on both forges: on GitLab the note lands on the issue that happens to carry that iid (the two are numbered apart), on GitHub it lands on the pull request through the issues endpoint although `ci.issue-comment` is specified as "the write-back to an issue of the project's own repository" (State Catalogue 09 § Issues by Number or URL, line 173).

The operator decided on 2026-11-09 that these functional defects get a plan. Deliverable 3 reopens the part of ADR `provider-ci/009` that left `issueComment` unguarded and is therefore ask-at-refine (R07). All line numbers are those of `origin/main` at `d1fb719f`; this plan re-reads them at the head.

Not here (owned elsewhere, decided elsewhere or left open): the phase value of `handed_back`/`returned` in the specification (`WorkflowEngine.ended`) is an operator fork recorded in `epic.md` and is untouched; the `Primitive` wrapper `ci.pr-view` and its outcomes (the assembly `plan-marshall-mcp`); the review and finalize slice that will own "a comment on a pull request" (`ci.pr-comment`, no staged plan); PLAN-V2-93 (the hand-written `Dispatcher` of `GitHubClientTest`, `InstallationTokensTest`, `GitLabClientTest`), PLAN-V2-92 (provider test data) and PLAN-V2-103 (assertion messages) own the test conformance of the files this plan touches; the other leftovers of the analyses are in Carried Open Items.

## Deliverables

1. **A pull-request tab URL names its pull request (failing case first).** `ForgeUrl.resolveGitHub` (lines 244 to 267) requires exactly four path segments (line 245) and `resolveGitLab` (lines 269 to 294) requires the `-` separator at the third segment from the end (line 270), so `https://github.com/<owner>/<name>/pull/7/files` is `INVALID` ("a GitHub or Forgejo source URL has four path segments") and `https://gitlab.com/<group>/<project>/-/merge_requests/7/diffs` is `INVALID` ("a GitLab source URL ends with /-/issues/<n> or /-/merge_requests/<n>"), both by the reading of the code. Write the failing cases first in `ForgeUrlTest`: each of the two URLs (generated owner, name, group and number around the literal operation and tab segments, which are the grammar) must resolve with `Kind.PULL_REQUEST` and that number; they fail against `d1fb719f` (report the failing run). Then accept exactly one trailing tab segment after the number of a pull-request path, from a closed list per forge, and nothing after an issue number: GitHub `files`, `commits`, `checks`; Forgejo `files`, `commits`; GitLab `diffs`, `commits`, `pipelines`, `changes` (the list is HYPOTHESIS, taken from the forges' web interfaces; the outline verifies it against their documentation and records it in the Javadoc). A tab on an issue path (`/issues/7/files`), an unknown tab, two trailing segments and a tab after a zero or padded number stay `INVALID`; the number rule (ASCII digits, no leading zero, at most nine digits; lines 296 to 307) is unchanged; a query and a fragment stay ignored. **Done when:** the cases for the three forges pass and failed before, the negative cases (issue path with a tab, unknown tab, two segments) pass, the existing `reportsInvalidUrls` and `coversRemainingGrammarBranches` cases pass unchanged, and the class Javadoc (lines 24 to 33) and `provider-ci.adoc` state the grammar with the tab list.
2. **`ForgeUrl.issue()`, the missing half of the split.** `ForgeUrl.pullRequest()` (lines 161 to 166) returns the `PullRequestRef` exactly when the kind is `PULL_REQUEST`; the issue side has no accessor, so a consumer that holds a resolved URL builds an `IssueRef` from `repository()` and `number()` whatever the kind (ADR `provider-ci/009` says "the split is made by the type a consumer holds", and the type of the issue side cannot be obtained from the URL by kind). Add `Optional<IssueRef> issue()`, present exactly when the kind is `ISSUE`, mirroring `pullRequest()` (the outline records that `Optional` is a return type here, CLAUDE.md). Failing case first: `ForgeUrlTest` gets the symmetric case to `names no pull request for an issue URL` (line 99) — an issue URL has an `issue()` and no `pullRequest()`, a pull-request URL the reverse — which does not compile against `d1fb719f` (report that). `ForgeUrl.number()` and `kind()` stay components of the record (their callers in the assembly are outside this repository; a removal is a decision for the operator and not taken here). **Done when:** the case passes, `provider-ci.adoc` (lines 42 and 127 to 129) names `issue()` beside `pullRequest()` and tells a consumer to obtain an `IssueRef` from `issue()` and a `PullRequestRef` from `pullRequest()`, and no production class of this repository builds an `IssueRef` from a `ForgeUrl` by hand (a search is reported; none is expected, the consumers live in the assembly).
3. **`issueComment` on a pull-request number (R07: ask at refine).** `GitHubCiProvider.issueComment` (lines 176 to 192) refuses a foreign origin and a blank body and then posts through `userClient().postComment(...)` (line 185), which targets `issues/{n}/comments`; `GitHubClient.postComment` (Javadoc lines 246 to 255) accepts "a pull request or issue number". `GitLabCiProvider.issueComment` (lines 143 to 160) posts through `GitLabClient.issueComment(long)` (line 332) to `issues/{iid}/notes`. ADR `provider-ci/009` (line 41) decided "`issueComment` gets no pull-request guard" and rejected the guard for GitHub as "a read before every comment"; the specification writes back twice per plan (after Phase 2 and after Phase 3, State Catalogue 09 line 173), so the read costs two requests per plan, and `issueView` already flags the `pull_request` member (`GitHubCiProvider.java` line 171). The default of this plan: **GitHub** — `issueComment` reads the issue first with the credential the comment uses, answers `REJECTED` "is a pull request" without sending the post when the read flags one (the reason of `issueView`, line 171), and propagates a failed read as its outcome (`issues: write` covers the read; the outline verifies that for the installation token and the user token of `GitHubCiProvider`); **GitLab** — no guard is possible from the number: `issues/{iid}/notes` addresses an issue by GitLab's own numbering, so a merge-request iid is by definition the iid of some issue, and a probe of `merge_requests/{iid}` would restore the defect ADR `provider-ci/006` removed; the adapter keeps its behaviour, the contract Javadoc says so, and the protection is Deliverable 2's type. Failing cases first: (a) `GitHubCiProviderTest` — the mock serves `GET issues/7` with a `pull_request` member and counts requests to `POST issues/7/comments`: the outcome is `REJECTED` and the count is 0 (fails against `d1fb719f`: the post is sent and answers `OK`; report the failing run); (b) the same number without the member posts as today (`postsComment`, line 525, stays green and gains the read in its dispatcher); (c) a failing read (`404`, `403`, `429`, `5xx`) is the outcome of `issueView` for the same status, no post is sent; (d) `GitLabCiProviderTest` — a characterisation case: the mock serves both `issues/9` and `merge_requests/9`, `issueComment` requests `POST issues/9/notes` and never a `merge_requests` path. The alternative the operator may choose instead is to keep ADR `provider-ci/009` and ship Deliverables 1, 2 and 4 only; the plan then records (a) to (c) as dropped. **Done when:** under the default (a) to (d) pass, (a) failed before, a new ADR supersedes in part the `issueComment` bullet and the third alternative of ADR 009 and says what the GitLab limit is, and the Javadoc of `CiProvider.issueComment` (lines 67 to 74) states both behaviours (it names only the foreign origin today).
4. **The statements say what the code does.** `provider-ci.adoc` lines 198 to 199 ("`issueComment` gets no pull-request guard, because `IssueRef` carries no kind (module ADR 009)") is rewritten to the outcome of Deliverable 3; `CiProvider.issueView` Javadoc (lines 60 to 65) and `prView` Javadoc keep their statements and gain the `issue()` / `pullRequest()` pointer; `provider-github.adoc` (lines 67 and 109) and `provider-gitlab.adoc` (line 71) state the guard and the GitLab limit; ADR 009 gets a "superseded in part by 010" note in its Status and its Consequences bullet "`issueComment` on a pull-request number still posts on GitHub" is corrected by the new ADR, not edited in place; `doc/Traceability.adoc` adds the lines of the requirement this plan implements (the PM-EXEC-5 paragraph at line 994 names the pull-request read; the sentence at lines 981 to 982 that still says the read "is not implemented yet" is read against R08 and corrected only if the outline concludes that correcting a now-false sentence of the plan's own requirement is within R08, otherwise it is carried). **Done when:** the statements are corrected, the ADR follows `doc/adr/template.adoc`, and every link resolves (R17).

**Done when:** Deliverables 1, 2 and 4, and Deliverable 3 as the operator answers it at refine; the public signatures of `CiProvider`, `IssueRef` and `PullRequestRef` are unchanged (`ForgeUrl` gains one method). **Sonar:** the SonarCloud search of the pull request (`pullRequest=<N>&resolved=false`) lists no open issue other than one dismissed with its reason, and its quality gate is green, before the pull request is reported ready. **Build:** `verify -Ppre-commit` (its rewrites reviewed and committed), then `verify` of `pm-provider-ci`, `pm-provider-github` and `pm-provider-gitlab` (where a full run does not finish inside the host's bound, the targeted `-Dtest` runs of the changed classes and the per-module run, each reported in the pull request body) and `verify -Pcoverage` are green; `verify -Pintegration-tests -pl pm-core -am` is not owed (no `pm-core` file). **Links:** run the links check (R17) from the main checkout against the documentation checkout at its `origin/main` (`git -C ../plan-marshall-documentation fetch origin main` first; the sibling checkout lags).
