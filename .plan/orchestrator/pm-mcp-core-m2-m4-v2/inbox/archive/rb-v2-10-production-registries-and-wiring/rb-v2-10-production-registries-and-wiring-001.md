## 10. The Maven Central 429 (a CI observation, reported separately)

**What happened.** One job, `integration-tests / test` at head `9aa4a1be`, failed although the code was green:

```
Failed to collect dependencies at org.apache.maven.surefire:surefire-junit-platform:jar:3.6.0:
  Could not transfer … from/to central (https://repo.maven.apache.org/maven2):
  status code: 429, reason phrase: Too Many Requests
```

Failsafe could not resolve its provider, no integration test ran, and the report assembly then found no report directory.
A re-run of the same run (`44301175934`) passed, and every other Maven job in that run passed, so this is a transient
external condition, not a defect of the change.

**General or ours?** General as a phenomenon — Central rate-limits by client IP and hosted runners share egress pools.
Structural for us in its exposure, for two reasons visible in the log:

1. The restored cache is `Linux-m2-<hash>` with `restore-keys: Linux-m2` and `fail-on-cache-miss: false`. Its key is
   derived from this repository, but the surefire/failsafe version comes from the parent POM in the organisation registry:
   a parent-only bump to 3.6.0 changes no local key, so the new provider is never in the archive. GitHub caches are
   immutable per key, so that archive cannot pick it up later — every run fetches the delta live.
2. Five Maven jobs of the same run resolve the same coordinates in parallel from one egress IP, and the integration profile
   pulls failsafe's provider only at the last moment.

**What would fix it, cheapest first.**

1. Back-off instead of failing: `-Dmaven.wagon.http.retryHandler.count=5` (Aether:
   `-Daether.connector.http.retryHandler.count=5`). One property, and it is exactly the class of failure retries exist for.
2. Warm the cache under the profile that needs the artifact: a `warm` job running `dependency:go-offline
   -Pintegration-tests` and saving the cache, so the provider is a hit rather than a live fetch.
3. Order the jobs (`integration-tests` after `build`) so parallel jobs stop racing the same coordinates.
4. Key the cache on the effective dependency set, including the resolved parent version or a manual rotation suffix, to
   defeat the immutable-key freeze.
5. An organisation mirror/proxy or a pre-warmed runner image — most effective, and an infrastructure decision.

Items 1–4 live in `cuioss/cuioss-organization`'s reusable workflows (pinned `v0.44.0` by SHA), or are operator decisions;
none belongs to this plan's surface, so nothing was changed here. Recommended as a CI-hardening follow-up in that
repository, with the run id `44301175934` as the evidence.
