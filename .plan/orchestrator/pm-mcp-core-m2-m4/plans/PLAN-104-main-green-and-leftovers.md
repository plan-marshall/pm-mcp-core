## Objective

`main` is red. `FindingSchemaParityTest.enumerationsEqualSchema` fails at `20ce71c8` (run on 2026-10-25 with `test -pl pm-core -am -Dtest=FindingSchemaParityTest`: `values of de.planmarshall.core.findings.FindingSourceKind at 'source' ==> expected: <[analysis, arch_gate, capability_tests, ci, …]> but was: <[analysis, arch_gate, ci, …]>`). The cause is a specification-only pull request: #177 added `capability_tests` to the `source` enum of the findings ledger record in `doc/specification/store-schemas/03-findings-and-review-records.adoc` and no code followed. It was the second time in four days (#171 broke the same test and PLAN-29 fixed it on its own branch), and it will happen again, because the reusable workflow that builds this repository skips the whole build when a pull request changes only `.adoc` files, while the schema parity tests read the specification's `.adoc` files as their input (ADR `doc/adr/007`). The operator decided on 2026-10-25 to switch the skipping off.

This plan does four things, in this order: it turns `main` green (Deliverable 1); it closes the hole so a specification-only pull request runs the parity tests (Deliverable 2); it clears the owed findings the lane of PLAN-31 reported after its merge, with the three major ones corroborated in the code (Deliverables 3 to 5 and the minors of 6); and it clears the other small, mechanical leftovers of the landed plans that no staged plan owns (Deliverables 7 to 9). It is a plan of fixes: no new capability, no new dependency, no new package.

## Deliverables

1. **Green `main`: the finding source `capability_tests`.** Add `CAPABILITY_TESTS("capability_tests")` to `FindingSourceKind` (`pm-core/.../core/findings/`, after `DEPENDENCY_DELTA`, the constant its wire name follows in the schema), update the list of wire names in `FindingSourceKeyTest`, and keep the neutrality guard as it is (`ProviderNeutralityArchTest` exempts exactly `GITHUB_PR` and `GITLAB_MR`; the new constant is a server check and names no provider). **Verify first, in the pull request body:** run the whole build once with test failures ignored (`verify -Dmaven.test.failure.ignore=true`) at the branch point and list every failing test of every module; the orchestrator measured `pm-core` only for the whole module (3419 tests, 1 failure, the build stops there), and then ran every test class that reads the specification in every module (339 tests: 338 passed, 6 skipped, 1 failed: this one), so no other specification-reading test is red; the rest of the unit tests of `pm-workflow`, `pm-runtime` and the providers were not reached, because a full `verify` stalled past a 1500-second bound on the orchestrator's host (two runs; the lane of PLAN-29 saw the same stall in a module its diff did not touch), so run the modules one by one if the full build stalls for you too and report which one stalls. A further red that is caused by a specification part newer than its record and is mechanical (an enum value, a member) is fixed the same way in this deliverable; any other red is reported as a lead and not fixed here. Extend `pm-core/doc/developer/core-findings.adoc` where it lists the sources, and write one ADR in `pm-core/doc/adr/core-findings/` if the fix takes a decision (it does not take one for a plain enum value: then say so in the pull request body and write none).
2. **Close the hole: do not skip the build for a specification-only pull request.** Set `maven-build.skip-on-docs-only: false` in `.github/project.yml`, with a comment that names the reason (the parity tests read `doc/specification/**/*.adoc`, ADR `doc/adr/007`). Name the pinned reusable workflow (`cuioss/cuioss-organization` `reusable-maven-build.yml` at the SHA of `.github/workflows/maven.yml`, v0.42.0) and the input in the pull request body, as read from that workflow. Write one repository ADR in `doc/adr/` (next free number; Status, Date, Context, Decision, Alternatives considered, Consequences, Source): the decision is the operator's of 2026-10-25; alternatives are keeping the skip and asking the author of a schema change to run the parity tests locally, and a parity-only job on docs-only pull requests (a new workflow file, which needs the operator's explicit decision); the consequence is a full build, about eight minutes, on every pull request. This pull request changes a non-`.adoc` file, so its own build runs; that it also holds for a docs-only pull request can only be proven by the next one, and the pull request body says so as an unverified expectation. Add the one line to `doc/adr/README.adoc`.
3. **`MetricsStore` writes through the scope transaction.** `MetricsStore` is built over an `AtomicStoreFile` and writes `metrics.json` outside the scope's `ScopeTransaction`, so the digest sidecar does not cover it, although `store-schemas/13` (§ Which stores a sidecar covers) lists `metrics.json` among the stores "each written by a transaction of the scope". Write it the way the stores that already do (`WaiverLog`, `QuestionLog`, `WorkflowStatusStore`) write: through `ScopeTransaction.replace` of the scope, so the sidecar entry is recorded. Its public behaviour (one row per attempt, a second row refused, foreign rows kept verbatim) does not change; its constructor changes to what the scope-transaction stores take. There is no production caller of the store yet, so no caller changes. Tests in `MetricsStoreTest`: a row appended through the store has a sidecar entry; an out-of-band edit of `metrics.json` is reported by the integrity check as the other covered stores' edits are.
4. **`ChangeLedger` writes through the scope transaction.** The same for `change-ledger.jsonl`: it is built over a `JsonlStoreFile` and `append` draws no sidecar entry; write it through `ScopeTransaction.append`. Tests in `ChangeLedgerTest` as for D3 (sidecar entry, out-of-band edit).
5. **`QualificationSettingsStore` refuses a stale revision.** `store-schemas/12` states the `revision` of the operator files: "incremented by every write; a change against an older revision is refused with `conflict`". `QualificationSettingsStore.write(settings)` takes no revision, so it cannot refuse. Change it to take the revision the caller read and refuse with a `conflict` refusal (the kind the store refusals of `core.store` already carry, or the nearest existing one; do not invent a second vocabulary) when the document's revision differs, and read the revision back with the settings. Tests in `QualificationSettingsStoreTest`: a write against the current revision succeeds and increments it; a write against an older revision is refused and the document is unchanged.
6. **The minor findings of the PLAN-31 review.** (a) `MetricsStore` does not enforce the per-scope row partition of `store-schemas/05` § Scope (the epic and workspace files hold only task rows and served-read rows with `phase: null`, the workspace file also the `worker_idle` rows, and those are never in a plan's figures): refuse a row that does not belong to the scope of the store, with a test per scope. (b) `QualificationSettings` does not check that `skip_roles` holds no role twice: refuse a duplicate, with a test.
