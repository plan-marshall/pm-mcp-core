## Deliverables

The bullets of `doc/plans/process-designer.adoc` § What, in its words.

1. Specification first*: the package writes the change Designing a Process into `plan-marshall-documentation` as part of its own work, once it and UC-PLN-3 are agreed: the requirement the change drafts in the workflow requirements (today no requirement lets the operator change the process of a plan); the machine level of workflow units and its precedence; the validation endpoint with its dry-run composition; the place and remove endpoints and their audit; the project-level placing as a short landing; the catalogue of building blocks served to the client.
2. What can be designed*: a unit the operator may own, the project-owned units of the state catalogue (the phase units, `remediation.*`, `replan`, `adjudicate.decisions`, `git.commit_and_push`), the variants of the plan behaviour axes (`landing.*`, `method.*`, `ask.*`), and recipes; a compiled-only unit (epic, setup, bootstrap, source units, `chat`, …) is served read-only as a building block, and placing one, or a unit of its name, is refused.
3. The axis variants as owned units*: each variant of `landing.*`, `method.*`, and `ask.*` becomes an owned unit with the compiled invariants of the part of the process it takes over (a landing variant those of the landing part of `finalize`, a method variant those of the order of tasks in `execute`, an asking variant those of the phase transitions it waits at). An axis's variants are a closed list: a variant can be changed, never added; placing a variant name the axis does not list is refused.
4. Recipes at project level only*: a recipe's workflow lives beside its recipe, `.marshall/recipes/<id>.pmwf`, and is designed and placed only there; the machine level holds workflow units, never recipes, and placing a recipe at machine level is refused.
5. The machine level*: a new level of workflow units, `<PM_MCP_BASE>/workflows/<unit>.pmwf` (the operator's, never committed), in force for every project of the machine that has no copy of its own. *This package builds the unit resolver*, in the loader of `project-units-and-invariants` and in the composition of the plan instance alike: a unit resolves by the precedence project copy › machine copy › compiled default, and only an absent unit defers to the next level; a unit present but unparsable or violating a declaration bound or an invariant never falls back to the next level: it refuses the lifecycle of every project it is in force for, naming the file and line. The plan's own choice of an axis variant stays as the change Plan Behaviour Axes defines (Use Cases, Plan Behaviour Axes). A machine unit is held to the same declaration bounds and compiled invariants as a project unit.
6. No copies at setup*: the setup no longer copies every default unit into `.marshall/config/` (`setup.prepare-workspace`); a project holds only the units it changes. The package changes this in the specification (Workflow DSL § Project-Owned Workflow Units, items 1 and 2; Domain Extensions § Setup State Machine; State Catalogue § Setup; Filesystem Layout § Project Store; Store Schemas § Project Configuration) and in the code (the setup unit, and the loader of `project-units-and-invariants` where it is already implemented). The plan instance's header digests name the level and file each unit came from, so a changed machine unit is adopted through the existing `config_drift` like a changed project unit.
7. The installed units*: for a project, each designable unit in force with its level, and the text of each level present (project copy, machine copy, compiled default), so the designer can start from any of them; a compiled default only as text to copy. For the machine, with no project chosen, the machine level's units with the compiled defaults, so a machine-level unit is designed without a project.
8. Validation*: one endpoint takes the unit's text, its kind and name, and a target project or the machine (then composed against every enrolled project the unit would reach, each finding naming its project), and validates it exactly as the loader would load it: the parse, the static verification rules, the compiled invariants of a project-owned unit, and a composition dry-run, a plan instance composed with the unit against the project's effective configuration, roles, and providers, started nowhere and stored nowhere. The answer lists the findings, each with its rule, line, and column; the parsed structure of the unit (its states, calls, outcomes, and transitions) whenever the text parses, also when other rules find problems, so the web app keeps its structure view in step without a parser of its own; and, when there are no findings, the composed process in the structure the plan view shows (UC-PLN-1). The validation runs nothing of the unit. The text, pasted or from an uploaded file, must be UTF-8 within a size limit the runtime declares as a bound; a text that is not, or exceeds it, is refused before the parse.
9. The catalogue of building blocks, in two scopes*: for a project, as that project resolves it (its copies over the machine's over the compiled defaults, its effective role set); for the machine, the compiled and machine-level units and the machine's role set. Validation for a machine target still runs against every enrolled project the unit reaches.
10. The catalogue is complete*: every element the DSL can use, each with what the designer inserts and what it needs: the primitives of `do`, `auto`, `job`, and `guard` with their parameter records and outcomes; the guards; the link relations and their forms; the condition kinds; the reusable and compiled sub-workflows with their parameters and outcomes, the phases among them as sub-workflows; the roles of the effective role set with their class; the declarable parameters with their compiled bounds; the keywords and clauses (`state`, `skill`, `link`, `call`, `declare`, `migrate`, …) with a template each.
11. One source for the catalogue*: it is generated from the registries the parser, the static verifier, and the composition use (the primitive SPI, the role sets, the unit loader), never from a list kept apart, so what it offers is exactly what validation accepts. It carries the runtime's version and a digest over its content; the digest changes after an upgrade or a placing, and the client reloads it then.
12. Placing*: at machine level, writing the machine copy; at project level, writing `.marshall/config/<unit>.pmwf` in the project's checkout and landing it as a short landing like `git.land-removal` and the epic's ledger (one commit, landed by the project's landing: `landing.pull-request` or `landing.main`; with `landing.files` it stays uncommitted in the working tree). A project unit is in force for a plan when the plan's checkout or worktree has it: a new plan takes it once it has landed on the base branch; a running plan adopts it through `config_drift`, where the composition rules allow it, once its worktree gets it at its next sync with the base; with `landing.files` it stays in the operator's checkout and no plan takes it until it is committed. A machine placing or removing validates against every enrolled project the unit would reach (for a removal, the unit of the next level) and is refused while any of them fails, naming each such project. Every placing validates again in the same request and refuses a unit with a finding; it carries the digest of the unit it replaces (none for a new one) and is refused with the current one where that changed meanwhile, so the difference the client showed is the one confirmed. Removing a placed unit returns to the next level, the project's copy through the same short landing.
13. Path confinement*: every route that names a unit, at machine and at project level, validates the name against the canonical unit-name grammar (the `state_id` of the Identifier Registry: no path separator, no `..`, no absolute path) and accepts only a name the catalogue lists as designable for that level; the path it resolves to is then checked to lie inside its target directory (`<PM_MCP_BASE>/workflows/`, `.marshall/config/`, `.marshall/recipes/`) after normalisation and the resolution of links, before any write or delete. A request that fails either check is refused with `unit_name_invalid` (`400`) before anything is read, written, or removed.
14. Audit*: every placing and removing as an audit record of `audit-trail`: who, when, the channel, the level, the project, the unit, and the digests before and after.
15. The endpoints* (the change fixes their names; proposed): `GET /api/v1/projects/{project_id}/workflows` (the installed units of a project), `GET /api/v1/workflows` (the machine level's installed units with the compiled defaults), `GET /api/v1/projects/{project_id}/workflows/catalogue` (the building blocks as the project resolves them), `GET /api/v1/workflows/catalogue` (the building blocks of the machine scope), `POST /api/v1/workflows/validate` (text, kind, name, and the target: a project id, or `machine` with no project, which composes against every enrolled project the unit reaches → findings, the parsed structure, and the composed process), `PUT` and `DELETE /api/v1/workflows/{unit}` (machine level), `PUT` and `DELETE /api/v1/projects/{project_id}/workflows/{unit}` (project level; a recipe's workflow is a unit of kind `recipe` on the same routes and goes to `.marshall/recipes/<id>.pmwf` beside its recipe, every other unit to `.marshall/config/<unit>.pmwf`) (project level); none of them is `cli_only`: the web app reaches them on the runtime's own `/api/v1/` through the web listener with its device secret, with no CLI in between, so a paired device and the browser on the loopback listener read, validate, place, and remove; placing and removing are operator acts, audited with their channel. Downloading needs no endpoint: the client writes the text it holds.
16. Out of this package: a unit designed for one plan only and its promotion, and a model's help in designing (open points of the use case).

**Done when** (the package's own acceptance): The requirement and the specification of the change are merged in `plan-marshall-documentation`; a fixture unit at each level shows the precedence project copy › machine copy › compiled default in the loader and in the composition alike, only an absent unit defers, and removing a copy returns to the next level; a unit name with a separator, `..`, or an absolute path, a name the catalogue does not list as designable, and a name whose path resolves outside its target directory (through a link) are each refused with `unit_name_invalid` on the machine and the project routes, for placing and for removing, and nothing is written or deleted; ## Standing Constraints

Set by the operator for every plan of this epic on 2026-10-09, beside the rules of `CLAUDE.md`:

- **Java 25 is the baseline.** Write for Java 25 and use its language and library features where they fit; no fallback for an older release. The release comes from the parent POM and is not overridden here.
- **HTTP calls go through `cui-http`.** No direct `java.net.http` or other HTTP client. The build forbids `cui-http` in `pm-core` and `pm-workflow`, so an HTTP call belongs in `pm-runtime` or a provider module, behind an interface the foundation declares.
- **HTTP tests use `cui-test-mockwebserver-junit5`.** Every test that involves HTTP runs against it; no hand-made fake server. The operator's statement is the consent `CLAUDE.md` requires for adding it as a test-scope dependency.
- **Work the package as the index says** (`doc/plans/README.adoc` § How to Work a Package, as reworded by #19): the usual plan-marshall flow — a branch, the commits of the plan, a pull request opened at finalize. No draft pull request claims the package; before starting, list the open pull requests for one that names it. The pull request sets the package's row to `done` within its commits. Build the trace matrix of `traced-implementation` before code, deliver the remainder the roadmap item leaves, and finish with `verify`, `verify -Ppre-commit`, `verify -Pcoverage` and `verify -Pintegration-tests` green.
- **Documents.** Javadoc, `package-info.java` and the work package file live here. Requirement and specification documents, the user documentation, the deletion of implemented specification sections and watch items and the roadmap update are made directly in `plan-marshall-documentation` by this plan, in a pull request there that need not name the code pull request; merging it is the operator's.
- **Module documentation (operator decision 2026-10-11).** Documentation of the code lives in its module, in this plan's pull request, not in `plan-marshall-documentation`: the developer documentation of each package this plan changes in the developer file of each package it changes (`{module}/doc/developer/{package}.adoc`) (create or extend it: what the package is for, its main types and how they work together, how to use and extend it, invariants and failure modes, links to the specification sections it implements), and one ADR per design decision taken — every operator decision and every choice between alternatives — in `{module}/doc/adr/{package}/` as `NNN-{slug}.adoc`, the next free number of that directory, with the sections of `doc/adr/template.adoc` (Status, Date, Context, Decision, Alternatives considered, Consequences, Source) or, before that template exists, those same sections. A decision binding the whole repository goes to `doc/adr/`. The module's `README.adoc` gets one line only when this plan adds a new package; it is otherwise left alone. Layout: workstream WS-10.
- **Settled design: a refused project path is a value.** The confinement check that landed with #19 lives in `pm-core` package `core.store` (`PathConfinement`, `WorkspaceRoots`, `ConfinementOutcome`) and `pm-runtime` package `runtime.workspace` (`WorkspaceConfinement`). A refusal is returned as `ConfinementOutcome` carrying `path_traversal_rejected`; no checked exception type exists or is added. No consumer is wired to it yet (`pm-provider-git` included): a package that performs a file or repository operation for a project adopts the check itself.
- **Do not leave a design choice open that changes the file set.** Where two readings of a deliverable differ in the files they create, ask the operator at refine instead of deferring the choice to implementation.
- **One file is shared by every plan.** In `doc/plans/README.adoc` change only this package's own row.
- **Log messages: the holder of your module, next free identifier** (operator decision 2026-10-13; pm-mcp-core #64, ADR `doc/adr/005-one-log-message-holder-per-module.adoc`). A new INFO, WARN or ERROR record goes into the holder of the module whose production code logs it, at the next free identifier of its level (INFO 1-99, WARN 100-199, ERROR 200-299, the same ranges in every holder); for this plan: `WorkflowLogMessages` (`de.planmarshall.workflow.log`, prefix `PM_WORKFLOW`); `CoreLogMessages` (`de.planmarshall.core.log`, prefix `PM_CORE`). A record two modules log goes to the lower one (`pm-core`); a module logs only through its own holder and `CoreLogMessages`. There are no workstream blocks and nothing is renumbered. A provider's first record creates its holder `de.planmarshall.provider.<x>.log.<X>LogMessages` (prefix `PM_PROVIDER_<X>`) with a `package-info.java`, and adds the prefix to `KNOWN_PREFIXES` in `CoreLogMessagesTest`. After a rebase, run the holder's test, which refuses an identifier used twice or outside its level's range, and move to the next free one. The same identifiers go into `doc/LogMessages.adoc` of `plan-marshall-documentation`, under the holder's section, in the documentation pull request.

- **Format versions stay 1 (operator decision 2026-10-13).** Nothing is released yet, so every versioned artifact (`format_version` of a store document, record, sidecar, journal, codec) stays at version 1. A format change replaces version 1 in place: no version bump, no reader for an older version, no migration. Do not raise a `FORMAT_VERSION` constant, a `format_version` in a fixture, schema or specification example, or an ADR that records a bump.
