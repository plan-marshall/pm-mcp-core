## Objective

Implement the work package `process-designer` of `doc/plans/process-designer.adoc`: designing a plan's process. Serves: roadmap Milestone 11 (the process designer); Use Cases, UC-PLN-3; the process designer of the web app of `pm-mcp-clients` (the terminal client offers none). Where: pm-workflow (the machine level of workflow units and its precedence in the loader and the composition, the validation with its composition dry-run, the catalogue of building blocks); pm-core (the machine's workflow units and recipes); pm-runtime (the designer endpoints, the project-level placing as the short landing `git.land-unit`). The package file is the brief; this spec adds what the orchestrator observed and the constraints of the epic.

## Deliverables

The bullets of `doc/plans/process-designer.adoc` § What, in its words (regenerated by cleanup at 99971f3 from the package file).

1. Implements Workflow DSL § Designing a Process and the levels of § Designable Workflow Units, Levels & Compiled Invariants (items 1, 2, 4, and 5), with the short landing `git.land-unit` of State Catalogue § Short Landings and the recipes' places of Domain Extensions § A Recipe Is a Workflow (`PM-WF-22`, `PM-IMPL-5`).
2. What can be designed: the closed set of designable units: the phase sub-workflows `phase-1-init.pmwf` to `phase-6-finalize.pmwf` and `land.pmwf`, `git-commit-and-push.pmwf`, `remediation-*.pmwf`, `replan.pmwf`, `adjudicate-decisions.pmwf`, the variants of the plan behaviour axes (`landing.*`, `method.*`, `ask.*`), each held to the compiled invariants of the part of the process it takes over (`INV-AXIS-1`), and the recipes' workflows (type `recipe`). An axis's variants are a closed list: a variant is changed, never added. A compiled-only unit (the plan unit, the epic, setup, onboarding, bootstrap, source units, `chat`, …) is served read-only as a building block.
3. The levels: the compiled default, the machine's copy (`<PM_MCP_BASE>/workflows/<unit>.pmwf`, a recipe's at `<PM_MCP_BASE>/recipes/<id>.pmwf`, the operator's, never committed), and the project's copy (`.marshall/config/<unit>.pmwf`, a recipe's at `.marshall/recipes/<id>.pmwf`). This package builds the unit resolver, in the loader of `project-units-and-invariants` and in the composition of the plan instance alike: a unit resolves project copy › machine copy › compiled default, and only an absent unit defers to the next level; a unit present but invalid never falls back: a refused machine unit refuses the plan lifecycle of every project it reaches, a refused project unit that project's, naming file and line. The plan instance's header records for every unit the level it resolved at (`origin`: `default`, `machine`, or `project`), and the project's effective configuration lists its units with the level in force. A machine recipe is offered in every project on the machine, and a project's recipe of the same key takes its place there.
4. No first copy: the setup copies no default unit into `.marshall/config/`; a project holds only the units it changes, and the code where the setup unit or the loader of `project-units-and-invariants` assumed a first copy is changed accordingly. A changed machine or project unit raises `config_drift` at the next phase handshake of every plan it reaches and is adopted (event `config_adopted`) only when it verifies and still contains the plan's position.
5. The installed units (`GET /api/v1/projects/{project_id}/workflows`, `GET /api/v1/workflows`): for a project the designable units with, per level, whether a copy exists, its text and digest, and which level is in force; for the machine the machine level's units with the compiled defaults, so a machine-level unit is designed with no project chosen.
6. The catalogue of building blocks, in two scopes (`GET /api/v1/projects/{project_id}/workflows/catalogue`, `GET /api/v1/workflows/catalogue`): for a project as it resolves them (its copies over the machine's over the compiled defaults, its effective role set), for the machine the compiled and machine-level units and the machine's role set. It is complete (the primitives of `do`, `auto`, `job`, and `guard` with their parameter records and outcomes; the guards and their condition kinds; the link relations and forms; the reusable and compiled sub-workflows with their parameters, entries, and exits, the phases among them; the roles with their class; the declarable parameters with their compiled bounds; the keywords and clauses with a template each), each unit shown by the name and description of its frontmatter; it is generated from the registries the parser, the static verification, and the composition use, never from a list kept apart, and carries the runtime's version and a digest that changes after an upgrade or a placing.
7. Validation (`POST /api/v1/workflows/validate`: text, kind, name, and the target, a project or the machine): exactly as the units of that level load: the frontmatter's format, fields, and interface (their parser and rules are implemented: Workflow DSL Developer Guide § The Unit Frontmatter, Workflow Verification Developer Guide § Interface Rules and Unit Types), the parse, Rules 1–12, the compiled invariants, and a dry-run composition against the project's effective configuration, roles, skills, and providers (Rules 13 and 14), for a machine target against every enrolled project the unit would reach, each finding naming its project; with no enrolled project the dry run is reported `not_run` with the reason `no_project`. The answer lists the findings with rule or invariant, line, and column, and for a valid unit the composed process in the form of the plan's process resource. The dry run starts and stores nothing.
8. Placing and removing (`PUT` and `DELETE /api/v1/workflows/{unit}` at machine level, `PUT` and `DELETE /api/v1/projects/{project_id}/workflows/{unit}` at project level, a recipe's workflow under the recipe's key): operator acts that re-validate in the same request, at machine level against every enrolled project the unit would reach (a removal validating the unit of the next level), refused with `unit_invalid` and each failing project's findings, and with `no_project_to_compose` while no project is enrolled; carrying the digest of the unit they replace, refused with `conflict` when it changed meanwhile; refused with `unit_not_designable` for a well-formed name that the catalogue does not list as designable for that level (a compiled-only unit such as `chat`, a name outside the designable set, a variant name its axis does not list, and the key of a built-in or domain recipe); refused with `unit_invalid` when the unit fails validation, among them when its author is `plan-marshall` or its type, entries, or exits differ from those of the unit it replaces (`INV-GEN-1`).
9. Project level as a short landing: a unit placed or removed at project level is written to `.marshall/config/` (a recipe's to `.marshall/recipes/`) and landed by one commit through `git.land-unit`, by the project's landing (`landing.pull-request` or `landing.main`; with `landing.files` it stays uncommitted in the working tree); until it has landed it shows in the project's running work, and a failed landing waits for the operator (the hold `landing_failed`, `git-land-unit.failed`). A new plan takes a project unit once it has landed on the base branch, a running plan through `config_drift` at its next sync with the base; with `landing.files` no plan takes it until it is committed. A machine unit is in force from its placing.
10. Path confinement: every route that names a unit accepts only a name of the canonical unit-name grammar (the `state_id` of the Identifier Registry: no path separator, no `..`, no absolute path), and writes or deletes only after checking that the resolved path lies inside its target directory (`<PM_MCP_BASE>/workflows/`, `<PM_MCP_BASE>/recipes/`, `.marshall/config/`, `.marshall/recipes/`) after normalisation and the resolution of links; a malformed name or a path outside its directory is refused `unit_name_invalid` (`400`) before anything is read, written, or removed, and a well-formed name the catalogue does not list as designable for that level `unit_not_designable` (above), also before anything is written or removed.
11. The web listeners, no audit record: every designer endpoint is on the runtime's own `/api/v1/`, none `cli_only`, reached by the web app through the loopback or the LAN listener with its device secret, so a paired device and the loopback browser read, validate, place, and remove. Placing and removing write no audit record: the origin of a unit is its frontmatter (author, modification date, release). Downloading needs no endpoint: the client writes the text it holds.
12. Out of this package: a unit designed for one plan only and its promotion, and a model's help in designing.

## Standing Constraints

Set by the operator for every plan of this epic on 2026-10-09, beside the rules of `CLAUDE.md`:

- **Java 25 is the baseline.** Write for Java 25 and use its language and library features where they fit; no fallback for an older release. The release comes from the parent POM and is not overridden here.
- **HTTP calls go through `cui-http`.** No direct `java.net.http` or other HTTP client. The build forbids `cui-http` in `pm-core` and `pm-workflow`, so an HTTP call belongs in `pm-runtime` or a provider module, behind an interface the foundation declares.
- **HTTP tests use `cui-test-mockwebserver-junit5`.** Every test that involves HTTP runs against it; no hand-made fake server. The operator's statement is the consent `CLAUDE.md` requires for adding it as a test-scope dependency.
- **Work the package as the index says** (`doc/plans/README.adoc` § How to Work a Package, as reworded by #19): the usual plan-marshall flow — a branch, the commits of the plan, a pull request opened at finalize. No draft pull request claims the package; before starting, list the open pull requests for one that names it. The pull request removes the package's row from the index and deletes its package file within its commits, and drops the package from the _Depends on_ column of every row that names it. Build the trace matrix of `traced-implementation` before code, deliver the remainder the roadmap item leaves, and finish with `verify`, `verify -Ppre-commit`, `verify -Pcoverage` and `verify -Pintegration-tests` green.
- **Documents (operator decision 2026-10-15, pm-mcp-core ADR 007).** The specifications, the implementation watch and the traceability of the engine live in this repository: `doc/specification/`, `doc/implementation-watch/`, `doc/Traceability.adoc`, and the log message reference `doc/LogMessages.adoc`. This plan's one pull request carries the code, the tests, Javadoc and `package-info.java`, the developer documentation and ADRs, the deletion of the implemented specification sections and watch items, a correction of a specification statement it proves wrong, and the `Implementation:`, `Verified by:` and `Documentation:` lines of the requirements it implements in `doc/Traceability.adoc`. It opens a pull request in `plan-marshall-documentation` only to correct a requirement or to change `cross-cutting.adoc` or a specification that lives there; merging that one is the operator's. The concept and user documentation of the slice and the roadmap check-off are written there at the milestone exit: list them in the pull request body as **Owed to the milestone exit**.
- **Module documentation (operator decision 2026-10-11).** Documentation of the code lives in its module, in this plan's pull request, not in `plan-marshall-documentation`: the developer documentation of each package this plan changes in the developer file of each package it changes (`{module}/doc/developer/{package}.adoc`) (create or extend it: what the package is for, its main types and how they work together, how to use and extend it, invariants and failure modes, links to the specification sections it implements), and one ADR per design decision taken — every operator decision and every choice between alternatives — in `{module}/doc/adr/{package}/` as `NNN-{slug}.adoc`, the next free number of that directory, with the sections of `doc/adr/template.adoc` (Status, Date, Context, Decision, Alternatives considered, Consequences, Source) or, before that template exists, those same sections. A decision binding the whole repository goes to `doc/adr/`. The module's `README.adoc` gets one line only when this plan adds a new package; it is otherwise left alone. Layout: workstream WS-10.
- **Settled design: a refused project path is a value.** The confinement check that landed with #19 lives in `pm-core` package `core.store` (`PathConfinement`, `WorkspaceRoots`, `ConfinementOutcome`) and `pm-runtime` package `runtime.workspace` (`WorkspaceConfinement`). A refusal is returned as `ConfinementOutcome` carrying `path_traversal_rejected`; no checked exception type exists or is added. No consumer is wired to it yet (`pm-provider-git` included): a package that performs a file or repository operation for a project adopts the check itself.
- **Do not leave a design choice open that changes the file set.** Where two readings of a deliverable differ in the files they create, ask the operator at refine instead of deferring the choice to implementation.
- **Files shared by every plan.** In `doc/plans/README.adoc` remove only this package's own row (and its name from the _Depends on_ column); in `doc/Traceability.adoc` add only the sections of the requirements this package implements. Neither is a declared surface.
- **Specifications can be test input (found by PLAN-69, 2026-10-18).** A schema-parity test reads blocks of the `.adoc` specifications under `doc/specification/` (for example `WorkflowStatusSchemaParityTest` reads the JSON schema block after `== Workflow State Store` of `store-schemas/02-workflow-state-store.adoc`). Before the outline deletes or edits the implemented sections of a specification part, search the test tree for readers of that file, list each as a read file of the deliverable and state which blocks must stay byte-stable; a block a test reads is not deleted with the covered prose.
- **Checklist for `pm-workflow` code (found by PLAN-69, 2026-10-18).** (1) A refusal added for a workflow-DSL construct has exactly one owner, the parser or the verifier; every verifier refusal fixture is a tree the parser accepts, and fixture-count success criteria are written after that split. (2) A new pre-parsing layer in front of the lexer accepts at least what the lexer accepts (line endings, whitespace); add a CRLF twin fixture for every new line-oriented reader. (3) Where a printer and a reader must agree on a lexical rule, the printer calls the reader's predicate. (4) A completeness test over an enum derives the expected set from the enum at run time. (5) An exception to an invariant for one caller is scoped to that caller, with a refusing fixture from every other caller that reaches the check. (6) When a concept is generalised (start state to starting states), sweep every diagnostic message that names the old one.
- **Checklist for durable multi-step protocols in `pm-runtime` and `core.store` (found by PLAN-74, 2026-10-18; four review rounds each found another unguarded transition of the credential-store move).** (1) A resume decides from the pair (record phase, state actually recorded), never from the phase alone, and a guard added to one phase branch gets its symmetric guard on every other branch; enumerate (phase x recorded state x writer) with a test per cell before the first review. (2) While a durable in-progress record exists, every other writer of the state it switches is refused under the same lock, and an authorization is verified against durable state, never asserted by the caller. (3) The record that drives recovery is deleted last, after every side effect (audit event, clean-up after a failure) is durable. (4) A decision with side effects (which store, which key) is decided once and persisted, never re-derived per call from a probe that can flap. (5) A copy-then-switch move has a test with a pre-populated target (an overlapping key and a target-only key) and a failure injected after the copy; the pre-existing-target hazard is checked for every kind of object the protocol copies (entries, integrity key, sidecars) in the same task. (6) A store's temp-file namespace is disjoint from its legal entry-name namespace. (7) A fix of a state-machine transition lists the specification section, the ADR, the Javadoc and the test that state it among its affected files and updates them in the same commit; ADR and test are checked against the specification text, not against the code they document. (8) The invariants of a multi-write protocol are stated per crash window, not per phase. (9) A test that asserts a file location derives the expected path from the production layout independently, never from the object under test. (10) A native binding is loaded once; only what can change at runtime (a lock state) is probed per operation.
- **Facts about `pm-runtime` (found by PLAN-20, 2026-10-18).** (1) FFM downcall descriptors (`MacSecurity`, `Posix`, the `kill(2)` descriptor of `KillBinding` and `ProcessGroupSignals`) are registered in `pm-runtime/src/main/resources/META-INF/native-image/de.planmarshall/pm-runtime-credentials/reachability-metadata.json`, not in the `plan-marshall-mcp` assembly; verify a location claim with a path query, not with a Javadoc sentence. (2) `ProjectRecovery` is public and wired by the `pm-mcp-server` assembly in `plan-marshall-mcp`: a change of its factory methods needs a source-compatible overload or a named follow-up in `plan-marshall-mcp` after the SNAPSHOT deploy; the outline says which. (3) Signal numbers differ between Linux and macOS: a table of signal names for a job killed by a signal is chosen per OS, never taken from the Linux table. (4) In `pm-runtime`, suppress a Sonar rule inline at the declaration with a stated reason beside it where the design requires the flagged shape (seen: S2142, S3077, S6539, S1075), rather than reshaping the design or excluding the rule for the file.
- **Renumber the ADRs against `origin/main` before finalize and after every rebase (found by PLAN-14, 2026-10-18).** An ADR added to a module ADR directory (for example `pm-core/doc/adr/core-store/`) can take a number another plan took in the same directory; different slugs mean different file names, so git reports no conflict and the duplicate-number gate of the branch-cleanup step scans only `doc/adr`. List the touched ADR directories with `git ls-tree origin/main` and renumber the plan's ADRs to the next free numbers; PLAN-14 renumbered twice.
- **Log messages: the holder of your module, next free identifier** (operator decision 2026-10-13; pm-mcp-core #64, ADR `doc/adr/005-one-log-message-holder-per-module.adoc`). A new INFO, WARN or ERROR record goes into the holder of the module whose production code logs it, at the next free identifier of its level (INFO 1-99, WARN 100-199, ERROR 200-299, the same ranges in every holder); for this plan: `WorkflowLogMessages` (`de.planmarshall.workflow.log`, prefix `PM_WORKFLOW`); `CoreLogMessages` (`de.planmarshall.core.log`, prefix `PM_CORE`). A record two modules log goes to the lower one (`pm-core`); a module logs only through its own holder and `CoreLogMessages`. There are no workstream blocks and nothing is renumbered. A provider's first record creates its holder `de.planmarshall.provider.<x>.log.<X>LogMessages` (prefix `PM_PROVIDER_<X>`) with a `package-info.java`, and adds the prefix to `KNOWN_PREFIXES` in `CoreLogMessagesTest`. After a rebase, run the holder's test, which refuses an identifier used twice or outside its level's range, and move to the next free one. The same identifiers go into `doc/LogMessages.adoc` of this repository, under the holder's section.

- **Format versions stay 1 (operator decision 2026-10-13).** Nothing is released yet, so every versioned artifact (`format_version` of a store document, record, sidecar, journal, codec) stays at version 1. A format change replaces version 1 in place: no version bump, no reader for an older version, no migration. Do not raise a `FORMAT_VERSION` constant, a `format_version` in a fixture, schema or specification example, or an ADR that records a bump.
