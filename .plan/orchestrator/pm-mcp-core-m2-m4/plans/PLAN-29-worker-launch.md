1. The job kind `llm`: the launch composed from the role's effective `harness`, `model`, and `effort` (`role-sets-and-model-caller`) and the client profile, a model tier rendered into the model `headless.model_tiers` maps it to; the job-private directory, the MCP configuration delivered as the profile says; `harness_version` in the job record, the version in force at the spawn, probed again where the executable's digest changed.
2. The job token: minted at spawn, only its hash in the job record, revoked with the job's fate; the registry over the job records. A worker's identity in the audit rows is its `job_id`, role, and generation; the delivery record and skill delivery are per worker generation.
3. The harness enrolment store and the confinement exceptions of `llm` jobs: the `client_id` an open pattern of the effective profile set; the required `usage_report` and the `events` stage results kept with the entry (their values are `token-usage`'s and `worker-activity`'s); one store API for `pm-operator enrol-harness` and the onboarding's `harness.enrol`. Launch refusals carry their reason and name the act that resolves it in both clients.
4. The ephemeral flag withheld, the session stored, and the job-private directory kept for a role that may resume after a question, and the launch of a resumed generation with `headless.resumability.resume.argv`, are `question-continuation`'s; this package composes the launch they parameterise.
5. The launch prompt's shared prefix and the launch refusals: the writing skill `skill://pm/writing/SKILL.md` is required for every task whose links carry free text, derived by the server from the link schemas (a parameter of type `text`, or a named parameter schema with a `string` field that has neither `enum` nor `pattern`) when the offer or the launch is composed, never from the role artifact; the shim paragraph, the core conduct skill, the task-protocol skill and the role skill with its further skills are rendered byte-identically for every launch of a role on the same skill digests and client profile and come first, with nothing that varies per launch before or between them, so a harness's prompt cache can serve the shared part. The class's launch loads the project's instruction files and skill directories and no plugin, hook, MCP server, endpoint or environment value from any settings file of the project, the checkout or the user (the capability `extension_isolation`). The harness is an enrolled host tool (`harness.enrol`, `pm-operator enrol-harness`), and before every launch the runtime re-digests the executable; a changed digest is accepted only on the profile's `update_evidence` and then only when the version probe reports a version inside `headless.supported_versions`, audited `harness_updated` with the new version and digest written to `harnesses.json`, and every other case refuses the launch before spawn with `harness_not_enrolled`, `harness_update_unverified` or `harness_version_unsupported` in the job record's `refusal_reason` (Model Work § Launch Prompt & Contract Envelope; § Skill Delivery Record & Re-Delivery; § Working Directory, Project Files & Zero-Tool Isolation; § Harness Eligibility & Launch Refusals; Store Schemas § Harness Enrolment Store; § Job Record).

**Done when** (the package's own acceptance): A launch-vector test per role class against a fixture profile; a tampered harness enrolment refuses the launch; a `zero_tool` launch has no tool, no MCP entry and no loaded setting; a launch under a role assignment or plan override uses the effective values, a tier rendered to the profile's model; the job record carries `harness_version`, probed again after a digest change; a harness the operator added from a verified profile is enrolled and launched like a shipped one. A task whose links carry free text is launched with the writing skill derived from the link schemas and one whose links do not is not; two launches of one role for two tasks agree byte for byte up to the end of the role skill; a worker loads the project's instruction files and skill directories and no plugin, hook, MCP server, endpoint or environment value from any settings file; a `string` field with an `enum` or a `pattern` does not trigger it either; a role artifact that names the writing skill does not add it to a task whose links carry no free text; before every launch the executable is re-digested; a launch of a changed executable without passed update evidence is refused `harness_update_unverified`, one outside the supported range `harness_version_unsupported`, one of an unenrolled harness `harness_not_enrolled`, each recorded in the job record's `refusal_reason`, and an accepted self-update rewrites `harnesses.json` with the new version and digest and is audited `harness_updated`. **Sonar:** the SonarCloud search of the pull request (`pullRequest=<N>&resolved=false`) lists no open issue other than one dismissed with its reason, and its quality gate is green, before the pull request is reported ready.

## Carried From PLAN-84: Termination Step 3a For A Worker

Decided by the operator on 2026-10-22 (the analysis of PLAN-84, #135 `0bf64f7`): this package owns the worker half of termination step 3a of `doc/specification/job-runtime/01-pipeline-and-subprocesses.adoc` (§ Process Termination & Cancellation Protocol, step 3a). The package file does not name it; this plan carries it. #135 built it for a probe only: `ProcessTreeTracker` records a probe's descendants with their start instants, refreshes them while the job runs, sweeps them at its end and audits a survivor as `job_descendant_survived` (ADR `pm-runtime/doc/adr/runtime-job/013-record-and-sweep-descendants.adoc`, `PM_RUNTIME-137` and `-138`).

- **Deliver:** a job of the kind `llm` gets the same recording, sweep and audit as a probe, with a test that a descendant of a fixture worker that leaves the group is ended with the job and a survivor is audited. Read first: `SubprocessJobRunner` (the kind condition at the start of the supervision, and the Javadoc sentence "a worker's descendants are the supervisor's, which starts the worker"), `ProcessTreeTracker`, `TerminationProtocol.terminate(long pid, boolean leaderMayLive)` and ADRs `runtime-job/010` to `013`. ADR 013 and that Javadoc say the supervisor wires the tracker for a worker, because the supervisor starts it; the runner starts every job it is given, so the wiring is one condition in the runner for the kind `llm`, and this package decides it at the trace matrix, records the decision in an ADR, and tells `supervisor` (PLAN-30) in the pull request body if the wiring has to sit in its start path instead.
- **Not here:** the Linux child-subreaper of the launcher (`PR_SET_CHILD_SUBREAPER` in `pm-exec`, a binary of `pm-mcp-clients`): a package there is owed (Open Defects of the epic); this package launches through the launcher as the specification describes and works with a launcher that stays as the job's process. The sentence "and the runtime status shows it" has no runtime-status surface in this repository; the trace matrix names where a survivor is shown (the audit record is the only place today) and reports it if none exists.
