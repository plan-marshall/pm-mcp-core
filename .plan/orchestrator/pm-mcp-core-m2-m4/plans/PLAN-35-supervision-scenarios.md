## Deliverables

The bullets of `doc/plans/supervision-scenarios.adoc` § What, in its words (regenerated by cleanup at 99971f3 from the package file).

1. `pm-scenario` scenarios of the worker faults, recycling, the start-failure guard, consultation, fencing, and a runtime crash with a leased task.
2. A worker off track, from a scripted output stream of the fixture harness: one scenario per signal (`repeating`, `no_progress`, `over_size`, `outside_footprint`), raised at its threshold and never before, and per action (`show`, `nudge`, `yield`, `restart`), taken and recorded with its signal without ending the plan or waiting for the operator (`worker-activity`).
3. A pause at once of a plan with a leased task, and the missing answer acknowledgement of a continuing worker (`question-continuation`).
4. Operator acts at operator waits are given by the scenario script; where `scenario-replay-harness` has no directive for one, the trace matrix names it and this package adds it.
5. The same faults against real processes are `plan-marshall-mcp` / `worker-integration-tests`.
6. The behavioural conformance harness: the scenarios of `pm-conformance` (`PM-TEST-6`) run against a live model as a worker of a role on a fixture repository, and this package builds their runs and baselines on top of the shipped `scenario-replay-harness`: _Control First_ (a rule enters model-facing content, or is changed there, only with a scenario whose run against the version without the rule or the change scores `violated` in the same harness run; when that control holds, the rule is not added, because nothing shows it is needed, and the run report records both verdicts of the pair), _Combined Pressure_ (a scenario for a rule that is broken under pressure combines at least three pressures in its `pressure`: time, sunk cost, authority, exhaustion, or the plan's own instruction to violate it), and _Read Matches_ (before the first baseline of a new scenario is accepted, a person reads every sample its observation predicate matched and every sample it did not, and records the result with the baseline; a predicate that matched wrongly is corrected first). Every scenario declares its `rule_ref`, `situation`, `pressure`, `observation`, `binding_context`, `enforcement_class`, `tolerance_band`, `population` and `negative_control`, and a `violated` or `indeterminate` verdict is resolved by a recorded operator decision, never by the harness (Workflow DSL § Behavioural Conformance Harness).
7. The comparison footprint: a run that compares two versions of model-facing content or of a role configuration runs both versions over the same tasks, several times each, and reports per version, beside the verdicts, the tokens and the revisits of every run (the navigation figures of Model Work § Navigation Figures) with their spread, split into focused tasks and tasks that span several modules; a difference is reported `measured` only when the runs of both versions were drawn from the same tasks at random within the one run, and `estimated` otherwise; a single run per version is never a comparison, because runs of the same task with the same version differ by more than twice in tokens (Workflow DSL § Comparison Footprint).

**Done when** (the package's own acceptance): One scenario per fault of the fault matrix and per off-track signal and action, each replayed twice to the same stores; no scenario relies on a session or a session generation. A rule that enters model-facing content has a control scenario that scores `violated` against the version without it, both verdicts in the run report; a pressure scenario combines at least three pressures; a new baseline records the reading of every matched and unmatched sample, and a predicate that matched wrongly is corrected before the baseline is accepted; a comparison of two versions reports tokens and revisits per run with their spread over several runs of the same tasks each, split into focused tasks and tasks that span several modules, `measured` only for a randomised same-run draw and `estimated` otherwise, and never from a single run per version; every scenario declares the nine fields of the scenario record, a rule's pair of verdicts is recorded and the rule is not added when that control holds, and a `violated` or `indeterminate` verdict is resolved by a recorded operator decision, never by the harness. **Sonar:** the SonarCloud search of the pull request (`pullRequest=<N>&resolved=false`) lists no open issue other than one dismissed with its reason, and its quality gate is green, before the pull request is reported ready. **Build:** `verify -Ppre-commit` (its rewrites reviewed and committed), then `verify` of every module the plan changes (`pm-workflow`, and `pm-runtime` where D1/D3 reach it; where a full run does not finish inside the host's bound, the targeted `-Dtest` runs of the changed classes and the per-module run, each reported in the pull request body), `verify -Pcoverage` and the integration tests of every changed module with tests (`verify -Pintegration-tests -pl <module> -am`, only on `pm-core` and `pm-runtime`) are green. **Links:** run the links check (R17) from the main checkout against the documentation checkout at its `origin/main` (`git -C ../plan-marshall-documentation fetch origin main`, then `trace.py` over a checkout of that revision, or fast-forward the sibling first): a `BROKEN LINKS` count that names an item deleted in the sibling is the sibling's own links, not a defect of this change.
