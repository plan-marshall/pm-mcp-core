## Deliverables

The bullets of `doc/plans/supervision-scenarios.adoc` § What, in its words (regenerated by cleanup at 99971f3 from the package file).

1. `pm-scenario` scenarios of the worker faults, recycling, the start-failure guard, consultation, fencing, and a runtime crash with a leased task.
2. A worker off track, from a scripted output stream of the fixture harness: one scenario per signal (`repeating`, `no_progress`, `over_size`, `outside_footprint`), raised at its threshold and never before, and per action (`show`, `nudge`, `yield`, `restart`), taken and recorded with its signal without ending the plan or waiting for the operator (`worker-activity`).
3. A pause at once of a plan with a leased task, and the missing answer acknowledgement of a continuing worker (`question-continuation`).
4. Operator acts at operator waits are given by the scenario script; where `scenario-replay-harness` has no directive for one, the trace matrix names it and this package adds it.
5. The same faults against real processes are `plan-marshall-mcp` / `worker-integration-tests`.
6. The behavioural conformance harness: the scenarios of `pm-conformance` (`PM-TEST-6`) run against a live model as a worker of a role on a fixture repository, and this package builds their runs and baselines on top of the shipped `scenario-replay-harness`: _Control First_ (a rule enters model-facing content, or is changed there, only with a scenario whose run against the version without the rule or the change scores `violated` in the same harness run; when that control holds, the rule is not added, because nothing shows it is needed, and the run report records both verdicts of the pair), _Combined Pressure_ (a scenario for a rule that is broken under pressure combines at least three pressures in its `pressure`: time, sunk cost, authority, exhaustion, or the plan's own instruction to violate it), and _Read Matches_ (before the first baseline of a new scenario is accepted, a person reads every sample its observation predicate matched and every sample it did not, and records the result with the baseline; a predicate that matched wrongly is corrected first). Every scenario declares its `rule_ref`, `situation`, `pressure`, `observation`, `binding_context`, `enforcement_class`, `tolerance_band`, `population` and `negative_control`, and a `violated` or `indeterminate` verdict is resolved by a recorded operator decision, never by the harness (Workflow DSL § Behavioural Conformance Harness).
7. The comparison footprint: a run that compares two versions of model-facing content or of a role configuration runs both versions over the same tasks, several times each, and reports per version, beside the verdicts, the tokens and the revisits of every run (the navigation figures of Model Work § Navigation Figures) with their spread, split into focused tasks and tasks that span several modules; a difference is reported `measured` only when the runs of both versions were drawn from the same tasks at random within the one run, and `estimated` otherwise; a single run per version is never a comparison, because runs of the same task with the same version differ by more than twice in tokens (Workflow DSL § Comparison Footprint).

**Done when** (the package's own acceptance): One scenario per fault of the fault matrix and per off-track signal and action, each replayed twice to the same stores; no scenario relies on a session or a session generation. A rule that enters model-facing content has a control scenario that scores `violated` against the version without it, both verdicts in the run report; a pressure scenario combines at least three pressures; a new baseline records the reading of every matched and unmatched sample, and a predicate that matched wrongly is corrected before the baseline is accepted; a comparison of two versions reports tokens and revisits per run with their spread over several runs of the same tasks each, split into focused tasks and tasks that span several modules, `measured` only for a randomised same-run draw and `estimated` otherwise, and never from a single run per version; every scenario declares the nine fields of the scenario record, a rule's pair of verdicts is recorded and the rule is not added when that control holds, and a `violated` or `indeterminate` verdict is resolved by a recorded operator decision, never by the harness.

## Standing Constraints

Set by the operator for every plan of this epic on 2026-10-09, beside the rules of `CLAUDE.md`:

- **Java 25 is the baseline.** Write for Java 25 and use its language and library features where they fit; no fallback for an older release. The release comes from the parent POM and is not overridden here.
- **HTTP calls go through `cui-http`.** No direct `java.net.http` or other HTTP client. The build forbids `cui-http` in `pm-core` and `pm-workflow`, so an HTTP call belongs in `pm-runtime` or a provider module, behind an interface the foundation declares.
- **HTTP tests use `cui-test-mockwebserver-junit5`.** Every test that involves HTTP runs against it; no hand-made fake server. The operator's statement is the consent `CLAUDE.md` requires for adding it as a test-scope dependency.
- **Work the package as the index says** (`doc/plans/README.adoc` § How to Work a Package, as reworded by #19): the usual plan-marshall flow — a branch, the commits of the plan, a pull request opened at finalize. No draft pull request claims the package; before starting, list the open pull requests for one that names it. Build the trace matrix of `traced-implementation` before code, deliver the remainder the roadmap item leaves, and finish with `verify`, `verify -Ppre-commit`, `verify -Pcoverage` and `verify -Pintegration-tests` green.
- **Documents (operator decision 2026-10-15, pm-mcp-core ADR 007).** The specifications, the implementation watch and the traceability of the engine live in this repository: `doc/specification/`, `doc/implementation-watch/`, `doc/Traceability.adoc`, and the log message reference `doc/LogMessages.adoc`. - **Module documentation (operator decision 2026-10-11).** Documentation of the code lives in its module, in this plan's pull request, not in `plan-marshall-documentation`: the developer documentation of each package this plan changes in `pm-workflow/doc/developer/workflow-scenario.adoc` (create or extend it: what the package is for, its main types and how they work together, how to use and extend it, invariants and failure modes, links to the specification sections it implements), and one ADR per design decision taken — every operator decision and every choice between alternatives — in `pm-workflow/doc/adr/workflow-scenario/` as `NNN-{slug}.adoc`, the next free number of that directory, with the sections of `doc/adr/template.adoc` (Status, Date, Context, Decision, Alternatives considered, Consequences, Source) or, before that template exists, those same sections.
