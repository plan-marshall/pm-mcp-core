## Objective

Implement the work package `start-from-clients` of `doc/plans/start-from-clients.adoc`: starting work from the clients, and the source directory. Serves: roadmap Milestone 7 (the plan bootstrap with the sources `description`, `issue`, and `lesson`), Milestone 10 (the sources `local_changes`, `pr`, and `documents`), Milestone 12 (the epic bootstrap); Use Cases, UC-STA-1 to UC-STA-4, UC-STA-7 to UC-STA-9; starting work in both clients of `pm-mcp-clients`. Where: pm-workflow (the bootstrap and source units, the end of the session-driven units, the static verifier); pm-core (the pending entry, the source directory and its manifest, `origin`, the epic header's sources); pm-runtime (the entry endpoints, the listing of files). The package file is the brief; this spec adds what the orchestrator observed and the constraints of the epic.

**Parked:** the index gives the package the status `open` (at a8a4214), but it waits on packages that are not done: `operator-wait-and-machine-scope`, `machine-onboarding-unit`, `project-onboarding-unit`, `removed-concepts`. Re-ground this spec before emitting it.

The bullets of `doc/plans/start-from-clients.adoc` § What, in its words (regenerated by cleanup at a8a4214).

1. Implements Workflow DSL § All Interaction in the Operator's Clients; State Catalogue § Starting from the Clients with the bootstraps `bootstrap-plan` and `bootstrap-epic`, the Source Units, Documents as a Source, Issues by Number or URL, and Asked When Needed; Filesystem Layout § The Source Directory; Store Schemas § Pending Entry; Model Work § What Is on This Machine Is Trusted and § Screened Once Stored; Store Schemas § A Claimed Lesson Ends with the Landing; the entry's address in Runtime Model § Events per Scope (`PM-WF-10`, `PM-ARCH-11`, `PM-SEC-1`).
2. The operator's clients only: the bootstraps of a plan and an epic run as units of operator waits that the clients drive; the session-driven units, the entry session, and the channel `session` of answers go from the code (`OutcomeClass`, the static verifier's rules for session units and their fixtures), the channels of an answer being `web`, `cli`, and `quorum`.
3. The setup gate: `start.open`, `start-epic.open`, and the re-check of `start.create-scope` call the machine-onboarding guard of `operator-wait-and-machine-scope` first, so no plan or epic starts while the machine's first onboarding has not reached `onboard.completed` (`machine_not_onboarded`, naming the terminal client and the web app), beside the rest of the setup gate of `start.open`.
4. Sources as a list: `start.sources` and `start-epic.sources`, offering only the kinds that combine with those already listed (a pull request or the local changes only with descriptions and documents, never both); the description stored by the main workflow; the source units `source-documents`, `source-issue` (number or URL, always stored as its URL, the structured fields; another repository on the operator's grant, whose _no_ goes to `source-issue.failed`; without a credential for the forge a public issue is read and another fails naming the credential), and the existing ones of lesson, local changes, pull request, and epic row, each writing into the source directory.
5. Rate limits: a fetch of an issue or a pull request that the forge refuses for its rate limit, with or without a credential, fails the source with the cause `rate_limited` and `resets_at` from the forge's answer; it is not retried by itself, and the operator tries again or adds a credential for the forge.
6. Documents, copy or move: the machine key `sources.documents_mode` (`copy`, `move`, or `ask`, the default); with `ask` the operator wait `source-documents.mode` with _copy_ preselected, where _always_ stores `copy` or `move` as the machine's value; otherwise straight to `source-documents.store`. A move removes a file git tracks from git through the short landing `git.land-removal`, landed by the project's landing (`landing.pull-request` or `landing.main`); with `landing.files` the removal stays uncommitted in the working tree.
7. An entry never expires: a pending entry has no time limit (Timeouts § Pending Entry); it stays among the project's open entries, offered to continue in both clients, until it is started or abandoned, or deleted with the release of its project. The pending entry record's maximum age in the code (24 hours, `PENDING_ENTRY_MAX_AGE` of `PeriodicSweep`) and the sweep step `PendingEntryRecordsSweep` that removes older records go; the sweep removes only the directory of an entry already started or abandoned whose removal a stop cut off, by that evidence (Runtime Model § Periodic Sweep).
8. The source directory: created with the entry, moved into the plan or the epic's machine store at creation; the manifest; `origin` naming the sources; the epic header listing them; `request.md` composed from them; `epic.decompose` reading them.
9. Screened once stored: fetch, level-1 validator, store, screener over the stored copy, the verdict in the manifest; nothing but the screener reads an external source before a clean verdict or the operator's acceptance; the operator's text and the documents on the machine are never screened.
10. Fail closed: a screener that fails, or a role `screener` with no qualified configuration, leaves the source unscreened with the cause in the operator wait `source-<kind>.unscreened` (`source-issue.unscreened`, `source-pr.unscreened`): try again, remove it, or accept it explicitly as untrusted, recorded with its reason like an accepted flagged source; a failure is never shown as `suspicious`.
11. The other sources (UC-STA-7 to UC-STA-9): pull request, lesson, and local changes as sub-workflows storing into the source directory; an issue's and a pull request's URL stored. A pull request's changed files are stored as its head and marked untrusted unless the operator authored it, never read by a model as instructions, the plan's own gates applying to them; its title and body screened as an issue's. A lesson: `source-lesson.resolve` with the premise check; a lesson claimed meanwhile, retired, or in a damaged store back to `source-lesson.choose` with the cause; a premise that no longer holds to the operator wait `source-lesson.premise` with the evidence, where _use it anyway_ stores the lesson with the evidence for the plan, _retire_ retires it in the lesson store, and _remove_ leaves it as it is, both adding nothing. The local changes: `source-local-changes.confirm` with _not now_ back to `start.sources`, a checkout without changes failing the source with that cause; the plan takes the land lane and lands them by the project's landing.
12. The start's end: the landing is not asked at the start; while the project's landing in force is `landing.files`, `start.sources` does not offer the local changes and shows the reason naming the project's setting `landing` (the landing variants are `machine-onboarding-unit`'s); `start.create` re-checks what creation needs (`landing.files` refused for a plan from local changes) and returns to `start.ready` with the cause where something changed meanwhile.
13. A claimed lesson ends with the landing: the lesson of a source is claimed at the plan's creation and retired when the plan lands its changes (the merge of `landing.pull-request`, the push of `landing.main`; verdict `applied`, `by` the plan), released when it ends without landing them (handed back with `landing.files`, cancelled, abandoned, released, aborted, deleted), the lesson staying `active`.
14. An epic's sources in its ledger (`.marshall/epics/<epic_id>/sources/`, committed and landed), so that adoption and every decomposition read them.
15. Chat while starting: `start.sources` and `start-epic.sources` leave room for the choice Chat that `chat` adds on top of this package, and the source directory keeps its transcript (moved at the creation, deleted with an abandoned entry, never a source the plan reads); the chat itself and its one change, the description through `start.store-description`, are that package's.
16. Entries addressed like plans and epics: created under their project (`POST /api/v1/projects/{project_id}/entries`, the kind `plan` or `epic`), addressed at the top level by id (`/api/v1/entries/{entry_id}`, its events at `/api/v1/entries/{entry_id}/events`); `POST /api/v1/entries` goes.
17. Loopback only: the listing of files, a move, and documents outside the checkout only from the terminal client and the loopback listener.
18. Asked when needed: posture and base branch leave the start: where neither the plan's own settings, the project (`plan_defaults.posture`), nor the machine sets them, `init.classify` asks both in the one operator wait `init.options`; whether the outline is reviewed is the plan's asking variant's (`outline_review`). `parallelization_scope` becomes the project key `epic.parallelization_scope` (machine default 1), which a new epic takes and which is never asked; it is raised through _Next plan_ (`plan-and-epic-control`) or the project's settings.
19. Where `entity-addressing`, `plan-instance`, or `project-units-and-invariants` have already implemented the session-driven bootstrap, this package restructures them.

**Done when** (the package's own acceptance): No unit is driven by a session, and no answer has the channel `session`; a test per source kind stores it in the source directory with its manifest entry; a plan and an epic start from several sources and keep them after creation; no model but the screener reads an external source before its verdict, shown by a test that fails the screening and one whose screener fails or has no qualified configuration, leaving the source unscreened until tried again, removed, or accepted as untrusted; a pull request's changed files are never read as instructions; a rate-limited fetch of an issue and of a pull request fails with `rate_limited` and `resets_at` and is not retried; a pending entry older than a day is still offered and no sweep removes it, while the directory of an entry already started or abandoned whose removal a stop cut off is removed by the sweep; a start of a plan and of an epic is refused `machine_not_onboarded` while the machine's onboarding is not complete; each branch of a lesson, unavailable and a premise that no longer holds, ends as specified; posture and base branch are asked in `init.options` only where no level sets them, and `parallelization_scope` never; `start.sources` does not offer the local changes while the project's landing is `landing.files`, with the reason, and `start.create` refuses `landing.files` for a plan from local changes; documents are asked copy or move only with `ask`; a claimed lesson is retired on a merge and on a push to the base branch and released on every other end.

## Standing Constraints

Set by the operator for every plan of this epic on 2026-10-09, beside the rules of `CLAUDE.md`:

- **Java 25 is the baseline.** Write for Java 25 and use its language and library features where they fit; no fallback for an older release. The release comes from the parent POM and is not overridden here.
- **HTTP calls go through `cui-http`.** No direct `java.net.http` or other HTTP client. The build forbids `cui-http` in `pm-core` and `pm-workflow`, so an HTTP call belongs in `pm-runtime` or a provider module, behind an interface the foundation declares.
- **HTTP tests use `cui-test-mockwebserver-junit5`.** Every test that involves HTTP runs against it; no hand-made fake server. The operator's statement is the consent `CLAUDE.md` requires for adding it as a test-scope dependency.
- **Work the package as the index says** (`doc/plans/README.adoc` § How to Work a Package, as reworded by #19): the usual plan-marshall flow — a branch, the commits of the plan, a pull request opened at finalize. No draft pull request claims the package; before starting, list the open pull requests for one that names it. The pull request sets the package's row to `done` within its commits. Build the trace matrix of `traced-implementation` before code, deliver the remainder the roadmap item leaves, and finish with `verify`, `verify -Ppre-commit`, `verify -Pcoverage` and `verify -Pintegration-tests` green.
- **Documents.** Javadoc, `package-info.java` and the work package file live here. Requirement and specification documents, the user documentation, the deletion of implemented specification sections and watch items and the roadmap update are made directly in `plan-marshall-documentation` by this plan, in a pull request there that need not name the code pull request; merging it is the operator's.
- **Module documentation (operator decision 2026-10-11).** Documentation of the code lives in its module, in this plan's pull request, not in `plan-marshall-documentation`: the developer documentation of each package this plan changes in the developer file of each package it changes (`{module}/doc/developer/{package}.adoc`) (create or extend it: what the package is for, its main types and how they work together, how to use and extend it, invariants and failure modes, links to the specification sections it implements), and one ADR per design decision taken — every operator decision and every choice between alternatives — in `{module}/doc/adr/{package}/` as `NNN-{slug}.adoc`, the next free number of that directory, with the sections of `doc/adr/template.adoc` (Status, Date, Context, Decision, Alternatives considered, Consequences, Source) or, before that template exists, those same sections. A decision binding the whole repository goes to `doc/adr/`. The module's `README.adoc` gets one line only when this plan adds a new package; it is otherwise left alone. Layout: workstream WS-10.
- **Settled design: a refused project path is a value.** The confinement check that landed with #19 lives in `pm-core` package `core.store` (`PathConfinement`, `WorkspaceRoots`, `ConfinementOutcome`) and `pm-runtime` package `runtime.workspace` (`WorkspaceConfinement`). A refusal is returned as `ConfinementOutcome` carrying `path_traversal_rejected`; no checked exception type exists or is added. No consumer is wired to it yet (`pm-provider-git` included): a package that performs a file or repository operation for a project adopts the check itself.
- **Do not leave a design choice open that changes the file set.** Where two readings of a deliverable differ in the files they create, ask the operator at refine instead of deferring the choice to implementation.
- **One file is shared by every plan.** In `doc/plans/README.adoc` change only this package's own row.
- **Log messages: the holder of your module, next free identifier** (operator decision 2026-10-13; pm-mcp-core #64, ADR `doc/adr/005-one-log-message-holder-per-module.adoc`). A new INFO, WARN or ERROR record goes into the holder of the module whose production code logs it, at the next free identifier of its level (INFO 1-99, WARN 100-199, ERROR 200-299, the same ranges in every holder); for this plan: `WorkflowLogMessages` (`de.planmarshall.workflow.log`, prefix `PM_WORKFLOW`); `CoreLogMessages` (`de.planmarshall.core.log`, prefix `PM_CORE`). A record two modules log goes to the lower one (`pm-core`); a module logs only through its own holder and `CoreLogMessages`. There are no workstream blocks and nothing is renumbered. A provider's first record creates its holder `de.planmarshall.provider.<x>.log.<X>LogMessages` (prefix `PM_PROVIDER_<X>`) with a `package-info.java`, and adds the prefix to `KNOWN_PREFIXES` in `CoreLogMessagesTest`. After a rebase, run the holder's test, which refuses an identifier used twice or outside its level's range, and move to the next free one. The same identifiers go into `doc/LogMessages.adoc` of `plan-marshall-documentation`, under the holder's section, in the documentation pull request.

- **Format versions stay 1 (operator decision 2026-10-13).** Nothing is released yet, so every versioned artifact (`format_version` of a store document, record, sidecar, journal, codec) stays at version 1. A format change replaces version 1 in place: no version bump, no reader for an older version, no migration. Do not raise a `FORMAT_VERSION` constant, a `format_version` in a fixture, schema or specification example, or an ADR that records a bump.
