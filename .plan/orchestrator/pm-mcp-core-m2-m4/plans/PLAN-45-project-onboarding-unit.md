## Objective

Implement the work package `project-onboarding-unit` of `doc/plans/project-onboarding-unit.adoc`: the project onboarding unit. Serves: roadmap Milestone 7 (the onboarding of a project as one process); Use Cases, UC-PRJ-1, UC-PRJ-2 (UC-PRJ-3, the release, is `plan-and-epic-control`'s); the onboarding of a project in both clients of `pm-mcp-clients`. Where: pm-workflow (the unit in its own scope per project, the setup's choices as operator waits); pm-core (detection, enrolment writes, the project's values over the machine's); pm-runtime (the projects of the machine: favourites, recent, most used). The package file is the brief; this spec adds what the orchestrator observed and the constraints of the epic.

**Parked:** the index gives the package the status `open` (at a8a4214), but it waits on packages that are not done: `operator-wait-and-machine-scope`, `machine-onboarding-unit`. Re-ground this spec before emitting it.

## Deliverables

The bullets of `doc/plans/project-onboarding-unit.adoc` § What, in its words (regenerated by cleanup at a8a4214).

1. Implements CLI & Security § Onboarding a Project as One Process, State Catalogue § Project Onboarding, § Project Setup, Store Schemas § Project Values over Machine Values, and Runtime Model § The Projects of the Machine with its store Store Schemas § The Operator's Projects (`PM-EXT-8`, `PM-SEC-8`).
2. The gate: the start of a project's onboarding calls the machine-onboarding guard of `operator-wait-and-machine-scope` first and is refused while the machine's first onboarding has not reached `onboard.completed` (`machine_not_onboarded` in the setup gate, `onboarding_incomplete` (`409`) over the local API, naming the missing step and both clients).
3. The unit: `project.checkout` to `project.enrol` in a scope of its own per project being onboarded (several at once, the machine scope untouched), then the project setup; detection after the consent kind `inspect_checkout` (it reads the checkout and runs the host tools' version probes, and changes nothing): the remote, base branch, build wrappers, host tools, language servers, and scripts with a check line each; the id proposed from the remote; the enrolment written as `pm-operator enrol` writes it.
4. The checkout's scripts: `project.run-consent` (consent kind `run_checkout_scripts`) answered `yes`, `yes_remember` (for this project), or `no`; a remembered yes kept in the machine's `consents.json` keyed by the project and each script's digest (the store of `machine-onboarding-unit`), never in the enrolment: the entry lists every script it covers with its digest, and `project.run-consent` computes the digest of each script it would run from the checkout and is passed without a question only when every one is listed for this project with that digest, so a script not listed, a changed script, or an entry of another project asks again, and a `yes_remember` replaces the list; a `yes_remember` given before the project has its id is held with the onboarding's entry and written under the confirmed `project_id` in the transaction of `project.enrol`, an onboarding that does not reach its enrolment remembering nothing; the scripts run confined like a job, never without one of the two yes links; _no_ goes on to `project.identity` with what needs the scripts unknown, not asked again in that run.
5. The setup in the specification's order, its choices operator waits served to both clients, no session driving it: `project.setup` calls the setup (`first_run`): `setup.entry`, `setup.prepare-workspace`, `setup.check-operator-files`, which ends with its exit `operator_values`; `project.operator`; the setup called again at its entry that starts at `setup.probe-integration-variants` and `setup.verify-credentials` (an invalid variant back to `project.operator` with its findings); `setup.project-settings` (base branch, branch prefix, lanes); `setup.detect-domains`; `setup.discover-modules`; `setup.seed-build-map` (derived from the modules); `setup.select-providers` (the team's: the CI provider from the remote or overridden, code analysis, review bots); `setup.configure-finalize` (the finalize steps and the project's landing variant, one of the variants `machine-onboarding-unit` defines, validated against the project there, a machine default that does not fit refused with the reason); `setup.probe-merge-queue` with `setup.merge-queue` where one could be enforced; `setup.qualify-consent` and `setup.qualify-roles`; `setup.enrich-consent` and `setup.enrich-architecture`; `setup.commit-changes` (commit, or leave to commit) and `setup.land-changes`; `project.completed`. A step that cannot pass waits in `setup.needs-repair`, whose retry runs it again.
6. Consents of model use: `setup.qualify-consent` and `setup.enrich-consent` (consent kind `model_cost`), their expected use shown in tokens, never as money (`token-usage`), asked only where roles need grading or modules a description; _no_ skips the step with its reason, to be run later, and the setup goes on (the project ready without descriptions).
7. The project's values over the machine's: `project.operator` shows the operator's values only (the model language, the allowed models, the role assignment, the method and asking axes, the integration variant and credential of each provider, the commit identity), each proposed from the machine and recorded for the project only when changed; the team's values (the landing axis, the providers' declaration) stay in the setup and `.marshall/config/`; `project_defaults` as the machine's value of the project's operator keys, one rule for all. A change of an operator value carries the revision it was made against and is refused with `conflict` and the current value when another change came first (the rule of `machine-onboarding-unit`, CLI & Security § Concurrent Changes of a Setting).
8. The projects of the machine: favourites and their order in the machine store `explorer.json`, recent and most used from the operator's acts in a project.

**Done when** (the package's own acceptance): A test onboards a fixture checkout from `project.checkout` to a ready project without a session, and one shows its start refused while the machine's onboarding is not complete; a test shows a refused consent leaving the checkout unread, a refused script consent going on without the scripts and not asked again in the run, and a remembered one kept in `consents.json` only and written at `project.enrol`, none remembered by an onboarding that does not reach it; a remembered script consent passes the state only for the same project and the same digests, a changed script, an added script, and the entry of another project each asked again; a test walks the setup's states in their order, refuses a landing variant that does not fit the project at `setup.configure-finalize`, and skips the qualification and the description on _no_ with their reasons; a test shows an accepted machine proposal recording nothing for the project and a changed one recorded, and a change against an older revision refused with `conflict` and the current value; `pm-operator enrol` still enrols as a direct verb with its arguments as the answers.

## Standing Constraints

Set by the operator for every plan of this epic on 2026-10-09, beside the rules of `CLAUDE.md`:

- **Java 25 is the baseline.** Write for Java 25 and use its language and library features where they fit; no fallback for an older release. The release comes from the parent POM and is not overridden here.
- **HTTP calls go through `cui-http`.** No direct `java.net.http` or other HTTP client. The build forbids `cui-http` in `pm-core` and `pm-workflow`, so an HTTP call belongs in `pm-runtime` or a provider module, behind an interface the foundation declares.
- **HTTP tests use `cui-test-mockwebserver-junit5`.** Every test that involves HTTP runs against it; no hand-made fake server. The operator's statement is the consent `CLAUDE.md` requires for adding it as a test-scope dependency.
- **Work the package as the index says** (`doc/plans/README.adoc` § How to Work a Package, as reworded by #19): the usual plan-marshall flow — a branch, the commits of the plan, a pull request opened at finalize. No draft pull request claims the package; before starting, list the open pull requests for one that names it. The pull request sets the package's row to `done` within its commits. Build the trace matrix of `traced-implementation` before code, deliver the remainder the roadmap item leaves, and finish with `verify`, `verify -Ppre-commit`, `verify -Pcoverage` and `verify -Pintegration-tests` green.
- **Documents.** Javadoc, `package-info.java` and the work package file live here. Requirement and specification documents, the user documentation, the deletion of implemented specification sections and watch items and the roadmap update are made directly in `plan-marshall-documentation` by this plan, in a pull request there that need not name the code pull request; merging it is the operator's.
- **Module documentation (operator decision 2026-10-11).** Documentation of the code lives in its module, in this plan's pull request, not in `plan-marshall-documentation`: the developer documentation of each package this plan changes in the developer file of each package it changes (`{module}/doc/developer/{package}.adoc`) (create or extend it: what the package is for, its main types and how they work together, how to use and extend it, invariants and failure modes, links to the specification sections it implements), and one ADR per design decision taken — every operator decision and every choice between alternatives — in `{module}/doc/adr/{package}/` as `NNN-{slug}.adoc`, the next free number of that directory, with the sections of `doc/adr/template.adoc` (Status, Date, Context, Decision, Alternatives considered, Consequences, Source) or, before that template exists, those same sections. A decision binding the whole repository goes to `doc/adr/`. The module's `README.adoc` gets one line only when this plan adds a new package; it is otherwise left alone. Layout: workstream WS-10.
- **Settled design: a refused project path is a value.** The confinement check that landed with #19 lives in `pm-core` package `core.store` (`PathConfinement`, `WorkspaceRoots`, `ConfinementOutcome`) and `pm-runtime` package `runtime.workspace` (`WorkspaceConfinement`). A refusal is returned as `ConfinementOutcome` carrying `path_traversal_rejected`; no checked exception type exists or is added. No consumer is wired to it yet (`pm-provider-git` included): a package that performs a file or repository operation for a project adopts the check itself.
- **Do not leave a design choice open that changes the file set.** Where two readings of a deliverable differ in the files they create, ask the operator at refine instead of deferring the choice to implementation.
- **One file is shared by every plan.** In `doc/plans/README.adoc` change only this package's own row.
- **Log messages: the holder of your module, next free identifier** (operator decision 2026-10-13; pm-mcp-core #64, ADR `doc/adr/005-one-log-message-holder-per-module.adoc`). A new INFO, WARN or ERROR record goes into the holder of the module whose production code logs it, at the next free identifier of its level (INFO 1-99, WARN 100-199, ERROR 200-299, the same ranges in every holder); for this plan: `WorkflowLogMessages` (`de.planmarshall.workflow.log`, prefix `PM_WORKFLOW`); `CoreLogMessages` (`de.planmarshall.core.log`, prefix `PM_CORE`); `RuntimeLogMessages` (`de.planmarshall.runtime.log`, prefix `PM_RUNTIME`). A record two modules log goes to the lower one (`pm-core`); a module logs only through its own holder and `CoreLogMessages`. There are no workstream blocks and nothing is renumbered. A provider's first record creates its holder `de.planmarshall.provider.<x>.log.<X>LogMessages` (prefix `PM_PROVIDER_<X>`) with a `package-info.java`, and adds the prefix to `KNOWN_PREFIXES` in `CoreLogMessagesTest`. After a rebase, run the holder's test, which refuses an identifier used twice or outside its level's range, and move to the next free one. The same identifiers go into `doc/LogMessages.adoc` of `plan-marshall-documentation`, under the holder's section, in the documentation pull request.

- **Format versions stay 1 (operator decision 2026-10-13).** Nothing is released yet, so every versioned artifact (`format_version` of a store document, record, sidecar, journal, codec) stays at version 1. A format change replaces version 1 in place: no version bump, no reader for an older version, no migration. Do not raise a `FORMAT_VERSION` constant, a `format_version` in a fixture, schema or specification example, or an ADR that records a bump.
