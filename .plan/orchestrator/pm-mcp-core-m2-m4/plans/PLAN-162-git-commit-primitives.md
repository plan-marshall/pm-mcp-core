## Objective

The sub-workflow `git.commit_and_push` routes on the outcomes of three primitives that exist in no code (`git.resolve-message`, `git.template-message`, `git.stage-and-commit`; the directory `pm-workflow/.../primitive/` holds `package-info.java` only, and the only trace of `git.stage-and-commit` is the example in `workflow-dsl/05-primitives.adoc` line 150), and the entity kind `commit-message` of the state `git.compose-message` (`job llm commit-message role commit-message`) is not among the six default kinds. This plan builds them in the two layers the module structure prescribes: the `git.*` primitives are classes of the provider module `pm-provider-git` that build against the SPI of `pm-core` (module-structure: "the `git.*` and `ci.*` primitives of the provider modules"), and the kind is a default of `EntityKindRegistry` in `pm-workflow`. The primitive SPI gives a primitive a context that names only the scope (`WorkflowExecutionContext.scopeId()`), so everything the stages need from the world comes through ONE port, `CommitSite`, which the assembly implements; the rules themselves are pure and tested here:

- the commit-message rules: Conventional Commit validation (the existing `ConventionalCommitValidator`, not a second validator), the trailer `Co-Authored-By: {name} <{email}>` resolved from the operator's `commit_trailer`, then the machine default, then the compiled default `plan-marshall <noreply@cuioss.de>`, appended exactly once, a model-supplied trailer refused;
- the staging set of a scope and the boundary half of the footprint check, with every path confined by `PathConfinement`;
- the three primitives over `CommitSite` and the git contract `GitOperations.commit`, whose `CommitInput.paths` `PLAN-160` adds;
- the entity kind `commit-message` and its return evaluation.

**Decisions this spec takes (each becomes an ADR, R06):**

1. *The primitives live in `pm-provider-git`, in a new package `provider.git.primitive`,* not in `pm-workflow` (a module that must not see JGit and holds the plan-domain primitives) and not in the assembly. The assembly constructs the `PrimitiveRegistry` from them; that call is the only wrapper it owes.
2. *One port, `CommitSite`,* resolved per call from the scope id: the worktree root, the scope kind (`PLAN`, `EPIC`, `WORKSPACE`), the epic's archive flag, the dirty paths of the checkout (the porcelain list, `.marshall/local/**` ignored), the operator's trailer and identity, the machine default of the trailer, the agent identity. `pm-provider-git` declares it and implements nothing of it (no store read, no second git command line); a test implements it with a record.
3. *The staging set is derived from the scope, never from the checkout* (`06-reusable-sub-workflows.adoc` line 244): plan, the dirty paths inside the worktree after the boundary check; epic, `.marshall/epics/**` and, while the epic archives, `.marshall/archived-epics/**`; workspace, `.marshall/config/**`, `.gitignore`, `.marshall/project-architecture/**`. A dirty path outside the set is never staged and is a boundary breach (check 1). The set is a set of FILES (`PLAN-160` decision 2). The same function is what the assembly's `InputBindingContext` of `PLAN-160` calls for the staging-set bound of a `files` input.
4. *The trailer is appended by the commit-time class alone.* `CommitMessages.withTrailer` is the only code that writes a `Co-Authored-By:` line; it refuses a message that already holds one in any case and position (the rule `commit.co-authored-by` of the existing validator), so the commit carries exactly one trailer, the resolved one. `trailer_source` (`configured`, `default`, `invalid_ignored` per half) is returned as a fact for the audit record and is never rendered in `facts`.
5. *Failures the SPI cannot express as a condition are closed FAILURE outcomes, additive to the state catalogue's list.* `git.stage-and-commit` declares `committed`, `nothing_to_commit`, `hook_failed`, `attempts_exhausted` (the catalogue's four) and three additive ones: `footprint_violation` (facts `offending_files`, bounded), `message_refused` (facts `rule`, `line`) and `commit_failed` (the git contract's `FAILED`, `CAPABILITY_MISSING`, `NOT_A_REPOSITORY`, `PATH_REFUSED`). The engine maps `footprint_violation` to the condition of the same name (`state-catalogue/01` `condition-footprint_violation`); that mapping is the engine's and is a hand-off. Alternative: leave the check to the engine before the primitive runs — rejected because the specification makes it the primitive's first step for every caller (Stage 4). The operator may veto.
6. *The check is the boundary half only.* Check (1) (no dirty path outside the staging set, none outside the plan's worktree) is pure and built here. Checks (2) (an enrolled wrapper's `pinned_files` changed) and (3) (a main-checkout path outside `.marshall/local/` absent from `entry_baseline`) read stores and the job runtime; they are `CommitSite` methods (`pinnedFilesChanged()`, `mainCheckoutBreaches()`) whose implementation is the assembly's, and the primitive treats their answer as it treats check 1.
7. *The entity kind `commit-message` is `EntityKind("commit-message", "entity", "commit-message.evaluate")`,* the shape of the single-submit kinds `decision`, `triage` and `simplify`; its return evaluation is a primitive of this plan (outcome `valid` only: the message was validated as a Conventional Commit and refused for a trailer at the link, `PM-WF-6` step 5, before the task closed). `infeasible` and `lost` are the reserved engine outcomes the state already routes (`git.template-message`).
8. *`git.template-message` renders from facts and decides nothing:* the template message of the caller's step from `git.diff-summary` (type by the priority `fix > feat > perf > refactor > docs > style > test > chore > ci`, scope, the step subject) is a pure function of the summary; the diff summary itself is a `CommitSite` method.

## Standing Constraints

- **Log messages: none expected.** A refusal is an outcome with facts.
- **No command line from a value.** The message goes to the repository through `GitOperations.commit` (API) and never into a process argument; the paths are repository-relative files, confined, never a pathspec the primitive composes. The CLI variant (`git commit -F -`, `--pathspec-from-file=- --pathspec-file-nul`) is not in the repository and is not built here.
- **No generic `Exception`** is caught or thrown; the refusals of `CommitMessages`, `StagingSets` and `PathConfinement` are returned values (R09).
- **`pm-provider-git` depends on `pm-core` only;** it never sees `pm-workflow` (module-structure line 586). The verification test of Deliverable 4 must not add a dependency; if it would, it moves to the assembly and the deliverable keeps the kind and the evaluation primitive only (R07, decided at the outline and stated in the first progress note).
- **`GitOperations`, `JGitOperations` and `ConventionalCommitValidator` are read, not edited;** `CommitInput.paths` is `PLAN-160`'s.
- **Add no dependency and no plugin** (CLAUDE.md).
