## Objective

Implement the work package `machine-onboarding-unit` of `doc/plans/machine-onboarding-unit.adoc`: the onboarding of the machine. Serves: roadmap Milestone 7 (the machine scope and its onboarding), Milestone 10 (the landing axis, the plan's overrides), Milestone 14 (a harness the operator adds, verified under `verify_harness_profile`); Use Cases, UC-ONB-1 to UC-ONB-10; the onboarding and the machine's settings in both clients of `pm-mcp-clients`. Where: pm-workflow (the onboarding's sub-workflows in the machine scope, the machine's settings, the plan axes and overrides in the composition); pm-core (the consent, catalogue, steward, role, and credential stores); pm-runtime (the harness scan and probes, provider verification). The package file is the brief; this spec adds what the orchestrator observed and the constraints of the epic.


**Why the credential-store aspect is on the critical path (analysed 2026-10-19 from plan-marshall-mcp #88 and #90).** The daemon serves only the store recorded in `credentials.store` of `machine-config.json` and refuses every credential operation until one is recorded: `CredentialsResource` answers `409 {"error":"onboarding_incomplete"}` (proven by `KeyringIT.refusesBeforeStoreChoice` against the packaged daemon). The only legitimate writer is this package's credential-store aspect, through `CredentialStoreChoice.record(LockManager, user, Store)` of `pm-runtime`. At `91b60d5` of `plan-marshall-mcp` and `ce43548` of this repository no production code calls it, so a fresh install cannot enter a credential until this aspect exists. The aspect is not separable from the machine scope: its states run in the machine-scope sub-workflows (`operator-wait-and-machine-scope`). The operator verb already exists and is not part of this spec: `pm-operator config credentials --store os|file` is implemented in `pm-mcp-clients` (`ConfigCommand.CredentialsCommand`) and designed in its terminal-client design (§ A Later Change Moves the Tokens), with `pm-operator credentials migrate os|file` named by the specification for the move; what no repository provides is the runtime side the verb talks to (the verb posts to `/api/v1/config/credentials`, which neither this repository, `plan-marshall-mcp` nor the specifications define). This package's aspect is that runtime side; the client's call path is the clients' to check.

The client side is `onboarding-contract` of `pm-mcp-clients`.
2. The onboarding's sub-workflows in the machine scope of `operator-wait-and-machine-scope`: languages, harnesses (one scan, a default), models, roles, credentials, providers, plan defaults; each aspect a compiled sub-workflow with the parameter `onboard_run` (`first_run`, `reconfigure`); the first run from `onboard.entry` through `onboard.mode` (guided or automatic), a later run of one aspect from the machine's settings (`settings.choose`) with its current values as the proposal, returning there.
3. The consent store `consents.json` and its closed list of kinds, among them `check_credential_store` (asked in `store.consent`, only for an OS store; the file store is checked without one) and `verify_providers` (asked in `providers.verify-consent`); a project's kind with its project, and `run_checkout_scripts` with the digest of each script, in this store only, never in an enrolment; the consent state before every action: each action state is reached only through its consent state (`<sub-workflow>.consent` or `<sub-workflow>.<action>-consent`) answered `yes` or `yes_remember`, or passed without a question where the kind is remembered in the store, and `no` records nothing and leaves the scope in the consent state, an optional action going on without the action; an act of the operator's own, a credential the operator types, stored without a consent.
4. The harness scan, the login and model probes, and the verification of an unknown harness, as confined jobs of the kind `probe`; the verification runs only from `harness.verify-profile` after `harness.add-consent` answered `yes` with the expected tokens of its stages shown, the kind `verify_harness_profile` never remembered and so asked before every verification, in a first run and in a reconfiguration alike, and the draft validated as a profile before anything runs; the profile fields they read. The harnesses are listed in the order of their `client_id`, every supported worker-eligible one preselected and the first of them the default; the same order serves `auto.run` and the first enrolled harness of `roles.default`. The verification records per usage figure what the harness reports (`reported`, `not_applicable`, `missing`, as `token-usage` specifies), and the harness list shows each harness's usage coverage for its version: tokens `complete`, `partial` with the figures missing, or `not_reported`. The step needs one usable harness: the last chosen one cannot be left out, and when none is found or every chosen one fails its probe the step goes to `harness.none` (an operator wait with `recheck` and `add`, naming each known harness's install hint, the onboarding resting there until the operator acts).
5. The model catalogue, the default and the operator's role assignment; the steward role outside both: not among the roles `roles.load` lists, always on the default harness with that harness's default model, outside the catalogue (`model_not_allowed` never applies to it), exempt from qualification, and its submits.
6. The credential-store aspect (`store.choose`, `store.consent`, `store.check`, `store.confirm-move`, `store.move`), a failed move going to `store.unavailable` with `credential_store_failed` and the old store kept, over the delivered store of `pm-runtime` (`CredentialStoreChoice`, which records the operator's choice, and `CredentialStoreMove`, which moves the entries; the automatic selection is removed); the machine's provider defaults and their verification.
7. The automatic onboarding with its consent and its result (reasons, items); _change_ on `auto.result` calls that one aspect as a later run (`onboard_run: reconfigure`, its current values as the proposal) through `onboard.next` and returns to the result; a state it cannot decide alone (a login, a token, no harness found, the model ids of a harness that cannot list its models) shown as in the guided run.
8. The machine's settings (UC-ONB-10), states of the onboarding unit reached from `onboard.completed`: `settings.choose` (the recorded aspects, the remembered consents, the documents mode, the cleanup's durations, the credentials with their status, the paired devices, which are acted on through their own endpoints); reconfigure an aspect as a later run of its sub-workflow; withdraw a consent (`settings.withdraw`, `settings.remove-consent`, audited, asked again at its next action); the documents mode (`settings.documents-mode`, `settings.record`: the machine key `sources.documents_mode`, `copy`, `move`, or `ask`, the default, which `start-source-intake` reads); the cleanup's durations (`settings.cleanup-durations`, `settings.record`: the machine's `cleanup.*` durations per kind and the reminder's days, which `cleanup` reads); the providers checked again on request (`settings.verify-providers`, `call providers` at its entry `verify` over every chosen provider); a credential rotated or replaced (`settings.credential`, `settings.store-credential`, every token derived from the old secret dropped), verified again through `providers.verify-consent`, `providers.verify`, and `providers.failed`, after which a plan held by the expired credential goes on.
9. Concurrent changes of a setting (CLI & Security § Concurrent Changes of a Setting): every change of a recorded value, of the machine's settings here, of a project's operator values in `project-onboarding-unit`, and of a plan's own values in `plan-and-epic-control`, carries the revision of the settings it was made against; the first change wins, a later one against an older revision is refused with `conflict` (`409`) and the current value, which the operator may change again on top of it; nothing is merged and nothing is overwritten unseen.
10. The plan behaviour axes and plan overrides in the composition: each variant a sub-workflow named with its axis as prefix, an axis's variants a closed list; the method variant (`method.test-first`, `method.tests-after`) called by `plan.order-tasks` of `phase-4-plan`, the asking variant (`ask.every-phase`, `ask.key-points`, `ask.questions-only`) by the plan unit's `phases.ask`; a landing variant composed into the step list of `phase-6-finalize` at its landing orders, which keeps its checks and reviews, with `landing.pull-request` (push, pull request, its reviews, merge), `landing.main` (commit and push on the base branch), and `landing.files` (no commit, the changes written into the main checkout's working tree, the plan handed back), apart from the land lane; the binding of each axis at the plan's start; the composition event `override`, the prune reasons `plan_default` and `merge_by_operator`, and the removal of the shipped rule `auto-merge-off` are implemented (Plan Instance Developer Guide § The Plan Behaviour Axes); `overrides.json` with a role's harness, model, and effort, the variant of each axis and of an integration, and the optional providers.
11. Validation of the landing: `defaults.validate` checks only what the machine provides (a provider for `landing.pull-request`), never a repository; a landing variant is validated where a project is known (its setup, a plan's start, a plan's settings), refusing `landing.pull-request` without a provider and `landing.main` on a protected base branch with the reason, also a machine default that does not fit the project.
