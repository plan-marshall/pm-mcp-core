== Purpose
_Requirements: link:{docs}/Requirements.adoc#PM-IMPL-1[PM-IMPL-1], link:{docs}/requirements/09-technology.adoc#PM-TECH-2[PM-TECH-2]_

Package `de.planmarshall.provider.github` holds the native GitHub client of PM-MCP: GitHub App authentication, the fixed
GraphQL documents for review threads and the merge queue, and the REST calls of the review path. It builds on the shared
HTTP base `pm-provider-http` (link:../../../pm-provider-http/doc/developer/provider-http.adoc[`provider.http`]) and names
GitHub; the base names no forge.

The module is a client, not a CI workflow: the engine's `ci` contract (`CiProvider`,
link:../../../pm-provider-ci/doc/developer/provider-ci.adoc[`provider.ci`]) is implemented on top of these calls by
`GitHubCiProvider`, and this package returns typed results and closed outcomes.

== Authentication

A call follows one path:

. The client asks `InstallationTokens` for a token for `(installation, repository, GitHubOperation)`.
2. `InstallationTokens` returns a token it still holds, or signs a fresh `GitHubAppJwt` with the private key it reads at
   that moment and mints a token over the shared HTTP base.
3. The minted token is registered for redaction and kept in memory, keyed as above, until 300 seconds before its expiry.
4. `HttpClient` sends it as `Authorization: Bearer …` to the endpoint origin only.

A comment on a pull request travels through the issue-comment endpoint
(`POST /repos/{owner}/{repo}/issues/{number}/comments`) and still needs `pull_requests: write`: GitHub answers a token
narrowed to `issues: write` alone with `403` there. That is why `PULL_REQUEST_COMMENT` and `ISSUE_COMMENT` are two
operations with different permission sets.

== Invariants and Failure Modes

* *The private key is read per mint and never cached.* A rotated key is used on the next mint, and the key never reaches a
  log, an exception message or a result detail.
* *A token lives in memory only.* It is never written to a store; the reuse map is dropped when the client closes. The
  redaction registry covers a token that appears in a provider message.
* *A token is narrowed.* Every operation names its permission set, so a client that only reads review threads cannot write
  a comment or enqueue a merge.
* *A rate limit is an outcome.* The base reports `RATE_LIMITED` with its reset instant; the client never waits inside a
  call.
* *An incomplete read is not the full set.* The review-thread read follows the GraphQL page info with a page cap
  (`MAX_THREAD_PAGES`, 20), and the changed-files read the `Link` pagination with its cap (`MAX_FILE_PAGES`, 30); an
  incomplete read is an outcome the caller can see, never a silently short list.
* *A pull request in any state is read the same way.* A closed or merged pull request is `OK` with its state, and a
  pull request on another origin or forge is refused before a request is sent.
* *The merge queue is bound to the head.* `enqueue` sends the expected head oid, so a queue entry cannot be created for a
  head the caller did not review.
* *Remote text is untrusted.* A comment body and an author login are data; a caller that emits or persists them passes a
  provider message through the runtime's redaction.
* *A blank optional value is absent.* A blank user id is filtered out and the identity read is `FAILED`, never handed
  to `Identity` as a blank; a blank milestone title is read as no milestone. `Identity` and `Issue` keep refusing a
  blank, and the adapter filters it where the JSON enters.
* *An expiry the parser cannot read is no expiry.* The token expiry header is read in the `yyyy-MM-dd HH:mm:ss z` form
  and in the ISO and offset forms (`+0000`, `+00:00`) of the same instant; a header in none of those forms is reported
  as no expiry, never as an error and never as a guessed instant.

== The CI Adapter

`GitHubCiProvider` implements the CI contract on the native variant. A provider is bound to one web origin and one
credential. `whoami` reads `GET /user` and, with a repository named, `GET /repos/{owner}/{repo}` for the permissions; the
kind comes from the token prefix (`github_pat_` fine-grained, `ghp_` classic), the scopes from `x-oauth-scopes` and the
expiry from `github-authentication-token-expiration`, both response headers the shared base keeps for
`HttpClient.getWithHeaders`. The expiry is read in the `yyyy-MM-dd HH:mm:ss z` form and in the ISO and offset forms of
the same instant (`+0000`, `+00:00`); a header the parser cannot read is reported as no expiry, and a blank user id or
milestone title is filtered as absent. For a GitHub App the adapter reads the App's slug from `GET /app` with the App
JWT, the bot user id from `GET /users/{slug}[bot]` and the operator's login from `GET /user` with the user access token.
`issueView` reads `GET /repos/{owner}/{repo}/issues/{n}` with the token the caller minted for
`GitHubOperation.ISSUE_READ`, flags the `pull_request` member and refuses a pull request. `issueComment` posts through
`GitHubClient.postComment` and derives the comment URL. An issue on another origin or of another forge is refused before
a request is sent.

[#_the_pull_request_read]
=== The Pull-Request Read

`prView` refuses a pull request on another origin or of another forge with `REJECTED` before a request is sent. It then
makes up to three REST reads, the same for every state of the pull request:

. `GET /repos/{owner}/{repo}/pulls/{n}` (`GitHubClient.pullRequest`): the state, title, body, base ref, head ref, head
  commit, head repository (`head.repo`, owner and name), `maintainer_can_modify` and `changed_files`. `closed` with
  `merged: true` is `MERGED`, `closed` otherwise `CLOSED`, `open` `OPEN`; a state outside these, or a body without the
  state, title, base ref, head ref, head commit or changed-file count, is `FAILED`. An issue number is answered `404` by
  GitHub and is `NOT_FOUND`. The head is a fork when its repository is another than the base's (`base.repo.full_name`).
. `GET /repos/{owner}/{repo}/pulls/{n}/files?per_page=100` (`GitHubClient.pullRequestFiles`): the `filename` of each
  changed file, through the `Link` pagination of the shared base. A page that is not a JSON array is `FAILED`.
. `GET /repos/{owner}/{repo}` (`GitHubClient.canPush`): the `permissions.push` member of the repository the head is
  writable by, read only when it decides the answer.

*The two caps of the changed paths.* The read stops after `MAX_FILE_PAGES` (30) pages of 100 files; a list the page cap
(or a next link outside the origin) cut is `PAGE_CAP`. GitHub itself lists at most 3000 files for one pull request, which
the 30 pages reach; a list read to its last page that is still shorter than `changed_files` is `PROVIDER_RESULT_CAP`.
Every other list is `COMPLETE`.

*`headWritable` per head kind.*

* A head in the base repository is writable when `permissions.push` of that repository is `true`.
* A fork head is writable when the author allows maintainer edits (`maintainer_can_modify`) and `permissions.push` of
  the base repository is `true`; without maintainer edits it is not writable, and no permission read is sent.
* A head repository GitHub no longer knows (`head.repo` is `null`, a deleted fork) is not writable, the head repository is
  absent, and no permission read is sent.
* An absent `permissions.push` member reads as not writable, and so does a `404` of the permission read (a repository the
  credential cannot see); the read continues with the head not writable.

*`headWritable` per credential kind.* The `push` fact is read with the credential that authors the writes: a token
provider (`forToken`) with its own token, a GitHub App provider (`forApp`) with the operator's user access token, not
with the installation token that reads the pull request and its files. The installation token's own `permissions`
member therefore never decides the answer
(link:../../../pm-provider-ci/doc/adr/provider-ci/007-head-writable-is-the-credentials-push-fact.adoc[`provider.ci` ADR
007]).

*The permission set.* An installation token for the pull-request read is minted for `GitHubOperation.PULL_REQUEST_READ`:
`pull_requests: read`, `contents: read` and `metadata: read`, the set the specification names for this read. The
installation token never reads the permission fact; the user access token does.

A refused read (a `404`, a `403`, a `401` or a `5xx`) on the pull request or its files is mapped to its outcome by the
shared base, and a rate limit is `RATE_LIMITED` with its reset instant; nothing is read after a refused read. Two cases
are kept apart from `NOT_FOUND`, which says that the pull request does not exist: a `404` of the files read, after the
pull request was read, is `FAILED` with a fixed reason, and a `404` of the permission read is not an error but the head
being not writable. A refused permission read otherwise (a `403`, a `401` or a `5xx`) is mapped by the shared base.

== Extending the Client

. Add the operation to `GitHubOperation` with the narrowest permission set it needs.
2. Add a fixed GraphQL document as a resource where the operation reads; a REST call goes through `HttpClient.send`.
3. Return `Result<T>` and map a failed `Response` with `Result.failed`, so a credential refusal (`AUTH_FAILED`,
   `PERMISSION_DENIED`) is told apart from a provider refusal (`REJECTED`) and from a failure (`FAILED`).
4. Add the call to `GitHubClientTest` with a canned route response and a matched control for each documented failure.

== Pitfalls

* *Do not mint a token for the whole installation.* A token narrowed to the repository and the operation is the point;
  a broad token widens what a bug in one call can reach.
* *Do not hold a token past its margin.* A token used inside the last 300 seconds can expire during a request; the client
  mints a new one instead.
* *Do not put a body in a query string or a file.* The body is an in-memory request payload.
* *Do not treat a permission error as a failure.* `PERMISSION_DENIED` is a configuration or consent problem, and the
  caller reports it as such, not as a transport failure.
