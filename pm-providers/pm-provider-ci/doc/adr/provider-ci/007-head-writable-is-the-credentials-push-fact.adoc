= ADR 007: `headWritable` Is the Credential's Push Fact
:nofooter:

== Status

Accepted.

== Date

2026-11-05.

== Context

The plan source `pr` of a start adopts an open pull request for repair: the plan's branch is the pull request's head
branch, and `source-pr.observe` requires that head to be writable by the agent identity, answering `head_not_writable`
otherwise, for example for the head of a fork without push access (State Catalogue 09 § `source-pr.observe`; Phase
Workflows 01 § Plan Source Contracts, `pr`). `ci.pr-view` is the read behind that check, so it has to state whether the
head is writable.

The two forges say it differently. GitHub reports `permissions.push` on a repository and, for a fork head, whether the
author allows the maintainers of the base to push (`maintainer_can_modify`). GitLab reports an access level per project
(project or group membership, Developer is 30) and, for a fork merge request, whether the author allows the members of
the target project to push (`allow_collaboration`). A GitHub App reads with an installation token but authors its writes
with the operator's user access token. A permission member a forge leaves out of a response says nothing either way.

`Identity.permissions` already carries the permissions a forge reports for a repository, under the forge's own names
(refine finding S3).

== Decision

`PullRequest.headWritable` is a boolean: the provider's statement, at the moment of the read, that the credential the
provider is bound to can push to the head branch. Each adapter decides it from its forge's facts:

* *GitHub.* A head in the base repository is writable when `permissions.push` of that repository is `true`. A fork head
  is writable when `maintainer_can_modify` is `true` and `permissions.push` of the base repository is `true`. A head
  repository GitHub no longer knows (`head.repo` is `null`) is not writable. The `push` fact is read with the
  credential that authors the writes: the provider's own token, or for a GitHub App provider the user access token,
  never the installation token.
* *GitLab.* A same-project merge request is writable when the credential has Developer access (30) or more on the
  project. A fork merge request is writable when `allow_collaboration` is `true` and the credential has Developer access
  or more on the target project. A source project GitLab no longer knows is not writable.

An absent permission member, an access level the response does not carry, and a repository the credential cannot see
(a `404` of the `push` read) read as not writable, and the read continues. The read adds no
portable push vocabulary to `Identity.permissions`, which keeps the provider's names, and `headWritable` is not
re-derived from it.

== Alternatives Considered

* *Expose the raw permission facts and let the consumer decide.* Every consumer would repeat the forge-specific rule
  per head kind, and the consumer in the assembly would have to name the forges the contract keeps out of it.
* *Add a portable push entry to `Identity.permissions`.* It would mix a vocabulary of the contract into the provider's
  own names and still not answer the fork case, which depends on the pull request, not on the repository alone (S3).
* *Read the `push` fact with the installation token of a GitHub App.* The installation token is not the credential
  that pushes, so its answer is the wrong fact; the user access token is.
* *Read an absent permission as writable.* A head the forge did not confirm would be adopted and fail at the first
  push instead of at `source-pr.observe`.

== Consequences

* A consumer maps `OK` with `headWritable` `false` on an open pull request to `head_not_writable` without knowing the
  forge.
* `headWritable` is no lasting grant: a branch protection rule, a changed membership or a moved head can still refuse a
  push, and `start.create` and `finalize.adopt-pr` observe the head again rather than rely on an earlier read.
* A GitHub App provider needs the user access token for the `push` read alone; the pull request and its files are read
  with the installation token. A fork head without maintainer edits or collaboration costs no permission read.
* A forge added later states its own rule in its adapter and keeps the meaning of the boolean.
