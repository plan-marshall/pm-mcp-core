= ADR provider-git-primitive 008: The Staging Set Refuses What the Commit Refuses
:nofooter:

== Status

Accepted

== Date

2026-11-22

== Context

The staging set of a scope accepted a dirty name that the commit refuses with `PATH_REFUSED`: a name that begins with
`:`, contains a backslash, a control character or a newline, or is the `dir/` entry of an embedded repository (git lists
both by their directory, `dir/`). The commit then failed closed as `failed` with
the reason `commit_failed` and the git detail `PATH_REFUSED` before anything was staged, so one odd file name blocked the
whole plan commit — an availability defect, not an integrity one. The textual rule of a commit path existed only in
`JGitOperations`, so the staging set had no way to agree with it (landing of PLAN-V2-20, L3-2, L3-7, L3-8). The
file-system and tracked-tree refusals had the same gap: a modified submodule is listed by its name alone (git lists it as
`sub`, not `sub/`), and the worktree holds it as a directory, so the commit refused it while the staging set staged it; a
tracked directory that a file replaced is refused by the index and the head tree, and the staging set staged it too
(landing of PLAN-V2-169, carried item 90a).

== Decision

* `CommitPathRefusals` is the one rule of a path a commit cannot stage, in three parts: the textual rule of
  `CommitPaths.isRefusedText`, the file-system rule (no directory, no absolute name, nothing outside the root, no parent
  that a symbolic link carries outside the real root), and the tracked-tree rule (no name that is a directory of the index
  or of the head tree although the worktree no longer holds it as one). Both `JGitOperations.commit` and
  `StagingSets.derive` apply it, so the two cannot disagree.
* `CommitPaths.isRefusedText` is the textual part: it is not empty, does not begin with `:` or `/`,
  holds no backslash and no control character (a newline among them, and the NUL that is one), and has no empty, `.` or
  `..` segment. A directory entry fails it through its empty segment.
* `JGitOperations.commit` refuses a path that fails the rule with `PATH_REFUSED` before anything is staged, and
  `StagingSets.derive` puts it in the `outside` set of the staging set. The footprint check therefore refuses it with
  `footprint_violation` and names it, a typed answer of the primitive instead of a git detail surfaced through
  `commit_failed`.
* The dirty paths of the site are NUL-separated (`-z`; `core.quotePath=false` alone still escapes a quote, a backslash
  and a control character), list an embedded repository by its directory (`newdir/`) and a modified submodule by its name
  (`sub`), and list a rename by both sides, the old path and the new one; the staging set reads them as they come, so an
  embedded repository and a modified submodule are both a footprint violation and a rename is staged on both sides.
* The commit's own refusal stays: a bound `files` path is refused at the bind (`path.staging`), and a path that reaches
  the commit anyway is refused there instead of being read as a pathspec.

== Alternatives Considered

* *Keep the failure at the commit.* Not taken: a single odd file name blocks the whole plan commit, and the operator
  sees a git detail where the footprint check has a named violation and a remedy.
* *A second copy of the textual rule in `StagingSets`.* Not taken: two copies of one rule are how the two diverged;
  the rule is text, so it needs neither the file system nor the variant of the contract.
* *Confine the whole path and follow its last name in the staging set.* Not taken: the site's dirty list is the answer
  to which names the checkout holds, and a symbolic link is a legal commit entry that following would refuse.
* *Let the staging set repeat the file-system and tracked-tree checks itself.* Not taken: they are the commit's own
  rule, and a second copy would drift exactly as the textual one did (`PLAN-V2-172`).

== Consequences

* A dirty name no commit can stage reaches the operator as `footprint_violation` naming it; the condition's remedy
  (revert or remove the entry) applies as for any other breach.
* `CommitPathsTest` pins the textual rule, `StagingSetsTest` the `outside` answer per refused class, and
  `JGitOperationsPathTest` the commit's unchanged refusal — the modified submodule and the tracked directory a file
  replaced are proved on real repositories there, beside the staging set that must answer the same
  (`modifiedSubmoduleIsRefusedByBoth`, `trackedDirectoryReplacedByAFileIsRefusedByBoth`).
* A new textual refusal is added to `CommitPaths` once and reaches both the commit and the staging set; a new
  file-system or tracked-tree refusal is added to `CommitPathRefusals` once and reaches both as well.
