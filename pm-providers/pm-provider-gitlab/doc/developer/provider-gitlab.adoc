== Purpose

A field, parameter or record component whose value may be absent is written `@Nullable T` since the null-contract conversion; `Optional<T>` is returned for absence only.

_Requirements: link:{docs}/Requirements.adoc#PM-IMPL-1[PM-IMPL-1], link:{docs}/requirements/09-technology.adoc#PM-TECH-2[PM-TECH-2]_

Package `de.planmarshall.provider.gitlab` connects the engine to GitLab in two variants: the native REST client over the
shared HTTP base `pm-provider-http` (link:../../../pm-provider-http/doc/developer/provider-http.adoc[`provider.http`]), and
the argument vectors of the `glab` CLI variant. Both cover the same merge path and review operations; the engine picks
one by the enrolment's provider configuration.

The package is a client, not a CI workflow: it returns typed results and closed outcomes, and the engine's `ci` contract
(`CiProvider`, link:../../../pm-provider-ci/doc/developer/provider-ci.adoc[`provider.ci`]) is built on top of them by
`GitLabCiProvider`.

== The Native Client

The client is constructed with an `HttpClient` already pinned to the GitLab origin and with the project path. It sends
the bearer token the base resolves per request. Every merge call carries the expected head `sha`: a merge or a train add
is refused by GitLab when the head moved, rather than merging a head the caller did not review.

`discussions(iid)` reads the notes of every discussion and follows pagination with a page cap. `Discussion.resolved()`
is true when every note that can be resolved is resolved; a note that cannot be resolved is filtered out and does not
count either way.

`tokenIdentity()` answers through `GET personal_access_tokens/self`; when GitLab refuses that with `400` because the token
is of another type, the client reads `GET /user` instead and still answers a `TokenIdentity`. Only a failed read is an
outcome, not a `TokenIdentity` with missing scopes.

== The CI Adapter

`GitLabCiProvider` implements the CI contract on the native variant. A provider is bound to one web origin and one
credential. `whoami` maps `GitLabClient.tokenIdentity()` (the `personal_access_tokens/self` record, with the `GET /user`
fallback for a token that is no personal access token) to the contract's `Identity`: the login and bot flag come from
`GET /user`, the kind from the bot user (`project_<id>_bot_…` a project token, `group_<id>_bot_…` a group token, a token
without a record an OAuth token, everything else a personal token), the scopes and expiry from the token record, and the
permissions from the `permissions` object of `GET /projects/{path}`. `issueView` reads
`GET /projects/{id}/issues/{iid}` and `issueComment` posts to `POST /projects/{id}/issues/{iid}/notes`, each with the
project path URL-encoded as the client does. An issue on another origin or of another forge is refused before a request
is sent. A missing issue is `NOT_FOUND`; the adapter does not probe a merge request, so the issue and merge-request
number spaces stay apart (link:../../../pm-provider-ci/doc/adr/provider-ci/006-a-missing-gitlab-issue-is-not-found.adoc[`provider.ci`
ADR 006]). The login and the user id come from `GET /user`: a blank user id falls back to the token record's `user_id`,
and an identity whose two ids are both blank is `FAILED`, never a thrown exception. A blank milestone title is no
milestone.

[#_the_merge_request_read]
=== The Merge-Request Read

`prView` reads a merge request; the contract calls it a pull request. A merge request on another origin or of another
forge is refused with `REJECTED` before a request is sent. The read is the same for every state and is made of the
following REST reads, each with the project path or id URL-encoded:

. `GET /projects/{id}/merge_requests/{iid}` (`GitLabClient.mergeRequest`): the state, title, description,
  `target_branch`, `source_branch`, `sha`, `source_project_id`, `target_project_id`, `allow_collaboration` and
  whether `changes_count` is the string `1000+` (GitLab's diff limit capped the changed files). A body
  without the state, title, branches, `sha` or target project is `FAILED`. GitLab numbers issues and merge requests
  apart, so an issue iid without a merge request of the same iid is `NOT_FOUND`.
. `GET /projects/{id}/merge_requests/{iid}/diffs?per_page=100` (`GitLabClient.mergeRequestDiffs`): the `new_path` of each
  diff, through the `Link` pagination of the shared base. The paginated diffs endpoint exists from GitLab 15.7 on, which
  is the minimum version of the read; a page that is not a JSON array, or a diff without a usable `new_path`, is `FAILED`
  with a fixed reason, because the read compares no changed-file count with the list and a dropped diff would read as
  `COMPLETE`.
. `GET /projects/{id}` (`GitLabClient.project`), by the numeric id of the target or the source project: the project's
  `path_with_namespace` and whether the credential's access level, as a project member (`permissions.project_access`)
  or a group member (`permissions.group_access`), is Developer (30) or above. A response that carries neither level
  reads as below Developer.

*The state mapping.* `opened` is `OPEN`, `merged` is `MERGED`, and `closed` and `locked` are `CLOSED`; any other state is
`FAILED`. `locked` is the state GitLab gives a merge request while it is being merged, and the contract has no state
for that passage
(link:../../../pm-provider-ci/doc/adr/provider-ci/008-a-non-open-pull-request-is-a-value.adoc[`provider.ci` ADR 008]).

*The two caps of the changed paths.* The diffs read stops after `MAX_PAGES` (50) pages of 100 diffs; a list the page
cap (or a next link outside the origin) cut is `PAGE_CAP`. GitLab itself lists no file past its diff limit (1000 files
by default) and does not paginate beyond it; it states the condition in the merge request's `changes_count`, which is
then the string `1000+` instead of a number. A list read to its last page of a merge request with `changes_count`
`1000+` is `PROVIDER_RESULT_CAP`. `PAGE_CAP` comes first: a read the local cap stopped ended before GitLab's limit
could be seen. Every other list is `COMPLETE`.

*`headWritable` for a same-project and a fork merge request.*

* A same-project merge request (the source project is the target project) has its head in the addressed repository; it
  is writable when the credential has Developer access or more on the project.
* A fork merge request has its head in the source project, read by its id for its path; it is writable when the author
  allows collaboration (`allow_collaboration`) and the credential has Developer access or more on the target project.
  Without collaboration it is not writable, and the target project is not read.
* A source project GitLab no longer knows (no `source_project_id`, or a `404` for the source project) leaves the head
  repository absent and the head not writable.

The rule and its reason are recorded in
link:../../../pm-provider-ci/doc/adr/provider-ci/007-head-writable-is-the-credentials-push-fact.adoc[`provider.ci` ADR
007]. A refused read of the merge request, its diffs or a project is mapped to its outcome by the shared base, and a
rate limit is `RATE_LIMITED` with its reset instant. `NOT_FOUND` says that the merge request does not exist, so a `404`
of the diffs or of a target project read after the merge request was read is `FAILED` with a fixed reason; on GitLab
older than 15.7 the diffs endpoint does not exist, and the reason names the minimum version. The one `404` of a later
read that is a value is the source-project read of a fork (a deleted or hidden fork: the head repository is absent and
the head not writable); every other non-`OK` outcome of a later read, such as a `403` or a `500` of the source project or
a failure of the target-project read, is propagated as the failure it is.

== The `glab` Variant

`GlabCommands` composes the argument vector and the payload of one invocation, and the caller runs it. Three rules shape
it:

* *A body is standard input, never an argument and never a file.* `reply`, `createMergeRequest` and every other call with
  a body pass `--input -` and return the JSON as `Invocation.stdin`.
* *Every identifier that enters the vector is validated.* The host, a discussion id and a branch each match a pattern
  first, the project path is URL-encoded, and a job id is range-checked, so no value can start with `-` and be read as a
  flag.
* *The operation set is closed.* Each method answers one fixed `glab api` call; a caller cannot compose an arbitrary
  argument vector through this type.

== Invariants and Failure Modes

* *The head is part of the merge.* Both variants send the expected head; a moved head is an outcome of the call, never a
  silent merge of another commit.
* *A body is never an argument.* A body on a command line is visible in the process table and may be logged; the `glab`
  variant streams it on standard input, and the native variant sends it in memory.
* *A paginated read is complete or marked incomplete.* The page cap is a safety bound; a caller that needs the whole set
  checks the completeness the base reports, not the length of the list.
* *A credential refusal is not a failure.* `AUTH_FAILED` and `PERMISSION_DENIED` are told apart from `REJECTED` and
  `FAILED`, and the caller reports the first two as a configuration problem.
* *The token is not in a vector or a result.* The `glab` CLI resolves its own credential; the native client's token comes
  from the base and is never put into an argument or a detail.
* *A blank optional value is absent.* A blank user id falls back to the token record, a blank milestone title is no
  milestone, and an identity with no id at all is `FAILED`; `Identity` and `Issue` keep refusing a blank, and the adapter
  filters it where the JSON enters.
* *A missing issue is not found.* `issueView` answers `NOT_FOUND` for a missing issue and sends no merge-request probe;
  GitLab numbers issues and merge requests apart, so only the pull-request view may read a merge-request number.
* *A merge request in any state is a value.* `closed`, `merged` and `locked` are `OK` with their mapped state, and a
  diff list cut by the page cap is `PAGE_CAP` and one cut by GitLab's diff limit `PROVIDER_RESULT_CAP`, never presented
  as the whole list.

== Extending the Package

. Add the operation to `GitLabClient` with `Result<T>` and to `GlabCommands` with an `Invocation`, or to one variant only
   where the other cannot express it; the engine's contract names which variants it supports.
2. Validate every identifier the vector takes, and pass every body on standard input.
3. Add a canned route response to `GitLabClientTest` and the expected vector and stdin to `GlabCommandsTest`.
4. Document in the method's Javadoc which outcome a moved head, a refused permission and a missing job trace answer.

== Pitfalls

* *Do not pass a description or a note as an argument.* It is a body, and the `glab` variant passes it on standard input.
* *Do not omit the expected head.* A merge without it merges whatever the head is at the moment of the call.
* *Do not read an unresolvable note as a verdict.* The resolved rule ignores notes that cannot be resolved; a caller that
  needs to know whether any note is unresolved reads the notes, not only `resolved()`.
* *Do not build a vector by string concatenation.* Compose the list as `GlabCommands` does, with each value validated on
  its own.
