== Purpose
_Requirements: link:{docs}/Requirements.adoc#PM-IMPL-1[PM-IMPL-1]_

Package `de.planmarshall.core.findings` of `pm-core` holds the normalized finding and the contracts every producer of
findings implements: what a finding is, what a scope is asked about, under which key a producer is registered and how a
finding is answered on its provider. The provider modules are where the calls belong; no implementation of these
contracts exists in this repository yet, and the store and the workflow own recording what is observed.

The package holds declarations, validation and lookup only: it makes no HTTP call, writes no file or store and depends
on no store class. Why the contract lives in the foundation and not in a provider module is stated in
link:{docs}/specification/module-structure.adoc#findings-analysis-contracts[Module Structure § Findings &
Code-Analysis Contracts].

== Scope and Registry Key
_Requirements: link:{docs}/Requirements.adoc#PM-IMPL-1[PM-IMPL-1]_

`FindingScope(kind, commitSha, prNumber)` is built through `FindingScope.commit(sha)` or
`FindingScope.pullRequest(sha, number)`. The commit is 40 or 64 lower-case hexadecimal digits; the number is set for a
pull request only and is at least 1. The same type is the scope of `FindingSource.fetch` and the target of
`CodeAnalysisProvider.status` and `issues`, so one value describes what is asked about across both packages.

`FindingSourceKey(kind, provider)` is built through `FindingSourceKey.of(kind)` or
`FindingSourceKey.analysis(providerId)`. `kind` is a `FindingSourceKind`, the closed `source` vocabulary of the findings
store; `provider` is set for `analysis` only and matches the provider-id pattern, which
`FindingSourceKey.isProviderId(value)` checks and which the analysis result, the finding and the analysis registry
share. The key mirrors the store's invariant (`provider` iff `source` is `analysis`): a finding is fetched and answered
under the key it is stored under, and two code analysis providers are two keys.

== Implementing a Provider
_Requirements: link:{docs}/Requirements.adoc#PM-IMPL-1[PM-IMPL-1]_

* *A source of findings* implements `FindingSource`: `key()` returns its `FindingSourceKey`, and `fetch(scope)` returns
  the normalized findings of the scope in the provider's order. Every finding it returns carries the key's `source`
  and, for `analysis`, the key's `provider`.
* *An answer to findings* implements `FindingResponder` under the same key as the source whose findings it answers:
  `respond(finding, disposition, reason)`.
* *A code analysis provider* implements `CodeAnalysisProvider` of `core.analysis` and, where it files its issues in the
  ledger, a `FindingSource` under `FindingSourceKey.analysis(id)` as well
  (link:core-analysis.adoc[`core.analysis`]).

The registries take their members in the constructor: `new FindingRegistry(sources, responders)`. Nothing is
discovered on the classpath; the assembly produces the registry from the provider modules it wires. Both registries are
immutable. A second member under the same key (sources and responders each) and a provider id outside the pattern are
refused with `IllegalArgumentException`. `source(key)` and `responder(key)` answer `Optional`; an unregistered key is
empty, which is not an outcome of an operation.

== Invariants and Failure Modes

* *Register under the store's key, not under a provider name.* A source is found by the `source` value the store
  records and, for `analysis`, by the provider id. A key of its own (a provider name, a review-bot name) would fetch
  findings under one key and store them under another.
* *Nothing in `pm-core` names a provider.* No class of `pm-core` depends on a provider package, and no class, package or
  member name contains a forge or analysis-service name, ignoring case. The single exemption is the constants
  `GITHUB_PR` and `GITLAB_MR` of `FindingSourceKind`, whose names are fixed by the store's closed `source` vocabulary.
* *The package stays declarations, serialization and validation.* No class here depends on an HTTP client, a
  `java.nio.file.Files` writing method, `FileOutputStream`, `FileWriter`, `RandomAccessFile` or `FileChannel`, or on a
  `core.store` class.
* *The wire vocabulary has one source.* A caller tells a value apart by its constant, never by a string it wrote
  itself; the schema parity test proves that the enums equal the schema's `enum` members.

Both boundary rules are ArchUnit rules over the main classes of `pm-core`, and each is applied to control fixtures on
which it must fail, so a rule that matches nothing is noticed.

== Adding a Source or an Answer

. Implement `FindingSource`, `FindingResponder` or both in the provider module, and return the provider's key from
  `key()`.
. Make every returned finding carry the key's `source` and, for `analysis`, the key's `provider`.
. Register the instance in the registry the assembly builds, together with the provider's other contracts.
. Add a fixture implementation and its registration case to the registry test; a duplicate key is refused, an
  unregistered key is empty and another provider's key is empty.

== Pitfalls

* *A copied enumeration is wrong after the next schema change.* Link the enum constant; only the schema parity test
  compares the two, and it does so over the whole record.
* *A finding without its provider is unanswerable.* The store's invariant is `provider` iff `source` is `analysis`;
  a finding of an analysis without a provider cannot be routed back to the provider that reported it.
* *An empty lookup is not a refusal.* `source(key)` returning empty means the runtime has no such provider; it is not a
  failed fetch and must not be reported as one.
