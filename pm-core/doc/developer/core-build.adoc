== Purpose

_Requirements:_ link:{docs}/Requirements.adoc#PM-IMPL-6[PM-IMPL-6], link:{docs}/Requirements.adoc#PM-TEST-2[PM-TEST-2]

Package `de.planmarshall.core.build` of `pm-core` holds the native parsers of build output: a parser reads the text one
build tool wrote and returns the diagnostics the tool reported, the status it printed, the test counts it aggregated and
the verdict on whether it ran a test at all. No external script is called and no Python runs (PM-IMPL-6).

Nine parsers are implemented: Maven, Gradle and the OpenRewrite finding log of a Maven build, plus the six JavaScript
and Python tools — npm errors, TypeScript, ESLint, Jest, TAP and the pyproject log of pytest, ruff and mypy. Each is
ported from the `plan-marshall` parser module of the same tool, and its tests are ported from that module's pytest suite.

A parser is a pure function of the log text. It reads no file except through `BuildLogText.read`, holds no state, opens no
process and consults no configuration.

== Main Types

|link:{src}/Diagnostic.java[`Diagnostic`]

== The Result Model

_Requirements:_ link:{spec}/job-runtime/03-parsers-and-gates.adoc#_native_build_output_parsers[Job Runtime Specification § Native Build Output Parsers]

The model separates facts a consumer must not conflate (link:../adr/core-build/001-the-parsed-build-keeps-five-facts-apart.adoc[ADR 001]):

* `status` is what the tool printed. A `testFailureIgnore` run that printed `BUILD SUCCESS` over two errored tests is
  `SUCCESS` with `failed = 2`; the parser does not resolve the contradiction, the gate does.
* `successMarker` records that the positive banner was seen, so the contradiction stays readable after the status is
  consumed.
* `testCounts` distinguishes three states: absent (`null`, the log carried no count line), `Unmeasured` (counts the parser
  could not aggregate) and `Measured`. Nothing reports a zero in place of an absence (the aggregation defect the
  implementation watch recorded as PM-WATCH-JOB-10, closed by this package and deleted from the watch document).
* `noTestsRan` holds only on a successful build with its success marker, its own positive "no tests" marker and no count
  line. A measured count of zero never produces it.

`TestCounts.Measured` refuses a total that is not `passed + failed + skipped`, and `ParsedBuild` refuses a `noTestsRan`
verdict its other facts do not support; both are enforced in the compact constructor, so a builder cannot produce an
inconsistent result.

== The Parsers

=== Maven

`MavenOutputParser.parse(String)` scans the `[ERROR]` and `[WARNING]` lines, strips the level prefix and files what is
left as a diagnostic:

* a line of Maven's failure epilogue — the `-e`/`-X` advice, the `[Help N]` URLs, the report and dump-file pointers, the
  reactor rows Maven 4 prints at error level, and the `BUILD FAILURE` banner — is dropped whole, each line matched
  against a compiled pattern with a full match;
* a `Tests run:` line with zero failures and zero errors is not a diagnostic;
* a line starting with `->` is a continuation and is skipped;
* the location is taken from the line, the category from the compiled table, and the diagnostic is deduplicated by
  category, file, line and the first 100 characters of the message, so the reactor summary and the per-module output of
  one error produce one diagnostic;
* the last contiguous stack-trace block of the log is attached to the last filed diagnostic, as in the original.

The test counts sum every Surefire and Failsafe summary block. A `Tests run:` line carrying `Time elapsed` repeats a
block's counts and is excluded; a line inside a test-plugin execution, after the `[INFO] Results:` marker, is a summary
block and is summed across modules and plugins; any other line is ambiguous, and one ambiguous line makes the population
`Unmeasured`. Each summary block is attributed to the runner of the nearest preceding execution header, and `byRunner`
carries the executed count (total minus skipped) per runner; an execution header of another plugin resets the attribution,
so an interleaved build under-counts — which is why a log with the `MultiThreadedBuilder` banner keeps the summed total and
omits `byRunner`.

=== Gradle

`GradleOutputParser.parse(String)` skips the stack frames, the continuation lines (`->`, `>`) and every line whose text
matches no category, derives the severity from the category (compilation, test and dependency are errors, everything else
is a warning) and takes the location from `<path>.<ext>:<line>[:<col>]`. The counts sum every
`N tests completed, M failed[, K skipped]` line. Because a successful Gradle build prints no count line at all, the
absence of a count is never a verdict: `noTestsRan` needs Gradle's own statement that its filter matched no test.

=== The OpenRewrite Log

`OpenRewriteLogParser.parse(String, boolean domainActive)` reads the structured `WARN` lines `cui-open-rewrite` `#118`
emits, one recipe finding per line, and classifies each by its identifier (`CUI_REWRITE-100` newly detected,
`CUI_REWRITE-101` pre-existing), never by the human verb of the message. The domain state is an argument, so the parse
stays a pure function of its inputs.

The verdicts are fail-closed and checked in this order: `not_observed` when the log carries no `rewrite:run` goal
execution; `domain_inactive` when the domain is not active; `parse_error` when a line carries a finding identifier but no
longer matches the pinned template; `observed` otherwise, carrying the findings. Only `observed` carries findings.

=== The Six JavaScript and Python Parsers

The six tools share the result model and the counts rules of the JVM parsers, and each is a scanner over the lines the
tool prints. None of them prints a positive success banner, so `successMarker` is `false` for the npm tools and for
pyproject except where a pytest summary reports a passed count.

* *npm errors* — every `npm ERR! code` line opens a block. `ERESOLVE` is `NPM_DEPENDENCY`, and its
  `Could not resolve dependency:` trailer names the peer dependency and its origin when the trailer carries them; `E404`
  is `NPM_ERROR` and names the quoted package specification it could not find; every other code is `NPM_ERROR` with the
  block's first reportable line, which is the code line itself. Both named forms point into `package.json` without a line.
* *TypeScript* — the two `tsc` diagnostic forms, each a `COMPILATION_ERROR` carrying file, line, column and
  `TSnnnn: message`. Both forms are scanned over every line, so a log that mixes them keeps all of its diagnostics.
* *ESLint* — a file-header line sets the file and each `line:col severity message rule` row below it is a `LINT_ERROR`
  whose message is the rule prefixed to the text. The problem summary is parsed beside the rows into
  `EslintResult.problems()`: it counts every problem the formatter reported, including a row the scanner cannot place,
  which is why the two counts legitimately disagree. The status is `FAILURE` only when a filed row has error severity.
* *Jest* — a `FAIL` header names the file, a `●` marker opens a test block, and the block closes at the first blank line
  after a stack frame. Each closed block is a `TEST_FAILURE` carrying the suite, the first stack frame's line and the
  collected frames. The `Tests:` summary blocks supply the counts.
* *TAP* — each `not ok N - <name>` line is a `TEST_FAILURE`; the YAML block that follows supplies `error`, `location` and
  `stack`, and without a block the test's own name is the message. The `# tests` / `# pass` / `# fail` / `# skipped`
  block supplies the counts.
* *pyproject* — the log is scanned for mypy (`path:line: error: message`, including a `.pyi` stub path and a
  `path:line:column:` run), ruff (`path:line:column: CODE message`) and pytest (`FAILED` and collection/setup `ERROR`
  short-summary lines), each tool independently, and the diagnostics are combined in that order — a multi-tool log is
  grouped by tool, not sorted by line. A pytest failure or error resolves its `FAILURES` or `ERRORS` block by the node id
  the summary line names, takes the deepest `path.py:NN` frame of the block's traceback as its location (ignoring
  captured-output sections), and — for a collection error whose summary line carries no message tail — the exception line
  of the block's `E` gutter. A trailing `@<group>` of a pytest-xdist node id is stripped before the block is looked up, and
  a node id that carries a space or the ` - ` delimiter is split outside its parameter brackets.

=== Counts of the Six

Every summary block contributes to the counts: Jest sums every `Tests:` block, TAP every `# tests` block and pytest
every summary line, so a log that concatenates several runs (one per package, or one per matrix entry) reports the sum
rather than the first or last block. A block whose total is not the sum of its parts — `Tests: 7 total` with no parts, a
`# tests 5` with two passing tests — is `Unmeasured`, never a set of figures that disagree with itself. A measured zero
stays a measured zero: no tool of the six prints a positive "no tests" marker, so `noTestsRan` is `false` throughout, and
a filter that matched nothing reports either pytest's own `no tests ran` line (no count at all) or TAP's
`# tests 0` (a measured zero).

== Adding a Parser

1. Add the parser class: a static-only class (`@UtilityClass`) with `parse(String)` and `parse(Path)`, returning
   `ParsedBuild` (or a typed result for a parser whose verdict is not a build status). Read the log through
   `BuildLogText.read`, take the location through `JvmFileLocation.parse` where the tool prints a JVM location, and — where
   the message text decides the category — put the patterns in a compiled table rather than in the parser.
2. Write the pytest-case roster and the fixtures: `{data}/<tool>/original-cases.txt` lists every case of the original
   suite, mapped to the fixtures derived from it or excluded with a reason — several cases may map to one fixture, and one
   case may need several; one `*.txt` fixture per case group and one `deliberate:` fixture per deliberate change; the
   original's own log files copied beside them when a case uses one. See
   link:{data}/PROVENANCE.adoc[`ported/build/PROVENANCE.adoc`].
3. Add the test class: a `@ParameterizedTest` over the fixtures of the directory, the roster closure check and a fixture
   floor, and a record-invariant test for each new record.
4. Record a deliberate change in link:../adr/core-build/002-deliberate-changes-against-the-ported-parsers.adoc[ADR 002]
   and in the specification paragraph, or do not make one.

== Deliberate Changes

The port reproduces the originals' parsing and changes five JVM behaviours on purpose; each has a `deliberate:` fixture that
asserts the corrected behaviour (link:../adr/core-build/002-deliberate-changes-against-the-ported-parsers.adoc[ADR 002]).
The one a reader meets first is that an `[ERROR]` line no pattern recognises is `unrecognized` rather than a real
category; the others are that an unmeasured population carries no number, that `no_tests_ran` needs the tool's marker,
that the Gradle counts sum every block, and that an OpenRewrite format drift is a `parse_error`. The Maven failure-trailer
drop and the passing-count skip are *not* changes: the original does both.

The six JavaScript and Python parsers add their own changes
(link:../adr/core-build/003-the-six-remaining-parsers-and-their-deliberate-changes.adoc[ADR 003]), each with a
`deliberate:` fixture or a named unit test: one npm diagnostic per error block rather than only the first, both `tsc`
forms scanned, the ESLint problem summary reported, every summary block summed, a contradictory summary reported
`unmeasured`, the pytest location taken from the deepest traceback frame, a pytest-xdist `@<group>` suffix stripped, the
wider mypy forms (a `.pyi` path and a column-numbered line) read, a spaced pytest `FAILED` node id filed, an unread Jest
`Tests:` summary reported `unmeasured`, and a printed failure marker (a TAP `not ok` without a description, a Jest `Tests:`
failure count) turning the status red even when no diagnostic is filed.

== Ported Tests and Fixture Provenance

_Requirements:_ link:{spec}/store-schemas/13-leases-integrity-testing.adoc#ported-tests[Store Schemas Specification § Ported-Primitive Tests]

The tests follow the ported-primitive convention: the original and its pytest suite are read by hand at a pinned commit,
the test data are plain files derived from them and committed below `src/test/resources/ported/build/`, each fixture is
headed either `original: plan-marshall@<pin> <pytest path>::<case>` or `deliberate: <name>`, and nothing runs Python,
starts a `plan-marshall` script, reads the sibling checkout or compares a Java result with a Python result at test time.

[source,text]
----
src/test/resources/ported/build/
  PROVENANCE.adoc          the pinned commit and where each directory's originals live
  <tool>/original-cases.txt  roster: every pytest case -> its fixtures, or excluded with a reason
  <tool>/*.txt               one scenario per fixture (headers, log, expectations)
  <tool>/*.log               the original's own log fixtures, copied byte for byte
----

The fixtures are enumerated from their directory, never listed by hand; `BuildLogFixtures` refuses a malformed fixture
(unknown header, another pin, an undeclared directive, a wrong arity, an unreadable `log-file`) naming the file and the
line, so a broken scenario fails the suite instead of being skipped. A test that leaves a directive of its fixture
unevaluated fails through `BuildLogFixtures.assertConsumed`. The roster is closed in both directions by
`BuildLogFixtures.assertRoster`.

The pinned commit is `BuildLogFixtures.PIN`; it is advanced by re-reading the original at the new commit and moving every
`original:` header and every `suite:` line with it, because the loader refuses any other commit.

== The Unparsed Evidence

_Requirement:_ link:{req}/06-execution.adoc#PM-EXEC-6[PM-EXEC-6]

`UnparsedEvidence` is the evidence a build job hands on when it ended `failed_unparsed` (Job Runtime § Unparseable Output Fallback): the bounded, redacted tail of the raw log and the resource URI of the full log. `UnparsedEvidence.of(planId, jobId, rawLog)` keeps the tail of the last `MAX_LINES` (50) lines, redacts every secret-shaped value through `SecretRedactor`, and keeps at most `MAX_BYTES` (4096) bytes of UTF-8 counted from the end, so the byte bound can cut the earliest retained line; the URI is `pm://plan/{plan_id}/builds/{job_id}/log`. The record has no diagnostic component by design: a failure handler gets the log's own words, never a compiler error the parser did not locate. The full log stays `<job_id>.log` beside the job record, which the URI names.

== Invariants and Failure Modes

* *A parser never guesses a count.* No summary block, an unaggregatable block or a quiet log never yields a zero.
* *A parser never invents a diagnostic.* A trailer line, a passing test count, a stack frame and a continuation line are
  not diagnostics; an unrecognised error is `unrecognized`, which says what it is.
* *A verdict is not a default.* `noTestsRan` is false unless the tool said so; `null` counts are not "zero tests".
* *The model is immutable.* The diagnostics list and the per-runner map are frozen in the compact constructor.
* *No state crosses a parse.* Two calls with the same text return equal results; nothing is cached.
