== Purpose

_Requirements:_ link:{docs}/Requirements.adoc#PM-IMPL-6[PM-IMPL-6], link:{docs}/Requirements.adoc#PM-TEST-2[PM-TEST-2]

Package `de.planmarshall.core.build` of `pm-core` holds the native parsers of build output: a parser reads the text one
build tool wrote and returns the diagnostics the tool reported, the status it printed, the test counts it aggregated and
the verdict on whether it ran a test at all. No external script is called and no Python runs (PM-IMPL-6).

Nine parsers are implemented: Maven, Gradle and the OpenRewrite finding log of a Maven build, plus the six JavaScript
and Python tools — npm errors, TypeScript, ESLint, Jest, TAP and the pyproject log of pytest, ruff and mypy. Each is
ported from the `plan-marshall` parser module of the same tool, and its tests are ported from that module's pytest suite.

The package also carries the four native coverage report parsers — JaCoCo, Cobertura, LCOV and Istanbul — which read a
coverage artifact and answer the threshold question. They are ported from `plan-marshall`'s format-agnostic
`script-shared/scripts/build/_coverage_parse.py` and follow its rules, with the model and the XML hardening recorded in
link:../adr/core-build/005-the-coverage-model-and-the-xml-hardening.adoc[ADR `core-build/005`].

A parser is a pure function of the log text. It reads no file except through `BuildLogText.read`, holds no state, opens no
process and consults no configuration. A coverage parser is a pure function of the report text in the same way: it reads
no file except through its own `parse(Path)` overload, and it returns either the report or a refusal.

Neither the read nor a pattern runs unbounded for any of the nine parsers: the read takes the log's tail above a data
cap, and every line is cut at a data bound before a pattern sees it
(<<_the_bounds_of_a_read_and_of_a_parse>>).

== The Result Model

_Requirements:_ link:{spec}/job-runtime/03-parsers-and-gates.adoc#_native_build_output_parsers[Job Runtime Specification § Native Build Output Parsers]

The model separates facts a consumer must not conflate (link:../adr/core-build/001-the-parsed-build-keeps-five-facts-apart.adoc[ADR 001]):

* `status` is what the tool printed. A `testFailureIgnore` run that printed `BUILD SUCCESS` over two errored tests is
  `SUCCESS` with `failed = 2`; the parser does not resolve the contradiction, the gate does.
* `successMarker` records that the positive success marker was seen — the tool's banner or the passing summary it printed —
  so the contradiction stays readable after the status is consumed.
* `testCounts` distinguishes three states: absent (`null`, the log carried no count line), `Unmeasured` (counts the parser
  could not aggregate) and `Measured`. Nothing reports a zero in place of an absence (the aggregation defect the
  implementation watch recorded as PM-WATCH-JOB-10, closed by this package and deleted from the watch document).
* `noTestsRan` holds only on a successful build with its success marker, its own positive "no tests" marker and no count
  line. A measured count of zero never produces it.

`TestCounts.Measured` refuses a total that is not `passed + failed + skipped`, and `ParsedBuild` refuses a `noTestsRan`
verdict its other facts do not support; both are enforced in the compact constructor, so a builder cannot produce an
inconsistent result.

== The Parsers

=== Maven

`MavenOutputParser.parse(String)` scans the `[ERROR]` and `[WARNING]` lines, strips the level prefix and files what is
left as a diagnostic:

* a line of Maven's failure epilogue — the `-e`/`-X` advice, the `[Help N]` URLs, the report and dump-file pointers, the
  reactor rows Maven 4 prints at error level, and the `BUILD FAILURE` banner — is dropped whole, each line matched
  against a compiled pattern with a full match;
* a `Tests run:` line with zero failures and zero errors is not a diagnostic;
* a line starting with `->` is a continuation and is skipped;
* the location is taken from the line, the category from the compiled table, and the diagnostic is deduplicated by
  category, file, line and the first 100 characters of the message, so the reactor summary and the per-module output of
  one error produce one diagnostic;
* the last contiguous stack-trace block of the log is attached to the last filed diagnostic, as in the original.

The test counts sum every Surefire and Failsafe summary block. A `Tests run:` line carrying `Time elapsed` repeats a
block's counts and is excluded; a line inside a test-plugin execution, after the `[INFO] Results:` marker, is a summary
block and is summed across modules and plugins; any other line is ambiguous, and one ambiguous line makes the population
`Unmeasured`. Each summary block is attributed to the runner of the nearest preceding execution header, and `byRunner`
carries the executed count (total minus skipped) per runner; an execution header of another plugin resets the attribution,
so an interleaved build under-counts — which is why a log with the `MultiThreadedBuilder` banner keeps the summed total and
omits `byRunner`.

=== Gradle

`GradleOutputParser.parse(String)` skips the stack frames, the continuation lines (`->`, `>`) and every line whose text
matches no category, derives the severity from the category (compilation, test and dependency are errors, everything else
is a warning) and takes the location from `<path>.<ext>:<line>[:<col>]`. The counts sum every
`N tests completed, M failed[, K skipped]` line. Because a successful Gradle build prints no count line at all, the
absence of a count is never a verdict: `noTestsRan` needs Gradle's own statement that its filter matched no test.

=== The OpenRewrite Log

`OpenRewriteLogParser.parse(String, boolean domainActive)` reads the structured `WARN` lines `cui-open-rewrite` `#118`
emits, one recipe finding per line, and classifies each by its identifier (`CUI_REWRITE-100` newly detected,
`CUI_REWRITE-101` pre-existing), never by the human verb of the message. The domain state is an argument, so the parse
stays a pure function of its inputs.

The verdicts are fail-closed and checked in this order: `not_observed` when the log carries no `rewrite:run` goal
execution; `domain_inactive` when the domain is not active; `parse_error` when a line carries a finding identifier but no
longer matches the pinned template; `observed` otherwise, carrying the findings. Only `observed` carries findings.

=== The Six JavaScript and Python Parsers

The six tools share the result model and the counts rules of the JVM parsers, and each is a scanner over the lines the
tool prints. The marker is the passing summary the tool itself prints: Jest's `Tests:` summary and TAP's `# tests` / `# pass`
/ `# fail` block are the marker when they report at least one passed test and no failed test, and the install family's
completion line (`added 150 packages in 10s`, `up to date, audited 5 packages`) is the marker of a clean install. A clean
`tsc` or ESLint run prints nothing at all, so `successMarker` stays `false` there and a zero exit stays `indeterminate`; a
pytest summary that reports a passed count is the marker of the pyproject parser. ADR
link:../../../pm-runtime/doc/adr/runtime-job/016-the-npm-passing-summary-is-the-success-marker.adoc[`runtime-job/016`] records the decision.

* *npm errors* — every `npm ERR! code` line (npm up to 11) or `npm error code` line (npm 12 on) opens a block. `ERESOLVE` is `NPM_DEPENDENCY`, and its
  `Could not resolve dependency:` trailer names the peer dependency and its origin when the trailer carries them; `E404`
  is `NPM_ERROR` and names the quoted package specification it could not find; every other code is `NPM_ERROR` with the
  block's first reportable line, which is the code line itself. Both named forms point into `package.json` without a line.
  A log with no error block whose install completion line reads `added|removed|changed N packages` or
  `up to date, audited N packages` is a clean install: it files no diagnostic and sets the success marker; the runtime
  adapter admits that marker only for a job whose verb is `install` or `clean-install`
  (link:../../../pm-runtime/doc/adr/runtime-job/018-the-install-marker-needs-an-install-verb.adoc[ADR `runtime-job/018`]).
  Every message of the parser — the generic block's, the `ERESOLVE` and the `E404` one — is redacted through
  `SecretRedactor` before it is cut to the stored length, so a truncated message cannot keep half a secret. The
  `ERESOLVE` and `E404` messages are not built from dependency names alone: the quoted specifier and the peer and `from`
  tokens are log text and can carry a registry URL with user information.
* *TypeScript* — the two `tsc` diagnostic forms, each a `COMPILATION_ERROR` carrying file, line, column and
  `TSnnnn: message`. Both forms are scanned over every line, so a log that mixes them keeps all of its diagnostics.
* *ESLint* — a file-header line sets the file and each `line:col severity message rule` row below it is a `LINT_ERROR`
  whose message is the rule prefixed to the text. The problem summary is parsed beside the rows into
  `EslintResult.problems()`: it counts every problem the formatter reported, including a row the scanner cannot place,
  which is why the two counts legitimately disagree. The status is `FAILURE` only when a filed row has error severity.
* *Jest* — a `FAIL` header names the file, a `●` marker opens a test block, and the block closes at the first blank line
  after a stack frame. Each closed block is a `TEST_FAILURE` carrying the suite, the first stack frame's line and the
  collected frames. The `Tests:` summary blocks supply the counts.
* *TAP* — each `not ok N - <name>` line is a `TEST_FAILURE`; the YAML block that follows supplies `error`, `location` and
  `stack`, and without a block the test's own name is the message. The `# tests` / `# pass` / `# fail` / `# skipped`
  block supplies the counts. The plan is checked per run: a run starts at every line that starts with `TAP version`, and
  the lines before the first such line, or the whole log when it carries none, are one run. A run's top-level plan
  lines `1..N` (their counts summed) are compared with that run's own number of top-level test points (`ok` / `not ok`
  at the start of a line): when they differ, the run did not finish the plan it announced — the evidence class of
  `Bail out!` — and the passing summary is no marker, even with exit 0. The log finished its plan only when every run
  did, so in a log of concatenated runs (`npm test --workspaces`) a later run cannot supply the point an earlier run is
  missing; the counts stay as the summary measured them, summed over all runs. The plan is compared with the test points and not with the
  `# tests` total, because `node --test` plans one top-level point per suite and counts the tests inside the suites
  (the original's real log `npm-tap-test-real.log` of the fixture `npm-tap-success` prints `1..4` beside `# tests 5`). An indented (subtest) plan line or test point
  is not read, and a run without a top-level plan line announced no plan, so it finished it.
* *pyproject* — the log is scanned for mypy (`path:line: error: message`, including a `.pyi` stub path and a
  `path:line:column:` run), ruff (`path:line:column: CODE message`) and pytest (`FAILED` and collection/setup `ERROR`
  short-summary lines), each tool independently, and the diagnostics are combined in that order — a multi-tool log is
  grouped by tool, not sorted by line. A pytest failure or error resolves its `FAILURES` or `ERRORS` block by the node id
  the summary line names, takes the deepest `path.py:NN` frame of the block's traceback as its location (ignoring
  captured-output sections), and — for a collection error whose summary line carries no message tail — the exception line
  of the block's `E` gutter. A trailing `@<group>` of a pytest-xdist node id is stripped before the block is looked up, and
  a node id that carries a space or the ` - ` delimiter is split outside its parameter brackets.

=== Counts of the Six

Every summary block contributes to the counts: Jest sums every `Tests:` block, TAP every `# tests` block and pytest
every summary line, so a log that concatenates several runs (one per package, or one per matrix entry) reports the sum
rather than the first or last block. A block whose total is not the sum of its parts — `Tests: 7 total` with no parts, a
`# tests 5` with two passing tests — is `Unmeasured`, never a set of figures that disagree with itself. A measured zero
stays a measured zero: no tool of the six prints a positive "no tests" marker, so `noTestsRan` is `false` throughout, and
a filter that matched nothing reports either pytest's own `no tests ran` line (no count at all) or TAP's
`# tests 0` (a measured zero).

== The Coverage Reports

_Requirements:_ link:{docs}/Requirements.adoc#PM-EXEC-6[PM-EXEC-6], link:{docs}/Requirements.adoc#PM-TEST-2[PM-TEST-2]

The four coverage parsers share one model and one hardening, and each reads one format's artifact. They are pure
functions of the report text and return `CoverageParseResult`: a `Parsed` report or a `Refused` value that names the
format and the reason. A report that cannot be read is never a report of zeros.

=== The model and the verdict

`CoverageReport` carries the `CoverageFormat`, the `CoverageMetrics` of the overall percentages and the `CoverageItem`
list. `CoverageMetrics` keeps an absent metric `null`, so a format that carries no branch or statement counter is
distinguishable from a measured zero; only the line percentage is required. `CoverageItem` carries the name (a class or
a file), the optional source file, the line and branch percentages and the `missedMethods` detail.

`CoverageReport.evaluate(threshold)` decides the verdict from the **overall line percentage only** and builds the
low-coverage list from **each item's line percentage only** (`>=` passes). A branch, instruction, function or statement
percentage never changes either: a report whose branch coverage is below the threshold passes when its line coverage is
above it, and a high branch percentage does not rescue a low line.

The percentages compared are the ones the parser stored, already rounded to two decimals, so the rounding happens before
the comparison: a line coverage of 79.996 % is stored as `80.0` and passes a threshold of 80 (`CoverageReportTest` pins
the boundary).

=== A zero denominator is absent

A counter whose denominator is zero measured nothing, so it has no percentage: `CoveragePercentages.percentage` returns
an empty `Optional` for a zero total, and no parser writes `0.0` for it. Where a format reports a line counter per item,
an item whose line counter is `0/0` is no item (a Cobertura class carries no counter of its own, so Cobertura decides at
the root, where a `lines-valid` of `0` refuses the report); a branch, function or instruction counter of `0/0` leaves
that metric `null`, and a report whose overall line counter is `0/0` is refused with the reason `no lines measured`. A rate is read as text through
`BigDecimal` and checked to `0..1`, so `NaN`, `Infinity` and the hexadecimal floating-point forms are refused rather
than read.

=== JaCoCo

`JacocoReportParser.parse` walks the report once through `CoverageXmlReader` and takes the `INSTRUCTION`, `BRANCH`,
`LINE` and `METHOD` counters of the report element as the overall percentages, each `covered / (missed + covered)`; a
counter the report does not carry, or one of `0/0`, leaves its metric `null`, and a report without a `LINE` counter, or
with an overall `LINE` counter of `0/0`, is refused. A class without a `LINE` counter, or with one of `0/0`, is left out
of the measured items. Per class it takes the `LINE` counter (and the `BRANCH` counter where present, `null` at `0/0`);
each method whose `METHOD` counter has a missed part contributes its name to `missedMethods`, and `<init>` and `<clinit>`
are excluded because they are not methods a test is expected to call. The class name is dotted (`com/example/A` becomes
`com.example.A`). A counter type that appears twice at the report root, or twice directly within one class, is refused,
naming the repeated type, so a later counter can never override an earlier one.

=== Cobertura

`CoberturaReportParser.parse` takes the root `line-rate` and `branch-rate` as the overall percentages — a missing root
`line-rate` is a refusal and a missing `branch-rate` leaves the branch metric `null` — and each class's `line-rate` as
an item, naming its `filename`. A method whose `line-rate` is zero contributes its name to `missedMethods`. A rate that
is not a plain decimal number within `0..1` is refused.

Cobertura's `class` elements carry no `lines-valid` or `branches-valid`, so the zero rule is decided at the root. A root
`lines-valid="0"` refuses the report (`no lines measured`). A root `branches-valid` of `0`, or none, measured no branch,
so the overall branch metric and the branch rate of every class are `null`; under a root that measured branches, a
`branch-rate="0"` is a measured `0.0`.

=== LCOV

`LcovReportParser.parse` reads the line-oriented records from `SF:` to `end_of_record` and sums every record into the
overall percentages: `line` from `LH/LF`, `branch` from `BRH/BRF`, `function` from `FNH/FNF`, and `statement` equals
`line` because LCOV has no statement counter. A metric no record carries is `null`, not a zero, and so is a `BRF:0` or
`FNF:0`. Each record is an item, except a record with `LF:0`, and a report whose summed `LF` is `0` is refused. A `DA:`
record is per-line detail and never enters a percentage. A record that is not terminated, or carries no `LF/LH`
counter, is a truncation and is refused, as is a covered count above its total. A record that carries one of the
counter lines `LF`, `LH`, `BRF`, `BRH`, `FNF` or `FNH` twice is refused, naming the repeated line type, so a later `LH`
can never turn a record with no line hit into a fully covered one. The report is read line by line, never
split whole, and a line longer than the line limit of <<_the_bounded_read_of_a_report>> is refused, naming the limit.

=== Istanbul

`IstanbulSummaryParser.parse` streams the document with Jackson rather than binding it to a tree. The `total` object
supplies the `pct` of `lines`, `statements`, `functions` and `branches`; every other top-level object is one file item,
with `lines.pct` as its line percentage and `branches.pct` as its branch percentage. Each metric's `total` is read
beside its `pct`: a `total` of `0` leaves the metric absent whatever the `pct` says, a file whose `lines.total` is `0`
is no item, and a summary whose `total.lines.total` is `0` is refused. A metric object without a `total` is refused,
naming the metric (`total.lines.total is absent`), so a metric is never read from its `pct` alone. A truncated document,
a metric without a numeric `pct`, a document without `total` and a key that appears twice in one object (Jackson's
`STRICT_DUPLICATE_DETECTION`, so a later `total` can never override an earlier one) are refused.

=== The XML hardening

Both XML parsers read their report as untrusted input through `CoverageXmlReader`, and the parser itself is the defence:
there is no text scan before it. The factory turns DTD support off, turns external entities off, keeps entity
references from being replaced, and resolves every external reference to an empty stream, so a DTD or entity that tries
to reach a file or a URL reads nothing. With DTD support off the JDK reader still parses JaCoCo's own `DOCTYPE` with a
system identifier, so the declaration is tolerated and never resolved or fetched. The walk refuses an `ENTITY_REFERENCE`
event, so an entity reference in element content is refused, never expanded. An undeclared entity reference in an
attribute value raises no such event: the reader drops it from the value, so it is never expanded and never resolved either, and the
report is read without it. As defence in depth, the factory also sets `XMLConstants.ACCESS_EXTERNAL_DTD` and
`ACCESS_EXTERNAL_SCHEMA` to `""` — no protocol allowed for an external DTD or schema — where the implementation accepts
the two properties; an implementation that refuses one with an `IllegalArgumentException` keeps the other properties
in force. The JDK's built-in StAX implementation is the supported one, and it accepts both. The decisions, with the
measured behaviour of the JDK reader, are recorded in
link:../adr/core-build/008-the-coverage-parsers-read-with-dtd-off-and-bounded.adoc[ADR `core-build/008`], which
supersedes the hardening part of
link:../adr/core-build/005-the-coverage-model-and-the-xml-hardening.adoc[ADR `core-build/005`], and the two access
properties in
link:../adr/core-build/009-the-redactor-shapes-the-diagnostic-redaction-and-the-input-bounds.adoc[ADR `core-build/009`].
The hostile prologs are probed by `CoverageXmlHardeningTest` through a resolver that counts its calls, and the same test
asserts that the factory the reader builds carries both access properties as `""`.

=== The bounded read of a report

_Requirements:_ link:{docs}/Requirements.adoc#PM-ARCH-8[PM-ARCH-8], link:{docs}/Requirements.adoc#PM-IMPL-5[PM-IMPL-5]

A coverage report is read as a stream, never whole: the `parse(Path)` overloads open the file through
`CoverageReportStream`, a counting stream that refuses the read once more than the cap of the module's coverage limits
resource has been read, naming the cap. The XML parsers hand that stream to `CoverageXmlReader.parse(InputStream)`, which
honours the document's own encoding declaration and byte-order mark; LCOV reads it as UTF-8 through a `BufferedReader`,
and Istanbul through Jackson.

include::../../src/main/resources/de/planmarshall/core/build/coverage-limits.properties[tag=coverage-max-bytes]

An LCOV line longer than the line limit of the same resource is refused before it is read whole:

include::../../src/main/resources/de/planmarshall/core/build/coverage-limits.properties[tag=coverage-max-line-length]

Both values are data, read with `LimitProperties` when `CoverageReportStream` initialises; there is no literal in the code.
A limit that sizes an `int` quantity — the LCOV line limit here, the two limits of `BuildLogText` — is read through
`LimitProperties.readInt`, which refuses a value above `Integer.MAX_VALUE` with an `IllegalStateException` naming the
resource and the key, the same fault of the build as an absent or negative value, instead of failing the class's
initialisation with the bare exception of `Math.toIntExact`. The arithmetic on the limits cannot overflow either:
`CoverageReportStream` computes the room left before the cap without adding to a value near `Long.MAX_VALUE`, and LCOV
compares a line's length with its limit as a `long`. A report file that cannot be read is refused naming its file name
only (`CoverageRefusals`): a file-system failure carries the full path in its message, so its message is never passed
through.

A refusal echoes report content — a counter type, a counter value, an `SF:` name — and that echo is bounded at the one
seam every refusal passes, `CoverageRefusals.of`: the reason keeps the format prefix and at most the first 256
characters of the detail (`CoverageRefusals.MAX_DETAIL_LENGTH`), never splitting a surrogate pair. The echo sites of the
parsers stay as they are.

== The Bounds of a Read and of a Parse

_Requirements:_ link:{docs}/Requirements.adoc#PM-ARCH-8[PM-ARCH-8], link:{docs}/Requirements.adoc#PM-IMPL-5[PM-IMPL-5]

A build log is written by the operator's own build, but a dependency or a test can put any line in it, so neither the read
nor a pattern runs unbounded (link:../adr/core-build/007-the-read-and-the-patterns-are-bounded.adoc[ADR `core-build/007`]).

`BuildLogText.read` takes at most the cap of the module's limits resource, counted from the end of the file and from the
first line beginning inside it, so a log longer than the cap reaches a parser as its tail. The cut can leave a partial
ANSI escape at the head of the tail; `stripAnsi` does not match it and the fragment stays in the text, which no parser
pattern reads as a marker.

include::../../src/main/resources/de/planmarshall/core/build/build-limits.properties[tag=log-max-bytes]

All nine parsers cut every line at the per-line bound of the same resource before a pattern of theirs sees the text
(`BuildLogText.boundLines`), once at the entry both `parse` overloads share: `MavenOutputParser`,
`OpenRewriteLogParser` and `PyprojectOutputParser` since ADR `core-build/007`, and `GradleOutputParser`,
`NpmErrorParser`, `TypeScriptOutputParser`, `EslintOutputParser`, `JestOutputParser` and `TapOutputParser` since
link:../adr/core-build/009-the-redactor-shapes-the-diagnostic-redaction-and-the-input-bounds.adoc[ADR `core-build/009`].
The runtime's dispatcher `BuildOutputParser` cuts the stripped text the same way before its dispatch patterns, and its
multi-line markers start on horizontal space (`^[ \t]*`, as `NpmErrorParser.INSTALL_SUMMARY` does) rather than on
`^\s*`, so no repetition of theirs crosses a line end. One cut bounds every expression of a parser at once — a pattern
that backtracks over a line of repeated tokens included — and a line is cut at its head, because the marker a parser
reads is at a line's start. `BuildLogBoundsTest` feeds a million blank or whitespace lines and a hostile line of the
bound's length through the six parsers, and `BuildOutputParserTest` of `pm-runtime` does the same through the
dispatcher; each asserts the result of a fixed input, never a wall-clock run.

include::../../src/main/resources/de/planmarshall/core/build/build-limits.properties[tag=max-line-length]

Three patterns are rewritten on top of the cut, each held to the ported expression's result by a differential test over
generated lines (`BuildLogBoundsTest`): the Maven execution header and the OpenRewrite finding line are asked a
necessary-condition pre-test first (a header needs an `@`, a finding line needs both its identifier prefix and ` by `),
and the pytest summary line is answered in two steps — the earliest verdict word, then the `in <seconds>s` tail after it —
for every line without a line terminator, while a line that carries one is answered by the ported expression. A
pre-test bounds the shapes the analyses named; a line that carries the token it tests still backtracks inside the
expression, bounded by the line cut. The pytest exception and section patterns measured linear and are left as they are.
A test that bounds a pattern names its input length and its bound, and uses a preemptive timeout; it never compares two
wall-clock runs.

Both values are data: editing the properties resource changes the bound, and the class that names it reads the value when
it initialises. There is no literal in the code and no runtime override.

== Adding a Parser

1. Add the parser class: a static-only class (`@UtilityClass`) with `parse(String)` and `parse(Path)`, returning
   `ParsedBuild` (or a typed result for a parser whose verdict is not a build status). Read the log through
   `BuildLogText.read`, cut every line through `BuildLogText.boundLines` before a pattern sees the text
   (<<_the_bounds_of_a_read_and_of_a_parse>>), take the location through `JvmFileLocation.parse` where the tool prints a
   JVM location, and — where the message text decides the category — put the patterns in a compiled table rather than in
   the parser.
2. Write the pytest-case roster and the fixtures: `{data}/<tool>/original-cases.txt` lists every case of the original
   suite, mapped to the fixtures derived from it or excluded with a reason — several cases may map to one fixture, and one
   case may need several; one `*.txt` fixture per case group and one `deliberate:` fixture per deliberate change; the
   original's own log files copied beside them when a case uses one. See
   link:{data}/PROVENANCE.adoc[`ported/build/PROVENANCE.adoc`].
3. Add the test class: a `@ParameterizedTest` over the fixtures of the directory, the roster closure check and a fixture
   floor, and a record-invariant test for each new record.
4. Record a deliberate change in link:../adr/core-build/002-deliberate-changes-against-the-ported-parsers.adoc[ADR 002]
   and in the specification paragraph, or do not make one.

== Deliberate Changes

The port reproduces the originals' parsing and changes five JVM behaviours on purpose; each has a `deliberate:` fixture that
asserts the corrected behaviour (link:../adr/core-build/002-deliberate-changes-against-the-ported-parsers.adoc[ADR 002]).
The one a reader meets first is that an `[ERROR]` line no pattern recognises is `unrecognized` rather than a real
category; the others are that an unmeasured population carries no number, that `no_tests_ran` needs the tool's marker,
that the Gradle counts sum every block, and that an OpenRewrite format drift is a `parse_error`. The Maven failure-trailer
drop and the passing-count skip are *not* changes: the original does both.

The six JavaScript and Python parsers add their own changes
(link:../adr/core-build/003-the-six-remaining-parsers-and-their-deliberate-changes.adoc[ADR 003]), each with a
`deliberate:` fixture or a named unit test: one npm diagnostic per error block rather than only the first, both `tsc`
forms scanned, the ESLint problem summary reported, every summary block summed, a contradictory summary reported
`unmeasured`, the pytest location taken from the deepest traceback frame, a pytest-xdist `@<group>` suffix stripped, the
wider mypy forms (a `.pyi` path and a column-numbered line) read, a spaced pytest `FAILED` node id filed, an unread Jest
`Tests:` summary reported `unmeasured`, and a printed failure marker (a TAP `not ok` without a description, a Jest `Tests:`
failure count) turning the status red even when no diagnostic is filed.

== Ported Tests and Fixture Provenance

_Requirements:_ link:{spec}/store-schemas/13-leases-integrity-testing.adoc#ported-tests[Store Schemas Specification § Ported-Primitive Tests]

The tests follow the ported-primitive convention: the original and its pytest suite are read by hand at a pinned commit,
the test data are plain files derived from them and committed below `src/test/resources/ported/build/`, each fixture is
headed either `original: plan-marshall@<pin> <pytest path>::<case>` or `deliberate: <name>`, and nothing runs Python,
starts a `plan-marshall` script, reads the sibling checkout or compares a Java result with a Python result at test time.

[source,text]
----
src/test/resources/ported/build/
  PROVENANCE.adoc          the pinned commit and where each directory's originals live
  <tool>/original-cases.txt  roster: every pytest case -> its fixtures, or excluded with a reason
  <tool>/*.txt               one scenario per fixture (headers, log, expectations)
  <tool>/*.log               the original's own log fixtures, copied byte for byte
----

The fixtures are enumerated from their directory, never listed by hand; `BuildLogFixtures` refuses a malformed fixture
(unknown header, another pin, an undeclared directive, a wrong arity, an unreadable `log-file`) naming the file and the
line, so a broken scenario fails the suite instead of being skipped. A test that leaves a directive of its fixture
unevaluated fails through `BuildLogFixtures.assertConsumed`. The roster is closed in both directions by
`BuildLogFixtures.assertRoster`.

The pinned commit is `BuildLogFixtures.PIN`; it is advanced by re-reading the original at the new commit and moving every
`original:` header and every `suite:` line with it, because the loader refuses any other commit.

The coverage fixtures follow the same convention without the scenario grammar: they are plain report files below
`src/test/resources/ported/coverage/`, copied byte for byte from the original's own fixture directory at the full pin
recorded in link:{coverage-data}/PROVENANCE.adoc[`ported/coverage/PROVENANCE.adoc`], plus one `deliberate-` file per
behaviour the port decides on top of the original. A coverage parser test reads its fixture through the class path and
compares the figures with literals read out of the report by hand; no test runs Python.

== The Unparsed Evidence

_Requirement:_ link:{docs}/Requirements.adoc#PM-EXEC-6[PM-EXEC-6]

`UnparsedEvidence` is the evidence a build job hands on when it ended `failed_unparsed` (Job Runtime § Unparseable Output Fallback): the bounded, redacted tail of the raw log and the resource URI of the full log. `UnparsedEvidence.of(planId, jobId, rawLog)` strips the ANSI escapes through `BuildLogText.stripAnsi`, reduces each carriage-return frame run to its last frame in one character pass that lists no line, takes the tail of the last `MAX_LINES` (50) lines by scanning back for line beginnings, cuts every kept line to its last `BuildLogText.MAX_LINE_LENGTH` characters, redacts every secret-shaped value through `SecretRedactor`, and keeps at most `MAX_BYTES` (4096) bytes of UTF-8 counted from the end, so the byte bound can cut the earliest retained line. The line cut keeps a line's end, as the byte bound does, because the excerpt is a tail; it comes before the redaction because it is what bounds the redactor's cost on a long hostile line. The accepted residue of that order: a secret that straddles the line cut loses its label before the redactor sees it, so the rest of its value is unlabeled and the label-anchored shapes do not match it. It stays readable only where the byte bound keeps it, which takes a retained value of about 4096 characters or more; masking the retained text of a cut line instead would trade evidence for that case and is a maintainer decision. The URI is `pm://plan/{plan_id}/builds/{job_id}/log`. A million-line log costs the reduced text, never an entry per line. The record has no diagnostic component by design: a failure handler gets the log's own words, never a compiler error the parser did not locate. The full log stays `<job_id>.log` beside the job record, which the URI names.

== Invariants and Failure Modes

* *A parser never guesses a count.* No summary block, an unaggregatable block or a quiet log never yields a zero.
* *A parser never invents a diagnostic.* A trailer line, a passing test count, a stack frame and a continuation line are
  not diagnostics; an unrecognised error is `unrecognized`, which says what it is.
* *A verdict is not a default.* `noTestsRan` is false unless the tool said so; `null` counts are not "zero tests".
* *The model is immutable.* The diagnostics list and the per-runner map are frozen in the compact constructor.
* *No state crosses a parse.* Two calls with the same text return equal results; nothing is cached.
* *A refused report is not a report of zeros.* A coverage report that cannot be read is `CoverageParseResult.Refused`,
  which carries the format and the reason; there is no result in which a refusal has been turned into percentages.
* *The threshold reads the line only.* `CoverageReport.evaluate` compares the overall line percentage and each item's
  line percentage, and no other metric changes either.
* *A coverage document is untrusted.* The XML readers tolerate a `DOCTYPE` without resolving it, refuse an entity
  reference in element content and drop an undeclared one in an attribute value, never expanding or resolving either; a malformed or
  duplicate-keyed JSON summary is a refusal, not a zero; and a report is read within a byte cap.
* *A repeated counter is refused, never an override.* JaCoCo refuses a counter type repeated at the report root or within
  one class, LCOV a counter line repeated within one record, and Istanbul a key repeated within one object.
* *A counter that measured nothing is absent.* A `0/0` counter is never a measured `0.0`.
