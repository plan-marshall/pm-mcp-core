== Purpose
_Requirements: link:{docs}/Requirements.adoc#PM-WORK-1[PM-WORK-1],
link:{docs}/Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2]_

Package `de.planmarshall.core.role` of `pm-core` owns the *role*: one JSON artifact per role, the shipped, machine and
project sets it lives in, the effective configuration the role runs on, and the two digests that bind a worker
generation and a qualification record to it. No class of this package names a harness: a harness is its harness profile
(link:core-profile.adoc[`core.profile`]), and a role is the document an operator or the release supplies. The two roles
the specification fixes by name — the judge and the steward — appear only as the model caller's and the catalog's
named exemptions.

The package owns five things:

* the *artifact validator*, the closed schema of a role artifact including the members whose bounds are compiled
  (`off_track` thresholds, the form of a `zero_tool` role);
* the *set loader*, the whole-artifact precedence of the shipped, machine and project sets;
* the *effective configuration*, the six levels that supply the harness, model and effort of a role;
* the *two digests*, the configuration digest of a worker generation and the qualification digest of a record;
* *validation against the harness profile and the model catalogue*, the table of reasons that makes an invalid role
  undefined.

The stores the package reads — the machine and project `role-assignments.json`, the plan's `overrides.json`, the model
catalogues, the harness profiles, the enrolment, the skills and the machine configuration — arrive through one port,
link:{core-java}/de/planmarshall/core/role/RoleEnvironment.java[`RoleEnvironment`].
This package does not write them; the runtime never reads a role, a harness or a model from git-tracked configuration.

Specification: `model-work/01-roles-and-configuration.adoc`,
`harness-profiles/01-profile-schema.adoc#role-classes`,
`store-schemas/12-machine-stores.adoc#model-catalogue` and `#role-assignments-store`,
`workflow-dsl/09-plan-instance.adoc#plan-overrides`. The escalation assignment, the shipped role content and the
qualification text of `model-work/01` are not implemented by this package.

A role name validates through link:core-id.adoc[`RoleName` of `core.id`], the one definition of the grammar; the harness
member a role artifact names validates through `HarnessId` of the same package.

== The Three Sets

[cols="1,3,2"]
|===
|Set |Where |Notes

|Shipped
|`classpath:/roles/<name>.json`, supplied by the assembly
|Read by `ShippedRoles`; `default-assignment.json` and the `qualification/` subdirectory are not roles and are skipped.

|Machine
|`<PM_MCP_BASE>/roles/<name>.json`
|The operator, for every project of the machine; holds no qualification records.

|Project
|`<PM_MCP_BASE>/projects/<project_id>/roles/<name>.json`
|The operator, for one project; holds the records the operator makes under `qualification/`.
|===

An artifact replaces the artifact of the same name in a lower set *as a whole*; members are never merged. A higher set
adds a role the lower sets do not define. An artifact of a higher set that fails validation leaves the role *undefined*:
`RoleSetLoader` removes the lower artifact rather than falling back to it, because the specification says an invalid
role counts as undefined.

An edited artifact or a changed assignment applies at every composition, every task creation and every offer: the
loader reads the sets afresh at every call, and `RoleCatalog` creates the set per resolution rather than caching it. This
guide is where the rule is stated; `model-work/01` points here for it.

== The Effective Configuration

`RoleCatalog.resolve(role, planOverride)` takes the role's harness, model and effort from these levels, each later level
overriding only what it names:

[cols="1,4"]
|===
|Level |Source

|1 |The shipped artifact's own `harness`, `model`, `effort`, where it defines the role
|2 |The machine artifact's three members, where it defines the role (it replaces the shipped artifact as a whole)
|3 |The machine's `role-assignments.json`
|4 |The project artifact's three members, where it defines the role (it replaces the artifact of the lower sets as a
whole, so its members come after the machine assignment)
|5 |The project's `role-assignments.json`
|6 |The plan's `overrides.json` (`roles.<name>`)
|===

`RoleSetLoader` reports the set the effective artifact came from, so the catalog inserts the artifact's own members at
their level. Where a project artifact exists, the machine assignment of level 3 has no effect: the project artifact
replaces the artifact it landed on, its three members included. Where no project artifact exists, the machine assignment
lands on the machine or shipped artifact and applies.

`RoleAssignment` carries three nullable members. A `null` member means "this level names nothing"; an `EffortValue`
whose `value` is `null` means "this level names no effort flag", which clears the effort of the levels below. The
distinction is load-bearing and is the reason `EffortValue` exists as a wrapper.

The steward is the exception: `resolveSteward()` takes its harness from `harnesses.default` of `machine-config.json`,
its model from the tier `standard` of that harness's profile, and the effort of its default assignment. Its artifact's
`harness` and `model` are not read, and `model_not_allowed` never applies to it. Every resolution of the steward routes
there, also when a composed unit names it, so no caller reads its artifact's values.

`EffectiveRole` carries the values a worker generation needs: the effective artifact, the three effective values, the
resolved skills with their digests, the harness major.minor, the weights identity where the harness reports one, the
continuation bounds cut to the harness's `headless.resumability`, one effective off-track setting per signal (a signal
the artifact does not name takes the compiled threshold and the action `show`), the context budget (artifact, then
harness fallback, then the compiled `400000`) and the effective idle wakeups.

`LongContextThresholds` is the other reading of the harness profile the envelope budget needs: the per-model
long-context price thresholds of `headless.long_context_thresholds`. It sits beside `HarnessProfile` rather than in it,
because the envelope computation is its only reader and a new component of that record ripples into every constructor of
it (link:../adr/core-profile/016-the-long-context-thresholds-sit-beside-the-harness-profile.adoc[ADR core-profile/016]).
`of(LoadedProfile)` reads the document; `forModel` answers `OptionalInt`, empty for a model the profile names no entry
for.

== The Two Digests

`RoleDigests.configuration(role)` is the SHA-256 of the canonical JSON (RFC 8785) of

----
{"artifact": <effective artifact without description, with the effective harness, model, effort>,
 "harness_version": "<major.minor>",
 "skill_digests": {"<skill URI>": "<sha256>"}}
----

It identifies the configuration a worker generation is started with; an offer compares it, and a generation with an
outdated digest is offered no task.

`RoleDigests.qualification(role)` is the SHA-256 of the canonical JSON of exactly the graded members:

----
{"configuration": {"harness": ..., "harness_version": ..., "model": ..., "effort": ...,
                   "tools": [...], "class": ..., "skill_digests": {...}},
 "weights_identity": "..."}
----

The `configuration` object is the shape of the qualification record's `configuration` member. The weights identity is
added beside it only where the harness reports one, so an enrolment that starts reporting it invalidates the record.

Both digests are 64 lower-case hexadecimal digits, because the configuration digest and the record's
`qualification_digest` carry that pattern.

*Pitfall (carried here from the qualification watch).* A digest bound to too many members makes a role fall to
its conservative fallback for an edit the grading never measured; one bound to too few stays valid after the model or a
skill changed. The rule: a change of `count`, `recycling`, `budget_floor_seconds`, `context_budget_tokens`, `questions`,
`off_track` or `form` changes the configuration digest and keeps the qualification digest; a change of `description`
changes neither; a change of `harness`, `model`, `effort`, `tools`, `class`, a skill digest or the harness major.minor
changes both; the weights identity changes only the qualification digest. `RoleDigestTest` is the table.

== Validation

`RoleValidation.check(...)` runs the rows of the specification's table in order and refuses the role with the first that
fails:

[cols="2,4"]
|===
|Reason |Checked against

|`schema_invalid` |`RoleArtifactValidator`: the closed schema, the name against the file name and the reserved
keywords of the workflow language, `recycling` for `warm`, `questions`/`off_track` not on `zero_tool`, an `off_track`
threshold above the compiled value or below its floor
|`harness_unknown` |`RoleEnvironment.profile` and `.enrolledHarness`
|`harness_not_eligible` |`worker.eligible`
|`harness_class_not_runnable` |`headless.classes.<class>` non-null
|`model_restricted` |`worker.restricted_models` where the class is enforced (always for `zero_tool`)
|`effort_unsupported` |`headless.model_efforts` of the model (or `*`)
|`model_not_allowed` |the effective catalogue, the project's else the machine's; never the steward
|`tool_not_permitted` |the tool set of the class, the PM-MCP tools every role names, the forbidden harness tools
|`form_not_permitted` |a `zero_tool` role is `fresh`
|`skill_unresolved` |`RoleEnvironment.resolveSkill`, and the first skill is a role or an extension skill
|===

The table has no `session_first_not_permitted`; `RoleValidationReason` deliberately does not declare it.

`RoleValidationReason` is the refusal vocabulary; `RoleRefusal` carries the role, the reason, the JSON Pointer where a
value broke a rule, and a detail. `RoleCatalog` turns a refusal into `RoleResolution.Undefined` — the consumer's
"undefined" is a value, not an exception.

== Role Qualification

Package `de.planmarshall.core.role.qualification` holds the measurements of a grading and the rules that decide whether
they qualify a role (Model Work § Role Qualification; Store Schemas § Role Qualification Record). It knows nothing
about workers: a grading offers its items through the `GradingHarness` port and its rubric answers through the
`JudgeScorer` port, and the run that uses them is
link:../../../pm-workflow/doc/developer/workflow-model.adoc[`workflow.model`'s `RoleGrader`].

`QualificationRecord` is the value of one grading: the role, the qualification digest it is bound to, the graded
`configuration` (harness, harness major.minor, model, effort, tools, class and skill digests), the corpus revision, the
missed sources of a partial import, the measurements per form (`fresh`, and `warm` for every role that is not
`zero_tool`), the warm-fresh gap, the ungraded count, the judge instrument check's result where the check ran, and every
item's run with its answer, score, tokens, duration and `checkout`. A topic result answers the mark `thin` from its own
graded count (`TopicResult.THIN_LIMIT`, twenty): the mark never becomes a stored state that could contradict the count,
it changes no verdict, and the codec writes it beside the count as the schema requires.
`QualificationRecordCodec` is its one wire shape; `QualificationRecordStore` writes the project set's
`qualification/<role>.json` by atomic rename under the store's lock, and a lookup reads the project set before the set
of the artifact (`QualificationRecords.firstOf`). `JudgeCheck` and `JudgeCheckStore` do the same for
`qualification/judge-check.json`.

`RoleTopics` gives a role its topics from the corpus items' `role` field: `own` and `generic` for a writer or read-only
role, and `own` alone for a `zero_tool` role. Only `draft` and `confirmed` items count, and the `judge/` topic grades no
role.

[TIP]
====
The record stores measurements, never a pass flag. `QualificationCheck` decides at every check, against the project's
current `agreement_level` and `allowed_gap`, which form the record qualifies. A changed level therefore applies to every
existing record at once.
====

`QualificationCheck` refuses (or downgrades) a record for these reasons. Its `catchRate` answers
`Optional<BigDecimal>`. It is `Optional.empty()` when the record did not grade the form, when the corpus has no
suspicious items, or when the form has no graded run of a suspicious item.

[cols="2,4"]
|===
|Code |Meaning

|`no_topics` |the role has no corpus topic, so it cannot qualify
|`stale_digest` |the record is bound to another qualification digest
|`stale_corpus` |the record was graded on another corpus revision
|`ungraded_items` |an item's judge task closed `lost`, so the record qualifies no form
|`catch_rate_below_level` |the screener's suspicious items are caught less often than the agreement level
|`missing_fresh_form`, `missing_warm_form` |the record does not hold the form
|`missing_topic` |the record holds no result for a topic of the role's corpus
|`below_agreement_level` |a topic is below the project's level
|`below_constant_baseline` |a topic does not exceed its constant baseline by the compiled margin `10`
|`too_uniform` |a topic's baseline plus the margin exceeds `100`; the corpus needs items of other references
|`warm_fresh_gap_exceeded` |the warm-fresh gap exceeds the project's allowed gap (the role still qualifies fresh)
|===

`ConstantBaseline` computes the constant baseline of a topic: for every option key of its `exact_choice` items, the
percent of the graded items whose reference is that key, the largest being the baseline. A rubric item sits in the
denominator and never in a numerator. `Scoring` scores a closed item against its reference and accepted alternatives (a
control is right only when it reports nothing) and decides whether a rubric score reaches the item's pass threshold.
`JudgeInstrumentCheck` runs the judge twice per judge-topic item — oracle and blind, with the reference withheld from
the blind prompt — and records the two accuracies and the baseline; `JudgeCheck.Verdict.of` passes only when the
oracle exceeds the baseline and the blind accuracy by the margin and nothing is unscored. The check blocks no grading:
the role grading records its result (`JudgeCheckResult.PASSED` or `FAILED`) in the qualification record and runs either
way, and a corpus without a `judge/` item records no result at all, so `GradingOutcome.Refused` declares no refusal on
the check. The conformance harness keeps its own `judge_unchecked` refusal.

== Invariants and Failure Modes

* *Absence is `Optional` or `@Nullable`*: the members and the rule are listed once, in
  <<_the_null_contract_of_this_package>>.
* A role set, an assignment and an override are operator files. Never add a code path that reads them from the
  repository.
* Validation is per read. A value that a later change makes invalid (an unenrolled harness, a model the catalogue no
  longer allows) makes the role invalid at its next read, exactly like an invalid artifact.
* An invalid role never falls back to a lower set.
* `RoleEnvironment` is the only way out of the package. A new external fact is a new port method, not a file read.
* The shipped reader skips `default-assignment.json` and every subdirectory. A new reserved file in `classpath:/roles/`
  needs the same treatment, or the build test fails with "not named by a role name".
* A role is never named by a reserved keyword of the workflow language: `RoleArtifactValidator` refuses it as
  `schema_invalid` and `ShippedRoles` refuses the file, as the workflow verifier refuses it where a state names a role.
  The keyword set is a copy of the verifier's, because `pm-core` cannot read `pm-workflow`; a keyword added there is
  added in `RoleArtifactValidator` too.

== Tests

`RoleArtifactValidatorTest` (the closed schema, every `schema_invalid` case), `RoleSetLoaderTest` (whole-artifact
precedence, the invalid higher artifact, the name check, the superseded refusal), `RoleValidationTableTest` (the table
row by row, the reason set and the steward control), `RoleEffectiveConfigurationTest` (the levels, the fresh read, the
steward, the catalogue precedence), `RoleDigestTest` (the digest table), `EffectiveRoleFactsTest` (the resumability cut,
the context-budget and idle fallbacks, the off-track defaults), `ShippedRolesTest` (the classpath reader and the
reserved file), `QualificationCheckTest` (the validity matrix, the level change, the baseline and the warm downgrade),
`ConstantBaselineTest`, `RoleTopicsTest`, `ScoringTest`, `JudgeCheckTest` (the oracle and blind accuracies, the lost
judge task, the stale record), `QualificationRecordCodecTest`, `QualificationRecordStoreTest` and
`QualificationSchemaParityTest` (the two grading schema files, their members, enumerations and the validity of the
written documents: the judge-check record as written, and the qualification record with its topic mark and its optional
judge check).

== Tokens and the Split
_Requirements: link:{docs}/Requirements.adoc#PM-WF-14[PM-WF-14], link:{docs}/Requirements.adoc#PM-CLIENT-5[PM-CLIENT-5]_

`TokenTotal` carries the total a grading measure used and can carry the split beside it: `tokens_in` and `tokens_out`.
The split is a measured pair that sums to the total, or `unmeasured` at both when it is unknown; an unmeasured total
carries no split, and `plus` sums the split only when both addends have one. The qualification and judge-check records
persist `total_tokens` alone (`store-schemas/16`); a view derives the split on read
(link:../adr/core-store/048-token-split-derived-on-read-and-the-coverage-aggregate.adoc[ADR core-store/048]), and a
document that carries either member is refused as undeclared. The two writers refuse a `TokenTotal` that carries a split
with an `IllegalArgumentException` rather than drop it: no producer of a grading builds one, so a split there is an
internal fault. The decision calibration record's schema requires the two
members, and `TokenTotal` keeps the split for it until the codec owed with the package that builds it exists. The cost
is never part of a grading record. A total of `0` is refused (the lower bound is `1`), and a split that does not sum to
the total is refused at construction.

`QualificationRecordCodecTest` covers the split of `TokenTotal` and asserts that a written total that carries one is
refused;
`QualificationSchemaParityTest` reads the two schema files and validates the written documents against their schemas:
the judge-check record as written, and the qualification record with its topic mark and its optional judge check.

link:../adr/core-role/006-grading-records-persist-the-total-only.adoc[ADR 006]: the qualification and judge-check
records persist the total only. link:../adr/core-role/005-token-total-carries-the-split.adoc[ADR 005] is superseded in
the part that named those two records as writers of the split; its decision for the decision calibration record stands.

== The Null Contract of This Package

A field, a parameter and a record component of this package carry `@Nullable` where the state may be absent; `Optional`
stays the type of the absence a method returns
(link:../../../doc/adr/021-optional-fields-parameters-and-record-components-are-nullable-states.adoc[repository ADR
021]). The JSON readers that may see a `null` answer `Optional`, and the caller keeps the `orElse(null)` in the member.

The `@Nullable` members of the package:

* the weights identity of `EffectiveRole`;
* the `harness`, `model` and `effort` components of `RoleAssignment`;
* the default harness of `MachineConfiguration`;
* the reason of `RoleResolution.Undefined`;
* the `previous` record of `GradingPlan`;
* a qualification's `effort` and `duration_ms`, and a grading's `pass_threshold`;
* `QualificationCheck.Verdict.qualifiedForm`, `null` when the record qualifies no form;
* the `profile`, `enrolled` and `catalogue` parameters of `RoleValidation.check`: no client profile has the harness,
  the harness is not enrolled, or no effective model catalogue exists; each refuses the role with its reason.

`EffectiveRole.idleWakeups` is a `@Nullable Integer`, `null` when neither the artifact nor the harness sets it, which
the launch composer writes as the zero-defaulted `idle_wakeups`
(link:../../../doc/adr/029-primitive-optional-components-are-nullable-boxed-numbers.adoc[repository ADR 029]).
`HarnessProfile.askUserTool` is non-null: the profile projection always supplies a value, `""` for an endpoint and for
a harness that declares no tool
(link:../../../doc/adr/031-the-harness-profile-ask-user-tool-is-non-null.adoc[repository ADR 031]). The `catalogue` of
`RoleAssignmentValidation.Facts` is a type of `core.config` and is described in its guide
(link:core-config.adoc[`core.config`]).
