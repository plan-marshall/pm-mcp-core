= Task Queue Developer Guide (`core.queue`)
:nofooter:

`de.planmarshall.core.queue` owns the persisted side of the task protocol: the queue task record of one unit of model
work, the queue of a project and of the machine scope, the generation fence and the activity journal of a task. The
protocol that moves a task — offer, acknowledgement, lease, fence, outcome, re-offer and skill delivery — is
`de.planmarshall.workflow.task` and is documented in
link:../../../pm-workflow/doc/developer/workflow-task.adoc[`workflow.task`].

== What the package is for

A plan task (`TASK-NNN`) is a step of a plan. A *queue task* is one unit of model work: a `job llm` state creates one
per entity, a `consult role` link creates one for the consulted role. The scope store is authoritative for which tasks a
model state owns and how they ended (`active_tasks` of `mcp/status.json`); the queue task record is
authoritative for the delivery — its lease, its attempts, the off-track signals of its workers and its consultations.

Specification: link:../../../doc/specification/store-schemas/16-task-queue.adoc[Store Schemas § Task Queue, § Queue Task
Record and § Activity Journal], link:../../../doc/specification/model-work/02-task-protocol.adoc[Model Work § Task
Protocol], link:../../../doc/specification/model-work/03-supervision-and-recycling.adoc[§ A Worker Off Track].

== The types and how they work together

`QueueTaskId`::
`qt-` and 16 random lower-case hexadecimal digits. The id is the name of the record file and, for a consultation, the
`consultation_id`.

`QueueTaskRecord`::
One record per task, with the closed schema of `queue/<queue_task_id>.json`: the kind (`work` or `consultation`), the
role and its class, the scope (`plan`, `epic`, `workspace` or `machine`), the entity, the creating state, the status,
the continuation after a question, the current lease, the attempts, the signals, the consultations and the closed
outcome with its reason. Its nested types are the closed vocabularies of the schema (`Status`, `Outcome`, `LostReason`,
`AttemptEnd`, `SignalName`, `SignalAction`, `ContinuationForm`, `FallbackReason`, `ConsultationStatus`, `DeliveredTo`).
`validate()` holds the combinations the schema rules out; it runs when a record is written and when one is read, never
on an intermediate value, so a record can be built member by member through its `with` methods
(link:../adr/core-queue/005-record-combinations-checked-at-the-write-boundary.adoc[ADR 005]).

`QueueTaskRecordCodec`::
The one reader and writer of a record. It accepts exactly one shape through `core.store`'s `StrictJson`, and writes
every field in the order of the schema, so a record read back is written back byte for byte.
`TaskQueueSchemaParityTest` keeps the fields, the required members and every enum equal to the schema file beside the
codecs, `de/planmarshall/core/queue/queue-task.schema.json` (and `activity-entry.schema.json` for an activity entry),
read from the class path through `SchemaResource`, and validates every written record against it. Document 16 of the
store schemas includes both files (link:../../../doc/adr/016-schemas-are-files-of-the-implementing-module.adoc[ADR 016]).

`QueueStore`::
The records of one queue. `ofProject(base, projectId, locks)` is `projects/<project_id>/queue/` under
`locks/queue.lock`; `ofMachine(base, locks)` is `machine/queue/` under `machine/locks/queue.lock`. `create` writes the
first record of a task; `updateAll` revises all records in one transaction on the queue lock and writes only those that
changed; `read`, `records` and `queueTaskIds` read without a lock. A file that is not `<queue_task_id>.json` is no
record.

`FencedGenerations`::
`queue/fences.json`, the generations the supervisor fenced, with the instant of each. The fence is persisted beside the
queue under the queue lock, so a late call of a replaced generation is refused after a restart
(link:../adr/core-queue/004-generation-fence-beside-the-queue.adoc[ADR 004]). The fence document is not a queue task
record and the listing skips it.

`ActivityEntry` and `ActivityEntryCodec`::
One line of `tasks/activity/<queue_task_id>.jsonl`: what a worker did (the harness kinds `text`, `tool_call`,
`tool_result`, `file_changed`, `turn`) or what the server recorded (`link`, `question`, `answer_ack`, `signal`,
`attempt_end`). The `usage` object belongs to another package and is kept as the raw JSON text it was read with.

`ActivityJournal`::
The journal of a scope: `plans/<plan_id>/tasks/activity/`, `epics/<epic_id>/tasks/activity/`,
`workspace/tasks/activity/` or `machine/tasks/activity/`. It appends one entry per line under the leaf lock of the
sibling `<queue_task_id>.jsonl.lock` — a bounded journal is replaced by an atomic rename, so the lock cannot sit on the
journal itself (link:../adr/core-queue/006-the-journal-lock-is-a-sibling-file.adoc[ADR 006]) — cuts a torn last line
before the next append, and keeps the compiled bound of 5,000 entries by dropping the oldest `text` entries first and
never a server entry; a journal whose excess lies in server entries alone keeps them, because a server entry is never
cut. It masks the entry it writes and offers `archiveInto(task, directory)` and `delete(task)` for the plan's archive
and its cleanup (link:../adr/core-queue/008-the-journal-masks-at-its-write-boundary.adoc[ADR 008]).

`ActivityEventMapping` and `SecretRedactor`::
The projection of the profile's `headless.events` block (`ActivityEventMapping`) and the redaction of what the journal
writes (`SecretRedactor`). `SecretRedactor` masks a credential-shaped assignment, a
bearer value, the provider token shapes (GitHub, Slack and the npm `npm_` access token), the user information of a URL,
the value of a spaced credential flag of a closed list, and a PEM or PGP private-key block carried inside one text; each
shape is anchored to its own form so prose cannot match it (its Javadoc names them, and
<<redactor-shapes>> lists them with what each leaves readable). The line mapper `ActivityEventMapper` itself lives in
`pm-runtime` (`runtime.worker`) and reads the projection; the mapping is never read from the profile on the stream path
(link:../adr/core-queue/007-the-events-mapping-is-projected.adoc[ADR 007]) and the journal redacts at its write boundary
(link:../adr/core-queue/008-the-journal-masks-at-its-write-boundary.adoc[ADR 008]). `ActivityEventMapping.of`
answers `Optional<ActivityEventMapping>`: a profile whose `headless.events` is `null` is `Optional.empty()`, never a
`null` value, because every production package is `@NullMarked`.

ADR number 009 of this package is retired: it decided the navigation figures, which the work package
`deferred-code-removal` deleted with the record. The next ADR of `core-queue` takes 010.

[#redactor-shapes]
== The Redactor's Shapes and What Stays Readable

`SecretRedactor` is deliberately narrow: a false positive costs a piece of the operator's evidence, a false negative
writes a credential to a store. It masks the shapes below and leaves every other text alone; the decisions are
link:../adr/core-build/006-the-redactor-shapes-and-the-npm-diagnostic-redaction.adoc[ADR `core-build/006`] and
link:../adr/core-build/009-the-redactor-shapes-the-diagnostic-redaction-and-the-input-bounds.adoc[ADR `core-build/009`].
The replacement keeps the label, so a reader still sees what was removed, and redacting redacted text changes nothing.

[cols="2,3,3",options="header"]
|===
|Shape |Masked |Stays readable, and why

|Credential assignment (`password=`, `token:`, `api_key=`, a camelCase `fooSecret=`) and an `Authorization:` header with
`Bearer`, `Basic` or `Token`
|the value after the separator
|a secret in a query parameter whose name is no listed label; and under an `Authorization:` header of another scheme
(`Digest`, `Negotiate`) the scheme word is taken as the value and masked, while the credential after it stays readable.

|Bearer value
|the value after `Bearer`
|a bare JSON Web Token without `Bearer` and an AWS access-key id: no label and no anchored shape marks them.

|Provider tokens (`sk-`, `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`, `xox[abprs]-`)
|the whole token
|a shorter run after the prefix.

|npm access token
|`npm_` followed by exactly 36 alphanumeric characters
|a run of 37 or more characters after `npm_`, a run followed by `_` and a run preceded by a word character: none of them
is an npm token, and a package name that starts with `npm_` keeps its text (an operator decision).

|URL user information (`scheme://user:secret@host`)
|the secret, also when it holds a raw `/`, `?`, `#` or `@` (it runs to the last `@` of the token), when the user holds a
raw `@` (the user runs to the first colon), and behind a percent-encoded scheme separator (`https%3A%2F%2Fuser:secret@host`)
|the single-user form `https://<token>@host`, which has no colon and so no secret part (an operator decision, a known
residue); `scheme://host:8080/path`; a path with a colon; prose. The false-positive costs: a `host:port/path` followed
later on the same token by a raw `@` is read as user information, and its port and path up to that `@` are masked; and
a credentialed URL followed later on the same token by a raw `@` (an `@scope` path segment
`https://user:secret@registry.example/@scope/pkg`, an e-mail address) masks its host and path up to that last `@`,
because the secret runs to the last `@` of the token.

|Spaced credential flag of the closed list `--password`, `--passwd`, `--passphrase`, `--token`, `--secret`,
`--auth-token`, `--api-key`, `--apikey`, `--access-token`, `--client-secret`, `--otp`, in any case
|an unquoted value to the next whitespace (a `,`, `;` or quote included); a quoted value to its closing quote, across at
most one line end; an unclosed quote masks the rest of its line, and an escaped quote (`\"`) is no close
|a flag outside the list (`--key value`, an operator decision) and `--password-file notes.txt`, a different flag. The
false-positive cost: usage text such as `--token <token>` masks the placeholder.

|PEM private-key block and PGP private-key block (`-----BEGIN PGP PRIVATE KEY BLOCK-----`)
|the block from its `BEGIN` line to its `END` line; a block without its `END` line is masked to the end of the text (the
over-masking is kept: masking too much costs evidence, a readable key body costs the credential)
|a block whose `BEGIN` line lies before the excerpt window, so that the text starts inside it: nothing in the text marks
the body as a key, and the window is not widened to reach the marker. Prose that names `PRIVATE KEY` outside a marker.
|===

*The journal path strips escape sequences.* `SecretRedactor.redact(ActivityEntry)` strips the terminal escape sequences
of the text, the tool target and the link target through `BuildLogText.stripAnsi` of `core.build` — the expression the
unparsed excerpt uses — before it redacts them, so a colour code between a label and its value
(`ESC[1mpassword ESC[0m=value`) cannot hide the value. The journal therefore stores no escape sequence; the bound of
each part is applied after the redaction. `redactText(String)` leaves escape sequences to its caller. This makes
`core.queue` depend on `core.build`, which already depends on `core.queue`; no guard forbids the cycle of packages, and
ADR `core-build/009` records it.

*The cost is bounded on every path.* No pattern of the redactor carries a time bound, so each caller bounds the text
before it is redacted. The unparsed excerpt cuts every kept line to `BuildLogText.MAX_LINE_LENGTH` characters before the
redaction; the npm diagnostic is composed from lines `NpmErrorParser` has already cut at its entry; and the journal path
redacts an entry whose compiled bounds hold already (`ActivityEntry.TEXT_BOUND` of 2000 code points for the text, 1000
for a tool target, 128 for a link target), both in `ActivityJournal` and in `ActivityRecorder` of `pm-runtime`. The URL
shape is two patterns applied in sequence, one for `://` and one for the percent-encoded `%3A%2F%2F`; in each the scheme
and the user are possessive and the scheme starts only where no scheme character precedes it, while the secret is a
greedy `\S+` that gives characters back to the last `@` of the token. Its cost is therefore not linear: a token without
that `@` is scanned back once from each scheme start, quadratic in one line at worst, and the line cut above is what
bounds it. The quoted credential-flag value is an unrolled loop (a plain run, then escape pairs each followed by a plain
run) with possessive repetitions only, so it neither backtracks nor recurses per character. The residue: `ProviderVerification` of `pm-runtime` (`runtime.credentials`) redacts a probe answer the
assembly supplies, and that input is not bounded here.

== How to use and extend it

Create the record through the builder and hand it to `QueueStore.create`; change it through the protocol, which asks the
store to revise all records in one transaction. A new closed value is a new constant of the matching enum plus the same
constant in the schema file `queue-task.schema.json` and in `TaskQueueSchemaParityTest`; the parity test then fails until
both agree. A new field is a new component of `QueueTaskRecord`, a field in the codec in schema order, and a line in the
schema file; the parity test compares all three.

The runtime writes the `agent_started` detection through `workflow.task`'s protocol, which asks the audit log for one
`security` record naming the executable; the record here carries the matching `signals[]` entry with the action
`restart`.

== Invariants and failure modes

* A record is written only under its queue lock, as an atomic write-and-rename; a reader sees the record before or after
  a write, never a part of one.
* `validate()` runs before every write and after every read: a record that breaks a combination of the schema is
  refused, not repaired.
* An `agent_started` signal always takes the action `restart`; the record, the activity entry and the codec all refuse
  any other action.
* A fenced generation's call is refused before the lease and every link check, after the job's own end; the fence
  outlives the runtime that wrote it.
* *The null contract is the type*: every optional member of `ActivityEntry` — text, tool, result, path, stop reason,
  usage, link, question id, signal, end and unmapped lines — and the target of a tool call and of a link is declared
  `@Nullable`; a test for one of them is therefore live, not dead. `SecretRedactor.redactText` answers
  `Optional<String>`: an absent value is `Optional.empty()`, never `null`.
* A queue that does not exist is empty, never an error; a record that exists and does not parse is a `StoreRefusal`
  naming the file, never an empty record.
* A torn last line of a journal is cut by the next append; `seq` is never reused.
* The journal's leaf lock is the sibling `<queue_task_id>.jsonl.lock`: the journal itself is replaced by a rename when it
  exceeds its bound, and a lock on the replaced inode would exclude nobody. Its OS lock is on that sibling, never on the
  journal: a store write opens and closes a channel on the journal and would release a lock taken on it
  (link:../adr/core-store/068-leaf-key-os-lock-on-a-sidecar.adoc[ADR core-store/068]).
* Deleting a journal is an act of the one runtime: `delete(task)` holds the leaf key while it unlinks the journal and
  its sidecar, so the held OS lock lies on an unlinked inode afterwards and a second runtime that created the sidecar
  again would lock a different inode. The runtime singleton lock is what excludes that second runtime.
* Every text, tool target and link target is stripped of its escape sequences and masked before the write; a masked
  value is stored masked, and a secret of a shape the redactor knows is never in the journal at rest (the shapes it
  leaves readable are listed in <<redactor-shapes>>).
