== Purpose
_Requirements: link:{docs}/Requirements.adoc#PM-SEC-8[PM-SEC-8], link:{docs}/Requirements.adoc#PM-WORK-1[PM-WORK-1],
link:{docs}/Requirements.adoc#PM-EXT-6[PM-EXT-6]_

Package `de.planmarshall.core.config` of `pm-core` owns the machine's and the project's stores that the onboarding
writes and that everything else only reads:

* the *consent store* `consents.json`, its closed list of kinds and the consent-before-acting rule
  ({spec}/store-schemas/12-machine-stores.adoc#consent[Store Schemas § Consent Before Acting]);
* the *model catalogue* `model-catalogue.json`, of the machine or of one project
  ({spec}/store-schemas/12-machine-stores.adoc#model-catalogue[§ Model Catalogue]);
* the *role assignments* `role-assignments.json`, of the machine or of one project
  ({spec}/store-schemas/12-machine-stores.adoc#role-assignments-store[§ Role Assignments]), with the release's default
  assignment and the proposal {@code roles.default} shows
  ({spec}/model-work/01-roles-and-configuration.adoc#default-assignment[Model Work § Default Role Assignment]);
* the *settings-conflict refusal* every one of those stores raises on a change against an older revision
  ({spec}/store-schemas/12-machine-stores.adoc#machine-config[Store Schemas § Machine Configuration Store], the
  operator-file revision rule);
* the *effective configuration key table*: every addressable node of the three configuration files with its value domain
  and whether the configuration compiles a default for it
  ({spec}/store-schemas/07-project-configuration.adoc#project-configuration-store[Store Schemas § Effective
  Configuration and Sources]).

The package never reads a file for a fact another package owns: the role package reads the assignments through
`RoleEnvironment`, the model catalogue through the same port, and the runtime is to wire both (no production
implementation of the port exists in this repository yet; the onboarding's units and the assembly are owed). The package names no provider
and no harness beyond the client-id grammar; the machine's provider defaults live in the runtime
(link:../../../pm-runtime/doc/developer/runtime-config.adoc[`runtime.config`]), because `pm-core` stays
provider-neutral (its architecture guard).

Specification (the sections this package was built against): `store-schemas/12-machine-stores.adoc#consent`,
`#model-catalogue`, `#role-assignments-store`; `model-work/01-roles-and-configuration.adoc#role-assignment`,
`#default-assignment` and `#steward-role`; `credentials-and-enrolment/01-provider-credentials.adoc#provider-verification`
for the consent `verify_providers`. The package's pull request does not delete those specification sections: the
onboarding units that run them live in `plan-marshall-mcp`, and the sections also describe the settings, the automatic
run and the plan axes, which other plans still owe (`machine-onboarding-unit`, PLAN-108 and PLAN-109). The deletion
belongs to the packages that complete the document.

== The Consent Store

`ConsentStore` reads and writes `consents.json` under `locks/consents.lock`. A document that does not exist reads as no
entry at revision `0`. A write reads the document again under the lock, checks the caller's revision, replaces the entry
of the (kind, project) it changes, increments `revision` and writes the document back.

`ConsentKind` is the closed list, each kind with how long a `yes_remember` lasts:

[cols="2,1,2"]
|===
|Scope |Remembered |Kinds

|Machine |for the machine, one entry for every project
|`scan_harnesses`, `fetch_icons`, `probe_harness_login`, `probe_harness_models`, `model_advice`,
`check_credential_store`, `scan_providers`, `verify_providers`, `check_updates`

|Project |for the project, `run_checkout_scripts` also for the digest of each script
|`inspect_checkout`, `run_checkout_scripts`, `model_cost`

|Never |asked afresh at every action
|`verify_harness_profile`, `auto_run`
|===

`ConsentGate` is the rule, not a store: given the store's snapshot and the operator's answer it decides whether the
action runs. It answers `yes` (run, record nothing), `yes_remember` (run, and hand back the entry for
`ConsentStore.grant`), `no` (record nothing, leave the scope in its consent state), and passes a remembered kind without
a question. Every answer is validated before the remembered snapshot is looked at: a paired device belongs to a web
answer and to its grammar, and a device on the `cli` channel or a malformed one is refused for `yes`, `no`,
`yes_remember` and a remembered kind alike, as the method's contract states. A `yes_remember` for a kind that is never
remembered is refused, as is a project the kind does not belong to.
`ConsentGate.operatorAct()` is the other half of the rule: an act of the operator's own — a secret the operator types —
needs no consent, and is stored on that act.

A consent covers its kind and never a wider one, because the lookup is by the kind alone: a remembered `scan_harnesses`
runs no login or model probe. `ConsentStore.ofProject` and `removeProject` carry the entries of a project, which the
cleanup drops with the project's machine store.

A remembered and a withdrawn consent each append their `operator` audit record (`consent_remembered`,
`consent_withdrawn`) inside the write's transaction and before the store is replaced, so a committed consent always has
its record and a sink that refuses it aborts the change
(link:../../doc/adr/core-config/003-the-consent-record-is-handed-over-before-the-write.adoc[ADR 003]).

== The Model Catalogue

`ModelCatalogueStore` reads and writes `model-catalogue.json` of the machine (under `locks/model-catalogue.lock`) or of a
project (under the project's `locks/local-config.lock`). The document is closed, so a write replaces it from its model:
the allowed models per harness — each with its source (`probe` or `operator`) and the instant it was recorded — and the
revision. A write drops the entries of a harness that is no longer enrolled, as the specification requires.

`Snapshot.catalogue()` projects the document to the role package's `ModelCatalogue`, which is what validation asks
whether a model is allowed on a harness.

== The Role Assignments

`RoleAssignmentsStore` reads and writes `role-assignments.json` of the machine (`locks/role-assignments.lock`) or of a
project (the project's `locks/local-config.lock`). `RoleAssignmentValue` keeps the schema's three states of the effort —
`INHERIT` (the member is absent and the lower level's effort stays), `DEFAULT` (`null`, the profile's default effort) and
`VALUE` — and the optional `Escalation` of a role. `Snapshot.assignments()` projects the document to the role package's
`RoleAssignments`.

`DefaultAssignment` reads the release's `classpath:/roles/default-assignment.json` beside the shipped role set.
`RoleAssignmentProposal.propose` applies it: per assignable role — every role of the effective set except the steward —
the preferred harness where it is enrolled, else the first enrolled harness whose profile runs the role's class; the
model that harness maps the role's tier to, where the catalogue allows it; and the default's effort narrowed to what the
harness accepts for that model. A role whose default cannot be met is reported without a value, with the reason and the
advisory beside it.

`RoleAssignmentValidation` is what `roles.write` runs first: the harness is enrolled and worker-eligible, the profile runs
the role's class, the model is allowed by the effective catalogue and the effort is one the harness accepts — for the
role's own values and for its escalation, with the reason of the validation table. The steward never appears in the
proposal, and `model_not_allowed` never applies to it: its configuration comes from the machine's default harness and
that harness's tier `standard`, which `StewardConfiguration` and `RoleCatalog` resolve.

== The Project Onboarding's Values and Consents

The project onboarding's framework-free parts live here, beside the stores they write through; the unit that drives
them (`project-onboarding.pmwf`) is content of `plan-marshall-mcp`
(link:../../../doc/specification/state-catalogue/15-project-onboarding.adoc#state-catalogue-project-onboarding[State
Catalogue § Project Onboarding]).

`CheckoutScripts`:: The digests a `run_checkout_scripts` consent is keyed by
(link:../../../doc/specification/store-schemas/12-machine-stores.adoc#consent[Store Schemas § Consent Before Acting]).
`digest(checkoutRoot, scriptPaths)` reads each script at its repository-relative path through directory handles opened from
the checkout root (`SecureDirectoryStream`), so no component of the path can be replaced by a symbolic link between the
check and the digest, and answers one `ConsentScript` per path in the state's order; a path that leaves the checkout, an
absolute path, an absent file, a directory, a symbolic link, a file system without secure traversal and a repeated path
are refused rather than digested, so no consent covers a script the state cannot run.

`PendingConsent`:: A `yes_remember` of a project-scoped kind given before the project has its id: the hold lives with the
onboarding's entry (the unit's), and `resolvedFor(projectId)` materializes it under the confirmed id. Recording it
through `ConsentStore.grant` at `project.enrol`, in the consents store's own transaction, is the unit's step; this type
holds the value and never writes a store.

`RunConsents`:: The kinds one onboarding run already answered `no`: `asksAgain(kind)` is false for a refused optional
consent, so `project.run-consent` goes on without the scripts and does not ask again in that run. It records the answer of
the run, never a store entry.

`ProjectIdentityProposal`:: The id and display name proposed at `project.identity`, from the remote: the id from the
remote's name, made valid by the identifier grammar of `LockKey` and unique on the machine (`-2`, `-3`, …), the display
name `<owner>/<name>`. A remote without owner and name, and a name no valid id can be made from, propose nothing.

`SetupRun`, `SetupAspect`:: The closed lists of the setup's four entries and six aspects, read by the unit that routes a
run and by the runtime that serves the links, so the names exist once. `workflow.setup`'s `SetupRunDerivation` decides
which run a call records.

`ProjectValueProposal`:: One value of a project over the machine's
(link:../../../doc/specification/store-schemas/08-project-configuration-local.adoc#project-levels[Store Schemas § Project
Values over Machine Values]): the machine's value is the proposal, accepting it records nothing, and a changed value is
the one the project records. The rule is the same for every machine-backed key and aspect, so no such key carries a rule
of its own. Two keys sit outside it: the transcription methods, which the project may only narrow (`TranscribeMethods`,
called before an override is recorded), and the commit identity where neither the project nor the machine holds one — the
specification proposes the operator's global git identity and records it on the operator's acceptance, and
`ProjectValueProposal` covers only a value it can propose.

`TranscribeMethods`:: The one value a project may only narrow. `chosen(methods, machineMethods)` accepts a subset of the
machine's and refuses a method the machine does not allow with `invalid_arguments`.

== A Change Against an Older Revision

Every one of the stores takes the revision its caller read. The first change wins; a later one against an older revision
is refused with `SettingsConflict` — the code `conflict`, the status `409`, the revision the change named, the revision
the document holds and the current value of the setting, which the operator may change again on top of it. Nothing is
merged and nothing is overwritten unseen. `SettingsConflict` exists beside `StoreRefusal` because it carries the current
value, which the store-refusal vocabulary has no field for
(link:../../doc/adr/core-config/001-the-settings-conflict-carries-the-current-value.adoc[ADR 001]).

== The Effective Configuration Key Table

_Requirements: link:{docs}/Requirements.adoc#PM-EXT-6[PM-EXT-6]_

`EffectiveConfigKeys` is the compiled table of the keys the effective configuration resolves
({spec}/store-schemas/07-project-configuration.adoc#project-configuration-store[Store Schemas § Effective Configuration
and Sources]). It holds 100 keys: 16 of `project.json`, 20 of `workflow.json` and 64 of `local-config.json`. Each is an
`EffectiveConfigKey` — the key, its `ConfigValueDomain` and whether the configuration compiles a default for it.

*The grammar.* An effective key is `stem "." segment {"." segment}`. The stems are `project`, `workflow` and
`local-config`; `derived.` names a fact and is refused with a message that says a fact is read by kind. A segment is an
identifier (`[a-z][a-z0-9_-]*`) or the single wildcard `*`; an empty segment, a segment that is neither, and a key with no
dotted path are refused.

*A key is any addressable node.* A node with members is a key of domain `Object` beside its members, so
`local-config.commit_trailer` and `local-config.commit_trailer.email` are both keys. A map node — the finalize `steps`,
the `project_steps`, the upstream MCP `servers`, the `derivation_resolvers` — contributes the wildcard segment `*`, which
stands for exactly one non-empty segment: `workflow.plan.phase-6-finalize.steps.*.lane`. `EffectiveConfigKeys.find`
answers the exact key or the one key whose wildcard the form's segment stands for, never a prefix of a key, so a misspelt
key resolves to nothing instead of to a shorter one. The verifier's registry is an exact lookup and a unit's
`config_key` admits identifiers only, so a wildcard row serves the effective-value machinery rather than a
`reads_config` declaration; the schema keyword `not` is not modelled, which over-approximates a range by the values it
excludes (`project_steps.*.order` admits 11 and 70).

*The domain.* `ConfigValueDomain` is sealed with seven members: `Enumeration(values)` (`enum` and `const`),
`IntegerRange(min?, max?)` (either bound may be absent), `Bool`, `Text`, `ListOf(element)`, `Object` and
`Union(alternatives)` (`oneOf`; the three cleanup durations are `integer` at least 7 or `never`).

*The compiled default.* `hasCompiledDefault` is true when the schema node carries the `default` keyword or the key is
one of the five prose defaults the parity test classifies. A key whose presence is itself the answer has no default, and
neither has a key whose value is derived.

*Adding a key.* The table is pinned to the schemas, so a key arrives in three steps:

. Change the schema resource of the file (`config-project.schema.json`, `config-workflow.schema.json` or
  `local-config.schema.json`).
. Add the row to `EffectiveConfigKeys`, with the domain the schema states and whether a default exists; a new prose
  default is classified in `PROSE_DEFAULTS` with its reason.
. Run `EffectiveConfigKeysSchemaParityTest`. It walks the schemas, derives every key, domain and default flag, and fails
  on a key, an enumeration value, a bound or a `default` keyword the table disagrees with — and on a description that
  states a default the test does not classify.

== Invariants and Failure Modes

* *An optional effort is `Optional` at the parser and `@Nullable` at the validator*: `nullableString` answers
  `Optional`, the codec maps it with `EffortValue::new`, and `RoleAssignmentValue.of` accepts a `@Nullable String`.

* *A named effort is never `null`*: `RoleAssignmentValue` refuses `VALUE` with an `EffortValue` whose value is `null`
  (`IllegalArgumentException`, "A named effort value must not be null"). The cleared effort is `DEFAULT`, written as
  `effort: null`; a `VALUE` with a `null` value would be written the same way and read back as `DEFAULT`, a silent
  change of the effort setting.
* A document of another format version, or one that does not parse as its one shape, is refused with a `StoreRefusal`
  naming the file; a reader never repairs, migrates or rewrites it.
* A write happens only under the document's lock, and only while the caller's revision is the one the document holds.
* A consent entry is unique per (kind, project); the store replaces the entry instead of adding a second one.
* No store creates the operator's directory: the runtime creates the project store and the state directory, and the
  stores write the files inside them.
* `ConsentGate` refuses a `yes_remember` for `verify_harness_profile` and `auto_run`, so a caller that offers the link
  fails loudly instead of remembering a kind the specification says is never remembered.
* A `PendingConsent` is never a store entry: it is held with the onboarding's entry and written under the confirmed
  `project_id` at `project.enrol`, in the consents store's own transaction, so an onboarding that abandons before its
  enrolment remembers nothing. The write is the unit's step; the type holds the value.
* `ProjectValueProposal.recorded` answers empty for the machine's own value, so accepting a proposal writes no key and the
  project keeps following the machine.

== Testing

The stores are tested against `@TempDir` roots with a lock manager that records its keys: the shapes a document accepts
and refuses, the three effort states, the escalation, the drop of an unenrolled harness, the conflict that carries the
current value, and the gate's answers and scope rules. `RoleAssignmentProposalTest` builds a role set from inline
artifacts and a default assignment from an inline document, so the proposal is proved without a release.

== The Null Contract of This Package

A field, a parameter and a record component of this package carry `@Nullable` where the state may be absent; `Optional`
stays the type of the absence a method returns (link:../../../doc/adr/021-optional-fields-parameters-and-record-components-are-nullable-states.adoc[repository ADR 021]). `Consent.projectId` and `Consent.deviceId`, `ConsentGate.Request.projectId` and `ConsentGate.Decision.toRecord`, the `projectId`/`effort`/`escalation` parameters and components of the assignments, and `RoleAssignmentValue.effortValue` are `@Nullable`; a codec writes the absent member exactly as it wrote `Optional.empty()`.
