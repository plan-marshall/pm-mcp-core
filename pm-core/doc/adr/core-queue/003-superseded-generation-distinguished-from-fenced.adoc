= ADR 003: A Generation Superseded by an `enter` Is Told from a Fenced One by the Generation Issued at Its Fence
:nofooter:

== Status

Superseded by the work package `removed-concepts` (2026-10-20): the record and the concept it describes are removed.

== Date

2026-10-13

== Context

Every newer generation of a session key fences the older ones. A generation fenced by a `pm-mcp enter` must be told
apart from one fenced by the relay: a request carrying it is answered at the transport with `generation_superseded`,
and the relay then binds again, while every other call of a fenced generation is refused `generation_fenced`.

The schema of the session generation record holds `fenced_at`, the instant of the fence, but no member that names
what fenced it; the schema is closed, so a member cannot be added without a specification change. Each generation holds
its own `issued_at` and `issued_by` (`enter`, `relay_start` or `new_session`).

== Decision

What fenced a generation is derived when the record is read, not stored:

1. An issue fences every earlier generation of its session key in the same write, at the instant of the issue: the
   fenced generations get `fenced_at` equal to the new generation's `issued_at`.
2. The issue instants of one session key strictly increase: an issue whose clock reads an instant not after the latest
   issue of its key takes the next nanosecond after it (`SessionGenerationStore.issueInstant`). So exactly one
   generation of the key was issued at any `fenced_at` of the key.
3. `SessionGenerationCodec.read` derives `SessionGeneration.Fence.byEnter`: a fenced generation is superseded when the
   generation of the same key issued at its `fenced_at` was issued by `enter`. The writer drops the flag, so a record
   the store wrote reads back equal.
4. `GenerationCheck.of` answers `Superseded` (code `generation_superseded`) for a fence by an `enter` and `Fenced`
   (code `generation_fenced`) for every other fence; `Current` and `Unknown` otherwise.

== Alternatives Considered

1. *A member `fenced_by` in the record*.
   _Rejected_: the closed schema of the specification has no such member; the information is already in the record.
2. *Compare instants without the strict increase*.
   _Rejected_: two issues of one key within the clock's resolution would have the same instant, and the generation that
   fenced could not be named.
3. *Keep the flag in memory only*.
   _Rejected_: the record is read by every call and must answer the same after a restart.

== Consequences

* The issue instants of a key are unique, possibly one nanosecond after the clock; `issued_at` is still the instant of
  the issue to the clock's resolution.
* A fenced generation whose fencing generation was removed by the sweep cannot remain: the removal takes a generation
  fenced by a removed one with it, so every fenced entry that stays keeps the generation it is derived from.
* `SessionGenerationCodecTest` covers the derivation; `SessionGenerationStoreTest` checks a generation replaced by an
  `enter` as `Superseded` and a fenced one as `Fenced`.
