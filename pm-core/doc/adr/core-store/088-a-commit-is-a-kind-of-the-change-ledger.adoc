= ADR 088: A Commit Is a Kind of the Change Ledger
:nofooter:

== Status

Accepted

== Date

2026-11-23

== Context

The ledger's `kind` carried `build`, `change`, `job`, `task_diff` and `baseline_red`, and none of them recorded the
commit itself: a `change` row names a footprint change, not the commit that carried it, so a reader could not attribute
a commit to the tree it was made on. The freshness verb never needed such a row for its own decision:
`git.pre-commit-verify-freshness` is specified to read `build` and `baseline_red` rows of the same `worktree_sha` — or,
without one, the latest succeeded build row whose changed paths since its recorded head are all build-neutral — and
answers the `fresh` and `exempt` verdicts without a commit row (State Catalogue § `git.verify-freshness`; Workflow DSL
§ Six-Stage Execution Contract, stage 5). The new kind is the attribution record those rows cannot be.

The format is a stored contract: `change-ledger-record.schema.json` is read by a schema-parity test (R10), and a new
kind is a stored-format change. The spec marked the format-version question ask-at-refine (R13); the operator confirmed
on 2026-11-23 (question 2 of the runbook-lane outline) that the version stays `1` and the kind is added in place.

== Decision

`ChangeLedgerRecord.Kind` gains `commit` (`"commit"`), and the schema's `kind` enum and description gain it too. A
`commit` row carries:

* `worktree_sha` — the working-tree digest of the tree the commit was made on, with its version, exactly as every other
  row. It is taken *before* the commit. The digest takes the `HEAD` commit id and every path the status reports as its
  input (Working-Tree Hash, rule 1), so the commit's own move of `HEAD` and of the status path set changes it: a digest
  taken before the commit can never equal the live digest after it. Before the commit it is the state the commit was made
  on: when the tree is the one the latest successful build ran on, it equals that build row's digest; otherwise a build
  row need not carry it — a later step may have left the tree other than it built. Once the commit exists, old tree-keyed
  rows no longer match, and only a new `build` or `baseline_red` row for the new tree, an `exempt` verdict (which needs no
  build), or the latest succeeded build row whose changed paths since its recorded head are all build-neutral licenses the
  push (State Catalogue § `git.verify-freshness`);
* `commit_sha` — the commit that was made, required for this kind alone (`ChangeLedgerRecord` refuses a `commit` row
  without it);
* `changed_paths` — the paths the commit carried;
* `change_origin` — `plan_change` or `quality_gate_autofix`, as for a `change` row;
* `recorded_at` — the instant of the append.

The codec needs no change: it reads the kind by its wire name and writes the members it already writes. The parity test
`ChangeLedgerSchemaParityTest.recordEnumerations` keeps the enum equal to the schema's, and
`ChangeLedgerCommitRowTest` pins the row's round trip and its refusal.

The format version stays `1`; a `commit` row is written and read in place, with no reader for an older shape.

== Alternatives Considered

1. *Record the commit in the existing `change` row.*
   _Rejected_: a `change` row is a footprint change and may be written for a path set no commit carried; one row cannot
   mean both, and a reader could no longer tell which a line is.
2. *A separate ledger file for commits.*
   _Rejected_: the attribution record belongs beside the tree history it annotates; a second file would have to be read
   with the ledger and kept in step, and the append-only discipline of `change-ledger.jsonl` already covers it.
3. *Bump the format version to 2.*
   _Rejected_: R13 keeps every version at `1` before the release and replaces the shape in place; a bump would add a
   reader and a migration for nothing.

== Consequences

* A commit is attributable to the tree it was made on: the row's digest equals the digest of the build row when the tree
  is the one that build ran on. The freshness verb itself is specified to read `kind = "build"` and
  `kind = "baseline_red"` rows, and without one the latest succeeded build row whose changed paths since its recorded
  head are all build-neutral, never a `commit` row (State Catalogue § `git.verify-freshness`; the verb is not wired in
  this checkout); the `commit` row is the attribution record, not an input of the gate.
* The schema's `kind` enum and the record's enum move together; a new kind that skips one side fails the parity test.
* `doc/Traceability.adoc` no longer lists the change-ledger commit row as unimplemented.
