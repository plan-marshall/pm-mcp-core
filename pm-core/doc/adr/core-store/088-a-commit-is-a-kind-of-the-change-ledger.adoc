= ADR 088: A Commit Is a Kind of the Change Ledger
:nofooter:

== Status

Accepted

== Date

2026-11-23

== Context

`git.pre-commit-verify-freshness` reads `change-ledger.jsonl` for a `fresh` row, an `exempt` row and a
`baseline_red` row of the same `worktree_sha` (State Catalogue § `git.stage-and-commit`; Workflow DSL § Six-Stage
Execution Contract, stage 4). The ledger's `kind` carried `build`, `change`, `job`, `task_diff` and `baseline_red`, and
none of them recorded the commit itself: a `change` row names a footprint change, not the commit that carried it, so a
gate could not attribute a commit to the tree it was made on.

The format is a stored contract: `change-ledger-record.schema.json` is read by a schema-parity test (R10), and a new
kind is a stored-format change. The spec marked the format-version question ask-at-refine (R13); the operator confirmed
on 2026-11-23 (question 2 of the runbook-lane outline) that the version stays `1` and the kind is added in place.

== Decision

`ChangeLedgerRecord.Kind` gains `commit` (`"commit"`), and the schema's `kind` enum and description gain it too. A
`commit` row carries:

* `worktree_sha` — the working-tree digest of the tree the commit was made on, with its version, exactly as every other
  row. It is taken *before* the commit. The digest takes the `HEAD` commit id and every path the status reports as its
  input (Working-Tree Hash, rule 1), so the commit's own move of `HEAD` and of the status path set changes it: a digest
  taken after the commit is the digest of another tree than the one the commit was made on. Taken before the commit it is
  the state the commit was made on: when no `mutates_source` step changed the tree after the latest successful build it
  equals that build row's digest, and when one did, no build row carries it — the `freshness_reconcile` stamp then holds
  the build's digest beside this commit, and that pair is what licensed the push;
* `commit_sha` — the commit that was made, required for this kind alone (`ChangeLedgerRecord` refuses a `commit` row
  without it);
* `changed_paths` — the paths the commit carried;
* `change_origin` — `plan_change` or `quality_gate_autofix`, as for a `change` row;
* `recorded_at` — the instant of the append.

The codec needs no change: it reads the kind by its wire name and writes the members it already writes. The parity test
`ChangeLedgerSchemaParityTest.recordEnumerations` keeps the enum equal to the schema's, and
`ChangeLedgerCommitRowTest` pins the row's round trip and its refusal.

The format version stays `1`; a `commit` row is written and read in place, with no reader for an older shape.

== Alternatives Considered

1. *Record the commit in the existing `change` row.*
   _Rejected_: a `change` row is a footprint change and may be written for a path set no commit carried; one row cannot
   mean both, and the freshness gate would have to guess which a line is.
2. *A separate ledger file for commits.*
   _Rejected_: the gate reads one file for the tree's history; a second file would have to be read with it and kept in
   step, and the append-only discipline of `change-ledger.jsonl` already covers it.
3. *Bump the format version to 2.*
   _Rejected_: R13 keeps every version at `1` before the release and replaces the shape in place; a bump would add a
   reader and a migration for nothing.

== Consequences

* A commit is attributable to the tree it was made on: the row's digest equals the licensing build row's when the tree is
  the built one, and a `freshness_reconcile` stamp carries the build's digest beside the commit when a later step changed
  it. The freshness verb itself
  reads `kind = "build"` and `kind = "baseline_red"` rows and the `freshness_reconcile` stamp, never a `commit` row
  (State Catalogue § `git.verify-freshness`); the `commit` row is the attribution record, not an input of the gate.
* The schema's `kind` enum and the record's enum move together; a new kind that skips one side fails the parity test.
* `doc/Traceability.adoc` no longer lists the change-ledger commit row as unimplemented.
