= ADR 087: The Commit Attempt Caps Are a Member of the Workflow State
:nofooter:

== Status

Accepted

== Date

2026-11-23

== Context

`git.commit-fix` is bounded by two counters (Timeouts & Budgets § Commit Sub-Process Attempt Caps; State Catalogue §
`git.stage-and-commit`): at most three failed commit attempts per identical staged change set — the staged tree id and
the message — reset when either half changes, and at most three `git.commit-fix` tasks per call frame, reset by a new
call. No code held either counter. A budget that a runtime restart may reset is no budget, so the counters must survive
a drain and a restart (PM-WF-7, PM-ARCH-4), exactly as `retry_counters` does.

The counter is read and written by the commit sub-process, but the workflow state store is a `pm-core` contract: a
value persisted in it is a `pm-core` type, and the commit primitive of `pm-provider-git` must not define one. The
outline put two questions to the operator (R07): where the counter persists, and whether it is a derived fact or a
status member. The operator chose a new status member on 2026-11-23 (question 1 of the runbook lane's outline).

== Decision

The two caps are a new typed member of `WorkflowStatus`, `commit_attempt_caps`, written through `WorkflowStatusCodec`
and declared in `status.schema.json` with a codec parity test. The member is `null` before the first counted event and
an object `{change_set, frame}` otherwise:

* `change_set` is `{staged_tree, message_digest, attempts}`: the staged tree id, the SHA-256 of the message and the
  failed attempts of that change set, at most three. The tree id's grammar is SHA-1 only — `[0-9a-f]{40}` — so a SHA-256
  tree id is refused rather than stored, and `message_digest` is `[0-9a-f]{64}`.
* `frame` is `{frame_id, tasks}`: the identity of the call frame and the `git.commit-fix` tasks taken in it, at most
  three. A change of frame restarts the count at one: the tasks of another frame replace the entry instead of adding to
  it.

The persisted value is data only, `CommitAttemptCaps` in `de.planmarshall.core.store`; the transitions live in the pure
class `CommitAttemptCounter` in the same package, beside the value, so both the engine (which may depend on `pm-core`
alone) and the assembly may count through it. A
counted attempt of another change set, or of another frame, replaces the entry and starts at one, which is the
specification's own reset rule. The value never exceeds the cap.

The counter answers one predicate per cap — `changeSetCapSpent()` and `frameCapSpent()` — and holds no combined
predicate. The caller's rule is therefore explicit rather than enforced by the value: after a `hook_failed` outcome of
`git.stage-and-commit` it reads both predicates and writes their disjunction,
`changeSetCapSpent() || frameCapSpent()`, as the `attempts_exhausted` outcome. The two counters are counted at their own
events — the change-set cap at a failed commit attempt, the frame cap at a `git.commit-fix` task — but a counting event
reads nothing, so the frame cap being spent after the third `git.commit-fix` task does not end the loop before the commit
attempt that follows it runs. The rule is stated, not enforced: the state catalogue's `git.stage-and-commit` row is the
specification, and `CommitAttemptCounterTest.Hazard` pins each arm of the disjunction one at a time, not the disjunction
or the read after `hook_failed`. Neither the counting nor that routing is wired in this checkout: the engine counts no
attempt of
the primitive (ADR `provider-git-primitive/005`, the external hand-off, which names these counters), so the ordering above
is the intended contract of that hand-off, not behaviour the code performs yet.

The format version stays `1` (R13): the member is added in place, with no reader for an older shape. No version question
was put for this member: the ask-at-refine question of the outline of `PLAN-V2-176` was the change ledger's format
version, which the operator answered with `1` and the kind added in place (ADR `088`, answer 2 of that outline), so the
two records agree on what was asked.

== Alternatives Considered

1. *Reuse `retry_counters` with two new retry rules.*
   _Rejected_: the schema describes a `retry_counters` entry as bound to a state whose primitive counts the retry, and
   the change-set key is no state id but the pair of digests. The reset-by-identity semantics would sit sideways in a
   member whose contract says a budget is never reset.
2. *Derive the counts from the change ledger.*
   _Rejected_: a derived fact is recomputed on read; a budget that must be persisted and never lost by a restart is the
   opposite of a derived value, and the ledger holds no failed-attempt row to derive from.
3. *A pure class with no store shape.*
   _Rejected_: nothing would survive a restart, and the specification's cap is a budget, not a computed answer.

== Consequences

* `WorkflowStatusCodecTest` round-trips the member and `WorkflowStatusSchemaParityTest` pins its two counters, both
  digest patterns, the maximum `3` and the frame id rule against the schema; `CommitAttemptCapsTest` pins the value's
  grammar and `CommitAttemptCounterTest` the reset and cap rules, including the PM-WATCH-DSL-28 hazard: a fix that
  changes the staged tree resets the change-set counter, and the frame counter still ends the loop.
* The engine or the assembly that wires the commit sub-process takes the counter from the status store instead of
  holding it in memory; the class lives in `pm-core`, so the engine may reach it without depending on the provider.
