= ADR 084: The Move Carries the Manifest's Files and No Other
:nofooter:

== Status

Accepted

== Date

2026-11-22

== Context

The source directory `pending/<entry_id>/sources/` is defined by its manifest: a source is a set of files with their
size and SHA-256, and the manifest is the record of what the entry holds (Filesystem Layout § The Source Directory). The
store-level move wrote one store per manifest entry and then this was not so: two sources could name one file path, so
the move collected one store path twice and `ScopeTransaction` refused the second target with an
`IllegalArgumentException` while the target was added — a failure the transaction cannot attribute to either source; a
source could name `sources.json`, the manifest's own file, with the same refusal; a file of `sources/` that no manifest
entry named was silently left behind and deleted with the entry's directory; and the stored file was read with
`Files.readAllBytes`, which follows a symbolic link, so a link in the entry's directory could make the move read a file
outside it.

== Decision

Five rules, each enforced where its input is defined:

1. `SourceManifest` refuses a path that two sources name, a path that repeats another in case or in another Unicode
   normalisation form, a path that is the directory of another, and a path that is the manifest's own file name
   (`sources.json`) or lies below it, in any case,
   with an `IllegalArgumentException` naming the path and the source. Each collision rule answers with its own message
   — the path stored twice, the two names in one case, the two names in one Unicode normalisation form, the file and
   its directory — so a refusal names the rule it enforces; a pair whose names differ in case although the fold
   compares them in one normalisation form is the case rule, because the case fold is what unifies it. The stored
   manifest's read (`SourceManifestCodec.read`) refuses through the record's own canonical constructor, so it carries
   the same text. The case is folded and the path normalised to NFC
   before and after that fold — the case mapping can itself produce a non-NFC string — because the paths are the
   operator's file names and a case-insensitive or normalisation-insensitive filesystem
   addresses one file in either form; a file and its directory
   are refused together because one create target cannot be both. The manifest is built where an entry is written, so
   the refusal happens before a directory is staged.
   The operator kept the full width of this fold on 2026-11-23, asked by deliverable 3 of `PLAN-V2-174` after
   `PLAN-V2-171` deferred it (R07): it is `Locale.ROOT` upper case then lower case over the NFC form, so it also
   refuses `ß` against `ss`, `ı` against `i`, a ligature against its letters, and a composed against a decomposed name,
   even where a case-sensitive filesystem keeps the two files apart. The alternatives — narrowing the fold to ASCII and
   a documented Unicode set, and refusing at write while tolerating the collision at read — were not taken, because
   only the full fold never lets one manifest carry two files that a case- or normalisation-insensitive filesystem
   conflates. The cost is accepted: a manifest stored under the earlier case-only rule whose paths collide now reads as
   a `StoreRefusal` from the record's own constructor, with `format_version` still 1 (ADR 085).
2. `PendingEntryCreation.move` refuses to carry an entry whose source directory holds a file or a link that no manifest
   entry names — the manifest itself excepted — with a `StoreRefusal` naming the file, so nothing of the entry is
   dropped silently when its directory is deleted after the move. A link below the source directory is refused as the
   link it is, whether or not the manifest names it.
3. A stored file is read only after its canonical path was checked to lie in the source directory, only when it is a
   regular file, and with `LinkOption.NOFOLLOW_LINKS`, so a symbolic link is refused instead of followed, a path that
   leaves the directory through a link is refused with it, and a FIFO or another special file the manifest names is
   refused instead of being opened — that open would block under the workspace lock. The check and the open are two
   calls and not one atomic act, so a file replaced by a FIFO between them is opened and the move blocks under the
   lock; plain Java opens no file without waiting for a FIFO's peer, so the bound is the platform's and the check only
   narrows the window. The guide states the bound beside the rule, and `PendingEntryCreationTest` proves the refusal
   with a FIFO, the special file whose open blocks, under a deadline that fails if the file is opened.
4. The transcript is refused as a whole, as the source directory's files are: a transcript that is a link or no
   directory, and a link or a file that is no regular file inside it, refuse the move with a `StoreRefusal`, so the
   transcript a `finish` deletes with the directory is exactly the transcript that was carried.
5. The caller's verification is the guard of the paths: `move`, `discard`, `read` and `readSources` resolve through
   `JournalScope.resolve`, which follows a link in a parent directory, while `verify` reaches every store through
   `JournalScope.resolveWithoutLinks` and refuses a link below the path base. A caller that acts on an entry verifies it
   under the lock first; the periodic sweep does, and a direct caller carries what the links point at.

== Alternatives Considered

1. *Let the transaction refuse the duplicate path.*
   _Rejected_: the refusal is an `IllegalArgumentException` from the target collection, indistinguishable from a store
   the transaction may not write, and it names no source a caller can act on.
2. *Skip a file the manifest does not name.*
   _Rejected_: the file is deleted with the entry's directory, so a source would be lost without a trace.
3. *Copy the whole source directory instead of the manifest's files.*
   _Rejected_: then the manifest is no longer the record of what is carried, and the size and digest verification of
   each file would be lost.
4. *Follow a link and verify its content against the manifest.*
   _Rejected_: the digest would match whatever the link points at, so an entry's directory could redirect a read
   outside it.
5. *Narrow the fold to ASCII and a documented Unicode set.*
   _Rejected_ (operator, 2026-11-23): it admits `ß` against `ss` and the other pairs as two files, which a
   case-insensitive volume conflates, so one manifest could describe one file twice.
6. *Refuse a colliding path at write and tolerate it at read.*
   _Rejected_ (operator, 2026-11-23): the reader would accept a manifest the writer refuses, so a stored manifest could
   describe two paths one file addresses; it would also need a second, lenient construction of the record.

== Consequences

* The entry's file set is exactly its manifest: a file another tool writes into `sources/` must be entered in the
  manifest before a move carries it, and the refusal names it when it is not.
* The manifest can no longer describe a directory whose files collide, which the store-level move would otherwise have
  written twice, and it no longer admits two paths a case-insensitive filesystem conflates or a file and its directory.
* A symbolic link in a source directory or a link in the transcript is a refusal, never a read, and so is a FIFO or
  another special file a source names: the operator removes the link or the special file, or abandons the entry.
* `SourceManifestCodecTest`, `PendingEntryCreationTest` and `PendingEntryStoreTest` carry the refusals; the guide
  (§ The Pending Entry) states them.
