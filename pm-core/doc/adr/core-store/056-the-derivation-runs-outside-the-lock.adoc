= ADR 056: The Derivation Runs Outside the Lock and the Write Keeps a Newer Result
:nofooter:

== Status

Accepted

== Date

2026-11-01

== Context

A refresh of a derived fact may call a provider: a network derivation reads the repository settings, the branch
protection and the credential's permissions. The store is written by read-modify-write on one document under
`locks/derived-facts.lock`, and a refresh may itself run inside a plan, epic or workspace transaction whose scope lock
the caller already holds. Two refreshers of the same fact can run at once, from the setup reconcile and from a plan.

== Decision

The derivation runs outside the lock. The refresh reads the document without a lock, decides from that read whether to
derive, calls the derivation, and then opens one short transaction on `LockKey.derivedFacts(base, projectId)` that
re-reads the document under the lock, changes the one entry and writes it through `AtomicStoreFile`.

The write re-reads the entry and, when the stored entry carries the same `input_digest` with a later `derived_at` than
the attempt, keeps the stored entry and returns its reading. Two refreshers of the same fact therefore do not overwrite
a newer result with an older one.

Two refreshes of different digests are last-writer-wins. A digest names an input snapshot, and the store has no rule
that orders two different snapshots: the later writer's value is the one the store holds, and the reading a caller
receives is the entry as it stands after its own attempt. Ordering by `derived_at` alone would be wrong, because a
caller that started from an older snapshot may still write at a later instant.

== Alternatives Considered

* Holding the lock across the derivation: a provider call under the derived-facts lock would make every writer of the
  file wait behind a network round trip, and a caller that already holds a scope lock would wait behind it with a lock
  of a later level held, which is the shape the total order exists to forbid.
* Compare-and-set on the whole file: the write would fail and retry on any concurrent write, even one of another key,
  so two independent refreshers would serialize on retries instead of on the one short write. The entry-level rule
  needs no retry and keeps an unrelated entry untouched.

== Consequences

* The decision is taken on a read outside the lock and may be stale by the time the write runs; the re-read under the
  lock is the authority for the entry that is kept.
* A derivation that a concurrent refresh made unnecessary is still paid for once; it is never written over the newer
  entry.
* The derived-facts lock is held for the re-read and the write only and stays where `LockLevel.DERIVED_FACTS` places
  it, after every scope lock.
* `DerivedFactStoreConcurrencyTest`, `DerivedFactStoreLockTest` and `LockOrderTest` state it.
