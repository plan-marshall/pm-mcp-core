= ADR 034: The Waiver Logs Are Appended Only Through the Plan's Scope Transaction
:nofooter:

== Status

Accepted

== Date

2026-10-18

== Context

The operator waives a gate, raises a remediation budget or revokes such a waiver of a plan (PM-SEC-3), and every
evaluation of a gate that relied on a `met` waiver is recorded. Both are evidence of operator authority: a waiver that
was changed in place, or a consumption that was dropped, would rewrite what the operator decided and what the gate
admitted. The plan's stores are written through its `ScopeTransaction`, which journals a target, repairs a torn tail of
a JSONL store first and records the digest of every store in the plan's sidecar.

== Decision

* The waiver log `plans/<plan_id>/waivers.jsonl` (`WaiverLog` of `WaiverRecord`) and the consumption log
  `plans/<plan_id>/waiver-consumptions.jsonl` (`WaiverConsumptionLog` of `WaiverConsumptionRecord`) are append-only
  logs of the plan scope; only a plan has them.
* An append adds one line as an append target to the caller's transaction of the plan and never commits on its own; a
  transaction of another scope is refused. No method rewrites or removes a line.
* A revocation is a new `revoked` line with the same waiver id. The current state of a waiver is the last readable line
  of its id, taken whole; a torn last line is no version of its waiver.
* That the operator's act is the only writer of the waiver log and `waiver.lookup` the only writer of the consumption
  log is the rule of those callers, not of the store.

== Alternatives Considered

1. *Rewrite the current state of every waiver into one file, a map by waiver id.* _Not taken_: it rewrites the
   operator's record on every act and loses the history that the audit mirror and the `reason_class` recurrence read;
   the append is the evidence.
2. *One file per waiver id.* _Not taken_: the plan's transaction and digest sidecar would carry one target per waiver,
   and a revocation is naturally a line of the same log; the last readable line of the id is already the current state.
3. *Append straight to the file, with an fsync, outside the scope transaction.* _Not taken_: the line would be invisible
   to the plan's transaction journal and its digest sidecar, so it could neither be rolled forward after a stop nor be
   detected as an edit. The JSONL store's next append still repairs a torn last line, but nothing would record that the
   line was ever intended, and the plan's sidecar would not cover it.
4. *Keep the consumptions inside `waivers.jsonl`.* _Not taken_: the waiver log has exactly one writer, the operator's
   act, and a consumption is the evaluation that relied on it, written by `waiver.lookup`; one log would mix the
   authority with its use and give the file two writers.

== Consequences

* Every waiver and consumption line is journaled, recovered and covered by the plan's digest sidecar, so an edit
  outside a transaction is detected as for any store of the plan.
* A reader that wants the state of a waiver reads the log and takes the last readable line; there is no current-state
  file to keep in step.
* The read is the specified one, and it has a cost the specification accepts: a line that is refused when read (of
  another format version, or damaged) is skipped, so a `revoked` line that is refused leaves the earlier `waived` line
  as the current line of the waiver. No writer in this repository emits such a line. A caller that gates on a waiver
  consults `refused()` of the log and treats a log that holds a refused line as not deciding the waiver, as the
  question log's append gate does (link:039-question-append-refused-while-the-log-holds-a-refused-line.adoc[ADR 039]).
* A later writer of either log has to go through the append; the store offers no other write.
