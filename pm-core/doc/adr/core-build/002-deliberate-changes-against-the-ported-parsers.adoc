= ADR 002: The Deliberate Changes against the Ported plan-marshall Parsers
:nofooter:

== Status

Accepted

== Date

2026-11-01

== Context

Each parser of `core.build` is a port of one `plan-marshall` module. The ported tests take their test data and their
expected values from the original and its pytest suite, so a port that simply copied every behaviour would also copy the
behaviours that produced the defects of the implementation watch.

Three defects are recorded there (PM-WATCH-JOB-10, -11, -18; the first and third were closed by this package and their
items deleted from the watch document): a green multi-module build reported `tests_run: 0`; a test
filter matching nothing was not reported as having run nothing; the failure-trailer advice of the build tool was filed as
located findings, and an unrecognised `[ERROR]` line was given a real category. The ported originals fix part of this —
the Maven parser drops the trailer with a `fullmatch` table and skips a passing `Tests run:` line — and leave the rest.

== Decision

The port reproduces the originals' parsing exactly, and records every behaviour it changes as a deliberate change with a
fixture of its own (`deliberate:` header) that asserts the corrected behaviour, never a value of the original. There are
five:

[cols="2,3",options="header"]
|===
|Change |Asserted by

|An `[ERROR]` line no pattern of the compiled table recognises is `Category.UNRECOGNIZED`, never a real category. A
`[WARNING]` line without a match keeps the original's `Category.OTHER`, so the change is scoped to the level the
specification names.
|`ported/build/maven/deliberate-unrecognized-error.txt`

|An unmeasured test population carries no number: `TestCounts.Unmeasured` has no count accessor. The original keeps the
summed counts of an unmeasured population. The port therefore loses the original's `failed > 0` signal for a quiet
(`-q`) log, which an `[INFO]`-level failing count line also leaves unfiled; recovering that signal — a failing
`Tests run:` line filed regardless of its level, or a status derived at the gate — belongs to the wiring plan
(PLAN-V2-36), not to this model.
|`ported/build/maven/deliberate-unmeasured-on-success.txt`

|`no_tests_ran` needs the tool's own positive marker (`No tests to run.` for Maven, `No tests found for given includes`
for Gradle) over a successful build with no count line; a measured count of zero never produces it. The original has no
such verdict at all.
|`ported/build/maven/deliberate-zero-count-is-no-no-tests-ran.txt`,
`ported/build/maven/deliberate-no-tests-ran-positive-marker.txt`,
`ported/build/gradle/deliberate-gradle-no-tests-marker.txt`

|The Gradle counts follow the Maven rule: every `N tests completed` block contributes. The original keeps the last
match.
|`ported/build/gradle/deliberate-gradle-two-test-tasks.txt`

|An OpenRewrite log line that carries a finding identifier but no longer matches the pinned template — a reworded verb,
a blank capture, a colon-less identifier or a location outside the {@code int} range — is
`RewriteVerdict.PARSE_ERROR`. The original silently ignores such a line, so a format drift would read as zero findings.
|`ported/build/openrewrite/deliberate-rewrite-parse-error.txt`,
`deliberate-rewrite-colonless-identifier.txt`
|===

Two behaviours that do not exist in this package's model are *inputs*, not changes of the parse: the java-cui domain
state is an argument of the OpenRewrite parse (the original resolves a marshal.json verb and dispatches a subprocess), and
the parser has no CLI exit code (the original's `cmd_parse` returns one).

Everything else is held as in the original, including the behaviours that look surprising:

* The Maven failure trailer is dropped whole against a compiled table matched with a full match, so a reworded trailer
line is filed again (`ported/build/maven/maven-trailer-dropped.txt`,
`maven-trailer-reworded.txt`). This is the original's behaviour, not a change.
* A passing `Tests run:` line is not a diagnostic, and a line starting with `->` is a continuation.
* The stack-trace collector attaches the last contiguous trace block to the last filed diagnostic
  (`StackTraceCollector`).
* A Gradle line whose text matches no category is not filed at all, and Gradle's severity follows its category set.

== Alternatives Considered

1. *Port every behaviour unchanged.* Not taken: it would leave the aggregation, zero-filter and trailer guards open in the
   port, and the specification names the corrected behaviour as the requirement.
2. *Clean up each surprise and record nothing.* Not taken: a change the ported tests do not state reads as an accident
   of the port. Each change has a fixture of its own, so a later reader can tell the port's intent from the original's
   behaviour.
3. *Fix the stack-trace attachment.* Not taken in this plan: it is not a defect the specification names, and changing it
   would make the port's expected values disagree with the original's for no recorded benefit. It is named here so a later
   change can take it deliberately.

== Consequences

A consumer that compares a `plan-marshall` result with this one sees the five differences listed above and the two input
differences, and no others. A change of any ported behaviour must now either keep its fixture green or change the fixture
and this record with it.

The `unrecognized` category and the `no_tests_ran` rule are visible in the specification's paragraph and in the developer
guide, so a sibling port (the npm and Python parsers) can adopt them rather than rediscovering them.
